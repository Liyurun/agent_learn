      <h3>先算一笔账：Agent 为什么这么贵、这么慢</h3>
      <p class="cjk">优化之前，先理解成本与延迟从哪里来。和单次问答不同，<mark class="key2">一个 Agent 任务是一个循环，往往要调用模型几次到几十次，每次都把不断膨胀的上下文重新喂进去</mark>。于是成本和延迟被两个因素放大：<strong>① 步数多</strong>——每一步都是一次完整的模型调用；<strong>② 上下文长</strong>——历史动作、观测、工具结果层层累积，输入 token 随步数线性甚至超线性增长。这就是为什么"单次调用很便宜"的直觉在 Agent 上会严重失真——真正该盯的是<strong>每任务成本</strong>而非每次调用成本。</p>
      <p class="cjk">延迟同理。用户感知的不是单次 TTFT，而是"从我下达指令到我拿到最终结果"的<strong>端到端时延</strong>，它等于所有步骤延迟之和。因此优化 Agent 的延迟，减少步数和缩短每步耗时同样重要。</p>
      <p class="cjk">这里有一个必须建立的定量直觉：<mark class="key2">在 Agent 里，输入 token 往往远多于输出 token</mark>。因为每一步都要把"系统提示 + 工具定义 + 全部历史动作与观测"重新塞进去，而模型这一步只吐出很短的一个动作。这解释了两件事：其一，<strong>提示词缓存</strong>为什么对 Agent 收益巨大——它复用的正是那个每步都重复、又长又稳定的前缀；其二，<strong>上下文瘦身</strong>为什么是降本主力——砍掉冗余历史，等于每一步都省钱。反过来也提醒你：一味追求"输出更短"对 Agent 成本影响有限，真正的杠杆在输入侧。理解成本结构，你才不会把力气花错地方。</p>

      <h3>成本 / 延迟优化四杠杆</h3>
      <p class="cjk">别一上来就换模型。按<strong>路由分流、缓存复用、并行流式、上下文瘦身</strong>四个方向对症下药，往往能在不牺牲效果的前提下大幅降本提速。每个杠杆该盯什么指标，见下。</p>
      <div class="interactive" id="costLatencyPanel"></div>

      <p class="cjk"><strong>杠杆一·模型路由（routing）。</strong>核心思想是<mark class="key">"好钢用在刀刃上"</mark>：不是所有步骤都需要最强最贵的模型。简单的意图分类、格式化、抽取用小模型/快模型；只有复杂规划、关键推理才升级到旗舰模型。实现上可以做<strong>难度分级路由</strong>（先用小模型判断任务难度，再决定用哪档模型）或<strong>级联（cascade）</strong>（先让便宜模型试，置信度不够或校验不过再升级到贵模型）。路由的收益往往最大，因为它直接砍掉了"用大炮打蚊子"的浪费。</p>

      <p class="cjk"><strong>杠杆二·缓存（caching）。</strong>分两层：<strong>① 提示词缓存（prompt caching）</strong>——把稳定不变的前缀（系统提示、工具定义、长文档）缓存住，后续请求复用，省掉重复的输入处理成本与时延。这对 Agent 尤其有效，因为它每一步都带着几乎相同的长系统提示。用好它的关键是<strong>把稳定内容放前面、把变化内容放后面</strong>，让公共前缀最大化。<strong>② 语义/结果缓存</strong>——对高度重复的查询直接复用历史答案。要小心缓存失效（数据更新了缓存还旧）和"看似相同实则不同"的误命中。</p>

      <p class="cjk"><strong>杠杆三·并行与流式（parallel &amp; streaming）。</strong>并行是指<mark class="key2">相互独立的子任务/工具调用不要串行等待，而是并发发起</mark>——比如同时查三个数据源、同时读五个文件。这不省钱但显著降延迟（把"求和"变成"取最大值"）。流式（streaming）则是让模型边生成边返回，大幅改善<strong>首字节时间 TTFT</strong>与体感——用户看到内容在动，比干等一个完整回复的焦虑小得多。注意：并行只对<em>无依赖</em>的步骤有效，有先后依赖的步骤强行并行会出错。</p>

      <p class="cjk"><strong>杠杆四·上下文瘦身（context pruning）。</strong>这是 Agent 特有且回报极高的杠杆，因为上下文长度直接决定每步成本。手段包括：<strong>压缩历史</strong>（把早期冗长的观测总结成短摘要，见第 4 章）、<strong>裁剪无关</strong>（只保留与当前子任务相关的信息）、<strong>外置记忆</strong>（把长内容存到外部，用时再检索片段而非全量塞入）、<strong>结构化观测</strong>（工具只返回必要字段，别把整个 JSON 灌进去）。<mark class="key">上下文越精炼，不仅越便宜越快，模型也越不容易被无关信息干扰而走神</mark>——降本和提质在这里是一致的。</p>

      <div class="callout tip">
        <span class="label">进阶杠杆：投机解码与预算控制</span>
        <span class="cjk"><strong>投机解码（speculative decoding）</strong>是一种推理加速技术：用一个小的"草稿模型"快速猜测接下来的若干 token，再让大模型一次性并行验证，猜对的部分直接采纳。它在<em>不改变输出分布</em>的前提下降低生成延迟，属于推理层的免费午餐（多用于自建推理服务）。<strong>预算控制（budget control）</strong>则是给每个任务设硬上限——最大步数、最大 token、最大花费、最大时长，任一触顶就熔断兜底。它是防止"一个卡住的 Agent 烧掉整月预算"的安全阀，呼应第 1 章的 MAX_STEPS。</span>
      </div>

      <h3>把路由写成代码：级联的骨架</h3>
      <p class="cjk">光说"路由"太空，面试官会追问"具体怎么实现"。下面这段级联路由骨架，把"先便宜后昂贵、置信不够再升级"的思想落成代码：</p>
      <div class="code-label">Python · 级联路由（cascade routing）</div>
      <pre><code><span class="kw">def</span> <span class="fn">answer</span>(task):
    draft = <span class="fn">cheap_model</span>(task)                 <span class="cm"># 先用便宜/快的小模型试</span>
    <span class="kw">if</span> <span class="fn">confident</span>(draft) <span class="kw">and</span> <span class="fn">validate</span>(draft):  <span class="cm"># 置信度够且通过校验</span>
        <span class="kw">return</span> draft                          <span class="cm"># 大多数简单任务到此为止，省钱</span>
    <span class="kw">return</span> <span class="fn">strong_model</span>(task)                <span class="cm"># 只有难 / 不确定的才升级到旗舰模型</span></code></pre>
      <p class="cjk">这段代码的精髓在两处：<code>confident</code> 是<strong>路由的闸门</strong>（可用模型自评、启发式规则或轻量分类器实现），<code>validate</code> 是<strong>质量的兜底</strong>（用可自动判定的检查拦住小模型的低质输出）。关键的工程直觉是：<mark class="key">只要小模型能吃下足够比例的简单流量，即使少数任务要跑两次模型，整体成本仍显著下降</mark>。反例是——若你的任务几乎都很难，级联反而多花一遍便宜模型的钱，此时不如直接上强模型。所以路由不是银弹，收益取决于你流量的难度分布。</p>

      <div class="callout warn">
        <span class="label">成本延迟优化的常见误区</span>
        <span class="cjk">① <strong>过早优化</strong>——效果都没达标就死磕成本，本末倒置。② <strong>只优化单次调用</strong>——忽视 Agent 是多步循环，真正的大头在步数与上下文。③ <strong>盲目上小模型</strong>——把关键推理也降级，省了钱却掉了成功率，反而因反复重试更贵。④ <strong>为并行而并行</strong>——把有依赖的步骤强行并发，制造数据竞争与错误。⑤ <strong>缓存不设失效策略</strong>——返回过期结果，埋下正确性隐患。</span>
      </div>

      <h3>安全对齐：能力越强，边界越要收紧</h3>
      <p class="cjk">Agent 能调工具、执行代码、访问外部内容，攻击面比纯聊天大得多。核心威胁是<strong>间接提示注入（indirect prompt injection）</strong>——恶意指令藏在被 Agent 读取的网页 / 文档 / 邮件里，劫持它去泄密或执行危险动作。它之所以危险，是因为 Agent 天生难以区分"这段文字是我要处理的<em>数据</em>"还是"这段文字是给我的<em>指令</em>"。防御要<strong>分层纵深</strong>（呼应第 12 章）：输入侧用分类器拦越狱、指令层做权限隔离（区分可信的系统指令与不可信的外部内容）、动作层最小权限 + 沙箱、输出侧做校验。此外还要警惕<strong>对齐失败（misalignment）</strong>——模型追求的目标与人类意图偏离，比如为了"完成任务"而抄近道、隐瞒错误或钻规则空子。</p>

      <div class="table-wrap">
        <table>
          <thead><tr><th>防御层</th><th>威胁</th><th>手段</th></tr></thead>
          <tbody>
            <tr><td>输入侧</td><td>越狱、提示注入</td><td>输入分类器、内容过滤、可信/不可信来源标记</td></tr>
            <tr><td>指令层</td><td>外部内容冒充指令</td><td>指令与数据隔离、外部内容降权、不让数据改变控制流</td></tr>
            <tr><td>动作层</td><td>危险/越权操作</td><td>最小权限、沙箱隔离、危险动作人工确认、白名单</td></tr>
            <tr><td>输出侧</td><td>泄密、有害内容</td><td>输出校验、敏感信息脱敏、出站过滤</td></tr>
          </tbody>
        </table>
      </div>

      <p class="cjk">这里要特别拎出<strong>动作层</strong>细讲，因为它是"提示注入被绕过之后的最后一道硬防线"，也是面试区分深浅的地方。提示层的防御（在系统提示里写"不要泄密"）本质是"劝说"，攻击者总能找到新话术绕过；而动作层的防御是"物理隔离"，即便模型被骗了，它<em>能造成的伤害</em>也被死死框住。具体落地包括几条：<strong>最小权限</strong>——只授予完成当下任务所必需的工具与数据范围，读写分离、敏感操作单独授权；<strong>沙箱执行</strong>——代码执行、文件操作、网络访问都放进隔离环境，限制其可触达的资源；<strong>动作白名单与确认闸门</strong>——把动作分级，低风险自动放行、高风险（删除、支付、外发）强制人工确认；<strong>幂等与可回滚</strong>——尽量让动作可撤销，为误操作留后路。一句话记住：<mark class="key">别指望模型永远不被骗，要设计成"即使它被骗了也捅不出大娄子"。</mark></p>

      <h3>红队（red teaming）：主动找漏洞而非等着被打</h3>
      <p class="cjk"><strong>红队</strong>是在上线前<mark class="key">主动扮演攻击者，用各种恶意/边缘输入去攻击自己的 Agent，把漏洞在真实攻击发生前暴露出来</mark>。它和常规评估的区别在于：评估看"正常任务做得好不好"，红队看"被恶意利用时会不会出大事"。典型红队场景包括：诱导它执行越权动作、通过外部内容注入劫持它、诱导它泄露系统提示或敏感数据、诱导它生成有害内容、构造让它无限循环烧钱的输入。成熟团队会把红队做成<strong>持续过程</strong>（每次重大改动后重跑攻击集），而不是上线前的一次性活动，并把发现的攻击样例沉淀进回归评估集，形成"攻击—修补—回归"的闭环。</p>

      <div class="callout warn">
        <span class="label">安全对齐的常见误区</span>
        <span class="cjk">① <strong>只在提示词里写"不要做坏事"</strong>——提示层防线极易被绕过，必须有动作层的硬隔离。② <strong>给 Agent 过大权限图省事</strong>——最小权限不是可选项，是底线。③ <strong>信任外部内容</strong>——把网页/文档里的文字当可信指令，正中间接注入下怀。④ <strong>把红队当一次性任务</strong>——攻击面随功能演进，安全要持续做。⑤ <strong>只防外部攻击、不防对齐失败</strong>——模型"好心办坏事"式的走捷径同样危险。</span>
      </div>

      <h3>可观测性：看不见就治不了</h3>
      <p class="cjk">成本、延迟、安全这三件事有一个共同前提——<strong>你得先能看见发生了什么</strong>。Agent 是多步、非确定、常常跨工具的系统，一旦线上出问题，"它到底在第几步、因为什么、花了多少、走了哪条路"如果查不出来，一切优化和防护都是空中楼阁。因此生产级 Agent 必须内建<strong>可观测性（observability）</strong>，至少覆盖三个层次：</p>
      <ul class="hub-list">
        <li><strong>轨迹追踪（tracing）</strong>：完整记录每一步的输入、模型输出、工具调用与返回、耗时与 token，串成一条可回放的调用链。出问题时能精确定位到"是第几步、哪个工具、什么输入"导致的。</li>
        <li><strong>指标监控（metrics）</strong>：实时盯住每任务成本、P95 延迟、成功率、工具错误率、重试率、人工接管率等，设阈值告警，让退化在用户投诉前就被发现。</li>
        <li><strong>结构化日志与审计（logging &amp; audit）</strong>：为敏感/危险动作留下可审计的记录，既服务排障，也服务安全合规——出了事能追溯"谁在什么时候让它做了什么"。</li>
      </ul>
      <p class="cjk">一个实用心法是<mark class="key2">"每一次线上失败，都应该在你的可观测系统里留下足够定位它的证据"</mark>。如果一次失败查完日志仍不知道原因，那说明你的观测埋点不够，这本身就是要补的技术债。可观测性不是锦上添花，而是把前面所有优化与防护"闭环"起来的地基——它连接了第 18 章的评估（离线证据）与生产运营（在线证据）。</p>

      <h3>优雅降级：允许失败，但要体面地失败</h3>
      <p class="cjk">生产系统一个成熟的心态是：<strong>不追求永不失败，而追求失败时不失控</strong>。Agent 天生非确定、会犯错，与其幻想 100% 成功，不如设计好"出错时怎么办"。几条关键的降级策略：<strong>超时与熔断</strong>——单步或整任务超过阈值就中止，不让它无限拖；<strong>重试与退避</strong>——瞬时错误（网络抖动、限流）自动重试，但要有次数上限和指数退避，避免雪崩；<strong>回退到人</strong>——多次失败或触及不确定边界时，优雅地把任务转交人工，并附上已有的上下文，而不是硬憋一个错误答案糊弄用户；<strong>兜底话术</strong>——实在完不成时，诚实地说"我暂时无法完成这一步"，比编造一个假结果好得多。<mark class="key">能优雅降级的 Agent，用户信任度反而更高</mark>——因为它可预期、不会用一本正经的错误答案坑人。面试里主动谈"失败处理"，往往比只谈"如何成功"更能体现你有真实上线经验。</p>

      <h3>生产可靠性原则自测（对标 12-Factor Agents）</h3>
      <p class="cjk">HumanLayer 的 <strong>12-Factor Agents</strong> 把大量生产落地经验提炼成一组工程原则，核心理念是<mark class="key2">"别把关键控制权交给框架黑盒，自己掌握上下文、提示词与控制流"</mark><a class="cite" href="https://github.com/humanlayer/12-factor-agents" target="_blank" rel="noopener">[来源]</a>。它的名字致敬了经典的"12-Factor App"，精神一脉相承：<strong>可控、可测、可移植、可运维</strong>。下面精选 9 条做成 checklist——勾选你已在项目里做到的，进度存在本机，全绿意味着你的 Agent 已具备生产级骨架。</p>
      <div class="interactive" id="productionPrinciples"></div>

      <p class="cjk">这些原则背后有几条贯穿始终的主线，值得在面试里点透：</p>
      <ul class="hub-list">
        <li><strong>自己拥有上下文与提示词</strong>：把"喂给模型的到底是什么"牢牢攥在手里，而不是让框架偷偷帮你拼——因为上下文质量直接决定输出质量。</li>
        <li><strong>把 Agent 做成无状态、可组合的小单元</strong>：状态外置、职责单一，便于测试、复用和排障，而不是一个无所不包的巨型黑盒。</li>
        <li><strong>控制流握在自己手里</strong>：错误处理、重试、终止条件、人工介入点，都应是你显式设计的，而不是听天由命。</li>
        <li><strong>把人放进环里（human-in-the-loop）</strong>：关键动作留出人工确认的接口，让 Agent 能优雅地"请求帮助"而非硬闯。</li>
        <li><strong>用小而专的 Agent，而非大而全</strong>：范围收窄的 Agent 更可控、更可靠，也更容易评估——这与第 1 章"先判断需要几级自主"一脉相承。</li>
      </ul>

      <h3>面试追问链</h3>
      <p class="cjk">"上线经验"类题目的追问链，会从优化一路逼到安全，再逼到工程原则：</p>
      <ul class="hub-list">
        <li><strong>Q1：</strong>你的 Agent 太贵/太慢，你怎么优化？→ 先分析瓶颈（步数还是上下文），再上四杠杆：路由、缓存、并行流式、上下文瘦身。</li>
        <li><strong>Q2：</strong>你用什么指标衡量优化效果？→ TTFT、P95 延迟、每任务成本、吞吐；强调"先测量再优化"。</li>
        <li><strong>Q3：</strong>换小模型会不会掉效果？→ 引出难度分级路由与级联，关键推理不降级，并用评估守住准确率。</li>
        <li><strong>Q4：</strong>Agent 的最大安全风险是什么？→ 间接提示注入；讲分层纵深防御与指令/数据隔离。</li>
        <li><strong>Q5：</strong>你怎么在上线前发现这些风险？→ 红队，持续做，把攻击样例沉淀进回归集。</li>
        <li><strong>Q6：</strong>有没有成体系的生产原则？→ 12-Factor Agents：自控上下文/提示词/控制流、无状态小单元、人在环路、小而专。</li>
      </ul>

        <span class="cjk">把 Agent 扛到生产，要同时算好两笔账。<strong>成本与延迟</strong>：盯住"每任务成本"和"端到端时延"这两个真正的靶子，用<strong>路由、缓存、并行流式、上下文瘦身</strong>四杠杆对症下药，辅以投机解码与预算控制，并坚持"先测量再优化"。<strong>安全与对齐</strong>：以间接提示注入为头号假想敌，做<strong>输入-指令-动作-输出</strong>的分层纵深防御与最小权限，用<strong>红队</strong>持续主动找漏洞，并警惕模型自身的对齐失败。最后用 <strong>12-Factor Agents</strong> 的工程原则收口：<mark class="key">自己掌握上下文、提示词与控制流，做小而专、可测可控的 Agent</mark>——这正是全书从"什么是 Agent"到"如何把 Agent 做成生产系统"的最终落点。</span>
