      <h2 class="chap-title"><span class="kicker">16</span>模型后训练：从 SFT 到 RLHF / DPO / GRPO</h2>
      <p class="cjk">大多数 Agent 工程师不需要亲手训练模型，但<mark class="key">"什么时候该微调、该用哪种后训练方法"</mark>是高频进阶面试题，也是你判断"要不要投入训练资源"的关键。这一章把后训练体系讲清楚，重点不是记住名字，而是<strong>建立选择的判断力</strong>：预训练和后训练各自解决什么问题、一个基座模型如何被"驯化"成能对话、能对齐、能推理、能当 Agent 用的模型。理解这条链路，你才能在面试里从容回答"你们为什么用 DPO 不用 PPO""奖励模型会不会被骗"这类会拉开层次的追问。</p>

      <h3>预训练 vs 后训练：两种截然不同的目标</h3>
      <p class="cjk">要理解后训练，先要看清它和预训练的分工。<strong>预训练（pre-training）</strong>做的是"在海量无标注文本上做下一个 token 预测"，目标是让模型习得语言规律、世界知识与推理的"原材料"。它消耗的算力占整个训练成本的绝大部分，产出的是一个知识渊博但"不听话"的<strong>基座模型（base model）</strong>——你问它问题，它可能续写出更多问题，因为它只学过"接着往下写"，没学过"回答你"。</p>
      <p class="cjk"><strong>后训练（post-training）</strong>则是在基座模型之上，用相对少得多的数据和算力，把它的行为塑造成人类想要的样子：<mark class="key">听懂指令、按格式作答、拒绝有害请求、符合人类偏好、会调用工具。</mark>一个精辟的类比是：预训练像是让一个人读遍了图书馆，后训练则是教他"在什么场合说什么话、怎么把知识组织成有用的回答"。知识主要在预训练阶段注入，后训练极难灌进大量新知识——这也是后面"微调 vs RAG"判断的根基：想补知识，别指望微调。</p>
      <p class="cjk">这条分工线还解释了一个反直觉的现象：<strong>为什么后训练用很少的数据就能大幅改变模型行为，却几乎不能教会它新事实？</strong>因为后训练本质上是在"激活并对齐"预训练已经学到的能力，而不是从零灌输。模型在预训练里其实已经"见过"如何礼貌回答、如何写代码、如何拒绝危险请求，只是这些能力被淹没在"续写一切文本"的通用目标里；后训练做的是把探照灯打到正确的行为上，让模型默认走这条路。理解这一点，你就能解释很多现象：为什么少量高质量数据比海量数据更重要、为什么微调容易"学偏风格却学不进知识"、为什么想让模型掌握最新事实要靠检索而非训练。这条主线会贯穿本章后面对每种方法的判断。</p>

      <h3>先问：真的需要微调吗？</h3>
      <p class="cjk">微调不是默认动作，而是<strong>排除法之后</strong>的选择——它成本高、会引入维护负担，还可能损伤模型的通用能力。业界共识的优先级是：<mark class="key2">提示工程 → RAG / 上下文工程 → 微调</mark>，能用前者解决就别急着训练。下面这条决策链帮你按顺序自问。</p>

      <h3>后训练流水线：预训练 → SFT → 偏好对齐</h3>
      <p class="cjk">现代对话/Agent 模型的诞生分三段：<strong>预训练</strong>（在海量文本上学语言与世界知识）→ <strong>SFT 监督微调</strong>（学会遵循指令、按格式作答）→ <strong>偏好对齐</strong>（让输出更符合人类偏好，如有用、无害、诚实）。ChatGPT 的经典路线正是 SFT + RLHF<a class="cite" href="https://arxiv.org/abs/2203.02155" target="_blank" rel="noopener">[来源]</a>。下面把偏好对齐的三条主流路线放在一起对比。</p>
      <div class="interactive" id="postTrainingPanel"></div>

      <div class="callout tip">
        <span class="label">一句话记住区别</span>
        <span class="cjk"><strong>SFT</strong> 教"照着做"；<strong>RLHF</strong> 教"什么更好"但要额外训奖励模型 + 跑 PPO；<strong>DPO</strong> 把 RLHF 两步合成一步、免奖励模型，是开源社区偏好对齐的默认选择<a class="cite" href="https://arxiv.org/abs/2305.18290" target="_blank" rel="noopener">[来源]</a>；<strong>GRPO</strong> 免 Critic、配合可验证奖励，DeepSeek-R1 用它训出长链推理能力<a class="cite" href="https://arxiv.org/abs/2501.12948" target="_blank" rel="noopener">[来源]</a>。</span>
      </div>

      <h3>SFT 数据构造：格式、质量与多样性</h3>
      <p class="cjk"><strong>SFT（Supervised Fine-Tuning，监督微调）</strong>的本质极其朴素：把训练数据组织成"（指令，理想回答）"的成对样本，让模型在这些样本上继续做下一个 token 预测，只不过这次的"续写目标"是人类精心写好的标准答案。它教给模型的不是新知识，而是<mark class="key">"面对这类输入，应该以这种格式、这种口吻、这种结构去回答"的行为模板</mark>。一条典型的 SFT 样本会被套进对话模板（chat template），带上 <code>system</code> / <code>user</code> / <code>assistant</code> 角色标记，并且通常只对 assistant 段计算损失（loss masking），因为我们只想让模型学"怎么答"，不想让它学"怎么问"。</p>
      <p class="cjk">SFT 数据的三条黄金准则，面试里能说清楚就是加分项：</p>
      <ul class="hub-list">
        <li><strong>质量优先于数量</strong>：少量高质量、人工精修的样本，往往胜过海量嘈杂样本。业界一个被反复验证的经验是"对齐主要是激发预训练已有的能力，而非灌输新能力"，因此几千到几万条打磨精良的指令数据，就可能显著改变模型行为。</li>
        <li><strong>多样性覆盖</strong>：指令的<em>任务类型</em>（问答、改写、抽取、编码、拒答）、<em>领域</em>、<em>难度</em>、<em>长度</em>都要有分布，否则模型会在没覆盖到的场景上退化。多样性不足是 SFT 最隐蔽的坑。</li>
        <li><strong>格式一致</strong>：模板、字段、拒答话术要统一，模型对格式极其敏感；训练与推理时的模板必须完全对齐，否则性能会莫名其妙地垮。</li>
      </ul>

      <p class="cjk"><strong>数据从哪来、怎么清洗？</strong>后训练效果的天花板≈数据质量的天花板。三个常见做法：<strong>人工标注</strong>（最贵最准，适合定义"什么是好回答"的黄金标准）、<strong>合成数据</strong>（用强模型批量生成指令-回答对，再用规则或模型过滤，成本低但需警惕同质化与错误累积）、<strong>蒸馏</strong>（用大模型的输出训练小模型，把能力"蒸"进小模型——注意这受被蒸馏模型的许可协议约束）。实践中往往是三者混合：人工写"种子"与评审标准，合成扩量，蒸馏补强特定能力。面试里能说清"我会怎么构造/清洗后训练数据"，比只会背方法名更打动人。</p>
      <p class="cjk">一套可复用的数据构造流水线通常是这样的：<strong>① 收集种子指令</strong>（从真实用户日志、业务场景、标注专家手写中来，保证真实分布）→ <strong>② 扩增</strong>（用强模型对种子做改写、加难度、换领域，快速放量）→ <strong>③ 生成回答</strong>（可让强模型多次采样，或人工书写标杆答案）→ <strong>④ 过滤清洗</strong>（去重、去毒、去格式错误、用规则或"LLM 裁判"打分筛低质）→ <strong>⑤ 配比与去污</strong>（按任务类型调整配比，并剔除与评测集重叠的样本防数据污染）。这条流水线里，<mark class="key">过滤和配比往往比生成更决定最终效果</mark>——很多团队栽在"生成了一百万条却没认真清洗"，结果模型学了一堆同质化套话。</p>
      <div class="callout warn">
        <span class="label">数据侧常见误区</span>
        <span class="cjk">① <strong>只堆量不控质</strong>——十万条脏数据不如一万条精修。② <strong>合成数据不去重不过滤</strong>——强模型的系统性偏差会被放大，还可能引入"幻觉答案"。③ <strong>训练模板与推理模板不一致</strong>——最常见的"训练时好、上线就崩"元凶。④ <strong>把该用 RAG 的知识需求硬塞进 SFT</strong>——知识会过时、会遗忘，且极难覆盖全。⑤ <strong>数据集与评测集重叠</strong>——刷高了分却是自欺欺人，上线立刻现原形。</span>
      </div>

      <h3>RLHF 三阶段：SFT → 奖励模型 → PPO</h3>
      <p class="cjk"><strong>RLHF（Reinforcement Learning from Human Feedback，人类反馈强化学习）</strong>是让 ChatGPT 一炮而红的对齐范式，它回答的问题是 SFT 回答不了的：<mark class="key2">当"好回答"难以写成标准答案、只能靠"A 比 B 好"来判断时，怎么训练？</mark>它由三个阶段串成：</p>
      <ol style="padding-left:1.2em">
        <li class="cjk"><strong>阶段一：SFT</strong>。先用监督微调得到一个会遵循指令的初始策略模型，作为后续 RL 的起点。</li>
        <li class="cjk"><strong>阶段二：训练奖励模型（Reward Model, RM）</strong>。让人类对同一提示下模型产生的多个回答做<em>排序</em>（哪个更好），用这些成对偏好数据训练一个打分模型，它能给任意"提示+回答"输出一个标量分数，近似"人类有多喜欢这个回答"。</li>
        <li class="cjk"><strong>阶段三：用 RL 优化策略</strong>。以奖励模型的打分作为奖励信号，用 <strong>PPO</strong> 等强化学习算法更新策略模型，让它倾向于生成高分回答，同时用 KL 约束防止它跑得离原模型太远。</li>
      </ol>

      <p class="cjk">这里最关键的洞察是：<strong>为什么不直接用人类实时打分做 RL？</strong>因为人类反馈太慢太贵，无法支撑 RL 动辄百万次的采样评分。奖励模型的作用，就是把"昂贵、稀疏的人类判断"<mark class="key">蒸馏成一个可以被高频、廉价查询的自动评分器</mark>，让 RL 得以规模化运转。这就是 RLHF 三阶段结构的根本动机。</p>

      <h3>奖励模型：怎么训，以及为什么会被"骗"</h3>
      <p class="cjk">奖励模型通常用同一基座加一个标量输出头，训练目标是<strong>成对偏好损失</strong>：对于人类标注"回答 A 优于 B"的样本，让 RM 给 A 的分数尽量高于 B（Bradley-Terry 式的成对比较）。它学的不是绝对分数，而是<em>相对排序</em>。这解释了它的两大软肋：</p>
      <ul class="hub-list">
        <li><strong>奖励攻击 / 奖励作弊（reward hacking）</strong>：策略模型会找到"骗高分但人类未必真喜欢"的捷径，比如回答变得冗长、堆砌讨好性套话、过度自信。因为 RM 只是人类偏好的<em>不完美代理</em>，一旦被过度优化，代理与真实目标就会脱钩（Goodhart 定律：当指标成为目标，它就不再是好指标）。</li>
        <li><strong>分布漂移</strong>：随着策略模型进化，它产生的回答越来越偏离 RM 训练时见过的分布，RM 的打分越来越不可靠。工业界常用做法是<strong>迭代式</strong>——训一阵、重新采集偏好、更新 RM，循环推进。</li>
      </ul>
      <div class="callout warn">
        <span class="label">面试高频陷阱</span>
        <span class="cjk">被问"RLHF 有什么问题"时，只答"要标注很贵"是浅层答案。高分答法要点出：<strong>奖励作弊</strong>（代理目标被钻空子）、<strong>对长度/风格的偏置</strong>、<strong>RM 与策略的分布漂移</strong>，以及需要 <strong>KL 约束</strong>兜住这一切。能说出"这是 Goodhart 定律在起作用"会显得很有体系感。</span>
      </div>

      <h3>PPO：为什么复杂，KL 约束在防什么</h3>
      <p class="cjk"><strong>PPO（Proximal Policy Optimization，近端策略优化）</strong>是 RLHF 阶段三最经典的算法。它的核心思想是"小步快跑、别更新太猛"：通过一个裁剪（clipping）的目标函数，限制新策略相对旧策略的变化幅度，避免一次更新把模型带崩。在语言模型场景里，PPO 的完整装置相当重，通常要同时在显存里放<mark class="key">四个模型</mark>：正在训练的<strong>策略模型（Actor）</strong>、估计状态价值的<strong>Critic（价值网络）</strong>、打分的<strong>奖励模型</strong>、以及作为 KL 参考的<strong>冻结参考模型（reference）</strong>。</p>
      <p class="cjk">其中 <strong>KL 惩罚</strong>是理解 RLHF 稳定性的钥匙：在奖励里加一项"策略与参考模型输出分布的 KL 散度"惩罚，<mark class="key2">它的作用是把模型"拴"在原始 SFT 模型附近，既防止为了骗奖励而胡说八道，也防止灾难性遗忘掉预训练学来的通用能力。</mark>没有这个约束，PPO 极易退化成"输出乱码但奖励很高"。PPO 效果强，但工程复杂、显存吃紧、超参敏感、训练不稳定——这正是 DPO、GRPO 想要简化的痛点。</p>
      <p class="cjk">为什么要区分 Actor 和 Critic？这是从经典强化学习继承来的<strong>Actor-Critic</strong>思想：Actor 负责"做动作"（生成 token），Critic 负责"评估当前处境有多好"（估计价值），用 Critic 的价值估计来降低策略梯度的方差，让训练更稳。代价是 Critic 本身也是一个和策略模型同量级的网络，既吃显存又难训——在长序列的语言任务里，"每个 token 的价值到底是多少"本就很难准确估计。这就是为什么 GRPO 敢于把 Critic 整个砍掉：它用"同一问题多次采样、组内相对比较"这种更省的方式来估计优势，绕开了训练价值网络这块硬骨头。把这条"为省显存与稳定性而做的演化"讲清楚，你就能顺畅地从 PPO 过渡到 GRPO，而不是把它们当成互不相关的名词。</p>

      <h3>DPO：把 RLHF 拉直成一步</h3>
      <p class="cjk"><strong>DPO（Direct Preference Optimization，直接偏好优化）</strong>的洞见非常漂亮：既然最终目标是让模型偏好人类喜欢的回答，<mark class="key">那就不必绕道"训奖励模型 + 跑 RL"，可以用一个巧妙的数学变换，把偏好数据直接变成一个类似分类的监督损失</mark><a class="cite" href="https://arxiv.org/abs/2305.18290" target="_blank" rel="noopener">[来源]</a>。它同样需要成对偏好数据（chosen 优于 rejected），但训练时只需策略模型和一个冻结的参考模型，没有独立奖励模型、没有采样循环、没有 Critic。</p>

            <tr><td>需要奖励模型</td><td>是（单独训练）</td><td>否（隐式）</td></tr>
            <tr><td>训练时模型数</td><td>约四个</td><td>两个（策略+参考）</td></tr>
            <tr><td>训练稳定性</td><td>较难调，超参敏感</td><td>更稳定、更像 SFT</td></tr>
            <tr><td>是否在线采样</td><td>是</td><td>否（离线偏好数据）</td></tr>
            <tr><td>典型场景</td><td>大厂旗舰对齐、精细控制</td><td>开源社区默认偏好对齐</td></tr>
          </tbody>
        </table>
      </div>
      <p class="cjk">DPO 的代价是它通常基于<strong>离线</strong>偏好数据，缺少 PPO 那种"边训边采、动态探索"的能力，因此在需要复杂在线探索的任务上，上限可能不及精调好的 PPO。但对绝大多数团队来说，DPO 用更低的工程成本换来接近的效果，成了偏好对齐的默认起点。面试里被问"为什么选 DPO"，标准答法是：<strong>更简单、更稳定、免奖励模型，对我们的资源与场景性价比最高</strong>。</p>

      <h3>GRPO：免 Critic 与可验证奖励</h3>
      <p class="cjk"><strong>GRPO（Group Relative Policy Optimization，分组相对策略优化）</strong>是 DeepSeek 提出并在 R1 推理模型上大放异彩的方法<a class="cite" href="https://arxiv.org/abs/2501.12948" target="_blank" rel="noopener">[来源]</a>。它相对 PPO 的关键简化是<mark class="key">去掉了 Critic（价值网络）</mark>：对同一个问题采样一<em>组</em>回答，用这组回答奖励的<strong>组内相对高低</strong>（每个回答减去组内均值再归一化）来当作优势（advantage）估计，从而省掉了昂贵且难训的价值网络。</p>
      <p class="cjk">GRPO 真正的威力来自它和<strong>可验证奖励（verifiable / rule-based reward）</strong>的组合：在数学、代码这类<em>答案可自动判对错</em>的任务上，奖励不需要一个易被攻击的神经网络 RM，而是直接用"答案是否正确""代码是否通过测试""格式是否合规"这类规则给分。<mark class="key2">规则奖励几乎无法被"骗"，配合 GRPO 的组内对比，就能稳定地把模型往"真的把题做对"的方向推</mark>——这正是长链推理（long CoT）、自我反思能力得以涌现的训练基础。理解这一点，你也就理解了近两年"推理模型"浪潮的技术底座。</p>

      <h3>拒绝采样与 RLAIF：两条低成本增益路线</h3>
      <p class="cjk"><strong>拒绝采样（Rejection Sampling，含 Best-of-N）</strong>是一条常被低估但极其实用的路线。它的思路简单直接：对每个提示，让模型采样生成 N 个候选回答，用一个评判器（奖励模型、规则校验或更强的模型）挑出最好的，<mark class="key">再把这些"筛选出的优质回答"当作新的 SFT 数据回灌训练</mark>。这本质上是"用推理时算力换数据质量"，工程上比 PPO 简单得多，常作为完整 RLHF 之前的低成本预热，或与之交替进行。它也是很多"自我改进"流程的核心构件。</p>
      <p class="cjk"><strong>RLAIF（RL from AI Feedback，AI 反馈强化学习）</strong>则针对"人类标注太贵"的痛点，<mark class="key2">用 AI 模型来代替人类产出偏好标签</mark>。其代表是 Anthropic 的 <strong>Constitutional AI</strong>：给模型一套"宪法"原则（一组书面准则），让它据此对自己的回答做批评与修订，并用 AI 判断的偏好来做后续对齐<a class="cite" href="https://arxiv.org/abs/2212.08073" target="_blank" rel="noopener">[来源]</a>。RLAIF 的优点是可扩展、便宜、一致性高；风险是会继承并放大裁判模型自身的偏见，因此常与少量人类标注混合校准。面试里能对比"RLHF 用人、RLAIF 用 AI、可验证奖励用规则"这三种反馈来源，说明你对"奖励从哪来"有系统认知。</p>

      <h3>让你"用得起"：PEFT / LoRA / QLoRA 与量化</h3>
      <p class="cjk">全参数微调一个大模型对个人和小团队不现实。<strong>PEFT（参数高效微调）</strong>只更新极小一部分参数：<strong>LoRA</strong> 给权重加一对低秩矩阵、只训这对小矩阵，冻结原始权重，训练完可合并回去或作为"插件"按需加载；<strong>QLoRA</strong> 进一步把基座模型量化到 4-bit 再加 LoRA，让单张消费级显卡也能微调数十亿参数模型<a class="cite" href="https://arxiv.org/abs/2305.14314" target="_blank" rel="noopener">[来源]</a>。<strong>量化</strong>（把权重从 16-bit 压到 8/4-bit）则是推理侧降本的常用手段——用少量精度换显存与速度。这套工具链的意义在于：<mark class="key">它把"微调"从只有大厂玩得起，变成了小团队也能实践的日常工程</mark>，也让"为不同客户维护多个 LoRA 插件"这种轻量定制模式成为可能。</p>
      <p class="cjk">LoRA 为什么能"只训一点点就管用"？直觉是：微调阶段权重的<em>更新量</em>往往是低秩的——真正需要改变的方向没那么多，因此用两个瘦长的小矩阵之积去近似这个更新，既省参数又够表达。实践中有几个要点值得记住：<strong>秩 r 是关键超参</strong>（太小欠拟合、太大失去省参优势，需按任务规模试）；<strong>LoRA 训练与推理的模板仍要一致</strong>（和全量微调一样敏感）；<strong>多个 LoRA 可热插拔甚至加权组合</strong>，这让"一个基座 + 多套轻量适配器"的多租户部署非常经济。反过来，LoRA 也不是万能：当任务与预训练分布差异极大、需要模型学到明显的新能力时，全参数微调的上限仍更高。面试里能讲清"LoRA 省在哪、什么时候不够用"，比只说"它省显存"更有说服力。</p>

      <h3>后训练对 Agent 能力的影响</h3>
      <p class="cjk">对做 Agent 的人来说，后训练不是抽象话题，它直接决定了模型"当 Agent 好不好用"。几个关键联系：</p>
      <ul class="hub-list">
        <li><strong>工具调用与指令遵循</strong>：模型能不能稳定输出合法的工具调用格式、严格遵循系统提示的约束，很大程度上是 SFT/对齐阶段"喂"出来的。基座模型几乎不会自发做好这些。</li>
        <li><strong>长链推理与自我修正</strong>：GRPO + 可验证奖励训出的推理能力，正是 Agent 在多步任务里"想清楚再行动、错了会反思"的底层来源，直接影响规划与纠错质量。</li>
        <li><strong>格式与可靠性</strong>：Agent 循环对输出格式极敏感，一次 JSON 破损就可能中断整个流程；后训练对结构化输出的稳定性有决定性作用。</li>
        <li><strong>安全与拒答边界</strong>：对齐阶段塑造的"该拒就拒"行为，是 Agent 面对提示注入、危险指令时的第一道软性防线（硬防线仍需第 12 章的护栏）。</li>
      </ul>
      <div class="callout tip">
        <span class="label">面试要点</span>
        <span class="cjk">当被问"你们要不要为 Agent 微调模型"，成熟的答法不是非黑即白，而是分层判断：<strong>行为/格式/风格问题</strong>（如稳定输出特定工具调用格式）→ 微调收益高；<strong>知识/时效问题</strong>（如产品文档、实时数据）→ 用 RAG，别微调；<strong>能力问题</strong>（如更强推理）→ 通常换更强基座比自己训更划算。先分清是哪类问题，是这道题的分水岭。</span>
      </div>

      <h3>何时微调 vs 提示工程：一张决策表</h3>
      <p class="cjk">这是本章落地价值最高的一节，也是面试的收口题。把常见诉求映射到手段上：</p>
      <div class="table-wrap">
        <table>
          <thead><tr><th>你的诉求</th><th>首选手段</th><th>为什么</th></tr></thead>
          <tbody>
            <tr><td>补充最新/私有知识</td><td>RAG / 上下文工程</td><td>知识易过时，微调难灌入且会遗忘</td></tr>
            <tr><td>调整回答格式/口吻/结构</td><td>提示工程 → 不够再 SFT</td><td>行为类问题微调收益高</td></tr>
            <tr><td>稳定输出特定工具调用</td><td>提示工程 + 少量 SFT</td><td>格式一致性靠样本"喂"</td></tr>
            <tr><td>对齐主观偏好（好/无害）</td><td>DPO（资源少）/ RLHF（要精控）</td><td>好坏靠比较而非标准答案</td></tr>
            <tr><td>提升数学/代码正确率</td><td>GRPO + 可验证奖励</td><td>答案可自动判分，规则奖励难被骗</td></tr>
            <tr><td>降本/上私有部署</td><td>量化 + LoRA</td><td>精度换显存，插件式轻量定制</td></tr>
          </tbody>
        </table>
      </div>

      <h3>面试追问链</h3>
      <p class="cjk">后训练这块的面试常从"要不要微调"起步，一路追到具体算法的取舍，提前演练这条链能让你层层接得住：</p>
      <ul class="hub-list">
        <li><strong>Q1：</strong>预训练和后训练分别解决什么？→ 前者注入知识与能力，后者塑造行为与对齐，知识几乎不在后训练加入。</li>
        <li><strong>Q2：</strong>我想让模型懂我们最新的产品文档，该微调吗？→ 不该，这是知识/时效问题，用 RAG；引出微调 vs 提示工程决策表。</li>
        <li><strong>Q3：</strong>那 RLHF 到底在干嘛？→ 讲三阶段（SFT→RM→PPO），点出奖励模型是"把昂贵人类判断蒸馏成可高频查询的评分器"。</li>
        <li><strong>Q4：</strong>RLHF 有什么坑？→ 奖励作弊、长度/风格偏置、分布漂移、Goodhart 定律，靠 KL 约束兜底。</li>
        <li><strong>Q5：</strong>DPO / GRPO 相比 PPO 好在哪？→ DPO 免奖励模型、更稳更简单；GRPO 免 Critic、配可验证奖励训推理，收尾到"选型看资源与任务是否可自动判分"。</li>
      </ul>

      <div class="callout tip">
        <span class="label">本章小结</span>
        <span class="cjk">后训练的主线是"预训练注入能力、后训练塑造行为"。SFT 教模型照着做，靠的是高质量、多样、格式一致的数据；RLHF 用三阶段（SFT→奖励模型→PPO）解决"好坏只能比较"的对齐问题，但要提防奖励作弊与分布漂移，靠 KL 约束稳住；DPO 把它拉直成一步、免奖励模型，成为开源默认；GRPO 免 Critic、配合可验证奖励，撑起了长链推理浪潮；拒绝采样与 RLAIF 则是低成本增益路线。对 Agent 工程师而言，最有价值的能力不是复现某个算法，而是<strong>先分清"知识问题用 RAG、行为问题用微调、能力问题换基座"，再在微调内部按资源与任务可判分性选对方法</strong>。</span>
      </div>
