      <h3>为什么需要标准基准</h3>
      <p class="cjk">自建评估容易陷入三个陷阱：<strong>不可比</strong>（每家指标不同，你说的"85 分"和别人说的"85 分"根本不是一回事）、<strong>不可复现</strong>（环境和数据不公开，别人无法验证）、<strong>选择性报喜</strong>（只挑擅长的样例展示，回避软肋）。标准基准用<strong>统一任务集 + 自动判定</strong>把这三个洞堵上：任务固定、判分脚本公开、榜单公开，于是不同系统才能横向可比。</p>
      <p class="cjk">但基准是一把双刃剑。它同时带来一个隐患：<mark class="key2">刷榜刷出来的高分不等于真实可用</mark>。当一个基准变成兵家必争之地，团队会开始针对它的题型、判分逻辑、甚至已泄漏的答案做优化，这叫<strong>基准过拟合（benchmark overfitting）</strong>。所以成熟的做法是"两条腿走路"：既看公开榜单判断相对水位，也建自己贴近业务的私有评估集做绝对验收（呼应第 11 章）。面试里能主动点出这层张力，往往比背出某个榜单第一名更能体现判断力。</p>

      <div class="callout tip">
        <span class="label">一句话记住基准的价值</span>
        <span class="cjk">基准不是用来"证明我最强"的营销工具，而是用来"发现我在哪一类能力上系统性偏弱"的诊断工具。把它当体检报告读，而不是当奖状挂。</span>
      </div>

      <h3>六大基准逐一拆解：各自测什么</h3>
      <p class="cjk">主流 Agent 基准可以按"动作空间"和"环境真实度"两个维度铺开：从纯文本工具调用，到浏览器操作，再到整台电脑的图形界面。下面把六个高频基准逐一讲清它<strong>测什么能力、难在哪、用什么指标、有什么局限</strong>。</p>

      <p class="cjk"><strong>① GAIA（General AI Assistants）</strong>——考查<strong>通用助手</strong>能力。题目是人类日常真实会问的复杂问题，往往需要多步推理、联网检索、读文件、看图表、做算术等多种能力组合才能答对，且答案唯一、可自动核验。它设计了<strong>由易到难的多个难度等级</strong>，越高级越需要更长的工具链。<em>难点</em>在于：单一能力再强也不够，必须把检索、阅读、计算、多模态理解串成一条不断链的长链条，任何一环断了答案就错。<em>指标</em>是精确匹配式的准确率（answer accuracy）。<em>局限</em>是答案唯一、偏"找事实"，对开放式创作、长程改造类任务覆盖不足。<mark class="key">GAIA 上人类得分约 92%，而 2023 年 GPT-4 + 插件仅约 15%</mark><a class="cite" href="https://arxiv.org/abs/2311.12983" target="_blank" rel="noopener">[来源]</a>，这个巨大鸿沟正是它的价值所在。</p>

      <p class="cjk"><strong>② SWE-bench</strong>——考查<strong>真实修 bug</strong>能力，是 Coding Agent 的试金石。任务取自流行开源项目的真实 GitHub issue：给你一个仓库快照和一份问题描述，要求你产出一个 patch，让原本失败的测试通过。<em>难点</em>在于：要在庞大陌生代码库里定位问题、理解上下文、写出不破坏其他功能的修复——这就是真实工程师的日常。<em>指标</em>是<strong>解决率（resolved rate）</strong>，即提交的补丁能让隐藏测试全部通过的比例。它还有一个<strong>经人工核验的子集（SWE-bench Verified）</strong>，剔除了描述不清、测试有歧义的脏样例，让分数更可信。<em>局限</em>是集中在特定语言/项目生态，且"测试通过"不完全等于"修得优雅"。</p>

      <p class="cjk"><strong>③ τ-bench（tau-bench）</strong>——考查<strong>工具调用对话的可靠性</strong>。它模拟真实客服场景（如零售、航空），让 Agent 一边和"用户"多轮对话、一边按照<strong>业务规则手册</strong>调用工具（查订单、改预订、退款）。<em>难点</em>在于：不仅要会用工具，还要严格遵守政策约束、在信息不全时追问、拒绝违规请求。<em>指标</em>上它首创了 <strong>pass^k</strong>（连续 k 次独立运行都成功的概率），专门暴露"能成一次≠稳定可用"的可靠性短板<a class="cite" href="https://arxiv.org/abs/2406.12045" target="_blank" rel="noopener">[来源]</a>。<em>局限</em>是场景经过简化，真实客服的模糊性与情绪对抗更复杂。</p>

      <p class="cjk"><strong>④ OSWorld</strong>——考查<strong>真实电脑操作</strong>。它在真实操作系统里布置跨应用任务（改文档、调设置、处理文件、在多个软件间流转），Agent 通过看截图、操作鼠标键盘来完成。<em>难点</em>在于：动作空间是开放的像素坐标，界面千变万化，还要跨应用保持目标不漂移。<em>指标</em>是基于任务终态的<strong>执行成功判定</strong>——用脚本检查文件内容、系统状态是否达到预期，而不是看它"说自己做完了"。<mark class="key2">OSWorld 上人类约 72%，早期最强多模态模型一度不足 15%</mark><a class="cite" href="https://os-world.github.io/" target="_blank" rel="noopener">[来源]</a>。<em>局限</em>是环境搭建重、跑一次慢、成本高。</p>

      <p class="cjk"><strong>⑤ WebArena</strong>——考查<strong>网页操作</strong>。它自建了可复现的真实网站副本（电商、论坛、代码托管、内容管理系统等），让 Agent 在浏览器里完成"下单""发帖""改配置"这类端到端任务。<em>难点</em>在于：网页状态复杂、需要多步导航、要处理动态加载与表单。<em>指标</em>是<strong>功能正确性（functional correctness）</strong>——不是看页面长得对不对，而是看后端状态是否真的被正确改变。<em>局限</em>是网站是固定副本，缺少真实互联网的噪声、反爬和登录墙。</p>

      <p class="cjk"><strong>⑥ terminal-bench</strong>——考查<strong>命令行/终端环境</strong>下的操作能力。它把任务放进受控的沙箱终端里，让 Agent 通过敲命令来完成配置环境、处理数据、运维脚本等工作。<em>难点</em>在于：命令有副作用且不可轻易撤销，错一步可能污染环境；需要读懂报错、迭代纠错。<em>指标</em>同样是基于任务终态的自动判定（文件/进程/输出是否符合预期）。<em>局限</em>是偏向工程运维类任务，覆盖面窄，但对评估"能不能安全地动真实系统"很有针对性。</p>

      <h3>指标的深水区：pass@k、pass^k 与"成功"到底怎么判</h3>
      <p class="cjk">很多候选人只知道"准确率"，一到追问就露怯。评估指标里有几个必须分清的概念：</p>
      <ul class="hub-list">
        <li><strong>pass@k</strong>：跑 k 次，只要<em>有一次</em>成功就算过。它衡量的是"模型有没有能力做到"，偏乐观，适合评估上限（潜力）。</li>
        <li><strong>pass^k</strong>：跑 k 次，必须<em>每一次</em>都成功才算过。它衡量的是"稳不稳定"，偏悲观，暴露可靠性短板。<mark class="key">一个 pass@1 很高但 pass^8 骤降的系统，意味着它靠运气而非靠稳定能力</mark>——这正是生产环境最怕的。</li>
        <li><strong>解决率 / 终态判定</strong>：不看模型"自称完成"，而看环境的客观终态（测试是否通过、文件是否正确、订单是否真的被创建）。这叫<strong>结果导向判定</strong>，比让 LLM 打分更抗作弊。</li>
      </ul>
      <p class="cjk">此外还要区分<strong>结果评估</strong>与<strong>过程/轨迹评估</strong>：前者只看最终对不对，后者看它"每一步走得对不对"（有没有多余动作、有没有绕远路、有没有违规调用）。面试时能说清"我用终态判成败、用轨迹分析定位是哪一步坏的"，就展现了完整的评估方法论。</p>
      <p class="cjk">与轨迹评估配套的，是一套<strong>错误分类学（error taxonomy）</strong>：把失败按根因归类，才能对症下药，而不是笼统地说"成功率低"。常见的失败类别包括：<strong>规划错误</strong>（一开始方向就错了）、<strong>工具选择错误</strong>（该用 A 却用了 B）、<strong>参数错误</strong>（工具选对但入参错）、<strong>幻觉</strong>（编造不存在的事实或结果）、<strong>循环/卡死</strong>（反复重复同一无效动作）、<strong>提前放弃或过早收尾</strong>（没做完就宣称完成）。<mark class="key">把 100 次失败按这套分类打上标签，你立刻能看出瓶颈是"不会规划"还是"工具用不对"，从而知道该改提示词、改工具设计还是换模型</mark>。这一步是把评估从"打分"升级为"驱动改进"的关键跳板，也是资深候选人和初级候选人在评估话题上的分水岭。</p>

      <h3>如何选基准：先问自己三件事</h3>
      <p class="cjk">面对一长串基准，不要盲目全刷。选基准前先回答三个问题，就能收敛到该盯哪几个：</p>
      <div class="table-wrap">
        <table>
          <thead><tr><th>你要回答的问题</th><th>决定了</th><th>对应基准偏好</th></tr></thead>
          <tbody>
            <tr><td>我的 Agent 主要做什么形态的任务？</td><td>动作空间</td><td>写代码→SWE-bench；操作软件→OSWorld；跑网页→WebArena；工具对话→τ-bench</td></tr>
            <tr><td>我更担心"能不能做到"还是"稳不稳定"？</td><td>指标口径</td><td>看上限用 pass@k；看可靠性用 pass^k / 多次重复</td></tr>
            <tr><td>我的用户任务和基准任务分布像不像？</td><td>外部效度</td><td>越不像，越要补自建私有评估集</td></tr>
          </tbody>
        </table>
      </div>
      <p class="cjk">一个务实的组合拳是：<strong>用 1–2 个贴近形态的公开基准</strong>建立与业界的相对坐标，<strong>再用一个私有评估集</strong>做贴合业务的绝对验收。只依赖公开基准，你会优化到"榜单好看但用户不买账"；只做私有集，你又失去了和外部对比的参照系。</p>

      <h3>如何防数据污染（contamination）</h3>
      <p class="cjk">评估的头号信任杀手是<strong>数据污染</strong>——测试题（或答案）以某种方式进了模型的训练数据，于是分数虚高，其实是"背过答案"而非"真会做"。这在以爬取全网为训练来源的大模型时代尤其严重，公开在 GitHub / arXiv 上的基准很容易被无意收录。防污染要从多个角度下手：</p>
      <ul class="hub-list">
        <li><strong>时间隔离</strong>：优先用模型训练截止日期<em>之后</em>才出现的新任务/新样例来测，天然排除"背过"的可能。</li>
        <li><strong>私有 / 隐藏测试集</strong>：只公开题面、不公开答案与判分细节，或干脆用不公开的内部题库，让针对性刷分无从下手。</li>
        <li><strong>动态/程序化生成</strong>：用模板或规则实时生成同类但具体值不同的题，模型无法靠记忆特定答案取巧。</li>
        <li><strong>污染探针</strong>：故意构造"只有见过原题才可能答对"的检查项（如原题里的罕见拼写、特定顺序），若模型异常擅长这些，就要警惕。</li>
        <li><strong>轨迹审查</strong>：看它是"推理出来的"还是"直接秒答"，异常一致的完美答案往往是记忆而非推理的信号。</li>
      </ul>
      <div class="callout warn">
        <span class="label">常见误区与反模式</span>
        <span class="cjk">① <strong>唯榜单论</strong>——把公开榜单第一当成"生产可用"，忽视了任务分布与你的业务未必一致。② <strong>只报 pass@1</strong>——回避可靠性，掩盖"跑十次成一次"的真相。③ <strong>让 LLM 给自己打分且不设锚点</strong>——评审模型可能系统性偏袒某类风格，务必配人工校准与结果导向判定。④ <strong>忽视污染</strong>——不做时间隔离就宣称"超越人类"，很可能是背题。⑤ <strong>拿单点分数下结论</strong>——不报告方差/多次重复，运气成分被当成能力。</span>
      </div>

      <h3>从基准到你自己的评估流水线</h3>
      <p class="cjk">基准的方法论可以直接借鉴到自研评估，做成一条能长期跑的流水线：<strong>①</strong> 准备贴近业务的任务集，并为每个任务定义<strong>可自动判定</strong>的成功标准（终态检查优先于主观打分）；<strong>②</strong> 关注一致性而非单次运气——借鉴 τ-bench 的 <strong>pass^k</strong>思路，让每个任务重复多次、报告成功率与方差，暴露"能成一次≠稳定可用"的短板<a class="cite" href="https://arxiv.org/abs/2406.12045" target="_blank" rel="noopener">[来源]</a>；<strong>③</strong> <strong>组件级 + 轨迹级</strong>评估结合，既看端到端成败，也能定位是检索、规划还是工具调用哪一步出的问题；<strong>④</strong> 把评估接入 CI，每次改提示词/换模型都自动回归，防止"改好了一个用例、悄悄改坏三个"。</p>
      <p class="cjk">这套流水线的终极目标，是把"我感觉变好了"升级为"我有一条可复现、可回归、能定位问题的证据链"。当面试官问"你怎么知道你的优化真的有效"，你能把这条链讲出来，就已经赢了。</p>

      <h3>LLM-as-judge：省力但危险的裁判</h3>
      <p class="cjk">当成功标准无法用脚本自动判定（比如"这段回答写得好不好""这个总结准不准确"），很多团队会祭出 <strong>LLM-as-judge</strong>——让另一个强模型来给答案打分。它的确省下了大量人工标注，但它是一把需要小心握持的双刃剑，面试里被追问时要能讲清它的系统性偏差：</p>
      <ul class="hub-list">
        <li><strong>位置偏差（position bias）</strong>：做两两对比时，裁判会倾向于选靠前（或靠后）的那个答案，与内容质量无关。缓解办法是交换顺序各评一次、取一致结果。</li>
        <li><strong>啰嗦偏差（verbosity bias）</strong>：裁判常常偏爱更长、更啰嗦的回答，哪怕它并不更正确。要在评分标准里显式约束"简洁不扣分"。</li>
        <li><strong>自我偏爱（self-preference）</strong>：模型可能偏袒和自己风格相近的输出，用同源模型既当选手又当裁判尤其危险。</li>
        <li><strong>标准漂移</strong>：不给明确评分细则时，裁判的尺度会飘忽不定，导致同一答案不同次打分不一致。</li>
      </ul>
      <p class="cjk">正确用法是：<mark class="key">给裁判一份清晰的评分量规（rubric），让它按维度打分并给出理由，再用一批人工标注样本校准裁判与人的一致性</mark>。只有当裁判和人的判断高度吻合时，它的分数才可信。把 LLM-as-judge 当成"需要先被评估的评估器"，而不是无条件信任的黑箱裁判，是成熟工程师的标志。</p>

      <h3>离线评估与在线评估：上线不是终点</h3>
      <p class="cjk">基准和自研评估集大多属于<strong>离线评估（offline evaluation）</strong>——在固定数据集上、上线前跑。但真实世界的分布永远比任何数据集更丰富，所以还需要<strong>在线评估（online evaluation）</strong>作为补充，两者构成完整闭环：</p>
      <div class="table-wrap">
        <table>
          <thead><tr><th>维度</th><th>离线评估</th><th>在线评估</th></tr></thead>
          <tbody>
            <tr><td>时机</td><td>上线前，固定数据集</td><td>上线后，真实流量</td></tr>
            <tr><td>信号</td><td>基准分、成功率、方差</td><td>用户满意度、任务完成率、人工接管率</td></tr>
            <tr><td>手段</td><td>回归测试、CI 卡口</td><td>A/B 实验、灰度、线上监控</td></tr>
            <tr><td>优点</td><td>可控、可复现、迭代快</td><td>贴近真实、能抓分布漂移</td></tr>
            <tr><td>局限</td><td>覆盖不到长尾真实场景</td><td>慢、有风险、需要流量</td></tr>
          </tbody>
        </table>
      </div>
      <p class="cjk">一个健康的评估体系是<mark class="key2">"离线守门、在线兜底"</mark>：离线评估在 CI 里拦住明显退步的改动，在线评估通过 A/B 与监控捕捉离线抓不到的真实问题（如新出现的用户意图、数据分布漂移），再把线上暴露的坏样例回灌进离线集，形成不断扩充的回归资产。面试里能画出这个闭环，说明你懂的是"评估作为一套长期运营的系统"，而非"跑个分交差"。</p>
      <div class="callout tip">
        <span class="label">一个容易被忽视的在线信号</span>
        <span class="cjk"><strong>人工接管率 / 求助率</strong>是被严重低估的健康度指标：如果 Agent 频繁触发人工介入或用户频繁重问，即便离线分很高，也说明它在真实场景里并不好用。把"用户是不是不得不来救场"当成一等公民指标，往往比任何离线分数都诚实。</span>
      </div>

      <h3>面试追问链</h3>
      <p class="cjk">评估这个主题的追问链非常经典，从"知道基准"一路逼到"懂评估方法论"：</p>
      <ul class="hub-list">
        <li><strong>Q1：</strong>你了解哪些 Agent 评估基准？→ 按能力维度铺开：GAIA（通用）、SWE-bench（代码）、τ-bench（工具对话）、OSWorld（电脑）、WebArena（网页）、terminal-bench（终端）。</li>
        <li><strong>Q2：</strong>它们分别测什么、指标是什么？→ 讲清能力、动作空间与关键指标（解决率、pass^k、终态判定）。</li>
        <li><strong>Q3：</strong>pass@k 和 pass^k 有什么区别？→ 前者看上限、偏乐观；后者看稳定性、偏悲观，暴露可靠性。</li>
        <li><strong>Q4：</strong>公开榜单分高就能上线吗？→ 引出基准过拟合、任务分布外部效度，强调补私有评估集。</li>
        <li><strong>Q5：</strong>怎么防止评估被数据污染？→ 时间隔离、隐藏/动态题集、污染探针、轨迹审查。</li>
        <li><strong>Q6：</strong>那你自己的评估流水线怎么搭？→ 自动判定 + 多次重复报方差 + 组件/轨迹分层 + 接入 CI 回归。</li>
      </ul>

        <span class="label">本章小结</span>
        <span class="cjk">评估是 Agent 工程的"度量衡"。标准基准（GAIA、SWE-bench、τ-bench、OSWorld、WebArena、terminal-bench）按不同能力维度提供了可比、可复现的公共标尺，但它们是<strong>诊断工具而非奖状</strong>——警惕基准过拟合与数据污染。掌握 pass@k 与 pass^k 的分野、结果导向的终态判定、以及"公开基准定坐标 + 私有集做验收"的组合拳，你才能把"我感觉不错"升级为"我有可复现、可回归、能定位问题的证据链"。这条证据链，正是从"会做 Demo"到"能上生产"的分水岭。</span>
