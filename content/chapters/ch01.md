      <h2 class="chap-title"><span class="kicker">01</span>什么是 Agent</h2>
      <p class="cjk">面试第一问几乎总是"你怎么理解 Agent"。一个能拿分的回答，必须讲清它与普通 LLM 应用的本质区别。<mark class="key">传统软件让用户自己完成工作流，而 Agent 能够代表用户、以高度自主的方式执行同样的工作流</mark><sup><a href="#cite-2">[2]</a></sup>。换句话说，把大模型从"一问一答的文本生成器"变成"能规划、能调用工具、能根据结果自我修正的执行体"，才叫 Agent。</p>
      <div class="interactive-mini" id="insightBacklink-ch1"></div>

      <div class="callout tip">
        <span class="label">📎 本章对照的开源一手资料（建议边读边开）</span>
        <span class="cjk">这本手册是<strong>中文精讲 + 导航层</strong>，概念定义都对齐权威一手材料，不自造口径。本章"Workflow vs Agent""何时别上 Agent"的原始出处，回到这三份：<br>
        ① <a href="https://www.anthropic.com/engineering/building-effective-agents" target="_blank" rel="noopener">Anthropic《Building Effective Agents》</a>（Schluntz &amp; Zhang，2024-12）——"多数 Agent 应该是 Workflow"的一手论述；<br>
        ② <a href="https://cdn.openai.com/business-guides-and-resources/a-practical-guide-to-building-agents.pdf" target="_blank" rel="noopener">OpenAI《A Practical Guide to Building Agents》</a>（2025，34 页 PDF）——OpenAI 侧"宽定义"与设计模式；<br>
        ③ <a href="https://arxiv.org/abs/2210.03629" target="_blank" rel="noopener">ReAct 论文（arXiv:2210.03629）</a>——"推理与行动交替"这一 Agent 循环的学术源头。</span>
      </div>

      <h3>Agent 与普通 LLM 应用的分界线</h3>
      <p class="cjk">判断一个系统是不是 Agent，看它是否同时具备三个特征：<strong>目标导向</strong>（围绕一个目标持续行动而非单次响应）、<strong>自主决策</strong>（自己决定下一步做什么、用哪个工具）、<strong>多步循环</strong>（观察结果 → 再决策 → 再行动，直到完成或触发终止）。缺了循环，它只是一次带工具的函数调用；缺了自主，它只是一条写死的流水线。</p>

      <div class="callout tip">
        <span class="label">面试要点</span>
        <span class="cjk">不要把"用了 LLM"等同于"做了 Agent"。一个只调用一次模型、返回结果就结束的接口不是 Agent；一个能自己判断"信息不够，再搜一次"的系统才是。这个区分是初面高频送分点，也是拉开候选人层次的地方。</span>
      </div>

      <h3>Agent 发展简史：三次范式迁移</h3>
      <p class="cjk">面试官偶尔会问"Agent 是不是这两年才有的新概念"，这时能讲清它的历史脉络，会显得你有全局视野。所谓"智能体"（agent）在 AI 学科里是个老词，它经历了三次大的范式迁移：</p>
      <ul class="hub-list">
        <li><strong>符号主义时代（专家系统 / BDI 架构）</strong>：早期智能体基于人工编写的规则与逻辑推理，代表是"信念-愿望-意图（Belief–Desire–Intention）"模型。它能自主决策，但知识全靠人工灌入，无法泛化，脆弱且难维护。</li>
        <li><strong>强化学习时代（RL Agent）</strong>：智能体通过与环境交互、以奖励信号学习策略，AlphaGo、Atari 游戏智能体是标志。它在<em>封闭、可模拟</em>的环境里超越人类，但需要海量交互样本，且难以迁移到开放的现实任务。</li>
        <li><strong>大模型时代（LLM Agent）</strong>：2022 年 ReAct 把"推理与行动交替"引入语言模型，2023 年 AutoGPT、BabyAGI 掀起"自主 Agent"热潮（也暴露了无限循环、目标漂移等问题），2024 年工具调用（function calling / tool use）被各大模型厂商标准化，2025—2026 年行业从"炫技 demo"收敛到"可交付的生产系统"。</li>
      </ul>
      <p class="cjk"><mark class="key2">LLM Agent 的真正突破，不在于"更会决策"，而在于它天然携带了海量世界知识与语言接口</mark>——这让它无需为每个新任务重新训练，就能通过提示词与工具即时适配。这也是为什么"Agent"这个老概念，直到 LLM 出现才真正走向大规模落地。理解这条脉络，你就能回答"LLM Agent 与传统 RL Agent 有何本质不同"这类拉开层次的追问。</p>

      <h3>Anthropic 与 OpenAI 的"定义之争"</h3>
      <p class="cjk">"Agent 到底该怎么定义"在业界并没有统一答案，主流厂商的口径存在耐人寻味的分歧，这本身就是一道很好的开放题。</p>
      <ul class="hub-list">
        <li><strong>Anthropic 的"窄定义"</strong>：明确把 <strong>Workflow</strong>（由代码预先编排、LLM 只填节点）与 <strong>Agent</strong>（LLM 在运行时动态决定自己的流程与工具使用）区分开，并反复强调"能用简单方案就别上 Agent"<sup><a href="#cite-3">[3]</a></sup>。这是一种偏工程、偏克制的定义。</li>
        <li><strong>OpenAI 的"宽定义"</strong>：倾向于把凡是"能代表用户自主完成任务"的系统都称为 Agent，把 Workflow 视作 Agent 的一种实现形态，而非对立面。这种定义更偏产品、更强调"自主代办"的用户价值。</li>
      </ul>
      <p class="cjk">这场分歧的实质，是"从工程可靠性出发"还是"从用户价值出发"看问题。<mark class="key">面试中的高分答法不是站队，而是指出：定义的宽窄取决于你站在哪个视角，重要的是团队内部对"自主"的边界达成共识</mark>——否则同一个"Agent"需求，产品、研发、测试三方理解会完全不同，直接导致返工。</p>

      <h3>Workflow 与 Agent：别一上来就上 Agent</h3>
      <p class="cjk">这是 2026 年最重要的工程共识之一。<mark class="key2">Workflow（工作流）更简单、更便宜、更可靠、更好调试——在 80% 的场景里它才是正确答案</mark><sup><a href="#cite-3">[3]</a></sup>。当任务路径是确定的、可以预先编排的，就用固定的 Workflow（LLM 只负责其中某几步）；只有当任务真正需要动态决策、路径无法预先枚举时，才引入自主 Agent。面试时能主动说出"我会先评估要不要用 Agent"，往往比直接堆架构更能体现工程成熟度。</p>

      <h3>Agent 与 RPA / chatbot / workflow 引擎的区别</h3>
      <p class="cjk">"自动化"不是新词。在 Agent 之前，企业里早已有一堆"能自动干活"的系统：RPA、规则聊天机器人、BPM/工作流引擎。面试官很喜欢用"这不就是升级版 RPA 吗"来试探你是否真懂 Agent 的独特性。把它们摆在一张表里对比，答案就清晰了：</p>
      <div class="table-wrap">
        <table>
          <thead>
            <tr><th>系统</th><th>决策方式</th><th>处理非结构化输入</th><th>面对变化时</th><th>本质局限</th></tr>
          </thead>
          <tbody>
            <tr><td><strong>RPA</strong>（如 UiPath）</td><td>录制/编写的固定脚本，按坐标或选择器操作 UI</td><td>几乎不能</td><td>界面一变就崩，需人工重录</td><td>脆弱、无理解、无泛化</td></tr>
            <tr><td><strong>规则 chatbot</strong>（如早期客服机器人）</td><td>意图识别 + 预设话术树</td><td>弱，靠关键词/槽位</td><td>遇到没预设的问法就答非所问</td><td>只能覆盖穷举过的路径</td></tr>
            <tr><td><strong>Workflow 引擎</strong>（如 BPM/Airflow）</td><td>开发者预先编排的 DAG</td><td>取决于节点实现</td><td>需人工改流程图</td><td>路径必须可预先枚举</td></tr>
            <tr><td><strong>LLM Agent</strong></td><td>模型运行时基于语义理解动态决策</td><td>强，天然处理自然语言/图像</td><td>能自主调整策略、重试、换工具</td><td>不可预测、成本高、需护栏</td></tr>
          </tbody>
        </table>
      </div>
      <p class="cjk">一句话点透区别：<mark class="key">RPA 复刻的是"人的手"（机械操作），规则 chatbot 复刻的是"人的话术脚本"，workflow 引擎复刻的是"人画好的流程图"，而 Agent 复刻的是"人面对未知问题时的临场决策"</mark>。前三者的智能都固化在开发时，运行时只是回放；Agent 的智能则发生在运行时。这也决定了它们的适用边界：任务越确定、越高频、越要求稳定，越应该用前三者；任务越开放、越需要理解与应变，才越值得上 Agent。</p>
      <div class="callout warn">
        <span class="label">常见误区</span>
        <span class="cjk">别把"Agent 更先进"理解成"Agent 应该取代 RPA/workflow"。成熟的生产架构往往是<strong>混合的</strong>：用确定性的 workflow 引擎做主干与编排，只在真正需要"理解与决策"的节点嵌入 Agent。用 Agent 去做本可以用一条 SQL 或一个 RPA 脚本稳定完成的事，是既贵又不可靠的过度设计。</span>
      </div>

      <h3>Agent 的自主性光谱</h3>
      <p class="cjk">自主性不是"有或没有"，而是一条连续光谱：从"人类审批每一步"到"完全自主直到交付结果"。生产系统通常落在中间——关键动作（如发邮件、改数据库、花钱）设置 <strong>human-in-the-loop（人工确认）</strong>，低风险动作放开自主。理解这条光谱，能帮你在面试中回答"如何平衡自动化与安全"这类开放题。</p>
      <p class="cjk">更实用的做法，是把"人在环"细分成三种介入形态，面试时能报出这三个词就很加分：<strong>human-in-the-loop</strong>（每个关键动作前人工审批，最安全也最慢）、<strong>human-on-the-loop</strong>（人不逐步审批，但实时监控、可随时叫停，兼顾效率与安全）、<strong>human-out-of-the-loop</strong>（完全自主，只在事后审计，仅适用于低风险可逆场景）。<mark class="key">选择哪种介入形态，本质上是在"错误代价"与"人力成本"之间定价</mark>：动作越不可逆、错了越贵，就越要把人往"环里"推。一个成熟的系统甚至会<em>动态调整</em>——平时 on-the-loop 放开跑，一旦 Agent 的置信度下降或触碰到敏感资源，就自动升级为 in-the-loop 请求人工确认。</p>

      <h3>用形式化视角重新理解 Agent</h3>
      <p class="cjk">口语化的定义能应付初面，但要在系统设计题上站稳，你需要一个更精确的心智模型。学术界通常把智能体抽象为一个在环境中持续运转的<strong>感知-决策-行动循环（Perception–Decision–Action Loop）</strong>：Agent 在每一时刻 <em>t</em> 感知到环境状态的一个观测 <em>o<sub>t</sub></em>，结合自身维护的内部状态（记忆）<em>s<sub>t</sub></em>，通过一个策略函数 <em>π</em> 产生一个动作 <em>a<sub>t</sub></em>；动作作用于环境后改变了世界，产生新的观测 <em>o<sub>t+1</sub></em>，循环继续，直到目标达成或触发终止条件。</p>
      <p class="cjk">在 LLM 时代，这个抽象被具体化为：<mark class="key">策略 π 就是"大模型 + 提示词 + 可用工具集"，观测就是塞进上下文窗口的一切信息，动作就是模型输出的一次工具调用或最终答复，环境就是文件系统、API、数据库、浏览器乃至真实世界</mark>。理解这一点，你就能把五花八门的框架（LangGraph、smolagents、OpenAI Agents SDK）都还原成"如何组织这个循环"的不同工程实现，而不会被 API 名词淹没。</p>

      <div class="callout tip">
        <span class="label">为什么这样理解很值钱</span>
        <span class="cjk">当面试官抛出一个陌生框架或一个开放式架构题，能把它映射回"感知什么、内部状态是什么、策略如何决策、动作空间有多大、何时终止"这五个要素的候选人，几乎总能给出有条理的回答。这是从"背 API"升级到"懂本质"的分水岭。</span>
      </div>

      <h3>自主性的五个层级：一个可迁移的分级框架</h3>
      <p class="cjk">把自主性光谱进一步离散化，可以借鉴自动驾驶 L0–L5 的思路，建立一套在面试中极具说服力的分级语言。它的价值在于：当你描述一个真实项目时，能精准地说"我们做的是 L3 而不是 L5"，从而体现你对能力边界与风险的清醒认知。</p>
      <div class="table-wrap">
        <table>
          <thead>
            <tr><th>层级</th><th>名称</th><th>特征</th><th>典型形态</th></tr>
          </thead>
          <tbody>
            <tr><td>L0</td><td>纯 LLM 调用</td><td>单次输入输出，无循环、无工具</td><td>翻译、摘要、改写接口</td></tr>
            <tr><td>L1</td><td>工具增强</td><td>可调用一次外部工具补充信息，但路径固定</td><td>带检索的问答（朴素 RAG）</td></tr>
            <tr><td>L2</td><td>链式工作流</td><td>多步骤按预定义 DAG 编排，LLM 负责其中节点</td><td>固定管线的抽取-分类-写入</td></tr>
            <tr><td>L3</td><td>受限自主 Agent</td><td>运行时自主决策，但在受限动作空间内，关键动作需人工确认</td><td>企业客服、报销助手</td></tr>
            <tr><td>L4</td><td>高度自主 Agent</td><td>长程任务自主规划、自我修正，人只看结果</td><td>Coding Agent、深度研究 Agent</td></tr>
            <tr><td>L5</td><td>完全自治</td><td>跨领域、开放世界、自设目标</td><td>目前仍是研究愿景</td></tr>
          </tbody>
        </table>
      </div>
      <p class="cjk">现实中的绝大多数生产系统落在 <span class="tag">L2–L4</span>。一个反复出现的工程教训是：<mark class="key2">不要在 L2 就能解决的问题上强行做 L4</mark>——过度自主意味着更高的成本、更差的可预测性和更难的调试。资深工程师的价值，恰恰体现在能准确判断"这个需求到底需要几级自主"。</p>

      <h3>Agent 能力的三大支柱</h3>
      <p class="cjk">如果说四大组件（第 2 章）是 Agent 的"解剖结构"，那么支撑它真正运转起来的，是三大能力支柱，它们也是后续章节的主线：</p>
      <ul class="hub-list">
        <li><strong>规划（Planning）</strong>：把一个模糊的大目标分解为可执行的子步骤，并在执行中根据反馈调整计划。对应 ReAct、Plan-and-Execute 等设计模式（第 3 章）。</li>
        <li><strong>工具使用（Tool Use）</strong>：通过结构化接口与外部世界交互，把语言模型的"想法"落地为"行动"。工具的设计质量直接决定 Agent 的能力上限（第 2、6 章）。</li>
        <li><strong>记忆（Memory）</strong>：在超出单次上下文窗口的时间尺度上保留、检索、更新信息，是 Agent 能否处理长程任务的命门（第 4、5 章）。</li>
      </ul>

      <h3>经济学视角：能力-成本-风险三角</h3>
      <p class="cjk">技术面试之外，越来越多的系统设计题和总监面会从"账"的角度考你：<em>为什么这个功能值得做成 Agent？它贵在哪、险在哪？</em>回答这类问题，需要一个超越技术的框架。我把它概括为<strong>能力-成本-风险三角（Capability–Cost–Risk Triangle）</strong>：任何一个 Agent 化决策，都是在这三者之间做权衡，且三者相互牵制、无法同时最优。</p>
      <figure class="diagram"><pre class="mermaid">

    C2 -.降本手段.-> C3
</pre><figcaption>图 1-1　Agent 决策的能力-成本-风险三角</figcaption></figure>
      <ul class="hub-list">
        <li><strong>能力（Capability）</strong>：Agent 能处理多开放、多长程的任务。提升能力通常靠更强的模型、更多的工具、更高的自主性。</li>
        <li><strong>成本（Cost）</strong>：不只是 token 费用。一次自主循环可能调用模型十几次，叠加工具延迟，端到端耗时从秒级涨到分钟级；还有开发、评估、监控、维护的<em>工程成本</em>，后者常被低估。</li>
        <li><strong>风险（Risk）</strong>：包括出错的代价（发错邮件 vs 转错账）、不可控性（自主越高越难预测）、以及安全攻击面（提示注入、越权调用工具）。</li>
      </ul>
      <p class="cjk">三角的价值在于揭示<mark class="key2">你几乎无法同时把三者都优化到最好</mark>：想要更强能力（更高自主），成本和风险就上升；想压成本（用小模型、限步数），能力就打折；想降风险（处处人工确认），又牺牲了自动化带来的效率。<mark class="key">资深工程师的核心能力，就是根据业务把三角调到合适的平衡点</mark>——比如金融场景把风险权重拉满、宁可牺牲自动化率；而内部研发工具则可以容忍更高风险换取能力。面试中若能主动用这个框架分析"要不要做、做到什么程度"，会显著区别于只会谈技术的候选人。</p>
      <div class="callout tip">
        <span class="label">高分表达</span>
        <span class="cjk">当被问"这个需求你会怎么设计"，先别急着画架构。可以说："我会先看这个任务错了的代价有多大——如果是不可逆的高风险动作，我会把自主性压低、加人工确认；如果是低风险高频任务，我会评估 Agent 的循环成本是否划算，很多时候一个 workflow 反而更优。"这就是在用能力-成本-风险三角说话。</span>
      </div>

      <h3>真实产品拆解：把概念落到地面</h3>
      <p class="cjk">光谈定义容易空。把几个广为人知的产品按"自主层级、动作空间、护栏设计"拆开，能让你的回答立刻有血有肉。<strong>注意：以下是基于其公开产品形态的定性拆解，不涉及任何未公开的内部数字。</strong></p>
      <div class="card-grid">
        <div class="card">
          <h4>Coding Agent（如 IDE 内的编码助手）</h4>
          <p>典型 <span class="tag">L4</span>。动作空间大：读写文件、跑测试、执行命令、检索代码库。护栏靠"改动可 diff 可回滚、命令需确认、在沙箱/分支里运行"。它是长程自主的代表——能自己跑测试、看报错、再改代码，循环多轮。</p>
        </div>
        <div class="card">
          <h4>深度研究 Agent（Deep Research 类）</h4>
          <p>典型 <span class="tag">L4</span>，但动作空间偏"只读"（搜索、浏览、综合）。因为几乎没有破坏性副作用，可以放开自主性跑很久；主要风险是"信息真假与幻觉"，护栏靠引用溯源与交叉验证。</p>
        </div>
        <div class="card">
          <h4>企业客服 / 报销助手</h4>
          <p>典型 <span class="tag">L3</span>。动作空间受限（查订单、发起退款申请），关键动作（真正退款）走 human-in-the-loop 或额度限制。它体现了"受限自主"的工程智慧：让 Agent 做判断，但把不可逆动作卡在人手里。</p>
        </div>
        <div class="card">
          <h4>浏览器操作 Agent（Computer Use 类）</h4>
          <p>介于 <span class="tag">L3</span> 与 <span class="tag amber">L4</span>。动作空间极大（几乎能点任何按钮），风险也最高，因此常配合"敏感操作前截图确认、限定网站白名单"等护栏。它展示了动作空间越大、护栏必须越重的规律。</p>
        </div>
      </div>
      <p class="cjk">把这四个产品串起来看，你会发现一条清晰的工程规律：<mark class="key">动作空间越大、副作用越不可逆，护栏就必须越重，自主性反而要越谨慎</mark>。这正是能力-成本-风险三角在产品层面的具体投影。面试中被问"你用过哪些 Agent 产品、它们怎么设计的"，用"自主层级 + 动作空间 + 护栏"这三把尺子去拆，永远比复述功能列表更显专业。</p>

      <h3>一个最小 Agent 的心智模型</h3>
      <p class="cjk">褪去所有框架的包装，一个 Agent 的核心就是一个"带工具的 while 循环"。下面这段伪代码值得你在面试白板上默写下来——它比任何框架 API 都更能证明你懂 Agent 的本质：</p>
      <div class="table-wrap">
        <table>
          <thead><tr><th>最小 Agent 循环（伪代码）</th></tr></thead>
          <tbody>
            <tr><td><code>state = [system_prompt, user_goal]</code></td></tr>
            <tr><td><code>for step in range(MAX_STEPS):</code></td></tr>
            <tr><td><code>&nbsp;&nbsp;action = LLM(state, tools)&nbsp;&nbsp;# 决策：产生工具调用或终止</code></td></tr>
            <tr><td><code>&nbsp;&nbsp;if action.is_final: return action.answer&nbsp;&nbsp;# 终止条件</code></td></tr>
            <tr><td><code>&nbsp;&nbsp;observation = execute(action)&nbsp;&nbsp;# 行动：调用工具</code></td></tr>
            <tr><td><code>&nbsp;&nbsp;state.append(action); state.append(observation)&nbsp;&nbsp;# 感知：写回上下文</code></td></tr>
            <tr><td><code>return fallback()&nbsp;&nbsp;# 兜底：达到步数上限仍未完成</code></td></tr>
          </tbody>
        </table>
      </div>
      <p class="cjk">这短短几行藏着三个生产系统必须回答的关键问题：<strong>MAX_STEPS</strong> 如何设定（防止无限循环、控制成本）？<strong>终止条件</strong>如何判定（模型自称完成 ≠ 真的完成）？<strong>state</strong> 无限增长怎么办（上下文爆炸，需要压缩与裁剪，见第 4 章）？把这三点讲透，就能自然过渡到"Agent 工程化"这个更硬核的话题。</p>

      <div class="callout warn">
        <span class="label">常见误区与反模式</span>
        <span class="cjk">① <strong>"套了 Agent 框架就是 Agent"</strong>——用了 LangGraph 却写死每一步，本质仍是 Workflow。② <strong>"自主性越高越先进"</strong>——过度自主是成本与不可控的根源，不是加分项。③ <strong>"Agent 能替代确定性代码"</strong>——能用普通函数解决的，永远不要交给 LLM 循环去猜。④ <strong>混淆"多次调用模型"与"自主决策"</strong>——固定调用三次模型的管线不是 Agent，能自己决定"要不要再查一次"的才是。</span>
      </div>

      <h3>常见面试陷阱题拆解</h3>
      <p class="cjk">这一章对应的知识点，面试官常包装成"看似简单、实则埋坑"的问题。提前识别陷阱的<em>意图</em>，比背标准答案更重要。</p>
      <div class="table-wrap">
        <table>
          <thead>
            <tr><th>陷阱题</th><th>它在考什么</th><th>踩分点（错误答法）</th><th>高分答法</th></tr>
          </thead>
          <tbody>
            <tr><td>"用了大模型是不是就算 Agent？"</td><td>能否区分"调用 LLM"与"自主循环"</td><td>答"是"，或含糊带过</td><td>否。缺了自主决策与多步循环，只是一次带 LLM 的函数调用</td></tr>
            <tr><td>"是不是自主性越高越好？"</td><td>是否理解成本与风险</td><td>答"当然，越自主越智能"</td><td>否。自主性要匹配任务风险，过度自主是成本与不可控之源</td></tr>
            <tr><td>"这个需求你会怎么做 Agent？"（其实用 workflow 就够）</td><td>是否有"先判断要不要 Agent"的意识</td><td>直接开始堆多 Agent 架构</td><td>先评估：路径确定就用 workflow，只有需动态决策才上 Agent</td></tr>
            <tr><td>"多 Agent 是不是比单 Agent 强？"</td><td>是否盲目追新架构</td><td>答"多 Agent 更先进"</td><td>不一定。多 Agent 引入协调与通信开销，多数场景单 Agent 加好工具更优</td></tr>
            <tr><td>"Agent 能不能完全取代人？"</td><td>对能力边界的清醒认知</td><td>过度承诺"很快就能"</td><td>看任务风险与可逆性；高风险不可逆动作仍需 human-in-the-loop</td></tr>
          </tbody>
        </table>
      </div>
      <p class="cjk">这些陷阱题有一个共同的"解法内核"：<mark class="key2">面试官想看的不是你会不会用 Agent，而是你知不知道 Agent 的边界</mark>。凡是把话说得越满、越"什么都能做"的回答，越暴露经验不足；反而是能主动指出"这里不该用 Agent""这里要加护栏"的回答，最能体现工程成熟度。</p>

      <h3>面试追问链</h3>
      <p class="cjk">这一章的知识点在面试中往往以"层层深入"的方式被追问，提前演练这条链路能让你从容不迫：</p>
      <ul class="hub-list">
        <li><strong>Q1：</strong>什么是 Agent？→ 从"目标导向 + 自主决策 + 多步循环"三特征切入。</li>
        <li><strong>Q2：</strong>它和普通 LLM 应用有什么区别？→ 引出感知-决策-行动循环，强调"自主"与"循环"。</li>
        <li><strong>Q3：</strong>那什么时候<em>不</em>该用 Agent？→ 抛出 Workflow vs Agent 判断框架与 80/20 经验。</li>
        <li><strong>Q4：</strong>如果非要用，你怎么控制它的风险？→ 引出自主性光谱、human-in-the-loop、MAX_STEPS 与终止条件。</li>
        <li><strong>Q5：</strong>给我画一下最小 Agent 的结构。→ 默写"带工具的 while 循环"伪代码，收尾。</li>
      </ul>

      <div class="callout tip">
        <span class="label">本章小结</span>
        <span class="cjk">Agent 的本质是一个"以目标为导向、能自主决策、在感知-决策-行动循环中调用工具并自我修正"的执行体。它与 LLM 的分界线在于"自主"与"循环"，与 Workflow 的分界线在于"运行时动态决策"。工程实践的第一性原则是：<strong>先判断需不需要 Agent，再判断需要几级自主</strong>——克制，往往比堆架构更能体现成熟度。掌握形式化循环、自主性分级和最小心智模型这三件"思维武器"，你就为后续所有章节打下了稳固的地基。</span>
      </div>
