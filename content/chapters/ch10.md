      <h3>朴素 RAG 的局限：为什么"先检索再生成"不够用</h3>
      <p class="cjk">朴素 RAG（Naive RAG）的流程极其朴素：把用户问题向量化 → 在向量库里做一次 Top-K 相似度检索 → 把命中的片段拼进提示词 → 让模型生成答案。它在"问题和答案都直白、知识库干净"的场景里够用，但一旦进入真实业务，一连串结构性缺陷就会暴露：</p>
      <ul class="hub-list">
        <li><strong>单次检索的赌注</strong>：只检索一次，检索质量就成了整个系统的天花板。第一次没搜到，后面生成得再好也是"基于错误前提的胡编"。</li>
        <li><strong>查询与文档的语义鸿沟</strong>：用户问"这药孕妇能吃吗"，文档里写的是"妊娠期用药禁忌"。用户的口语查询和专业文档的措辞常常对不上，纯语义检索也未必能跨越这道鸿沟。</li>
        <li><strong>缺乏多跳推理能力</strong>：面对"A 公司 CEO 的母校在哪个城市"这类需要串联多个事实的问题，一次检索拿不全所有中间事实，朴素 RAG 束手无策。</li>
        <li><strong>无关问题也强行检索</strong>：用户只是打了句招呼，朴素管线照样跑一遍检索，既浪费算力，又可能把无关片段塞进上下文干扰生成。</li>
        <li><strong>检索到垃圾也照单全收</strong>：它没有"这批结果不够好，我该换个问法重搜"的判断力，检索器返回什么就用什么。</li>
      </ul>
      <p class="cjk">这些局限的根子在于：<mark class="key2">朴素 RAG 把检索当成一条写死的管线，而不是一个可以被判断、被调整、被重复的决策过程</mark>。Agentic RAG 的全部改进，都是围绕"把检索从固定管线升级为 Agent 的自主行为"这一核心思想展开的——这也正好呼应了本手册反复强调的 Workflow 与 Agent 之别。</p>
      <div class="callout warn">
        <span class="label">常见误区</span>
        <span class="cjk">① <strong>"RAG 就是把文档塞进提示词"</strong>——塞进去只是最后一步，检索质量才是决定成败的关键，"garbage in, garbage out"。② <strong>"上下文窗口够大就不需要 RAG"</strong>——长上下文缓解了容量问题，但没解决"从海量知识里精准定位"和"成本/延迟"问题，检索依然必要。③ <strong>"提高 Top-K 就能提召回"</strong>——K 越大噪声越多，可能反而稀释关键信息、增加成本，需靠重排而非一味加量。</span>
      </div>

      <h3>检索即工具：Agentic RAG 的核心思想</h3>
      <p class="cjk">Agentic RAG 的第一性原理，是把"检索"从管线里的固定一步，改造成 Agent 工具箱里的<strong>一个可调用的工具</strong>。这个视角的转变带来一连串能力跃迁：</p>
      <ul class="hub-list">
        <li><strong>按需检索</strong>：Agent 先判断"这个问题我需不需要查外部知识"。寒暄、常识、可直接回答的，就不检索——省成本、降延迟、减噪声。</li>
        <li><strong>多次检索</strong>：一次不够就搜第二次、第三次，每次带着上一次的结果调整查询，天然支持多跳问题。</li>
        <li><strong>多源检索</strong>：可以同时拥有"内部知识库检索""网页搜索""数据库查询"多个工具，由 Agent 判断该用哪个。</li>
        <li><strong>自我评估</strong>：拿到结果后先自评"够不够回答"，不够就改写查询重搜——这就是下文 self-RAG 的雏形。</li>
      </ul>
      <p class="cjk">下面这段用 smolagents 实现的例子，正是把检索封装成 <code>@tool</code>，交给 Agent 自主编排的最小范式：</p>

      <div class="code-label">Python · 用 smolagents 做 Agentic RAG（检索即工具）</div>
      <pre><code><span class="kw">from</span> smolagents <span class="kw">import</span> tool, CodeAgent, InferenceClientModel

<span class="kw">@tool</span>
<span class="kw">def</span> <span class="fn">retrieve_docs</span>(query: str, k: int = 3) -> str:
    <span class="st">"""从内部知识库检索与 query 最相关的 k 段文本。

    Args:
        query: 检索查询语句
        k: 返回片段数量
    """</span>
    hits = vector_store.similarity_search(query, k=k)   <span class="cm"># 你的向量库</span>
    <span class="kw">return</span> <span class="st">"\n\n"</span>.join(h.page_content <span class="kw">for</span> h <span class="kw">in</span> hits)

<span class="cm"># Agent 会自主判断何时检索、如何改写查询、要不要多轮检索</span>
agent = CodeAgent(tools=[retrieve_docs], model=InferenceClientModel())
agent.run(<span class="st">"根据公司报销制度，出差高铁票能否全额报销？依据是哪条？"</span>)</code></pre>
      <p class="cjk">这段代码看似简单，藏着 Agentic RAG 的两处关键设计：其一，工具的 <strong>docstring 就是给模型看的说明书</strong>——"从内部知识库检索与 query 最相关的 k 段文本"以及参数注释，会被框架提取成工具描述，模型据此判断"何时、以什么 query、取几段"来调用它，所以描述必须写清楚（工具描述的重要性见第 6 章）。其二，<code>query</code> 和 <code>k</code> 都是<strong>模型运行时自己决定的参数</strong>，而非写死——这正是"检索即工具"与朴素管线的分水岭：Agent 可以第一次用宽泛的 query 探路，发现不够再用更精确的 query 补搜，甚至调大 <code>k</code>。回到示例问题"高铁票能否全额报销、依据哪条"，一个好的 Agent 会先检索"差旅报销 高铁"，若发现命中片段只讲了额度没讲凭证，它会再搜一次"报销 凭证 要求"，最后综合作答并标注依据条款——整个多轮检索的决策，都由模型在循环中自主完成。</p>

      <h3>查询改写：跨越"问法"与"写法"的鸿沟</h3>
      <p class="cjk">检索失败的头号原因，是用户的问法和文档的写法对不上。查询改写（query rewriting / transformation）就是在检索前对原始查询做一层加工，让它更容易命中。几种主流手法各有适用场景：</p>
      <div class="table-wrap">
        <table>
          <thead>
            <tr><th>手法</th><th>做法</th><th>解决的问题</th></tr>
          </thead>
          <tbody>
            <tr><td>查询扩展/改写</td><td>让 LLM 把口语问题改写成更规范、含同义词的检索式</td><td>问法与文档措辞不一致</td></tr>
            <tr><td>多查询生成</td><td>由一个问题生成多个不同角度的查询并分别检索、合并去重</td><td>单一查询召回面窄</td></tr>
            <tr><td>子问题分解</td><td>把复杂问题拆成若干子问题，分别检索再汇总</td><td>多跳、复合型问题</td></tr>
            <tr><td>HyDE（假设性文档）</td><td>先让 LLM 生成一段"假想答案"，再用它去检索</td><td>问题短、信息量小，难匹配长文档</td></tr>
            <tr><td>回退式提问</td><td>先问一个更宽泛的背景问题，补足上下文再检索细节</td><td>问题过于具体、缺乏背景锚点</td></tr>
          </tbody>
        </table>
      </div>
      <p class="cjk">在 Agentic RAG 里，查询改写不必写成固定的预处理步骤，而可以<strong>内化为 Agent 的自主行为</strong>：Agent 第一次检索效果不好，就自己换个措辞、拆个子问题重搜。<mark class="key">HyDE 的思路尤其巧妙——它把"query 与 doc 的匹配"转化为"doc 与 doc 的匹配"</mark>：假设性答案虽然可能有事实错误，但在向量空间里往往比原始短查询更接近真实文档，从而提升召回。</p>

      <h3>Self-RAG 与反思：让 Agent 自评检索质量</h3>
      <p class="cjk">Self-RAG（自我反思式 RAG）的核心，是给检索-生成过程加上一层<strong>自我批判（self-critique）</strong>。它让模型在关键节点自问自答：这个问题需要检索吗？检索回来的片段和问题相关吗？我生成的答案有没有被这些片段支撑（还是我在编）？根据这些"反思"信号，系统再决定是重新检索、换查询，还是放心作答。这套思路把第 3 章的"反思模式（Reflection）"具体落到了 RAG 场景。</p>
      <figure class="diagram">
        <pre class="mermaid">
flowchart TD
    Q[用户问题] --> N{需要检索?}
    N -->|否| GEN[直接生成]
    N -->|是| R[检索片段]
    R --> REL{片段相关?}
    REL -->|否| RW[改写查询] --> R
    REL -->|是| G[生成带引用的答案]
    G --> SUP{答案被片段支撑?}
    SUP -->|否, 疑似幻觉| RW
    SUP -->|是| OUT[输出 + 引用]

      </figure>
      <p class="cjk">这三道关口对应三类反思信号：<strong>是否检索</strong>（避免无谓检索）、<strong>相关性</strong>（过滤噪声片段）、<strong>支撑度/事实性</strong>（防止答案脱离证据）。落地时可用轻量分类器或让主模型输出结构化的自评字段来实现。它的代价是<strong>更多的模型调用与延迟</strong>，所以要在"质量"与"成本"间权衡：高风险问答（医疗、法务、金融）值得开启完整反思，低风险闲聊则不必。</p>
      <div class="callout tip">
        <span class="label">面试高分答法</span>
        <span class="cjk">被问"怎么让 RAG 更可靠"，别只说"加个重排"。把 self-RAG 的三道关口讲出来——<strong>要不要检索、检索得准不准、答案有没有据可依</strong>——并点明它本质是"用额外的推理成本换取更高的事实性"，这种"讲清楚取舍"的答法最能打动面试官。</span>
      </div>

      <h3>chunk 切分：RAG 里最被低估的一环</h3>
      <p class="cjk">"检索质量差"的问题，很多时候根子不在检索算法，而在<strong>切分（chunking）</strong>——如果一个知识点被切成了两半，或者一个 chunk 里塞了五个不相关主题，再好的检索器也无能为力。切分策略的选择直接决定了检索的粒度与语义完整性：</p>
      <div class="table-wrap">
        <table>
          <thead>
            <tr><th>切分策略</th><th>特点</th><th>适用</th></tr>
          </thead>
          <tbody>
            <tr><td>固定长度 + 重叠</td><td>按字符/token 定长切，相邻块留 overlap 防止切断语义</td><td>通用基线，简单可靠</td></tr>
            <tr><td>按结构切分</td><td>顺着标题、段落、列表等文档结构切</td><td>结构清晰的文档（手册、Wiki）</td></tr>
            <tr><td>语义切分</td><td>用句向量检测语义边界，在话题切换处断开</td><td>叙述连贯、无明显结构的长文</td></tr>
            <tr><td>父子/多粒度</td><td>用小块检索、用其所属大块喂给生成（small-to-big）</td><td>需要精确命中又要足够上下文</td></tr>
          </tbody>
        </table>
      </div>
      <p class="cjk">切分要在两股张力间找平衡：<strong>块太小</strong>，检索精准但上下文不完整，模型看不全就容易答偏；<strong>块太大</strong>，语义被稀释、噪声混入、还浪费上下文预算。两个实用技巧：一是<strong>重叠（overlap）</strong>，让相邻块共享一段边界文本，避免关键句正好被切断；二是<strong>父子块（small-to-big）</strong>，检索时用语义聚焦的小块提高命中率，喂给模型时替换成它所在的大块以补全上下文——这是工程上性价比很高的做法。此外，给每个 chunk 附上<strong>元数据</strong>（来源、标题、章节、时间），能支撑过滤检索与引用溯源。</p>

      <h3>混合检索：稠密与稀疏各补所短</h3>
      <p class="cjk">检索器主要分两类，各有盲区，合起来才完整：</p>
      <ul class="hub-list">
        <li><strong>稠密检索（dense / 向量检索）</strong>：把文本编码成向量，靠语义相似度匹配。擅长"意思相近但用词不同"，但对<strong>精确的专有名词、编号、罕见词</strong>不敏感——"ORD-2024-517"这种字符串它可能匹配得很糊。</li>
        <li><strong>稀疏检索（sparse / 关键词，如 BM25）</strong>：基于词频匹配，擅长<strong>精确关键词、术语、代码、编号</strong>，但对同义改写和语义无能为力。</li>
      </ul>
      <p class="cjk"><mark class="key2">混合检索（hybrid search）就是让两者并行检索，再把结果融合</mark>。融合的常用做法是 RRF（Reciprocal Rank Fusion，倒数排名融合）：不依赖两个检索器分数的绝对量纲，而是按各自的排名位次做加权合并，稳健且实现简单。实践中，混合检索几乎总是优于单一检索——语义召回负责"意思对得上"，关键词召回负责"术语不漏掉"，两条腿走路才稳。</p>
      <p class="cjk">稠密检索这一侧还有个绕不开的选择：<strong>嵌入模型（embedding model）</strong>。它决定了"语义相似"到底怎么算，直接框定了检索质量的上限。选型时要权衡几个维度：<strong>是否支持中文/多语言</strong>（跨语言检索需要多语模型）、<strong>向量维度</strong>（维度高表达力强但存储与计算更贵）、<strong>领域适配</strong>（通用模型在医疗、法律等专业语料上可能水土不服，必要时做领域微调）、<strong>最大输入长度</strong>（与 chunk 大小要匹配，否则长块会被截断）。一个容易被忽视但很关键的原则是：<mark class="key">建库（索引）与查询必须用同一个嵌入模型</mark>——换了模型就得重建整个索引，否则查询向量和文档向量根本不在同一个语义空间里，检索结果会一塌糊涂。向量存进向量数据库后，近似最近邻（ANN）索引（如 HNSW）负责在海量向量里快速找相似，它用少量精度换取数量级的速度提升，是检索能否规模化的工程基础。</p>

      <h3>重排：用精排模型把好钢用在刀刃上</h3>
      <p class="cjk">检索（召回）追求的是"别漏"，所以会取回几十上百个候选；但塞进上下文的名额有限，还得追求"够准"。这中间就需要<strong>重排（rerank）</strong>：用一个更强、更慢的模型对召回结果做精细打分，选出最相关的少数几条。</p>
      <p class="cjk">关键在于理解<strong>双编码器与交叉编码器的分工</strong>：召回阶段用<strong>双编码器（bi-encoder）</strong>——问题和文档分别独立编码成向量，可离线预计算、检索极快，但精度有限；重排阶段用<strong>交叉编码器（cross-encoder）</strong>——把"问题 + 文档"拼在一起送进模型联合打分，能捕捉细粒度的相关性，精度高但慢，只能用于少量候选。<mark class="key">这就是经典的"召回—精排"两段式架构：先用快而糙的召回海选，再用慢而精的重排决赛</mark>。它用很小的额外延迟，换来了送进生成环节的上下文质量的显著提升，是提升 RAG 效果性价比最高的一步之一。</p>
      <div class="callout warn">
        <span class="label">常见误区与反模式</span>
        <span class="cjk">① <strong>只召回不重排</strong>——直接把 Top-K 向量检索结果喂给模型，噪声片段会挤占名额、稀释关键信息。② <strong>重排候选集过大</strong>——交叉编码器很慢，对上百条全部重排会拖垮延迟，通常先召回几十条再重排。③ <strong>混淆召回与精排的目标</strong>——召回优化的是"覆盖率/召回率"，精排优化的是"顺序/精确率"，两者指标和模型都不同，不能一把梭。④ <strong>忽视元数据过滤</strong>——先按时间、权限、来源过滤，再做语义检索，能同时提质量和保安全。</span>
      </div>

      <h3>RAG 评估：不能优化你无法度量的东西</h3>
      <p class="cjk">RAG 系统由检索和生成两段串联，评估也要<strong>分段做</strong>，否则无法定位到底是哪段拖了后腿。这套评估语言是面试里体现"工程严谨性"的高地：</p>
      <div class="table-wrap">
        <table>
          <thead>
            <tr><th>评估对象</th><th>关注维度</th><th>常见指标/方法</th></tr>
          </thead>
          <tbody>
            <tr><td>检索段</td><td>该找的有没有找到、找回的有没有用</td><td>命中率/召回率、上下文精确率、上下文相关性</td></tr>
            <tr><td>生成段</td><td>答案是否忠于证据、是否答到点上</td><td>忠实度（faithfulness）、答案相关性</td></tr>
            <tr><td>端到端</td><td>用户视角的整体质量</td><td>人工评分、A/B 测试、线上反馈信号</td></tr>
          </tbody>
        </table>
      </div>
      <p class="cjk">这里最值得强调的两个指标是<strong>上下文相关性</strong>（检索回来的片段与问题相不相关，衡量检索段）和<strong>忠实度</strong>（答案是否完全由检索到的片段支撑、有没有超纲编造，衡量生成段）。二者一拆，就能回答"到底是没搜到，还是搜到了但模型没用好"这个诊断性问题。评估手段上，可用"LLM-as-a-judge"（让另一个模型按标准打分）做规模化的离线评估，但要警惕它自身的偏差，关键结论仍需人工抽检校准。<mark class="key2">评估的价值不在追求某个漂亮的绝对分数，而在于建立一个能持续观察"改动是让系统变好还是变坏"的度量回路</mark>。</p>
      <p class="cjk">实操中最难的往往不是选指标，而是<strong>怎么低成本地搭起一个评估集</strong>。一个可行的冷启动路径：先从真实业务问题里挑几十条有代表性的、覆盖不同难度与主题，人工标注"标准答案 + 应命中的证据片段"；再用 LLM 基于知识库批量"反向生成"问答对扩充规模，人工抽检去噪。有了这套评估集，任何一次改动（换嵌入模型、调 chunk 大小、加重排）都能跑一遍看指标涨跌，把"拍脑袋调参"变成"数据驱动迭代"。上线后还要闭合<strong>在线反馈回路</strong>：收集用户的点赞点踩、追问率、复制率等隐式信号，与离线指标互相印证——离线指标保证不退步，在线信号反映真实体验。</p>

      <h3>防幻觉：让 RAG 答之有据</h3>
      <p class="cjk">RAG 的初衷之一就是用外部证据压制幻觉，但用不好反而会产生"看起来有据、实则张冠李戴"的更隐蔽的幻觉。系统性的防护要多管齐下：</p>
      <ul class="hub-list">
        <li><strong>强制引用来源</strong>：要求模型对每个关键论断标注它引用的片段编号，让答案可溯源、可核查。答案里指不出出处的论断，就是高危幻觉。</li>
        <li><strong>"答不出就说不知道"</strong>：在提示词里明确授权模型"检索内容不足以回答时，应如实说明而非编造"，这条约束能显著减少硬编。</li>
        <li><strong>忠实度校验</strong>：生成后再跑一道 self-RAG 式的支撑度检查，发现答案与证据不符就重生成或降级。</li>
        <li><strong>约束生成范围</strong>：通过提示与结构化输出，把模型的发挥限制在"基于给定上下文"，减少它调用参数化知识"自由发挥"。</li>
      </ul>
      <p class="cjk">要点在于承认一个事实：<strong>RAG 降低幻觉但不能消灭幻觉</strong>。检索错了、片段有歧义、模型误读证据，都会导致"有据的错误"。因此高风险场景必须叠加引用溯源与人工复核，把"可核查"作为设计目标，而不是盲信模型的自信。</p>
      <div class="callout warn">
        <span class="label">常见误区</span>
        <span class="cjk">① <strong>"有引用就等于正确"</strong>——模型可能引用了片段却曲解了它，甚至标注了不相关的来源号，引用要能被抽检验证而非只做样子。② <strong>把参数化知识和检索知识混着用</strong>——模型用自己"记得"的旧知识补充检索内容，看似流畅实则可能过时或错误，高风险场景应明确要求"只依据给定上下文"。③ <strong>用"我不确定"当万能挡箭牌</strong>——过度保守、动辄拒答会摧毁可用性，诚实兜底要和"尽力答"平衡，可通过检索置信度分级来控制。</span>
      </div>

      <h3>GraphRAG：当关系比相似度更重要</h3>
      <p class="cjk">向量 RAG 擅长"找相似的片段"，但不擅长"沿着实体间的关系做推理"。<strong>GraphRAG（图 RAG）</strong>的思路是先从语料里抽取<strong>知识图谱</strong>（实体作为节点、关系作为边），检索时不只找相似片段，还能沿着图上的关系游走、聚合，从而回答那些需要<strong>全局视角或多跳关系</strong>的问题。</p>
      <div class="table-wrap">
        <table>
          <thead>
            <tr><th>问题类型</th><th>向量 RAG</th><th>GraphRAG</th></tr>
          </thead>
          <tbody>
            <tr><td>"文档里怎么说 X 的"（局部事实）</td><td><span class="tag">✔ 擅长</span></td><td>可</td></tr>
            <tr><td>"A 和 B through C 有什么关联"（多跳关系）</td><td>弱</td><td><span class="tag">✔ 擅长</span></td></tr>
            <tr><td>"整篇资料的主题脉络是什么"（全局摘要）</td><td>弱</td><td><span class="tag">✔ 擅长</span></td></tr>
            <tr><td>构建与维护成本</td><td><span class="tag">低</span></td><td><span class="tag amber">高（需抽取图谱）</span></td></tr>
          </tbody>
        </table>
      </div>
      <p class="cjk">GraphRAG 的强项是<strong>多跳关系推理</strong>与<strong>全局性问题</strong>（如"总结这批文档反映的主要矛盾"），但代价也很实在：<mark class="key">构建和维护知识图谱的成本高、抽取本身也可能引入错误</mark>。因此它不是向量 RAG 的替代品，而是补充——在"关系密集、需要全局洞察"的场景（如尽调、情报分析、复杂知识库）才值得投入。面试里能说清"GraphRAG 解决的是向量检索的关系盲区，但要为它更高的构建成本负责"，就说明你理解了技术选型的边界。</p>

      <h3 id="rag-endtoend">动手：从零写一个能跑通的 RAG 问答（完整代码）</h3>
      <p class="cjk">前面把每个环节的原理讲透了，但面试官和真实项目最终都会问同一句话：<mark class="key">"那你把它跑起来给我看看。"</mark> 这一节就把上文所有零件——<strong>切分 → 向量化 → 混合检索（向量 + BM25 + RRF 融合）→ 重排 → 带引用生成 → 忠实度自检</strong>——拼成一份可以直接复制运行的最小系统。它刻意不依赖任何重型框架和向量数据库，只用 <code>numpy</code> 手算余弦相似度，这样你能看清每一步到底发生了什么；理解之后，把检索层换成 Qdrant / Chroma 只是"换实现不换思路"。</p>
      <div class="callout tip">
        <span class="label">先装依赖（一次即可）</span>
        <span class="cjk">这份示例依赖三个轻量库：<code>pip install sentence-transformers rank-bm25 numpy</code>。生成环节用任意 OpenAI 兼容接口，通过 <code>LLM_BASE_URL</code> 与 <code>OPENAI_API_KEY</code> 环境变量注入连接信息（本地 Ollama、vLLM 也兼容），不要把密钥写进代码。嵌入与重排都用开源模型，首次运行会自动下载权重，之后离线可跑。</span>
      </div>

      <p class="cjk"><strong>第 0 步 · 准备知识库并切分。</strong>真实项目里文档来自 PDF、网页、Wiki；这里为了可运行，直接用几段内置文本代替。关键是切分函数——按段落聚合、带重叠、每个 chunk 保留来源元数据，这正是上文"chunk 是最被低估的一环"的落地：</p>
      <div class="code-label">Python · 第 0 步：文档切分（带重叠 + 元数据）</div>
      <pre><code><span class="kw">from</span> dataclasses <span class="kw">import</span> dataclass, field

<span class="kw">@dataclass</span>
<span class="kw">class</span> <span class="fn">Chunk</span>:
    id: int
    text: str
    source: str                      <span class="cm"># 来源文件/URL，用于最终引用溯源</span>

<span class="cm"># 真实场景：用 pypdf / trafilatura 抽取原文，这里用内置语料代替</span>
KNOWLEDGE = {
    <span class="st">"报销制度.md"</span>: <span class="st">"""员工因公出差产生的城市间交通费，凭正式票据实报实销。
高铁票、动车票支持全额报销，需上传票根或电子行程单作为凭证。
出租车、网约车费用单次上限 100 元，超出部分需部门经理审批。
餐补按出差天数计算，每人每天 80 元，无需提供发票。"""</span>,
    <span class="st">"请假制度.md"</span>: <span class="st">"""年假天数依据入职年限计算，满 1 年 5 天，满 10 年 10 天。
病假需提供三甲医院证明，单次超过 3 天由 HR 备案。
调休需在事发后 5 个工作日内在系统提交，逾期作废。"""</span>,
}

<span class="kw">def</span> <span class="fn">chunk_documents</span>(knowledge, size=120, overlap=30):
    <span class="st">"""按字符定长切分并保留重叠，避免关键句被切断。"""</span>
    chunks, cid = [], 0
    <span class="kw">for</span> source, doc <span class="kw">in</span> knowledge.items():
        doc = doc.replace(<span class="st">"\n"</span>, <span class="st">""</span>)
        start = 0
        <span class="kw">while</span> start &lt; len(doc):
            piece = doc[start:start + size]
            chunks.append(Chunk(id=cid, text=piece, source=source))
            cid += 1
            start += size - overlap          <span class="cm"># 关键：步长 = 块长 - 重叠</span>
    <span class="kw">return</span> chunks

CHUNKS = <span class="fn">chunk_documents</span>(KNOWLEDGE)
print(<span class="st">f"共切出 {len(CHUNKS)} 个 chunk"</span>)</code></pre>

      <p class="cjk"><strong>第 1 步 · 建两路索引。</strong>稠密索引用句向量（<code>sentence-transformers</code>），稀疏索引用 <code>BM25</code>。牢记上文的铁律：<mark class="key2">建库与查询必须用同一个嵌入模型</mark>，否则查询向量和文档向量不在同一语义空间。这里把嵌入向量提前算好并归一化，检索时点积即余弦相似度：</p>
      <div class="code-label">Python · 第 1 步：稠密（向量）+ 稀疏（BM25）双索引</div>
      <pre><code><span class="kw">import</span> numpy <span class="kw">as</span> np
<span class="kw">from</span> sentence_transformers <span class="kw">import</span> SentenceTransformer
<span class="kw">from</span> rank_bm25 <span class="kw">import</span> BM25Okapi

<span class="cm"># 多语言小模型，中文可用；换模型必须重建索引</span>
embedder = SentenceTransformer(<span class="st">"paraphrase-multilingual-MiniLM-L12-v2"</span>)

<span class="kw">def</span> <span class="fn">l2_normalize</span>(m):
    <span class="kw">return</span> m / (np.linalg.norm(m, axis=1, keepdims=<span class="kw">True</span>) + 1e-9)

<span class="cm"># 稠密索引：预先编码 + 归一化（离线可预计算，这是 bi-encoder 的优势）</span>
DOC_VECS = <span class="fn">l2_normalize</span>(embedder.encode([c.text <span class="kw">for</span> c <span class="kw">in</span> CHUNKS]))

<span class="cm"># 稀疏索引：BM25 需要分好词的语料（中文可用 jieba，这里简化为字符）</span>
bm25 = BM25Okapi([list(c.text) <span class="kw">for</span> c <span class="kw">in</span> CHUNKS])</code></pre>

      <p class="cjk"><strong>第 2 步 · 混合检索 + RRF 融合。</strong>两路各自召回一个排名列表，再用 <strong>RRF（倒数排名融合）</strong>合并——它只看名次不看分数量纲，稳健且实现极简。这段代码就是上文"两条腿走路"那句话的可执行版本：</p>
      <div class="code-label">Python · 第 2 步：混合检索，RRF 融合双路排名</div>
      <pre><code><span class="kw">def</span> <span class="fn">dense_search</span>(query, k=10):
    qv = <span class="fn">l2_normalize</span>(embedder.encode([query]))[0]
    scores = DOC_VECS @ qv                       <span class="cm"># 归一化后点积 = 余弦相似度</span>
    <span class="kw">return</span> list(np.argsort(scores)[::-1][:k])     <span class="cm"># 返回 chunk 下标，按相似度降序</span>

<span class="kw">def</span> <span class="fn">sparse_search</span>(query, k=10):
    scores = bm25.get_scores(list(query))
    <span class="kw">return</span> list(np.argsort(scores)[::-1][:k])

<span class="kw">def</span> <span class="fn">rrf_fuse</span>(rank_lists, k=60):
    <span class="st">"""Reciprocal Rank Fusion：分数 = Σ 1/(k + 名次)。"""</span>
    fused = {}
    <span class="kw">for</span> ranks <span class="kw">in</span> rank_lists:
        <span class="kw">for</span> pos, doc_id <span class="kw">in</span> enumerate(ranks):
            fused[doc_id] = fused.get(doc_id, 0) + 1 / (k + pos)
    <span class="kw">return</span> sorted(fused, key=fused.get, reverse=<span class="kw">True</span>)

<span class="kw">def</span> <span class="fn">hybrid_search</span>(query, k=6):
    dense = <span class="fn">dense_search</span>(query)
    sparse = <span class="fn">sparse_search</span>(query)
    <span class="kw">return</span> [CHUNKS[i] <span class="kw">for</span> i <span class="kw">in</span> <span class="fn">rrf_fuse</span>([dense, sparse])[:k]]</code></pre>

      <p class="cjk"><strong>第 3 步 · 重排（cross-encoder 精排）。</strong>召回追求"别漏"，重排追求"够准"。把召回的少量候选交给交叉编码器，"问题 + 片段"拼在一起联合打分，选出最相关的 top-n 送进生成。这一步用很小的延迟换来上下文质量的显著提升：</p>
      <div class="code-label">Python · 第 3 步：交叉编码器重排，海选转决赛</div>
      <pre><code><span class="kw">from</span> sentence_transformers <span class="kw">import</span> CrossEncoder

reranker = CrossEncoder(<span class="st">"BAAI/bge-reranker-base"</span>)   <span class="cm"># 慢而精，只用于少量候选</span>

<span class="kw">def</span> <span class="fn">rerank</span>(query, candidates, top_n=3):
    pairs = [(query, c.text) <span class="kw">for</span> c <span class="kw">in</span> candidates]
    scores = reranker.predict(pairs)
    ranked = sorted(zip(candidates, scores), key=<span class="kw">lambda</span> x: x[1], reverse=<span class="kw">True</span>)
    <span class="kw">return</span> [c <span class="kw">for</span> c, _ <span class="kw">in</span> ranked[:top_n]]   <span class="cm"># 只留最相关的 top_n 条</span></code></pre>

      <p class="cjk"><strong>第 4 步 · 带引用的生成 + 兜底。</strong>把重排后的片段编号拼进上下文，并在提示词里下两道硬约束：<mark class="key">每个论断必须标注 [编号] 来源；上下文不足以回答时必须说"资料中未提及"而非编造</mark>。这正是防幻觉的前两板斧落到提示层：</p>
      <div class="code-label">Python · 第 4 步：拼上下文 → 带引用生成 → 诚实兜底</div>
      <pre><code><span class="kw">import</span> os
<span class="kw">from</span> openai <span class="kw">import</span> OpenAI
client = OpenAI(
    base_url=os.environ[<span class="st">"LLM_BASE_URL"</span>],
    api_key=os.environ[<span class="st">"OPENAI_API_KEY"</span>],
)

SYSTEM = <span class="st">"""你是严谨的企业知识库助手，必须遵守：
1. 只依据【参考资料】回答，禁止使用你自己记忆里的知识。

        messages=[

    <span class="kw">return</span> resp.choices[0].message.content</code></pre>

      <p class="cjk"><strong>第 5 步 · 忠实度自检（self-RAG 的落地）。</strong>生成完再补一道关：让模型判断"这个答案是否完全被给定片段支撑"。这就是上文 self-RAG 三道关口里的"支撑度"检查——发现疑似幻觉就可以触发重搜或降级，把"可核查"变成流程里的一环而非口号：</p>
      <div class="code-label">Python · 第 5 步：忠实度校验，拦住"有据的幻觉"</div>

      <p class="cjk"><strong>第 6 步 · 组装成完整管线。</strong>把六个零件串起来，就是一条"检索 → 重排 → 生成 → 自检"的可运行 RAG。跑起来问"高铁票能不能全额报销、依据哪条"，它会命中报销制度片段、给出带 [编号] 的答案，并在自检不通过时诚实兜底：</p>
      <div class="code-label">Python · 组装：一条端到端可运行的 RAG 问答</div>

    <span class="kw">return</span> answer

      <p class="cjk"><code>app/rag.py</code> 保留前文 <code>rag_answer(query)</code> 的函数边界，把内存向量召回替换成 Qdrant 查询。离线索引任务须使用同一个 <code>EMBEDDING_MODEL</code> 创建集合，并为每个 point 写入 <code>text</code> 与 <code>source</code> payload；前文的切分代码可直接移到离线任务中。重排、带引用生成和忠实度自检仍在查询链内，因此检索质量与答案可核查性没有因容器化而丢失：</p>
      <div class="code-label">app/rag.py · Qdrant 检索适配与原有 rag_answer 管线</div>
      <pre><code>import os
from dataclasses import dataclass

from openai import OpenAI
from qdrant_client import QdrantClient
from sentence_transformers import CrossEncoder, SentenceTransformer

QDRANT_URL = os.getenv("QDRANT_URL", "http://localhost:6333")
QDRANT_COLLECTION = os.getenv("QDRANT_COLLECTION", "handbook_chunks")
EMBEDDING_MODEL = os.getenv(
    "EMBEDDING_MODEL", "paraphrase-multilingual-MiniLM-L12-v2"
)
LLM_MODEL = os.getenv("LLM_MODEL", "gpt-4o-mini")

qdrant = QdrantClient(url=QDRANT_URL, timeout=5)
embedder = SentenceTransformer(EMBEDDING_MODEL)
reranker = CrossEncoder("BAAI/bge-reranker-base")

llm_options = {}
if os.getenv("LLM_BASE_URL"):
    llm_options["base_url"] = os.environ["LLM_BASE_URL"]
llm = OpenAI(**llm_options)  # 从运行时环境读取 OPENAI_API_KEY


@dataclass
class Chunk:
    id: str
    text: str
    source: str


def check_vector_store() -&gt; None:
    """集合不存在或 Qdrant 不可达时抛出异常。"""
    qdrant.get_collection(QDRANT_COLLECTION)


def retrieve_from_qdrant(query: str, k: int = 6) -&gt; list[Chunk]:
    vector = embedder.encode(query, normalize_embeddings=True).tolist()
    points = qdrant.query_points(
        collection_name=QDRANT_COLLECTION,
        query=vector,
        limit=k,
        with_payload=True,
    ).points
    return [
        Chunk(
            id=str(point.id),
            text=str(point.payload["text"]),
            source=str(point.payload.get("source", "unknown")),
        )
        for point in points
        if point.payload and "text" in point.payload
    ]


def rerank(query: str, candidates: list[Chunk], top_n: int = 3) -&gt; list[Chunk]:
    if not candidates:
        return []
    scores = reranker.predict([(query, chunk.text) for chunk in candidates])
    ranked = sorted(
        zip(candidates, scores), key=lambda item: item[1], reverse=True
    )
    return [chunk for chunk, _ in ranked[:top_n]]


def generate(query: str, chunks: list[Chunk]) -&gt; str:
    if not chunks:
        return "资料中未提及。"
    context = "\n".join(
        f"[{chunk.id}]（来源：{chunk.source}）{chunk.text}" for chunk in chunks
    )
    response = llm.chat.completions.create(
        model=LLM_MODEL,
        temperature=0,
        messages=[
            {
                "role": "system",
                "content": (
                    "只依据参考资料回答；每个关键论断标注 [编号]；"
                    "资料不足时回答“资料中未提及”。"
                ),
            },
            {
                "role": "user",
                "content": f"【参考资料】\n{context}\n\n【问题】{query}",
            },
        ],
    )
    return response.choices[0].message.content or "资料中未提及。"


def faithfulness_check(answer: str, chunks: list[Chunk]) -&gt; bool:
    context = "\n".join(f"[{chunk.id}] {chunk.text}" for chunk in chunks)
    verdict = llm.chat.completions.create(
        model=LLM_MODEL,
        temperature=0,
        messages=[{
            "role": "user",
            "content": (
                f"资料：\n{context}\n\n答案：{answer}\n\n"
                "答案是否完全被资料支撑？只回 SUPPORTED 或 UNSUPPORTED。"
            ),
        }],
    ).choices[0].message.content or ""
    return verdict.strip() == "SUPPORTED"


def rag_answer(query: str) -&gt; str:
    top = rerank(query, retrieve_from_qdrant(query, k=6), top_n=3)
    answer = generate(query, top)
    if top and not faithfulness_check(answer, top):
        return "（自检未通过，已拦截）该问题现有资料无法可靠回答。"
    return answer</code></pre>

      <p class="cjk">FastAPI 用 Pydantic 固定请求和响应结构。模型推理、Qdrant 客户端和 LLM SDK 都是阻塞调用，异步路由不能直接执行它们；<code>run_in_threadpool()</code> 把工作移出事件循环。健康检查真正访问 Qdrant 集合，失败返回 503；查询异常只记录在服务端，对调用方统一返回 500，不暴露连接字符串、密钥或内部堆栈。</p>

class QueryRequest(BaseModel):
    question: str = Field(min_length=1, max_length=2000)

    @field_validator("question")
    @classmethod
    def reject_blank_question(cls, value: str) -&gt; str:
        value = value.strip()
        if not value:
            raise ValueError("question must not be blank")
        return value


class QueryResponse(BaseModel):
    answer: str


@app.get("/healthz", status_code=status.HTTP_200_OK)
async def healthz() -&gt; dict[str, str]:

        await run_in_threadpool(check_vector_store)
    except Exception:

            status_code=status.HTTP_503_SERVICE_UNAVAILABLE,
            detail="vector store unavailable",

      <h3>面试追问链</h3>
      <p class="cjk">RAG 的追问几乎总是沿着"朴素管线 → 每个环节怎么优化 → 怎么保证可靠"的路径层层深入，提前把这条链演练熟：</p>
      <ul class="hub-list">
        <li><strong>Q1：</strong>讲讲 RAG 的基本流程？→ 从"切分 → 向量化 → 检索 → 拼接 → 生成"的朴素管线切入，点出它是最小可用形态。</li>
        <li><strong>Q2：</strong>朴素 RAG 有什么问题？→ 抛出单次检索的赌注、语义鸿沟、多跳无力、无关也检索等结构性缺陷。</li>
        <li><strong>Q3：</strong>那怎么改进？→ 引出"检索即工具"的 Agentic RAG，以及查询改写、混合检索、重排三板斧。</li>
        <li><strong>Q4：</strong>检索质量怎么保证、怎么评估？→ 讲混合检索 + 重排的召回-精排架构，再讲检索段/生成段分段评估（上下文相关性 vs 忠实度）。</li>
        <li><strong>Q5：</strong>怎么防幻觉、让答案可信？→ 收到强制引用、答不出就说不知道、self-RAG 忠实度校验，并承认"RAG 降低但不消灭幻觉"。</li>
        <li><strong>Q6：</strong>如果是多跳关系或全局性问题呢？→ 升华到 GraphRAG，说明它补的是向量检索的关系盲区，但要为构建成本负责。</li>
        <li><strong>Q7：</strong>如何交付和扩容 RAG 服务？→ 用无状态 FastAPI 镜像承载查询，把 Qdrant 作为独立共享向量库并挂持久卷；健康检查控制流量与启动依赖，密钥在运行时注入，运行中还要有超时与重试。Compose 适合单机交付，水平扩容交给生产编排平台，并在入口补鉴权和限流。</li>
      </ul>
