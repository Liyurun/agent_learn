      <h2 class="chap-title"><span class="kicker">23</span>语音与实时交互 Agent：让 Agent 会听会说</h2>
      <p class="cjk">前面二十二章的 Agent 都是"打字聊天"——用户敲一段、Agent 回一段，回合分明、不慌不忙。但真实世界里最自然的交互是<mark class="key">语音</mark>：打电话、语音助手、实时口译、陪练。语音把 Agent 从"文字回合制"推向了"实时全双工"，随之而来的是一整套文字 Agent 从没遇到过的硬骨头——<strong>延迟必须压到人耳能接受的范围、用户随时会打断、听和说要同时进行</strong>。这一章讲清楚做一个"会听会说"的 Agent 到底难在哪、有哪两条主流技术路线、以及 2025 年 8 月正式商用的 OpenAI Realtime API 把哪些复杂度替你扛掉了。这是 2026 年 Agent 落地最热的方向之一，也是面试里越来越常出现的系统设计题。</p>

      <h3>为什么语音 Agent 比文字 Agent 难一个数量级</h3>
      <p class="cjk">把一个文字 Agent 接上语音，绝不是"前面加个语音识别、后面加个语音合成"那么简单。真正的难点在于<mark class="key2">交互范式变了</mark>：文字聊天是"回合制"——你说完、我再说，中间静默无所谓；而人类对话是<strong>全双工（full-duplex）</strong>的——双方可以同时说话、随时插话、用"嗯""对"来实时反馈。要让 Agent 像人一样自然，就得直面三个文字世界不存在的问题：</p>
      <ul class="hub-list">
        <li><strong>延迟是生死线</strong>：文字回答慢一两秒没人在意，但语音对话里超过一秒的沉默就让人以为"断线了"。研究和产品经验普遍把<mark class="key">端到端 700ms 以内</mark>视为"自然对话"的门槛，这逼着整条链路的每一环都必须流式、并行。</li>
        <li><strong>打断（barge-in）是刚需</strong>：用户听 Agent 说了两句发现不对，会直接开口打断。Agent 必须能<strong>一边说一边听</strong>，检测到用户开口就立刻停止播放、丢弃没说完的话、转去听——这就是全双工的核心难点。</li>
        <li><strong>轮次判断（turn-taking）没有回车键</strong>：文字里用户按回车就代表"我说完了"，语音里没有这个信号。Agent 得靠<strong>语音活动检测（VAD）</strong>和<strong>端点判定（endpointing）</strong>去猜"用户是真说完了，还是只是停顿喘口气"——判早了会抢话，判晚了显得反应迟钝。</li>
      </ul>
      <div class="callout warn">
        <span class="label">一个反直觉的事实</span>
        <span class="cjk">语音 Agent 里，最难的往往不是"听懂"和"说出来"这两个 AI 问题，而是<mark class="key2">"什么时候该说、什么时候该闭嘴"这个交互时序问题</mark>。ASR 和 TTS 已经相当成熟，但把打断、静音判定、回声消除、网络抖动这些工程细节调到"像和真人打电话一样顺"，才是产品体验的分水岭。别小看这一点——面试官问你语音 Agent，考的常常正是你对这些"非 AI"难点的认知深度。</span>
      </div>

      <h3>先打个比方：对讲机 vs 打电话</h3>
      <p class="cjk">文字 Agent 和语音 Agent 的差别，就像<mark class="key">对讲机和打电话</mark>的差别。</p>
      <p class="cjk"><strong>文字聊天像用对讲机（半双工）</strong>：你说完得喊一声"完毕"，松开按钮，对方才能说；同一时刻只有一个人能讲，泾渭分明。中间沉默多久都无所谓，反正大家都在等那句"完毕"。前面二十二章的 Agent 全是这种——用户敲回车（相当于喊"完毕"），Agent 才开始答。</p>
      <p class="cjk"><strong>语音对话像打电话（全双工）</strong>：两个人可以同时出声，你讲的时候我能"嗯、对、然后呢"地随时插话，我觉得你讲错了会直接打断你。<mark class="key2">没有"完毕"这个信号</mark>——我得自己判断你是真讲完了，还是只是喘口气。而且线路一卡、沉默超过一秒，你就会紧张地问"喂？还在吗？"。</p>
      <p class="cjk">语音 Agent 的所有难点，都是"从对讲机升级到打电话"逼出来的：没有"完毕"信号 → 要做<strong>轮次判断</strong>；对方随时插话 → 要能<strong>被打断</strong>；沉默超一秒就出戏 → <strong>延迟</strong>是生死线；两人同时出声 → 得<strong>边说边听（全双工）</strong>。把这个"打电话"的画面装进脑子，后面的 VAD、端点判定、打断、延迟预算就全是水到渠成的常识了。</p>

      <h3>两条技术路线：级联式 vs 端到端语音</h3>
      <p class="cjk">造一个语音 Agent，业界有两条主流架构，理解它们的取舍是本章的核心。</p>
      <p class="cjk"><strong>路线一：级联式管线（Cascaded，STT → LLM → TTS）。</strong>这是最经典、最好理解的做法：先用语音识别（ASR/STT）把用户的话转成文字，把文字喂给一个普通的文字 LLM（就是你前面二十二章学的那个 Agent）推理出回答，再用语音合成（TTS）把回答文字念出来。三个模块像流水线一样串起来。它的最大好处是<mark class="key">每一环都透明、可替换、可调试</mark>——你能看到中间的转录文本、能审查 LLM 的推理、能单独换掉任何一个组件，还能在识别文本上做敏感词过滤、合规审计。</p>
      <p class="cjk"><strong>路线二：端到端语音模型（Speech-to-Speech / 全双工大模型）。</strong>直接用一个原生多模态模型"音频进、音频出"，中间不经过文字，比如 OpenAI 的 <code>gpt-realtime</code>、Amazon Nova Sonic。它把"听—想—说"融进一个模型，天然理解语气、停顿、情绪，延迟也更低（少了模块间的来回）。代价是<mark class="key2">它更像一个黑盒</mark>——难以在中间插入自定义逻辑、难以逐段调试、可替换性差。</p>
      <div class="table-wrap">
        <table>
          <thead><tr><th>维度</th><th>级联式 STT→LLM→TTS</th><th>端到端语音（S2S）</th></tr></thead>
          <tbody>
            <tr><td>延迟</td><td>流式下约 300–600ms</td><td>更低，约 200–300ms（少了文字往返）</td></tr>
            <tr><td>可控性</td><td>高：每级可单独替换/调参</td><td>低：单一模型，粒度粗</td></tr>
            <tr><td>可调试/合规</td><td>强：可看转录、审查每一级</td><td>弱：音进音出，难追踪失败</td></tr>
            <tr><td>副语言信息（语气/情绪）</td><td>易丢失（经文字瓶颈）</td><td>原生保留</td></tr>
            <tr><td>成熟度/生态</td><td>成熟，组件丰富可自由搭</td><td>较新，闭源为主</td></tr>
          </tbody>
        </table>
      </div>
      <p class="cjk">延迟数据来自公开对比：级联式在充分流式化后约 300–600ms，端到端约 200–300ms<a class="cite" href="https://livekit.com/blog/sequential-pipeline-architecture-voice-agents" target="_blank" rel="noopener">[来源]</a>；而在可控性、实时上下文注入和可调试性上，级联式明显占优、端到端仍不够成熟<a class="cite" href="https://www.assemblyai.com/blog/speech-to-speech-for-voice-agents" target="_blank" rel="noopener">[来源]</a>。<mark class="key">选型不是"新的一定好"</mark>：需要严格合规、复杂业务逻辑、自定义工具编排的企业场景，级联式的透明可控往往更实用；追求极致自然度和最低延迟的陪伴、闲聊类产品，端到端更有优势。这又是一次全书反复出现的判断——按场景取舍，而非追新。</p>

      <h3>拆解延迟预算：700ms 到底花在哪</h3>
      <p class="cjk">既然延迟是生死线，就得知道时间都去哪了。以级联式为例，一次"用户说完话到 Agent 开口"的延迟，是一串环节的累加：</p>
      <div class="table-wrap">
        <table>
          <thead><tr><th>环节</th><th>典型耗时</th><th>说明</th></tr></thead>
          <tbody>
            <tr><td>VAD 帧判定</td><td>10–50ms</td><td>持续运行，判断"这一帧有没有人声"</td></tr>
            <tr><td>端点判定（用户说完了吗）</td><td>150–300ms</td><td>由静音时长/置信度阈值决定，最容易调错</td></tr>
            <tr><td>STT 出最终文本</td><td>~100ms（流式 p50）</td><td>流式识别边说边出</td></tr>
            <tr><td>LLM 首 token（TTFT）</td><td>数百 ms</td><td>取决于模型与提示长度</td></tr>
            <tr><td>TTS 首个音频块</td><td>~100ms</td><td>流式合成，边生成边播</td></tr>
          </tbody>
        </table>
      </div>
      <p class="cjk">环节耗时的量级参考自公开的语音系统延迟拆解<a class="cite" href="https://github.com/ombharatiya/ai-system-design-guide/blob/main/18-voice-and-audio-agents/01-realtime-voice-agents.md" target="_blank" rel="noopener">[来源]</a>。关键洞察有两个：<mark class="key2">第一，端点判定是最容易被忽视却最影响体验的一环</mark>——静音阈值设太短，用户喘口气就被抢话；设太长，Agent 反应像卡了。第二，<mark class="key">要压总延迟，靠的是"流式 + 并行 + 重叠"，而不是把每一环单独加速</mark>：STT 边听边出、LLM 边想边吐、TTS 边合成边播，让下一环不必等上一环完全结束——理想情况下总延迟趋近于各环节里最慢的那个，而不是所有环节之和。这就是为什么"全流式"是语音 Agent 的第一工程原则。</p>

      <h3>核心组件：VAD、端点判定与打断</h3>
      <p class="cjk">三个词经常被混为一谈，面试里能讲清区别就是加分项：</p>
      <ul class="hub-list">
        <li><strong>VAD（Voice Activity Detection，语音活动检测）</strong>：最底层，只判断"当前这一小段音频里有没有人在说话"，输出"有声/无声"。它是所有上层判断的基础。</li>
        <li><strong>端点判定（Endpointing / Turn Detection）</strong>：在 VAD 之上，判断"用户这一轮是不是说完了"。它不只看静音时长，成熟方案还会结合语义（这句话听起来说完了吗）来降低误判。</li>
        <li><strong>打断（Barge-in）</strong>：当 Agent 正在播放语音时，VAD 检测到用户开口，系统要立刻做三件事——<strong>停止 TTS 播放、清空还没播的音频缓冲、把控制权交回给"听"</strong>。做不好打断，Agent 就会自顾自把话说完，体验瞬间崩塌。</li>
      </ul>
      <div class="callout tip">
        <span class="label">打断为什么难</span>
        <span class="cjk">难点在于<strong>回声</strong>：Agent 自己播放的声音会被麦克风重新收进来，VAD 可能把"Agent 自己的声音"误判成"用户在说话"，触发假打断。所以真实系统要做<mark class="key">回声消除（AEC）</mark>，把扬声器输出从麦克风输入里减掉。这类"信号处理"细节，正是语音 Agent 比文字 Agent 多出来的隐藏工程量——也是为什么大家越来越倾向用托管的 Realtime API，把这些脏活交给平台。</span>
      </div>

      <h3>逐秒走查：一通"外卖催单"电话到底发生了什么</h3>
      <p class="cjk">把上面的组件串起来，我们逐秒回放一通真实场景——用户打电话给外卖店的语音客服催单。你会看到 VAD、端点判定、打断、填充语、工具调用是怎么在毫秒级别配合的：</p>
      <div class="table-wrap">
        <table>
          <thead><tr><th>时间线</th><th>发生了什么</th><th>背后哪个组件在工作</th></tr></thead>
          <tbody>
            <tr><td>0.0s</td><td>用户："喂，我那个订单……"（说到一半停顿了）</td><td>VAD 检测到人声，STT 开始流式转写</td></tr>
            <tr><td>0.8s</td><td>用户停顿 0.3 秒——Agent <strong>忍住没抢话</strong></td><td>端点判定：静音才 0.3s，判"还没说完"，继续听 ✅</td></tr>
            <tr><td>1.1s</td><td>用户续："……到现在还没送到，帮我看看"</td><td>果然没说完，幸亏刚才没抢话</td></tr>
            <tr><td>1.9s</td><td>用户彻底沉默 0.6 秒</td><td>端点判定：超过阈值，判"这轮说完了"，触发回答</td></tr>
            <tr><td>2.1s</td><td>Agent 开口："好的，我马上帮您查一下订单状态。"</td><td>先说<strong>填充语</strong>，同时后台并行发起查单工具调用</td></tr>
            <tr><td>2.1–3.0s</td><td>后台查数据库（约 900ms），用户耳朵里是 Agent 在说填充语，<strong>不觉得卡</strong></td><td>工具调用与话音重叠，用填充语掩盖延迟</td></tr>
            <tr><td>3.2s</td><td>Agent："您的订单显示骑手正在——"</td><td>TTS 流式播放查到的结果</td></tr>
            <tr><td>3.5s</td><td>用户急了，插嘴："那还要多久啊？！"</td><td>VAD 检测到用户开口 → <strong>打断</strong>：立刻停播、清空剩余音频、转去听</td></tr>
            <tr><td>3.6s</td><td>Agent 秒停，改听用户新问题</td><td>回声消除保证没把自己的话误当成用户打断</td></tr>
          </tbody>
        </table>
      </div>
      <p class="cjk">这通电话里，真正决定"像不像真人"的全是<mark class="key">交互时序</mark>：0.8s 那次<strong>忍住没抢话</strong>（端点判定调得好）、2.1s 的<strong>填充语</strong>掩盖了 900ms 查单延迟、3.5s 被<strong>干净利落地打断</strong>。三个细节任何一个没做好，用户都会觉得"这机器人好蠢/好卡/好没礼貌"。<mark class="key2">你看，从头到尾没提"模型多聪明"——语音 Agent 的体验胜负手，几乎全在这些非 AI 的时序工程上</mark>。这也正是面试官追着问的地方。</p>

      <h3>OpenAI Realtime API：把复杂度打包</h3>
      <p class="cjk">2025 年 8 月 28 日，OpenAI 宣布 Realtime API 正式商用（GA），同时发布面向生产级语音 Agent 的语音模型 <code>gpt-realtime</code><a class="cite" href="https://openai.com/index/introducing-the-realtime-api/" target="_blank" rel="noopener">[来源]</a>。它走的是<strong>端到端语音</strong>路线，把上面那些让人头疼的延迟、打断、轮次判断大部分替你处理好，让你能用相对少的代码搭出一个能打电话、能被打断的语音 Agent。几个对工程落地最关键的特性：</p>
      <ul class="hub-list">
        <li><strong>事件驱动的持久连接</strong>：不是一问一答的 HTTP 请求，而是一条长连接，双方通过<mark class="key">事件</mark>沟通——你发送音频流事件，服务端持续推回"用户开始说话""转录更新""音频输出块""被打断"等事件。整个交互是异步、流式的。</li>
        <li><strong>两种传输方式，各有其位</strong>：官方推荐<strong>浏览器/客户端用 WebRTC</strong>（自带抗抖动、回声处理，适合不稳定网络），<strong>服务端到服务端用 WebSocket</strong>（简单直接，网络可控）。选错传输是新手常见坑。</li>
        <li><strong>内置轮次检测与打断</strong>：服务端集成了 VAD 和轮次判定，能自动识别用户说完、并在用户打断时发出中断事件——你不用自己从零写这套时序逻辑。</li>
        <li><strong>生产级能力</strong>：GA 版还带来了 <strong>SIP 电话网络接入</strong>（直接对接呼叫中心/电话）、<strong>可复用提示词</strong>、图像输入与远程 MCP 工具调用等<a class="cite" href="https://openai.com/index/introducing-gpt-realtime/" target="_blank" rel="noopener">[来源]</a>——意味着它已经不只是 demo 玩具，而是能撑起真实语音客服的基础设施。</li>
      </ul>
      <div class="callout warn">
        <span class="label">安全坑：别把长期密钥放进浏览器</span>
        <span class="cjk">浏览器端用 WebRTC 直连时，<mark class="key2">绝不能把你的 OpenAI 长期 API Key 写进前端代码</mark>——那等于把家门钥匙贴在门上。正确姿势是：前端先请求你自己的后端，后端用长期 Key 换一个<strong>短期临时凭证（ephemeral token）</strong>返回给前端，前端拿这个一次性、短时效的 token 去建立 WebRTC 连接。这是所有"客户端直连大模型"场景的通用安全范式，面试常考。</span>
      </div>

      <h3>一个最小骨架：建立会话并处理事件</h3>
      <p class="cjk">下面用服务端 WebSocket 的方式，展示 Realtime API "事件驱动"的心智模型——注意它和普通 <code>chat.completions</code> 的根本不同：你是在<mark class="key">收发一串事件</mark>，而不是发一个请求等一个响应。</p>
      <div class="code-label">Python · Realtime API 事件循环骨架（服务端 WebSocket，示意）</div>
      <pre><code><span class="kw">import</span> asyncio, json, websockets

<span class="kw">async</span> <span class="kw">def</span> <span class="fn">voice_agent</span>():
    url = <span class="st">"wss://api.openai.com/v1/realtime?model=gpt-realtime"</span>
    headers = {<span class="st">"Authorization"</span>: <span class="st">f"Bearer {API_KEY}"</span>}
    <span class="kw">async</span> <span class="kw">with</span> websockets.connect(url, extra_headers=headers) <span class="kw">as</span> ws:
        <span class="cm"># 1) 配置会话：开启服务端 VAD，让它自动判轮次与打断</span>
        <span class="kw">await</span> ws.send(json.dumps({
            <span class="st">"type"</span>: <span class="st">"session.update"</span>,
            <span class="st">"session"</span>: {
                <span class="st">"instructions"</span>: <span class="st">"你是耐心的电话客服，回答简短口语化。"</span>,
                <span class="st">"turn_detection"</span>: {<span class="st">"type"</span>: <span class="st">"server_vad"</span>},  <span class="cm"># 平台代管轮次检测</span>
            },
        }))
        <span class="cm"># 2) 持续接收服务端推回的事件</span>
        <span class="kw">async</span> <span class="kw">for</span> raw <span class="kw">in</span> ws:
            evt = json.loads(raw)
            <span class="kw">if</span> evt[<span class="st">"type"</span>] == <span class="st">"input_audio_buffer.speech_started"</span>:
                stop_playback()                 <span class="cm"># ← 用户开口：立刻停播，实现打断</span>
            <span class="kw">elif</span> evt[<span class="st">"type"</span>] == <span class="st">"response.audio.delta"</span>:
                play_audio_chunk(evt[<span class="st">"delta"</span>])   <span class="cm"># 流式播放音频块</span>
            <span class="kw">elif</span> evt[<span class="st">"type"</span>] == <span class="st">"response.done"</span>:
                <span class="kw">pass</span>                             <span class="cm"># 本轮回答播完</span></code></pre>
      <p class="cjk">这段代码的价值不在于能直接跑，而在于让你看清语音 Agent 的<mark class="key2">异步事件心智模型</mark>：<code>speech_started</code> 事件触发打断、<code>audio.delta</code> 事件驱动流式播放。把这套"事件流"想明白，你面对任何实时语音框架（LiveKit、Pipecat 等）都能快速上手，因为它们本质上都是在管理同一类事件。</p>

      <h3>工程落地的隐藏坑</h3>
      <p class="cjk">语音 Agent 从 demo 到生产，会踩到一堆文字 Agent 从没有的坑：</p>
      <ul class="hub-list">
        <li><strong>成本按时间计费</strong>：语音模型通常按音频时长计费，一通长电话可能比想象中贵得多；要做时长上限、静默挂断策略。</li>
        <li><strong>工具调用会撕裂对话节奏</strong>：当 Agent 需要查数据库（耗时几百毫秒到几秒），用户会听到突兀的沉默。成熟做法是<mark class="key">用"填充语"掩盖延迟</mark>——先说一句"好的，我帮您查一下"，同时后台执行工具调用。</li>
        <li><strong>ASR 错字会毒害下游</strong>：级联式里，识别把"张伟"听成"张薇"，LLM 就基于错误前提回答。关键实体（人名、单号、金额）要设计确认回读机制。</li>
        <li><strong>可观测性更难</strong>：文字对话可以直接看日志，语音要把音频、转录、事件时间线一起记录，才能复盘"为什么它抢话了"。第 5、11 章的追踪思想在这里同样适用，只是维度更多。</li>
      </ul>

      <h3>面试追问链</h3>
      <p class="cjk">语音/实时交互是 2026 年的热门系统设计题，面试官会顺着"你是否真造过"往下问：</p>
      <ul class="hub-list">
        <li><strong>Q1：</strong>级联式和端到端语音怎么选？→ 要合规/可控/复杂逻辑选级联（透明可调试）；要极致自然度/最低延迟选端到端（音进音出、保留语气）。</li>
        <li><strong>Q2：</strong>VAD、端点判定、打断三者什么关系？→ VAD 判有没有人声；端点判定判用户是否说完；打断是 Agent 说话时被用户插话要立刻停播转听。</li>
        <li><strong>Q3：</strong>怎么把端到端延迟压到 700ms 内？→ 全链路流式 + 并行重叠，让总延迟趋近最慢环节而非各环节之和；重点调端点判定阈值。</li>
        <li><strong>Q4：</strong>浏览器直连 Realtime API，Key 怎么办？→ 绝不放前端；后端用长期 Key 换短时效 ephemeral token 下发给前端。</li>
        <li><strong>Q5：</strong>WebRTC 和 WebSocket 什么时候用哪个？→ 浏览器/弱网用 WebRTC（抗抖动、回声处理）；服务端到服务端用 WebSocket（简单可控）。</li>
        <li><strong>Q6：</strong>Agent 查工具时用户听到沉默怎么办？→ 用填充语（"稍等我查一下"）掩盖延迟，同时后台并行执行工具调用。</li>
        <li><strong>Q7：</strong>打断为什么会误触发？→ Agent 自己的声音被麦克风收回，需回声消除（AEC）把扬声器输出从输入里减掉。</li>
      </ul>

      <div class="callout tip">
        <span class="label">本章小结</span>
        <span class="cjk">语音把 Agent 从"文字回合制"推向"实时全双工"，难点不在"听懂/说出来"，而在<mark class="key">延迟（<700ms 才自然）、打断（边说边听）、轮次判断（没有回车键）</mark>这三道交互时序题。两条路线各有取舍：<strong>级联式</strong>（STT→LLM→TTS）透明可控、可调试合规；<strong>端到端语音</strong>延迟更低、保留语气但像黑盒。压延迟靠<strong>全流式+并行重叠</strong>而非单点加速。2025 年 8 月 GA 的 <strong>OpenAI Realtime API</strong>（<code>gpt-realtime</code>）用事件驱动的长连接，把 VAD、轮次检测、打断打包好，浏览器用 WebRTC、服务端用 WebSocket，并记得用<mark class="key2">临时凭证</mark>保护密钥。记住这条主线：<strong>回合制 → 全双工，慢一秒就出戏，工程的胜负手在时序而非模型</strong>。</span>
