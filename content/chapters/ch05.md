      <h2 class="chap-title"><span class="kicker">05</span>记忆系统</h2>
      <p class="cjk">记忆决定了 Agent 能否"跨越单次对话"变得真正有用。没有记忆，每次交互都是失忆的重新开始；有了记忆，Agent 才能记住用户偏好、积累经验、处理长程任务。面试里"如何给 Agent 设计记忆系统"是高频系统设计题，而且极难糊弄——因为它同时考察你对上下文窗口、检索、存储、数据一致性乃至隐私合规的综合理解。<mark class="key">一个只会说"存向量、做检索"的候选人，和一个能讲清"什么该记、什么该忘、冲突了听谁的、多个用户怎么隔离"的候选人，水平立判。</mark></p>

      <div class="callout tip">
        <span class="label">📎 本章对照的开源一手资料（建议边读边开）</span>

      <h3>为什么记忆是 Agent 的命门</h3>
      <p class="cjk">大模型本身是"无状态"的：每一次调用，它只能看到你这一次塞进上下文窗口的内容，调用结束后什么都不记得。这带来两个根本约束。其一是<strong>窗口有限</strong>——即便是号称支持数十万 token 的长上下文模型，把所有历史一股脑塞进去也会带来成本飙升、延迟增加，以及"大海捞针"式的注意力稀释（信息越多，模型越容易忽略中间部分）。其二是<strong>会话易失</strong>——用户关掉对话再回来，Agent 就"失忆"了，无法延续上次的偏好与结论。记忆系统正是为了在"模型无状态"与"任务需要连续性"之间架起桥梁。</p>
      <p class="cjk">从系统视角看，记忆本质是一个<strong>状态外置</strong>问题：把本该无限增长的对话状态，从昂贵、易失、有限的上下文窗口，搬到廉价、持久、可扩展的外部存储里，再在需要时精准地取回一小部分注入上下文。<mark class="key2">记忆工程的全部艺术，就在于"存什么、怎么存、何时取、取多少"这四个动词之间的权衡。</mark>把握住这条主线，后面所有细节都能串起来。</p>

      <h3>短期记忆 vs 长期记忆</h3>
      <div class="table-wrap">
        <table>
          <thead>
            <tr><th>维度</th><th>短期记忆（Short-term）</th><th>长期记忆（Long-term）</th></tr>
          </thead>
          <tbody>
            <tr><td>载体</td><td>上下文窗口内的对话历史、中间结果</td><td>外部存储：向量库 / 键值库 / 数据库</td></tr>
            <tr><td>生命周期</td><td>单次会话（session）</td><td>跨会话持久保留</td></tr>
            <tr><td>容量</td><td>受窗口 token 限制</td><td>理论上无限</td></tr>
            <tr><td>访问方式</td><td>直接在上下文中</td><td>需检索（retrieval）后注入</td></tr>
            <tr><td>典型内容</td><td>当前任务状态、最近几轮对话</td><td>用户画像、历史结论、领域知识</td></tr>
          </tbody>
        </table>
      </div>
      <p class="cjk">这两者不是二选一，而是<strong>分工协作</strong>：短期记忆保证"当前这件事"的连贯，长期记忆保证"跨越时间"的积累。一个常见误解是把长期记忆当成"更大的短期记忆"，于是拼命扩窗口。但扩窗口解决不了持久化问题——会话一断，窗口里的一切照样清零。<mark class="key">长上下文与长期记忆是正交的两件事：前者关乎"这一次能看多少"，后者关乎"下一次还记不记得"。</mark></p>
      <p class="cjk">短期记忆自身也需要工程化管理。当对话轮数变多，历史会撑爆窗口，此时要做<strong>滚动摘要</strong>（把久远的对话压成一句话摘要）、<strong>草稿板（scratchpad）</strong>（把中间推理、工具结果单独存放，只在需要时回看）等技巧。这部分与第 4 章的上下文工程紧密相连——可以把短期记忆理解为"上下文工程在时间维度上的延伸"。</p>

      <h3>长期记忆的三种类型</h3>
      <p class="cjk">借鉴认知科学，主流做法把长期记忆分成三类，回答时能说出这三种会很加分<sup><a href="#cite-6">[6]</a></sup>：</p>
      <ul class="cjk">
        <li><strong>语义记忆（Semantic）</strong>：事实与知识——用户是谁、偏好什么、领域概念。常以"用户画像"或知识库形式存在。</li>
        <li><strong>情景记忆（Episodic）</strong>：过去发生的具体事件与经历——"上次我是怎么解决这个问题的"，常用于 few-shot 示例。</li>
        <li><strong>程序记忆（Procedural）</strong>：如何做事的规则与技能——系统提示词、行为准则，可随反馈迭代更新。</li>
      </ul>
      <p class="cjk">这套分类不是学术噱头，它直接对应<strong>三种不同的存储与使用方式</strong>，理解这点能让你的回答立刻具备工程质感：</p>
      <div class="table-wrap">
        <table>
          <thead>
            <tr><th>类型</th><th>存的是什么</th><th>典型存储</th><th>如何被使用</th><th>更新频率</th></tr>
          </thead>
          <tbody>
            <tr><td>语义记忆</td><td>关于"是什么"的事实</td><td>键值库 / 向量库 / 结构化表</td><td>检索后拼进 system 或 user 消息</td><td>随事实变化增量更新</td></tr>
            <tr><td>情景记忆</td><td>关于"发生过什么"的经历</td><td>向量库（带时间戳）</td><td>作为 few-shot 范例注入</td><td>只追加，很少改写</td></tr>
            <tr><td>程序记忆</td><td>关于"该怎么做"的规则</td><td>提示词模板 / 规则库</td><td>直接写进系统提示</td><td>基于反馈慢速迭代</td></tr>
          </tbody>
        </table>
      </div>
      <p class="cjk">一个有说服力的例子：客服 Agent 里，"该用户是企业版付费客户"是语义记忆；"上次这位用户因为发票问题投诉过、最后靠补开红字发票解决"是情景记忆；"遇到发票类问题先核对开票抬头再走审批流"则是程序记忆。三者叠加，Agent 才既懂"这个人"，又懂"这件事该怎么办"。<mark class="key2">面试时用一个贯穿三类记忆的具体场景来讲，比干背定义有效十倍。</mark></p>

      <h3>记忆的写入时机：热路径 vs 后台</h3>
      <p class="cjk">什么时候把东西写进长期记忆？有两种策略：<strong>在热路径中（in the hot path）</strong>——推理过程中实时判断并写入，实时性好但增加延迟；<strong>在后台（in the background）</strong>——会话结束后异步总结再写入，不影响响应速度但有滞后。生产系统常两者结合。这个取舍点是面试深挖记忆设计时的高质量回答。</p>
      <div class="table-wrap">
        <table>
          <thead>
            <tr><th>维度</th><th>热路径写入</th><th>后台写入</th></tr>
          </thead>
          <tbody>
            <tr><td>时机</td><td>推理过程中同步执行</td><td>会话结束或空闲时异步执行</td></tr>
            <tr><td>延迟影响</td><td>拖慢当前响应</td><td>不影响用户感知延迟</td></tr>
            <tr><td>一致性</td><td>写入即刻可用，同会话立即生效</td><td>存在滞后，可能跨会话才生效</td></tr>
            <tr><td>适用</td><td>关键事实（如"用户过敏原"须立刻生效）</td><td>批量总结、画像更新、去重巩固</td></tr>
          </tbody>
        </table>
      </div>
      <p class="cjk">工程上更稳妥的折中是<strong>"热路径打标 + 后台巩固"</strong>：推理时用极轻量的判断把候选记忆快速标记入队，真正耗算力的抽取、去重、冲突消解交给后台任务批处理。这样既不拖慢响应，又能保证重要信息不丢。<mark class="key">凡是涉及"实时性 vs 成本/延迟"的取舍题，先亮出两端、再给折中方案，几乎是通用的高分答题模板。</mark></p>

      <div class="callout warn">
        <span class="label">别把记忆做成 RAG 的同义词</span>
        <span class="cjk">很多人一提记忆就是"存向量、做检索"。但长期记忆不只是语义检索——它还包括<strong>什么该记、什么该忘、如何更新已有记忆</strong>。一个成熟回答应涵盖：记忆的抽取、去重、冲突消解与遗忘策略，而不只是"塞进向量库再搜出来"。</span>
      </div>

      <h3>记忆生命周期：抽取 → 巩固 → 检索 → 更新 → 遗忘</h3>
      <p class="cjk">把长期记忆当成一个有完整生命周期的系统来设计，才能答出深度。五个环节缺一不可：</p>
      <ul class="hub-list">
        <li><strong>抽取（Extraction）</strong>：从对话中识别值得长期保留的信息。不是所有内容都值得记——闲聊寒暄不该进记忆，"用户对花生过敏"这类事实才该。</li>
        <li><strong>巩固（Consolidation）</strong>：把新信息与已有记忆整合。发现"用户搬到了上海"时，应更新旧的"在北京"记录，而非并列存储导致矛盾。</li>
        <li><strong>检索（Retrieval）</strong>：按当前任务召回相关记忆。可用语义相似度，也可结合时间衰减、重要性加权。</li>
        <li><strong>更新（Update）</strong>：记忆会过时，需要机制去修订而非只增不改。</li>
        <li><strong>遗忘（Forgetting）</strong>：主动淘汰过时、低价值的记忆，防止记忆库无限膨胀、检索噪声增大。</li>
      </ul>
      <p class="cjk">这五个环节最容易被忽略的是<strong>巩固</strong>与<strong>遗忘</strong>——大多数人只做了"抽取 + 检索"这两头，中间的整合与末端的淘汰全部缺席，结果就是记忆库既有矛盾又无限膨胀。可以借一个类比帮助记忆：人脑睡眠时会把白天的短期记忆"巩固"为长期记忆、并淘汰无关细节，Agent 的后台记忆任务扮演的正是这个"睡眠巩固"的角色。<mark class="key">把生命周期讲全，尤其点出巩固与遗忘，是区分"读过教程"与"做过系统"的关键信号。</mark></p>
      <div class="callout tip">
        <span class="label">冲突消解是难点</span>
        <span class="cjk">面试中如果你能主动谈"记忆冲突怎么处理"，会立刻拉开差距。当新旧记忆矛盾时（用户先说喜欢喝咖啡、后说戒了咖啡因），朴素向量库会把两条都检索出来，让模型无所适从。成熟方案要么带时间戳"以最新为准"，要么在写入时就做巩固更新。这正是 Mem0、Zep 这类记忆框架的核心价值。</span>
      </div>

      <h3>向量记忆 vs 结构化记忆：不是二选一</h3>
      <p class="cjk">"记忆用什么存"是系统设计题的必答项。两条主流路线各有擅长，成熟系统往往<strong>并用</strong>：</p>
      <div class="table-wrap">
        <table>
          <thead>
            <tr><th>维度</th><th>向量记忆（Vector）</th><th>结构化记忆（Structured）</th></tr>
          </thead>
          <tbody>
            <tr><td>形态</td><td>文本切片 + 嵌入向量</td><td>键值对 / 关系表 / 知识图谱三元组</td></tr>
            <tr><td>擅长</td><td>语义模糊匹配、开放式召回</td><td>精确查询、聚合统计、多跳推理</td></tr>
            <tr><td>短板</td><td>无法精确过滤、结果不可枚举</td><td>需预定义 schema、难处理自由文本</td></tr>
            <tr><td>典型查询</td><td>"用户提过哪些和旅行相关的偏好"</td><td>"用户的会员等级是什么""同事有几人"</td></tr>
            <tr><td>更新语义</td><td>难以"就地修改"，多为追加</td><td>可 UPDATE / DELETE，天然支持修订</td></tr>
          </tbody>
        </table>
      </div>
      <p class="cjk">一个实用的经验法则：<mark class="key">强事实、需要精确与一致性的记忆（会员等级、账户余额、过敏原）放结构化存储；软性、需要语义联想的记忆（用户口吻偏好、历史经历片段）放向量库。</mark>把"用户住在上海"这种既是事实又可能被语义检索的信息，同时以结构化字段（canonical，用于精确更新）和向量（用于模糊召回）双写，是很多记忆框架的实际做法。这也解释了为什么结构化记忆天然更好做"更新与遗忘"——它支持就地修改，而向量记忆往往只能追加、靠后处理去重。</p>

      <h3>向量检索的局限与混合检索</h3>
      <p class="cjk">纯向量语义检索并非万能。它擅长"意思相近"，却不擅长精确匹配（如订单号、专有名词）和时间/结构化过滤。<mark class="key">生产级记忆系统往往采用混合检索</mark>：向量召回 + 关键词（BM25）召回 + 元数据过滤（时间、用户、类型），再用重排序模型融合。此外，把记忆组织成<strong>知识图谱</strong>（实体 + 关系）能更好地回答"用户的同事都有谁"这类需要多跳推理的问题——这是 GraphRAG 与图记忆的思路。</p>
      <p class="cjk">混合检索之所以有效，是因为不同召回通道的<strong>失败模式互补</strong>：向量召回会漏掉"字面精确但语义不突出"的项（如一个具体订单号），BM25 关键词召回则能兜住它；反过来，用户换了种说法、字面完全不同但意思一致时，向量召回又能补上 BM25 的漏。元数据过滤则负责把"根本不该出现"的记忆（别的用户、过期时间段）在召回前就排除。融合多路结果时常用 <strong>RRF（Reciprocal Rank Fusion，倒数排名融合）</strong>这类无需调参的排名融合法，再交给交叉编码重排序模型做精排。</p>
      <div class="callout warn">
        <span class="label">检索命中 ≠ 记忆有用</span>
        <span class="cjk">很多人只优化"召回率"，却忽略了注入上下文的记忆<strong>数量与质量</strong>。塞太多低相关记忆会稀释注意力、增加成本，甚至把模型带偏（检索到的过时记忆盖过了正确信息）。成熟做法是设一个相关性阈值 + top-k 上限，宁缺毋滥；并且记录"这条记忆被检索出来后有没有真正被用到"，用它反哺重要性打分与遗忘策略。</span>
      </div>

      <h3>记忆的抽取与巩固：一段可落地代码</h3>
      <p class="cjk">把前面讲的"抽取 → 巩固 → 冲突消解"落到代码，能让面试官确信你不是纸上谈兵。下面是一个精简但完整的写入流程骨架，核心思路是：<strong>先让 LLM 从对话里抽出结构化事实，再拿每条事实去向量库找近邻，最后由 LLM 判定这是"新增/更新/无操作/删除"中的哪一种</strong>——这正是 Mem0 一类框架的核心机制。</p>
      <div class="code-label">Python · 记忆写入的抽取-巩固流程</div>
      <pre><code><span class="cm"># 第一步：从最近对话中抽取"值得长期记忆"的结构化事实</span>
<span class="kw">def</span> <span class="fn">extract_memories</span>(messages) -&gt; list[dict]:
    prompt = <span class="st">"从对话中抽取值得长期保留的用户事实，忽略闲聊；"</span> \
             <span class="st">"每条输出 {text, type, entity} 的 JSON 列表。"</span>
    <span class="kw">return</span> llm_json(prompt, messages)  <span class="cm"># type ∈ semantic/episodic/procedural</span>

<span class="cm"># 第二步：对每条候选事实，检索近邻并决定如何巩固</span>
<span class="kw">def</span> <span class="fn">consolidate</span>(fact, store, user_id):
    neighbors = store.search(fact[<span class="st">"text"</span>], user_id=user_id, k=<span class="st">5</span>)
    decision = llm_json(
        <span class="st">"给定新事实与已有相似记忆，判定 ADD / UPDATE / DELETE / NOOP。"</span>,
        {<span class="st">"new"</span>: fact, <span class="st">"existing"</span>: neighbors},
    )
    <span class="kw">if</span> decision[<span class="st">"op"</span>] == <span class="st">"ADD"</span>:
        store.insert(fact, user_id=user_id, ts=now())      <span class="cm"># 全新事实</span>
    <span class="kw">elif</span> decision[<span class="st">"op"</span>] == <span class="st">"UPDATE"</span>:
        store.update(decision[<span class="st">"id"</span>], fact, ts=now())        <span class="cm"># 覆盖旧值，避免矛盾并存</span>
    <span class="kw">elif</span> decision[<span class="st">"op"</span>] == <span class="st">"DELETE"</span>:
        store.soft_delete(decision[<span class="st">"id"</span>])                 <span class="cm"># 用户否定了旧事实</span>
    <span class="cm"># NOOP：信息已存在，什么都不做，天然去重</span></code></pre>
      <p class="cjk">为什么这样写？关键有三点：<strong>①</strong> 抽取与巩固分离，抽取只负责"从噪声里挑信号"，巩固负责"和旧记忆对齐"，职责单一便于调试；<strong>②</strong> 用 <code>UPDATE</code> 而非无脑 <code>ADD</code>，从写入源头消灭"喜欢咖啡"与"戒了咖啡因"并存的矛盾；<strong>③</strong> <code>soft_delete</code>（软删除）而非物理删除，保留审计痕迹，也便于误删回滚。<mark class="key2">冲突消解的最佳时机是写入时而非检索时——写入时处理一次，检索时永远干净。</mark></p>

      <h3>记忆压缩：对抗无限增长</h3>
      <p class="cjk">记忆库会随时间单调增长，若不治理，检索会越来越慢、噪声越来越大、成本越来越高。<strong>记忆压缩</strong>就是用可控的信息损失换取规模可控，常见手段有三层：</p>
      <ul class="hub-list">
        <li><strong>摘要合并</strong>：把同一主题下零散的多条记忆归并成一条更抽象的记忆（"用户多次询问退款流程" → "用户高频关注退款"），降低条数。</li>
        <li><strong>分层记忆</strong>：仿照缓存的多级结构，近期/高频记忆留在"快取"层，久远/低频记忆下沉到"冷存"层甚至归档，检索时优先查热层。</li>
        <li><strong>重要性衰减</strong>：给每条记忆一个随时间衰减、随命中回升的分数，低于阈值的进入遗忘候选。这与短期记忆里的滚动摘要一脉相承，只是作用在更长的时间尺度上。</li>
      </ul>
      <div class="callout warn">
        <span class="label">压缩是把双刃剑</span>
        <span class="cjk">摘要合并会丢失细节：把三次不同投诉压成"多次投诉"，就丢掉了每次的具体缘由。遗忘更危险——删错一条关键事实（比如过敏原），后果可能很严重。原则是：<strong>可逆优先于不可逆</strong>（先降权、归档，再谈物理删除），<strong>高价值事实不参与激进压缩</strong>（用类型或重要性标记豁免）。</span>
      </div>

      <h3>多用户隔离与隐私合规</h3>
      <p class="cjk">一旦记忆系统上线服务真实用户，<strong>隔离</strong>就从"锦上添花"变成"生死线"。最基本也最致命的错误，是把 A 用户的记忆检索给了 B 用户——这不仅是体验问题，更是数据泄露与合规事故。工程上的硬性要求：</p>
      <ul class="hub-list">
        <li><strong>强制命名空间</strong>：每条记忆都带 <code>user_id</code>（乃至 <code>org_id</code>、<code>session_id</code>）作为分区键，检索时把它作为<strong>不可绕过的过滤条件</strong>，而不是排序后再筛——过滤必须发生在召回阶段。</li>
        <li><strong>多租户存储隔离</strong>：SaaS 场景常按租户分库/分集合，防止一次查询错误就跨租户串数据；高敏场景甚至物理隔离。</li>
        <li><strong>可删除与可导出</strong>：满足"被遗忘权"等合规要求，用户要求删除时，必须能连同派生的摘要、向量一并清除，而不只是删原文。</li>
        <li><strong>敏感信息治理</strong>：抽取阶段就识别并脱敏 PII（个人身份信息），避免把身份证号、银行卡号这类信息长期沉淀进记忆库。</li>
      </ul>
      <div class="code-label">Python · 检索必须带上隔离过滤</div>
      <pre><code><span class="cm"># 反例：先全局检索再过滤 —— 有跨用户泄露风险，且浪费算力</span>
<span class="cm"># hits = store.search(query, k=20); hits = [h for h in hits if h.user_id == uid]</span>

<span class="cm"># 正例：把 user_id 作为召回阶段的硬过滤条件</span>
hits = store.search(
    query,
    filter={<span class="st">"user_id"</span>: uid, <span class="st">"deleted"</span>: <span class="kw">False</span>},  <span class="cm"># 隔离 + 排除软删除</span>
    k=<span class="st">8</span>,
)</code></pre>
      <p class="cjk">面试里若被问"多用户场景怎么做记忆"，能主动点出"过滤要发生在召回阶段而非事后筛选"和"被遗忘权要级联删除派生数据"，是很强的加分项——它说明你把记忆当成一个真实的生产数据系统，而不只是一个 demo。</p>

      <h3>记忆系统怎么评估</h3>
      <p class="cjk">很多候选人能讲清怎么"建"记忆，却答不出怎么"评"记忆——而后者恰恰是资深工程师的分水岭：没有度量，就无法判断记忆策略是变好还是变差。评估要分两层看。<strong>检索层</strong>关注"该取回的取回了吗、不该取的排除了吗"，可用召回率、精确率以及命中记忆的实际使用率来衡量；<strong>系统层</strong>关注"记忆最终有没有让任务做得更好"，要用带记忆与不带记忆的对照实验，比较任务成功率、答案一致性和用户满意度。</p>
      <p class="cjk">还有两类容易被忽视却极具杀伤力的失败必须专门盯：其一是<strong>记忆污染</strong>——一条被错误抽取或过时的记忆持续被检索出来，反复把模型带偏，这类问题要靠"记忆可溯源 + 命中审计"来定位；其二是<strong>陈旧读取</strong>——后台写入尚未完成，用户却已发起了依赖新记忆的提问，需要靠热路径打标或读己之写（read-your-writes）一致性来缓解。<mark class="key2">能把记忆当成"需要被持续观测和评估的数据管线"来谈，你的回答就从"会用工具"跃升到了"会做系统"。</mark></p>
