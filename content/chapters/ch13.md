      <h3>第一层 · 概念基础（初面送分，必须全对）</h3>
      <p class="cjk">这一层的题几乎每场必问，答错直接出局、答好只是及格线。诀窍是<strong>用精确的分界线代替模糊的形容词</strong>：不要说"更智能""更强大"，而要说清"多了循环、多了自主决策"。</p>

      <div class="qa">
        <div class="q"><span class="qmark">Q1</span>什么是 AI Agent？它和普通的 LLM 调用有什么区别？<span class="difficulty easy">EASY</span></div>
        <div class="a cjk"><span class="amark">A</span><strong>考点：</strong>能否讲出"Agent"与"带工具的一次模型调用"的本质分界，而不是背定义。<br><strong>高分答法：</strong>Agent 是能<strong>代表用户自主执行工作流</strong>的系统，三大特征——目标导向、自主决策、多步循环（观察→决策→行动直到完成）；普通 LLM 调用是"一问一答"的单次生成，没有循环、不能自主决定下一步。一句话收尾：<mark class="key">能自己判断"信息不够，再搜一次"的才是 Agent。</mark><br><strong>常见扣分点：</strong>把"用了 LLM"或"调用了工具一次"就说成 Agent；只强调"更智能"这类空话。<br><strong>追问：</strong>那固定调用三次模型的管线算 Agent 吗？（答：不算，缺自主决策）（详见第 1 章）</div>
      </div>

      <div class="qa">
        <div class="q"><span class="qmark">Q2</span>一个 Agent 由哪些核心组件构成？<span class="difficulty easy">EASY</span></div>
        <div class="a cjk"><span class="amark">A</span><strong>考点：</strong>是否有清晰的"解剖结构"心智模型，能边说边画。<br><strong>高分答法：</strong>四大件——<strong>推理引擎</strong>（LLM + 规划，负责决策）、<strong>工具使用</strong>（伸向外部世界的手，通过 JSON Schema 声明）、<strong>记忆</strong>（短期上下文 + 长期外部存储）、<strong>通信层</strong>（消息与协议，多 Agent 协作的基础）。最好顺手画出"推理↔工具↔记忆"的核心循环图。<br><strong>常见扣分点：</strong>只说"就是个大模型 + prompt"，忽略记忆与循环；把工具和记忆混为一谈。<br><strong>追问：</strong>这四件里哪个最容易成为瓶颈？（答：记忆/上下文管理，长程任务的命门）（详见第 2 章）</div>
      </div>

      <div class="qa">
        <div class="q"><span class="qmark">Q3</span>ReAct 模式是什么？为什么它这么常用？<span class="difficulty easy">EASY</span></div>
        <div class="a cjk"><span class="amark">A</span><strong>考点：</strong>能否说清 ReAct 的三段循环及其"为什么流行、代价是什么"。<br><strong>高分答法：</strong>ReAct = Reasoning + Acting，把每一步拆成 <strong>Thought → Action → Observation</strong> 的循环：先想该做什么，再调工具，拿到结果后继续想，直到得出答案。它常用是因为<strong>直观、通用、可解释</strong>——几乎所有框架的默认 Agent 都是 ReAct 变体。<br><strong>常见扣分点：</strong>只说"边想边做"却讲不出三段结构；不提缺点（步数多、token 消耗大、易累积错误）。<br><strong>追问：</strong>ReAct 步数太多怎么优化？（答：Plan-and-Execute 先规划再执行、CodeAct 合并动作）（详见第 3 章）</div>
      </div>

      <div class="qa">
        <div class="q"><span class="qmark">Q4</span>什么是 MCP？用一句话向外行解释。<span class="difficulty easy">EASY</span></div>
        <div class="a cjk"><span class="amark">A</span><strong>考点：</strong>能否用一个精准比喻讲清 MCP 解决的"M×N 对接爆炸"问题。<br><strong>高分答法：</strong>MCP（模型上下文协议）是连接 AI 模型与外部工具/数据的<strong>开放标准</strong>，比喻成<mark class="key2">"AI 应用的 USB-C 接口"</mark>最形象。它把过去 M 个模型 × N 个工具的 M×N 定制对接，降为 M+N 的标准化即插即用。核心角色：Host、Client、Server。<br><strong>常见扣分点：</strong>把 MCP 说成"某家公司的私有 SDK"；讲不清它和 Function Calling 的层次差异。<br><strong>追问：</strong>MCP Server 和 Client 分别跑在哪？（答：Server 暴露工具/资源，Client 由 Host 应用发起连接）（详见第 6 章）</div>
      </div>

      <h3>第二层 · 设计与权衡（区分度题，体现判断力）</h3>
      <p class="cjk">这一层不看你会不会名词，看你<strong>会不会做取舍</strong>。面试官想听到"我在什么条件下选 A、什么条件下选 B"，最忌讳"都很好、看情况"这种没有立场的答案。</p>

      <div class="qa">
        <div class="q"><span class="qmark">Q5</span>什么时候该用 Agent，什么时候不该用？<span class="difficulty mid">MEDIUM</span></div>
        <div class="a cjk"><span class="amark">A</span><strong>考点：</strong>工程成熟度——是否会"先评估要不要上 Agent"。<br><strong>高分答法：</strong>核心判断是<strong>任务路径是否确定</strong>。路径确定、可预先编排 → 用 Workflow（更简单、便宜、可靠、好调试，覆盖约 80% 场景）；路径不确定、需要运行时动态决策 → 才用 Agent。主动说 <mark class="key">"我会先评估要不要用 Agent"</mark> 本身就是加分项。反例：固定的"分类→抽取→入库"流程不该做成 Agent。<br><strong>常见扣分点：</strong>无脑推崇 Agent；把"能用 Agent"等同于"该用 Agent"。<br><strong>追问：</strong>Workflow 里也能用 LLM，那界线到底在哪？（答：控制流是否由模型在运行时决定）（详见第 1、7 章）</div>
      </div>

      <div class="qa">
        <div class="q"><span class="qmark">Q6</span>什么是上下文工程？和提示词工程有何不同？<span class="difficulty mid">MEDIUM</span></div>
        <div class="a cjk"><span class="amark">A</span><strong>考点：</strong>是否理解"从写好一句 prompt 升级到管理整个上下文状态"。<br><strong>高分答法：</strong>上下文工程是"在推理每一步，把恰好合适的信息、以恰好合适的格式放进上下文窗口"的手艺，是提示词工程的自然演进——不再只关注单句 prompt，而是管理<strong>整个上下文状态</strong>。核心策略四件套：<strong>Write / Select / Compress / Isolate</strong>；目标是对抗"上下文腐烂"，用尽量小的高信号 token 集合。<br><strong>常见扣分点：</strong>把它等同于"写更长的 prompt"；说不出四件套。<br><strong>追问：</strong>上下文越长越好吗？（答：不是，长上下文会稀释注意力、抬高成本、引发 lost-in-the-middle）（详见第 4 章）</div>
      </div>

      <div class="qa">
        <div class="q"><span class="qmark">Q7</span>如何给 Agent 设计记忆系统？<span class="difficulty mid">MEDIUM</span></div>
        <div class="a cjk"><span class="amark">A</span><strong>考点：</strong>是否把"记忆"理解为一套读写策略，而非"接个向量库"。<br><strong>高分答法：</strong>分两层——<strong>短期记忆</strong>（上下文窗口内，单会话）+ <strong>长期记忆</strong>（外部存储，跨会话）。长期记忆再按认知科学分三类：<strong>语义</strong>（事实/画像）、<strong>情景</strong>（历史事件/few-shot）、<strong>程序</strong>（规则/系统提示）。进阶点：写入时机（热路径 vs 后台异步）、以及记忆的<strong>去重、冲突消解、遗忘</strong>策略。<br><strong>常见扣分点：</strong>把记忆等同于向量检索；只谈"存"不谈"何时写、如何淘汰"。<br><strong>追问：</strong>两条记忆矛盾了怎么办？（答：加时间戳/来源可信度做冲突消解，或以最新覆盖旧的）（详见第 5 章）</div>
      </div>

      <div class="qa">
        <div class="q"><span class="qmark">Q8</span>Multi-Agent 多智能体一定比单 Agent 好吗？<span class="difficulty mid">MEDIUM</span></div>
        <div class="a cjk"><span class="amark">A</span><strong>考点：</strong>能否识别多 Agent 的适用边界与隐藏成本。<br><strong>高分答法：</strong>不是。<mark class="key2">只有当任务真正可并行，或不同子任务需要不同系统提示词/工具集时才用多 Agent</mark>；否则协调开销、上下文同步成本会反噬收益。不要因为"某框架让它变简单"就用。能主动说"多 Agent 不是银弹"比盲目推崇更让人信服。<br><strong>常见扣分点：</strong>认为"拆得越细越专业"；忽略上下文在子 Agent 间传递的损耗。<br><strong>追问：</strong>什么任务最适合并行多 Agent？（答：彼此独立、可分而治之的检索/调研类子任务）（详见第 3 章）</div>
      </div>

      <div class="qa">
        <div class="q"><span class="qmark">Q9</span>传统 RAG 和 Agentic RAG 有什么区别？<span class="difficulty mid">MEDIUM</span></div>
        <div class="a cjk"><span class="amark">A</span><strong>考点：</strong>能否点出"检索从固定管线变成 Agent 手里的工具"这一质变。<br><strong>高分答法：</strong>传统 RAG 是"先检索再生成"的<strong>固定管线</strong>，检索一次、不管好坏都拿去生成；Agentic RAG 把检索变成 <strong>Agent 手里的一个工具</strong>，由它自主决定要不要搜、搜什么、要不要改写查询重搜、多轮检索。后者能自评检索质量（self-RAG 思想），更适合复杂问题。<br><strong>常见扣分点：</strong>只说"Agentic 更强"却讲不出"自主决定检索"这个机制差异。<br><strong>追问：</strong>Agentic RAG 的代价是什么？（答：多轮检索带来延迟与成本上升，需要限轮数）（详见第 10 章）</div>
      </div>

      <div class="qa">
        <div class="q"><span class="qmark">Q10</span>MCP 和 Function Calling 是一回事吗？<span class="difficulty mid">MEDIUM</span></div>
        <div class="a cjk"><span class="amark">A</span><strong>考点：</strong>能否区分"模型层能力"与"应用层协议"两个层次。<br><strong>高分答法：</strong>不是。Function Calling 是<strong>模型层面</strong>的单次工具调用能力（模型输出该调哪个函数、传什么参数）；MCP 是<strong>应用层面</strong>的标准化协议，规定工具如何被发现、连接、复用。类比：Function Calling 是"会打电话"，MCP 是"统一的电话网络标准"。<br><strong>常见扣分点：</strong>把两者对立起来，说"有了 MCP 就不用 Function Calling"（实际上 MCP 之上仍靠模型的工具调用能力）。<br><strong>追问：</strong>没有 MCP 就不能用工具了吗？（答：能，只是每个工具都要手写对接，M×N 成本高）（详见第 6 章）</div>
      </div>

      <h3>第三层 · 工程与实战（高级题，决定薪资档位）</h3>
      <p class="cjk">这一层是薪资分水岭。评判标准从"知道概念"变成"能把问题—对策成对说出来、能报出监控指标、能讲清降级方案"。答题时多用具体抓手，少用"我会注意一下"这种虚词。</p>

      <div class="qa">
        <div class="q"><span class="qmark">Q11</span>你怎么评估一个 Agent 的好坏？<span class="difficulty hard">HARD</span></div>
        <div class="a cjk"><span class="amark">A</span><strong>考点：</strong>能否给出"分层评估 + 闭环迭代"的系统方法，而非只说"看准确率"。<br><strong>高分答法：</strong>不能用精确匹配。要分层评：<strong>最终结果</strong>（成功率、LLM-as-Judge）+ <strong>执行轨迹</strong>（工具选得对不对、有无绕路）+ <strong>RAG 质量</strong>（相关性、忠实度）+ <strong>工程指标</strong>（延迟、成本、失败率）。方法上 LLM-as-Judge / Ground Truth 对照 / 人工评估三者结合。强调<mark class="key">闭环</mark>：建评估集→定指标→自动化回归→上线 tracing 监控→线上 badcase 反哺评估集。<br><strong>常见扣分点：</strong>只谈单点准确率；不提轨迹评估与线上反馈闭环。<br><strong>追问：</strong>没有 ground truth 怎么评？（答：LLM-as-Judge + 人工抽检，配对比较代替打分）（详见第 11 章）</div>
      </div>

      <div class="qa">
        <div class="q"><span class="qmark">Q12</span>Agent 常见的失败模式有哪些？怎么应对？<span class="difficulty hard">HARD</span></div>
        <div class="a cjk"><span class="amark">A</span><strong>考点：</strong>是否踩过坑——能否把"问题→对策"成对、成体系地讲出来。<br><strong>高分答法：</strong>五大典型：<strong>无限循环</strong>（→ max_steps 上限 + 循环检测）、<strong>上下文爆炸</strong>（→ 压缩 + 笔记外置 + 子 Agent 隔离）、<strong>错误累积</strong>（→ Reflection 自检 + 关键步骤验证 + 人工确认）、<strong>提示注入</strong>（→ 隔离不可信内容 + 最小权限）、<strong>幻觉工具调用</strong>（→ schema 校验 + 工具白名单 + 失败重试）。<br><strong>常见扣分点：</strong>只罗列问题不给对策；对策泛泛而谈（"加强测试"）。<br><strong>追问：</strong>怎么发现 Agent 在绕路？（答：看 tracing 轨迹、异常步数/重复调用告警）（详见第 12 章）</div>
      </div>

      <div class="qa">
        <div class="q"><span class="qmark">Q13</span>让 Agent 直接写代码执行（CodeAct）有什么优劣？<span class="difficulty hard">HARD</span></div>
        <div class="a cjk"><span class="amark">A</span><strong>考点：</strong>能否同时讲清"表达力优势"和"安全代价"两面。<br><strong>高分答法：</strong>优势：代码天然支持循环、条件、组合多个工具调用，比拼 JSON 更灵活，研究显示可减少约 30% 步骤。劣势与风险：<mark class="key2">任意代码执行是重大安全隐患，必须在沙箱（E2B / Docker）中运行</mark>，并限制可导入的库、可访问的资源。smolagents 的 CodeAgent 就是典型代表。<br><strong>常见扣分点：</strong>只夸灵活不谈沙箱；忽略资源/网络/时长限制。<br><strong>追问：</strong>沙箱之外还要防什么？（答：限制出网、限时限内存、白名单库、隔离密钥）（详见第 7、8 章）</div>
      </div>

      <div class="qa">
        <div class="q"><span class="qmark">Q14</span>如何控制 Agent 的成本和延迟？<span class="difficulty hard">HARD</span></div>
        <div class="a cjk"><span class="amark">A</span><strong>考点：</strong>是否有"从上下文根子上降本"的意识，而不只是换便宜模型。<br><strong>高分答法：</strong>成本：设步数/ token 预算上限、缓存重复调用、能用小模型的步骤不上大模型、按需加载工具与上下文。延迟：并行独立工具调用、流式返回、慢工具设超时与降级、减少无谓推理轮次。根子上——<strong>好的上下文工程本身就是最大的降本手段</strong>，token 少了钱和时间都省。<br><strong>常见扣分点：</strong>只说"换小模型"；忽略并行化与缓存。<br><strong>追问：</strong>哪种缓存最有效？（答：提示前缀缓存 + 工具结果缓存，对重复系统提示尤其省）（详见第 4、12 章）</div>
      </div>

      <div class="qa">
        <div class="q"><span class="qmark">Q15</span>生产环境里如何防止 Agent 被提示注入攻击？<span class="difficulty hard">HARD</span></div>
        <div class="a cjk"><span class="amark">A</span><strong>考点：</strong>能否给出"多层防御 + 零信任外部内容"的安全心智。<br><strong>高分答法：</strong>多层防御：<strong>①</strong> 隔离不可信内容（把外部网页/文档内容与系统指令明确分区，不让其冒充指令）；<strong>②</strong> 最小权限（工具只给必要权限，危险动作走 human-in-the-loop）；<strong>③</strong> 输出校验（对工具参数、最终动作做规则校验）；<strong>④</strong> 沙箱执行任何代码/命令。核心心智：<mark class="key">永远不要信任模型看到的外部内容。</mark><br><strong>常见扣分点：</strong>指望"在系统提示里写一句别被骗"就能防住；只靠模型自律。<br><strong>追问：</strong>间接注入（网页里藏指令）怎么防？（答：内容分区 + 剥离可执行意图 + 危险动作强制人工确认）（详见第 12 章）</div>
      </div>

      <div class="qa">
        <div class="q"><span class="qmark">Q16</span>为什么很多团队从重框架回退到轻量方案甚至直接调 API？<span class="difficulty hard">HARD</span></div>
        <div class="a cjk"><span class="amark">A</span><strong>考点：</strong>是否理解"抽象层的收益与代价"，而非跟风黑/捧某框架。<br><strong>高分答法：</strong>因为重框架的抽象层在生产中会变成"黑盒负担"：难调试、难定位问题、行为不透明、被框架的设计假设绑架。经验是<mark class="key2">最成功的实现往往用简单可组合的模式，而非复杂框架</mark>——框架适合快速起步，成熟后常需减少抽象、贴近底层 API 以获得可控性。<br><strong>常见扣分点：</strong>一味说"框架不好"；说不出框架在原型期的价值。<br><strong>追问：</strong>那你会怎么选？（答：原型用框架加速，核心链路成熟后逐步"去抽象"）（详见第 7 章）</div>
      </div>

      <h3>第四层 · 架构与组件（把"解剖结构"讲透）</h3>
      <p class="cjk">当面试官深入到组件级，他想确认你不是只在"应用层拼积木"，而是理解每个部件的职责边界与设计约束。</p>

      <div class="qa">
        <div class="q"><span class="qmark">Q17</span>Agent 里的"推理引擎"和普通调用 LLM 有什么额外要求？<span class="difficulty mid">MEDIUM</span></div>
        <div class="a cjk"><span class="amark">A</span><strong>考点：</strong>能否说出"推理引擎"要额外承担规划、工具选择与终止判断。<br><strong>高分答法：</strong>推理引擎不只是生成文本，它要在每一步做三件事：<strong>决定下一步动作</strong>（选工具 / 继续想 / 终止）、<strong>产出结构化调用</strong>（符合 schema 的参数）、<strong>基于观测自我修正</strong>。因此对模型的要求是强指令遵循、稳定的结构化输出、以及较好的长上下文推理。<br><strong>常见扣分点：</strong>把它当纯文本生成器；忽略"终止判断"这个工程难点。<br><strong>追问：</strong>模型说自己完成了就真完成了吗？（答：不一定，需要外部校验，模型自述 ≠ 真实完成）</div>
      </div>

      <div class="qa">
        <div class="q"><span class="qmark">Q18</span>设计一个好用的工具（Tool）有哪些原则？<span class="difficulty mid">MEDIUM</span></div>
        <div class="a cjk"><span class="amark">A</span><strong>考点：</strong>是否明白"工具设计质量直接决定 Agent 能力上限"。<br><strong>高分答法：</strong>关键原则：<strong>命名与描述清晰</strong>（模型靠 description 决定何时调用）、<strong>参数最小且强类型</strong>（用 schema 约束，减少幻觉参数）、<strong>返回精炼高信号</strong>（别把整页原始数据塞回上下文）、<strong>错误可读</strong>（失败时给出可让模型自我修正的信息）、<strong>粒度合适</strong>（既不过碎也不过粗）。<br><strong>常见扣分点：</strong>工具描述含糊、返回超长原始文本、错误信息无法指导修正。<br><strong>追问：</strong>工具太多模型选错怎么办？（答：按需加载 / 分组 / 用检索挑工具，减少同时暴露的工具数）（详见第 2、6 章）</div>
      </div>

      <div class="qa">
        <div class="q"><span class="qmark">Q19</span>短期记忆和长期记忆的边界在哪？如何联动？<span class="difficulty mid">MEDIUM</span></div>
        <div class="a cjk"><span class="amark">A</span><strong>考点：</strong>能否讲清"上下文窗口内 vs 外部持久化"的边界及读写通路。<br><strong>高分答法：</strong>短期记忆 = 当前上下文窗口内的对话与中间结果，随会话结束消失；长期记忆 = 外部存储（向量库 / KV / 文件 / 数据库），跨会话保留。联动方式：检索长期记忆中相关片段 <strong>Select</strong> 进上下文，会话结束把值得留存的信息 <strong>Write</strong> 回长期存储，上下文过长时 <strong>Compress</strong> 成摘要。<br><strong>常见扣分点：</strong>把"上下文窗口大"当成"有长期记忆"。<br><strong>追问：</strong>长期记忆怎么保证检索到的是相关的？（答：好的写入结构 + 元数据过滤 + reranking）（详见第 4、5 章）</div>
      </div>

      <h3>第五层 · 框架选型（讲得出对比才算懂）</h3>
      <p class="cjk">框架题的陷阱是"报菜名"。高分回答的共性是<strong>先给一句定位、再给一个适用场景、最后给你的选择理由</strong>，而不是逐个复述文档。</p>

      <div class="qa">
        <div class="q"><span class="qmark">Q20</span>LangGraph、smolagents、PydanticAI、OpenAI Agents SDK 各自的定位是什么？<span class="difficulty mid">MEDIUM</span></div>
        <div class="a cjk"><span class="amark">A</span><strong>考点：</strong>能否用"范式差异"而非功能清单来区分它们。<br><strong>高分答法：</strong>一句话定位：<strong>LangGraph</strong> 以"图/状态机"编排见长，适合需要显式控制流、分支与回环的复杂工作流；<strong>smolagents</strong> 轻量、主打 CodeAgent（让模型写代码来行动）；<strong>PydanticAI</strong> 强调类型安全与结构化输出，工程上稳；<strong>OpenAI Agents SDK</strong> 官方轻量封装、贴近其模型能力。选型看你要的是"编排控制力"还是"轻量可控"。<br><strong>常见扣分点：</strong>把它们说得"都差不多"；只背 API 不谈范式。<br><strong>追问：</strong>你的项目为什么选它？（答：结合任务是否需要显式图编排 / 代码行动 / 强类型来解释）（详见第 7 章）</div>
      </div>

      <div class="qa">
        <div class="q"><span class="qmark">Q21</span>什么时候该"去框架化"、直接用底层 API？<span class="difficulty hard">HARD</span></div>
        <div class="a cjk"><span class="amark">A</span><strong>考点：</strong>是否理解抽象层的边际收益递减。<br><strong>高分答法：</strong>当出现这些信号就该考虑去抽象：调试时总要"穿透"框架去看真实请求、框架的默认行为和你的需求冲突、性能/成本被隐藏调用拖累、团队要长期维护核心链路。原则是<strong>原型期用框架抢速度，核心链路成熟后贴近底层 API 换可控性</strong>。<br><strong>常见扣分点：</strong>非黑即白地"框架无用论"或"必须上框架"。<br><strong>追问：</strong>去框架后怎么不重复造轮子？（答：只保留自己需要的少量可组合模式，而非重写整个生态）（详见第 7 章）</div>
      </div>

      <div class="qa">
        <div class="q"><span class="qmark">Q22</span>图（Graph）编排范式和 ReAct 循环范式各自适合什么？<span class="difficulty hard">HARD</span></div>
        <div class="a cjk"><span class="amark">A</span><strong>考点：</strong>能否把"确定性控制流 vs 自主循环"映射到两种范式。<br><strong>高分答法：</strong>Graph 范式把流程显式建成节点与边，控制流可预测、易回归、方便加分支与回环——适合<strong>路径大体确定、局部需要判断</strong>的场景；ReAct 循环把控制权交给模型逐步决策，灵活但可预测性差——适合<strong>路径无法预先枚举</strong>的探索式任务。二者常混用：外层用 Graph 编排，某个节点内跑一个受限的 ReAct 子 Agent。<br><strong>常见扣分点：</strong>认为二者互斥、只能二选一。<br><strong>追问：</strong>怎么在 Graph 里防止某节点的 Agent 失控？（答：节点内限步数 + 超时 + 输出校验）（详见第 3、7 章）</div>
      </div>

      <h3>第六层 · RAG 与检索专题</h3>
      <p class="cjk">RAG 是落地最广的场景，也是最容易"看起来会、其实答不深"的地方。面试官爱按"排查链路"追问，所以要能沿着<strong>切分→嵌入→检索→重排→生成</strong>逐环节讲。</p>

      <div class="qa">
        <div class="q"><span class="qmark">Q23</span>一个 RAG 系统检索不准，你会从哪些环节排查？<span class="difficulty hard">HARD</span></div>
        <div class="a cjk"><span class="amark">A</span><strong>考点：</strong>有没有"全链路排障"的结构化思路。<br><strong>高分答法：</strong>沿链路逐段查：<strong>①切分</strong>（chunk 太大混入噪声、太小切断语义）；<strong>②嵌入</strong>（模型是否匹配领域/语言，是否需要指令式 embedding）；<strong>③查询</strong>（是否需要查询改写、扩展、HyDE）；<strong>④检索</strong>（纯向量召回不够，可加关键词/BM25 做混合检索）；<strong>⑤重排</strong>（用 reranker 精排 top-k）；<strong>⑥生成</strong>（prompt 是否让模型只依据检索内容作答）。<br><strong>常见扣分点：</strong>一上来就说"换个更强的 embedding 模型"，不做分段定位。<br><strong>追问：</strong>怎么判断是召回问题还是生成问题？（答：先看检索到的片段里是否包含答案）（详见第 10 章）</div>
      </div>

      <div class="qa">
        <div class="q"><span class="qmark">Q24</span>chunking（切分）策略怎么选？<span class="difficulty mid">MEDIUM</span></div>
        <div class="a cjk"><span class="amark">A</span><strong>考点：</strong>能否讲清切分对召回质量的影响与取舍。<br><strong>高分答法：</strong>没有万能值，取决于文档结构：结构化文档按标题/段落等语义边界切；长文可用滑动窗口 + 重叠避免切断上下文；表格/代码要保持单元完整。核心权衡：<strong>块越大上下文越完整但噪声越多、召回越不精准；块越小越精准但可能丢上下文</strong>。可配合"父子块"（检索用小块、喂给模型用其所在大块）。<br><strong>常见扣分点：</strong>给一个死板的固定字数当"标准答案"。<br><strong>追问：</strong>怎么验证切分好坏？（答：用检索命中率/相关性指标在评估集上对比）（详见第 10 章）</div>
      </div>

      <div class="qa">
        <div class="q"><span class="qmark">Q25</span>什么是 reranking，为什么向量检索之后还需要它？<span class="difficulty mid">MEDIUM</span></div>
        <div class="a cjk"><span class="amark">A</span><strong>考点：</strong>能否区分"双塔召回"与"交叉编码精排"的取舍。<br><strong>高分答法：</strong>向量检索（双塔/bi-encoder）把 query 和文档各自编码后算相似度，快但精度有限、可能召回"相关但不精确"的块；reranker（交叉编码/cross-encoder）把 query 与候选块拼在一起联合打分，更准但更慢。所以典型做法是<strong>先用向量粗召回一批，再用 reranker 精排出真正 top-k</strong>，兼顾速度与精度。<br><strong>常见扣分点：</strong>说不清为什么不直接全量用 reranker（答：太慢，成本高）。<br><strong>追问：</strong>混合检索里怎么融合多路结果？（答：如按分数归一化融合或用 reranker 统一重排）（详见第 10 章）</div>
      </div>

      <div class="qa">
        <div class="q"><span class="qmark">Q26</span>如何评估 RAG 的检索质量与生成忠实度？<span class="difficulty hard">HARD</span></div>
        <div class="a cjk"><span class="amark">A</span><strong>考点：</strong>能否把 RAG 拆成"检索指标 + 生成指标"两组来评。<br><strong>高分答法：</strong>检索侧看<strong>上下文相关性/召回</strong>（检索到的片段是否包含答案）；生成侧看<strong>忠实度</strong>（回答是否只基于检索内容、有没有编造）和<strong>答案相关性</strong>（是否切题）。方法上可用 LLM-as-Judge 对"问题-检索片段-回答"三元组打分，并用带标注的评估集回归。<br><strong>常见扣分点：</strong>只看最终答案对不对，不拆检索与生成，导致定位不到问题。<br><strong>追问：</strong>忠实度低但答案"看起来对"怎么办？（答：这其实是幻觉隐患，要强制引用出处 + 校验）（详见第 10、11 章）</div>
      </div>

      <h3>第七层 · 评估与可观测专题</h3>
      <p class="cjk">评估题是资深岗的"照妖镜"。能不能报出监控指标、能不能设计裁判、能不能做线上回归，直接暴露你有没有真正把 Agent 送上过生产。</p>

      <div class="qa">
        <div class="q"><span class="qmark">Q27</span>LLM-as-Judge 有哪些坑，如何提升它的可信度？<span class="difficulty hard">HARD</span></div>
        <div class="a cjk"><span class="amark">A</span><strong>考点：</strong>是否清楚"用模型评模型"的偏差来源与缓解手段。<br><strong>高分答法：</strong>常见坑：位置偏好（偏向靠前答案）、长度偏好（偏爱长答案）、自我偏好（偏向同源模型）、评分不稳定。缓解：给<strong>明确评分标准（rubric）</strong>、用<strong>成对比较</strong>代替绝对打分、交换位置消偏、少量人工标注做校准、对关键场景保留人工抽检。<br><strong>常见扣分点：</strong>把 LLM-as-Judge 当"绝对真理"，不做校准。<br><strong>追问：</strong>怎么知道你的裁判本身靠谱？（答：用人工标注集验证裁判与人的一致性）（详见第 11 章）</div>
      </div>

      <div class="qa">
        <div class="q"><span class="qmark">Q28</span>怎么评估一个长程 Agent 的执行轨迹，而不只是最终答案？<span class="difficulty hard">HARD</span></div>
        <div class="a cjk"><span class="amark">A</span><strong>考点：</strong>是否理解"结果对不代表过程对"。<br><strong>高分答法：</strong>轨迹评估看几件事：<strong>工具选择是否正确</strong>、<strong>有无冗余/绕路步骤</strong>、<strong>是否在正确时机终止</strong>、<strong>中间步骤是否基于观测正确修正</strong>。可以对照参考轨迹（如果有）或用 LLM-as-Judge 评价轨迹合理性，同时统计步数、重复调用率等结构化指标。<br><strong>常见扣分点：</strong>只看成功率，忽略"蒙对"和"高成本绕路"。<br><strong>追问：</strong>为什么结果对也要看轨迹？（答：绕路会推高成本延迟，且换个输入就可能失败）（详见第 11 章）</div>
      </div>

      <div class="qa">
        <div class="q"><span class="qmark">Q29</span>线上如何做 tracing 和监控？<span class="difficulty mid">MEDIUM</span></div>
        <div class="a cjk"><span class="amark">A</span><strong>考点：</strong>能否说出该记录哪些字段、监控哪些指标、如何闭环。<br><strong>高分答法：</strong>记录每次运行的完整轨迹（每步的输入/输出、工具调用、token、耗时、错误），聚合出<strong>成功率、平均步数、P95 延迟、单次成本、工具失败率</strong>等指标；对异常（步数超阈、循环、错误率飙升）告警；把线上 badcase 回流到评估集形成闭环。<br><strong>常见扣分点：</strong>只记最终输入输出，缺中间步骤，出问题无法复盘。<br><strong>追问：</strong>数据太多存不下怎么办？（答：采样 + 对失败/异常全量留存）（详见第 11、12 章）</div>
      </div>

      <h3>第八层 · 多 Agent 协作专题</h3>
      <p class="cjk">多 Agent 题最忌"越复杂越先进"的心态。面试官想看你能不能<strong>先论证必要性</strong>，再讲拓扑与信息流。</p>

      <div class="qa">
        <div class="q"><span class="qmark">Q30</span>多 Agent 系统有哪些常见的协作拓扑？<span class="difficulty mid">MEDIUM</span></div>
        <div class="a cjk"><span class="amark">A</span><strong>考点：</strong>能否说出几种编排模式及其适用场景。<br><strong>高分答法：</strong>常见几类：<strong>orchestrator-worker（主管-工人）</strong>——一个主 Agent 拆解任务、分发给子 Agent 并汇总；<strong>并行/分而治之</strong>——多个独立子 Agent 同时处理可拆分子任务；<strong>流水线（顺序交接）</strong>——按阶段串行传递；<strong>辩论/评审</strong>——多个 Agent 相互批判提升质量。选型看任务是否可并行、是否需要专门化角色。<br><strong>常见扣分点：</strong>只知道"一个主一个从"，说不出并行/评审等模式。<br><strong>追问：</strong>主管模式的瓶颈在哪？（答：主 Agent 的汇总与上下文承载，容易成为上下文瓶颈）（详见第 3 章）</div>
      </div>

      <div class="qa">
        <div class="q"><span class="qmark">Q31</span>多 Agent 之间的上下文/信息如何传递？有什么损耗？<span class="difficulty hard">HARD</span></div>
        <div class="a cjk"><span class="amark">A</span><strong>考点：</strong>是否意识到"子 Agent 隔离"的双刃剑。<br><strong>高分答法：</strong>子 Agent 隔离上下文能防止单个上下文爆炸、让每个角色聚焦；但代价是<strong>信息在交接时会丢失</strong>——主 Agent 传给子 Agent 的只是压缩后的任务描述，子 Agent 的中间发现也未必完整回传。缓解：定义清晰的交接契约（结构化输入输出）、必要信息显式传递、避免让子 Agent"猜"缺失的背景。<br><strong>常见扣分点：</strong>假设子 Agent 天然共享全部上下文。<br><strong>追问：</strong>怎么减少交接信息损耗？（答：结构化 handoff schema + 关键上下文冗余传递）（详见第 3、4 章）</div>
      </div>

      <div class="qa">
        <div class="q"><span class="qmark">Q32</span>orchestrator-worker 模式适合什么任务，什么时候会"翻车"？<span class="difficulty mid">MEDIUM</span></div>
        <div class="a cjk"><span class="amark">A</span><strong>考点：</strong>能否评估该模式的收益与代价。<br><strong>高分答法：</strong>适合<strong>可清晰拆解、子任务彼此独立且可并行</strong>的场景（如多来源调研、批量处理）。翻车常见于：子任务其实强耦合、需要频繁互相依赖结果，导致主 Agent 反复协调、上下文来回同步，协调开销超过并行收益。此时单 Agent 顺序执行反而更简单可靠。<br><strong>常见扣分点：</strong>把它当成万能架构，忽略耦合任务的协调成本。<br><strong>追问：</strong>并行子 Agent 结果冲突怎么合并？（答：主 Agent 做去重/仲裁，或定义合并规则）（详见第 3 章）</div>
      </div>

      <h3>第九层 · 后训练与微调专题</h3>
      <p class="cjk">后训练题近年越问越多。关键不是背算法名，而是能讲清<strong>"什么时候该训、训哪一层、用什么范式"</strong>的决策逻辑，并守住"能用 prompt/RAG 解决就别急着训"的工程克制。</p>

      <div class="qa">
        <div class="q"><span class="qmark">Q33</span>SFT、RLHF、DPO 的区别与各自适用场景？<span class="difficulty hard">HARD</span></div>
        <div class="a cjk"><span class="amark">A</span><strong>考点：</strong>能否讲清三者"用什么数据、优化什么目标"。<br><strong>高分答法：</strong><strong>SFT（监督微调）</strong>用"输入-理想输出"对，让模型模仿示范，学格式与基本能力；<strong>RLHF</strong>先训一个奖励模型再用强化学习优化，让输出对齐人类偏好，效果强但流程复杂、训练不稳定；<strong>DPO</strong>用成对偏好数据直接优化偏好目标，跳过显式奖励模型，更简单稳定，是 RLHF 的常见轻量替代。一般顺序是先 SFT 再做偏好对齐。<br><strong>常见扣分点：</strong>把三者并列成"三选一"，讲不出先后与依赖关系。<br><strong>追问：</strong>为什么 DPO 更受欢迎？（答：省去奖励模型、实现简单、训练更稳）（详见第 9 章）</div>
      </div>

      <div class="qa">
        <div class="q"><span class="qmark">Q34</span>什么时候该微调，什么时候用 RAG / prompt 就够？<span class="difficulty hard">HARD</span></div>
        <div class="a cjk"><span class="amark">A</span><strong>考点：</strong>是否有"先便宜后昂贵"的能力选型阶梯。<br><strong>高分答法：</strong>决策阶梯：<strong>先 prompt/few-shot</strong>（最便宜、可快速迭代）→ <strong>知识缺口用 RAG</strong>（外挂知识、可更新、可溯源）→ <strong>行为/风格/格式稳定不了才微调</strong>（教模型"怎么做"而非"知道什么"）。<mark class="key2">缺知识用 RAG，缺行为用微调</mark>是常用的一刀切记忆法。微调成本高、数据要求高、还要重复维护，能不训尽量不训。<br><strong>常见扣分点：</strong>一上来就说"微调"，把知识更新问题错配给微调。<br><strong>追问：</strong>微调能解决幻觉吗？（答：不能根治，知识型幻觉更该靠 RAG + 校验）（详见第 9、10 章）</div>
      </div>

      <div class="qa">
        <div class="q"><span class="qmark">Q35</span>什么是面向工具使用 / function-calling 的后训练？<span class="difficulty mid">MEDIUM</span></div>
        <div class="a cjk"><span class="amark">A</span><strong>考点：</strong>是否理解"工具调用能力可以被专门训练"。<br><strong>高分答法：</strong>就是用大量"何时该调哪个工具、传什么参数、如何根据返回继续"的示范/偏好数据来后训练模型，让它在结构化输出、参数正确性、多步工具编排上更稳。这也是为什么不同模型的"工具调用能力"差异明显。工程上如果通用模型工具调用不稳，除了改 prompt/schema，也可考虑用领域数据做这类后训练。<br><strong>常见扣分点：</strong>以为工具调用只是 prompt 技巧，与模型训练无关。<br><strong>追问：</strong>没有训练资源怎么提升工具调用稳定性？（答：更严格的 schema、更清晰的工具描述、失败重试与校验）（详见第 2、9 章）</div>
      </div>

      <div class="qa">
        <div class="q"><span class="qmark">Q36</span>面向 Agent 的强化学习（用结果奖励训练）解决什么问题？<span class="difficulty hard">HARD</span></div>
        <div class="a cjk"><span class="amark">A</span><strong>考点：</strong>能否讲清"用任务成败作为奖励信号"的思路与难点。<br><strong>高分答法：</strong>思路是让 Agent 在环境中反复尝试，用<strong>任务是否成功/轨迹质量</strong>作为奖励来优化策略，从而提升长程规划与工具编排能力，而不只是模仿静态示范。难点在于：奖励稀疏（长程任务只有最后有信号）、信用分配难（哪一步立功不好定）、需要可复现的环境与大量交互成本。<br><strong>常见扣分点：</strong>把它和 RLHF 混为一谈（RLHF 对齐偏好，这里优化任务成败）。<br><strong>追问：</strong>奖励太稀疏怎么办？（答：过程奖励/中间里程碑、更强的评估器给密集反馈）（详见第 9 章）</div>
      </div>

      <h3>快问快答 · 易错概念补漏</h3>
      <p class="cjk">这些是"一句话就该答对"的送分题，但也是紧张时最容易含糊的地方。目标是脱口而出、不拖泥带水。</p>

      <div class="qa">
        <div class="q"><span class="qmark">Q37</span>temperature 调高调低分别影响什么？<span class="difficulty easy">EASY</span></div>
        <div class="a cjk"><span class="amark">A</span>控制采样随机性：<strong>低</strong>更确定、更保守，适合工具调用、抽取、需要稳定复现的场景；<strong>高</strong>更发散、更有创造性，适合头脑风暴。Agent 的决策步通常倾向较低温度以求稳定。<strong>扣分点：</strong>说成"控制模型聪明程度"。</div>
      </div>

      <div class="qa">
        <div class="q"><span class="qmark">Q38</span>幻觉（hallucination）的本质是什么？<span class="difficulty easy">EASY</span></div>
        <div class="a cjk"><span class="amark">A</span>模型按语言概率生成了"流畅但无事实依据"的内容——它优化的是"像不像对的"而非"是不是对的"。缓解靠 RAG 提供依据、强制引用出处、输出校验，而非指望模型自觉。<strong>扣分点：</strong>把幻觉当"bug"，以为微调就能根治。</div>
      </div>

      <div class="qa">
        <div class="q"><span class="qmark">Q39</span>上下文窗口和 token 是什么关系？<span class="difficulty easy">EASY</span></div>
        <div class="a cjk"><span class="amark">A</span>token 是模型处理文本的最小单位，上下文窗口是一次能容纳的 token 上限（输入 + 输出共享）。窗口是硬约束，也是成本来源——所以要做上下文压缩与裁剪。<strong>扣分点：</strong>把 token 当"字符"或"单词"一一对应。</div>
      </div>

      <div class="qa">
        <div class="q"><span class="qmark">Q40</span>embedding 和向量数据库各自解决什么？<span class="difficulty easy">EASY</span></div>
        <div class="a cjk"><span class="amark">A</span>embedding 把文本映射成能表达语义的向量，"意思相近向量相近"；向量数据库负责海量向量的存储与快速近邻检索。二者配合支撑语义检索。<strong>扣分点：</strong>把 embedding 说成"压缩"或"加密"。</div>
      </div>

      <div class="qa">
        <div class="q"><span class="qmark">Q41</span>human-in-the-loop 应该卡在哪些动作上？<span class="difficulty easy">EASY</span></div>
        <div class="a cjk"><span class="amark">A</span>卡在<strong>高风险、不可逆</strong>的动作：花钱、发对外消息、改/删数据、执行危险命令。低风险动作放开自主，才能兼顾安全与效率。<strong>扣分点：</strong>要么处处审批（失去自动化意义）、要么全放开（失控风险）。</div>
      </div>

      <div class="qa">
        <div class="q"><span class="qmark">Q42</span>structured output（结构化输出）为什么对 Agent 很关键？<span class="difficulty easy">EASY</span></div>
        <div class="a cjk"><span class="amark">A</span>因为 Agent 的动作要被程序解析执行——工具调用、参数、路由都依赖稳定的结构（JSON / schema）。结构化输出 + schema 校验能大幅降低"解析失败"和"幻觉参数"。<strong>扣分点：</strong>只当它是"格式好看"，忽略它是可靠执行的前提。</div>
      </div>

      <div class="callout warn">
        <span class="label">答题通用反模式（任何题都别犯）</span>
        <span class="cjk">① <strong>只给结论不给取舍</strong>——面试官要的是"为什么"，不是"是什么"。② <strong>堆名词不讲机制</strong>——说了一串框架/算法名却讲不清原理，反而暴露短板。③ <strong>无脑追新追复杂</strong>——把"多 Agent / 微调 / 重框架"当先进标志，恰恰显得不成熟。④ <strong>编造数字与出处</strong>——报不出的数字就用"量级/趋势"描述，<mark class="key">宁可说"我不确定具体数字，但机制是……"，也不要编。</mark></span>
      </div>

      <div class="callout tip">
        <span class="label">本章小结</span>
        <span class="cjk">这份题库的用法不是"背答案"，而是把每题的<strong>考点、高分答法、扣分点、追问</strong>四件套内化成条件反射。真正拉开差距的，是三种能力：<strong>划清分界线</strong>（Agent vs LLM、MCP vs Function Calling、缺知识用 RAG 缺行为用微调）、<strong>成对讲问题与对策</strong>（失败模式、安全、成本延迟都要一问一答成套）、以及<strong>能接住追问</strong>（每个结论都预备好"下一层为什么"）。把概念、架构、工程、框架、RAG、评估、多 Agent、后训练八大板块各准备两三个能讲透的题，你在初面到终面的任何深挖里都不会失速。下一章我们解决"知道了怎么说得漂亮"——答题框架与项目准备。</span>
      </div>
