      <h2 class="chap-title"><span class="kicker">09</span>工程化 PydanticAI</h2>
      <p class="cjk">smolagents 让你理解原理，<strong>PydanticAI</strong> 让你写出能上生产的代码。它由 Pydantic（被 OpenAI SDK、LangChain 等广泛依赖的数据校验库）团队打造，把"类型安全 + 结构化输出 + 依赖注入"带进 Agent 开发，被称为"Agent 界的 FastAPI"<sup><a href="#cite-10">[10]</a></sup>。</p>
      <p class="cjk">面试里一旦聊到"你怎么把 Agent 从 Demo 推到生产"，考察的其实不再是"会不会调模型"，而是<strong>工程素养</strong>：输出可不可控、依赖可不可替换、错误可不可恢复、行为可不可测试、上线后可不可观测。PydanticAI 之所以值得单独成章，正是因为它把这些工程关切原生地内建进框架，而不是让你事后打补丁。理解它的设计哲学，你在回答"框架选型"这类开放题时就能跳出"谁更火"的表层，落到"谁把生产要素做进了类型系统"的本质。</p>
      <p class="cjk">本章将沿着一条"从内到外"的主线展开：先讲清<strong>类型即契约</strong>这一设计哲学，再逐层落到结构化输出、依赖注入、错误处理与重试、pytest 测试策略、流式与异步、FastAPI 生产部署、消息历史与可观测性，最后回到与 smolagents 的取舍对比。你会发现，这些看似分散的话题其实被同一根线索串起来——<mark class="key2">把大模型的不确定性，用类型、依赖与显式契约层层收敛成可控、可测、可维护的工程对象</mark>。读完本章，你不仅能写出能上线的 PydanticAI 代码，更能在面试中把"我懂 Agent 工程化"这句话讲得有骨有肉。</p>

      <h3>为什么"类型即契约"是生产 Agent 的第一原则</h3>
      <p class="cjk">大模型的输出天然是<strong>非确定性文本</strong>，而下游的业务代码要的是<strong>确定性数据结构</strong>。这两者之间的鸿沟，就是绝大多数 LLM 应用在生产中翻车的根源：今天模型返回一段带 Markdown 代码围栏的 JSON，明天多加了一句"以下是您要的结果"，后天字段名从 <code>score</code> 变成了 <code>Score</code>。任何用正则或字符串裁剪去"抠"结果的方案，都会在流量上来后被各种边缘情况击穿。</p>
      <p class="cjk">PydanticAI 的核心主张是把<strong>类型当作 Agent 与业务之间的契约</strong>：你用 Pydantic 模型声明"我要的结果长什么样"，框架负责把模型的自由文本约束、解析、校验成这个结构，校验不过就驱动模型自我修正。<mark class="key">这本质上是把"解析的责任"从脆弱的后处理代码，前移到了有 schema 约束、可自动重试的框架层</mark>。对面试官而言，能说清"为什么结构化输出不是锦上添花而是生产刚需"，比背出十个 API 更能体现你的成熟度。</p>
      <div class="callout tip">
        <span class="label">面试要点</span>
        <span class="cjk">"Agent 界的 FastAPI"这个类比要能展开讲：FastAPI 用 Pydantic 把 HTTP 请求/响应变成类型安全的对象，PydanticAI 用同一套心智把 LLM 的输入依赖与输出结果也变成类型安全的对象。二者共享<strong>类型驱动、依赖注入、自动校验</strong>的设计基因，所以对写过 FastAPI 的团队几乎零学习成本——这正是它在工程团队里快速被接受的原因。</span>
      </div>
      <p class="cjk">还有一个常被忽略却很关键的设计：<strong>模型无关（model-agnostic）</strong>。PydanticAI 用统一接口抽象了 OpenAI、Anthropic、Google 等不同厂商的模型，声明时只需一个像 <code>"openai:gpt-4o"</code> 的字符串，切换厂商基本不用改业务代码。这在生产上意味着两件事：一是<strong>供应商解耦</strong>——某家限流或涨价时能快速切换，避免被单一厂商锁定；二是<strong>分环境用不同模型</strong>——线上用能力强的大模型，测试用便宜的小模型甚至前面提到的假模型。把"框架帮你隔离了模型差异"讲清楚，也是选型题的一个加分点。</p>

      <h3>类型安全的结构化输出</h3>
      <p class="cjk">生产系统最怕模型返回一团自由文本无法解析。PydanticAI 用 <code>output_type</code> 强制模型输出符合 Pydantic 模型的结构化数据，<strong>校验不通过会自动让模型重试</strong>——这是它相较 smolagents 最关键的工程优势。</p>
      <div class="code-label">Python · 结构化输出的 Agent</div>
      <pre><code><span class="cm"># pip install pydantic-ai</span>
<span class="kw">from</span> pydantic <span class="kw">import</span> BaseModel
<span class="kw">from</span> pydantic_ai <span class="kw">import</span> Agent

<span class="kw">class</span> <span class="fn">ResumeScore</span>(BaseModel):
    score: int          <span class="cm"># 0-100 匹配分</span>
    strengths: list[str]
    risks: list[str]
    recommend: bool

<span class="cm"># output_type 保证返回值一定是 ResumeScore 结构</span>
agent = Agent(
    <span class="st">"openai:gpt-4o"</span>,
    output_type=ResumeScore,
    system_prompt=<span class="st">"你是资深技术面试官，评估候选人与岗位的匹配度。"</span>,
)

result = agent.run_sync(<span class="st">"岗位: Agent 工程师；简历: 3 年 NLP，做过 RAG 与工具调用……"</span>)
<span class="kw">print</span>(result.output.score, result.output.recommend)  <span class="cm"># 直接拿到强类型字段</span></code></pre>

      <p class="cjk">这段代码的价值不在"能跑"，而在<strong>每一处设计都在为可维护性买单</strong>。逐行读懂它的"为什么"：</p>
      <ul class="hub-list">
        <li><strong><code>class ResumeScore(BaseModel)</code></strong>：用声明式的字段与类型定义"合法结果"的边界。<code>score: int</code> 不只是提示，它会在运行时被真实校验——模型若把分数写成字符串 <code>"85"</code>，Pydantic 会尝试强转，转不了就报错触发重试。</li>
        <li><strong><code>output_type=ResumeScore</code></strong>：这一行是核心。框架据此为模型生成对应的 JSON Schema（借由工具/函数调用或原生结构化输出机制约束解码），并在收到响应后自动 <code>model_validate</code>。你的业务代码从此拿到的永远是 <code>ResumeScore</code> 对象，而不是一段需要自己解析的字符串。</li>
        <li><strong><code>result.output.score</code></strong>：IDE 能自动补全、类型检查器（mypy/pyright）能静态发现拼写错误。<mark class="key2">把运行时才暴露的错误提前到编码期，正是"类型安全"对工程效率的真实回报</mark>。</li>
      </ul>
      <p class="cjk">进一步地，Pydantic 的字段约束（如 <code>Field(ge=0, le=100)</code>）、自定义校验器（<code>field_validator</code>）都能叠加到 <code>output_type</code> 上，形成一层"业务规则即校验"的护栏。当模型输出越界的分数或自相矛盾的字段时，校验失败信息会作为反馈回传给模型，让它在下一轮修正——这就是"结构化输出 + 自动重试"闭环带来的鲁棒性。</p>
      <p class="cjk">值得多问一句"底层是怎么保证结构的"，这也是面试官爱挖的深度点。主流实现路径有两条：一是<strong>借工具/函数调用（tool/function calling）</strong>，把目标 schema 伪装成一个"工具"，模型通过调用它来"填参数"，从而产出结构化 JSON；二是<strong>原生结构化输出（约束解码）</strong>，模型在解码阶段就被 schema 约束，只能生成合法结构。PydanticAI 会根据所选模型的能力自动挑选合适的机制，你只需声明 <code>output_type</code>。理解这一层，你就能回答"为什么有的模型结构化输出更稳"——因为它们支持更强的约束解码，而非仅靠提示词祈祷。</p>
      <div class="callout warn">
        <span class="label">常见误区</span>
        <span class="cjk">① <strong>把 <code>output_type</code> 当万能银弹</strong>——它保证"结构合法"，不保证"内容正确"，一个格式完美但事实错误的分数依然是错的，仍需评估与事实核验。② <strong>schema 设计过度嵌套</strong>——层层嵌套的复杂模型会显著增加模型出错与重试的概率，字段应尽量扁平、语义清晰。③ <strong>用自由文本字段架空类型</strong>——把所有内容塞进一个 <code>str</code> 大字段，等于放弃了结构化的全部好处。</span>
      </div>

      <h3>工具与依赖注入</h3>
      <p class="cjk">PydanticAI 用 <code>@agent.tool</code> 注册工具，并通过 <code>RunContext</code> 做<strong>依赖注入</strong>——把数据库连接、用户身份等运行时依赖优雅地传给工具，避免全局变量。这套模式对写过 FastAPI 的人极其亲切，也是它"工程化"的体现。</p>

      <div class="code-label">Python · 工具 + 依赖注入</div>
      <pre><code><span class="kw">from</span> dataclasses <span class="kw">import</span> dataclass
<span class="kw">from</span> pydantic_ai <span class="kw">import</span> Agent, RunContext

<span class="kw">@dataclass</span>
<span class="kw">class</span> <span class="fn">Deps</span>:
    db: object          <span class="cm"># 运行时注入的数据库连接</span>

agent = Agent(<span class="st">"openai:gpt-4o"</span>, deps_type=Deps)

<span class="kw">@agent.tool</span>
<span class="kw">async def</span> <span class="fn">get_user_orders</span>(ctx: RunContext[Deps], user_id: int) -> list[dict]:
    <span class="st">"""查询指定用户的历史订单。"""</span>
    <span class="kw">return</span> <span class="kw">await</span> ctx.deps.db.fetch_orders(user_id)   <span class="cm"># 用注入的 db</span>

result = agent.run_sync(<span class="st">"用户 42 最近买了什么？"</span>, deps=Deps(db=my_db))</code></pre>

      <p class="cjk">依赖注入（Dependency Injection, DI）看似只是"把参数传进去"，实则解决了 Agent 工程化里一个隐蔽而致命的问题：<strong>工具函数不该知道它依赖的东西从哪来</strong>。如果工具内部直接 <code>import global_db</code>，那么这个工具就被钉死在了某个全局状态上——单元测试时无法替换成假数据库，多租户场景无法为不同用户注入不同连接，切换环境（测试/预发/生产）需要改代码。</p>
      <p class="cjk">PydanticAI 用 <code>deps_type</code> + <code>RunContext</code> 把依赖<strong>显式化、参数化</strong>：运行时通过 <code>run_sync(..., deps=...)</code> 注入，工具通过 <code>ctx.deps</code> 取用。这带来三个直接收益：</p>
      <ul class="hub-list">
        <li><strong>可测试</strong>：测试时注入一个 <code>FakeDB</code>，无需真连数据库，也无需 monkeypatch 全局变量（详见下文测试策略）。</li>
        <li><strong>可复用</strong>：同一个 Agent 定义，为不同租户/用户注入不同依赖即可复用，无需为每个场景复制一份。</li>
        <li><strong>类型安全</strong>：<code>RunContext[Deps]</code> 让 <code>ctx.deps</code> 拥有完整类型提示，误用即被静态检查器拦下。</li>
      </ul>
      <div class="callout tip">
        <span class="label">面试高分答法</span>
        <span class="cjk">被问"DI 有什么用"时，别停在"避免全局变量"。要点出它是<strong>可测试性的前提</strong>：正因为依赖能被注入，才能被替换成 Mock，才能做无副作用的单元测试。把"依赖注入 → 可替换 → 可测试 → 可持续交付"这条因果链讲通，就是资深工程师的答法。</span>
      </div>

      <h3>错误处理与重试：把不确定性关进笼子</h3>
      <p class="cjk">Agent 生产化的一半工作量都在处理"出错怎么办"。PydanticAI 把错误分成几类，分别有对应的处置手段，理清它们是面试与实战的硬核考点：</p>
      <div class="table-wrap">
        <table>
          <thead>
            <tr><th>错误类型</th><th>触发场景</th><th>处置策略</th></tr>
          </thead>
          <tbody>
            <tr><td>输出校验失败</td><td>模型返回不符合 <code>output_type</code> 的结构</td><td>框架自动把校验错误回传模型重试（受 <code>retries</code> 上限约束）</td></tr>
            <tr><td>工具参数非法</td><td>模型调用工具时传了非法参数</td><td>工具内 <code>raise ModelRetry("原因")</code>，把可读原因反馈给模型重试</td></tr>
            <tr><td>下游服务异常</td><td>数据库/API 超时、限流、5xx</td><td>工具内做<strong>确定性重试</strong>（指数退避），区别于让模型重试</td></tr>
            <tr><td>超出重试上限</td><td>多次修正仍失败</td><td>抛出 <code>UnexpectedModelBehavior</code>，由上层兜底降级</td></tr>
          </tbody>
        </table>
      </div>
      <div class="code-label">Python · ModelRetry 与重试上限</div>
      <pre><code><span class="kw">from</span> pydantic_ai <span class="kw">import</span> Agent, RunContext, ModelRetry

<span class="cm"># retries 控制"因校验/ModelRetry 触发的模型级重试"次数上限</span>
agent = Agent(<span class="st">"openai:gpt-4o"</span>, deps_type=Deps, retries=2)

<span class="kw">@agent.tool</span>
<span class="kw">async def</span> <span class="fn">get_order</span>(ctx: RunContext[Deps], order_id: str) -> dict:
    <span class="st">"""按订单号查询订单。"""</span>
    <span class="kw">if</span> <span class="kw">not</span> order_id.startswith(<span class="st">"ORD-"</span>):
        <span class="cm"># 不是抛异常崩溃，而是告诉模型"哪里错了、该怎么改"</span>
        <span class="kw">raise</span> ModelRetry(<span class="st">"order_id 必须以 ORD- 开头，请向用户确认后重试"</span>)
    order = <span class="kw">await</span> ctx.deps.db.fetch_order(order_id)
    <span class="kw">if</span> order <span class="kw">is</span> <span class="kw">None</span>:
        <span class="kw">raise</span> ModelRetry(<span class="st">f"未找到订单 {order_id}，请核对单号"</span>)
    <span class="kw">return</span> order</code></pre>
      <p class="cjk">这里的关键区分是<strong>"模型级重试"与"系统级重试"的分工</strong>：</p>
      <ul class="hub-list">
        <li><strong>模型级重试（<code>ModelRetry</code> / 校验失败）</strong>：问题出在"模型的决策或输出"，解法是把<em>可读的错误原因</em>反馈给模型，让它换个参数、换个查询、修正格式。这类重试要设上限（如 <code>retries=2</code>），否则可能陷入"改了又错"的循环并烧钱。</li>
        <li><strong>系统级重试</strong>：问题出在"外部世界的抖动"（网络超时、限流），解法是在工具内部用<strong>指数退避 + 抖动</strong>做确定性重试，这类重试对模型透明，不应消耗模型的推理轮次。</li>
      </ul>
      <p class="cjk">为什么这条分工线如此重要？因为把两类重试混为一谈，会同时踩两个坑：一方面，让模型去"重试"一个网络超时纯属浪费——模型改不了网络，只会白白多花一轮推理的 token 与延迟；另一方面，用简单的 <code>try/except</code> 死循环去兜"模型输出格式错误"，则丢掉了 <code>ModelRetry</code> 携带的<em>纠错语义</em>——模型看不到"错在哪、该怎么改"，只会重复同样的错误。<mark class="key2">正确的心智是：能让代码确定性解决的（退避、重连、限流）绝不交给模型；只有需要"重新决策/重新表达"的，才回传给模型</mark>。此外，还应区分<strong>可重试错误</strong>与<strong>不可重试错误</strong>：401 鉴权失败、参数根本非法这类问题，重试多少次都不会好，应快速失败并告警，而非傻等退避。</p>
      <div class="callout warn">
        <span class="label">常见误区与反模式</span>
        <span class="cjk">① <strong>用异常崩溃代替 <code>ModelRetry</code></strong>——直接 <code>raise ValueError</code> 会中断整个运行，而 <code>ModelRetry</code> 给了模型自我纠错的机会。② <strong>重试没有上限</strong>——无上限的模型重试是成本黑洞和延迟杀手，必须封顶并有兜底。③ <strong>把系统抖动交给模型重试</strong>——网络超时让模型"再想一次"毫无意义，只会浪费 token；该在工具层退避重连。④ <strong>吞掉错误信息</strong>——反馈给模型的错误必须<em>可读、可行动</em>，"invalid input"远不如"order_id 必须以 ORD- 开头"有用。</span>
      </div>

      <h3>测试策略：用 pytest 给 Agent 上安全带</h3>
      <p class="cjk">"你怎么测试一个会调 LLM 的系统？"是区分初级与资深的分水岭问题。难点在于 LLM 的<strong>非确定性</strong>与<strong>调用成本</strong>：你不能在 CI 里对着真实模型跑几百个用例——慢、贵、结果还飘。正确的测试金字塔应当分层设计：</p>
      <div class="table-wrap">
        <table>
          <thead>
            <tr><th>测试层级</th><th>测什么</th><th>怎么测</th></tr>
          </thead>
          <tbody>
            <tr><td>单元测试（占比最大）</td><td>工具函数的纯逻辑、依赖注入、校验规则</td><td>注入 Fake 依赖，用 <code>TestModel</code>/<code>FunctionModel</code> 替换真实模型，完全离线、确定、免费</td></tr>
            <tr><td>集成测试</td><td>Agent + 真实工具链的连通性</td><td>少量用例连真实或桩服务，验证端到端不报错</td></tr>
            <tr><td>评估测试（Eval）</td><td>输出质量、事实性、格式合规率</td><td>用小而精的评估集打分，关注趋势而非单次绝对值（见第 10 章 RAG 评估）</td></tr>
          </tbody>
        </table>
      </div>
      <p class="cjk">PydanticAI 为可测试性做了两个关键设计：一是前述的<strong>依赖注入</strong>让外部资源可被替换；二是内置了 <code>TestModel</code> 与 <code>FunctionModel</code> 两个"假模型"，让你在不触碰真实 API 的前提下，用确定性的方式驱动 Agent 走完流程。</p>
      <div class="code-label">Python · pytest 单元测试（离线、确定、无网络）</div>
      <pre><code><span class="kw">import</span> pytest
<span class="kw">from</span> pydantic_ai <span class="kw">import</span> Agent
<span class="kw">from</span> pydantic_ai.models.test <span class="kw">import</span> TestModel

<span class="kw">class</span> <span class="fn">FakeDB</span>:
    <span class="kw">async def</span> <span class="fn">fetch_order</span>(self, order_id):
        <span class="kw">return</span> {<span class="st">"id"</span>: order_id, <span class="st">"amount"</span>: 100}  <span class="cm"># 固定桩数据</span>

<span class="kw">def</span> <span class="fn">test_get_order_tool</span>():
    <span class="cm"># override_model：把真实 LLM 换成 TestModel，不发任何网络请求</span>
    <span class="kw">with</span> agent.override(model=TestModel(), deps=Deps(db=FakeDB())):
        result = agent.run_sync(<span class="st">"查订单 ORD-1"</span>)
    <span class="kw">assert</span> result.output <span class="kw">is</span> <span class="kw">not</span> <span class="kw">None</span>       <span class="cm"># 断言流程走通、结构合法</span>

<span class="cm"># FunctionModel 可精确编排"模型第 n 步该调哪个工具、返回什么"</span>
<span class="cm"># 适合测试多轮工具调用、重试路径等复杂控制流</span></code></pre>
      <div class="callout tip">
        <span class="label">面试要点</span>
        <span class="cjk">强调两条原则：<strong>确定性优先</strong>——绝大多数用例用假模型跑，保证 CI 快而稳；<strong>关注可测的东西</strong>——测"工具逻辑对不对、结构合不合法、重试路径通不通"，而非苛求"模型每次都答对"。把"非确定性系统"用"确定性测试 + 抽样评估"两条腿覆盖，是标准的高分框架。</span>
      </div>

      <h3>流式输出与异步：延迟体验的两把钥匙</h3>
      <p class="cjk">生产 Agent 的用户体验很大程度取决于<strong>首字延迟</strong>与<strong>吞吐</strong>，对应两项能力：流式（streaming）与异步（async）。二者常被混为一谈，但解决的是不同问题。</p>
      <ul class="hub-list">
        <li><strong>流式</strong>解决的是<em>感知延迟</em>：模型边生成边吐字，用户在几百毫秒内看到第一段文字，而非干等整段生成完。PydanticAI 提供 <code>run_stream</code>，甚至能<strong>在流式过程中增量校验结构化输出</strong>——边流边构建 Pydantic 对象。</li>
        <li><strong>异步</strong>解决的是<em>并发吞吐</em>：Agent 大量时间耗在等待模型/工具的 I/O 上，用 <code>async/await</code> 能让单进程在等待期间处理其他请求，显著提升 QPS。PydanticAI 原生 async 优先，<code>run</code> 是协程，<code>run_sync</code> 只是同步封装。</li>
      </ul>
      <div class="code-label">Python · 异步 + 流式</div>
      <pre><code><span class="kw">import</span> asyncio

<span class="kw">async def</span> <span class="fn">main</span>():
    <span class="cm"># 异步：不阻塞事件循环，可与其他协程并发</span>
    <span class="kw">async with</span> agent.run_stream(<span class="st">"用三点总结这份报销制度"</span>) <span class="kw">as</span> resp:
        <span class="kw">async for</span> chunk <span class="kw">in</span> resp.stream_text(delta=<span class="kw">True</span>):
            <span class="kw">print</span>(chunk, end=<span class="st">""</span>, flush=<span class="kw">True</span>)  <span class="cm"># 增量吐字，降低首字延迟</span>

asyncio.run(main())</code></pre>
      <div class="callout warn">
        <span class="label">常见误区</span>
        <span class="cjk">① <strong>在 async 代码里调用阻塞 IO</strong>——工具里用同步的 <code>requests</code> 会卡死整个事件循环，async 场景应全程使用异步客户端。② <strong>流式与结构化输出的取舍</strong>——需要严格结构化时，"边流边校验"实现更复杂；若下游必须拿到完整对象，有时不流式反而更简单可靠。③ <strong>把流式当性能银弹</strong>——流式改善的是"感知延迟"，并不减少总 token 数与总耗时。</span>
      </div>

      <h3>FastAPI 生产部署：把 Agent 包成服务</h3>
      <p class="cjk">PydanticAI 与 FastAPI 是天作之合——同一套 Pydantic 模型，既是 Agent 的 <code>output_type</code>，又能直接作为 FastAPI 的响应模型，实现"一次定义，两端复用"。部署时要把握几个生产要点：</p>
      <div class="code-label">Python · 把 Agent 暴露为 FastAPI 接口</div>
      <pre><code><span class="kw">from</span> fastapi <span class="kw">import</span> FastAPI, Depends
<span class="kw">from</span> fastapi.responses <span class="kw">import</span> StreamingResponse

app = FastAPI()

<span class="cm"># 复用 Agent 的输出模型作为 API 响应模型：一处定义，两端类型安全</span>
<span class="kw">@app.post</span>(<span class="st">"/score"</span>, response_model=ResumeScore)
<span class="kw">async def</span> <span class="fn">score</span>(payload: dict, db=Depends(get_db)):
    result = <span class="kw">await</span> agent.run(payload[<span class="st">"text"</span>], deps=Deps(db=db))
    <span class="kw">return</span> result.output          <span class="cm"># 已是 ResumeScore，FastAPI 直接序列化</span>

<span class="cm"># 流式接口：把 Agent 的增量输出透传给前端</span>
<span class="kw">@app.post</span>(<span class="st">"/chat"</span>)
<span class="kw">async def</span> <span class="fn">chat</span>(payload: dict):
    <span class="kw">async def</span> <span class="fn">gen</span>():
        <span class="kw">async with</span> agent.run_stream(payload[<span class="st">"q"</span>]) <span class="kw">as</span> resp:
            <span class="kw">async for</span> delta <span class="kw">in</span> resp.stream_text(delta=<span class="kw">True</span>):
                <span class="kw">yield</span> delta
    <span class="kw">return</span> StreamingResponse(gen(), media_type=<span class="st">"text/event-stream"</span>)</code></pre>
      <p class="cjk">生产部署的检查清单（面试常被追问"上线要注意什么"）：</p>
      <ul class="hub-list">
        <li><strong>可观测性</strong>：接入结构化日志与追踪（PydanticAI 原生支持 OpenTelemetry / Logfire 风格的埋点），记录每次运行的工具调用、重试次数、token 用量，出问题能定位。</li>
        <li><strong>超时与并发控制</strong>：为单次运行设总超时、为工具设分项超时；用信号量或队列限制并发，防止把下游模型 API 打到限流。</li>
        <li><strong>成本护栏</strong>：限制 <code>MAX_STEPS</code> 与 <code>retries</code>，对超长上下文做裁剪（见第 4 章），并对单请求 token 预算设上限。</li>
        <li><strong>优雅降级</strong>：模型不可用或超预算时，返回确定性兜底而非把异常抛给用户。</li>
        <li><strong>无状态化</strong>：把会话/记忆放到外部存储，服务本身无状态，才能水平扩容。</li>
      </ul>
      <p class="cjk">这套接口设计里藏着 PydanticAI 最优雅的一点：<mark class="key">同一个 <code>ResumeScore</code> 模型，在 Agent 侧是"约束模型输出的契约"，在 API 侧是"约束响应体的契约"</mark>。两端共享类型，意味着自动生成的 OpenAPI 文档、前端据此生成的 TypeScript 类型、后端的校验逻辑全部同源，改一处字段，编译器会替你把所有该改的地方都标红。这种"单一事实来源（single source of truth）"正是类型驱动开发的复利所在——它把"接口文档和实现不一致"这个团队协作里的经典痛点，从根上消除了。部署形态上，无状态化后既可以用传统的容器 + 负载均衡横向扩容，也能放到 Serverless；后者要额外留意<strong>冷启动</strong>与<strong>长连接（流式）</strong>的兼容性，长流式响应在部分函数计算平台上有超时限制，需要评估。</p>

      <h3>消息历史与多轮对话：把"记忆"做成可控的状态</h3>
      <p class="cjk">单次 <code>run</code> 是无记忆的，但真实产品几乎都是多轮对话。PydanticAI 用 <strong>消息历史（message history）</strong>把上一轮的完整交互（用户输入、模型响应、工具调用与结果）序列化出来，下一轮通过 <code>message_history</code> 传回去，形成连续会话。这套设计的工程含义值得展开：</p>
      <div class="code-label">Python · 多轮对话的状态传递</div>
      <pre><code>r1 = agent.run_sync(<span class="st">"我叫小明，帮我记一下"</span>)
<span class="cm"># all_messages() 拿到本轮完整消息（含工具调用），可序列化后落库</span>
history = r1.all_messages()

<span class="cm"># 下一轮把历史传回，模型即可"记得"上下文</span>
r2 = agent.run_sync(<span class="st">"我叫什么？"</span>, message_history=history)
<span class="kw">print</span>(r2.output)   <span class="cm"># 小明</span></code></pre>
      <p class="cjk">把记忆做成<strong>显式的、可序列化的状态</strong>，而不是藏在某个全局对象里，带来两个生产级好处：一是<strong>无状态服务</strong>——会话历史存到 Redis/数据库，任意实例都能续接对话，天然支持水平扩容；二是<strong>可控裁剪</strong>——历史会随轮次膨胀撑爆上下文，你可以在回传前做摘要压缩或按 token 预算截断（记忆与上下文管理的系统方法见第 4、5 章）。<mark class="key2">"记忆是外置的状态而非框架的黑箱"，这一点想清楚了，你才能回答"多实例部署时对话怎么保持连贯"这类系统设计题</mark>。</p>

      <h3>可观测性与调试：让黑箱变成可复盘的轨迹</h3>
      <p class="cjk">Agent 出问题时最令人抓狂的是"不知道它当时在想什么"。生产系统必须让每一次运行都留下<strong>可复盘的轨迹</strong>：模型看到了什么上下文、决定调用哪个工具、传了什么参数、工具返回了什么、重试了几次、最终 token 花了多少。PydanticAI 在设计上原生支持基于 OpenTelemetry 的埋点（配合 Pydantic 团队的 Logfire 或任意兼容后端），把这些信息结构化地导出。</p>
      <ul class="hub-list">
        <li><strong>结构化追踪（tracing）</strong>：把一次 <code>run</code> 展开成一棵 span 树，每次模型调用、每次工具执行都是一个 span，配合耗时与 token 计数，能一眼看出瓶颈在模型还是在某个慢工具。</li>
        <li><strong>结果对象自带诊断信息</strong>：<code>result.usage()</code> 给出 token 用量，<code>result.all_messages()</code> 给出完整消息链——这两者是线上排障与成本核算的第一手材料。</li>
        <li><strong>调试回放</strong>：把出错请求的消息历史存下来，用 <code>FunctionModel</code> 在本地离线复现那条决策路径，比盲猜高效得多。</li>
      </ul>
      <div class="callout warn">
        <span class="label">常见误区</span>
        <span class="cjk">① <strong>只记最终输出不记中间过程</strong>——Agent 的 bug 大多藏在"某一步工具调用"，缺了中间轨迹等于盲人摸象。② <strong>日志里明文打印敏感数据</strong>——工具参数、依赖里常含用户隐私或密钥，埋点时要脱敏。③ <strong>不统计 token 用量</strong>——不观测成本，一次异常的长循环就可能悄悄烧掉大额账单。</span>
      </div>

      <h3>与 smolagents 的深度对比：不是谁更好，而是各司其职</h3>
      <p class="cjk">前面的表格给出了场景速查，这里补充"为什么"的机制层面对比，让你在面试里能讲出取舍背后的道理。两者代表了 Agent 框架的<strong>两种哲学</strong>：</p>
      <ul class="hub-list">
        <li><strong>smolagents——"代码即动作"（code-as-action）</strong>：让模型直接写 Python 代码并执行，动作空间极其灵活，适合探索式、需要自由组合工具的任务，也是理解 Agent 原理的最佳教具（见第 8 章）。代价是执行需要沙箱、输出难以严格约束、可预测性偏低。</li>
        <li><strong>PydanticAI——"类型即契约"（type-as-contract）</strong>：用结构化输出、依赖注入、显式重试把 Agent 的行为收进类型系统与工程规范里，适合<strong>确定性要求高、需长期维护、要接入现有服务</strong>的生产系统。代价是灵活度不如让模型自由写代码。</li>
      </ul>
      <p class="cjk">一句话总结这条选型主线：<mark class="key">用 smolagents 想清楚"能不能做、怎么做"，用 PydanticAI 把"做对、做稳、做得可维护"落地</mark>。二者不是替代关系——很多团队用 smolagents 做原型验证，再用 PydanticAI 重写为生产服务。面试时能说出"我会分阶段选型"，远比站队某个框架更能体现工程判断力。</p>

          <thead>
            <tr><th>对比维度</th><th>smolagents</th><th>PydanticAI</th></tr>

            <tr><td>核心范式</td><td>代码即动作，模型写代码执行</td><td>类型即契约，结构化输入输出</td></tr>
            <tr><td>输出可控性</td><td>弱（自由文本/代码结果）</td><td>强（Pydantic 校验 + 自动重试）</td></tr>
            <tr><td>可测试性</td><td>依赖沙箱，较难做纯单测</td><td>DI + 假模型，天然易测</td></tr>
            <tr><td>与既有服务集成</td><td>需自行封装</td><td>与 FastAPI/Pydantic 生态无缝</td></tr>
            <tr><td>心智负担</td><td>低，几行即可跑通</td><td>需先设计类型与依赖</td></tr>
            <tr><td>最佳定位</td><td>原理教学、探索式原型</td><td>长期维护的生产服务</td></tr>

      <h3>面试追问链</h3>
      <p class="cjk">围绕"Agent 工程化"，面试官常沿着"能跑 → 能测 → 能上线 → 能维护"的路径层层加压，提前演练这条链：</p>
      <ul class="hub-list">
        <li><strong>Q1：</strong>PydanticAI 和 smolagents 有什么区别？→ 从"类型即契约 vs 代码即动作"两种哲学切入，落到结构化输出与生产可维护性。</li>
        <li><strong>Q2：</strong>为什么结构化输出这么重要？→ 讲"非确定性文本 vs 确定性数据结构"的鸿沟，以及把解析责任前移到框架层。</li>
        <li><strong>Q3：</strong>模型输出不符合结构怎么办？→ 引出校验失败自动重试、<code>ModelRetry</code>，并区分模型级与系统级重试。</li>
        <li><strong>Q4：</strong>你怎么测试这套系统？→ 抛出测试金字塔、依赖注入 + <code>TestModel</code>/<code>FunctionModel</code>、"确定性测试 + 抽样评估"。</li>
        <li><strong>Q5：</strong>上生产还要注意什么？→ 收尾到可观测性、超时并发、成本护栏、优雅降级、无状态化，并顺带讲流式与异步的区别。</li>
      </ul>

      <div class="callout tip">
        <span class="label">本章小结</span>
        <span class="cjk">PydanticAI 的价值可以浓缩成一句话：<strong>把 Agent 的不确定性关进类型系统与工程规范的笼子里</strong>。它以"类型即契约"为核心，用 <code>output_type</code> 保证结构合法、用依赖注入换来可测试与可复用、用 <code>ModelRetry</code> 与重试上限管住错误、用 <code>TestModel</code> 让非确定性系统可被确定性地测试、用与 FastAPI 的天然亲和把 Agent 平滑包成生产服务，并用流式与异步分别优化感知延迟与并发吞吐。记住选型主线：<mark class="key2">smolagents 帮你想清楚，PydanticAI 帮你做稳当</mark>——从"能跑的 Demo"到"能维护的生产系统"，中间隔着的正是这一整套工程化能力。</span>
