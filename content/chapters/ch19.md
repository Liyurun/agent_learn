      <h3>从 LLM 到 LMM：让 Agent"看见"</h3>
      <p class="cjk">多模态大模型（LMM，Large Multimodal Model）能同时理解<strong>图像 + 文本</strong>：读懂截图、图表、文档版面、UI 元素。这让 Agent 不再依赖结构化 API，而是像人一样<strong>看屏幕做事</strong>——对那些没有 API、没有可访问性树（accessibility tree）、只能"用眼睛看"的老旧软件尤其有价值。它把 Agent 的可达范围，从"有接口的世界"扩展到了"有屏幕的世界"。</p>
      <p class="cjk">要理解它的能力，先拆开"视觉理解"这一层到底包含什么。一个能操作电脑的 Agent，它的视觉栈通常要同时具备三种能力：<strong>识别（这是什么控件——按钮、输入框、下拉菜单、复选框）</strong>、<strong>阅读（OCR：读出控件上的文字、页面里的正文）</strong>、<strong>布局理解（这些元素的空间关系——谁在谁上面、哪个是当前激活的标签页）</strong>。三者缺一不可：只会 OCR 不懂布局，它读得出字却不知道点哪；只懂布局不会阅读，它找得到框却不知道框里要填什么。</p>
      <p class="cjk">这里还藏着一个常被忽视的工程细节——<strong>分辨率与坐标系</strong>。截图有原始像素尺寸，但模型看到的往往是被缩放/切分后的图，模型输出的坐标需要正确<strong>映射回真实屏幕坐标</strong>，任何缩放比例的错配都会让点击整体偏移。此外高分辨率截图意味着更多图像 token，而图像 token 通常比等量文本 token 更"重"。于是就有了一个绕不开的权衡：<mark class="key">分辨率高，看得清但又贵又慢；分辨率低，省钱但可能看不清小字小控件</mark>。成熟做法是按需调节——概览时用低清、需要读细节时对关注区域局部放大，而不是全程顶格高清。</p>

      <div class="callout tip">
        <span class="label">面试要点</span>
        <span class="cjk">被问"Computer Use 和普通 RAG Agent 的本质区别"时，抓住一句话：<mark class="key2">普通 Agent 的观测是文本、动作是 API 调用；Computer Use 的观测是像素截图、动作是鼠标键盘坐标</mark>。观测与动作空间的形态变了，一切难点（定位、可靠性、成本）都由此派生。</span>
      </div>

      <h3>Computer Use 的核心循环：截图循环</h3>
      <p class="cjk">GUI Agent 的工作方式是一个<strong>感知-决策-行动</strong>循环：<mark class="key2">截图 → 理解界面 → 定位目标元素坐标 → 点击 / 输入 → 再截图确认</mark>，如此往复直到完成任务。这本质上还是 ReAct（见第 3 章），只不过"观察"变成了截图、"动作"变成了鼠标键盘操作。这个循环有个专门的名字——<strong>截图循环（screenshot loop）</strong>，它是所有 Computer Use 系统的心跳。</p>
      <div class="interactive" id="multimodalPanel"></div>

      <figure class="diagram"><pre class="mermaid">

      <p class="cjk">这个循环里最容易被忽视、却最关键的一环是<strong>"再截图确认"</strong>。人类点完按钮会下意识看一眼"弹窗出来了没"，Agent 也必须如此：动作执行后必须重新截图，验证界面是否真的进入了预期状态。<mark class="key">没有闭环验证的 GUI Agent，就是在"盲操作"——它以为点中了，其实点空了，然后在错误的界面上继续叠加错误。</mark>这也是为什么截图循环无法省略中间的截图步骤，哪怕它很贵。</p>

      <h3>grounding：从"知道点什么"到"知道点哪里"</h3>
      <p class="cjk">这是 Computer Use 最核心的技术难点，也是面试最爱深挖的地方。<strong>grounding（视觉定位/接地）</strong>指的是：把一个语义意图（"点击那个蓝色的登录按钮"）转换成一个<strong>可执行的精确像素坐标</strong>（如屏幕上的 x=640, y=380）。模型"知道该点登录按钮"是理解问题，"知道登录按钮在屏幕的哪个像素"是 grounding 问题——这两件事的难度完全不在一个量级。</p>
      <p class="cjk">grounding 的主流实现路径有几条，各有取舍：</p>
      <div class="table-wrap">
        <table>
          <thead><tr><th>路径</th><th>做法</th><th>优点</th><th>短板</th></tr></thead>
          <tbody>
            <tr><td>纯视觉直接输出坐标</td><td>让 LMM 直接吐出点击坐标</td><td>通用、不依赖底层接口</td><td>精度是最大瓶颈，易点偏</td></tr>
            <tr><td>Set-of-Mark 标注</td><td>先给可交互元素编号打框，模型只需选"点几号"</td><td>把坐标回归降级为选择题，更稳</td><td>依赖前置元素检测的质量</td></tr>
            <tr><td>可访问性树 / DOM</td><td>读取结构化控件树，按元素定位</td><td>精确、可靠</td><td>很多软件不提供，网页可用 OS 应用常缺</td></tr>
            <tr><td>混合方案</td><td>能拿结构化就用，拿不到回退纯视觉</td><td>兼顾可靠与通用</td><td>工程复杂度高</td></tr>
          </tbody>
        </table>
      </div>
      <p class="cjk">面试里如果你能说出"我会优先用 Set-of-Mark 或可访问性树把 grounding 从坐标回归降级成选择题，只有在拿不到结构化信息时才回退到纯视觉坐标预测"，就展现了对这条难点的真实理解，而不是停留在"让模型点一下"的表面。</p>

      <h3>专用 GUI 模型 vs 通用多模态模型</h3>
      <p class="cjk">实现 Computer Use，业界有两条技术路线，理解它们的分野能让你的回答更有层次：</p>
      <ul class="hub-list">
        <li><strong>通用多模态大模型 + 工具封装</strong>：直接用一个强大的通用 LMM，配上"截图输入、坐标动作输出"的工具协议。优点是通用、跟得上底座模型的能力升级；短板是通用模型未必在"精确点击哪个像素"这件事上被专门优化过，grounding 精度可能偏弱。</li>
        <li><strong>面向 GUI 专门训练/微调的模型</strong>：用大量"截图—元素坐标"配对数据专门训练，让模型在界面元素定位上更精准。优点是 grounding 更稳；短板是需要专门的数据与训练投入，且泛化到没见过的界面类型时可能打折。</li>
      </ul>
      <p class="cjk">现实中的强系统往往<strong>两者结合</strong>：用通用模型做高层理解与规划，用更擅长定位的能力（专用模型或 Set-of-Mark 等结构化手段）解决"点哪里"。这背后是一条通用心法——<mark class="key">把"理解要做什么"和"定位在哪里做"解耦成两个可以分别优化的子问题</mark>，而不是指望一个模型同时把两件难事都做到完美。值得强调的是：无论走哪条路线，<strong>"截图—理解—定位—操作—再截图"</strong>这个闭环骨架都不变，变化的只是每一环用什么组件实现。这也解释了为什么理解截图循环这个抽象，比记住某个具体产品名更重要——产品会迭代，循环不会变。</p>

      <h3>GUI 操作的动作空间</h3>
      <p class="cjk">Computer Use 的动作空间比 API 调用丰富也危险得多。典型动作包括：<strong>点击（单击/双击/右键）、输入文本、按快捷键、滚动、拖拽、悬停、等待</strong>。相比一次干净的函数调用，这些动作有两个本质区别：<strong>① 有连续状态与副作用</strong>——每个动作都改变了屏幕，下一步依赖上一步的结果；<strong>② 难以原子回滚</strong>——点错了删除按钮，文件可能就没了。因此成熟系统会给危险动作（删除、提交、支付）加确认关卡，并偏好"可撤销优先"的动作序列（呼应第 1 章的人在环路与自主性光谱）。</p>

      <h3>长程操作：目标不漂移是最大考验</h3>
      <p class="cjk"><strong>长程操作（long-horizon control）</strong>指一个任务要跨越几十甚至上百个动作、跨多个界面/软件才能完成（如"把这份表格里的数据逐条录入到那个系统并生成报告"）。它的核心难点不是单步准不准，而是<strong>目标在漫长步骤中会逐渐漂移</strong>：</p>
      <ul class="hub-list">
        <li><strong>误差累积</strong>：每步 95% 正确，连做 30 步的整体成功率会被指数级拉低——这是长程任务成功率骤降的数学根源。</li>
        <li><strong>上下文膨胀</strong>：每一步都塞进一张高分辨率截图，几十步后上下文爆炸，早期目标被淹没或挤出窗口（呼应第 4 章上下文管理）。</li>
        <li><strong>状态跟丢</strong>：跨软件切换后，Agent 忘了"我原本要干嘛""进行到哪一步了"。</li>
        <li><strong>无法从错误中恢复</strong>：走错一步后不会回退，反而在错误路径上越陷越深。</li>
      </ul>
      <p class="cjk">应对手段包括：显式维护一份<strong>任务待办清单/进度笔记</strong>（把"还要做什么"外置到上下文里，抗漂移）、<strong>分层规划</strong>（高层计划 + 低层执行分离）、<strong>定期自检</strong>（每隔几步截图核对是否还在正轨）、以及<strong>失败重试与回退</strong>机制。这些手段的共同思想是：<mark class="key">不指望模型一口气不出错，而是设计能"察觉偏离并纠正"的闭环。</mark></p>

      <h3>用代码把截图循环讲清楚</h3>
      <p class="cjk">面试白板上，若能写出截图循环的骨架代码，会比任何描述都有说服力。下面这段伪代码浓缩了前面所有要点——闭环验证、grounding、进度笔记、危险动作确认、步数上限：</p>
      <div class="code-label">Python · Computer Use 截图循环骨架</div>
      <pre><code><span class="cm"># 目标外置为进度笔记，抗长程漂移</span>
notes = <span class="fn">TaskNotes</span>(goal)
<span class="kw">for</span> step <span class="kw">in</span> <span class="fn">range</span>(MAX_STEPS):
    screenshot = <span class="fn">capture_screen</span>()                 <span class="cm"># 感知：每步重新截图，不记死坐标</span>
    plan = <span class="fn">lmm</span>(screenshot, notes)               <span class="cm"># 理解界面 + 参考进度笔记决策</span>
    <span class="kw">if</span> plan.done:
        <span class="kw">return</span> plan.result                      <span class="cm"># 终止：任务完成</span>
    target = <span class="fn">ground</span>(screenshot, plan.intent)    <span class="cm"># grounding：意图→精确坐标/元素</span>
    <span class="kw">if</span> plan.action.is_risky:                     <span class="cm"># 危险动作（删除/支付）人工确认</span>
        <span class="fn">ask_human</span>(plan.action)
    <span class="fn">execute</span>(plan.action, target)               <span class="cm"># 行动：点击/输入/滚动</span>
    after = <span class="fn">capture_screen</span>()                     <span class="cm"># 闭环验证：动作后再截图</span>
    <span class="kw">if</span> <span class="kw">not</span> <span class="fn">verify</span>(after, plan.expect):        <span class="cm"># 没进入预期状态则重试或回退</span>
        notes.<span class="fn">record_failure</span>(step)
    notes.<span class="fn">update</span>(after)                        <span class="cm"># 更新进度，供下一步参考</span>
<span class="kw">return</span> <span class="fn">fallback</span>()                            <span class="cm"># 兜底：达步数上限仍未完成</span></code></pre>
      <p class="cjk">逐行看，它回答了几个生产必答题：<strong>为什么每步都重新截图</strong>（界面会变，记死坐标必崩）？<strong>为什么动作后要 verify</strong>（防止盲操作叠加错误）？<strong>为什么要 notes</strong>（把目标外置，抵抗长程漂移与上下文膨胀）？<strong>为什么危险动作要 ask_human</strong>（不可逆操作要留人工闸门）？<strong>为什么要 MAX_STEPS</strong>（防止卡死循环烧钱，呼应第 1 章）？把这几个"为什么"讲透，你就从"知道 Computer Use 是什么"升级到了"知道怎么把它做可靠"。</p>

      <div class="callout warn">
        <span class="label">最硬的三块骨头</span>
        <span class="cjk"><strong>坐标定位精度</strong>——"点这个按钮"要落到准确像素，是最易失误处；<strong>长程操作</strong>——跨多个界面保持目标不漂移；<strong>成本</strong>——图像 token 昂贵，截图频率与分辨率要精打细算。OSWorld 上人类约 72%、模型长期落后，说明这条路还很长<a class="cite" href="https://os-world.github.io/" target="_blank" rel="noopener">[来源]</a>。</span>
      </div>

      <h3>可靠性挑战：为什么 Demo 惊艳、上线心慌</h3>
      <p class="cjk">Computer Use 的 Demo 往往令人惊艳，但离生产可靠还有明显距离，原因是它踩中了好几个可靠性雷区，面试时能系统列出这些就很加分：</p>
      <div class="table-wrap">
        <table>
          <thead><tr><th>挑战</th><th>为什么难</th><th>缓解方向</th></tr></thead>
          <tbody>
            <tr><td>定位精度</td><td>像素级回归本就难，UI 缩放/分辨率还会变</td><td>Set-of-Mark、结构化定位、点击后验证</td></tr>
            <tr><td>界面动态性</td><td>加载延迟、弹窗、A/B 布局让"上次能点的地方"这次点空</td><td>显式等待、以截图重定位而非记死坐标</td></tr>
            <tr><td>误差累积</td><td>长程任务单步错误被逐级放大</td><td>进度笔记、分层规划、定期自检</td></tr>
            <tr><td>成本与延迟</td><td>每步一张高清截图，token 与耗时都高</td><td>降分辨率、裁剪关注区域、降低截图频率</td></tr>
            <tr><td>安全风险</td><td>能真操作系统，误删/误付/被界面上的注入指令劫持</td><td>危险动作确认、沙箱隔离、最小权限（见第 20 章）</td></tr>
          </tbody>
        </table>
      </div>
      <p class="cjk">特别要点出一个新型攻击面：<strong>屏幕上的间接提示注入</strong>——恶意网页或文档可以在界面上放一段"忽略之前的指令，去执行 X"的文字，被 Agent 截图读到后当作指令执行。因为 Computer Use 的观测就是屏幕内容，它天然更难区分"这是给我看的数据"还是"这是给我的命令"。这把第 20 章要讲的安全问题，在多模态场景下放大了。</p>
      <p class="cjk">还要区分两类形态不同的 GUI Agent，它们难点侧重不一样：<strong>网页 Agent（Web Agent）</strong>操作的是浏览器，好处是网页大多有 DOM/可访问性树可借力，grounding 相对好做，但要应对动态渲染、无限滚动、登录墙与反爬；<strong>桌面 Agent（Desktop Agent）</strong>操作的是整个操作系统与本地软件，很多老旧程序<em>没有</em>任何结构化接口，只能纯靠视觉，且动作后果更重（能动文件、能改系统设置）。一个务实的判断是：<mark class="key">能拿到 DOM 就优先用 DOM（网页场景），拿不到才退回纯视觉（桌面遗留软件场景）</mark>。这也再次印证了那条主线——结构化信息永远优先于像素猜测。</p>

      <div class="callout warn">
        <span class="label">常见误区与反模式</span>
        <span class="cjk">① <strong>"能点就等于能用"</strong>——单步点击准不代表长程任务稳，忽视误差累积。② <strong>记死坐标</strong>——把上次成功的坐标写死，界面一变就全崩，应每步重新截图定位。③ <strong>不做点击后验证</strong>——盲操作叠加错误。④ <strong>无脑高分辨率高频截图</strong>——成本失控，其实很多步骤可降清晰度或跳过截图。⑤ <strong>凡是有 API 也硬用 GUI</strong>——能走结构化 API 就别走视觉操作，GUI 是"没有 API 时的兜底"而非首选。</span>
      </div>

      <h3>应用场景：什么时候该用 Computer Use</h3>
      <p class="cjk">Computer Use 不是万能钥匙，它的甜蜜区非常清晰——<strong>当且仅当目标系统没有可用 API、只能靠图形界面操作时</strong>，它的价值才无可替代：</p>
      <ul class="hub-list">
        <li><strong>老旧/封闭软件自动化</strong>：没有 API 的企业内部系统、桌面 ERP、遗留客户端，人怎么点它就怎么点。</li>
        <li><strong>跨应用流程</strong>：需要在浏览器、表格、邮件、内部系统之间来回搬运数据的"数字文员"类工作。</li>
        <li><strong>网页端到端操作</strong>：订票、比价、填表、信息采集等浏览器任务（对应 WebArena 那类形态）。</li>
        <li><strong>软件测试与 QA</strong>：模拟用户操作跑端到端回归，发现 UI 层的问题。</li>
        <li><strong>无障碍辅助</strong>：帮助行动不便的用户用自然语言驱动电脑。</li>
      </ul>
      <p class="cjk">反过来，凡是能通过结构化 API、数据库、命令行完成的任务，都应优先走那些更快、更便宜、更可靠的路径。<mark class="key">Computer Use 的定位是"通用兜底层"：它保证了 Agent 在没有任何专用接口时，仍然有办法把事做完</mark>——但这份通用性是用成本、速度和可靠性换来的，不到必要时不轻易动用。</p>

      <h3>怎么评估一个 Computer Use Agent</h3>
      <p class="cjk">面试常有一记"回马枪"：讲完能力后追问"那你怎么衡量它做得好不好？"这时要能把第 18 章的评估思想落到多模态场景。核心原则是<strong>看终态、不看自述</strong>——不要相信 Agent"我已经完成了"的声明，而要用脚本检查环境的客观结果：文件内容对不对、系统设置改没改、订单是否真的被创建。这正是 OSWorld、WebArena 这类基准采用的判定方式（见第 18 章）。除了成败，还应关注几个专属于 GUI 场景的维度：</p>
      <ul class="hub-list">
        <li><strong>步数效率</strong>：完成任务用了多少步、有没有大量无效点击与绕路，反映动作规划质量。</li>
        <li><strong>稳定性（多次重复）</strong>：同一任务跑多次的成功率与方差——GUI 的随机性更大，单次成功尤其不能说明问题，用 pass^k 思路暴露"靠运气"的假象。</li>
        <li><strong>恢复能力</strong>：故意注入一次点错或一个意外弹窗，看它能否察觉并纠偏，而非在错误路径上一条道走到黑。</li>
        <li><strong>安全红线</strong>：在含有诱导性文字的界面上测试，看它会不会被屏幕上的注入指令带跑。</li>
      </ul>
      <p class="cjk">把这套评估讲出来，你就完成了从"炫能力"到"讲工程"的闭环——因为<mark class="key2">一个 Computer Use Agent 能不能上生产，最终不取决于它 Demo 有多惊艳，而取决于它在这些维度上的可复现表现。</mark></p>

      <div class="callout tip">
        <span class="label">面试高分收口</span>
        <span class="cjk">当被问"你怎么看 Computer Use 的现状"，别只喊口号说它多强。高分答法是给出一个有分寸的判断：<strong>它打开了"操作一切软件"的想象空间，但当前在长程可靠性、定位精度和成本上仍有明显短板，因此更适合"人盯着、可回退、动作可控"的半自主场景，而非无人值守的全自主部署</strong>。能同时讲清"能力上限"和"落地边界"，比单纯吹能力更能体现你对这项技术的成熟判断——这正是第 1 章"先判断需要几级自主"在多模态场景的延续。</span>
      </div>

      <h3>面试追问链</h3>
      <p class="cjk">多模态 Agent 的追问链会从"是什么"逐步逼到"怎么把它做可靠"：</p>
      <ul class="hub-list">
        <li><strong>Q1：</strong>什么是 Computer Use / GUI Agent？→ 从"看屏幕、用鼠标键盘操作"切入，点明观测是截图、动作是坐标。</li>
        <li><strong>Q2：</strong>它的核心循环是怎样的？→ 讲截图循环：截图→理解→定位→操作→再截图确认，本质是多模态版 ReAct。</li>
        <li><strong>Q3：</strong>最难的技术点是什么？→ grounding（语义意图→精确像素坐标），展开 Set-of-Mark / 可访问性树 / 纯视觉的取舍。</li>
        <li><strong>Q4：</strong>长程任务为什么容易失败？→ 误差累积、上下文膨胀、目标漂移；用进度笔记 + 分层规划 + 定期自检缓解。</li>
        <li><strong>Q5：</strong>要上生产还有哪些坑？→ 界面动态性、成本延迟、屏幕上的间接提示注入等安全风险。</li>
        <li><strong>Q6：</strong>什么场景才值得用它？→ 没有 API 的老旧软件、跨应用流程；有 API 就别硬用 GUI。</li>
      </ul>

      <div class="callout tip">
        <span class="label">本章小结</span>
        <span class="cjk">多模态 Agent 把观测从文本升级为像素截图、把动作从 API 调用升级为鼠标键盘操作，从而能操作一切"有屏幕"的软件。它的心跳是<strong>截图循环</strong>，核心难点是 <strong>grounding</strong>（语义意图到精确坐标），最大考验是<strong>长程操作中的目标漂移与误差累积</strong>。工程上要靠 Set-of-Mark/结构化定位提精度、进度笔记与分层规划抗漂移、降分辨率与降频控成本、危险动作确认与沙箱保安全。记住它的定位：<mark class="key2">Computer Use 是"没有 API 时的通用兜底"，能力惊艳但代价高昂，能走结构化接口就别走视觉操作。</mark></span>
      </div>
