    <section class="chapter" id="ch11">
      <h2 class="chap-title"><span class="kicker">11</span>评估与可观测性</h2>
      <p class="cjk"><mark class="key2">"你怎么知道你的 Agent 是好的？"</mark>——这是区分"做过 demo"和"做过产品"的分水岭问题。Agent 的输出不确定、路径多样，不能用传统单元测试的精确匹配来评，必须建立系统的评估体系。答不好这题，再花哨的架构都会被打折。面试官问这句话，真正想确认的是：你有没有把"感觉不错"翻译成"可度量、可回归、可归因"的工程能力。</p>
      <div class="interactive-mini" id="insightBacklink-ch11"></div>

      <p class="cjk">本章沿着一条主线展开：<strong>先想清楚评估什么（结果与过程），再解决怎么造评估集，接着攻克 LLM-as-Judge 的偏差、轨迹与组件级评估、RAG 专属指标，最后把可观测性、CI 回归和线上监控串成一个自我进化的闭环。</strong>贯穿始终的原则是：<mark class="key">评估不是上线前的一次性检查，而是与系统同寿命的基础设施</mark>。</p>

      <h3>评估什么：结果 + 过程</h3>
      <p class="cjk">传统软件测的是"给定输入，输出是否等于期望值"；Agent 测的是"给定目标，它能不能靠谱地把事办成"。因为同一个目标可以有多条正确路径，也可以有多种可接受的答案，所以必须<strong>同时评"结果"和"过程"</strong>：结果决定用户是否满意，过程决定这份满意能不能被稳定复现。只看结果，你会被"蒙对"的样本误导；只看过程，你又可能奖励了"步骤很规范但答案是错的"。</p>
      <div class="table-wrap">
        <table>
          <thead>
            <tr><th>层面</th><th>评估内容</th><th>常用指标 / 方法</th></tr>
          </thead>
          <tbody>
            <tr><td><strong>最终结果</strong></td><td>答案是否正确、完整、符合要求</td><td>准确率、任务成功率、LLM-as-Judge 打分</td></tr>
            <tr><td><strong>执行轨迹</strong></td><td>工具选得对不对、步数是否合理、有无绕路</td><td>轨迹评估（trajectory）、工具调用准确率</td></tr>
            <tr><td><strong>RAG 质量</strong></td><td>检索相关性、答案忠实度（不幻觉）</td><td>上下文相关性、faithfulness、答案相关性</td></tr>
            <tr><td><strong>工程指标</strong></td><td>延迟、token 成本、错误率</td><td>P95 延迟、单次任务成本、失败率</td></tr>
          </tbody>
        </table>
      </div>
      <p class="cjk">一个实用的记法是"<strong>结果对不对、路径值不值、跑得起不起</strong>"三问：第一问对应质量，第二问对应效率（步数、绕路、无谓工具调用），第三问对应工程约束（延迟、成本、稳定性）。三者往往此消彼长——把步数放到无限大能提升成功率，却会把成本和延迟拖垮，所以评估报告里最好把它们并排呈现，而不是只报一个漂亮的准确率。</p>

      <h3>评估集怎么构建：Agent 质量的地基</h3>
      <p class="cjk">很多团队的评估之所以"看起来在测、其实什么都没保住"，根子在评估集。一个能用的评估集要满足三条：<strong>代表性</strong>（分布贴近真实流量）、<strong>覆盖性</strong>（包含长尾与边界）、<strong>可判定性</strong>（每条样本有明确的判定方式）。构建时按下面的来源分层采集，比拍脑袋编样本靠谱得多：</p>
      <ul class="hub-list">
        <li><strong>真实流量抽样</strong>：从线上日志按场景分层采样，保证主干场景的分布不失真——这是评估集的"骨架"。</li>
        <li><strong>失败样本回流</strong>：把线上 badcase、用户投诉、人工兜底过的对话固化为回归用例，专门守住"曾经栽过的坑"。</li>
        <li><strong>边界与对抗样本</strong>：空输入、超长输入、歧义指令、越权请求、注入尝试，用来压测护栏与鲁棒性。</li>
        <li><strong>合成数据补长尾</strong>：用强模型批量生成罕见场景，再由人工抽检把关，解决真实数据里稀缺的组合。</li>
      </ul>
      <p class="cjk">规模上不必贪多：<mark class="key2">评估集贵在"每个样本都有明确意图和判定标准"，而不是数量堆砌</mark>。给每条样本打上标签（场景、难度、期望工具、是否含标准答案），后续才能做分层报告——"整体成功率 82%，但退款场景只有 61%"这种切片，远比一个总分更有决策价值。评估集要<strong>版本化</strong>并与代码一起进 Git，评测结果才可复现、可比较。</p>
      <div class="callout warn">
        <span class="label">常见误区</span>
        <span class="cjk">① <strong>用训练/调试用过的样本当评估集</strong>——数据泄漏会让分数虚高。② <strong>只收集正例</strong>——没有失败样本，评估无法暴露真实风险。③ <strong>评估集一成不变</strong>——业务在变、模型在换，评估集不迭代就会与线上脱节。④ <strong>把标准答案写死成单一字符串</strong>——开放式回答需要语义判定或多参考答案，硬匹配只会误杀正确输出。</span>
      </div>

      <h3>三种主流评估方法</h3>
      <ul class="hub-list">
        <li><strong>Ground Truth 对照（有标准答案）</strong>：准备带标准答案的测试集跑回归，适合有明确对错的任务（分类、抽取、可校验计算）。判定可用精确匹配、集合级 F1，或语义相似度阈值，成本低、可完全自动化。</li>
        <li><strong>LLM-as-Judge（用模型当裁判）</strong>：让一个强模型按评分标准给 Agent 输出打分，适合大规模、主观质量评估（有用性、语气、忠实度）。核心是给裁判清晰、可判定的评分 rubric，否则打分会漂移。</li>
        <li><strong>人工评估</strong>：最准但最贵，通常不作为主力，而是用于<strong>校准自动评估</strong>——抽样打分，反过来检验 Judge 与人类的一致性（如打分相关性），并为 rubric 迭代提供依据。</li>
      </ul>
      <p class="cjk">三者是分工而非替代：能用 Ground Truth 就别请 Judge（更便宜更稳），Judge 用于覆盖不可枚举的开放输出，人工则做金标准与定期校准。健康的比例是"自动为主、人工为锚"，让人力花在最能提升评估可信度的地方。</p>

      <h3>LLM-as-Judge 的正确打开方式</h3>
      <p class="cjk">"用模型评模型"是规模化评估的主力，但用不好会被"看起来对"骗过去。面试里能说清它的<strong>偏差与对策</strong>，是资深信号。研究里已被反复记录的三类系统性偏差如下 <a class="cite" href="https://arxiv.org/html/2601.22025v1" target="_blank" rel="noopener">[来源]</a>：</p>
      <div class="table-wrap">
        <table>
          <thead>
            <tr><th>偏差</th><th>表现</th><th>典型量级</th><th>对策</th></tr>
          </thead>
          <tbody>
            <tr><td><strong>位置偏差</strong></td><td>系统性偏爱靠前 / 靠后的选项</td><td>约 5–15%</td><td>随机化顺序、双向各评一次取平均</td></tr>
            <tr><td><strong>啰嗦偏差</strong></td><td>不管质量，偏爱更长的回答</td><td>约 10–20%</td><td>长度归一化、rubric 明确"简洁也可满分"</td></tr>
            <tr><td><strong>自偏好偏差</strong></td><td>偏爱与裁判同源模型的输出</td><td>因模型而异</td><td>用不同厂商模型当裁判、对裁判致盲品牌</td></tr>
          </tbody>
        </table>
      </div>
      <p class="cjk">落地要点：<strong>①</strong> rubric 要具体到可判定（如"忠实度：每条事实都必须有上下文支撑"），并<strong>要求结构化输出</strong>（JSON：分数 + 理由）；<strong>②</strong> 校准材料里放入<strong>负例</strong>与"流畅但错误"的 trick 样本，专门检验裁判会不会被文采骗过；<strong>③</strong> 随机化顺序、准则次序与模型身份，做致盲评测 <a class="cite" href="https://futureagi.com/blog/llm-as-judge-best-practices-2026/" target="_blank" rel="noopener">[来源]</a><a class="cite" href="https://utkarshgarg.com/posts/llm-as-a-judge-field-guide/" target="_blank" rel="noopener">[来源]</a>。</p>
      <p class="cjk">除了偏差，还有两个工程细节决定 Judge 好不好用。其一是<strong>打分粒度</strong>：连续的 1–10 分区分度差、抖动大，实践中更推荐<strong>少档位的离散评分</strong>（如 0/1、或"差/合格/优"三档）配一句判定理由，既稳定又便于聚合。其二是<strong>成对比较优于绝对打分</strong>：让裁判在 A、B 两个回答里选更好的，比给单个回答打绝对分更符合模型的判别能力，做模型/版本 A/B 对比时尤其稳。</p>
      <div class="code-label">Python · LLM-as-Judge 的结构化输出与致盲</div>
      <pre><code><span class="cm"># 关键：低档位打分 + 强制理由 + 随机化顺序（对抗位置偏差）</span>
<span class="kw">import</span> random, json

JUDGE_PROMPT = <span class="st">"""你是严格的评审。仅依据【评分标准】判定，不受长度与文采影响。
评分标准：{rubric}
返回 JSON：{{"verdict": "A"|"B"|"tie", "reason": "一句话依据"}}
回答A：{a}
回答B：{b}"""</span>

<span class="kw">def</span> <span class="fn">judge_pair</span>(rubric, ans1, ans2, model):
    <span class="cm"># 随机决定谁排前面，记录映射，避免系统性偏爱某一位置</span>
    swap = random.random() &lt; <span class="st">0.5</span>
    a, b = (ans2, ans1) <span class="kw">if</span> swap <span class="kw">else</span> (ans1, ans2)
    out = json.loads(model(JUDGE_PROMPT.format(rubric=rubric, a=a, b=b)))
    <span class="cm"># 把裁判视角的 A/B 还原回真实的 ans1/ans2</span>
    <span class="kw">if</span> out[<span class="st">"verdict"</span>] <span class="kw">in</span> (<span class="st">"A"</span>, <span class="st">"B"</span>) <span class="kw">and</span> swap:
        out[<span class="st">"verdict"</span>] = <span class="st">"B"</span> <span class="kw">if</span> out[<span class="st">"verdict"</span>] == <span class="st">"A"</span> <span class="kw">else</span> <span class="st">"A"</span>
    <span class="kw">return</span> out</code></pre>
      <p class="cjk">这段代码把三条对策落进了工程：随机化顺序对抗位置偏差、结构化 JSON 便于批量聚合、强制"理由"字段让每个分数可追溯（异常分数能被人工快速复核）。真正投产前，务必先用人工标注过的校准集测一遍 Judge 与人类的一致性——<strong>没校准过的裁判，等于没校准过的秤</strong>。</p>

      <h3>轨迹评估：不只看答案对不对</h3>
      <p class="cjk">同样答对，一个 Agent 用 2 步、另一个用 11 步绕了一大圈，两者的生产价值天差地别。<mark class="key">轨迹评估（trajectory evaluation）关注的是"过程质量"</mark>：工具选得对不对、参数填得准不准、有没有重复/多余调用、步数是否合理、是否在正确的时机终止。它回答的是"这次成功是可复现的能力，还是侥幸"。常见的轨迹评估维度：</p>
      <div class="table-wrap">
        <table>
          <thead><tr><th>维度</th><th>问题</th><th>度量思路</th></tr></thead>
          <tbody>
            <tr><td><strong>工具选择</strong></td><td>该用检索时却去算数？</td><td>与期望工具序列比对，算工具选择准确率</td></tr>
            <tr><td><strong>参数正确性</strong></td><td>调对了工具但传错了参数？</td><td>关键参数字段级校验</td></tr>
            <tr><td><strong>路径效率</strong></td><td>有没有重复调用、无效绕路？</td><td>实际步数 / 最优步数，重复调用计数</td></tr>
            <tr><td><strong>终止判断</strong></td><td>该停不停、或没做完就停？</td><td>提前终止率、超步兜底率</td></tr>
          </tbody>
        </table>
      </div>
      <p class="cjk">轨迹评估有两种口径：<strong>严格顺序匹配</strong>（要求工具调用序列与参考轨迹一致，适合路径确定的任务）与<strong>集合/子序列匹配</strong>（只要求关键工具都被正确调用、顺序可放宽，适合有多条合理路径的开放任务）。选错口径会误伤——对开放任务强行要求顺序一致，会把很多同样正确的路径判成"错"。实践中常把两者结合：核心工具用集合匹配保证"做对了关键动作"，效率指标用步数比衡量"做得够不够利落"。</p>
      <p class="cjk">轨迹评估还有一个常被忽视的价值：<strong>它能提前预警"看起来对、实则脆弱"的成功</strong>。一个 Agent 靠碰运气蒙对了答案，其轨迹往往杂乱——反复试错、无关工具乱调、步数远超合理值。只看结果指标你会给它满分，但轨迹指标会亮起黄灯，提示这条路径不可复现、换个输入就会崩。因此在做版本对比时，如果两个版本结果成功率相近，就该转而比较它们的轨迹效率与稳定性，选那个"赢得更干净"的版本。这种把"过程可复现性"纳入决策的意识，是资深工程师区别于调参新手的地方。</p>

      <h3>组件级评估 vs 端到端评估</h3>
      <p class="cjk">Agent 是多组件流水线：意图理解 → 规划 → 检索 → 工具调用 → 生成。只做端到端评估，你知道"整体不行"却不知道"哪一环拖了后腿"；只做组件级评估，各环都达标却可能"接起来就崩"。两者必须并用，形成"先定位、再验收"的组合拳。</p>
      <div class="table-wrap">
        <table>
          <thead><tr><th></th><th>组件级评估</th><th>端到端评估</th></tr></thead>
          <tbody>
            <tr><td>关注点</td><td>单个环节（检索/规划/生成）的质量</td><td>整条链路的最终成功率</td></tr>
            <tr><td>优势</td><td>可精确归因、定位瓶颈</td><td>贴近真实用户体验</td></tr>
            <tr><td>局限</td><td>各环达标不代表整体达标</td><td>失败时难定位根因</td></tr>
            <tr><td>适用</td><td>迭代优化、回归定位</td><td>版本验收、上线门禁</td></tr>
          </tbody>
        </table>
      </div>
      <p class="cjk">一个高分的答法是：<strong>用端到端指标做"红灯/绿灯"的验收门禁，用组件级指标做"红灯亮了去哪修"的归因工具。</strong>比如端到端成功率下降，先看组件级仪表盘——若检索命中率骤降，问题在知识库或 embedding；若检索正常但答案忠实度下降，问题多半在生成或 prompt。这种"分层归因"的表达，能立刻让面试官感到你排查过真实系统。</p>

      <h3>RAG 评估：检索与生成分开量</h3>
      <p class="cjk">RAG 是最常被单独考的组件，因为它的失败可以清晰拆成两半：<strong>检索错了</strong>（没找到该找的）还是<strong>生成错了</strong>（找到了却答歪/编造）。业界常用的一组指标正是围绕这条拆分线展开的：</p>
      <div class="table-wrap">
        <table>
          <thead><tr><th>指标</th><th>衡量什么</th><th>低分意味着</th></tr></thead>
          <tbody>
            <tr><td><strong>上下文相关性</strong>（context relevance）</td><td>检索到的片段与问题相关吗</td><td>检索/排序有问题，或知识库缺内容</td></tr>
            <tr><td><strong>上下文召回</strong>（context recall）</td><td>回答所需的信息都被检索到了吗</td><td>召回不足，chunk 切分或 top-k 需调整</td></tr>
            <tr><td><strong>忠实度</strong>（faithfulness）</td><td>答案是否只基于检索到的上下文</td><td>模型在"脑补"，出现幻觉</td></tr>
            <tr><td><strong>答案相关性</strong>（answer relevance）</td><td>答案是否切题、没跑偏</td><td>答非所问，或塞入无关内容</td></tr>
          </tbody>
        </table>
      </div>
      <p class="cjk">这四个指标构成一个诊断矩阵：<mark class="key2">上下文相关性/召回诊断"检索侧"，忠实度/答案相关性诊断"生成侧"</mark>。若上下文相关性高但忠实度低，说明"资料给对了、模型却不老实"，该在 prompt 里强制"只依据上下文作答、无据则说不知道"，或加一道引用核对；若上下文相关性本身就低，再怎么调 prompt 也是徒劳，应先修检索（改切分、加重排序 rerank、扩充知识库）。忠实度的判定天然适合 LLM-as-Judge——把答案拆成一条条事实陈述，逐条核对能否由上下文支撑，这种"陈述级核验"比整体打分更能揪出局部幻觉。</p>
      <p class="cjk">面试里常被追问"RAG 效果不好你从哪下手"，一个高分的排查顺序是：<strong>先看忠实度还是检索</strong>。因为如果检索侧本身就没召回正确信息，那生成侧再怎么优化都是空中楼阁——这是"garbage in, garbage out"在 RAG 里的具体体现。所以正确的诊断路径是自下而上：第一步确认上下文召回是否足够（该有的信息进上下文了吗），第二步确认上下文相关性（进来的内容有没有被无关片段稀释），第三步才轮到忠实度与答案相关性（资料齐了模型有没有好好用）。把这个"先检索、后生成"的排查次序讲清楚，比零散地报几个指标名更能体现你真正调过 RAG 系统。</p>

      <h3>可观测性：给 Agent 装上"黑匣子"</h3>
      <p class="cjk">生产 Agent 必须能追踪每一次运行的完整轨迹：每步的输入输出、工具调用、token 消耗、耗时。主流工具用 <strong>tracing（链路追踪）</strong>记录这些，出问题能回放定位。常见方案：<strong>LangSmith</strong>（LangChain 生态）、<strong>Langfuse</strong>（开源）、<strong>Arize Phoenix</strong>，以及基于 <strong>OpenTelemetry</strong> 的标准化埋点。PydanticAI 原生集成 <strong>Pydantic Logfire</strong>，可直接观测每次 run 的轨迹。</p>
      <p class="cjk">要理解 tracing，先理解它的数据模型：一次完整运行是一个 <strong>trace</strong>，其中每个可观测的操作（一次 LLM 调用、一次工具执行、一次检索）是一个 <strong>span</strong>，span 之间以父子关系嵌套，构成一棵可回放的调用树。每个 span 上挂着<strong>属性</strong>（模型名、输入输出、token 数、耗时、是否报错）。有了这棵树，"第 7 步为什么突然变慢""哪一次工具调用返回了脏数据""成本主要花在哪个环节"都能被逐层下钻定位——这正是评估无法替代的、面向单次会话的取证能力。</p>
      <p class="cjk">评估回答"整体好不好"，可观测性回答"这一次为什么不好"，二者互补：线上 tracing 抓到的异常会话，正是回流进评估集的最佳素材，从而把"观测"接回"评估"的闭环。</p>

      <h3>OpenTelemetry GenAI 语义约定：一次埋点，处处可用</h3>
      <p class="cjk">2025 年起，<strong>OpenTelemetry 的 GenAI 语义约定</strong>把"怎么埋点"标准化了：用统一的属性（如 <code>gen_ai.operation.name</code>、<code>gen_ai.provider.name</code>、<code>gen_ai.request.model</code>）和 span 名（如 <code>invoke_agent</code>、<code>execute_tool</code>）描述 LLM / Agent / 工具调用，一次埋点即可导出到 Datadog、Langfuse、Phoenix 等任意兼容后端，避免被单一平台锁定 <a class="cite" href="https://www.datadoghq.com/blog/llm-otel-semantic-convention/" target="_blank" rel="noopener">[来源]</a>。面试时提到"我们按 OTel GenAI 约定埋点，后端可插拔"，比只报一个工具名更有说服力。</p>
      <p class="cjk">它为什么重要？因为 Agent 可观测领域工具林立，各家属性命名五花八门，若直接绑定某个 SDK，换后端就得重写埋点。语义约定的价值就在于<strong>把"语义"与"后端"解耦</strong>：你在代码里只按标准约定描述"这是一次 agent 调用、用的哪个模型、消耗多少 token"，至于把这些数据送去哪个平台展示，是导出层的配置问题。这既保护了埋点投入，也让跨团队、跨工具的数据可以对齐口径。回答选型题时，"先按开放标准埋点、后端保持可替换"是一个显示架构成熟度的表述。</p>

      <h3>主流评估 / 可观测平台横向对比</h3>
      <p class="cjk">下面把常见方案做成可查阅的卡片：先看它属于"全栈平台"还是"指标库"，再看是否开源、最适合什么栈。选型时优先跟随你的框架生态，而不是盲目追新——评估/观测工具的价值在于"用起来、持续用"，而不是功能清单最长。</p>

      <h3>CI 回归：把评估接进流水线</h3>
      <p class="cjk">评估只有变成"每次改动自动触发"，才真正产生防护价值。<mark class="key">把评估集当成 Agent 的"单元测试 + 集成测试"</mark>：改了 prompt、换了模型、调了检索参数，CI 就自动在评估集上跑一遍，对比关键指标与基线（baseline），达标才允许合并。核心机制有三：</p>
      <ul class="hub-list">
        <li><strong>基线快照</strong>：把当前版本的分层指标存为基线，PR 的评测结果与之逐项对比。</li>
        <li><strong>回归门禁</strong>：设定阈值（如"整体成功率不得低于基线 2 个百分点、任一关键场景不得跌破下限"），触发即挡住合并。</li>
        <li><strong>差异报告</strong>：不仅报总分，还要列出"哪些样本从对变错"，让评审能看到具体退化用例而非一个冷冰冰的数字。</li>
      </ul>
      <div class="callout warn">
        <span class="label">CI 回归的现实坑</span>
        <span class="cjk">① <strong>非确定性抖动</strong>——LLM 输出随机，单次跑分会波动，需固定随机种子/降低温度，或多次取均值并容忍一个小误差带，避免"红一次绿一次"的假警报。② <strong>成本失控</strong>——全量评估集每次 PR 都跑很烧钱，可用"小集快跑（PR 门禁）+ 全集慢跑（合并/每日）"的分层策略。③ <strong>Judge 漂移</strong>——裁判模型升级会让历史分数不可比，应固定 Judge 版本并记录在报告里。</span>
      </div>

      <h3>线上监控闭环：让系统自我进化</h3>
      <p class="cjk">上线不是终点。线下评估集再全，也覆盖不了真实世界的全部长尾；模型、数据、用户行为都在漂移。所以要建一个<strong>持续闭环</strong>，让线上反馈不断反哺离线评估：</p>
      <figure class="diagram"><pre class="mermaid">
flowchart LR
    A[线上流量] --> B[全量 tracing 埋点]
    B --> C[实时指标监控\n成功率/延迟/成本/错误率]
    C --> D{告警/采样}
    D --> E[人工复核 badcase]
    E --> F[回流进评估集]
    F --> G[离线回归 + CI 门禁]
    G --> H[修复/迭代上线]
    H --> A
</pre><figcaption>图 11-1　评估-观测-回流的持续闭环</figcaption></figure>
      <p class="cjk">这个闭环里有几件事必须做实：<strong>线上指标监控</strong>（任务成功率、P95 延迟、单次成本、工具错误率、护栏拦截率）配<strong>告警阈值</strong>，异常能第一时间被发现；<strong>采样 + 反馈信号</strong>（用户点赞/点踩、人工兜底率、复购/完成率等业务指标）帮你定位"哪些会话质量差"；被复核确认的 badcase <strong>固化回评估集</strong>，下次回归就再也不会犯同样的错。<mark class="key2">离线评估保证"不退步"，线上监控保证"能发现新问题"，两者合起来才是完整的质量体系。</mark></p>
      <div class="callout tip">
        <span class="label">离线评估 vs 线上监控</span>
        <span class="cjk">别把两者混为一谈：<strong>离线评估</strong>是"发布前、在固定评估集上、可复现地"衡量能力，用于回归与选型；<strong>线上监控</strong>是"发布后、在真实流量上、实时地"观测行为，用于发现漂移与故障。面试中能把"评估集回归"和"生产监控"分清楚，并说明它们如何通过 badcase 回流互相喂养，是很强的加分项。</span>
      </div>

      <h3>评估的成本与效率：分层跑评</h3>
      <p class="cjk">评估本身是要花钱花时间的：一次 LLM-as-Judge 就是一次模型调用，全量评估集乘以多个指标、再乘以多次重复取均值，成本会迅速膨胀。因此成熟团队不会"每次都全量跑"，而是像测试金字塔一样做<strong>分层跑评</strong>：底层是量大、便宜、可确定判定的用例（用 Ground Truth 秒级跑完），中层是需要 Judge 的主观质量样本，顶层是少量最昂贵的人工评估。改动越轻、越频繁，就跑越靠底层的快集；越接近发布，才触发越完整、越贵的评估。</p>
      <p class="cjk">再叠加三个降本技巧：<strong>结果缓存</strong>——相同"输入 + 版本"的评测结果可复用，避免重复付费；<strong>分层采样</strong>——日常回归只跑覆盖主干的小集，全量集留给合并或每日定时任务；<strong>Judge 降配</strong>——用更便宜的模型做初筛，只把"模棱两可"的样本升级给更强的裁判复核。<mark class="key2">评估体系的可持续性，取决于它是否便宜到"团队愿意每天跑"</mark>——一套精确但没人跑得起的评估，等于没有评估。这也是选型时把"评估能不能自动化、跑一遍要多少钱"当作硬指标的原因。</p>

      <h3>面试追问链</h3>
      <p class="cjk">评估与可观测性是 Agent 岗位的高频深水区，追问往往一环扣一环，提前演练这条链路能让你稳住阵脚：</p>
      <ul class="hub-list">
        <li><strong>Q1：</strong>你怎么知道 Agent 好不好？→ 从"结果 + 过程"双维度切入，引出评估集与分层指标。</li>
        <li><strong>Q2：</strong>评估集从哪来、怎么保证有效？→ 真实抽样 + 失败回流 + 边界/对抗 + 合成补长尾，强调代表性与可判定性。</li>
        <li><strong>Q3：</strong>大规模主观质量怎么评？→ LLM-as-Judge，主动讲三类偏差与对策（致盲、成对比较、低档位打分、人工校准）。</li>
        <li><strong>Q4：</strong>答案对了但你怎么确认过程也靠谱？→ 引出轨迹评估与组件级 vs 端到端的分层归因；RAG 场景补检索/生成拆分指标。</li>
        <li><strong>Q5：</strong>上线后怎么持续保证质量？→ 收在 CI 回归门禁 + OTel 标准化 tracing + 线上监控闭环 + badcase 回流。</li>
      </ul>

      <div class="callout tip">
        <span class="label">本章小结</span>
        <span class="cjk">评估 Agent 的核心是"<strong>结果 + 过程</strong>"双维度，地基是一个代表性、覆盖性、可判定的<strong>评估集</strong>。规模化主观评估靠 LLM-as-Judge，但必须直面位置/啰嗦/自偏好三类偏差，用致盲、成对比较、低档位打分与人工校准来治理；过程质量靠轨迹评估，归因能力靠组件级与端到端并用，RAG 则拆成检索与生成分别量化（相关性、召回、忠实度、答案相关性）。可观测性以 tracing 给系统装上"黑匣子"，并借 OpenTelemetry GenAI 语义约定做到"一次埋点、后端可插拔"。最后，用 <strong>CI 回归</strong>守住"不退步"、用<strong>线上监控 + badcase 回流</strong>发现"新问题"，把评估、观测、迭代拧成一个自我进化的闭环——<mark class="key">能把这套闭环讲清楚的候选人，才算真正"做过产品"。</mark></span>
      </div>
