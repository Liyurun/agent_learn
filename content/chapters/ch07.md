      <h3>抽象层级：把六个框架放到同一根轴上</h3>
      <p class="cjk">面试里如果你只会说"我用过 X"，很难拿高分；能把这些框架按<strong>抽象层级</strong>串成一条轴、并说清每一层"隐藏了什么、暴露了什么"，才是体系化理解的标志。从底到顶大致是四层：<strong>原生 API 层</strong>（直接 <code>while</code> 循环调用 messages 接口，什么都自己管）→ <strong>极薄封装层</strong>（smolagents、OpenAI Agents SDK：帮你管好循环与工具协议，但不藏提示词）→ <strong>类型/工程层</strong>（PydanticAI：在薄封装之上叠加类型安全与结构化输出）→ <strong>编排/多智能体层</strong>（LangGraph、CrewAI、AutoGen：把状态、分支、多角色协作也接管了）。<mark class="key">越往上，你写的代码越少，但你"不知道框架替你做了什么"的部分越多。</mark>选型的第一性问题永远是：这一层帮我省下的复杂度，值不值得我交出去的控制权？</p>

      <h3>smolagents：用"代码即行动"看清 Agent 本质</h3>
      <p class="cjk">smolagents 出自 Hugging Face，定位是"极简"。它最核心的主张是 <strong>CodeAct</strong>——让 Agent 直接写一段 Python 代码来调用工具、组合逻辑，而不是逐个吐出 JSON 工具调用。它的价值有二：一是<strong>教学透明</strong>，核心循环极薄，你能几乎"裸眼"看到"拼上下文 → 生成代码 → 执行 → 观察 → 再生成"这个第 1 章讲过的 while 循环；二是<strong>表达力</strong>，循环、条件、就地数据处理都能在一步内完成（详见第 8 章）。它的短板同样明显：CodeAct 意味着"任意代码执行"，必须配沙箱；内置的可观测性、多智能体编排、复杂状态管理都不是它的强项。<mark class="key2">把它当"显微镜"和"快速原型工具"，而不是"重型生产平台"，才是正确用法。</mark></p>

      <h3>PydanticAI：把类型安全带进 Agent 开发</h3>
      <p class="cjk">PydanticAI 由 Pydantic 团队打造，思路是把大家在 FastAPI 里熟悉的"类型驱动 + 依赖注入 + 优雅工程"体验搬到 Agent 上。它的关键抽象是：用 Pydantic 模型声明<strong>结构化输出的 schema</strong>，框架负责校验模型返回是否符合类型，不符合就要求重试；工具的参数与返回也走同一套类型系统。对生产系统而言，这一层的价值是<strong>把"模型输出不可靠"这个根本风险，收敛成一个可校验、可重试、可静态检查的边界</strong>。它抽象不厚、不锁定模型供应商，适合"要上线、要类型安全、要结构化输出"的团队。代价是：它更关心"单个 Agent 的工程质量"，对复杂多智能体编排着墨较少，那类需求要靠自己组合或换用编排层框架。</p>

      <h3>OpenAI Agents SDK：官方原生的轻量选择</h3>
      <p class="cjk">OpenAI Agents SDK 是 OpenAI 推出的轻量级官方框架，抽象也很低。它的几个核心概念值得记住：<strong>Agent</strong>（模型 + 指令 + 工具的封装）、<strong>handoff</strong>（一个 Agent 把任务"移交"给另一个更专精的 Agent，是它做多智能体的主要方式）、<strong>guardrail</strong>（对输入输出做校验与拦截）、以及内置的 <strong>tracing</strong>（开箱可观测）。它的甜点区非常清晰：<mark class="key2">你本来就重度使用 OpenAI 生态、想要官方长期维护、又需要用 handoff 做"路由式"多智能体</mark>。它的取舍在于：与 OpenAI 生态贴得较近（虽然也支持其他兼容接口），而且作为较新的官方 SDK，其抽象与最佳实践仍在演进。</p>

      <h3>LangGraph：把 Agent 建模成一张状态图</h3>
      <p class="cjk">LangGraph 出自 LangChain 团队，是这批框架里抽象程度最高、也最"重"的一个，但它的重是有针对性的。它的核心心智模型是：<strong>把整个 Agent 系统建模成一张有向图</strong>——节点是"要执行的一步"（调模型、调工具、做判断），边是"下一步去哪"，图上流动着一个显式的 <strong>State（状态对象）</strong>。这个模型带来的能力是别的轻框架给不了的：<strong>精确控制每个节点与分支、条件跳转、循环、并行、检查点（checkpoint）与断点续跑、以及在任意节点插入 human-in-the-loop</strong>。当你的任务是"复杂、有状态、需要精确控制流"，LangGraph 的强控制力就物有所值。它的代价是学习曲线陡、样板代码多、心智负担重——用它做一个简单任务，属于典型的"杀鸡用牛刀"。</p>

      <h3>CrewAI 与 AutoGen：两种多智能体协作范式</h3>
      <p class="cjk"><strong>CrewAI</strong> 的定位是"角色扮演式多智能体"。它的核心隐喻是一支<strong>团队（Crew）</strong>：你定义若干个有<strong>角色（role）、目标（goal）、背景故事（backstory）</strong>的 Agent，再把任务（task）分派下去，让它们像同事一样协作——可以顺序执行，也可以有层级式的"管理者"分派与汇总。它的甜点区是<strong>任务天然可按角色分工</strong>的场景，比如"调研员找资料 → 分析师提炼 → 写手成稿"。这套"角色 + 协作"的高层抽象让原型搭建很快、表达很直观，代价是：多智能体之间的对话与交接会显著增加 token 与延迟成本，且当协作逻辑复杂时，高层抽象反而不如显式状态图好调试和控制。</p>
      <p class="cjk"><strong>AutoGen</strong> 来自 Microsoft，核心抽象是<strong>可对话的 Agent（ConversableAgent）</strong>：多个 Agent 通过"发消息—回消息"的会话来协作，典型如一个 <code>AssistantAgent</code>（写代码/给方案）与一个 <code>UserProxyAgent</code>（代表用户、可执行代码并反馈结果）来回对话，直到任务完成。它擅长<strong>群聊式（group chat）的多 Agent 协作与研究性探索</strong>，在"让多个角色围绕一个问题反复讨论、互相纠错"这类场景中很有表现力。它的取舍与 CrewAI 类似：对话式协作灵活但成本与不可控性更高，且更偏研究/实验气质，用于生产时要格外注意收敛与终止控制。<mark class="key2">一句话区分：CrewAI 像"给团队排好分工的项目经理"，AutoGen 像"让专家们开个会反复讨论"。</mark></p>

      <h3>为什么本宝典主线选 smolagents + PydanticAI</h3>
      <p class="cjk">这是一个刻意的教学决策，也回应了"LangGraph 太臃肿"的直觉。<strong>smolagents</strong> 核心逻辑仅约一千行代码，抽象极薄，让你能直接看清 Agent 循环的本质——而且它主打<mark class="key2">CodeAct（让 Agent 直接写 Python 代码来调用工具，而非拼 JSON）</mark>，研究表明这种方式比传统 JSON 工具调用减少约 30% 的步骤<sup><a href="#cite-9">[9]</a></sup>。<strong>PydanticAI</strong> 则把 FastAPI 那套"类型安全 + 优雅工程"的体验带到 Agent 开发，产出可直接用于生产。两者都轻、都不锁定你，学完能平滑迁移到任何重框架。</p>
      <p class="cjk">这套搭配还暗含一个学习哲学：<strong>先理解、再工程</strong>。用 smolagents 把"循环、工具、终止、上下文"这些第一性概念看透（第 8 章），你的知识就不会绑死在某个框架的 API 上；再用 PydanticAI 补上"类型安全、结构化输出、可校验边界"这些生产必备的工程能力。这两块能力——<em>对本质的理解</em>与<em>对工程的把控</em>——恰恰是面试官最想验证的。反过来，如果一上来就学 LangGraph，你很容易把"会配置节点和边"误当成"懂 Agent"，一旦被追问循环内部或抽象成本就露怯。<mark class="key">学习顺序本身，就是一种选型智慧。</mark></p>

      <h3>抽象层的代价：为什么"重框架"会反噬</h3>
      <p class="cjk">"LangGraph 太臃肿"的直觉背后有其道理。任何高抽象框架都在用"隐藏细节换开发速度"，但当你需要精细控制时，这些被隐藏的细节就变成了负担。<mark class="key">重框架的三个典型代价</mark>：① <strong>调试黑盒</strong>——出错时你面对的是框架内部的调用栈而非你的业务逻辑；② <strong>提示词失控</strong>——框架偷偷往上下文里塞了你看不见的模板，既浪费 token 又可能干扰模型；③ <strong>升级绑架</strong>——框架的 breaking change 会强迫你跟着改。这正是 Anthropic 建议"生产环境往往需要减少抽象层、直接用底层 API"的原因。</p>
      <p class="cjk">要在面试里把"抽象成本"讲透，最好把它拆成一笔<strong>可以算的账</strong>：你交出去的是<em>控制权</em>与<em>透明度</em>，换回来的是<em>起步速度</em>与<em>内置能力</em>。这笔交易在项目早期通常划算——原型阶段你最缺的就是速度；但随着系统进入生产、进入"要控成本、要调 bug、要满足合规"的阶段，天平会逐渐倒向"控制权更值钱"。这解释了一个常见现象：<mark class="key2">很多团队用重框架快速做出了 demo，却在上线前后经历一次"去框架化"重构，把关键路径下沉到原生 API。</mark>能预判到这条曲线，你就能在面试里给出"分阶段选型"的成熟答案，而不是非黑即白地站队。</p>
      <p class="cjk">再补一个容易被忽视的隐性成本——<strong>认知成本</strong>。团队每引入一个重框架，就等于要求每个成员额外掌握它的一整套概念（节点、边、状态、回调、装饰器……）。当框架的抽象与你的业务模型不一致时，工程师会花大量时间"把业务翻译成框架的语言"，这部分开销从不出现在性能报告里，却实实在在拖慢迭代。轻框架之所以"轻"，一半是代码轻，另一半正是这份认知负担轻。</p>
      <div class="callout warn">
        <span class="label">一个务实的中间路线</span>
        <span class="cjk">并非"全用框架"或"全手写"二选一。成熟团队常见的做法是：<strong>用轻框架搭骨架，在关键路径上下沉到原生 API</strong>。比如用 PydanticAI 管理类型与结构化输出，但把最核心的推理循环手写清楚，保证可控可调试。学习阶段更要如此——先用 smolagents 看清循环本质，再谈框架。</span>
      </div>

      <h3>何时不该用框架：自己写反而更好</h3>
      <p class="cjk">面试官很爱反向发问："什么情况下你会<em>不</em>用任何 Agent 框架、直接手写循环？"这是一道区分"框架使用者"与"系统设计者"的题。给出几个明确信号：</p>
      <ul class="hub-list">
        <li><strong>逻辑足够简单</strong>：只需要"调模型 → 调一两个工具 → 返回"，一个几十行的 <code>while</code> 循环就够了，引入框架反而增加依赖与黑盒。</li>
        <li><strong>需要极致控制上下文</strong>：当你要逐字节地掌控"放什么进上下文、怎么裁剪、怎么压缩"（见第 4 章），任何会偷偷改上下文的框架都是干扰，手写最省心。</li>
        <li><strong>对成本/延迟极度敏感</strong>：手写循环没有框架的额外调用与包装开销，也便于精确埋点、精算每一次 token 消耗。</li>
        <li><strong>依赖要最小化</strong>：某些生产环境（如受限的企业内网、边缘设备）不欢迎庞大依赖树，越少第三方库越好维护、越好做安全审计。</li>
        <li><strong>框架成为瓶颈</strong>：当你发现"大部分时间在跟框架的抽象搏斗、绕过它的默认行为"，就是该把它拆掉的信号。</li>
      </ul>
      <p class="cjk">反过来，<strong>该用框架的信号</strong>也要能说清：需要现成的可观测/追踪、需要复杂状态与断点续跑、需要多智能体协作的成熟范式、团队要统一工程约定与协作规范——这些"从零手写会重复造轮子且容易出错"的地方，正是框架真正省事的地方。<mark class="key">判断标准不是"框架好不好"，而是"这件事自己写的边际成本，是否高于框架带来的边际收益"。</mark></p>

      <h3>生态与社区：选型里最容易被忽视的一维</h3>
      <p class="cjk">框架的"内核"往往只占体验的一半，另一半在生态。评估生态时看几件事：<strong>模型接入的广度</strong>（是否只绑一家，还是能无缝切换多家供应商与开源模型）、<strong>工具与集成</strong>（检索、向量库、数据库、浏览器等常用工具是否有现成集成）、<strong>可观测生态</strong>（是否能接入主流 tracing/评估平台）、<strong>文档与示例质量</strong>（能否快速找到贴近你场景的范例）、以及<strong>社区活跃度与维护节奏</strong>（issue 响应、版本发布是否健康）。一个"内核优雅但生态孤立"的框架，落地时你会被迫自己造大量适配层；而一个"内核一般但生态繁荣"的框架，反而可能更快跑通端到端。<mark class="key2">生态是"隐藏的开发速度"，选型时要显式地把它算进去。</mark></p>
      <div class="callout tip">
        <span class="label">面试加分点</span>
        <span class="cjk">当被问"你怎么评估一个刚出的新框架"，除了功能，主动提"我会看它的<strong>维护健康度</strong>与<strong>生态成熟度</strong>——一个功能再炫但半年没更新、issue 无人回应的框架，我不会放进生产"，能立刻体现你的工程风险意识。切忌为"炫技"而追新框架。</span>
      </div>

      <h3>迁移成本：为什么"薄抽象"是一种战略保险</h3>
      <p class="cjk">框架会过时、会被弃坑、会出现更好的替代——所以从第一天起就要问："如果将来要换框架，我的业务代码要重写多少？"迁移成本的高低，本质取决于<strong>你的核心资产与框架的耦合有多深</strong>。真正值钱、迁移时最该保住的资产其实与框架无关：<strong>精心打磨的提示词、工具的定义与实现、评估集与评测流程、业务领域逻辑</strong>。聪明的架构会用一个<mark class="key">薄薄的适配层（自定义的 Agent/Tool 接口）把这些资产与具体框架隔开</mark>，让框架变成"可替换的零件"而非"长进血肉里的器官"。这也正是本宝典主线选 smolagents + PydanticAI 的深层理由之一——它们抽象薄、不锁定，学到的东西（循环本质、类型化边界）可以平滑迁移到任何重框架，而不是把你训练成"只会某一个框架 API 的人"。</p>

      <h3>框架无关的评估维度</h3>
      <p class="cjk">抛开具体框架，评估任何一个 Agent 框架都可以用这套维度打分，面试时能体现你的判断体系：</p>
      <ul class="hub-list">
        <li><strong>控制粒度</strong>：能否精确干预每一步的输入输出？（LangGraph 强，smolagents 中）</li>
        <li><strong>可观测性</strong>：是否内置 tracing、能否看清每步轨迹？</li>
        <li><strong>类型安全</strong>：输入输出是否有 schema 校验？（PydanticAI 是标杆）</li>
        <li><strong>生态与集成</strong>：模型、工具、向量库、可观测平台的支持是否广？</li>
        <li><strong>抽象透明度</strong>：你能不能看懂它到底往上下文里放了什么？</li>
        <li><strong>迁移成本</strong>：换框架时业务代码要重写多少？</li>
      </ul>

      <p class="cjk">把"迁移成本"落到代码上，最有效的手法是<strong>依赖倒置</strong>：让你的业务代码依赖一个自己定义的抽象接口，而不是直接依赖某个框架的具体类。下面这段"薄适配层"示意，展示了如何把框架关进一个可替换的角落——业务侧永远只看见 <code>AgentRunner</code>，换框架时只改这一个文件：</p>
      <div class="code-label">Python · 用薄适配层隔离框架依赖</div>
      <pre><code><span class="kw">from</span> abc <span class="kw">import</span> ABC, abstractmethod

<span class="cm"># 业务代码只依赖这个自定义接口，不 import 任何具体框架</span>
<span class="kw">class</span> <span class="fn">AgentRunner</span>(ABC):
    <span class="kw">@abstractmethod</span>
    <span class="kw">def</span> <span class="fn">run</span>(self, goal: str) -> str: ...

<span class="cm"># 适配层：把某个框架"翻译"成我们的接口，换框架只改这里</span>
<span class="kw">class</span> <span class="fn">SmolagentsRunner</span>(AgentRunner):
    <span class="kw">def</span> <span class="fn">__init__</span>(self, tools, model):
        <span class="kw">from</span> smolagents <span class="kw">import</span> CodeAgent
        self._agent = CodeAgent(tools=tools, model=model)
    <span class="kw">def</span> <span class="fn">run</span>(self, goal: str) -> str:
        <span class="kw">return</span> self._agent.run(goal)

<span class="cm"># 业务侧：面向 AgentRunner 编程，与框架完全解耦</span>
<span class="kw">def</span> <span class="fn">handle_request</span>(runner: AgentRunner, goal: str) -> str:
    <span class="kw">return</span> runner.run(goal)</code></pre>
      <p class="cjk">这段代码本身很短，思想却是"抗过时"的关键：<mark class="key">框架是零件，接口是契约</mark>。哪天要从 smolagents 换到 LangGraph，你只需再写一个 <code>LangGraphRunner</code> 实现同一个 <code>run</code> 契约，<code>handle_request</code> 与所有业务逻辑一行都不用动。面试里能主动画出这层隔离，等于直接告诉面试官"我做过要长期维护的系统"。</p>

      <div class="callout warn">
        <span class="label">选型常见误区</span>
        <span class="cjk">① <strong>"Star 多就是好"</strong>——热度不等于适配你的任务与团队。② <strong>"新框架更先进就该上"</strong>——生产系统更看重稳定与维护健康度，追新是风险。③ <strong>"选了重框架就一劳永逸"</strong>——恰恰相反，抽象越重、被绑架越深、迁移越痛。④ <strong>"框架能替我想清楚架构"</strong>——框架只解决"怎么实现"，"要不要用 Agent、要几级自主"这些第一性问题（第 1 章）它替不了你。⑤ <strong>"多智能体一定比单智能体强"</strong>——多 Agent 协作会成倍放大成本、延迟与不可控性，能单则单。</span>
      </div>

      <h3>面试追问链</h3>
      <ul class="hub-list">
        <li><strong>Q1：</strong>你用过哪些 Agent 框架、怎么选的？→ 用"任务特征 + 团队诉求 + 取舍"的话术模板。</li>
        <li><strong>Q2：</strong>为什么不直接用 LangGraph？→ 抽象层的三个代价 + "能用轻的不用重的"。</li>
        <li><strong>Q3：</strong>什么时候反而该上 LangGraph？→ 复杂有状态、需精确控制流与分支的场景。</li>
        <li><strong>Q4：</strong>怎么评价一个框架好不好？→ 抛出六个框架无关的评估维度（尤其别漏掉生态与迁移成本）。</li>
        <li><strong>Q5：</strong>什么情况下你会不用任何框架、自己手写？→ 逻辑简单、要极致控制上下文/成本、依赖最小化、框架成瓶颈这四类信号。</li>
        <li><strong>Q6：</strong>你怎么降低将来换框架的代价？→ 用薄适配层做依赖倒置，保住提示词、工具、评估集这些与框架无关的核心资产。</li>
      </ul>

      <div class="callout tip">
        <span class="label">本章小结</span>
        <span class="cjk">框架选型考的不是"你会用哪个"，而是"你懂不懂取舍"。核心原则：<strong>能不用框架就不用，能用轻的不用重的，需要精细控制时敢于下沉到原生 API</strong>。本宝典主线选 smolagents（看清原理）+ PydanticAI（工程落地），因为它们轻、透明、不锁定，学完能平滑迁移到任何重框架。记住：框架是加速器，不是拐杖。</span>
      </div>
