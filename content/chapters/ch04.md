      <h2 class="chap-title"><span class="kicker">04</span>上下文工程</h2>
      <p class="cjk">如果说 2023 年的关键词是"提示词工程"，那么 2026 年就是<mark class="key">上下文工程（Context Engineering）</mark>。它指的是<strong>在推理的每一步，把恰好合适的信息、以恰好合适的格式，放进模型的上下文窗口</strong>的这门手艺。Anthropic 将其定义为"提示词工程的自然演进"：不再只关注怎么写一句好 prompt，而是关注怎么管理整个上下文状态<sup><a href="#cite-1">[1]</a></sup>。对 Agent 而言，这是比模型选择更能决定成败的一环。</p>
      <p class="cjk">为什么它对 Agent 尤其关键？因为普通 LLM 应用往往是"一次性"的——拼好 prompt、拿到答案就结束。而 Agent 是<strong>在多步循环里反复读写同一块上下文</strong>：每一步的工具调用、观察结果、中间推理都会被追加进去。上下文因此不再是静态的输入，而是一个<em>随时间增长、需要主动治理的状态</em>。谁能管好这块状态，谁的 Agent 才能跑得久、跑得稳、跑得省。本章就沿着"机制→失效→四策略→分区→压缩→缓存→prompt 结构→token 预算"这条主线，把这门手艺讲透。</p>

      <h3>先搞懂机制：上下文窗口到底是什么</h3>
      <p class="cjk">要谈治理，先懂机制。<strong>上下文窗口（Context Window）</strong>是模型单次前向推理能"看到"的 token 总量上限，涵盖系统提示、历史对话、工具定义、检索内容和本次输出预留的空间——它们共享同一个预算。理解三件事，你就抓住了上下文工程的物理基础：</p>
      <ul class="hub-list">
        <li><strong>注意力是全局的、也是有代价的</strong>：Transformer 的自注意力让每个 token 都能"看到"其它所有 token，这是模型能整合上下文的根源；但注意力的计算与显存开销随序列长度增长而显著上升，长上下文既慢又贵。</li>
        <li><strong>位置不是平权的</strong>：受"迷失在中间（lost in the middle）"现象影响，模型对开头和结尾的信息更敏感，对正中间的信息更容易忽略。这直接决定了"关键信息该放哪"的排布策略。</li>
        <li><strong>窗口是硬边界</strong>：一旦总 token 超出上限，要么报错、要么被截断。Agent 长跑时历史无限增长，触碰这条边界只是时间问题——这就是压缩与检索存在的根本原因。</li>
      </ul>
      <div class="callout tip">
        <span class="label">一个反直觉的事实</span>
        <span class="cjk">窗口"能装 20 万 token"不等于"装满 20 万还好用"。可用容量（模型仍能可靠推理的长度）通常远小于标称容量。<mark class="key">把标称窗口当作物理上限，把"高信号预算"当作工程上限</mark>——后者才是你每一步真正要精打细算的东西。</span>
      </div>

      <h3>为什么上下文是稀缺资源</h3>
      <p class="cjk">大模型的上下文窗口看似很大，但它是有限且会"衰减"的资源。研究和实践都反复证明一个现象——<mark class="key2">上下文腐烂（Context Rot）</mark>：随着 token 数量增加，模型准确回忆信息的能力会下降<sup><a href="#cite-5">[5]</a></sup>。窗口越满，模型越容易忽略中间的关键信息、被无关内容干扰。因此上下文工程的核心心法是：<strong>找到能最大化产出正确结果的、尽可能小的高信号 token 集合</strong>，而不是把所有能塞的都塞进去。</p>
      <p class="cjk"><strong>Context Rot 的机制拆解。</strong>它不是单一原因，而是几股力量叠加：其一，序列越长，注意力越"稀释"，真正相关的 token 分到的注意力权重相对下降；其二，无关内容越多，越容易与关键信息产生语义干扰；其三，"迷失在中间"让塞在长历史正中的关键约束被系统性忽略。三者共同作用的结果是——<mark class="key">上下文长度与任务准确率并非单调正相关，超过某个甜点区后，加得越多反而错得越多</mark>。这解释了为什么"把所有资料一股脑塞进超长窗口"往往不如"精选一小段高相关内容"。</p>

      <div class="callout warn">
        <span class="label">四大失效模式</span>
        <span class="cjk">上下文出问题通常表现为四种：<strong>Context Poisoning（污染）</strong>——幻觉或错误进入上下文并被反复引用；<strong>Context Distraction（分心）</strong>——上下文太长压过了模型的训练知识；<strong>Context Confusion（混淆）</strong>——无关内容影响了输出；<strong>Context Clash（冲突）</strong>——上下文中不同部分自相矛盾。面试被问"长任务为什么越跑越差"，答这四点即可。</span>
      </div>
      <div class="table-wrap">
        <table>
          <thead><tr><th>失效模式</th><th>典型症状</th><th>对策</th></tr></thead>
          <tbody>
            <tr><td>Poisoning 污染</td><td>一个早期幻觉被后续步骤当真、反复引用放大</td><td>关键事实做校验后再入上下文；隔离不可信来源</td></tr>
            <tr><td>Distraction 分心</td><td>历史过长，模型"忘记"任务目标只顾复读上文</td><td>压缩历史、把目标周期性重申</td></tr>
            <tr><td>Confusion 混淆</td><td>无关工具/文档误导模型选错动作</td><td>按需加载（Select），减少无关噪声</td></tr>
            <tr><td>Clash 冲突</td><td>新旧信息矛盾，模型摇摆或给出错误折中</td><td>压缩时显式保留"最新已定结论"，标注时效</td></tr>
          </tbody>
        </table>
      </div>

      <h3>四大核心策略：Write / Select / Compress / Isolate</h3>
      <p class="cjk">LangChain 把上下文工程的战术总结成四类，是目前最流行的记忆框架，务必记牢<sup><a href="#cite-6">[6]</a></sup>：</p>

      <div class="card-grid">
        <div class="card">
          <h4>✍️ Write 写入</h4>
          <p>把信息存到上下文窗口之外——如草稿板（scratchpad）、长期记忆库，供后续步骤取用，避免一次性全塞进去。</p>
        </div>
        <div class="card">
          <h4>🎯 Select 选择</h4>
          <p>在需要时才把相关信息拉进上下文——如 RAG 检索、按需加载工具定义、召回相关记忆。</p>
        </div>
        <div class="card">
          <h4>🗜️ Compress 压缩</h4>
          <p>对历史做摘要或裁剪，只保留完成任务所必需的 token，对抗上下文腐烂。</p>
        </div>
        <div class="card">
          <h4>🧩 Isolate 隔离</h4>
          <p>把上下文拆分到多个 Agent 或沙箱环境中，各自维护独立的、更聚焦的上下文。</p>
        </div>
      </div>

      <p class="cjk">四个字诀看似简单，落到工程里各有门道。下面逐一给出<strong>机制</strong>与<strong>可落地的代码骨架</strong>，帮你从"知道名词"升级到"讲得清怎么实现"。</p>

      <p class="cjk"><strong>① Write（写入）的机制。</strong>核心是把"当前这一步不需要、但以后可能要用"的信息移出上下文，存到外部载体：短期用<strong>草稿板</strong>（本轮任务的中间笔记），长期用<strong>记忆库</strong>（跨会话的事实、偏好）。这样上下文里只留"指针"或摘要，需要时再取回全文。它对抗的是"什么都留在对话里导致膨胀"。</p>
      <div class="code-label">Python · Write：把中间结果写到上下文外</div>
      <pre><code><span class="kw">class</span> <span class="fn">Scratchpad</span>:
    <span class="kw">def</span> <span class="fn">__init__</span>(self, store):
        self.store = store          <span class="cm"># 外部 KV / 文件 / 向量库</span>
    <span class="kw">def</span> <span class="fn">write</span>(self, key, value):
        self.store[key] = value     <span class="cm"># 全文存外部，不进上下文</span>
        <span class="kw">return</span> <span class="fn">f</span><span class="st">"[已存 {key}，{len(value)} 字，需要时用 read({key}) 取回]"</span>  <span class="cm"># 上下文里只放一行指针</span>
    <span class="kw">def</span> <span class="fn">read</span>(self, key):
        <span class="kw">return</span> self.store.get(key, <span class="st">""</span>)   <span class="cm"># 真正需要时才拉回全文</span></code></pre>

      <p class="cjk"><strong>② Select（选择）的机制。</strong>与其把所有可能相关的东西都放进去，不如在每一步<strong>按当前需要动态检索</strong>：用 RAG 拉相关文档、按意图只加载相关工具子集、按语义召回相关的历史记忆。它对抗的是 Context Confusion——无关内容越少，模型选择越准。关键在检索质量：召回不准，Select 就变成"精准地喂错东西"。</p>
      <div class="code-label">Python · Select：按需检索 + 按需加载工具</div>
      <pre><code><span class="kw">def</span> <span class="fn">build_context</span>(query, all_tools, memory, k=5):
    docs   = retriever.search(query, top_k=k)        <span class="cm"># 只取最相关的 k 条，而非全量</span>
    recall = memory.semantic_recall(query, top_k=3)  <span class="cm"># 召回相关的历史记忆</span>
    tools  = select_relevant_tools(query, all_tools) <span class="cm"># 按意图只挂相关工具，减少干扰</span>
    <span class="kw">return</span> assemble(system_prompt, tools, recall, docs, query)</code></pre>

      <p class="cjk"><strong>③ Compress（压缩）的机制</strong>将在下文"Compaction 实战"里详述，核心是对历史做摘要或裁剪。<strong>④ Isolate（隔离）的机制</strong>是把不同关注点的上下文拆到独立的执行体里——最典型的就是子 Agent：每个子 Agent 只维护自己聚焦任务所需的上下文，主 Agent 只接收提炼后的结论。它既缓解单一窗口膨胀，又天然防止不同任务的信息互相污染（呼应第 3 章 Multi-Agent）。</p>

      <h3>长任务的三种落地手法</h3>
      <p class="cjk">当任务超出单个上下文窗口时，Anthropic 总结了三种被验证有效的技术<sup><a href="#cite-1">[1]</a></sup>：<strong>压缩（Compaction）</strong>——把接近上限的对话总结后，用摘要开启新窗口；<strong>结构化笔记（Note-taking）</strong>——把关键状态写到上下文外的持久记忆，需要时再读回；<strong>子代理架构（Sub-agent）</strong>——用专职子 Agent 处理聚焦任务，只把提炼后的结论返回主 Agent。这三招几乎是所有长程 Agent 的标配。</p>
      <p class="cjk">把四策略和三手法对上号，你就有了一张完整的地图：<strong>Compaction 是 Compress 的具体落地</strong>，<strong>Note-taking 是 Write 的具体落地</strong>，<strong>Sub-agent 是 Isolate 的具体落地</strong>，而 Select（检索）贯穿三者之间——无论用哪种手法，需要时都要能把外部存下的信息准确地拉回来。面试里能把"策略层（四字诀）"与"手法层（三招）"这样映射起来讲，立刻显出体系感。</p>
      <p class="cjk"><strong>为什么结构化笔记（Note-taking）比裸压缩更稳。</strong>压缩是"把长的变短"，不可避免有损；而 Note-taking 是主动地、结构化地把关键状态写到上下文外的持久载体（如一个 <code>progress.md</code> 或状态对象），每步更新、需要时读回。它的好处有三：一是关键状态有了"单一事实来源"，不会随历史被压缩而丢失；二是笔记本身可被人类审阅、被断点续跑复用；三是它把"易变的过程"和"沉淀的结论"分离，让上下文更干净。很多长程 Coding Agent 之所以能跨越几十步不迷失，靠的正是一份持续维护的任务清单，而非指望模型"记住"整段历史。</p>

      <div class="callout tip">
        <span class="label">工程直觉</span>
        <span class="cjk">好的上下文工程遵循一个朴素原则：<strong>把上下文当成预算来花</strong>。每加入一段内容前问自己——它对当前这一步决策是否必要？能不能等真正需要时再检索进来？这种"吝啬"的心态，正是资深与新手的分水岭。</span>
      </div>

      <h3>上下文的四个功能分区</h3>
      <p class="cjk">要精细管理上下文，先要理解它内部其实分成几个功能不同的"区"。一个组织良好的 Agent 上下文通常包含：</p>
      <ul class="hub-list">
        <li><strong>指令区（System / Developer）</strong>：角色设定、行为准则、约束条件。这是最"贵"的位置，模型对它的遵循度最高，应保持精炼稳定。</li>
        <li><strong>工具区（Tools）</strong>：可用工具的定义与描述。工具越多占用越大，因此才有"按需加载工具"（Select 策略）的做法。</li>
        <li><strong>记忆/检索区（Retrieved Context）</strong>：从长期记忆或 RAG 拉进来的相关信息。质量比数量重要，塞太多反而引发 Context Distraction。</li>
        <li><strong>历史区（Conversation History）</strong>：对话与工具调用的历史轨迹。这是增长最快、最需要压缩的部分。</li>
      </ul>
      <p class="cjk">理解分区后你会发现，<mark class="key">上下文工程的本质是在固定的 token 预算内，为这四个区做动态分配</mark>。历史区膨胀时就压缩它，好腾出预算给更关键的检索区。</p>
      <p class="cjk"><strong>分区还决定了排布顺序。</strong>结合前面讲的"位置不平权"与 KV-Cache（见下文），分区应按<em>稳定性从高到低</em>由前往后排：指令区最稳、放最前；工具区次之；检索区和历史区最易变、放后面，其中当前用户请求与最新观察放在最末尾（模型对结尾最敏感）。这套排布同时照顾了"关键信息易被读到"和"稳定前缀可被缓存"两个目标。下面这段展示了如何在组装时给每个分区分配预算并按序拼接：</p>
      <div class="code-label">Python · 分区预算分配与有序组装</div>
      <pre><code>BUDGET = 32000  <span class="cm"># 本次可用总 token 预算</span>
alloc = {<span class="st">"system"</span>: 0.10, <span class="st">"tools"</span>: 0.15, <span class="st">"retrieved"</span>: 0.35, <span class="st">"history"</span>: 0.40}

<span class="kw">def</span> <span class="fn">assemble_context</span>(parts):
    ctx = []
    <span class="kw">for</span> zone <span class="kw">in</span> [<span class="st">"system"</span>, <span class="st">"tools"</span>, <span class="st">"retrieved"</span>, <span class="st">"history"</span>]:  <span class="cm"># 稳定→易变，顺序固定</span>
        cap = int(BUDGET * alloc[zone])
        ctx.append(fit_to_budget(parts[zone], cap))   <span class="cm"># 超预算的分区先裁剪/摘要</span>
    ctx.append(parts[<span class="st">"current_user_msg"</span>])   <span class="cm"># 最新请求放最末，位置最敏感</span>
    <span class="kw">return</span> ctx</code></pre>

      <h3>Compaction 实战：什么时候压、怎么压</h3>
      <p class="cjk">压缩不是等窗口满了才做的应急措施，而应是有策略的常规操作。常见触发点是"上下文使用率达到阈值（如 70-80%）"。压缩的关键在于<strong>保真</strong>——总结历史时必须保留：未完成的任务目标、已确认的关键事实、待办事项、以及对后续决策有影响的约束。容易丢失的恰恰是这些"状态性"信息。</p>
      <p class="cjk"><strong>压缩策略的谱系。</strong>从轻到重有几档，应按需选用而非一刀切：<strong>裁剪（Trimming）</strong>——直接丢弃最旧、最不相关的轮次，最省算力但可能丢信息；<strong>滚动摘要（Rolling Summary）</strong>——把较旧的历史压成一段摘要、保留最近 N 轮原文，兼顾成本与保真；<strong>结构化压缩</strong>——用固定模板把历史抽成"目标 / 已知事实 / 待办 / 约束"四栏，最可靠也最贵。生产里常见组合：近处保原文、远处滚动摘要、关键状态用结构化模板锁定。</p>
      <div class="code-label">Python · 阈值触发的滚动摘要压缩</div>
      <pre><code><span class="kw">def</span> <span class="fn">maybe_compact</span>(history, llm, limit, ratio=0.75, keep_recent=6):
    <span class="kw">if</span> token_count(history) &lt; limit * ratio:   <span class="cm"># 未到阈值不动，避免过度压缩</span>
        <span class="kw">return</span> history
    old, recent = history[:-keep_recent], history[-keep_recent:]  <span class="cm"># 近 N 轮保原文</span>
    summary = llm.summarize(old, template=STATE_TEMPLATE)   <span class="cm"># 远处用结构化模板压缩</span>
    <span class="cm"># STATE_TEMPLATE 强制保留：未完成目标 / 已定结论 / 待办 / 约束</span>
    <span class="kw">return</span> [summary] + recent   <span class="cm"># 摘要在前，最近原文在后</span></code></pre>
      <div class="callout warn">
        <span class="label">压缩的陷阱</span>
        <span class="cjk">粗暴的压缩会导致 Agent"失忆式翻车"：把前面已经确认"用户要的是 A 方案"这一关键决策摘要掉了，压缩后 Agent 又开始纠结 A 还是 B。因此生产级的 Compaction 往往用一个<strong>专门的摘要提示词</strong>，明确要求模型"保留所有未完成目标与已定决策"，而不是简单地"总结上文"。</span>
      </div>

      <h3>KV-Cache：被忽视的成本杠杆</h3>
      <p class="cjk">上下文工程不只关乎准确率，还直接影响成本与延迟。现代推理引擎会缓存上下文前缀的 KV-Cache——<mark class="key2">只要上下文的前缀不变，这部分就能命中缓存，大幅降低延迟与费用</mark>。这带来一个重要的工程原则：<strong>把稳定的内容（系统提示、工具定义）放在上下文最前面，把易变的内容（最新对话）放在最后</strong>。如果你每一步都在开头插入变化的时间戳，就会让整个缓存失效。Manus 等团队公开分享过，KV-Cache 命中率是 Agent 成本优化的头号杠杆。</p>
      <p class="cjk"><strong>机制拆解：为什么前缀不变才能命中。</strong>自回归推理时，每个 token 的 Key/Value 向量只依赖它前面的 token。因此只要上下文的<em>某段前缀逐字节完全一致</em>，这段前缀算出的 KV 就能被复用，无需重算——这就是"前缀缓存（prefix caching）"。一旦前缀中任何一个 token 变了，从该 token 起往后的缓存全部失效。这条机制直接推导出三条可操作的守则：</p>
      <ul class="hub-list">
        <li><strong>稳定前缀绝不乱动</strong>：系统提示、工具定义一经确定就固定下来，不要每轮重排或插入动态字段。</li>
        <li><strong>动态内容一律后置</strong>：时间戳、随机 ID、用户最新输入都放到上下文尾部，把"缓存失效点"推到最后。</li>
        <li><strong>只追加、不改写历史</strong>：新内容 append 到末尾而非插入中间；一旦压缩重写了历史，就等于主动放弃了这部分缓存，故压缩频率也要权衡。</li>
      </ul>
      <div class="callout warn">
        <span class="label">缓存杀手清单</span>
        <span class="cjk">这些常见写法会悄悄摧毁缓存命中率：① 系统提示开头放"当前时间：14:32:07"这类每秒都变的字段；② 每轮重新排序工具列表或记忆片段；③ 在历史中间插入或删除消息；④ 用不稳定的 JSON 序列化（键顺序随机）。<mark class="key">把"什么会让前缀变化"内化成肌肉记忆，是成本优化的第一步。</mark></span>
      </div>

      <h3>Prompt 结构化：让上下文可被稳定解析</h3>
      <p class="cjk">上下文不只是"塞什么"，还包括"怎么排版"。同样的信息，结构清晰与堆成一团，模型的遵循度天差地别。<strong>结构化的三个抓手：</strong>其一，用明确的<strong>分节标记</strong>（如 XML 风格标签 <code>&lt;task&gt;</code>、<code>&lt;context&gt;</code>、<code>&lt;rules&gt;</code> 或 Markdown 标题）把指令、背景、数据、输出要求分开，模型更容易定位各部分职责；其二，把<strong>最重要的约束放在开头与结尾</strong>（呼应位置敏感性），中间放可容忍被略读的背景资料；其三，对期望输出<strong>给出格式契约</strong>（如"只返回 JSON，字段为……"），降低解析失败率。</p>
      <div class="code-label">文本 · 结构化 prompt 骨架（分节 + 输出契约）</div>
      <pre><code>&lt;role&gt;你是严谨的订单排查助手，只依据 &lt;context&gt; 作答，缺依据就说不知道&lt;/role&gt;

&lt;context&gt;
{检索到的相关订单与政策，按需注入，不相关的不要放}
&lt;/context&gt;

&lt;task&gt;判断用户是否满足退款条件，并说明依据&lt;/task&gt;

&lt;output_format&gt;
仅输出 JSON: {"eligible": true|false, "reason": "...", "cite": ["订单号"]}
&lt;/output_format&gt;</code></pre>
      <p class="cjk">这种结构化还有个隐性好处：<mark class="key2">分节标签让"哪部分该缓存、哪部分该按需替换"一目了然</mark>——固定的 <code>role</code>/<code>output_format</code> 可进稳定前缀，只有 <code>context</code> 随每次检索变化。结构化因此同时服务于准确率与成本两个目标。</p>

      <h3>Token 预算管理：把上下文当账本来记</h3>
      <p class="cjk">前面反复出现"预算"二字，这里把它落成可执行的纪律。<strong>Token 预算管理</strong>就是：为一次推理设定总 token 上限，给各功能分区分配配额，实时核算占用，超支时按优先级<strong>回收</strong>。它把"上下文别塞太多"这句正确的废话，变成可度量、可自动执行的规则。</p>
      <div class="table-wrap">
        <table>
          <thead><tr><th>分区</th><th>建议优先级</th><th>超支时的回收动作</th></tr></thead>
          <tbody>
            <tr><td>指令区（System）</td><td>最高，几乎不动</td><td>仅精简冗词，不删规则</td></tr>
            <tr><td>当前请求 / 最新观察</td><td>最高</td><td>不动（这是本步决策依据）</td></tr>
            <tr><td>检索区（Retrieved）</td><td>中，按相关度</td><td>降低 top_k、丢弃低分片段</td></tr>
            <tr><td>历史区（History）</td><td>最低（可再生）</td><td>滚动摘要 / 裁剪最旧轮次</td></tr>
          </tbody>
        </table>
      </div>
      <div class="code-label">Python · 带优先级的预算回收</div>
      <pre><code><span class="kw">def</span> <span class="fn">enforce_budget</span>(zones, budget):
    <span class="cm"># zones 按优先级从低到高排列的可回收顺序</span>
    <span class="kw">while</span> total_tokens(zones) &gt; budget:
        <span class="kw">for</span> z <span class="kw">in</span> [<span class="st">"history"</span>, <span class="st">"retrieved"</span>]:   <span class="cm"># 先回收低优先级、可再生的分区</span>
            <span class="kw">if</span> total_tokens(zones) &lt;= budget:
                <span class="kw">break</span>
            zones[z] = shrink(zones[z])       <span class="cm"># 摘要历史 / 减少检索条数</span>
        <span class="kw">if</span> not shrinkable(zones):
            <span class="kw">raise</span> BudgetExceeded    <span class="cm"># 无可回收：宁可显式失败，也别悄悄截断关键区</span>
    <span class="kw">return</span> zones</code></pre>
      <p class="cjk">最后一行的态度值得强调：<mark class="key">当预算实在不够时，显式报错或触发子任务拆分，好过悄悄截掉可能含关键约束的内容</mark>。很多"长任务莫名其妙做错"的根因，就是框架在你看不见的地方默默截断了上下文。把预算管理显式化，本身就是一种可观测性。</p>

      <h3>把手艺串起来：一个订单排查 Agent 的上下文流</h3>
      <p class="cjk">概念讲多了容易散，用一个具体场景把本章所有手法串起来。设想一个跑了几十轮的订单排查 Agent，它一步步经历：<strong>启动</strong>时把稳定的角色设定与输出契约放进指令区（进稳定前缀，供 KV-Cache 命中）；<strong>每一步</strong>只用 Select 按当前问题检索相关订单和政策，而不是把整个知识库塞进去；查到的大段原始数据用 Write 存到草稿板，上下文里只留一行指针；<strong>跑到第 20 轮</strong>历史逼近阈值时触发 Compaction，用结构化模板把前 15 轮压成"目标 / 已确认事实 / 待办 / 约束"四栏摘要，最近 6 轮保原文；<strong>遇到需要专门核算退款金额</strong>的子问题，就用 Isolate 派一个子 Agent 单独算好、只回传结论。整条链路里，token 预算像账本一样被实时核算，一旦超支优先回收可再生的历史区。</p>
      <p class="cjk">这个例子的价值在于：<mark class="key2">四策略、三手法、分区、缓存、预算并不是孤立的知识点，而是同一件事在不同环节的体现</mark>。面试时若能像这样用一个场景把它们自然串起来，远胜过逐条背诵——它证明你真正理解了"上下文是一个需要全程治理的动态状态"。</p>

      <div class="callout warn">
        <span class="label">常见误区与反模式</span>
        <span class="cjk">① <strong>"窗口大就往死里塞"</strong>——忽视 Context Rot，长上下文反而降准确率。② <strong>"检索越多越保险"</strong>——高 top_k 引入噪声，触发混淆，召回质量比数量重要。③ <strong>"压缩就是简单总结上文"</strong>——不锁定关键状态会导致失忆式翻车。④ <strong>"上下文工程等于 RAG"</strong>——RAG 只是 Select 策略的一种，上下文工程还涵盖写入、压缩、隔离与全局预算分配。⑤ <strong>"缓存是运维的事"</strong>——前缀是否稳定由 prompt 结构决定，恰恰是工程师每天在写的代码。</span>
      </div>

      <h3>面试追问链</h3>
      <ul class="hub-list">
        <li><strong>Q1：</strong>什么是上下文工程？→ 提示词工程的演进，管理整个上下文状态而非单句 prompt。</li>
        <li><strong>Q2：</strong>长任务为什么越跑越差？→ Context Rot + 四大失效模式（污染/分心/混淆/冲突）。</li>
        <li><strong>Q3：</strong>超出窗口怎么办？→ Write/Select/Compress/Isolate 四策略 + Compaction/Note-taking/Sub-agent 三手法，并说清二者的映射关系。</li>
        <li><strong>Q4：</strong>压缩时最容易丢什么、怎么防？→ 丢"状态性信息"（未完成目标/已定结论/约束）；用专门摘要提示词强制保留。</li>
        <li><strong>Q5：</strong>怎么降低 Agent 的成本？→ 引出 KV-Cache 前缀缓存机制与"稳定前缀 + 动态后置 + 只追加"三守则。</li>
        <li><strong>Q6：</strong>给固定预算，你怎么在四个分区之间分配 token？→ 按优先级分配 + 超支时回收可再生的历史/检索区，宁可显式失败也不悄悄截断。</li>
      </ul>

      <div class="callout tip">
        <span class="label">本章小结</span>
        <span class="cjk">上下文工程是 2026 年 Agent 工程的核心手艺，本质是<strong>在有限的 token 预算内动态分配四个功能分区</strong>，对抗 Context Rot。机制层面要懂上下文窗口、位置敏感性与前缀缓存；战术层面记住 Write/Select/Compress/Isolate 四字诀与 Compaction/Note-taking/Sub-agent 三手法，并知道它们如何一一对应；成本层面记住"稳定前缀 + KV-Cache"；纪律层面把 token 预算当账本来记、显式管理回收。一句话总结：<strong>不是把上下文塞满，而是把最高信号的 token 放到最该在的位置。</strong></span>
      </div>
