      <h4>① 推理引擎（Reasoning Engine）</h4>
      <p class="cjk">大模型本体加上一套规划策略，是 Agent 的"大脑"。它负责把大目标拆成小步骤、决定每一步做什么。常见规划策略包括 <strong>ReAct</strong>（推理与行动交替）、<strong>Plan-and-Execute</strong>（先规划完整计划再执行）等，将在第 3 章展开。</p>

      <h4>② 工具使用（Tool Use）</h4>
      <p class="cjk">工具是 Agent 伸向外部世界的手：调用 API、查数据库、执行代码、搜索网页。工具通过 <strong>JSON Schema</strong> 声明名称、描述与参数，模型据此决定何时调用、传什么参数。工具设计的好坏直接决定 Agent 的成败——描述含糊、参数过多、职责不清的"万能工具"是新手最常见的坑。</p>

      <h4>③ 记忆（Memory）</h4>
      <p class="cjk">分两层：<strong>短期记忆</strong>是当前上下文窗口内的对话与中间结果；<strong>长期记忆</strong>是外部的向量库或键值存储，用于跨会话保留知识。记忆管理是 Agent 能否处理长任务的关键，第 5 章专门讲。</p>

      <h4>④ 通信层（Communication Layer）</h4>
      <p class="cjk">负责 Agent 与外部（用户、其他 Agent、工具服务）之间的消息传递与协议。在多智能体系统里，它决定 Agent 之间如何协作；MCP 协议（第 6 章）正是标准化这一层的努力。</p>

      <div class="callout warn">
        <span class="label">常见追问</span>
        <span class="cjk">"这四块里哪个最容易出问题？" —— 工具使用与记忆管理。工具描述不清会让模型乱调用；上下文管理不当会导致"上下文污染"，让 Agent 越跑越偏。能主动指出这两个痛点，说明你真正做过 Agent，而不只是读过文档。</span>
      </div>

      <h3>推理引擎：不止是"调用一个大模型"</h3>
      <p class="cjk">很多人把推理引擎简单等同于"调 GPT-4 的 API"，这在面试中会显得单薄。更准确的理解是：<mark class="key">推理引擎 = 基座模型（提供语言与世界知识）+ 提示词架构（system/developer/user 分层）+ 规划策略（如何组织思考）+ 输出解析（把自然语言变成结构化动作）</mark>。这四层任何一层出问题，Agent 都会失效。</p>
      <p class="cjk">先说<strong>提示词架构</strong>为什么要分层。<code>system</code>（有的厂商细分出 <code>developer</code>）承载稳定不变的角色、规则与工具说明，优先级最高；<code>user</code> 承载当轮请求；历史消息则以 <code>assistant/tool</code> 角色回填。分层的意义在于<em>指令优先级</em>：当用户输入与系统规则冲突时，模型应优先遵循系统层。这也是防提示注入的第一道防线——把"不可协商的安全规则"放在 system，把"不可信的外部数据"（如网页内容、工具返回）标注清楚，避免模型把数据当指令执行。</p>
      <p class="cjk">再说<strong>输出解析</strong>，它是推理引擎最容易被忽视却最易出错的一环。模型要发起一次工具调用，本质是输出一段结构化文本（通常是 JSON）。现代模型用原生的 function calling / tool use 接口来保证格式，但底层仍可能出现字段缺失、类型错误、幻觉出不存在的工具名。工程上的标准做法是"解析 + 校验 + 反馈重试"：</p>
      <div class="code-label">Python · 推理引擎的"决策—校验—重试"骨架</div>
      <pre><code><span class="cm"># 用 JSON Schema 校验模型产出的工具调用，失败则把错误反馈回上下文让模型自纠</span>
<span class="kw">import</span> json, jsonschema

<span class="kw">def</span> <span class="fn">decide_and_validate</span>(state, tools_schema, max_retry=2):
    <span class="kw">for</span> attempt <span class="kw">in</span> range(max_retry + 1):
        raw = llm_call(state)                 <span class="cm"># 模型产出一次动作（工具调用）</span>
        <span class="kw">try</span>:
            call = json.loads(raw)
            jsonschema.validate(call, tools_schema)  <span class="cm"># 校验名称/参数/类型</span>
            <span class="kw">return</span> call                    <span class="cm"># 通过则返回结构化动作</span>
        <span class="kw">except</span> (json.JSONDecodeError, jsonschema.ValidationError) <span class="kw">as</span> e:
            <span class="cm"># 把具体错误写回上下文，引导模型下一轮自我修正</span>
            state.append({<span class="st">"role"</span>: <span class="st">"tool"</span>,
                          <span class="st">"content"</span>: <span class="st">f"格式错误：{e}。请严格按 schema 重新输出。"</span>})
    <span class="kw">raise</span> RuntimeError(<span class="st">"多次重试仍无法产出合法工具调用"</span>)</code></pre>
      <p class="cjk">这段代码揭示了一个关键取舍：<strong>把可靠性做在引擎层还是模型层</strong>。强模型指令遵循好，可以少写校验；弱模型/开源小模型则必须靠外层的校验重试来兜底。下面这个真实案例把这个取舍讲得很透。</p>
      <p class="cjk">举个具体的失效案例：某团队把一个在 GPT-4 上跑得很好的 Agent 直接换成开源小模型，结果工具调用成功率从 95% 暴跌到 40%。排查后发现，问题不在"模型不够聪明"，而在小模型对 JSON Schema 的遵循能力弱——它经常输出格式错误的工具调用。<strong>这说明推理引擎的可靠性，很大程度上取决于模型的"指令遵循"与"结构化输出"能力，而不只是通用智力。</strong>这也是为什么工程上常给弱模型加一层"输出校验 + 重试"来兜底。</p>
      <div class="callout tip">
        <span class="label">面试考点</span>
        <span class="cjk">被问"推理引擎里最容易踩的坑是什么"，答"输出格式不稳定"能立刻显出实战经验。延伸答法：温度（temperature）设太高会让工具调用更不稳定，生产上工具调用环节常把温度调低甚至设 0；同时用结构化输出（JSON mode / 原生 tool use）而非让模型"自由发挥"再去正则解析。</span>
      </div>

      <h3>规划策略：推理引擎如何"想清楚再动手"</h3>
      <p class="cjk">推理引擎的第二层能力是<strong>规划</strong>——决定"分几步、每步做什么、出错怎么退"。这是第 3 章的主题，但作为组件机制，这里先建立心智：规划策略本质是在<em>规划深度</em>与<em>反馈频率</em>之间取舍。</p>
      <div class="table-wrap">
        <table>
          <thead><tr><th>策略</th><th>机制</th><th>优点</th><th>代价 / 适用</th></tr></thead>
          <tbody>
            <tr><td><strong>ReAct</strong></td><td>推理与行动交替：想一步、做一步、看结果再想</td><td>反馈及时、容错好、实现简单</td><td>无全局计划，长任务易"绕路"</td></tr>
            <tr><td><strong>Plan-and-Execute</strong></td><td>先生成完整计划，再逐步执行</td><td>全局视野、步数可控、成本可预估</td><td>计划僵化，环境突变时需重规划</td></tr>
            <tr><td><strong>Reflexion / 自我反思</strong></td><td>执行后回看、总结失败、下一轮改进</td><td>能从错误中学习、提升成功率</td><td>额外的反思轮次抬高成本与延迟</td></tr>
          </tbody>
        </table>
      </div>
      <p class="cjk">面试里若被追问"你会怎么选"，标准思路是：<mark class="key2">短程、环境多变的任务用 ReAct；步骤多、彼此依赖、需要成本可控的长任务用 Plan-and-Execute；对成功率要求高、允许多花钱的关键任务再叠加反思</mark>。三者也常组合使用，不是互斥选项。</p>

      <h3>工具使用：Agent 能力的真正边界</h3>
      <p class="cjk">一个残酷的事实是：<mark class="key2">Agent 的能力上限不由模型决定，而由你给它的工具决定</mark>。再聪明的模型，没有"发邮件"的工具就发不了邮件。因此工具设计是 Agent 工程中回报最高的投入之一。好的工具遵循几条原则：</p>
      <ul class="hub-list">
        <li><strong>单一职责</strong>：一个工具只做一件事。"万能工具"（一个函数带十几个可选参数）会让模型频繁传错参数。</li>
        <li><strong>描述即接口</strong>：工具的 description 是写给模型看的"文档"，要用模型能理解的语言说清"什么时候用、传什么、返回什么"。描述质量直接决定调用准确率。</li>
        <li><strong>错误信息友好</strong>：工具报错时，返回的错误信息应该能指导模型如何修正（如"日期格式应为 YYYY-MM-DD"），而不是抛一个堆栈跟踪。</li>
        <li><strong>幂等与安全</strong>：有副作用的工具（删除、支付）要么设计成幂等，要么强制 human-in-the-loop 确认。</li>
      </ul>
      <div class="callout tip">
        <span class="label">工程经验</span>
        <span class="cjk">当 Agent 表现不佳时，新手第一反应是"换个更强的模型"或"改提示词"，而资深工程师往往先问："是不是工具设计有问题？"——把一个 <code>query_database(sql)</code> 拆成 <code>search_user(name)</code>、<code>get_order(id)</code> 这样语义明确的小工具，准确率的提升常常远超换模型。</span>
      </div>
      <p class="cjk">把上面的原则落到代码，一个"好工具"长这样——注意描述、参数约束与错误反馈三处细节：</p>
      <div class="code-label">Python · 一个设计良好的工具定义</div>
      <pre><code><span class="cm"># 单一职责 + 清晰描述 + 受约束参数 + 可指导的错误信息</span>
<span class="kw">def</span> <span class="fn">get_order</span>(order_id: str) -&gt; dict:
    <span class="st">"""按订单号查询订单状态与金额。
    仅用于查询单个已存在订单；批量或模糊查询请勿使用本工具。
    Args: order_id 形如 'ORD-20260101-0001' 的订单号。
    """</span>
    <span class="kw">if</span> <span class="kw">not</span> re.match(<span class="st">r"^ORD-\d{8}-\d{4}$"</span>, order_id):
        <span class="cm"># 错误信息要能指导模型自我修正，而非抛裸栈</span>
        <span class="kw">return</span> {<span class="st">"error"</span>: <span class="st">"order_id 格式应为 ORD-YYYYMMDD-NNNN，请核对后重试"</span>}
    order = db.find(order_id)
    <span class="kw">if</span> order <span class="kw">is</span> <span class="kw">None</span>:
        <span class="kw">return</span> {<span class="st">"error"</span>: <span class="st">f"未找到订单 {order_id}，可先用 search_order 按条件检索"</span>}
    <span class="kw">return</span> {<span class="st">"id"</span>: order.id, <span class="st">"status"</span>: order.status, <span class="st">"amount"</span>: order.amount}</code></pre>
      <p class="cjk">这里的取舍值得展开：<strong>工具粒度</strong>是一门平衡艺术。粒度太粗（一个 <code>do_everything</code>），模型难以正确传参、也难判断何时用；粒度太细（几十个碎工具），又会撑爆工具列表、增加模型的选择负担，反而降低准确率。经验法则是<mark class="key">让工具数量控制在模型能"一眼看懂如何选择"的范围，把语义相近的能力合并、把职责不同的能力拆开</mark>。当工具确实很多时，用"工具分组 / 按需检索工具"的方式动态注入，而不是一次性把上百个工具塞进上下文。</p>
      <div class="callout warn">
        <span class="label">工具层常见失败模式</span>
        <span class="cjk">① <strong>描述含糊</strong>导致模型选错工具或该用时不用；② <strong>参数过多/可选参数太多</strong>导致频繁传错；③ <strong>错误只抛堆栈</strong>，模型看不懂无法自纠，陷入重复失败；④ <strong>返回体过大</strong>（如把整张表塞回上下文），既烧 token 又稀释关键信息；⑤ <strong>副作用工具无幂等/无确认</strong>，一次误调用造成不可逆后果。</span>
      </div>
      <div class="callout tip">
        <span class="label">面试考点</span>
        <span class="cjk">被追问"工具太多怎么办"，标准答法有三层：其一，合并语义相近的工具、砍掉冗余；其二，按当前任务<strong>动态检索并注入</strong>相关工具子集，而非一次性全塞进上下文；其三，用<strong>分层/命名空间</strong>组织工具（如先选类别再选具体工具）。能说出"工具列表本身也占上下文、也会干扰选择"，说明你真正理解工具与推理引擎是耦合的，而非各自独立。</span>
      </div>

      <h3>记忆：短期与长期的分工</h3>
      <p class="cjk">把记忆拆成短期和长期，本质是在回答"信息放在哪里"。短期记忆（上下文窗口）读写最快但容量有限且昂贵；长期记忆（向量库/数据库/文件）容量近乎无限但需要显式检索。二者的关系类似计算机的"内存 vs 硬盘"。设计记忆系统的核心决策是：<strong>哪些信息值得写入长期记忆、什么时候检索、检索多少条塞回上下文</strong>——这三个问题会在第 4、5 章展开，是长程 Agent 的命门。</p>
      <p class="cjk">进一步细分，实践中的记忆往往不止两层，而是四种角色，面试时能报全会显得体系完整：</p>
      <div class="table-wrap">
        <table>
          <thead><tr><th>记忆类型</th><th>存放什么</th><th>典型实现</th><th>关键取舍</th></tr></thead>
          <tbody>
            <tr><td><strong>工作记忆</strong>（短期）</td><td>当前任务的对话与中间结果</td><td>上下文窗口 / 消息列表</td><td>快但贵、有长度上限，需裁剪压缩</td></tr>
            <tr><td><strong>情景记忆</strong>（长期）</td><td>过往交互、用户偏好、历史事件</td><td>向量库（语义检索）</td><td>召回质量取决于切分与 embedding</td></tr>
            <tr><td><strong>语义记忆</strong>（长期）</td><td>事实、知识、文档</td><td>向量库 + 知识库 / 图数据库</td><td>需处理时效性与冲突</td></tr>
            <tr><td><strong>过程记忆</strong></td><td>技能、可复用的操作流程</td><td>提示词模板 / 工具 / 微调</td><td>更新慢，改动需重新固化</td></tr>
          </tbody>
        </table>
      </div>
      <p class="cjk">最核心的工程机制是<strong>上下文管理</strong>：当对话变长、逼近窗口上限时，不能简单截断（会丢关键信息），常见做法是"滚动摘要 + 检索回注"。下面这段骨架演示了这一机制：</p>
      <div class="code-label">Python · 短期记忆的摘要压缩 + 长期记忆检索回注</div>
      <pre><code><span class="kw">def</span> <span class="fn">build_context</span>(history, query, window_budget=6000):
    <span class="cm"># 1) 短期：预算够就全带，不够就把旧消息压成摘要</span>
    <span class="kw">if</span> token_len(history) &gt; window_budget:
        old, recent = split_by_budget(history, keep_recent=window_budget // 2)
        summary = llm_summarize(old)          <span class="cm"># 把旧对话压成要点，防丢关键事实</span>
        short_term = [summary] + recent
    <span class="kw">else</span>:
        short_term = history
    <span class="cm"># 2) 长期：按当前 query 语义检索 top-k，回注到上下文</span>
    recalled = vector_store.search(query, top_k=4)
    <span class="kw">return</span> short_term + format_recall(recalled)</code></pre>
      <p class="cjk">这里的取舍很典型：<mark class="key">摘要压缩省了 token，却可能丢失后续才用得上的细节；检索回注补回了知识，却可能召回不相关内容造成"上下文污染"</mark>。<code>top_k</code> 设大提升召回但稀释信噪比、增加成本，设小则可能漏掉关键证据。这些参数没有万能值，要靠评估集调。第 4、5 章会系统展开，这里先建立"记忆 = 主动的上下文工程，而非被动堆历史"的认知。</p>
      <div class="callout warn">
        <span class="label">记忆层常见失败模式</span>
        <span class="cjk">① <strong>上下文爆炸</strong>：无脑堆历史直到超出窗口而报错或被静默截断；② <strong>上下文污染</strong>：把错误的中间结果或不相关召回喂回去，Agent 越跑越偏；③ <strong>摘要失真</strong>：压缩时丢掉了后面才需要的关键约束；④ <strong>检索错配</strong>：切分粒度或 embedding 不当，召回一堆噪声；⑤ <strong>长期记忆不更新</strong>：用户偏好变了却仍用旧记忆，答非所需。</span>
      </div>

      <h3>通信层：从单 Agent 到协作系统</h3>
      <p class="cjk">在单 Agent 场景，通信层往往被忽略——它就是"用户消息进、Agent 回复出"。但一旦进入多 Agent 或需要标准化对接外部工具，通信层就成了架构核心。它要解决：消息格式（如何序列化）、协议（同步还是异步、如何传递工具调用）、以及跨 Agent 的状态同步。<strong>MCP（第 6 章）正是把"Agent 如何标准化地连接工具与数据源"这一层协议化</strong>，让工具可以像 USB 设备一样即插即用。</p>
      <p class="cjk">通信层的机制可以分两个方向理解。<strong>纵向（Agent 与工具/数据源）</strong>：关注如何标准化地暴露和调用能力，MCP 这类协议的价值在于把"每接一个工具就写一次适配"变成"一次接入、处处复用"，降低集成的边际成本。<strong>横向（Agent 与 Agent）</strong>：关注多个智能体如何分工协作，常见拓扑有<em>管道式</em>（上游产出交下游）、<em>主管-下属式</em>（一个 orchestrator 分派子任务给专才 Agent）、<em>对等辩论式</em>（多个 Agent 互相质疑以提高答案质量）。<mark class="key2">拓扑选择的核心取舍是"能力增益"与"协调开销"</mark>：多 Agent 能带来专业化分工与并行，但也引入消息往返延迟、状态一致性与"谁说了算"的仲裁难题。</p>
      <p class="cjk">用一段"主管-下属"式的伪代码，能直观看出通信层在多 Agent 里承担的"消息路由 + 状态汇聚"职责：</p>
      <div class="code-label">Python · 主管 Agent 分派并汇聚子 Agent 结果（简化）</div>
      <pre><code><span class="kw">def</span> <span class="fn">orchestrate</span>(goal):
    subtasks = planner.decompose(goal)          <span class="cm"># 主管把目标拆成子任务</span>
    results = []
    <span class="kw">for</span> t <span class="kw">in</span> subtasks:
        worker = route_to_worker(t.type)        <span class="cm"># 通信层：按能力路由到专才 Agent</span>
        msg = build_message(t, shared_state)    <span class="cm"># 显式携带意图，避免语义丢失</span>
        results.append(worker.run(msg))         <span class="cm"># 可并行；需处理超时与失败</span>
    <span class="kw">return</span> synthesizer.merge(results)            <span class="cm"># 汇聚：解决冲突并产出统一答复</span></code></pre>
      <p class="cjk">这段代码里藏着通信层最难的三件事：<strong>路由</strong>（把子任务发给对的 Agent）、<strong>意图传递</strong>（<code>build_message</code> 要把"为什么做这一步"带过去，否则下游只见树木不见森林）、<strong>结果合并</strong>（<code>merge</code> 要处理多个 Agent 给出的矛盾结论）。这也解释了为什么"能用单 Agent 就别上多 Agent"是主流建议——每多一个 Agent，这三件事的复杂度都会上升。</p>
      <div class="callout warn">
        <span class="label">通信层常见失败模式</span>
        <span class="cjk">① <strong>消息语义丢失</strong>：Agent 间传递时上下文被截断，下游"不知道上游为什么这么做"；② <strong>协调死锁 / 循环</strong>：两个 Agent 互相等待或反复把任务踢来踢去；③ <strong>状态不一致</strong>：多个 Agent 对共享状态的读写产生竞态；④ <strong>过度拆分</strong>：为多 Agent 而多 Agent，协调开销吃掉了分工收益。面试中能主动说"多 Agent 不是银弹，先看单 Agent + 好工具能不能解决"，是成熟度的体现。</span>
      </div>

      <h3>四大组件如何协同：一次完整调用的数据流</h3>
      <p class="cjk">把四块拼起来看一次真实调用：用户目标经<strong>通信层</strong>进入，<strong>推理引擎</strong>结合<strong>记忆</strong>中的历史决定"先查订单"，输出一个<strong>工具</strong>调用；工具返回结果经通信层写回<strong>记忆</strong>（短期上下文）；推理引擎再次决策，判断信息是否充分……如此循环，直到产出最终答复。<mark class="key">四大组件不是静态的框图，而是在"感知-决策-行动循环"（第 1 章）中动态流转的角色</mark>。理解这个数据流，你就能在系统设计题里回答"数据在你的 Agent 里是怎么流动的"这类高阶问题。</p>
      <p class="cjk">下面这张时序图把"一次带工具调用的完整回合"画清楚，白板上能默写出来会非常加分——它把四个组件之间的<em>消息顺序</em>显式化了：</p>
      <figure class="diagram"><pre class="mermaid">

      <p class="cjk">这张图暗含三个面试常追问的节点：<strong>记忆读写发生在决策前后各一次</strong>（读上下文、写观察）；<strong>工具返回的既可能是结果也可能是错误</strong>（错误也是一种观察，要能驱动下一轮自纠）；<strong>"信息是否充分"的判断就是终止条件</strong>（判错会导致过早收尾或无限循环）。把数据流讲成"消息如何在四个角色间流动"，远比复述框图更能证明你懂机制。</p>

      <h3>组件边界：哪些交给模型，哪些写死代码</h3>
      <p class="cjk">四大组件里最考验工程判断力的，是划清"模型该管什么、代码该管什么"的边界。一个反复出现的教训是：<mark class="key">凡是能用确定性代码可靠完成的，就不要交给模型去"猜"</mark>。模型擅长的是理解、决策、生成这些"软"能力；而校验、计算、格式化、权限控制这些"硬"逻辑，交给代码更便宜也更可靠。</p>
      <div class="table-wrap">
        <table>
          <thead><tr><th>职责</th><th>交给模型（推理引擎）</th><th>写死在代码里</th></tr></thead>
          <tbody>
            <tr><td>决定"下一步做什么"</td><td>是（这是 Agent 的核心价值）</td><td>否则就退化成 workflow</td></tr>
            <tr><td>数值计算、日期换算</td><td>否（模型算术不可靠）</td><td>是，用工具/函数精确计算</td></tr>
            <tr><td>参数与权限校验</td><td>否（不能靠模型自觉）</td><td>是，在工具入口强制校验</td></tr>
            <tr><td>从自然语言抽取意图</td><td>是（模型强项）</td><td>否</td></tr>
            <tr><td>高风险动作的最终执行</td><td>否（需人工确认门槛）</td><td>是，代码层加确认与额度限制</td></tr>
          </tbody>
        </table>
      </div>
      <p class="cjk">这条边界还有一个推论：<strong>不要让推理引擎承担它不该承担的确定性责任</strong>。比如"金额是否超过额度"这种判断，若靠提示词叮嘱模型"记得检查额度"，迟早会漏；正确做法是把额度校验做进工具或代码层，模型即便想越权也调不动。<mark class="key2">好的 Agent 架构，是让模型只在"真正需要判断"的地方判断，把可以确定的都用代码兜住</mark>——这既省 token，又把风险关进了确定性的笼子。面试中能主动画出这条边界，往往比罗列组件更能体现你对系统可靠性的理解。</p>

      <h3>组件级失败模式总览与排查顺序</h3>
      <p class="cjk">把前面各组件的失败模式汇成一张"急救表"，是面试里回答"Agent 出问题你怎么定位"的最佳武器。<mark class="key2">排查要按数据流逆向定位：先看现象落在哪个组件，再对症下药，而不是一上来就换模型</mark>。</p>
      <div class="table-wrap">
        <table>
          <thead><tr><th>组件</th><th>典型故障现象</th><th>根因方向</th><th>首选对策</th></tr></thead>
          <tbody>
            <tr><td>推理引擎</td><td>工具调用格式错、选错工具、不肯终止</td><td>指令遵循弱、提示词含糊、温度过高</td><td>结构化输出 + 校验重试、降温度、拆清 system 规则</td></tr>
            <tr><td>工具使用</td><td>频繁传错参、该调不调、报错后反复失败</td><td>描述含糊、粒度不当、错误信息不友好</td><td>拆细工具、改描述、让错误可指导自纠</td></tr>
            <tr><td>记忆</td><td>越跑越偏、忘记早期约束、召回噪声</td><td>上下文污染/爆炸、摘要失真、检索错配</td><td>摘要压缩、裁剪无关、调 top_k 与切分</td></tr>
            <tr><td>通信层</td><td>多 Agent 死锁/循环、状态不一致</td><td>拓扑不当、上下文传递丢失</td><td>简化拓扑、显式传递意图、加仲裁与超时</td></tr>
          </tbody>
        </table>
      </div>
      <div class="callout tip">
        <span class="label">面试要点</span>
        <span class="cjk">当被问"线上 Agent 突然成功率下降，你怎么排查"，按这张表的顺序讲：先复现并看错误落在哪个组件（看 trace/日志），是格式错就查推理引擎与工具 schema，是"越跑越偏"就查记忆与上下文，是多 Agent 卡住就查通信与拓扑。<strong>能说出"我会先看 trace 定位到组件，再对症处理"，比直接说"我会换个大模型"专业得多。</strong></span>
      </div>

      <h3>面试追问链</h3>
      <ul class="hub-list">
        <li><strong>Q1：</strong>画一下 Agent 的架构？→ 四大组件 + 执行循环图。</li>
        <li><strong>Q2：</strong>这四块哪个最容易出问题？→ 工具使用与记忆管理，各举一个失效案例。</li>
        <li><strong>Q3：</strong>Agent 表现不好，你怎么排查？→ 按组件级失败模式表逆向定位，先查工具设计与输出格式、再查上下文，而非急着换模型。</li>
        <li><strong>Q4：</strong>推理引擎为什么不只是"调一个大模型"？→ 拆出基座 + 提示词分层 + 规划策略 + 输出解析四层，讲结构化输出与校验重试。</li>
        <li><strong>Q5：</strong>记忆只有短期长期两层吗？→ 补上工作/情景/语义/过程四类，讲上下文管理机制与取舍。</li>
        <li><strong>Q6：</strong>通信层在单 Agent 里有存在感吗？→ 引出纵向（MCP 连工具）与横向（多 Agent 拓扑）两个方向，展示知识广度。</li>
      </ul>

      <div class="callout tip">
        <span class="label">本章小结</span>
        <span class="cjk">Agent = 推理引擎 + 工具使用 + 记忆 + 通信层，四者在执行循环中动态协作。工程上最值得投入的是<strong>工具设计</strong>（决定能力边界）与<strong>记忆管理</strong>（决定长程能力）。记住一句话：Agent 的能力上限不由模型的聪明程度决定，而由你给它的工具和你如何管理它的上下文决定。</span>
