      <h2 class="chap-title"><span class="kicker">17</span>Coding Agent 架构剖析</h2>
      <p class="cjk">Coding Agent（如 Devin、Claude Code、SWE-agent）是当下最热、也最能体现 Agent 工程功力的方向。它的核心不是"会写代码"——大模型早就会——而是<mark class="key">"能在真实代码库里定位问题 → 改对 → 用测试证明改对"的完整闭环</mark>。这一章拆解它的独特挑战与架构。为什么面试官偏爱这个话题？因为它把前面所有章节——上下文工程、工具设计、规划、记忆、评估、护栏——全都压缩进了一个可验证、可量化、有真实产品落地的场景里。答得好，等于把整本书的能力做了一次实战演练。</p>

      <h3>Coding Agent 的四个独特挑战</h3>
      <div class="card-grid">
        <div class="card">
          <h4>🔍 代码库检索</h4>
          <p>真实仓库几十万行，上下文窗口装不下。靠 grep / 符号索引 / 向量检索先定位相关文件——这是编码版的上下文工程。</p>
        </div>
        <div class="card">
          <h4>✏️ 多文件编辑</h4>
          <p>改一个函数签名要同步所有调用点。多文件一致性是最容易翻车的地方，需要结构化 diff 与精确行编辑。</p>
        </div>
        <div class="card">
          <h4>🧪 测试反馈闭环</h4>
          <p>测试输出是 Agent 最可靠的"真值奖励"——由红转绿证明改对了。没有测试就只能盲改。</p>
        </div>
        <div class="card">
          <h4>⏳ 长程任务</h4>
          <p>一个 issue 可能要几十步。要设步数上限、循环检测，并把中间状态持久化以便续跑。</p>
        </div>
      </div>
      <p class="cjk">这四个挑战不是并列的清单，而是一条<strong>因果链</strong>：因为代码库太大所以要检索定位；因为定位到的改动要跨文件所以要保证多文件一致；因为改完不知道对不对所以要用测试来验证；因为一次改不对所以要多轮迭代、任务变长。把这条链讲清楚，你就抓住了 Coding Agent 架构设计的全部动机。下面逐环节展开。</p>

      <h3>代码库理解：让 Agent"看懂"一个陌生工程</h3>
      <p class="cjk">人类工程师接手一个陌生仓库时，会先看目录结构、README、入口文件，再顺着调用关系摸清模块边界。Coding Agent 也需要类似的"建立心智地图"过程，但它没有人类的直觉，只能靠工具主动探查。理解代码库通常分三个层次：<strong>结构层</strong>（目录树、模块划分、构建配置、依赖清单）、<strong>语义层</strong>（符号定义、类型关系、函数调用图）、<strong>意图层</strong>（这段代码想解决什么问题、约定俗成的写法是什么）。</p>
      <p class="cjk">一个关键设计取舍是：<mark class="key2">要不要预先建一份全库索引，还是让 Agent 按需现查？</mark>预建索引（符号表、调用图、向量库）检索快、召回全，但要维护、会过时、对超大仓库成本高；按需现查（现场跑 grep、读文件、查符号）实现简单、永远最新，但每次都要花步数探索。现代 Coding Agent 越来越倾向<strong>轻索引 + 强现查</strong>：少量结构信息预置，大部分定位靠 Agent 自主用命令行工具动态探索——这也呼应了"上下文工程"的核心思想：<strong>不是把整个仓库塞进上下文，而是让 Agent 学会按需取用</strong>。</p>
      <p class="cjk">这里有个容易被忽视但极其重要的输入：<strong>仓库自身的"约定文档"</strong>。很多成熟 Coding Agent 会优先读取诸如 README、贡献指南、以及仓库根目录下专门给 Agent 看的说明文件（约定项目结构、构建命令、测试方式、代码风格）。这类"给 Agent 的地图"能极大减少盲目探索的步数——它把人类工程师脑子里的隐性知识显式化，让 Agent 不必每次都从零摸索"怎么跑测试""依赖怎么装"。面试里若被问"怎么让 Coding Agent 更快上手一个陌生仓库"，回答"先读约定文档 + 结构探查，再按需检索"，会显得你懂真实工程而非只懂算法。</p>

      <h3>检索与定位：grep、符号索引与向量检索的取舍</h3>
      <p class="cjk">"在几十万行里找到该改的那几行"是 Coding Agent 的第一道硬功夫。三类主流手段各有擅长，成熟系统往往组合使用：</p>
      <div class="table-wrap">
        <table>
          <thead><tr><th>手段</th><th>擅长</th><th>短板</th></tr></thead>
          <tbody>
            <tr><td>词法检索（grep / ripgrep）</td><td>精确匹配已知标识符、报错字符串，快且零维护</td><td>不懂语义，改了名就找不到，同名歧义多</td></tr>
            <tr><td>符号索引（LSP / ctags / AST）</td><td>精确的定义跳转、找引用、类型关系</td><td>需按语言配置，跨语言/动态语言支持参差</td></tr>
            <tr><td>向量检索（embedding）</td><td>模糊语义匹配，"实现登录的地方在哪"</td><td>召回不精确，需切分与维护索引，会过时</td></tr>
          </tbody>
        </table>
      </div>
      <p class="cjk">一个被反复验证的经验是：<mark class="key">对代码而言，词法与符号检索往往比向量检索更可靠</mark>。因为代码里的标识符是精确的、可枚举的，一次 grep 报错信息就能直达出错点，而向量检索的"语义近似"在需要精确定位的场景反而引入噪声。实践中的高效路线常是：先用报错栈/关键字 grep 缩小范围，再用符号跳转确认调用关系，向量检索作为"我不知道确切名字"时的补充。面试里能说清"我不会无脑上向量库，代码定位优先词法+符号"，是很实在的加分点。</p>

      <h3>核心架构：一个修 bug Agent 的完整轨迹</h3>
      <p class="cjk">下面把一个 <strong>SWE-bench 式</strong>修 bug Agent 的执行过程做成可点击的时间线。注意它本质上是一个<strong>编码版 ReAct 循环</strong>：理解 → 复现 → 计划 → 编辑 → 跑测试 → 按报错迭代。点每一步看它在做什么、以及背后的工程要点。</p>
      <div class="interactive" id="codingAgentTrace"></div>
      <p class="cjk">这个轨迹里藏着 Coding Agent 与普通问答 Agent 最大的不同：<mark class="key2">它有一个近乎"真值"的反馈信号——测试结果</mark>。普通 Agent 常常不知道自己答得对不对，只能靠模型自评；而修 bug Agent 每改一轮就能跑一次测试，红变绿就是客观的成功信号。这把"自我修正"从玄学变成了工程：有明确目标、有可测反馈、有迭代终止条件。理解这一点，你就懂了为什么 Coding 是目前 Agent 落地最成熟的领域之一。</p>
      <p class="cjk">值得强调的是各步骤的<strong>顺序不是随意的</strong>：先"理解+复现"确保动手前真的搞清了问题、并建立了一个能证明修复成功的失败测试；再"计划"避免上来就乱改；然后才"编辑→测试→迭代"。这个顺序和资深工程师修 bug 的心智完全一致，也是把 Agent 从"碰运气"拉到"有方法"的关键。一个反面案例是：跳过复现直接改，改完测试恰好过了，但其实压根没修到点子上，只是掩盖了症状——所以"先写/找到一个会失败的测试"几乎是修 bug Agent 的黄金第一步。</p>

      <h3>编辑-运行-测试循环：Coding Agent 的心脏</h3>
      <p class="cjk">如果说普通 Agent 的核心是"感知-决策-行动"循环，那么 Coding Agent 的核心就是它的特化版：<strong>编辑（edit）→ 运行（run）→ 测试（test）→ 读报错（observe）→ 再编辑</strong>。这个闭环之所以强大，是因为每一环都产生了<strong>结构化、高信息量的反馈</strong>：编译器报错精确到行、测试失败带断言信息、栈追踪指向出错位置。Agent 把这些反馈读回上下文，就能做出比"盲改"精确得多的下一步决策。</p>
      <div class="code-label">Bash · 编辑-运行-测试循环（示意）</div>
      <pre><code><span class="cm"># 1) 先复现：确认 bug 存在（预期红）</span>
pytest tests/test_auth.py::test_login -x

<span class="cm"># 2) 精确编辑：仅改动定位到的行，保持最小 diff</span>
apply_patch auth.py   <span class="cm"># 结构化补丁，而非整文件重写</span>

<span class="cm"># 3) 重新运行：由红转绿即为成功信号</span>
pytest tests/test_auth.py::test_login -x

<span class="cm"># 4) 回归：跑更大范围，防止改坏别处</span>
pytest tests/ -q</code></pre>
      <p class="cjk">工程上有几个决定成败的细节：<strong>先复现再修</strong>（没复现就改是盲改，改完也无法证明修好了）；<strong>最小 diff 原则</strong>（改动越小越可控、越好审查，也越不容易引入回归）；<strong>先窄后宽地跑测试</strong>（先跑目标用例快速反馈，再跑全量回归防副作用）；<strong>把失败报错原文喂回上下文</strong>（而不是让模型凭记忆猜错在哪）。这些看似琐碎，却是把 Coding Agent 成功率从"偶尔能行"提到"稳定可用"的关键。</p>
      <p class="cjk">这个闭环还有一个更深的价值：<mark class="key">它让 Agent 的"探索"变得可承受</mark>。因为每一步都有廉价、客观的验证，Agent 可以大胆尝试一个假设、跑测试、发现不对就回退，再试下一个——这种"生成并验证（generate-and-verify）"的循环，正是它在没有人类实时指导下还能收敛到正确答案的底层机制。相比之下，缺乏可执行反馈的任务（如"写一篇好文案"）就没这么幸运，只能依赖更弱的模型自评。<strong>可执行反馈的有无，几乎决定了一个 Agent 任务的难度上限</strong>，这也是为什么"有测试的代码修复"比"无标准答案的开放任务"更容易做出可靠系统。</p>
      <div class="callout warn">
        <span class="label">常见误区与反模式</span>
        <span class="cjk">① <strong>不复现直接改</strong>——无法验证是否真修好，还可能改错地方。② <strong>整文件重写替代精确补丁</strong>——diff 巨大、易冲突、难审查，还常把无关代码改坏。③ <strong>只跑目标测试不跑回归</strong>——修好一个坑，悄悄踩塌三个。④ <strong>被测试"骗"</strong>——为了让测试变绿而删断言、改测试本身或写死返回值，这是 Coding 版的"奖励作弊"，必须在验证环节防住。</span>
      </div>

      <h3>SWE-bench：Coding Agent 的试金石与评测流程</h3>
      <p class="cjk"><strong>SWE-bench</strong> 是评估 Coding Agent 的代表性基准，它的设计极其贴近真实工作：<mark class="key">取真实开源仓库里的真实 GitHub issue，让 Agent 在给定的代码库快照上提交补丁，再用该 issue 对应的真实测试用例来判定是否解决</mark><a class="cite" href="https://arxiv.org/abs/2310.06770" target="_blank" rel="noopener">[来源]</a>。它的评测流程值得掌握，因为面试常问"你怎么评估一个 Coding Agent"：</p>
      <ul class="hub-list">
        <li><strong>输入</strong>：一个仓库在特定 commit 的状态 + 一段 issue 描述（自然语言的 bug/需求）。</li>
        <li><strong>产出</strong>：Agent 生成一个补丁（patch/diff），应用到代码库上。</li>
        <li><strong>判定</strong>：运行隐藏的"验证测试集"。关键在于同时看两类测试——<em>FAIL_TO_PASS</em>（原本失败、修复后应通过，证明真解决了问题）与 <em>PASS_TO_PASS</em>（原本通过、修复后仍应通过，证明没改坏别处）。两者都过才算成功。</li>
        <li><strong>指标</strong>：解决率（resolve rate），即成功解决的 issue 占比。</li>
      </ul>
      <p class="cjk">为什么这个设计重要？因为它用<strong>可执行测试</strong>而非"看起来对不对"来判分，几乎无法靠花言巧语蒙混——这正是可验证奖励在评测侧的体现（呼应第 16 章）。它也催生了两条技术路线之争：<strong>SWE-agent</strong> 强调给 Agent 一套精心设计的"代理-计算机接口"（ACI）让它自主操作<a class="cite" href="https://arxiv.org/abs/2405.15793" target="_blank" rel="noopener">[来源]</a>；而一些方案则用更结构化的流水线约束 Agent 的自由度。面试里能对比"纯自主 vs 结构化管线"在 SWE-bench 上的权衡，非常出彩。</p>
      <div class="callout tip">
        <span class="label">面试要点</span>
        <span class="cjk">被问"怎么评估 Coding Agent"，别只说"跑 SWE-bench"。高分答法要点出：① 用 FAIL_TO_PASS + PASS_TO_PASS 双重判定，兼顾"修好了"和"没改坏"；② 警惕数据污染（模型可能预训练时见过这些公开 issue 的答案）；③ 单一解决率不够，还要看成本、步数、token 消耗和稳定性。</span>
      </div>

      <h3>多文件编辑：一致性从哪来</h3>
      <p class="cjk">改一处签名、动一个接口，往往要牵动整个仓库的多个文件——这是 Coding Agent 最容易翻车的地方。难点有三：<strong>定位所有受影响点</strong>（漏改一个调用点就编译失败或运行时崩）、<strong>保持改动一致</strong>（命名、类型、导入要全局对齐）、<strong>让每处编辑都精确落地</strong>（在正确的行插入/替换，不误伤相邻代码）。工程上的主流解法是用<strong>结构化编辑</strong>而非自由文本替换：</p>
      <ul class="hub-list">
        <li><strong>基于 diff/patch 的编辑</strong>：让模型产出标准补丁（如统一 diff 格式），系统负责应用与冲突检测，比"整文件重写"精确得多、审查友好。</li>
        <li><strong>基于查找-替换块（search/replace block）的编辑</strong>：模型给出"原文片段 → 新片段"的成对块，系统精确匹配再替换，避免行号漂移问题。</li>
        <li><strong>依赖符号索引找全引用</strong>：先用"find references"列出所有调用点，再逐一编辑，比让模型凭记忆列举更可靠。</li>
      </ul>
      <p class="cjk">核心思想是<mark class="key2">把"编辑"这个动作本身做成一个可靠、可校验的工具，而不是信任模型直接输出正确的整份文件</mark>。模型擅长决定"改什么"，不擅长逐字符地"精确落地一大段文本"；把落地交给确定性的工具，把决策留给模型，是多文件编辑不崩的关键分工。</p>

      <h3>工具设计：给 Coding Agent 一套好用的"手"</h3>
      <p class="cjk">Coding Agent 的能力上限，很大程度由它的工具集（第 6 章的原则在这里具体化）决定。设计要点是<strong>为 Agent 而非为人设计接口</strong>：人用的 IDE 有大量视觉交互，而 Agent 需要的是简洁、确定、反馈清晰的文本接口。一套典型的 Coding Agent 工具集包括：</p>
      <div class="table-wrap">
        <table>
          <thead><tr><th>工具类别</th><th>示例</th><th>设计要点</th></tr></thead>
          <tbody>
            <tr><td>导航</td><td>列目录、读文件（带行号）、找符号</td><td>读文件要能分段，避免一次塞爆上下文</td></tr>
            <tr><td>检索</td><td>grep/正则、找引用</td><td>返回带上下文的匹配，便于模型判断</td></tr>
            <tr><td>编辑</td><td>应用补丁、查找-替换块</td><td>结构化、可校验、失败要明确报错</td></tr>
            <tr><td>执行</td><td>跑命令、跑测试、装依赖</td><td>沙箱内执行，回传 stdout/stderr/退出码</td></tr>
            <tr><td>版本控制</td><td>看 diff、提交、回滚</td><td>让 Agent 能回退到已知良好状态</td></tr>
          </tbody>
        </table>
      </div>
      <p class="cjk">两个高价值设计取舍：其一，<mark class="key">工具的错误信息要"对模型友好"</mark>——补丁应用失败时，返回"哪一块没匹配上、当前实际内容是什么"，远比只返回"failed"有用，因为模型能据此自我纠正。其二，<strong>动作的粒度</strong>：给一堆细粒度工具（读、写、跑）灵活但步数多，给少量粗粒度工具（"实现这个功能"）省步数但难控制；成熟系统多在中间，并常采用 <strong>CodeAct</strong> 让模型用代码本身来组合动作（见下方提示框）。</p>

      <div class="callout tip">
        <span class="label">CodeAct 范式（呼应第 7 章）</span>
        <span class="cjk">很多 Coding Agent 采用 <strong>CodeAct</strong>：让模型直接<strong>写代码来表达动作</strong>（调用、循环、组合），而不是产出一串 JSON 工具调用。研究显示可执行代码作为动作空间比 JSON/文本更高效、成功率更高——这正是第 7 章 <strong>smolagents</strong> 主打的 <code>CodeAgent</code> 思路<a class="cite" href="https://arxiv.org/abs/2402.01030" target="_blank" rel="noopener">[来源]</a>。</span>
      </div>

      <h3>安全底线：沙箱执行</h3>
      <p class="cjk">Coding Agent 要执行任意生成的代码，<mark class="key2">必须在隔离沙箱里跑</mark>——用 <strong>E2B</strong>、<strong>Docker</strong> 容器或微虚拟机，限制文件系统、网络与资源，防止误删数据或被提示注入劫持去执行恶意命令。这是"能力越强、边界越要收紧"的典型体现。</p>
      <p class="cjk">沙箱设计要回答几个具体问题：<strong>隔离边界在哪</strong>（容器 vs 微虚拟机，后者隔离更强、启动稍慢）；<strong>网络策略</strong>（默认断网还是白名单放行，防止代码把数据外传或拉取恶意依赖）；<strong>资源上限</strong>（CPU/内存/超时，防止死循环耗尽资源）；<strong>状态持久化</strong>（长任务需要把工作区快照下来，崩溃后能续跑）；<strong>幂等与可回滚</strong>（用版本控制让 Agent 随时回到已知良好状态）。一个常被忽视的威胁是<strong>间接提示注入</strong>：Agent 读取的代码注释、issue 描述、依赖文档里可能藏着"请执行 rm -rf"之类的恶意指令，沙箱是抵御这类攻击最后也最硬的一道防线（与第 12 章护栏配合）。</p>

      <h3>长程任务：上下文管理与状态持久化</h3>
      <p class="cjk">一个真实 issue 可能要几十步才能解决，这就撞上了 Coding Agent 最硬的天花板：<mark class="key">上下文窗口装不下整个探索历史</mark>。每读一个文件、每跑一次测试、每看一段报错，都在往上下文里堆信息，几十步之后早就溢出了。处理长程任务的核心，是把"无限增长的历史"压缩成"够用的工作记忆"：</p>
      <ul class="hub-list">
        <li><strong>分层记忆</strong>：把"当前目标与计划"放在最显眼处常驻，把"已完成步骤"压缩成摘要，把"原始文件内容"用完即弃、需要时再读回——而不是让所有原文永远占着上下文。</li>
        <li><strong>外置状态</strong>：把计划清单、已改文件列表、待办项写进一个外部文件或结构化笔记（相当于 Agent 的"工作簿"），既省 token 又能在崩溃/续跑时恢复。</li>
        <li><strong>子任务分解</strong>：把大 issue 拆成可独立完成、可独立验证的小任务，每个子任务用较短的上下文完成，避免"一根长上下文跑到底"。</li>
        <li><strong>循环检测</strong>：监测"反复改同一处却测试一直不过"的死循环，触发时换策略、回滚或求助，而不是无脑烧 token。</li>
      </ul>
      <p class="cjk">这也解释了为什么 Coding Agent 特别看重<strong>版本控制与检查点</strong>：把 git 当成天然的状态快照，每完成一个可验证的小步就提交一次，跑坏了能干净回滚到"已知良好状态"。<mark class="key2">长程能力的本质不是"上下文更长"，而是"更会管理状态"</mark>——这是它和记忆、上下文工程（第 4、5 章）深度耦合的地方，也是把玩具 demo 和能扛真实任务的系统区分开的关键。</p>

      <h3>人机协作：自主与可控之间</h3>
      <p class="cjk">Coding Agent 落地的一个核心张力是：<strong>放多少自主权</strong>。全自主（给个 issue 就走，人只看结果）想象空间大，但一旦跑偏，浪费的是大量算力和一堆需要推翻的改动；强协作（每步都要人确认）安全，但效率低、失去了 Agent 的意义。实践中普遍采用<mark class="key">分级授权</mark>：低风险动作（读文件、跑测试、查检索）完全放开；中风险动作（写文件、装依赖）在沙箱内自由；高风险动作（提交 PR、改数据库、执行部署、动生产配置）设 human-in-the-loop 确认。</p>
      <p class="cjk">另一个协作关键点是<strong>可观测性与可干预性</strong>：好的 Coding Agent 产品会实时展示它的计划、正在改的 diff、跑测试的结果，让人能在中途看懂、纠偏甚至接管。<strong>计划先行</strong>（先让 Agent 给出方案让人过目再动手）能大幅降低"跑了半天方向就错"的浪费。这也解释了为什么优秀产品都强调"透明的执行轨迹"——它既是调试手段，也是建立用户信任的基础。</p>

      <h3>设计取舍全景：Devin / Cursor / Claude Code</h3>
      <p class="cjk">当前主流 Coding Agent 产品代表了不同的设计哲学，理解它们的取舍比记住功能列表重要得多：</p>
      <div class="table-wrap">
        <table>
          <thead><tr><th>形态</th><th>定位</th><th>核心取舍</th></tr></thead>
          <tbody>
            <tr><td>Devin 式</td><td>云端自主 Agent，接近"AI 同事"</td><td>高自主、长程任务、自带云沙箱；胜在端到端，代价是可控性与透明度更难做</td></tr>
            <tr><td>Cursor 式</td><td>深度集成 IDE 的 AI 编辑器</td><td>人在回路、编辑器内即时协作；胜在开发者掌控感强、反馈快，偏"增强人"而非"替代人"</td></tr>
            <tr><td>Claude Code 式</td><td>终端里的命令行 Agent</td><td>贴近工程师真实工作流（shell/git/测试），轻量可组合、可脚本化；自主与协作可按需切换</td></tr>
          </tbody>
        </table>
      </div>
      <p class="cjk">这几种形态的差异，本质上落在三条轴上：<strong>自主度</strong>（全自主 ↔ 人在回路）、<strong>集成位置</strong>（云端独立环境 ↔ 本地 IDE/终端）、<strong>交互粒度</strong>（提交整个任务 ↔ 逐步协作）。<mark class="key2">没有绝对最优，只有场景最优</mark>：明确定义、有完整测试、可后台跑的任务适合高自主形态；探索性强、需要人类品味与频繁纠偏的工作更适合 IDE 内协作。面试里被问"你会怎么设计一个 Coding Agent"，能沿这三条轴陈述取舍，并给出"我会先做计划审查 + 沙箱 + 测试驱动，把自主度做成可调"的答案，远胜于罗列功能。</p>
      <p class="cjk">还有一个跨越所有形态的共识值得记住：<strong>底层模型能力和上层脚手架（scaffold）是相乘关系，而非替代关系</strong>。同一个模型，配上更好的工具接口、更贴心的错误反馈、更合理的检索与编辑机制，SWE-bench 解决率可能天差地别；反过来，脚手架再精巧也补不齐一个基础推理能力不足的模型。这解释了为什么这个领域同时在两条战线上前进——模型侧靠后训练（尤其是第 16 章讲的可验证奖励 + GRPO）把编码与推理能力练强，产品侧靠工程把这份能力"接出来、用得稳"。<mark class="key">谁能把"强模型 × 好脚手架 × 可信验证 × 透明协作"这四项乘到最大，谁就能造出真正好用的 Coding Agent。</mark>这也是本章想留给你的最终判断框架。</p>

      <h3>面试追问链</h3>
      <p class="cjk">Coding Agent 的面试往往从"它难在哪"起步，一路追到具体的架构决策，提前串一遍这条链：</p>
      <ul class="hub-list">
        <li><strong>Q1：</strong>Coding Agent 比"让模型写代码"难在哪？→ 难在真实仓库的定位、多文件一致性、用测试验证、长程迭代四件事。</li>
        <li><strong>Q2：</strong>几十万行仓库怎么找到该改的地方？→ 词法/符号检索优先、向量检索补充，别无脑上向量库。</li>
        <li><strong>Q3：</strong>它怎么知道自己改对了？→ 编辑-运行-测试闭环，测试结果是近乎真值的奖励；引出先复现、最小 diff、跑回归。</li>
        <li><strong>Q4：</strong>你会怎么评估它？→ SWE-bench 的 FAIL_TO_PASS + PASS_TO_PASS 双判定，同时警惕数据污染与成本指标。</li>
        <li><strong>Q5：</strong>怎么保证安全、怎么设计人机协作？→ 沙箱隔离 + 分级授权 + 计划先行 + 透明轨迹；收尾到 Devin/Cursor/Claude Code 三条设计轴的取舍。</li>
      </ul>

      <div class="callout tip">
        <span class="label">本章小结</span>
        <span class="cjk">Coding Agent 的本质是"在真实代码库里定位问题 → 改对 → 用测试证明改对"的可验证闭环，它把上下文工程、工具设计、规划、评估、护栏全部落到一个场景里。四大挑战（检索、多文件编辑、测试反馈、长程任务）构成一条因果链；核心是编辑-运行-测试循环，靠测试提供近乎真值的反馈；定位优先词法与符号检索，编辑要用结构化补丁保证多文件一致；SWE-bench 用 FAIL_TO_PASS + PASS_TO_PASS 双重判定给出可信评测；沙箱与分级授权守住安全底线。Devin、Cursor、Claude Code 代表了自主度、集成位置、交互粒度三条轴上的不同取舍——<strong>没有最优解，只有把自主度做成可调、把验证做成可信、把执行做成透明</strong>，才是成熟的 Coding Agent 设计观。</span>
      </div>
