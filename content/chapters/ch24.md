      <h2 class="chap-title"><span class="kicker">24</span>云原生部署与数据飞轮：从"能跑"到"跑好、越跑越好"</h2>
      <p class="cjk">前面二十三章解决的是"Agent 会不会想、会不会用工具、会不会听说"。但一个残酷的现实是：<mark class="key">在你笔记本上 demo 跑通，和在生产环境扛住一万个用户，中间隔着一整个工程学科</mark>。这一章讲两件把 Agent 真正"送上天"的事：一是<strong>云原生部署</strong>——怎么把 Agent 打包、部署、弹性扩缩、管住状态；二是<strong>数据飞轮</strong>——怎么让线上真实流量反过来喂养 Agent，让它随着用的人越多而越来越强。前者是"活下去"，后者是"越活越好"。这两块是从"会写 Agent"到"能运营 Agent"的分水岭，也是资深岗面试最能拉开差距的地方。</p>

      <h3>为什么 Agent 部署和传统 Web 服务不一样</h3>
      <p class="cjk">你可能会想："部署嘛，不就是打个 Docker、扔上 K8s？"传统无状态 Web 服务确实如此，但 Agent 有几个特性，让它的部署格外棘手：</p>
      <ul class="hub-list">
        <li><strong>请求极不均匀、极慢</strong>：普通 API 几十毫秒返回，一次 Agent 请求可能跑几十秒到几分钟（多轮推理 + 多次工具调用），还高度依赖外部 LLM API 的延迟。按传统 QPS 思路配容量会严重误判。</li>
        <li><strong>它是有状态的</strong>：Agent 有对话历史、有多步任务的中间进度、有记忆。一旦某个实例挂了或被弹性缩容干掉，<mark class="key2">跑到一半的任务和上下文就没了</mark>——这是无状态 Web 服务不用操心的。</li>
        <li><strong>成本结构反常</strong>：主要成本不在 CPU/内存，而在 <strong>LLM token 调用</strong>。一个 CPU 占用极低的实例，可能正烧着大把 token 费用，传统按资源利用率的扩缩容信号会失灵。</li>
        <li><strong>失败是常态</strong>：依赖的 LLM API 会限流、会超时、会偶发抽风。Agent 系统必须把"外部依赖不可靠"当默认前提来设计重试、降级、熔断。</li>
      </ul>
      <div class="callout warn">
        <span class="label">核心认知</span>
        <span class="cjk">部署 Agent 的第一课，是承认它<mark class="key">既像 Web 服务（要高可用、要弹性）又像长时任务系统（有状态、耗时长、易失败）</mark>。照搬无状态微服务那套会翻车。下面的容器化、扩缩容、状态持久化，都是围绕"如何驯服这个又慢、又有状态、又依赖外部的怪兽"展开的。</span>
      </div>

      <h3>先打个比方：集装箱、码头和越来越准的物流</h3>
      <p class="cjk">整章的术语听着高大上，其实全能用<mark class="key">港口物流</mark>比明白：</p>
      <ul class="hub-list">
        <li><strong>容器化（Docker）＝把货打进标准集装箱</strong>：以前搬货，散装的箱子形状各异、这个港口能装那个港口装不了（"在我机器上是好的"）。集装箱标准化之后，<strong>不管哪条船、哪个码头、哪辆卡车，都能严丝合缝地装卸</strong>——你的代码连同依赖打成镜像，到哪台服务器都一样跑。</li>
        <li><strong>Kubernetes ＝自动化的码头调度中心</strong>：一个繁忙港口有成百上千个集装箱，靠人指挥要乱套。K8s 就是那个自动调度系统：<strong>决定每个箱子放哪条船（调度）、箱子掉海里了自动补一个（自愈）、货多了自动加船、货少了自动撤船（弹性伸缩）</strong>。</li>
        <li><strong>状态外置 ＝贵重货物存进码头仓库，别锁在某条船肚子里</strong>：如果把对话历史、任务进度锁在某个容器（某条船）内存里，这条船一沉（实例崩溃/被缩容），货就全没了。正确做法是把状态<strong>存进岸上的仓库（Redis、数据库、向量库）</strong>，这样任何一条船都能随时被替换，货还在。</li>
        <li><strong>数据飞轮 ＝越跑越准的物流网络</strong>：每一趟运输都记录下"哪条航线堵、哪个环节慢"，拿这些真实数据不断优化调度，网络就越用越高效。Agent 也一样——线上每一次真实对话都是养料。</li>
      </ul>
      <p class="cjk">把这幅"港口"画面记住：<mark class="key2">集装箱（一致）、调度中心（弹性自愈）、岸上仓库（状态外置）、越跑越准（飞轮）</mark>。下面每一节，都是在给这四样东西填工程细节。</p>

      <h3>容器化：让 Agent"到哪都一样跑"</h3>
      <p class="cjk">部署的地基是<strong>容器化（Docker）</strong>。它把你的代码、Python 版本、所有依赖库、系统环境打包成一个不可变的<strong>镜像（image）</strong>，做到"我这能跑，你那也一定能跑"，彻底消灭"在我机器上是好的"这类玄学问题。对 Agent 项目，容器化还有额外的好处：依赖固定（LLM SDK、向量库客户端版本锁死，避免线上线下不一致）、易于水平复制（要扛更多用户，就多起几个一模一样的容器）。</p>
      <div class="code-label">Dockerfile · 一个 Agent 服务的容器化骨架（示意）</div>
      <pre><code><span class="kw">FROM</span> python:3.12-slim
<span class="kw">WORKDIR</span> /app

<span class="cm"># 先拷依赖清单并安装——利用镜像层缓存，代码改动不必重装依赖</span>
<span class="kw">COPY</span> requirements.txt .
<span class="kw">RUN</span> pip install --no-cache-dir -r requirements.txt

<span class="kw">COPY</span> . .

<span class="cm"># 用 gunicorn 起多 worker；密钥绝不写进镜像，运行时用环境变量注入</span>
<span class="kw">ENV</span> PYTHONUNBUFFERED=1
<span class="kw">EXPOSE</span> 8000
<span class="kw">CMD</span> [<span class="st">"gunicorn"</span>, <span class="st">"-w"</span>, <span class="st">"4"</span>, <span class="st">"-k"</span>, <span class="st">"uvicorn.workers.UvicornWorker"</span>, <span class="st">"app:app"</span>, <span class="st">"-b"</span>, <span class="st">"0.0.0.0:8000"</span>]</code></pre>
      <div class="callout warn">
        <span class="label">镜像里的两个红线</span>
        <span class="cjk">① <strong>密钥绝不打进镜像</strong>：API Key、数据库密码要在运行时用环境变量或密钥管理服务（K8s Secret、云厂商 KMS）注入，写进镜像等于泄露。② <strong>镜像要瘦</strong>：用 <code>slim</code> 基础镜像、多阶段构建，别把训练数据、测试文件塞进去——镜像越小，启动越快，这对下面要讲的弹性扩缩容至关重要。</span>
      </div>

      <h3>Kubernetes 与弹性伸缩：按需给资源</h3>
      <p class="cjk">有了镜像，接下来要解决"用户忽多忽少怎么办"。<strong>Kubernetes（K8s）</strong>是事实上的容器编排标准，它替你做三件核心事：<strong>调度</strong>（把容器分配到合适的机器）、<strong>自愈</strong>（容器挂了自动重启、机器坏了自动迁移）、<strong>弹性伸缩</strong>（流量大了自动多起几个副本，流量小了自动收回）。对 Agent 服务，最关键的是<mark class="key">弹性伸缩（autoscaling）</mark>——白天高峰起 20 个副本，凌晨低谷缩到 2 个，既扛得住又不浪费钱。</p>
      <p class="cjk">但这里有个 Agent 专属的坑：<mark class="key2">传统 K8s 的水平自动扩缩（HPA）默认看 CPU 利用率，而 Agent 实例的瓶颈根本不在 CPU</mark>——它大部分时间在"等 LLM API 返回"，CPU 几乎是闲的。用 CPU 当扩缩信号，会出现"明明请求已经堆积、用户在排队，但 CPU 不高、系统死活不扩容"的荒诞局面。正确做法是用<strong>自定义指标</strong>扩缩容：比如"并发进行中的请求数""请求队列长度""平均响应延迟"。这是把传统 Web 运维经验直接套到 Agent 上最常见、也最致命的误区之一。</p>
      <div class="table-wrap">
        <table>
          <thead><tr><th>扩缩信号</th><th>适合传统 Web</th><th>适合 Agent</th><th>说明</th></tr></thead>
          <tbody>
            <tr><td>CPU 利用率</td><td>✅</td><td>❌</td><td>Agent 大多在等 I/O，CPU 不反映真实负载</td></tr>
            <tr><td>并发请求数 / 队列长度</td><td>✅</td><td>✅✅</td><td>直接反映"有多少人在等"，最贴合 Agent</td></tr>
            <tr><td>p95 响应延迟</td><td>✅</td><td>✅</td><td>延迟涨说明扛不住了，该扩容</td></tr>

      </div>

      <h3>Serverless：另一种取舍</h3>
      <p class="cjk">除了自己管 K8s，还有一条更省心的路：<strong>Serverless（无服务器）</strong>——把代码交给云平台，它按调用次数和执行时长计费，没请求时缩到零、不花一分钱，来请求了自动拉起。对<mark class="key">流量稀疏、突发、又不想养一支运维团队</mark>的 Agent 应用（比如内部工具、低频场景），Serverless 很香。但它对 Agent 有两个硬约束要警惕：</p>
      <ul class="hub-list">
        <li><strong>执行时长上限</strong>：不少 Serverless 平台单次执行有超时限制（如几分钟）。一个需要长时间多轮推理的 Agent 任务，可能还没跑完就被强杀——这类长任务要拆分或改用别的部署形态。</li>
        <li><strong>冷启动</strong>：缩到零之后第一个请求要等平台拉起实例、加载依赖，可能有明显延迟。对上一章的语音 Agent 这种延迟敏感场景，冷启动几乎不可接受。</li>
      </ul>
      <div class="callout tip">
        <span class="label">怎么选：K8s vs Serverless</span>
        <span class="cjk">经验法则：<strong>流量持续、量大、任务长、要精细控制</strong> → 自管 K8s；<strong>流量稀疏、突发、任务短、想省运维</strong> → Serverless。很多成熟系统是混合的：核心长时 Agent 跑在 K8s，边缘的轻量函数（如 webhook、异步通知）用 Serverless。又是那句话——<mark class="key">没有最好的架构，只有最适合当前流量与团队的架构</mark>。</span>
      </div>

      <h3>状态持久化：别让崩溃抹掉一切</h3>
      <p class="cjk">这是 Agent 部署里最容易被 demo 思维坑到的一点。开发时，对话历史、任务进度往往就存在进程内存里——图省事，但<mark class="key2">一旦实例重启、崩溃、或被弹性缩容干掉，内存里的一切灰飞烟灭</mark>：用户的对话断了、跑了一半的多步任务丢了。生产级 Agent 必须把状态<strong>外置</strong>到进程之外的持久化存储，让任何一个实例都是"可随时替换的无状态外壳"，真正的状态在外部：</p>
      <ul class="hub-list">
        <li><strong>会话/短期记忆</strong>：放 Redis 这类快取，快速读写、可设过期。</li>
        <li><strong>长期记忆/知识</strong>：放向量库 + 数据库（呼应第 6、10 章）。</li>
        <li><strong>长任务的执行进度</strong>：把每步结果检查点（checkpoint）落库，实例挂了换一个实例能从断点续跑——这正是 LangGraph 等框架的 checkpointer、持久化状态图想解决的问题。</li>
      </ul>
      <p class="cjk">把状态外置后，你就能安心做弹性伸缩：随便杀掉哪个副本都不心疼，因为它身上没有不可恢复的东西。<mark class="key">"实例无状态、状态外置"是让 Agent 既高可用又可弹性的地基</mark>，这条原则和第 19 章讲的生产可靠性原则一脉相承。</p>

      <h3>数据飞轮：让 Agent 越用越强</h3>
      <p class="cjk">部署解决了"活下去"，<strong>数据飞轮（data flywheel）</strong>解决"越活越好"。它的思想借自互联网增长飞轮：<mark class="key">用户使用 → 产生真实数据 → 用数据改进产品 → 产品变好 → 更多人用 → 产生更多数据</mark>，形成正循环。对 Agent，这个飞轮具体转起来是这样一条闭环：</p>
      <figure class="diagram">
        <pre class="mermaid">
flowchart LR
    U[真实用户使用] --> L[记录轨迹+反馈]
    L --> M[挖掘失败案例/难例]
    M --> D[补进评估集+训练数据]
    D --> I[改提示/补检索/微调]
    I --> B[Agent 变强]
    B --> U
        </pre>
        <figcaption>图 24-2　Agent 数据飞轮：线上真实流量反哺，越转越强</figcaption>
      </figure>
      <p class="cjk">拆开看这条闭环的每一环，都能对应到前面章节的能力：</p>
      <ul class="hub-list">
        <li><strong>采集</strong>：靠第 5、11 章的可观测性，把每一次真实对话的完整轨迹（输入、推理、工具调用、输出）和用户反馈（点赞点踩、是否转人工、是否重问）记录下来。<mark class="key2">没有埋点，就没有飞轮</mark>——这是第一步也是最容易被跳过的一步。</li>
        <li><strong>挖掘</strong>：从海量真实流量里筛出"金子"——被点踩的、触发了兜底的、用户反复追问的失败案例，正是最有价值的改进线索，远比你在办公室里凭空想象的测试用例真实。</li>
        <li><strong>沉淀</strong>：把这些真实难例补进第 11 章的评估集，让评估集随线上问题持续生长，越来越贴近真实分布。</li>
        <li><strong>改进</strong>：根据问题类型选最省的手段——大多数问题改提示词（第 21 章）或补检索文档（第 10 章）就能解决；只有当某类能力系统性欠缺、且数据量足够时，才动用第 16 章的微调（SFT/RL）。</li>
      </ul>
      <div class="callout warn">
        <span class="label">飞轮的两条纪律</span>
        <span class="cjk">① <strong>先埋点，后一切</strong>：数据飞轮的燃料是数据，产品上线第一天就要把轨迹和反馈采集做好，否则等你想改进时手里空空。② <strong>别一上来就想微调</strong>：微调成本高、周期长、易翻车。飞轮的绝大部分收益来自"改提示 + 补检索 + 扩评估集"这些轻量迭代，微调是最后的、也是最重的手段。把飞轮理解成"持续的数据驱动迭代"，而不是"不停地训模型"。</span>
      </div>

      <h3>一个故事：客服 Agent 是怎么"越用越强"的</h3>
      <p class="cjk">抽象的飞轮不好记，我们讲个具体的小故事——某电商的退货客服 Agent，上线三个月是怎么一步步变强的：</p>
      <ul class="hub-list">
        <li><strong>第 1 周（埋点先行）</strong>：团队没急着堆功能，而是先把每通对话的完整轨迹（用户问了啥、Agent 怎么推理、调了哪个工具、最后答了啥）和反馈（用户点了"没解决"、还是转了人工）全存下来。此刻飞轮还没转，但<mark class="key">燃料箱开始蓄油</mark>。</li>
        <li><strong>第 3 周（挖到金子）</strong>：一查数据发现，"没解决"的对话里有 40% 都卡在同一句话——用户问"跨境订单能不能退"，Agent 一律答"可以"，结果跨境根本不支持退货，用户投诉暴增。<mark class="key2">这条真实失败案例，比产品经理拍脑袋想的测试用例值钱一百倍</mark>。</li>
        <li><strong>第 4 周（轻量迭代，不碰模型）</strong>：怎么修？没微调、没重训，只做了两件小事——① 把"跨境不支持退货"这条规则补进检索知识库（第 10 章）；② 在 system prompt 里加一句"涉及跨境订单，先核对退货政策再答"（第 21 章）。同时把这个 case 加进评估集（第 11 章），防止以后改坏了没人发现。</li>
        <li><strong>第 6 周（见效 + 继续转）</strong>："跨境退货"这类投诉几乎归零。而新的埋点又浮现出下一批高频失败（比如"退货运费谁出"），团队接着挖、接着补……<mark class="key">飞轮转起来了：用得越多 → 暴露的真实问题越多 → 修得越准 → 用户越满意 → 用得更多</mark>。</li>
        <li><strong>第 3 个月（万不得已才微调）</strong>：只有当发现某一整类能力（比如"识别用户情绪并调整话术"）靠改提示和补检索怎么都调不好、且已经攒够了几千条标注数据时，才最后动用微调这门"重炮"。</li>
      </ul>
      <p class="cjk">这个故事的每一步都踩在飞轮的闭环上：<strong>埋点 → 挖失败难例 → 补检索/改提示/扩评估集 → 变强</strong>。注意通篇最贵的"微调"被放到了最后、且被严格限定条件——这正是"先埋点、轻迭代、慎微调"的真实写照。<mark class="key2">竞争对手能抄走你的提示词，但抄不走你这三个月里积累的真实失败案例和越修越准的判断力</mark>，这就是数据飞轮作为护城河的意义。</p>

      <p class="cjk">数据飞轮是 Agent 产品真正的护城河：模型大家都能调 API，但<mark class="key">你线上积累的真实交互数据、以及由它驱动的持续改进能力，是竞争对手抄不走的</mark>。这也是为什么"能运营 Agent"比"能写 Agent"值钱得多——前者手里握着一台越转越快的增长引擎。</p>

      <h3>面试追问链</h3>
      <p class="cjk">部署与飞轮是资深岗的分水岭题，面试官爱考"你有没有真把 Agent 运营起来过"：</p>
      <ul class="hub-list">
        <li><strong>Q1：</strong>Agent 部署和普通 Web 服务有何不同？→ 请求慢且不均、有状态、成本在 token 不在 CPU、外部依赖易失败。</li>
        <li><strong>Q2：</strong>为什么 Agent 不能用 CPU 做扩缩容信号？→ 它多在等 LLM I/O，CPU 闲着；该用并发请求数/队列长度/延迟等自定义指标。</li>
        <li><strong>Q3：</strong>K8s 和 Serverless 怎么选？→ 流量持续/长任务/要控制用 K8s；流量稀疏/短任务/省运维用 Serverless，注意超时与冷启动。</li>
        <li><strong>Q4：</strong>怎么保证实例崩溃不丢任务？→ 实例无状态、状态外置（Redis/向量库/DB），长任务做检查点，可断点续跑。</li>
        <li><strong>Q5：</strong>什么是数据飞轮，怎么落地？→ 使用→采集轨迹反馈→挖失败案例→补评估集/训练数据→改进→变强的正循环；前提是先做好埋点。</li>
        <li><strong>Q6：</strong>飞轮里改进 Agent 优先用什么手段？→ 优先改提示/补检索/扩评估集这些轻量迭代，微调是最后重手段。</li>
        <li><strong>Q7：</strong>Agent 产品的护城河是什么？→ 线上真实交互数据 + 数据飞轮驱动的持续改进能力，竞品抄不走。</li>
      </ul>

      <div class="callout tip">
        <span class="label">本章小结</span>
        <span class="cjk">把 Agent 送上生产，要过两关。第一关"活下去"——<strong>容器化</strong>保证到处一样跑（密钥别进镜像），<strong>K8s/Serverless</strong> 做弹性伸缩（Agent 要用并发/延迟而非 CPU 当扩缩信号），<mark class="key">实例无状态、状态外置</mark>（Redis+向量库+检查点）保证崩溃不丢任务。第二关"越活越好"——用<strong>数据飞轮</strong>让线上真实流量反哺：<mark class="key2">采集轨迹与反馈 → 挖失败难例 → 补评估集/训练数据 → 改提示/补检索/（必要时）微调 → Agent 变强 → 更多使用</mark>。先埋点、轻迭代、慎微调。记住这条主线：<strong>部署让 Agent 活着，飞轮让 Agent 进化——而真实数据与持续迭代能力，才是抄不走的护城河</strong>。至此，全书从原理、框架、工程到部署运营的完整闭环就此合拢。</span>
