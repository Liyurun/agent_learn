      <h2 class="chap-title"><span class="kicker">22</span>高级推理与搜索式规划：从链到树到图</h2>
      <p class="cjk">上一章的思维链（CoT）解决了"让模型想一步再答"，但它有一个根本局限：<mark class="key">推理是一条不可回头的直线</mark>——一旦某步走岔，整条链就废了，模型没有"这条路不对，我退回去换一条"的能力。人类解难题时可不是这样：我们会同时构想几种思路、评估哪条更有希望、走不通就回退。这一章讲的就是把这种"探索—评估—回溯"的能力赋予 LLM 的一系列前沿方法：<strong>Tree of Thoughts、ReWOO、LATS、Graph of Thoughts</strong>。它们代表了 Agent 推理从"线性链"到"树搜索"再到"图结构"的演进主线，是高频进阶面试题，也是你判断"要不要为难题上重型推理框架"的知识基础。</p>

      <div class="callout tip">

      <h3>先建立主线：从 CoT 到搜索，缺的是什么</h3>
      <p class="cjk">要理解这些方法，先看清 CoT 到底缺什么。CoT 是一条<strong>线性的、贪心的、一次成型</strong>的推理链——模型顺着往下写，不回头、不比较、不评估。这在"路径基本唯一"的问题上够用，但面对需要试错、需要规划、有多种可能走法的难题（如数学谜题、复杂决策），线性链就会力不从心。补齐的关键有两个动作：<mark class="key2">一是"生成多条候选路径"（探索），二是"评估路径好坏并据此选择/回溯"（搜索）</mark>。把这两个动作加进来，推理就从"写一条链"升级成"在一个解空间里搜索"。下面四种方法，本质都是在回答"怎么把探索和搜索加进 LLM 推理"这个问题，只是结构越来越复杂。</p>

      <h3>先打个比方：走迷宫的三种走法</h3>
      <p class="cjk">这几种方法听起来玄乎，其实用<mark class="key">走迷宫</mark>一比就全通了。假设你要从迷宫入口走到出口：</p>
      <ul class="hub-list">
        <li><strong>CoT（链）＝闭着眼一路往前走</strong>：每到岔路口凭直觉选一条，绝不回头。运气好一次走通，运气差撞了墙也只能干瞪眼——因为你没记路、也不允许折返。这就是"线性、贪心、一次成型"。</li>
        <li><strong>ToT（树）＝带着记号笔探路</strong>：到岔路口先把几条路都瞄一眼、估一估哪条更像通向出口（评估），选最有希望的走；走到死胡同就<strong>退回上一个岔路口</strong>换另一条（回溯）。慢是慢点，但能系统地把迷宫走通。</li>
        <li><strong>GoT（图）＝一群人分头探还能拼地图</strong>：好几个人从不同入口同时探，各自画出一段路，最后<strong>把大家的地图拼（合并）成一张完整的</strong>。适合那种"必须把好几段结果凑起来才有答案"的迷宫。</li>
      </ul>
      <p class="cjk">而 <strong>ReWOO</strong> 不改走法，它省的是"体力"：与其每走一步都把"我从哪来、路过哪些地方"重新念叨一遍（token 反复膨胀），不如<mark class="key2">出发前先把整条路线一次性规划好，然后闷头走完</mark>。<strong>LATS</strong> 则是"带着概率论的探路老手"——不仅回溯，还会用一套数学（蒙特卡洛树搜索）精打细算"这条路值不值得再深入探"，是最聪明也最费劲的走法。记住这个迷宫比喻，下面每个方法你都能对号入座。</p>

      <h3>Tree of Thoughts（ToT）：把推理变成树搜索</h3>
      <p class="cjk"><strong>Tree of Thoughts（ToT）</strong>由 Yao 等人在 2023 年提出，核心思想是把问题求解建模为<mark class="key">对一棵"思维树"的搜索</mark>：树上每个节点是一个中间状态（一个"想法"），模型在每个节点生成多条候选想法作为分支，再用一个评估函数给每条分支打分，然后用 BFS 或 DFS 等搜索算法遍历这棵树，支持<strong>前瞻（lookahead）</strong>和<strong>回溯（backtracking）</strong>——发现某条路走不通就退回上一个岔口换一条<a class="cite" href="https://arxiv.org/abs/2305.10601" target="_blank" rel="noopener">[来源]</a>。</p>
      <p class="cjk">和 CoT 对比，ToT 补上的正是 CoT 缺的两块：CoT 只有一条链、不评估、不回头；ToT 有多条分支、显式评估每条分支、走不通能回溯。论文在需要规划与试错的任务（如数字游戏 Game of 24、创意写作等）上验证了它相比 CoT 的优势<a class="cite" href="https://arxiv.org/abs/2305.10601" target="_blank" rel="noopener">[来源]</a>。ToT 需要你定义四个组件，理解它们就理解了 ToT 的骨架：</p>
      <ul class="hub-list">
        <li><strong>思维分解</strong>：把问题拆成若干推理步骤，每步作为树的一层。</li>
        <li><strong>想法生成器</strong>：在每个节点让模型产出 k 条候选想法（分支）。</li>
        <li><strong>状态评估器</strong>：给每个状态打分（"这条路有多大希望到达正解"），这是 ToT 的灵魂——评估质量直接决定搜索效率。</li>
        <li><strong>搜索算法</strong>：BFS（每层保留最优的几个）或 DFS（一条路走到底，不行就回溯）。</li>
      </ul>
      <div class="callout warn">
        <span class="label">ToT 的代价</span>
        <span class="cjk">强大不是免费的。ToT 要在每个节点生成多条想法、还要逐个评估，<mark class="key2">LLM 调用次数和 token 消耗相比单链 CoT 大幅上升</mark>，计算成本高、延迟大。所以它只适合"难到值得为它烧钱"的问题；日常任务用 ToT 是杀鸡用牛刀。这也再次印证全书的判断准则：复杂度要用在刀刃上。</span>
      </div>

      <h3>手把手走一遍：用 ToT 玩"24 点"</h3>
      <p class="cjk">光说组件太抽象，我们拿 ToT 论文里的经典题目——<strong>24 点游戏</strong>走一遍，你立刻就懂"树搜索"到底在干嘛。规则：给 4 个数字，用加减乘除（每个数用一次）算出 24。给定 <code>4, 9, 10, 13</code>。</p>
      <p class="cjk"><strong>CoT 会怎么做？</strong>它一条链往下写：<code>4+9=13，13+10=23，23+13=36≠24</code>——算错了，但链已经写死，它不会回头，这题就答砸了。<strong>ToT 怎么做？</strong>它把"每一步选两个数做一次运算"当成树的一层，逐层展开、评估、剪枝：</p>
      <div class="table-wrap">
        <table>
          <thead><tr><th>层</th><th>动作</th><th>生成的候选（分支）</th><th>状态评估器打分</th></tr></thead>
          <tbody>
            <tr><td>第 1 步</td><td>从 4,9,10,13 里挑两个做一次运算</td><td>① 13-9=4 → 剩 <code>4,4,10</code><br>② 10-4=6 → 剩 <code>6,9,13</code><br>③ 4+9=13 → 剩 <code>13,10,13</code></td><td>① 有希望（4×？想到 4×(10-4)…）<br>② 有希望（6×？→ 6×(13-9)=24！）<br>③ 感觉难，<strong>剪枝✗</strong></td></tr>
            <tr><td>第 2 步</td><td>沿"有希望"的分支②继续：6,9,13</td><td>13-9=4 → 剩 <code>6,4</code></td><td>6×4=24，就在眼前，高分保留</td></tr>
            <tr><td>第 3 步</td><td>剩 6,4 做最后一次运算</td><td>6×4 = <strong>24</strong> ✅</td><td>命中目标，搜索成功</td></tr>
          </tbody>
        </table>
      </div>
      <p class="cjk">看清 ToT 的三个动作了吗？<mark class="key">① 每步生成多个候选（探索）；② 用评估器判断"这条路有没有希望到 24"并剪掉没戏的（评估）；③ 沿最有希望的分支往下、走不通就回退换分支（搜索/回溯）</mark>。答案 <code>(13-9)×(10-4)=24</code> 就是这样被"搜"出来的，而不是像 CoT 那样"一条道走到黑撞了南墙"。这也解释了为什么 ToT 贵——光第 1 步就要让模型生成好几个候选、再逐个评估打分，一道题的 LLM 调用次数是 CoT 的好几倍。</p>

      <h3>ReWOO：把推理和工具观察解耦，省 token</h3>
      <p class="cjk">前面几种方法关注"怎么想得更好"，<strong>ReWOO（Reasoning WithOut Observation）</strong>关注的是另一个痛点：<mark class="key">在工具增强的场景里，怎么少浪费 token</mark>。回想第 3 章的 ReAct——它是"推理→行动→观察"交错循环，每调用一次工具，就要把观察结果拼回提示词再喂给模型推理下一步。问题是：随着步数增加，前面所有的观察结果反复出现在上下文里，token 快速膨胀、成本飙升。</p>
      <p class="cjk">ReWOO 的解法是把"推理"和"观察"<strong>解耦</strong>：由一个 <strong>Planner</strong> 先一次性生成完整的推理蓝图（列出要做哪几步、每步调用什么工具、步骤间怎么依赖），然后集中执行这些工具调用，最后由 <strong>Solver</strong> 拿着计划和所有工具结果一次性汇总出答案。这样模型不必在每一步都把历史观察重新读一遍。论文报告在 HotpotQA 上取得约 <strong>5 倍</strong>的 token 效率提升与约 <strong>4%</strong> 的准确率提升<a class="cite" href="https://arxiv.org/abs/2305.18323" target="_blank" rel="noopener">[来源]</a>。</p>
      <div class="table-wrap">
        <table>
          <thead><tr><th>维度</th><th>ReAct（交错式）</th><th>ReWOO（解耦式）</th></tr></thead>
          <tbody>
            <tr><td>推理与观察</td><td>每步交错，观察拼回上下文</td><td>先规划全部，再集中执行</td></tr>
            <tr><td>token 消耗</td><td>随步数膨胀（观察反复出现）</td><td>显著更省（不重复喂观察）</td></tr>
            <tr><td>纠错灵活性</td><td>高：每步都能根据观察调整</td><td>低：计划前置，中途偏差难即时纠正</td></tr>
            <tr><td>适用</td><td>高度依赖中间结果、需动态调整</td><td>步骤相对可预先规划、追求效率</td></tr>
          </tbody>
        </table>
      </div>
      <p class="cjk">这张对比表就是面试答点：ReWOO 用"计划前置"换"token 效率"，但代价是牺牲了 ReAct"边走边看边调"的灵活性——如果某步工具结果和预期差很多，ReWOO 因为计划已经定死，纠错不如 ReAct 及时。<mark class="key2">没有免费的午餐，只有针对场景的取舍</mark>。</p>
      <p class="cjk">为什么 ReWOO 能省这么多 token？我们算一笔<strong>直观的账</strong>。假设一个任务要调 3 次工具，每次观察结果约 500 token，问题本身约 200 token：</p>
      <div class="table-wrap">
        <table>
          <thead><tr><th></th><th>ReAct（交错式，观察反复带上）</th><th>ReWOO（解耦式，观察不重复喂）</th></tr></thead>
          <tbody>
            <tr><td>第 1 次推理</td><td>问题 200</td><td>Planner 一次读问题 200，产出完整计划</td></tr>
            <tr><td>第 2 次推理</td><td>问题 200 + 观察1 500 = 700</td><td>（工具按计划执行，<strong>不再喂给模型</strong>）</td></tr>
            <tr><td>第 3 次推理</td><td>问题 200 + 观察1+2 = 1200</td><td>—</td></tr>
            <tr><td>最后汇总</td><td>问题 200 + 观察1+2+3 = 1700</td><td>Solver 一次性读 问题 + 3 份观察 ≈ 1700</td></tr>
            <tr><td><strong>累计输入 token</strong></td><td><strong>≈ 3800</strong>（观察被反复重读）</td><td><strong>≈ 1900</strong>（每份观察只读一次）</td></tr>
          </tbody>
        </table>
      </div>
      <p class="cjk">看出门道了吗？ReAct 的毛病是<mark class="key">"观察结果像滚雪球一样反复出现在每一轮上下文里"</mark>——步数越多，重复喂进去的历史观察越多，token 呈"叠加式"膨胀。ReWOO 因为"先规划、集中执行、最后一次性汇总"，<strong>每份观察只被模型读一次</strong>，所以省得多。论文在 HotpotQA 上报出约 5 倍 token 效率提升，就是这个机制在多步、多工具任务上放大后的效果。这笔账也顺带点破了它的软肋：因为计划一开始就定死，万一"观察1"的结果和预期南辕北辙，ReWOO 不像 ReAct 那样能立刻见机行事、改道重来。</p>

      <h3>LATS：用蒙特卡洛树搜索统一推理、行动与规划</h3>
      <p class="cjk"><strong>LATS（Language Agent Tree Search）</strong>可以理解为"ToT 的加强版 + ReAct 的融合"。它是首个把<mark class="key">推理、行动、规划</mark>统一到一个框架里的方法，核心是把<strong>蒙特卡洛树搜索（MCTS）</strong>引入 LLM 智能体：通过"选择—扩展—评估—回传"的 MCTS 循环刻意构造和探索多条轨迹，并结合<strong>环境反馈</strong>与<strong>自我反思</strong>来指导搜索方向，全程无需额外训练<a class="cite" href="https://arxiv.org/abs/2310.04406" target="_blank" rel="noopener">[来源]</a>。</p>
      <p class="cjk">和 ToT 的关键区别在于：ToT 主要在"纯推理"的思维树上搜索，而 LATS 的节点是"能与环境交互的行动轨迹"——它既会想（推理），也会做（调用工具、观察反馈），还会用 MCTS 系统性地权衡"该继续深挖这条路，还是回头探索别的路"。这让它在需要与环境交互并做决策的任务（编程、问答、网页操作等）上表现更强。代价也最重：<mark class="key2">MCTS 要展开大量节点、反复做价值评估，LLM 调用和延迟成本是这几种方法里最高的之一</mark>，几乎只在"离线、追求极致成功率、不在乎慢和贵"的场景才划算。</p>

      <h3>Graph of Thoughts（GoT）：当思路需要"合并"</h3>
      <p class="cjk">树结构解决了分叉和回溯，但还有一类问题它表达不了：<mark class="key">把多个子结果"汇聚"成一个</mark>。比如"把一个大列表分块分别排序，再归并成整体有序"——这需要多条思路先分头推进、再合并，树的"只分叉不汇合"结构做不到。<strong>Graph of Thoughts（GoT）</strong>把思维建模为任意的<strong>有向图</strong>：顶点是想法，边是依赖，想法之间可以被<strong>合并（aggregate）</strong>、<strong>精炼（refine）</strong>、反馈循环，从而突破了链（CoT）只能顺序、树（ToT）只能分叉的限制<a class="cite" href="https://arxiv.org/abs/2308.09687" target="_blank" rel="noopener">[来源]</a>。</p>
      <p class="cjk">一句话记住这条演进：<mark class="key2">CoT 是链、ToT 是树、GoT 是图</mark>，表达能力依次增强，实现和调度的复杂度也依次上升。GoT 适合那些"能分解成子问题、子解又需要再聚合"的复杂任务（排序、集合运算等聚合型问题）。据综述转述，GoT 在排序任务上相比 ToT 有明显的质量提升与成本下降，但要落地一个图结构的调度器，工程复杂度远高于前几种<a class="cite" href="https://arxiv.org/abs/2308.09687" target="_blank" rel="noopener">[来源]</a>。</p>

      </div>
      <div class="callout tip">
        <span class="label">和前面章节怎么串起来</span>
        <span class="cjk">别把这些当孤立技巧。它们和第 3 章的 <strong>Plan-and-Execute</strong>、<strong>Reflexion</strong> 是同一条脉络：Plan-and-Execute 是"先规划后执行"的朴素版，ReWOO 是它在"省 token"方向的精化；Reflexion 的"反思—改进"正是 LATS 里"自我反思指导搜索"的组成部分；而 ToT/GoT 则是把 CoT 从"一条链"扩展到"多条路径的结构化搜索"。<mark class="key">一条主线贯穿：Agent 的推理能力，就是沿着"单链 → 反思 → 规划 → 树/图搜索"不断加入探索与评估的过程。</mark></span>
      </div>

      <h3>工程现实：什么时候真的该用它们</h3>
      <p class="cjk">讲了这么多"高级"方法，最重要的一条工程忠告反而是：<mark class="key2">绝大多数生产系统用不上 ToT/LATS/GoT</mark>。它们成本高、延迟大、实现复杂，只有当你面对的是"高价值、难度大、可离线、且简单方法确实搞不定"的问题（如复杂数学求解、需要深度规划的自动化科研）时，才值得投入。日常业务 Agent，一个写好的 ReAct + 恰当的提示工程（上一章）+ 必要的反思，往往就够了。<strong>知道这些方法存在、理解它们解决什么、能判断何时该用</strong>——这才是这一章对多数工程师的真正价值，也是面试官真正想考察的判断力，而不是要你去手写一个 MCTS。</p>

      <h3>面试追问链</h3>
      <p class="cjk">高级推理类题目，面试官爱考"你是否理解演进关系与取舍"：</p>
      <ul class="hub-list">
        <li><strong>Q1：</strong>CoT 有什么局限，ToT 怎么补？→ CoT 线性不回头；ToT 加入多分支探索、状态评估与回溯，把推理变成树搜索。</li>
        <li><strong>Q2：</strong>ReWOO 相比 ReAct 好在哪、差在哪？→ 好在推理与观察解耦、省 token（约 5×）；差在计划前置、中途纠错不如 ReAct 灵活。</li>
        <li><strong>Q3：</strong>LATS 的核心是什么？→ 把 MCTS 引入 Agent，统一推理/行动/规划并结合反思；代价是成本极高。</li>
        <li><strong>Q4：</strong>为什么会有 Graph of Thoughts？→ 树只能分叉不能合并，GoT 用图支持思路的聚合与精炼。</li>
        <li><strong>Q5：</strong>这几种和 Plan-and-Execute/Reflexion 什么关系？→ 同一条"加入探索与评估"的脉络：规划、反思、树/图搜索都是给线性推理补能力。</li>
        <li><strong>Q6：</strong>生产里你会用哪个？→ 多数用 ReAct + 提示工程 + 反思就够；ToT/LATS 只在高价值难题且可离线时才划算。</li>
      </ul>

      <div class="callout tip">
        <span class="label">本章小结</span>
        <span class="cjk">Agent 的推理能力沿着<strong>链 → 树 → 图</strong>不断进化，本质都是给"线性的 CoT"补上<mark class="key">探索（生成多条路径）</mark>与<mark class="key">搜索（评估并选择/回溯）</mark>两种能力。<strong>ToT</strong> 用树搜索做多路径探索与回溯；<strong>ReWOO</strong> 把推理与工具观察解耦以省 token；<strong>LATS</strong> 用 MCTS 统一推理/行动/规划、成本最高；<strong>GoT</strong> 用图结构支持思路合并与精炼。它们威力大、代价也大，工程上<strong>够用即止</strong>——多数系统 ReAct + 好提示词就能打，真正的本事是<mark class="key">知道它们存在、理解取舍、判断何时该用</mark>。</span>
      </div>
