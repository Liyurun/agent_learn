      <h2 class="chap-title"><span class="kicker">03</span>六大核心设计模式</h2>
      <p class="cjk">设计模式是 Agent 的"招式库"，也是面试进阶题的主战场。掌握下面六个模式，既能应对"你知道哪些 Agentic 模式"的直接提问，也能在系统设计题里信手拈来。<mark class="key">设计模式的价值不在于名词本身，而在于它把"如何组织感知—决策—行动循环"这件事沉淀成了可复用、可组合、可讲清取舍的工程套路</mark>——面试官真正想听的，是你能不能针对一个具体任务说清"为什么选它、代价是什么、什么时候不该用"。</p>
      <p class="cjk">下面这张总览表先给你一个鸟瞰：六大模式各自解决什么问题、适合什么场景、要付出什么代价。读完全章后，建议你合上书，凭记忆复述这张表，并给每一行补上一句"失败模式"——能做到这一点，基本就达到了中高级面试对设计模式的考察深度。要强调的是，这六者<strong>并非平行的六选一</strong>：ReAct 与 Planning 是两种"控制流骨架"，Tool Use 是所有 Agent 共享的地基，Reflection 与 Evaluator-Optimizer 是"质量增强层"，Multi-Agent 则是"拓扑层"的扩展——理解它们所处的层次，比死记名字更能帮你在设计题里灵活组合。</p>

      <h3>ReAct：最该吃透的基础模式</h3>
      <p class="cjk">ReAct 把 Agent 的每一步拆成 <strong>Thought（思考）→ Action（行动）→ Observation（观察）</strong> 的循环。模型先想"我该做什么"，再输出一个工具调用，拿到结果后继续想下一步，直到得出答案。它是最直观、也最通用的 Agent 骨架，几乎所有框架的默认 Agent 都是 ReAct 的变体。</p>
      <p class="cjk"><strong>定义与直觉。</strong>ReAct 是 "Reasoning + Acting" 的缩写，核心洞察是：把"思维链推理"和"工具调用"交织在同一条轨迹里，让二者互相纠偏。纯推理（Chain-of-Thought）容易一路自说自话地滑向幻觉，因为它没有任何外部信号来校正；纯行动（只调工具不推理）又缺乏对"下一步该查什么"的规划。ReAct 让模型在每次行动前先用一句自然语言"想"出理由，行动后再把真实的 Observation 拉回上下文——<mark class="key">推理为行动指路，观察为推理纠偏</mark>，这就是它比二者单独使用都更稳健的根本原因。</p>
      <p class="cjk"><strong>适用场景。</strong>凡是"信息不全、路径无法预先枚举、需要边探索边决定下一步"的任务，ReAct 都是首选骨架：开放式问答、需要多次检索的研究、要读文件再改代码的编程助手、要根据页面反馈决定点哪里的浏览器 Agent。反过来，如果任务路径完全确定（如"抽取字段→写库"），用 ReAct 反而是杀鸡用牛刀——固定 Workflow 更省更稳（见第 1 章）。</p>

      <p class="cjk"><strong>最小实现：一段能默写的 ReAct 循环。</strong>面试白板上，能手写出下面这段骨架，胜过背十个框架 API。它的要点是：把工具描述与格式约束写进系统提示，在循环里不断把 <code>action</code> 与 <code>observation</code> 追加回上下文，并用"是否产出最终答复"作为终止判据，同时用 <code>MAX_STEPS</code> 兜底防止无限循环。</p>
      <div class="code-label">Python · 极简 ReAct 循环骨架</div>
      <pre><code><span class="cm"># 系统提示里约定输出格式：先 Thought，再 Action(JSON)，或给出 Final Answer</span>
<span class="kw">def</span> <span class="fn">react_agent</span>(goal, tools, llm, max_steps=8):
    ctx = [system_prompt(tools), {<span class="st">"role"</span>: <span class="st">"user"</span>, <span class="st">"content"</span>: goal}]
    <span class="kw">for</span> step <span class="kw">in</span> range(max_steps):
        out = llm(ctx)                      <span class="cm"># 一次推理：产出 Thought + Action 或 Final</span>
        <span class="kw">if</span> out.is_final:                    <span class="cm"># 终止条件：模型认为信息已充分</span>
            <span class="kw">return</span> out.answer
        obs = tools[out.action.name](**out.action.args)  <span class="cm"># 行动：真实调用工具</span>
        ctx.append(out.raw)                 <span class="cm"># 把 Thought+Action 写回上下文</span>
        ctx.append({<span class="st">"role"</span>: <span class="st">"tool"</span>, <span class="st">"content"</span>: obs})  <span class="cm"># 把 Observation 写回</span>
    <span class="kw">return</span> summarize_best_effort(ctx)      <span class="cm"># 兜底：达步数上限仍未完成</span></code></pre>
      <p class="cjk">这段代码里藏着三个生产必答题：<strong>格式解析的鲁棒性</strong>（模型偶尔不按格式输出，需容错重试或用结构化输出/function calling 强约束）、<strong>Observation 的裁剪</strong>（工具返回可能是几十 KB 的网页，直接塞回会撑爆上下文，需摘要或截断）、<strong>终止判定</strong>（模型自称"完成"未必真完成，高价值场景要外部校验）。</p>

            <tr><td>易于加护栏（步数上限、循环检测）</td><td>依赖模型的格式遵循能力，需要容错</td></tr>

      <div class="callout warn">
        <span class="label">ReAct 的典型失败模式</span>
        <span class="cjk">① <strong>工具复读机</strong>——用同样的参数反复调同一个工具，陷入死循环（对策：循环检测 + 步数上限）。② <strong>观察截断丢信息</strong>——为省 token 把关键结果截掉，导致后续推理无据可依。③ <strong>假完成</strong>——模型在信息不足时提前宣布 Final Answer（对策：让它先自检"证据是否支持结论"）。④ <strong>推理漂移</strong>——Thought 越写越长却不落到 Action，空耗 token。</span>
      </div>
      <p class="cjk"><strong>何时选用。</strong>把 ReAct 当作默认起点：当你不确定用什么模式时，先用 ReAct 跑通，再根据观察到的问题（步数太多→加 Planning；质量不够→加 Reflection；单 Agent 上下文爆炸→拆 Multi-Agent）逐步升级。这是最务实的演进路线。</p>

      <h3>Tool Use：所有 Agent 的地基</h3>
      <p class="cjk"><strong>定义。</strong>Tool Use（工具调用，也叫 Function Calling）指让模型输出一段结构化的调用意图（工具名 + 参数），由外部运行时真正执行，再把结果作为 Observation 回灌。它是把语言模型的"想法"落地为"行动"的唯一通道——没有工具，Agent 就只能空谈；有了工具，它才能读文件、查数据库、调 API、控制浏览器。<mark class="key">工具设计的质量，直接决定 Agent 能力的上限</mark>：一个描述含糊、参数设计糟糕的工具，会让再强的模型也频繁调错。</p>
      <p class="cjk"><strong>适用场景。</strong>几乎所有真实 Agent。区别只在工具的粒度与数量：客服助手可能只需三五个工具，编程 Agent 可能需要文件读写、执行、检索十余个。经验法则是<strong>宁可少而精，不要多而杂</strong>——工具越多，模型选错的概率越高，工具定义占用的上下文也越大（这正是第 4 章"按需加载工具"的动因）。</p>
      <div class="code-label">Python · 工具定义与调用（function calling 风格）</div>
      <pre><code><span class="cm"># 好工具 = 清晰的名字 + 精确的描述 + 严格的参数 schema + 可预期的返回</span>
tools = [{
  <span class="st">"name"</span>: <span class="st">"search_orders"</span>,
  <span class="st">"description"</span>: <span class="st">"按用户ID查询近90天订单；仅返回已支付订单"</span>,  <span class="cm"># 描述写清边界</span>
  <span class="st">"parameters"</span>: {
    <span class="st">"user_id"</span>: {<span class="st">"type"</span>: <span class="st">"string"</span>, <span class="st">"required"</span>: <span class="kw">True</span>},
    <span class="st">"limit"</span>:   {<span class="st">"type"</span>: <span class="st">"integer"</span>, <span class="st">"default"</span>: 10, <span class="st">"max"</span>: 50}
  }
}]

<span class="kw">def</span> <span class="fn">dispatch</span>(call):
    <span class="kw">try</span>:
        result = REGISTRY[call.name](**validate(call.args))   <span class="cm"># 先校验参数再执行</span>
        <span class="kw">return</span> {<span class="st">"ok"</span>: <span class="kw">True</span>, <span class="st">"data"</span>: result}
    <span class="kw">except</span> ToolError <span class="kw">as</span> e:
        <span class="kw">return</span> {<span class="st">"ok"</span>: <span class="kw">False</span>, <span class="st">"error"</span>: <span class="fn">str</span>(e)}   <span class="cm"># 把错误当作可观察信号回灌，让模型自我修正</span></code></pre>
      <p class="cjk">上面这段的精髓是最后一行：<mark class="key2">工具报错不要直接抛出中断循环，而应把错误信息作为 Observation 喂回模型</mark>，让它自己"看到"参数错了、换个方式重试。这是把脆弱的调用变成鲁棒 Agent 的关键一招。</p>

      <h3>Multi-Agent：别为了用而用</h3>
      <p class="cjk">多智能体很吸引人，但<mark class="key2">只有当任务真正可并行、或不同子任务需要不同的系统提示词和工具集时才该用；不要因为某个框架让它变简单就用它——协调开销是真实存在的</mark><sup><a href="#cite-4">[4]</a></sup>。面试时如果你能主动点出"多 Agent 不是银弹"，会比盲目推崇更让人信服。</p>
      <p class="cjk"><strong>两种主流拓扑。</strong>其一是 <strong>Orchestrator-Worker（编排者—工作者）</strong>：一个主 Agent 负责拆解任务、分派给若干专职子 Agent、汇总结果——这是最常见、最可控的结构，深度研究、代码库大规模改造多用它。其二是 <strong>去中心化协作</strong>：多个对等 Agent 通过共享消息区互相通信、辩论、投票——更灵活但更难控，容易发散。面试里能说清"我倾向 Orchestrator-Worker，因为它的控制流和上下文边界更清晰"，是成熟度的体现。</p>
      <p class="cjk"><strong>为什么协调开销真实存在。</strong>子 Agent 之间不共享上下文，主 Agent 必须把背景"翻译"给每个子 Agent，子 Agent 的结论又要"翻译"回来——这中间存在信息损耗与 token 放大。此外还有一致性问题：两个子 Agent 可能基于不同假设给出互相矛盾的结论，主 Agent 要能识别并裁决。<strong>何时选用：</strong>任务能切成弱耦合的并行块（如"分别调研 5 家供应商"）、或每块需要迥异的专长/工具时才上；若子任务强耦合、需频繁互相依赖中间结果，单 Agent 反而更稳更省。</p>

      </div>
      <div class="callout warn">
        <span class="label">Multi-Agent 的失败模式</span>
        <span class="cjk">① <strong>过度拆分</strong>——把本可单 Agent 完成的任务硬拆成多 Agent，徒增开销。② <strong>上下文丢失</strong>——主 Agent 分派时没把关键约束传给子 Agent，子 Agent 各干各的。③ <strong>结论冲突无仲裁</strong>——多个子 Agent 结果打架却没人裁决。④ <strong>成本失控</strong>——并行意味着同时多路调用，费用可能数倍于单 Agent。</span>
      </div>

      <div class="callout tip">
        <span class="label">失败模式速记</span>
        <span class="cjk">Agent 三大经典翻车点：<strong>无限循环</strong>（反复调同一个工具）、<strong>上下文爆炸</strong>（历史塞满窗口）、<strong>错误累积</strong>（一步错步步错）。对应的护栏是：硬性步数上限、循环检测、上下文压缩。这组"问题—对策"在第 4、11、12 章还会反复出现。</span>

      <h3>Planning：从"边走边看"到"先谋后动"</h3>
      <p class="cjk">ReAct 是"走一步看一步"，而 Planning 模式强调<strong>先制定完整计划再执行</strong>。典型代表是 Plan-and-Execute：一个 Planner 先把大目标分解成有序子任务清单，再由 Executor 逐个执行。它的优势在长程任务中很明显——ReAct 每一步都要把完整历史喂给模型做决策，步数一多就会上下文爆炸且容易"迷失方向"；而先规划能让 Agent 始终锚定全局目标。</p>
      <p class="cjk"><strong>定义与直觉。</strong>Planning 把"决定做什么"与"具体去做"两个关注点分离：Planner 只负责在高层面把目标拆成结构化的步骤列表（可以是线性清单，也可以是带依赖的 DAG），Executor 则专注执行单个步骤（内部往往就是一个小的 ReAct 循环）。这种分离带来两个好处：一是全局视野始终由计划承载，单步执行的上下文可以只装当前子任务，大幅缓解上下文膨胀；二是计划本身可被审阅、被人工干预、被缓存复用。</p>
      <div class="code-label">Python · Plan-and-Execute 骨架（含重规划）</div>
      <pre><code><span class="kw">def</span> <span class="fn">plan_and_execute</span>(goal, llm, executor):
    plan = llm.plan(goal)                    <span class="cm"># 1. 先生成有序子任务清单</span>
    results = []
    <span class="kw">while</span> plan:
        step = plan.pop(0)                   <span class="cm"># 2. 取出下一个子任务</span>
        obs = executor.run(step, results)    <span class="cm"># 3. 执行（内部可以是 ReAct）</span>
        results.append(obs)
        <span class="kw">if</span> llm.should_replan(goal, plan, obs):   <span class="cm"># 4. 关键：检查计划是否仍成立</span>
            plan = llm.replan(goal, results) <span class="cm"># 结果推翻假设时，重规划剩余步骤</span>
    <span class="kw">return</span> llm.synthesize(goal, results)      <span class="cm"># 5. 汇总子结果，产出最终答复</span></code></pre>
      <p class="cjk">但 Planning 有个致命弱点：<mark class="key2">计划会过时</mark>。如果第 2 步的执行结果推翻了原计划的假设，还死守原计划就会全盘皆错。因此成熟的实现都带有<strong>重规划（re-planning）</strong>机制：每执行完一个子任务就检查"计划还成立吗"，必要时让 Planner 重新规划剩余步骤（对应上面代码第 4 步）。面试时能点出"Planning 必须配重规划"，是区分读过文档和真正实现过的关键。</p>
      <div class="table-wrap">
        <table>
          <thead><tr><th>优点</th><th>缺点 / 代价</th></tr></thead>
          <tbody>
            <tr><td>锚定全局目标，长程不迷失</td><td>规划本身消耗一次昂贵调用，短任务不划算</td></tr>
            <tr><td>单步上下文更聚焦，缓解膨胀</td><td>计划易过时，必须配重规划否则遇意外即崩</td></tr>
            <tr><td>计划可审阅/人工干预/缓存复用</td><td>Planner 出错会污染整条执行链</td></tr>
          </tbody>
        </table>
      </div>
      <div class="callout warn">
        <span class="label">Planning 的失败模式</span>
        <span class="cjk">① <strong>无重规划</strong>——死守初始计划，第一步意外就满盘皆输。② <strong>计划过度细化</strong>——把不可预知的后期步骤也硬编排，执行时全对不上。③ <strong>Planner 幻觉步骤</strong>——规划出根本无法执行的动作。④ <strong>短任务过度规划</strong>——三步能搞定的事先花一次调用做计划，纯浪费。<strong>何时选用：</strong>步骤多（通常 5 步以上）、目标明确、子任务间有清晰依赖的长程任务。</span>
      </div>

      <h3>Reflection：让 Agent 自我批判</h3>
      <p class="cjk">Reflection（反思）模式让 Agent 对自己的输出进行自我批判并迭代改进，典型如 Reflexion、Self-Refine。流程是：生成初稿 → 自我评审（指出问题）→ 根据评审修订 → 再评审……直到满足质量标准或达到轮次上限。它在代码生成、写作、数学推理等"有明确好坏标准"的任务上效果显著。</p>
      <p class="cjk"><strong>定义与直觉。</strong>Reflection 的核心假设是：<mark class="key">模型"批判一段文本"往往比"一次性写对"更容易</mark>——就像人写完初稿再回头改，更容易发现漏洞。它让同一个模型切换到"审稿人"视角，用一套明确的检查清单（是否覆盖需求？有没有逻辑漏洞？代码能否通过测试？）审视自己的产出，再据此修订。若能引入外部信号（如让代码真正跑一遍、拿到报错），反思质量会显著提升，因为这时批判有了客观依据而非凭空自省。</p>
      <div class="code-label">Python · Self-Refine 式反思循环</div>
      <pre><code><span class="kw">def</span> <span class="fn">reflect</span>(task, llm, max_rounds=3):
    draft = llm.generate(task)                       <span class="cm"># 初稿</span>
    <span class="kw">for</span> r <span class="kw">in</span> range(max_rounds):
        critique = llm.critique(task, draft)         <span class="cm"># 自我评审：指出具体问题</span>
        <span class="kw">if</span> critique.is_good_enough:                  <span class="cm"># 满足标准就提前退出</span>
            <span class="kw">break</span>
        draft = llm.revise(task, draft, critique)    <span class="cm"># 依据评审修订</span>
    <span class="kw">return</span> draft</code></pre>
      <div class="callout tip">
        <span class="label">工程权衡</span>
        <span class="cjk">Reflection 用"更多的 token 和延迟"换"更高的质量"。它不是免费午餐——每多一轮反思就多一次完整的模型调用。生产上要设定<strong>反思轮次上限</strong>（通常 1-3 轮边际收益就急剧下降），并且只在高价值任务上开启。盲目开无限反思，成本会失控。</span>
      </div>
      <div class="callout warn">
        <span class="label">Reflection 的失败模式</span>
        <span class="cjk">① <strong>自我表扬</strong>——模型审自己往往手下留情，评审流于形式（对策：给出严格 rubric，或改用 Evaluator-Optimizer）。② <strong>越改越差</strong>——修订引入新问题，几轮后不收敛（对策：保留最优版本，可回退）。③ <strong>无外部信号空转</strong>——没有测试/工具校验，纯靠自省容易原地打转。<strong>何时选用：</strong>有明确好坏标准、且质量比成本更重要的生成任务（代码、正式文案、数学推导）。</span>
      </div>

      <h3>Evaluator-Optimizer：把"评委"独立出来</h3>
      <p class="cjk">Reflection 是"自己评自己"，而 Evaluator-Optimizer 把评估者独立成一个专门的 Agent（甚至用不同的模型）。生成者产出方案，评估者按明确的评分标准打分并给出改进建议，生成者据此优化，循环往复。这种"生成-评估"分离的好处是：评估者可以用更严格的标准或专门微调过的模型，避免"自己给自己打高分"的偏袒。它与第 11 章的 LLM-as-Judge 评估思想一脉相承。</p>
      <p class="cjk"><strong>定义与直觉。</strong>它可以看作 Reflection 的"去偏袒版本"：把评审者从生成者身上剥离，形成生成器（Generator）与评估器（Evaluator）两个独立角色。评估器持有客观、稳定的评分标准（rubric），甚至可以是规则校验、单元测试、或另一套模型；它输出的不是模糊的"改改吧"，而是结构化的分数 + 具体扣分点。生成器把这些反馈当作优化方向迭代。当评估信号足够客观时（如"是否通过全部测试用例"），这个循环能逼近很高的质量上限。</p>
      <div class="code-label">Python · Evaluator-Optimizer 循环</div>
      <pre><code><span class="kw">def</span> <span class="fn">evaluator_optimizer</span>(task, generator, evaluator, target=0.9, max_iter=4):
    cand = generator.produce(task)
    <span class="kw">for</span> i <span class="kw">in</span> range(max_iter):
        score, feedback = evaluator.score(task, cand)   <span class="cm"># 独立评委：分数 + 结构化建议</span>
        <span class="kw">if</span> score &gt;= target:                             <span class="cm"># 达标即停</span>
            <span class="kw">return</span> cand
        cand = generator.improve(task, cand, feedback)  <span class="cm"># 定向优化，而非盲目重写</span>
    <span class="kw">return</span> cand    <span class="cm"># 达到迭代上限，返回当前最优</span></code></pre>
      <div class="table-wrap">
        <table>
          <thead><tr><th>对比</th><th>Reflection</th><th>Evaluator-Optimizer</th></tr></thead>
          <tbody>
            <tr><td>评审者</td><td>生成者自己</td><td>独立角色/模型/规则</td></tr>
            <tr><td>偏袒风险</td><td>高（易自我表扬）</td><td>低（评委独立）</td></tr>
            <tr><td>成本</td><td>较低（单模型）</td><td>较高（双模型调用）</td></tr>
            <tr><td>最适合</td><td>快速迭代、成本敏感</td><td>有客观 rubric、质量优先</td></tr>
          </tbody>
        </table>
      </div>
      <div class="callout warn">
        <span class="label">Evaluator-Optimizer 的失败模式</span>
        <span class="cjk">① <strong>评委标准漂移</strong>——rubric 含糊导致评分不稳定，优化方向乱跳。② <strong>目标分不可达</strong>——target 设太高导致每次都跑满迭代上限，成本翻倍。③ <strong>反馈不可执行</strong>——评委只说"不够好"却不给具体扣分点，生成器无从下手。<strong>何时选用：</strong>存在明确、可客观计算或可稳定判定的评分标准，且愿意为质量支付双倍调用成本的迭代任务。</span>
      </div>

      <h3>模式不是互斥的：真实系统是组合拳</h3>
      <p class="cjk">面试新手容易把六大模式当成"六选一"，但<mark class="key">真实的生产 Agent 往往是多种模式的组合</mark>。例如一个深度研究 Agent：用 <strong>Planning</strong> 拆解研究大纲，每个子主题内用 <strong>ReAct</strong> 循环搜索与阅读，用 <strong>Tool Use</strong> 调用搜索/浏览工具，最后用 <strong>Reflection</strong> 审查报告的完整性与一致性。能画出这样一张"模式组合图"，比单纯罗列六个名词更能打动面试官。</p>
      <p class="cjk">再举两个常见组合，帮你在设计题里信手拈来：<strong>编程 Agent</strong>通常是"ReAct（读文件→改代码→跑测试→看报错）+ Evaluator-Optimizer（用测试结果作为客观评委驱动迭代）+ Tool Use（文件、执行、检索）"；<strong>大规模内容生产线</strong>则常见"Planning（拆章节）+ 各章 Multi-Agent 并行起草 + Evaluator-Optimizer 统一 rubric 把关 + 主 Agent 汇总"。<mark class="key2">组合的原则是分层：先用 ReAct/Planning 定控制流骨架，再用 Tool Use 打地基，最后按质量与并行需求叠加 Reflection/Evaluator-Optimizer/Multi-Agent 增强层</mark>。</p>

        <span class="cjk">一句话记住这套决策：<strong>能不用 Agent 就不用，要用先搭骨架（路径不定 ReAct、长程清晰 Planning），骨架之上必打 Tool Use 地基，质量吃紧加反思或独立评委，能并行且需分工再上多 Agent</strong>。切记每叠加一层都在增加成本与不可控性，克制是资深工程师的默认姿态。</span>

      <div class="callout warn">
        <span class="label">常见误区</span>
        <span class="cjk">① <strong>"模式越多越好"</strong>——每种模式都有成本，用不对反而拖累。② <strong>"Planning 一定优于 ReAct"</strong>——短任务上 Planning 的规划开销反而是浪费。③ <strong>"上了 Multi-Agent 就更智能"</strong>——多数场景单 Agent + 好工具更稳更省。④ <strong>忽略重规划</strong>——Planning 不配重规划，遇到意外就崩。</span>
      </div>
