      <h3>安装与第一个 Agent</h3>
      <p class="cjk">smolagents 的招牌是 <code>CodeAgent</code>——它让模型<strong>直接生成并执行 Python 代码</strong>来完成任务，而不是拼 JSON 参数。装好后，一个能联网搜索的 Agent 只需几行：</p>

      <div class="code-label">Python · 第一个 CodeAgent（smolagents 1.26）</div>
      <pre><code><span class="cm"># pip install "smolagents[toolkit]"　　# toolkit 这个 extra 才自带 WebSearchTool</span>
<span class="kw">from</span> smolagents <span class="kw">import</span> CodeAgent, WebSearchTool, InferenceClientModel

<span class="cm"># 1) 选一个模型作为推理引擎（不传 model_id 会用一个默认模型）</span>
model = InferenceClientModel(model_id=<span class="st">"Qwen/Qwen2.5-Coder-32B-Instruct"</span>)

<span class="cm"># 2) 给 Agent 配上工具（这里是网页搜索）</span>
agent = CodeAgent(tools=[WebSearchTool()], model=model)

<span class="cm"># 3) 交给它一个目标，它会自己规划、写代码、调工具、迭代</span>
agent.run(<span class="st">"2026 年 8 月，A 股和港股哪个指数今年以来涨幅更高？给出数字。"</span>)</code></pre>

      <p class="cjk">运行后你会看到 Agent 一步步"思考 → 写代码 → 执行 → 观察结果 → 再思考"，直到给出答案——这就是第 3 章 ReAct 循环的活演示。<mark class="key">看清这个循环，你就抓住了所有 Agent 框架的共同内核。</mark></p>

      <p class="cjk">这几行里，每一行对应 Agent 的一个器官：</p>
      <ul class="hub-list">
        <li><strong>第 1 行 <code>from smolagents import ...</code></strong>：一次性引入三个角色——<code>CodeAgent</code>（Agent 循环本体）、<code>WebSearchTool</code>（一个现成工具）、<code>InferenceClientModel</code>（模型客户端）。注意这三者是<em>正交</em>的：Agent 负责循环，工具负责能力，模型负责推理，三者解耦是所有框架的通用设计。</li>
        <li><strong><code>model = InferenceClientModel(model_id=...)</code></strong>：这里选定"大脑"。Agent 本身不含智能，全部推理都委托给这个模型；<code>model_id</code> 换成别的模型就换了大脑，而 Agent 逻辑一行不用改——这就是"模型可替换"。CodeAct 对模型的代码能力有要求，所以示例选了一个 Coder 系模型。</li>
        <li><strong><code>agent = CodeAgent(tools=[...], model=model)</code></strong>：把"大脑 + 工具箱"组装成一个 Agent。<code>tools</code> 是一个列表，意味着你可以塞进任意多个工具；Agent 会把这些工具的签名与说明自动整理进系统提示，让模型知道"我手上有什么可用"。</li>
        <li><strong><code>agent.run("...")</code></strong>：一句话启动整个循环。你只给"目标"，不给"步骤"——如何拆解、先搜什么、要不要再搜一次，全由 Agent 在运行时自主决定。这正是它与"写死流程的 Workflow"的分界线（见第 1 章）。</li>
      </ul>
      <div class="callout tip">
        <span class="label">读代码的正确姿势</span>
        <span class="cjk">初学者常盯着 API 名字记，其实更该记<strong>职责划分</strong>：模型=推理、工具=能力、Agent=循环、run=目标输入。任何 Agent 框架换个名字都逃不出这四块。把这张"骨架图"刻进脑子，你读任何框架的 Hello World 都能三秒看懂它在干嘛。</span>
      </div>

      <h3>手写一遍循环：把框架的"魔法"祛魅</h3>
      <p class="cjk">要真正相信"smolagents 只是个薄壳"，最好的办法是把它内部逻辑用最朴素的伪代码手写一遍。下面这段不依赖任何框架，却和 <code>agent.run()</code> 干的是同一件事——它能帮你在面试白板上证明"我懂框架内部"，而不是只会调 API：</p>
      <div class="code-label">Python · 手写一个极简的 CodeAct 循环（伪代码）</div>
      <pre><code><span class="kw">def</span> <span class="fn">code_agent_loop</span>(goal, tools, model, max_steps=<span class="st">8</span>):
    <span class="cm"># memory 就是不断增长的上下文：系统提示 + 工具说明 + 历史</span>
    memory = [system_prompt(tools), user(goal)]
    <span class="kw">for</span> step <span class="kw">in</span> range(max_steps):
        code = model.generate(memory)          <span class="cm"># 1) 让模型写一段 Python</span>
        <span class="kw">if</span> calls_final_answer(code):           <span class="cm"># 2) 看它是否宣布收工</span>
            <span class="kw">return</span> extract_answer(code)
        obs = sandbox_exec(code, tools)        <span class="cm"># 3) 在沙箱里真跑，拿到 stdout/报错</span>
        memory.append(assistant(code))         <span class="cm"># 4) 把代码与观察一起写回上下文</span>
        memory.append(observation(obs))
    <span class="kw">return</span> fallback()                          <span class="cm"># 5) 步数耗尽的兜底</span></code></pre>
      <p class="cjk">对照着看你会恍然大悟：smolagents 的 <code>CodeAgent</code> 无非把这五步做得更健壮（提示词模板、错误捕获、导入白名单、结构化日志），<em>骨架完全一样</em>。当面试官问"你能不用框架实现一个 Agent 吗"，你把这段默写出来，再补一句"框架帮我做的是第 3 步的沙箱和第 1 步的提示词工程"，可信度立刻拉满。<mark class="key">框架不是魔法，是把这段循环产品化。</mark></p>

      <h3>自定义工具：一个装饰器的事</h3>
      <p class="cjk">工具就是普通 Python 函数，加个 <code>@tool</code> 装饰器、写清类型标注和 docstring 即可——<strong>docstring 会被喂给模型当作工具说明，所以必须写清楚</strong>。这是"工具设计"这一考点的最佳实操。</p>

      <div class="code-label">Python · 自定义工具</div>
      <pre><code><span class="kw">from</span> smolagents <span class="kw">import</span> tool, CodeAgent, InferenceClientModel

<span class="kw">@tool</span>
<span class="kw">def</span> <span class="fn">get_exchange_rate</span>(base: str, target: str) -> float:
    <span class="st">"""查询实时汇率。

    Args:
        base: 源货币代码，如 'USD'
        target: 目标货币代码，如 'CNY'
    """</span>
    <span class="cm"># 真实项目里这里调用汇率 API，这里用示意值</span>
    rates = {(<span class="st">"USD"</span>, <span class="st">"CNY"</span>): 7.15}
    <span class="kw">return</span> rates.get((base, target), 0.0)

agent = CodeAgent(tools=[get_exchange_rate], model=InferenceClientModel())
agent.run(<span class="st">"我有 200 美元，能换多少人民币？"</span>)</code></pre>

      <p class="cjk">这段工具定义里，有三个决定"模型能不能正确用你的工具"的细节：</p>
      <ul class="hub-list">
        <li><strong><code>@tool</code> 装饰器</strong>：它做的事是把一个普通函数"登记"成 Agent 可调用的工具——自动读取函数名、参数类型标注、返回类型和 docstring，拼装成模型能理解的工具描述。没有它，这就只是个普通函数，Agent 根本"看不见"。</li>
        <li><strong>类型标注 <code>base: str, target: str -> float</code></strong>：类型不是给人看的注释，而是给模型的<em>契约</em>。模型据此知道该传字符串、期待拿到浮点数；CodeAct 生成的代码也会照此调用。省略类型标注，模型就容易传错类型导致运行时报错。</li>
        <li><strong>docstring</strong>：这是<mark class="key">整段代码里最该字斟句酌的部分</mark>——它会被原样喂进模型的上下文，充当"这个工具是干什么的、每个参数什么含义"的说明书。写得含糊（比如只写"查汇率"），模型就可能乱传参数或在不该用时误用它；写清楚（说明单位、举例参数值），调用准确率立刻提升。这正是第 6 章"工具设计"考点的实操落点。</li>
      </ul>
      <p class="cjk">运行时会发生什么？模型读到目标"200 美元换人民币"，发现手上有 <code>get_exchange_rate</code> 工具，于是<strong>自己写出一段 Python</strong>：调用 <code>get_exchange_rate("USD", "CNY")</code> 拿到汇率、乘以 200、再 <code>print</code> 或传给 <code>final_answer</code>。注意这里的关键——<em>乘法这一步不需要再问模型</em>，它就在 Agent 写的代码里顺手算了。这就是 CodeAct 相比 JSON 工具调用的直观优势：<strong>取数与算数在同一段代码里一气呵成，不必把中间结果绕回上下文再让模型算一遍。</strong></p>

      <div class="callout tip">
        <span class="label">CodeAct 的威力与风险</span>
        <span class="cjk">让 Agent 写代码执行，能自然完成循环、条件、组合多个工具调用，比 JSON 调用更灵活高效。<strong>但代价是安全</strong>：模型生成的代码必须在<mark class="key2">沙箱（如 E2B、Docker）</mark>里执行，绝不能直接跑在生产主机上。面试被问"CodeAct 有什么风险"，答"任意代码执行 → 必须沙箱隔离"就到位了。</span>
      </div>

      <h3>CodeAct vs JSON Tool Calling：一场范式之争</h3>
      <p class="cjk">smolagents 的招牌 CodeAct 值得单独讲透，因为它是近年 Agent 设计的一个重要洞见。传统方式下，模型每次只能输出一个 JSON 工具调用；而 CodeAct 让模型直接写一段 Python，可以在一步内完成"循环调用、条件判断、组合多个工具、就地处理数据"。</p>
      <div class="table-wrap">
        <table>
          <thead><tr><th>维度</th><th>JSON Tool Calling</th><th>CodeAct（代码即行动）</th></tr></thead>
          <tbody>
            <tr><td>表达力</td><td>单次单工具，组合逻辑靠多轮</td><td>循环/条件/组合一步搞定</td></tr>
            <tr><td>步骤数</td><td>多（每个动作一轮）</td><td>少（研究显示约减少 30%）</td></tr>
            <tr><td>数据处理</td><td>需把中间结果塞回上下文</td><td>可在代码里就地处理，不占上下文</td></tr>
            <tr><td>安全性</td><td>动作空间受限，相对安全</td><td>任意代码执行，必须沙箱</td></tr>
            <tr><td>模型要求</td><td>会遵循 schema 即可</td><td>需要较强代码能力</td></tr>
          </tbody>
        </table>
      </div>
      <p class="cjk">一个直观例子："把这 10 个城市的天气都查出来，找出最热的三个。" JSON 方式要 10+ 轮工具调用再让模型比较；CodeAct 只需一段 <code>for</code> 循环 + <code>sorted()</code>，一步完成。这就是"约减少 30% 步骤"的来源。</p>
      <p class="cjk">但要答出高分，你必须补上另一半——<strong>CodeAct 不是万能药，JSON 工具调用在很多场景反而更合适</strong>。当动作本身就是"一次原子操作"（比如"下单""发一条消息""改一个字段"），根本没有循环与组合可言，此时 CodeAct 那点表达力优势用不上，反而白白背上"任意代码执行"的安全包袱。此外，JSON 调用的<strong>动作空间是受限、可枚举的</strong>，天然更好做权限控制与审计——你能明确知道模型"只能调这几个函数"；而 CodeAct 理论上能写任何 Python，审计面大得多。<mark class="key2">选型心法：以"数据处理、批量、组合逻辑"为主的任务偏 CodeAct；以"少数几个高风险原子动作"为主的任务偏 JSON 工具调用。</mark></p>
      <p class="cjk">值得一提的是，smolagents 并不强迫你只用 CodeAct——它同时提供 <code>ToolCallingAgent</code>，走的正是传统 JSON 工具调用范式。也就是说，<strong>同一个框架里你可以按任务性质在两种范式间切换</strong>：探索式、需要就地算数据的用 <code>CodeAgent</code>，动作固定且高风险的用 <code>ToolCallingAgent</code>。理解"这不是二选一的信仰之争，而是按任务选工具"，是这道题从"背结论"升级到"会决策"的关键。</p>

      <h3>看清 smolagents 的执行循环</h3>
      <p class="cjk">smolagents 之所以适合学习，是因为它的循环几乎是"裸露"的。它内部做的事，本质就是第 1 章那个"带工具的 while 循环"：把系统提示 + 任务 + 历史拼成上下文 → 调模型生成一段代码 → 在沙箱执行 → 把执行结果（stdout / 报错）作为 Observation 拼回上下文 → 再调模型……直到模型调用 <code>final_answer()</code>。理解这一点，你就能在面试中回答"框架内部到底发生了什么"，而不是把它当黑盒。</p>

      <figure class="diagram"><pre class="mermaid">
flowchart TD
    A[系统提示 + 工具说明 + 任务] --> B[拼装上下文 memory]
    B --> C[调用模型生成一段 Python 代码]
    C --> D{代码里调用了<br/>final_answer 吗?}
    D -->|否| E[在沙箱中执行代码]
    E --> F[捕获 stdout / 返回值 / 报错<br/>作为 Observation]
    F --> G{达到 max_steps?}
    G -->|否| B

</pre><figcaption>图 8-1　smolagents 的执行循环：一个"生成代码—沙箱执行—观察回填"的受控 while 循环</figcaption></figure>

      <p class="cjk">把这张图对照第 1 章的伪代码看，你会发现它们是同构的，只是 smolagents 把"动作"具体化成了"写并执行一段 Python"。有几个工程细节值得特别留意：</p>
      <ul class="hub-list">
        <li><strong>memory（记忆/历史）不是无限的</strong>：每一轮的代码与 Observation 都会追加进上下文，步数一多就会撑爆窗口。这就是第 4 章"上下文管理"要解决的问题——生产里往往要对历史做裁剪或摘要。</li>
        <li><strong>Observation 是"执行结果"而非"模型幻觉"</strong>：代码在沙箱真跑，<code>print</code> 出来的、抛出的异常，都是<em>真实</em>反馈。这正是 Agent 能"自我修正"的物理基础——它能看到自己上一步代码报了什么错，然后改。</li>
        <li><strong>final_answer 是唯一的正规出口</strong>：模型必须显式调用它来结束循环，否则会一直转到 <code>max_steps</code>。所以"终止"是被工具化的，而不是靠猜模型"说完了没有"。</li>
        <li><strong>max_steps 是安全阀</strong>：它是防止无限循环、控制成本的硬边界，也是第 1 章那三问（步数、终止、上下文膨胀）在 smolagents 里的直接体现。</li>
      </ul>
      <p class="cjk">这套循环里还藏着 Agent"自我修正"的秘密，值得单独点破：当第 <em>k</em> 步生成的代码报错，报错信息会作为 Observation 原样回填进上下文；第 <em>k+1</em> 步模型就能<strong>看着自己刚才的错误堆栈</strong>去改代码——这就是所谓"反思/自愈"能力在最朴素层面的实现，它不需要任何花哨机制，只需要"把执行结果如实喂回去"。理解了这一点，你就明白为什么<mark class="key2">"Observation 的质量"直接决定"Agent 能不能纠错"</mark>：如果工具吞掉异常、只回一句"失败了"，模型就无从改起；如果如实回传具体报错，它往往能自己修好。这也是"工具要返回干净且有信息量的结果"这条准则的深层原因。</p>

      <h3>多步任务：观察一次真实的循环轨迹</h3>
      <p class="cjk">单看代码不够直观，最好把一个多步任务的轨迹想象出来。以"把这 10 个城市的天气都查出来，找出最热的三个"为例，一次典型的 CodeAgent 运行大致会经历这样几步：</p>
      <div class="table-wrap">
        <table>
          <thead><tr><th>步骤</th><th>模型生成的代码（示意）</th><th>Observation（回填的观察）</th></tr></thead>
          <tbody>
            <tr><td>Step 1</td><td><code>for c in cities: print(get_weather(c))</code></td><td>10 个城市的温度被逐个打印出来</td></tr>
            <tr><td>Step 2</td><td><code>top3 = sorted(data, key=..., reverse=True)[:3]</code></td><td>得到排序后的前三名列表</td></tr>
            <tr><td>Step 3</td><td><code>final_answer(top3)</code></td><td>循环结束，返回最终答案</td></tr>
          </tbody>
        </table>
      </div>
      <p class="cjk">对比一下 JSON 工具调用会怎么做：它每次只能发一个 <code>get_weather</code> 调用，10 个城市就是 10 轮往返，再加至少 1 轮让模型比较排序——十几轮起步。而 CodeAct 用一个 <code>for</code> 循环 + <code>sorted()</code> 两三步搞定。<mark class="key2">这就是"约减少 30% 步骤"在真实任务里的样子：把可以用代码表达的控制流，从"多轮模型往返"压缩进"一次代码执行"。</mark>步骤少不仅更快更省钱，还更稳——往返越少，中途跑偏的机会越少。</p>
      <p class="cjk">把这个多工具协作的场景写成可运行代码，能更清楚地看到"组合多个工具"在 smolagents 里有多自然——你只管把工具丢进列表，剩下的"先查天气、再排序、最后作答"这套编排全由 Agent 自己写代码完成：</p>
      <div class="code-label">Python · 多工具协作的多步任务</div>
      <pre><code><span class="kw">from</span> smolagents <span class="kw">import</span> tool, CodeAgent, InferenceClientModel

<span class="kw">@tool</span>
<span class="kw">def</span> <span class="fn">get_weather</span>(city: str) -> float:
    <span class="st">"""返回城市当前气温（摄氏度）。

    Args:
        city: 城市名，如 '北京'
    """</span>
    <span class="kw">return</span> weather_api.query(city)  <span class="cm"># 真实实现调用天气 API</span>

agent = CodeAgent(tools=[get_weather], model=InferenceClientModel(),
                  max_steps=<span class="st">6</span>)  <span class="cm"># 别忘了 max_steps 安全阀</span>

agent.run(<span class="st">"查这 10 个城市的气温，返回最热的三个及其温度。"</span>)</code></pre>
      <p class="cjk">注意这里我们只提供了一个 <code>get_weather</code> 工具，但没有写任何"循环 10 次""排序取前三"的编排代码——这些<strong>控制流是 Agent 在运行时自己写出来的</strong>。这正是 Agent 与传统程序的分野：你描述"要什么"（目标），它决定"怎么做"（步骤）。同时留意 <code>max_steps=6</code>，它是防止 Agent 在数据异常时无限重试的安全阀，任何多步任务都不该省。</p>

      <div class="callout tip">
        <span class="label">工具设计的黄金准则</span>
        <span class="cjk">跑通多步任务后，你会切身体会到：<strong>Agent 的能力上限，往往不由模型决定，而由工具的设计质量决定</strong>。几条可直接照做的准则：① <strong>工具要"粗粒度"</strong>——给一个 <code>search_and_summarize</code> 通常比给 <code>open_url</code>+<code>read</code>+<code>summarize</code> 三个碎工具更好用，能减少 Agent 的编排负担；② <strong>返回值要"信息密集且干净"</strong>——别把一大坨原始 HTML 丢回去，先在工具内部提炼，省上下文也少犯错；③ <strong>docstring 要像写给新同事的说明</strong>——讲清用途、每个参数、返回什么、什么时候<em>不</em>该用它。这套准则是第 6 章的核心考点，smolagents 只是让你第一次亲手实践它。</span>
      </div>

      <h3>沙箱方案怎么选</h3>
      <p class="cjk">CodeAct 的安全关键在沙箱。这里有一个<mark class="key">很多中文教程都说错的关键事实</mark>：smolagents 内置的 <code>LocalPythonExecutor</code>（默认执行器）<strong>不是安全边界</strong>——官方 README 原话是 "not a security boundary，must not be used to run untrusted code"。它只做了尽力而为的限制（限制导入等），但能被绕过。所以真实的选型是：</p>
      <div class="table-wrap">
        <table>
          <thead><tr><th>方案</th><th>是否安全边界</th><th>部署成本</th><th>适用场景</th></tr></thead>
          <tbody>
            <tr><td>LocalPythonExecutor（默认）</td><td><span class="tag amber">否，仅尽力限制</span></td><td>零，开箱即用</td><td>本地学习、原型、输入<strong>完全可信</strong></td></tr>
            <tr><td>Docker 容器（<code>executor_type="docker"</code>）</td><td><span class="tag">是（进程/文件系统隔离）</span></td><td>需自建与运维</td><td>企业内网自托管、数据不出域</td></tr>
            <tr><td>E2B / Modal / Blaxel 云沙箱</td><td><span class="tag">是（托管隔离环境）</span></td><td>低（托管，按用量）</td><td>面向公网不可信输入、快速上线</td></tr>
          </tbody>
        </table>
      </div>
      <p class="cjk">选型抓两个变量：<strong>输入是否可信</strong>与<strong>数据能否出域</strong>。面向公网、输入不可信 → 云沙箱或严格配置的容器；数据敏感、不能出企业边界 → 自托管 Docker；只是自己学、跑可信任务 → 默认执行器够用，但心里要清楚它不防恶意代码。<mark class="key2">面试时能主动纠正"本地执行器不是安全沙箱"这一点，比背一堆方案名更能证明你读过源码/官方文档。</mark></p>

      <h3>常见报错与排查思路</h3>
      <p class="cjk">上手 smolagents 时，几类报错几乎人人都会撞上。把"现象 → 根因 → 处理"三段式记熟，既能救急，也是面试里展示"能落地、会调试"的好素材：</p>
      <div class="table-wrap">
        <table>
          <thead><tr><th>典型现象</th><th>根因</th><th>处理思路</th></tr></thead>
          <tbody>
            <tr><td>生成的代码频繁语法错 / 逻辑错</td><td>模型代码能力不足以驾驭 CodeAct</td><td>换代码能力更强的模型；把任务拆小；在提示里给示例</td></tr>
            <tr><td>Agent 转到 max_steps 也没结束</td><td>任务太发散，或模型没学会调用 final_answer</td><td>收窄任务边界；调高/调低 max_steps；在提示里强调"完成后必须调用 final_answer"</td></tr>
            <tr><td>工具被乱用 / 传错参数</td><td>docstring 或类型标注写得含糊</td><td>重写 docstring（讲清用途、单位、示例）；补全类型标注</td></tr>
            <tr><td>ImportError / 模块不可用</td><td>受限解释器默认不允许该导入</td><td>确认该库是否在白名单；或改用容器/云沙箱放开权限</td></tr>
            <tr><td>认证 / 额度类报错</td><td>模型或工具的密钥、配额问题</td><td>检查环境变量与密钥；确认额度与网络出口；工具内做好异常处理</td></tr>
          </tbody>
        </table>
      </div>
      <p class="cjk">通用的排查心法是<mark class="key">"先看轨迹，再定位环节"</mark>：smolagents 会把每一步生成的代码和 Observation 打印出来，读日志就能判断问题出在<strong>模型（代码写错）、工具（返回异常或说明不清）、还是循环控制（该停不停）</strong>。这三分法能让你在面试里把"怎么 debug 一个 Agent"回答得非常有条理——不要笼统说"看报错"，而要说"我先看它是哪一步、哪个环节出的问题"。</p>

      <h3>常见坑</h3>
      <div class="callout warn">
        <span class="label">smolagents 实操避坑</span>
        <span class="cjk">① <strong>docstring 写太随意</strong>——它就是给模型看的工具说明，含糊会导致乱调用。② <strong>模型代码能力不足</strong>——用弱模型跑 CodeAct，生成的代码常报语法错，建议配代码能力强的模型（如 Qwen-Coder、GPT-4 系列）。③ <strong>忘了设 max_steps</strong>——探索式任务可能停不下来，务必设步数上限。④ <strong>直接在主机执行</strong>——安全红线，必须沙箱。</span>
      </div>

      <h3>一个能直接跑的完整脚本</h3>
      <p class="cjk">前面的片段都是为讲解拆开的。这里给一份<strong>复制粘贴就能跑</strong>的完整版本——自定义工具 + 内置搜索 + 步数上限 + 基本异常处理，对照 smolagents 1.26 核对。前提：先 <code>pip install "smolagents[toolkit]"</code>，并设好 <code>HF_TOKEN</code> 环境变量（免费 HF 账号自带额度）。</p>
      <div class="code-label">Python · 可运行的最小完整 Agent（quickstart.py）</div>
      <pre><code><span class="kw">import</span> os
<span class="kw">from</span> smolagents <span class="kw">import</span> CodeAgent, WebSearchTool, InferenceClientModel, tool

<span class="kw">@tool</span>
<span class="kw">def</span> <span class="fn">convert_currency</span>(amount: float, base: str, target: str) -> float:
    <span class="st">"""按固定示例汇率换算金额（真实项目请替换成汇率 API）。

    Args:
        amount: 金额数值，如 200
        base: 源货币代码，如 'USD'
        target: 目标货币代码，如 'CNY'
    """</span>
    rates = {(<span class="st">"USD"</span>, <span class="st">"CNY"</span>): 7.15, (<span class="st">"CNY"</span>, <span class="st">"USD"</span>): 0.14}
    rate = rates.get((base, target))
    <span class="kw">if</span> rate <span class="kw">is</span> <span class="kw">None</span>:
        <span class="kw">raise</span> ValueError(<span class="st">f"暂不支持 {base}->{target}，请扩展 rates 表"</span>)
    <span class="kw">return</span> round(amount * rate, <span class="st">2</span>)

model = InferenceClientModel(model_id=<span class="st">"Qwen/Qwen2.5-Coder-32B-Instruct"</span>)
agent = CodeAgent(
    tools=[WebSearchTool(), convert_currency],
    model=model,
    max_steps=<span class="st">6</span>,          <span class="cm"># 安全阀：防止无限循环、控成本</span>
)

<span class="kw">if</span> __name__ == <span class="st">"__main__"</span>:
    <span class="kw">try</span>:
        result = agent.run(<span class="st">"帮我查一下 1 盎司黄金现在大约多少美元，再换算成人民币。"</span>)
        print(<span class="st">"\n最终答案："</span>, result)
    <span class="kw">except</span> Exception <span class="kw">as</span> e:
        <span class="cm"># 生产里这里应接入结构化日志 / 告警，而不是简单打印</span>
        print(<span class="st">"运行失败："</span>, repr(e))</code></pre>
      <p class="cjk">这份脚本刻意保留了两处"生产味"：<code>convert_currency</code> 在不支持的币种上<strong>主动抛异常</strong>（而不是返回 0 骗过模型），以及外层的 <code>try/except</code> 兜底。它们不影响 demo 跑通，却是把玩具代码和线上代码区分开的第一道分水岭。</p>

      <h3>从"跑通"到"上线"：与生产的差距</h3>
      <p class="cjk">上面这份脚本能跑，但离上线还差一整章工程。smolagents 替你省略、而生产里你必须亲手补上的，至少有这几块：</p>
      <ul class="hub-list">
        <li><strong>安全隔离</strong>：demo 用默认执行器，生产必须换成容器或云沙箱，并对可执行的库、网络出口、文件访问做白名单收紧。</li>
        <li><strong>可观测性</strong>：demo 靠打印日志看轨迹，生产要接入结构化的 tracing——记录每一步的输入输出、耗时、token 消耗，方便回溯与告警（见第 10 章相关话题）。</li>
        <li><strong>成本与延迟控制</strong>：每一步都在烧 token，生产要设预算上限、缓存可复用结果、必要时用更便宜的模型分级处理。</li>
        <li><strong>评估与回归</strong>：demo 跑对一次就高兴，生产要有评估集来量化"改了提示词/换了模型后，成功率是升是降"，防止改一处坏一片（见第 9 章）。</li>
        <li><strong>错误恢复与幂等</strong>：工具会超时、会失败，生产要有重试、降级、以及"重复执行不会造成副作用"的幂等设计。</li>
        <li><strong>护栏与人工确认</strong>：涉及花钱、改数据、发消息的高风险动作，要有 human-in-the-loop 或规则拦截，而不是全交给模型自主决定。</li>
      </ul>
      <div class="callout warn">
        <span class="label">别把 demo 当生产</span>
        <span class="cjk">smolagents 的"几行跑通"是它的教学优点，也是最大的误导来源。<strong>它让你以为 Agent 很简单，其实简单的只是 demo。</strong>真正的难度在上面那六块工程上。面试里如果你能主动指出"这段示例代码离生产还差安全、可观测、评估、成本控制……"，会立刻和只会敲教程的候选人拉开差距。</span>
      </div>

      <h3>面试追问链</h3>
      <ul class="hub-list">
        <li><strong>Q1：</strong>smolagents 和别的框架有什么不同？→ 抽象极薄、主打 CodeAct，适合看清循环本质。</li>
        <li><strong>Q2：</strong>CodeAct 和 JSON 工具调用怎么选、各有什么优劣？→ 表达力 vs 安全，用"10 城市天气"的例子讲清"约减少 30% 步骤"。</li>

        <li><strong>Q6：</strong>这段 demo 离上线还差什么？→ 安全、可观测、成本、评估、错误恢复、护栏六块工程。</li>
      </ul>

      <div class="callout tip">
        <span class="label">本章小结</span>
        <span class="cjk">smolagents 用极薄的抽象让你看清 Agent 循环的本质，其核心创新 CodeAct（让模型写代码而非拼 JSON）在表达力和步骤效率上有明显优势，代价是必须用沙箱隔离执行。学习路径建议：<strong>先用它跑通几个真实任务、观察每一步的思考-代码-观察循环，把"框架黑盒"变成"透明循环"</strong>，这是通往任何重框架的最佳起点。再往深一层记住三句话：<strong>CodeAct 与 JSON 工具调用不是信仰之争，而是按任务选工具；docstring 与类型标注是工具能被正确使用的前提；demo 跑通离生产还差安全、可观测、成本、评估、错误恢复、护栏六块工程。</strong>把这三句话讲清楚，你在"框架实操"这一考区就能稳稳拿分。</span>
