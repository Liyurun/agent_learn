      <h2 class="chap-title"><span class="kicker">06</span>MCP 模型上下文协议</h2>
      <p class="cjk"><mark class="key">MCP（Model Context Protocol，模型上下文协议）</mark>是 Anthropic 于 2024 年 11 月开源的开放标准，用来标准化应用向大模型提供上下文与工具的方式<sup><a href="#cite-7">[7]</a></sup>。一个经典比喻广为流传：<mark class="key2">MCP 就像 AI 应用的 USB-C 接口</mark>——正如 USB-C 统一了设备与外设的连接，MCP 统一了 AI 模型与外部工具、数据源的连接方式<sup><a href="#cite-7">[7]</a></sup>。2025 年它已被 OpenAI、Google DeepMind 等主流厂商采纳，成为事实标准。</p>
      <p class="cjk">为什么面试越来越爱问 MCP？因为它站在了一个关键的行业转折点上：当"给模型接工具"从各家闭门造车的私有实现，走向一个开放、可互操作的协议标准时，谁理解协议、谁就能理解整个 Agent 生态的连接方式。<mark class="key">面试官考 MCP，本质是在考你有没有从"会调 API"上升到"懂系统集成与协议设计"的视角。</mark>能把它讲成一个"解决集成组合爆炸的工程标准"，而不只是"又一个工具调用框架"，是拉开层次的关键。</p>

      <div class="callout tip">
        <span class="label">📎 本章对照的开源一手资料（建议边读边开）</span>
        <span class="cjk">MCP 是活的协议，规范在持续演进。本章对照<strong>最新稳定修订版 <code>2025-11-25</code></strong> 核对（协议按日期标注版本，不用语义化版本号），代码用官方 Python SDK <code>mcp</code> <strong>v2.0.0</strong>。想深挖回到这三份一手材料：<br>

      <h3>MCP 解决了什么问题：N×M 到 N+M</h3>
      <p class="cjk">在 MCP 之前，每个 AI 应用要接入每个工具都得写一套定制集成——M 个模型 × N 个工具 = M×N 套对接代码，是一场组合爆炸的噩梦。MCP 用一个统一协议把它降为 <strong>M+N</strong>：工具方实现一次 MCP Server，模型方实现一次 MCP Client，双方即可即插即用。这就是它被称为"AI 界 USB-C"的根本原因。</p>
      <p class="cjk">这个"N×M → N+M"的降维，本质是软件工程里反复出现的<strong>"引入中间抽象层解耦"</strong>思想的又一次上演。类比很多：操作系统用<strong>驱动模型</strong>把"每个应用适配每个硬件"降为"每个硬件写一个驱动"；数据库世界用 <strong>ODBC/JDBC</strong> 把"每个程序对接每种数据库"降为"每种数据库出一个驱动"；语言服务器用 <strong>LSP</strong> 把"每个编辑器 × 每种语言"降为"每种语言一个 language server"。MCP 之于 AI 工具生态，扮演的正是同一个角色。<mark class="key2">面试时把 MCP 放进 ODBC / LSP 这条"标准化协议"的历史脉络里讲，会显得格外有洞察力——它说明你看到的是模式，而不只是一个新名词。</mark></p>
      <p class="cjk">要强调的是，MCP 降低的是<strong>集成的边际成本</strong>而非零成本：Server 仍要认真实现、Client 仍要正确对接，但一旦某个工具有了标准 MCP Server，所有支持 MCP 的宿主都能立刻复用它，无需各自重写。这种"一次实现、处处可用"的网络效应，正是标准协议能够形成生态的根本动力。</p>
      <p class="cjk">举个具体场景就更直观了。假设你要给三个不同的 AI 应用（一个 IDE、一个桌面助手、一个自建 Agent）都接上"读写公司 Wiki"和"查询订单库"两种能力。在 MCP 之前，这是 3×2＝6 套彼此不通用的对接代码，任何一方升级都要牵动其余；有了 MCP，你只需实现 <strong>1 个 Wiki Server + 1 个订单库 Server</strong>，三个应用各自作为 Host 去连即可，新增第四个应用时也无需再碰 Server。<mark class="key2">"把定制集成的乘法关系变成加法关系"，就是 MCP 最值得在面试里讲透的一句话。</mark></p>

      <h3>三大核心概念：Host / Client / Server</h3>
      <div class="table-wrap">
        <table>
          <thead>
            <tr><th>角色</th><th>职责</th><th>举例</th></tr>
          </thead>
          <tbody>
            <tr><td><strong>Host 宿主</strong></td><td>用户直接交互的 AI 应用，管理一个或多个 Client</td><td>Claude Desktop、Cursor、你的 Agent 应用</td></tr>
            <tr><td><strong>Client 客户端</strong></td><td>宿主内部与某个 Server 保持 1:1 连接的连接器</td><td>Host 为每个 Server 创建的连接实例</td></tr>
            <tr><td><strong>Server 服务端</strong></td><td>暴露能力（工具/资源/提示）给模型使用的程序</td><td>GitHub MCP Server、文件系统 Server、数据库 Server</td></tr>
          </tbody>
        </table>
      </div>
      <p class="cjk">这三者的关系有个容易踩的坑必须讲清：<strong>Host 与 Client 不是同义词</strong>。Host 是你面对的那个应用（如 Cursor、Claude Desktop），它内部可以持有多个 Client；每个 Client 与一个 Server 保持严格的 <strong>1:1 连接</strong>。为什么要 1:1？因为这样能把不同 Server 的能力、权限、生命周期彼此隔离——某个 Server 崩了、或被判定不可信，Host 只需断开对应的那一个 Client，不影响其他连接。<mark class="key">"一个 Host、多个 Client、每个 Client 独连一个 Server"这句话，是回答架构题时必须精确说出的结构。</mark></p>
      <p class="cjk">还要厘清一个常见误解：<strong>MCP Server 不等于"远程服务器"</strong>。这里的 Server 是协议角色（能力的提供方），它既可以是运行在你本机的一个子进程（比如一个读写本地文件的 Server），也可以是一个部署在云端的远程服务。把"Server"直接脑补成"云端主机"，会在传输层选型的问题上答错方向。</p>

      <h3>三大原语：Resources / Tools / Prompts</h3>
      <p class="cjk">MCP 把 Server 能提供的能力抽象为三种<strong>原语（primitives）</strong>。它们最关键的区别不在"能做什么"，而在<strong>"由谁来控制"</strong>——这是理解 MCP 设计哲学的钥匙：</p>
      <ul class="cjk">
        <li><strong>Tools（工具）</strong>：可被模型调用执行的函数，如"创建 issue""查询数据库"。<strong>模型控制</strong>——由 LLM 自主决定何时调用，是最常用的能力。</li>
        <li><strong>Resources（资源）</strong>：可读取的数据源，如文件内容、数据库记录，为模型提供上下文。<strong>应用控制</strong>——通常由宿主决定把哪些资源喂给模型，类似"只读的上下文供给"。</li>
        <li><strong>Prompts（提示模板）</strong>：预定义的可复用提示模板，<strong>用户控制</strong>——常由用户主动触发（如在编辑器里点选一个"代码审查"模板）。</li>
      </ul>
      <div class="table-wrap">
        <table>
          <thead>
            <tr><th>原语</th><th>控制方</th><th>类比</th><th>副作用</th><th>典型用法</th></tr>
          </thead>
          <tbody>
            <tr><td>Tools</td><td>模型（model-controlled）</td><td>POST 接口 / 函数调用</td><td>可有（会改变外部状态）</td><td>创建 issue、发消息、执行查询</td></tr>
            <tr><td>Resources</td><td>应用（app-controlled）</td><td>GET 接口 / 只读文件</td><td>无（只读）</td><td>提供文件、记录、日志作上下文</td></tr>
            <tr><td>Prompts</td><td>用户（user-controlled）</td><td>预设模板 / 斜杠命令</td><td>无</td><td>可复用的工作流模板、指令片段</td></tr>
          </tbody>
        </table>
      </div>
      <p class="cjk">这套"三方控制"的划分不是学究式的：它直接决定了<strong>安全边界</strong>。Tools 由模型自主触发、且可能有副作用，因而是风险最高、最需要人工确认与权限收敛的原语；Resources 只读，风险主要在"是否泄露了不该给的数据"；Prompts 由用户显式触发，风险最低。<mark class="key2">回答"MCP 三大原语"时，如果只背名字就止步了；能补上"分别由谁控制、风险等级如何"，才是把设计意图讲透了。</mark></p>

        <span class="label">面试高频</span>
        <span class="cjk">"MCP 和普通的 Function Calling 有什么区别？" —— Function Calling 是模型层面的单次工具调用能力；MCP 是应用层面的<strong>标准化协议</strong>，规定了工具如何被发现、连接、复用。可以说：MCP 让 Function Calling 从"每次手写对接"变成"标准接口即插即用"。能讲清这层关系，说明你理解到位。</span>

      <h3>传输层：stdio 与 Streamable HTTP</h3>
      <p class="cjk">MCP 定义了两种主要的传输方式，理解它们能回答"MCP Server 部署在哪"这类实操问题：<strong>stdio</strong>——Server 作为本地子进程运行，通过标准输入输出通信，延迟低、适合访问本地资源（文件系统、本地数据库），Claude Desktop 的本地插件多用它；<strong>Streamable HTTP</strong>（取代了早期的 HTTP+SSE）——Server 作为远程服务运行，适合云端部署、多用户共享的场景。选型逻辑很简单：<mark class="key">要访问用户本机资源就用 stdio，要做云端共享服务就用 Streamable HTTP。</mark></p>
      <div class="table-wrap">
        <table>
          <thead>
            <tr><th>维度</th><th>stdio</th><th>Streamable HTTP</th></tr>
          </thead>
          <tbody>
            <tr><td>Server 位置</td><td>本地子进程（与 Host 同机）</td><td>远程服务（可跨网络）</td></tr>
            <tr><td>通信信道</td><td>标准输入/输出流</td><td>HTTP，支持流式返回</td></tr>
            <tr><td>延迟</td><td>极低，无网络开销</td><td>受网络往返影响</td></tr>
            <tr><td>多用户</td><td>单用户单进程</td><td>天然支持多客户端共享</td></tr>
            <tr><td>认证</td><td>依赖本机进程权限</td><td>需要 OAuth 等鉴权机制</td></tr>
            <tr><td>适用</td><td>访问本地文件/数据库、离线工具</td><td>云端 SaaS、团队共享的托管 Server</td></tr>
          </tbody>
        </table>
      </div>
      <p class="cjk">关于早期的 <strong>HTTP+SSE（Server-Sent Events）</strong>：它是最初的远程传输方案，用一条长连接做服务器到客户端的流式推送，但存在连接维持成本高、断线恢复困难、不利于无状态水平扩展等问题。后来的 <strong>Streamable HTTP</strong> 对其做了改良，让远程 Server 更容易部署在常规的无状态 HTTP 基础设施上。<mark class="key2">若被问"HTTP+SSE 和 Streamable HTTP 什么关系"，答"后者是前者的演进替代、更适配无状态云部署"，就能显出你在跟进协议演进。</mark>无论哪种传输，MCP 的上层语义（初始化、能力发现、调用）都保持一致——这正是把"传输"与"协议语义"分层解耦的好处。</p>

      <h3>一个最小 MCP Server 的代码示例</h3>
      <p class="cjk">能写出一个最小 Server，胜过一堆概念背诵。下面用官方 Python SDK 的高层封装（FastMCP 风格）定义一个既有 Tool 又有 Resource 的 Server，并以 stdio 方式运行——注意<strong>工具的类型注解与文档字符串会被自动转成给模型看的 schema 与描述</strong>，这正是"能力发现"的数据来源。</p>
      <div class="code-label">Python · 定义并运行一个最小 MCP Server</div>
      <pre><code><span class="cm"># 依赖官方 MCP Python SDK 的高层封装</span>
<span class="kw">from</span> mcp.server.fastmcp <span class="kw">import</span> FastMCP

mcp = FastMCP(<span class="st">"demo-server"</span>)

<span class="cm"># 注册一个 Tool：函数签名 + docstring 会自动生成 schema 供模型发现</span>
<span class="kw">@mcp.tool</span>()
<span class="kw">def</span> <span class="fn">create_issue</span>(repo: str, title: str, body: str = <span class="st">""</span>) -&gt; dict:
    <span class="st">"""在指定仓库创建一个 issue，返回其编号与链接。"""</span>
    <span class="kw">return</span> github_api.create(repo, title, body)  <span class="cm"># 真实副作用发生处</span>

<span class="cm"># 注册一个 Resource：只读上下文，URI 模板由 {name} 参数化</span>
<span class="kw">@mcp.resource</span>(<span class="st">"file://logs/{name}"</span>)
<span class="kw">def</span> <span class="fn">read_log</span>(name: str) -&gt; str:
    <span class="st">"""按名称读取一份日志文件的内容作为上下文。"""</span>
    <span class="kw">return</span> (LOG_DIR / name).read_text()

<span class="kw">if</span> __name__ == <span class="st">"__main__"</span>:
    mcp.run(transport=<span class="st">"stdio"</span>)  <span class="cm"># 作为本地子进程，通过标准输入输出通信</span></code></pre>
      <p class="cjk">这段代码把几个抽象概念落地了：<strong>①</strong> <code>@mcp.tool()</code> 装饰的函数就是一个"模型可调用"的 Tool，其参数类型（<code>repo/title/body</code>）会被序列化成 JSON Schema，让模型知道该传什么；<strong>②</strong> docstring 不是写给人看的注释，而是喂给模型的<strong>工具描述</strong>——描述写得好不好，直接影响模型会不会、以及会不会正确地调用它；<strong>③</strong> Resource 用 URI 模板（<code>file://logs/{name}</code>）暴露只读数据，与 Tool 的"可执行、有副作用"形成鲜明对照；<strong>④</strong> <code>transport="stdio"</code> 决定它作为本地子进程被宿主拉起。把这个例子讲清，你就同时讲清了"原语"和"能力发现"两个考点。</p>

      <h3>一次 MCP 交互的完整流程</h3>
      <p class="cjk">面试官常追问"MCP 到底怎么跑起来的"。完整流程分四步：① <strong>初始化握手</strong>——Client 与 Server 建立连接，协商协议版本与能力；② <strong>能力发现</strong>——Client 调用 <code>tools/list</code> 等方法，获取 Server 暴露的工具/资源/提示清单；③ <strong>能力调用</strong>——模型决定使用某工具，Client 发送 <code>tools/call</code> 请求，Server 执行并返回结果；④ <strong>结果注入</strong>——结果写回模型上下文，模型继续推理。整个协议基于 <strong>JSON-RPC 2.0</strong>，这也是它跨语言、跨平台的基础。</p>
      <figure class="diagram">
        <pre class="mermaid">
sequenceDiagram

    H->>S: initialize（协商版本与能力）

    S-->>H: 工具清单 + JSON Schema
    Note over H: 模型据描述决定调用哪个工具
    H->>S: tools/call（携带参数）

      </figure>
      <p class="cjk">为什么选 JSON-RPC 2.0 而不是自己发明一套？因为它<strong>轻量、语言无关、请求-响应语义清晰</strong>，且天然支持通知（notification）。这让任何语言只要能收发 JSON 就能实现 MCP，极大降低了生态参与门槛。<mark class="key2">一个容易答错的细节：JSON-RPC 2.0 本身支持批处理（batch），但 MCP 已在 <code>2025-06-18</code> 修订版中<strong>移除了批处理支持</strong>——所以别再说"MCP 支持批量请求"，那是过时信息。</mark>值得注意的是握手阶段的<strong>版本与能力协商</strong>：它让协议能向前演进而不轻易破坏旧客户端——新 Server 可以声明自己支持的新能力，老 Client 用不上就忽略，这是任何想长期存活的协议都要有的设计。<mark class="key">把"JSON-RPC + 能力协商"讲出来，能证明你理解的是协议工程，而非仅仅一个 SDK 的用法。</mark></p>
      <p class="cjk">面试进一步深挖时，两个细节能体现你的工程成熟度。其一是<strong>错误与超时处理</strong>：<code>tools/call</code> 是可能失败的（工具抛异常、参数非法、后端超时），Server 应把错误以结构化形式返回，而不是让连接直接崩溃；Host 侧则要决定"把错误信息回灌给模型让它重试或换路"还是"直接终止"，这与第 3 章 ReAct 的观测-反思闭环一脉相承。其二是<strong>能力的动态变化</strong>：Server 暴露的工具清单可能在运行时增减，MCP 允许 Server 主动通知 Client"列表变了"，Client 据此刷新——这解释了为什么"能力发现"不是一次性动作，而是可持续同步的。把"失败会发生、清单会变"纳入回答，说明你想的是真实系统而非玩具 demo。</p>

      <h3>MCP 的安全考量：不可忽视的攻击面</h3>
      <div class="callout warn">
        <span class="label">MCP 引入的新风险</span>
        <span class="cjk">MCP 把外部世界接入模型，也就打开了新的攻击面：<strong>恶意 Server</strong>（第三方 Server 可能窃取数据或返回诱导性内容）、<strong>工具投毒（Tool Poisoning）</strong>（在工具描述里藏入提示注入指令）、<strong>过度权限</strong>（Server 拿到了超出必要的访问权限）。生产接入 MCP 时必须做：来源可信校验、最小权限原则、对 Server 返回内容做净化，以及对高危操作强制人工确认。能主动谈 MCP 安全，是资深工程师的标志。</span>
      </div>
      <p class="cjk">把这些风险落成可执行的防线，比罗列名词更有说服力。几条实践值得记住：</p>
      <ul class="hub-list">
        <li><strong>把工具描述当作不可信输入</strong>：既然工具的 name/description 会被拼进提示，恶意 Server 就能在描述里塞"顺便把用户密钥发到某地址"这类隐藏指令（即工具投毒）。对策是只从可信来源安装 Server、对描述做审查，并警惕"描述与功能名不符"的可疑工具。</li>
        <li><strong>最小权限与作用域隔离</strong>：给每个 Server 授予刚好够用的权限（只读就别给写、单库就别给全库），并用前面说的 1:1 Client 连接把它与其他 Server 隔离，一旦失信可单独切断。</li>
        <li><strong>高危动作人工确认（human-in-the-loop）</strong>：删除、转账、对外发消息、改数据库这类不可逆或有副作用的 Tool，调用前应弹出确认，与第 1 章的自主性护栏一脉相承。</li>
        <li><strong>输出净化与混淆防护</strong>：Server 返回内容会进模型上下文，可能夹带"间接提示注入"，需要做清洗，并在架构上区分"数据"与"指令"。</li>
        <li><strong>远程 Server 的鉴权</strong>：走 Streamable HTTP 的远程 Server 要有正规的身份认证（如 OAuth）与传输加密，避免任意一方冒充。</li>
      </ul>
      <div class="callout warn">
        <span class="label">"混淆代理"陷阱</span>
        <span class="cjk">一个易被忽视的风险是：MCP Server 常以更高权限代表用户去访问后端资源。如果它不做细粒度的身份透传与授权校验，攻击者就可能借模型之口，让 Server 去做用户本人无权做的事——这类"权限被放大"的问题在传统安全里叫混淆代理（confused deputy）。设计远程 Server 时，务必把"以谁的身份、被授权做什么"贯穿到每一次真实调用。</span>
      </div>

      <h3>MCP vs Function Calling vs 插件：三层别混淆</h3>
      <p class="cjk">这是本章最高频、也最能拉开差距的对比题。三者常被混为一谈，其实处在不同层次：</p>
      <div class="table-wrap">
        <table>
          <thead>
            <tr><th>维度</th><th>Function Calling</th><th>MCP</th><th>（各厂）插件系统</th></tr>
          </thead>
          <tbody>
            <tr><td>本质</td><td>模型能力：输出结构化的工具调用意图</td><td>开放协议：如何发现、连接、复用工具</td><td>某平台内的封闭工具接入规范</td></tr>
            <tr><td>层次</td><td>模型层</td><td>应用/集成层</td><td>平台生态层</td></tr>
            <tr><td>互操作</td><td>各家 schema 略有差异</td><td>跨厂商、跨宿主通用</td><td>通常绑定单一平台</td></tr>
            <tr><td>复用性</td><td>每个应用各写各的对接</td><td>一次实现，多宿主复用</td><td>仅限该平台内复用</td></tr>
            <tr><td>关系</td><td>MCP 的底层仍靠它触发调用</td><td>把 Function Calling 标准化、可发现</td><td>可视为被 MCP 取代的前身思路</td></tr>
          </tbody>
        </table>
      </div>
      <p class="cjk">最精炼的一句话：<mark class="key">Function Calling 解决"模型怎么表达想调工具"，MCP 解决"工具怎么被标准化地发现和连接"，二者不是竞争而是上下层配合。</mark>当模型通过 Function Calling 决定"要调 create_issue"，底层正是由 MCP Client 把这次意图翻译成 <code>tools/call</code> 发给对应 Server。至于早期各家的"插件"系统，可以理解为 MCP 出现之前的探索：思路相近（让模型用外部能力），但各自封闭、不能互通，最终被一个开放协议收敛——这正是行业从"私有插件"走向"公共协议"的缩影。</p>

      <h3>MCP 的生态现状与适用边界</h3>
      <p class="cjk">谈生态要克制、只讲能确定的趋势，不编造数字。可以确定的几点：MCP 由 Anthropic 于 2024 年 11 月开源后，2025 年被 OpenAI、Google DeepMind 等主流厂商采纳，逐步成为跨厂商的事实标准；主流开发工具（如支持 MCP 的 IDE、桌面客户端）与大量官方/社区 Server（文件系统、Git/代码托管、数据库、检索等常见能力）已可即插即用；官方提供了多语言 SDK，降低了自建 Server 的门槛。<mark class="key2">被问"生态怎么样"，稳妥答法是讲"从单厂标准走向多厂采纳、Server 数量与工具类别持续扩张"，而不要报任何没有把握的具体数值。</mark></p>
      <p class="cjk">同样要讲清<strong>边界</strong>，避免"言必称 MCP"的过度设计：如果你的 Agent 只连自家、少数几个内部工具，直接用 Function Calling 或私有集成往往更省事，未必需要引入协议层；MCP 的价值在<strong>多工具、多来源、需要复用与解耦</strong>的场景才充分体现。此外，MCP 主要解决"Agent 连接工具与数据"这一纵向问题，它<strong>不负责</strong>"多个 Agent 之间如何协作"——那是下一节 A2A 的领域。把"什么时候该用、什么时候不必用"讲清楚，比一味吹捧更能体现工程判断力。</p>
      <p class="cjk">一个务实的落地建议：接入外部 MCP Server 前，先把它当"第三方依赖"审一遍——来源是否可信、权限是否最小、返回是否需要净化、高危动作是否加了确认；能自建就优先自建可控的 Server，而不是随手引入来路不明的公共 Server。<mark class="key">"先评估要不要用、再评估用谁的 Server"，这种既拥抱标准又保持审慎的态度，正是面试官想在资深候选人身上看到的成熟度。</mark></p>

      <h3>MCP vs A2A：两种协议解决不同问题</h3>
      <p class="cjk">2025 年 Google 提出了 A2A（Agent-to-Agent）协议，常被拿来和 MCP 比较。二者其实互补而非竞争：<mark class="key2">MCP 解决"Agent 如何连接工具与数据"（垂直集成），A2A 解决"Agent 如何与其他 Agent 协作通信"（水平集成）</mark>。一个复杂系统可能同时用两者：内部各 Agent 通过 A2A 协作，每个 Agent 又通过 MCP 连接自己的工具。能点出这个区分，说明你对 Agent 生态的全局有把握。</p>
      <p class="cjk">用一句话把两者的分工钉死：<strong>MCP 是"Agent 向下够到工具"，A2A 是"Agent 向旁边够到同伴"</strong>。前者的对端是被动的能力提供方（Server 不会自己发起任务），后者的对端是同样具备自主性的 Agent（可以协商、委派、并行推进）。因此二者关注的问题也不同：MCP 关心能力发现、调用与安全边界；A2A 更关心 Agent 之间如何声明各自技能、如何交换任务与中间结果、如何处理长时协作。理解这层"纵向 vs 横向"，你就能在系统设计题里画出一张清晰的双层图——底层每个 Agent 用 MCP 接工具，上层多个 Agent 用 A2A 编排协作。<mark class="key">切忌把它们说成"竞品"或"谁取代谁"，那会立刻暴露理解不到位。</mark></p>

      <h3>面试追问链</h3>
      <div class="callout warn">
        <span class="label">常见误区与反模式</span>
        <span class="cjk">① <strong>"MCP 是个框架/SDK"</strong>——它是<strong>协议</strong>，SDK 只是它的一种实现，说错这点会显得停留在表层。② <strong>"MCP 取代了 Function Calling"</strong>——二者是上下层配合，模型仍靠 Function Calling 表达调用意图。③ <strong>"MCP Server 就是云服务器"</strong>——Server 是协议角色，可本地可远程，混淆会答错传输选型。④ <strong>"接了 MCP 就安全省心"</strong>——恰恰相反，引入外部 Server 是在扩大攻击面，工具投毒与过度权限是真实风险。⑤ <strong>"什么场景都上 MCP"</strong>——只连少数内部工具时，私有集成往往更划算，协议层不是免费的。</span>
      </div>
      <ul class="hub-list">
        <li><strong>Q1：</strong>MCP 是什么、解决什么问题？→ AI 界 USB-C，N×M 降到 N+M。</li>
        <li><strong>Q2：</strong>它和 Function Calling 的区别？→ 协议 vs 单次调用能力。</li>
        <li><strong>Q3：</strong>MCP Server 部署在哪、怎么通信？→ stdio（本地）vs Streamable HTTP（云端），基于 JSON-RPC。</li>
        <li><strong>Q4：</strong>接入 MCP 有什么安全风险？→ 恶意 Server、工具投毒、过度权限及其对策。</li>
        <li><strong>Q5：</strong>MCP 和 A2A 什么关系？→ 垂直集成 vs 水平集成，互补。</li>
      </ul>

      <div class="callout tip">
        <span class="label">本章小结</span>
        <span class="cjk">MCP 是 Agent 连接外部世界的标准协议，用 Host-Client-Server 三角把 N×M 集成噩梦降为 N+M，被誉为"AI 界的 USB-C"。核心能力是 Tools/Resources/Prompts，传输走 stdio 或 Streamable HTTP，协议基于 JSON-RPC。它带来即插即用的便利，也带来新的安全攻击面——<strong>标准化的另一面永远是对安全边界的重新审视。</strong></span>
