## 真实问题

补录报销单方案要接真实模型时，团队踩了个「协议」的坑。他们先按 Anthropic 的 Computer use 写了一套处理代码：解析 `tool_use` 块、读 `action` 字段、按 `coordinate: [x, y]` 点击、用 `tool_result` 回填。跑通后，产品经理说「我们也想接 OpenAI 的 computer-use 做 A/B 对比」。工程师想当然地复制了一份代码去改，结果发现两家**字段名、动作结构、回填方式全不一样**：OpenAI 返回的是 `computer_call`、坐标是分开的 `x`/`y`、回填要用 `computer_call_output`，还要求 `truncation="auto"`。两份处理代码很快开始漂移——改了 Anthropic 分支忘了改 OpenAI 分支，bug 层出不穷。

这暴露了一个工程真相：**两家的操作循环形状一致（看截图→出动作→执行→回填截图），但协议字段各不相同**。要同时对接，就得像第 8 章处理 `tool_calls` / `tool_use` 那样，写一个归一化层把差异折叠掉。这一节把两家的公开机制讲清，并给出归一化的最小实现。

## 原理：同构的循环，不同的字段

先看两家公开机制的共性——都是第 2 节讲的操作循环：

- **OpenAI computer-use**：通过 `computer-use-preview` 模型 + `computer_use_preview` 工具，走在 Responses API（不支持 Chat Completions）。五步循环：发请求（带 `computer` 工具、`display_width`/`display_height`、`environment`）→ 收到含 `computer_call` 的响应（含建议动作）→ 执行动作 → 截图 → 用 `computer_call_output` 回填并重复 [来源](https://platform.openai.com/docs/guides/tools-computer-use)。
- **Anthropic Computer use**：通过带 `computer` 工具的请求，模型返回 `tool_use` 块，`input.action` 指定动作（`left_click`、`type`、`key`、`mouse_move`、`scroll` 等），坐标用 `coordinate: [x, y]`；执行后用 `tool_result` 回填截图 [来源](https://platform.claude.com/docs/en/agents-and-tools/tool-use/computer-use-tool)。

差异对照（字段名与结构，具体以当前官方文档为准）：

| 维度 | Anthropic Computer use | OpenAI computer-use |
|---|---|---|
| 入口 | 带 `computer` 工具的 Messages 请求 | Responses API + `computer_use_preview` 工具 |
| 模型侧输出 | `tool_use` 块 | `computer_call` 项 |
| 动作字段 | `input.action`（如 `left_click`） | `action.type`（如 `click`） |
| 坐标表示 | `coordinate: [x, y]` | 分开的 `x`、`y` |
| 结果回填 | `tool_result` 块带 `tool_use_id` + 截图 | `computer_call_output` 带 `call_id` + `computer_screenshot` |
| 特有要求 | 声明屏幕分辨率、显示号 | 需设 `truncation="auto"`；reasoning 项须回带 |
| 安全信号 | 文档提示注入风险与隔离建议 | `pending_safety_checks` 需显式确认 |

两家都不是「模型直接操作电脑」——模型只输出**建议动作**，真正的点击/输入由你的执行器（Playwright、xdotool、pyautogui 等）在沙箱环境里执行，再把新截图送回，与第 8 章「模型只说不做」的铁律完全一致。

## 现象与输入

把「同一个点击意图，两家表达不同」拆成可观测字段：
```text
意图：在 (1160,640) 处左键点击

Anthropic 模型输出（tool_use 块）：
  {"type":"tool_use","name":"computer",
   "input":{"action":"left_click","coordinate":[1160,640]}}

OpenAI 模型输出（computer_call 项）：
  {"type":"computer_call","call_id":"c1",
   "action":{"type":"click","button":"left","x":1160,"y":640}}

归一化目标：两者都折叠成 UnifiedAction(kind="click", x=1160, y=640)
之后主循环只处理 UnifiedAction，不关心它来自哪家。
```
## 最小可运行演示

下面写一个归一化层，把两家的动作折叠成统一内部结构，并说明两家回填格式的差异。它不联网、不需要 API Key（仅按公开文档的字段形状构造，不发真实请求）。
```python
from __future__ import annotations
from dataclasses import dataclass


@dataclass
class UnifiedAction:
    kind: str            # click / type / key / scroll / screenshot / done
    x: int = 0
    y: int = 0
    text: str = ""


def from_anthropic(block: dict) -> UnifiedAction:
    """Anthropic: {"type":"tool_use","name":"computer",
                   "input":{"action":"left_click","coordinate":[x,y]}}"""
    inp = block.get("input", {})
    act = inp.get("action")
    if act in ("left_click", "right_click", "middle_click"):
        x, y = inp.get("coordinate", [0, 0])
        return UnifiedAction("click", x, y)
    if act == "type":
        return UnifiedAction("type", text=inp.get("text", ""))
    if act == "key":
        return UnifiedAction("key", text=inp.get("text", ""))
    if act == "screenshot":
        return UnifiedAction("screenshot")
    return UnifiedAction("done")


def from_openai(item: dict) -> UnifiedAction:
    """OpenAI: {"type":"computer_call","action":{"type":"click","x":..,"y":..}}"""
    a = item.get("action", {})
    t = a.get("type")
    if t == "click":
        return UnifiedAction("click", a.get("x", 0), a.get("y", 0))
    if t == "type":
        return UnifiedAction("type", text=a.get("text", ""))
    if t == "keypress":
        return UnifiedAction("key", text=",".join(a.get("keys", [])))
    if t == "screenshot":
        return UnifiedAction("screenshot")
    return UnifiedAction("done")


def run() -> None:
    # 同一个"点击(1160,640)"意图，两家表达不同，归一化后应一致
    anthropic_block = {"type": "tool_use", "name": "computer",
                       "input": {"action": "left_click", "coordinate": [1160, 640]}}
    openai_item = {"type": "computer_call", "call_id": "c1",
                   "action": {"type": "click", "button": "left", "x": 1160, "y": 640}}

    ua = from_anthropic(anthropic_block)
    uo = from_openai(openai_item)
    print(f"Anthropic 块 -> {ua}")
    print(f"OpenAI   项 -> {uo}")
    print(f"归一化后一致={ua == uo}")

    print("\n回填格式（各以官方文档为准）：")
    print("  Anthropic: 用 tool_result 块带 tool_use_id + 截图图片内容")
    print("  OpenAI:    用 computer_call_output 带 call_id + computer_screenshot(image_url)")


if __name__ == "__main__":
    run()
```
保存为 `normalize.py`，运行 `python normalize.py`。完整预期输出：
```text
Anthropic 块 -> UnifiedAction(kind='click', x=1160, y=640, text='')
OpenAI   项 -> UnifiedAction(kind='click', x=1160, y=640, text='')
归一化后一致=True

回填格式（各以官方文档为准）：
  Anthropic: 用 tool_result 块带 tool_use_id + 截图图片内容
  OpenAI:    用 computer_call_output 带 call_id + computer_screenshot(image_url)
```
这段输出证明：两家形状迥异的动作，经归一化层折叠后完全一致，主循环从此只需处理 `UnifiedAction`。回填部分只打印说明而不构造，是因为回填格式细节（字段名、图片编码）最容易变，正确做法是**把它隔离在归一化层里、以官方文档为准**，而非散落在业务代码各处。

## 真实系统对应

**官方公开机制**：OpenAI 文档给出完整五步循环、`computer_use_preview` 工具参数、Playwright/Docker 环境搭建、`reasoning` 项须随请求回带、`pending_safety_checks` 需确认、beta 阶段不建议用于全权限或高风险任务 [来源](https://platform.openai.com/docs/guides/tools-computer-use)；Anthropic 文档给出动作清单、坐标语义、分辨率建议、以及「越狱/提示注入可能持续存在，Claude 有时会执行网页或图片中发现的指令」的明确风险声明 [来源](https://platform.claude.com/docs/en/agents-and-tools/tool-use/computer-use-tool)。**通用工程模式**：归一化层、把易变字段隔离在适配器里，是可迁移到任何多厂商对接的做法。**教学参考实现**：上面的 `from_anthropic` / `from_openai` 只覆盖几个常见动作，真实实现需覆盖全部动作类型并做健壮的缺省处理。

需要点明边界：`computer-use-preview`、`computer_20250124` 等模型/工具标识、动作全集、分辨率上限、beta/preview 状态都会随版本变化——本节讲的是**「两家同构循环 + 字段差异 + 归一化」这个稳定结构**，具体拼写和可用动作一律以检索时的官方文档为准，不要把某次抓到的字段名写死成永久契约。

## 生产踩坑

| 症状 | 根因 | 如何观测与复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| 两家处理代码各改各的漂移 | 没有归一化层、复制粘贴两份 | diff 两份分支看不一致 | 用 UnifiedAction 归一化层 | 只对接一家时可暂缓 |
| OpenAI 请求报错要 truncation | 未设 truncation="auto" | 不设该参数即复现 400 | 按文档设 truncation="auto" | 其他工具无此要求 |
| OpenAI 多轮请求失败 | 丢了 reasoning 项没回带 | 过滤掉 reasoning 后复现 | 把 reasoning 项随 computer_call 一起回带 | 用 previous_response_id 托管时另算 |
| 把 preview 用于高风险场景 | 无视 beta 风险声明 | 在生产付款流程直接放开 | 沙箱 + 人工确认 + 限权 | 受控演示环境风险低 |
| 硬编码动作字段名 | 未隔离易变协议细节 | 官方改字段后整体崩 | 字段解析集中在适配器 | 短期一次性脚本可接受 |
| 分辨率声明与截图不符 | display 尺寸和实际截图不一致 | 声明 1024×768 却发别的尺寸 | 声明尺寸=实际截图尺寸 | 同尺寸时不触发 |

## 思考：为什么对接多家 Computer Use API 必须先做归一化层，而不是各写各的？

### 回答

因为 Computer Use 的协议字段是「高频变动 + 高度相似 + 分散调用」三者叠加，不归一化必然陷入维护地狱。高度相似：两家的循环形状一模一样（看截图→出动作→执行→回填），只是字段名和结构不同，这意味着业务逻辑（怎么点、怎么等稳定、怎么加护栏）本可以完全复用；如果各写各的，等于把同一套逻辑抄了两遍，任何一次逻辑修改都要改两处，漏改一处就是 bug。高频变动：`computer-use-preview` 还在 beta，动作全集、分辨率上限、必填参数（如 `truncation`）都可能变，把这些易变细节散落在业务代码各处，一次协议更新就要全局搜索替换，风险极高。分散调用：动作解析、坐标回缩、结果回填散布在主循环多个位置，不集中就无法统一测试。归一化层把这三个问题一次性解决：它像一个「翻译官」，对上暴露稳定的 `UnifiedAction` 给业务逻辑，对下把各家易变字段隔离在适配器里；协议一变只改适配器、业务代码零改动；新增一家厂商只加一个 `from_xxx()`。这与第 8 章处理 `tool_calls` / `tool_use` 归一化是同一个工程原则——**把易变的外部契约隔离在边界层，让核心逻辑对变化免疫。**

### 面试精简表达

两家循环同构、字段各异且还在 beta 高频变动，各写各的会重复逻辑、漏改出 bug、协议一变全局崩。归一化层对上给稳定 UnifiedAction、对下隔离易变字段，协议变只改适配器、加厂商只加一个解析函数。

## 机制推导：为什么 OpenAI 要求「reasoning 项必须回带」

OpenAI 文档特别强调：如果你自己管理输入数组（不用 `previous_response_id`），必须把 `reasoning` 项连同 `computer_call` 一起回带，否则请求会失败 [来源](https://platform.openai.com/docs/guides/tools-computer-use)。这背后的机制是：CUA 模型的决策依赖它自己上一步的推理链，`reasoning` 项承载了「模型为什么决定点这里」的中间思考，是模型保持决策连贯的上下文。如果你回填截图时把 reasoning 丢了，模型下一轮就「失忆」了——它看不到自己上一步的推理，可能重新规划甚至前后矛盾。

由此推出一条工程结论：**在 Computer Use 里，「要回带给模型的东西」不只有截图，还包括模型自己产出的推理/状态项**。这和第 8 章「模型无状态、每轮重发历史」是同一条铁律的延伸——只是这里「历史」不仅是消息，还包含模型的 reasoning。实现归一化层时，除了折叠动作，也要正确处理这些「必须回带」的项：要么用厂商的会话托管（`previous_response_id`）省心，要么自己完整维护包含 reasoning 的输入序列，绝不能只回填截图就了事。
