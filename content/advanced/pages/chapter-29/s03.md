## 真实问题

补录报销单的循环跑通后，团队把它部署到财务同事的高分屏工作站上，成功率却从测试机的 80% 暴跌到不足 10%。诡异的是：模型的决策日志看起来全对——「点保存按钮」的意图正确，输出的坐标也「看起来合理」，可鼠标就是点在按钮左上方老远的地方。

排查了一整天才定位到元凶：测试机是 1280×800 的普通屏，生产机是 2560×1600 的高分屏。团队为了省 token，把截图统一缩小到 1280×800 再喂给模型，模型也就在**缩小图的坐标系**里返回坐标（比如 `(1080, 640)`），可执行器却把这个坐标直接当**真实屏幕坐标**去点——真实按钮明明在 `(2160, 1280)`，偏了一千多像素。这个「忘记把模型坐标按缩放比回缩到真实分辨率」的 bug，是 Computer Use 里最经典、最坑、也最容易被官方文档反复提醒的一个。

## 原理：坐标缩放与两种绕开像素的思路

多模态模型处理图像有像素预算，真实系统普遍会把大截图**缩小**后再发给模型。这就引入一条铁律：**模型返回的坐标是「它看到的那张图」的坐标系，必须按缩放比换算回真实分辨率**。Anthropic 官方直接给出建议：分辨率太低会导致点击精度差，建议以 1280×720 之类为基线；模型看到的是缩放后的图，返回的坐标也在缩放后的空间，需要换算回真实屏幕 [来源](https://platform.claude.com/docs/en/agents-and-tools/tool-use/computer-use-tool)。

既然纯像素定位这么脆弱，工程上有两条「绕开或加固」的思路：

- **set-of-mark（标记集提示，SoM）**：先在截图上给每个可交互元素叠加一个编号标签（①②③…），让模型只需回答「点标号 ②」，运行时再查表拿到该编号对应的真实坐标。这把「回归精确像素」降级成「多选题选编号」，大幅降低定位难度和缩放误差。
- **结构化定位**：网页有 DOM（Document Object Model，文档对象模型）、桌面有无障碍树（Accessibility Tree），能直接给出元素的角色、名字和位置。用它们定位，根本不需要模型猜坐标（详见第 6 节）。
```text
纯像素坐标（脆）：      模型 ── 输出 (1080,640) ──▶ 必须 ×(2560/1280) 回缩到 (2160,1280)
                                                └─ 忘了回缩 = 点偏一千像素

set-of-mark（稳）：     截图叠标号 ①②③ ──▶ 模型只答"点②" ──▶ 查表得真实坐标 (2160,1280)

结构化定位（最稳）：    DOM/无障碍树 ──▶ role=button,name=保存 ──▶ 直接拿到元素引用，零坐标
```
## 现象与输入

把「忘记回缩」这个坑拆成可观测的数字，触目惊心：
```text
真实屏幕：2560×1600（高分屏）
喂给模型：1280×800（缩小一半）
真实按钮中心：(2160, 1280)

模型在缩小图上正确定位到：(1080, 640)   ← 相对缩小图，这是对的
反模式：直接把 (1080,640) 当真实坐标点  ← 曼哈顿偏差 = |1080-2160|+|640-1280| = 1720 像素（点空）
正确：按 ×2 回缩到 (2160,1280)          ← 曼哈顿偏差 = 0（命中）
set-of-mark：模型答"点②"，查表得 (2160,1280) ← 零缩放误差
```
## 最小可运行演示

下面演示坐标缩放的正反两条路，以及 set-of-mark 如何绕开缩放误差。它不联网、不需要 API Key。
```python
from __future__ import annotations


REAL_W, REAL_H = 2560, 1600         # 真实屏幕（高分屏）
MODEL_W, MODEL_H = 1280, 800        # 喂给模型的缩小图

BUTTON_REAL = (2160, 1280)  # "结算/保存"按钮在真实屏幕上的中心


def to_model_space(x, y):
    return (x * MODEL_W // REAL_W, y * MODEL_H // REAL_H)


def to_real_space(x, y):
    return (x * REAL_W // MODEL_W, y * REAL_H // MODEL_H)


def run() -> None:
    # 模型看到的是缩小图，它按缩小图坐标系输出点击点
    model_click = to_model_space(*BUTTON_REAL)
    print(f"真实按钮中心={BUTTON_REAL}  缩小图上应点={model_click}")

    # 反模式：直接把模型坐标当真实坐标用 -> 偏差巨大
    wrong = model_click
    err = abs(wrong[0] - BUTTON_REAL[0]) + abs(wrong[1] - BUTTON_REAL[1])
    print(f"[忘记回缩] 直接用 {wrong} 当真实坐标 -> 曼哈顿偏差 {err} 像素（点空）")

    # 正确：按缩放比回缩到真实坐标系
    right = to_real_space(*model_click)
    err2 = abs(right[0] - BUTTON_REAL[0]) + abs(right[1] - BUTTON_REAL[1])
    print(f"[正确回缩] 回缩到 {right} -> 曼哈顿偏差 {err2} 像素（命中）")

    # set-of-mark：给元素编号，模型只输出编号，运行时查表拿真实坐标
    marks = {1: ("优惠码输入框", (600, 500)),
             2: ("结算", BUTTON_REAL),
             3: ("清空购物车", (400, 1280))}
    model_choice = 2                        # 模型说"点标号 2"
    name, real_xy = marks[model_choice]
    print(f"[set-of-mark] 模型选编号={model_choice} -> {name} 真实坐标={real_xy}（零缩放误差）")


if __name__ == "__main__":
    run()
```
保存为 `scaling.py`，运行 `python scaling.py`。完整预期输出：
```text
真实按钮中心=(2160, 1280)  缩小图上应点=(1080, 640)
[忘记回缩] 直接用 (1080, 640) 当真实坐标 -> 曼哈顿偏差 1720 像素（点空）
[正确回缩] 回缩到 (2160, 1280) -> 曼哈顿偏差 0 像素（命中）
[set-of-mark] 模型选编号=2 -> 结算 真实坐标=(2160, 1280)（零缩放误差）
```
这段输出把三件事钉死：模型在缩小图上定位是对的（`(1080,640)`）；直接拿来当真实坐标偏了 1720 像素（点空）；按比例回缩后偏差归零（命中）；而 set-of-mark 让模型只选编号，从一开始就绕开了缩放这个坑。生产里最稳的是「能用结构化就用结构化，退而求其次用 set-of-mark，最后才是纯像素 + 严格回缩」。

## 真实系统对应

**官方公开机制**：Anthropic 明确列出分辨率对精度的影响与建议基线（如「精度差 → 提高分辨率」），并说明动作坐标语义（`left_click` 带 `coordinate: [x, y]`）[来源](https://platform.claude.com/docs/en/agents-and-tools/tool-use/computer-use-tool)；OpenAI 的 `computer_use_preview` 工具要求在请求里声明 `display_width` / `display_height`，模型返回的 `computer_call` 动作坐标即基于这个声明的显示尺寸 [来源](https://platform.openai.com/docs/guides/tools-computer-use)。**通用工程模式**：截图缩放 + 坐标回缩、set-of-mark 叠标号、结构化优先，都是可迁移的定位加固手段。**教学参考实现**：上面的整数比例缩放是简化，真实缩放可能保持长宽比并带 padding，回缩公式需相应调整。

需要点明边界：不同模型对「你该发多大分辨率」的建议不同，且会随版本变化（例如更强的模型可能支持更高分辨率作为「甜点」）；具体数值一律以当前官方文档为准，不要把某次检索到的分辨率写死进代码。关键是记住机制——**声明的显示尺寸、模型返回坐标、真实屏幕三者的坐标系必须对齐**。

## 生产踩坑

| 症状 | 根因 | 如何观测与复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| 高分屏上点击全偏一千像素 | 忘记把模型坐标回缩到真实分辨率 | 换高分屏部署即复现 | 统一声明显示尺寸并严格回缩 | 模型图与真实屏同分辨率时无此坑 |
| 缩放后小字看不清、认错 | 缩得太狠丢失细节 | 把截图缩到极小复现读错 | 在预算内取较高分辨率或裁剪关注区 | 大字稀疏界面影响小 |
| 长宽比失真导致 x/y 各偏 | 缩放没保持长宽比 | 非等比缩放后对比 x/y 偏差 | 等比缩放 + padding，回缩对齐 | 本就等比时不触发 |
| 换台机器成功率骤降 | 分辨率/缩放/DPI 环境差异 | 跨机对比命中率 | 固定显示尺寸、环境标准化 | 单一固定环境影响小 |
| set-of-mark 标号遮住内容 | 叠加标签压住了关键文字 | 密集界面叠标号复现遮挡 | 标号半透明/避让、必要时分区叠 | 稀疏界面影响小 |
| 依赖坐标的脚本改版即崩 | 硬编码绝对坐标 | 界面挪动元素复现点空 | 优先结构化定位、坐标仅兜底 | 绝对静态界面短期可用 |

## 思考：为什么说 set-of-mark 和结构化定位比「让模型直接吐坐标」更工程友好？

### 回答

因为它们把「高精度回归」问题转化成了「低精度选择」问题，从根上降低了出错概率和对分辨率的敏感度。让模型直接吐像素坐标，本质是要它在连续的二维空间里做精确回归——目标越小、屏幕越大、缩放越狠，命中窗口越窄，且必须外接一套严丝合缝的坐标回缩逻辑，任何一环（声明尺寸、缩放比、长宽比、DPI）对不齐都会整体点偏。而 set-of-mark 把候选元素离散成有限编号，模型只需在「几个选项里挑一个」，这是它更擅长的分类任务，且编号到真实坐标的映射由运行时精确维护，模型再也碰不到缩放。结构化定位更进一步：连截图都不必依赖，直接用 DOM/无障碍树的元素引用点击，既精确又省 token（不用传大图）还稳定（元素挪位置了，按 role+name 照样能找到）。工程上的取舍是：能拿到结构就用结构，拿不到结构（canvas、图片、自绘控件、桌面软件）就用 set-of-mark 加固，最后才退回纯像素并配严格回缩。这也是为什么成熟的浏览器 Agent 大多以结构化为主、视觉为辅。

### 面试精简表达

直接吐坐标是连续空间的高精度回归，对目标大小、分辨率、缩放极敏感且要外接回缩逻辑；set-of-mark 把它降级成选编号（分类），结构化定位直接用元素引用绕开坐标，二者更稳、更省、更抗界面变化。

## 优化前后对比：从「换屏就崩」到「跨环境稳定」

优化前，团队的定位链路是：截图缩到 1280×800 → 模型吐坐标 → 直接点。这条链路在测试机上恰好因为「测试机本就是 1280×800、缩放比为 1」而侥幸跑通，一上高分屏就暴露了「坐标系不对齐」的致命缺陷——这是典型的「在特殊环境下侥幸通过、换环境即崩」的隐蔽 bug。

优化分三步落地。第一步先止血：统一「声明的显示尺寸 = 缩放后尺寸」，并在执行器点击前强制把模型坐标按 `真实尺寸 / 声明尺寸` 回缩，跨机命中率立刻回到 75% 以上。第二步做加固：对关键的写操作按钮（保存、提交）改用 set-of-mark，运行时先用无障碍信息给这些按钮叠编号，模型只选编号，把这几步的命中率拉到 95%+。第三步治本：网页部分整体切到结构化定位（第 6 节），彻底摆脱缩放。每一步都用「跨三台不同分辨率机器的命中率」做回归验收，确保不再出现「换屏就崩」。这个顺序的逻辑是——先对齐坐标系止血，再对高危步加固，最后从架构上消灭坐标依赖。
