## 真实问题

补录报销单立项时，方案评审会上吵了起来。运维负责人拍板：「这不就是 RPA 吗？我们财务早就用 UiPath 跑对账了，直接录一遍回放不就行了，为什么要上什么大模型 Agent，又贵又不靠谱？」

这个质疑很合理，也很致命。团队真的先用 RPA 试了一版：录制「点新建→填金额→点保存」的固定脚本。头两天跑得挺好，第三天全崩了——那个老系统做了次小改版，「新建」按钮从左上角挪到了右上角，脚本还照着旧坐标点，点了个空；更糟的是改版顺带加了个「请阅读新版报销制度」的弹窗，脚本剧本里压根没这一幕，直接卡死。财务同事吐槽：「这脚本比我还娇气，网站打个喷嚏它就趴下。」这场翻车，恰好把 Computer Use 和 RPA 的本质区别摆上了台面，也是面试高频题。

## 原理：录制回放 vs 每步重看

传统 RPA（Robotic Process Automation，机器人流程自动化，如 UiPath、Automation Anywhere）本质是**录制—回放**：人先手把手演示一遍流程，工具记录下「在坐标 X 点击、在元素 Y 输入」的固定脚本，之后机械重放。核心特征是**基于固定规则和精确定位**。它的死穴也正在于此——**极度脆弱**：

- 界面改版、按钮挪位 → 脚本点空，流程崩溃；
- 弹出没预料到的对话框 → 脚本卡死，剧本里没这一幕；
- 换了分辨率、语言、字体 → 定位失效。

RPA 工程师有个共识：**「维护 RPA 脚本的成本，往往超过当初开发它的成本。」** 因为界面一直在变，脚本永远在追着修。

Computer Use Agent 的根本不同，是它**每一步都重新看屏幕、重新理解、重新决策**（第 2 节的操作循环），而不是回放固定脚本。这带来了 RPA 梦寐以求的**适应性**：

- 按钮挪位置了？模型这一帧重新看，还能认出「新建」在哪；
- 冒出意外弹窗？模型能看懂「这是个制度提示框」，决定先关掉再继续；
- 没有明确剧本的模糊任务（「找到最便宜的机票并下单」）也能处理，因为它靠**理解目标**而非**回放步骤**。

## 现象与输入

把「改版后一个跑崩、一个跑通」拆成可观测的输入，差异一目了然：
```text
改版后的登录页：
  - "登录"按钮从旧坐标 (300,400) 挪到了新坐标 (500,450)
  - 首次访问弹出一个"接受Cookie"框在 (640,300)  ← 剧本外的意外

RPA 回放旧脚本：
  点旧坐标 (300,400) -> 那里已无元素 -> 点空
  剧本里没有"cookie 框"这一幕 -> 无分支可走 -> 流程崩溃

Computer Use 每帧重看：
  第1帧看到 cookie 框 -> 理解"这是意外弹窗" -> 先点 (640,300) 关掉
  第2帧重新看 -> 认出登录按钮已在 (500,450) -> 点它 -> 登录成功
```
## 最小可运行演示

下面用一个 mock 的「改版页面」（按钮挪位 + 意外弹窗），让 RPA 回放和 Computer Use 各跑一遍，看差异。它不联网、不需要 API Key。
```python
from __future__ import annotations


class ChangedPage:
    """改版后的页面：按钮挪了位置，且首次访问会弹 cookie 框。"""
    def __init__(self):
        self.cookie_shown = True
        self.login_button = (500, 450)       # 改版后的新坐标
        self.logged_in = False

    def elements(self) -> dict:
        # 每帧"重新截图"能看到的可交互元素
        els = {}
        if self.cookie_shown:
            els["接受Cookie"] = (640, 300)
        if not self.logged_in:
            els["登录"] = self.login_button
        return els

    def click_at(self, x, y) -> str:
        if self.cookie_shown and (x, y) == (640, 300):
            self.cookie_shown = False
            return "关闭了 cookie 框"
        if not self.cookie_shown and (x, y) == self.login_button:
            self.logged_in = True
            return "登录成功"
        return "点空（无元素）"


def rpa_replay(page: ChangedPage) -> str:
    """RPA：回放旧脚本——直接点旧坐标 (300,400)，剧本里没有 cookie 这一幕。"""
    result = page.click_at(300, 400)         # 旧坐标，已失效
    return f"RPA 回放旧坐标(300,400) -> {result}；剧本无 cookie 分支 -> 流程崩溃"


def computer_use(page: ChangedPage) -> str:
    """Computer Use：每帧重看元素，先处理意外弹窗，再按新位置点登录。"""
    log = []
    for _ in range(5):                       # 带步数上限
        els = page.elements()                # 重新"截图"识别
        if "接受Cookie" in els:              # 看懂意外弹窗，先处理
            x, y = els["接受Cookie"]
            log.append("看到意外 cookie 框 -> " + page.click_at(x, y))
            continue
        if "登录" in els:                    # 按识别到的新位置点
            x, y = els["登录"]
            log.append(f"识别到登录按钮@{ (x, y) } -> " + page.click_at(x, y))
            continue
        break
    log.append(f"最终登录状态={page.logged_in}")
    return "Computer Use：\n    " + "\n    ".join(log)


def run() -> None:
    print(rpa_replay(ChangedPage()))
    print()
    print(computer_use(ChangedPage()))


if __name__ == "__main__":
    run()
```
保存为 `rpa_vs_cua.py`，运行 `python rpa_vs_cua.py`。完整预期输出：
```text
RPA 回放旧坐标(300,400) -> 点空（无元素）；剧本无 cookie 分支 -> 流程崩溃

Computer Use：
    看到意外 cookie 框 -> 关闭了 cookie 框
    识别到登录按钮@(500, 450) -> 登录成功
    最终登录状态=True
```
这段对比把差异钉死：`rpa_replay` 只会点死记的旧坐标，遇到挪位和弹窗就废；`computer_use` 每轮 `page.elements()` 重新「看」当前有哪些元素，因此能先处理意外的 cookie 框、再按识别到的新位置点登录。注意 `computer_use` 里那个 `for _ in range(5)` 步数上限——即便是「随机应变」的 Agent，也必须有硬上限防死循环（回扣第 2 节铁律三）。

## 真实系统对应

**官方公开机制**：OpenAI 在 CUA / Operator 发布材料里明确「训练模型像人一样与图形界面交互」，并强调它能处理此前需要为每个网站定制脚本的任务 [来源](https://openai.com/index/computer-using-agent/)；Anthropic 的 Computer use 也是「看截图→出动作」的实时决策而非回放 [来源](https://platform.claude.com/docs/en/agents-and-tools/tool-use/computer-use-tool)。**通用工程模式**：「每步重新感知、临场决策」对界面变化的适应性，是 Computer Use 相对 RPA 的结构性优势。**教学参考实现**：上面的 `ChangedPage` 只为对比两种策略，真实 RPA 工具有更复杂的元素选择器与容错，真实 Computer Use 的「看懂弹窗」由多模态模型完成，不是查字典。

需要点明边界：现代 RPA 工具也在融合 AI（如加入视觉识别、异常处理），并非只有最原始的坐标回放；本节对比的是「纯录制回放」这一经典范式与「每步重新理解决策」这一新范式的机制差异，不是对某款具体产品的全面评价。

## 生产踩坑

| 症状 | 根因 | 如何观测与复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| 界面小改版脚本就崩 | RPA 硬编码坐标/选择器 | 挪动按钮位置复现点空 | 稳定任务仍用 RPA 但加监控告警 | 十年不变的界面影响小 |
| 意外弹窗导致卡死 | 剧本无异常分支 | 注入未预期对话框复现 | Computer Use 临场处理或 RPA 加兜底分支 | 全封闭受控界面较少弹窗 |
| 盲目用 CUA 替换稳定 RPA | 忽视单次成本与稳定性 | 对高频任务算 CUA 单次成本 | 稳定高频保留 RPA | 长尾多变任务另议 |
| CUA 处理稳定任务反而不稳 | 引入了模型随机性 | 同一稳定流程多跑看波动 | 稳定任务不该上 CUA | 需判断/多变任务才用 CUA |
| 期望 CUA 零维护 | 误以为适应性=永不出错 | 长期跑统计失败分布 | 配监控、关键步校验、人工兜底 | 短期演示可暂不配 |

## 思考：Computer Use 和 RPA 有什么本质区别？为什么说它们互补而非替代？

### 回答

本质区别在「定位与决策的时机」。RPA 是**预先固化**：开发时就把「点哪个坐标、填哪个字段」写死成脚本，运行时机械回放，不做任何实时判断——所以它在界面不变时又快又稳又便宜（一次运行几乎零推理成本），但界面一变、冒出意外，剧本里没有的它一律应付不了，脆弱且维护成本高。Computer Use 是**运行时决策**：每一步都重新截图、重新理解当前界面、重新决定下一动作——所以它有适应性，能跟上改版、能处理意外弹窗、能执行没有精确剧本的模糊目标，但代价是每步都要多模态推理，更贵、更慢、还带随机性（会犯错）。

说它们互补而非替代，是因为两者的最优场景恰好错开。一个每天跑一万次、界面十年不变的「从固定系统导出报表」任务，RPA 又快又便宜又稳，用 Computer Use 纯属杀鸡用牛刀，还更贵更不稳；反过来，一个「处理各种长得都不一样的供应商网站」的任务，RPA 要为每个站写脚本且天天崩，这才是 Computer Use 的主场。成熟团队的做法是分流：稳定、高频、规则明确的走 RPA；多变、长尾、需判断的走 Computer Use，甚至在一条流程里混用（稳定段用 RPA、易变段用 CUA）。只会说「Computer Use 更先进」而不谈它更贵更不稳，反而显得不成熟。

### 面试精简表达

RPA 是开发时固化脚本、运行时回放，稳但脆、便宜；Computer Use 是每步重新看屏幕临场决策，有适应性但贵且有随机性。二者最优场景错开——稳定高频用 RPA、多变长尾用 CUA，互补而非替代。

### 反例

有团队被「AI 更先进」带节奏，把一个每天跑八千次、界面三年没动的银行对账 RPA 全量换成 Computer Use，结果单次成本涨了几十倍、还因为模型偶发误判引入了对账错误，两周后灰溜溜回滚。教训：**判断该用哪个，看的是任务的稳定性和频率，不是技术的新旧。**
