## 真实问题

补录报销单的试点跑了两周，团队做了次复盘，数据很扎心。单张报销单大约 4 步（新建、填金额、填事由、保存），成功率约 85%，还能接受。但当他们想扩展到「一次性处理一个季度的整套费用报销流程」——涉及登录、筛选、逐项核对、批量提交，约 20 步——成功率暴跌到不足 40%，而且每跑一次要两三分钟、烧掉的图像 token 费用是纯文本任务的几十倍。

产品经理不理解：「单步 85% 挺高的啊，怎么串起来就崩成这样？」这个「单步看着还行、串起来惨不忍睹」的现象，正是 Computer Use 到 2026 年仍未跨过的三道坎——**可靠性（误差累积）、延迟、成本**。这一节把它们量化清楚，这也是面试里「Computer Use 现在能大规模生产用吗」的标准考点。

## 原理：三大局限

### 局限一：可靠性——步数越多，崩得越狠

Computer Use 是**多步串联**过程，每步都可能出错（看错界面、点偏坐标、误判状态），而错误会**沿链路累积放大**。假设每步成功率 95%（已相当乐观），端到端成功率是各步的乘积：
```text
  3 步任务：0.95³  ≈ 86%
 10 步任务：0.95¹⁰ ≈ 60%
 20 步任务：0.95²⁰ ≈ 36%
```
这就是**误差累积**：单步看着挺准，串起来就崩。它解释了为什么 Computer Use 在「点几下就完成」的短任务上尚可，一到「几十步的复杂流程」就急剧劣化。这也和公开基准吻合——OSWorld（一个桌面任务基准）的人类基线约 72.4%，而模型发布时普遍远低于此，直到 2026 年前后靠「多次采样择优」等工程手段才逐步逼近甚至宣称超过人类基线 [来源](https://openai.com/index/computer-using-agent/) [来源](https://www.simular.ai/articles/agent-s3)。

提升端到端成功率的关键工程手段：**缩短任务链、给关键步骤加校验、失败能重试**。其中「关键步重试」效果最显著——如果一步允许重试几次，等效单步成功率大幅提升，端到端成功率会戏剧性回升（下面演示会量化）。

### 局限二：延迟——每一步都要「看图思考」

文本 Agent 调一次 API 是毫秒到秒级；Computer Use 走一步要**截图 → 上传图片 → 多模态推理 → 输出动作 → 执行 → 等界面稳定**，一步动辄数秒。20 步任务跑一两分钟很正常。这个量级决定了它**目前不适合要求实时响应的交互场景**，更适合「后台异步跑批」。

### 局限三：成本——图像 token 很贵

多模态模型处理图像消耗大量 token（一张高分辨率截图可等价上千 token），而 Computer Use **每步都要传一张图**，甚至传历史多张图。成本因此远高于纯文本 Agent。缓解方向：降分辨率、裁剪关注区、少传历史图、能用结构化定位（第 6 节）就别传大图。

三大局限汇总：

| 局限 | 根因 | 量化/表现 | 缓解方向 |
|---|---|---|---|
| 可靠性 | 多步误差累积 | 0.95¹⁰≈60%、0.95²⁰≈36% | 缩短链路、关键步校验、可重试 |
| 延迟 | 每步截图+多模态推理 | 单步数秒、20 步一两分钟 | 异步跑批、结构化省掉部分视觉 |
| 成本 | 图像 token 昂贵且每步都传 | 数十倍于纯文本任务 | 降分辨率、裁剪关注区、少传历史图 |

## 现象与输入

把「单步高、端到端低、重试后回升」拆成可观测的模拟输入：
```text
单步成功率 p=0.95，蒙特卡洛 20000 次：
   3 步：实测≈86%  对照解析 p^3
  10 步：实测≈60%  对照解析 p^10
  20 步：实测≈36%  对照解析 p^20

关键步允许最多重试 2 次后（等效单步成功率≈1-0.05³）：
  10 步：60% -> 接近 100%
  20 步：36% -> 接近 100%
```
## 最小可运行演示

下面用固定种子模拟「每步成功率 p 的 n 步任务」，统计端到端成功率并与解析值 p^n 对照，再演示「关键步重试」如何把成功率提上去。它不联网、不需要 API Key。
```python
from __future__ import annotations
import random


def simulate(p_step: float, n_steps: int, trials: int, seed: int = 42) -> float:
    rng = random.Random(seed)
    ok = 0
    for _ in range(trials):
        success = True
        for _ in range(n_steps):
            if rng.random() > p_step:      # 这一步失败
                success = False
                break
        ok += 1 if success else 0
    return ok / trials


def simulate_with_retry(p_step: float, n_steps: int, trials: int,
                        retries: int = 2, seed: int = 7) -> float:
    """关键步可重试：每步最多再试 retries 次，等效单步成功率提升。"""
    rng = random.Random(seed)
    ok = 0
    for _ in range(trials):
        success = True
        for _ in range(n_steps):
            step_ok = any(rng.random() <= p_step for _ in range(retries + 1))
            if not step_ok:
                success = False
                break
        ok += 1 if success else 0
    return ok / trials


def run() -> None:
    p, trials = 0.95, 20000
    print(f"单步成功率 p={p}，蒙特卡洛 {trials} 次：")
    for n in (3, 10, 20):
        emp = simulate(p, n, trials)
        ana = p ** n
        print(f"  {n:>2} 步任务：实测≈{emp:.2%}  解析 p^{n}≈{ana:.2%}")
    print("结论：步数越多，端到端成功率指数级下滑（误差累积）")

    print("\n关键步加校验重试（每步最多重试 2 次）后：")
    for n in (10, 20):
        base = simulate(p, n, trials)
        better = simulate_with_retry(p, n, trials, retries=2)
        print(f"  {n:>2} 步：{base:.2%} -> {better:.2%}")


if __name__ == "__main__":
    run()
```
保存为 `reliability.py`，运行 `python reliability.py`。完整预期输出：
```text
单步成功率 p=0.95，蒙特卡洛 20000 次：
   3 步任务：实测≈85.58%  解析 p^3≈85.74%
  10 步任务：实测≈59.90%  解析 p^10≈59.87%
  20 步任务：实测≈35.44%  解析 p^20≈35.85%
结论：步数越多，端到端成功率指数级下滑（误差累积）

关键步加校验重试（每步最多重试 2 次）后：
  10 步：59.90% -> 99.93%
  20 步：35.44% -> 99.77%
```
这段输出把误差累积和重试的威力量化到位：实测值与解析式 `p^n` 高度吻合（验证了「乘积」模型）；而给每步加最多 2 次重试后，等效单步成功率从 0.95 提升到约 `1-0.05³≈0.99988`，20 步端到端成功率从 36% 飙到近 100%。这就是为什么「关键步可重试」是 Computer Use 里性价比最高的可靠性手段——**它直接攻击「乘积」的底数**。当然，重试的前提是该步骤幂等或可安全重做（只读操作天然安全，写操作要配幂等键，见第 8 节）。

## 真实系统对应

**官方公开机制**：OpenAI 在 CUA 发布材料里公布 OSWorld≈38.1%、WebArena≈58.1% 等基准与人类基线（OSWorld≈72.4%、WebArena≈78.2%）的差距，并明确 `computer-use-preview` 处于 beta、不建议用于高风险或全权限场景 [来源](https://openai.com/index/computer-using-agent/) [来源](https://platform.openai.com/docs/guides/tools-computer-use)；Simular 公布 Agent S3 在 OSWorld≈72.6%、宣称首次超过人类基线，且依赖「宽度扩展/多次采样」 [来源](https://www.simular.ai/articles/agent-s3)。**通用工程模式**：误差累积的乘积模型、关键步重试、缩短链路、异步跑批，都是可迁移的可靠性/成本工程。**教学参考实现**：上面的蒙特卡洛把「每步独立同分布」理想化了，真实任务里步骤成功率不均、错误会传染（一步错导致后续更易错），实际下滑可能比 `p^n` 更陡。

需要点明边界：基准分数会随模型迭代快速变化，且不同基准（桌面 OSWorld vs 网页 WebArena）、不同评测条件（步数上限、采样次数）差异极大，不能拿一个数字下「Computer Use 已经/还没到位」的绝对结论；正确姿势是**在你自己的任务分布上实测**，把基准分只当作「现实标尺」而非承诺。

## 生产踩坑

| 症状 | 根因 | 如何观测与复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| 长任务成功率断崖下跌 | 多步误差累积 | 逐步加长任务链看成功率曲线 | 拆短链路、关键步重试与校验 | 3 步内短任务影响小 |
| 重试反而造成重复副作用 | 对非幂等写操作盲目重试 | 让提交步骤重试复现双提交 | 只重试幂等步、写操作配幂等键 | 只读步骤重试安全 |
| 交互场景等待体验差 | 每步秒级延迟 | 前台等它跑 20 步计时 | 改异步跑批、进度反馈 | 后台批处理可接受 |
| 账单暴涨 | 每步传高清历史图 | 统计单任务图像 token | 降分辨率、裁关注区、少传历史图、结构化 | 极少步任务影响小 |
| 拿基准分当生产承诺 | 忽视评测条件差异 | 对比不同步数/采样下的分数 | 在自有任务分布上实测 | 内部窄任务可另定阈值 |
| 靠加大采样硬堆成功率 | 只提成功率不看成本 | 统计 best-of-N 的成本倍数 | 权衡成功率与成本、设预算上限 | 高价值低频任务可接受 |

## 思考：面试官问「Computer Use 现在能大规模生产用吗」，怎么答才成熟？

### 回答

答案是「分场景，且要用数据说话」，而不是一句「能」或「不能」。先亮三大约束并量化：可靠性受多步误差累积制约，单步 95% 的乐观假设下，10 步就掉到约 60%、20 步约 36%（能当场算出 `0.95^n` 就非常加分）；延迟是每步秒级，长任务要一两分钟；成本因每步传图像 token 而远高于纯文本。再给现实标尺：到 2026 年，通用桌面基准 OSWorld 的人类基线约 72.4%，模型靠工程手段才刚摸到甚至宣称略超，说明「闭眼交给它」还不成熟。然后给出「什么场景能用」的判断：**低频、可容忍延迟、有人工兜底、任务链短或关键步可幂等重试**的场景可以上，比如后台批量数据搬运、探索性 UI 测试；反之，**高频实时、零容错、关键路径**的场景现在不该用。最后点出提升手段：拆短链路、关键步校验与重试（直接攻击乘积底数，最有效）、能结构化定位就别纯视觉（省成本又提精度）、多次采样择优（但要算成本账）。这样从「量化约束→现实标尺→场景判断→提升手段」四层展开，既显示你懂原理，又显示你有生产判断力。

### 面试精简表达

分场景：可靠性 0.95^n 指数衰减（10 步≈60%）、延迟秒级、成本高，2026 年 OSWorld 才刚摸到人类基线。适合低频、可容忍延迟、有人工兜底、关键步可幂等重试的任务；不适合高频实时零容错关键路径。提升靠拆短链路、关键步重试、结构化定位。

## 事故回放：20 步季度报销为何崩到 40%

回到开头的季度报销任务。20 步、单步约 95%，理论端到端 `0.95²⁰≈36%`，实测 40%——基本吻合。团队起初想「换个更强的模型把单步提到 98%」，但 `0.98²⁰≈67%` 仍不理想，且更强模型更贵更慢，性价比低。

真正见效的是三招组合。第一招拆短链路：把「一个 20 步大任务」拆成「登录（一次）+ 每张单据独立 4 步子任务」，子任务成功率 `0.95⁴≈81%`，且子任务之间解耦，一张失败不影响其他。第二招关键步重试：对「填金额」「点保存」这两个关键步加校验（填完读回来核对）+ 最多重试 2 次，把这两步的等效成功率拉到 99.9%+。第三招失败可续跑：把已完成的单据记账，中断后从断点续跑而非从头重来。三招下来，季度报销的整体完成率（允许少量单据转人工）回到 90% 以上，成本也因拆短、少传历史图而下降。这个复盘的核心教训是——**对付误差累积，「拆短 + 关键步重试」比「换更大模型」性价比高得多，因为它直接攻击乘积结构，而非线性地提一点单步概率。**
