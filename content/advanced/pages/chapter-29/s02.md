## 真实问题

补录报销单的第二次试验，暴露了一个更隐蔽的坑。工程师把循环写成了「截一次图，让模型一口气规划出全部步骤，然后挨个执行」——就像人先看一眼屏幕，然后闭着眼睛把后面的点击全做完。结果第一步点「新建」成功，第二步就错位了：因为点了「新建」后弹出的是一个**新的对话框**，屏幕早已不是最初那张截图，模型却还在照着旧截图规划的坐标去点，自然全崩。

改成「每点一步就重新截一次图、重新让模型看当前屏幕再决定下一步」后，成功率立刻上来了。但新问题又冒出来：有时点完「保存」立刻截图，截到的是「保存中…」的加载态转圈画面，模型误判成「按钮没反应」，又点了一次，结果**提交了两张重复报销单**。这两个坑——**必须每步重新观察**和**必须等界面稳定再观察**——正是 Computer Use 操作循环的两条命脉。

## 原理：把 ReAct 循环搬到图形界面

Computer Use 的本质，是把第 4 章的 ReAct（Reasoning and Acting，推理并行动）循环搬到了**图形界面**上。区别在于：观察不再是工具返回的 JSON，而是一张**屏幕截图**；动作不再是调用 API，而是**鼠标点击、键盘输入、滚动**这些底层操作。OpenAI 官方把这个过程描述为一个「持续循环」：工具发出像 `click(x,y)` 或 `type(text)` 的动作，你的代码在计算机或浏览器环境里执行，再把结果截图送回模型，模型据此理解环境状态并给出下一个动作 [来源](https://platform.openai.com/docs/guides/tools-computer-use)。

把循环拆成五个阶段：
```text
     ┌──────────────────────────────────────────────┐
     │                                              │
     ▼                                              │
 ① 截图 (Observe)   把当前屏幕状态截成一张图            │
     │                                              │
     ▼                                              │
 ② 理解 (Perceive)  多模态模型看图：现在是什么界面？     │
     │              目标元素在哪？                    │
     ▼                                              │
 ③ 决策 (Decide)    下一步做什么？                     │
     │              (点击/输入/滚动/等待/结束)          │
     ▼                                              │
 ④ 定位 (Ground)    把"点保存"翻译成具体坐标             │
     │              action = click(x=1160, y=640)   │
     ▼                                              │
 ⑤ 执行 (Act)       驱动鼠标/键盘真正操作 ──────────────┘
                    然后回到 ① 重新截图看结果
```
把它压成三条必须刻进脑子的铁律：

- **铁律一：每一步都重新截图。** 界面状态在变——上一步点了按钮，这一步的画面已经不同。Computer Use 主要靠「重新看当前屏幕」推进，而非像文本 Agent 那样靠「上下文累积」。
- **铁律二：观察前必须等界面稳定。** 界面是异步渲染的，点完按钮页面可能还在加载，立刻截图会看到「过渡态」，导致误判、重复操作。
- **铁律三：必须有硬步数上限。** GUI 操作出错时特别容易陷入死循环（反复点一个点不动的按钮），没有上限就是灾难。

## 现象与输入

把补录报销单的循环拆成可观测的状态推进，就能看清「重新观察」如何驱动流程：
```text
step1 观察 state=empty          -> 决策 click(300,200)  点"用户名/申请人"框
step2 观察 state=focus_username -> 决策 type "alice"    输入内容
step3 观察 state=typed          -> 决策 click(300,400)  点"登录/保存"按钮
step4 观察 state=logged_in      -> 决策 done            自然终止

关键：每一行的"观察 state=..."都不同——正是"重新截图"看到了状态变化，
才让模型能做出正确的下一步决策。若沿用 step1 的旧截图，step2 起全错。
```
## 最小可运行演示

下面用一个 mock 的「环境」（两步表单）+ 确定性「模型」，走完截图→理解决策→定位→执行→再截图的完整闭环，含 `max_steps` 硬上限与 `done` 自然终止。它不联网、不需要 API Key。
```python
from __future__ import annotations
from dataclasses import dataclass, field


@dataclass
class Action:
    type: str                 # click / type / done
    x: int = 0
    y: int = 0
    text: str = ""


class MockEnv:
    """两步表单：先点"用户名框"并输入，再点"登录"按钮，状态推进。"""
    def __init__(self):
        self.state = "empty"          # empty -> focus_username -> typed -> logged_in
        self.username_box = (300, 200)
        self.login_button = (300, 400)

    def screenshot(self) -> dict:
        # 返回"可观测状态"，模拟一张截图
        return {"state": self.state,
                "username_box": self.username_box,
                "login_button": self.login_button}

    def click(self, x, y):
        if (x, y) == self.username_box and self.state == "empty":
            self.state = "focus_username"
        elif (x, y) == self.login_button and self.state == "typed":
            self.state = "logged_in"

    def type_text(self, text):
        if self.state == "focus_username":
            self.state = "typed"


class ScriptedModel:
    """确定性模型：看当前截图的 state，决定下一个动作。"""
    def decide(self, shot: dict) -> Action:
        s = shot["state"]
        if s == "empty":
            x, y = shot["username_box"]
            return Action("click", x, y)
        if s == "focus_username":
            return Action("type", text="alice")
        if s == "typed":
            x, y = shot["login_button"]
            return Action("click", x, y)
        return Action("done", text="已登录成功")


@dataclass
class Agent:
    env: MockEnv
    model: ScriptedModel
    max_steps: int = 10
    trace: list = field(default_factory=list)

    def run(self) -> dict:
        for step in range(1, self.max_steps + 1):
            shot = self.env.screenshot()                       # ① 观察：截图
            action = self.model.decide(shot)                   # ②③ 理解+决策
            self.trace.append(
                f"[S{step}] 观察 state={shot['state']:<14} -> 决策 {action.type}"
                + (f"({action.x},{action.y})" if action.type == "click" else "")
                + (f" '{action.text}'" if action.type == "type" else ""))
            if action.type == "done":                          # 自然终止
                self.trace.append(f"[S{step}] 任务完成：{action.text}")
                return {"status": "success", "steps": step}
            self._execute(action)                              # ④⑤ 定位+执行
        return {"status": "max_steps_reached", "steps": self.max_steps}

    def _execute(self, a: Action):
        if a.type == "click":
            self.env.click(a.x, a.y)
        elif a.type == "type":
            self.env.type_text(a.text)


def run() -> None:
    agent = Agent(MockEnv(), ScriptedModel())
    result = agent.run()
    print("\n".join(agent.trace))
    print("RESULT:", result)


if __name__ == "__main__":
    run()
```
保存为 `loop.py`，运行 `python loop.py`。完整预期输出：
```text
[S1] 观察 state=empty          -> 决策 click(300,200)
[S2] 观察 state=focus_username -> 决策 type 'alice'
[S3] 观察 state=typed          -> 决策 click(300,400)
[S4] 观察 state=logged_in      -> 决策 done
[S4] 任务完成：已登录成功
RESULT: {'status': 'success', 'steps': 4}
```
这段轨迹逐行对应五阶段循环：每个 `[S*]` 都先 `screenshot()`（①）再 `decide()`（②③），然后 `_execute()`（④⑤）驱动状态推进。注意 `ScriptedModel.decide` **只看当前 `state`**，不看历史——这正是「每步重新观察」的体现。把 `MockEnv` 换成真实的截图执行器、把 `ScriptedModel` 换成真实多模态客户端，主循环骨架一行都不用改，这就是操作循环抽象的价值。

## 真实系统对应

**官方公开机制**：OpenAI 把 CUA 循环明确列为五步——发请求（含 `computer` 工具与显示尺寸）→收到 `computer_call`（含建议动作）→执行动作→截图捕获新状态→把截图作为 `computer_call_output` 发回并重复，直到模型不再请求动作 [来源](https://platform.openai.com/docs/guides/tools-computer-use)；Anthropic 的 Computer use 同样是「模型看截图 → 返回鼠标键盘动作 → 执行 → 再截图」的循环，动作包括 `screenshot`、`left_click`、`type`、`key` 等 [来源](https://platform.claude.com/docs/en/agents-and-tools/tool-use/computer-use-tool)。**通用工程模式**：把「观察—决策—执行—再观察」抽象成带步数上限的主循环，是可迁移到任何厂商的骨架。**教学参考实现**：上面的 `MockEnv` / `ScriptedModel` 只为演示控制流，不代表任何产品的推理逻辑。

需要点明边界：真实系统的「截图」是一张 PNG 图片经 base64 编码后传给模型（OpenAI 用 `computer_call_output` 里的 `image_url`，Anthropic 用图片内容块），而非本例的字典 `state`；本例用字典只为让状态推进可逐字复核，不代表传输格式。

## 生产踩坑

| 症状 | 根因 | 如何观测与复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| 第二步起坐标全错位 | 只截一次图后闭眼执行 | 让第一步动作触发弹窗后继续复现 | 每步重新截图再决策 | 界面完全静态可简化 |
| 点完立刻截到"加载中"误判 | 未等界面稳定就观察 | 在动作后插 0 延迟截图复现 | 等页面稳定（轮询帧或等元素出现） | 瞬时响应页面影响小 |
| 重复提交/重复下单 | 误判无响应后重复点击 | 让保存接口延迟返回复现双提交 | 等稳定 + 幂等键 + 高危确认 | 只读操作重复无害 |
| 卡死在点不动的按钮 | 无步数上限、无停滞检测 | 让按钮永远无反应复现死循环 | for step in range(max_steps) 兜底 + 相邻帧相同则报警 | 明确短任务可设小上限 |
| 每步都截高清大图烧 token | 未控制截图分辨率 | 统计每步图像 token 消耗 | 降分辨率、裁剪关注区 | 需读小字时另议 |

## 思考：为什么 Computer Use 必须「每步重新截图」，而文本 Agent 靠上下文累积就够？

### 回答

根源在于两者的「世界状态」表示方式不同。文本 Agent 的世界是一段可累积的对话历史：每次工具调用的结果都是文本，追加到上下文里，模型看着完整历史就能推进，过去的信息不会「过期」。而 Computer Use 的世界是一块**不断被覆盖的屏幕**：上一步点了按钮，屏幕就变了，之前那张截图描述的状态已经作废——你不能靠「累积旧截图」推理当前该点哪，因为当前长什么样只有重新截图才知道。更关键的是，GUI 操作有大量模型无法预判的副作用：一次点击可能弹出对话框、跳转页面、触发动画，这些都不是模型「想」出来的，必须「看」到。所以 Computer Use 的循环是「感知驱动」的——每步先重新感知真实世界，再决策；而文本 Agent 更接近「记忆驱动」。这也解释了为什么「等界面稳定再截图」是刚需：如果在过渡态截图，等于给模型看了一张「假的当前状态」，决策必然出错。

### 面试精简表达

文本 Agent 的世界是可累积的对话历史，旧信息不过期；Computer Use 的世界是不断被覆盖的屏幕，旧截图立刻作废，且点击有不可预判的副作用，只能每步重新截图感知真实状态。

### 反例

有人为了省 token，把「每步截图」改成「让模型一次规划 5 步后连续执行」。这在界面绝对静态时偶尔能跑通，但只要中间任何一步触发了非预期的界面变化（弹窗、跳转、报错），后 4 步就全部对着一张过期截图操作，轨迹彻底崩坏——而且因为没有中途观察，你连它在哪一步开始错的都不知道。这就是为什么「批量规划」是 Computer Use 的反模式。

## 事故回放：两张重复报销单是怎么来的

回到开头。执行器点完「保存」后，代码里写的是 `time.sleep(0.3)` 就截图。但那台老系统的保存接口平均要 1.2 秒才返回，于是 0.3 秒时截到的是「保存中…」转圈画面。模型看到「按钮还在、没有成功提示」，合理地判断「上次点击没生效」，于是又点了一次保存——两次点击都被后端接受，生成了两张金额相同的报销单。

复盘后修复分三层：其一，把「傻等固定秒数」改成「等界面稳定」——轮询截图，直到相邻两帧的关注区基本一致，或直到「保存成功」提示出现，才认为界面稳定可观察；其二，给保存这类写操作加幂等键（回扣第 8 章），后端识别到同一业务意图的重复提交直接去重；其三，把「保存」列为高危动作，执行前过一道确认护栏（见第 8 节）。优化前只有一句「偶发重复报销单」的模糊报障；优化后，每一步都有「观察到的界面状态 + 等待了多久 + 是否稳定」的可追溯记录，重复提交从根子上被堵住。这三层恰好对应 Computer Use 循环里「观察时机」「执行副作用」「高危拦截」三个最容易埋雷的位置。
