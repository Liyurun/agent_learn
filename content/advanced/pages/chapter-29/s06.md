## 真实问题

报销单项目里有一半任务其实发生在**浏览器**里：从几个供应商的报销门户网站上抓发票、核对金额。团队一开始沿用了通用 Computer Use 那套「截图→纯视觉定位坐标→点击」的方案，结果又贵又慢又不稳——每一步都要传一张高清网页截图（图像 token 很贵），模型还经常在密集的表格里点错单元格。

一位做过前端的同事提醒：「网页又不是一张图，它有 DOM（Document Object Model，文档对象模型）啊，每个按钮、输入框都是结构化的元素，为什么要让模型盯着像素猜坐标？」团队切到基于浏览器无障碍树（Accessibility Tree）的方案后，效果立竿见影：不再传大图（省 token）、按元素的角色和名字精确点击（不再点错）、界面小改版也能靠语义找到元素（更稳）。这揭示了一条重要工程分野：**浏览器场景有结构可用，就不该退回纯像素**。

## 原理：结构化定位为什么在浏览器里更优

通用桌面 Computer Use 被迫走纯视觉（桌面软件常拿不到可靠结构），但**浏览器是个特例**：每个网页都有 DOM 和无障碍树——一个结构化、层级化的 UI 表示，和屏幕阅读器（screen reader）给视障用户用的是同一套，含元素的角色（button、link、textbox）、名字、状态和父子关系 [来源](https://playwright.dev/)。这带来三重优势：

- **省 token**：给模型一段文本化的无障碍快照，比传一张高清截图便宜得多；
- **精确稳定**：按 `role=button, name=保存` 定位，不受分辨率/缩放影响，按钮挪位置也照样找得到；
- **LLM 友好**：文本结构可直接读，无需视觉模型逐像素解析。

但结构化不是万能的。有些内容拿不到可用结构——`<canvas>` 自绘图形、图片里的按钮、自定义渲染的控件、验证码——这时只能退回纯视觉坐标。所以业界成熟做法（如 Playwright MCP）是**双模式融合**：**默认用无障碍树的结构化定位，遇到没有可用结构的内容时再切换到视觉模式**（暴露坐标动作、返回截图，代价是更耗 token 且依赖视觉模型）[来源](https://playwright.dev/)。
```text
                    ┌── 有可用结构？ ──┐
   网页当前状态 ────▶│                │
                    ▼                ▼
             是：结构化定位        否：纯视觉兜底
         role=button,name=保存    截图 -> 模型出坐标
         直接拿元素引用点击        (canvas/图片/验证码)
         省token·精确·抗改版      通用但贵·受缩放影响
```
## 现象与输入

把「同一个点登录意图，两种页面走不同路」拆成可观测输入：
```text
DomPage（普通网页，有无障碍树）：
  tree = [ {role:textbox,name:用户名}, {role:textbox,name:密码},
           {role:button, name:登录} ]
  -> 融合定位器查到 role=button,name=登录 -> 拿到元素引用 e21 -> 结构化点击（稳）

CanvasPage（自绘 canvas，无结构）：
  拿不到 tree，只有像素
  -> 融合定位器退回视觉，模型定位"登录按钮" -> (612,430) -> 像素点击（兜底）
```
## 最小可运行演示

下面写一个「融合定位器」：能拿到结构就用结构，拿不到再退回纯视觉。它不联网、不需要 API Key。
```python
from __future__ import annotations


class DomPage:
    """普通网页：有无障碍树（accessibility tree），元素可按 role+name 命中。"""
    kind = "dom"
    tree = [
        {"role": "textbox", "name": "用户名", "ref": "e12"},
        {"role": "textbox", "name": "密码", "ref": "e13"},
        {"role": "button", "name": "登录", "ref": "e21"},
    ]

    def query(self, role, name):
        for el in self.tree:
            if el["role"] == role and el["name"] == name:
                return el["ref"]
        return None


class CanvasPage:
    """自绘 canvas 页面：拿不到结构，只有像素。视觉模型给出坐标。"""
    kind = "pixel"

    def vision_locate(self, description):
        # mock 一个视觉模型：把"登录按钮"定位到像素坐标
        table = {"登录按钮": (612, 430)}
        return table.get(description)


class FusionLocator:
    """融合定位器：能拿结构就用结构，拿不到再退回纯视觉。"""

    def locate_login(self, page) -> dict:
        if getattr(page, "kind", None) == "dom":
            ref = page.query("button", "登录")
            if ref:
                return {"strategy": "结构化(DOM/无障碍树)", "target": ref,
                        "note": "精确稳定，不受缩放影响，省 token"}
        # 兜底：纯视觉像素坐标
        xy = page.vision_locate("登录按钮")
        return {"strategy": "纯视觉像素坐标", "target": xy,
                "note": "通用但受分辨率/缩放影响，需回缩坐标"}


def run() -> None:
    loc = FusionLocator()
    for page in (DomPage(), CanvasPage()):
        r = loc.locate_login(page)
        print(f"[{page.kind:>5} 页面] 走「{r['strategy']}」-> 目标={r['target']}  ({r['note']})")


if __name__ == "__main__":
    run()
```
保存为 `browser_locate.py`，运行 `python browser_locate.py`。完整预期输出：
```text
[  dom 页面] 走「结构化(DOM/无障碍树)」-> 目标=e21  (精确稳定，不受缩放影响，省 token)
[pixel 页面] 走「纯视觉像素坐标」-> 目标=(612, 430)  (通用但受分辨率/缩放影响，需回缩坐标)
```
这段输出把「融合」策略钉死：`FusionLocator` 先探测页面是否有结构（`kind == "dom"`），有就用 `role=button, name=登录` 拿元素引用，没有才退回视觉定位。真实系统里，`DomPage.tree` 由 Playwright 抓取的无障碍快照提供，`CanvasPage.vision_locate` 由多模态模型完成——但「结构优先、视觉兜底」的分派逻辑一模一样。

## 真实系统对应

**官方公开机制**：OpenAI 的 CUA 官方指南直接用 Playwright 作为浏览器执行环境示例，给出 `page.mouse.click(x, y)`、`page.keyboard.type(text)` 等动作映射，并建议沙箱化（`chromiumSandbox`、`env={}`、禁扩展/文件系统）[来源](https://platform.openai.com/docs/guides/tools-computer-use)；Playwright 官方提供无障碍树快照能力，是结构化定位的基础 [来源](https://playwright.dev/)。**通用工程模式**：「结构优先、视觉兜底」的融合定位，以及「浏览器 Agent 用 DOM/无障碍树、通用桌面 Agent 才被迫纯视觉」的分野，是可迁移的架构选择。**教学参考实现**：上面的 `DomPage` / `FusionLocator` 只为演示分派逻辑，真实无障碍树远比这复杂（含层级、状态、可见性），需处理隐藏元素、iframe、shadow DOM 等。

需要点明边界：无障碍树的质量取决于网页是否规范（语义化标签、`aria-label` 等）——写得差的页面无障碍信息残缺，结构化定位也会失效，这时仍要靠视觉兜底。所以「结构优先」是**默认策略**而非绝对保证，健壮的浏览器 Agent 必须两条腿走路。

## 生产踩坑

| 症状 | 根因 | 如何观测与复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| 网页任务又贵又慢 | 用纯视觉截图而非结构化 | 统计每步图像 token 消耗 | 默认用无障碍树、视觉兜底 | canvas/图片内容只能视觉 |
| 密集表格点错单元格 | 纯像素在密集布局易偏 | 在数据表里纯视觉点击复现 | 用结构化元素引用定位 | 无结构的自绘表格另议 |
| canvas/验证码定位失败 | 无可用 DOM 结构 | 对 canvas 元素查 DOM 为空 | 切视觉模式或走专门通道 | 规范语义页面不触发 |
| 无障碍树残缺定位不到 | 页面缺语义标签/aria | 对非语义化页面抓快照 | 视觉兜底 + 反馈页面改进 | 规范页面结构完整 |
| 本地浏览器被恶意页攻击 | 未沙箱化裸跑 | 访问恶意页观察越权 | chromiumSandbox+env空+禁扩展/文件系统 | 完全离线可信页风险低 |
| iframe/shadow DOM 找不到元素 | 未穿透嵌套上下文 | 在 iframe 内元素上定位失败 | 递归进入 frame/shadow root | 无嵌套的简单页不触发 |

## 思考：既然纯视觉能操作任何界面，为什么浏览器 Agent 还要费劲用 DOM/无障碍树？

### 回答

因为「能做」和「做得又好又省又稳」是两回事，而浏览器恰好提供了让后者成为可能的结构。纯视觉的通用性是它在桌面软件上的无奈优势——桌面软件常常拿不到可靠结构，只能靠像素。但浏览器不一样：每个网页天然带 DOM 和无障碍树，白白扔掉这份现成的结构化信息、退回让模型盯着像素猜坐标，是三重浪费。第一浪费成本：纯视觉每步都要传高清截图，图像 token 很贵，而无障碍快照是紧凑文本，便宜一个数量级。第二浪费精度：密集表格、小按钮上纯视觉容易点偏，而按 `role+name` 定位是精确命中，还外接一套坐标回缩逻辑（第 3 节）就是额外的出错点。第三浪费稳定性：纯视觉对分辨率、缩放、字体敏感，界面小改版就可能失效，而结构化定位按语义找元素，按钮挪了位置照样点得到。所以对浏览器 Agent，正确姿势是「结构优先、视觉兜底」——默认吃 DOM/无障碍树的红利，只在 canvas、图片、验证码这类真的没有结构的地方才动用昂贵的视觉。这也解释了为什么专门的浏览器自动化方案（Playwright 系）大多以无障碍树为主干，而不是把浏览器当成一块普通屏幕来截图。

### 面试精简表达

浏览器天然有 DOM/无障碍树，用它定位比纯视觉更省 token、更精确、更抗改版；纯视觉是桌面软件拿不到结构时的无奈兜底。浏览器 Agent 应结构优先、视觉兜底，只在 canvas/图片/验证码等无结构处才用视觉。

## 优化前后对比：从「截图猜坐标」到「读结构点元素」

优化前，供应商门户抓发票的链路是：每步截高清网页图 → 传给多模态模型 → 模型吐坐标 → 回缩后点击。一个 15 步的抓取任务，光图像 token 就占了绝大部分成本，且在发票明细表这种密集布局里，模型平均每五次点击就点错一次单元格，抓错金额。

优化切到结构化：用 Playwright 抓取页面无障碍快照，把「发票金额单元格」按其在表格中的角色和文本内容精确定位，直接拿元素引用点击/读取。效果三方面立竿见影——单步不再传大图，token 成本降到零头；按语义精确命中，点错率从 20% 降到近乎为零；供应商门户小改版（挪动列顺序）时，因为是按语义而非坐标定位，脚本无需修改照常跑通。只有极少数嵌在图片里的电子章需要识别时，才临时切到视觉模式。验收用「跨三家不同供应商门户的抓取准确率 + 单任务 token 成本」双指标，确认结构化路径既准又省。这个优化的逻辑是——**浏览器给了你结构这份免费午餐，先把它吃干净，视觉只留给真正没有结构的角落。**
