## 真实问题

补录报销单的第一次试验，卡在了一个反直觉的地方。团队先拿多模态模型做了个「可行性验证」：把系统截图发给模型，问「这是什么页面、有哪些字段」，模型答得头头是道——「这是报销单新建页，有申请人、金额、事由、附件四个字段，右下角有保存按钮」。团队大喜，以为成了。

可真正接上执行器让它「点保存」时，翻车了：模型嘴上说「保存按钮在右下角」，输出的坐标却落在按钮下方 60 像素的空白处，点了个寂寞。连续几十次，模型「描述界面」几乎全对，「说出按钮的精确像素位置」却频频偏移。工程师一度怀疑是执行器有 bug，查了半天才明白：**「能描述屏幕上有什么」和「能精确说出某个元素在哪个像素」，是两种不同的能力**，前者过关不代表后者过关。这道认知鸿沟，是本章第一块地基。

## 原理：视觉理解与 GUI grounding 的分层

多模态 Agent（Multimodal Agent）指能同时理解、处理多种信息形态（文本、图像、音频、视频）的 Agent。对 Computer Use 而言，最关键的模态是**视觉**，而视觉能力要拆成两个递进层次：

- **视觉理解（Visual Understanding）**：给模型一张图，它能描述内容、回答问题、读取文字（光学字符识别，Optical Character Recognition，OCR）。比如「这张发票金额多少」「屏幕上有几个按钮」。这是**被动看懂**——回答的是「有什么」。
- **GUI grounding（Graphical User Interface Grounding，图形界面接地/定位）**：不只看懂图里有什么，还要理解这是一个**可交互界面**，并能把「要点的那个按钮」精确对应到像素坐标 `(x, y)` 或某个具体元素。这是**主动定位到可操作元素**——回答的是「点哪里」。

两层的鸿沟比想象中大。一个模型能准确描述「屏幕上有一个保存按钮」（视觉理解过关），却未必能准确说出「保存按钮的中心在第 1160 列、第 640 行像素」（grounding 可能偏移）。**Computer Use 的成败，很大程度上卡在 GUI grounding 这一层的精度上**——因为操作系统只认坐标，描述得再好，坐标偏了就是点空。
```text
视觉理解：  截图 ──▶ "这是报销单新建页，有 4 个字段和一个保存按钮"   （描述性，回答"有什么"）
                          │
                          ▼
GUI 理解：  截图 ──▶ "保存按钮是右下角那个蓝色矩形，中心坐标 (1160,640)，
                     点它会提交表单"                            （可操作 + 精确定位"点哪里"）
```
## 现象与输入

把「模型描述对了但点偏了」这个现象拆成可观测字段，就能看清两层能力的分离：
```text
输入：一张 1280x800 的报销单截图（含 4 个元素及其真实包围盒）

视觉理解输出（对）：
  "这是购物车/表单页面，包含 1 个标题、1 个输入框、2 个按钮"

GUI grounding 输出（可能偏）：
  目标"结算/保存" -> 若输出 (1160,640) 落在按钮框内 -> 命中
                  -> 若输出 (1065,640) 偏了 95 像素 -> 落到空白处 -> 点空
```
关键在于：视觉理解只要「大致认出有个按钮」就算对，而 grounding 要求坐标**落在按钮的包围盒内部**，容错空间小得多。一旦坐标偏出边界，后续整条操作轨迹就从这一步开始崩塌。

## 最小可运行演示

下面用一个 mock 的「截图」（元素清单 + 各元素真实包围盒）分别跑视觉理解与 GUI grounding，并演示 grounding 偏移几十像素就会点空。它不联网、不需要 API Key。
```python
from __future__ import annotations


SCREENSHOT = {  # mock 截图：每个元素给出角色、可见文字、真实包围盒 (x1,y1,x2,y2)
    "w": 1280, "h": 800,
    "elements": [
        {"role": "text", "name": "购物车（3 件商品）", "box": (60, 40, 520, 90)},
        {"role": "input", "name": "优惠码", "box": (60, 300, 520, 350)},
        {"role": "button", "name": "结算", "box": (1080, 600, 1240, 680)},
        {"role": "button", "name": "清空购物车", "box": (60, 600, 300, 680)},
    ],
}


def describe(shot: dict) -> str:
    """视觉理解：只做被动内容描述。"""
    kinds = {}
    for el in shot["elements"]:
        kinds[el["role"]] = kinds.get(el["role"], 0) + 1
    parts = [f"{n}个{r}" for r, n in kinds.items()]
    return "这是一个购物车页面，包含 " + "、".join(parts)


def center(box):
    x1, y1, x2, y2 = box
    return ((x1 + x2) // 2, (y1 + y2) // 2)


def hit(box, x, y) -> bool:
    x1, y1, x2, y2 = box
    return x1 <= x <= x2 and y1 <= y <= y2


def ground(shot: dict, target_name: str, bias=(0, 0)):
    """GUI grounding：把语义意图翻译成像素坐标。bias 模拟模型的定位偏移。"""
    for el in shot["elements"]:
        if el["name"] == target_name:
            cx, cy = center(el["box"])
            return (cx + bias[0], cy + bias[1]), el["box"]
    raise KeyError(target_name)


def run() -> None:
    print("[视觉理解]", describe(SCREENSHOT))

    # 完美 grounding：坐标落在"结算"按钮内部
    (x, y), box = ground(SCREENSHOT, "结算", bias=(0, 0))
    print(f"[GUI grounding] 目标=结算 -> 输出坐标({x},{y}) 命中={hit(box, x, y)}")

    # 偏移 95 像素：点空，落到相邻区域，后续轨迹全崩
    (x2, y2), box2 = ground(SCREENSHOT, "结算", bias=(-95, 0))
    landed = next((e["name"] for e in SCREENSHOT["elements"]
                   if hit(e["box"], x2, y2)), "空白处")
    print(f"[偏移演示]   目标=结算 -> 输出坐标({x2},{y2}) 命中={hit(box2, x2, y2)}"
          f" 实际落在: {landed}")


if __name__ == "__main__":
    run()
```
保存为 `grounding.py`，运行 `python grounding.py`。完整预期输出：
```text
[视觉理解] 这是一个购物车页面，包含 1个text、1个input、2个button
[GUI grounding] 目标=结算 -> 输出坐标(1160,640) 命中=True
[偏移演示]   目标=结算 -> 输出坐标(1065,640) 命中=False 实际落在: 空白处
```
这段输出把两层能力钉死：`describe` 只要认出「有几个什么」就算视觉理解过关；`ground` 却要求坐标落进包围盒，偏 95 像素就点空。把 `bias` 改成 `(0, 0)` 与 `(-95, 0)`，你能亲眼看到「同一个正确的语义意图，因为定位精度不同，一个命中一个点空」——这正是真实 Computer Use 里最主要的失败来源。

## 真实系统对应

**官方公开机制**：Anthropic 的 Computer use 工具要求模型直接输出坐标动作，如 `left_click` 带 `coordinate: [x, y]`，即模型必须完成从语义到像素的 grounding [来源](https://platform.claude.com/docs/en/agents-and-tools/tool-use/computer-use-tool)；OpenAI 的 CUA（Computer-Using Agent）在官方博客里明确「训练它像人一样与图形界面——按钮、菜单、文本框——交互」，并给出 OSWorld、WebArena 等 grounding 相关基准 [来源](https://openai.com/index/computer-using-agent/)。**通用工程模式**：把「视觉理解」与「GUI grounding」分开评测（描述准确率 vs 点击命中率）是可迁移的评估拆分。**教学参考实现**：上面的 `describe` / `ground` 只为演示两层差异，真实模型的定位由端到端网络完成，不是查包围盒表。

需要点明一个边界：真实模型没有「包围盒查询表」可用，它是从像素直接回归坐标，因此精度受分辨率、缩放、界面密度影响（详见第 3 节坐标缩放）。本节的查表只是把「命中/点空」这个可观测结果显性化，不代表模型内部机制。

## 生产踩坑

| 症状 | 根因 | 如何观测与复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| 描述界面很准但点击总偏 | 只验证了视觉理解，没验 grounding | 分别统计描述准确率与点击命中率 | 用命中率而非描述质量做验收 | 有 DOM 可用时可绕开像素定位 |
| 小按钮/密集工具栏点不准 | 目标包围盒太小，容错空间小 | 缩小按钮尺寸复现点空率上升 | 提高分辨率、放大关注区、用结构化定位 | 大按钮稀疏布局影响小 |
| 认错相邻元素 | 语义相近的元素挨得太近 | 让「保存/另存为」相邻复现误点 | 让模型先复述目标文字再定位 | 元素唯一且间距大时不易发生 |
| 中文/特殊字体 OCR 读错 | 视觉理解层的文字识别偏差 | 用艺术字/低对比文字复现读错 | 提高对比度、必要时取 DOM 文本 | 标准字体清晰截图较稳 |

## 思考：为什么说 GUI grounding 是 Computer Use 的瓶颈，而不是视觉理解？

### 回答

因为二者的容错空间完全不同，而 Computer Use 的每一步都直接依赖 grounding 的精度。视觉理解是「软」判据：模型说「屏幕上有个保存按钮」，就算它对按钮颜色、位置的描述略有出入，也不影响「知道有这么个东西」这个结论——描述是给人看的，人能容忍模糊。而 grounding 是「硬」判据：操作系统只认坐标，模型输出 `(x, y)` 必须落在按钮的包围盒内部，偏出几十像素就是点空，点空后界面没按预期变化，模型下一帧看到的是错误状态，于是决策继续错，整条轨迹从这一步崩塌。更要命的是误差会沿多步链路累积（见第 7 节），单步 grounding 偏差率哪怕只有 5%，几十步下来端到端成功率就掉到很低。所以工程上真正要死磕的，不是「模型能不能看懂界面」（这早就过关了），而是「模型能不能稳定地把意图落成精确坐标」——这正是各家在 OSWorld 上你追我赶的核心战场。

### 面试精简表达

视觉理解是软判据、能容忍模糊；grounding 是硬判据、坐标偏出包围盒就点空且误差沿链路累积。Computer Use 每步都依赖精确坐标，所以卡在 grounding 而非描述。

## 机制推导：为什么「先描述再定位」能提升命中率

一个在实践中反复被验证的技巧是：让模型在输出坐标前，先用文字复述「我要点的是那个写着『保存』的蓝色按钮，它在表单右下角」。这看似多此一举，实则有机制依据。让模型显式生成对目标的文字描述，等价于第 4 章讲的思维链（Chain-of-Thought，CoT，逐步推理）在视觉定位上的应用——它把「一步到位从像素回归坐标」拆成了「先锁定语义目标、再定位其像素位置」两个子步骤，降低了单步的认知负荷。

由此推出两条工程结论。其一，**动作描述里带上目标的可见文字（label）比只给坐标更稳**：Anthropic 和 OpenAI 的动作结构都允许附带对目标的文字说明，利用这一点能让定位更可控。其二，**当界面提供结构化信息时应优先用它绕开纯像素定位**：网页的 DOM、桌面的无障碍树（Accessibility Tree）能直接给出元素的语义和位置，用它们做 grounding 比让模型「盯着像素猜坐标」稳得多——这条会在第 3、第 6 节被反复用到。
