## 真实问题

一个团队的 Demo 惊艳全场：一个能自动处理报销单的 Agent，从 OCR（Optical Character Recognition，光学字符识别）读票、抽字段、查预算、写审批意见，一气呵成。管理层拍板上线。三周后，财务发来一封措辞不太好看的邮件：这个月自动处理的报销单里，约有八分之一在某个环节出了错——有的把餐费归成了差旅，有的审批意见引用了错误的预算科目，还有的干脆卡在中途没有产出。奇怪的是，团队单独测每一个环节，成功率都在 95% 以上。

问题出在哪？出在**没有人把每一步的成功率乘起来**。这是「不该用 Agent（或不该把链路拉这么长）」的最典型信号：**当一个任务由多个必须全对的步骤串成、而每步都有一定失败概率时，整体成功率会以指数速度崩塌**。本节讲清「什么时候不该用 Agent」，核心就是这个必须算的数——复合错误率。

## 原理：不该用 Agent 的六个信号

以下信号出现时，你大概率**不需要**一个开放循环的 Agent，而应退回到确定性更强的工作流 [来源](https://www.anthropic.com/engineering/building-effective-agents)：

- **流程可以画成确定的流程图**：步骤固定、可事先画清，就直接写成代码或工作流，不要交给模型即兴发挥。这是第一道、也是最有效的筛子。
- **步数固定且少**：只有两三步的任务，用提示链（Prompt Chaining）即可，开放循环是杀鸡用牛刀。
- **分支可枚举**：所有可能路径都能列举出来，用路由（Routing）比开放 Agent 更可控、更好测。
- **延迟/成本预算紧张**：Agent 的多轮循环会成倍放大延迟与 token 成本，预算紧时它可能直接出局。
- **错误代价高且方差不可容忍**：这是最关键的一点——错误会在多步中累乘，见下文的复合错误。
- **无法评估**：如果你没法判断 Agent 做得对不对，就无法迭代改进，上线即失控。Anthropic 反复强调，能否评估是决定要不要放开自主性的前提之一 [来源](https://www.anthropic.com/engineering/building-effective-agents)。

## 复合错误：一个必须算的数

Agent 的多步循环有一个隐蔽的风险——**误差会累乘**。假设每一步的成功率是 95%，看起来很高，但一个 20 步的任务：
```text
0.95 ^ 20 ≈ 0.36
```
整体成功率骤降到约 **36%**。步数越多，复合错误越致命。这解释了为什么「步骤多、每步都必须对」的任务不适合开放式 Agent，而更适合拆成带校验 gate（关卡）的工作流。开头那批出错八分之一的报销单，正是「单步 95%、链路约八步」的必然结果：`0.95^8 ≈ 0.66`，也就是说约三分之一会在某处出错，其中一部分被下游校验挡住，剩下的就漏成了那「八分之一」。

为什么「加校验 gate」有效？因为它在错误累乘之前就把错误**截断**了——一旦某步校验不通过就重试或回退，不让错误往后传染。这就是工作流（带 gate）常常比开放 Agent 更可靠的数学原因。第 05 节会用完整可运行代码把这条曲线画满整张表；本节先建立直觉。

## 最小可运行演示

先用一段最短的代码建立「复合错误」的生理级警觉：同样的单步成功率，随着步数增加，整体成功率如何崩塌。纯 Python、不联网。
```python
def overall_success(step_success: float, steps: int) -> float:
    """整体成功率 = 单步成功率 的 步数次方（假设各步独立）。"""
    return step_success ** steps


def gate_success(step_success: float, steps: int, gate_every: int) -> float:
    """每 gate_every 步加一道校验 gate（假设 gate 能拦截并重试到成功），
    近似效果是把链路截成若干段，整体成功率取决于最长的一段。"""
    longest_segment = min(gate_every, steps)
    return step_success ** longest_segment


def main() -> None:
    p, steps = 0.95, 20
    print(f"单步成功率={p:.0%}，步数={steps}")
    print(f"无 gate 整体成功率 : {overall_success(p, steps):.0%}")
    print(f"每 4 步一道 gate    : {gate_success(p, steps, 4):.0%}（按最长段近似）")


if __name__ == "__main__":
    main()
```
保存为 `compound_error.py`，运行 `python compound_error.py`。预期输出：
```text
单步成功率=95%，步数=20
无 gate 整体成功率 : 36%
每 4 步一道 gate    : 81%（按最长段近似）
```
`gate_success` 是一个教学化的近似：它假设每道 gate 都能拦住错误并重试到成功，于是把长链路截成若干独立小段，整体只受「最长一段」的复合错误影响。它不是精确模型（真实 gate 也会失败、重试也有成本），但足以说明一个硬道理：**在 20 步链路里每 4 步插一道 gate，整体成功率从 36% 拉回到约 81%**——截断错误传播的收益是巨大的。

## 一个经典判断案例：发票处理为什么不该用 Agent

**场景**：PM 说「我们要做一个 Agent，自动处理上传的发票，抽取金额、日期、供应商等固定字段」。

**分析**：字段是固定的、流程是确定的（抽取 → 校验 → 格式化输出），完全可以画成流程图。它的每一步都不需要模型「自主决定下一步做什么」。

**正确答案**：这是一个 **workflow**（几次固定的 LLM 调用 + 校验），不是循环 Agent。虽然 PM 用了「Agent」这个词，但工程上正确的实现是确定性工作流——更快、更便宜、更可控、更好评估。用第 03 节的三信号一验：信号一「模糊性」直接不满足（路径可画出流程图），到这里就该停手了。

这个案例几乎是面试场景题的标准模板。它的价值在于教你一件事：**需求方用了「Agent」这个词，不代表工程上就该做成 Agent**。你的判断力体现在能顶住措辞、按任务本质选型。

## 真实系统对应

**官方公开机制**：Anthropic 在《Building Effective Agents》中明确主张「**找到满足需求的最简方案，只在必要时才增加复杂度；很多应用根本不需要 Agent，优化单次调用 + 检索/示例通常就够了**」，并把「工作流」列为「任务可预测、追求一致性」时的首选 [来源](https://www.anthropic.com/engineering/building-effective-agents)。这直接支持本节的六个信号。Anthropic 的多智能体博客也从反面补充：**当任务需要所有 Agent 共享同一上下文、或子任务间依赖很强时，多智能体并不适合**，此时更集中的工作流反而更好 [来源](https://www.anthropic.com/engineering/multi-agent-research-system)。**通用工程模式**：「复合成功率 = 单步成功率 ^ 步数」是可靠性工程里串联系统可靠性的经典公式（各步独立假设下），并非 AI 独有。**教学参考实现**：`compound_error.py` 里的 `gate_success` 是刻意简化的近似模型，用于建立直觉，不代表任何生产系统的精确可靠性计算。

## 生产踩坑

| 症状 | 根因 | 如何观测与复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| Demo 通过但上线错误率高 | 只测短链路，忽略复合错误 | 按真实步数算 p^n；用 15-20 步复现 | 压步数或加校验 gate 截断传播 | 短链路且单步极高可不担心 |
| 单步都 95% 整体却常错 | 没把每步成功率乘起来 | 逐步统计成功率后连乘 | 上线前用 p^n 估整体，设门槛 | 各步强相关时公式需修正 |
| 确定流程被做成开放循环 | 需求方说了「Agent」就照做 | 复核能否画出确定流程图 | 顶住措辞，按任务本质选工作流 | 路径确实不可预知的除外 |
| 无法判断 Agent 对错仍上线 | 缺少评估手段 | 检查是否有金标准/评估集 | 先补评估再放开自主性 | 有人工兜底的低风险场景可放宽 |
| 预算紧仍上多轮循环 | 未核算延迟/成本上限 | 记录每次运行轮数与 token | 设预算上限，超限降级 | 高价值任务可另议 |
| 加了 gate 但错误仍穿透 | gate 只记录不拦截 | 注入错误看 gate 是否阻断 | gate 必须能中止/重试/回退 | gate 自身也会失败，需监控 |

## 思考：既然复合错误这么可怕，是不是步数多的任务都不能用 Agent？

### 回答

不是。复合错误的对策有两条，而不是「一律禁用 Agent」：一是**压步数**（把长链路拆成短工作流，或让模型少绕弯路），二是**顶高单步成功率**（更强的模型、更严的工具校验、更好的提示）。更关键的是加**校验 gate 截断错误传播**——在错误累乘之前就拦住它，把一条长链路在数学上切成若干条短链路，整体成功率就只受最长一段影响。所以「步数多」本身不是禁用理由，「步数多 + 每步都必须对 + 无法加 gate 截断」才是。很多真正需要 Agent 的探索型任务，恰恰可以容忍中途试错（走错了回溯即可），它们的「有效步数」并不等于表面轮数。

### 面试精简表达

复合错误不是判 Agent 死刑，而是给出两条工程铁律：要么压步数，要么顶高单步成功率，最有效的是加 gate 把长链路截成短链路。

## 事故回放：一道校验 gate 值多少钱

某电商的「自动改价」链路最初是一个七步的开放循环：读取商品 → 拉竞品价 → 算建议价 → 校验价格区间 → 写库 → 通知 → 记录。单步成功率约 96%，`0.96^7 ≈ 0.75`，也就是每四次改价约有一次会在某步出错。上线后出现过一次严重事故：某步把「竞品价」误当「成本价」，算出了一个远低于成本的建议价，而后续步骤没有独立校验，错误一路穿透写进了库，导致一批商品以亏本价售出了近两个小时。

复盘后，团队没有换更大的模型，而是在「算建议价」和「写库」之间加了一道**确定性校验 gate**：建议价必须落在 `[成本价×1.05, 历史最高价×1.2]` 区间内，否则中止并转人工。这道 gate 是纯规则、不依赖模型，几乎不增加延迟，却把「亏本价穿透」这类错误的传播彻底截断。事故后半年再没出现过同类问题。

这次事故的账很好算：加 gate 前，整条链路的可靠性受七步连乘拖累；加 gate 后，危险动作（写库）之前有一道确定性闸门，错误在这里被拦截而非放大。**一道纯规则的校验 gate，往往比「把模型换大一号」更便宜、更可靠地解决复合错误**——这正是「带 gate 的工作流常胜过开放 Agent」的现实写照。
