## 真实问题

选型会议上，两个方案僵持不下。A 方案说「用工作流，把流程写死，稳」；B 方案说「用 Agent，灵活，未来好扩展」。双方各执一词，最后往往是「谁资历高听谁的」或「先按 Agent 做，反正显得先进」收场。这种拍脑袋的选型，正是第 04 节那批「八分之一出错的报销单」的源头——**决策没有依据一套可复述、可走通的判据，而是依据气氛和职级**。本节把前几节的信号（模糊性、复合错误、可评估性）合并成**一棵可以从上往下顺着走的决策树**，再把树上的每个叶子对应到 Claude Code、OpenAI Agents SDK、LangGraph 等真实系统的公开机制，让选型从「辩论」变成「查表」。

## 原理：把决策清单变成一棵可走通的树

先把前几节的判断整理成一份可操作的决策阶梯（对应第 02 节的自主性光谱）：

| 任务特征 | 推荐方案 | 自主性 |
|---|---|---|
| 单次转换 / 分类 / 抽取 | 单次增强 LLM 调用 | 最低 |
| 固定顺序的多步骤 | 提示链（Prompt Chaining） | 低 |
| 输入可分类、分支可枚举 | 路由（Routing） | 低 |
| 独立子任务可并行 | 并行化（Parallelization） | 中 |
| 子任务需动态分解 | 编排者-工作者（Orchestrator-Workers） | 中高 |
| 需多轮迭代精炼、路径不可预知 | 开放式循环 Agent | 高 |

**决策原则**：从上往下看，选**能满足需求的最上面那一行**。不要一上来就冲到最底行。

表格是「查」的，决策树是「走」的。下面这棵树把第 03、04 节的信号和上表的清单合并成一条可以从上往下顺着走的判断路径：
```text
   任务来了
     │
     ▼
   流程能画成确定的流程图吗？
     ├─ 能 ──▶ 步数是不是固定且少（≤3步）？
     │         ├─ 是 ──▶ 【提示链】
     │         └─ 否 ──▶ 分支能枚举吗？
     │                    ├─ 能 ──▶ 【路由】
     │                    └─ 子任务能并行？──▶ 【并行化】
     │
     └─ 不能（路径不可预知）──▶ 错误代价高 / 无法评估？
                                ├─ 是 ──▶ 慎用！先补评估、加人工 gate
                                └─ 否 ──▶ 子任务需动态分解？
                                           ├─ 是 ──▶ 【编排者-工作者】
                                           └─ 否 ──▶ 【开放式循环 Agent】
```
这棵树的第一个分叉「流程能不能画成流程图」是最关键的**筛子**——它一下就把大部分任务筛到了低自主性那一侧。只有当你诚实地回答「不能，我确实无法预知它要走几步、走哪条路」时，才有资格进入右侧的高自主性区域。而即使进了右侧，也要先过「错误代价 / 可评估性」这道关（呼应第 04 节的两个信号）。

## 最小可运行演示

把这棵决策树写成一个纯 Python 函数：输入任务特征的一组布尔量，输出推荐方案。这个练习能强迫你把模糊的「感觉这任务挺复杂」拆成明确的判据。
```python
"""方案推荐器：把决策树写成代码。保存为 recommend_pattern.py 运行。"""


def recommend_pattern(
    can_draw_flowchart: bool,   # 流程能否画成确定流程图
    steps_fixed_few: bool,      # 步数是否固定且少
    branches_enumerable: bool,  # 分支是否可枚举
    can_parallelize: bool,      # 子任务是否可并行
    needs_dynamic_decompose: bool,  # 是否需要动态分解子任务
    high_error_cost: bool,      # 错误代价是否高
    evaluable: bool,            # 是否可评估
) -> str:
    if can_draw_flowchart:                       # 第一道筛子
        if steps_fixed_few:
            return "提示链（Prompt Chaining）"
        if branches_enumerable:
            return "路由（Routing）"
        if can_parallelize:
            return "并行化（Parallelization）"
        return "组合式工作流"
    # 走到这里说明路径不可预知
    if high_error_cost or not evaluable:
        return "慎用 Agent：先补齐评估体系与人工审核 gate"
    if needs_dynamic_decompose:
        return "编排者-工作者（Orchestrator-Workers）"
    return "开放式循环 Agent"


def main() -> None:
    print("发票处理     ->", recommend_pattern(True, True, True, False, False, True, True))
    print("意图分流     ->", recommend_pattern(True, False, True, False, False, False, True))
    print("未知领域调研 ->", recommend_pattern(False, False, False, False, True, False, True))
    print("高风险无评估 ->", recommend_pattern(False, False, False, False, True, True, False))


if __name__ == "__main__":
    main()
```
保存为 `recommend_pattern.py`，运行 `python recommend_pattern.py`。预期输出：
```text
发票处理     -> 提示链（Prompt Chaining）
意图分流     -> 路由（Routing）
未知领域调研 -> 编排者-工作者（Orchestrator-Workers）
高风险无评估 -> 慎用 Agent：先补齐评估体系与人工审核 gate
```
讲解三处关键：

- **第一个 `if can_draw_flowchart`** 就是决策树那道最关键的筛子——它把「能画流程图」的任务全部导向工作流分支，「发票处理」和「意图分流」都在这里被筛走。
- **`if high_error_cost or not evaluable`** 体现了第 04 节的两个「不该用 Agent」信号：错误代价高或无法评估时，即使路径不可预知，也不该贸然放开自主性，而要先补护栏和评估——「高风险无评估」这一例就落在这里。
- 把主观判断（「这任务复杂吗」）拆成一组明确的布尔量（步数固定吗、分支可枚举吗），**本身就是一种工程训练**——它逼你把「感觉」变成「判据」。

## 用两个案例对照走一遍决策树

把第 README 里的贯穿案例 A（发票处理）和案例 B（未知领域调研）并排丢进树里：

**案例 A（发票处理）**：流程能画成流程图吗？**能**（抽取→校验→格式化，字段固定）。它在第一道筛子就被归到工作流一侧，步数固定且少 → **提示链**。它甚至走不到「要不要用 Agent」那一侧。这就是决策树的威力：**它让「PM 说要 Agent」这种需求方的措辞，不再能左右你的工程判断。**

**案例 B（未知领域调研）**：流程能画成流程图吗？**不能**（搜几次、顺哪条线索深入取决于中途发现）。进入右侧后：错误代价高吗？相对可容忍（综述可人工复核）。可评估吗？可以。子任务需动态分解吗？是 → **编排者-工作者 / 开放式 Agent**。这里的自主性不是浪费，而是刚需。

把两个案例的分界线并排看，就无比清晰：

| | 发票处理 | 未知领域调研 |
|---|---|---|
| 流程能否画成流程图 | 能 | 不能 |
| 步数 | 固定（3 步） | 不可预知 |
| 路径是否随输入变化 | 否 | 是 |
| 正确方案 | 工作流（提示链） | 开放式 Agent |

## 真实系统往往是「混合体」：外层工作流 + 内层 Agent

前面容易给人一个二选一的错觉——要么纯工作流，要么纯 Agent。但生产级系统里最常见、也最务实的形态是**混合（hybrid）**：用确定性工作流搭好可控的骨架，只在真正需要灵活性的那一两个环节，嵌入一个受约束的 Agent。

以「智能客服工单处理系统」为例：
```text
   ┌─────────────────────────────────────────────────────┐
   │  外层：确定性工作流（骨架，可控、可评估）              │
   │                                                       │
   │  接收工单 → 【路由:分类】 → ... → 归档 → 通知用户        │
   │                  │                                     │
   │                  ▼ （只有"复杂技术问题"这一类）          │
   │        ┌──────────────────────────┐                   │
   │        │ 内层：开放式 Agent（灵活）  │                   │
   │        │ 自主查文档/查日志/试方案    │  ← 只在这里放开    │
   │        │ 迭代排障，最多 N 步         │     自主性         │
   │        └──────────────────────────┘                   │
   └─────────────────────────────────────────────────────┘
```
这个设计的精妙之处：

- **绝大多数工单**（密码重置、账单查询等）走确定的路由 + 工作流分支，快、便宜、可预测；
- **只有「复杂技术问题」这一小类**——它的排障路径确实无法事先画出流程图——才交给内层 Agent 自主探索；
- 内层 Agent 被**外层框住**：有明确输入边界、有 `max_steps` 上限、失败会回退到「转人工」。自主性被限制在一个「安全的沙盒格子」里。

这就把复合错误的风险**局部化**了：整个系统 90% 的路径是低复合错误的工作流，只有 10% 的路径承担 Agent 的高方差，而且那 10% 还有兜底。**这远比「整个系统做成一个大 Agent」稳健得多。**

## 真实系统对应

**官方公开机制**：Anthropic《Building Effective Agents》公开了五种可组合的工作流模式——提示链、路由、并行化、编排者-工作者、评估者-优化者（Evaluator-Optimizer），并把开放式 Agent 单列，主张「先组合工作流，只在必要时才上 Agent」 [来源](https://www.anthropic.com/engineering/building-effective-agents)。这份清单正是本节决策树叶子的来源。落到具体产品：

- **OpenAI Agents SDK（Software Development Kit，软件开发工具包）** 公开提供 `handoffs`（智能体交接）、`guardrails`（护栏）等原语，天然支持「用确定性路由把大多数请求分流、只把疑难交给自主 Agent」的混合形态。
- **LangGraph** 用「图（graph）+ 节点（node）+ 边（edge）」显式编排：你可以把确定性步骤画成固定边，也可以在某个节点内放一个开放循环，正对应「外层工作流 + 内层 Agent」。
- **Claude Code** 作为编程 Agent，本身处于光谱高自主性端（自主决定读哪些文件、跑什么命令），但它也提供 `CLAUDE.md` 规则、权限确认等确定性护栏——这也是「给自主性套上确定性边界」的公开机制。

**通用工程模式**：「稳定骨架 + 局部弹性」是软件架构里的常见手法（如状态机里嵌入可插拔策略）。把高方差组件关进带兜底的沙盒，是可靠性设计通识。**教学参考实现**：`recommend_pattern.py` 的分支顺序和客服系统的分层图是本书为讲清判断而构造的示例，不代表任何产品的实际路由逻辑。

## 生产踩坑

| 症状 | 根因 | 如何观测与复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| 选型靠职级和气氛拍板 | 缺一套可复述的判据 | 让决策者照决策树走一遍并记录分叉 | 用 `recommend_pattern` 把判断变查表 | 全新问题域需先补判据再套树 |
| 整个系统做成一个大 Agent | 未把自主性局部化 | 分路径统计成功率与成本 | 外层工作流骨架 + 内层受约束 Agent | 极简单系统无需分层 |
| 内层 Agent 无上限拖垮系统 | 未设 max_steps / 超时 / 兜底 | 记录内层轮数分布与超时率 | 设步数上限，超限回退转人工 | 离线批处理可放宽 |
| 混合系统边界不清导致漏兜底 | 内外层职责未定义清 | 注入内层失败看是否回退 | 明确内层输入契约与失败出口 | 无 |
| 「显得先进」而选 Agent | 把技术选型当形象工程 | 复核任务是否真需自主性 | 以复合错误与成本反问收益 | 研究性探索项目可例外 |
| 决策树走到叶子却选错框架 | 把「模式」与「框架」混为一谈 | 核对框架是否支持该模式原语 | 先定模式再选支持它的框架 | 自研可绕过框架限制 |

## 思考：一个复杂业务系统，你会把它整个做成 Agent 吗？

### 回答

不会。我会用确定性工作流搭骨架、保证主流程可控可评估，只在少数「路径确实无法事先画出流程图」的环节，嵌入一个受约束的 Agent（带步数上限和人工兜底）。这样做有三个好处：一是把复合错误局部化——系统绝大多数路径是低复合错误的工作流，只有一小部分承担 Agent 的高方差；二是把成本局部化——不必让每个简单请求都去烧多轮循环；三是可评估性更好——确定性骨架容易测，内层 Agent 只需针对那一类疑难任务单独评估。能主动说出「把自主性局部化」，是资深工程判断的标志，比「全做成 Agent 显得先进」成熟得多。

### 面试精简表达

不整个做成 Agent。外层用确定性工作流搭骨架（可控、可评估、便宜），只在路径不可预知的环节嵌入带步数上限和人工兜底的受约束 Agent，把复合错误和成本局部化。

### 反例

如果这个「复杂业务系统」其实就是一个纯探索型任务（比如整个产品就是一个自主研究助手），且没有可拆分的确定性骨架，那么强行套「外层工作流」反而是画蛇添足——此时应直接构建受约束的 Agent，并把重心放在评估、护栏和成本控制上。混合架构是常见解，不是唯一解。

## 事故回放：把「大 Agent」拆成混合体后成本降了七成

某企业内部知识助手最初是一个「大一统 Agent」：无论用户问「报销政策是什么」还是「帮我排查这个跨系统的数据不一致」，都走同一个开放循环。上线后月度 token 账单居高不下，且简单问题偶尔也会因为多轮循环「想太多」而给出啰嗦甚至跑偏的答案。团队分析发现，约 85% 的提问是「一次检索就能答」的政策/流程类问题，只有 15% 是真正需要跨系统探索的疑难。

重构方案完全照本节的决策树：先加一层**路由**把提问分成「可直答」和「需探索」；可直答类走「单次带检索的增强调用」；需探索类才进入一个 `max_steps` 受限、且带人工兜底的内层 Agent。重构后，85% 的流量落在低成本的确定性路径上，月度 token 成本下降约七成，简单问题的答案也更简洁准确，而疑难问题的解决质量保持不变。

这次重构没有引入任何新模型、新框架，只是**把自主性从「全局」收敛到「局部」**。它印证了本节的核心：真实系统的最优形态往往不是「纯工作流」或「纯 Agent」，而是「确定性骨架 + 局部受约束自主性」的混合体——决策树帮你找到那个该放开自主性的、唯一的「格子」。
