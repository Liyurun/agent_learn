## 真实问题

一个团队内部为「我们这个系统到底算不算 Agent」吵了两周。有人说「它会调用工具，当然是 Agent」；有人说「它的每一步都是我们代码写死的，只是中间塞了几次模型调用，不算 Agent」。两派都拿得出理由，谁也说服不了谁。这场争吵之所以无解，是因为双方都把「是不是 Agent」当成了一个**是/否的开关**。真实系统不是开关，而是一条**连续光谱**：从「代码完全写死、模型只做局部判断」的固定流水线，到「模型自主决定每一步做什么」的全自主 Agent，中间有无数刻度。把它当二元问题，就会陷入无谓的命名之争；把它当光谱，问题立刻变成可回答的工程问题——「我们该停在光谱的哪个刻度上」。

## 原理：自主性是一条连续光谱

Anthropic 在《Building Effective Agents》中给出的一个关键区分是：**工作流（workflow）** 是「通过预先写好的代码路径来编排 LLM 和工具」的系统，而 **Agent** 是「由 LLM 动态决定自己的流程和工具用法」的系统 [来源](https://www.anthropic.com/engineering/building-effective-agents)。二者不是对立的两个盒子，而是同一条「控制权」轴上的两端：**你把多少「决定下一步做什么」的控制权交给了模型**。

沿这条轴从左（低自主性）到右（高自主性），典型刻度是：
```text
低自主性 ◀────────────────────────────────────────────────▶ 高自主性
 单次调用   提示链      路由       并行化    编排者-工作者   开放式Agent
  │          │          │          │            │             │
 一次        固定顺序    按类分流   独立子任务   动态分解        模型自主
 增强调用    多步        到分支     并行跑        再汇总          决定流程
  │          │          │          │            │             │
 控制权全在你手里 ──────────────────────────▶ 控制权逐格让渡给模型
```
- **单次调用（Augmented LLM）**：一次带工具/检索的增强调用，路径最短、最可控。
- **提示链（Prompt Chaining）**：把任务拆成固定顺序的若干步，每步一次调用，步与步之间可加校验 gate。
- **路由（Routing）**：先对输入分类，再分流到不同的下游处理分支，分支本身是确定的。
- **并行化（Parallelization）**：把可独立处理的子任务并行跑，再聚合，用于降延迟或多视角投票。
- **编排者-工作者（Orchestrator-Workers）**：一个编排者动态地把任务分解成子任务、分派给工作者、再汇总——分解是模型决定的，自主性开始明显上升。
- **开放式 Agent（Autonomous Agent）**：模型在循环中自主决定下一步做什么、用哪个工具、何时停止，控制权大幅让渡给模型。

关键洞察：**前四种通常仍属「工作流」范畴（控制流由你的代码主导），后两种自主性明显更高**。它们不是「谁更先进」，而是「把多少不确定性交给了模型」的不同选择。

## 核心洞察：自主性是成本，而非特性

要在光谱上选对刻度，必须先接受 Anthropic 提出的一个反直觉但极其重要的原则：

> 「Agent 可以处理复杂任务，但它们的实现往往更简单直接。也正因如此，**自主性（agency）带来的是更高的成本，以及潜在的错误累积**，所以应当只在收益值得时才提高自主性。」 [来源](https://www.anthropic.com/engineering/building-effective-agents)

换句话说，给系统更多自主性，意味着更高的延迟、更高的成本、更难预测的行为和更难的调试。正确的思路不是「怎么把它做得更 Agentic」，而是「**在满足需求的前提下，用最简单、自主性最低的方案**」。Anthropic 的建议很直接：**先找最简方案，只有当简单方案被证明不足时，才增加复杂度。**

### 自主性到底「贵」在哪四个地方

「自主性是成本」这句话很精辟，但要真正内化它，你得说清楚成本具体体现在哪。每让渡一格控制权给模型，你就在四个维度上付出代价：

| 成本维度 | 为什么变贵 | 具体表现 |
|---|---|---|
| 延迟 | 多轮循环串行等待，每轮都要等模型返回 | 一个 10 轮任务的响应时间约是单次调用的 10 倍 |
| 金钱（token） | 每轮都把历史带上重新推理，上下文越滚越长 | token 消耗随轮数近似平方级增长 |
| 可预测性 | 模型自主决策，路径不固定 | 同样的输入，两次运行可能走不同的路 |
| 可调试性 | 出错时难定位是哪一轮、哪个决策错了 | 无法像确定性代码那样打断点稳定复现 |

其中「token 随轮数近似平方级增长」最容易被忽视。为什么是平方级？因为第 N 轮的输入包含了前 N-1 轮的全部历史。下一节的实战会用代码把它算给你看，这里先记住结论：**轮数翻倍，成本远不止翻倍**。

## 最小可运行演示

把这条光谱做成一个可查询的「自主性刻度尺」，输入你打算让渡给模型的控制权，输出它落在光谱的哪一格、对应的成本画像。这段代码不联网、不需要任何依赖。
```python
from dataclasses import dataclass


@dataclass
class Level:
    rank: int          # 自主性等级，越大越自主
    name: str
    who_decides: str   # 谁决定「下一步做什么」
    cost_profile: str  # 成本画像


SPECTRUM = [
    Level(1, "单次调用",        "你的代码（就一步）",   "最低延迟/成本，路径唯一"),
    Level(2, "提示链",          "你的代码（固定顺序）", "低成本，可加校验 gate"),
    Level(3, "路由",            "你的代码（按类分流）", "低成本，分支确定"),
    Level(4, "并行化",          "你的代码（并行聚合）", "中等成本，延迟被并行摊薄"),
    Level(5, "编排者-工作者",   "模型（动态分解）",     "中高成本，token 显著上升"),
    Level(6, "开放式 Agent",    "模型（自主循环）",     "最高成本，随轮数近似平方级增长"),
]


def locate(agency_rank: int) -> Level:
    """按你愿意让渡的自主性等级，定位光谱刻度。"""
    agency_rank = max(1, min(6, agency_rank))
    return SPECTRUM[agency_rank - 1]


def main() -> None:
    for want in (1, 3, 6):
        lv = locate(want)
        print(f"等级{lv.rank} {lv.name}｜决策者：{lv.who_decides}｜成本：{lv.cost_profile}")


if __name__ == "__main__":
    main()
```
保存为 `agency_spectrum.py`，运行 `python agency_spectrum.py`。预期输出：
```text
等级1 单次调用｜决策者：你的代码（就一步）｜成本：最低延迟/成本，路径唯一
等级3 路由｜决策者：你的代码（按类分流）｜成本：低成本，分支确定
等级6 开放式 Agent｜决策者：模型（自主循环）｜成本：最高成本，随轮数近似平方级增长
```
这段代码把「是不是 Agent」这个二元争论，替换成了「你在第几格」这个可讨论的连续量。团队开会时，与其争「算不算 Agent」，不如指着输出问：「我们现在在等级几？需求真的需要爬到等级 6 吗？」

## 别走极端：低自主性不是「更好」，只是「更合适」

「自主性是成本」这个原则极其重要，但有一个常见误读：**把它理解成「自主性越低越好，能不用 Agent 就不用」**。这是矫枉过正。正确理解是：自主性是一件需要「按需购买」的东西——你要为它付延迟、成本、不可预测的代价，所以只在它能换来足够价值时才买，而不是「越少越好」。

举个反面例子：如果一个任务本质上路径不可预知（比如开放式调研），你却硬要用固定工作流去套，会发生什么？你会写出一堆 `if-else` 试图枚举所有情况，结果永远漏掉真实世界里的长尾分支，系统脆得一碰就碎。**在这种任务上，低自主性不是省成本，而是根本做不成。**

所以这条原则更准确的表述是一个双向平衡：
```text
   自主性给太多                       自主性给太少
   （用 Agent 做确定的事）             （用工作流做不确定的事）
   ┌────────────────┐               ┌────────────────────┐
   │ 白付延迟/成本    │               │ if-else 枚举不完     │
   │ 结果不可预测     │   ←平衡点→     │ 长尾分支必漏         │
   │ 调试困难        │               │ 系统脆弱易崩         │
   └────────────────┘               └────────────────────┘
        过度工程                          能力不足
```
平衡点在哪？就是下一节要给的那句话：**「能不能事先把流程图画出来。」** 画得出来，多给的自主性就是浪费；画不出来，省下的自主性就是缺陷。**判断力不是一味求简，而是精准匹配。**

## 真实系统对应

**官方公开机制**：Anthropic 在《Building Effective Agents》里明确把系统分为「workflow」与「agent」两类，并强调「找到满足需求的最简方案，往往不需要构建 Agent」 [来源](https://www.anthropic.com/engineering/building-effective-agents)。这直接支持「自主性是光谱、要选最合适刻度」的判断。落到产品上：OpenAI Agents SDK（Software Development Kit，软件开发工具包）公开提供从「单次带工具的调用」到「多智能体交接（handoff）」的不同抽象，正对应光谱的不同刻度；LangGraph 允许你用图（graph）显式编排确定性节点，也允许在节点内放开放循环，同样体现「同一框架可停在不同刻度」。**通用工程模式**：把「控制权归属」作为系统设计的一等公民，是分布式系统与自动化领域的通用做法（谁来决定重试、分支、终止）。**教学参考实现**：`agency_spectrum.py` 的六级划分是本书为教学而做的离散化；真实系统往往是连续且可混合的，不要把「等级 4」当成某个产品的官方术语。

## 生产踩坑

| 症状 | 根因 | 如何观测与复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| 团队为「算不算 Agent」长期争论 | 把自主性当二元开关而非光谱 | 让各方在光谱上标出「谁决定下一步」 | 用「控制权归属」定位刻度，停止命名之争 | 对外沟通时仍可用「Agent」作通俗称呼 |
| 简单任务用了开放循环，成本翻数倍 | 默认「更 Agentic 更先进」 | 对比同任务用提示链的 token 与延迟 | 从最低刻度起步，确证不足再上移 | 探索型任务不适用「越低越好」 |
| 不确定任务用工作流，长尾频繁失败 | 低自主性能力不足 | 统计 if-else 未覆盖的分支占比 | 在真正不可预知处放开自主性 | 高风险动作仍需外部护栏 |
| 上移自主性后延迟不可控 | 未设步数/超时上限 | 记录每次运行的轮数分布 | 设 max_steps 与超时，超限回退 | 硬实时场景不建议开放循环 |
| 混合系统内层 Agent 拖垮整体 SLO | 自主性未局部化 | 分路径统计成功率与 P99 延迟 | 把 Agent 关进带兜底的「沙盒格子」 | 非关键路径可放宽 |

（SLO：Service Level Objective，服务水平目标。P99 指第 99 百分位延迟。）

## 思考：为什么说「自主性越低越好」是一种误读？

### 回答

因为它把「成本最小化」错当成了「目标」。自主性确实是成本，但你构建系统是为了完成任务，不是为了省成本本身。当任务的路径无法事先画出（下一步取决于上一步的、不可预知的结果）时，低自主性方案会用大量 `if-else` 去枚举分支，而真实世界的长尾分支永远枚举不完，于是系统在这些分支上直接失败——此时低自主性不是「省钱」，而是「做不成」。正确的表述是双向平衡：自主性给太多是过度工程（白付延迟、成本、不可预测），给太少是能力不足（长尾必漏、系统脆弱）。判断力体现在**精准匹配**任务所需的自主性，而不是一味求低或求高。

### 面试精简表达

「越低越好」错在把手段当目的。自主性要按需购买：确定性任务多买就是浪费，不确定任务少买就是缺陷。目标是匹配，不是最小化。

## 优化前后对比：同一个「文档问答」需求爬错了刻度

某知识库问答系统最初被做成开放式 Agent：模型自主决定检索几次、读哪些片段、要不要追加检索。上线后每次问答平均 6 轮循环、延迟 8 秒、token 消耗是预期的 5 倍，而用户问的九成其实是「一次检索就能答」的简单事实型问题。

团队按光谱把它降级重构：先用一个**路由**（等级 3）把问题分成「简单事实」「需多跳推理」两类；简单事实走**单次带检索的增强调用**（等级 1），多跳推理才走一个**受约束的小循环**（带 max_steps=3）。重构后，九成流量落在等级 1，平均延迟从 8 秒降到 1.5 秒，token 成本降到原来的四分之一，而复杂问题的质量没有下降。

| 维度 | 重构前（全上等级 6） | 重构后（按类分级） | 验证方式 |
|---|---|---|---|
| 平均自主性刻度 | 等级 6，全部开放循环 | 九成走等级 1/3，一成走受约束循环 | 统计各刻度的流量占比 |
| 平均延迟 | 约 8 秒 | 约 1.5 秒 | 固定问题集回归测试 |
| token 成本 | 基线 | 约为基线的 1/4 | 同问题集对比 API 用量 |
| 复杂问题质量 | 基线 | 持平 | 人工标注多跳问题答案 |

这个案例的教训是：**先按任务分类，再给每类匹配最合适的刻度**，几乎总比「整个系统一刀切爬到最高刻度」更省、更快、更稳。它也预告了第 06 节的主题——真实系统往往是把不同刻度混合在一起的「混合体」。
