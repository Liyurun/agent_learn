## 真实问题

一位工程师收到需求：「帮我做一个能自动排查线上告警根因的助手。」他第一反应是「这不确定性很高，肯定要上 Agent」。但当他真去拆解时发现，八成的告警其实是那几类固定问题（磁盘满、证书过期、依赖服务超时），完全可以用规则匹配 + 固定检查脚本解决；只有约两成是「症状怪异、需要顺着日志一路深挖、路径无法预知」的疑难杂症。如果他一开始就把整个系统做成开放 Agent，那八成本可秒级解决的常见告警会被拖进多轮循环，又慢又贵；可如果他因噎废食完全不用 Agent，那两成真正需要探索的疑难又会卡死在写不完的 `if-else` 里。

**「该不该用 Agent」不是对系统整体的一次表态，而是对每一类任务的分别判断。** 本节给出三条正向信号——当任务同时满足它们时，Agent 的自主性不是浪费，而是刚需。

## 原理：Agent 擅长的三类任务特征

综合 Anthropic《Building Effective Agents》与多篇工程实践的共识，Agent（相对工作流）真正发挥价值，需要任务同时具备三个特征 [来源](https://www.anthropic.com/engineering/building-effective-agents)：

**信号一：模糊性（Ambiguity）——决策路径难以事先画出。**
任务的解法不是一条固定路径，而是「走一步看一步」：下一步做什么，取决于上一步的、无法预先枚举的结果。经典例子是编程 Agent 实现一个功能——创建哪些文件、加哪些依赖、改哪几行，取决于它读到的代码现状，无法在动手前写死。Anthropic 给出的字面判据是：**当问题开放、无法预先确定步骤的数量或顺序、且路径无法硬编码时，Agent 才是恰当选择。**

**信号二：多步且需迭代（Multi-step & Iterative）——需要基于中间反馈反复调整。**
任务不是「一次转换就完事」，而是需要多轮「行动 → 观察 → 再决策」的循环，且每轮都要参考真实环境返回的反馈来修正方向。如果一个任务两三步就能走完、且顺序固定，用提示链即可，用不着开放循环。

**信号三：需要与外部环境交互（Tool Use & Environment Interaction）——必须调工具、看真实结果。**
任务的推进依赖真实世界的反馈：查数据库、跑测试、读文件、调 API（Application Programming Interface，应用程序接口）。模型必须能发起动作、拿到观察结果、再据此决定下一步。纯靠模型内部知识就能一次答完的任务，不需要 Agent 的行动闭环。

**三条信号是「与」的关系，不是「或」。** 只满足「多步」不够（固定多步用提示链）；只满足「要调工具」不够（一次带工具的增强调用就行）。**只有当三条同时成立——路径模糊、需迭代、要交互——自主性才从「成本」变成「刚需」。**

## 一个正面案例：为什么「未知领域调研」该用 Agent

**场景**：「帮我调研一个我不熟悉的新兴技术，自主搜索、阅读、交叉验证多个来源后写一份综述。我无法预知它需要搜几次、顺着哪条线索深入。」

逐条验证三信号：

- 模糊性？**是**。搜几次、顺着哪条线索深挖，取决于搜到的内容，无法事先画出流程图。
- 多步且需迭代？**是**。要根据前一轮搜到的材料决定下一轮搜什么，反复交叉验证。
- 需与外部交互？**是**。必须真实调用搜索、抓取网页、阅读内容。

三条全中，所以这是开放式 Agent 的典型场景。这里的自主性不是浪费，而是刚需——你无法用固定工作流替代它，因为你根本画不出那张流程图。

## 最小可运行演示

把三条信号写成一个可运行的「Agent 适用性打分器」：三条全中才建议 Agent，否则给出更合适的降级方案。纯 Python、不联网。
```python
from dataclasses import dataclass


@dataclass
class TaskSignals:
    ambiguous_path: bool      # 信号1：路径模糊，画不出流程图
    multi_step_iterative: bool  # 信号2：多步且需基于反馈迭代
    needs_tool_interaction: bool  # 信号3：需与外部环境交互


def advise(sig: TaskSignals) -> str:
    hits = [sig.ambiguous_path, sig.multi_step_iterative, sig.needs_tool_interaction]
    score = sum(hits)
    if score == 3:
        return "建议：开放式 Agent（三条信号全中，自主性是刚需）"
    if not sig.ambiguous_path:
        return "降级：路径可画出流程图 -> 用工作流（提示链/路由）"
    if not sig.multi_step_iterative:
        return "降级：无需迭代 -> 用一次增强调用"
    return "降级：无需外部交互 -> 用纯推理调用（可加 CoT）"


def main() -> None:
    cases = {
        "未知领域调研": TaskSignals(True, True, True),
        "发票字段抽取": TaskSignals(False, True, True),
        "情感分类":     TaskSignals(False, False, False),
    }
    for name, sig in cases.items():
        print(f"{name:<10} -> {advise(sig)}")


if __name__ == "__main__":
    main()
```
保存为 `agent_fit.py`，运行 `python agent_fit.py`。预期输出：
```text
未知领域调研   -> 建议：开放式 Agent（三条信号全中，自主性是刚需）
发票字段抽取   -> 降级：路径可画出流程图 -> 用工作流（提示链/路由）
情感分类       -> 降级：路径可画出流程图 -> 用工作流（提示链/路由）
```
注意「发票字段抽取」虽然满足「多步」和「要调工具」，但因为**路径可以画出流程图**（信号一不满足），打分器就把它降级为工作流——这正是三条信号「与」关系的体现：缺一条，就不该贸然上 Agent。

## 真实系统对应

**官方公开机制**：Anthropic 的多智能体研究系统博客给出了一个具体的正面案例——他们的 Research 功能面对的正是「开放式研究」这类无法预先规划步骤的任务，因此采用了「主智能体分派多个子智能体并行探索」的架构 [来源](https://www.anthropic.com/engineering/multi-agent-research-system)。博客明确说明，这类架构「烧 token 很快：多智能体系统大约消耗单次聊天的 15 倍 token」，因此**只有当任务价值足够高、能覆盖这份开销时才划算**——这从成本侧反向印证了「三信号全中的高价值任务」才配得上 Agent。同一篇博客还指出：**需要所有智能体共享同一上下文、或子任务之间有很多依赖的领域，并不适合多智能体**，这正对应「信号一模糊性」的反面（依赖强、可预先规划的任务用工作流更好）。**通用工程模式**：把「适用性」拆成一组布尔信号再做「与」判断，是需求分析的通用手法。**教学参考实现**：`agent_fit.py` 的降级建议是教学简化，真实选型还要叠加错误代价、可评估性等约束（见第 04、06 节）。

## 生产踩坑

| 症状 | 根因 | 如何观测与复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| 常见告警也被拖进多轮循环 | 未按任务类别分流，整体上了 Agent | 统计各类任务的轮数分布 | 高频固定类走工作流，疑难才进 Agent | 疑难类仍需保留 Agent |
| 「多步」被误当 Agent 信号 | 忽略「路径是否可画出流程图」 | 复核该任务能否事先画流程图 | 固定多步用提示链而非开放循环 | 步骤会随输入改变的除外 |
| 调研类任务被硬套固定流程 | 误判其路径可预知 | 观察 if-else 覆盖不到的长尾比例 | 在真正模糊处放开自主性 | 有强合规约束时需加护栏 |
| Agent 适用但成本超预算 | 高价值判断缺失，盲目上多智能体 | 对比单次聊天与多智能体 token 倍数 | 用「任务价值 vs 15x 开销」核算 | 低价值任务不应上多智能体 |
| 子任务强依赖却硬拆多智能体 | 误判可并行 | 检查子任务间的数据依赖 | 强依赖/需共享上下文的用单体或工作流 | 真正独立的子任务可并行 |

## 思考：为什么「多步任务」不等于「该用 Agent」？

### 回答

因为「多步」只描述了任务的长度，没描述它的**可预测性**。一个多步任务如果每一步的顺序和内容都能事先确定（比如「翻译 → 校对语气 → 输出」这三步固定不变），它就能被画成一张确定的流程图，用提示链实现即可——提示链本身就是多步的，但它是工作流，不是 Agent。真正需要 Agent 的是「多步 **且** 下一步取决于上一步不可预知的结果」的任务：你事先不知道要走几步、走哪几步。所以判断的关键从来不是「几步」，而是「这些步骤能不能事先画出来」。把「多步」当成 Agent 信号，是最常见的选型错误之一。

### 反例

「每月账单生成」是一个十几步的多步任务（拉数据 → 计算 → 生成 PDF → 归档 → 发送），步数很多，但每一步都固定、可画流程图，因此正确方案是确定性工作流而非 Agent。步数多不构成用 Agent 的理由。

## 事故回放：把「疑难排障」拆出来才救活了系统

某运维平台最初把「告警根因分析」整体做成一个开放 Agent，希望它能应对所有告警。上线后两个问题同时爆发：一是常见告警（占八成）也走多轮循环，平均处理时间从原先规则引擎的 2 秒涨到 25 秒，值班同学抱怨「简单问题也要等半天」；二是 token 账单一个月涨了近十倍，因为每条告警都在烧多轮推理。

团队按三信号重新拆分：先做**分类**，把告警分成「已知模式」和「疑难」两类。已知模式（磁盘满、证书过期等）路径完全可画出流程图——信号一不满足——于是走确定性检查脚本，秒级返回；只有「疑难」类（症状不匹配任何已知模式、需顺着日志链路深挖、路径不可预知）三信号全中，才交给一个带 `max_steps` 上限的 Agent。

重构后，八成告警回到秒级响应，token 成本降回可控区间，而那两成疑难告警的自动定位率反而提升了——因为 Agent 不再被大量简单任务稀释注意力和预算，可以在真正需要探索的地方投入更多轮次。这个事故的教训与第 02 节一致：**先按任务类别判断三信号，再分别匹配自主性**，比对整个系统一次性表态要可靠得多。
