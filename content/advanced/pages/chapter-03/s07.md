## 真实问题

前六节把「该不该用 Agent」的方法讲透了，但两个场景会把方法逼到墙角：一个是**面试**——面试官不会问「什么是 Agent」，而会追问「你怎么判断、怎么定量、遇到反例怎么办」；一个是**上线评审**——评审不会看你 Demo 多惊艳，而会问「复合错误算过没、gate 加在哪、失败怎么兜底」。本节把散落在前几节的判断，收敛成一组高频「思考+回答」和几张可直接照抄的生产建议表，帮你走完从「懂原理」到「过面试、能上线」的最后一公里。

## 上线前自检清单（可运行）

先给一段可运行的自检工具：把前几节的判断固化成一份 checklist，输入你的实际情况，输出「能不能上线」。纯 Python、不联网。
```python
"""上线前自检清单。保存为 preflight_checklist.py 运行。"""

CHECKS = [
    ("能画出确定流程图", "能 -> 优先工作流；不能才考虑 Agent"),
    ("按真实步数算过 p^n", "整体成功率低于门槛就压步数/加 gate"),
    ("关键动作前有确定性校验 gate", "危险动作必须能被中止/回退"),
    ("有评估集能判断对错", "没有就先补评估，别上线"),
    ("自主循环设了 max_steps 与超时", "超限必须回退/转人工"),
    ("重试仅用于可检测且幂等的步骤", "非幂等步骤先加幂等键"),
    ("高方差组件已局部化并有兜底", "别让内层 Agent 拖垮整体 SLO"),
]


def run(answers) -> None:
    passed = sum(1 for a in answers if a)
    print(f"通过 {passed}/{len(CHECKS)} 项")
    for (name, advice), ok in zip(CHECKS, answers):
        mark = "OK " if ok else "!! "
        print(f"[{mark}] {name}｜{advice}")
    print("结论：", "可评估上线" if passed == len(CHECKS) else "存在阻塞项，先补齐再上线")


def main() -> None:
    answers = [True, False, True, False, True, True, True]  # 第 2、4 项未通过
    run(answers)


if __name__ == "__main__":
    main()
```
保存为 `preflight_checklist.py`，运行 `python preflight_checklist.py`。预期输出：
```text
通过 5/7 项
[OK ] 能画出确定流程图｜能 -> 优先工作流；不能才考虑 Agent
[!! ] 按真实步数算过 p^n｜整体成功率低于门槛就压步数/加 gate
[OK ] 关键动作前有确定性校验 gate｜危险动作必须能被中止/回退
[!! ] 有评估集能判断对错｜没有就先补评估，别上线
[OK ] 自主循环设了 max_steps 与超时｜超限必须回退/转人工
[OK ] 重试仅用于可检测且幂等的步骤｜非幂等步骤先加幂等键
[OK ] 高方差组件已局部化并有兜底｜别让内层 Agent 拖垮整体 SLO
结论： 存在阻塞项，先补齐再上线
```
（SLO：Service Level Objective，服务水平目标。）这个清单的价值在于：它把「上线评审」从一场即兴问答，变成一次逐项打勾——**任何一项没通过，都是明确的、可行动的阻塞项**，而不是模糊的「感觉还差点」。

## 真实系统对应

**官方公开机制**：Anthropic 的多智能体研究系统博客公开了几条可直接搬进评审的经验：多智能体系统约消耗单次聊天 **15 倍** token，因此只适合高价值任务；给子智能体的任务描述必须包含「明确目标、输出格式、可用工具与来源、任务边界」，否则子智能体会重复劳动或漏做；还要用「effort scaling（努力度分级）」规则告诉智能体「简单事实查询用 1 个智能体调 3-10 次工具，复杂研究才展开更多」 [来源](https://www.anthropic.com/engineering/multi-agent-research-system)。这些都是「何时该用、用多少 Agent」的一手证据。《Building Effective Agents》则从原则侧强调「保持简单、在关键步骤设检查点、能评估再放开自主性」 [来源](https://www.anthropic.com/engineering/building-effective-agents)。**通用工程模式**：上线前 checklist、失败兜底、幂等键都是可靠性工程通识。**教学参考实现**：`preflight_checklist.py` 的七项是本书对前六节的归纳，不同团队应按自身风险裁剪，不构成合规清单。

## 思考：面试官问「你怎么评估一个多步 Agent 靠不靠谱」，怎么答？

### 回答

分三步定量回答，而不是说「多测测」。第一步问清「任务大概几步、每步成功率多少」，用复合公式 `p^n` 估算整体成功率——比如单步 95%、20 步，整体只有约 36%。第二步判断这个数够不够：不够就讨论两条对策，压步数（拆短、加校验 gate 截断错误传播）或顶高单步成功率（更强模型、更严工具校验、可检测且幂等步骤上加重试）。第三步谈评估与观测：有没有金标准评估集、能不能回放每次实际输入、失败时能否定位到是哪一步先偏离。能把复合错误公式和这张衰减表主动搬出来，直接甩开只会说「多测测」的候选人。

### 面试精简表达

先用 `p^n` 估整体成功率，太低就压步数或加 gate；再看有没有评估集和可回放的 trace。定量 + 可评估，是判断靠不靠谱的两只脚。

## 思考：为什么说「token 随轮数近似平方级增长」？

### 回答

因为在一个把全部历史都带上重新推理的多轮 Agent 里，第 N 轮的输入包含了前 N-1 轮的所有内容。第 1 轮输入约 1 份、第 2 轮约 2 份、……第 N 轮约 N 份，累计消耗约是 `1+2+…+N = N(N+1)/2`，即与轮数的平方成正比。这就是为什么「轮数翻倍，成本远不止翻倍」——从 5 轮到 10 轮，累计 token 不是翻一倍，而是约翻两倍。它和复合错误是硬币的两面：轮数既在指数上压垮成功率，又在平方上抬高成本。所以「压步数」几乎总是双赢——同时救成功率和成本。

### 反例

如果实现上做了上下文裁剪/摘要（每轮只带固定长度的近期窗口 + 结构化摘要），单轮输入不再随轮数线性增长，累计就退化为近似线性而非平方。所以「平方级」是「朴素地把全部历史都带上」的默认行为，不是不可避免的定律——这正是卷七上下文工程要解决的问题。

## 思考：ReAct 是 Agent 的分水岭，那 CoT 还有用吗？

### 回答

非常有用，而且是 ReAct 的组成部分。ReAct 的每一步「Thought（思考）」本质上就是一次局部的 CoT——它用推理链决定「这一步该做什么动作」。CoT 解决的是「怎么想清楚」，ReAct 在此之上加了「想完能去做、做完能看结果」。所以二者不是替代关系，而是包含关系：没有好的 CoT，ReAct 每一步的决策质量就上不去；没有 ReAct 的行动闭环，再好的 CoT 也只能停在脑内推理。工程上，你会在纯推理/分类任务里单独用 CoT（属于工作流），在需要与环境交互的任务里用 ReAct 式循环（属于 Agent）。

### 面试精简表达

CoT 是「想清楚」，ReAct 是「想清楚 + 做 + 看」。ReAct 每步的 Thought 就是 CoT，二者是包含关系，不是替代关系。

## 思考：MCP 被采纳、还交给了 Linux 基金会，这对「何时该用 Agent」的判断有什么实际影响？

### 回答

它降低了「集成成本」这项在决策中的权重。过去评估要不要上 Agent，「接每个工具都要写一套胶水」是一笔沉重的隐性成本，可能让你倾向于「能不接就不接、能不上 Agent 就不上」。MCP（Model Context Protocol，模型上下文协议）把工具集成从「N×M 胶水」变成「N+M 标准接口」，2025 年 12 月又与 goose、AGENTS.md 一起成为 Linux 基金会 Agentic AI Foundation 的创始项目，治理从单一厂商迁入中立基金会，进一步降低了「押注某家标准会被废弃」的风险 [来源](https://blog.modelcontextprotocol.io/posts/2025-12-09-mcp-joins-agentic-ai-foundation/)。所以今天做选型，工具接入不再是拦路虎——但这不改变前几节的核心判据：**模糊性、复合错误、可评估性**依然是决定要不要用 Agent 的主因，MCP 只是让「一旦决定要用，落地更省事」。别把「集成变便宜了」误读成「所以该多用 Agent」。

## 思考：Anthropic 说多智能体烧 15 倍 token，那多智能体是不是基本不该用？

### 回答

不是。15 倍开销是一个「门槛」而非「禁令」。Anthropic 的原文逻辑是：多智能体值不值，取决于**任务价值能否覆盖这份开销**，以及任务是否**可并行、子任务是否相对独立** [来源](https://www.anthropic.com/engineering/multi-agent-research-system)。它明确指出，需要所有智能体共享同一上下文、或子任务间依赖很强的领域，并不适合多智能体——那种情况下单体 Agent 或工作流更好。所以正确的判断是三问：任务价值够高吗（值 15 倍吗）？子任务能并行吗？它们之间依赖弱吗？三者都成立，多智能体才划算；否则宁可用单体或工作流。把「烧 15 倍」当成「一律不用」，和把它当成「随便用」一样，都是没读懂那句话的条件。

### 面试精简表达

15 倍是门槛不是禁令。三问：任务值 15 倍吗、能并行吗、子任务依赖弱吗——都成立才上多智能体。

## 思考：需求方明确说「要做 Agent」，你判断该用工作流，怎么沟通？

### 回答

不要在「叫不叫 Agent」这个词上纠缠，而是把话题拉到需求方真正关心的三件事：更快、更便宜、更可靠。我会说：「这个流程的字段和步骤是固定的，能画出流程图；如果做成开放循环，复合错误会让整体成功率下降、延迟和成本上升；用确定性工作流反而更快、更便宜、也更好评估。对外我们完全可以继续叫它 Agent（这是产品称呼），但工程实现上我建议用带校验的工作流。」关键是**用对方的目标（成本、可靠性）说话，而不是用工程术语纠正对方**。必要时把第 05 节的复合错误表摆出来，让数字替你沟通。

### 反例

如果需求本质确实是探索型（比如「帮我调研未知领域」），需求方说要 Agent 是对的，此时不该为了「显得克制」硬塞工作流——那会让系统在长尾分支上频繁失败。沟通的目标是匹配任务本质，不是无条件劝退 Agent。

## 生产建议：三张表怎么用

三张表按「时间顺序」组织，对应一个 Agent 项目的三个阶段。**选型与架构阶段**（表一）在写代码前用，防止一开始就选错自主性等级；**可靠性与复合错误阶段**（表二）在实现和联调时用，防止复合错误把成功率拖垮；**运行与兜底阶段**（表三）在上线前和上线后用，防止自主循环失控、失败无兜底、事故无法定位。

用法建议是「反向排查」：出了问题，先看它属于哪个阶段的症状，再对照该表的「如何观测与复现」列去复现，然后按「修复与预防」列动手，最后用「不适用边界」列检查自己是不是过度修复了。**这三张表和第 05 节的复合错误账本、第 06 节的决策树，共同构成一套可复用的工程判断工具**——它们的目标始终一致：让「该不该用 Agent、用多少、怎么兜底」这些判断，从依赖资历和气氛，变成依赖可复述、可验证、可定量的依据。

## 事故回放：一次评审如何拦下一个注定失败的项目

某团队提报一个「全自动合同审查 Agent」：上传合同，Agent 自主逐条审查、标注风险、给出修改建议、直接回填到合同并发给对方。评审会上，评审人没有讨论「模型选哪个」，而是照本章方法逐项过：

第一问「能画出确定流程图吗」——部分能（条款分类、关键字段抽取是确定的），部分不能（风险判断是开放的）。这说明它应该是混合体，而非一个大 Agent。第二问「按真实步数算过 p^n 吗」——团队没算。现场一算，全自动链路约 12 步、单步乐观估计 92%，`0.92^12 ≈ 37%`，意味着近三分之二的合同会在某处出错。第三问「危险动作有 gate 吗」——最危险的「直接回填并发给对方」没有任何人工确认。第四问「有评估集吗」——没有，无法判断风险标注对不对。

结论是这个项目当前形态**不能上线**：不是因为技术不行，而是因为它同时踩了「复合错误过高、危险动作无 gate、无法评估」三条红线。评审给出的改法正是本章的方法：把确定部分（分类、抽取）做成工作流，只把「风险判断」交给受约束的内层 Agent；「回填并发送」前必须加人工确认 gate；先建一个带标注的评估集再谈自动化程度。三个月后，改造成混合体、且只做「审查建议」不做「自动发送」的版本顺利上线。**这次评审拦下的不是一个坏主意，而是一个好主意的错误形态**——这正是本章想教会你的判断力。
