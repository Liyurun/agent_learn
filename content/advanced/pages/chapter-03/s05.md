## 真实问题

「多给模型几轮循环又不会怎样。」——这句话几乎每个团队都听过。说这话的人不是不聪明，而是**没有把复合错误算成一个具体的数**。当讨论停留在「感觉还行」「应该没问题」的口头层面时，谁的嗓门大谁就赢。本节要做的，是把「复合错误」从一句可以争辩的口号，变成一张谁都无法反驳的账本：只用纯 Python 标准库（不联网、不装任何包），把「单步成功率」和「步数」两个变量一起扫一遍，画出数值表和 ASCII 曲线。等你亲眼看到「单步 95% 到 20 步只剩 36%」这张表，再有人说「多几轮无所谓」，你把账本摆出来就行。

## 原理：串联系统的可靠性公式

如果一个任务由 n 个步骤串成，每一步都必须成功任务才算成功，且各步成功与否相互独立，那么整体成功率就是各步成功率的乘积。当每步成功率都是同一个值 p 时，公式简化为：
```text
整体成功率 = p ^ n
```
这就是可靠性工程里「串联系统」的经典结论：**串联系统的整体可靠性，永远低于其中最弱的那一环，且随环节数指数下降。** 它不是 AI 独有的定律，而是任何「必须步步都对」的流程共有的数学事实。对 Agent 而言，「步数 n」就是它自主循环的轮数或工作流的阶段数，「单步成功率 p」就是每一步（一次工具调用、一次判断、一次生成）不出错的概率。

两个必须记住的推论：

1. **单步的微小退步，会被步数指数放大。** 单步从 99% 降到 95%（只差 4 个百分点），在 20 步处整体成功率从 82% 崩到 36%。
2. **加校验 gate（关卡）等价于把长链路截成短链路。** 若在链路中每隔 k 步插一道能拦截并重试的 gate，整体成功率近似只受「最长一段」（长度约 k）的复合错误影响，从而大幅回升。

## 最小可运行演示（完整版）

下面是一段**完全可运行、只依赖 Python 标准库**的程序。它做三件事：打印单步成功率 × 步数的二维数值表、画出 ASCII 复合错误曲线、对比「无 gate」与「加 gate」的整体成功率。
```python
"""复合错误率实战：纯标准库，无需联网、无需 API Key。
保存为 compound_error_lab.py，运行 python compound_error_lab.py。
"""


def overall_success(step_success: float, steps: int) -> float:
    """整体成功率 = 单步成功率 ^ 步数（各步独立假设）。"""
    return step_success ** steps


def print_table(step_rates, step_counts) -> None:
    """打印「单步成功率 × 步数」的整体成功率二维表。"""
    header = "单步\\步数 | " + " | ".join(f"{n:>4}步" for n in step_counts)
    print(header)
    print("-" * len(header))
    for p in step_rates:
        cells = " | ".join(f"{overall_success(p, n):>4.0%}" for n in step_counts)
        print(f"{p:>7.0%} | {cells}")


def ascii_curve(step_success: float, max_steps: int, width: int = 50) -> None:
    """用 ASCII 画一条整体成功率随步数衰减的曲线。"""
    print(f"\n单步成功率 = {step_success:.0%} 时，整体成功率随步数衰减：")
    for n in range(1, max_steps + 1):
        rate = overall_success(step_success, n)
        bar = "#" * round(rate * width)
        print(f"{n:>2}步 |{bar:<{width}}| {rate:>4.0%}")


def gate_success(step_success: float, steps: int, gate_every: int) -> float:
    """教学近似：每 gate_every 步一道可拦截并重试到成功的 gate，
    整体成功率近似只受最长一段（长度 = min(gate_every, steps)）影响。"""
    longest = min(gate_every, steps)
    return step_success ** longest


def main() -> None:
    step_rates = (0.99, 0.95, 0.90, 0.80)
    step_counts = (5, 10, 20, 50)

    print("=== 表一：整体成功率 = 单步成功率 ^ 步数 ===")
    print_table(step_rates, step_counts)

    ascii_curve(0.95, 20)

    print("\n=== 表二：20 步链路，加 gate 前后对比（单步 95%） ===")
    p, steps = 0.95, 20
    print(f"无 gate               : {overall_success(p, steps):>4.0%}")
    for k in (10, 5, 2):
        print(f"每 {k:>2} 步一道 gate      : {gate_success(p, steps, k):>4.0%}（按最长段近似）")


if __name__ == "__main__":
    main()
```

## 逐点解读这张表

表一是本章最该被截图存下来的一张：

- **看 95% 那一行**：单步 95% 听起来很棒，但到 20 步只剩 36%，到 50 步只剩 8%。**「每步都不错」不等于「整体能成」。**
- **看 20 步那一列的对角**：单步从 99% 降到 90%，20 步的整体成功率从 82% 崩到 12%——**单步一点点退步，整体断崖式下跌**。这就是「单步微小退步被步数指数放大」的推论一。
- **越往右下越绝望**：长任务（步数多）+ 中等可靠（单步 80-90%）= 几乎必然失败。红线区域是工程上必须绕开的死亡地带。

表二则给出希望：同样是 20 步、单步 95% 的链路，无 gate 时整体只有 36%，但每 2 步插一道 gate 后回升到约 90%。**gate 不改变单步成功率，只改变错误的传播距离**，就能把整体成功率从「几乎必失败」拉回「基本可用」。这就是推论二的可视化证明，也解释了为什么「带 gate 的工作流」在长链路上常常打败「开放 Agent」。

从这张账本能提炼出两条工程铁律：

1. **要么把步数压下来**（拆成短工作流、让模型少绕弯路）；
2. **要么把单步成功率顶上去**（更好的提示、更强的模型、更严的工具校验）。

而只要能在关键位置加 gate 截断错误传播，第一条就能以最低成本实现。

## 进一步：允许重试的复合成功率

上面的模型假设「一步失败，整个任务就失败」。但很多真实 Agent 允许**重试**：某步失败可以再试若干次，只要有一次成功就继续。加入重试后，单步的「有效成功率」会提升。下面这段代码把重试也算进来，仍然只用标准库。
```python
"""在复合模型里加入「每步可重试 r 次」。保存为 retry_success.py 运行。"""


def step_with_retry(step_success: float, retries: int) -> float:
    """一步在最多 (retries+1) 次尝试内至少成功一次的概率。
    = 1 - (全部失败的概率) = 1 - (1-p)^(retries+1)
    """
    return 1 - (1 - step_success) ** (retries + 1)


def overall_with_retry(step_success: float, steps: int, retries: int) -> float:
    effective = step_with_retry(step_success, retries)
    return effective ** steps


def main() -> None:
    p, steps = 0.90, 20
    print(f"单步成功率={p:.0%}，步数={steps}")
    for r in (0, 1, 2, 3):
        eff = step_with_retry(p, r)
        total = overall_with_retry(p, steps, r)
        print(f"每步重试{r}次 -> 有效单步{eff:.1%}，整体成功率{total:.0%}")


if __name__ == "__main__":
    main()
```
保存为 `retry_success.py`，运行 `python retry_success.py`。预期输出：
```text
单步成功率=90%，步数=20
每步重试0次 -> 有效单步90.0%，整体成功率12%
每步重试1次 -> 有效单步99.0%，整体成功率82%
每步重试2次 -> 有效单步99.9%，整体成功率98%
每步重试3次 -> 有效单步100.0%，整体成功率100%
```
这段代码揭示了另一条降低复合错误的路径：**在错误可检测、可安全重试的步骤上引入重试**，能把有效单步成功率从 90% 顶到 99% 以上，整体成功率从 12% 拉回 82% 甚至更高。但它有一个隐含前提——**错误必须能被检测到，且重试必须是安全（幂等）的**。如果一步「写数据库」失败后重试会重复写入，或者失败根本检测不出来，重试不但无益反而有害。所以重试是复合错误的解药，但只对「可检测 + 幂等」的步骤有效，这也是为什么第 04 节强调的确定性校验 gate 如此重要——gate 正是「让错误可检测」的手段。

## 真实系统对应

**官方公开机制**：Anthropic 在《Building Effective Agents》中明确把「错误会随步数累积（compounding errors）」列为提高自主性的主要代价之一，并建议用「在关键步骤设置检查点/让人类介入」来控制 [来源](https://www.anthropic.com/engineering/building-effective-agents)。这正对应本节的 gate 与重试思路。**通用工程模式**：`p^n` 是串联系统可靠性的标准公式，重试模型 `1-(1-p)^k` 是并联/重试可靠性的标准公式，二者都属可靠性工程通识，可迁移到任何多步流程。**教学参考实现**：本节所有代码都是为讲清数学而构造的教学模型；`gate_success` 的「最长段近似」和重试模型的「独立、可检测、幂等」都是简化假设，真实系统的失败往往相关、部分不可检测、部分不可重试，需按实际情况建模，不能把这些数字当作生产承诺。

## 生产踩坑

| 症状 | 根因 | 如何观测与复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| 用「感觉还行」拍板上线 | 没把复合错误算成数 | 跑 `compound_error_lab.py` 出表 | 上线前强制用 p^n 估整体成功率 | 极短链路可豁免 |
| 重试后错误反而变多 | 在非幂等步骤上重试 | 注入失败看是否重复副作用 | 只对可检测且幂等的步骤重试 | 写操作需先加幂等键 |
| 加了 gate 成功率没升 | gate 只观测不拦截/不重试 | 检查 gate 是否真的中止链路 | gate 必须能中止、重试或回退 | gate 自身失败需监控 |
| 各步强相关时估算失真 | 误用独立性假设 | 检查步骤间是否共享同一错误源 | 相关步骤合并估算或做实测 | 完全独立时公式准确 |
| 只顶单步没压步数，成本爆炸 | 忽视步数才是指数底数上的指数 | 对比压步数 vs 换大模型的收益 | 优先压步数/加 gate，再谈换模型 | 单步极低时需先救单步 |
| 曲线被误读成线性下降 | 不理解指数衰减 | 让团队照着 ASCII 曲线复述形状 | 用凹曲线图建立指数直觉 | 无 |

## 思考：为什么「压步数」通常比「换更大的模型」更划算？

### 回答

因为在 `整体成功率 = p^n` 里，步数 n 站在**指数位置**，而模型能力影响的是底数 p。压步数是直接缩小指数，收益是几何级的：把 20 步压到 10 步，等于把 `p^20` 变成 `p^10`，在 p=0.95 时整体成功率从 36% 直接翻倍到 60%。而「换更大模型」通常只能把单步 p 提升几个百分点（比如从 95% 到 97%），在长链路上被指数稀释后收益有限，且换模型往往意味着更高的单价和延迟。更重要的是，「加校验 gate 压有效步数」几乎不增加延迟、成本极低，却能把长链路在数学上截成短链路。所以工程上的优先级通常是：先压步数 / 加 gate，再谈重试，最后才考虑换更大的模型——除非单步成功率低到连短链路都撑不住，那时才需要先救单步。

### 面试精简表达

n 在指数上，p 在底数上。压步数是砍指数，收益几何级；换大模型是抬底数，收益被指数稀释。所以优先压步数、加 gate，最后才换模型。

## 完整实践：给一条真实链路做体检

把前面的工具组合起来，给一条假设的真实链路做一次「可靠性体检」。这段代码仍然只用标准库，输入一条链路各步的成功率，输出整体成功率、最弱环节、以及「加一道 gate 在哪最划算」的建议。
```python
"""链路可靠性体检。保存为 pipeline_health.py 运行。"""


def health_check(step_rates):
    steps = list(enumerate(step_rates, start=1))
    overall = 1.0
    for _, p in steps:
        overall *= p
    weakest = min(steps, key=lambda kv: kv[1])
    # 若在最弱环节后加一道 gate（把它单独隔离并重试到成功），
    # 近似把该步的有效成功率视为 1.0，重算整体。
    improved = overall / weakest[1]
    return {
        "整体成功率": overall,
        "最弱环节": f"第{weakest[0]}步（{weakest[1]:.0%}）",
        "在最弱环节加gate后": improved,
    }


def main() -> None:
    pipeline = [0.98, 0.95, 0.85, 0.97, 0.90]  # 一条 5 步链路各步成功率
    report = health_check(pipeline)
    print(f"链路各步成功率: {pipeline}")
    for k, v in report.items():
        print(f"{k}: {v:.0%}" if isinstance(v, float) else f"{k}: {v}")


if __name__ == "__main__":
    main()
```
保存为 `pipeline_health.py`，运行 `python pipeline_health.py`。预期输出：
```text
链路各步成功率: [0.98, 0.95, 0.85, 0.97, 0.9]
整体成功率: 69%
最弱环节: 第3步（85%）
在最弱环节加gate后: 81%
```
这个体检器把抽象的「加 gate」落到了「加在哪一步」：它找出最弱的第 3 步（85%），并算出如果在这里加一道能拦截重试的 gate，整体成功率能从 69% 提到 81%——用最少的 gate 换最大的收益。这就是「把复合错误算成账本」的终点：不只是吓唬自己「会崩」，而是精确指出**在哪里加护栏最值钱**。
