## 真实问题

「上线三天才发现退步」故障平息后，团队想给客服 Agent 装一块「仪表盘」，让下次退步在小时级、而不是天级被发现。第一版仪表盘只放了一个数字：**任务成功率**。上线第二版 prompt 时，这个数字从 82% 掉到 79%——降了，但幅度不大，值班同学犹豫「要不要回滚」。直到有人追问「工具正确率呢？平均步数呢？强停率呢？」，才发现这些**过程指标**根本没采集。事后补上才知道：那 3 个百分点的成功率下降背后，是工具正确率从 90% 崩到 74%、平均步数从 6 涨到 10——**结果指标只轻微异动，过程指标早已剧烈报警**。只看一个成功率，等于只看体温不看血压。

这一节讲评估的量化底座：哪些是结果指标、哪些是过程指标，为什么过程指标常是「先行指标」，以及如何用「结果 × 轨迹」的差值和四象限计数，识别被聚合数字掩盖的结构性问题。

## 原理：结果指标 vs 过程指标

评估指标分两层，对应上一章讲的结果评估与轨迹评估：

| 类别 | 指标 | 回答的问题 | 特性 |
|---|---|---|---|
| 结果指标 | 任务成功率 | 任务最终做对没 | 滞后（用户已受影响才降） |
| 结果指标 | 一次解决率 | 是否一句话解决、无需转人工 | 滞后、贴近业务 |
| 过程指标 | 工具正确率 | 关键工具用对没 | 先行 |
| 过程指标 | 平均步数 | 有没有绕路 | 先行 |
| 过程指标 | P95 延迟 | 尾部体验是否糟糕 | 先行 |
| 过程指标 | token 成本 | 单次任务烧多少钱 | 先行 |
| 过程指标 | 强停率 | 多少任务在打转触顶 | 先行 |

一个关键洞察：**过程指标往往是先行指标，结果指标是滞后指标**。成功率是「用户已经受影响了才降」，而工具正确率、平均步数、强停率往往在成功率崩之前就开始异动。盯住先行指标，你能在用户投诉之前发现问题——这正是开头故障应该、却没能做到的。

τ-bench 等基准也把「任务成功率（是否达成目标状态）」作为核心度量，同时越来越强调工具调用与多轮状态保持的正确性 [来源](https://www.codesota.com/guides/agentic-benchmarks)。

### P95 而非平均：为什么尾部延迟更重要

延迟一定要看 P95/P99 而非平均值。平均值会被大量快请求拉低，掩盖「有 5% 的用户等了 18 秒」这种糟糕体验。生产监控几乎总是看分位数——一个 P50 只有 2 秒但 P95 高达 18 秒的系统，对那 5% 的用户就是灾难。

## 最小可运行演示

下面把一次运行的关键指标结构化成数据类，聚合出结果指标与过程指标，并用「结果 × 轨迹」四象限逐条计数，揭示聚合数字如何掩盖问题。
```python
"""演示：任务成功率 / 工具正确率 / 过程指标的结构化采集与聚合。"""
from dataclasses import dataclass
from statistics import mean, quantiles


@dataclass
class RunMetrics:
    success: bool          # 任务是否成功（结果层）
    tool_correct: bool     # 关键工具是否用对（轨迹层）
    steps: int             # 模型往返轮次
    tokens: int            # 累计 token
    latency_s: float       # 端到端延迟
    hit_max_iters: bool    # 是否触发强制停止上限


def aggregate(runs) -> dict:
    n = len(runs)
    lat = sorted(r.latency_s for r in runs)
    return {
        "task_success_rate": round(sum(r.success for r in runs) / n, 3),
        "tool_correct_rate": round(sum(r.tool_correct for r in runs) / n, 3),
        "avg_steps": round(mean(r.steps for r in runs), 2),
        "avg_tokens": round(mean(r.tokens for r in runs), 1),
        "p95_latency": round(quantiles(lat, n=20)[18], 2),
        "forced_stop_rate": round(sum(r.hit_max_iters for r in runs) / n, 3),
    }


def run() -> None:
    runs = [
        RunMetrics(True,  True,  4,  1200,  2.1, False),
        RunMetrics(True,  True,  6,  2100,  3.4, False),
        RunMetrics(True,  False, 9,  4200,  7.9, False),   # 结果对但工具用错=侥幸成功
        RunMetrics(False, True, 11,  5000, 11.2, False),   # 工具对但结果错=知识/数据问题
        RunMetrics(False, False, 20, 9000, 18.0, True),    # 循环失控触发强停
    ]
    m = aggregate(runs)
    for k, v in m.items():
        print(f"{k}={v}")
    gap = m["task_success_rate"] - m["tool_correct_rate"]
    print(f"结果-轨迹差={round(gap,3)}  (聚合后可能相互抵消，会掩盖问题)")
    # 四象限逐条统计：揭示聚合指标掩盖的结构
    quad = {"理想": 0, "侥幸成功": 0, "好过程坏结果": 0, "彻底失败": 0}
    for r in runs:
        if r.success and r.tool_correct:
            quad["理想"] += 1
        elif r.success and not r.tool_correct:
            quad["侥幸成功"] += 1
        elif not r.success and r.tool_correct:
            quad["好过程坏结果"] += 1
        else:
            quad["彻底失败"] += 1
    print(f"四象限={quad}  (gap=0 也藏着1条侥幸成功+1条好过程坏结果)")


if __name__ == "__main__":
    run()
```
保存为 `demo06_metrics.py`，运行 `python demo06_metrics.py`。完整预期输出：
```text
task_success_rate=0.6
tool_correct_rate=0.6
avg_steps=10
avg_tokens=4300
p95_latency=22.76
forced_stop_rate=0.2
结果-轨迹差=0.0  (聚合后可能相互抵消，会掩盖问题)
四象限={'理想': 2, '侥幸成功': 1, '好过程坏结果': 1, '彻底失败': 1}  (gap=0 也藏着1条侥幸成功+1条好过程坏结果)
```
逐行讲解：

- 任务成功率和工具正确率**都是 0.6，差值为 0**——如果只看这两个聚合数字，你会以为「结果和过程一样健康」。这正是聚合指标最危险的地方。
- 四象限逐条计数才揭示真相：5 条运行里有 **1 条侥幸成功**（结果对但工具用错）和 **1 条好过程坏结果**（工具对但结果错）。这两类在聚合时相互抵消，让 gap=0，但它们是完全不同的问题——前者要靠轨迹约束堵、后者要查知识库/数据。**聚合掩盖结构，必须下钻到四象限或分类维度才能看清。**
- `forced_stop_rate=0.2`（那条 20 步触发强停的运行）是被严重低估的健康指标：强停率悄悄升高，说明越来越多任务在打转、没能自然完成，这是循环失控（第 17 章详谈）的先行信号。
- `p95_latency=22.76` 明显高于多数运行的延迟，正是「尾部体验糟糕」的量化——用平均值就会被前几条快请求掩盖。

## 真实系统对应

**官方公开机制**：Anthropic 多智能体系统把「工具效率（是否用对工具、次数是否合理）」列为 LLM 裁判的评估维度之一 [来源](https://www.anthropic.com/engineering/multi-agent-research-system)；主流 Agent 基准（τ-bench、SWE-bench 等）以任务成功率 / pass@1 为主指标 [来源](https://www.codesota.com/guides/agentic-benchmarks)；LangSmith 支持在评估里自定义任意数值指标并做聚合与趋势监控 [来源](https://docs.langchain.com/langsmith/evaluation-concepts)。**通用工程模式**：结果 + 过程双层指标、看 P95、盯先行指标、下钻四象限，是可迁移到任何监控栈的做法。**教学参考实现**：上面的 `RunMetrics` 字段与聚合方式是教学构造，真实系统的指标口径（如「一步」怎么定义、成功怎么判）需按业务约定。

需要点明边界：指标口径必须团队统一约定并固定，否则跨版本对比会失真——比如「步数」是算模型往返还是算工具调用、「成功」是结果对还是结果+轨迹都对，不同定义会得出不同结论。指标是决策依据，但阈值（多少成功率算达标、强停率多高该报警）由团队按业务风险设定，不是普适常数。

## 生产踩坑

| 症状 | 根因 | 如何观测与复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| 成功率微降却不知严重性 | 只采集结果指标 | 补采工具正确率/步数/强停率 | 结果 + 过程双层指标 | 无工具的纯生成任务 |
| 聚合数字掩盖结构性问题 | 只看总体均值 | 下钻四象限 / 分类维度 | 四象限计数 + 分类通过率 | 单一类任务无需下钻 |
| 尾部用户体验被平均掩盖 | 只看平均延迟 | 补 P95/P99 分位数 | 监控 P95/P99 而非均值 | 延迟方差极小时均值够用 |
| 循环失控无人察觉 | 未监控强停率 | 统计触顶轮次上限比例 | 把强停率设为报警项 | 明确单步任务不设循环 |
| token 成本悄悄翻倍 | 未按任务采集 token | 统计每任务累计 token 趋势 | 监控单任务 token 成本 | 短对话成本可忽略 |
| 跨版本对比结论矛盾 | 指标口径不一致 | 核对「步/成功」定义 | 固定并文档化指标口径 | 同版本内部对比影响小 |
| 侥幸成功与好过程坏结果混淆 | 只看 result-trajectory 差值 | 差值为 0 时下钻四象限 | 逐条四象限分类而非只看差 | 结果与轨迹强相关时差异小 |

## 思考：为什么说「过程指标是先行指标、成功率是滞后指标」？这对监控意味着什么？

### 回答

因为它们在因果链上的位置不同。任务成功率是链条的**末端结果**——它下降，意味着任务已经真的失败了、用户已经受到了影响，这是「事后」的信号。而工具正确率、平均步数、强停率这些过程指标处在链条的**中间环节**——它们度量的是「Agent 干活的方式」，方式先变坏，结果才随之变坏。开头故障是完美例证：新 prompt 上线后，工具正确率（是否先核验再退款）立刻从 90% 崩到 74%、平均步数从 6 涨到 10，这些先行指标在第一天就剧烈报警了；但任务成功率因为「小额订单跳过核验也碰巧对」而只轻微降了 3 个点，滞后了整整三天才在大额订单事故里暴露。对监控的意味是：**报警应该主要挂在先行指标上，而不是等成功率降了才动**。具体做法是——给工具正确率、强停率、平均步数、P95 延迟设阈值和趋势报警，让它们在成功率还没明显下降时就把值班同学叫醒；成功率则作为「确认伤害程度」的滞后校验。这样你抢的是「用户投诉之前」的时间窗，而不是「投诉之后」救火。

### 面试精简表达

成功率是末端结果、下降时用户已受影响（滞后）；工具正确率/步数/强停率是中间环节、方式先变坏（先行）。监控要把报警主要挂在先行指标上，抢在成功率下降和用户投诉之前发现问题。

## 深挖：为什么「结果-轨迹差值」不够，必须下钻四象限

演示里有个反直觉的结果：任务成功率和工具正确率都是 0.6，差值为 0，看起来「结果和过程完全一致、都健康一半」。但下钻四象限发现，这个 0 是**两类相反问题相互抵消**出来的：1 条「侥幸成功」（结果对、工具错）和 1 条「好过程坏结果」（结果错、工具对）在聚合里一正一负抵消了。如果你只看差值，会以为系统没有结构性问题；实际上它同时藏着两种需要完全不同修复手段的病。

这揭示了指标聚合的一条通则：**均值和差值会抹平结构，任何决策前都要问一句「这个数字下面藏着什么分布」**。侥幸成功要靠轨迹约束（第 3 节的 superset / 红线）去堵——因为它的结果对，普通结果评估抓不到；好过程坏结果要去查知识库和工具返回的数据质量——因为它的推理框架是对的，问题在数据。两者混在一个差值里，你连往哪个方向排查都不知道。所以生产里的指标面板，除了给聚合数字，一定要能一键下钻到分类维度和四象限，让「相互抵消的问题」现出原形。这也是为什么第 6 节的回归门禁不能只卡「整体通过率」，还要卡「分类通过率」和「红线」——单一聚合数字太容易被局部抵消掩盖。
