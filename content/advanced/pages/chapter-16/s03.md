## 真实问题

「上线三天才发现退步」故障里最刺眼的细节是：**结果层的指标一度看起来没那么糟**。因为很多退款对话里，模型虽然跳过了 `query_order` 核验，但用户的订单恰好是小额、合规的，退款结果「碰巧对了」。只有当遇到大额、需审批的订单时，「跳过核验」才酿成事故。也就是说——**只看结果，你会把一批「侥幸成功」误判为健康**；只有把中间轨迹（trajectory，Agent 一步步调了哪些工具、按什么顺序）也纳入评估，才能在事故发生前抓到「过程已经坏了」。

这一节讲轨迹评估：它评什么、有哪几种从松到严的匹配粒度、怎么用查准查全兼顾「关键步骤必到」和「允许探索」，并对齐 LangSmith AgentEvals 的四种公开匹配模式。

## 原理：结果 × 轨迹的四象限

把「结果对不对」和「轨迹好不好」两个维度交叉，得到四种典型情况：
```text
                轨迹好(高效/合理)        轨迹差(绕路/漏关键步)
              ┌────────────────────┬────────────────────┐
   结果对     │  理想               │  侥幸成功            │
              │  可复现、可信任      │  换个输入可能就崩    │
              ├────────────────────┼────────────────────┤
   结果错     │  好过程坏结果        │  彻底失败           │
              │  多半是知识/数据问题 │  推理与执行都崩了    │
              └────────────────────┴────────────────────┘
```
这张图的价值在于：**「结果对」并不等于「没问题」**。右上角的「侥幸成功」是生产里最隐蔽的坑——它在演示和小额场景里表现完美，一旦输入分布稍变（遇到大额订单）就原形毕露，开头故障正是这一格。而左下角「好过程坏结果」反而是好消息：它说明 Agent 的推理框架是对的，问题多半出在某个工具返回了脏数据或知识库不全，定位起来更容易。

轨迹评估回答的问题和结果评估互补：

| 评估维度 | 评估对象 | 回答的问题 |
|---|---|---|
| 结果评估（Outcome） | 最终输出 | 任务完成得对不对、好不好？ |
| 轨迹评估（Trajectory） | 中间过程 | 工具用对了吗？顺序合理吗？有没有漏关键步或绕路？ |

LangSmith 明确把 Agent 评估拆成最终响应、单步、轨迹三类，其中轨迹评估「评估 Agent 采取的所有步骤」，输入是整体输入、输出是工具调用序列 [来源](https://docs.langchain.com/langsmith/evaluate-complex-agent)。

## 原理：轨迹匹配的四种粒度（对齐 AgentEvals）

LangSmith 的 AgentEvals 包提供 `create_trajectory_match_evaluator`，给出四种从严到松的匹配模式 [来源](https://docs.langchain.com/langsmith/trajectory-evals)：

| 模式 | 含义 | 适用场景 |
|---|---|---|
| `strict` | 消息与工具调用完全一致、顺序一致 | 强流程：如必须「先核验政策再授权」 |
| `unordered` | 同一批工具调用，顺序可不同 | 子任务并行、无先后依赖的检索 |
| `subset` | Agent 只调用了参考内的工具（不越界） | 查效率：确保没乱调无关工具 |
| `superset` | Agent 至少覆盖参考里的关键工具（可有额外） | 查底线：确保必做动作都做了 |

选哪种，取决于任务对「路径唯一性」的要求。开头的退款流程「先 `query_order` 核验、再 `check_refund_policy`、最后 `issue_refund`」是顺序敏感的强流程，适合 `strict`；而「同时查天气和活动」这类无先后依赖的，用 `unordered` 就够。除了整段匹配，还有更贴近实战的**关键步骤查准查全**：定义「必须出现的关键工具调用」，用 precision / recall 衡量，允许 Agent 有额外的探索性调用。

## 最小可运行演示

下面用纯 Python 实现这四种模式加关键步骤 precision/recall/F1，语义对齐 AgentEvals。演示里「实际轨迹」比「参考轨迹」多查了一次物流（探索性调用），看四种模式如何给出不同结论。
```python
"""演示：轨迹评估的四种匹配模式 + 关键步骤 precision/recall，对齐 agentevals 语义。"""
from typing import Callable


def _names(traj):
    return [step["name"] for step in traj if step.get("type") == "tool_call"]


def strict_match(actual, reference) -> bool:
    """严格：工具调用序列与参考完全一致（名称+顺序+参数）。"""
    a = [(s["name"], tuple(sorted(s["args"].items())))
         for s in actual if s.get("type") == "tool_call"]
    r = [(s["name"], tuple(sorted(s["args"].items())))
         for s in reference if s.get("type") == "tool_call"]
    return a == r


def unordered_match(actual, reference) -> bool:
    """顺序无关：工具调用集合一致，顺序可不同。"""
    return sorted(_names(actual)) == sorted(_names(reference))


def superset_match(actual, reference) -> bool:
    """超集：至少覆盖参考里的全部关键工具，允许额外调用。"""
    need, got = _names(reference), _names(actual)
    return all(got.count(n) >= need.count(n) for n in set(need))


def subset_match(actual, reference) -> bool:
    """子集：只用参考内的工具，不得越界乱调（查效率）。"""
    ref = set(_names(reference))
    return all(n in ref for n in _names(actual))


def key_step_prf(actual, must_call):
    """关键步骤查准/查全/F1：允许探索性调用，只考核必经关键步。"""
    got = set(_names(actual))
    need = set(must_call)
    tp = len(got & need)
    precision = tp / len(got) if got else 0.0
    recall = tp / len(need) if need else 0.0
    f1 = 2 * precision * recall / (precision + recall) if (precision + recall) else 0.0
    return round(precision, 2), round(recall, 2), round(f1, 2)


def run() -> None:
    reference = [
        {"type": "tool_call", "name": "query_order", "args": {"id": "A-2026"}},
        {"type": "tool_call", "name": "check_refund_policy", "args": {"amt": 88}},
        {"type": "tool_call", "name": "issue_refund", "args": {"amt": 88}},
    ]
    # 实际轨迹：顺序对但中间多查了一次物流（探索性调用）
    actual = [
        {"type": "tool_call", "name": "query_order", "args": {"id": "A-2026"}},
        {"type": "tool_call", "name": "track_logistics", "args": {"id": "A-2026"}},
        {"type": "tool_call", "name": "check_refund_policy", "args": {"amt": 88}},
        {"type": "tool_call", "name": "issue_refund", "args": {"amt": 88}},
    ]
    print(f"strict   ={strict_match(actual, reference)}")
    print(f"unordered={unordered_match(actual, reference)}")
    print(f"superset ={superset_match(actual, reference)}")
    print(f"subset   ={subset_match(actual, reference)}")
    p, r, f = key_step_prf(actual, must_call=["query_order", "check_refund_policy", "issue_refund"])
    print(f"关键步骤 precision={p} recall={r} f1={f}")


if __name__ == "__main__":
    run()
```
保存为 `demo03_trajectory.py`，运行 `python demo03_trajectory.py`。完整预期输出：
```text
strict   =False
unordered=False
superset =True
subset   =False
关键步骤 precision=0.75 recall=1.0 f1=0.86
```
逐行讲解：

- `strict=False`：实际轨迹多了 `track_logistics`，序列和参考不完全一致，严格模式判失败——它太苛刻，适合真正的强流程。
- `unordered=False`：不是顺序问题，而是**集合就不同**（多了一个工具），所以顺序无关模式也判失败。
- `superset=True`：三个关键工具 `query_order / check_refund_policy / issue_refund` **全都覆盖到了**，允许额外调用，所以超集模式通过——这正好用来「查底线：必做的做了没」。
- `subset=False`：实际调用了参考外的 `track_logistics`，越界了，所以子集模式判失败——它用来「查效率：有没有乱调无关工具」。
- 关键步骤 `precision=0.75`（4 个调用里 3 个是关键步）、`recall=1.0`（3 个关键步一个不漏）、`f1=0.86`：这是最贴近实战的粒度——**recall=1.0 保证「该做的都做了」，precision=0.75 提示「有一次探索性调用，效率略有余地」**，既不像 strict 那样一刀切失败，又能量化「绕路程度」。

## 真实系统对应

**官方公开机制**：AgentEvals 的 `create_trajectory_match_evaluator` 提供 strict/unordered/subset/superset 四模式，默认「同名同参」才算相等，可通过 `tool_args_match_mode` 定制参数比较；还提供 `create_trajectory_llm_as_judge` 用 LLM 评轨迹的合理性、无需参考轨迹 [来源](https://docs.langchain.com/langsmith/trajectory-evals)。**通用工程模式**：把轨迹抽象成工具调用序列、用「集合/顺序/查准查全」多粒度判定，是可迁移到任何栈的做法。**教学参考实现**：上面的 `strict_match` 等函数只为讲清语义，真实 AgentEvals 还比较消息内容、工具结果等更多字段。

需要点明边界：轨迹评估的前提是你**能拿到完整轨迹**——即每一步的工具调用、参数、结果都被结构化记录（这正是第 17 章可观测性要解决的）。没有 trace，轨迹评估无从谈起。此外，「黄金轨迹」本身要维护：任务允许多种合理解法时，硬编一条参考轨迹会误伤合理的替代路径，此时应改用 superset（查关键步）或 LLM 裁判评轨迹合理性，而非 strict。

## 生产踩坑

| 症状 | 根因 | 如何观测与复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| 侥幸成功被当健康 | 只看结果不看轨迹 | 对结果对的样本查轨迹是否漏关键步 | 结果 + 轨迹双维度评估 | 无工具的纯生成任务 |
| 大额退款漏核验 | 无 must_call 轨迹约束 | 检查轨迹是否含 query_order | superset 卡关键步 + 顺序约束 | 只读无副作用任务 |
| strict 误伤合理替代路径 | 任务多解却用严格匹配 | 换一条合理解法即判失败 | 改 superset 或 LLM 裁判评轨迹 | 单一强流程本就该 strict |
| 乱调无关工具没人管 | 无 subset 约束 | 注入一次无关调用看是否放行 | subset 查效率、限制越界 | 探索期允许自由探索 |
| 轨迹评估跑不起来 | 没有结构化 trace | 查是否记录每步工具调用与结果 | 先补可观测再做轨迹评估 | 单步任务轨迹退化为结果 |
| 参数对了工具对了仍误判 | 参数比较模式过严 | 数值精度/大小写差异致不等 | 调 tool_args_match_mode 容差 | 需精确参数的金额类调用 |

## 思考：为什么说「侥幸成功」比「彻底失败」更危险？

### 回答

因为彻底失败是「显性」的、会被立刻发现并修复，而侥幸成功是「隐性」的、会被误判为健康从而带着定时炸弹上线。彻底失败——结果错、轨迹也乱——在任何一层评估里都会亮红，用户一眼看出不对，团队马上排查，它的危害被限制在「被发现」的那一刻。侥幸成功则相反：结果碰巧对了，聚合的成功率指标好看，演示时表现完美，于是顺利通过评审、全量上线；但它的「对」建立在运气上（输入恰好落在简单区间、工具漏调也没造成后果），一旦真实流量的分布稍微一移（比如从小额订单移到大额订单），同样的坏轨迹就会酿成真实事故。开头故障就是典型：跳过核验在小额退款里没事，在大额退款里就是「未经审批直接退款」的资损。危险的本质是**它欺骗了你的评估**——让你以为系统健康，从而放松了本该有的防线。防它的唯一办法就是不只看结果、还看轨迹：用 superset 卡住「必经关键步」、用红线卡住「绝对不能做的事」，让侥幸成功在离线评估里就因「轨迹漏关键步」而亮红。

### 面试精简表达

彻底失败是显性的、会被立刻修；侥幸成功是隐性的、结果碰巧对但轨迹已坏，会被误判健康带炸弹上线，输入分布一变就出事。必须靠轨迹评估（关键步 + 红线）才能抓住它。

## 深挖：黄金轨迹不是越严越好，而是「按任务选粒度」

新手常有个误解：轨迹评估就该用 strict，越严越安全。恰恰相反——**匹配粒度选错，比不做轨迹评估还糟**，因为它会制造大量假阴性（把合理的替代路径判为失败），逼得团队要么频繁维护黄金轨迹、要么干脆关掉轨迹评估。正确的选法是问一句「这个任务的路径唯一吗」：

- **路径唯一、顺序敏感、且涉及安全**（先鉴权再退款、先核验再下单）：用 `strict` 或 `superset + 顺序约束`，这类流程就该被死死卡住。
- **需要一组工具但顺序无所谓**（并行查多个数据源）：用 `unordered`。
- **只关心「关键步别漏」，允许 Agent 自由探索**（大多数真实任务）：用 `superset` 或关键步骤 recall，这是最常用、最耐维护的粒度。
- **想额外保证「别乱调、要高效」**：叠加 `subset` 或看 precision。

一个实用组合是：用 `superset`（recall 视角）守住底线「关键步一个不能漏」，同时看 precision「有没有绕路」但不把它设为硬门禁——这样既保证安全，又给 Agent 留出合理的探索空间。开头故障如果当初就对退款任务加了一条 `superset` 约束「必须包含 query_order + check_refund_policy」，那版跳过核验的 prompt 在离线评估里就会因 recall < 1.0 而直接亮红，根本上不了线。
