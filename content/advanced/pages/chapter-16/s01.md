## 真实问题

回到开头那次「上线三天才发现退步」的故障。复盘会上，团队负责人把上线前的聊天记录翻出来：4 月 18 日上午，工程师在群里发了六段新旧 prompt 的对比截图，配文「明显礼貌多了，我先全量了」。没有人反对，因为**没有任何一个数字可以反对**——当时手上唯一的判据是「读起来的感觉」。三天后一次解决率从 82% 掉到 71%，损失的是真金白银的客服人力与用户耐心，而这本可以在上线前十分钟被一道离线评估拦下。

这一节要把「无法评估 = 不能上线」这条硬原则钉死，并讲清一件反直觉的事：Agent 评估之所以难，不是工程师偷懒，而是 LLM（Large Language Model，大语言模型）应用天然缺了传统软件的三道防线。理解了「难在哪」，你才不会用错方法——比如指望把 `temperature` 调到 0 就万事大吉。

## 原理：LLM 应用丢失了传统软件的三道防线

传统软件工程靠三道防线把「改坏了」挡在上线之前：**编译器**（语法/类型错误当场报错）、**单元测试**（输入 X 断言输出必等于 Y）、**类型系统**（约束数据结构）。LLM 应用把这三道防线几乎全丢了：

- 模型不会「编译报错」：一段烂 prompt 照样能跑出结果，只是结果差。
- 同样的输入，今天和明天、这次和下次的输出可能不同，`assert x == y` 直接失效。
- 自然语言没有静态类型来约束「这段回复必须先核验订单再退款」。

所以评估集本质上是我们为**概率系统重新发明的回归测试**。它不是锦上添花，而是补回那三道被 LLM 拿走的防线。Anthropic 在《Building Effective Agents》里反复强调：要保持简单、可度量，先用评估建立地基再增加复杂度 [来源](https://www.anthropic.com/engineering/building-effective-agents)。

把 Agent 评估比传统单元测试难的四个特性列清楚：

| 维度 | 传统单元测试 | Agent 评估 |
|---|---|---|
| 判定方式 | 精确相等 `assert x == y` | 语义匹配 / 评分 / 阈值 |
| 输出空间 | 有限、确定 | 开放、无限 |
| 一次运行结论 | 可信（确定性） | 需多次采样看分布 |
| 关注点 | 只看最终返回值 | 结果 + 中间轨迹 |
| 通过标准 | 二元（过 / 不过） | 连续分数 + 通过率 |
| 失败定位 | 堆栈直接指向行号 | 需 trace（追踪）才能定位是哪一步 |

这张表最重要的 takeaway：**Agent 评估里「跑一次通过」几乎没有意义**。因为非确定性，你必须跑多次，看它的通过率是 5/5 还是 3/5，这才有统计意义。

## 深挖：非确定性从哪来，为什么 `temperature=0` 关不掉

很多人第一反应是「把 temperature 设成 0 不就确定了吗」。这是最常见的误区。采样温度设为 0 只能让模型在**同一次推理**里趋向选概率最高的 token，但它并不能保证跨请求、跨时间、跨硬件完全一致：

- **浮点非结合性**：GPU 上的并行归约运算，不同 batch 大小、不同并发下累加顺序可能不同，浮点误差会让 logits 出现微小差异，在两个概率相近的候选 token 之间「翻盘」。
- **服务端版本漂移**：你调用的是别人的 API，模型权重、系统 prompt、路由策略随时可能被供应商悄悄更新。
- **上下文差异**：多步 Agent 里，第一步一个微小措辞差异，会像蝴蝶效应一样让后续每一步都走上不同分支。

结论：**非确定性是 LLM 系统的固有属性，不能靠一个参数消除，只能靠评估方法去容纳它**。这就是为什么要从「精确相等」转向「通过率 / 打分 / 分布」这类更宽松的判定。

## 最小可运行演示

下面用一个确定性可复现的「抖动模型」模拟真实模型的非确定性：它单次答对的概率是 60%，用固定 seed 让输出可逐字复核。重点看「只跑一次」如何得出自相矛盾的结论，而 pass@k / 通过率才稳定可信。
```python
"""演示：为什么 Agent 评估「跑一次通过」几乎没有意义（非确定性 + 通过率）。"""
import random


class JitterModel:
    """确定性可复现的『抖动模型』：同一问题在不同采样里给出对/错答案，
    用固定 seed 模拟真实模型的非确定性，让输出可逐字复核。"""

    def __init__(self, correct_prob: float) -> None:
        self.correct_prob = correct_prob

    def answer(self, question: str, rng: random.Random) -> str:
        gold = "88.00"
        return gold if rng.random() < self.correct_prob else "83.00"


def pass_at_k(model, question, gold, k, seed):
    """对同一样本采样 k 次，返回『至少一次答对』(pass@k) 与『每次都对』(pass^k)。"""
    rng = random.Random(seed)
    hits = [model.answer(question, rng) == gold for _ in range(k)]
    return any(hits), all(hits), sum(hits)


def run() -> None:
    model = JitterModel(correct_prob=0.6)     # 单次答对概率 60%
    q, gold, k = "订单 A-2026 应退多少钱？", "88.00", 5
    any_hit, all_hit, n = pass_at_k(model, q, gold, k, seed=2026)
    print(f"单次答对概率=0.60  采样次数k={k}")
    print(f"pass@{k}(至少一次对)={any_hit}  命中 {n}/{k}")
    print(f"pass^{k}(每次都对)={all_hit}")
    # 只跑一次会怎样：换 4 个 seed 各跑一次，结论互相矛盾
    single = []
    for s in (1, 2, 3, 4):
        rng = random.Random(s)
        single.append(model.answer(q, rng) == gold)
    print(f"只跑一次的结论(4个seed)={single}  <- 同一Agent时对时错")


if __name__ == "__main__":
    run()
```
保存为 `demo01_nondeterminism.py`，运行 `python demo01_nondeterminism.py`。完整预期输出：
```text
单次答对概率=0.60  采样次数k=5
pass@5(至少一次对)=True  命中 4/5
pass^5(每次都对)=False
只跑一次的结论(4个seed)=[True, False, True, True]  <- 同一Agent时对时错
```
逐行讲解：

- `JitterModel` 用固定 `random.Random(seed)` 保证输出可复现，这是把「非确定性」搬进确定性演示的教学技巧——真实模型的抖动无法复现，但道理一样。
- `pass@k` 和 `pass^k` 是两个极端：前者「至少一次对」偏乐观（常用于代码生成的 pass@k），后者「每次都对」偏严格。生产里更常看的是**命中率 `n/k`**（这里 4/5=80%），它落在两个极端之间，最能反映真实可靠度。
- 最后四行是全节的题眼：**同一个 Agent、同一道题，只跑一次的结论是 `[True, False, True, True]`——时对时错**。谁在演示时恰好抽到 True 就说「能用」，本质是拿运气当结论。

## 真实系统对应

**官方公开机制**：LangSmith 的评估概念文档明确把评估分为「离线（对数据集）」与「在线（对生产流量）」，并指出对非确定性系统要看聚合指标而非单次结果 [来源](https://docs.langchain.com/langsmith/evaluation-concepts)；OpenAI Evals 把「量化分数、随时间追踪、跨模型版本对比、用于门禁部署」列为核心用途 [来源](https://developers.openai.com/api/docs/guides/evals)。**通用工程模式**：多次采样看通过率、把评估当回归测试、上线前设准入门槛，是可迁移到任何厂商的方法。**教学参考实现**：上面的 `JitterModel` 只为让「非确定性」可复现，不代表任何真实模型的采样分布。

需要点明一个边界：`temperature=0` 在某些确定性子任务（如固定格式抽取）里确实能显著降低抖动，此时对这些子任务跑较少次数是合理的成本权衡；但只要链路里有任何一步走真实大模型推理，就不能假设整体完全确定。

## 生产踩坑

| 症状 | 根因 | 如何观测与复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| 灰度「跑几个例子还行」后翻车 | 单次结果当结论 | 同一样本采样 5 次看命中分布 | 多次采样看通过率再决策 | 确定性规则子任务可少采样 |
| 以为 temperature=0 就能只跑一次 | 误以为温度消除全部随机 | 同一输入跨时间多次调用对比 | 承认非确定性，用分布判定 | 纯抽取类子任务抖动确实很小 |
| 优化两周说不清好没好 | 无评估基线可对比 | 让人复述「怎么知道变好了」 | 先建离线基线再优化 | 探索期原型可暂缓，但上线前必补 |
| 换新模型不敢换 | 无法量化换后是否退步 | 用同一评估集跑新旧模型 | 评估集做跨模型对照 | 无评估集时先补集再评估 |
| 单元测试思路套 Agent 全红 | 用 assert 精确相等 | 断言 LLM 输出严格相等即失败 | 改用语义匹配 / 评分 / 阈值 | 结构化 JSON 字段可精确校验 |

## 思考：面试官问「你们上线一个 Agent 功能前怎么判断它够好了」，弱答案和强答案差在哪？

### 回答

差在有没有把「好」变成可度量、可对比、可回归的东西。弱答案是「我们测了几个例子看着还行」——它经不起追问：测了几个？覆盖了哪些真实场景？跑了几次？和上一版比是升是降？这些全答不上来，说明「好」还停留在感觉层面。强答案有三个支点：其一，有一个**从线上真实 case 沉淀的离线评估集**，而不是临时拍脑袋造的几个例子；其二，看**多个维度**——任务成功率、工具正确率、成本/延迟，而不是只看措辞；其三，设了**准入门槛与回归对比**，改动前后跑同一评估集，整体通过率不许比基线跌超过某阈值、关键类不许崩盘、红线零容忍，达不到就不上线。一句话概括：弱答案把评估当「上线前瞄一眼」，强答案把评估当「上线的准入闸门」。能再补一句「而且我们承认非确定性，所以每条样本采样多次看通过率而非跑一次」，就显得真正踩过坑。

### 面试精简表达

弱答案「测了几个例子还行」；强答案「有从线上沉淀的离线评估集，跑通过率+工具正确率+成本三维、多次采样看分布、设了准入门槛与回归对比，达不到不上线」。

## 事故回放：那六段「读起来更顺」的截图为什么骗了所有人

回到 4 月 18 日的群聊。六段对比截图全都是「安抚话术」的措辞对比——旧版「好的，帮您退款」，新版「非常理解您的心情，这就为您处理」。所有人的注意力都被吸引到「哪句更礼貌」上，而**没有一个人问：新版有没有在退款前调用 `query_order` 核验订单？** 事后拉轨迹日志才发现，新 prompt 加长了共情前缀，挤占了模型的注意力，让它在约 11% 的退款对话里跳过了核验步骤直接答应退款。

这暴露了两个更深的教训。第一，**措辞是最容易被评估、也最容易误导人的维度**——它直观、可读，于是抢走了本该分给「任务是否完成、工具是否用对」的注意力。第二，**没有轨迹评估，你连问题出在哪都不知道**：如果当时有一条「退款必经 query_order」的轨迹约束（第 3 节），这版 prompt 在离线评估里就会亮红，根本到不了全量。优化前只有六段截图和一句「感觉更顺」；优化后，每次 prompt 改动都要过一遍固定评估集，结果与轨迹一起亮灯，措辞好不好只是其中一盏灯而已。
