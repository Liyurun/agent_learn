## 真实问题

「上线三天才发现退步」故障复盘的最后一问是：「别人家的 Agent 是怎么防住这种退步的？」有人提议「我们直接刷 τ-bench、SWE-bench 这些公开榜单，分高就说明我们的 Agent 强」。这个想法一半对一半错。公开基准（benchmark）能告诉你「模型/框架在标准任务上的相对水平」，但它**测不出你的客服 Agent 会不会跳过退款核验**——因为那是你的业务、你的工具、你的红线。更关键的是，基准分数高的 Agent 在生产里翻车是常态：一篇 2026 年的综述标题就叫《Your Agent Aced the Benchmark. Production Disagreed.》（你的 Agent 刷爆了基准，生产却不同意）[来源](https://www.channel.tel/blog/ai-agent-evaluation-benchmarks-predict-production)。

这一节讲两件事：主流公开基准（2026 年现状）各自测什么、局限在哪、怎么正确使用；以及真正能防住开头那种退步的——**从真实失败沉淀的私有回归测试集 + CI（Continuous Integration，持续集成）门禁**。

## 原理：公开基准的地图（2026 年现状）

Agent 基准在 2026 年已有十几个，按测什么大致分几类。下表汇总几个高频基准的定位（分数随榜单更新，以最新官方榜单为准）[来源](https://www.codesota.com/guides/agentic-benchmarks) [来源](https://www.channel.tel/blog/ai-agent-evaluation-benchmarks-predict-production)：

| 基准 | 测什么 | 人类基线（约） | 生产相关性 | 局限 |
|---|---|---|---|---|
| τ-bench / τ²-bench | 工具调用 + 多轮对话 + 状态保持（零售/航空/电信客服） | ~95% | 很高 | 场景固定，覆盖不了你的私有工具 |
| SWE-bench Verified | 真实代码仓库缺陷修复 | ~95% | 高 | 仅限代码域 |
| GAIA | 多步推理 + 工具使用的通用助理 | ~92% | 中 | 偏问答，非长流程副作用 |
| WebArena / OSWorld | 网页/操作系统的真实环境操作 | 72%~78% | 高（但极难） | 环境搭建重，评测慢 |

几个必须记住的判断：

- **基准会饱和**：一年前有区分度的基准，今年 SOTA（State of the Art，业界最佳）可能已逼近人类基线甚至「刷爆」，此时它就失去了区分力（如某些 τ²-bench 子集已接近饱和）[来源](https://codersera.com/blog/ai-agent-benchmarks-state-of-leaderboard-may-2026/)。
- **基准分 ≠ 生产表现**：基准是「标准化考试」，你的业务是「真实工作」；两者输入分布、工具集、失败代价都不同。
- **基准用来选型，不用来验收**：它帮你在「用哪个模型/框架」时做横向对比，但「我这版改动能不能上线」必须靠你自己的私有评估集。

## 原理：回归测试才是防退步的主力

真正能防住开头那种退步的，是**回归测试**：把每一个修好的 bug、每一次事故沉淀成评估样本，此后任何改动都要重新跑一遍，通过率低于门槛就拒绝合并。这就是把第 1 节说的「评估集是为概率系统重新发明的回归测试」落地成 CI 门禁。

回归门禁的三条硬规则（缺一不可）：

1. **整体通过率不许比基线跌超过容忍度**（如 2 个百分点，容忍正常随机波动）。
2. **没有任何单一分类崩盘**（如某类跌超 10 个点即拒绝，防「总分不降、局部崩盘」）。
3. **红线零容忍**（如「大额退款未审批」违规数必须为 0，一次都不许）。

OpenAI Evals 明确把评估用途定位为「量化分数、随时间追踪、跨模型版本对比、用于门禁部署」[来源](https://developers.openai.com/api/docs/guides/evals)；LangSmith 也把离线评估定位为「在用户之前抓回归」[来源](https://www.langchain.com/langsmith/evaluation)。

## 最小可运行演示

下面把回归门禁做成可运行代码：对基线 Agent 和引入了回归的 buggy Agent 各跑一遍评估集，门禁按三条硬规则判定是否放行。
```python
"""演示：回归门禁——CI 里对比基线，整体不降、无单类崩盘、红线零容忍才放行。"""


def run_suite(agent, cases, samples=3):
    """对每条样本采样多次，返回整体/分类通过率与红线违规数。"""
    passed = total = 0
    per_cat = {}
    redline_violations = 0
    for c in cases:
        cp = 0
        for i in range(samples):
            out = agent(c["q"], seed=i)
            ok = out["answer"] == c["gold"]
            # 红线：金额>500 未经审批直接退款
            if c.get("redline") and out.get("did_refund_without_approval"):
                redline_violations += 1
            cp += ok
            passed += ok
            total += 1
        slot = per_cat.setdefault(c["cat"], [0, 0])
        slot[0] += cp
        slot[1] += samples
    return {
        "overall": round(passed / total, 3),
        "per_category": {k: round(v[0] / v[1], 3) for k, v in per_cat.items()},
        "redline_violations": redline_violations,
    }


def gate(baseline, current, tol=0.02, cat_drop=0.10):
    """回归门禁：三条硬规则，任一不满足即拒绝合并。"""
    reasons = []
    if current["overall"] < baseline["overall"] - tol:
        reasons.append(f"整体通过率回归 {baseline['overall']}->{current['overall']}")
    for cat, rate in current["per_category"].items():
        base = baseline["per_category"].get(cat, 0)
        if rate < base - cat_drop:
            reasons.append(f"分类[{cat}]崩盘 {base}->{rate}")
    if current["redline_violations"] > 0:      # 红线零容忍
        reasons.append(f"触碰红线 {current['redline_violations']} 次")
    return (len(reasons) == 0), reasons


def good_agent(q, seed=0):
    table = {"退款金额": "88.00", "物流": "已签收", "大额退款": "需人工审批"}
    for kw, ans in table.items():
        if kw in q:
            return {"answer": ans, "did_refund_without_approval": False}
    return {"answer": "未知", "did_refund_without_approval": False}


def buggy_agent(q, seed=0):
    """引入回归：大额退款绕过审批，且物流类答错。"""
    if "大额退款" in q:
        return {"answer": "已退款", "did_refund_without_approval": True}
    if "物流" in q:
        return {"answer": "在途" if seed else "已签收",
                "did_refund_without_approval": False}
    if "退款金额" in q:
        return {"answer": "88.00", "did_refund_without_approval": False}
    return {"answer": "未知", "did_refund_without_approval": False}


def run() -> None:
    cases = [
        {"q": "退款金额是多少", "gold": "88.00", "cat": "退款"},
        {"q": "物流到哪了", "gold": "已签收", "cat": "查询"},
        {"q": "大额退款怎么办", "gold": "需人工审批", "cat": "退款", "redline": True},
    ]
    baseline = run_suite(good_agent, cases)
    current = run_suite(buggy_agent, cases)
    print("baseline=", baseline)
    print("current =", current)
    ok, reasons = gate(baseline, current)
    print(f"门禁通过={ok}")
    for r in reasons:
        print(f"  拒绝原因: {r}")


if __name__ == "__main__":
    run()
```
保存为 `demo07_regression_gate.py`，运行 `python demo07_regression_gate.py`。完整预期输出：
```text
baseline= {'overall': 1.0, 'per_category': {'退款': 1.0, '查询': 1.0}, 'redline_violations': 0}
current = {'overall': 0.444, 'per_category': {'退款': 0.5, '查询': 0.333}, 'redline_violations': 3}
门禁通过=False
  拒绝原因: 整体通过率回归 1.0->0.444
  拒绝原因: 分类[退款]崩盘 1.0->0.5
  拒绝原因: 分类[查询]崩盘 1.0->0.333
  拒绝原因: 触碰红线 3 次
```
逐行讲解：

- `baseline` 全绿（整体 1.0、各类 1.0、红线 0），这是上线前固化的准入基线。
- `buggy_agent` 模拟了开头那种回归：大额退款绕过审批（红线）+ 物流类抖动答错。跑出来 `current` 整体掉到 0.444、退款类掉到 0.5、查询类掉到 0.333、红线违规 3 次。
- `gate` 一次性给出**四条拒绝原因**：整体回归、退款类崩盘、查询类崩盘、触碰红线。这就是回归门禁的价值——它不是给一个模糊的「变差了」，而是**逐条列出为什么拒绝合并**，值班同学照着就能定位。
- 特别注意红线那条：即便整体通过率没崩，只要 `redline_violations > 0`，门禁也会拒绝。**红线是零容忍的独立闸门**，因为「大额退款未审批」一次就是真金白银的资损，通过率再高也不能拿它冒险。开头故障如果当初就有这道门禁，那版 prompt 根本合不进主干。

## 真实系统对应

**官方公开机制**：OpenAI Evals 支持对同一评估在不同模型/参数上跑并对比、用于部署门禁（注意其托管 Evals 平台有弃用时间线，能力向 API 侧迁移，以官方公告为准）[来源](https://developers.openai.com/api/docs/guides/evals)；LangSmith 的离线评估用于「在用户之前抓回归」并支持接入 CI [来源](https://www.langchain.com/langsmith/evaluation)；公开 Agent 基准（τ-bench、SWE-bench、GAIA、WebArena）提供标准化任务与任务成功率口径 [来源](https://www.codesota.com/guides/agentic-benchmarks)。**通用工程模式**：三条硬规则的回归门禁、私有集验收 + 公开集选型、失败沉淀成回归样本，是可迁移到任何 CI 系统的做法。**教学参考实现**：上面的 `gate` 阈值（0.02、0.10）是教学值，真实门槛需按你评估集的方差实测校准。

需要点明边界：公开基准分数随榜单和模型迭代快速变化，本文列的人类基线与相对难度是某次检索的快照，务必以最新官方榜单为准；不要把「某模型某榜单分数」写死进决策文档。此外，回归门禁的阈值不是普适常数——评估集方差大就要放宽容忍度、否则随机波动会频繁误拒。

## 生产踩坑

| 症状 | 根因 | 如何观测与复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| 刷榜分高线上却翻车 | 拿公开基准当验收标准 | 对比基准输入与你的真实分布 | 基准选型、私有集验收 | 通用能力横向对比可用基准 |
| 评估集泄题、分虚高 | 评估样本被拿去调优 prompt | 检查 few-shot 是否含评估样本 | held-out 集与调优数据隔离 | 无 |
| 总分不降但某类崩盘 | 门禁只卡整体通过率 | 引入单类回归看是否放行 | 门禁加分类崩盘规则 | 单一类任务 |
| 大额退款回归被放行 | 门禁无红线零容忍规则 | 让 buggy agent 触红线 | 红线设独立零容忍闸门 | 无副作用只读任务 |
| 门禁频繁误拒正常改动 | 容忍度过严、未考虑方差 | 空跑同版本看波动幅度 | 按评估集方差调容忍度 | 方差极小的确定性子任务 |
| 用饱和基准做区分 | 基准已逼近人类基线 | 看 SOTA 与人类基线差距 | 换更难或私有基准 | 尚有区分度的基准仍可用 |
| 回归集长期不更新 | 无失败回流机制 | 检查近月有无新样本入库 | 事故/差评自动沉淀成样本 | 业务极稳定时更新可放缓 |

## 思考：公开基准分数很高，为什么不能直接拿来当「可以上线」的依据？

### 回答

因为公开基准和你的生产环境测的根本不是同一件事。基准是「标准化考试」：固定的任务集、固定的工具、固定的评分口径，追求的是让不同模型/框架可横向比较。而你的生产是「真实工作」：你自己的私有工具（`query_order`、`issue_refund`）、你自己的业务红线（大额退款要审批）、你自己的用户输入分布（长尾、口语、夹带情绪）、你自己的失败代价（一次资损远比答错一道题严重）。这四样基准全都覆盖不到。所以基准分高只能说明「这个模型在标准任务上相对强」，说明不了「它在你的客服场景里不会跳过核验」——开头故障那种退步，任何公开基准都测不出来，因为它压根不知道你有个 `query_order` 必须先调。而且基准还会饱和：当 SOTA 逼近人类基线，分数差异更多是噪声而非真实能力差。正确的分工是：**公开基准用来选型**（在候选模型/框架之间横向对比、缩小范围），**私有回归集用来验收**（这一版改动能不能上线，必须跑你自己从真实失败沉淀的评估集 + 三道门禁）。把基准分当上线依据，等于拿高考分数证明「我今天的工作没出错」——维度都对不上。

### 面试精简表达

基准测的是标准化任务、可横向比模型；你的生产有私有工具、业务红线、真实分布、失败代价，基准全覆盖不到，还会饱和。所以基准用来选型、私有回归集用来验收，不能拿基准分当上线依据。

## 深挖：评估集「泄题」——最隐蔽的分数造假

回归测试有个反噬的陷阱：**评估集泄题**。如果你把评估集里的样本也拿去优化 prompt（比如塞进 few-shot 示例、或据此专门调参），Agent 就会「背答案」——评估分虚高，线上照崩。这就像把考试题提前发给学生，考出来的高分毫无意义。

泄题之所以隐蔽，是因为它不会报错、不会亮红，反而让你的评估指标越来越好看，给你强烈的虚假信心。等到线上真实流量（没见过的题）一来，才发现 Agent 只会做「背过的题」。防泄题的核心是**严格隔离**：

- 留一个 **held-out 集**（保留集），从不用于任何优化、调参、few-shot，只用于最终上线验收——就像期末考的密封卷。
- 优化用的数据（开发集）和验收用的数据（held-out）物理隔离、专人管理，杜绝无意间的交叉。
- 定期从新的线上失败里补充 held-out，因为一旦某批样本被团队反复看过、优化过，它就「见过光」了、区分力下降，需要新鲜的未见样本补充。

这条和第 1 节的主题呼应：评估集是为概率系统重新发明的回归测试，而任何回归测试一旦被拿去「训练」被测对象，就失去了作为独立防线的意义。面试里如果被问「评估分很高但线上不好，可能什么原因」，泄题是必答的第一条，其次才是「评估集分布和线上不一致」「只看结果没看轨迹」「裁判没校准」。
