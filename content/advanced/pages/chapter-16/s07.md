## 真实问题

「上线三天才发现退步」结案后，团队想把教训沉淀成一份能防复发的清单，却发现难点不在「知道要评估」，而在**评估体系本身有太多可以做错的地方**：数据集会泄题、裁判有偏差、只看结果会漏侥幸成功、只看聚合会被局部抵消掩盖、门禁阈值太严会误拒太松会放行、基准分高会给人虚假信心……一句「我们上了评估」根本不构成保障。把评估各环节的坑逐条列成「症状—根因—观测—修复—边界」，再用多道「思考+回答」把全章方法论收口，才是这份清单的价值。

这一节做两件事：先给出一张覆盖 Agent 评估端到端各环节的生产建议矩阵与一个可运行的「评估健康度自检器」；再用多道对齐高频面试题的「思考+回答」把全章收尾。

## 诊断顺序：评估体系自身的分层自检

当有人说「我们的评估好像不太靠谱」，不要笼统地「加更多样本」，而是按评估流水线分层自检，每层都有可观测证据：

1. **数据层**：评估集是否从真实失败沉淀？是否和调优数据隔离（防泄题）?分类是否平衡？覆盖是否追得上线上分布？
2. **采样层**：是否多次采样看通过率，而非跑一次？采样次数是否够(关键样本更多)？
3. **判定层**：可判定任务是否优先用标准答案？开放任务的裁判是否校准过（Cohen's Kappa 达标）？是否防了位置/长度/自我偏好偏差？
4. **轨迹层**：是否不只看结果、也看轨迹？关键步（must_call）和红线（must_not_do）是否落进约束？
5. **指标层**：是否结果 + 过程双层？是否看 P95 而非均值？是否盯先行指标？聚合是否能下钻分类/四象限？
6. **门禁层**：CI 是否卡整体通过率 + 分类崩盘 + 红线零容忍三条？阈值是否按方差校准？
7. **闭环层**：线上失败是否回流成新样本？held-out 是否定期更新？

## 生产建议：Agent 评估端到端症状矩阵

下面把全章各环节的坑汇成一张矩阵，每行都是一个真实会发生、可观测、有修复、也有不适用边界的条目。它是这份清单的主体。

| 症状 | 根因 | 如何观测与复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| 上线才发现退步 | 无离线基线对比 | 回放上线前后同一批样本 | 改动前必过离线基线 | 探索期原型可暂缓 |
| 灰度「跑几个还行」翻车 | 单次结果当结论 | 同样本采样 5 次看命中分布 | 多次采样看通过率 | 确定性子任务可少采样 |
| 以为 temperature=0 就确定 | 误以为温度消除全部随机 | 同输入跨时间多次调用 | 承认非确定性、看分布 | 纯抽取子任务抖动小 |
| 离线分高线上却差 | 数据集分布≠真实分布 | 对比离线与线上输入分布 | 从线上回流样本补集 | 输入稳定领域差异小 |
| 失败样本白白流失 | 在线只打分不回收 | 检查 bad case 是否落库 | 失败样本结构化回流 | 无法结构化的一次性输入 |
| 侥幸成功被当健康 | 只看结果不看轨迹 | 对结果对的样本查轨迹 | 结果 + 轨迹双维度评估 | 无工具纯生成任务 |
| 大额退款漏核验 | 无 must_call 轨迹约束 | 检查轨迹是否含关键步 | superset 卡关键步 + 顺序 | 只读无副作用任务 |
| strict 误伤合理替代路径 | 任务多解却用严格匹配 | 换合理解法即判失败 | 改 superset 或 LLM 裁判评轨迹 | 单一强流程本就该 strict |
| 礼貌空话得高分 | rubric 未锚定「是否解决」 | 构造礼貌空话样本 | rubric 以行为描述锚定 | 纯语气评估另论 |
| 成对比较结论随顺序变 | 位置偏差 | 交换顺序看翻转率 | 两序各跑取平均 | 单答案打分无此问题 |
| 选手当裁判分虚高 | 自我偏好偏差 | 换另一家模型交叉打分 | 裁判用不同模型 | 无更强模型时靠人工 |
| 裁判分与人工总对不上 | 裁判未校准 | 算 Cohen's Kappa | 校准 rubric 至 kappa 达标 | 一致率高时无需频繁校准 |
| 成功率微降不知严重性 | 只采集结果指标 | 补采工具正确率/步数/强停率 | 结果 + 过程双层指标 | 无工具纯生成任务 |
| 聚合掩盖结构性问题 | 只看总体均值 | 下钻四象限/分类维度 | 四象限计数 + 分类通过率 | 单一类任务 |
| 尾部体验被平均掩盖 | 只看平均延迟 | 补 P95/P99 | 监控分位数而非均值 | 延迟方差极小时 |
| 循环失控无人察觉 | 未监控强停率 | 统计触顶轮次比例 | 强停率设报警项 | 明确单步任务 |
| 刷榜分高线上翻车 | 拿公开基准当验收 | 对比基准与真实分布 | 基准选型、私有集验收 | 通用能力横向对比 |
| 评估集泄题分虚高 | 评估样本被拿去调优 | 查 few-shot 是否含评估样本 | held-out 与调优数据隔离 | 无 |
| 门禁只卡整体、局部崩盘 | 门禁规则不全 | 引入单类回归看是否放行 | 加分类崩盘 + 红线规则 | 单一类任务 |
| 门禁频繁误拒 | 容忍度过严未顾方差 | 空跑同版本看波动 | 按方差调容忍度 | 确定性子任务 |
| 用饱和基准做区分 | 基准逼近人类基线 | 看 SOTA 与基线差距 | 换更难或私有基准 | 尚有区分度的基准 |

RBAC（Role-Based Access Control，基于角色的访问控制）应管控「谁能看评估数据与线上 trace」；PII（Personally Identifiable Information，个人可识别信息）在写入评估集与追踪前应最小化与脱敏；SLO（Service Level Objective，服务级目标）里可把 P95 延迟与任务成功率设为可度量目标。

## 最小可运行演示：评估健康度自检器

把上面的分层自检固化成一个规则树，输入一组评估体系的现状指标，输出首要缺陷层，避免「一切归结为样本不够」。
```python
"""评估健康度自检器（纯 Python）：把『评估好像不靠谱』拆到可行动的层。"""
from __future__ import annotations


def self_check(s: dict) -> list[str]:
    findings = []
    if s["samples_per_case"] < 3:
        findings.append("采样层：采样次数不足，单次结果不可信，提到至少3-5次")
    if not s["dataset_isolated"]:
        findings.append("数据层：评估集与调优数据未隔离，存在泄题风险，建 held-out")
    if s["judge_kappa"] < 0.6:
        findings.append("判定层：裁判与人工一致性偏低(kappa<0.6)，先校准 rubric")
    if not s["trajectory_checked"]:
        findings.append("轨迹层：只看结果未看轨迹，补 must_call/must_not_do 约束")
    if not s["watch_leading_metrics"]:
        findings.append("指标层：未盯先行指标(工具正确率/强停率)，补过程指标监控")
    if not s["gate_has_redline"]:
        findings.append("门禁层：门禁缺红线零容忍规则，高风险动作可能被放行")
    return findings or ["评估体系健康，保持线上失败回流与 held-out 定期更新"]


def run() -> None:
    status = {
        "samples_per_case": 1,        # 只跑一次
        "dataset_isolated": False,    # 未隔离，可能泄题
        "judge_kappa": 0.47,          # 裁判没校准好
        "trajectory_checked": False,  # 只看结果
        "watch_leading_metrics": True,
        "gate_has_redline": False,    # 门禁没红线
    }
    for line in self_check(status):
        print(line)


if __name__ == "__main__":
    run()
```
保存为 `demo08_self_check.py`，运行 `python demo08_self_check.py`。完整预期输出：
```text
采样层：采样次数不足，单次结果不可信，提到至少3-5次
数据层：评估集与调优数据未隔离，存在泄题风险，建 held-out
判定层：裁判与人工一致性偏低(kappa<0.6)，先校准 rubric
轨迹层：只看结果未看轨迹，补 must_call/must_not_do 约束
门禁层：门禁缺红线零容忍规则，高风险动作可能被放行
```
（注：示例里 `watch_leading_metrics=True` 已达标，所以「指标层」的告警不出现——把该字段设为 `False` 才会多出一条「指标层：未盯先行指标…」。）这个规则树只用于**缩小范围**，不替代逐样本的深入分析：它告诉你评估体系先补哪一层，具体修复仍要回到实际数据与轨迹。示例里五条同时命中，说明这套评估体系在采样、数据隔离、裁判校准、轨迹、门禁五层都有缺口——恰好覆盖了开头故障能发生的全部前提。

## 真实系统对应

**官方公开机制**：本节引用的方法分别对应 LangSmith（离线/在线、轨迹、LLM 裁判、人工反馈校准）[来源](https://docs.langchain.com/langsmith/evaluation-concepts)、OpenAI Evals（版本对比、门禁部署、多类打分器）[来源](https://developers.openai.com/api/docs/guides/evals)、Anthropic（rubric 裁判五维度、小样本迭代裁判）[来源](https://www.anthropic.com/engineering/multi-agent-research-system) 的公开机制。**通用工程模式**：分层自检、症状矩阵、健康度规则树、RBAC/脱敏/SLO 治理，是可迁移到任何评估栈的框架。**教学参考实现**：上面的规则树阈值（如 kappa<0.6、采样<3）为教学值，需按业务实测校准，不是普适常数。

需要点明边界：采样率、脱敏策略、trace 保留期、门禁阈值、谁能看评估数据，都是团队按风险与合规设计的工程决策；本文不声称任何平台会自动完成这些治理。可观测与评估平台提供的是能力，怎么用、留多久、谁能看，都是团队自己的责任。

## 思考：面试官问「讲一下你会怎么给一个 Agent 搭一套完整的评估体系」，怎么答得有层次？

### 回答

分四层递进。第一层给双轨骨架：离线评估（开发期对固定数据集跑批、防回归、卡上线门禁）+ 在线评估（生产期对真实流量抽样打分、实时发现退步），并让二者闭环——线上抓到的每个 bad case 结构化回流成离线样本，评估集随真实流量一起生长。第二层点评估的两个维度：结果评估（任务做对没，用标准答案 + LLM 裁判）+ 轨迹评估（做得好不好、可复现吗，用 must_call 卡关键步、must_not_do 卡红线），并强调「结果对≠没问题」，要用四象限识别侥幸成功。第三层展开三个易错工程细节，正好覆盖本章：因为非确定性，每条样本要多次采样看通过率而非跑一次；开放输出的裁判本身有位置/长度/自我偏好偏差、必须用 Cohen's Kappa 和人工校准；指标要结果+过程双层、盯先行指标、看 P95、聚合可下钻分类和四象限。第四层落到门禁与治理：CI 卡「整体通过率不降 + 无单类崩盘 + 红线零容忍」三条，公开基准只用来选型、私有 held-out 用来验收并严防泄题，评估数据做 RBAC 和 PII 脱敏。最后用「上线三天才发现退步」这类具体故障收尾——只测措辞没测轨迹、只跑几次没看通过率、没有门禁没有红线——证明你不只背框架，还踩过坑。这样从骨架到维度到细节到治理，层次就出来了。

### 面试精简表达

先讲离线+在线双轨闭环骨架，再点结果+轨迹两维度（含四象限识别侥幸成功），然后展开多次采样看通过率、裁判校准防偏差、结果+过程双层指标三个细节，最后落到 CI 三条门禁 + 基准选型/私有验收/防泄题 + 治理，用一个真实故障收口。

## 思考：为什么说「评估驱动开发」比「凭感觉调 prompt」是本质区别，而不只是流程差异？

### 回答

因为它改变的是「你凭什么做决策」的认知论基础，而不只是多加了一个步骤。凭感觉调 prompt 时，你的每一次改动决策依据是「我读着觉得更好了」——这是主观的、不可复核的、会被措辞和长度这类表面特征带偏的（开头故障就是被「读起来更礼貌」骗了）。评估驱动开发把决策依据换成「一组可度量、可对比、可回归的数字」：改动前跑基线、改动后跑同一评估集、逐维度对比、达门槛才上线。这是从「艺术」到「工程」的跃迁——工程的定义就是「可度量、可复现、可迭代」。具体体现在三件凭感觉永远做不到的事：其一，安全换模型/改 prompt，因为你能量化「换了到底升还是降」，不再因恐惧而错过升级；其二，防住回归，因为每个修过的 bug 都变成回归样本，改 A 不会悄悄弄坏 B；其三，团队可协作，因为「好」有了客观定义，不再是谁嗓门大谁说了算。评估驱动开发对应第 10 章的 Evaluator-Optimizer 模式在开发流程层面的放大——用评估这个「裁判」驱动整个 Agent 的持续优化。没有评估基线的优化，都是自我感动。

### 面试精简表达

它改变的是决策依据：凭感觉靠主观读感（会被措辞带偏），评估驱动靠可度量可回归的数字。这让「安全换模型、防回归、团队协作」三件凭感觉做不到的事成为可能，是从艺术到工程的跃迁。

## 思考：如果只能给一个 Agent 评估体系加一样东西，你会加什么？为什么？

### 回答

我会加「从线上失败回流的私有回归集 + 一道带红线的 CI 门禁」——把它当成一个不可分割的整体。理由是它同时补上了开头故障暴露的两个最致命缺口，且投入产出比最高。第一，它解决「上线前拦不住退步」：任何 prompt/模型/流程改动都要先跑这个集、过这道门禁，达不到就合不进主干，退步在合并前就被挡住，而不是三天后靠用户投诉发现。第二，它解决「评估集追不上真实世界」：因为集子是从线上真实失败持续沉淀的，它天然覆盖最难、最有信息量的长尾样本，越用越强，而不是闭门造车的一次性产物。第三，红线零容忍这一条单独拎出来，直接堵住「大额退款未审批」这类一次就资损的高风险动作——通过率再高也不能拿它冒险。如果非要排序，我认为「多次采样看通过率」「裁判校准」「过程指标」都很重要，但它们都是在「有一个可回归、能卡门禁的私有集」之上才谈得上发挥作用的——没有这个地基，再精细的裁判和指标也只是漂亮的仪表盘，拦不住任何一次退步上线。所以如果只能加一样，我加这个地基。

### 面试精简表达

加「从线上失败回流的私有回归集 + 带红线零容忍的 CI 门禁」。它同时补上「上线前拦不住退步」和「评估集追不上真实世界」两个致命缺口，红线还堵住一次即资损的高风险动作；其他方法都要在这个地基上才发挥作用。
