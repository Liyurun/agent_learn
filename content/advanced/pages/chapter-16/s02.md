## 真实问题

「上线三天才发现退步」故障的直接成因，是团队只有一种评估形态：上线前拿几个例子肉眼看。他们既没有**离线评估**（改动前对一个固定数据集跑批、和基线对比），也没有**在线评估**（上线后对真实流量抽样打分、实时发现退步）。结果是——开发期看不到退步、生产期也看不到退步，只能等三天后客服主管用「工单感觉变多了」这种滞后的人肉信号来兜底。

这一节把评估按「什么时候用、评什么、拿什么当输入」拆成离线与在线两种形态，讲清它们各自解决什么问题、为什么必须**两者都要**，以及最关键的一环：如何让在线发现的失败样本**回流**到离线数据集，形成越用越强的闭环。

## 原理：离线是「考试」，在线是「体检」

LangSmith 评估概念文档把评估明确分为两类 [来源](https://docs.langchain.com/langsmith/evaluation-concepts)：

| 维度 | 离线评估（Offline） | 在线评估（Online） |
|---|---|---|
| 时机 | 开发期、上线前 | 生产期、上线后 |
| 输入 | 固定数据集（含标准答案） | 真实线上流量（通常无标准答案） |
| 目的 | 对比版本、防回归、卡门禁 | 实时发现退步、度量真实质量 |
| 评判 | 标准答案匹配 + LLM 裁判 + 轨迹 | LLM 裁判 + 用户反馈信号 |
| 类比 | 闭卷考试（有标准答案） | 日常体检（看真实身体指标） |
| 频率 | 每次改动 / 每次提交 | 持续、按采样率 |

一句话记忆：**离线评估回答「我改的这版比上一版好吗」，在线评估回答「线上此刻到底好不好」**。两者缺一：只有离线，你的评估集永远追不上真实用户的长尾输入；只有在线，你没法在上线前拦住退步，只能事后救火。开头故障恰恰是两者都缺。

LangSmith 官方也强调，离线评估用于「开发期在精选数据集上对比 Agent 版本、跑基准、在用户之前抓回归」，在线评估用于「对实时流量打分、发现问题、度量质量」[来源](https://www.langchain.com/langsmith/evaluation)。

### 在线评估靠什么打分：裁判 + 用户反馈

线上流量通常没有标准答案（你不知道用户「真正想要」什么），所以在线评估主要靠两类信号：

1. **在线 LLM 裁判**：对抽样到的对话实时打分（是否解决问题、是否礼貌、是否安全）。因为是全量的一个采样子集，成本可控。
2. **隐式/显式用户反馈**：点赞点踩、是否转人工、是否重复追问、会话时长等。这些是「免费的、真实的」质量信号，比任何裁判都贴近用户真实体验。

## 最小可运行演示

下面把离线评估（对固定数据集每条采样多次、算总/分类通过率）与在线评估（对线上流量按比例抽样、送裁判、回收失败样本）放在一个脚本里对照。注意在线抽样如何**回收失败样本**——这就是下一节闭环的起点。
```python
"""演示：离线评估（对固定数据集跑批）与在线评估（对线上流量抽样打分）的分工。"""
from dataclasses import dataclass, field


@dataclass
class EvalCase:
    id: str
    question: str
    gold: str
    category: str


def offline_eval(agent, cases, samples=3):
    """离线评估：对固定数据集每条采样多次，算总通过率与分类通过率。"""
    passed = total = 0
    per_cat = {}
    for c in cases:
        cp = 0
        for i in range(samples):
            ok = agent(c.question, seed=i) == c.gold
            cp += ok
            passed += ok
            total += 1
        slot = per_cat.setdefault(c.category, [0, 0])
        slot[0] += cp
        slot[1] += samples
    return {
        "overall": round(passed / total, 3),
        "per_category": {k: round(v[0] / v[1], 3) for k, v in per_cat.items()},
    }


def online_sample(stream, sample_rate, judge):
    """在线评估：对线上流量按比例抽样送裁判，估计线上质量并回收失败样本。"""
    scored, fails = [], []
    for i, ev in enumerate(stream):
        if i % int(1 / sample_rate) != 0:      # 确定性抽样：每 1/rate 条取一条
            continue
        s = judge(ev)
        scored.append(s)
        if s < 4:
            fails.append(ev["q"])
    online_rate = round(sum(s >= 4 for s in scored) / len(scored), 3)
    return {"sampled": len(scored), "online_pass_rate": online_rate,
            "recovered_failures": fails}


def toy_agent(question, seed=0):
    table = {"退款金额": "88.00", "物流状态": "已签收", "退款政策": "7天无理由"}
    for kw, ans in table.items():
        if kw in question:
            return ans if seed != 2 or kw != "退款金额" else "错值"  # 第3次抖动
    return "未知"


def toy_judge(ev):
    return 5 if ev["a"] == ev["gold"] else 2


def run() -> None:
    cases = [
        EvalCase("c1", "退款金额是多少", "88.00", "退款"),
        EvalCase("c2", "物流状态如何", "已签收", "查询"),
        EvalCase("c3", "退款政策是什么", "7天无理由", "查询"),
    ]
    print("== 离线评估(固定数据集) ==")
    print(offline_eval(toy_agent, cases, samples=3))

    stream = [
        {"q": "物流状态", "a": "在途", "gold": "已签收"},     # 被抽样：失败
        {"q": "退款金额", "a": "88.00", "gold": "88.00"},      # 跳过
        {"q": "退款政策", "a": "7天无理由", "gold": "7天无理由"},  # 被抽样：通过
        {"q": "改地址", "a": "已修改", "gold": "已修改"},       # 跳过
    ]
    print("== 在线评估(线上抽样) ==")
    print(online_sample(stream, sample_rate=0.5, judge=toy_judge))


if __name__ == "__main__":
    run()
```
保存为 `demo02_offline_online.py`，运行 `python demo02_offline_online.py`。完整预期输出：
```text
== 离线评估(固定数据集) ==
{'overall': 0.889, 'per_category': {'退款': 0.667, '查询': 1.0}}
== 在线评估(线上抽样) ==
{'sampled': 2, 'online_pass_rate': 0.5, 'recovered_failures': ['物流状态']}
```
逐行讲解：

- 离线部分 `overall=0.889`（8/9 通过），但**分类拆开看**才发现「退款」类只有 0.667——因为 `toy_agent` 在第 3 次采样对退款问题故意抖动出错。这印证了上一节的原则：多次采样 + 分类统计，才能看出被总分掩盖的弱项。
- 在线部分 `sample_rate=0.5` 表示每 2 条抽 1 条，所以 4 条流量只抽了 2 条（`sampled=2`）。抽到的「物流状态」答错被裁判判 2 分（<4），于是进了 `recovered_failures`。
- `recovered_failures=['物流状态']` 是全节最重要的产出：**在线评估不只是打个分，更要把失败样本捞回来**。这条「物流状态答成在途而非已签收」的线上失败，下一步就该被结构化成一条离线评估样本，补进数据集——这就是闭环的第一块砖。

## 真实系统对应

**官方公开机制**：LangSmith 支持离线评估（`evaluate()` 对数据集跑批）与在线评估（上传评估器对生产 trace 实时打分），并提供多轮在线评估器专门看对话轨迹 [来源](https://docs.langchain.com/langsmith/online-evaluations-multi-turn) [来源](https://www.langchain.com/langsmith/evaluation)；OpenAI Evals 允许对同一评估在不同模型与参数上反复运行，用于版本对比与部署门禁 [来源](https://developers.openai.com/api/docs/guides/evals)。**通用工程模式**：离线跑批 + 在线抽样 + 失败回流是可迁移到任何栈的评估双轨制。**教学参考实现**：上面的 `toy_agent`、`toy_judge`、按下标取模的确定性抽样，仅为让输出可复核，真实系统的抽样通常是随机采样 + 分层采样。

需要点明边界：在线评估会带来额外成本（每条抽样都要跑一次裁判）与数据保留问题——LangSmith 文档就提示多轮在线评估器默认会延长 trace 保留期，可按需退出 [来源](https://docs.langchain.com/langsmith/online-evaluations-multi-turn)。采样率、保留期、谁能看这些数据，都是团队按成本与合规做的工程决策，本文不声称任何平台会自动替你决定。

## 生产踩坑

| 症状 | 根因 | 如何观测与复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| 上线前看不到退步 | 只有肉眼测、无离线基线 | 对固定集跑新旧版对比 | 建离线评估集 + 基线对比 | 探索期原型可暂缓 |
| 上线后退步无感 | 无在线评估、只等投诉 | 对线上抽样跑裁判看趋势 | 上在线评估 + 用户反馈信号 | 内部小流量工具风险低 |
| 离线分高线上却差 | 数据集分布 ≠ 真实分布 | 对比离线样本与线上输入分布 | 从线上回流样本补集 | 领域封闭、输入稳定时差异小 |
| 总分好看局部崩盘 | 只看 overall 不看分类 | 按 category 拆开统计 | 分类通过率 + 关键类单独看 | 单一类任务无需拆分 |
| 在线评估成本失控 | 全量都送裁判 | 统计裁判调用量与账单 | 按采样率抽样 + 分层采样 | 低流量场景可提高采样率 |
| 失败样本白白流失 | 在线只打分不回收 | 检查有没有 bad case 落库 | 失败样本结构化回流数据集 | 无法结构化的一次性输入 |
| trace 保留期意外拉长 | 未注意在线评估默认延长保留 | 查看数据保留配置 | 按需退出自动延长 | 需长期审计的场景本就要留 |

## 思考：为什么说「只有离线评估」或「只有在线评估」都不够？

### 回答

因为它们覆盖的是评估的两个不同阶段，各自有对方补不上的盲区。只有离线评估的盲区是**追不上真实分布**：你的数据集是过去某个时点造的，而真实用户的输入永远在漂移、长尾、出新花样；离线分再高，也只能证明「在我见过的样本上没退步」，证明不了「线上此刻没出新问题」。开头故障如果只有离线评估、评估集里恰好没有「加长共情前缀会挤掉核验步骤」这类样本，照样漏。只有在线评估的盲区是**无法在上线前拦截**：在线评估是事后的、被动的，它能告诉你「线上正在变差」，但那时用户已经受影响了，你失去了「改动合并前就把退步挡住」的机会。正确姿势是双轨并行且形成闭环：离线当上线前的准入闸门（防已知问题回归），在线当上线后的实时体检（发现未知的新问题），并把在线抓到的每一个 bad case 回流成离线样本——这样离线集会随真实流量一起生长，逐渐把「未知问题」变成「已知的、被守住的问题」。

### 面试精简表达

离线追不上真实分布、只能防已知回归；在线无法上线前拦截、只能事后发现。二者并行且让线上失败回流到离线集，才既防回归又追得上真实世界。

## 深挖：让评估集从真实失败中「生长」

一开始就想造一个完美评估集，会撞上两堵墙。第一堵是**想象力有限**：你在办公室里想不出用户会怎么刁难 Agent，真实用户输入的分布永远比脑补的更长尾。开头那个「加长共情前缀挤掉核验步骤」的 bad case，就是没人会主动去造、只有真实流量才暴露的。第二堵是**成本前置且浪费**：花一个月造 1000 条样本，可能 800 条覆盖的都是 Agent 早就能轻松处理的简单情况，真正有区分度的难例反而没覆盖。

而「从失败中生长」的策略，本质上是让**真实流量帮你做主动学习（active learning）**：系统会自动把最难、最有信息量的样本（也就是它失败的那些）推到你面前，你只需把它们固化下来。上一节演示里 `recovered_failures` 捞回的「物流状态」失败，就该被结构化成一条 `EvalCase`（含标准答案「已签收」、分类「查询」、来源「线上抽样 2026-xx」），补进离线集。半年后你回看，这条样本能立刻告诉你它为什么存在、防的是哪类退步。这比闭门造车现实得多，也是把「离线—在线闭环」真正跑起来的关键动作。
