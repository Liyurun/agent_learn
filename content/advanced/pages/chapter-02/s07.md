## 真实问题

一个把前六节都学扎实的团队，信心满满地把订单助手扩展到客服、售后、物流三个场景后上线。两周内他们收到一串看似无关的告警：有时“回答变短”，有时“调错工具”，有时“跨用户看到了别人的订单”，还有一次“退款又被执行了”。他们最初把这些当成各自独立的偶发 bug 去修，越修越乱。直到复盘时才发现：这些症状全都能追溯到五件套里某个组件的边界没守住——回答变短是 Model 输出预留不足，调错工具是 Tools 描述退化，跨用户是 Memory 缺租户隔离，退款重现是护栏又被写回了推理层。

本节把第 2 章所有原理在生产环境里最容易塌方的地方系统汇总成一张大表，再集中回答一批高频的工程与面试思考题。它是全章的“落地检查清单”——当你的 Agent 出问题时，可以对照它按组件定位根因。

## 五件套故障总表

下面这张表覆盖五件套各自最常见的生产故障。诊断原则和第 27 章一致：先固定输入复现，再按组件分层定位，不要一上来就“换更大模型”。

| 症状 | 根因 | 如何观测与复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| 回答突然变短或被截断 | Model 输出预留不足，输入挤占了输出额度 | 记录停止原因与输入 Token 量 | 为输出锁定额度，精简输入 | 分类等短输出任务可设小额度 |
| 无脑上最强模型成本翻倍收益甚微 | 误把模型当作文机，未做分层路由 | 统计各轮决策难度分布 | 简单决策用小模型，难点用强模型 | 极高价值单次决策可直接用强模型 |
| 代码正则解析模型文本频繁崩溃 | 未用函数调用/结构化输出约束格式 | 注入措辞变体统计解析失败率 | 改用函数调用或 strict 结构化输出 | 纯问答无工具时可不用 |
| 结构化输出合法却执行了危险动作 | 把 Schema 合法误当作动作被允许 | 让模型产出合法 refund 决策 | 权限校验放执行层，与格式校验分离 | 无 |
| 提示里写了禁止仍被执行 | 护栏只在提示层，未落执行层 | 用改写措辞的危险指令绕过 | 关键动作在工具内做确定性校验 | 无 |
| 模型频繁选错工具 | Tools 名称/描述含糊或近义工具过多 | 对比描述质量与工具选择准确率 | 按说明书标准重写描述、裁剪候选、两阶段路由 | 只读低风险工具容错稍高 |
| 传给工具的参数格式错乱 | 参数缺类型、示例与必填标注 | 记录调用参数统计校验失败率 | 参数加类型注解与示例，调用前校验 | 无 |
| 被提示注入诱导执行危险动作 | 把工具输出/用户文本当指令信任 | 在工具返回里植入越权指令做红队 | 工具输出当数据不当指令，执行层兜底 | 纯内部可信工具风险较低 |
| 高风险动作无人工介入 | 缺少人工审核 gate | 检查写操作是否有审批环节 | 高风险工具接人工审核或二次确认 | 明确授权的自动化批处理例外 |
| 复合请求只做第一步就停 | Planning 缺失，多步当单步 | 给含 3+ 子任务请求观察执行 | 显式分解为子目标队列逐个执行 | 单步简单请求无需规划 |
| 反思陷入无限自我否定 | 反思无终止条件 | 观察是否反复推翻自己 | 限定反思轮数并要求可执行修正 | 无 |
| 跨会话失忆反复追问同一信息 | 只有短期记忆，缺长期沉淀 | 新开会话问上次给过的信息 | 关键偏好写长期记忆，会话开始时取回 | 一次性任务无需长期记忆 |
| 长期记忆检索不命中 | 检索粒度或相似度阈值不当 | 查看实际检索到的片段 | 调整切块、重排、阈值，关键事实结构化存 | 键值精确查询不涉及 |
| 短期记忆塞满导致成本飙升或截断 | 该进长期的信息堆在上下文 | 监控每轮输入 Token 与截断 | 当前任务必需留短期，其余移长期检索 | 窗口充裕的短任务可放宽 |
| 跨用户/租户信息串味 | Memory 键缺少用户或租户维度 | 用两个用户交叉测试 | 记忆键带用户/租户，做访问控制 | 无 |
| Agent 陷入死循环 | 循环无终止条件或步数上限 | 打印每轮 action 观察重复 | 设 max_steps 上限并检查记忆避免重复 | 明确流式长任务需更大上限 |
| 某次失败无法定位在哪一步 | 未按阶段打点观测 | 移除阶段日志后复现 | 建立阶段级 Trace，先定位阶段再查组件 | 无 |
| 换模型版本后行为突变难复现 | 未固定模型版本与温度 | 复现时未锁定 model id 与 temperature | 请求固定模型版本并记录到 Trace | 有意做 A/B 实验时例外 |

RBAC（Role-Based Access Control，基于角色的访问控制）适合给不同工具与数据划分权限边界；SLO（Service Level Objective，服务级目标）应把“任务成功率、约束遵循率”纳入，而不只看延迟与 Token；PII（Personally Identifiable Information，个人可识别信息）在记忆与 Trace 里必须最小化和脱敏。

## 最小可运行演示

把上面的“先定位阶段、再查组件”做成一个可运行的分层诊断器：给它一组观测指标，它按组件顺序报出第一/所有偏离项，而不是笼统地说“质量下降”。纯 Python，无需 API Key。
```python
def diagnose(m: dict) -> list[str]:
    findings = []
    # 感知/记忆层
    if not m["evidence_in_context"]:
        findings.append("感知/记忆：关键信息未进入上下文（召回或读取故障）")
    if m["cross_tenant_leak"]:
        findings.append("记忆：跨租户串味，记忆键缺用户隔离")
    # 推理/模型层
    if m["stop_reason"] == "max_tokens":
        findings.append("模型：输出被截断，输入挤占了输出预留")
    if m["parse_failed"]:
        findings.append("模型：结构化输出解析失败，需约束 Schema")
    # 行动/护栏层
    if m["high_risk_without_approval"]:
        findings.append("护栏：高风险动作未经审核，护栏未落执行层")
    if m["wrong_tool_rate"] > 0.1:
        findings.append("工具：选错率偏高，检查描述与候选集")
    # 规划层
    if m["subgoals_missed"] > 0:
        findings.append("规划：复合任务有子目标遗漏")
    return findings or ["未见组件级偏离，固定输入做进一步消融"]

def main() -> None:
    metrics = {
        "evidence_in_context": True,
        "cross_tenant_leak": False,
        "stop_reason": "end_turn",
        "parse_failed": False,
        "high_risk_without_approval": True,   # 命中：退款又被执行
        "wrong_tool_rate": 0.03,
        "subgoals_missed": 1,                  # 命中：漏了一个子目标
    }
    print("\n".join(diagnose(metrics)))

if __name__ == "__main__":
    main()
```
保存为 `diagnose_agent.py`，运行 `python diagnose_agent.py`，预期输出：
```text
护栏：高风险动作未经审核，护栏未落执行层
规划：复合任务有子目标遗漏
```
诊断器允许并列报出多个根因（本例同时命中护栏和规划两层），而不是遇到第一项就停。它只负责缩小范围到具体组件，真正的修复仍要打开对应的 Trace 和输入快照。把这段逻辑接到线上，就能把“Agent 质量下降”这类无法行动的告警，翻译成“护栏层 + 规划层出问题”这类可以派单的结论。

## 真实系统对应

**官方公开机制**：OpenAI 的指南把护栏分成相关性/安全分类器、PII 过滤、内容审核、工具风险评级、基于规则的确定性防护和输出校验多层，并建议高风险动作执行前暂停检查或升级人工 [来源](https://cdn.openai.com/business-guides-and-resources/a-practical-guide-to-building-agents.pdf)；函数调用与结构化输出保证工具调用与参数的可解析性 [来源](https://platform.openai.com/docs/guides/function-calling) [来源](https://openai.com/index/introducing-structured-outputs-in-the-api/)。**通用工程模式**：把五件套故障映射成可观测指标（输出预留、工具选错率、证据进入率、子目标覆盖率、跨租户隔离、恢复成功率），先定位组件再修复。**教学参考实现**：`diagnose` 的规则树是为教学构造的，真实系统会把每个判断连接到可打开的 Trace 与输入快照，并把阈值做成团队可配置项，而非硬编码。

## 思考：面试官问“你怎么设计一个 Agent 的核心组件？”，如何系统作答？

### 回答

用五件套作为骨架，逐件说清“职责 + 边界 + 关键决定”。**Model**：定位为决策器而非作文机，产出结构化决策，做分层路由控成本。**Tools**：按风险分级，每个工具写清“使用说明书”（名称+用途+触发时机+参数示例），坚持“模型提议、运行时处置”。**Instructions**：软护栏提升体验，但关键护栏落执行层做确定性校验，高风险动作接人工。**Planning**：复合任务显式分解为子目标并加反思，避免漏步。**Memory**：区分短期（当前任务必需、用完即弃）与长期（跨会话有用、带来源与时效、按用户隔离）。最后强调它们不是孤立模块，而是在“感知—推理—行动—观察—记忆”循环里彼此喂养。这样回答既覆盖全、又体现了对边界与协同的理解，远胜于只背组件名。

### 面试精简表达

“模型做决策不是写作文、工具按风险分级并写好说明书、护栏落执行层、复杂任务先规划、记忆分短长期，五件套在循环里协同。”

## 思考：为什么“组件齐全”的 Agent 仍会翻车？

### 回答

因为“有这个组件”和“这个组件的边界设计对了”是两回事。本章开场的订单助手五件套俱全，仍退错了 680 元，根因是 Instructions 里的护栏只是自然语言请求、没落到 refund 函数的执行层。同理，有 Memory 但不做用户隔离会串味，有 Tools 但描述含糊会选错，有 Model 但当作文机用会浪费成本，有 Planning 但不加反思会漏步。**组件是必要条件不是充分条件**——真正决定 Agent 可靠性的是每个组件的职责边界（模型输出什么、护栏放哪层、记忆怎么隔离）和它们在循环里的协同。所以排障时不能停在“组件都有啊”，要追问“每个组件的边界守住了吗”。

## 思考：诊断 Agent 故障时，为什么不能一上来就“换更大模型”？

### 回答

因为大多数 Agent 故障不在模型能力，而在组件边界或工程接线。换更大模型对以下故障完全无效：正确信息根本没进入上下文（感知/记忆故障，模型再强也读不到不存在的东西）、护栏没落执行层（危险动作照样执行）、工具描述含糊（模型再强也在猜）、跨租户串味（这是记忆键设计问题）、复合任务漏步（这是规划缺失）。换大模型有时能“暂时压住”表象，却掩盖真正的根因，还大幅抬高成本。正确顺序是先固定输入复现，再按五件套分层定位第一个偏离的组件，对症修复。只有当确认是“决策质量本身不足”时，升级模型才是对的解法。这也是本节诊断器“先报组件、把模型放在最后”的设计理由。

### 反例

若系统正在发生明确的越权写入（如退款被反复执行），应先在执行层停用危险能力止损，再从容排查，不能等走完完整诊断流程——先观测再重构适用于质量与成本优化，不适用于正在发生的资金安全事故。

## 思考：本章的心智模型如何迁移到评估一个陌生的 AI 产品？

### 回答

拿五件套当“透镜”逐项拆解即可。给定一个陌生的 AI 产品（编程助手、客服机器人、研究助手等），依次问：它的 **Model** 是什么、做没做分层路由；它有哪些 **Tools**、风险怎么分级、护栏在哪层；它的 **Instructions/护栏** 是软的还是落到执行层；它有没有真正的 **Planning**（能否处理多步任务、会不会反思），还是每次都一步到位；它的 **Memory** 是只有上下文（关掉重开就失忆）还是有跨会话长期记忆。做完这套拆解你往往会发现：很多号称“AI Agent”的产品其实缺 Planning 或 Memory，更接近增强型大语言模型或固定工作流，而非完整 Agent——这正好呼应第 1 章的自主性判断和 Anthropic 对 Workflow 与 Agent 的区分 [来源](https://www.anthropic.com/engineering/building-effective-agents)。这种拆解能力在系统设计面试里极其有用，能让你快速说清“这个产品到底是什么、缺了哪件套、因此有什么局限”。

## 事故回放：三个告警其实是同一堂课

回到本节开场那三个“看似无关”的告警，把它们放回五件套框架，会发现它们讲的是同一堂课：**每个组件都有一条不能越的边界，越界就出事。** “回答变短”是模型没为输出留额度，边界是“输入不能吃掉输出预留”；“调错工具”是工具描述退化，边界是“描述必须让模型能准确选择”；“跨用户串味”是记忆键没带用户维度，边界是“记忆必须按所有者隔离”；“退款重现”是有人图省事把护栏挪回了推理层，边界是“关键护栏必须在执行层”。

团队最初把它们当四个独立 bug 各自打补丁，所以越修越乱——因为他们在症状层面打转。当他们改用五件套框架，先问“这是哪件套的边界被越了”，四个问题立刻归位到四个组件，修复方案也随之清晰。这说明本章心智模型的最大价值不在“记住五个词”，而在**它提供了一个把杂乱症状归因到组件边界的坐标系**。有了这个坐标系，无论未来遇到什么新框架、什么新故障，你都能先定位到“哪件套、哪条边界”，再动手修，而不是在症状的海洋里乱撞。

## 全章回顾：从清单到坐标系

学完第 2 章，你手里应该有三样东西。第一是一张**不遗漏的组件清单**——Model、Tools、Instructions、Planning、Memory 五件套，由 OpenAI 与 Lilian Weng 两套权威划分取并集而来，你能说清它们“视角不同而非对错”。第二是一个**动态运转模型**——感知—推理—行动—观察—记忆循环，你理解“组件是零件、循环是运转”，也能手写一个把五件套拼起来、能拦退款、能规划多步、能读写记忆的可运行骨架。第三，也是最重要的，是一个**故障归因坐标系**——当 Agent 出问题时，你能先定位到“哪件套、哪条边界”，再对症修复，而不是笼统地“换个模型试试”。

这三样东西是拆解任何 Agent 系统的通用工具。后续章节会把每一件套展开成专题：规划的深入方法（第 4 章）、记忆的检索与管理（第 5 章）、工具与安全（第 6、8 章）、模型路由与成本（第 18 章）、上下文工程（第 27 章）。但无论走多远，你都会不断回到这一章建立的坐标系——因为五件套和它们在循环里的协同，是 Agent 这门工程的地基。
