## 真实问题

一个团队把订单助手的模型从便宜的小模型换成最强的旗舰模型，期望“回答更准”，结果账单涨了四倍，任务成功率却几乎没变。复盘时他们才意识到一个误区：他们一直以为模型在 Agent 里的工作是“把答案写得更漂亮”，所以直觉是“越强的模型文笔越好、越准”。但订单助手的每一轮里，模型真正在做的不是写作文，而是**做一个决策**——该调 `search_order` 还是该 `final`（直接回答）。绝大多数轮次的这个决策，一个小模型就能做对；只有极少数复杂推理才需要旗舰模型。他们为“作文能力”付费，但 Agent 需要的是“决策能力”。

本节要澄清的就是这个最根本的认知：**在 Agent 里，模型是个“决策器”，不是“作文机”。** 想清楚模型每一轮到底输出什么，函数调用、结构化输出、分层路由这些机制才会变得顺理成章。

## 原理：模型每一轮输出的是“结构化决策”

在普通聊天场景里，模型输出的是一段自然语言答案。但在 Agent 语境里，模型每一轮真正输出的是一个**结构化的决策**：调哪个工具、传什么参数，或者“我说完了（final）”。这个差异是理解 Agent 里模型角色的钥匙。
```text
   聊天场景                       Agent 场景
   用户问 ──▶ 模型 ──▶ 答案文本    当前上下文 ──▶ 模型 ──▶ {动作, 参数}
                                                     │
                                          ┌──────────┴──────────┐
                                          │  调工具 A(参数...)   │
                                          │  调工具 B(参数...)   │
                                          │  final(最终回答文本) │
                                          └─────────────────────┘
```
正因为 Agent 需要模型输出“可被代码执行的决策”而非“散文”，两个机制才变得关键：

- **函数调用（Function Calling）**：开发者在请求里描述一组函数（名称、说明、参数 JSON Schema），模型据此产出符合 Schema 的函数名与参数，由开发者的代码去执行，执行结果可再喂回模型形成闭环 [来源](https://platform.openai.com/docs/guides/function-calling)。
- **结构化输出（Structured Outputs）**：开发者提供一个 JSON Schema，模型被约束为严格产出符合该 Schema 的 JSON；在支持的模型上开启 `strict: true` 可确保参数遵循 Schema，不符合的请求会报错而非蒙混过关 [来源](https://openai.com/index/introducing-structured-outputs-in-the-api/)。

这两个机制的共同作用，是把模型从“输出散文”约束成“输出可执行的决策”。它们是 Agent 工程可靠性的基石——没有它们，代码就得去正则解析模型的自由文本来猜“它想调哪个工具”，脆弱且不可靠。

## 现象与输入：把“作文机”和“决策器”摆在一起

用贯穿案例对照两种心智模型，差异一目了然：

| 维度 | 把模型当“作文机” | 把模型当“决策器” |
|---|---|---|
| 每轮输出 | 一段自然语言 | `{action, arg}` 结构化决策 |
| 代码如何用输出 | 直接展示给用户 | 解析后路由到对应工具 |
| 靠什么保证可用 | 人读得懂就行 | 函数调用 / 结构化输出约束 Schema |
| 选型直觉 | 越强文笔越好 | 多数决策小模型够用，难点才用强模型 |
| 出错表现 | 答得啰嗦 | 调错工具、传错参数、该停不停 |

把模型定位成决策器后，选型逻辑就变了：不是“无脑上最强模型”，而是**分层路由**——简单决策用便宜的小模型，复杂推理用强模型。

## 最小可运行演示

下面用纯 Python 模拟“模型产出结构化决策”，并做一次 Schema 校验（不需要 API Key，用规则代替真实模型）。它展示的正是函数调用背后的数据形态：模型给出 `{action, arg}`，代码先校验再执行。
```python
import json

ACTION_SCHEMA = {"search_order": True, "refund": True, "final": True}  # 允许的动作 Schema：动作名 -> 参数是否必填

def model_decide(task: str, memory: str) -> dict:
    """模拟模型产出结构化决策（真实系统由函数调用/结构化输出得到同样的 JSON）。"""
    if "退款" in task:
        return {"action": "refund", "arg": {"order_id": "A100", "amount": 680}}
    if "A100" in task and "已发货" not in memory:
        return {"action": "search_order", "arg": {"order_id": "A100"}}
    return {"action": "final", "arg": {"text": f"查询结果：{memory}"}}

def validate(decision: dict) -> bool:
    """结构化输出的作用：确保决策符合可执行的 Schema，否则拒绝。"""
    action = decision.get("action")
    if action not in ACTION_SCHEMA:
        return False
    if ACTION_SCHEMA[action] and "arg" not in decision:
        return False
    return True

def main() -> None:
    for task, mem in [("查订单 A100", ""), ("我要退款", ""), ("查订单 A100", "已发货")]:
        d = model_decide(task, mem)
        ok = validate(d)
        print(f"输入={task!r:16} 决策={json.dumps(d, ensure_ascii=False)} 合法={ok}")

if __name__ == "__main__":
    main()
```
保存为 `decision_model.py`，运行 `python decision_model.py`，预期输出：
```text
输入='查订单 A100'       决策={"action": "search_order", "arg": {"order_id": "A100"}} 合法=True
输入='我要退款'           决策={"action": "refund", "arg": {"order_id": "A100", "amount": 680}} 合法=True
输入='查订单 A100'       决策={"action": "final", "arg": {"text": "查询结果：已发货"}} 合法=True
```
注意第二行：模型“决定”调 `refund`，`validate` 认为它结构合法（Schema 层面确实是个合法决策）。这说明一个关键点——**结构化输出只保证“格式对”，不保证“该不该做”**。“该不该退款”是护栏问题，不是 Schema 问题，必须在执行层用代码拦（第 04 节详解）。把“格式校验”和“权限校验”混为一谈，是新手最常见的安全漏洞。

## 真实系统对应

**官方公开机制**：OpenAI 的函数调用文档描述了“描述函数→模型产出符合 Schema 的调用→代码执行→结果回喂”的完整闭环，并支持一次产出多个工具调用 [来源](https://platform.openai.com/docs/guides/function-calling)；结构化输出通过 `response_format` 传入 JSON Schema，`strict: true` 时保证参数遵循 Schema，不符合的 Schema 会被拒绝 [来源](https://openai.com/index/introducing-structured-outputs-in-the-api/)。OpenAI 的《A Practical Guide to Building Agents》也把 Model 列为决策核心，并建议“先用能力最强的模型建立基线，再尝试用小模型替换那些能达标的环节”，这正是分层路由的官方版表述 [来源](https://cdn.openai.com/business-guides-and-resources/a-practical-guide-to-building-agents.pdf)。**通用工程模式**：把模型抽象成“上下文进、结构化决策出”，据此设计分层路由与 Schema 校验。**教学参考实现**：上面的 `model_decide` 用 `if` 规则冒充模型，只为让决策的数据形态可见；真实系统由模型经函数调用产出同样形状的 JSON。

## 生产踩坑

| 症状 | 根因 | 如何观测与复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| 无脑上最强模型，成本翻倍收益甚微 | 误把模型当作文机，为文笔付费 | 统计各轮决策难度分布，多数是简单路由 | 分层路由：简单决策用小模型，难点用强模型 | 极高价值单次决策可直接用强模型 |
| 代码正则解析模型自由文本，频繁崩 | 没用函数调用/结构化输出约束格式 | 注入措辞变体，观察解析失败率 | 改用函数调用或 `strict` 结构化输出 | 纯问答无需工具时可不用 |
| 结构化输出通过了却仍执行了危险操作 | 把 Schema 合法当成动作被允许 | 让模型产出合法的 `refund` 决策 | 权限校验放执行层，与格式校验分离 | 无 |
| 换了模型版本后行为突变难复现 | 没固定模型版本与温度 | 复现时未锁定 model id、temperature | 请求里固定模型版本、记录到 Trace | 有意做 A/B 实验时例外 |
| 模型该停不停、多轮空转 | 决策 Schema 里没有明确的 `final` 出口 | 观察是否始终不产出终止决策 | Schema 显式提供 `final` 动作并鼓励使用 | 探索类任务允许多轮 |
| 小模型频繁调错工具 | 决策超出小模型能力，或工具描述差 | 对比大小模型在同输入的工具选择 | 该环节升级模型或改进工具描述 | 只读低风险工具容错高 |

## 思考：为什么说“Agent 里的模型是决策器而不是作文机”？

### 回答

因为在 Agent 的每一轮循环里，模型的产出会被代码解析、路由去执行某个动作，而不是直接展示给用户。它要回答的问题是“下一步该干什么”——调哪个工具、传什么参数，还是任务已完成可以停止。这个产出必须是**可被程序确定性消费**的结构化决策，所以函数调用和结构化输出才如此关键。如果还把模型当作文机，就会用自然语言输出、再用正则去猜它的意图，既脆弱又不可靠。理解这个定位，选型、Schema 设计、护栏放置的所有决定都会随之改变：你会为“决策准确率”而非“文笔”付费。

### 面试精简表达

“聊天时模型输出答案，Agent 里模型输出动作。前者给人看，后者给代码执行，所以必须结构化。”

## 思考：分层路由为什么能省钱？请算一笔账。

### 回答

假设订单助手平均每个任务要 8 轮循环，其中 6 轮是简单决策（该调哪个工具），2 轮是复杂推理（如何组合多源信息给结论）。若 8 轮全用旗舰模型，成本 = 8 × 强模型单价。若 6 轮用便宜小模型（单价约为强模型的十分之一）、2 轮用强模型，成本 ≈ 6 × 0.1 + 2 × 1 = 2.6 个强模型单价，只有原来的约三分之一，而由于难点仍交给强模型，任务成功率几乎不降。这就是分层路由的经济学：**不是所有决策都值得用最贵的脑子，把贵的算力花在真正的难点上**。OpenAI 的指南也建议先用最强模型建基线，再逐环节替换成能达标的更小模型 [来源](https://cdn.openai.com/business-guides-and-resources/a-practical-guide-to-building-agents.pdf)。
```text
   全用强模型（贵）           分层路由（省）
   ┌──────────────┐         ┌──────────────────────────┐
   │ 8 轮 × 强模型 │         │ 6 轮 × 小模型(简单/路由)   │
   │              │         │ 2 轮 × 强模型(复杂推理)     │
   └──────────────┘         └──────────────────────────┘
   成本 100%                 成本 ~33%，质量几乎不变
```
## 机制推导：为什么结构化输出不能替代护栏

上面的演示里出现过一个反直觉现象：`refund` 决策通过了 `validate`（Schema 合法），但它显然不该被执行。这暴露了两种校验的本质区别。**结构化输出解决的是“格式确定性”**——保证模型产出的 JSON 字段齐全、类型正确、能被代码解析，它回答的问题是“这个决策能不能被程序读懂”。**护栏解决的是“行为合法性”**——保证这个动作在当前上下文下被允许执行，它回答的问题是“这个决策该不该被执行”。

两者作用在不同环节：格式校验在“解析模型输出”这一步，行为校验在“执行动作”这一步。一个格式完美的 `refund(A100, 680)` 决策，格式校验会放行，但执行层的权限校验必须拦下（因为 `approved_by_human` 为假）。把这两件事分开，是 Agent 安全设计的基本功。很多“模型被诱导执行了危险操作”的事故，根因就是团队以为“我用了结构化输出、格式很规范”就等于安全了——格式规范只是让危险操作“长得规矩”，并没有阻止它。第 04 节会把执行层护栏讲透。

## 结构化输出的可靠性边界

需要提醒一个来自一手资料的边界：`strict: true` 的结构化输出能在支持的模型和配置上保证“参数遵循 Schema”，但它对 Schema 的复杂度有约束——只支持 JSON Schema 的一个子集，不符合要求或过于复杂的 Schema 会被拒绝 [来源](https://openai.com/index/introducing-structured-outputs-in-the-api/)。因此工程上不要设计过深、过于动态的参数结构，而应保持 Schema 扁平、字段明确。另外，“格式一定对”不代表“内容一定合理”——模型仍可能在合法格式内填入错误的订单号或不合理的金额，这类内容错误要靠业务校验（如订单号是否存在、金额是否超限）兜底，而不是靠 Schema。

把模型定位成“受 Schema 约束的决策器”，我们就能顺畅过渡到下一节：模型产出的决策要么指向“调用某个工具”，要么受“指令与护栏”约束。工具和指令这两件套，正是把模型的决策安全落地的关键，也是第 04 节的主题。
