## 真实问题

一位学员把前面五节的组件都“背”下来了，也能对每个组件讲得头头是道，可当被要求“现在写一个能跑的 Agent”时，他卡住了——他不知道这五个零件在代码里到底怎么接线、循环从哪起、护栏插在哪一步、记忆什么时候读什么时候写。这是学习 Agent 最常见的“断层”：**懂了每个零件，却没见过它们装在一起转起来的样子。** 很多教程用框架 API 一笔带过（`agent = Agent(...); agent.run()`），学员反而更看不清内部发生了什么。

本节的目标就是消除这个断层：给出一个**完全可运行、无需 API Key、纯 Python 标准库**的 Agent 骨架，把 Model、Tools、Instructions、Planning、Memory 五件套显式地摆进感知—推理—行动—观察—记忆循环里，每一段代码都用注释点名它对应哪个组件、哪个阶段。然后我们逐行读懂它，并回放它处理贯穿案例两条测试输入 T1、T2 的完整轨迹。读完这一节，你应该能脱离任何框架，从零手写一个五件套 Agent。

## 原理：骨架的五个接线点

在动手前，先明确五件套在一个最小骨架里各自的“接线点”：
```text
   组件            在骨架里的接线点
   Instructions   模块顶部的字符串常量，加载进循环、约束推理（软护栏）
   Tools          函数 + 一张注册表（名称→{函数, 风险等级}）
   Memory         一个类，short_term(读/写) + long_term(note/recall)
   Model+Planning model_decide()：输入上下文，输出 {action, arg} 结构化决策
   Loop           for 循环：感知→推理→行动→观察→记忆，final 时退出
   执行层护栏      高风险工具执行前的 try/except 硬校验（最后防线）
```
关键设计原则来自前面五节：模型只产出结构化决策（第 03 节），工具按风险分级、高风险走执行层护栏（第 04 节），记忆分短期/长期（第 05 节），整个过程是一个由模型决定“下一步/是否停止”的循环（第 02 节）。

## 最小可运行演示

下面是完整骨架，可直接运行。它用规则模拟模型决策（因此无需 API Key），但**决策的数据形态、循环结构、护栏位置与真实 Agent 完全一致**——把 `model_decide` 换成一次真实的函数调用请求，骨架的其余部分几乎不用动。
```python
from dataclasses import dataclass, field

## ===================== Instructions（指令 + 护栏，软护栏） =====================
INSTRUCTIONS = (
    "你是电商订单助手 order-assistant。\n"
    "- 可以查询订单状态（只读）。\n"
    "- 涉及退款属于高风险写操作，必须先经人工审核，不得自行退款。\n"
    "- 信息足够就直接回答，不要重复查询同一订单。"
)

## ===================== Tools（工具：名称 + 说明 + 参数 + 风险） =====================
def search_order(order_id: str) -> str:
    """按订单号查询订单状态（只读，风险=低）。"""
    db = {"A100": "已发货，预计明天送达", "A101": "备货中"}
    return db.get(order_id, "订单不存在")

def refund(order_id: str, amount: float, approved_by_human: bool = False) -> str:
    """对订单退款（写操作，风险=高）。执行层硬护栏：无人工审核一律拒绝。"""
    if not approved_by_human:
        raise PermissionError("退款必须经人工审核，拒绝执行")
    if amount > 1000:
        raise ValueError("单笔退款超过上限，需升级审批")
    return f"已退款 {amount} 元至订单 {order_id}"

TOOLS = {
    "search_order": {"fn": search_order, "risk": "low"},
    "refund": {"fn": refund, "risk": "high"},
}

## ===================== Memory（记忆：短期 + 长期） =====================
@dataclass
class Memory:
    short_term: list = field(default_factory=list)   # 本轮上下文
    long_term: dict = field(default_factory=dict)    # 跨会话键值
    def write(self, obs: str) -> None:
        self.short_term.append(obs)
    def read(self) -> str:
        return " | ".join(self.short_term)
    def note_fact(self, key: str, value: str) -> None:
        self.long_term[key] = value
    def recall_fact(self, key: str):
        return self.long_term.get(key)

## ===================== Model + Planning（决策核心 + 规划） =====================
def model_decide(task: str, mem: Memory) -> dict:
    """产出结构化决策 {action, arg}。真实系统由函数调用/结构化输出得到同形状 JSON。"""
    # 软护栏：退款意图先在推理层引导（不是最终防线）
    if "退款" in task or "退" in task:
        return {"action": "refund", "arg": {"order_id": "A100", "amount": 680}}
    # 规划：先查再答；已查到就不重复查
    if "A100" in task and "已发货" not in mem.read():
        return {"action": "search_order", "arg": {"order_id": "A100"}}
    return {"action": "final", "arg": {"text": f"查询结果：{mem.read()}"}}

## ===================== Loop（把五件套转起来：感知-推理-行动-观察-记忆） =====================
def agent(task: str, mem: Memory, max_steps: int = 5) -> str:
    print(f"[Instructions] 已加载 {len(INSTRUCTIONS)} 字符指令")
    for step in range(1, max_steps + 1):
        print(f"[{step}] 感知：任务={task!r} 记忆={mem.read()!r}")
        decision = model_decide(task, mem)                       # 推理
        action, arg = decision["action"], decision["arg"]
        print(f"[{step}] 推理：决策={action} 参数={arg}")
        if action == "final":
            print(f"[{step}] 行动：输出最终回答")
            return arg["text"]
        tool = TOOLS[action]
        if tool["risk"] == "high":                               # 执行层硬护栏
            try:
                result = tool["fn"](**arg)                       # 未带 approved -> 抛异常
            except PermissionError as e:
                print(f"[{step}] 行动：高风险工具被执行层护栏拦下：{e}")
                return "抱歉，退款需人工审核，已为你转交人工处理。"
        else:
            result = tool["fn"](**arg)                           # 低风险工具直接执行
        print(f"[{step}] 观察：{result}")
        mem.write(result)                                        # 记忆(写)
    return "达到步数上限"

def main() -> None:
    print("=== T1：查询订单（只读，应正常完成）===")
    mem1 = Memory()
    print("最终回答：", agent("帮我查一下订单 A100 的状态", mem1))
    mem1.note_fact("last_order", "A100")                         # 沉淀长期记忆
    print("长期记忆 last_order =", mem1.recall_fact("last_order"))

    print("\n=== T2：退款（高风险，应被执行层护栏拦下）===")
    mem2 = Memory()
    print("最终回答：", agent("我要对订单 A100 退款", mem2))

if __name__ == "__main__":
    main()
```
保存为 `order_agent.py`，运行 `python order_agent.py`。完整输入就是代码里内置的两条测试输入 T1、T2；预期输出为：
```text
=== T1：查询订单（只读，应正常完成）===
[Instructions] 已加载 97 字符指令
[1] 感知：任务='帮我查一下订单 A100 的状态' 记忆=''
[1] 推理：决策=search_order 参数={'order_id': 'A100'}
[1] 观察：已发货，预计明天送达
[2] 感知：任务='帮我查一下订单 A100 的状态' 记忆='已发货，预计明天送达'
[2] 推理：决策=final 参数={'text': '查询结果：已发货，预计明天送达'}
[2] 行动：输出最终回答
最终回答： 查询结果：已发货，预计明天送达
长期记忆 last_order = A100

=== T2：退款（高风险，应被执行层护栏拦下）===
[Instructions] 已加载 97 字符指令
[1] 感知：任务='我要对订单 A100 退款' 记忆=''
[1] 推理：决策=refund 参数={'order_id': 'A100', 'amount': 680}
[1] 行动：高风险工具被执行层护栏拦下：退款必须经人工审核，拒绝执行
最终回答： 抱歉，退款需人工审核，已为你转交人工处理。
```
## 逐段讲解：把五件套一一点名

- `INSTRUCTIONS`：**指令**组件，既有角色设定（订单助手），也有护栏（退款需人工审核）。它是用自然语言写的**软护栏**——第一道防线，但不是最后防线。
- `search_order` / `refund` + `TOOLS` 注册表：**工具**组件。每个工具带 `risk` 风险等级，`search_order` 是只读低风险，`refund` 是写操作高风险。`refund` 内部的 `if not approved_by_human: raise` 是**执行层硬护栏**（第 04 节的核心）。
- `class Memory`：**记忆**组件，`short_term`（本轮上下文，`write`/`read`）与 `long_term`（跨会话键值，`note_fact`/`recall_fact`）显式分离（第 05 节）。
- `model_decide`：**模型 + 规划**。它产出 `{action, arg}` 结构化决策（第 03 节），其中“已发货就不重复查”是规划的雏形（先查再答、避免重复）。
- `agent` 里的 `for` 循环：**循环本体**，把感知（打印任务与记忆）、推理（`model_decide`）、行动（调工具）、观察（打印结果）、记忆（`mem.write`）串起来，`max_steps` 是防失控的安全阀。
- 循环里对 `tool["risk"] == "high"` 的 `try/except`：**执行层护栏在骨架里的接线点**。高风险工具即使被模型“决定”调用，也会因缺少人工审核而抛异常、被捕获并转人工——这正是开场 680 元事故的根治方案。

## 真实系统对应

**官方公开机制**：OpenAI 的指南给出的 `Agent(name=..., instructions=..., tools=[...])` 示例，正是把 Instructions 与 Tools 作为构造参数、由运行时循环驱动的形态；它也建议对高风险工具在执行前暂停做护栏检查 [来源](https://cdn.openai.com/business-guides-and-resources/a-practical-guide-to-building-agents.pdf)。把本骨架的 `model_decide` 换成一次真实函数调用，返回的工具名与参数 JSON 会替代规则决策，其余循环、护栏、记忆逻辑不变 [来源](https://platform.openai.com/docs/guides/function-calling)。**通用工程模式**：用“工具注册表 + 风险等级 + 执行层护栏 + 记忆分层 + 有上限的循环”组织任意 Agent，这套结构与具体框架无关。**教学参考实现**：`model_decide` 用 `if` 规则冒充模型、`long_term` 用内存字典冒充外部库、护栏用一个布尔冒充审批系统，都是为了免依赖可运行；真实系统会接入模型、持久化存储和审批工作流。LangGraph 等框架把这里的“循环 + 状态”做成显式的状态图与检查点，但内核仍是同一个五件套循环。

## 生产踩坑

| 症状 | 根因 | 如何观测与复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| 骨架跑起来但无法定位卡在哪一步 | 没有按阶段打点 | 移除 print 后复现，对比可读性 | 每轮每阶段打 step+stage 标签，接 Trace | 生产环境改为结构化日志而非 print |
| 换成真实模型后护栏失效 | 护栏写在 model_decide（软层），没在工具里 | 让模型产出退款决策观察是否执行 | 护栏必须在工具执行处（本骨架已如此） | 无 |
| 循环偶发不终止 | final 出口未被触发或缺步数上限 | 构造模型始终不产 final 的输入 | 保留 max_steps 上限 + 明确 final 决策 | 流式长任务需更大上限 |
| 高风险工具异常未捕获导致进程崩 | 只在低风险路径考虑正常返回 | 直接触发 refund 无审核 | 高风险工具调用包 try/except 并转人工 | 无 |
| 记忆跨请求串味 | 复用同一个 Memory 实例给不同会话 | T1、T2 共用一个 mem 交叉验证 | 每会话新建 Memory，长期记忆按用户键隔离 | 单用户单会话场景可放宽 |
| 工具参数与决策 arg 对不上导致 TypeError | 决策 arg 字段与函数签名不一致 | 故意让 arg 少一个字段 | 用结构化输出约束 Schema + 调用前校验 | 无 |
| 加了新工具模型却从不调用 | 未注册进 TOOLS 或描述缺失 | 检查注册表与决策分支 | 新工具登记注册表并补充清晰描述 | 无 |

## 思考：这个骨架和用框架写的 Agent，本质区别在哪？

### 回答

本质没有区别，只有“谁来写循环”的区别。框架（如 LangGraph、OpenAI Agents SDK）把“循环、工具调度、状态管理、重试”这些脚手架替你写好了，你只需配置指令、注册工具、选模型；而本骨架把这些脚手架显式摊开，让你看清每个零件的接线点。理解骨架的价值在于：**当框架出问题时，你知道去哪一层排查**——是感知没读到记忆、推理决策错了、行动执行失败，还是护栏没生效。很多人用框架用了很久却调不动 bug，正是因为从没见过没有框架时它长什么样。建议的学习路径是：先手写一遍骨架建立心智模型，再用框架提升工程效率，这样框架对你就是“透明”的而非“魔法”。

### 面试精简表达

“框架帮你写了循环和调度，骨架让你看清接线点；先手写理解本质，再用框架提效，出问题才知道查哪层。”

## 思考：把 model_decide 换成真实模型，需要改动骨架的哪些地方？

### 回答

改动面很小，这正是好骨架的标志。需要改的只有 `model_decide` 内部：把规则判断换成“组装上下文（指令 + 记忆 + 当前任务）→ 调用模型的函数调用接口 → 拿到模型返回的工具名与参数 JSON → 整理成 `{action, arg}` 返回” [来源](https://platform.openai.com/docs/guides/function-calling)。骨架的其余部分几乎不动：循环结构不变、`TOOLS` 注册表不变、`Memory` 不变、执行层护栏不变、`max_steps` 不变。需要额外注意三点：一是用结构化输出约束返回 Schema，避免解析失败（第 03 节）；二是模型可能一次返回多个工具调用，循环要能逐个处理；三是护栏绝不能跟着搬进 `model_decide`——它必须留在工具执行处，因为真实模型比规则更可能被诱导产出危险决策。改动小、护栏不动，这就是“护栏落在执行层”在架构上的红利。

## 扩展方向：从骨架到生产的三步

这个骨架是最小可运行版，离生产还有距离，但扩展路径是清晰的三步。**第一步，把模拟件换成真实件**：`model_decide` 接真实模型的函数调用，`long_term` 换成向量库或键值存储，`refund` 的 `approved_by_human` 接真实审批工作流。**第二步，把可观测性补上**：把 `print` 换成结构化 Trace，每轮记录 `trace_id`、阶段、决策、Token 用量、工具退出码，让线上故障能定位到具体阶段和组件（第 07 节会详细讲诊断方法）。**第三步，把韧性补上**：给工具调用加超时与重试、给写操作加幂等键、给循环加检查点以便崩溃后恢复。

值得强调的是，这三步扩展**没有一步需要推翻骨架的结构**——五件套的接线点、循环骨架、护栏位置始终不变，变的只是每个点背后的实现从“教学模拟”升级为“生产组件”。这也回答了“为什么要先手写骨架”：它给你一个稳定的心智坐标系，之后无论用什么框架、接什么模型、上什么存储，你都能把它们对应回这五个接线点。下一节，我们把这个骨架在生产环境里可能踩的每一个坑系统地列出来，并集中回答一批高频面试与工程思考题。
