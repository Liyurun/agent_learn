## 真实问题

第 01 节合并出五件套后，一位读者提了个尖锐的问题：“把 Model、Tools、Instructions、Planning、Memory 五个词记下来，我就会做 Agent 了吗？”答案是——不会。他随后拿这五个词去看一个真实项目的代码，发现每个组件都能找到对应的类和函数，可他还是说不清“这些零件是怎么让 Agent 动起来的”。这正是**只有静态清单、没有动态模型**的典型症状：知道有哪些零件，不等于知道发动机怎么转。

本节要补上的就是这块“运转模型”。我们把五件套放进一个统一循环——**感知 → 推理 → 行动 → 观察 → 记忆**，让静态清单变成动态过程。掌握这个循环后，你拿到任何一个 Agent 的代码，都能立刻定位“它现在转到哪一步、这一步动用了哪个组件”。

## 原理：五个阶段的循环

无论采用哪套组件划分，Agent 的运转都可归纳为一个循环：
```text
        ┌──────────────────────────────────────────┐
        │                                            │
        ▼                                            │
   ┌────────┐   ┌────────┐   ┌────────┐   ┌──────────┐
   │ 感知    │──▶│ 推理    │──▶│ 行动    │──▶│ 观察结果  │
   │(输入/   │   │(规划/   │   │(调用    │   │(环境反馈) │
   │ 反馈)   │   │ 决策)   │   │ 工具)   │   │          │
   └────────┘   └────────┘   └────────┘   └──────────┘
        ▲                                            │
        │              ┌────────┐                    │
        └──────────────│ 记忆    │◀───────────────────┘
                       │(读/写)  │
                       └────────┘
```
- **感知**：接收用户输入或上一轮行动的观察结果，连同记忆凑成本轮上下文；
- **推理**：结合指令与记忆，规划下一步动作（这一步由大语言模型完成）；
- **行动**：调用工具、生成输出，对环境产生影响；
- **观察**：拿到工具执行的结果或环境反馈；
- **记忆**：贯穿始终，短期记忆保存当前对话上下文，长期记忆存储可跨会话调用的知识。

这个循环把第 1 章“大语言模型 + 循环 + 工具 + 反馈”的直觉，进一步落到了可实现的组件上。它与 ReAct（Reasoning and Acting，推理与行动）范式高度一致——ReAct 让模型在“推理轨迹”和“行动”之间交替进行，推理帮助模型规划与纠错，行动让模型从外部获取信息 [来源](https://arxiv.org/abs/2210.03629)。本节的“推理→行动→观察→再推理”正是 ReAct 的循环骨架。

## 现象与输入：五件套如何映射进循环

上一节合并出的五件套是“零件清单”，这一节的循环是它们的“运转姿态”。把静态组件和动态阶段对起来看，理解会立刻立体：

| 循环阶段 | 主要动用的组件 | 这一步在干什么 |
|---|---|---|
| 感知 | Memory（读历史） | 把输入和记忆凑成上下文 |
| 推理 | Model + Instructions + Planning | 在护栏内决定下一步、拆任务、反思 |
| 行动 | Tools | 运行时执行工具（模型只提议，代码执行） |
| 观察 | （把结果交回感知） | 接收环境反馈 |
| 记忆 | Memory（写） | 把关键结论存下来供后续轮次使用 |

关键要理解：**组件是“零件”，循环是“运转”**。同样五个零件，静止摆着是一张清单，转起来才是一个 Agent。这也解释了为什么第 1 章说“循环是灵魂”——没有循环，五件套只是一个增强型大语言模型。

## 最小可运行演示

下面用贯穿案例订单助手，把循环的五个阶段显式打印出来。代码用规则模拟模型决策（无需 API Key），目的是让你**看见每一轮转到了哪个阶段、动用了哪个组件**，而不是被框架 API 遮住。
```python
INSTRUCTIONS = "只能查询订单，不得执行退款；信息足够就直接回答。"  # Instructions

def search_order(order_id: str) -> str:                              # Tools
    return {"A100": "已发货，预计明天送达"}.get(order_id, "订单不存在")

class Memory:                                                        # Memory
    def __init__(self): self.short_term = []
    def write(self, obs): self.short_term.append(obs)
    def read(self): return " | ".join(self.short_term)

def model_decide(task, mem):                                         # Model + Planning
    if "退款" in task:
        return {"action": "final", "text": "抱歉，我无权退款，请转人工。"}
    if "A100" in task and "已发货" not in mem.read():                 # 规划：先查再答
        return {"action": "search_order", "arg": "A100"}
    return {"action": "final", "text": f"查询结果：{mem.read()}"}

def agent(task, max_steps=5):
    mem = Memory()
    for step in range(1, max_steps + 1):
        print(f"[{step}] 感知：任务={task!r} 记忆={mem.read()!r}")
        decision = model_decide(task, mem)                          # 推理
        print(f"[{step}] 推理：决定 {decision['action']}")
        if decision["action"] == "final":
            print(f"[{step}] 行动：输出最终回答")
            return decision["text"]
        result = search_order(decision["arg"])                      # 行动
        print(f"[{step}] 观察：{result}")
        mem.write(result)                                           # 记忆(写)
    return "达到步数上限"

print("=== T1 ===");  print(agent("帮我查一下订单 A100 的状态"))
print("=== T2 ===");  print(agent("我要对订单 A100 退款"))
```
保存为 `loop_trace.py`，运行 `python loop_trace.py`，预期输出：
```text
=== T1 ===
[1] 感知：任务='帮我查一下订单 A100 的状态' 记忆=''
[1] 推理：决定 search_order
[1] 观察：已发货，预计明天送达
[2] 感知：任务='帮我查一下订单 A100 的状态' 记忆='已发货，预计明天送达'
[2] 推理：决定 final
[2] 行动：输出最终回答
查询结果：已发货，预计明天送达
=== T2 ===
[1] 感知：任务='我要对订单 A100 退款' 记忆=''
[1] 推理：决定 final
[1] 行动：输出最终回答
抱歉，我无权退款，请转人工。
```
读这段轨迹，你能清楚看到 T1 转了两轮（第一轮查、第二轮答），T2 只转了一轮（推理阶段就被指令拦下）。**同一套五件套，因为输入不同走出了不同的循环路径**——这正是“模型控制工作流”的体现。注意 T2 这里的拦截仍在推理层、且是字符串匹配，属于“软护栏”，第 04 节会讲为什么真正的护栏要落到执行层。

## 真实系统对应

**官方公开机制**：ReAct 论文明确提出“推理轨迹 + 行动”交替的范式，并在多跳问答、事实核查、交互决策任务上验证了它优于纯推理或纯行动 [来源](https://arxiv.org/abs/2210.03629)。Anthropic 的《Building Effective Agents》把这种“模型在循环里调用工具、根据环境反馈决定下一步”的形态定义为 Agent，与预先写死流程的 Workflow 相区别 [来源](https://www.anthropic.com/engineering/building-effective-agents)。**通用工程模式**：把 Agent 运行时抽象成“感知—推理—行动—观察—记忆”五阶段状态机，便于打点观测——每一轮记录进入了哪个阶段、动用了哪个组件、Token 花在哪里。**教学参考实现**：上面的 `agent` 循环用 `print` 暴露每一步，是为了教学可见，真实系统会把这些轨迹写进结构化日志或 Trace（追踪）系统而非直接打印。

## 生产踩坑

| 症状 | 根因 | 如何观测与复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| Agent 陷入死循环反复调同一个工具 | 循环没有终止条件或步数上限 | 打印每轮 action，观察是否重复 | 设 `max_steps` 安全阀 + 检查记忆避免重复调用 | 明确的流式长任务需更大的上限 |
| 记忆写了但下一轮读不到 | 感知阶段没有把记忆拼进上下文 | 在感知步打印记忆内容 | 确保感知阶段显式读取并拼接记忆 | 无状态单轮任务不需要 |
| 观察结果未回写，模型“忘了”刚查到的信息 | 缺少“观察→记忆(写)”这条边 | 检查工具返回后是否落库/落上下文 | 每次工具调用后强制写回记忆 | 纯 fire-and-forget 通知类工具例外 |
| 循环转很多轮但产出没进展 | 推理阶段没有“是否已足够”的判断 | 记录每轮是否有新信息进入记忆 | 推理时显式判断“信息是否足够可停止” | 探索类任务允许多轮无结论 |
| 分不清某次失败发生在哪一步 | 没有按阶段打点 | 给每轮每阶段加 step 与 stage 标签 | 建立阶段级 Trace，先定位阶段再查组件 | 无 |

## 思考：为什么“循环”而不是“流水线”才是 Agent 的本质？

### 回答

流水线是“预先写死的固定步骤序列”——先做 A、再做 B、最后做 C，步数和顺序在代码里定死。循环的关键区别在于**“是否继续、下一步做什么”由模型基于观察结果动态决定**。在本节的 T1 里，模型查到订单后判断“信息够了，可以停”；如果它没查到，会判断“再查一次”。这个“查几次、要不要再查”的决定权在模型手里，而不是代码写死“固定查 2 次”。一旦这个决定权交给模型，系统就从流水线升级为 Agent；反之，把决定权收回代码，它就退回工作流。所以本质不在“有没有循环体”，而在“循环的终止与分支由谁决定”。

### 反例

如果把 `model_decide` 改成“无论如何都先调一次 search_order 再 final”，那么无论用户问什么，它都固定两步——这就退化成了流水线，即使它写在 `for` 循环里。可见循环的形式不等于 Agent 的实质，实质是控制权的归属。

## 思考：这个五阶段循环和 ReAct 是什么关系？

### 回答

本节的“感知—推理—行动—观察—记忆”循环是 ReAct 范式的一个工程化、显式化版本。ReAct 的核心贡献是提出让模型交替产生“推理轨迹（thought）”和“行动（action）”，行动的结果作为“观察（observation）”再喂回模型继续推理 [来源](https://arxiv.org/abs/2210.03629)。本节的循环把 ReAct 的“thought / action / observation”对应到“推理 / 行动 / 观察”，并额外显式化了两件 ReAct 论文默认隐含的事：一是“感知”阶段要主动把记忆拼进上下文，二是“记忆”作为跨轮持久层要显式读写。换句话说，ReAct 描述的是模型层面的交替模式，本节循环描述的是工程层面的组件运转，两者是同一件事的不同抽象层。

## 机制推导：从“一次调用”到“持续循环”

一个容易被忽略的点是：大语言模型本身是**无状态**的——每次 API 调用都是独立的，模型不会自动记得上一轮说过什么。那么“循环”和“记忆”从哪来？答案是：它们都由模型外的代码搭建。循环体（`for step in range(max_steps)`）是代码写的；每轮把历史拼进上下文（感知阶段的 `mem.read()`）也是代码做的；把工具结果写回（`mem.write(result)`）还是代码做的。**模型只负责“给定当前上下文，产出下一步决策”这一件事，其余的状态维持、循环推进、记忆读写，全是工程搭的脚手架。**

理解这一点非常重要，因为它划清了“模型能力”和“工程责任”的边界。当 Agent 出现“失忆”时，十有八九不是模型变笨了，而是工程侧的“感知阶段没把记忆拼进去”或“观察阶段没把结果写回”。当 Agent 死循环时，也不是模型的错，而是工程侧没设终止条件。把循环显式画成五阶段状态机，最大的收益就是**故障可以被定位到具体阶段**：是感知没读到、推理判断错、行动执行失败，还是记忆没写回。这种“先定位阶段、再查组件”的排障方法，会在第 07 节的生产诊断里反复用到。

## 循环与组件的协同：一次完整轨迹回放

再用贯穿案例走一遍完整协同，把五件套在循环里如何“彼此喂养”看清楚。用户输入“帮我查订单 A100”，第一轮：感知阶段 Memory 读到空历史，把用户输入作为上下文；推理阶段 Model 在 Instructions 护栏内、用 Planning 判断“我还不知道订单状态，得先查”，产出决策“调 search_order”；行动阶段 Tools 执行查询；观察阶段拿到“已发货”；记忆阶段把“已发货”写进短期记忆。第二轮：感知阶段 Memory 这次读到了“已发货”，推理阶段 Model 判断“信息够了，可以回答”，产出最终答案，循环结束。

在这条轨迹里，没有任何一个组件是孤立工作的：Planning 产出“下一步计划”，Tools 去执行，Memory 保存执行结果供下一轮 Planning 参考，Instructions 全程约束推理不越界，Model 在每一轮做“下一步做什么”的决策。**五件套从来不是各干各的，它们在循环里首尾相接、互相喂养**——这也是为什么单看组件清单学不会做 Agent，必须看它们在循环里的协同。下一节我们放大循环最核心的“推理”阶段，看模型这个决策核心到底在输出什么。
