## 真实问题

一位候选人在面试里被问“Agent 由哪些组件构成”，他背出“规划、记忆、工具”，面试官追问“那 OpenAI 的说法呢”，他愣住了，因为他看过的另一篇资料写的是“模型、工具、指令”，两套对不上，他以为自己记错了。其实两套都对——它们出自两份都极具影响力的一手资料，只是**站在不同层面描述同一个东西**。分不清这一点，不仅面试会卡壳，工程上也会走弯路：只学 OpenAI 那套的人容易忽略“记忆和规划要专门设计”，只学 Lilian Weng 那套的人容易忽略“护栏得当成一等工程问题”。

本节要解决的就是这个混淆：把两套划分放在一张桌子上对照，说清各自看重什么、在哪里重叠、如何合并成一个不遗漏的“五件套”清单。合并之后的清单，才是后面所有小节拆解的对象。

## 原理：两套划分分别看什么

第一套来自 OpenAI 的《A Practical Guide to Building Agents》，它把 Agent 拆成三件 [来源](https://cdn.openai.com/business-guides-and-resources/a-practical-guide-to-building-agents.pdf)：

| 组件 | 职责 | 一句话理解 |
|---|---|---|
| Model（模型） | 推理与决策的核心，决定“下一步做什么” | Agent 的大脑 |
| Tools（工具） | 获取信息、影响外部世界的手段 | Agent 的手脚 |
| Instructions（指令） | 定义行为规范、目标与护栏 | Agent 的规矩 |

第二套来自 Lilian Weng 的《LLM Powered Autonomous Agents》，她把“LLM 作为核心大脑”之外的能力拆成三件 [来源](https://lilianweng.github.io/posts/2023-06-23-agent/)：

| 组件 | 职责 | 一句话理解 |
|---|---|---|
| Planning（规划） | 任务分解、制定子目标、反思与自我批评 | Agent 的谋划 |
| Memory（记忆） | 短期记忆（上下文）与长期记忆（外部存储） | Agent 的经验 |
| Tool Use（工具使用） | 调用外部 API 或函数扩展模型能力 | Agent 的行动 |

两套划分不是竞争关系。OpenAI 的指南面向**产品与工程团队**——他们关心“怎么把这东西做出来、上线、别出事”，所以把 Instructions（把行为规范和护栏写清楚）单列为一件，因为在生产里“模型该做什么、绝不能做什么”是第一位的工程问题。Lilian Weng 的博客面向**研究与理解**——她关心“一个自主体需要哪些认知能力”，所以拆出 Planning（会不会拆解、会不会反思）和 Memory（能不能记住），因为这是从能力维度看智能体的自然切法。

用一个比喻：描述同一辆车，修车师傅会说“发动机、变速箱、底盘”（工程视角），驾校教练会说“动力、转向、刹车”（能力视角）。两套词说的是同一辆车。

## 现象与输入：把两套划分叠在一张表上

把两套划分逐能力对照，交集与各自侧重就一目了然：

| 能力维度 | OpenAI 是否单列 | Lilian Weng 是否单列 | 说明 |
|---|:---:|:---:|---|
| 决策核心 | 是（Model） | 隐含（决策由 LLM 大脑做） | 两者都以模型为大脑 |
| 行动能力 | 是（Tools） | 是（Tool Use） | 完全对应，同一件事 |
| 行为规范与护栏 | 是（Instructions） | 未单列 | OpenAI 的工程侧重 |
| 任务分解与反思 | 未单列 | 是（Planning） | Weng 的认知侧重 |
| 记忆 | 未单列 | 是（Memory） | Weng 的认知侧重 |

读这张表的要点是：两套都有“决策核心”和“行动能力”，这是重叠区；差异在于 OpenAI 额外把“护栏”提到台面，Weng 额外把“规划”和“记忆”提到台面。**把两套的并集取出来，就得到一个谁都不遗漏的完整清单。**

合并后的“全组件清单”即：**Model + Tools + Instructions + Planning + Memory** 五件套。这正是后续各小节要逐个拆解、并在第 06 节组装成骨架的全部内容。

## 最小可运行演示

下面用一段纯 Python（无需 API Key）把“同一个 Agent、两种拆法”变成可执行的数据结构。它把贯穿案例订单助手的五个零件分别打上“来自哪套划分”的标签，然后打印出并集清单，直观展示合并过程。
```python
OPENAI_VIEW = {
    "Model": "决策核心：决定下一步做什么",
    "Tools": "行动手段：查询订单、退款",
    "Instructions": "行为规范与护栏：退款需人工审核",
}
WENG_VIEW = {
    "Planning": "任务分解与反思：先查再答",
    "Memory": "经验：短期上下文 + 长期用户历史",
    "Tool Use": "调用外部函数：等价于 Tools",
}

ALIAS = {"Tool Use": "Tools"}  # Tool Use 与 Tools 是同一件事，合并时视为一个键

def merge(a: dict, b: dict) -> dict:
    merged = dict(a)
    for name, duty in b.items():
        key = ALIAS.get(name, name)
        if key in merged:
            merged[key] += f"；（Weng 视角同样强调：{name}）"
        else:
            merged[key] = duty
    return merged

def main() -> None:
    five = merge(OPENAI_VIEW, WENG_VIEW)
    print(f"合并后组件数：{len(five)}")
    for i, (name, duty) in enumerate(five.items(), 1):
        print(f"{i}. {name}：{duty}")

if __name__ == "__main__":
    main()
```
保存为 `two_taxonomies.py`，运行 `python two_taxonomies.py`，预期输出：
```text
合并后组件数：5
1. Model：决策核心：决定下一步做什么
2. Tools：行动手段：查询订单、退款；（Weng 视角同样强调：Tool Use）
3. Instructions：行为规范与护栏：退款需人工审核
4. Planning：任务分解与反思：先查再答
5. Memory：经验：短期上下文 + 长期用户历史
```
这段代码的价值不在算法，而在于它把“合并”这个抽象动作变成一个可核验的结果：`Tool Use` 被识别为 `Tools` 的别名而合并，最终恰好落到 5 个键。你可以把 `ALIAS` 里的合并规则改掉，观察组件数如何变化，从而亲手体会“为什么是五件套而不是六件套”。

## 真实系统对应

**官方公开机制**：OpenAI 的指南在示例代码里用 `Agent(name=..., instructions=..., tools=[...])` 的形式把三件套写进 Agents SDK（Software Development Kit，软件开发工具包），其中 `instructions` 参数正对应 Instructions 组件，`tools` 列表对应 Tools 组件，而 Model 由运行时选择 [来源](https://cdn.openai.com/business-guides-and-resources/a-practical-guide-to-building-agents.pdf)。Lilian Weng 的博客则用一张系统图把 LLM 放中心，Planning、Memory、Tool Use 环绕四周 [来源](https://lilianweng.github.io/posts/2023-06-23-agent/)。**通用工程模式**：把两套并集当作“组件检查清单”，在设计任何 Agent 时逐项自问“我这套系统有没有显式设计规划？有没有独立的记忆层？护栏落在哪里？”**教学参考实现**：上面的 `merge` 函数只是演示合并逻辑，任何真实框架都不会用别名字典来“拼装”组件。

Anthropic 的《Building Effective Agents》没有用这两套词，而是从“增强型 LLM（augmented LLM）”出发，强调检索、工具、记忆是给模型的增强能力，工作流与 Agent 是这些增强能力的不同组合方式 [来源](https://www.anthropic.com/engineering/building-effective-agents)。三份资料措辞不同，但都承认“模型 + 工具 + 记忆 + 编排/规划 + 规范”这组要素，交叉印证了五件套的合理性。

## 生产踩坑

| 症状 | 根因 | 如何观测与复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| 团队只按 OpenAI 三件套建系统，长任务频繁“失忆” | 没把 Memory 当一等组件设计，全靠上下文窗口 | 把同一任务拉长到 20 轮，检查早期约束是否还在输入里 | 显式引入短期/长期记忆层，关键事实带来源固定 | 单轮问答类应用确实不需要长期记忆 |
| 只学 Weng 三件套，上线后被提示注入绕过 | 没把 Instructions/护栏当一等组件，护栏只写在提示里 | 用“换个措辞的危险指令”做红队测试 | 把护栏落到工具执行层做确定性校验 | 纯只读、无副作用的 Demo 风险较低 |
| 面试答“组件”只背一套，被追问即卡壳 | 不理解两套是不同视角 | 自测：能否说出两套的重叠项与差异项 | 记忆“并集 = 五件套 + 视角差异”框架 | 无 |
| 把 Tools 和 Tool Use 当成两个不同组件 | 没识别出别名重叠 | 画对照表检查交集 | 明确二者等价，合并计一件 | 无 |

## 思考：面试问“Agent 由哪些组件构成”，怎样回答能拿高分？

### 回答

不要只背一套。高分回答分三步：先点明“业界有两套常被引用的划分”——OpenAI 强调 Model / Tools / Instructions（偏工程落地），Lilian Weng 强调 Planning / Memory / Tool Use（偏认知能力）；再说明“二者是视角不同而非对错”，OpenAI 站在产品团队角度所以把护栏单列，Weng 站在研究角度所以把规划和记忆单列；最后给出并集结论——合起来是 **Model、Tools、Instructions、Planning、Memory** 五件套，其中 Tools 与 Tool Use 是同一件。能主动指出“视角差异”而不是纠结“听谁的”，是理解深度的信号。

### 面试精简表达

“两套划分是同一辆车的两种拆法：OpenAI 是修车师傅看零件（模型/工具/指令），Weng 是教练看能力（规划/记忆/工具）；取并集就是五件套，Tool Use 和 Tools 是一回事。”

## 思考：为什么“合并成五件套”比“选一套背下来”更有工程价值？

### 回答

因为工程落地时任何一件缺失都会出事，而单独一套划分都会“遗漏一部分”。只按 OpenAI 三件套建系统，容易忘记专门设计 Memory 和 Planning，结果长任务失忆、复杂任务硬答；只按 Weng 三件套建系统，容易忽视 Instructions 与护栏，结果被提示注入绕过。五件套是一张“别漏项”的检查清单：设计时逐项确认“模型选型、工具接口、指令与护栏、规划策略、记忆分层”都被显式设计过，就能避免上线后才发现某一维度完全没人负责。

## 视角差异的更深一层：为什么会“同物异名”

“同一个东西有两套名字”在工程史上很常见，根源是**描述者的目标不同，因而切分维度不同**。OpenAI 的读者要交付产品，他们的第一问题是“这玩意上线会不会闯祸”，所以护栏（Instructions）必须被提到与模型、工具并列的高度——在他们的世界里，一个没写清护栏的 Agent 是不能上线的半成品。Lilian Weng 的读者要理解智能，他们的第一问题是“一个自主体需要哪些认知能力才能自己完成复杂任务”，所以规划（会不会拆解、会不会反思）和记忆（能不能积累经验）必须被单列——在她的世界里，一个不会规划、没有记忆的系统只是个会调工具的问答机。

这也解释了为什么 Anthropic 又用了第三套词（增强型 LLM + 工作流/Agent）：他们的目标是帮工程师**判断该不该用 Agent、用哪种编排**，所以他们的切分维度是“自主性从低到高的组合方式”，而不是“零件清单”[来源](https://www.anthropic.com/engineering/building-effective-agents)。三套词服务三种目标，彼此不冲突。理解这一层，你以后再遇到“第四套、第五套划分”也不会慌——先问“作者想解决什么问题、因此按什么维度切”，答案自然浮现。

## 一个常见误解的澄清

初学者常问：“既然 Weng 没把 Instructions 单列，是不是说明她认为护栏不重要？”不是。Weng 的博客把“系统提示/角色设定”默认包含在给 LLM 的上下文里，只是没有把它拎出来当独立组件强调；这是**详略选择**，不是**观点否定**。同理，OpenAI 没单列 Memory 和 Planning，也不代表它认为不需要——它的指南在别处讨论了会话状态与多步编排，只是没有把它们塞进“三件套”这个最精炼的记忆锚点。读一手资料时，区分“作者没强调”和“作者反对”是一项重要的阅读素养，否则很容易把“表达的侧重”误读成“立场的对立”。

因此，本章后续统一采用五件套作为拆解框架：它不是要取代任何一套原始划分，而是把三份一手资料的共识提取出来，做成一张不遗漏、可核对的工程清单。下一节，我们把这张静态清单“转起来”，看它在感知—推理—行动—记忆的循环里如何各就各位。
