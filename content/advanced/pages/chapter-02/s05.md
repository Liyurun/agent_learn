## 真实问题

订单助手上了一个新功能：处理“批量退货 + 重新下单 + 改地址”的组合请求。第一次测试就翻车了——用户说“把 A100、A101 两单退了，用退款的钱重新下一单发到我新地址”，助手直接调了一次 `refund(A100)` 就停了，既没处理 A101，也没下单、没改地址。它不是不会用工具，而是**面对多步任务时没有“先拆解、再逐步执行、中途还能回看进度”的能力**。这就是缺少 Planning（规划）。

同一周还有另一个投诉：用户上午问过“我常用地址是望京”，下午再来对话，助手完全不记得，又问了一遍地址。这不是模型笨，而是**跨会话的信息没有被存下来、需要时也没被取回**。这就是缺少 Memory（记忆）的长期部分。

本节讲清 Agent 五件套里最后两件——Planning 让 Agent 能应对复杂任务，Memory 让 Agent 有跨越上下文的连续性。它们是 Lilian Weng 划分里被单独强调的两件认知能力 [来源](https://lilianweng.github.io/posts/2023-06-23-agent/)。

## 原理一：Planning——把大任务拆小、并能反思

规划让 Agent 面对复杂任务时不至于“一口吃成胖子”。它包含两个子能力：**任务分解**（把大目标拆成有序的子目标）和**反思**（对已完成的步骤自我批评、发现错误、纠正）。常见方法有 CoT（Chain-of-Thought，思维链）、Tree of Thoughts 等。

为什么规划能提升表现？直觉上的原因是：大语言模型是“自回归”逐词生成的，它没有“草稿纸”——如果逼它对一个复杂问题一步到位给答案，它必须在生成第一个字之前就把全部推理在“脑内”完成，这超出了它的能力。CoT（思维链）相当于**给模型一张草稿纸**：让它把中间推理显式写出来，每一步都在前一步基础上继续，把一个大跳跃拆成若干小跳跃。Wei 等人的研究表明，让模型生成中间推理步骤能显著提升它在算术、常识和符号推理任务上的表现 [来源](https://arxiv.org/abs/2201.11903)。反思则更进一步——让模型回头看自己的产出、发现错误、修正，相当于“自己给自己批改作业”，这也是 ReAct 里“推理轨迹帮助模型追踪和更新行动计划、处理异常”的价值所在 [来源](https://arxiv.org/abs/2210.03629)。
```text
   无规划（硬答）                有规划（拆解+反思）
   问题 ──▶ 答案                问题
   （一步到位，                  ├─ 子目标1：退 A100 ──▶ 做 ──┐
    大跳跃易错）                 ├─ 子目标2：退 A101 ──▶ 做 ──┤
                                ├─ 子目标3：重新下单 ─▶ 做 ──┤
                                ├─ 子目标4：改地址 ──▶ 做 ──┤
                                └─ 反思：漏了哪步？────────────┘
                                        │ 修正
                                        ▼
                                       答案（小步、可纠错）
```
## 原理二：Memory——短期与长期

记忆分两类。**短期记忆**约等于“上下文内学习（in-context learning）”，即塞进上下文窗口的对话历史，受窗口大小限制；**长期记忆**是外部存储（常用向量数据库），通过快速检索调用近乎无限的历史信息 [来源](https://lilianweng.github.io/posts/2023-06-23-agent/)。用一个类比记牢：

- 短期记忆像人的“工作记忆”——你正在心算时脑子里暂存的那几个数字，容量小、一走神就没了（对应上下文窗口，会话结束就丢失）；
- 长期记忆像“笔记本”——写下来的东西可以永久保存，需要时翻出来查（对应外部向量库，可跨会话检索）。
```text
   短期记忆（工作记忆）              长期记忆（笔记本）
   ┌────────────────┐              ┌────────────────────┐
   │ 上下文窗口       │              │ 外部向量库/数据库    │
   │ - 本轮对话历史   │  写入关键信息  │ - 用户长期偏好      │
   │ - 容量有限       │ ───────────▶ │ - 历史结论          │
   │ - 会话结束即丢   │  需要时检索    │ - 近乎无限、可跨会话 │
   └────────────────┘ ◀─────────── └────────────────────┘
```
一个关键的工程权衡：**当前任务必需的信息放短期（上下文），跨会话才用得上的知识放长期（外部库）**。短期记忆模型“立刻能看到”但每个 token 都要花钱、且窗口会满；长期记忆省 token、可无限扩展，但需要一次检索、且检索不一定命中。用长期记忆做检索增强，正是 RAG（Retrieval-Augmented Generation，检索增强生成）的思路——把外部知识检索出来拼进上下文再生成，以缓解模型知识过期和幻觉 [来源](https://arxiv.org/abs/2005.11401)。

## 最小可运行演示

下面用纯 Python 把“规划 + 短期/长期记忆”一次演示清楚，解决开场的组合任务。它先把大任务拆成子目标队列（Planning），逐个执行并把结果写进短期记忆，最后把“用户新地址”沉淀进长期记忆供下次会话使用。无需 API Key。
```python
class Memory:
    def __init__(self):
        self.short_term: list[str] = []          # 本轮上下文，会话结束即弃
        self.long_term: dict[str, str] = {}      # 跨会话键值，需要时取回
    def write_short(self, obs): self.short_term.append(obs)
    def note_fact(self, key, value): self.long_term[key] = value
    def recall_fact(self, key): return self.long_term.get(key)

def plan(task: str) -> list[str]:
    """任务分解：把复合请求拆成有序子目标（Planning 的核心）。"""
    steps = []
    if "退" in task:
        steps += [f"退款:{oid}" for oid in ("A100", "A101")]
    if "重新下一单" in task or "重新下单" in task:
        steps.append("重新下单")
    if "地址" in task:
        steps.append("更新地址:望京SOHO")
    return steps

def execute(step: str, mem: Memory) -> str:
    if step.startswith("退款"):
        return f"已提交人工审核：{step}"
    if step == "重新下单":
        return "已创建新订单 A200"
    if step.startswith("更新地址"):
        addr = step.split(":", 1)[1]
        mem.note_fact("default_address", addr)   # 沉淀进长期记忆
        return f"已更新默认地址为 {addr}"
    return "未知步骤"

def agent(task: str) -> Memory:
    mem = Memory()
    subgoals = plan(task)
    print(f"规划得到 {len(subgoals)} 个子目标：{subgoals}")
    for i, step in enumerate(subgoals, 1):
        result = execute(step, mem)
        mem.write_short(result)
        print(f"  步骤{i} {step} -> {result}")
    # 反思：检查是否所有子目标都已产生结果
    if len(mem.short_term) == len(subgoals):
        print("反思：全部子目标已完成，无遗漏")
    return mem

def main() -> None:
    mem = agent("把 A100、A101 两单退了，用退款的钱重新下一单发到我新地址")
    print("会话结束，短期记忆清空。长期记忆保留：")
    print(f"  下次会话可回忆默认地址 = {mem.recall_fact('default_address')}")

if __name__ == "__main__":
    main()
```
保存为 `plan_memory.py`，运行 `python plan_memory.py`，预期输出：
```text
规划得到 4 个子目标：['退款:A100', '退款:A101', '重新下单', '更新地址:望京SOHO']
  步骤1 退款:A100 -> 已提交人工审核：退款:A100
  步骤2 退款:A101 -> 已提交人工审核：退款:A101
  步骤3 重新下单 -> 已创建新订单 A200
  步骤4 更新地址:望京SOHO -> 已更新默认地址为 望京SOHO
会话结束，短期记忆清空。长期记忆保留：
  下次会话可回忆默认地址 = 望京SOHO
```
对照开场的两个投诉：`plan` 把复合请求拆成 4 个子目标，逐个执行不再漏步（解决了“只退一单就停”）；`note_fact` 把“新地址”写进长期记忆，`recall_fact` 让下次会话能取回（解决了“下午又问一遍地址”）。注意退款步骤仍返回“已提交人工审核”，因为第 04 节的执行层护栏依然生效——**规划和记忆不会绕过安全边界**。

## 真实系统对应

**官方公开机制**：Lilian Weng 把 Planning（任务分解 + 反思）和 Memory（短期 = 上下文内学习，长期 = 外部向量存储）作为 LLM 自主智能体的两大组件明确列出 [来源](https://lilianweng.github.io/posts/2023-06-23-agent/)；CoT 提升推理、ReAct 交替推理与行动、RAG 用外部检索增强，都是有论文支撑的机制 [来源](https://arxiv.org/abs/2201.11903) [来源](https://arxiv.org/abs/2210.03629) [来源](https://arxiv.org/abs/2005.11401)。**通用工程模式**：把长期记忆实现为向量库或键值存储 + 检索，把规划实现为显式的子目标队列或状态图（如 LangGraph 的图结构）。**教学参考实现**：上面的 `plan` 用关键词匹配来“拆任务”，`long_term` 用内存字典充当外部库；真实系统的分解由模型完成、长期记忆是持久化的向量/键值存储、检索是语义相似度查询，而非字典 `get`。规划的深入方法（CoT、Tree of Thoughts、Reflexion 等）是第 4 章主题，记忆的检索、切块、时效管理是第 5 章主题，本节只建立组件级直觉。

## 生产踩坑

| 症状 | 根因 | 如何观测与复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| 复合请求只做了第一步就停 | 没有任务分解，模型把多步当单步 | 给一个含 3+ 子任务的请求观察执行 | 显式规划成子目标队列，逐个执行并核对 | 单步简单请求无需规划 |
| 拆出的子目标有遗漏或顺序错 | 分解质量差、缺反思 | 对比子目标清单与用户原始意图 | 执行后加反思步校验覆盖度与顺序 | 顺序无关任务可放宽 |
| 跨会话“失忆”，反复问同样信息 | 只有短期记忆，无长期沉淀 | 新开会话问上次给过的信息 | 关键偏好写长期记忆，会话开始时取回 | 一次性任务无需长期记忆 |
| 长期记忆检索不命中 | 检索粒度/相似度阈值不当 | 查实际检索到的片段 | 调整切块、重排、阈值；关键事实结构化存 | 键值精确查询不涉及此问题 |
| 什么都往长期记忆塞，越来越乱 | 没区分“该沉淀 vs 用完即弃” | 统计长期记忆增长与命中率 | 只沉淀跨会话有用的信息，加来源与时效 | 审计场景需长期保留 |
| 短期记忆塞满导致成本飙升或截断 | 把该进长期的信息堆在上下文 | 监控每轮输入 token 与截断 | 当前任务必需留短期，其余移长期检索 | 窗口充裕的短任务可放宽 |
| 反思变成无限自我否定循环 | 反思没有终止条件 | 观察是否反复推翻自己 | 限定反思轮数、要求给出可执行修正 | 无 |
| 长期记忆跨用户串味 | 记忆键缺少用户/租户隔离 | 用两个用户交叉测试 | 记忆键带用户/租户维度，访问控制 | 无 |

## 思考：什么信息该进短期记忆、什么该进长期记忆？

### 回答

判断准则是**“这条信息在当前任务之外还用得上吗”**。用得上就进长期，用不上就进短期（用完即弃）。具体地：当前任务必需、且任务结束就无价值的信息（如“本轮已查到 A100 已发货”）放短期记忆，随会话结束丢弃；跨会话反复有用的信息（如“用户默认地址”“用户过敏原”“用户长期偏好”）放长期记忆，带上来源和时效，下次会话主动取回。判断时还要问两个补充问题：一是“它会不会失效”（会失效的要带时效，如地址可能变），二是“它属于谁”（要按用户/租户隔离，防止跨用户串味）。核心权衡是成本与可得性：短期立刻可见但费 token、会挤满窗口；长期省 token、可无限扩展，但要一次检索且可能不命中。

### 面试精简表达

“当前任务用完就丢的进短期，跨会话还要用的进长期；长期记忆要带来源、时效和用户隔离。”

## 思考：规划（尤其是 CoT）为什么能让模型答得更准？

### 回答

因为大语言模型是自回归逐词生成的，没有独立的“思考空间”。如果逼它对复杂问题一步到位输出答案，它必须在生成第一个词之前就把全部推理在内部完成，这对多步问题很容易出错。CoT（思维链）相当于给模型一张草稿纸，让它把中间推理显式写出来——每一步都建立在前一步之上，把一个容易出错的大跳跃拆成若干个更可靠的小跳跃，Wei 等人的实验证明这能显著提升算术、常识、符号推理的表现 [来源](https://arxiv.org/abs/2201.11903)。任务分解是同样的思想用在“行动”上：把复合任务拆成有序子目标逐个完成，避免漏步。反思则是让模型回看产出、发现并纠正错误。三者的共同本质是**用“显式的、可检查的中间步骤”替代“一步到位的黑箱跳跃”**。

## 机制推导：规划、记忆、工具如何彼此喂养

一个常见误区是把五件套当成各自独立的模块。实际上，规划、记忆、工具在循环里是**首尾相扣、互相供给**的。规划产出“下一步子目标”，工具去执行这个子目标，执行结果由记忆保存下来，下一轮规划再基于记忆里的最新进度决定“接下来做哪个子目标、要不要修正计划”。在开场的组合任务里，这个协同清晰可见：`plan` 产出四个子目标（规划），`execute` 逐个调用对应能力（工具），每步结果写进 `short_term`（记忆），最后的反思步靠“已完成结果数是否等于子目标数”来判断有没有漏（规划的反思用到了记忆里的执行记录）。

这种协同还解释了为什么“缺一件套”的系统会表现出特定的病症。缺规划：复合任务只做第一步（开场投诉一）。缺长期记忆：跨会话失忆（开场投诉二）。缺短期记忆：同一轮里刚查到的信息下一步就忘。缺工具：只能说不能做。缺护栏（指令）：危险动作裸奔（第 04 节的 680 元事故）。把五件套放进循环、让它们互相喂养，Agent 才能稳定处理真实世界里那些“多步、跨会话、还不能出安全事故”的任务。
