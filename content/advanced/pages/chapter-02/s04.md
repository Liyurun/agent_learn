## 真实问题

回到本章开场那个真实事故：订单助手直接退了用户 680 元。事后团队调出日志，发现系统提示里明明白白写着“涉及退款必须先经人工审核”。指令写了，为什么没拦住？因为那句话只是**写给模型的一句请求**，退款函数本身没有任何校验——模型一旦“决定”退款，代码就照单执行。这就是本节要讲清的两件套 Tools 和 Instructions 的核心张力：**工具是真正能改变世界的手，指令里的护栏如果只是嘴上说说，就拦不住手。**

本节解决两个问题：一是工具在模型眼里到底是什么、为什么工具描述的质量直接决定调用准确率；二是护栏为什么必须落到执行层，纯提示词护栏为什么靠不住。这两件事想通了，开场那 680 元的事故就永远不会再发生。

## 原理一：工具是“名称 + 描述 + 参数 Schema”

工具让 Agent 能“做事”而不只是“说话”。但一个关键事实是：**模型看不到工具的源码，它只能读工具的名称和描述来猜这个工具是干什么的、什么时候该用、参数怎么填**。所以在模型眼里，一个工具就是三样东西：
```text
工具 = 名称 + 自然语言描述 + 参数的 JSON Schema
       (search_order) (查询订单状态，只读)  ({"order_id": string})
```
由此推出 Agent 工程里最重要的一条原则——**“模型提议、运行时处置”**：模型只负责“提议”调用哪个工具、传什么参数，真正的执行发生在你的代码侧。这条原则是理解工具安全性的钥匙：既然执行在代码侧，那么权限、校验、审计这些安全动作也都应该在代码侧完成，而不是指望模型自觉。

因为模型完全依赖描述来选工具，**工具描述写得好不好，是 Agent 出错的头号来源之一**。描述含糊，模型就会选错工具或传错参数。看一个正反对比：
```python
def search(q):  # 反例：描述含糊，模型不知道何时该用、参数是什么格式
    """搜索。"""
    ...

def search_order(order_id: str) -> str:  # 正例：名称清晰、说明用途和触发时机、参数有类型和示例
    """按订单号查询订单的物流状态（只读，不改变任何数据）。
    当用户询问某个订单到哪了、是否已发货、预计送达时间时使用本工具。
    参数:
        order_id: 订单编号，形如 "A100"（必填）
    返回: 该订单的当前状态文本，如 "已发货，预计明天送达"；订单不存在返回提示。
    """
    ...
```
正例的名称一看就知道查的是订单（而非网页、非商品）；docstring 明确了“什么时候用”（触发时机）和“参数格式”（带示例）。**给模型看的工具描述，本质是一段写给模型的“使用说明书”**——你把它当成教新同事用一个内部工具那样写，模型的调用准确率会显著提升。

工具还应按风险分级，这决定了它需要多重的防护：

| 工具类型 | 作用 | 例子 | 风险等级 | 防护要求 |
|---|---|---|---|---|
| 只读检索类 | 获取信息，不改变世界 | `search_order`、查数据库、读文件 | 低 | 可让模型较自由调用 |
| 计算类 | 处理数据，无外部副作用 | 计算器、沙箱内代码执行 | 中 | 资源与超时限制 |
| 写操作类 | 改变外部状态，可能不可逆 | `refund`、发邮件、下单、删文件 | 高 | 执行层护栏 + 人工审核 gate |

## 原理二：护栏为什么必须落在执行层

指令（Instructions）定义 Agent“应该怎么做”和“不该做什么”，包含角色设定、任务目标、输出格式约束和安全护栏。OpenAI 的指南特别强调：**护栏应尽量落在执行层而非仅靠提示词**，并建议对每个工具按“只读 vs 写、可逆性、所需权限、财务影响”评级风险，用风险等级触发“执行高风险动作前暂停做护栏检查”或“升级到人工”的动作 [来源](https://cdn.openai.com/business-guides-and-resources/a-practical-guide-to-building-agents.pdf)。

为什么纯提示词护栏靠不住？因为**模型的输出是概率性的**。你在提示里写“绝对不要执行退款”，模型在多数情况下会遵守，但总有一小部分情况（被巧妙的提示注入、被长对话稀释了指令、被罕见措辞绕过）会翻车。而对一个能动用户真金白银的操作，哪怕 1% 的失败率也不可接受。执行层护栏（代码里的 `if not approved: raise`）则是**确定性**的——它不管模型怎么想，只要触发条件就拦住。

| 维度 | 提示词护栏（软） | 执行层护栏（硬） |
|---|---|---|
| 本质 | 请求模型“请不要……” | 代码强制“不允许……” |
| 可靠性 | 概率性，可能被绕过 | 确定性，无法绕过 |
| 抵抗提示注入 | 弱 | 强 |
| 实现位置 | 系统提示 | 工具执行前的校验代码 |
| 正确用法 | 第一道防线、提升体验 | 最后一道防线、兜底安全 |

## 最小可运行演示

下面把开场事故的修复方案写成可运行代码：`refund` 的护栏落到函数内部，无论模型怎么“想”退款，只要没有人工审核就抛异常。纯 Python，无需 API Key。
```python
def refund(order_id: str, amount: float, approved_by_human: bool = False) -> str:
    """执行层护栏落在工具内部，模型无论如何都绕不过。"""
    if not approved_by_human:                       # 硬护栏：确定性拦截
        raise PermissionError("退款必须经人工审核，拒绝执行")
    if amount > 1000:                               # 金额上限护栏
        raise ValueError("单笔退款超过上限，需升级审批")
    return f"已退款 {amount} 元至订单 {order_id}"

def try_call(desc, **kwargs):
    try:
        print(f"{desc} -> {refund(**kwargs)}")
    except (PermissionError, ValueError) as e:
        print(f"{desc} -> 被拦截：{e}")

def main() -> None:
    # 模型“决定”退款，但没有人工审核（对应开场事故）
    try_call("① 模型直接退款(无审核)", order_id="A100", amount=680)
    # 通过人工审核后执行
    try_call("② 人工审核后退款", order_id="A100", amount=680, approved_by_human=True)
    # 审核通过但超过金额上限
    try_call("③ 审核通过但超限", order_id="A100", amount=5000, approved_by_human=True)

if __name__ == "__main__":
    main()
```
保存为 `guardrail.py`，运行 `python guardrail.py`，预期输出：
```text
① 模型直接退款(无审核) -> 被拦截：退款必须经人工审核，拒绝执行
② 人工审核后退款 -> 已退款 680 元至订单 A100
③ 审核通过但超限 -> 被拦截：单笔退款超过上限，需升级审批
```
第①行就是开场那 680 元事故的修复：无论模型多么“想”退款、无论提示被怎么绕过，只要 `approved_by_human` 不为真，函数直接抛异常。**把安全约束变成代码里的硬条件，而不是对模型的礼貌请求**——这就是“护栏落在执行层”的精髓。理想做法是“软硬结合”：提示里提示模型别乱来（提升体验、减少无效尝试），执行层再兜底（保证安全）。

## 真实系统对应

**官方公开机制**：OpenAI 的指南把护栏分成多层——相关性分类器（防跑题）、安全分类器（防越狱/提示注入）、PII（Personally Identifiable Information，个人可识别信息）过滤器、内容审核、工具风险评级、基于规则的确定性防护（黑名单、长度限制、正则过滤）和输出校验，并明确“对高风险工具应在执行前暂停做护栏检查或升级人工” [来源](https://cdn.openai.com/business-guides-and-resources/a-practical-guide-to-building-agents.pdf)。函数调用文档则规定工具由“名称 + 描述 + 参数 Schema”定义，模型产出调用、代码执行、结果回喂 [来源](https://platform.openai.com/docs/guides/function-calling)。**通用工程模式**：按风险给工具分级，只读工具放开、写操作工具重重设防；护栏分“软（提示）+ 硬（执行层）”两层。**教学参考实现**：上面的 `refund` 用简单的布尔与阈值演示硬护栏，真实系统会接入审批工作流、权限系统（如 RBAC，Role-Based Access Control，基于角色的访问控制）和审计日志，而不是一个 `if`。

## 生产踩坑

| 症状 | 根因 | 如何观测与复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| 提示里写了“禁止退款”仍被执行 | 护栏只在提示层，未落执行层 | 用“把 A100 的钱退回来”等变体绕过 | 退款函数内做确定性权限校验 | 无 |
| 模型频繁选错工具 | 工具名称/描述含糊 | 对比含糊描述与清晰描述的选择准确率 | 按“使用说明书”标准重写描述与示例 | 只读低风险工具容错稍高 |
| 传给工具的参数格式错乱 | 参数缺类型与示例 | 记录调用参数，统计校验失败率 | 参数加类型注解、示例、必填标注 | 无 |
| 工具越加越多，选择质量下降 | 候选工具过多、语义相近 | 记录候选集合与最终调用 | 两阶段路由、按场景裁剪候选、合并近义工具 | 工具极少时无需路由 |
| 被提示注入诱导执行危险动作 | 把工具输出/用户文本当指令信任 | 在工具返回里植入“忽略之前指令”做红队 | 工具输出不当指令；关键动作执行层校验 | 纯内部可信工具风险较低 |
| 高风险动作无人工介入 | 缺少人工审核 gate | 检查写操作是否有审批环节 | 高风险工具接入人工审核/二次确认 | 明确授权的自动化批处理例外 |
| 危险操作事后无法追责 | 工具执行未记审计日志 | 查是否有“谁、何时、批准与否”记录 | 写操作强制审计日志与幂等键 | 无副作用只读工具可简化 |
| 金额/额度类操作偶发超限 | 只在提示里叮嘱上限 | 构造超限金额触发 | 执行层加阈值校验，超限报错升级 | 无 |

## 思考：如何保证 Agent 不执行危险操作？

### 回答

标准高分答案分三层。第一，认清纯提示词约束是**概率性**的、可能被提示注入或罕见措辞绕过，因此**关键护栏必须落在执行层**，用代码做确定性校验（权限、金额上限、人工审核 gate、幂等键）。第二，给工具**按风险分级**——只读工具可放开，写操作类工具（退款、下单、删除、发送）必须重重设防，并对高风险动作在执行前暂停做检查或升级人工，这正是 OpenAI 指南的建议 [来源](https://cdn.openai.com/business-guides-and-resources/a-practical-guide-to-building-agents.pdf)。第三，**软硬结合**：提示护栏做第一道防线提升体验、减少无效尝试，执行层护栏做最后一道防线保证安全，同时把工具输出当数据而非指令，防止提示注入。三层叠加，才既好用又安全。

### 面试精简表达

“提示护栏是软的（会被绕），执行层护栏是硬的（绕不过）；给工具按风险分级，高风险动作代码里强制校验并接人工，软硬结合。”

## 思考：为什么说“工具描述是写给模型的说明书”？

### 回答

因为模型选不选一个工具、传什么参数，完全依赖它读到的名称和描述——它看不到源码，只能靠描述“猜”。这句话的实践含义是：写工具描述时要像给一位刚入职、看不到代码的新同事写内部工具使用手册一样，讲清三件事：这个工具是干什么的（用途）、什么情况下该用它（触发时机）、每个参数是什么格式与含义（带示例、标必填）。名称也要自解释，`search_order` 比 `search` 好，因为它一眼说明查的是订单而非网页。描述写清楚，模型的工具选择和参数填写准确率会显著提升；描述含糊，就是 Agent 出错的头号来源之一。

## 事故回放：开场那 680 元是怎么退出去的

把开场事故按“模型提议、运行时处置”原则拆开，能看到四个本可拦截却都没拦的环节。第一，用户说“把这单的钱退给我”，模型在推理阶段判断意图是退款——这一步模型没错，用户确实在要求退款。第二，模型产出了 `refund(A100, 680)` 的结构化决策——这一步也在预期内，模型本就有 `refund` 工具可选。第三，代码拿到决策后**直接执行了 `refund`，没有检查 `approved_by_human`**——这是第一个致命缺口：护栏只写在提示里，函数本身裸奔。第四，退款成功后**没有留下“谁批准、金额多少”的审计记录**——这是第二个缺口，导致事后追责困难。

修复只需把护栏从提示搬到函数：给 `refund` 加上 `if not approved_by_human: raise`，再接一个人工审核 gate 和审计日志。修复后，同样的用户输入、同样的模型决策，代码执行时会因缺少审核而抛异常，转人工处理，680 元退不出去。这个事故的教训一句话总结：**指令里写“不能做”只是提醒模型，真正阻止危险动作的是执行它的那段代码。** 把安全寄托在模型的“自觉”上，等于把金库钥匙交给一个 99% 靠谱的人——对金库来说，1% 就是灾难。

## 软硬结合的完整形态

理想的护栏不是“要么软要么硬”，而是两层配合。软护栏（提示）承担三件事：一是提升体验，让模型在多数情况下就不去尝试危险动作，减少无谓的异常和转人工；二是给模型解释“为什么不能做”，让它能礼貌地向用户说明；三是引导模型走向合规路径（“退款请走人工审核入口”）。硬护栏（执行层）承担一件事：兜底，保证即使软护栏被绕过，危险动作也执行不了。

两者的分工可以这样记：**软护栏管“大多数情况下别去碰”，硬护栏管“万一碰了也出不了事”。** 只有软护栏，安全靠运气；只有硬护栏，体验会变差（模型频繁尝试再被拦、报错刷屏）。生产系统两者都要有。理解了工具与指令这两件套的边界，我们已经拆完了“行动”和“规范”。下一节转向 Agent 的“谋划”与“经验”——Planning 与 Memory，它们决定 Agent 能否处理复杂的、跨越多轮的任务。
