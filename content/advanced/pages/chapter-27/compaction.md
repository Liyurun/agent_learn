## 真实问题

排障 Agent 每五轮把“旧摘要 + 新消息”再次摘要。40 轮后，最初的“只读生产库”变成“优先不写库”，一次工具调用因此越权。摘要省下 Token，却把硬约束逐次稀释。

## 现象与输入
```text
原始事实：禁止向生产数据库写入
摘要 v1：本次主要进行只读诊断
摘要 v4：优先采用诊断方式
```
Compaction（上下文压缩）是有损变换。Tool Result Clearing（工具结果清理）则删除或替换已过时的大块结果。两者都要保留错误根因、证据指针和不可压缩事实。

## 原理

采用四层数据：

1. 固定事实：原样保存，有来源与版本。
2. 近期消息：保留原文。
3. 结构化摘要：目标、决定、未决问题、已验证结果。
4. 原始事件：外部持久化，必要时重新生成摘要。

避免“摘要的摘要”成为唯一来源。清理日志时保留失败测试名、首个根因堆栈、退出码和原文指针。

## 最小可运行演示
```python
def compact(history: list[str], facts: list[str], keep=2) -> dict:
    old, recent = history[:-keep], history[-keep:]
    return {
        "facts": facts,
        "summary": {"covered": len(old), "events": [x[:24] for x in old]},
        "recent": recent,
        "source_count": len(history),
    }

def main() -> None:
    history = ["读取配置", "测试失败:E_CONN", "定位连接池", "修改超时", "测试通过"]
    print(compact(history, ["禁止写生产库"]))

if __name__ == "__main__":
    main()
```
运行 `python compact_demo.py`，预期输出同时包含：
```text
'facts': ['禁止写生产库']
'source_count': 5
```
摘要记录覆盖范围，但原始历史仍是可恢复来源。

## 真实系统对应

Anthropic 官方文档公开了 Claude Code 的自动压缩及 `/compact`；Anthropic API 文档还公开 Context Editing（上下文编辑）能力，用于管理工具结果等上下文。公开机制说明“可压缩或清理”，并未公开 Claude Code 内部摘要提示与全部保留规则。上面的四层结构是教学方案。

## 生产踩坑

| 症状 | 根因 | 如何观测与复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| 摘要多轮后事实漂移 | 摘要递归摘要 | 对比每版摘要与原始事件 | 从原始窗口重建；事实独立固定 | 原文已依法删除时只能标注不确定性 |
| 清日志后无法定位 | 只保留“测试失败” | 检查摘要是否含测试名、退出码、根因 | 结构化保留根因和原文指针 | 敏感日志指针仍需访问控制 |
| 压缩频繁导致抖动 | 软阈值过低 | 统计压缩频率与节省量 | 设置滞回区间、批量压缩 | 极短会话无需压缩 |

## 思考：哪些信息绝不能只存在摘要中？

### 回答

安全与权限边界、用户明确硬约束、不可逆操作的批准、关键标识符、审计证据和已确认接口契约。它们应结构化保存并指向原始来源；摘要可重复这些内容，但不能成为唯一副本。

## 思考：什么时候清理工具结果反而危险？

### 回答

当结果包含唯一根因、后续操作所需 ID、未解析的安全告警或审计证据时。清理前应按工具类型定义最小保留字段；无法可靠提取时宁可卸载全文并保留可访问指针，而不是直接删除。

## 真实场景：摘要复利如何改变权限语义

数据库排障持续四十轮。第一轮的用户原话是“只能查询生产库，任何写操作必须由值班经理批准”。第十轮摘要写成“以只读诊断为主”；第二十轮再次压缩为“优先诊断”；第三十五轮模型建议执行修复语句，并把“优先”解释成可以例外。每一版单独看都通顺，但模态词从“禁止”漂移为“偏好”，权限语义已经改变。

复盘时，团队只有最新摘要，没有摘要覆盖的事件编号，无法判断失真在哪一轮发生。优化后，硬约束保存为结构化事实 `permission.write_prod=false`，并附原始消息 ID；摘要只记录调查进展。每次压缩都从未压缩的原始事件区间生成，摘要包含 `covers_from`、`covers_to` 和 `source_hash`。如果源事件被依法删除，系统明确标记不可重建，而不是假装摘要仍完整。

测试日志也有类似风险。原始输出两万行，其中第一处异常是连接池耗尽，后面数千个失败都是级联结果。按“保留最后一百行”会留下噪声、删掉根因；按工具类型提取首个异常、失败测试、退出码和产物指针，才既省空间又能排障。

## 压缩不是一种操作

历史压缩改变表达形式，目标是保留任务状态；工具结果清理删除已消费的大块数据；外部卸载把原文移出窗口但保留地址；上下文编辑则允许服务或客户端按规则管理既有内容。这些动作的可逆性不同。摘要通常有损，卸载在指针有效时可逆，删除可能不可逆。

因此每个变换都应产生报告：输入事件范围、保留字段、删除数量、原文位置、算法版本和校验值。没有报告时，Token 下降无法证明质量没有下降。对于授权、金额、资源 ID 和不可逆操作批准，最稳妥的做法是原样固定，并在执行层再次验证。

## 可运行的结构化压缩示例
```python
from hashlib import sha256

def structured_compact(events: list[dict], keep: int = 2) -> dict:
    old, recent = events[:-keep], events[-keep:]
    facts = [e for e in events if e["kind"] == "hard_fact"]
    source = repr(old).encode("utf-8")
    return {
        "facts": facts,
        "summary": {
            "covered_ids": [e["id"] for e in old],
            "decisions": [e["text"] for e in old if e["kind"] == "decision"],
            "source_hash": sha256(source).hexdigest()[:8],
        },
        "recent": recent,
    }

def main() -> None:
    events = [
        {"id": 1, "kind": "hard_fact", "text": "禁止写生产库"},
        {"id": 2, "kind": "decision", "text": "先检查连接池"},
        {"id": 3, "kind": "tool", "text": "ERROR pool exhausted"},
        {"id": 4, "kind": "decision", "text": "调整本地超时"},
    ]
    result = structured_compact(events)
    print("facts=", [x["text"] for x in result["facts"]])
    print("covered=", result["summary"]["covered_ids"])
    print("recent=", [x["id"] for x in result["recent"]])

if __name__ == "__main__":
    main()
```
保存为 `structured_compact.py` 并运行，完整预期输出：
```text
facts= ['禁止写生产库']
covered= [1, 2]
recent= [3, 4]
```
摘要覆盖事件一和二，但硬事实仍独立存在；事件三和四保留原文。`source_hash` 不打印，因此不同 Python 版本的对象表示差异不会影响示例输出。生产代码应使用规范化 JSON 计算哈希，并把原始事件存入受访问控制的事件库。

## 压缩质量如何验证

可构造三组断言。第一组检查硬事实逐字存在，金额、ID、否定词和批准人不能变；第二组检查任务连续性，摘要能回答“目标、已完成、失败原因、下一步”；第三组检查可追溯性，每个摘要结论至少指向一个原始事件。再用压缩前后的同一任务集做对照，比较成功率、约束遵循和输入量，而不是只看压缩比。

优化前每五轮重写整个旧摘要，文本越来越短但错误无法定位；优化后以原始事件为源、固定事实独立、最近消息原样保留，达到软阈值才批量压缩。压缩频率下降，缓存前缀也更稳定。若摘要质量低于阈值，系统可以扩大近期原文或从源事件重建。

## 官方能力与教学实现边界

Claude Code 文档公开自动压缩和用户可触发的压缩行为，Anthropic API 文档公开上下文编辑能力。公开内容说明这些功能可帮助管理长会话，并不意味着压缩无损，也没有公开产品内部使用的摘要提示、字段、阈值或全部保留规则。本页的四层数据、事件哈希和质量断言均为通用教学设计。

Context Editing 的具体支持范围、参数和与其他能力的组合方式会变化，接入时应查当前文档。不能因为 API 能清理旧工具结果，就默认任何工具结果都可删除；支付回执、审批 ID、安全告警与唯一错误堆栈可能必须保留或外部归档。

## 踩坑定位与优化对比

| 症状 | 优化前 | 优化后 | 定位信号 |
|---|---|---|---|
| “禁止”变“优先” | 递归摘要包含权限 | 权限事实原样固定 | 比较事实值和原始消息 |
| 日志变短却不能排障 | 按尾部行数截断 | 工具类型提取器保留首因 | 失败名、退出码、根因是否齐全 |
| 每几轮延迟突增 | 低阈值频繁重写 | 软硬阈值加滞回 | 压缩次数与节省量 |
| 摘要结论无法证明 | 没有覆盖范围 | 事件 ID、哈希和原文指针 | 任取结论反查来源 |
