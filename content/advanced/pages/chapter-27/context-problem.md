## 真实问题

一个客服 Agent 第一轮正确记录“用户对花生过敏”，第十轮却推荐含花生酱的套餐。团队继续润色系统提示，事故仍然出现。回放发现：过敏信息被埋在 30 段检索材料之间，而最新问题只问“这份套餐合适吗”。单轮措辞没有错，错误发生在跨轮信息调度。

Context Engineering（上下文工程）管理模型每次生成前可见的全部信息；Prompt Engineering（提示工程）主要优化指令表达。后者是前者的一部分，不能替代历史选择、工具加载、记忆取回和预算控制。

## 现象与输入
```text
系统：只能推荐符合过敏约束的菜品
第 2 轮用户：我对花生过敏
第 3—9 轮：菜单检索、配送地址、优惠日志……
第 10 轮用户：这份套餐合适吗？
```
失败上下文没有把“花生过敏”提取为不可压缩事实，也没有在生成前检查当前菜单。窗口“装得下”不等于模型“用得好”。

## 原理

一次 Agent 调用可抽象为：
```text
context(t) = stable_rules + selected_tools + pinned_facts
           + compacted_history + relevant_evidence + current_request
```
工程目标不是把资料全部塞入，而是让当前决策所需证据足够、冲突可见、来源可追踪，并为输出保留空间。选择错误会产生四类故障：缺失（没放进来）、冲突（新旧规则并存）、干扰（无关内容过多）、污染（不可信工具输出被当指令）。

## 最小可运行演示
```python
def assemble(user: str, facts: list[str], history: list[str]) -> str:
    blocks = ["## 不可压缩事实", *facts, "## 近期历史", *history[-2:], "## 当前请求", user]
    return "\n".join(blocks)

def main() -> None:
    text = assemble("这份花生鸡套餐合适吗？", ["用户对花生过敏"], ["已选择晚餐", "候选：花生鸡"])
    print(text)
    print("检查结果：不合适")

if __name__ == "__main__":
    main()
```
保存为 `context_problem.py`，运行 `python context_problem.py`。预期输出末行：
```text
检查结果：不合适
```
代码先固定高风险事实，再放近期证据和当前请求；真实系统还应做结构化校验，而不能仅依赖文本顺序。

## 真实系统对应

**官方公开机制**：Anthropic 的 Agent 指南建议从简单、可组合模式开始，并强调工具描述与结果反馈；Claude Code 文档公开了项目指令、规则和子智能体等上下文入口。**通用工程模式**：把长期约束、任务证据和当前请求分区。**教学参考实现**：上面的 `assemble` 只是演示，不代表任何产品内部拼接顺序。

## 生产踩坑

| 症状 | 根因 | 如何观测与复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| 长任务后违反硬约束 | 事实仅存在早期对话 | 回放每轮实际模型输入；插入 20 段噪声复现 | 抽取为带来源的固定事实；执行前校验 | 不应把未经确认的偏好固定化 |
| 回答引用过期规则 | 新旧版本同时存在 | Trace（追踪）记录规则版本 | 上下文只保留当前版本并标生效时间 | 法规审计仍需保留旧版于外部存档 |

## 思考：为什么更长的窗口不能替代上下文工程？

### 回答

窗口容量只解决“能否放入”，不保证信息相关、无冲突、位于易被利用的位置，也不控制重复输入的成本。窗口越大，未经选择的噪声和过期状态也可能越多。上下文工程还承担来源、权限、生命周期和恢复职责，这些都不是扩大长度自动获得的。

### 面试精简表达

长窗口是容量，上下文工程是调度；前者增加仓库面积，后者决定当前工作台摆什么。

## 事故回放：约束如何在十轮对话中消失

客服系统收到的第一条用户消息是“孩子八岁，对花生和腰果过敏”。系统随后调用菜单、库存、门店和优惠工具。菜单工具返回一百二十种菜品，优惠工具又附带整份活动条款。第十轮，用户点击“儿童能量套餐”并问能否下单。失败请求虽然包含最初消息，但固定事实区为空，菜单证据只写商品名，没有成分字段；模型被“儿童”“能量”两个词吸引，给出肯定答案。

把这次请求按责任边界拆开，可以得到四个独立问题。召回层没有把过敏信息升级为高风险事实；工具层没有返回结构化过敏原；组装层把八轮低价值日志放在事实之前；执行层没有用确定性规则阻止下单。润色“请认真关注过敏信息”只能碰运气，无法弥补后三项缺陷。

优化后的输入不再复述整段聊天，而是提供带来源的事实和可验证商品属性：
```text
[固定事实]
fact_id=allergy-17 value=花生,腰果 source=user-message-1 confirmed=true
[当前商品]
sku=KIDS-204 allergens=花生 source=menu-api version=2026-08-23
[当前请求]
判断是否可下单；若命中过敏原，必须拒绝并说明证据
```
输出同时经过业务规则校验。模型即使生成“可以”，订单服务也会比较两个集合并拒绝。上下文工程负责让模型看见事实和证据，权限与安全边界仍由模型外代码落实。

## 机制推导：从信息生命周期到组装计划

每段信息至少带五个属性：所有者、来源、可信度、生效范围和失效条件。用户确认的过敏信息由用户拥有，来源是原始消息，可信度为已确认，作用于当前账户，直到用户修改；工具日志则由某次调用产生，只对对应版本有效，通常在故障关闭后退出活跃窗口。缺少这些属性时，“记住它”会变成无限增长的文本堆积。

组装器可以据此执行三步。先做资格过滤，排除无权限、已过期或版本不匹配的块；再做必要性判断，把安全事实、当前请求和回答格式列为必需；最后在剩余预算中按边际价值选择证据。价值不是相关性分数的同义词：一条能否决危险动作的短事实，价值可能高于十段语义相似的介绍。

对于冲突内容，组装器不应偷偷选择“看起来较新”的一条。它应输出冲突集合、来源和生效时间，并在无法确定时停止高风险动作。这个设计把模型从事实裁判降为受证据约束的解释器。

## 完整输入输出与运行说明

前面的程序可扩充为可复制运行的安全判断器：
```python
def decide(allergies: set[str], item: dict) -> dict:
    matched = sorted(allergies & set(item["allergens"]))
    return {
        "allowed": not matched,
        "matched": matched,
        "evidence": item["source"],
    }

def main() -> None:
    user = {"allergies": {"花生", "腰果"}}
    item = {"sku": "KIDS-204", "allergens": ["花生"], "source": "menu-api@2026-08-23"}
    context = assemble(
        f"判断 {item['sku']} 是否可下单",
        ["用户过敏原：花生、腰果"],
        ["候选套餐：KIDS-204", "菜单接口已返回成分"],
    )
    print(context)
    print(decide(user["allergies"], item))

if __name__ == "__main__":
    main()
```
运行 `python context_problem.py` 的完整预期输出为：
```text
## 不可压缩事实
用户过敏原：花生、腰果
## 近期历史
候选套餐：KIDS-204
菜单接口已返回成分
## 当前请求
判断 KIDS-204 是否可下单
{'allowed': False, 'matched': ['花生'], 'evidence': 'menu-api@2026-08-23'}
```
这里的确定性集合判断是安全闸门，模型可负责把结果解释成人话。若菜单接口没有 `allergens` 字段，正确输出不是猜测，而是“证据不足，拒绝自动下单并请求人工确认”。

## 优化前后对比

| 维度 | 优化前 | 优化后 | 验证方式 |
|---|---|---|---|
| 高风险事实 | 只在早期聊天出现 | 独立固定并带来源 | 检查每轮组装清单 |
| 商品证据 | 商品名自然语言 | SKU、过敏原、版本结构化 | 对照菜单接口响应 |
| 冲突处理 | 模型自行猜新旧 | 显示冲突并阻止动作 | 注入两个版本复现 |
| 最终控制 | 依赖模型措辞 | 业务代码执行集合校验 | 用错误模型输出做故障注入 |

## 官方案例边界

Anthropic 的 Agent 指南公开讨论工具、反馈循环和组合模式，Claude Code 文档公开项目指令等入口；这些资料支持“上下文由多类信息组成”的判断。客服过敏案例、五属性模型和集合校验均为教学案例，不对应 Anthropic 产品功能。官方文档也没有承诺长窗口会自动提升约束遵循率，因此不能用窗口容量代替自己的风险控制。

当排查类似事故时，应先抓取模型实际收到的序列，而不是后台“理论上可用”的所有数据。证据在数据库中但未进入请求，属于召回或组装故障；证据已经进入请求却被冲突内容覆盖，需要重排、去重和评估；模型已正确拒绝但订单仍提交，则是执行层故障。三者的修复位置完全不同。
