## 真实问题

线上告警写着“Agent 回答质量下降”，但这个描述无法行动。根因可能在召回、版本、组装、模型、工具或输出解析。生产诊断必须先保存实际请求快照与 Trace（追踪），再按变量分层，不把一切归结为“上下文太长”。

## 诊断顺序

1. **复现**：固定任务、模型版本、温度、工具快照和数据版本。
2. **检查缺失**：正确证据是否被召回并实际进入模型输入。
3. **检查冲突**：规则与事实是否存在多版本。
4. **检查预算**：是否侵占输出、截断结构或加载过多工具。
5. **检查布局**：删除噪声、交换证据位置做消融。
6. **检查压缩**：摘要能否回溯到原始事件，硬事实是否完整。
7. **检查执行**：工具权限、幂等和结果解析是否正确。
8. **比较基线**：同一输入在固定模型上的多次结果与离线评估。

## 症状矩阵

| 症状 | 根因 | 观测与复现 | 修复 | 预防与边界 |
|---|---|---|---|---|
| 回答突然变短 | 输出预留不足 | 记录 stop reason 与输入量 | 锁定输出额度 | 分类任务可设较小额度 |
| 工具选错率升高 | 工具定义过多或近义 | 记录候选和调用 | 两阶段路由、重写描述 | 权限仍由执行层控制 |
| 事实时好时坏 | 证据位置和噪声 | 固定内容做位置消融 | 去重并把关键证据靠近问题 | 不宣称固定 U 形规律 |
| 旧政策被引用 | 版本冲突 | 记录来源与生效时间 | 过滤失效版本 | 历史分析需保留旧版 |
| 越跑越偏 | 摘要递归失真 | 摘要与原始事件 diff | 从原始记录重建 | 原文删除后标不确定 |
| 日志清理后无根因 | 清理规则只按长度 | 检查失败名、退出码、堆栈 | 工具类型专用提取器 | 敏感值应脱敏 |
| 子任务难合并 | 返回契约不一致 | 校验 schema | 固定字段与证据 ID | 开放研究允许未决项 |
| 恢复后重复发布 | 无幂等键 | 崩溃注入 | 动作日志与提交检查点 | 外部系统需支持幂等 |
| 缓存读为零 | 动态字段前置 | 前缀哈希与用量字段 | 稳定块前置 | 无共享前缀时正常 |
| 命中高仍昂贵 | 后缀持续膨胀 | 分解缓存与普通输入 | 批量压缩、清工具结果 | 不删除必要证据 |
| 搜索命中但答非所问 | 召回粒度错误 | 查看实际片段 | 调整切块和重排 | 位置优化不能修复错证据 |
| 跨租户信息泄露 | 缓存或记忆键缺少租户边界 | 安全测试与审计 | 租户隔离、访问控制 | 不依赖提示词做隔离 |
| 指标正常但用户失败 | 只量 Token/延迟 | 增加任务成功与约束遵循 | 建立端到端评估集 | 指标不取代人工复核 |
| 固定事实无限增长 | 不做失效管理 | 统计年龄和冲突 | 来源、版本、TTL 与确认 | 法律保留不等于上下文常驻 |
| 模型输入不可审计 | 日志只存最终答案 | 关联 trace_id 与输入快照 | 脱敏记录组装清单 | 隐私要求可能限制原文留存 |

TTL（Time To Live，生存时间）只能用于可过期偏好，不应自动删除法律保留或未完成事务。PII（Personally Identifiable Information，个人可识别信息）在追踪前应最小化和脱敏。

## 最小可运行演示
```python
def diagnose(metrics: dict) -> str:
    if metrics["required_tokens"] > metrics["input_budget"]:
        return "预算：精简规则或工具，禁止侵占输出预留"
    if not metrics["evidence_in_prompt"]:
        return "召回/组装：核对检索结果与最终请求"
    if metrics["conflicting_versions"]:
        return "冲突：按来源与生效时间选择版本"
    if metrics["cache_read"] == 0 and metrics["shared_prefix"]:
        return "缓存：检查动态字段是否位于前缀"
    return "运行固定输入消融实验"

def main() -> None:
    print(diagnose({
        "required_tokens": 700, "input_budget": 850,
        "evidence_in_prompt": True, "conflicting_versions": True,
        "cache_read": 0, "shared_prefix": True,
    }))

if __name__ == "__main__":
    main()
```
运行 `python diagnose.py`，预期输出：
```text
冲突：按来源与生效时间选择版本
```

## 真实系统对应

LangSmith 官方可观测性文档公开 Trace、运行树和元数据能力，可用于检查实际输入、工具调用和延迟。供应商 API 的用量与停止原因字段可用于预算诊断。具体采样、脱敏、保留期和告警阈值由团队根据风险设计；本文不声称平台自动完成这些治理。

## 思考：最重要的上下文工程指标是什么？

### 回答

没有单一指标。最低集合应包含任务成功率、硬约束遵循率、正确证据进入率、输入与输出 Token、缓存读写量、压缩频率、工具错误率、恢复成功率和端到端延迟。成本指标必须与任务结果联看，否则“少用 Token”可能只是少给了证据。

## 思考：如何把本章方法引入现有系统？

### 回答

先加观测而非先重写：记录每轮组装清单、来源、Token 分类和结果。用失败样本建立回归集，然后依次锁定输出预算、分离固定事实、清理工具结果、引入可恢复检查点，最后才考虑子智能体和缓存布局。每步做对照实验并保留回滚开关。

## 思考：上下文工程的安全底线是什么？

### 回答

不把提示当权限；不把工具输出默认当指令；不跨租户复用记忆；不在追踪和摘要里无界复制敏感数据；不可逆操作必须有授权、幂等和审计。上下文可帮助模型遵守规则，但最终控制要在模型之外强制执行。

## 值班现场：从模糊告警到可复现故障

凌晨两点，客服 Agent 的“正确解决率”在十分钟内从基线下降，Token 和延迟却没有明显异常。值班人员若只看资源指标，会误判为模型随机波动。抽取失败样本后发现，订单政策服务在午夜发布了新版本，检索索引仍返回旧文档；组装器又没有保留生效时间，模型在两个版本中选了措辞更完整的旧规则。

定位过程首先冻结五项变量：模型标识、温度、工具 schema、文档索引快照和请求输入。随后保存检索候选与最终组装序列。正确政策未进入候选，证明首要故障在索引更新；人工加入新政策后答案恢复，进一步排除模型能力不足。团队修复索引发布流程，并在组装前按版本和生效时间过滤；当多个版本都标为有效时，系统拒绝自动答复并报警。

优化前，告警只有一个总体成功率，无法区分召回、组装和执行；优化后，每个 trace 记录证据进入率、冲突数、各类 Token、停止原因、工具错误和动作结果。事故从四小时缩短为二十分钟定位。这个结果不是因为日志越多越好，而是因为日志能回答“哪一层第一次偏离预期”。

## 生产观测数据模型

一次运行至少关联 `trace_id`、任务类型、模型版本、输入数据版本和代码版本。组装阶段记录每个块的类别、来源、版本、估算 Token、是否选中及淘汰原因；模型阶段记录实际用量、缓存字段、停止原因和延迟；工具阶段记录参数摘要、权限决策、退出码和产物 ID；结果阶段记录任务成功、约束遵循和人工纠正。

原始提示可能含个人信息和密钥，不能为了可观测性无界保存。追踪管道应在写入前脱敏，敏感正文可以保存受控对象指针；访问记录与保留期要独立治理。若法规禁止留存原文，就保存最小必要结构和不可逆哈希，并接受复现能力受限。

## 可运行的分层诊断器
```python
def diagnose_full(m: dict) -> list[str]:
    findings = []
    if not m["gold_in_candidates"]:
        findings.append("召回：正确证据未进入候选")
    elif not m["gold_in_prompt"]:
        findings.append("组装：候选证据未进入最终请求")
    if m["active_versions"] > 1:
        findings.append("版本：存在多个生效版本")
    if m["required_tokens"] > m["input_budget"]:
        findings.append("预算：必需内容超限")
    if m["stop_reason"] == "max_tokens":
        findings.append("输出：达到长度上限")
    if m["tool_exit_code"] != 0:
        findings.append("工具：执行失败")
    return findings or ["需要固定输入做布局与模型消融"]

def main() -> None:
    metrics = {
        "gold_in_candidates": True,
        "gold_in_prompt": True,
        "active_versions": 2,
        "required_tokens": 700,
        "input_budget": 850,
        "stop_reason": "end_turn",
        "tool_exit_code": 0,
    }
    print("\n".join(diagnose_full(metrics)))

if __name__ == "__main__":
    main()
```
保存为 `diagnose_full.py`，执行 `python diagnose_full.py`。完整预期输出：
```text
版本：存在多个生效版本
```
如果把 `gold_in_candidates` 改为 `False`，输出还会包含召回故障；诊断器允许并列根因，而不是遇到第一项就停止。它只负责缩小范围，不会自动删除旧政策或重试工具。生产系统应把每个判断连接到可打开的 trace 和输入快照。

## 六类常见误诊

“上下文太长”常被当成通用解释，但输入长可能只是相关证据多。若正确证据未召回，裁剪上下文不会修复；若工具执行失败，重排提示也无效；若输出解析器拒绝合法答案，换模型只会改变表象。应找到第一个出现偏差的层。

“换更大模型”也可能暂时提升成功率，却掩盖版本冲突和不可恢复状态。更强模型仍无法读取未进入请求的证据，也不能为外部副作用自动提供幂等。“缓存命中高”只说明计算被复用，不说明动态后缀健康。“测试通过”若只覆盖 Mock，也不代表真实 API 参数和用量字段正确。

“压缩率越高越好”忽略信息损失。摘要从二千 Token 降到一百并不值得庆祝，除非任务成功和硬约束保持；“子智能体越多越好”忽略调用成本和快照冲突；“日志全部保存最安全”则忽略隐私、保留期和访问风险。

## 优化实验的前后对照

以一百条历史失败任务为固定回归集，先记录基线：任务成功率、硬约束违例、证据进入率、输入输出 Token、工具错误、恢复成功和端到端延迟。每次只改变一个环节。例如先加版本过滤，不同时更换模型和重写提示；再观察失败类型是否从“引用旧政策”转移。

预算优化前后要保持回答上限和任务集一致；压缩实验要保存未压缩原文；布局实验只交换位置；缓存实验保持语义字节稳定；子任务实验记录总调用成本而非只看主会话。没有对照，成本下降可能源自答案变短，成功率上升也可能来自数据版本变化。

| 优化 | 基线问题 | 单一改动 | 成功判据 | 回滚信号 |
|---|---|---|---|---|
| 版本过滤 | 旧政策被引用 | 只保留当前生效版本 | 引用 ID 命中金标准 | 合法历史查询被误删 |
| 输出预留 | 修复建议中途截断 | 固定最大输出额度 | 长度停止率下降 | 输入必需块频繁失败 |
| 日志清理 | 上下文被成功日志淹没 | 保留首因与原文指针 | 根因可定位且输入下降 | 唯一错误字段丢失 |
| 批量压缩 | 每轮重写导致漂移 | 软阈值加滞回 | 约束遵循不降 | 摘要无法回溯 |
| 稳定前缀 | 缓存读取为零 | 动态字段后移 | API 读缓存字段上升 | 政策更新未生效 |

## 官方工具能证明什么

LangSmith 等公开可观测平台能够记录运行树、输入输出、工具调用和元数据，供应商 API 可返回用量、停止原因等字段。这些能力提供证据载体，不会自动定义金标准、数据保留策略或故障责任。具体字段、采样和版本以当前官方文档为准。

Anthropic 的上下文编辑、提示缓存与 Claude Code 的压缩、子智能体等能力可以缓解特定问题，但没有任何单一功能能取代端到端观测。正文中的诊断顺序、指标集合和阈值属于通用工程方案，不是官方服务等级承诺。

## 思考：为何先观测再重构

### 回答

没有请求快照和分层指标时，团队只能用最终答案猜原因。先观测能建立失败基线，确认正确证据是否出现、预算如何分配、哪一步首次偏离。重构后还能用同一批样本比较，避免把随机波动当成收益。观测本身也要最小化敏感信息，不能以排障为由复制全部用户数据。

### 反例

若系统正在发生明确的越权写入，应先在执行层停用危险能力，再补观测，不能等待完整实验。先观测适用于质量和成本优化，不意味着延迟紧急止损。

## 思考：什么时候应该让 Agent 拒绝继续

### 回答

必需规则超过预算、证据版本冲突、不可逆动作状态未知、检查点版本无法解释、关键证据无权限访问或工具结果缺少必要字段时，应返回结构化失败并请求上游处理。继续生成一段流畅回答会掩盖不确定性。拒绝信息至少包含失败阶段、缺失证据和可恢复方式，但不得泄露敏感内部细节。

## 从告警到修复的运行过程

值班人员先选择一条失败 `trace_id`，导出经过脱敏的候选证据、最终请求和工具事件；用相同版本离线重放，确认能稳定失败；运行诊断器得到候选层级；修改单一环节后重放整套回归集；指标通过再灰度发布，并保留旧路径开关。若无法固定复现，则比较失败和成功样本的数据版本、请求路由和外部工具响应，不应直接调提示。

修复完成的证据包括：金标准政策进入候选且进入最终请求，废止版本被过滤，模型引用正确来源，执行动作符合权限，回归集未出现新类别退化。只有“示例这次答对”不足以关闭事故。
