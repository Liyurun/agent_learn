## 真实问题

一个代码审查 Agent 注册了 48 个工具，每轮都发送全部 JSON Schema（JSON Schema，JSON 结构约束）。用户只要求检查一个补丁，但工具定义和历史日志占满输入，模型输出在修复建议中途截断。根因不是模型不会审查，而是系统没有先锁定输出预算。

## 现象与输入
```text
窗口上限：4,000
输出预留：800
系统与固定事实：900
48 个工具定义：2,700
当前任务：300
合计输入：3,900 > 可用输入 3,200
```
正确顺序是先扣输出，再放不可省内容，最后按价值密度挑选工具、历史和证据。软阈值触发压缩，硬阈值拒绝调用。

## 原理

令窗口上限为 `W`、输出预留为 `R`、安全余量为 `S`，输入硬预算是 `B=W-R-S`。必需内容超过 `B` 时必须失败，不能偷用 `R`。动态工具加载根据任务意图只暴露候选集合，既减少 Token（词元）也降低误调用面。

## 最小可运行演示
```python
def count(text: str) -> int:
    return len(text)

def assemble(required: list[str], optional: list[str], window=120, reserve=30) -> tuple[list[str], int]:
    limit = window - reserve
    used = sum(map(count, required))
    if used > limit:
        raise ValueError(f"必需内容超预算：{used}/{limit}")
    result = list(required)
    for item in optional:
        if used + count(item) > limit:
            continue
        result.append(item)
        used += count(item)
    return result, used

def main() -> None:
    blocks, used = assemble(["规则：只读", "任务：审查补丁"], ["工具：diff", "日志：" + "x" * 100])
    print(f"输入={used}/90，输出预留=30")
    print(blocks)

if __name__ == "__main__":
    main()
```
运行 `python budget_demo.py`，预期输出包含：
```text
输入=19/90，输出预留=30
['规则：只读', '任务：审查补丁', '工具：diff']
```
字符计数仅用于确定性教学；生产系统应使用目标模型对应的 tokenizer（分词器），并为消息包装和工具协议保留安全余量。

## 真实系统对应

Anthropic 官方工具使用文档公开说明工具定义会成为模型输入，并建议写清工具描述。按任务筛选工具是由该公开行为推导出的通用工程策略，不代表平台一定使用同样的路由算法。Claude Code 的 Skill（技能）按需加载相关工作流，也体现“不要把所有知识一直放在窗口里”的原则。

## 生产踩坑

| 症状 | 根因 | 如何观测与复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| 输出经常被截断 | 输入挤占输出预留 | 记录 input/output/max token；构造超长工具表 | 先扣预留，硬阈值拒绝；按任务加载工具 | 极短分类任务可降低预留 |
| 成本随工具数线性上升 | 每轮发送所有 schema | 对比 5 与 50 工具输入量 | 两阶段路由、缩短描述、合并同义工具 | 高风险工具不能仅靠语义路由隐藏权限 |

## 思考：预算不足时为什么不能直接截断尾部？

### 回答

尾部通常包含当前请求、最新证据和输出格式，盲截会删除最有时效的信息，还可能把 JSON 或工具结果截成无效结构。应按语义类别和优先级删除：先去重复与低价值日志，再压缩早期历史，必要时减少工具；不可压缩事实和当前请求必须完整。

## 思考：动态工具加载会带来什么新风险？

### 回答

路由器可能漏掉真正需要的工具，因此应支持低置信度回退、记录候选与拒绝原因，并把权限控制放在执行层。动态加载是上下文优化，不是授权机制。

## 真实场景：审查任务为什么在最后一句被截断

某团队给代码审查 Agent 配置了代码读取、仓库搜索、工单、发布、数据库、监控等四十八个工具。一次仅含六十行的补丁审查，模型输入中系统规则占九百 Token，工具定义占二千七百，历史与补丁占三百，留给回复的额度只剩一百。结果列出三个风险后，在最重要的修复代码前触发长度停止。团队最初把问题归因于“回答太啰嗦”，要求模型简短，结果只是让分析依据一并消失。

请求快照显示，审查任务实际只需要 `read_file`、`read_diff` 和 `run_test`。数据库写入和发布工具既无关，又扩大误调用面。将工具按意图路由后，定义占用从二千七百降到三百四十；把输出预留从“剩多少算多少”改为固定八百，完整建议稳定返回。这里的改进来自预算顺序变化，而不是模型升级。

## 预算器的决策过程

预算不是一个总数字，而是带优先级的分配协议。先锁定输出预留和协议安全余量，再验证必需块。必需块包括系统安全规则、当前任务、不可压缩事实和最小输出格式；可选块包括候选工具、近期历史、检索证据与示例。必需块自身超限时应返回分类报告，要求上游缩短或拆分任务，不能悄悄删掉最后一条规则。

可选块的选择可用“收益除以成本”排序，但需要加覆盖约束。若十段证据都来自同一文件，单纯按相似度可能挤掉另一个关键模块；实际组装可先按来源选代表块，再在来源内部排序。工具也应保留回退路径：路由置信度低时加入只读发现工具，或先询问用户，而不是直接暴露所有高权限工具。

估算误差同样需要预算。字符数、词数和 Token 数没有固定换算关系，中文、代码、JSON、消息包装的比例各异。生产预算器应调用目标模型对应计数器，并在模型或 SDK 升级后用录制请求做回归。安全余量不是浪费，它覆盖工具协议包装、系统追加字段和计数版本差异。

## 可运行的带报告组装器
```python
def assemble_report(required, optional, window=120, reserve=30, margin=10):
    input_limit = window - reserve - margin
    used = sum(len(x) for x in required)
    if used > input_limit:
        raise ValueError(f"必需内容超预算：{used}/{input_limit}")
    selected, skipped = list(required), []
    for name, text in sorted(optional, key=lambda x: len(x[1])):
        if used + len(text) <= input_limit:
            selected.append(text)
            used += len(text)
        else:
            skipped.append(name)
    return {
        "input_limit": input_limit,
        "used": used,
        "output_reserve": reserve,
        "selected": selected,
        "skipped": skipped,
    }

def main() -> None:
    report = assemble_report(
        ["规则：只读", "任务：审查补丁"],
        [("diff", "工具：diff"), ("test", "工具：test"), ("发布", "工具：" + "发布" * 40)],
    )
    for key, value in report.items():
        print(f"{key}={value}")

if __name__ == "__main__":
    main()
```
保存为 `budget_report.py` 并执行 `python budget_report.py`。完整输入是两条必需块和三个带名称的候选工具，预期输出为：
```text
input_limit=80
used=26
output_reserve=30
selected=['规则：只读', '任务：审查补丁', '工具：diff', '工具：test']
skipped=['发布']
```
如果把窗口改为二十，程序应抛出“必需内容超预算”，这是一种正确失败。它让调用方知道任务需拆分，不会产出看似正常、实际缺少安全规则的请求。示例按文本长度排序只为保持输出确定；生产选择器还要结合相关性、来源覆盖、权限和任务阶段。

## 动态工具的完整边界

Anthropic 工具使用文档说明工具定义会进入模型可见输入，这是公开事实；Claude Code 的技能支持按需发现和加载，也是公开行为。由此可以推导“减少无关定义有助于控制输入与选择难度”，但官方资料没有公开 Claude Code 的内部路由特征、打分阈值或全部候选集合。示例中的排序函数不是官方算法。

动态加载不能撤销执行权限。即使某轮未向模型展示 `deploy`，后端也必须拒绝未授权调用；反过来，模型看见某工具也不代表获得权限。高风险系统把“可见工具”和“可执行能力”分别记录，前者优化上下文，后者由身份、策略和审批决定。

## 定位与优化对比

| 观测项 | 优化前 | 优化后 |
|---|---|---|
| 输出额度 | 输入拼完后取剩余值 | 请求开始即锁定，任何输入不得侵占 |
| 工具定义 | 四十八个全部发送 | 按意图选三个，并记录被排除原因 |
| 超限行为 | 尾部字符串截断 | 按完整语义块跳过，必需块超限则失败 |
| 计数方法 | 中文字符乘固定比例 | 使用目标模型计数器并留协议余量 |
| 排错证据 | 只保存总 Token | 分别记录规则、事实、工具、历史、证据、输出 |

当输出仍然被截断，先看停止原因是否为长度，再核对服务端实际 `max_tokens` 与本地报告。若本地认为有八百预留，服务端参数却只有二百，问题在调用配置；若参数正确但模型提前结束，可能是模型判断已完成，不应继续扩大预留。优化必须用实际停止原因区分这两种现象。
