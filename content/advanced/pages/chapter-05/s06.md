## 真实问题

用药 Agent 做大后，团队面临一个架构选择题：「既然向量记忆能存文本，干脆把用户 ID、订单、余额、过敏史全塞进一个向量库，检索时统一取回，不就简单了？」上线一测就翻车：查「用户 ID=10086 的未支付订单」，向量检索返回一堆「语义相近」但用户 ID 不对的订单；查「账户余额」，返回一个「差不多」的历史余额。**向量检索的本质是「模糊的语义相似」，它天生不擅长「精确、唯一、关系」这三类需求。** 这一节回答两个问题：真实的记忆架构如何混合多种存储；MemGPT、Generative Agents、LangGraph、ChatGPT、Claude 这些真实系统的公开记忆机制到底是怎样的。

## 原理：记忆选型与混合架构

向量记忆不是唯一选择。工程上常见三种记忆形态，各有擅长：

| 记忆类型 | 适合存什么 | 检索方式 | 典型后端 |
|---|---|---|---|
| 向量记忆 | 非结构化文本、语义相似检索 | 语义相似度（embedding） | Faiss / Milvus / pgvector |
| 结构化记忆 | 用户档案、订单、余额、明确字段 | 精确查询（SQL / KV） | 关系库 / 键值库 |
| 知识图谱记忆 | 实体与实体间的关系 | 图查询、关系推理 | 图数据库 |

选型原则一句话：**需要精确匹配的用结构化，需要语义相似的用向量，需要关系推理的用图。** 三个「全用向量会翻车」的反例，背后是同一个道理：
```text
反例一：精确条件查询「查用户 ID=10086 的未支付订单」
   → 精确字段过滤，语义相似度毫无意义。正解：SQL/KV。

反例二：强一致关键数据「账户余额是多少」
   → 必须精确、实时、唯一，不能近似。正解：数据库权威记录，绝不进向量库。

反例三：关系推理「张三的经理的经理是谁」
   → 多跳关系查询，向量库不存关系。正解：知识图谱。
```
真实生产 Agent 的记忆层因此往往是「多种记忆并存、按需路由」：
```text
                    ┌──────────────┐
     用户请求 ─────▶│  记忆路由器    │
                    └──────┬───────┘
          ┌───────────────┼────────────────┐
          ▼               ▼                ▼
   ┌────────────┐  ┌────────────┐   ┌────────────┐
   │ 结构化记忆  │  │  向量记忆   │   │ 知识图谱   │
   │(档案/订单/  │  │(聊天记录/   │   │ (实体关系) │
   │ 余额/过敏)  │  │ 文档)       │   │            │
   └────────────┘  └────────────┘   └────────────┘
        精确查询        语义检索          关系推理
```
路由器（简单规则或让模型判断）根据请求性质决定去哪套记忆取数，再汇总进上下文。这就是「用合适的工具做合适的事」在记忆层的体现。

## 最小可运行演示

下面用一个 MemGPT 式的分层记忆演示「主上下文（RAM）与外部存储（磁盘）之间的分页」，把架构思想落成可运行代码。纯标准库：
```python
"""MemGPT 式分层记忆分页：main context vs external storage。"""
from dataclasses import dataclass, field

@dataclass
class MemGPTLite:
    main_limit: int                                     # 主上下文容量（模拟 RAM）
    main: list[str] = field(default_factory=list)       # 常驻上下文
    external: list[str] = field(default_factory=list)   # 外部存储（模拟磁盘）
    log: list[str] = field(default_factory=list)

    def observe(self, msg: str) -> None:
        self.main.append(msg)
        if len(self.main) > self.main_limit:
            self._page_out()

    def _page_out(self) -> None:                        # 溢出：最旧一条换出到外部
        evicted = self.main.pop(0)
        self.external.append(evicted)
        self.log.append(f"page_out -> external: {evicted}")

    def recall(self, keyword: str) -> list[str]:        # 需要时从外部换入
        hits = [m for m in self.external if keyword in m]
        for h in hits:
            self.log.append(f"page_in <- external: {h}")
        return hits

def main() -> None:
    agent = MemGPTLite(main_limit=3)
    for m in ["系统:遵守用药安全", "用户:我对青霉素过敏", "用户:帮我查附近药房",
              "工具:返回3家药房", "用户:今天头痛想买药"]:
        agent.observe(m)
    print("主上下文(常驻):");  [print("  ", m) for m in agent.main]
    print("外部存储(换出):");  [print("  ", m) for m in agent.external]
    print("\n触发召回 keyword=青霉素：")
    for h in agent.recall("青霉素"):
        print("  召回:", h)
    print("\n控制流日志:");  [print("  ", line) for line in agent.log]

if __name__ == "__main__":
    main()
```
保存为 `memgpt_lite.py`，运行 `python memgpt_lite.py`。预期输出：
```text
主上下文(常驻):
   用户:帮我查附近药房
   工具:返回3家药房
   用户:今天头痛想买药
外部存储(换出):
   系统:遵守用药安全
   用户:我对青霉素过敏

触发召回 keyword=青霉素：
  召回: 用户:我对青霉素过敏

控制流日志:
   page_out -> external: 系统:遵守用药安全
   page_out -> external: 用户:我对青霉素过敏
   page_in <- external: 用户:我对青霉素过敏
```
注意这里的问题：过敏史被「换出」到外部后，只有显式 `recall("青霉素")` 才能取回。这正是 MemGPT 的核心思想，也是它的挑战——**分页的时机和召回的触发都需要智能决策**。真实 MemGPT 里，是让模型自己通过函数调用决定何时换入换出，而不是像这里用固定的容量规则。

## 真实系统对应

这一节的核心，把原理映射到五个真实系统的**公开机制**，并严守边界：

**MemGPT（Memory-GPT）** —— 论文《MemGPT: Towards LLMs as Operating Systems》提出「虚拟上下文管理（virtual context management）」，灵感来自操作系统的分层内存：把有限的上下文窗口类比为 RAM，把外部存储类比为磁盘，让 LLM 通过函数调用在两者间「分页（paging）」，并用中断机制管理自己与用户之间的控制流，从而在有限窗口内营造「近乎无限上下文」的假象 [来源](https://arxiv.org/abs/2310.08560)。上面的 `MemGPTLite` 就是这个思想的极简演示。

**Generative Agents（生成式智能体）** —— 论文《Generative Agents: Interactive Simulacra of Human Behavior》提出「记忆流（memory stream）」：一个追加式的自然语言日志，记录 Agent 的观察、交互与反思，每条带时间戳；检索时用 recency + importance + relevance 三信号加权打分（第 05 节已实现），并会把低层记忆「反思（reflection）」综合成更高层的洞察 [来源](https://arxiv.org/abs/2304.03442)。

**LangGraph / LangMem** —— LangGraph 官方文档把记忆分为短期（线程内、随 checkpointer 持久化）与长期（跨线程、按命名空间存取的 store），并按语义/情景/程序三类建模；程序记忆意味着 Agent 能从反馈中改写自己的指令 [来源](https://docs.langchain.com/oss/python/langgraph/persistence)。

**ChatGPT 记忆** —— OpenAI 公开两种机制：「saved memories（用户显式让它记住的事，除非删除会一直生效）」与「reference chat history（从过往对话中自动提炼洞察）」；2025 年 4 月引入的「dreaming」是一个后台过程，自动整理、合并、更新记忆状态，用户可随时在设置里关闭任一种 [来源](https://help.openai.com/en/articles/8590148-memory-faq)。

**Claude memory tool** —— Anthropic 的 memory tool 让模型在 `/memories` 目录下创建、读取、更新、删除文件，把学到的东西存到上下文窗口之外并在后续会话读回；关键是它是**客户端工具**——模型只发出记忆操作请求，实际存储由你的应用在你控制的基础设施上执行，因此存储位置和方式完全由你决定 [来源](https://docs.anthropic.com/en/docs/agents-and-tools/tool-use/memory-tool)。配合 context editing，可在工具结果累积时移除陈旧内容 [来源](https://www.anthropic.com/news/context-management)。

**边界声明**：以上都只陈述文档公开的外部行为与接口。这些系统的内部索引结构、提示模板、优先级算法、后台调度细节均未公开，本书不臆造。会变化的参数（窗口、维度、价格、目录路径、工具版本号）以各自当前官方文档为准。

## 生产踩坑

| 症状 | 根因 | 如何观测与复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| 精确查询返回「差不多」的错误结果 | 把精确/唯一数据放进向量库 | 用 ID 精确查对比向量召回 | 精确字段走结构化，向量只放语义文本 | 语义模糊检索本就该用向量 |
| 关系问题答不出多跳 | 向量库不存实体关系 | 问「X 的经理的经理」看能否答 | 关系推理用知识图谱 | 单跳事实向量+结构化够用 |
| 分页后关键信息取不回 | 换出后无有效召回触发 | 观察 page_out 后是否有 page_in | 让模型显式召回或对硬事实置顶不换出 | 一次性信息换出后不必召回 |
| 路由到错误的记忆存储 | 路由规则粗糙 | 记录每次请求路由到哪套存储 | 精细化路由规则或让模型判断并留证据 | 单一存储的简单系统无需路由 |
| 跨用户记忆串味 | 记忆键缺少用户/租户边界 | 安全测试：用户 A 能否检索到 B 的记忆 | 记忆命名空间隔离到 user/tenant | 不能靠提示词做隔离 |
| 照搬论文参数效果差 | 把论文权重/衰减当通用最优 | 在自己数据上对比默认与调优参数 | 用自己的评估集重新校准 | 复现论文实验时用原参数 |
| 误以为示例等于产品内部实现 | 混淆公开行为与内部机制 | 回查官方文档边界 | 只陈述可观察行为，推导明确标注 | — |

## 思考：MemGPT 和 RAG 式向量记忆是什么关系，冲突吗？

### 回答

不冲突，是**不同抽象层**的东西。RAG 式向量记忆关注「如何在海量外部知识里按语义找到相关片段」，它是一种检索机制。MemGPT 关注「如何让 LLM 自主管理有限上下文与无限外部存储之间的信息流动」，它是一种上下文管理架构——模型通过函数调用决定何时把信息换出到外部、何时换入回上下文。两者可以叠加：MemGPT 的「外部存储」完全可以用向量库实现，「换入」动作就是一次语义检索。可以这样理解：向量检索是「怎么取」，MemGPT 是「什么时候取、取回来放哪、什么时候再换出去」。前者是工具，后者是调度这个工具的操作系统式框架。

### 面试精简表达

向量检索是取回机制，MemGPT 是管理「取回/换出」时机的操作系统式架构；MemGPT 的外部存储可以就是一个向量库，两者是层次关系不是竞争关系。

## 思考：为什么真实系统几乎都是混合记忆，而不是纯向量？

### 回答

因为真实业务里同时存在三类本质不同的信息需求。第一类是**精确、唯一、强一致**的数据——用户 ID、余额、订单状态，这类必须用结构化存储，向量的「近似相似」在这里是灾难。第二类是**非结构化、需语义匹配**的文本——聊天记录、文档、用户偏好描述，这类才是向量记忆的主场。第三类是**实体间的关系**——组织架构、社交关系、依赖链，这类需要图查询。一个真实的 Agent 几乎必然同时碰到这三类需求（比如「查这个 VIP 用户（结构化）过去抱怨过什么（向量）以及他关联的企业账号（图）」），所以架构上必然是多存储并存 + 路由分发。纯向量方案要么在精确查询上出错，要么在关系推理上无能为力。选型的第一性原理不是「哪个技术先进」，而是「这条信息的检索需求是精确、语义还是关系」。

### 反例

反过来，也不能因为「混合架构更完整」就在一个只需要语义检索的简单场景（比如一个纯文档问答机器人）里硬上结构化库和图数据库——那是过度工程。混合是为了匹配真实的多元需求，需求单一时就用单一存储。架构复杂度应该由需求驱动，不是由「看起来更专业」驱动。

## 机制推导：从单会话记忆到「记忆操作系统」

把本章走过的路串起来，会看到一条清晰的抽象升级链。最原始的 Agent 只有短期记忆——上下文窗口（第 02 节）。加上向量检索，它有了长期记忆，能跨会话取回语义相关的片段（第 03、05 节）。加上写入/遗忘策略，长期记忆能保持高信噪比和时效性（第 04 节）。再往上，MemGPT 把「窗口与外部存储的信息流动」本身也交给模型自主管理，形成了「记忆操作系统」的雏形——模型不只是使用记忆，还调度记忆。

这条链解释了记忆系统演进的方向：**从「人写死规则管理记忆」走向「模型自主管理记忆」**，恰好呼应本书反复强调的分界线——流程由代码控制还是由模型控制。传统 RAG 是代码控制的固定检索；MemGPT 式架构、ChatGPT 的 dreaming、LangGraph 的程序记忆（Agent 自改指令）都是把记忆管理的一部分决策权交给模型。自主性带来灵活，也带来成本和不可预测性——什么时候该让模型自己决定换入换出、什么时候该用确定性规则兜底（比如高风险硬事实永远置顶不换出），是记忆架构设计的核心权衡，也是第 07 节生产实践要收束的地方。
