## 真实问题

同一个用药 Agent，另一类事故发生在「长会话」里。一位患者做了一次 40 轮的复杂问诊：描述症状、补充既往史、追问剂量、确认配送。第 3 轮她说过「我这次不要含酒精的药，正在开车」，助手当时记下了。到第 38 轮，模型推荐了一款含乙醇的止咳糖浆。回放发现：40 轮对话累计约 9000 字，早已超出为这次会话分配的窗口预算，第 3 轮那条约束被挤出了窗口——它不是被「淡忘」，而是被**一刀切掉**了。模型看到的输入里根本没有这句话，于是它「合理地」推荐了含酒精的药。

短期记忆的失败几乎都长这样：**不是模型记性差，而是关键信息被窗口的硬边界截断，或被淹没在中段而召回不到。** 这一节讲清短期记忆这个载体的两条硬约束——硬截断和「中间遗忘」——以及最基本的应对：token 预算与滑动窗口。

## 原理：短期记忆就是上下文内学习

**短期记忆**约等于「上下文内学习（in-context learning）」——当前这一轮，被放进 LLM 上下文窗口的全部内容：系统提示、历史对话、工具返回结果、本轮问题 [来源](https://lilianweng.github.io/posts/2023-06-23-agent/)。它是 Agent 每一轮决策的「工作台」。

它有三个特点，也是三条约束：

- **快而直接**：窗口内的信息模型直接「看到」，无需额外检索，保真度最高；
- **容量有限**：受上下文窗口大小限制。即便现代模型窗口越来越大，也不是无限的，且塞得越满越贵、召回质量越可能下降；
- **易失**：会话结束、或超出窗口被截断后，这部分就消失了——这正是第 01 节跨会话丢事实的直接原因。

短期记忆是工作台，不是仓库。把所有东西都堆在工作台上，只会让真正要用的工具被埋住。

## 为什么「塞满就变差」：两个隐性成本

「窗口大就多塞点」是新手常犯的错。要理解为什么不能这么干，得看两个隐性成本。

**成本一：算力与费用随长度超线性增长。** 自注意力的计算复杂度与序列长度成二次方关系（O(n²)）。工程上有 KV Cache（Key-Value Cache，键值缓存）、FlashAttention 等优化把常数压下来，但「更长上下文 = 更贵、更慢」这个大方向不变。为每一轮拖着一大堆无关历史，就是在为无用信息反复付费。

**成本二：中间遗忘（lost in the middle）。** Liu 等人的实验发现，当关键信息位于长上下文的中段时，模型的利用率明显下降——对开头和结尾的信息更敏感，对中段的信息容易「视而不见」，性能曲线呈现两端高、中间低的形状 [来源](https://arxiv.org/abs/2307.03172)。
```text
模型对长上下文不同位置的利用质量（示意，非精确曲线）：

利用率
  高 │████                          ████
     │████                          ████
     │████        ▁▁▁▁▁▁            ████
  低 │████       ▁      ▁▁          ████
     └────────────────────────────────────
      开头        中间（易被忽略）      结尾
```
两个成本合起来给出一个明确结论：**上下文不是越满越好，而应该「精」——只放和当前决策最相关的信息，其余交给长期记忆按需取回。** 这也是把短期与长期记忆分工的根本动机。注意：论文给出的是「相关信息位置影响性能」的统计规律，不宜当成对每个模型都成立的固定 U 形定律，只做「别把关键证据埋在中段」的工程指导。

## 最小可运行演示

下面这段代码把「短期记忆管理」落成最基本的两件事：**离线估算 token** 和 **滑动窗口保留最近对话**，并显式为模型输出预留额度。它纯标准库、无需联网：
```python
def est_tokens(text: str) -> int:
    """离线估算：非 ASCII（如中文）记 1 token，ASCII 每 4 字符约 1 token。
    这是教学估算，真实计数以对应模型的官方分词器为准。"""
    non_ascii = sum(1 for c in text if ord(c) > 127)
    ascii_cnt = len(text) - non_ascii
    return non_ascii + (ascii_cnt + 3) // 4

def fit_window(system: str, facts: list[str], history: list[str],
               window: int, output_reserve: int) -> dict:
    input_budget = window - output_reserve          # 关键：先扣掉输出预留
    used = est_tokens(system) + sum(est_tokens(f) for f in facts)
    kept, dropped = [], 0
    for msg in reversed(history):                    # 从最近往前保留
        t = est_tokens(msg)
        if used + t <= input_budget:
            kept.append(msg); used += t
        else:
            dropped += 1                             # 超预算：丢最旧的
    kept.reverse()
    return {"input_budget": input_budget, "used": used,
            "output_reserve": output_reserve, "kept": len(kept), "dropped": dropped}

def main() -> None:
    system = "你是医院导诊助手，必须遵守用药安全约束。" * 3
    facts = ["固定事实：用户对青霉素过敏（来源=初诊记录，状态=active）"]
    history = [f"第{i}轮对话：用户描述症状与既往史，助手给出初步建议。" for i in range(1, 41)]
    for k, v in fit_window(system, facts, history, window=800, output_reserve=200).items():
        print(f"{k} = {v}")

if __name__ == "__main__":
    main()
```
保存为 `short_term.py`，运行 `python short_term.py`。预期输出：
```text
input_budget = 600
used = 580
output_reserve = 200
kept = 19
dropped = 21
```
40 轮历史里有 21 轮因为超预算被丢弃，只保留了最近 19 轮。这正是第 3 轮约束「消失」的机制——它太旧了，被滑动窗口挤了出去。**这段代码也暴露了滑动窗口的根本缺陷：它按「新旧」而非「重要性」取舍，会把旧但关键的硬事实一并丢掉。** 修复办法不是把窗口调大（治标且更贵），而是把硬事实抽取成固定块置顶保留（第 04 节）、并把被丢弃的原文写入长期记忆按需取回（第 03、05 节）。注意代码里 `input_budget = window - output_reserve` 这一步：新手常把输入塞到接近窗口上限，结果模型还没说完就被截断。

## 真实系统对应

**官方公开机制**：LangGraph 把短期记忆建模为「线程内（thread-scoped）」状态，作为 Agent state 的一部分，通过 checkpointer 持久化到数据库，因而线程可随时恢复；长期记忆则是跨线程、跨会话、按命名空间存取的 store [来源](https://docs.langchain.com/oss/python/langgraph/persistence)。Anthropic 的上下文管理能力里，context editing 会在工具结果累积时移除陈旧内容、保留对话流，从而延长 Agent 可运行的时长 [来源](https://www.anthropic.com/news/context-management)。**通用工程模式**：为输出预留额度、滑动窗口保近期、把旧内容卸载到外部存储。**教学参考实现**：上面的 `est_tokens` 是离线近似，绝不能用来核对账单；接入真实模型时应替换为该模型官方的计数方法。

| 症状 | 根因 | 如何观测与复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| 长会话中期忘记早期约束 | 约束被滑动窗口挤出，属硬截断非渐忘 | 回放实际模型输入，检查该约束是否还在 | 抽取为固定事实置顶；原文入长期记忆 | 一次性偏好不必固定化 |

| 关键信息给了却没被用 | 埋在长上下文中段（lost in the middle） | 交换关键证据位置做消融对比 | 关键证据靠近问题、去重压缩 | 不宣称对所有模型成立固定 U 形 |
| 会话越长越慢越贵 | 每轮重发全部历史，O(n²) 成本 | 监控每轮输入 token 随轮数变化 | 滑动窗口 + 摘要 + 长期记忆卸载 | 短对话无需过早优化 |
| 工具返回长文本撑爆窗口 | 整段网页/日志全文入上下文 | 统计单条工具结果的 token 占比 | 先提炼要点/保留错误行再入窗口 | 需完整留档时存外部并放指针 |

## 思考：现在模型窗口都几十万 token 了，是不是就不需要 RAG 和长期记忆了？

### 回答

不是，三个理由。第一，**长上下文有二次方级的成本**，把所有历史全塞进去，又贵又慢，且随轮数单调增长。第二，**中间遗忘使超长上下文的有效召回打折扣**——信息「在窗口里」不等于「被用到」，埋在中段的关键证据可能被忽略。第三，**跨会话、跨用户的知识本就无法靠单次上下文承载**，今天窗口再大也接不住这个用户三个月前的过敏史。长窗口降低了对记忆系统的依赖强度，但没有取消它：窗口解决「这次能否放下」，记忆系统解决「跨时间的存、取、忘」。

### 反例

对于「一次性、单轮、无需跨会话」的短任务（比如把一段文本翻译成英文），确实不需要长期记忆，硬上一套向量库反而是过度设计。是否需要记忆系统，取决于任务是否有「跨轮/跨会话复用信息」的需求，而不是取决于窗口大小。

## 机制推导：短期记忆为什么必须和长期记忆分工

把短期记忆的三条约束（硬截断、二次方成本、中间遗忘）放在一起看，会自然推导出一个分工结论：**离当前决策越近的信息，越值得留在短期窗口里保真；越远、越可能过期、越不常用的信息，越应该卸载到长期存储按需取回。** 这就是「近保真、远卸载」原则。

它背后是一个价值密度判断。第 38 轮要决策时，第 37 轮的原文价值极高（刚刚发生、直接相关），第 3 轮那条「不要含酒精」的约束价值同样高（安全硬约束），但第 5 到第 20 轮的寒暄和已解决的追问价值很低。如果按「新旧」一刀切（滑动窗口），会误伤第 3 轮的高价值约束；如果全部保留，又会付二次方的成本还可能触发中间遗忘。正确的做法是**分层**：高价值硬事实无论多旧都置顶保留，低价值旧对话压缩成摘要或卸载到长期记忆，只有最近 K 轮保留原文。

这也解释了为什么单纯「调大窗口」不能根治问题：它只是把二次方成本和中间遗忘的临界点往后推，并没有解决「按重要性而非按新旧取舍」这个核心。真正的记忆工程，是在有限窗口内做**有优先级的信息调度**——这正是第 04 节写入/遗忘策略和第 05 节综合打分检索要解决的。

| 维度 | 优化前（纯滑动窗口） | 优化后（分层记忆） | 验证方式 |

| 早期硬约束 | 随窗口挤出即丢失 | 抽取为固定事实置顶保留 | 回放每轮组装清单，检查约束是否在 |
