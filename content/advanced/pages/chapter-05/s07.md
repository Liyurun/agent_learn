## 真实问题

用药 Agent 稳定运行三个月后，收到一条模糊告警：「用户投诉助手记错事」。这个描述无法直接行动——「记错」可能发生在写入（该记的没记）、检索（该取的没取回）、更新（旧记忆没被新值覆盖）、隔离（串了别的用户的记忆）或执行（取回了却没用上）任一层。生产诊断的第一步不是猜，而是**保存实际的记忆读写快照与检索结果**，再按层定位。这一节把记忆系统的生产经验收敛成一张大表和一组面试级思考回答。

## 记忆系统故障诊断顺序

1. **复现**：固定用户 ID、时间、模型版本、记忆库快照，确认能稳定重现「记错」。
2. **查写入**：该记的事实当初是否通过了写入闸门、是否真的落库（查写入日志）。
3. **查检索**：本轮生成前，正确记忆是否进入了检索候选、是否进入了最终上下文（查检索结果与组装清单）。
4. **查更新**：是否存在同一主题的多条冲突记忆（旧偏好没被新值覆盖）。
5. **查遗忘**：正确记忆是否被 TTL 或淘汰误删、是否被摘要压缩丢了细节。
6. **查隔离**：取回的记忆是否属于当前用户/租户，有无串味。
7. **查执行**：模型看到了正确记忆却没用上，属于提示或执行层问题。

## 生产建议表

下面是记忆系统的核心踩坑清单，按「症状 → 根因 → 如何观测与复现 → 修复与预防 → 不适用边界」组织，覆盖写入、检索、遗忘、隔离、成本、评估六个方面：

| 症状 | 根因 | 如何观测与复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| 该记的事实没记住 | 写入闸门阈值过高或抽取器漏抽 | 回放写入日志，查该事实是否被判低分 | 校准重要度阈值；高风险类别强制写入 | 一次性信息本就不该写 |
| 记忆库被噪声撑爆 | 无写入闸门，无差别追加 | 抽样统计低价值条目占比 | 加重要度闸门；定期压缩 | 需全量审计留档时另存原始日志 |
| 检索漏掉救命硬事实 | 只按相关度排序 | 用金标准查询对比 search 与综合检索 | 叠加重要度权重做综合打分 | 无风险差异场景可纯相关度 |
| 检索返回过期偏好 | 无 TTL，旧偏好长期生效 | 统计召回条目的年龄分布 | 时效性记忆设 TTL；近因衰减 | 法律保留记录不受 TTL 支配 |
| 同一主题返回矛盾记忆 | 写入只追加不更新 | 检索该主题看是否有冲突条 | 写入做更新/合并；标生效时间 | 需保留演化历史的审计场景留旧版 |
| 精确查询返回近似错误值 | 精确数据放进了向量库 | 用 ID 精确查对比向量召回 | 精确字段走结构化存储 | 语义模糊检索本就用向量 |
| 跨用户记忆串味 | 记忆键缺用户/租户命名空间 | 安全测试：A 能否检索到 B 的记忆 | 命名空间隔离到 user/tenant | 不能靠提示词做隔离 |
| 摘要压缩后丢关键约束 | 有损压缩丢了细节 | 摘要与原始对话 diff | 关键约束置顶保留；原文入长期记忆 | 纯闲聊丢细节可接受 |
| 长会话越跑越慢越贵 | 每轮重发全部历史 | 监控输入 token 随轮数变化 | 滑动窗口+摘要+长期记忆卸载 | 短对话无需优化 |
| 换 embedding 后检索全乱 | 新旧模型语义空间不同 | 混用后距离计算无意义 | 换模型全量重建索引与阈值 | 同模型同维度可增量 |
| 记忆无限增长、成本失控 | 只写不删无上限 | 监控条目数与存储成本曲线 | TTL+容量上限+定期压缩+冷归档 | 冷存储归档可放宽上限 |
| 追踪日志泄露敏感信息 | 写入前未脱敏，原文含隐私 | 审计追踪管道里的字段 | 写入前最小化并脱敏敏感字段 | 合规要求可能限制原文留存 |
| 模型看到事实却不用 | 提示未强调或执行层缺校验 | 检查输入含事实但输出违背 | 关键约束置顶+确定性业务校验兜底 | 非硬约束可容忍模型判断 |
| 指标正常但用户仍说记错 | 只量召回率/延迟，缺端到端 | 增加「记忆导致的任务成功率」 | 建端到端评估集含记忆相关用例 | 指标不取代人工复核 |

这里 TTL（Time To Live，生存时间）只能用于可过期的偏好，不应自动删除法律保留或未完成事务；PII（Personally Identifiable Information，个人可识别信息）在写入记忆与追踪前应最小化和脱敏，跨用户/租户隔离不能依赖提示词而应用命名空间和访问控制强制执行。

## 最小可运行演示

把上面的诊断顺序落成一个可运行的分层诊断器，纯标准库：
```python
def diagnose_memory(m: dict) -> list[str]:
    findings = []
    if not m["fact_written"]:
        findings.append("写入：该事实未通过闸门或未落库")
    elif not m["fact_in_candidates"]:
        findings.append("检索：正确记忆未进入候选")
    elif not m["fact_in_context"]:
        findings.append("组装：候选记忆未进入最终上下文")
    if m["conflicting_versions"] > 1:
        findings.append("更新：存在多个冲突版本")
    if m["cross_tenant_leak"]:
        findings.append("隔离：检索到其他租户记忆")
    if m["fact_in_context"] and m["violated_in_output"]:
        findings.append("执行：看到事实却违背，需业务校验兜底")
    return findings or ["需固定输入做检索排序与模型消融"]

def main() -> None:
    metrics = {
        "fact_written": True,
        "fact_in_candidates": True,
        "fact_in_context": True,
        "conflicting_versions": 1,
        "cross_tenant_leak": False,
        "violated_in_output": True,
    }
    print("\n".join(diagnose_memory(metrics)))

if __name__ == "__main__":
    main()
```
保存为 `diagnose_memory.py`，运行 `python diagnose_memory.py`。预期输出：
```text
执行：看到事实却违背，需业务校验兜底
```
把 `fact_in_candidates` 改成 `False`，输出会变成「检索：正确记忆未进入候选」。这个诊断器只负责缩小范围，不自动删记忆或改阈值；每个判断在生产里都应连到可打开的检索快照和写入日志。它体现了记忆诊断的核心原则：**先定位「哪一层第一次偏离预期」，而不是笼统归因为「记忆不行」。**

## 真实系统对应

**官方公开机制**：OpenAI 明确 ChatGPT 用户可删除单条记忆、清空全部或整体关闭，且提供临时聊天（Temporary Chat）以不使用记忆 [来源](https://help.openai.com/en/articles/8590148-memory-faq)——这对应生产中「用户对自身记忆的控制权」这一合规要求。Anthropic memory tool 的存储由客户端控制，因此脱敏、隔离、保留期治理的责任在应用侧 [来源](https://docs.anthropic.com/en/docs/agents-and-tools/tool-use/memory-tool)。**通用工程模式**：分层诊断、命名空间隔离、写入脱敏、端到端评估。**教学参考实现**：上面的诊断器字段和判断顺序是示例，真实系统的指标集、阈值和告警由团队按风险设计，本书不声称任何平台自动完成这些治理。

## 思考：记忆系统最重要的可观测指标是什么？

### 回答

没有单一指标，但最低集合应包含：**硬事实召回率**（救命/高风险事实是否被检索到并进入上下文）、**记忆导致的任务成功率**（区别于总体成功率，专门衡量记忆用对没用对）、**冲突版本数**（同主题矛盾记忆的数量）、**跨租户泄露数**（安全底线，应为零）、**记忆库年龄分布与增长曲线**（时效与成本健康度）、**写入/检索延迟**。关键原则是：成本类指标（token、条目数）必须与任务结果联看，否则「记得少」可能只是「漏了救命信息」。只盯召回率也不够——召回率高但取回的全是噪声，任务照样失败。指标要能回答「记忆帮到还是坑到了任务」，而不只是「记了多少、取了多快」。

## 思考：如何把一套记忆系统安全地引入现有 Agent？

### 回答

先加观测，再改机制。第一步记录每轮的记忆读写：写入了什么、检索候选是什么、最终进上下文的是什么、来源和时间戳。第二步用历史投诉建立回归集（比如那次青霉素事故）。然后按风险从低到高依次改：先做写入脱敏和用户/租户隔离（安全底线），再加写入闸门和 TTL（信噪比），再引入综合打分检索（召回质量），最后才考虑 MemGPT 式自主管理这类高自主性方案。每一步做对照实验、保留回滚开关，用同一批回归样本验证是否真的改善，避免把随机波动当收益。切忌一上来就重写整个记忆架构——那样出了问题无法定位是哪个改动导致的。

## 思考：记忆系统的安全底线是什么？

### 回答

五条不可逾越的底线。第一，**跨用户/租户绝不复用记忆**——隔离必须用命名空间和访问控制强制，不能靠提示词「请不要串」。第二，**写入和追踪前必须脱敏 PII**，不能为了「记得全」把身份证、银行卡、病历原文无界存进记忆库。第三，**用户对自身记忆有控制权**——能查看、删除、关闭，这既是合规要求也是信任基础（ChatGPT 就提供删除单条/清空/关闭）。第四，**高风险决策不能只信记忆**——取回了「过敏史」是好事，但最终该不该开这个药，必须有一道模型之外的确定性业务校验兜底。第五，**法律保留数据不受一般遗忘策略支配**——TTL 和淘汰只管可过期偏好，合规记录该归档到冷存储而非删除。记忆能帮模型遵守规则，但最终的安全控制永远在模型之外强制执行。

## 值班现场：从「记错事」到可复现故障

一个真实的排查过程。用户投诉「助手推荐了我明确说过不吃的东西」。值班人员先取该用户 ID 和投诉时间，导出当时的记忆读写快照：写入日志显示「用户不吃辣」在两周前成功落库，重要度 4；但本轮检索候选里没有这条。继续查检索：本轮查询是「推荐一家餐厅」，与「不吃辣」的字面/语义相关度都不高，纯相关度排序把它排到了 Top-K 之外——这是一次典型的「检索层漏召回硬偏好」故障，而非写入或执行问题。

修复方向随之明确：把「忌口」这类偏好的重要度上调，并在综合打分里给它足够权重，让它即便与「推荐餐厅」字面不相关也能进入上下文；同时在推荐环节加一道确定性过滤（命中忌口的候选直接排除），作为兜底。上线后用这条投诉做回归验证：同样的查询下「不吃辣」稳定进入上下文，且含辣餐厅被过滤。整个过程从「模糊投诉」到「定位在检索层」只花了二十分钟——不是因为日志多，而是因为日志能回答「记忆在哪一层第一次没帮上忙」。

## 六类常见误诊

「记忆不行」常被当成通用解释，但它可能只是某一层的问题。**误诊一**：把「漏召回」当「没记住」——事实其实在库里，只是检索没排进 Top-K，改写入闸门无用，该调检索排序。**误诊二**：把「过期误导」当「模型幻觉」——模型忠实地用了一条旧记忆，问题在没有 TTL 和更新，不在模型。**误诊三**：把「串味」当「检索不准」——取回的是别人的记忆，是隔离故障，调相似度阈值无济于事。**误诊四**：把「看到却违背」当「记忆缺失」——事实明明进了上下文，是执行层缺校验，补记忆没用。**误诊五**：把「摘要丢细节」当「没存过」——原文其实存过，是压缩弄丢了，该改压缩策略而非重新采集。**误诊六**：把「换模型后全乱」当「记忆库损坏」——是新旧 embedding 语义空间不兼容，该重建索引而非清库。每一类误诊的共同教训是：**先看证据落在哪一层，再动手，别用一个笼统结论掩盖具体的失败点。**

## 优化前后对照

以历史投诉构成固定回归集，每次只改一个环节并对照：

| 优化 | 基线问题 | 单一改动 | 成功判据 | 回滚信号 |
|---|---|---|---|---|
| 提升忌口重要度 | 硬偏好漏召回 | 上调该类重要度权重 | 硬偏好稳定进上下文 | 无关偏好挤占 Top-K |
| 加 TTL | 过期偏好误导 | 给时效偏好设生存时间 | 过期条目自动清理 | 误删仍有效的偏好 |
| 命名空间隔离 | 跨用户串味 | 记忆键加 user/tenant | 跨租户泄露数=0 | 合法共享数据被隔离 |
| 写入脱敏 | 追踪含 PII | 写入前最小化脱敏 | 敏感字段不落库 | 排障所需字段缺失 |
| 综合打分检索 | 只按相关度 | 叠加近因+重要度 | 硬事实召回率上升 | 相关结果被重要度淹没 |
| 业务校验兜底 | 看到却违背 | 命中忌口直接过滤 | 违规推荐归零 | 合法推荐被误杀 |

没有对照，召回率上升可能来自数据变化，成本下降可能只是答案变短。每个优化都要能回答「改善了哪个指标、代价是什么、什么时候该回滚」。

## 思考：什么时候应该让记忆系统「拒绝回答」而非硬答？

### 回答

当记忆状态存在无法自行消解的不确定性时，正确做法是返回结构化的「需要确认」而非流畅地硬答。具体触发条件：同一主题存在多个冲突记忆且无法判断哪个生效（比如两条矛盾的过敏记录）；高风险决策所依赖的关键记忆缺失或已过期（该记的过敏史查不到）；检索到的记忆无权限访问或疑似跨租户；关键记忆刚被摘要压缩、细节已不可回溯。这些情况下，硬答会用一段流畅的文字掩盖不确定性，风险极高。拒绝信息应包含：哪一层出了问题、缺什么、如何补（请用户确认或人工介入），但不得泄露其他用户的记忆或系统内部细节。这与第 04 节「遗忘要保护硬事实」、第 07 节「安全底线」是一致的——记忆系统的价值不只在「能答」，更在「知道自己什么时候不该答」。

### 反例

但「拒绝」不能滥用成推卸。如果只是普通偏好记忆缺失（比如不知道用户喜欢什么口味），正确做法是正常回答并顺便询问，而不是动辄拒绝——那会让产品变得难用。拒绝只适用于「硬答有实质风险」的场景，日常的信息不全应该用「先答 + 补问」优雅处理。把握的标准是：错了会不会造成安全/合规/信任的实质损害。
