## 真实问题

用药 Agent 上线一个月后，团队想给它加「跨会话记住用户偏好」的能力。第一版实现很朴素：把每次会话的完整文字直接拼接存进一个大文本文件，下次会话把整个文件塞进上下文。两周后这个文件涨到 12 万字，每轮请求都超预算、又慢又贵，而且模型还是答不准——因为它要在 12 万字里自己找那句「青霉素过敏」，命中率极低。真正的问题是：**长期记忆不能靠「全量回灌」，必须靠「按需检索」——每轮只取回与当前问题最相关的几条。** 而「按语义找相关」这件事，靠字符串匹配做不到（用户这次问「甲壳类会不会让他不舒服」，字面上根本没有「海鲜」二字），必须靠向量检索。这一节讲清向量检索的四个环节：embedding、余弦相似度、近似最近邻、分块。

## 原理：长期记忆 = 外部存储 + 检索

当信息量超出窗口，或需要跨会话保留时，就需要**长期记忆**——把信息存到外部，用时再检索回来 [来源](https://lilianweng.github.io/posts/2023-06-23-agent/)。最主流的实现是**向量存储（Vector Store）**，工作流程分写入和查询两条：
```text
写入：  文本 ──embedding──▶ 向量 ──▶ 存入向量库
                                       │
查询：  问题 ──embedding──▶ 向量 ──检索最相近的向量──▶ 取回对应文本 ──▶ 回填上下文
```
关键技术是**快速最大内积搜索（MIPS，Maximum Inner Product Search）**配合**近似最近邻（ANN，Approximate Nearest Neighbor）算法**（如 LSH、HNSW），让 Agent 能从近乎无限的历史里，毫秒级召回最相关片段 [来源](https://lilianweng.github.io/posts/2023-06-23-agent/)。用「近似」而非「精确」，是因为海量向量精确搜索太慢——ANN 用极小的精度损失换数量级的速度提升，是标准工程权衡。

## embedding：把语义变成坐标

要理解向量检索，先理解 embedding 在干什么。一句话：**embedding（嵌入）把一段文本映射成高维空间里的一个点（向量），使得「语义相近的文本，坐标也相近」。** OpenAI 的 text-embedding-3-small 默认输出 1536 维，text-embedding-3-large 默认 3072 维，且支持用 dimensions 参数在少量精度损失下降维 [来源](https://platform.openai.com/docs/guides/embeddings)。
```text
语义空间的直觉（降到二维看）：

        猫 •
      狗 •   • 宠物
                        • 汽车
                     卡车 •  • 火车
        ↑                    ↑
   动物聚成一簇         交通工具聚成另一簇

「猫」和「狗」向量距离近（语义相似），
「猫」和「汽车」距离远（语义无关）。
```
有了这个空间，「检索语义相关内容」就变成几何问题：**把查询也映射成点，找空间里离它最近的那些点。** 这就是向量检索的全部直觉，也是它超越关键词匹配的根源——它比的是「意思」，不是「字面」。衡量「近不近」通常用**余弦相似度**（两向量夹角余弦），只看方向不看长度，很适合文本语义比较；余弦越接近 1，方向越一致、语义越相近。OpenAI 文档指出其 embedding 已归一化，因此点积与余弦相似度会给出相同排序 [来源](https://platform.openai.com/docs/guides/embeddings)。

## 最小可运行演示

下面这段纯标准库代码把 embedding、余弦相似度、分块三件事串起来。为了零依赖可运行，`embed` 用「字袋」当玩具 embedding；真实系统换成模型输出即可，检索逻辑不变：
```python
import math
from collections import Counter

def embed(text: str) -> Counter:
    return Counter(text)                              # 玩具字袋 embedding

def cosine(a: Counter, b: Counter) -> float:
    common = set(a) & set(b)
    dot = sum(a[t] * b[t] for t in common)            # 点积
    na = math.sqrt(sum(v * v for v in a.values()))    # a 的模长
    nb = math.sqrt(sum(v * v for v in b.values()))    # b 的模长
    return dot / (na * nb) if na and nb else 0.0      # 特判除零，常见边界坑

def chunk_text(text: str, size: int, overlap: int) -> list[str]:
    chunks, start = [], 0
    while start < len(text):
        end = start + size
        chunks.append(text[start:end])
        if end >= len(text):
            break
        start = end - overlap                          # 下一块回退 overlap，制造重叠
    return chunks

def main() -> None:
    docs = ["青霉素过敏者禁用阿莫西林", "华法林与阿司匹林合用增加出血风险",
            "马拉松训练建议循序渐进"]
    q = "他能不能吃阿莫西林"
    print("=== 语义相似度排序 ===")
    for s, d in sorted(((cosine(embed(q), embed(d)), d) for d in docs), reverse=True):
        print(f"  {s:.3f}  {d}")
    doc = "背景介绍。" * 8 + "核心方法。" * 8 + "实验结论。" * 8
    pieces = chunk_text(doc, size=24, overlap=6)
    print(f"\n=== 分块：原文 {len(doc)} 字 -> {len(pieces)} 块 ===")
    for i, p in enumerate(pieces):
        print(f"  块{i+1}({len(p)}字): {p}")

if __name__ == "__main__":
    main()
```
保存为 `vector_basics.py`，运行 `python vector_basics.py`。预期输出（节选）：
```text
=== 语义相似度排序 ===
  0.348  青霉素过敏者禁用阿莫西林
  0.213  华法林与阿司匹林合用增加出血风险
  0.000  马拉松训练建议循序渐进

=== 分块：原文 120 字 -> 7 块 ===
  块1(24字): 背景介绍。背景介绍。背景介绍。背景介绍。背景介绍
  ...
```
「青霉素过敏者禁用阿莫西林」被排在最前，因为它和查询共享「阿莫西林」这些字。真实 embedding 不看字面重合而看深层语义，所以即便查询换成「甲壳类会不会让他不适」，也能召回「海鲜过敏」那条——这是语义检索超越关键词匹配的地方。但要注意：这里的玩具 `embed` 只会字面匹配，它演示的是**流程**，不是语义能力本身。

## 精确检索 vs 近似最近邻（ANN）

上面的暴力线性扫描是「精确最近邻」：一定能找到真正最近的 K 个，但每次查询要和库里每个向量比一遍，复杂度 O(N)。当 N 是千万、上亿时就崩了。**近似最近邻（ANN）** 的思路是：牺牲极小精度（偶尔漏掉真正最近的那个），换数量级的速度提升。

| 算法 | 核心思路 | 特点 |
|---|---|---|
| LSH（Locality-Sensitive Hashing，局部敏感哈希） | 用特殊哈希让相近向量大概率落进同一桶，只在桶内搜 | 实现简单，适合超高维 |
| HNSW（Hierarchical Navigable Small World，分层可导航小世界图） | 建多层图，高层稀疏做「高速公路」，低层密集做「本地路」，逐层逼近 | 目前主流，查询快、召回高 |
| IVF（Inverted File，倒排文件 + 聚类） | 先把向量聚成若干簇，查询时只搜最近几个簇 | 内存友好，适合海量数据 |
```text
HNSW 分层逼近直觉：

  第2层（稀疏）:   A ─────────────▶ E     ← 大步跳跃，快速接近目标区域
  第1层（较密）:   A ──▶ C ──▶ D ──▶ E     ← 中等步长
  第0层（最密）:   A─B─C─D...─E─F─G...      ← 精细定位最近邻
```
必须建立的观念：**「召回率」和「查询速度」是一对可调节的权衡。** ANN 的参数（HNSW 的 `ef_search`、IVF 的探测簇数 `nprobe`）本质上都在这条权衡曲线上滑动——调大更准但更慢，调小更快但可能漏检。

## 文本分块（Chunking）：写入前最易被忽视的一步

把文档写进向量库前，有一个决定成败却常被忽视的环节——**分块**。长文档不能整篇当一个向量存，原因有二：一是 embedding 模型有输入长度上限（如 text-embedding-3 上限约 8191 token），整篇塞不下；二是即便塞得下，「一整篇」的向量会把各种主题的语义平均成一团糊，检索既不精准、取回又太长。标准做法是先切块，每块单独 embedding、单独存储、单独检索。

分块的核心矛盾是「块大小」的权衡：
```text
块太小（每句一块）：
   ✅ 检索精准，命中就是那一句
   ❌ 语义被切碎，一个完整意思拆散在多块，检索到半句缺上下文

块太大（每章一块）：
   ✅ 语义完整
   ❌ 检索不精准，一块混多个主题；取回太长，稀释重点
```
常用折中是「固定大小 + 重叠（overlap）」：每块取固定长度，相邻块保留一小段重叠，避免把完整句子从中间劈开。上面 `chunk_text` 里 `start = end - overlap` 就是精髓——下一块起点往回退 overlap 个字，让关键句子即便落在块边界也能在两块里各出现一部分。真实系统还有更聪明的「语义分块」——按段落、标题、句子边界切，原则始终是**尽量让每块是一个语义自洽的单元**。分块质量直接决定检索天花板：块切坏了，embedding 再好、ANN 再快也救不回来。

## 真实系统对应

**官方公开机制**：OpenAI Embeddings 指南公开了 text-embedding-3-small（1536 维）与 text-embedding-3-large（3072 维）的默认维度、8191 token 输入上限、dimensions 降维参数，以及「向量已归一化，点积等价于余弦相似度」的性质 [来源](https://platform.openai.com/docs/guides/embeddings)。**通用工程模式**：写入分块→embedding→存库，查询 embedding→ANN 检索→回填。**教学参考实现**：`Counter(text)` 只是玩具，用来演示流程而非真实语义能力；生产中把 `embed` 换成模型调用、把线性扫描换成向量数据库的 ANN 索引即可，其余逻辑不变。ANN 算法（HNSW/IVF/LSH）是公开的通用算法，不归属任何单一厂商。

## 生产踩坑

| 症状 | 根因 | 如何观测与复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| RAG 召回全是半句、跑题 | 分块太大或按固定字数硬切，切碎表格/代码 | 打印实际召回的 chunk 原文 | 按语义边界分块 + 重叠；先修分块再调 ANN | 极短文档无需分块 |
| 换过滤条件后语义检索失效 | 精确条件当语义查询做 | 对比 SQL 过滤与向量检索结果 | 精确字段走结构化，语义走向量 | 见第 06 节混合架构 |
| 检索慢到不可用 | 百万级向量仍用线性扫描 | 压测查询延迟随库大小变化 | 引入 HNSW/IVF 索引 | 千级小库线性扫描够用 |
| 召回漏掉正确答案 | ANN 参数过激进（ef/nprobe 太小） | 用精确检索做金标准对比召回率 | 调大参数或加精确重排兜底 | 对召回不敏感场景可保持高速 |
| 换了 embedding 模型后旧向量失效 | 新旧模型维度/语义空间不同，不可混比 | 混用后计算距离得到无意义结果 | 换模型要全量重建索引 | 同模型同维度可增量追加 |
| 相似度普遍偏高、区分度差 | 未归一化或维度不匹配 | 检查向量模长与维度 | 归一化后用点积；统一维度 | 已归一化模型可直接点积 |

## 思考：为什么向量检索普遍用近似而不用精确？近似会不会漏掉答案？

### 回答

精确检索是 O(N) 线性扫描，海量向量下延迟不可接受；ANN 用图/哈希/聚类结构把复杂度降到近似对数级，代价是有极小概率漏检真正的最近邻。是否可接受取决于业务——多数 RAG 场景 top-k 召回丢一两个边缘结果无伤大雅；对召回极敏感的场景（如医疗、法务），可以调高 ANN 参数、缩小速度优势，甚至加一层精确重排（rerank）兜底：先用 ANN 快速召回一批候选，再用更精确的模型对候选重新打分。关键是把「召回率-延迟」这条权衡曲线摆到台面上,由业务风险决定参数,而不是默认吃厂商预设。

### 面试精简表达

精确是「保证找到但慢」，近似是「极大概率找到但快」；ANN 把召回率换成了可控的速度收益，敏感场景再用重排兜底。

## 机制推导：从「全量回灌」到「按需检索」的必然

回到本节开头 12 万字文件的教训。为什么「全量回灌」必然失败，而「按需检索」是唯一可扩展的路径？做一个简单的量级推演：假设一个活跃用户每天产生 2000 字有效记忆，一年就是约 70 万字。全量回灌意味着每轮请求都要处理这 70 万字——远超任何窗口，成本随时间无上限增长，且触发严重的中间遗忘。而任何一次具体提问，真正相关的往往只有几条记忆。

这就逼出向量检索的价值主张：**用一次 embedding + ANN 搜索，把「在 70 万字里找几条相关的」从 O(N) 的人工翻找，变成毫秒级的几何最近邻查询。** 它把长期记忆的规模上限从「窗口能装多少」解耦为「存储能放多少」，而检索成本只与「取回 Top-K」有关，几乎不随库总量增长。这也解释了为什么记忆系统的核心技术恰好是向量检索——它是唯一能在近乎无限的历史里做到「毫秒级按语义取回」的通用手段。但它有一个第 05 节要解决的天生缺陷：**纯相关度会把「本轮问题」这种字面最匹配的排在最前，而把「青霉素过敏」这种救命但字面不匹配的硬事实排在后面。** 检索不能只看相关度，这是下一步的关键。
