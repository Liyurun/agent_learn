## 真实问题

用药 Agent 的向量记忆上线三周后，检索质量不升反降。排查发现记忆库里塞满了噪声：「用户说了谢谢」「用户问现在几点」「用户这次想订牛排」这类一次性、无复用价值的闲聊被无差别写入，占了记忆条目的 70%。真正有价值的「青霉素过敏」被淹没在成千上万条垃圾里，检索时经常被挤出 Top-K。更糟的是，半年前用户随口说的「最近在减肥不吃主食」一直没被清理，如今她早已恢复正常饮食，这条过期偏好还在误导推荐。

这暴露了记忆系统最容易被跳过、却最影响长期质量的两个策略：**写入策略（什么该记）**和**遗忘策略（什么该忘）**。只做「存」和「取」，不做「筛」和「忘」，记忆库迟早退化成一个又贵又准的垃圾场。这一节把这两件事做成可运行代码。

## 原理：记忆的四种类型与写入触发

LangGraph 的记忆文档把长期记忆按人类类比分成三类，每类有不同的写入触发时机 [来源](https://docs.langchain.com/oss/python/langgraph/persistence)：

| 记忆类型 | 存什么 | 人类类比 | Agent 例子 | 写入触发 |
|---|---|---|---|---|
| 语义记忆（Semantic） | 关于实体的稳定事实 | 事实知识 | 「用户对青霉素过敏」 | 抽取器发现一条事实 |
| 情景记忆（Episodic） | 带时间戳的事件 | 亲历的经历 | 「2026-04-12 用户报告账单 bug」 | 检测到重要事件 |
| 程序记忆（Procedural） | 学到的行为/指令 | 本能与肌肉记忆 | 「对该用户总是先确认地址」 | 从反馈中强化 |

关键洞察：**不是所有信息都值得写入。** 写入需要一道闸门，判断「这条信息是否有跨会话复用价值」。一个实用的启发式是给每条候选记忆打一个「重要度」分：涉及安全、健康、身份、长期偏好的高分；一次性意图、寒暄、可随时重新获取的信息低分。低于阈值的不写。

遗忘同样需要显式设计，通常有三种互补机制：

- **TTL（Time To Live，生存时间）过期**：给有时效的记忆设一个存活时间，到期自动清理（如「本次会话想吃牛排」TTL=1 天）。
- **淘汰（Eviction）**：容量超限时按策略删除，常用 LRU（Least Recently Used，最近最少使用）——删掉最久没被命中的，但高重要度事实应受保护。
- **摘要压缩（Compaction）**：把大量旧对话压成简短摘要，用摘要替换原文，腾出空间——这是一种「有损但保主干」的遗忘。

## 最小可运行演示

下面这段代码把「写入闸门 + TTL 过期 + LRU 淘汰 + 重要度保护」串成一个可运行的记忆管理器，纯标准库：
```python
from dataclasses import dataclass

@dataclass
class Record:
    text: str
    importance: int       # 1-10，写入时打分
    ttl_hours: float      # 生存时间；用大数模拟「永不过期」
    age_hours: float      # 已存活时长
    last_used_hours: float  # 距上次命中的小时数

def should_write(text: str, importance: int, min_importance: int = 4) -> bool:
    """写入闸门：空文本或太琐碎（重要度低）不写。"""
    return bool(text.strip()) and importance >= min_importance

def evict(records: list[Record], capacity: int):
    removed = []
    # 1) TTL 过期先删
    alive = []
    for r in records:
        if r.age_hours > r.ttl_hours:
            removed.append(f"TTL过期: {r.text}")
        else:
            alive.append(r)
    # 2) 超容量按 LRU 淘汰，但 importance>=9 视为受保护
    if len(alive) > capacity:
        protected = [r for r in alive if r.importance >= 9]
        cand = sorted((r for r in alive if r.importance < 9),
                      key=lambda r: r.last_used_hours)   # 最近用过的排前
        keep = cand[:max(0, capacity - len(protected))]
        for r in cand[len(keep):]:
            removed.append(f"LRU淘汰: {r.text}")
        alive = protected + keep
    return alive, removed

def main() -> None:
    raw = [
        ("用户对青霉素过敏", 9, 1e9, 2000, 5),
        ("用户这次会话想订牛排", 3, 24, 30, 30),          # 重要度<4，被闸门拦下
        ("用户上周说喜欢靠窗座位", 5, 24 * 30, 24 * 40, 24 * 40),  # 超 TTL
        ("用户常用配送地址=朝阳区", 7, 1e9, 500, 10),
        ("用户偏好清淡口味", 4, 1e9, 100, 1),
    ]
    records = [Record(*row) for row in raw if should_write(row[0], row[1])]
    print(f"写入后条数 = {len(records)}")
    kept, removed = evict(records, capacity=3)
    print(f"淘汰后条数 = {len(kept)}")
    for line in removed:
        print("  -", line)
    print("保留：")
    for r in kept:
        print(f"  * {r.text} (imp={r.importance})")

if __name__ == "__main__":
    main()
```
保存为 `write_forget.py`，运行 `python write_forget.py`。预期输出：
```text
写入后条数 = 4
淘汰后条数 = 3
  - TTL过期: 用户上周说喜欢靠窗座位
保留：
  * 用户对青霉素过敏 (imp=9)
  * 用户常用配送地址=朝阳区 (imp=7)
  * 用户偏好清淡口味 (imp=4)
```
注意三件事：「想订牛排」重要度 3，被写入闸门直接拦下（写入后是 4 条不是 5 条）；「靠窗座位」存活 40 天超过 30 天 TTL，被清理；「青霉素过敏」重要度 9 受保护，即便容量紧张也绝不淘汰。这正是修复本节开头故障的三板斧：**闸门挡噪声、TTL 清过期、重要度护硬事实。**

## 摘要压缩：用代码演示「近保真、远摘要」

除了删除，另一种遗忘是「压缩」——把旧对话压成摘要，保留主干、丢弃细节。下面演示保留最近 K 轮原文、其余压成一句摘要：
```python
def summarize(messages: list[str]) -> str:
    """真实场景调 LLM 生成摘要，这里用拼接模拟。"""
    topics = [m.split("：", 1)[-1][:6] for m in messages]
    return f"[早期摘要：涉及 {', '.join(topics)} 等 {len(messages)} 条]"

def manage(history: list[str], keep_recent: int = 3) -> list[str]:
    if len(history) <= keep_recent:
        return history                          # 没超预算，原样返回
    old, recent = history[:-keep_recent], history[-keep_recent:]
    return [summarize(old)] + recent            # 摘要 + 近期原文

def main() -> None:
    history = [f"用户：第{i}轮问题ABC" for i in range(1, 9)]
    compact = manage(history, keep_recent=3)
    print(f"压缩前 {len(history)} 条 -> 压缩后 {len(compact)} 条")
    for m in compact:
        print("  ", m)

if __name__ == "__main__":
    main()
```
保存为 `compact.py`，运行 `python compact.py`。预期输出：
```text
压缩前 8 条 -> 压缩后 4 条
   [早期摘要：涉及 第1轮问题, 第2轮问题, 第3轮问题, 第4轮问题, 第5轮问题 等 5 条]
   用户：第6轮问题ABC
   用户：第7轮问题ABC
   用户：第8轮问题ABC
```
精髓在「分层保真」：离当前决策越近的信息越需要原汁原味，越远的越可压缩。研究型 Agent 跑几十上百轮，靠的正是这类压缩续命。但摘要是**有损压缩**，务必警惕它丢掉后面才发现「其实很重要」的细节——缓解办法是把关键约束在摘要时显式置顶，且原文别扔、存进长期记忆按需检索回。

## 真实系统对应

**官方公开机制**：OpenAI ChatGPT 的记忆分「saved memories（显式让它记住）」与「chat history / dreaming（后台自动从历史对话提炼、整理记忆）」两种，用户可删除单条、清空或整体关闭；官方明确 saved memories 除非删除会一直生效 [来源](https://help.openai.com/en/articles/8590148-memory-faq)。这正对应「显式写入」与「自动抽取写入」两条写入路径。Anthropic 的 memory tool 支持对 `/memories` 目录做创建、读取、更新、删除（含删除即遗忘），存储由你的应用控制 [来源](https://docs.anthropic.com/en/docs/agents-and-tools/tool-use/memory-tool)；其 context editing 会在工具结果累积时移除陈旧内容 [来源](https://www.anthropic.com/news/context-management)。**通用工程模式**：写入闸门、重要度打分、TTL、LRU、摘要压缩。**教学参考实现**：上面的阈值、TTL 天数和保护规则都是示例，真实系统需按业务风险调参并做审计。

## 生产踩坑

| 症状 | 根因 | 如何观测与复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| 记忆库被噪声撑爆、检索变差 | 无写入闸门，无差别写入闲聊 | 抽样记忆条目，统计低价值占比 | 加重要度闸门，低分不写 | 需完整审计留档的场景另存原始日志 |
| 过期偏好持续误导 | 无 TTL，旧偏好永久生效 | 统计记忆条目年龄分布 | 给时效性记忆设 TTL 到期清理 | 法律/合规记录不能用 TTL 自动删 |
| 高价值事实被误删 | 淘汰只按新旧不看重要度 | 检查被淘汰条目里有无高分事实 | 重要度阈值以上受保护 | 保护过多会让库无法收缩，需平衡 |
| 摘要后丢关键约束 | 有损压缩把细节丢了 | 摘要与原始对话 diff | 关键约束置顶保留；原文入长期记忆 | 纯闲聊摘要丢细节可接受 |
| 冲突记忆并存导致答非所问 | 新旧偏好都写入未做更新 | 检索同一主题看是否返回矛盾条 | 写入时做「更新/合并」而非只追加 | 需保留历史演化的审计场景要留旧版 |
| 记忆无限增长、成本失控 | 只写不删 | 监控条目数与存储成本随时间变化 | TTL + 容量上限 + 定期压缩 | 冷存储归档可放宽上限 |

## 思考：什么样的信息该写入长期记忆，什么不该？

### 回答

判断标准是**跨会话复用价值**加**风险等级**，而不是「模型这轮用没用到」。该写入的：涉及安全/健康/身份的硬事实（过敏史、正在服用的药）、稳定的长期偏好（口味、常用地址）、需要跨会话延续的任务状态。不该写入或应低优先的：一次性意图（这次想吃什么）、寒暄、可随时重新获取的信息（当前时间、当前天气）、未经确认的猜测。一个反直觉但重要的点：**「模型这轮引用了」不等于「该长期记住」**——它可能只是本轮临时相关；反过来，一条这轮没用到的过敏史，可能是下一轮的救命信息。所以写入决策要看信息的内在属性（时效、风险、复用性），不能看单轮相关性。

### 面试精简表达

高风险、跨会话、稳定复用的写；一次性、可重取、未确认的不写；写入看信息属性，不看单轮是否用到。

## 思考：为什么遗忘和记忆同样重要？

### 回答

因为记忆系统的价值不在「存得多」而在「取得准」。只存不忘会带来三个恶化：一是**信噪比下降**，噪声淹没高价值事实，检索 Top-K 越来越难命中真正相关的；二是**过期信息误导**，用户早已改变的偏好如果不清理，会持续产生错误推荐；三是**成本失控**，无上限增长的库既贵又慢。遗忘的本质是「主动维护信噪比和时效性」——TTL 管时效，淘汰管容量，摘要管长度，更新管冲突。人脑的遗忘是特性不是 bug，Agent 也一样：一个不会忘的系统，最终会被自己的历史压垮。唯一的例外是合规和高风险硬事实，它们的「保留」由法律和安全决定，不受一般遗忘策略支配。

### 反例

不能把遗忘当成「省空间」的手段而对法律保留数据、未完成事务、高风险硬约束一并删除。TTL 只适用于「可过期的偏好」；对「必须留存」的记录，正确做法是移到合规的冷存储归档，而不是从系统里抹掉。误用遗忘策略删除法律保留数据，是比「记太多」更严重的事故。

## 机制推导：写入、更新、遗忘构成记忆的生命周期

把这一节的策略串起来，会发现每条记忆都有一条完整的生命周期，而不是「写进去就不管了」。一条记忆诞生时要过**写入闸门**（够不够格进来）；存在期间可能被**更新/合并**（用户改了偏好，新值覆盖或与旧值合并，而非并存产生冲突）；随时间推移触发**遗忘**（TTL 到期、容量淘汰、或被压缩成摘要）；最终或被删除、或归档到冷存储。

这条生命周期解释了为什么「只做存取」的记忆系统必然退化：它只实现了「诞生」，缺了「更新」和「死亡」。缺更新，冲突记忆并存，检索返回自相矛盾的结果；缺死亡，噪声和过期信息无限累积，信噪比持续恶化。成熟的记忆系统必须为每条记忆维护足够的元数据——来源、时间戳、重要度、TTL、上次命中时间——才能在生命周期的每个节点做出正确决策。这也和第 06 节要讲的真实系统一致：ChatGPT 的 dreaming 会在后台「更新、合并、删除」记忆，Claude memory tool 提供完整的增删改，本质都是在管理记忆的完整生命周期，而不只是追加。
