## 真实问题

回到导读里的用药咨询 Agent。周一，患者写下「我对青霉素过敏，正在服用华法林抗凝」，助手回答无误。周三，同一患者从另一个入口问「头痛能吃什么药」，助手推荐了含阿莫西林（青霉素类）的复方感冒药，还建议叠加阿司匹林——两条都与既往病史冲突。日志显示模型本身没有退化，问题是：周三这条会话是全新线程，模型完全看不到周一说过的话。团队第一反应是把系统提示改成「务必关注过敏史！」，结果下一个长期用药患者又中招，因为系统提示里根本没有这个患者的过敏史，模型「无中生有」不出来。

这就是「无记忆 Agent」的典型失败：**它不是答错了一道题，而是每次都从零开始，无法把上一次对话里获得的关键事实带到下一次。** 记忆系统要解决的，正是「让正确信息跨越会话边界、在需要时重新出现在模型眼前」。

## 现象与输入

把两次会话并排看，故障一目了然：
```text
会话 A（周一，线程 t1）
  用户：我对青霉素过敏，正在服用华法林抗凝
  助手：已记录，用药时会避开青霉素类并注意抗凝相互作用   ← 本轮正确

会话 B（周三，线程 t2，全新上下文）
  用户：头痛能吃什么药？
  助手：推荐复方阿莫西林 + 阿司匹林                        ← 看不到 A 的事实，踩双重禁忌
```
失败的根源不是「模型不聪明」，而是会话 A 的过敏事实没有被抽取成一条**跨会话、带来源**的长期记忆，也就无法在会话 B 生成前被检索回填。窗口「这次装得下」不代表「下次还看得见」。

## 原理：记忆到底解决了什么

Lilian Weng 的自主 Agent 综述用一个类比把记忆讲清楚了 [来源](https://lilianweng.github.io/posts/2023-06-23-agent/)：

| 人类记忆 | Agent 对应 | 工程载体 |
|---|---|---|
| 感觉记忆（瞬时） | 对原始输入的即时编码 | 输入的 embedding 表示 |
| 短期 / 工作记忆 | 上下文内学习（in-context） | 塞进上下文窗口的信息 |
| 长期记忆 | 可随时检索的知识库 | 外部向量存储 + 检索 |

这个类比的价值在于：它把「记忆」这个抽象词，拆成两个有明确工程对应物的东西——**上下文窗口（短期）**和**外部存储 + 检索（长期）**。没有记忆的 Agent 只有第一层，一旦会话结束或窗口溢出，一切归零。

但类比不能滥用。工程上必须清醒三点本质差异，否则会做出错误设计：
```text
差异一：人脑是「渐忘」，Agent 短期记忆是「硬截断」
   超出上下文窗口的部分不是模糊化，而是被一刀切掉——要么在窗口内，要么彻底消失。

差异二：人脑「存」「取」一体，Agent 是分离的两套系统
   写入向量库、从向量库检索是两个独立动作，中间隔着 embedding 模型、索引、相似度计算，每一环都可能出错。

差异三：人脑记忆会「重构」，Agent 向量记忆是「死」的
   存进去什么，取出来还是什么；除非你显式做摘要、更新、遗忘，它不会自我演化。
```
理解这三点，就不会天真地以为「把所有历史丢进向量库就万事大吉」。记忆系统的写入、更新、遗忘策略，每一个都需要显式设计——这正是后面四节的主题。

## 最小可运行演示

用几行代码就能对比「有记忆」与「无记忆」在同一查询下的差别。这里用一个极简的字典当长期记忆，演示「跨会话回填事实」这个核心动作：
```python
def answer_without_memory(question: str) -> str:
    # 无记忆：只能看到本轮问题，看不到任何既往事实
    return f"[无记忆] 针对『{question}』：可以试试常见止痛药如阿司匹林或复方感冒药。"

def answer_with_memory(question: str, longterm: dict) -> str:
    # 有记忆：生成前先取回该用户的硬事实
    facts = longterm.get("user-42", [])
    blocked = [f for f in facts if "过敏" in f or "华法林" in f]
    warn = f"（已命中安全事实：{'；'.join(blocked)}）" if blocked else ""
    return f"[有记忆] 针对『{question}』{warn}：需避开青霉素类，并注意与华法林的相互作用，建议就医确认。"

def main() -> None:
    longterm = {"user-42": ["用户对青霉素过敏", "用户正在服用华法林抗凝"]}
    q = "头痛能吃什么药？"
    print(answer_without_memory(q))
    print(answer_with_memory(q, longterm))

if __name__ == "__main__":
    main()
```
保存为 `why_memory.py`，运行 `python why_memory.py`。预期输出：
```text
[无记忆] 针对『头痛能吃什么药？』：可以试试常见止痛药如阿司匹林或复方感冒药。
[有记忆] 针对『头痛能吃什么药？』（已命中安全事实：用户对青霉素过敏；用户正在服用华法林抗凝）：需避开青霉素类，并注意与华法林的相互作用，建议就医确认。
```
这段代码刻意简陋：真实系统里 `longterm` 是一个向量库，`get` 是一次语义检索，而不是按 key 精确取。但它已经说清了记忆的本质动作——**在生成前，把与本轮相关的既往事实重新放回模型眼前**。第 05 节会把这个 `get` 换成真正的语义检索。

## 真实系统对应

**官方公开机制**：OpenAI 在 ChatGPT 中提供两种记忆——「saved memories（用户显式让它记住的事）」与「reference chat history（从历史对话中自动提炼的洞察）」，且明确说明「除非删除，saved memories 会一直被后续回答考虑」[来源](https://help.openai.com/en/articles/8590148-memory-faq)。Anthropic 的 memory tool 让模型在 `/memories` 目录下创建、读取、更新、删除文件，把学到的东西存到上下文窗口之外，并在后续会话读回 [来源](https://docs.anthropic.com/en/docs/agents-and-tools/tool-use/memory-tool)。**通用工程模式**：把「跨会话必须保留的事实」抽取成带来源的长期记忆，生成前检索回填。**教学参考实现**：上面的 `answer_with_memory` 只是演示，不代表任何产品内部的记忆管理逻辑。

## 生产踩坑

| 症状 | 根因 | 如何观测与复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| 跨会话丢失关键事实 | 事实只存在单次会话上下文，会话结束即丢弃 | 新开线程重问同一问题，检查模型输入是否含该事实 | 抽取为跨会话长期记忆，生成前检索回填 | 一次性、无复用价值的闲聊不必长期化 |
| 反复询问用户已提供的信息 | 无长期记忆或检索没命中 | 统计「重复提问率」，回放实际检索结果 | 建立用户档案 + 语义检索；命中失败要打日志 | 需要实时确认的高风险信息应主动复核而非默认相信旧值 |
| 系统提示越写越长仍失效 | 把「个体事实」误当「全局规则」写进提示 | 检查提示里是否混入了具体用户数据 | 全局规则进系统提示，个体事实进长期记忆 | 少量真正全局的硬约束仍应在提示中显式声明 |
| 长任务中期忘记早期约束 | 早期约束被后续对话挤出窗口 | 注入 30 段噪声后回放，看约束是否仍在输入中 | 抽取为固定事实，每轮组装时置顶 | 未经确认的临时偏好不应固定化 |

## 思考：既然可以把所有历史都塞进超长上下文，为什么还需要独立的记忆系统？

### 回答

三个理由，缺一不可。第一，**跨会话与跨用户的知识本就无法靠单次上下文承载**——今天的会话再长，也装不下这个用户三个月前在另一条线程里说的过敏史，除非有一个持久化的外部存储把它接住。第二，**成本与延迟**：把全部历史每轮重发，输入随时间单调增长，注意力计算是序列长度的二次方关系，越长越贵越慢。第三，**有效召回会打折**：关键信息埋在超长上下文中段时，模型召回率明显下降（lost in the middle）。长窗口降低了对记忆系统的依赖，但没有取消它——它解决「这次能否放下」，记忆系统解决「以后能否再次找到、该不该找回、找回哪一条」。

### 面试精简表达

长上下文是「一次能摊多大」，记忆系统是「跨时间跨会话的存取与遗忘」；前者是工作台面积，后者是仓库加取货流程，两者互补而非替代。

## 事故回放：约束如何在一次线程切换中蒸发

把用药事故按责任边界拆开，会得到四个独立问题，每个都对应本章后续一节。**写入层**：周一的过敏信息从未被抽取成一条跨会话记忆，它随会话 A 的窗口一起消失（第 04 节）。**存储层**：系统没有区分「该长期保留的硬事实」和「一次性闲聊」，所以即便想存也不知道存什么（第 03、04 节）。**检索层**：周三没有任何机制在生成前按语义把过敏史取回来（第 03、05 节）。**执行层**：即便模型看到了事实，最终也应有一道确定性的用药禁忌校验作兜底，而不是完全信任模型措辞（第 07 节）。

润色系统提示只可能碰运气改善「执行层」的一小部分，完全无法弥补前三层的缺失。这说明一个反复出现的工程规律：**当 Agent「忘事」时，先别急着换模型或改提示，而要问「这条信息该不该记、记在哪、生成前有没有被取回」。** 定位到具体的层，修复才有的放矢。

## 从故障到需求：记忆系统的四个必答问题

这次事故最终逼出记忆系统的四个必答问题，它们构成本章的骨架：

- **该不该记（写入策略）**：过敏史该记，「今天想吃牛排」这种一次性意图不必长期化。写入需要一道闸门，否则记忆库会被噪声撑爆。
- **记在哪（短期 vs 长期、向量 vs 结构化）**：本轮意图放短期窗口；跨会话事实放长期存储；精确字段用结构化，语义文本用向量。
- **怎么取回（检索）**：不能只靠字面相关度，必须叠加「重要度」和「近因」，让救命的硬事实即便措辞不匹配也能被召回。
- **什么时候忘（遗忘策略）**：过期偏好用 TTL 清理，容量超限用淘汰，长历史用摘要压缩；但法律保留和高风险硬事实不能被随意删除。

这四个问题不是抽象分类，而是这次事故里四个真实的失败点。接下来每一节都在回答其中一个，并给出可运行的代码与可核对的输出。
