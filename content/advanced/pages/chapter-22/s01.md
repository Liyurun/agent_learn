## 真实问题

回到导读里那场终面。事后复盘时，面试官给出的原话是：「他画了满满一白板，但我不知道他从哪开始、要保护什么、又准备牺牲什么。」这句话点破了系统设计题最大的误区——**候选人以为面试官在考「你认识多少组件」，其实面试官在考「你能不能把一个开放问题，收敛成一条有头有尾、有边界有取舍的作答路径」**。开放题之所以难，正是因为它没有标准答案：你可以用单 Agent，也可以用多 Agent；可以强检索，也可以强推理。没有一套骨架，你就会像那位候选人一样，一头扎进组件细节，把 20 分钟花在最不拉分的地方。这一节要解决的就是这个问题：给你一套「拿到任何题都能套」的五步骨架，让你的作答从「一堆零件」变成「一条能被面试官顺着听下去的主线」。

## 原理：五步法是「立项到上线」的缩影

系统设计题的五步法不是凭空发明的答题模板，它是一个真实项目从立项到上线的压缩版。每一步都对应工程中一个不可省略的阶段，而且**前一步的产物就是后一步的输入**：
```text
1. 澄清需求   → 产出：功能 + 非功能需求清单（谁用/规模/延迟/红线/权限/边界）
2. 顶层架构   → 输入上一步的约束，产出：组件与数据流图（单/多 Agent、工具、记忆）
3. 核心流程   → 输入架构，产出：一条主链路的逐步流转（含失败分支）
4. 工程考量   → 输入流程，产出：评估/可观测/护栏/成本延迟的落地点
5. 权衡取舍   → 输入全局，产出：诚实交代牺牲了什么、为什么可接受
```
这个顺序不能乱。没澄清需求就画架构，等于闭卷答题——你不知道要不要权限过滤，就没法决定向量库要不要带元数据；没定架构就谈工程，等于空中楼阁——评估和护栏没有组件可以挂靠。OpenAI《A practical guide to building agents》强调的落地顺序与此高度一致：先确认这个问题是否真的需要 Agent、再选模型和工具、再设计编排、最后加护栏 [来源](https://cdn.openai.com/business-guides-and-resources/a-practical-guide-to-building-agents.pdf)。这与五步法「先想清楚再动手、护栏不能少」是同一套工程直觉。

### 为什么第 1 步和第 5 步最拉分

五步里，中间三步（架构、流程、工程）是「显功夫」，大多数认真准备过的候选人都能讲一些；而第 1 步澄清和第 5 步权衡是「暗功夫」，恰恰最能区分「做过系统的人」和「只看过教程的人」。**上来就画架构、不澄清需求**是新手的典型表现，因为教程里的例子都是「已经定义好的题」，从不教你先反问；**只讲方案、不谈权衡**说明缺乏生产经验，因为真实系统里没有免费的午餐，任何决策都在某条轴上做了牺牲。把这两步做扎实，你的作答立刻就从「合格」升到「亮眼」。

## 最小可运行演示

下面把五步法写成一个可运行的「作答评分器」：给它一份作答（五步各填了什么），它按「五步是否齐全 + 澄清是否挂钩了决策 + 流程是否带失败分支 + 权衡是否诚实」四条打分。这是**教学参考实现**，用来演示「一份好答案的结构长什么样」，不代表任何真实评测标准。
```python
"""第22.1节：系统设计题五步法作答的结构化自检评分器（纯 Python，无需 API Key）。"""
from dataclasses import dataclass, field


@dataclass
class Answer:
    clarify: list = field(default_factory=list)     ## 澄清出的约束
    clarify_links: dict = field(default_factory=dict)  ## 约束 -> 对应的设计决策
    arch: str = ""
    flow_has_failpath: bool = False                 ## 核心流程是否带失败分支
    eng: list = field(default_factory=list)         ## 工程四件套覆盖了哪些
    tradeoff_honest: bool = False                   ## 是否诚实说了牺牲


ENG_MUST = {"评估", "可观测", "护栏", "成本延迟"}


def score(a: Answer) -> dict:
    detail = {
        "澄清充分(>=4条)": len(a.clarify) >= 4,
        "澄清挂钩决策": len(a.clarify_links) >= 2,
        "画了架构": bool(a.arch),
        "流程带失败分支": a.flow_has_failpath,
        "工程四件套齐全": ENG_MUST.issubset(set(a.eng)),
        "权衡诚实": a.tradeoff_honest,
    }
    passed = sum(1 for v in detail.values() if v)
    return {"通过项": passed, "满分": len(detail), "明细": detail}


def run() -> None:
    good = Answer(
        clarify=["谁用", "规模QPS", "延迟", "质量红线", "权限"],
        clarify_links={"质量红线=不能编造": "无依据不作答+附引用",
                       "有权限差异": "检索前按部门元数据过滤"},
        arch="单Agent + Agentic RAG",
        flow_has_failpath=True,
        eng=["评估", "可观测", "护栏", "成本延迟"],
        tradeoff_honest=True,
    )
    bad = Answer(arch="一堆组件", eng=["功能实现"])  ## 跳过澄清与权衡的新手答案
    for name, a in [("优秀作答", good), ("新手作答", bad)]:
        r = score(a)
        print(f"[{name}] 通过 {r['通过项']}/{r['满分']}")
        for k, v in r["明细"].items():
            print(f"    {'OK ' if v else 'MISS'} {k}")


if __name__ == "__main__":
    run()
```
保存为 `s1_five_steps.py`，运行 `python s1_five_steps.py`。预期输出：
```text
[优秀作答] 通过 6/6
    OK  澄清充分(>=4条)
    OK  澄清挂钩决策
    OK  画了架构
    OK  流程带失败分支
    OK  工程四件套齐全
    OK  权衡诚实
[新手作答] 通过 1/6
    MISS 澄清充分(>=4条)
    MISS 澄清挂钩决策
    OK  画了架构
    MISS 流程带失败分支
    MISS 工程四件套齐全
    MISS 权衡诚实
```
这段代码的价值不在于「算出优秀作答得 6 分」——那是构造出来的；价值在于**把「好答案」的结构显式化**：不是看你画了多少组件，而是看澄清是否挂钩了决策、流程是否带失败分支、权衡是否诚实。新手作答之所以只得 1 分，正因为它把全部精力砸在「画了架构」这唯一一项上，而这一项恰恰是最不稀缺的。

## 真实系统对应

**官方公开机制**：OpenAI《A practical guide to building agents》把落地拆成「确认是否需要 Agent → 选模型与工具 → 设计编排 → 加护栏」的顺序，与五步法「先想清楚、护栏不能少」一致 [来源](https://cdn.openai.com/business-guides-and-resources/a-practical-guide-to-building-agents.pdf)；Anthropic《Building Effective Agents》主张从简单可组合模式起步、复杂度必须由收益证明，对应五步里的「权衡取舍」这一步的克制精神 [来源](https://www.anthropic.com/engineering/building-effective-agents)。**通用工程模式**：把开放问题收敛成「需求→架构→流程→工程→权衡」的答题骨架，是可迁移到任何系统设计场景（不限于 Agent）的方法论。**教学参考实现**：上面的评分器权重与判据是为讲清「好答案的结构」而构造，不代表任何公司的面试评分卡。

值得注意的是，业界的落地实践也印证了「先想清楚再动手」的价值——真正跑通生产的团队，都会先把「这个问题该不该上 Agent」问清楚，而不是默认上最复杂的架构。这一点在 Anthropic 和 OpenAI 两份指南里被反复强调 [来源](https://www.anthropic.com/engineering/building-effective-agents)[来源](https://cdn.openai.com/business-guides-and-resources/a-practical-guide-to-building-agents.pdf)。

## 生产踩坑

| 症状 | 根因 | 如何观测与复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| 上来就画架构，被追问三次全卡壳 | 跳过澄清，约束没搞清 | 回看作答，看开头 2 分钟是否在提问 | 强制前 2 分钟只做澄清，问满六项 | 面试官明确说「需求已给死」时可略 |
| 组件画满一白板却讲不清一次请求 | 有架构无流程，系统不会「活」 | 让人复述「一次请求怎么走」，卡住即缺流程 | 选一条主链路逐步走一遍，带失败分支 | 纯概念题不要求画流程 |
| 全程不提评估/护栏/成本 | 缺生产经验，只会讲功能 | 数一数作答里工程四件套提了几个 | 收尾固定抛「评估/可观测/护栏/成本」四问 | 一次性 demo 可弱化工程化 |
| 声称「这个方案很完美」 | 没有权衡意识 | 追问「缺点是什么」时答不上 | 每题至少讲一条真实牺牲及其理由 | 无 |
| 五步顺序讲乱，逻辑跳跃 | 没把五步当有依赖的流水线 | 录音回听，看步骤有无来回跳 | 严格按 1→5 推进，前一步产物喂后一步 | 无 |
| 澄清问了但没用上 | 澄清与设计脱钩，为问而问 | 检查每个澄清是否对应一处架构决策 | 澄清后显式说「因为X，所以我在架构里做Y」 | 无 |

## 思考：拿到一道完全没接触过的设计题（比如「设计一个 AI 法律合同审查 Agent」），如何用五步法在 30 秒内定好作答框架？

### 回答

关键在于五步法给了你一个「不依赖领域知识」的脚手架，哪怕对法律一窍不通，也能立刻搭出作答骨架。第一步澄清，套六问清单：谁用（律师还是普通人？决定专业度红线）、规模（每天审多少份合同？决定要不要批处理）、延迟（要秒回还是可以等？合同审查通常可异步）、质量红线（漏审一个风险条款的后果多严重？法律场景通常接近零容忍，直接推出「必须附条款出处、拿不准就标记人工复核」）、安全权限（合同含商业机密，是否要脱敏、要不要权限隔离）、边界（这一版只审中文标准合同，不做诉讼预测）。光是问完这六项，你就已经比「直接画架构」的人强了。第二步架构，套四层：接入层收合同文件、编排层判断是「逐条抽取风险」还是「自由问答」、能力层挂「条款检索 + 风险规则库 + 引用工具」、数据层放合同解析结果和法规库。第三步流程，走一条主链路：上传合同→切分条款→逐条比对风险规则→拿不准的标记人工复核→输出带出处的风险清单，失败分支是「解析失败就退回让用户确认格式」。第四步工程：评估用「专家标注好的合同风险集」测召回率，护栏是「无出处不下结论」，可观测记录每条风险命中了哪条规则，成本上长合同走 map-reduce 分条并行。第五步权衡：我牺牲了「全自动出结论」，改成「高风险项一律人工复核」，因为法律场景一次漏判的代价远高于慢一点。你看，全程没用到任何法律专业知识，五步法的脚手架就把一道陌生题撑成了完整作答——这正是它的威力：**它管的是「怎么答」，不是「答什么」**。

### 面试精简表达

五步法是不依赖领域知识的脚手架：六问澄清定红线（法律=近零容忍→附出处+人工复核）、四层套架构、主链路带失败分支、工程四件套挂上去、权衡诚实说牺牲。陌生题也能 30 秒搭出骨架，因为它管「怎么答」而非「答什么」。

## 事故回放：五步法如何救回那场「被问崩」的终面

把开头那场终面用五步法重放一遍，就能看清失分点是如何被逐个补上的。原版：候选人 0 分钟开始画向量库，20 分钟画完，被三连问击穿。五步法版：0–2 分钟先澄清，问出「要按部门权限过滤」「金融相关问答零容忍」两条硬约束，并当场说「因为要权限隔离，所以我的向量库必须带部门元数据；因为不能编造，所以我要做无依据不作答」——这一步就把面试官后来想追问的三个问题，提前变成了自己的设计理由。2–8 分钟画四层架构，边画边说每层职责。8–14 分钟走一次问答流程，主动带上「检索为空怎么办」的失败分支。14–18 分钟抛工程四件套，特别强调「幻觉率」是这个系统的头号指标。18–20 分钟收一条权衡：「我选单 Agent 牺牲了多跳推理，换来简单可追溯，符合准确优先场景。」同样是 20 分钟，同样的人，作答质量天差地别——差别不在知识，而在**有没有一条把开放问题收敛住的主线**。这就是本章要交给你的东西。
