## 真实问题

两道题，两个反向的翻车现场。**会议纪要那道**：某团队想做一个「会议纪要 Agent」，把一场 90 分钟、转写约 3 万字的会议整理成摘要、决议、待办。他们的第一版直接把 3 万字全塞进一次模型调用，结果前半段的决议记得清清楚楚，后半段的待办几乎全漏了，还时不时把 A 说的话安到 B 头上——这是典型的「长文本一次喂、注意力被稀释」。**多 Agent 客服那道**：另一个团队一听「客服要处理订单、物流、退换、推荐这么多领域」，条件反射地上了多 Agent，结果「订单」和「物流」两个 Agent 老被路由搞混，用户问个物流被丢给订单 Agent，转来转去还得重说一遍需求。这两道题放一起讲，正是要回答系统设计题里最关键的一类判断——**到底该不该上 Agent，该不该上多 Agent**。

## 例题三：会议纪要 Agent（批处理 / 异步型）

### 原理：审题与逐步作答（会议纪要）

**审题**：把一段会议录音/转写文本，自动整理成结构化纪要（摘要、决议、待办、责任人）。核心诉求是**长文本处理 + 结构化输出**，而且它是**离线批处理**，对实时性要求低。

**第 1 步 · 澄清需求**：

- 输入是什么？（已转写的文本，还是要先做语音转写 ASR（Automatic Speech Recognition，自动语音识别）？假设已有转写文本，聚焦纪要生成）
- 输出格式？（摘要 + 决议 + 待办清单 + 责任人 + 时间点，结构化）
- 会议多长？（可能一两小时，转写文本远超单次上下文窗口——这是核心约束）
- 时效要求？（会后几分钟内出即可，**可异步**，这决定了架构可以走批处理而非实时）

**第 2 步 · 顶层架构**：这题的关键判断是「**它更像 Workflow（工作流）而不是 Agent**」——流程相对固定（分段 → 各段处理 → 汇总），不需要模型动态决定流程。所以用**固定编排的工作流**更合适，能用 Workflow 就别硬上 Agent。
```text
转写文本 ──▶ 分段(chunk) ──▶ 逐段处理(并行) ──▶ 汇总合并 ──▶ 结构化纪要
                              │ 每段抽取：            │ 去重、合并同类项
                              │ 要点/决议/待办        │ 生成全局摘要
                              └───────────────────────┘
                                    ▼
                              结构化输出校验(schema)
```
**第 3 步 · 核心流程（带失败分支）**：

1. 把长转写按语义/时间切成多个 chunk（解决上下文超长问题）；
2. 对每个 chunk 并行调用模型，抽取该段的要点、决议、待办（map 阶段）；某段处理失败时跳过并标注「此段未能整理」，不让整个任务崩；
3. 汇总各段结果，去重、合并、消解冲突，生成全局摘要和统一的待办清单（reduce 阶段）；
4. 用 schema（结构模式）校验输出结构（如待办必须有「负责人 + 事项」），不合规则重试或修正。

**为什么用 map-reduce 而不是「一次性喂全文」**：会议转写常常几万字，超出单次上下文或即便塞得进也会导致注意力稀释、成本飙升、遗漏后半段（正是开头那起「后半段全漏」的成因）。map-reduce 把长文拆成小段分别处理再汇总，既绕过上下文限制，又能并行加速。这是长文本处理的经典套路，值得主动讲出来。

**第 4 步 · 工程考量**：

- **评估**：准备一批「人工整理好的纪要」做参考，用 LLM-as-a-judge（以大模型为裁判）或人工对比测「要点覆盖率、待办准确率」；
- **结构化护栏**：输出必须过 schema 校验，保证下游系统能消费；
- **成本**：并行处理提升速度但并发太多会撞限流，要控制并发度；对超长会议按段计费监控 token；
- **失败降级**：某段处理失败时跳过并标注，而不是整个任务失败。

**第 5 步 · 权衡**：

> 我选固定 Workflow 而非自主 Agent——牺牲了「动态灵活性」（比如没法自主决定要不要额外查资料），但换来**流程可控、成本可预测、结果稳定**。会议纪要是一个流程明确的任务，稳定和可预测比灵活更重要。map-reduce 分段则是在「上下文限制/成本」和「全局连贯性」之间做权衡：分段可能损失一点跨段连贯性，所以要在 reduce 阶段专门做一次全局整合来补救。

### 最小可运行演示（会议纪要 map-reduce）

下面用纯 Python 模拟 map-reduce：把长转写切段、逐段抽取待办（map）、汇总去重（reduce），并演示「单段失败跳过不影响整体」。这是**教学参考实现**，不联网、不需要 API Key。
```python
"""第22.5节：会议纪要的 map-reduce 分段抽取与降级（纯 Python，无需 API Key）。"""

TRANSCRIPT = [
    "张三：这个需求下周一前上线。李四负责后端。",
    "",   ## 模拟一段空/损坏的转写，map 阶段应跳过
    "王五：测试用例由我补，周三前完成。",
]


def map_extract(chunk: str, idx: int) -> dict:
    """map：从一段抽取待办；失败(空段)返回降级标记。"""
    if not chunk.strip():
        return {"seg": idx, "ok": False, "todos": [], "note": "此段未能整理"}
    todos = []
    for who, what in [("李四", "负责后端"), ("王五", "补测试用例")]:
        if who in chunk:
            todos.append({"owner": who, "task": what})
    return {"seg": idx, "ok": True, "todos": todos, "note": ""}


def reduce_merge(results: list) -> dict:
    """reduce：合并各段待办、去重、汇报降级段。"""
    todos, failed = [], []
    for r in results:
        if r["ok"]:
            todos.extend(r["todos"])
        else:
            failed.append(r["seg"])
    ## 按 owner 去重
    seen, dedup = set(), []
    for t in todos:
        if t["owner"] not in seen:
            seen.add(t["owner"])
            dedup.append(t)
    return {"待办": dedup, "未整理段": failed}


def run() -> None:
    mapped = [map_extract(c, i) for i, c in enumerate(TRANSCRIPT)]
    print("最终纪要：", reduce_merge(mapped))


if __name__ == "__main__":
    run()
```
保存为 `s5_minutes.py`，运行 `python s5_minutes.py`。预期输出：
```text
最终纪要： {'待办': [{'owner': '李四', 'task': '负责后端'}, {'owner': '王五', 'task': '补测试用例'}], '未整理段': [1]}
```
第 1 段（空段）被 map 阶段识别为「未能整理」并跳过，reduce 阶段把它标注在「未整理段」里，其余两段的待办正常合并去重——整个任务没有因为一段损坏而崩溃。这正是 map-reduce 相比「一次喂全文」的两大优势：**绕过上下文限制**、**单段失败可降级**。

## 例题四：多 Agent 智能客服系统（多 Agent 编排型）

### 原理：审题与逐步作答（多 Agent 客服）

**审题**：电商客服，用户咨询订单、物流、退换货、商品推荐等。核心诉求是**多领域 + 需要调用真实业务系统 + 高并发**。这是少数**真正适合多 Agent**的场景。

**第 1 步 · 澄清需求**：

- 业务领域有哪些？（订单、物流、售后/退换、商品咨询——领域边界清晰，这是能用多 Agent 的信号）
- 规模？（C 端高并发，峰值 QPS 可能上千，延迟要求秒级）
- 权限与安全？（退款、改地址是高危操作，需要校验和人工兜底）
- 转人工的条件？（Agent 搞不定时怎么优雅移交人工客服）

**第 2 步 · 顶层架构**：中心化路由的多 Agent（Manager/Router + 专职 Agent）。
```text
用户 ──▶ 路由 Agent（判断意图，分发）
              ├──▶ 订单 Agent   → 订单系统 API
              ├──▶ 物流 Agent   → 物流查询 API
              ├──▶ 售后 Agent   → 退换/退款 API（高危，需护栏）
              └──▶ 商品 Agent   → 商品/推荐 API
                        │
                  转人工兜底（置信度低/高危/用户要求）
```
**为什么这里适合多 Agent**：这个场景同时命中了「明确的多领域边界」和「权限隔离需求」（只有售后 Agent 能碰退款）。领域清晰、工具各不相同、还需要权限隔离，正是多 Agent 优于单 Agent 的典型情形。面试时一定要显式说出「我为什么在这里选多 Agent」，而不是默认多 Agent 高级——开头那起「订单物流老路由错」的翻车，恰恰是因为拆得不合理，而不是因为不该用多 Agent。

**第 3 步 · 核心流程（一次退款咨询，带失败分支）**：

1. 用户说「我要退款」，**路由 Agent** 判断意图为「售后」，分发给售后 Agent，并把必要上下文（用户 ID、订单信息）打包传递；路由置信度低时不硬分，转人工；
2. 售后 Agent 调用订单 API 核实订单状态、是否符合退款条件；
3. 退款是**高危操作**，触发护栏：金额超阈值/状态异常时转人工审批，否则走自动退款并记录（幂等键防重复退款）；
4. 完成后回传结果给用户；若中途置信度低或用户不满，**优雅转人工**。

**第 4 步 · 工程考量**：

- **路由准确率**：这是多 Agent 系统的头号指标。优化路由 prompt、给每个 Agent 清晰的职责描述和 few-shot（少样本）例子，记录并定期分析误路由案例；
- **上下文传递**：handoff（交接）时要打包完整上下文，避免「转过去后信息丢了、用户要重说一遍」；
- **护栏**：退款/改地址等写操作要金额阈值、幂等、人工审批兜底；
- **高并发**：无状态 Agent + 会话状态外置（存 Redis 等），便于水平扩展；对下游业务 API 做限流、超时、缓存；
- **评估**：分领域测意图路由准确率、任务完成率、转人工率。

**第 5 步 · 权衡**：

> 我用多 Agent 换来了**职责清晰、权限隔离、易于分团队维护**，代价是引入了**路由错误和上下文传递**这两个新问题，以及更高的整体延迟。对客服这种领域边界清晰、且退款等操作需要权限隔离的场景，这个代价值得付。但我不会把 Agent 拆得太细——如果「订单」和「物流」经常被路由混淆，我会考虑合并，因为过细的拆分反而让路由更难。

### 最小可运行演示（客服路由 + 高危兜底）

下面用纯 Python 模拟客服系统的两条核心机制：**意图路由 + 置信度兜底**、**退款高危转人工审批**。这是**教学参考实现**，不联网、不需要 API Key。
```python
"""第22.5节：客服意图路由 + 置信度兜底 + 退款高危审批（纯 Python，无需 API Key）。"""

ROUTE_RULES = {
    "订单": ["订单", "下单", "什么时候发"],
    "物流": ["物流", "快递", "到哪了"],
    "售后": ["退款", "退货", "换货"],
    "商品": ["推荐", "有没有", "参数"],
}
REFUND_THRESHOLD = 300.0   ## 超过此金额的退款强制人工审批


def route(text: str) -> tuple:
    """返回 (意图, 命中词数)；命中数就是简化的置信度。"""
    best, score = "转人工", 0
    for intent, kws in ROUTE_RULES.items():
        hit = sum(1 for k in kws if k in text)
        if hit > score:
            best, score = intent, hit
    return best, score


def handle(text: str, amount: float = 0.0) -> str:
    intent, conf = route(text)
    if conf == 0:                       ## 置信度为 0：不硬分，转人工
        return "路由置信度低 -> 优雅转人工"
    if intent == "售后" and amount > REFUND_THRESHOLD:
        return f"售后：退款 {amount} 元超阈值 -> 转人工审批（幂等键防重复）"
    return f"路由到[{intent}] Agent 处理（置信度={conf}）"


def run() -> None:
    print(handle("我的快递到哪了"))
    print(handle("我要退款", amount=328.0))    ## 高危：超阈值
    print(handle("我要退款", amount=50.0))     ## 小额：可自动
    print(handle("随便聊聊"))                  ## 无命中：转人工


if __name__ == "__main__":
    run()
```
保存为 `s5_router.py`，运行 `python s5_router.py`。预期输出：
```text
路由到[物流] Agent 处理（置信度=1）
售后：退款 328.0 元超阈值 -> 转人工审批（幂等键防重复）
路由到[售后] Agent 处理（置信度=1）
随便聊聊 -> 优雅转人工
```
注意第二行：328 元退款超过阈值，即便意图路由正确，也不自动执行，而是转人工审批——这就是高危写操作的兜底。最后一行：无任何命中词时不硬猜，而是优雅转人工——这就是置信度兜底，避免把用户丢给一个错误的 Agent。

## 真实系统对应

**官方公开机制（会议纪要）**：LangGraph 的 Send API 支持在运行时动态 fan-out（扇出）出多个并行分支、再 fan-in（扇入）汇总，正是 map-reduce 模式在图编排里的实现，对应本题「分段并行处理再汇总」的架构 [来源](https://langchain-ai.github.io/langgraph/concepts/multi_agent/)。**官方公开机制（多 Agent 客服）**：LangGraph 文档把多智能体拓扑分为 supervisor（监督者集中路由，中心协调者接收每条消息、分类意图、路由到专家、专家答完控制权回到 supervisor）与 network（对等 handoff），本题的中心化路由正对应 supervisor 拓扑 [来源](https://langchain-ai.github.io/langgraph/concepts/multi_agent/)；OpenAI Agents SDK 区分 handoffs（去中心化交接）与 manager/agents-as-tools（中心化编排），并支持敏感工具的人工审批中断/恢复，对应本题「退款转人工审批」[来源](https://github.com/openai/openai-agents-python/blob/main/docs/agents.md)[来源](https://openai.github.io/openai-agents-python/human_in_the_loop/)。真实落地规模上，Klarna 官方新闻稿称其 AI 助手上线首月处理约 230 万次对话、约占客服对话三分之二 [来源](https://www.klarna.com/international/press/klarna-ai-assistant-handles-two-thirds-of-customer-service-chats-in-its-first-month/)（此类口径随时间调整，以官方当前为准），说明客服是 Agent 落地最成熟的场景之一。**通用工程模式**：map-reduce 分段、schema 校验、单段降级、置信度兜底、handoff 打包上下文、幂等键、无状态 + 状态外置，都是可迁移的工程做法。**教学参考实现**：上面两段 mock（关键词路由、金额阈值、分段抽取）是为讲清机制而构造，真实系统会用模型分类 + 向量检索 + 完整业务 API，机制一致但实现更重。

## 生产踩坑

| 症状 | 根因 | 如何观测与复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| 会议后半段待办几乎全漏 | 长文一次喂，注意力稀释 | 对比全文一次喂 vs 分段的召回 | 用 map-reduce 分段抽取再汇总 | 短会议（几千字）可一次喂 |
| 分段后跨段决议对不上 | 只 map 不认真 reduce | 检查跨段冲突是否被消解 | reduce 阶段做全局整合与去重 | 无跨段依赖的会议可略 |
| 一段转写损坏整个任务崩 | 无单段降级 | 注入一段空/乱码转写 | 单段失败跳过并标注未整理 | 无 |
| 纪要格式乱，下游没法用 | 无结构化校验 | 用 schema 校验输出结构 | 输出过 schema，不合规则重试 | 纯给人看的摘要可放宽 |
| 硬上多 Agent，路由老出错 | 领域拆得过细/不该拆 | 统计各意图误路由率 | 边界不清就合并，够用先单 Agent | 领域清晰+需隔离时该拆 |
| 转专家后用户要重说需求 | handoff 没传上下文 | 看转接后上下文是否完整 | handoff 打包用户 ID/订单/历史 | 无 |
| 模型一句话「承诺」退款 | 高危写操作没审批 | 用大额退款请求测试 | 超阈值转人工 + 幂等键防重复 | 只读咨询无需审批 |
| 高并发下会话状态错乱 | Agent 有状态难扩展 | 压测下多会话串味 | 无状态 Agent + 状态外置存储 | 低并发内部工具可略 |

## 思考：同样是「领域很多」，为什么会议纪要不该上多 Agent，客服却该上？

### 回答

关键区别不在「领域多不多」，而在「流程是不是需要模型动态决策」和「领域之间是不是需要权限隔离」这两个维度。会议纪要虽然要抽取摘要、决议、待办、责任人好几类信息，但它的流程是**完全固定**的——永远是「切段→逐段抽取→汇总校验」，不存在「模型需要临场决定下一步做什么」的分支，也不存在「待办抽取 Agent 不能碰摘要」这种权限隔离需求。流程固定、无需隔离，就意味着一个 Workflow（甚至一个带结构化输出的单次调用循环）就能干净利落地搞定，上多 Agent 只会平白增加路由损耗和维护复杂度，是典型的过度设计。反观客服，它的领域之间是**真正分叉**的：用户这句话到底是问订单还是问物流，需要模型临场判断意图并路由（动态决策），而且「只有售后 Agent 能调退款 API」这种权限隔离是硬需求（订单 Agent 绝不能有退款权限）。动态路由 + 权限隔离这两个信号同时命中，多 Agent 才真正物有所值。所以我判断该不该上多 Agent，从来不看「领域数量」这个表面指标，而看「是否需要动态决策流程 + 是否需要按领域做权限隔离」这两个本质信号——会议纪要两个都不命中，客服两个都命中，选型自然相反。至于开头那起「客服路由老出错」的翻车，问题不在「不该用多 Agent」，而在「拆得太细」，把本可合并的订单和物流硬拆开，反而制造了路由难题——这提醒我们，即便该用多 Agent，粒度也要恰当。

### 面试精简表达

判断标准不是「领域多少」，是「要不要动态决策流程 + 要不要权限隔离」。会议纪要流程固定、无需隔离→用 Workflow；客服要动态路由意图、售后独占退款权限→用多 Agent。且即便用多 Agent 也别拆太细，订单物流常混淆就该合并。

## 优化前后对比：两道题的「翻车→修正」

**会议纪要**：优化前，3 万字一次喂给模型，后半段待办漏了一大半，还张冠李戴——注意力被长文本稀释。优化后，切成 chunk 并行 map 抽取、reduce 汇总去重、schema 校验，单段损坏也只标注不崩溃，召回和稳定性都上了一个台阶。**多 Agent 客服**：优化前，一听「领域多」就把订单、物流、售后、商品拆成四个 Agent，结果订单物流老路由错、转接还丢上下文。优化后，先用「动态决策 + 权限隔离」两信号确认该用多 Agent，再把易混淆的订单物流适当合并降低路由难度，handoff 打包完整上下文，退款超阈值转人工审批加幂等键。两道题一正一反，共同印证本章的选型心法：**Workflow 能解决的别硬上 Agent，单 Agent 能解决的别硬上多 Agent，即便该用多 Agent 也要把粒度拆得恰当**——选型判断力，才是设计题真正的分水岭。
