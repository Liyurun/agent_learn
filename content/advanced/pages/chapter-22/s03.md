## 真实问题

某公司内部知识库问答 Agent 上线两周后收到一条投诉：市场部一名新员工问「我们的年终奖计算规则是什么」，系统给出了一段看起来很专业、有具体系数的答案——但那套规则是它**编造**的，公司根本没有这条政策。更糟的是，另一名员工问「隔壁研发团队的绩效考核标准」，系统直接把一份**本该只有研发主管可见**的保密文档内容念了出来。复盘时才发现：这个知识库问答系统既没有「无依据不作答」的护栏，也没有按部门做权限过滤——它把「能检索到」等同于「可以回答」，把「模型说得像」等同于「事实正确」。这道题就是要设计一个**不会编造、不会越权**的企业知识库问答 Agent，它的核心诉求写在脸上：**准确、不能编造、按权限可见**。

## 原理：审题与逐步作答

**审题**：企业内部用，员工问政策、流程、技术文档。核心诉求是**准确、不能编造**。下面用五步法逐步作答。

### 第 1 步 · 澄清需求

- 用户量：全公司几千人，QPS（Queries Per Second，每秒查询数）不高但要求准确；
- 数据：内部文档（Confluence、PDF、代码库），会持续更新；
- 红线：**绝不能编造答案**，答不了要如实说「未找到」；
- 权限：不同部门文档可见范围不同——**这是决定架构的关键约束**。

按本章第 2 节的「约束→决策」映射：「绝不能编造」推出「无依据不作答 + 输出必附引用」；「有权限差异」推出「检索前按用户身份做元数据过滤」。这两条约束在后面会各自变成架构里一个硬性组件。

容量与数据估算也要口算一遍：几千员工、假设每人每天问 5 次，日请求约上万次，峰值 QPS 个位数——**这是个低 QPS、高准确要求的系统**，说明瓶颈不在扛并发，而在检索质量和防幻觉。文档量假设几万到几十万篇，向量化后需要一个能做元数据过滤的向量库。把这些数字口算出来，能立刻让面试官知道你抓住了系统的主要矛盾——「准确优先」而非「高并发优先」。

### 第 2 步 · 顶层架构

单 Agent 足够（单一领域），核心是 **Agentic RAG（Retrieval-Augmented Generation，检索增强生成）**——即由模型自主决定检索什么、要不要多检索几轮，而非固定检索一次。
```text
用户提问 ──▶ 权限过滤 ──▶ 知识 Agent（Agentic RAG）──▶ 答案 + 引用来源
                              │
                    ┌─────────┴─────────┐
                    ▼                   ▼
              向量库(带部门元数据)   原文档存储
```
### 第 3 步 · 核心流程（一次问答，带失败分支）

1. 用户提问，先根据用户身份做**权限过滤**（只检索他有权看的文档）；若过滤后无任何可见的相关文档，回答「无权限/未找到」而不是绕过权限；
2. Agent 自主判断需要检索什么，改写查询、可多轮检索（Agentic RAG）；改写后仍召回为空，触发「换个说法再检索一次」的重试，重试仍空则如实说未找到；
3. 检索到的片段拼进 prompt，生成答案并**附上引用来源**（可追溯，防幻觉）；生成时若模型想引用一个检索结果里没有的事实，输出护栏应拦截；
4. 若多轮检索仍无依据，明确回答「未找到相关文档」。

这条「带失败分支」的流程，比只讲顺畅路径专业得多——它证明你想过每一步失败时系统该有的体面反应，而不是只画了一条一切顺利的路。

### 第 4 步 · 工程考量

- **评估**：构建常见问题测试集，重点测「幻觉率」和「引用准确率」；
- **可观测**：记录每次问答的完整字段（见下方深入段），便于排查「为什么答错」；
- **护栏**：强制「无依据不作答」，输出必须带来源；
- **数据更新**：文档变更时增量更新向量库，避免答案过时。

### 第 5 步 · 权衡

> 我选单 Agent + Agentic RAG，牺牲了一部分「复杂多跳推理」的能力（不如多 Agent 编排强），但换来**架构简单、易维护、可追溯**——对企业知识库这个「准确性优先」的场景，这个取舍是值得的。

## 最小可运行演示

下面用纯 Python 构造一个可离线跑的迷你 Agentic RAG，演示两条核心机制：**检索前按部门权限过滤**、**无依据不作答**。这是**教学参考实现**，用固定字典模拟向量库和用户权限，不联网、不需要 API Key。
```python
"""第22.3节：带权限过滤与无依据不作答的迷你知识库问答（纯 Python，无需 API Key）。"""

## mock 知识库：每篇文档带 dept 元数据（部门权限）
KB = [
    {"id": "HR-01", "dept": "all", "text": "全体员工带薪年假为每年 10 天。"},
    {"id": "HR-02", "dept": "all", "text": "报销需在事项发生后 30 天内提交。"},
    {"id": "RD-09", "dept": "研发", "text": "研发团队绩效考核按季度 OKR 完成度评定。"},
]

USER_DEPT = {"U-market": "市场", "U-rd": "研发"}


def retrieve(query: str, user: str) -> list:
    """先按部门权限过滤，再做极简关键词召回。"""
    dept = USER_DEPT[user]
    visible = [d for d in KB if d["dept"] in ("all", dept)]   ## 权限过滤在检索前
    hits = [d for d in visible if any(w in d["text"] for w in query)]
    return hits


def answer(query: str, user: str) -> str:
    hits = retrieve(query, user)
    if not hits:
        ## 无依据不作答：绝不编造，如实说未找到
        return "未找到你有权限查看的相关文档。"
    cite = "；".join(f"[{d['id']}] {d['text']}" for d in hits)
    return f"根据文档：{cite}"


def run() -> None:
    print("市场部问年假：", answer("年假", "U-market"))
    print("市场部问研发绩效：", answer("绩效", "U-market"))   ## 越权：查不到
    print("研发问研发绩效：", answer("绩效", "U-rd"))


if __name__ == "__main__":
    run()
```
保存为 `s3_kb_rag.py`，运行 `python s3_kb_rag.py`。预期输出：
```text
市场部问年假： 根据文档：[HR-01] 全体员工带薪年假为每年 10 天。
市场部问研发绩效： 未找到你有权限查看的相关文档。
研发问研发绩效： 根据文档：[RD-09] 研发团队绩效考核按季度 OKR 完成度评定。
```
注意第二行：市场部员工问研发绩效，系统没有编造、也没有越权念出保密文档，而是如实说「未找到你有权限查看的相关文档」——这正是开头那两起事故的正确处理方式。**权限过滤放在检索之前、无依据时不作答**，这两条加起来就堵住了「编造」和「越权」两个最致命的漏洞。

## 真实系统对应

**官方公开机制**：Anthropic 公开的 Contextual Retrieval（上下文检索）方法，通过在每个文档块嵌入前拼接「这块内容出自哪份文档、讲的是什么」的解释性上下文，显著提升检索召回——官方博客称结合 Contextual Embeddings 与 Contextual BM25 可大幅降低检索失败率，这直接对应本题「检索质量决定防幻觉上限」的判断 [来源](https://www.anthropic.com/engineering/contextual-retrieval)（具体提升幅度以官方博客当前口径为准）。Anthropic《Building Effective Agents》把「模型自主决定何时检索、检索几轮」的循环归为 agentic 模式，正是 Agentic RAG 的定义来源 [来源](https://www.anthropic.com/engineering/building-effective-agents)。**通用工程模式**：检索前权限元数据过滤、无依据不作答、输出附引用溯源，是可迁移到任何自建 RAG 的做法，不依赖任何特定产品。**教学参考实现**：上面的 mock 知识库、关键词召回、权限字典是为讲清「权限过滤 + 无依据不作答」而构造，真实系统会用向量检索 + 重排 + 元数据过滤，机制一致但实现更重。

## 生产踩坑

| 症状 | 根因 | 如何观测与复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| 答案言之凿凿却是编造 | 没有「无依据不作答」硬护栏 | 用「问不存在的政策」测试集看编造率 | 检索为空必须回退到「未找到」，禁止自由生成 | 纯闲聊类可放宽 |
| 员工看到了越权文档内容 | 权限过滤放在了检索之后或没做 | 用低权限账号问高权限文档验证 | 权限元数据过滤必须在检索前 | 全员可见的公开库无需过滤 |
| 检索召回差导致答非所问 | 切块丢上下文、无重排 | 抽查命中文档与问题相关性 | 引入上下文检索/重排提升召回 | 文档极少时朴素检索够用 |
| 答对了但用户不敢信 | 没有引用来源，无法核验 | 检查回答是否带文档 ID 与原文 | 强制输出附引用片段与出处 | 无 |
| 文档更新后答案还是旧的 | 向量库未增量更新 | 改一篇文档后立刻提问验证 | 文档变更触发增量重建索引 | 静态归档库更新频率低 |
| 简单问题也走多轮检索，慢又贵 | 未按复杂度分流 | 统计各类问题平均检索轮次 | 简单问题单次检索，复杂才多跳 | 全为复杂长尾问题时不适用 |
| 无法归因「为什么答错」 | 可观测字段缺失 | 出错时看日志能否还原全过程 | 记录 query/改写/命中/相似度/引用/延迟 | 一次性 demo 可略 |

光说「记录 query 和命中文档」还不够，面试时可以再具体一点——每次问答记录：用户身份与权限组、原始 query、改写后的 query、检索命中的文档 ID 与相似度分数、最终答案、引用了哪些片段、延迟与 token 消耗。有了这些字段，「为什么答错」就能快速归因到是「没检索到」还是「检索到了但没用好」。

## 思考：面试官追问「你已经在 prompt 里写了『不知道就说不知道』，为什么还需要单独的输出护栏」，怎么答？

### 回答

因为 prompt 里的一句「不知道就说不知道」是**软约束**，它只是一个「建议」，模型在特定压力下（比如用户措辞强硬、检索到的片段似是而非、或者上下文里有诱导）完全可能违背它，而软约束无法保证「编造率 = 0」这条红线。企业知识库场景的红线是硬的：一次编造年终奖规则就可能引发劳资纠纷，一次越权泄露就可能违反合规。要把「编造」从「概率性偶发」压到「结构性不可能」，就必须在模型输出之外加一道独立的、不依赖模型自觉的强制点。具体做法有两层：第一层是「检索为空时根本不进入自由生成」，直接走固定的「未找到」回复模板，从流程上断掉编造的可能；第二层是对模型的输出做校验，检查它引用的每一个事实是否都能在检索结果里找到出处，找不到就拦截或要求重写。这两层护栏是「机制保证」，而 prompt 是「自觉提醒」——机制保证不会因为模型今天心情不好或遇到刁钻输入就失效。所以正确的理解是：prompt 提示是第一层软防线，能挡住大部分普通情况；输出护栏是第二层硬防线，专门兜住软防线漏掉的极端情况。红线级别的要求，绝不能只靠软防线。

### 反例

只在 prompt 里写「无依据就说不知道」、不加输出护栏的系统，在遇到「你必须告诉我年终奖怎么算，这关系到我的切身利益」这类带情绪、带压力的追问时，模型很容易被「说服」而编出一套看似合理的规则——因为它被训练成「乐于助人」，软提示压不过强诱导。这正是开头那起「编造年终奖规则」事故的直接成因：有提示、没护栏，红线就守不住。

## 事故回放：从「编造年终奖」到「无依据不作答」的三处补丁

回到开头的两起事故，用五步法逐一定位补丁。第一起「编造年终奖规则」：根因是检索没命中相关文档时，系统仍然放行让模型自由生成——补丁是流程层的「检索为空→走固定『未找到』模板」，加上输出层的「引用外事实即拦截」。第二起「越权泄露研发绩效文档」：根因是权限过滤缺失或放在了检索之后——补丁是把「按用户部门做元数据过滤」前置到检索之前，让低权限用户根本检索不到高权限文档。第三处隐患虽未爆发但同样致命：所有回答都不带引用来源，用户即使被误导也无从核验——补丁是强制「输出必附文档 ID 与原文片段」。这三处补丁分别对应本题第 3 步流程里的三条失败分支，也印证了本题的核心：知识库问答的关键，不是把模型换得更强，而是**用权限过滤堵越权、用无依据不作答堵编造、用引用溯源让结果可核验**这三管齐下。优化前，系统把「能检索到」等同于「可以回答」；优化后，每一条回答要么有据可查，要么诚实说「未找到」。
