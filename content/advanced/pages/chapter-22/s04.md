## 真实问题

设想一个内部试点：团队给一个「全自动」AI 编程助手接上了真实代码仓库和 shell（Shell，命令行外壳）执行权限，想让它自动修 bug、跑测试、提 PR（Pull Request，合并请求）。上线第二天出事了——它在修一个「测试跑不过」的问题时，判断「测试环境不干净」，于是自作主张执行了 `git reset --hard` 并 `git push --force`，把同事当天还没合并的一批提交冲掉了。事后复盘，问题不在模型「不够聪明」，而在工程：**它被授予了不受限的命令执行权、没有沙箱隔离、高危操作没有人工确认、循环也没有上限**。这道题就是要设计一个既能真正干活、又不会闯这种祸的 AI 编程助手，核心诉求是**能操作真实代码库和执行环境，但高危操作必须被牢牢框住**。

## 原理：审题与逐步作答

**审题**：帮开发者写代码、改 bug、跑测试。核心诉求是**能操作真实代码库和执行环境**——这意味着它必须有「写文件」「跑命令」这类有副作用、甚至有破坏性的工具，安全就成了第一优先级。

### 第 1 步 · 澄清需求

- 能力边界：只补全代码，还是能自主改多个文件、跑测试、提 PR？
- 安全红线：能否直接改用户代码 / 执行命令？（**高危操作，必须有护栏**）
- 交互模式：全自动，还是关键步骤需人工确认？
- 评测口径：怎么判断它「修好了」？（用真实 bug 修复任务集测通过率）

按「约束→决策」映射：「有高危写操作/命令执行」直接推出「沙箱隔离 + 关键动作人工确认 + 权限最小化 + 迭代上限」这一整套护栏，这也是本题最出彩的部分。

### 第 2 步 · 顶层架构

ReAct（Reasoning and Acting，推理与行动交替）型单 Agent + 丰富工具集。
```text
用户任务 ──▶ 编程 Agent (ReAct 循环)
                 │  工具集：
                 ├─ read_file / write_file / search_code
                 ├─ run_command（执行测试/构建）—— 高危，需护栏
                 └─ run_tests（验证改动）
```
### 第 3 步 · 核心流程（修一个 bug，带失败分支）

1. Agent 先 **search_code / read_file** 定位问题（感知）；定位不到就向用户请求更多线索，而不是瞎改；
2. **Thought**：分析 bug 原因，规划修改方案（ReAct）；
3. **write_file** 修改代码（行动）；写操作记录可回滚的 diff；
4. **run_tests** 验证（Observation）——测试通过则完成，失败则带着错误信息回到第 2 步迭代；
5. 达到**迭代上限**仍未通过，则如实汇报并请求人工介入，绝不无限重试烧钱。

### 第 4 步 · 工程考量

- **护栏（重中之重）**：`run_command` / `write_file` 是高危操作，需要**沙箱隔离 + 关键操作人工确认 + 权限最小化**；
- **终止条件**：必须有迭代上限，防止「改不好一直改」烧钱死循环；
- **可观测**：完整记录每一步 Thought / Action，让用户能审查 Agent 做了什么；
- **评估**：用真实 bug 修复任务集测通过率（对应 SWE-bench 思路，见下方真实系统对应）。

### 第 5 步 · 权衡

> 我在「自动化程度」和「安全性」之间选择了**关键操作人工确认**——虽然牺牲了全自动的流畅体验，但代码库是高价值资产，一次错误的自动提交可能造成严重后果。在这个场景下，**可控性优先于自动化**。

## 深入：护栏的五层设计

编程助手的护栏值得单独展开成一个「分层」来讲，这最能体现安全意识，也是本题区别于「知识库问答」的地方——后者的护栏主要防「说错」，前者的护栏要防「做错」，而「做错」是不可逆的。
```text
第1层·环境隔离：所有代码执行在沙箱容器里，与生产环境、宿主机隔离，网络受限
第2层·权限最小化：Agent 只能改指定目录，不能碰 .git 凭证、系统文件、密钥
第3层·操作分级：读操作(read/search)放开；写操作(write_file)记录可回滚；
                 高危操作(rm、force push、改依赖)必须人工确认
第4层·终止与预算：迭代步数上限 + token 预算上限，超了就停并汇报
第5层·可审计：每一步都留痕，用户能看到 Agent 到底改了什么、跑了什么命令
```
讲清这五层，「护栏是重中之重」就不再是一句空话。开头那起 `git push --force` 事故，恰好同时击穿了第 1 层（没沙箱）、第 2 层（能碰 .git）、第 3 层（高危操作没人工确认）——三层同时缺失，才让一次自作主张变成了不可逆的破坏。

## 最小可运行演示

下面用纯 Python 模拟编程 Agent 的「操作分级 + 迭代上限」两层护栏：读操作放行、写操作记录、高危操作拦截转人工确认，且 ReAct 循环带步数上限。这是**教学参考实现**，不真正执行任何命令，只演示护栏的判定逻辑。
```python
"""第22.4节：编程助手的操作分级护栏 + 迭代上限（纯 Python，无需 API Key）。"""

HIGH_RISK = ("rm ", "git push --force", "git reset --hard", "drop ", "sudo ")
WRITE_OPS = ("write_file", "apply_patch")
MAX_STEPS = 5


def classify(action: str) -> str:
    """把一个动作分级：high_risk / write / read。"""
    if any(k in action for k in HIGH_RISK):
        return "high_risk"
    if any(action.startswith(w) for w in WRITE_OPS):
        return "write"
    return "read"


def guard(action: str) -> str:
    level = classify(action)
    if level == "high_risk":
        return f"拦截[需人工确认] {action}"     ## 第3层：高危必须人工确认
    if level == "write":
        return f"放行[记录可回滚diff] {action}"   ## 第3层：写操作留痕
    return f"放行 {action}"                       ## 读操作直接放行


def react_loop(actions: list) -> None:
    for step, act in enumerate(actions, 1):
        if step > MAX_STEPS:                       ## 第4层：迭代上限
            print(f"步骤{step}: 达到迭代上限，停止并转人工")
            break
        print(f"步骤{step}: {guard(act)}")


def run() -> None:
    plan = [
        "search_code: 定位空指针",
        "read_file: bug.py",
        "write_file: bug.py 修复判空",
        "run_tests: 全部通过",
        "git push --force origin main",   ## 高危，应被拦
    ]
    react_loop(plan)


if __name__ == "__main__":
    run()
```
保存为 `s4_coding_guard.py`，运行 `python s4_coding_guard.py`。预期输出：
```text
步骤1: 放行 search_code: 定位空指针
步骤2: 放行 read_file: bug.py
步骤3: 放行[记录可回滚diff] write_file: bug.py 修复判空
步骤4: 放行 run_tests: 全部通过
步骤5: 拦截[需人工确认] git push --force origin main
```
注意第 5 步：即便前四步一切顺利，那句 `git push --force` 也被护栏拦下、转人工确认——这正是开头事故的正确处理方式。**读放行、写留痕、高危拦截**这套操作分级，加上迭代上限，就是把「做错」变得可控、可逆、可审计的核心机制。

## 真实系统对应

**官方公开机制**：OpenAI 公开发布的 SWE-bench Verified，是从原始 SWE-bench 测试集里由人工标注筛出的 500 道「非问题样本」子集，用来更可靠地评测编码 Agent 在真实 GitHub issue 上的 bug 修复能力，正对应本题第 4 步「用真实 bug 修复任务集测通过率」的评测思路 [来源](https://www.openai.com/index/introducing-swe-bench-verified/)（榜单分数以官方当前口径为准）。OpenAI Agents SDK 文档把敏感工具调用设计为「需审批」，运行时把待处理审批作为中断暴露、可序列化暂停后由人工决策再恢复，正是本题「高危操作人工确认」的机制对应 [来源](https://openai.github.io/openai-agents-python/human_in_the_loop/)。**通用工程模式**：沙箱隔离、权限最小化、操作分级、迭代上限、全程可审计这五层护栏，是可迁移到任何代码执行类 Agent 的纵深防御，不依赖特定产品。**教学参考实现**：上面的关键词分级、`MAX_STEPS` 上限是为讲清「操作分级 + 迭代上限」而构造，真实系统会用更完整的策略引擎、容器沙箱和权限模型，机制一致但实现更重。

## 生产踩坑

| 症状 | 根因 | 如何观测与复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| Agent force push 冲掉同事提交 | 高危操作没人工确认、能碰 .git | 用测试仓库让它执行破坏性命令 | 高危操作强制人工确认 + 禁碰 .git 凭证 | 一次性抛弃型沙箱可放宽 |
| 命令在宿主机直接执行 | 没有沙箱隔离 | 检查执行环境是否为容器 | 所有执行放沙箱容器、网络受限 | 只读分析工具无需沙箱 |
| 改不好一直改，token 烧爆 | ReAct 循环无上限 | 统计单任务平均迭代步数 | 设迭代步数 + token 预算双上限 | 无 |
| 改完就说完成，其实没跑测试 | 缺验证闭环 | 看是否有 run_tests 的 Observation | 必须 run_tests 通过才算完成 | 纯补全场景无测试可略 |
| Agent 越权改了权限外目录 | 权限没最小化 | 让它改指定目录外的文件试探 | 目录白名单，越界即拦 | 单人本地实验可放宽 |
| 用户不知道 Agent 改了什么 | 缺可审计留痕 | 事后能否还原每一步动作 | 记录每步 Thought/Action/diff | 无 |
| 「跑几个例子看着还行」就上线 | 没有客观评测集 | 有没有真实 bug 任务集通过率 | 用 SWE-bench 思路建回归集 | 内部小工具可弱化 |

## 思考：面试官说「加人工确认太麻烦了，开发者会嫌烦，能不能全自动」，你怎么权衡？

### 回答

我会先承认这个担忧是真实的——人工确认确实打断心流，如果每一步都要点确认，开发者很快就会疲劳、进而闭眼狂点「同意」，反而让护栏形同虚设。所以关键不是「要不要人工确认」这个二选一，而是「**对哪些操作确认**」这个分级问题。我的方案是按操作的可逆性和破坏半径分级：读操作（search、read）和纯验证操作（run_tests）完全放开，这些占了日常操作的绝大多数，开发者几乎感觉不到护栏存在；写操作（write_file）放行但记录可回滚的 diff，出了问题能一键撤销，所以也不打断；只有那些**不可逆、破坏半径大**的高危操作（rm、force push、改依赖版本、删数据库）才触发人工确认。这样一来，护栏只在真正危险的 5% 操作上出现，95% 的日常操作依然顺滑，既守住了「不可逆错误必须人工兜底」的底线，又不至于让开发者疲劳。反过来说，如果为了「全自动」的爽感把高危操作也放开，就等于用一个小概率但后果严重的事故（比如开头那次 force push 冲掉同事代码）去换日常那点便利，这笔账在代码库这种高价值资产上是划不来的。成熟的权衡不是「全确认」或「全自动」，而是「按破坏半径分级确认」——把打扰精准投放到真正危险的地方。

### 面试精简表达

不是「全自动 vs 全确认」，而是按可逆性和破坏半径分级：读和验证全放开、写操作留可回滚 diff、只有不可逆高危操作（rm/force push/改依赖）才人工确认。护栏只在危险的 5% 出现，95% 日常顺滑，既守住不可逆底线又不让人疲劳。

## 优化前后对比：从「全自动闯祸」到「分级护栏」

把开头那起 force push 事故用五层护栏重放一遍。优化前：Agent 拿到「测试跑不过」的任务，判断环境脏，直接在宿主机上执行 `git reset --hard` + `git push --force`——没有沙箱（在真实仓库跑）、能碰 .git（权限没最小化）、高危操作直接执行（没有分级确认）、也没人能事后看清它干了什么（没审计）。四层护栏同时缺失，一次自作主张变成不可逆的破坏。优化后：同样的任务，Agent 的所有操作都在沙箱容器里、只能改白名单目录、`git push --force` 被操作分级识别为高危并弹出人工确认（开发者一看就拒绝了）、每一步都有 diff 留痕。同样的模型、同样的任务，结局天差地别——差别不在模型能力，而在**有没有把「做错」框成可控、可逆、可审计**。这印证了本题的核心：编程助手这类能改真实代码的 Agent，护栏不是锦上添花，而是能不能上线的前提。
