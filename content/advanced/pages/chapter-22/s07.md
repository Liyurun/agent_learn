## 真实问题

一位面试官分享过他给候选人打分的「潜规则」：技术方案本身占分不到一半，另一半全在那些「不写在题面上的信号」——你有没有主动谈评估、有没有对高危操作露出安全意识、有没有诚实说出方案的缺点、五道不同的题你能不能给出五种不同的选型。他见过太多候选人技术细节讲得头头是道，却因为「全程不提怎么评估好坏」「声称方案完美无缺」「五道题一律无脑上多 Agent」被扣到及格线以下。反过来，也有候选人技术深度一般，但每道题都先澄清、主动谈工程化、诚实讲权衡、选型有理有据，最终拿了高分。这一节要做的，就是把这些「决定成败却容易被忽略」的加分项和红旗，系统地列出来，并把本章五道例题拉通成一张「选型光谱」——因为**能针对不同题给出不同选型、并说清理由，才是系统设计题的最高分表现**。

## 原理：加分项与红旗的一一对应

系统设计题的加分项和红旗，大多是同一枚硬币的两面——做到了是加分，做反了是红旗。把它们对照着记，临场就能一边亮加分项、一边主动避开红旗。

| 加分项 | 红旗 |
|---|---|
| 先澄清需求再设计 | 上来就画架构、不问需求 |
| 主动谈评估 / 可观测 / 护栏 | 只讲「功能怎么实现」，不谈工程化 |
| 明确说出设计的权衡取舍 | 声称方案「完美无缺」 |
| 对高危操作有安全意识 | 让 Agent 无限制执行命令 |
| 有明确的终止条件和失败降级 | 循环没有上限、异常直接崩溃 |
| 单/多 Agent 的选择有理有据 | 无脑上多 Agent 显得「高级」 |
| 会做粗略容量/成本估算 | 完全不考虑规模和成本 |
| 讲流程带上失败分支 | 只讲一切顺利的 happy path |
| 缩写与术语先讲清再用 | 满嘴黑话，面试官跟不上 |
| 引用真实系统的公开机制佐证 | 臆造厂商内部实现或编造数字 |

这张表里，前八条是本章反复强调的核心；后两条是「表达层」的加分项——即便技术判断到位，如果满嘴 RAG（Retrieval-Augmented Generation，检索增强生成）、MCP（Model Context Protocol，模型上下文协议）、CoT（Chain-of-Thought，思维链）却不解释，或者张口就说「某大厂内部就是这么实现的」这种无法核验的话，也会掉分。**能把复杂方案讲得让人听懂、且只引用可核验的公开机制**，本身就是专业度的体现。

## 深入：五道例题的横向选型光谱

把本章五道题放一起看，能看到「选型判断力」的完整光谱——这也是本章最想让你带走的东西。

| 例题 | 该不该用 Agent | 架构核心 | 头号工程关注 | 关键权衡 |
|---|---|---|---|---|
| 知识库问答 | 单 Agent（Agentic RAG） | 检索 + 权限过滤 + 引用 | 防幻觉、可追溯 | 牺牲多跳推理换简单可追溯 |
| 编程助手 | ReAct 单 Agent | 工具集 + 沙箱 | 高危操作五层护栏 | 牺牲全自动换可控安全 |
| 会议纪要 | 用 Workflow（不必 Agent） | map-reduce 分段汇总 | 长文本 + 结构化输出 | 牺牲灵活性换稳定可预测 |
| 智能客服 | 多 Agent（真的合适） | 路由 + 专职 Agent | 路由准确率 + 权限隔离 | 牺牲低延迟换职责隔离 |
| 数据分析 | ReAct 单 Agent | schema + 只读执行 | 执行安全 + 可核验 | 牺牲写能力换绝对安全 |

这张表本身就是一个强信号：**不是所有题都该上 Agent（会议纪要用 Workflow 更好），也不是所有 Agent 题都该用多 Agent（只有客服真正需要）**。五道题横跨「单 Agent / 多 Agent / 干脆不用 Agent」三种选择，每种选择都有它命中的信号——领域单一选单 Agent，多领域 + 权限隔离才选多 Agent，流程固定就退回 Workflow。当你能在面试里流畅地对不同题给出不同选型、并说清「我为什么这么选」，就等于向面试官证明了你有真正的架构判断力，而不是只会套一个模板。

## 最小可运行演示

下面把「选型判断」写成一个可运行的决策器：输入一道题的三个信号（流程是否固定、领域是否多且需隔离、是否有高危执行），输出推荐的架构选型。这是**教学参考实现**，用来演示「选型是可解释的规则推导，而非拍脑袋」。
```python
"""第22.7节：Agent 选型判断器——按信号推导单/多 Agent 或 Workflow（纯 Python，无需 API Key）。"""
from dataclasses import dataclass


@dataclass
class ProblemSignals:
    name: str
    fixed_flow: bool          ## 流程是否固定（不需模型动态决策）
    multi_domain_isolate: bool  ## 是否多领域且需权限隔离
    high_risk_exec: bool      ## 是否有高危执行（写文件/命令/SQL）


def choose(sig: ProblemSignals) -> str:
    if sig.fixed_flow:
        return "Workflow（流程固定，不必上 Agent）"
    if sig.multi_domain_isolate:
        return "多 Agent（多领域 + 权限隔离）"
    base = "单 Agent（ReAct/Agentic）"
    if sig.high_risk_exec:
        base += " + 沙箱/只读等护栏"
    return base


PROBLEMS = [
    ProblemSignals("知识库问答", False, False, False),
    ProblemSignals("编程助手", False, False, True),
    ProblemSignals("会议纪要", True, False, False),
    ProblemSignals("智能客服", False, True, False),
    ProblemSignals("数据分析", False, False, True),
]


def run() -> None:
    for p in PROBLEMS:
        print(f"{p.name:6s} -> {choose(p)}")


if __name__ == "__main__":
    run()
```
保存为 `s7_selector.py`，运行 `python s7_selector.py`。预期输出：
```text
知识库问答 -> 单 Agent（ReAct/Agentic）
编程助手   -> 单 Agent（ReAct/Agentic） + 沙箱/只读等护栏
会议纪要   -> Workflow（流程固定，不必上 Agent）
智能客服   -> 多 Agent（多领域 + 权限隔离）
数据分析   -> 单 Agent（ReAct/Agentic） + 沙箱/只读等护栏
```
这段代码把「选型」从玄学变成了可解释的规则：先看流程是否固定（固定就退回 Workflow），再看是否多领域 + 需隔离（是才上多 Agent），否则单 Agent，有高危执行就加护栏。面试时你不必真写这段代码，但脑子里有这套判断顺序，就能对任意新题快速、有理有据地定选型——这正是避开「无脑上多 Agent」这个头号红旗的方法。

## 真实系统对应

**官方公开机制**：Anthropic《Building Effective Agents》明确主张「能用简单可组合的模式就不要上复杂自治架构，多 Agent 的复杂度必须由收益证明」，这正是本节「不是所有题都该上多 Agent」的权威背书 [来源](https://www.anthropic.com/engineering/building-effective-agents)；OpenAI《A practical guide to building agents》建议先确认是否真的需要 Agent、从单 Agent 起步、把评估与护栏列为上线必备，对应本节「先澄清、主动谈工程化」的加分项 [来源](https://cdn.openai.com/business-guides-and-resources/a-practical-guide-to-building-agents.pdf)。**通用工程模式**：加分项/红旗对照、按信号推导选型、五题横向光谱，都是可迁移的面试与设计方法论。**教学参考实现**：上面的选型判断器规则是为讲清「选型可解释」而构造的简化版，真实场景的信号更多（成本、团队规模、维护成本等），需要综合权衡，不能只看三个布尔量。

## 生产踩坑

| 症状 | 根因 | 如何观测与复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| 五道题一律上多 Agent | 把多 Agent 当「高级」 | 看选型是否随题变化 | 用「流程固定/多领域隔离」信号判断 | 无 |
| 全程不提怎么评估好坏 | 缺生产思维 | 数作答里评估相关句子 | 每题收尾抛评估集与关键指标 | 一次性 demo 可弱化 |
| 说方案「完美无缺」 | 无权衡意识 | 追问缺点时答不上 | 每题至少一条真实牺牲 + 理由 | 无 |
| 高危操作只字不提护栏 | 缺安全意识 | 看写/执行操作是否配护栏 | 高危操作必配沙箱/只读/审批 | 纯只读查询风险低 |
| 循环没上限、异常就崩 | 无终止与降级 | 看是否有迭代上限/失败分支 | 设步数预算上限 + 单点降级 | 无 |
| 完全不估规模和成本 | 忽略非功能需求 | 追问 QPS/成本时无概念 | 口算日请求、峰值 QPS、token 量级 | 需求本就无规模压力时略 |
| 满嘴缩写不解释 | 忽视表达清晰度 | 看缩写首次是否给全称 | 缩写首次带英文全称再用 | 面向资深同行可适度精简 |
| 声称「大厂内部就这么做」 | 臆造无法核验的实现 | 追问出处时答不出 | 只引用有公开文档的机制 | 无 |

## 思考：面试临近结尾，面试官问「你还有什么想补充的」，怎么用这一句把整场作答的分数再抬一档？

### 回答

这个问题几乎每场都会问，是一个被严重低估的加分窗口，绝不能只回一句「没有了」。我会用它做三件事，把整场作答收束得更专业。第一，主动补一条前面没来得及展开的工程化底线，通常是评估或可观测——因为这两块最能体现生产思维，我会说「如果时间允许，我想强调这个系统上线前必须有一个评估集，把刚才澄清出来的红线（比如防幻觉、防越权）各写成一条会跑失败的测试，每次改 prompt 都回归，否则我没法证明它真的安全」。第二，诚实地补一条我这个方案的已知局限和演进方向，比如「我这一版为了准确优先牺牲了多跳推理，如果后续发现用户的复杂问题变多，我会考虑引入更强的检索规划，但那是被数据驱动的下一步，不是现在就上」——这既展示了权衡意识，又展示了「用数据驱动演进」的成熟。第三，如果我在作答中引用了某个真实系统的机制（比如护栏审批、supervisor 路由），我会强调「这些我引用的都是有公开文档支撑的外部行为，厂商内部的具体实现我不臆测」，主动划清「公开机制 vs 内部实现」的边界，这种严谨本身就是信号。这三件事——补工程底线、认已知局限、划真实性边界——每一件都精准命中了本节列的加分项，也主动避开了「称方案完美」「臆造内部实现」两个红旗。所以「你还有什么补充」不是客套，而是一个能让面试官在打分表上多写一行好评的机会，我一定会接住它。

### 面试精简表达

绝不说「没有了」。用三句收束抬分：一补工程底线（上线必须有评估集，把红线写成会失败的回归测试）；二认已知局限 + 数据驱动的演进方向（现在为准确牺牲了多跳，数据要求了再加）；三划真实性边界（引用的是公开机制，内部实现不臆测）。三句精准命中加分项、避开红旗。

## 本章收束：把「五步法 + 五道题」内化成条件反射

走完这七个小节，你手里应该有一套完整的系统设计题作战体系。**方法论层面**，五步法是骨架——澄清需求、顶层架构、核心流程、工程考量、权衡取舍，其中第 1 步澄清和第 5 步权衡最拉分；六问清单、四层套路、四件套、三条轴是可背诵的小抄。**案例层面**，五道例题给了你选型判断的完整光谱——知识库问答（单 Agent + Agentic RAG + 权限过滤 + 引用防幻觉）、编程助手（ReAct + 五层护栏 + 迭代上限）、会议纪要（认清是 Workflow + map-reduce + schema）、智能客服（真正适合多 Agent + 路由准确率 + 转人工兜底）、数据分析（先 get_schema 再只读 SQL + 可核验）。**信号层面**，十条加分项对十条红旗，从澄清到权衡到真实性边界，每一条都在告诉面试官「这是一个做过系统的人」。把这三层内化成条件反射，你面对任何一道开放式 Agent 设计题，都能从容地把它收敛成一条有澄清、有架构、有流程、有工程、有权衡的主线——这，就是本章想交给你的分水岭能力。
