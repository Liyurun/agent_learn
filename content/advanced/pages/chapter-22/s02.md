## 真实问题

某团队做过一次内部 Mock 面试统计：12 位候选人答同一道「设计一个客服 Agent」，有 10 位卡在同一个地方——**知道要「澄清需求」，但不知道具体问什么，张嘴问了句「用户量大概多少」就没词了**；有 8 位「知道要谈权衡」，但一到嘴边只会说「这个方案挺好的，可能有点慢」，说不出到底在哪条轴上牺牲了什么。这暴露出一个真相：五步法的骨架好记，但**每一步里「具体问什么、具体怎么画、具体权衡什么」才是真正的功夫**，也是本节要逐步拆开的。骨架是地图，本节给的是每一步的详细路书。

## 原理：每一步都有一套可背诵的「小抄」

五步法之所以能落地，是因为每一步都能压缩成一张可以背下来、临场直接调用的小抄。下面逐步展开。

### 第 1 步 · 澄清需求：六问清单

拿到任何设计题，脑子里过一遍这六个问题，挑相关的问出来：
```text
1. 谁在用、用来干嘛   面向 C 端还是内部员工？核心场景是什么？
2. 规模             多少用户、QPS 峰值、数据量多大？
3. 延迟要求         要秒回还是可以等几十秒？能不能异步/流式？
4. 质量红线         能不能容忍错误？金融/医疗/法律通常零容忍，闲聊可宽松
5. 安全与权限       有没有高危操作？不同用户可见范围是否不同？数据是否敏感？
6. 边界            哪些明确不做？这一版和未来版本的分界？
```
澄清不是走过场——**每一个澄清出来的约束，都会在后面变成一个具体的设计决策**。「金融场景零容忍」直接推出「必须附引用、无依据不作答」；「内部员工用、有权限差异」直接推出「检索前按用户身份做元数据过滤」；「可异步」直接推出「架构可以走批处理而非实时」。好的候选人会把澄清和后续设计显式挂钩，让面试官看到「我问这个，是因为它会影响那个」。

### 第 2 步 · 顶层架构：四层套路

不知道怎么画时，按这四层从上到下画，基本不会错：
```text
[接入层]  用户入口、鉴权、限流
    │
[编排层]  单/多 Agent、路由、循环控制、终止条件
    │
[能力层]  工具集（检索/执行/外部 API）、记忆（短期/长期）
    │
[数据层]  向量库、关系库、对象存储、缓存
```
画完主动说每层职责一句话，面试官就能顺着你的图理解整个系统。**切忌一上来就钻进「用哪个向量库、Embedding 用哪个模型」这种细节**——那是选定架构之后的事。先决定单 Agent 还是多 Agent（用领域边界是否清晰、是否需要权限隔离来判断），再往四层里填东西。

### 第 3 步 · 核心流程：带上失败分支

选最典型的一条链路（如「用户提问 → 检索 → 生成答案」），像讲故事一样把数据流走一遍，让面试官看到系统「活」起来。新手只讲 happy path（一切顺利的路径），高手会顺带讲「如果这一步失败/超时/无结果怎么办」。比如「检索没命中 → 就如实说未找到，而不是硬编」。带失败分支的流程，才显得你真在系统里跑过。

### 第 4 步 · 工程考量：四件套 + 一句话

主动抛出这四件事，最能体现生产思维：
```text
评估     有没有评估集？测什么指标（成功率、幻觉率、延迟、成本）？改动跑不跑回归？
可观测   出了问题能不能定位？有没有记录每一步的 Thought/Action/工具结果？
护栏     高危操作怎么防？输入输出怎么校验？提示注入怎么挡？
成本延迟  token 怎么控？慢在哪？能不能缓存/分级/并发？
```
一句话收尾：「把 Demo 变成能上线的系统，大部分工作量都在这些看不见的地方。」这句话本身就是加分项。

### 第 5 步 · 权衡取舍：三条轴

想不出取舍时，从这三条轴上找，明确说自己偏向了哪一端、因为场景更看重什么：
```text
轴1 准确性 vs 成本/延迟   更多检索 / 更强模型更准，但更贵更慢
轴2 自动化 vs 可控性      全自动流畅但危险，人工确认安全但慢
轴3 灵活性 vs 简单性      多 Agent / 复杂编排更灵活，但更难维护
```
## 最小可运行演示

下面把「澄清约束 → 设计决策」的挂钩关系，和「三条权衡轴」的选择，写成一个可运行的推导器。它演示的正是本节最核心的方法——**约束不是孤立的问题，而是能机械地推导出设计决策**。这是**教学参考实现**。
```python
"""第22.2节：从澄清约束推导设计决策，并在三条轴上定位权衡（纯 Python，无需 API Key）。"""

## 约束 -> 设计决策 的可迁移映射（通用工程模式）
CONSTRAINT_TO_DECISION = {
    "质量红线=零容忍": "无依据不作答 + 输出必附引用 + 拿不准转人工",
    "有权限差异": "检索前按用户身份做元数据过滤",
    "可异步": "走批处理 / map-reduce，而非实时链路",
    "有高危写操作": "关键动作人工审批 + 幂等键 + 权限最小化",
    "高并发": "无状态 Agent + 会话状态外置 + 下游限流缓存",
    "长文本超上下文": "分段 map + 汇总 reduce",
}

## 三条权衡轴：偏向哪端 + 场景理由
AXES = {
    "准确性 vs 成本延迟": ("准确性", "答错会误导决策，宁可慢且贵"),
    "自动化 vs 可控性": ("可控性", "高危操作一次错代价高，关键步人工确认"),
    "灵活性 vs 简单性": ("简单性", "领域单一，简单可维护优先"),
}


def derive(constraints: list) -> None:
    print("=== 约束 -> 设计决策 ===")
    for c in constraints:
        print(f"[{c}] -> {CONSTRAINT_TO_DECISION.get(c, '（需具体分析）')}")


def pick_tradeoff(axis: str) -> None:
    side, reason = AXES[axis]
    print(f"[{axis}] 偏向：{side}，因为 {reason}")


def run() -> None:
    derive(["质量红线=零容忍", "有权限差异", "有高危写操作"])
    print("=== 权衡定位 ===")
    for axis in AXES:
        pick_tradeoff(axis)


if __name__ == "__main__":
    run()
```
保存为 `s2_derive.py`，运行 `python s2_derive.py`。预期输出：
```text
=== 约束 -> 设计决策 ===
[质量红线=零容忍] -> 无依据不作答 + 输出必附引用 + 拿不准转人工
[有权限差异] -> 检索前按用户身份做元数据过滤
[有高危写操作] -> 关键动作人工审批 + 幂等键 + 权限最小化
=== 权衡定位 ===
[准确性 vs 成本延迟] 偏向：准确性，因为 答错会误导决策，宁可慢且贵
[自动化 vs 可控性] 偏向：可控性，因为 高危操作一次错代价高，关键步人工确认
[灵活性 vs 简单性] 偏向：简单性，因为 领域单一，简单可维护优先
```
这段代码把面试里最玄的两件事——「澄清有什么用」和「权衡怎么讲」——变成了可机械执行的映射。当你能在脑子里跑这个映射，澄清就不再是尬聊，而是「问一句、推一个决策」；权衡也不再是「感觉挺好」，而是「在这条轴上我偏向这端，因为这个场景看重这个」。

## 真实系统对应

**官方公开机制**：OpenAI Agents SDK 文档区分 handoffs（去中心化对等交接，控制权移交专家）与 manager/agents-as-tools（中心化编排，面向用户的 Agent 持有对话所有权、把专家当有边界的能力调用）两种模式，正是第 2 步「先定单/多 Agent 编排」要做的选择 [来源](https://github.com/openai/openai-agents-python/blob/main/docs/agents.md)；LangGraph 把多智能体拓扑分为 supervisor（监督者集中路由）与 network（对等 handoff），供第 2 步按场景取舍 [来源](https://langchain-ai.github.io/langgraph/concepts/multi_agent/)。**通用工程模式**：六问澄清清单、四层架构套路、失败分支、工程四件套、权衡三轴，都是可迁移到任意系统的方法论。**教学参考实现**：上面的「约束→决策」映射表是为讲清挂钩关系而构造，覆盖不了所有场景，真实项目需按题扩展。

## 生产踩坑

| 症状 | 根因 | 如何观测与复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| 澄清只会问「用户量多少」 | 没有可背的六问清单 | 数一下作答澄清了几项 | 背下六问：谁用/规模/延迟/红线/权限/边界 | 题干已把需求写死时略 |
| 架构画到「用哪个 Embedding」 | 过早钻细节，忘了分层 | 看架构图是否先分四层 | 先画接入-编排-能力-数据四层再填细节 | 明确要求讲选型时可下沉 |
| 单/多 Agent 拍脑袋选 | 没有判断标准 | 问「为什么多 Agent」答不清 | 用「领域边界+权限隔离」两信号判断 | 无 |
| 流程只讲 happy path | 没跑过真实系统 | 追问「失败怎么办」卡住 | 每步补「失败/超时/无结果怎么办」 | 无 |
| 工程只谈功能实现 | 缺四件套记忆法 | 数评估/可观测/护栏/成本提了几个 | 收尾固定抛四件套 + 一句话 | 一次性 demo 可弱化 |
| 权衡说「可能有点慢」 | 没有三条轴框架 | 追问「牺牲了什么」含糊 | 用三轴定位：偏哪端 + 场景理由 | 无 |
| 澄清和设计两张皮 | 为问而问，没挂钩 | 检查约束是否对应决策 | 每个约束后显式说「所以架构里做X」 | 无 |

## 思考：面试官问「你为什么不多问几个问题、直接开始设计不是更快吗」，怎么回答才显得成熟？

### 回答

我会先认同他的隐含担忧——澄清确实有成本，问太多会显得啰嗦、也会占用宝贵的作答时间——然后说清我的取舍逻辑：澄清不是越多越好，而是要问「会改变架构的那几个问题」，一旦某个问题的不同答案会导致完全不同的设计，它就必须问。举个具体对照：如果我不问「不同部门文档可见范围是否不同」，就有两种截然相反的架构——需要权限隔离的话，向量库必须带部门元数据、检索前必须做过滤；不需要的话，架构可以简单得多。这个问题的答案直接决定了一大块设计，不问就等于闭卷猜题，猜错了整个方案作废，远比多花 30 秒问一句昂贵。反过来，像「用什么颜色的按钮」这种不影响架构的问题，我一个都不会问。所以成熟的澄清不是「问得多」，而是「问得准」——只问那些会分叉出不同架构的问题，把有限的澄清预算花在刀刃上。这样回答，既承认了澄清有成本、不是越多越好，又展示了我能分辨「哪些问题值得问」，这本身就是工程判断力的体现。

### 面试精简表达

澄清不是越多越好，只问「会改变架构的问题」。比如「要不要权限隔离」，答案不同会分叉出完全不同的架构，不问就是闭卷猜题，猜错整个方案作废，比多问 30 秒昂贵得多；不影响架构的问题一个都不问。成熟在于问得准，不是问得多。

## 优化前后对比：从「张嘴就卡」到「问一句推一个决策」

把本节方法用在同一道题上，能看到澄清和权衡的质量如何被拉满。优化前，候选人澄清阶段：「用户量大概多少？……嗯，然后我就开始设计了。」权衡阶段：「这个方案挺好的，可能延迟有点高。」——澄清只问了一项且没用上，权衡是含糊的形容词。优化后，同一道题：澄清阶段连续问出「面向内部员工（推出要做权限）、金融相关问答零容忍（推出无依据不作答）、可以等几秒（推出可以走多轮 Agentic RAG）」三条，并每问一句就当场说出对应决策；权衡阶段用三轴定位：「我在准确性和延迟这条轴上偏向准确性，因为答错会误导员工决策，宁可让它多检索一轮、慢一点。」同样是澄清和权衡两个环节，优化后每一句都在推进设计、每一个取舍都挂在明确的轴上——这就是「有小抄」和「没小抄」的差距。把六问清单、四层套路、四件套、三条轴这四张小抄背熟，五步法就从「知道有这么回事」变成了「临场能用出来」。
