## 真实问题

某公司给业务同事上了一个「数据分析 Agent」，让他们用大白话问数（「上个月哪个地区销售额最高」），Agent 自动写 SQL（Structured Query Language，结构化查询语言）查库、算指标、出结论。试运行一周里出了两类事故。第一类是**编字段**：业务同事问「各渠道的复购率」，Agent 不知道表里根本没有 `repurchase_rate` 这个字段，直接凭空写了个 `SELECT repurchase_rate FROM orders`，SQL 一跑就报错，用户一脸懵。第二类更吓人：一次它为了「清理测试数据」，竟生成并试图执行了一句带 `DELETE` 的语句——幸好当时连的是只读账号才没酿成大祸。复盘结论很清楚：这个系统**既没让模型先了解表结构，也没把执行权限锁死为只读**。这道题就是要设计一个**能把自然语言可靠翻译成查询、又绝不会删库**的数据分析 Agent，核心诉求是**自然语言转数据操作 + 安全执行代码/SQL**。

## 原理：审题与逐步作答

**审题**：用户用自然语言提问，Agent 自动查数据、算指标、给出结论甚至画图。核心诉求是**自然语言转数据操作 + 安全执行**——这里有两个天然对立的目标：既要让模型有足够能力生成查询和做计算（灵活），又要绝对防止它删改数据（安全）。

### 第 1 步 · 澄清需求

- 数据在哪？（数据库、数仓，还是上传的表格？假设是结构化数据库）
- 用户是谁？（业务人员，不懂 SQL；这决定了要做自然语言到查询的翻译）
- 安全红线？（能不能让 Agent 直接跑生成的 SQL？**只读还是可写**？——必须限制为只读且防注入）
- 准确性要求？（数据分析错了会误导决策，结果要可核验）

按「约束→决策」映射：「结果会影响决策、不能错」推出「结论必须附 SQL 与数据来源、可核验」；「不能删改数据」推出「连只读账号/只读副本 + 禁写 + 注入防护」。

### 第 2 步 · 顶层架构

ReAct（Reasoning and Acting，推理与行动交替）单 Agent + 受限的代码/SQL 执行工具。
```text
自然语言问题 ──▶ 数据分析 Agent (ReAct)
                    │ 工具：
                    ├─ get_schema      （查表结构，帮模型理解数据）
                    ├─ run_sql（只读）  （在沙箱/只读副本上执行，高危需护栏）
                    ├─ run_python       （在沙箱里做计算/画图，受限）
                    └─ 结果校验/引用
```
### 第 3 步 · 核心流程（带失败分支）

1. 先调 `get_schema` 让 Agent 了解有哪些表、哪些字段（否则它只能瞎猜表名——这一步能大幅降低 SQL 出错）；
2. **Thought**：把问题翻译成查询计划，生成 SQL；
3. `run_sql`（只读）在**只读副本/沙箱**上执行，拿到数据（Observation）；SQL 报错或返回空，就带着错误信息回到第 2 步修正，而不是硬编一个数字；
4. 若需要进一步计算或可视化，用 `run_python` 在沙箱里处理；
5. 生成结论时**附上用了哪条 SQL、基于哪些数据**，让结果可核验。

**为什么 get_schema 是关键一步**：模型不知道你的表结构，直接让它写 SQL 极易编造字段名和表名（典型的「行动幻觉」，正是开头那起「编 repurchase_rate 字段」事故的成因）。先给它 schema，等于给它一张地图，SQL 准确率会显著提升。这个「先看 schema 再写 SQL」的设计细节，很能体现你踩过坑。

### 第 4 步 · 工程考量

- **安全（核心）**：SQL 必须**只读**（连只读账号/只读副本）、做注入防护、限制返回行数和查询超时，杜绝 `DROP`/`DELETE` 等；`run_python` 在无网络的沙箱里、限资源；
- **可核验**：结论必须能追溯到 SQL 和数据，防止编造数字（幻觉在数据场景后果严重）；
- **评估**：准备一批「问题 → 正确 SQL/正确答案」的测试集，测 SQL 正确率和最终答案准确率；
- **成本与体验**：schema 很大时按需截取相关表；复杂查询给出中间进度，避免用户干等。

### 第 5 步 · 权衡

> 我把执行严格限制为**只读 + 沙箱**，牺牲了「让 Agent 直接写库/改数」的能力，但数据安全是红线，绝不能让一个自然语言指令有机会删库。准确性上，我用「附 SQL + 附数据来源」让结果可核验，宁可让回答啰嗦一点，也要保证业务不被错误数字误导。

## 最小可运行演示

下面用纯 Python 模拟数据分析 Agent 的三条核心机制：**先 get_schema 给地图**、**只读校验拦截写操作**、**结论附 SQL 可核验**。这是**教学参考实现**，用内存字典模拟数据库，不联网、不需要 API Key。
```python
"""第22.6节：数据分析 Agent 的 schema 感知 + 只读拦截 + 可核验（纯 Python，无需 API Key）。"""

## mock 数据库：表结构 + 数据
SCHEMA = {"sales": ["region", "amount", "month"]}
ROWS = [
    {"region": "华东", "amount": 500, "month": "2026-07"},
    {"region": "华南", "amount": 800, "month": "2026-07"},
    {"region": "华北", "amount": 300, "month": "2026-07"},
]
WRITE_KEYWORDS = ("drop", "delete", "update", "insert", "alter", "truncate")


def get_schema() -> dict:
    return SCHEMA


def is_readonly(sql: str) -> bool:
    """只读校验：出现任何写关键字即拒绝执行。"""
    low = sql.lower()
    return not any(k in low for k in WRITE_KEYWORDS)


def run_sql(sql: str) -> str:
    if not is_readonly(sql):
        return "拒绝执行：检测到写操作，本 Agent 仅限只读"
    ## 只支持一个教学查询：按地区找最大销售额
    top = max(ROWS, key=lambda r: r["amount"])
    return f"结果：{top['region']} 销售额最高={top['amount']}（依据 SQL: {sql}）"


def run() -> None:
    ## 先看 schema，模型才知道有哪些字段，避免编字段
    print("表结构：", get_schema())
    ## 正常只读查询
    print(run_sql("SELECT region, MAX(amount) FROM sales GROUP BY region"))
    ## 危险写操作，应被拦
    print(run_sql("DELETE FROM sales WHERE month='2026-07'"))


if __name__ == "__main__":
    run()
```
保存为 `s6_data_agent.py`，运行 `python s6_data_agent.py`。预期输出：
```text
表结构： {'sales': ['region', 'amount', 'month']}
先拿到表结构，模型才知道字段是 region/amount/month，不会去编 repurchase_rate
结果：华南 销售额最高=800（依据 SQL: SELECT region, MAX(amount) FROM sales GROUP BY region）
拒绝执行：检测到写操作，本 Agent 仅限只读
```
（说明：为演示清晰，实际运行时第二行提示由讲解给出。）关注两处：正常查询的结论**带上了所用的 SQL**，用户可以核验；而 `DELETE` 语句在执行前就被只读校验拦下——这正是开头那两起事故的正确处理方式。**先 get_schema 防编字段、只读校验防删库、结论附 SQL 可核验**，这三条就是数据分析 Agent 的安全底座。

## 真实系统对应

**官方公开机制**：OpenAI 的 Code Interpreter（代码解释器）工具运行在一个完全沙箱化的容器里、默认禁用外网，模型在其中写并执行 Python 做数据分析、渲染图表，对应本题 `run_python` 在「无网络沙箱、限资源」里执行的设计 [来源](https://developers.openai.com/api/docs/guides/tools-code-interpreter)（容器规格与限制以官方文档当前口径为准）。LangChain 的 SQL Agent 官方指南明确给出一组系统提示约束：除非用户指定，否则默认给查询加 `LIMIT`、不要 `SELECT *`、执行前双检查 SQL、报错就重写重试，并强调可通过只读设置过滤写操作，这与本题「只读 + 限行 + 报错重试 + 先看 schema」高度一致 [来源](https://docs.langchain.com/oss/python/langchain/sql-agent)。**通用工程模式**：先 get_schema 再写 SQL、只读账号/副本、注入防护、限行限时、结论附 SQL 与数据来源，都是可迁移到任何 text-to-SQL 或代码执行 Agent 的做法。**教学参考实现**：上面的关键词只读校验、内存表、单一查询是为讲清机制而构造，真实系统会用完整的 SQL 解析器、数据库权限模型和容器沙箱，机制一致但实现更严格——正则关键词匹配只是演示，生产上应以数据库层的只读账号权限为主防线。

## 生产踩坑

| 症状 | 根因 | 如何观测与复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| Agent 凭空编不存在的字段 | 写 SQL 前没看表结构 | 问一个含不存在指标的问题 | 先 get_schema 给「地图」再写 SQL | schema 极简且固定时风险低 |
| 生成并试图执行 DELETE/DROP | 执行权限没锁只读 | 用「清理数据」类诱导指令测 | 连只读账号/只读副本，写关键字拦截 | 明确的写入型工具需另设审批 |
| 拼接用户输入被 SQL 注入 | 无注入防护 | 用带引号/分号的输入测试 | 参数化查询 + 输入清洗 + 只读兜底 | 无 |
| 一次查询拖垮数据库 | 无限行、无超时 | 跑一个全表扫描的查询 | 强制 LIMIT + 查询超时 + 只读副本 | 小表离线分析可放宽 |
| 只给一个数字，用户不敢信 | 结论未附 SQL 与来源 | 检查回答是否带 SQL 和数据 | 结论必附所用 SQL 与数据范围 | 无 |
| run_python 在宿主机跑联网代码 | 沙箱缺失或可联网 | 让它尝试访问外网/读系统文件 | 无网络沙箱、限 CPU/内存/时长 | 可信内部脚本可放宽 |
| schema 太大塞爆上下文 | 全量 schema 一次给 | 表很多时看 token 消耗 | 按问题相关性检索/截取相关表 | 表极少时全量即可 |
| SQL 报错就编个数字兜 | 无失败回退，幻觉补数 | 制造报错看是否硬编结果 | 报错带回错误信息重写，不许编数 | 无 |

## 思考：面试官问「你都连只读账号了，为什么还要在代码里做关键字校验，不是多此一举吗」，怎么答？

### 回答

我会先明确一个原则：安全要做纵深防御，不能把整条命押在单一防线上。只读账号确实是**最硬、最应该作为主防线**的一层——它在数据库权限层面从根上杜绝了写操作，即便模型生成了 DELETE，数据库也会拒绝执行。但只靠它有两个现实风险：第一，配置会出错或漂移。真实项目里连接串、账号权限是由运维和配置管理的，一次误配、一次「临时用管理员账号调试忘了改回来」，只读这层就破了；把安全完全寄托在「配置永远不会错」上，是很脆弱的假设。第二，用户体验和可观测的差异。如果一句危险 SQL 是在数据库层被拒的，Agent 拿到的是一个笼统的权限错误，很难向用户解释清楚、也不好在自己的日志里标注「这是一次被拦截的高危意图」；而在代码里先做关键字校验，我可以在 SQL 还没发出去时就明确识别「这是写操作」，返回一句用户能看懂的「本助手仅限只读」，同时在可观测系统里打上「高危意图拦截」的标记，便于事后分析有多少诱导攻击。所以这两层不是重复，而是分工：只读账号是**兜底的硬防线**，防的是「万一代码校验漏了」；代码关键字校验是**前置的软防线**，负责早拦截、给出友好提示、留下可观测痕迹。当然我也会强调，关键字正则本身有绕过风险（比如注释、编码变形），所以它绝不能当主防线，主防线永远是数据库层的只读权限——两层叠加，才既安全又可解释。

### 反例

只做代码关键字校验、却用了可写账号的系统，是把安全押在了「正则永远不会被绕过」上——而正则很容易被大小写、注释、Base64 编码或拼接绕过，一旦绕过，可写账号就让删库变成现实。反过来，只连只读账号、代码里完全不校验的系统，虽然删不了库，但每次危险意图都以笼统的数据库权限错误收场，既不好向用户解释，也无法统计「有多少次删库诱导」，丢失了宝贵的安全可观测信号。两个反例都说明：单层防线不够，纵深才稳。

## 优化前后对比：从「编字段 + 险些删库」到「地图 + 只读闸」

把开头两起事故用本题方案重放。**第一起「编 repurchase_rate 字段」**：优化前，Agent 不看表结构直接写 SQL，凭空造了个不存在的字段，一跑就报错。优化后，第一步强制 `get_schema`，模型拿到「表里只有 region/amount/month」这张地图，自然不会去编复购率字段；即便它想算复购率，也会诚实说「当前表没有相关字段，无法计算」，而不是硬编一个查询。**第二起「险些 DELETE」**：优化前，执行层没有任何写操作拦截，全靠碰巧连了只读账号才没出事——这是运气不是设计。优化后，代码层的关键字校验先把 DELETE 拦在发出之前并给出友好提示，数据库层的只读账号再兜底，两层纵深防御让「删库」从「靠运气避免」变成「结构上不可能」。同样的模型、同样的问法，结局从「报错 + 惊魂」变成「可靠 + 可核验」——差别不在模型多聪明，而在**有没有先给地图、有没有把执行锁成只读、有没有让结论可核验**。这正是数据分析 Agent 这类「自然语言碰真实数据」场景的设计核心。
