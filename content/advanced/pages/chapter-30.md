## 一次「一天烧掉三个月预算」的真实故障

设想一个已上线的客服 Agent。压测时它表现良好：单请求平均消耗约 6,000 token、响应 3 秒、每次约 $0.06。产品把它接入了真实客服入口。上线第 4 天上午十点，运营发现响应普遍变慢到 9 秒以上；当天下午财务告警：日消耗是预估的 **11 倍**。复盘拉出用量明细，三条线索浮出水面：其一，**平均步数从压测的 4 步涨到线上的 12 步**——真实用户的问题更绕，Agent 每一步都要重读越来越长的历史，输入 token 被平方级放大到单请求约 55,000；其二，**所有请求都用最贵的大模型**，哪怕是「你们几点下班」这种一句话就能答的问题；其三，一段 4,000 token 的系统提示 + 工具定义**每一轮都原样重发**，六轮下来同一段内容付了六次钱。更糟的是当天傍晚一次 prompt 改动引入 bug，让 Agent 对部分请求疯狂重试工具，**单请求 token 从 5.5 万飙到 20 万**，而团队只监控「日总花费」，直到第二天早上看日报才发现，一夜之间多烧了几万块。

这个故障贯穿全章。它把一句模糊的「Agent 又贵又慢」拆成可定位、可下手的工程问题：成本为什么会平方级失控（第 1 节）、哪些请求本不该动用大模型（第 2 节）、重复的前缀和重复的问题怎么不再付钱（第 3 节）、能等的任务和独立的调用怎么攒吞吐、抢墙上时间（第 4 节）、用户为什么觉得「卡死」以及怎么骗过这种感知（第 5 节）、慢到底慢在哪一环、上下文怎么压（第 6 节）、怎么在账单爆炸前几分钟就拦住它（第 7 节）、以及为什么你不可能既最快又最便宜还最聪明（第 8 节）。把这条链路走通，你就能回答面试里最实际的一类问题：「你们这套 Agent，一次调用花多少钱、几秒，怎么降下来的？」

## 你将得到什么

- 能凭记忆推导 Agent 输入 token 随步数呈 O(n²) 平方级增长的求和公式 `k·n(n+1)/2`，并据此解释「为什么减步数优先于换便宜模型」，产出是一张步数-成本对照表。
- 能设计前置分诊与级联（cascade）两种模型分层路由，量化各自在真实流量分布下的省钱幅度与质量风险，产出是可运行的成本对比。
- 能分清 KV Cache（Key-Value Cache，键值缓存）、prompt caching（提示缓存）、语义缓存（Semantic Cache）三层机制各省什么、各自的失效条件，产出是三者对照表与「时间戳击穿前缀」的复现。
- 能判断哪些任务该走批处理 API（省 50%、不即时返回）、哪些独立工具该并行执行（墙上时间取最慢者），产出是串并行耗时对比与批处理成本账。
- 能区分真实延迟与感知延迟，测量并优化 TTFT（Time To First Token，首 token 延迟）与 TPOT（Time Per Output Token，每输出 token 时间），产出是流式与非流式的 TTFT 对比。
- 能把总延迟拆解成网络/推理/工具/框架各环节做延迟预算（latency budget）分解，关注 P95/P99 尾延迟而非平均值，并用上下文压缩降低每轮基线。
- 能落地 per-request 粒度的成本可观测与「告警 + 硬熔断」两级机制，产出是一个能拦住长循环异常的 CostGuard。
- 能讲清质量-成本-延迟不可能三角，并针对金融、客服、实时对话、离线处理四类场景给出不同的最优权衡；并回答与成本性能工程相关的多道思考题。

## 最小环境核验 / 热身

导读页先给一段不联网、不需要 API Key 的热身代码，用来确认解释器可用，并把本章两条最核心的不变量固化成断言：输入 token 随步数**平方级累积**；缓存命中能把前缀费用**降一个量级**。
```python
import sys


def quadratic_input_tokens(n_steps, k=500):
    ## 第 step 步重读全部历史，总输入 = k*n(n+1)/2
    return sum(step * k for step in range(1, n_steps + 1))


def cache_hit_cost(tokens, base=3.0, hit_mult=0.1):
    ## 缓存命中按 0.1x 计费（示例倍率）
    return base * tokens / 1_000_000 * hit_mult


def main():
    print(f"Python={sys.version_info.major}.{sys.version_info.minor}")
    t5, t10 = quadratic_input_tokens(5), quadratic_input_tokens(10)
    ratio = t10 / t5
    print(f"5步输入={t5} tokens, 10步输入={t10} tokens, 倍数={ratio:.1f}x")
    assert 3.5 < ratio < 4.0, "步数翻倍成本应接近 4 倍（平方级）"
    full = 3.0 * 4000 / 1_000_000
    hit = cache_hit_cost(4000)
    print(f"4000token前缀：全价 ${full:.5f} vs 命中 ${hit:.5f}"
          f"（省 {(1-hit/full)*100:.0f}%）")
    assert hit < full * 0.2, "缓存命中应比全价便宜一个量级"
    print("热身通过：平方级累积、缓存降价两条不变量成立，可以开始阅读本章")


if __name__ == "__main__":
    main()
```
保存为 `warmup_ch30.py`，运行 `python warmup_ch30.py`。预期输出：
```text
Python=3.10
5步输入=7500 tokens, 10步输入=27500 tokens, 倍数=3.7x
4000token前缀：全价 $0.01200 vs 命中 $0.00120（省 90%）
热身通过：平方级累积、缓存降价两条不变量成立，可以开始阅读本章
```
Python 小版本可能不同，但需不低于 3.10。若「倍数」不接近 3.7，说明你改动了求和逻辑——这个 3.7 倍（步数从 5 翻到 10、成本近 4 倍）正是本章反复强调的平方级信号。
