## 真实问题

一次真实的面试复盘：候选人被问「用户投诉小蜜答非所问，你怎么办」，他 3 秒内脱口而出「我会优化 Prompt，再换个更强的模型」。面试官追问「你怎么知道是 Prompt 的问题？」他答不上来。又追问「你怎么证明换完就好了？」他说「感觉会好」。这一轮直接挂了——**不是因为方案错，而是因为他跳过了「定位」和「验证」，把场景题当成了背方案题**。

场景题最大的陷阱就是「急着给方案」。故障板上那 8 个超标指标（见本章导读），每一个都可能有五六种根因；不先定位就给方案，等于闭眼开药。面试官真正想听的，是你能不能像一名有生产经验的工程师那样：**先用数据定位到底哪一层出了问题，再分层给方案并说清先做哪个，最后用评估集回归证明真的变好了、且没引入新问题**。

## 原理：场景题的通用三段式骨架

不管遇到什么场景题——幻觉、慢、贵、传错参、路由错、不稳定——都可以套同一个结构。它保证你不漏掉关键环节，也把「分析过程」显性化给面试官看：
```text
第 1 段 · 定位（先别急着修）
   └─ 用 Trace（追踪）/ 日志 / 指标定位问题在哪一层，而不是凭直觉猜
      关键句：「我怎么知道是这层的问题」——答不上来就说明没定位

第 2 段 · 分层给方案（说清优先级）
   └─ 按层次列出可能根因和对应措施，明确「我会先做哪个、为什么」
      关键句：先做「不伤质量、见效快」的，再做「可能有代价、需验证」的

第 3 段 · 验证与兜底（用数据说话）
   └─ 怎么证明方案有效（评估集回归）、有没有引入新问题、失败了怎么兜底
      关键句：「我怎么证明改完就好了」——没有评估集回归就是瞎说
```
这三段的顺序不能乱：**定位在前，是因为不定位的方案是赌博；验证在后，是因为不验证的优化无法区分「真变好」和「随机波动」**。中间的分层给方案，考的是你对系统的结构化理解——能不能把一个模糊现象拆成检索层、Prompt 层、工具层、输出层这样的可定位单元。

## 最小可运行演示

下面这段代码把「三段式」做成一个可执行的自检器：任何场景题答案，只要缺了定位依据或验证方式，它就打回。你可以把它当成临场答题前的心里 checklist。
```python
"""第24.1节：场景题三段式答题自检器（纯 Python，无需 API Key）。"""
from dataclasses import dataclass, field


@dataclass
class SceneAnswer:
    question: str
    locate_by: str = ""              ## 第1段：靠什么定位（Trace/日志/指标）
    layered_plan: list = field(default_factory=list)   ## 第2段：分层方案（有序）
    verify_by: str = ""              ## 第3段：如何用数据验证
    tradeoff: str = ""               ## 加分项：主动说清代价


def grade(a: SceneAnswer) -> str:
    misses = []
    if not a.locate_by:
        misses.append("缺定位依据（会被追问'你怎么知道是这层'）")
    if len(a.layered_plan) < 2:
        misses.append("方案未分层（像背标准答案，不像排查）")
    if not a.verify_by:
        misses.append("缺验证方式（会被追问'怎么证明改好了'）")
    if misses:
        return "不及格：" + "；".join(misses)
    bonus = " [加分:主动谈权衡]" if a.tradeoff else ""
    return f"及格：定位[{a.locate_by}] → 方案{a.layered_plan} → 验证[{a.verify_by}]" + bonus


def run() -> None:
    good = SceneAnswer(
        question="Agent 答非所问怎么排查",
        locate_by="看 Trace 里实际召回的文档与最终输入",
        layered_plan=["检索层查召回", "Prompt 层查约束", "输出层查溯源"],
        verify_by="把失败样本收进评估集，改动后跑回归看指标",
        tradeoff="加护栏会增加约 100ms 延迟，需权衡",
    )
    bad = SceneAnswer(question="Agent 慢怎么办", layered_plan=["换个快模型"])
    print(grade(good))
    print(grade(bad))


if __name__ == "__main__":
    run()
```
保存为 `s1_selfcheck.py`，运行 `python s1_selfcheck.py`。完整预期输出：
```text
及格：定位[看 Trace 里实际召回的文档与最终输入] → 方案['检索层查召回', 'Prompt 层查约束', '输出层查溯源'] → 验证[把失败样本收进评估集，改动后跑回归看指标] [加分:主动谈权衡]
不及格：缺定位依据（会被追问'你怎么知道是这层'）；方案未分层（像背标准答案，不像排查）；缺验证方式（会被追问'怎么证明改好了'）
```
第二条「换个快模型」正是面试里最典型的减分答案：没定位、没分层、没验证，三样全缺。自检器把它一次性打回——这也是本章其余各节反复演示的排查纪律。

## 真实系统对应

**通用工程模式**：「定位 → 方案 → 验证」本质上是把软件工程的「可观测性驱动排障」和「回归测试」搬到 Agent 上。它不依赖任何特定产品，能迁移到任何自建系统。**官方公开机制对应**：这套骨架的三个支点都有真实系统背书——「定位」对应 LangSmith 公开的 Trace / 运行树 / 元数据能力，一次运行被组织成带父子关系的 span，可回看实际输入输出与延迟 [来源](https://docs.smith.langchain.com/evaluation/concepts)；「验证」对应 LangSmith 的数据集（Dataset）+ 评估器（Evaluator）模型，用固定测试集给目标函数打分 [来源](https://docs.langchain.com/langsmith/evaluation-quickstart.md)；「先量化再迭代」呼应 OpenAI《A practical guide to building agents》把评估与可观测列为上线必备 [来源](https://cdn.openai.com/business-guides-and-resources/a-practical-guide-to-building-agents.pdf)。**边界**：具体的采样率、保留期、评估器 Prompt、告警阈值由团队按风险设计，不是平台自动给你的。

## 生产踩坑

下面这张表把「场景题答不好」的常见死法列成可对照的排查项。首列是回答里暴露的坏味道，方便你临场自检。

| 症状 | 根因 | 如何观测与复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| 秒答「换更强模型」 | 跳过定位直接给方案 | 复盘录音里第一句是不是方案而非定位 | 强制先说「我会先看 Trace 哪层偏离」 | 已明确单一根因的极简问题 |
| 被追问「怎么知道是这层」卡壳 | 没有 Trace / 日志作依据 | 让对方问一次追问就露馅 | 定位必须引用可观测数据，不凭直觉 | 无观测系统的早期原型 |
| 方案是一大串并列点 | 没排优先级，像背清单 | 问「先做哪个」答不出顺序 | 按「不伤质量→需验证」排序 | 只有一个可选项的场景 |
| 说完方案就结束 | 缺验证闭环 | 问「怎么证明改好了」无评估集 | 每个方案配「跑评估集回归」 | 一次性脚本、不需回归 |
| 只报喜不谈代价 | 回避权衡显得不成熟 | 问「这么改有什么副作用」答无 | 主动说清代价（延迟/成本/质量三选二） | 确实零副作用的纯 bug 修复 |
| 把锅甩给「模型太笨」 | 缺「先改自己」的心态 | 归因全指向模型能力 | 先查自己的 Prompt/工具/上下文 | 已排除工程因素后确属能力上限 |

## 思考：为什么面试官反复追问「你怎么知道是这个原因」和「你怎么证明改好了」？

### 回答

因为这两个追问精准地卡在「有生产经验」和「只会背书」的分水岭上。第一个追问「你怎么知道是这个原因」考的是**定位能力**——有经验的人会说「我看 Trace 里实际召回的文档跟问题无关，所以判断是检索层」，而没经验的人只能说「我感觉是 Prompt 问题」。凭感觉猜根因，在真实系统里意味着你可能改了半天改错了地方。第二个追问「你怎么证明改好了」考的是**验证意识**——有经验的人会说「我把这批失败样本收进评估集，改动后跑回归，看幻觉率从 6.1% 是否降到 1% 以下」，没经验的人只能说「我试了几个例子感觉不错」。而「试几个例子感觉不错」是最大的红旗：它无法区分「真的系统性变好」和「恰好这几个例子蒙对了」，更没法防止你修好 A 场景却弄坏了 B 场景。这两个追问合起来，本质是在问：**你的判断是不是建立在可观测数据和可回归验证之上**。只要你回答任何场景题时都主动把「定位依据」和「验证方式」说出来，就等于提前把这两个追问答了，面试就稳了一大半。

### 面试精简表达

「怎么知道是这个原因」考定位——要靠 Trace/日志而非直觉；「怎么证明改好了」考验证——要靠评估集回归而非「感觉不错」。这两点是有生产经验的硬标志，答题时主动带上就赢了。

## 深入：场景题最能加分的四个动作与一句「满分骨架」

除了三段式结构，还有四个能显著加分的动作，几乎每道场景题都适用。**其一，先分析再方案**：展示你拆解问题的能力，而不是背方案。**其二，用 Trace / 评估数据说话**：一切优化和判断都基于测量。**其三，暴露真实踩坑经验**：说「我之前遇到过 X，后来发现根因是 Y」，比纯理论更有说服力——真实的坑是无法背出来的，它证明你真的做过。**其四，主动谈权衡**：任何优化都有代价（降本可能伤质量、加护栏可能增延迟、调低 temperature（采样温度）可能让回答变呆板），主动说清代价，比被追问后才补要成熟得多。

把这四点浓缩成一句可以背下来的「满分骨架」，几乎能收尾任何场景题：

> 「我会**先用 Trace / 数据定位到底是哪一层的问题**，而不是凭感觉猜；定位后**分层给方案、说清先做哪个、为什么**；改完**跑评估集做回归**，确认真的变好、且没引入新问题。而且我知道任何优化都有代价，比如这次加护栏会增加约 100ms 延迟，我会用评估集确认这个代价换来的质量提升是值得的。」

这段话把「定位—方案—验证—权衡」四件事一次讲全。后面每一节（幻觉、延迟、成本、传参、路由、注入、稳定性、评估、冷启动、人机边界）都是这套骨架的一次具体演练——你会看到同一副骨架如何套进完全不同的场景，并每次都用故障板上的真实数字把「验证」这一步坐实。
