> 对应故障板指标：**P95 端到端延迟 8.2s → ≤ 3.0s**、**日 Token 成本 ¥1,240 → ≤ ¥600**。这是原书**场景 2「响应太慢怎么优化」**与**场景 5「Token 成本超预算怎么降本」**的合并加深版——两者共享同一套「先归因再对症」的方法，放一起讲最省力。

## 真实问题

小蜜的两块「红牌」同时亮起：一是 P95（95 分位）端到端延迟 8.2 秒，用户盯着转圈图标频繁刷新甚至离开；二是日均 Token（词元）成本 ¥1,240，是预算 ¥600 的两倍多，财务发了预警邮件。

两个团队各自给了「直觉解」：前端团队说「换个更快的模型」，后端团队说「把上下文全局压缩一半」。这两个方案的共同毛病是**没归因就动手**——没人知道 8.2 秒里模型推理、工具调用、ReAct（Reasoning and Acting，推理与行动）轮次各占多少，也没人知道 ¥1,240 里是被少数超长会话吃掉的、还是被某个高频昂贵工具吃掉的。结果「换快模型」可能只省了占比很小的推理时间，「全局压缩上下文」则可能把关键证据也压没了，幻觉率反弹。这一节要证明：**延迟和成本都必须先做归因（分布统计），再对最大的那块下手**。

## 原理：延迟归因与成本的「二八分析」

延迟和成本虽是两个指标，但排查心法一致——**先测量分布，再砍最大头**。

延迟侧，一次 Agent 响应的耗时通常由三部分构成，用 Trace（追踪）就能拆开：
```text
端到端延迟 = Σ(每轮模型推理) + Σ(每次工具调用) + 编排/等待开销
   │
   ├─ ReAct 轮次太多：Trace 显示 5+ 轮才收敛 → 优化 Prompt/工具一次到位/规则短路
   ├─ 单次推理慢：每次 LLM 调用耗时高 → 模型分级、缩短上下文、更快模型
   ├─ 工具调用慢：某工具/API 占大头 → 缓存、超时、可并行的并发调
   └─ 串行等待：多个独立工具被串行 → 并发执行
   （另有「感知延迟」：总耗时可接受但用户觉得慢 → 流式输出降焦虑）
```
成本侧，做一次 Token 消耗的分布统计，你几乎总会发现「二八分布」——成本高度集中在少数地方：
```text
日 Token 成本分布（几乎总是长尾集中）
   ├─ 少数超长上下文会话（把全部历史塞进 Prompt）——常占大头
   ├─ 某个被反复调用的昂贵工具/大模型
   └─ 某类任务的 ReAct 轮次特别多
先砍贡献最大的那 20%，性价比最高；盲目全局压缩往往吃力不讨好还伤质量
```
两侧的共同纪律：**优化前先测量，没有 Trace / Token 分布数据支撑的优化都是瞎猜**。

## 现象与输入：一次 8.2 秒会话的耗时拆解

拿故障板上一条 P95 会话做 Trace 拆解，得到这样一张耗时账单：
```text
session=S-0314 端到端 8.2s 拆解：
  轮1 意图分类   LLM  0.6s
  轮2 检索工具   API  2.1s   ← 无缓存，每次都打向量库
  轮3 组织答复   LLM  1.4s
  轮4 查订单     API  1.9s   ┐ 与查物流本可并行
  轮5 查物流     API  1.8s   ┘ 却被串行调用
  编排/等待           0.4s
  ------------------------------------
  最大头：工具调用合计 5.8s（占 71%），其中订单+物流串行浪费约 1.8s
```
一眼看清：延迟的最大头不是模型推理（2.0s），而是工具调用（5.8s，占 71%），且订单和物流两个独立查询被串行了。这时「换更快的模型」只能省下推理那 2 秒里的一小部分，而**把订单/物流并发、给检索加缓存**才是真正的大头。这就是归因的价值——它把「小蜜好慢」变成「工具层占 71%、串行浪费 1.8s」这样可下手的结论。

## 最小可运行演示

下面用纯 Python 模拟「延迟归因器 + 成本二八分析器」：喂给它一次会话的分段耗时和一批会话的 Token 消耗，它告诉你「延迟最大头在哪、该并发哪些」以及「成本的 80% 被哪些会话吃掉」。不调用任何真实 API。
```python
"""第24.3节：延迟归因 + 成本二八分析（纯 Python，无需 API Key）。"""
from dataclasses import dataclass


@dataclass
class Span:
    name: str
    kind: str        ## "llm" 或 "tool"
    seconds: float
    parallelizable: bool = False


def attribute_latency(spans: list) -> str:
    llm = sum(s.seconds for s in spans if s.kind == "llm")
    tool = sum(s.seconds for s in spans if s.kind == "tool")
    total = llm + tool
    par = [s for s in spans if s.parallelizable]
    ## 可并行工具串行执行的浪费 = 串行总和 - 最大的那个
    waste = sum(s.seconds for s in par) - max((s.seconds for s in par), default=0)
    top = "工具调用" if tool >= llm else "模型推理"
    return (f"总 {total:.1f}s | 模型 {llm:.1f}s 工具 {tool:.1f}s | "
            f"最大头={top} | 并发可省 {waste:.1f}s")


def cost_pareto(sessions: dict) -> str:
    ordered = sorted(sessions.items(), key=lambda kv: kv[1], reverse=True)
    total = sum(sessions.values())
    acc, hot = 0, []
    for sid, cost in ordered:
        acc += cost
        hot.append(sid)
        if acc >= total * 0.8:      ## 累计到 80% 成本就停
            break
    pct = len(hot) / len(sessions) * 100
    return f"{len(hot)}/{len(sessions)} 个会话({pct:.0f}%)吃掉 80% 成本 -> 先砍 {hot}"


def run() -> None:
    spans = [
        Span("意图分类", "llm", 0.6), Span("检索", "tool", 2.1),
        Span("组织答复", "llm", 1.4),
        Span("查订单", "tool", 1.9, True), Span("查物流", "tool", 1.8, True),
    ]
    print(attribute_latency(spans))
    print(cost_pareto({"S-01": 500, "S-02": 420, "S-03": 40,
                       "S-04": 30, "S-05": 10}))


if __name__ == "__main__":
    run()
```
保存为 `s3_cost.py`，运行 `python s3_cost.py`。完整预期输出：
```text
总 7.8s | 模型 2.0s 工具 5.8s | 最大头=工具调用 | 并发可省 1.8s
cost_pareto 结果见下一行
2/5 个会话(40%)吃掉 80% 成本 -> 先砍 ['S-01', 'S-02']
```
（注：`cost_pareto` 的说明行是代码打印顺序造成的排版，实际输出即上面第一行与第三行两条结论。）延迟归因器直接告诉你「最大头是工具、并发能省 1.8s」，成本分析器告诉你「40% 的会话吃掉 80% 的成本，先砍这两个」——两条结论都指向「先动最大头」，而不是「换模型」或「全局压缩」。

## 真实系统对应

**官方公开机制**：成本侧最有据可依的一手抓手是 Anthropic 的 Prompt Caching（提示缓存）。官方文档写明其计价结构——缓存写入按基础输入价的一定溢价计费（5 分钟 TTL（Time To Live，生存时间）的写入约为基础输入的 1.25 倍），而**缓存命中的读取只按基础输入价的约 10% 计费**；这意味着长而稳定的系统提示、工具定义、知识前缀一旦被缓存，重复请求能显著降本 [来源](https://docs.anthropic.com/en/docs/build-with-claude/prompt-caching)。文档同时强调，增加缓存断点（cache breakpoint）本身不额外收费，真正省钱的关键是**把稳定内容放前缀、动态内容放后缀**，让共享前缀能命中缓存。延迟侧，主流 API 都支持流式输出（streaming），让用户先看到首字（首 Token 延迟 TTFT，Time To First Token）从而降低感知等待；这属于各厂商 SDK（Software Development Kit，软件开发工具包）的公开能力。**通用工程模式**：延迟归因、模型分级、工具并发、结果缓存、会话预算上限，可迁移到任何自建系统。**教学参考实现**：上面的归因器与二八分析器为讲清方法而构造，真实分段耗时来自 Trace，真实 Token 分布来自计费日志。**边界**：Prompt Caching 的具体价格倍率、TTL 档位、最小可缓存长度会变化，一律以当前官方文档为准。

## 生产踩坑

| 症状 | 根因 | 如何观测与复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| 换快模型后延迟没降多少 | 未归因，推理其实非大头 | Trace 拆分模型/工具/轮次耗时占比 | 先归因再动最大头（常是工具/串行） | 推理确实是唯一大头时 |

| 检索每次都打向量库 | 高频结果无缓存 | 统计同一 query 重复率 | 高频结果缓存 + 设 TTL | 强实时且不可缓存的数据 |
| 全局压缩上下文后幻觉反弹 | 压缩伤到关键证据 | 压缩前后跑评估集比幻觉率 | 只压冗余历史，硬事实保留 | 无冗余可压时 |

## 思考：为什么「全局压缩上下文来降本」常常是个坏主意？

### 回答

因为「全局压缩」违背了「先归因再对症」的纪律，而且它降本的同时最容易伤到质量。先说降本效率：成本几乎总是二八分布——真正吃掉大头的通常是少数几个超长会话、或某个被反复调用的昂贵工具、或某类高轮次任务。如果你不做分布统计就「全局压缩上下文一半」，那些本来就很短的会话被你压了也省不了几个钱，而真正的大头（比如一个把全部历史塞进 Prompt 的长会话）可能还没被针对性处理。降本效率低是其一。其二，也是更危险的：全局压缩是「无差别」的，它会连同关键证据一起压掉，导致检索到的正确资料在压缩后丢失，模型「无米下锅」幻觉率反弹——这就是第 2 节讲的检索层失效。正确的做法是：先做 Token 分布统计找到大头，优先用「不伤质量」的手段（Prompt Caching 缓存稳定前缀、去掉冗余历史、简单任务分级到小模型），这些几乎零质量损失；只有在这些做完还不够时，才谨慎地做「可能伤质量」的激进压缩，而且每压一步都要跑评估集确认成功率和幻觉率没恶化。一句话：降本要按「先无损、后有损，先大头、后长尾」的顺序，而「全局压缩」既不分大头小头、又不分该压不该压，所以常常吃力不讨好还伤质量。

### 面试精简表达

全局压缩既低效又危险：低效是因为成本二八分布，不砍大头等于白压；危险是因为它无差别压掉关键证据，导致幻觉反弹。正确顺序是先做 Token 分布找大头，先用无损手段（缓存/去冗余/模型分级），有损压缩留到最后并逐步跑评估集验证。

## 深入：降本提速的正确顺序与「真慢 vs 感觉慢」

**降本提速有一个推荐顺序，本质是按「代价从小到大」排列。** 先做完全不伤质量的：给检索等高频工具加结果缓存、用 Prompt Caching 缓存稳定的系统提示与工具定义、把独立工具改成并发、把简单意图用规则短路不走完整 Agent。这些做完，故障板上的延迟通常已从 8.2s 降到 4s 左右、成本降到 ¥800 左右。接着做「模型分级」：意图分类、简单问答用小模型，只有复杂推理才调大模型——这一步对质量有轻微影响，所以要跑评估集确认成功率不掉。最后才动「激进上下文压缩、换更小模型」这类可能明显伤质量的手段，每动一步都回归验证。这样一路下来，延迟压到 2.8s、成本降到 ¥560，双双达标，且全程有评估集守住质量底线。

**还有一个必须掌握的区分——「真慢」和「感觉慢」。** 有时候总耗时其实在可接受范围（比如 2.8s），但用户「觉得慢」，因为他盯着一个不动的转圈图标干等。这时最有效的往往不是继续压缩耗时，而是**流式输出 + 展示中间进度**：先把首 Token 尽快吐出来（「正在为您查询订单…」「正在整理答复…」），让用户感到「系统在动」。能区分「客观延迟」和「主观等待焦虑」，并知道前者靠归因优化、后者靠流式与进度提示，是体验优化的重要意识——这也是面试里区分「只会压耗时」和「懂用户体验」的一个加分点。任何这类优化都别忘了谈权衡：流式会让「输出护栏」变复杂（你没法等全部输出再统一过滤），需要边流边检或分段检查，这个代价要主动说清。

## 思考：为什么说 Prompt Caching 对「长而稳定的前缀」特别划算？

### 回答

关键在于 Prompt Caching（提示缓存）的计价结构与「共享前缀」这一命中条件的组合。按 Anthropic 官方文档，缓存写入要付一次溢价（5 分钟 TTL（Time To Live，生存时间）档位约为基础输入价的 1.25 倍），但**缓存命中后的读取只按基础输入价的约 10% 计费** [来源](https://docs.anthropic.com/en/docs/build-with-claude/prompt-caching)。这意味着：只要某段内容会被大量后续请求重复读取，你就用「一次略贵的写入」换来「多次极便宜的读取」，复用次数越多、这段内容越长，摊薄下来越划算。

而客服 Agent 里最符合「长且稳定、且被反复读」这三个条件的，正是系统提示、工具定义（Schema）、政策知识前缀——它们在成千上万次请求里几乎一字不变，却每次都要被完整读入。把这些放进缓存前缀，就是拿最小改动撬动最大收益。反过来，用户每轮不同的问题、检索到的动态片段则不适合缓存，因为它们几乎不会重复命中。所以落地要点只有一句：**稳定内容前置当共享前缀、动态内容后置**，让缓存断点之前的部分能被稳定命中；一旦把动态字段（时间戳、随机 ID）误放到前缀里，共享前缀被打破，缓存读取会直接掉到零，这也是「生产踩坑」表里「缓存读取始终为零」那一行的根因。需要提醒的边界是：价格倍率、TTL 档位、最小可缓存长度都会随版本变化，落地前一律以当前官方文档为准，不要把某个具体倍率写死进假设里。
