> 对应故障板指标：**评估集覆盖真实场景 0 条 → ≥ 200 条**。这是原书**场景 6「如何评估你做的 Agent 到底好不好」**与**场景 9「一条历史数据都没有，怎么从零构建评估集」**的合并加深版。前者讲「评估什么、怎么评」，后者讲「没数据时评估集从哪来」，两者是同一件事的一体两面。

## 真实问题

前面几节所有的「验证」都指向同一个前提：一套能跑回归的评估集。可小蜜的故障板上，「评估集覆盖真实场景」赫然写着 0 条。产品经理问工程师「你怎么证明这版比上版好」，工程师说「我自己试了几个例子，感觉挺好的」——这句话是面试和生产里最大的红旗，它等于承认「我没有系统评估，全凭感觉」。

更棘手的是,这是个刚上线的新业务，几乎没有历史数据。工程师的下意识反应是「没数据没法评估」。但这是个误区：**没数据不等于不能评估，评估集可以自己造、再逐步积累真实数据长大**。这一节要解决两个问题：其一，评估一个 Agent 到底要评什么、用什么方法（场景 6）；其二，一条历史数据都没有时，评估集怎么从零冷启动（场景 9）。

## 原理一：Agent 评估比传统模型难在「多步、路径不唯一」

传统分类模型评估简单——输入对应唯一标签，算准确率即可。Agent 难在它是**多步、路径不唯一**的：同一个任务，它可能一步到位，也可能绕 10 步、调错 3 次工具最后蒙对。所以评估要分两个层次，两者缺一不可：
```text
① 结果评估（任务成了吗）：
   任务是否完成（成功率）、答案是否正确、是否有幻觉
   只看结果的漏洞：它可能绕了 10 步、调错 3 次工具才蒙对，成本高且不稳定

② 过程评估（路径合理吗）：
   轨迹是否合理——有没有多余的工具调用、路由对不对、是否陷入循环
   只看过程的漏洞：轨迹漂亮但最终答案错了也没用

两者都看：任务成了 ✔ 且路径高效合理 ✔ ——这才是真正的好
```
评估方法则按「答案是否唯一」来选：
```text
有唯一标准答案（数学、SQL 结果、分类）→ 规则/精确匹配：客观可靠、便宜、快
开放式质量（回答好不好、摘要全不全）→ LLM-as-a-judge：灵活，但有偏差，关键场景要人工抽样校准
过程合理性 → 分析轨迹：轮次数、工具调用次数、是否命中正确文档、是否路由正确
```
三种方法组合用，别指望一种搞定所有。LLM-as-a-judge（Large Language Model as a Judge，用大模型当裁判）是开放式质量评估的主力，但它本身有偏差，需要用人工标注去校准评估器——这一点后面会展开。

## 原理二：冷启动评估集的三步走

没有历史数据，评估集按「造种子 → 扩充 → 回流」三步长出来：
```text
① 冷启动·人工造种子集（宁可少而准）
   和业务方一起，把最典型、最重要的场景手写成 20-50 条
   「问题 + 期望答案/期望行为」，覆盖核心用例 + 已知的边界/易错情况
        │
        ▼
② 扩充·半自动生成（扩到几百条）
   用大模型基于种子集生成变体（换问法、换实体），人工快速筛一遍
        │
        ▼
③ 迭代·从线上回流真实案例（最宝贵）
   上线后（哪怕小流量灰度），把真实失败案例、用户投诉、边界情况
   持续收进评估集 —— 真实失败案例是最宝贵的评估数据
```
贯穿全书的一条原则：**评估集是长期演进的资产，随业务和踩坑不断长大**，不要追求一上来就搞个「完美的大评估集」。先有一个小而准的种子集能跑起来，比纠结覆盖率更重要。

## 最小可运行演示

下面用纯 Python 演示一个「双层评估器」：对客观题用规则精确匹配，对主观题用一个 mock 的 LLM-as-a-judge（用关键词命中模拟打分，确定性可复核），最后同时输出「结果指标」和「过程指标」。它不调用任何真实模型。
```python
"""第24.5节：结果+过程双层评估器（纯 Python，无需 API Key）。"""
from dataclasses import dataclass


@dataclass
class Case:
    q: str
    kind: str            ## "objective"(规则判) 或 "subjective"(judge 判)
    expect: str          ## 客观题的标准答案 / 主观题的关键信息点
    answer: str          ## Agent 实际回答
    steps: int           ## 过程：本次用了几步
    max_steps: int       ## 过程：该任务合理步数上限


def rule_match(expect: str, answer: str) -> bool:
    return expect.strip() == answer.strip()


def mock_judge(key_points: str, answer: str) -> float:
    ## 教学 mock：命中的关键信息点比例当作 judge 分数
    pts = [p for p in key_points.split("|") if p]
    hit = sum(1 for p in pts if p in answer)
    return round(hit / len(pts), 2) if pts else 0.0


def evaluate(cases: list) -> dict:
    result_pass, process_ok = 0, 0
    for c in cases:
        ok = rule_match(c.expect, c.answer) if c.kind == "objective" \
            else mock_judge(c.expect, c.answer) >= 0.6
        result_pass += int(ok)
        process_ok += int(c.steps <= c.max_steps)   ## 过程：没超合理步数
    n = len(cases)
    return {"结果成功率": f"{result_pass}/{n}",
            "过程合理率": f"{process_ok}/{n}"}


def run() -> None:
    cases = [
        Case("1+1=?", "objective", "2", "2", 1, 2),
        Case("七天无理由能退吗", "subjective", "7天|无理由|符合条件",
             "符合条件的商品支持7天无理由退货", 2, 3),
        Case("退款到账时间", "subjective", "原路退回|1-7个工作日",
             "会退回", 6, 3),                      ## 信息不全 + 绕了 6 步
    ]
    print(evaluate(cases))


if __name__ == "__main__":
    run()
```
保存为 `s5_eval.py`，运行 `python s5_eval.py`。完整预期输出：
```text
{'结果成功率': '2/3', '过程合理率': '2/3'}
```
看第三条「退款到账时间」：它结果不合格（judge 打分低，因为漏了「原路退回」「1-7 个工作日」两个关键点），过程也不合格（用了 6 步超过合理上限 3 步）。这条正是「只看结果」或「只看过程」都会漏判、必须两者都看的例子——如果只看过程，它步数超标会被抓；如果只看结果，它信息不全会被抓；两个维度合起来才画出完整的「不够好」。

## 真实系统对应

**官方公开机制**：LangSmith 把评估建模为「数据集（Dataset）+ 评估器（Evaluator）+ 目标函数（Target function）」——数据集是一组测试输入与可选的参考输出，评估器给目标函数的输出打分，目标函数可以是单次 LLM 调用、一个模块或整条工作流 [来源](https://docs.langchain.com/langsmith/evaluation-quickstart.md)。它明确区分了「有参考答案用启发式/规则判分」与「无参考答案时越来越多用 LLM-as-a-judge 做分类/打分」两种模式 [来源](https://docs.smith.langchain.com/evaluation/concepts)。更关键的是，官方专门给出「用人工反馈改进 LLM-as-a-judge 评估器」的流程——把实验运行加入标注队列让人工专家标注，再用标注样本找出评估器与人工不一致的案例，迭代评估器 Prompt 提升对齐度 [来源](https://langchain.docs-hub.com/langsmith/improve-judge-evaluator-feedback)。这正印证了本节「LLM-as-a-judge 有偏差，关键场景要人工校准」的说法。**通用工程模式**：结果+过程双层评估、冷启动三步走、把失败案例回流成回归资产，可迁移到任何系统。**教学参考实现**：上面的 `mock_judge` 用关键词命中模拟评分为可复核而构造，真实系统用真实模型当裁判并配打分 Prompt。**边界**：LangSmith 的具体 API、评估器类型以当前官方文档为准。

## 生产踩坑

| 症状 | 根因 | 如何观测与复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| 「试了几个例子感觉不错」 | 无系统评估集 | 问「成功率多少」答不出数字 | 建覆盖真实场景的评估集算指标 | 纯探索期一次性 demo |
| 只看最终对不对 | 缺过程评估 | 蒙对的案例是否绕了很多步没被抓 | 加轨迹评估：轮次/工具次数/路由 | 单步任务无过程可言 |
| judge 打分和人不一致 | 评估器 Prompt 未校准 | 抽样人工标注对比 judge 分 | 用人工标注迭代评估器 Prompt | 客观题不需要 judge |
| judge 偏爱长答案 | LLM-as-a-judge 固有偏差 | 灌长短两版同质答案看分差 | 校准 + 关键场景人工抽检 | 已知无长度偏好时 |
| 改好 A 弄坏 B | 改动后不跑全量回归 | 只测新样本不测老样本 | 每次改动跑全评估集回归 | 一次性脚本 |
| 评估集覆盖不到真实坑 | 只造了理想样本 | 线上失败在评估集里找不到 | 把真实失败案例持续回流 | 业务极度稳定不变 |
| 追求一步到位大评估集 | 纠结覆盖率迟迟不上线 | 评估集迟迟建不完 | 先小而准跑起来再演进 | 高危领域需先充分覆盖 |
| 随机堆量但没抓住关键 | 数量优先于质量 | 5000 条却漏掉核心失败 | 精选覆盖核心用例+已知边界 | 需大样本统计显著性时 |
| 客观题也用 judge 打分 | 方法选错、又贵又飘 | 有标准答案却用模型判 | 有唯一答案就用规则匹配 | 答案表述多样需语义判 |
| 指标全绿但用户仍不满 | 只量代理指标 | 只测格式/长度不测任务成功 | 加端到端任务成功与约束遵循 | 指标不取代人工复核 |

> **加分对照·评估的红旗 vs 加分**：

| 维度 | 红旗回答 ❌ | 加分回答 ✅ |
|---|---|---|
| 意识 | 「我试了几个例子感觉不错」 | 有覆盖真实场景的评估集，每次改动跑回归 |
| 维度 | 只看最终答案对不对 | 结果评估 + 过程评估（轨迹是否合理） |
| 方法 | 全靠人眼看/一种方法打天下 | 客观题规则匹配、主观题 judge、抽样人工校准 |
| 没数据 | 「没数据没法评估」 | 人工造种子 + 大模型扩充 + 线上回流 |
| 演进 | 一次做完不管了 | 把真实失败案例持续收进评估集 |

## 思考：为什么「我自己试了几个例子感觉不错」是最大的红旗？

### 回答

因为这句话暴露了三个致命缺陷，任何一个在生产里都是灾难。第一，它无法区分「系统性变好」和「样本偶然蒙对」——你试的那几个例子可能恰好是模型擅长的，换一批就露馅，没有覆盖真实分布的评估集，你根本不知道整体成功率是多少。第二，它无法防止「改好 A 弄坏 B」的回归退化——你优化了退款场景，感觉不错就上线，却不知道这个改动可能悄悄弄坏了物流查询场景，因为你没有一套固定的回归集在每次改动后全量跑一遍。第三，它无法量化，也就无法比较和迭代——产品问「这版比上版好多少」，你只能说「感觉好一些」，而有评估集的人能说「成功率从 83% 提到 91%、幻觉率从 6.1% 降到 0.7%」。这三点合起来，说明「感觉不错」的人没有建立起「评估驱动」的工作方式，而评估驱动恰恰是资深与新手的分水岭：资深工程师的每一次优化都伴随「改动前后在固定评估集上的指标对比」，用数据说话而非凭感觉。所以面试官一听到「试了几个例子感觉不错」，基本就判定这个人没有真正的生产经验——因为凡是把 Agent 真正跑到线上并对质量负过责的人，都会被「改好一处弄坏另一处」的教训逼出评估集，绝不敢靠感觉。

### 面试精简表达

「感觉不错」有三宗罪：无法区分系统性变好与偶然蒙对、无法防回归退化、无法量化比较。评估驱动（每次改动在固定评估集上跑回归、用指标说话）是资深与新手的分水岭，没有评估集基本等于没有生产经验。

## 深入：从 0 到 200 条的落地过程与「质量 > 数量」

小蜜的评估集是这样从 0 长到 200 条的。**第一周·种子集**：产品、客服主管和工程师一起开了两小时会，把最高频和最要命的场景手写成 40 条——20 条核心用例（查订单、查物流、七天无理由、退款流程等），20 条已知易错的边界 case（涉投诉的、知识库没有的、参数容易传反的、含糊表述的）。宁可只有 40 条，但每条都精准对应一个「我们真正在乎的失败」。**第二周·扩充**：用大模型基于这 40 条种子生成变体（同一个意图换 5 种问法、换不同订单号和商品），人工快速筛掉不合理的，扩到约 220 条，并给每条标注「测什么指标」（成功率/幻觉/格式合规/是否正确转人工）和「客观题还是主观题」。**上线后·回流**：小流量灰度期间,把真实的失败案例、用户投诉、边界情况持续收进评估集——前两节里那 60 条幻觉样本、那些传参错误和误路由案例，全部沉淀成了回归资产。

这里有个反直觉但极重要的原则：**质量 > 数量**。50 条精心设计、覆盖关键场景和已知坑的用例，比 5000 条随机生成的更有用。因为评估集的价值不在「大」，而在「能不能抓住你真正在乎的失败」。设计种子集时，要特别包含**已知会出错的边界 case**——这些才是回归测试真正要守住的防线。前面每一节的「验证」都靠这套评估集坐实：第 2 节幻觉率的下降曲线、第 3 节降本后成功率没掉、第 4 节路由准确率从 83% 到 96%，全都是在这 220 条上跑出来的数字。评估集就是把「先分析再方案」的场景题心法闭环的那最后一环——**没有它，前面所有的「优化」都只是「感觉」；有了它，每一步优化才成了「用数据说话」的工程。**
