> 对应故障板指标：**工具传参错误率 12% → ≤ 2%**、**路由准确率 83% → ≥ 95%**。这是原书**场景 3「Agent 调用工具时经常传错参数」**与**场景 4「多 Agent 系统请求经常被路由到错误的 Agent」**的合并加深版。两者的共同心法是同一句：**先反思自己写的描述与拆分，别一上来怪模型太笨**。

## 真实问题

小蜜有两个「自作聪明」的毛病，都被误当成「模型不行」。

其一，退款工具经常传反参数。有一次用户说「我 3 月 1 日下单、3 月 5 日想退」，小蜜调用 `refund(order_id, start_date, end_date)` 时把 `start_date` 填成了 3 月 5 日、`end_date` 填成 3 月 1 日，导致「退货窗口为负」直接报错。传参错误率高达 12%。

其二，路由老是分错。一位用户说「我的订单金额不对，是不是多扣了钱，我要投诉」，路由模型把它判给了「订单查询 Agent」——因为「订单」「金额」这些词压过了「投诉」。订单 Agent 只查了下订单状态回「金额无误」，用户情绪进一步升级。路由准确率只有 83%。

两个毛病，团队的第一反应都是「模型太笨，换个更强的」。但真相是：**传参错误 80% 是工具描述（description）没写清楚参数之间的约束，路由错误则要先区分是「职责描述不清」还是「拆分本身有问题」**。改自己，往往比换模型见效快得多。

## 原理一：传错参数的五步排查顺序

模型传错参数，成熟工程师的第一反应不是「模型笨」，而是「我的工具是不是没定义好」。按下面五步顺序排查，这个顺序本身就是加分点——它体现「先改自己再怪模型」的心态：
```text
模型传错参数
   │
   ① 先看 description：说清用途、何时用、参数间约束了吗？ ──▶ 改清楚
   │     （最高频根因：如 start_date 必须早于 end_date，却没写）
   ② 再看参数说明：每个参数有类型 + 描述 + 示例吗？        ──▶ 补示例格式
   │
   ③ 加 schema 校验：非法参数能被拦住吗？                   ──▶ Pydantic 校验 + 错误喂回让模型改
   │
   ④ 看工具复杂度：参数太多、职责太杂？                     ──▶ 拆成几个简单工具
   │
   ⑤ 都做了还错：真是模型能力不足？                         ──▶ 换更强模型 / 加 few-shot（少样本）示例
```
最关键的是第①步里那个「参数间约束」：最常见的根因不是单个参数说不清，而是**参数之间的隐含约束没写进 description**。比如「预订/退货」工具里 `start_date` 必须早于 `end_date`，description 没写，模型就可能传反。把这类隐含约束显式写进 description，比事后校验更省事——事后校验只能拦下错误让模型重试（增加一轮延迟），而写清约束能让模型第一次就传对。

## 原理二：路由错误的两种根因，药方完全不同

多 Agent 路由错误有两种根因，混为一谈就会开错药：

1. **职责描述不清（软件问题）**：Agent 的边界在路由 Prompt 里没说清楚，模型分不清「这个问题该给谁」。**药方**：优化路由 Prompt、加 few-shot 例子、明确每个 Agent「负责什么、不负责什么」；对涉钱涉投诉这种红线，用规则前置无条件转人工，不交给模型判断。
2. **拆分本身有问题（架构问题）**：两个 Agent 的职责本来就高度重叠（比如「订单查询」和「物流查询」经常同时被一句话触发），再怎么优化 Prompt 都分不清。**药方**：合并这两个 Agent，而不是继续加规则。

怎么区分这两种根因？**看误路由案例的分布**：如果错误分散、各种各样，多半是描述不清；如果错误高度集中在「某两个 Agent 之间互相误分」，那就是这两个的拆分有问题。先分析误判模式，再决定是调 Prompt 还是改架构——这个诊断思路很能体现系统思维。故障板那条「金额不对我要投诉」被判成 order，属于第一种（红线该规则前置却没有），修法是把「投诉/赔偿/12315」这类高风险词做成规则红线，命中即无条件转人工。

## 最小可运行演示

下面用纯 Python 演示两件事：一个带参数约束校验的退货工具（模拟「schema 校验 + 错误喂回」），一个「误路由模式分析器」（统计错误分布判断是描述问题还是拆分问题）。都不调用真实模型。
```python
"""第24.4节：工具参数校验 + 误路由模式分析（纯 Python，无需 API Key）。"""
from collections import Counter
from datetime import date


## —— 传参：schema 校验 + 把错误喂回让模型改 ——
def refund(order_id: str, start: date, end: date) -> str:
    if start > end:
        ## 不合法就返回明确错误，供模型据此修正（而非直接崩溃）
        return f"ERROR: start({start}) 必须早于 end({end})，请交换后重试"
    return f"OK: 已为 {order_id} 受理退货窗口 {start}~{end}"


## —— 路由：分析误判分布，区分描述问题 vs 拆分问题 ——
def diagnose_routing(mis_routes: list) -> str:
    ## mis_routes 每项形如 ("真实意图", "被错分到")
    pairs = Counter(tuple(sorted(m)) for m in mis_routes)
    top_pair, top_cnt = pairs.most_common(1)[0]
    concentration = top_cnt / len(mis_routes)
    if concentration >= 0.6:
        return (f"误判集中在 {top_pair}（占 {concentration:.0%}）"
                f" -> 拆分问题：考虑合并这两个 Agent")
    return "误判分散 -> 描述问题：优化路由 Prompt + few-shot + 红线规则前置"


def run() -> None:
    print(refund("O-778", date(2026, 3, 5), date(2026, 3, 1)))  ## 传反
    print(refund("O-778", date(2026, 3, 1), date(2026, 3, 5)))  ## 正确
    print(diagnose_routing([("order", "logistics"), ("order", "logistics"),
                            ("order", "logistics"), ("knowledge", "order")]))
    print(diagnose_routing([("order", "knowledge"), ("logistics", "human"),
                            ("knowledge", "order"), ("human", "logistics")]))


if __name__ == "__main__":
    run()
```
保存为 `s4_tool.py`，运行 `python s4_tool.py`。完整预期输出：
```text
ERROR: start(2026-03-05) 必须早于 end(2026-03-01)，请交换后重试
OK: 已为 O-778 受理退货窗口 2026-03-01~2026-03-05
误判集中在 ('logistics', 'order')（占 75%） -> 拆分问题：考虑合并这两个 Agent
误判分散 -> 描述问题：优化路由 Prompt + few-shot + 红线规则前置
```
前两行演示「schema 校验 + 错误喂回」：传反时不崩溃，而是返回一句人类和模型都能读懂的错误，模型据此就能交换重试。后两行演示误路由诊断：第一批 75% 的错误都集中在 order↔logistics，判为「拆分问题、该合并」；第二批错误分散，判为「描述问题、调 Prompt」。**同样是路由错，诊断器把它们导向了完全不同的修法**——这正是场景 4 的核心。

## 真实系统对应

**官方公开机制**：工具的行为高度依赖其描述与参数 schema，这是各家函数调用/工具使用能力的公开事实——模型完全靠 description 和参数 schema 理解「这个工具干什么、参数怎么填」。OpenAI 把「检查工具调用的参数与结果」单列为 tool guardrail 一类控制手段 [来源](https://developers.openai.com/api/docs/guides/agents/guardrails-approvals.md)。路由侧，LangGraph 的 supervisor（监督者）拓扑里，中心协调者「接收每条消息、分类意图、路由到专家、专家答完控制权回到 supervisor」，正是本节路由的位置；而当两类专家职责高度重叠时，官方也建议重新审视拓扑而非无限加规则 [来源](https://langchain-ai.github.io/langgraph/concepts/multi_agent/)。Anthropic《Building Effective Agents》则主张能用简单可组合模式就不上复杂架构，多 Agent 复杂度必须由收益证明——这正对应「职责重叠就合并、别越拆越乱」[来源](https://www.anthropic.com/engineering/building-effective-agents)。**通用工程模式**：五步排查、schema 校验错误喂回、误路由分布分析、红线规则前置，可迁移到任何系统。**教学参考实现**：上面的 `refund` 与 `diagnose_routing` 为讲清方法而构造，真实校验常用 Pydantic，真实误判分布来自路由日志。**边界**：各家工具调用的字段名、schema 规范以当前官方文档为准。

## 生产踩坑

| 症状 | 根因 | 如何观测与复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| 日期/范围类参数传反 | description 没写参数间约束 | 用「先后顺序」类输入复现 | 把 start<end 等约束写进 description | 参数间本无约束时 |
| 参数格式五花八门 | 参数缺类型和示例 | 看错误参数是否格式各异 | 每个参数给类型+描述+示例格式 | 自由文本参数 |
| 非法参数直接崩溃 | 无 schema 校验 | 灌入越界值看是否抛异常 | Pydantic 校验，错误喂回让模型改 | 内部可信调用 |
| 一个大工具老填错 | 参数太多、职责太杂 | 统计该工具错误率是否偏高 | 拆成几个单一职责的小工具 | 参数确实必须一起给 |
| 投诉被当普通咨询 | 缺红线规则，全交给模型 | 用「订单+投诉」混合句复现 | 高风险词规则前置无条件转人工 | 无敏感语义的场景 |
| 含糊问题被硬分到某专家 | 无低置信兜底，取 argmax | 灌语义含糊句看是否仍硬分 | 置信度低于阈值转人工兜底 | 意图空间极小且互斥 |
| 某两个 Agent 反复互相误分 | 拆分本身职责重叠 | 统计误判是否集中在某对 | 合并这两个 Agent，别加规则 | 职责其实清晰只是描述差 |
| 越拆越多反而更难路由 | 无脑加 Agent 分流 | 对比 Agent 数与路由准确率 | 先看误判模式再决定合还是拆 | 领域确实需要细分专家 |
| 换了更强模型仍传错 | 根因在描述不在能力 | 固定描述只换模型看是否改善 | 回到第①步先改 description | 已排除工程因素确属能力上限 |
| 路由决策不可复盘 | 未记录 (label, score, reason) | 看日志有无路由三元组 | 每次路由写入可观测三元组 | 一次性脚本 |

> **加分对照·传参与路由的红旗 vs 加分**：

| 维度 | 红旗回答 ❌ | 加分回答 ✅ |
|---|---|---|
| 传参归因 | 「模型太笨/太蠢」 | 「先反思我的工具描述是不是没写清楚」 |
| description | 只写一句话干什么 | 说清用途、何时用、参数间约束关系 |
| 校验 | 不校验或直接崩 | schema 校验 + 非法参数喂回让模型改 |
| 路由第一反应 | 「再加个 Agent 分流」 | 先看误判模式，分描述问题还是拆分问题 |
| 路由架构 | 一味加 Agent 越拆越细 | 职责重叠就合并，红线规则前置 |

## 思考：为什么说「传错参数先反思工具描述」体现了实战经验，而「模型太笨」是新手信号？

### 回答

因为这两种归因方向，反映了你有没有真正调过工具、看过失败案例。新手没做过工程，遇到传参错误的第一反应是把锅甩给模型能力——「模型太笨，换个强的」。但真实经验会告诉你：模型完全靠工具的 description 和参数 schema 来理解「这个工具干什么、参数怎么填」，它看不到你脑子里的隐含约定。传参错误里高达八成的根因，其实是**工具定义没写清楚**，尤其是参数之间的隐含约束。举个具体的：退货工具 `refund(order_id, start_date, end_date)`，你心里知道 start 必须早于 end，但如果 description 里没写这条约束，模型面对「3 月 1 日下单、3 月 5 日退」这种输入，就可能按它读到的语序把日期填反。这时候换个更强的模型，它照样可能填反——因为问题不在能力，在你没告诉它约束。有经验的人会按五步顺序排查：先改 description 写清约束和示例，再加 schema 校验把非法参数拦下并喂回错误让模型自己改，还不行才考虑拆工具或换模型。「先改自己再怪模型」不只是态度问题，它对应一个客观事实——你能改的（描述、schema、拆分）见效快且便宜，而「换模型」既贵又常常治不了根。能说出「传参错误大多是描述问题，且参数间的隐含约束最容易被漏写」，就证明你真的排查过，而不是纸上谈兵。

### 面试精简表达

模型只靠 description 和 schema 理解工具，传参错误八成是描述没写清、尤其是参数间约束（如 start<end）被漏写。换强模型治不了这种根因。有经验的人按「改描述→补示例→加校验喂回→拆工具→才换模型」五步排查，先改自己见效快又便宜。

## 深入：从「一个黑箱 label」到「可解释、可迭代」的路由

优化前，小蜜的路由是一行 `label = classifier(q)`，直接取模型的 argmax（最大概率类别）。它有三个致命问题：一是**没有红线**，涉投诉/赔偿的输入完全交给模型判断，被「订单」「金额」等词带偏就误路由；二是**没有兜底**，含糊输入被强行归到某个专家，答非所问；三是**不可解释**，出了错只能看到一个 label，不知道模型有多确信、为什么这么分，根本没法复盘。

优化后引入「规则红线 → 模型分类 → 置信度兜底」三层，并让每次路由都产出 `(label, score, reason)` 三元组写进 Trace。可观测性随之提升：运营能统计「多少比例走了规则红线、多少走了低置信兜底、模型平均置信度多高」。这些数字反过来指导优化——比如低置信兜底里如果反复出现「保修相关」问题，说明该新增一个「售后保修」专家类别（这正是数据飞轮里「从低置信日志挖新意图」的来源）。落地后，故障板上路由准确率从 83% 提到 96%：其中规则前置把「投诉误分」这类高危错误直接清零，置信度兜底把「含糊硬分」转给人工，剩余误判经分布分析发现 order↔logistics 占比过高、于是把两者合并为「订单物流一体 Agent」，一举消除了最集中的那簇错误。传参侧同步把所有工具 description 补齐参数约束、接入 Pydantic 校验并把错误喂回，传参错误率从 12% 降到 1.8%。两个指标的改善，靠的都不是「换更强的模型」，而是「改自己的描述、拆分与校验」——这就是资深与新手在这道题上的分水岭。
