> 对应故障板：**评估集/数据从 0 起步的冷启动**、以及决定「哪些让 Agent 自动做、哪些必须人来做」的**人机协作边界**。这是原书**场景 10「全新业务冷启动没什么用户数据，Agent 效果怎么冷启动」**与**场景 11「什么时候该让 Agent 自动做、什么时候必须让人来做」**的合并加深版，也是全章的收尾——它把前六节的排障能力，落到「一个新 Agent 从零上线」的完整决策上。

## 真实问题

小蜜其实是从零起步的：上线第一天，没有任何历史对话、没有标注数据、没有已知的失败案例。团队面临两个纠结。

其一是**冷启动的心态**：有人主张「等积累够数据再上线，否则效果没保证」，于是产品迟迟不敢发布，陷入「没数据→不敢上→更没数据」的死循环。

其二是**人机边界的两极摇摆**：技术乐观派主张「能自动就全自动，退款、改地址都让 Agent 直接做」，结果第 14 天就出了那起「模型一句话承诺全额退款 328 元」的事故；被吓到之后又走向另一极端「所有操作都要人工确认」，结果 Agent 慢得还不如人工客服，失去了存在价值。

这两个纠结的答案，恰恰构成一个新 Agent 上线的完整方法论：**冷启动靠「规则兜底 + 飞轮」先跑起来，人机边界靠「风险 × 可逆性」分级**。

## 原理一：冷启动的正向飞轮——别憋大招

冷启动最忌「憋大招」——想把所有情况都想全了再上线。更好的做法是**先上一个有兜底、有人工审核的小版本，在真实使用中滚动数据和优化**。几个抓手：
```text
① 规则/知识兜底：数据少时别指望模型学出一切。把已知业务规则、FAQ、
   流程写进 Prompt 或做成工具，让 Agent 先有个「及格线」
② 借助模型通用能力：LLM 本身有大量通用知识，很多任务不需要私有数据就能做得不错
③ 人在环中（HITL，Human-in-the-Loop，人在环中）：冷启动阶段让人工审核/兜底
   Agent 输出，既保证质量，又顺便积累「人是怎么处理的」这类高质量数据
④ 小流量灰度 + 快速迭代：先给一小部分用户/场景用，密切观察，快速收集失败案例
⑤ 合成数据：必要时用 LLM 生成训练/评估用的合成数据，但要人工把关质量
```
这几个抓手转起来，就是一个正向飞轮：
```text
规则/通用能力兜底 → 小流量上线 → 人工审核+收集真实案例
        ↑                                    │
        └──── 优化 Prompt/工具/评估集 ←───────┘
（数据越用越多，效果越滚越好，形成飞轮）
```
注意这个飞轮和第 5 节的「冷启动评估集三步走」是同一个飞轮的两面：一面积累「评估用」的失败案例，一面积累「优化用」的真实数据。它们靠同一批线上回流数据驱动。

## 原理二：人机协作边界——按「风险 × 可逆性」分级

决定「自动 vs 人工」的核心原则，是按**操作的风险高低 × 可逆性**两个维度给操作分级，而不是「要么全放、要么全管」：
```text
低风险 + 可逆（查询、读取、生成草稿）
   → 全自动：出错了也没大碍、能撤销
中风险（改配置、批量操作）
   → 自动执行但记录可回滚，或给人一个「撤销窗口」
高风险 或 不可逆（转账、退款、删数据、发对外邮件、提交代码）
   → 人工确认后执行
```
除了按操作分级，还有几个**必须转人的时机**：Agent 置信度低、连续失败达到上限、用户明确要求转人工、涉及情感/投诉等需要人情味的场景。设计时要让转人工是「优雅移交」（带上下文摘要给人工），而不是生硬报错。

一句能记住的原则:**「让 Agent 自动做那些'做错了能轻松改回来'的事，让人来把关那些'做错了改不回来'的事。」** 可逆性是设计人机边界最实用的那把尺子。

## 最小可运行演示

下面用纯 Python 演示两件事：一个「操作分级决策器」（按风险 × 可逆性 + 置信度决定自动/审批/转人工），一个「冷启动兜底路由」（数据少时优先走规则，规则未命中再走模型，低置信转人工）。不调用任何真实模型。
```python
"""第24.7节：操作分级 + 冷启动兜底（纯 Python，无需 API Key）。"""
from dataclasses import dataclass


@dataclass
class Action:
    name: str
    risk: str            ## "low"/"mid"/"high"
    reversible: bool
    agent_confidence: float


def decide(a: Action) -> str:
    if a.risk == "high" or not a.reversible:
        return f"[{a.name}] 高风险或不可逆 → 人工确认后执行"
    if a.agent_confidence < 0.6:
        return f"[{a.name}] 置信度低({a.agent_confidence}) → 转人工兜底"
    if a.risk == "mid":
        return f"[{a.name}] 中风险 → 自动执行 + 记录可回滚 + 撤销窗口"
    return f"[{a.name}] 低风险可逆 → 全自动"


## 冷启动：规则兜底优先，未命中走模型，低置信转人工
FAQ_RULES = {"营业时间": "9:00-21:00", "退货时限": "7 天无理由"}


def cold_start_answer(q: str, model_conf: float) -> str:
    for k, v in FAQ_RULES.items():
        if k in q:
            return f"[规则命中] {k} → {v}"
    if model_conf < 0.6:
        return "[低置信] 转人工（并把这条记入待补 FAQ）"
    return f"[模型通用能力] 作答（置信度 {model_conf}）"


def run() -> None:
    for a in [Action("查订单状态", "low", True, 0.9),
              Action("批量改优惠券", "mid", True, 0.8),
              Action("退款 328 元", "high", False, 0.95),
              Action("推荐商品", "low", True, 0.4)]:
        print(decide(a))
    print(cold_start_answer("你们退货时限多久", 0.9))
    print(cold_start_answer("能帮我搭配一套穿搭吗", 0.5))


if __name__ == "__main__":
    run()
```
保存为 `s7_boundary.py`，运行 `python s7_boundary.py`。完整预期输出：
```text
[查订单状态] 低风险可逆 → 全自动
[批量改优惠券] 中风险 → 自动执行 + 记录可回滚 + 撤销窗口
[退款 328 元] 高风险或不可逆 → 人工确认后执行
[推荐商品] 置信度低(0.4) → 转人工兜底
[规则命中] 退货时限 → 7 天无理由
[低置信] 转人工（并把这条记入待补 FAQ）
```
看第三条「退款 328 元」：哪怕 Agent 置信度高达 0.95，因为它高风险且不可逆，也强制走人工确认——这正是能拦住第 14 天那起事故的关键。第四条「推荐商品」虽是低风险，但置信度只有 0.4，触发转人工兜底。冷启动侧，「退货时限」直接命中规则秒答（不依赖数据），「穿搭」低置信转人工并把这条记入待补 FAQ——数据就是这样一条条滚起来的。

## 真实系统对应

**官方公开机制**：OpenAI 把 human-in-the-loop approvals 单列为一类控制手段——对有副作用的敏感动作，在执行前暂停等待人工批准 [来源](https://developers.openai.com/api/docs/guides/agents/guardrails-approvals.md)。OpenAI Agents SDK 进一步给出机制：敏感工具声明为需审批，运行结果把「待处理审批」作为中断（interruption）暴露，用 `RunState` 序列化暂停的运行，在人工决策后恢复——这正是「高危动作人工确认」的工程实现 [来源](https://openai.github.io/openai-agents-python/human_in_the_loop/)。冷启动侧，OpenAI《A practical guide to building agents》建议从单 Agent 起步、真正需要时再扩展，并把人工护栏与评估列为上线必备 [来源](https://cdn.openai.com/business-guides-and-resources/a-practical-guide-to-building-agents.pdf)；Anthropic《Building Effective Agents》主张能简则简、复杂度由收益证明——都支持「先小步跑起来、别憋大招」[来源](https://www.anthropic.com/engineering/building-effective-agents)。**通用工程模式**：风险 × 可逆性分级、必须转人时机、优雅移交、冷启动飞轮、合成数据，可迁移到任何系统。**教学参考实现**：上面的 `decide` 与 `cold_start_answer` 为讲清方法而构造，真实置信度来自分类器或结构化输出。**边界**：SDK 的中断/恢复字段名以当前官方文档为准。

## 思考：为什么说「全自动」和「啥都要人确认」是两个都不好的极端，好的设计是什么？

### 回答

因为这两个极端各自放弃了 Agent 价值天平的一端，而好的设计是在天平上按每个操作的具体风险找平衡点。先看「全自动」的问题：它在高危场景会闯大祸。故障板第 14 天那起「模型一句话承诺全额退款 328 元」的事故就是典型——退款是不可逆的、有真金白银副作用的操作，把它交给一个会被情绪化话术带偏的模型自动执行，等于把公司的钱包交给一个不设防的自动门。再看「啥都要人确认」的问题：它让 Agent 失去了存在的意义。如果连「查个订单状态」「回答营业时间」这种零风险、可逆的操作都要人工点一下确认，那 Agent 比人工客服还慢、还占人力，用户不如直接找人工——这时候上 Agent 纯属负优化。所以两个极端的共同错误，是用「一刀切」代替了「按操作分级」。好的设计是按「风险 × 可逆性」两个维度给操作分级，在正确的地方设正确的关卡：低风险可逆的（查询、生成草稿）全自动，让 Agent 发挥效率优势；高风险或不可逆的（退款、删数据、发对外邮件）必须人工确认，把住安全底线；中间的（改配置、批量操作）自动执行但记录可回滚、留撤销窗口。再叠加几个「必须转人」的时机（置信度低、连续失败、用户要求、投诉等需人情味的场景）作为动态兜底，并让转人工是「带上下文的优雅移交」而非生硬报错。这样既守住了「做错了改不回来」的红线，又释放了「做错了能轻松改回来」那部分的自动化价值。一句话概括这把尺子：**可逆性决定谁来做——能改回来的让 Agent 做，改不回来的让人把关。**

### 面试精简表达

全自动在高危场景闯大祸（如自动承诺退款），全人工则让 Agent 失去价值（查订单也要点确认）。好设计按「风险×可逆性」分级：低风险可逆全自动、高风险不可逆人工确认、中风险可回滚+撤销窗口，再叠加置信度低/连续失败/投诉等必须转人的时机，且转人工要带上下文优雅移交。

## 深入：把 11 道场景题收敛成一副「满分骨架」

走到这里，本章 11 道场景题(幻觉、延迟、成本、传参、路由、评估、注入、稳定、冷启动评估、业务冷启动、人机边界)全部讲完。回头看,它们表面各异,内核却是同一副骨架——这也正是第 1 节心法的印证。几乎每道场景题,你都可以用下面这段「万能收尾」体现深度:

> 「我会**先用 Trace / 数据定位到底是哪一层的问题**,而不是凭感觉猜;定位后**分层给方案、说清先做哪个、为什么**;改完**跑评估集做回归**,确认真的变好、且没引入新问题。而且我知道任何优化都有代价,比如……(说一个权衡)。」

这段话把「定位—方案—验证—权衡」四件事一次讲全,是场景题的标准满分骨架。把它套进本章每道题验证一遍:**幻觉**——定位靠看 Trace 里 retrieved_docs,分检索/融合/Prompt/输出四层,验证靠幻觉率从 6.1% 到 0.7% 的下降曲线,权衡是加引用护栏增延迟;**延迟成本**——定位靠 Trace 归因和 Token 二八分析,先砍最大头,验证靠评估集确认降本没掉质量,权衡是模型分级可能轻微伤质量;**传参路由**——定位靠误判分布,先改描述再怪模型,验证靠传参错误率和路由准确率,权衡是拆合工具各有代价;**注入稳定**——定位靠红队集和归因,纵深防御/先稳输入,验证靠拦截率和一致率,权衡是注入无法一劳永逸;**冷启动人机边界**——定位靠飞轮的迭代斜率,规则兜底+风险分级,验证靠回流数据驱动的改善,权衡是自动化与可控性的取舍。

场景题的加分动作也在这副骨架里:**先分析再方案**(展示拆解能力)、**用数据说话**(一切基于测量)、**暴露真实踩坑**(说「我遇到过 X,根因是 Y」比理论更有说服力)、**主动谈权衡**(任何优化都有代价)。把这四点和「定位—方案—验证—权衡」四段结构焊在一起,你面对任何没见过的场景题,都能现场拆解、给出有条理的排查,并用故障板那样的数字把「我怎么证明改好了」坐实。这,就是场景与实战题真正要考的能力——**把技术知识翻译成可验证的排障方案**。
