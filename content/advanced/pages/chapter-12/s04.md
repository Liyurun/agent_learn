## 真实问题

报销团队的选型备忘录写到最后，卡在了"怎么让后来人不再重蹈覆辙"这一步。第一版备忘录是一张"需求→框架"的查找表，看起来清楚，但真到新项目落地时又出了岔子：一位工程师拿到"做一个客服工单分类 Agent"的需求，对着查找表找不到"客服工单"这一行，于是随手选了个"看起来功能最全"的框架——又一次唯功能论。问题出在哪？**查找表是"按需求名查框架"，可现实的需求往往描述得含糊、不在表里**，真正需要的是一套**能对任意模糊需求层层追问、自动收敛出答案**的方法。

这一节把选型整理成一棵**决策树**：它不靠"需求关键词匹配"，而靠"按顺序回答几个本质问题"来收敛。核心哲学是——**先排除不需要的，再在剩下的里选最匹配的**，而不是一上来就比谁功能多。

## 原理：一张可落地的选型决策树

真实选型往往需要层层追问。把选型整理成一棵决策树，按顺序回答几个问题即可收敛：
```text
开始
 │
 ▼
Q1: 流程是固定的，还是需要模型自主决策？
 ├─ 固定 ────────────────▶ 别上 Agent 框架，写确定性 workflow
 └─ 需要自主决策
      │
      ▼
   Q2: 核心诉求是"处理海量文档/知识库问答"吗？
      ├─ 是 ──────────────▶ LlamaIndex（数据连接器 + Agentic RAG）
      └─ 否
           │
           ▼
        Q3: 只是学习/演示/一次性原型？
           ├─ 是 ──────────▶ smolagents（最透明，看得清每一步）
           └─ 否（要上生产）
                │
                ▼
             Q4: 流程复杂到需要"循环/分支/暂停/人工介入/审计"吗？
                ├─ 是 ─────▶ LangGraph（图状态机，导演级控制）
                └─ 否
                     │
                     ▼
                  Q5: 需要多个角色分工协作，且想快速声明式搭建？
                     ├─ 是 ──▶ CrewAI（角色制，上手最快）
                     └─ 否 ──▶ PydanticAI（类型安全 + 可观测，工程化默认选择）

（正交项）无论走到哪个叶子：要接外部工具/数据源 → 叠加 MCP
（生态项）已深度绑定 OpenAI 且想要现成 handoff/guardrail → OpenAI Agents SDK
```
这棵树刻意把"是不是真的需要 Agent"放在第一问，把 PydanticAI 放在最后作为"没有特殊诉求时的稳妥默认"。**它体现了一个选型哲学：先排除不需要的（Q1 排除伪 Agent），再在剩下的里选最匹配的，而不是一上来就比谁功能多。** RAG 即 Retrieval-Augmented Generation（检索增强生成），MCP 即 Model Context Protocol（模型上下文协议）。

## 现象与输入：把决策树变成可回答的问题清单

决策树能落地的关键，是每一问都能被"业务事实"回答，而不是靠拍脑袋。把五个问题配上"用什么事实来回答"：

- **Q1（要不要 Agent）**：数流程里"需要模型临场判断"的分支数。若为 0，是 workflow；若 ≥1，才可能是 Agent。
- **Q2（是不是海量文档）**：看数据形态。主要是非结构化长文档、需要检索召回，走 RAG 分支。
- **Q3（是不是原型）**：看项目寿命。演示/教学/一次性 demo，选最透明的；要长期上线，进入生产分支。
- **Q4（要不要循环/审计/人工介入）**：看是否有"多级人工审批、需要暂停等待、要留完整审计轨迹、长时运行可恢复"。命中任一即走图状态机。
- **Q5（要不要多角色协作）**：看任务是否天然是"多个专业角色分工"，且你想用声明式快速搭出来。

## 最小可运行演示

下面把这棵决策树固化成一个纯 Python 函数：输入一份"业务事实"字典，输出推荐框架与推理路径。它演示了决策树最大的价值——**同一个业务，改一个事实，答案就变**（正是开头报销案例的教训）。它不联网、不需要 API Key。
```python
def recommend(f: dict) -> tuple[str, list[str]]:
    path = []
    if not f["needs_autonomy"]:
        path.append("Q1=固定流程")
        return "确定性 workflow（不上 Agent 框架）", path
    path.append("Q1=需自主决策")
    if f["is_doc_heavy"]:
        path.append("Q2=海量文档")
        return "LlamaIndex", path
    path.append("Q2=非文档密集")
    if f["is_prototype"]:
        path.append("Q3=学习/原型")
        return "smolagents", path
    path.append("Q3=上生产")
    if f["needs_loop_or_audit"]:
        path.append("Q4=需循环/暂停/人工介入/审计")
        return "LangGraph", path
    path.append("Q4=无需复杂控制")
    if f["needs_multi_role"]:
        path.append("Q5=多角色协作")
        return "CrewAI", path
    path.append("Q5=单Agent即可")
    return "PydanticAI（工程化默认）", path


def run() -> None:
    ## 报销案例：中等复杂度、单 Agent、要上生产、无需长审批链
    invoice = {"needs_autonomy": True, "is_doc_heavy": False, "is_prototype": False,
               "needs_loop_or_audit": False, "needs_multi_role": False}
    fw, path = recommend(invoice)
    print("报销审查 Agent →", fw)
    print("  路径：", " → ".join(path))

    ## 只改一个事实：审批链变成三级人工审核 + 完整审计轨迹
    invoice_v2 = {**invoice, "needs_loop_or_audit": True}
    fw2, path2 = recommend(invoice_v2)
    print("报销审查 Agent(加审计) →", fw2)
    print("  路径：", " → ".join(path2))


if __name__ == "__main__":
    run()
```
保存为 `decide.py`，运行 `python decide.py`。完整预期输出：
```text
报销审查 Agent → PydanticAI（工程化默认）
  路径： Q1=需自主决策 → Q2=非文档密集 → Q3=上生产 → Q4=无需复杂控制 → Q5=单Agent即可
报销审查 Agent(加审计) → LangGraph
  路径： Q1=需自主决策 → Q2=非文档密集 → Q3=上生产 → Q4=需循环/暂停/人工介入/审计 → Q5=单Agent即可
```
看这两行的对比：**只把"需要审计"从 False 改成 True，推荐就从 PydanticAI 翻转成 LangGraph。** 这就是决策树最想让你体会的一点——选型对业务细节极其敏感，同一个业务不同细节，答案可能完全不同。开头报销团队正是因为一开始没把这些事实问清楚，才凭"人气"草率拍板。

## 真实系统对应

**官方公开机制**：决策树各叶子的推荐都可在官方文档核验其适用场景——LlamaIndex 的 RAG 与数据连接器 [来源](https://github.com/run-llama/llama_index)、smolagents 的透明教具定位 [来源](https://github.com/huggingface/smolagents)、LangGraph v1 的循环/持久化/人工介入/检查点 [来源](https://docs.langchain.com/oss/python/releases/langgraph-v1)、CrewAI 的角色制声明 [来源](https://github.com/crewAIInc/crewAI)、PydanticAI 的类型安全工程化 [来源](https://github.com/pydantic/pydantic-ai)、OpenAI Agents SDK 的 handoffs/guardrails [来源](https://github.com/openai/openai-agents-python)。OpenAI《A practical guide to building agents》也从工程视角给出"何时该上 Agent、如何评估"的判断框架 [来源](https://cdn.openai.com/business-guides-and-resources/a-practical-guide-to-building-agents.pdf)。**通用工程模式**：把选型抽象成"先排除、再匹配"的决策树，是可迁移的方法论。**教学参考实现**：上面 `recommend()` 的分支阈值是本书为讲清方法而构造的，真实项目应结合团队栈、已有基建与合规要求微调，不是普适硬规则。

需要点明边界：决策树给的是"起点建议"，不是"唯一正确答案"。真实项目还要叠加团队已有技术栈、云厂商绑定、合规要求、招聘市场（能不能招到会这个框架的人）等约束。**决策树的价值是帮你把该问的问题问全、按理性顺序收敛，而不是取代你对具体约束的判断。**

## 生产踩坑

| 症状 | 根因 | 如何观测与复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| 需求不在查找表里就乱选 | 用"关键词查表"而非决策树 | 给一个表里没有的需求看能否选出 | 改用"先排除再匹配"的决策树 | 需求与表项完全对应时查表够用 |
| 跳过 Q1 直接比框架功能 | 没先排除"其实不用 Agent" | 数自主决策分支数发现为0 | 强制 Q1 先答，伪 Agent 走 workflow | 已确认是复杂 Agent 任务可略 |
| 业务细节没问清就拍板 | 决策树问题未落到业务事实 | 改一个事实答案就翻转 | 每问配"用什么事实回答" | 事实非常明确的简单任务 |
| 选完不考虑团队栈/合规约束 | 把树的叶子当终极答案 | 选出的框架团队无人会用 | 叶子结果再叠加团队/合规约束 | 全新团队无历史包袱时约束少 |
| 忘了叠加正交/生态项 | 只走主干忽略括号里的补充 | 需要接外部工具却没考虑 MCP | 每次收敛后过一遍正交/生态项 | 完全无外部工具需求时可略 |

## 思考：面试官给一个模糊的业务描述让你现场选型，高分答法是什么？

### 回答

**高分答法不是直接报框架名，而是先反问澄清，用决策树的问题去逼近答案。** 面试官故意把业务描述得模糊，考的就是你会不会问对问题。好的回答会顺着决策树反问：第一问"这个流程是固定的还是需要模型临场决策？"（先排除伪 Agent）；第二问"数据主要是结构化字段还是海量非结构化文档？"（分出 RAG 分支）；第三问"这是要长期上线还是一次性演示？"（分出原型分支）；第四问"有没有多级人工审核、需要暂停等待、要留完整审计轨迹？"（分出图状态机分支）；第五问"是不是天然由多个专业角色分工？"（分出角色制分支）。问完这几个，答案基本就收敛了，最后再补一句"要接外部工具的话叠加 MCP、深绑 OpenAI 生态可考虑 OpenAI Agents SDK"。这样展示的是**方法论**而非记忆力——你证明的是"给我任何模糊需求，我都能系统地收敛到合理选型"，而不是"我背下了哪个框架适合哪个场景"。记住：**能问对问题，比能背对答案更值钱。**

### 面试精简表达

别急着报框架名，先按决策树反问五个澄清问题（要不要自主决策/是不是文档密集/是否原型/要不要循环审计/要不要多角色），用问题逼近答案，最后叠加 MCP 与生态项。展示方法论而非记忆力。

## 深入：选型的四大常见误区

决策树能帮你避开四个反复出现的坑：

- **误区一：唯功能论。**"LangGraph 功能最全，那就选它"——功能全意味着抽象层低、要写的样板代码多、团队学习成本高。做一个简单抽取任务用 LangGraph，就像用工业机床削苹果。**匹配度 > 功能数。** 开头那位选"功能最全"框架做工单分类的工程师，就栽在这里。
- **误区二：唯人气论。** Star 数高不等于适合你（详见第 5 节）。报销团队按 Star 数选 AutoGen，是这个误区最惨痛的示范。
- **误区三：既要又要。** 试图找一个"什么都能做"的框架。现实是每个框架都有它最擅长的范式，越通用往往越平庸。**允许在一个系统里组合多个框架**（比如 LlamaIndex 做检索层 + PydanticAI 做结构化输出层）反而更务实。
- **误区四：忽视退出成本。** 选型时只看进入成本（好不好学），不看退出成本（将来想换掉它有多难）。深度绑定一个框架的私有抽象，会让迁移变得极其昂贵——这正是第 5 节要展开的"原理不变、薄适配器"的现实意义。

这四个误区有个共同点：**它们都是"跳过了理性追问、走了认知捷径"。** 决策树的作用，恰恰是强迫你走完追问、堵住这些捷径。把它贴在选型评审的墙上，每次选型前逐条对照，就能避开团队里 80% 的选型翻车。
