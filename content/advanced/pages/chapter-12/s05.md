## 真实问题

报销团队的 AutoGen 返工，本质是两个更深问题的叠加：**选型时没做活跃度体检**，**落地时没控制退出成本**。前者让他们没预见到 AutoGen 会进维护模式；后者让"换框架"这件事的代价被放大到"几乎要重写全部业务"。返工时最痛的发现是——他们的业务规则（发票字段校验逻辑、报销政策判断）全都写进了 AutoGen 的 Agent 类和消息回调里，和框架私有 API 死死缠在一起。想换到 PydanticAI，等于把六周写的东西大部分推倒重来。

这一节讲两件让选型"面向未来"的事：**怎么给框架做活跃度体检**（避免选到正在衰亡的框架），以及**怎么用薄适配器把退出成本压到最低**（即使选错了，换起来也不痛）。

## 原理：框架江湖变化极快，选型要看"活力"不看"存量"

框架成熟度有三条要牢记：

- **AutoGen 已进入维护模式**：微软把 AutoGen 与 Semantic Kernel 合并为 Microsoft Agent Framework（MAF），AutoGen 官方 README 引导新项目从 MAF 开始、老项目迁移 [来源](https://github.com/microsoft/autogen) [来源](https://github.com/microsoft/agent-framework)。选型前一定要看框架的**活跃度和官方动向**，别在"将被弃用"的框架上重投入。
- **Star 数不等于适合你**：Star 是历史累积的人气存量，反映不了当下的项目生命力。4–5 万 Star 的 AutoGen 已进维护模式，1.7–1.9 万 Star 的 PydanticAI 却在积极开发——看范式匹配度和活力，而非人气存量。
- **框架会变，原理不变**：本书前几卷的 ReAct（Reasoning and Acting，推理与行动）、记忆、工具、MCP（Model Context Protocol，模型上下文协议）、工作流模式，是所有框架的共同底座。**吃透原理，换框架只是换语法。**

## 现象与输入：一份可操作的"活跃度体检"清单

"看活跃度"不能靠感觉。给你一份可操作的体检清单，选型前逐项打勾：

| 体检项 | 健康信号 | 危险信号 |
|---|---|---|
| 最近一次发版 | 近数周内有 release | 半年以上无更新 |
| Issue 响应 | 核心 issue 有维护者回复 | 大量 issue 无人问津 |
| 官方动向 | 官方仍在推荐、有 roadmap | 官方引导迁移到别的项目（如 AutoGen→MAF） |
| 文档新鲜度 | 文档与最新 API 一致 | 文档示例已跑不通 |
| 破坏性变更节奏 | 有清晰的版本与迁移指南 | 频繁无预警地改 API |
| 依赖健康 | 依赖链清爽、无弃用告警 | 绑定了已停维护的底层库 |

**AutoGen 的教训**：它 Star 量级很高（4–5 万），单看人气是"顶流"，但"官方动向"这一项亮红灯——已引导迁移。如果你只看 Star 数就重投入，等于把地基盖在正在拆迁的地皮上。**活跃度体检的价值，就是在人气的表象下看清真实的项目生命力。**

## 最小可运行演示

下面用纯 Python 把体检清单固化成一个打分器：输入一个框架的六项体检信号，输出"是否建议在生产项目中投入"的结论。它会同时体检 AutoGen 与 PydanticAI，让你看到"高 Star 也可能被否决"。它不联网、不需要 API Key。
```python
CHECKLIST = ["最近发版", "issue响应", "官方动向", "文档新鲜度", "变更节奏", "依赖健康"]
VETO = "官方动向"   ## 官方引导迁移属于否决级信号，一票否决


def health_check(name: str, signals: dict) -> str:
    ## signals: 每项 True=健康, False=危险
    if not signals[VETO]:
        return f"{name}: 不建议投入生产（否决项『官方动向』亮红灯）"
    healthy = sum(1 for k in CHECKLIST if signals[k])
    verdict = "建议投入" if healthy >= 5 else "谨慎评估" if healthy >= 3 else "不建议投入"
    return f"{name}: {verdict}（健康项 {healthy}/6）"


def run() -> None:
    autogen = {"最近发版": False, "issue响应": True, "官方动向": False,
               "文档新鲜度": True, "变更节奏": False, "依赖健康": True}
    pydantic_ai = {"最近发版": True, "issue响应": True, "官方动向": True,
                   "文档新鲜度": True, "变更节奏": True, "依赖健康": True}
    print(health_check("AutoGen(Star~5万)", autogen))
    print(health_check("PydanticAI(Star~1.9万)", pydantic_ai))
    print("结论：高 Star 也可能被『官方动向』一票否决")


if __name__ == "__main__":
    run()
```
保存为 `health.py`，运行 `python health.py`。完整预期输出：
```text
AutoGen(Star~5万): 不建议投入生产（否决项『官方动向』亮红灯）
PydanticAI(Star~1.9万): 建议投入（健康项 6/6）
```
这段输出把开头故障的教训量化了：**AutoGen 即便 Star 数是 PydanticAI 的两倍多，也因为"官方动向"这一否决项而被直接排除。** 活跃度体检里，"官方是否引导迁移"是权重最高的一项——它比其余五项加起来还重要。

## 真实系统对应

**官方公开机制**：AutoGen 仓库 README 明确其维护模式与迁移建议 [来源](https://github.com/microsoft/autogen)；Microsoft Agent Framework 仓库说明它是 AutoGen 与 Semantic Kernel 的合并继任者 [来源](https://github.com/microsoft/agent-framework)；LangGraph v1 发布说明公开了版本演进与迁移指引 [来源](https://docs.langchain.com/oss/python/releases/langgraph-v1)。这些都是"官方动向"这一体检项可以直接查证的一手来源。**通用工程模式**：六项体检清单、否决级信号、薄适配器降低退出成本，都是可迁移到任何开源依赖评估的做法。**教学参考实现**：上面 `health_check()` 的阈值（健康项≥5 才建议投入）是本书为讲清方法而设，真实评估应结合项目风险偏好调整。

需要点明边界：体检清单给的是"当下快照"，而框架生命力会持续变化——今天健康的框架明年可能衰退，今天维护模式的项目其继任者（如 MAF）可能崛起。**体检不是一次性动作，而应在每次重大版本升级或重新选型时复查。** 另外，"官方引导迁移"未必意味着立刻不能用——AutoGen 仍能运行、社区仍处理问题，只是不该用于"要长期投入的新项目"。

## 生产踩坑

| 症状 | 根因 | 如何观测与复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| 选到正在衰亡的框架 | 只看 Star 不看活跃度 | 查最近发版与官方 README 动向 | 选型清单固定六项体检 | 内部自维护框架不受上游影响 |
| 官方迁移信号被忽略 | 没把"官方动向"当否决项 | 复现：高 Star 框架已挂迁移公告 | "官方引导迁移"一票否决 | 短期一次性项目容错高 |
| 换框架要重写全部业务 | 业务逻辑深度耦合框架私有 API | 数业务代码里 import 框架的行数 | 核心逻辑纯 Python + 薄适配器 | 一次性脚本无需考虑退出成本 |
| 依赖链里混入停维护底层库 | 只体检主框架没查依赖 | 扫描依赖树的弃用告警 | 体检覆盖依赖健康 | 依赖极少的微框架风险低 |
| 文档示例跑不通才发现框架凉了 | 没查文档新鲜度 | 照官方最新示例跑一遍 | 选型时先跑通官方 quickstart | 文档滞后但社区活跃时可容忍 |
| 频繁被无预警的破坏性变更打断 | 没查变更节奏与迁移指南 | 回看历史 release 的 breaking 记录 | 优先选有清晰迁移指南的框架 | 早期实验性项目本就多变 |

## 思考："框架会变，原理不变"这句话，在写代码时能具体指导你做什么？

### 回答

它指导你**用"纯逻辑 + 薄适配器"的分层写法，把退出成本压到最低**。"框架会变，原理不变"不只是一句安慰——它有非常实际的工程价值。具体做法：把"工具的真实实现""输出的数据结构""核心业务规则"都写成**不依赖任何框架的纯 Python**，只在最外层用一层薄薄的适配器接到具体框架的装饰器/API 上。这样将来从一个框架换到另一个，改的是那层适配器，而不是你的核心逻辑。对照两种写法：高迁移成本的写法是"业务逻辑与框架私有 API 深度耦合"，换框架等于重写业务；低迁移成本的写法是"业务逻辑是纯函数/纯数据，框架只是最外层一层可替换的壳"，换框架只改适配器。开头报销团队的痛，正是因为把发票校验规则全写进了 AutoGen 的 Agent 类和消息回调里——如果当初把校验规则写成独立的纯函数、只用一层适配器接到框架，那么从 AutoGen 换到 PydanticAI 就只是重写那层薄适配器，而不是推倒六周的成果。**这正是本书反复强调"吃透原理"的工程回报：原理写在你自己的代码里，框架只是可替换的外壳。**

### 面试精简表达

把工具实现、数据结构、业务规则写成不依赖框架的纯 Python，只在最外层用薄适配器接框架 API。换框架时只改适配器不改核心逻辑，退出成本从"重写业务"降到"改一层壳"。

## 深入：一段"薄适配器"写法的对照演示

用一段可运行的纯 Python 把"薄适配器"的价值演示出来：同一个发票校验规则（纯函数），分别用两个"假框架"的适配器接入，核心逻辑一行不改。
```python
## —— 核心业务规则：不依赖任何框架的纯函数（吃透原理写在自己代码里）——
def validate_invoice(amount: float, has_receipt: bool) -> dict:
    if not has_receipt:
        return {"verdict": "驳回", "reason": "缺少发票凭证"}
    if amount > 5000:
        return {"verdict": "需复核", "reason": "金额超过 5000 阈值"}
    return {"verdict": "通过", "reason": "符合报销规则"}


## —— 适配器 A：接入"框架A"（假设它要求工具返回字符串）——
def adapter_framework_a(amount, has_receipt):
    r = validate_invoice(amount, has_receipt)          ## 核心逻辑零改动
    return f"{r['verdict']}：{r['reason']}"


## —— 适配器 B：接入"框架B"（假设它要求工具返回结构化 dict）——
def adapter_framework_b(amount, has_receipt):
    return validate_invoice(amount, has_receipt)        ## 核心逻辑零改动


def run() -> None:
    print("框架A 适配器：", adapter_framework_a(6000, True))
    print("框架B 适配器：", adapter_framework_b(6000, True))
    print("换框架只改了适配器，validate_invoice 一行未动")


if __name__ == "__main__":
    run()
```
保存为 `adapter.py`，运行 `python adapter.py`。完整预期输出：
```text
框架A 适配器： 需复核：金额超过 5000 阈值
框架B 适配器： {'verdict': '需复核', 'reason': '金额超过 5000 阈值'}
```
两个适配器接的是两套完全不同的框架约定（一个要字符串、一个要 dict），但 `validate_invoice` 这个承载真正业务价值的函数一行都没改。**这就是"降低退出成本"的可运行证据：把不变的原理沉淀在纯代码里，让易变的框架只停留在最外层。** 当框架淘汰时，你丢掉的只是几行适配器，而不是团队几个月的业务积累。
