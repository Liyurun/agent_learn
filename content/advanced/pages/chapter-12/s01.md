## 真实问题

回到开头那家报销 SaaS 公司。返工复盘会上，最扎心的一句质问不是"为什么选了 AutoGen"，而是——"我们真的需要一个 Agent 框架吗？"这个任务的核心是"把发票抽成字段、按规则校验、打个分"，把它画成流程图后，团队愣住了：里面**只有一处**真正需要模型自主决策（判断某条模糊描述算不算合规风险），其余全是确定性步骤。也就是说，六周里他们花了大量精力去驯服一个多 Agent 对话框架的循环、消息、状态，而这些"重复劳动"本可以用几十行确定性代码 + 一次结构化输出调用解决。

这不是个例。Anthropic 在《Building Effective Agents》里给过一句被反复引用的忠告：许多 Agent 模式其实**几行 LLM API 调用就能实现**，框架不是必需品；用框架的前提是**理解它的底层假设**，因为错误的底层理解正是常见 bug 的来源 [来源](https://www.anthropic.com/engineering/building-effective-agents)。这一节要回答两个先于"选哪个框架"的问题：框架到底替你封装了什么（它的价值与代价从何而来），以及什么时候**根本不该**上框架。

## 原理：一个 Agent 框架封装的七层重复劳动

"框架封装重复劳动"这句话太抽象。把它拆开——任何一个 Agent 框架，无论叫什么名字，本质上都在替你处理下面这七件事：
```text
┌──────────────────────────────────────────────────────────┐
│                 一个 Agent 框架的内部构成（七层）             │
├──────────────────────────────────────────────────────────┤
│  ① 循环控制器   while(未完成){ 想 → 做 → 看 } 何时停？        │
│  ② 工具协议     把函数签名 → JSON Schema → 塞进 prompt       │
│  ③ 消息编排     system/user/assistant/tool 消息如何拼装      │
│  ④ 状态管理     多轮之间的记忆、中间变量放哪、如何流转          │
│  ⑤ 输出解析     从模型文本里抠出"要调哪个工具、参数是什么"     │
│  ⑥ 错误处理     工具报错、超时、解析失败时怎么重试             │
│  ⑦ 可观测性     每一步的 trace、token 消耗、延迟怎么记录       │
└──────────────────────────────────────────────────────────┘
```
如果你亲手写过一个裸的 ReAct（Reasoning and Acting，推理与行动）循环，就会发现上面七件事每一件都得自己处理，而且处理不好就会冒出各种诡异 bug。框架的价值，是把这七件事做成了"默认还不错"的实现。**它节省的不是"会不会写"，而是"写对所有边界情况"的时间。**

代价也正来自这里：当第 ⑤ 步的输出解析出问题、或第 ① 步的停止条件不符合你的预期时，如果你不知道框架内部这七层怎么串起来，你就只能对着黑箱干瞪眼。**"理解底层假设"的实际含义——不是让你去背源码，而是让你在出问题时知道该往哪一层看。** 报销团队的 AutoGen 原型出问题时，恰恰卡在这里：多 Agent 对话把第 ①③④ 层（循环、消息、状态）绕得极其复杂，出了 bug 谁也说不清对话在哪一轮跑偏了。

## 最小可运行演示

下面用一段纯 Python 把"七层"具象化：左边是"裸手写"要操心的七件事，右边是"框架接管后"你只需关心业务。程序会打印一张对照清单，并统计"你亲手要写的层数"从 7 降到几。它不联网、不需要 API Key。
```python
LAYERS = [
    "① 循环控制器（何时停）",
    "② 工具协议（函数→JSON Schema）",
    "③ 消息编排（多角色消息拼装）",
    "④ 状态管理（多轮记忆与中间变量）",
    "⑤ 输出解析（从文本抠出工具与参数）",
    "⑥ 错误处理（报错/超时/解析失败重试）",
    "⑦ 可观测性（trace/token/延迟）",
]


def build(mode: str) -> dict:
    ## 裸手写：七层全自己扛；上框架：框架接管六层，你只写业务
    framework_owned = set() if mode == "bare" else {0, 1, 2, 3, 4, 5}
    you_own = [l for i, l in enumerate(LAYERS) if i not in framework_owned]
    return {"你亲手要写的层": you_own, "剩余可观测性需你配置": 6 in framework_owned}


def run() -> None:
    for mode in ("bare", "framework"):
        r = build(mode)
        print(f"[{mode}] 你亲手要写：{len(r['你亲手要写的层'])} 层")
        for item in r["你亲手要写的层"]:
            print(f"    - {item}")
    print("结论：框架把重复劳动降到最少，但第⑦层可观测性仍需你主动配置")


if __name__ == "__main__":
    run()
```
保存为 `layers.py`，运行 `python layers.py`。完整预期输出：
```text
[bare] 你亲手要写：7 层
    - ① 循环控制器（何时停）
    - ② 工具协议（函数→JSON Schema）
    - ③ 消息编排（多角色消息拼装）
    - ④ 状态管理（多轮记忆与中间变量）
    - ⑤ 输出解析（从文本抠出工具与参数）
    - ⑥ 错误处理（报错/超时/解析失败重试）
    - ⑦ 可观测性（trace/token/延迟）
[framework] 你亲手要写：1 层
    - ⑦ 可观测性（trace/token/延迟）
结论：框架把重复劳动降到最少，但第⑦层可观测性仍需你主动配置
```
这段输出把"价值"量化了：裸写要扛七层，上框架大多降到一层。但注意最后那句——可观测性通常仍要你显式接入（这正是第 17 章要展开的），框架不会替你把所有事都办完。

## 真实系统对应

**官方公开机制**：Anthropic《Building Effective Agents》明确区分"workflow（预定义代码路径编排 LLM 与工具）"与"agent（LLM 动态决定自己的流程与工具使用）"，并建议"从最简单的方案做起，只在确有必要时才增加复杂度" [来源](https://www.anthropic.com/engineering/building-effective-agents)；OpenAI《A practical guide to building agents》同样从工程视角讨论"何时该上 Agent、如何评估复杂度" [来源](https://cdn.openai.com/business-guides-and-resources/a-practical-guide-to-building-agents.pdf)。**通用工程模式**：把七层重复劳动列成清单、逐层判断"框架替我做了什么"，是可迁移到任何框架评估的方法。**教学参考实现**：上面的 `build()` 只为把"七层"具象化，真实框架的分层与命名各不相同，不代表任何产品内部结构。

需要点明边界：不同框架接管的层不一样。smolagents 刻意把第 ⑤ 层（输出解析）做成"让模型直接写可执行 Python"，透明到逼近裸循环；LangGraph 把第 ①④ 层（循环与状态）做成显式的图与检查点；PydanticAI 在第 ②⑤ 层（工具协议与结构化输出解析）上做类型校验。**"框架封装了什么"这个问题，不同框架有不同答案——这正是下一节要逐个拆解的。**

## 生产踩坑

| 症状 | 根因 | 如何观测与复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| 简单抽取任务被套上重型框架 | 没先问"这是 workflow 还是 Agent" | 数流程里模型自主决策的分支数，若≤1 即过度 | 固定流程改写确定性 workflow + 一次结构化输出 | 确需多步自主决策的任务另算 |
| 框架出 bug 却无从下手 | 不清楚框架内部七层如何串联 | 定位 bug 时说不清卡在哪一层 | 出问题先按"循环/协议/解析/状态"分层排查 | 完全托管的低代码平台由厂商负责 |
| token 成本远超预期 | 框架抽象层带来隐藏的调用与重发 | 对比裸调与框架版的 input token | 评估抽象成本，延迟/成本敏感场景考虑裸写 | 复杂多轮任务框架收益能覆盖开销 |
| 以为上了框架就有可观测性 | 误以为第⑦层默认开箱 | 跑一遍看是否自动产生 trace | 显式接入追踪（Logfire/LangSmith 等） | 部分框架内置 tracing 需手动开启 |
| 团队学习成本吃掉交付时间 | 项目周期短却选了高学习曲线框架 | 统计上手到跑通的天数 | 短周期原型选低学习曲线或裸写 | 长期项目一次性学习成本会被摊薄 |

## 思考：什么时候"不该"用框架？请给一份可操作的判断清单。

### 回答

Anthropic 的忠告可以展开成一个明确清单。以下情况，直接裸调 API 往往比上框架更好：（1）**流程完全固定、无需模型自主决策**——这是"工作流"不是"Agent"，上框架是杀鸡用牛刀；（2）**只需要一次结构化输出**（抽取/分类）——一次 Function Calling 加一个校验库即可，无需循环控制；（3）**团队对框架完全陌生且项目周期极短**——学习曲线成本会超过框架收益；（4）**需要极致的延迟/成本控制**——框架的抽象层往往带来隐藏的 token 与调用开销。反过来，只有当任务是"多工具、多轮、需要记忆和重试的复杂自主决策"时，七层重复劳动的收益才开始显现，这时才值得上框架。一句能记住的原则：**先问"这是 workflow 还是 Agent"，再问"复杂度是否配得上框架的抽象成本"。** 开头的报销案例正是踩在第（1）（2）条上——一个中等复杂度的单 Agent 结构化输出任务，被硬塞进了多 Agent 对话框架。

### 面试精简表达

流程固定、一次性结构化输出、团队陌生且周期短、要极致压成本——这四种情况裸写更好；只有多工具多轮需记忆重试的复杂任务才值得上框架。先分清 workflow 与 Agent，再看复杂度配不配得上抽象成本。

## 深入：抽象的阶梯——框架处在哪一层

理解框架的另一个视角，是看它站在"抽象阶梯"的哪一级。越往上越省心、越往下越可控：
```text
抽象越高 ↑   ┌─────────────────────────┐
            │ 低代码/可视化编排平台      │  拖拽即用，最省心，最不可控
            ├─────────────────────────┤
            │ 高层 Agent 框架 (CrewAI)  │  声明角色即可跑
            ├─────────────────────────┤
            │ 工程化框架 (PydanticAI)   │  写业务，框架管校验与注入
            ├─────────────────────────┤
            │ 低层可控框架 (LangGraph)  │  自己画图，框架给状态机原语
            ├─────────────────────────┤
            │ 极简教具 (smolagents)     │  内核透明，逼近裸循环
            ├─────────────────────────┤
抽象越低 ↓   │ 裸 LLM API 调用          │  全都自己写，最累，最可控
            └─────────────────────────┘
```
这个阶梯解释了本书路线的用意：**从阶梯底部（smolagents 逼近裸循环）起步，你看得清每一层；等你理解了机制，再往上挑一个抽象层次合适的框架落地。** 直接从顶层的低代码平台入门，你会"会用但不懂"，一旦出问题就束手无策。报销团队的错误，某种意义上也是"抽象层次没选对"——他们需要的是中间偏工程化的一层（PydanticAI），却跳到了一个多 Agent 编排的高抽象范式，既不透明也不匹配。

> **经验**：面试或技术评审里，能画出这把"抽象阶梯"并说清"我们的团队和任务适合停在哪一级"的人，比只会罗列 API 的人专业度高出一个档次。抽象层次的选择，本质是在"省心"和"可控"之间为你的团队和业务找一个平衡点，而不是越省心越好、也不是越可控越好。
