## 真实问题

报销团队返工换到 PydanticAI 后，又冒出一个新纠结。他们之前为 AutoGen 版本写过一个"查企业税号真伪"的工具，现在换框架，这个工具要不要重写？更让人焦虑的是市场部同时在用另一个框架做客服 Agent，也需要同样的"查税号"能力——难道每个框架、每个项目都要各写一份、各维护一份？有人甚至提出："干脆统一到一个框架算了，省得工具到处重写。"这个念头很危险——它把"工具复用"和"框架统一"混为一谈了。

真正的解法是理解 MCP（Model Context Protocol，模型上下文协议）与框架的**正交关系**：框架管"怎么组织 Agent 逻辑"，MCP 管"怎么接入外部能力"，两者在不同维度，可叠加、可各自演化。想清楚这层关系，"查税号"工具就该做成一个 MCP Server，让所有框架、所有项目共享，而不是绑死在任何一个框架里。

## 原理：MCP 不是"第八个框架"

特别说明：MCP 不是"第八个框架"，而是与所有框架**正交**的标准层。无论你用 smolagents 还是 LangGraph，都可以通过 MCP 接入外部工具。可以把框架理解为"组织 Agent 逻辑的方式"，MCP 理解为"接入外部能力的标准接口"——两者在不同维度，可叠加使用 [来源](https://modelcontextprotocol.io/)。

MCP 由 Anthropic 发起，现已是一个开放规范，其规范定义了 Base Protocol（基于 JSON-RPC 的消息）、生命周期管理、授权，以及服务端能力（Resources 资源 / Prompts 提示 / Tools 工具）与客户端能力（Sampling 采样 / Roots 根目录列表）[来源](https://modelcontextprotocol.io/specification/2025-06-18/basic)。它的目标是缓解 N×M 的集成爆炸——N 个 Agent 应用 × M 个工具/数据源，如果每对都单独对接，组合数会爆炸；有了 MCP 这个统一接口，工具只需实现一次，任意框架都能接。

## 现象与输入：用一张图看清"正交"

"正交"这个词很多人听过但没画过图。画出来一目了然：
```text
            纵轴：怎么组织 Agent 逻辑（框架的维度）
                        ▲
      LangGraph  ───────┤
      PydanticAI ───────┤        每一个框架
      smolagents ───────┤        都能横向接上
      CrewAI     ───────┤        同一批 MCP 工具
                        │
   ─────────────────────┼──────────────────────────▶
   横轴：怎么接外部能力（MCP 的维度）
      MCP-Server-文件系统  MCP-Server-数据库  MCP-Server-浏览器 ...
```
框架在纵轴上互相竞争（你通常只选一个来组织逻辑），MCP 在横轴上提供工具供给（一套 MCP Server 可以被任意框架复用）。**因为不在同一根轴上，所以它们不冲突，可以自由组合。** 这就是"正交"的直观含义。回到报销团队的纠结："查税号"工具属于横轴（外部能力），"用哪个框架组织逻辑"属于纵轴——把工具做成 MCP Server 放到横轴上，纵轴换什么框架都不影响它，市场部的客服 Agent 也能直接接。

## 最小可运行演示

下面用纯 Python 模拟"一个 MCP 风格的工具 Server + 两个不同框架的适配器"，演示同一个工具如何被两个框架复用、且换框架时工具零改动。它不联网、不需要 API Key。
```python
## —— 一个 MCP 风格的工具 Server：只实现一次，暴露标准化的 name/schema/handler ——
class TaxIdServer:
    name = "verify_tax_id"
    input_schema = {"type": "object", "properties": {"tax_id": {"type": "string"}},
                    "required": ["tax_id"]}

    @staticmethod
    def call(tax_id: str) -> dict:
        valid = tax_id.startswith("91") and len(tax_id) == 18
        return {"tax_id": tax_id, "valid": valid}


## —— 框架A（如 PydanticAI 风格）的适配器：把 MCP 工具接成本框架的调用 ——
def framework_a_invoke(server, args: dict) -> str:
    r = server.call(**args)
    return f"[框架A] 税号 {r['tax_id']} 合规={r['valid']}"


## —— 框架B（如 LangGraph 风格）的适配器：同一个 server 原样接入 ——
def framework_b_invoke(server, args: dict) -> str:
    r = server.call(**args)
    return f"[框架B 节点输出] valid={r['valid']}"


def run() -> None:
    server = TaxIdServer()                       ## 工具只实现一次
    print("暴露的工具：", server.name, server.input_schema["required"])
    print(framework_a_invoke(server, {"tax_id": "91310000MA1FL0XXXX"}))
    print(framework_b_invoke(server, {"tax_id": "123"}))
    print("同一个 MCP 工具被两个框架复用，工具代码零改动")


if __name__ == "__main__":
    run()
```
保存为 `mcp_orthogonal.py`，运行 `python mcp_orthogonal.py`。完整预期输出：
```text
暴露的工具： verify_tax_id ['tax_id']
[框架A] 税号 91310000MA1FL0XXXX 合规=True
[框架B 节点输出] valid=False
```
看这段输出：`TaxIdServer` 只写了一次，却同时喂给了"框架A"和"框架B"两套完全不同的适配器。**这就是正交的可运行证据——工具在横轴、框架在纵轴，换框架不动工具、加框架也不动工具。** 报销团队的"查税号"工具做成这样，市场部客服 Agent 直接接入即可，不必重写、不必各维护一份。

## 真实系统对应

**官方公开机制**：MCP 官方规范定义了工具/资源/提示的标准化暴露方式、基于 JSON-RPC 的消息与传输（stdio、Streamable HTTP）[来源](https://modelcontextprotocol.io/specification/2025-06-18/basic) [来源](https://modelcontextprotocol.io/specification/2025-06-18/basic/transports)；主流框架（如 OpenAI Agents SDK、LangGraph、PydanticAI 等）均公开支持接入 MCP Server [来源](https://github.com/openai/openai-agents-python)。MCP 规范持续演进，2025-06-18 为一个稳定版、其后有更新版本，具体能力以官方规范页面为准 [来源](https://modelcontextprotocol.io/)。**通用工程模式**：把"外部能力"沉淀为可跨框架复用的标准化工具、与"逻辑组织"解耦，是可迁移的架构原则。**教学参考实现**：上面的 `TaxIdServer` 只为演示"一次实现、多框架复用"的正交性，并非真实 MCP Server 的完整实现（真实 MCP 涉及 JSON-RPC 握手、能力协商、传输层等）。

需要点明边界：MCP 是"接什么工具"的标准，不替代"怎么组织逻辑"的框架决策——你仍然要选一个框架来做循环控制、状态管理、消息编排。**MCP 让工具层可复用、可解耦，但它不会替你做选型；反过来，选好框架也不意味着工具就自动可复用——只有把工具做成 MCP 这样的标准化接口，复用才成立。** 第 9 章会深入 MCP 的协议细节，这里只需建立"正交、可叠加"的心智。

## 生产踩坑

| 症状 | 根因 | 如何观测与复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| 把 MCP 当"第八个框架"来二选一 | 没理解它是正交标准层 | 试图在"框架 vs MCP"里选一个 | 记住框架管逻辑、MCP 管工具，可叠加 | — |
| 每个框架各写一份同样的工具 | 工具绑死在框架私有 API 里 | 数同一能力被重复实现了几次 | 把工具做成 MCP Server 跨框架复用 | 只有单一框架单一项目时收益小 |
| 为了"工具复用"强行统一框架 | 混淆了工具复用与框架统一 | 复现：为省工具重写而绑死一个框架 | 工具走横轴 MCP，框架走纵轴各选 | 团队确需统一栈时另有考量 |
| 换框架时工具跟着一起重写 | 工具与逻辑未解耦 | 换框架发现工具也要改 | 工具经 MCP 解耦，换框架零改动 | 内联小工具解耦成本可能不划算 |
| 把工具结果里的指令当命令执行 | 未把外部工具输出视为不可信 | 工具返回里塞"忽略以上指令" | 工具结果做注入防护再喂模型 | 完全可信内部工具风险较低 |
| MCP Server 权限过宽被滥用 | 未按最小权限暴露能力 | 一个 Server 暴露了过多高危操作 | 按 RBAC 最小权限拆分 Server | 只读低危工具风险较低 |

> RBAC 即 Role-Based Access Control（基于角色的访问控制）。工具结果应被视为不可信输入，写入日志前对 PII（Personally Identifiable Information，个人可识别信息）做最小化与脱敏。

## 思考：面试官问"MCP 和 LangChain / LangGraph 是竞争关系吗？"，怎么答？

### 回答

**这是一道送分也送命的题——答"是竞争"直接暴露理解偏差。** 正确答法：它们是**正交的两个维度**，不在同一根轴上，所以谈不上竞争。MCP 管的是"接什么工具"——它是运行时与外部工具/数据源之间的标准化集成接口，目标是缓解 N×M 的集成爆炸，让一个工具实现一次就能被任意 Agent 应用接入；LangChain / LangGraph 管的是"怎么组织 Agent 逻辑"——循环控制、状态管理、图编排、消息拼装。落到代码里：MCP Server 把一个工具的名字、描述、输入 Schema 标准化地暴露出来，而 LangGraph 仍然负责"这个工具在图的哪个节点被调用、调用后走哪条边"。也就是说，**MCP 供给工具定义，框架驱动调用，二者互补叠加**——真实系统里常常是 MCP 提供工具、框架组织逻辑，同时使用。答完这层，再补一句正交带来的两个实际好处（工具复用、降低锁定），回答就完整了。理解了这层关系，你就不会把两者对立起来问"用哪个"。

### 面试精简表达

不是竞争，是正交。MCP 管"接什么工具"（跨框架复用的集成标准），框架管"怎么组织逻辑"（循环/状态/编排）。MCP 供给工具定义、框架驱动调用，二者叠加使用，带来工具复用与降低锁定两个好处。

## 深入：正交带来的两个实际好处，与"降低退出成本"是一体两面

正交不是抽象概念，它带来两个可量化的工程好处：

1. **工具复用**：你为项目 A（用 PydanticAI）写的一个 MCP 查税号工具，项目 B（用 LangGraph）可以原样接入，不必重写。工具投资一次，跨框架、跨项目复用。报销团队和市场部客服 Agent 共享同一个"查税号"MCP Server，就是这个好处的直接体现——一份代码、一处维护、两个团队受益。
2. **降低锁定**：因为外部能力是通过 MCP 标准接口接入的，将来换框架时，工具层几乎不用动。

第二个好处，与第 5 节讲的"用薄适配器降低退出成本"其实是**同一思路的两个侧面**。第 5 节说的是"把业务逻辑写成纯 Python + 薄适配器"，让逻辑不绑死框架；这一节说的是"把外部工具做成 MCP 标准接口"，让工具不绑死框架。前者管"你自己写的逻辑"，后者管"你接入的外部能力"——两者合起来，就构成了一套完整的"抗框架淘汰"的架构策略：**不管上层框架怎么更迭，你的核心资产（业务逻辑 + 外部工具）都停留在可复用、可迁移的一层，框架永远只是最外层那件可以随时脱换的外套。** 这正是本章反复强调"吃透原理、降低锁定"在架构上的落地形态。
