## 真实问题

报销团队返工后期，有位新来的工程师问了一个看似天真、实则切中要害的问题："我们下次是不是把这几个框架都学一遍，才不会再选错？"技术负责人的回答是："**别学框架，先学范式。**" 因为框架每年都在迭代甚至消亡——AutoGen 就是眼前的例子——如果你的知识是"记住了 AutoGen 的 API"，那它进维护模式的那天，你的知识就贬值一半。但如果你记住的是"AutoGen 属于多 Agent 对话范式，本质是在表达力和协作灵活性上做取舍"，那么无论它叫 AutoGen 还是 MAF，你都能一眼看穿它的定位。

这一节要回答：八大框架背后其实只有**三种设计哲学**；理解流派比记住框架名更重要，因为**范式抗贬值，框架名会作废**。

## 原理：三大范式流派

八大框架背后其实是三种设计哲学：

- **代码即动作流派（smolagents）**：让 Agent 直接输出并执行 Python 代码作为动作，而非受限的结构化工具调用。最贴近 Agent 本质，是最好的教具，但要执行不可信代码，必须配沙箱 [来源](https://github.com/huggingface/smolagents)。
- **类型安全 / 工程化流派（PydanticAI、OpenAI Agents SDK）**：强调结构化输出、类型校验、可观测性，把软件工程的严谨带入 Agent 开发。生产首选 [来源](https://github.com/pydantic/pydantic-ai)。
- **图 / 状态机流派（LangGraph）**：把 Agent 建模为节点和边的图，提供对流程的精细控制与可审计性，并支持持久化执行与检查点。适合复杂、长时、合规场景 [来源](https://docs.langchain.com/oss/python/releases/langgraph-v1)。

此外还有**角色制流派（CrewAI）** 强调"像组建团队一样声明角色"[来源](https://github.com/crewAIInc/crewAI)，**数据 / RAG（Retrieval-Augmented Generation，检索增强生成）流派（LlamaIndex）** 强调数据连接与检索 [来源](https://github.com/run-llama/llama_index)。而 AutoGen 属于"对话式多 Agent"范式的代表——但它已进维护模式，其范式思想被 Microsoft Agent Framework 继承。

## 现象与输入：三种流派的"一步动作"长什么样

流派的根本差异，在于"**Agent 的一步动作长什么样**"。用一张图直观对比：
```text
代码即动作流派：
   模型输出 ──▶  results = search("汇率"); rate = results[0]
                print(100 * rate)          ← 一步里能组合多个操作
                └── 表达力最强，但要执行不可信代码，需沙箱

类型安全流派：
   模型输出 ──▶  {"tool":"get_rate","args":{"base":"USD","target":"CNY"}}
                └── 结构清晰、可强校验、可自动重试，工程可控性最好

图/状态机流派：
   模型输出 ──▶  当前节点=调模型 → 条件边判断 → 下一节点=调工具
                └── 每一步走向都被图显式约束，可审计、可回溯、可暂停
```
把这三行放在一起看，你会发现它们其实是在"**表达力**"与"**可控性**"之间做不同的取舍：

| 流派 | 表达力 | 可控性 | 安全成本 | 最贴合的心智模型 |
|---|---|---|---|---|
| 代码即动作 | 最高 | 中 | 高（必须隔离执行） | 「给 Agent 一个 Python 解释器」 |
| 类型安全/工程化 | 中 | 高 | 低 | 「给 Agent 一份带校验的表单」 |
| 图/状态机 | 中（受图结构约束） | 最高 | 低 | 「给 Agent 一张导演分镜脚本」 |

理解了这个取舍，你就能一眼看穿任何新框架的定位——不管它营销话术怎么包装，它的"一步动作"总会落在这三种表达方式的某处。回到报销案例：那个"抽取+校验+打分"的任务，最需要的是"带校验的表单"（结构化、可强校验、可重试）——这正是类型安全流派的强项，也正是团队当初该选 PydanticAI 而非多 Agent 对话的根本原因。

## 最小可运行演示

下面用纯 Python 把三种流派的"一步动作"各自模拟出来：同一个任务"把 100 美元按汇率换成人民币"，看三种范式分别如何表达这一步动作，以及它们对"非法/危险动作"的不同处理方式。它不联网、不需要 API Key。
```python
import json

RATE = {"USD_CNY": 7.2}


## —— 流派1：代码即动作（表达力最高，但需沙箱拦截危险代码）——
def code_as_action(snippet: str) -> str:
    banned = ("import os", "open(", "__import__", "subprocess")
    if any(b in snippet for b in banned):
        return "沙箱拦截：检测到危险操作，拒绝执行"
    safe_env = {"rate": RATE["USD_CNY"]}
    exec(snippet, {"__builtins__": {}}, safe_env)     ## 教学演示，真实场景须用强隔离沙箱
    return f"执行结果 cny={safe_env.get('cny')}"


## —— 流派2：类型安全（结构化调用，先校验再执行）——
def typed_tool_call(call: dict) -> str:
    if call.get("tool") != "convert" or "amount" not in call.get("args", {}):
        return "校验失败：工具名或参数不合法，拒绝执行"
    amount = call["args"]["amount"]
    return f"结构化执行结果 cny={amount * RATE['USD_CNY']}"


## —— 流派3：图/状态机（每步走向被图显式约束）——
def graph_step(state: dict) -> dict:
    edges = {"start": "call_rate", "call_rate": "compute", "compute": "END"}
    node = state["node"]
    if node == "compute":
        state["cny"] = state["amount"] * RATE["USD_CNY"]
    state["node"] = edges[node]
    return state


def run() -> None:
    print("[代码即动作]", code_as_action("cny = 100 * rate"))
    print("[代码即动作]", code_as_action("import os; os.system('rm -rf /')"))
    print("[类型安全]  ", typed_tool_call({"tool": "convert", "args": {"amount": 100}}))
    print("[类型安全]  ", typed_tool_call({"tool": "delete_all", "args": {}}))
    st = {"node": "start", "amount": 100}
    while st["node"] != "END":
        st = graph_step(st)
    print("[图/状态机] 终态 cny=", st["cny"], " 路径已被图约束")


if __name__ == "__main__":
    run()
```
保存为 `paradigms.py`，运行 `python paradigms.py`。完整预期输出：
```text
[代码即动作] 执行结果 cny=720.0
[代码即动作] 沙箱拦截：检测到危险操作，拒绝执行
[类型安全]   结构化执行结果 cny=720.0
[类型安全]   校验失败：工具名或参数不合法，拒绝执行
[图/状态机] 终态 cny= 720.0  路径已被图约束
```
三段输出对应三种范式对"同一步动作"的不同表达：代码即动作最灵活（一行就算完）但危险动作要靠沙箱拦；类型安全靠 Schema 校验挡住非法调用；图/状态机则让每一步走向都被预设的边约束死。**表达力越高，安全成本越高；可控性越高，灵活性越受限——三行代码就把这个取舍演示清楚了。**

## 真实系统对应

**官方公开机制**：smolagents 官方明确其 CodeAgent 让模型"以代码形式表达动作"、并强调需在沙箱中执行 [来源](https://github.com/huggingface/smolagents)；PydanticAI 官方强调"类型安全""结构化、经校验的输出" [来源](https://github.com/pydantic/pydantic-ai)；LangGraph v1 官方描述"图/状态机、持久化执行、检查点、人工介入（Human-in-the-loop）" [来源](https://docs.langchain.com/oss/python/releases/langgraph-v1)。**通用工程模式**：用"一步动作的表达方式"去归类任何框架，并落到"表达力 vs 可控性"取舍上，是可迁移的判断法。**教学参考实现**：上面的三个函数只为演示三种范式的动作形态，`exec` 的简易黑名单绝不能用于生产——真实的代码即动作必须用强隔离沙箱（容器/微虚拟机）执行不可信代码。

需要点明边界：现实框架常常是"以某一派为主 + 混入其他派特性"。比如 OpenAI Agents SDK 以类型安全/工程化为主，但也提供 Handoffs 这种"多 Agent 移交"的能力；LangGraph 虽是图状态机，节点内部也可以调结构化工具。**范式是"主色调"而非"唯一色"——判断一个框架属于哪派，看它的"一步动作"最主要长什么样、它逼你用哪种心智模型思考。**

## 生产踩坑

| 症状 | 根因 | 如何观测与复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| 只记框架名，框架一淘汰知识就作废 | 记了 API 没记范式 | AutoGen 进维护模式后发现知识用不上 | 先归类范式，再学具体 API | 短期一次性项目影响小 |
| 代码即动作框架被注入危险代码 | 未用强隔离沙箱执行模型代码 | 让模型生成含 os.system 的代码复现 | 容器/微虚拟机沙箱 + 白名单 | 完全离线可信环境风险较低 |
| 用错范式导致处处别扭 | 范式与业务的动作形态不匹配 | 单Agent结构化任务硬用多Agent对话 | 按"一步动作"最贴合的范式选 | 混合需求可组合多范式 |
| 图/状态机把简单任务搞复杂 | 给无分支任务强加节点边 | 一条直线流程被画成十节点图 | 简单任务用类型安全范式即可 | 需审计/暂停/回溯时图范式才划算 |
| 误以为某框架"纯粹"属于一派 | 忽略框架的混合特性 | 在文档里发现它同时支持多种动作 | 判"主色调"而非贴唯一标签 | 学术分类可更严格 |

## 思考：为什么说"记范式比记框架名更值钱"？

### 回答

因为**范式是稳定的，框架名是易变的**。框架每年都在迭代甚至消亡——AutoGen 从顶流走向维护模式就是活生生的例子——如果你的知识建立在"记住了某框架的 API"上，那它一被弃用，你的知识就贬值一半。而"代码即动作、结构化工具调用、图状态机"这三种范式，是 Agent 领域被反复验证的三种组织方式，即使未来框架名字全变了，新框架也一定属于这三派之一或它们的组合。**记范式，你的知识就有了抗贬值能力；只记框架名，明年可能就作废一半。** 更实际的价值是：范式思维能让你在面试或技术评审里，说出"这个框架属于 XX 范式，本质是在表达力和可控性之间做了 YY 取舍"——这种回答比只会罗列 API 的人，专业度高出一个档次，因为它证明你理解的是"为什么这么设计"，而不只是"怎么调用"。范式思维，是资深工程师和 API 使用者的分水岭。

### 面试精简表达

框架会消亡、范式抗贬值。三种范式（代码即动作/结构化工具调用/图状态机）是稳定底座，新框架都是它们的变体或组合。记范式能让你秒判任何新框架的定位与取舍，记 API 只会随版本作废。

## 深入：从"一步动作"反推报销案例该选什么范式

把三范式的判断法套回开头的报销故障，答案几乎是自动浮现的。报销任务的一步动作是什么？——"给定一张发票的字段，判断它是否合规、输出结构化的通过/驳回/理由"。这是一个**需要强结构化、需要校验、需要可重试**的动作，它天然贴合"给 Agent 一份带校验的表单"这个心智模型，也就是**类型安全/工程化流派**。

反观团队当初选的多 Agent 对话范式，它的"一步动作"是"一个 Agent 对另一个 Agent 说一句话，再等对方回话"——这种范式的强项是"开放式协作、角色分工、发散讨论"，适合的是"写作+评审""辩论式求解"这类需要多视角碰撞的任务。把它用在一个"抽取-校验-打分"的确定性偏强的任务上，等于让两个 Agent 为了一件本可以一步算清的事反复寒暄，既慢又贵还难调。**这就是"范式不匹配"的代价——不是框架不好，而是它的『一步动作』和你的业务需要的『一步动作』根本不是一回事。** 学会用"一步动作"这把尺子去量业务，你就再也不会犯开头那种范式错配的错误。
