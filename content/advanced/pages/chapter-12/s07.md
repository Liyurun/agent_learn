## 真实问题

报销团队的返工结案后，公司想把教训沉淀成一份"任何团队做 Agent 框架选型前都要过一遍"的清单，却发现难点不在"知道要看范式"，而在**选型的失误往往是隐性的、滞后的**：一个错误的选型，可能三个月后才以"返工""迁移""性能不达标"的形式爆发，而那时已经很难追溯到最初那次拍脑袋。把一次"我们选错了"拆成可提前预防的层——需求判断层、范式匹配层、活跃度层、退出成本层、组合正交层——再给每层配上"症状—根因—观测—修复—边界"，才是这份清单的价值。

这一节做两件事：先给出一张覆盖框架选型全流程的生产建议矩阵与一个可运行的选型自检器；再用多道"思考+回答"把全章方法论收口，直接对齐高频面试题。

## 诊断顺序：选型出问题时，按层回溯

选型翻车后（或选型评审时），不要笼统地说"框架不行"，而要按下面的顺序分层回溯，每层都有可观测的信号：

1. **需求判断层**：这个任务真的需要 Agent 吗？数流程里"模型自主决策"的分支数，若为 0，本就该写 workflow。
2. **范式匹配层**：框架的"一步动作"和业务需要的"一步动作"是同一类吗？观测是否为了迁就框架范式写了大量别扭的胶水代码。
3. **活跃度层**：框架当下还在积极开发吗？观测最近发版、官方动向（有无迁移公告）。
4. **退出成本层**：业务逻辑和框架私有 API 耦合有多深？观测业务代码里直接 import 框架的行数占比。
5. **组合正交层**：外部工具是绑死在框架里，还是走了 MCP（Model Context Protocol，模型上下文协议）这类可复用接口？观测同一能力是否被多个框架各写了一份。
6. **成本延迟层**：框架的抽象层是否带来了不可接受的隐藏 token 与调用开销？观测同任务裸调与框架版的 token/延迟差。
7. **对照**：把候选框架用同一个最小任务各跑一遍原型（同输入、同模型），横向比可观测指标，而非只读文档。

## 生产建议：框架选型全流程症状矩阵

下面把全章各层的坑汇成一张矩阵，每行都是一个真实会发生、可观测、有修复、也有不适用边界的条目。它是这份清单的主体。

| 症状 | 根因 | 如何观测与复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| 简单抽取任务被套上重型框架 | 没先问"要不要 Agent" | 数自主决策分支数，≤1 即过度 | 固定流程改写确定性 workflow | 确需多步自主决策的任务另算 |
| 按 Star 数单一维度拍板选型 | 唯人气论 | 回看选型文档只有"人气"一条理由 | 用范式匹配+活跃度+退出成本三维评估 | 一次性玩具项目容错高 |
| 选到已进维护模式的框架 | 选型前没做活跃度体检 | 查仓库最近发版与官方迁移公告 | "官方引导迁移"设为一票否决项 | 内部自维护框架不受上游影响 |
| 范式不匹配导致处处别扭 | 业务的一步动作与框架范式错位 | 单Agent结构化任务硬用多Agent对话 | 按"一步动作"最贴合的范式选 | 混合需求可组合多范式 |
| 用"功能最全"框架做简单任务 | 唯功能论 | 简单抽取被套上图状态机 | 匹配度优先于功能数 | 确需全功能的复杂任务另算 |
| 试图找"什么都能做"的框架 | 既要又要 | 需求清单里塞进互相冲突的诉求 | 允许组合多框架各司其职 | 单一诉求场景无需组合 |
| 换框架时要重写全部业务 | 业务逻辑深度耦合框架私有 API | 数业务代码 import 框架的行数占比 | 核心逻辑纯 Python + 薄适配器 | 一次性脚本无需考虑退出成本 |
| 每个框架各写一份同样的工具 | 工具绑死框架、未走标准接口 | 数同一能力被重复实现几次 | 工具做成 MCP Server 跨框架复用 | 单框架单项目收益小 |
| 为省工具重写而强行统一框架 | 混淆工具复用与框架统一 | 复现：为工具复用绑死一个框架 | 工具走横轴 MCP、框架走纵轴各选 | 团队确需统一栈时另有考量 |
| 框架抽象带来隐藏 token 膨胀 | 未评估抽象成本 | 对比裸调与框架版 input token | 延迟/成本敏感场景考虑裸写 | 复杂多轮任务收益能覆盖开销 |
| 代码即动作框架被注入危险代码 | 未用强隔离沙箱执行模型代码 | 让模型生成含 os.system 的代码 | 容器/微虚拟机沙箱 + 白名单 | 完全离线可信环境风险较低 |
| 图/状态机把简单任务搞复杂 | 给无分支任务强加节点边 | 一条直线流程被画成十节点图 | 简单任务用类型安全范式即可 | 需审计/暂停/回溯时才划算 |
| 只记框架名、框架淘汰知识作废 | 记了 API 没记范式 | 框架进维护模式后知识用不上 | 先归类范式再学具体 API | 短期一次性项目影响小 |
| 文档示例跑不通才发现框架凉了 | 没查文档新鲜度 | 照官方最新示例跑一遍 | 选型时先跑通官方 quickstart | 文档滞后但社区活跃可容忍 |
| 依赖链混入停维护底层库 | 只体检主框架没查依赖 | 扫描依赖树的弃用告警 | 体检覆盖依赖健康 | 依赖极少的微框架风险低 |
| 忽略许可链里的传染性许可 | 只看主框架许可 | 扫描依赖树发现 GPL 类许可 | 上线前做许可合规扫描 | 纯内部工具风险较低 |
| 选完不考虑团队栈与招聘 | 把决策树叶子当终极答案 | 选出的框架团队无人会用 | 叶子结果再叠加团队/合规约束 | 全新团队无历史包袱时约束少 |
| 工具结果里的指令被当命令执行 | 未把外部工具输出视为不可信 | 工具返回里塞"忽略以上指令" | 工具结果做注入防护再喂模型 | 完全可信内部工具风险较低 |

CLI（Command-Line Interface，命令行界面）工具与 SDK（Software Development Kit，软件开发工具包）的版本、许可、方法名都会变化，上线前应以官方当前页面为准复核。

## 最小可运行演示：选型自检器

把上面的诊断顺序固化成一个规则树，输入一份选型自检信号，输出首要风险层，避免"一切归结为框架不行"。它不联网、不需要 API Key。
```python
"""选型自检器（纯 Python）：把"我们是不是要选错框架了"拆到可行动的层。"""
from __future__ import annotations


def audit(s: dict) -> list[str]:
    findings = []
    if s["autonomy_branches"] <= 1:
        findings.append("需求判断层：几乎无自主决策分支，考虑写 workflow 而非上 Agent 框架")
    if s["paradigm_mismatch"]:
        findings.append("范式匹配层：一步动作与框架范式错位，重选匹配范式")
    if s["maintenance_mode"]:
        findings.append("活跃度层：候选已进维护模式，触发一票否决")
    if s["framework_import_ratio"] > 0.3:
        findings.append("退出成本层：业务与框架耦合过深，抽出纯逻辑 + 薄适配器")
    if s["tool_duplicated_across_frameworks"]:
        findings.append("组合正交层：工具被多框架重复实现，改做 MCP Server 复用")
    return findings or ["各层信号正常，用最小任务跑原型做横向对照"]


def run() -> None:
    signals = {
        "autonomy_branches": 1,
        "paradigm_mismatch": True,
        "maintenance_mode": True,
        "framework_import_ratio": 0.5,
        "tool_duplicated_across_frameworks": True,
    }
    for line in audit(signals):
        print(line)


if __name__ == "__main__":
    run()
```
保存为 `audit.py`，运行 `python audit.py`。完整预期输出：
```text
需求判断层：几乎无自主决策分支，考虑写 workflow 而非上 Agent 框架
范式匹配层：一步动作与框架范式错位，重选匹配范式
活跃度层：候选已进维护模式，触发一票否决
退出成本层：业务与框架耦合过深，抽出纯逻辑 + 薄适配器
组合正交层：工具被多框架重复实现，改做 MCP Server 复用
```
这套信号刚好把开头"发票合规审查 Agent"的五处隐患一次点亮——它同时踩中了需求判断、范式匹配、活跃度、退出成本、组合正交五层。**这个规则树只用于缩小范围、按层排查，不替代真实的原型对照实验**：它告诉你先看哪一层，具体结论仍要回到用最小任务跑原型的横向对比。

## 思考：面试官问"你们为什么选了框架 X 而不是自己写？"，怎么答得有工程判断力？

### 回答

这道题考的不是你会不会用框架，而是你**有没有评估过不用框架的可能性**。好的回答分三步。第一步，给业务的复杂度画像：多工具吗？多轮吗？需要记忆吗？需要重试与错误恢复吗？需要可观测性吗？——用这些维度证明这个任务确实落在"复杂 Agent"而非"确定性 workflow"的区间。第二步，论证框架的收益超过它的抽象成本与学习曲线：框架帮我们接管了循环控制、工具协议、状态管理等七层重复劳动，让团队专注业务，而这些如果裸写，写对所有边界情况要花的时间远超学习框架的成本。第三步，也是最能体现判断力的一步——补一句"**其中固定的子流程我们仍然用裸代码实现，没有硬塞进 Agent**"，说明你不是无脑上框架，而是对"哪部分该用 Agent、哪部分该写确定性代码"做了区分。这样从"为什么需要 Agent"到"为什么框架收益够本"再到"哪里刻意没用框架"，你的回答就立刻显得有工程判断力，而不是"别人都用所以我也用"。

### 面试精简表达

先用复杂度画像（多工具/多轮/需记忆/需重试/需可观测）证明确实需要 Agent，再论证框架收益超过抽象成本与学习曲线，最后补一句"固定子流程仍用裸代码、没硬塞进 Agent"，展示你区分过 workflow 与 Agent。

## 思考："Star 数高的框架就更好"这个判断为什么不可靠？

### 回答

因为 **Star 数是历史累积的人气存量，反映不了当下的项目生命力，更反映不了它是否适合你的场景**。它至少在三个方面会误导你。其一，**时效性**：Star 是长期累积的，一个存在越久的项目 Star 越高，但存在越久也越可能进入生命周期后半段——AutoGen 就是活教材，它 Star 量级在八个框架里数一数二，却已进入维护模式、官方引导迁移到 Microsoft Agent Framework，此时高 Star 恰恰是"存在已久"的副作用而非"值得投入"的证据。其二，**适配性**：Star 反映的是"多少人给它加过星"，不是"它多适合你的场景"——4 万 Star 的 RAG 框架未必比 1.9 万 Star 的类型安全框架更适合你的结构化输出任务。其三，**可维护性**：Star 高不代表 issue 有人回、文档跟得上、破坏性变更有迁移指南。正确做法是用"活跃度体检"六项（最近发版、issue 响应、官方动向、文档新鲜度、变更节奏、依赖健康）替代单一 Star 指标，其中"官方是否引导迁移"是权重最高的否决项。**Star 唯一的正当用途，是粗略判断社区活跃度和踩坑资料的丰富度，而不是当选型的决定性依据。**

### 面试精简表达

Star 是人气存量，不反映当下活力与场景适配。AutoGen 高 Star 却已维护模式就是反例。改用活跃度体检六项（尤其"官方动向"这个否决项）替代单一 Star，Star 只用来粗判社区资料多少。

## 思考：本书为什么选 smolagents 作为"理解本质"的第一站？

### 回答

因为 smolagents 在"抽象阶梯"上最靠近底部、内核最透明，最适合让你**看清一个 Agent 的每一步到底怎么转**。它的核心范式是"代码即动作"（CodeAgent）——让模型直接输出并执行 Python 代码作为动作，而不是受限的结构化工具调用。这种范式最贴近 Agent 的本质："想—做—看"的循环里，"做"就是执行一段模型写的代码，透明到几乎等于你亲手写的裸 ReAct 循环。放在抽象阶梯上，它处于"极简教具"这一层，仅比最底部的"裸 LLM API 调用"高一级，比 LangGraph、PydanticAI、CrewAI 都更低、更透明。本书的路线设计正是从阶梯底部起步：**先用最透明的框架理解机制，你看得清循环控制、工具协议、状态管理每一层；等理解了本质，再往上挑一个抽象层次合适的框架落地。** 如果反过来从顶层的低代码平台或高抽象框架入门，你会"会用但不懂"，一旦出问题就束手无策——这恰恰是开头报销团队在多 Agent 对话框架里踩的坑：抽象太高、机制不透明，出了 bug 谁也说不清跑偏在哪一轮。

### 面试精简表达

smolagents 内核最透明、范式是"代码即动作"，在抽象阶梯上仅高于裸 API 调用。先用它看清 Agent 每一步的机制，再往上挑合适抽象层的框架落地，避免"会用但不懂"。

## 思考：允许"在一个系统里组合多个框架"，具体怎么组合才不乱？

### 回答

组合的关键是**按职责分层、让每个框架只做它最擅长的那一层，并用清晰的接口把层与层解耦**。一个常见且务实的组合是：用 LlamaIndex 做检索层（它的数据连接器与 RAG 最强），用 PydanticAI 做结构化输出层（类型安全、可校验），中间用一层纯数据结构（比如一个 Pydantic 模型）传递检索结果，而不是让两个框架的私有对象互相直接引用。这样做有三个好处：其一，每层可独立替换——将来检索层想换个框架，只要它仍吐出同样的数据结构，输出层就不用动；其二，避免"既要又要"的通病——不强求一个框架同时做好检索和结构化输出，而是让专业的做专业的；其三，外部工具走 MCP 横向接入，任意层都能复用。要避免的反模式是"层与层之间直接传递框架私有对象"——那会让两个框架深度耦合，等于同时背上两个框架的退出成本。**组合的纪律是：框架之间只通过『不依赖任何框架的纯数据结构』通信，绝不互相引用私有类型。** 这与第 5 节的"薄适配器"、第 6 节的"MCP 正交"是同一套解耦哲学在多框架组合场景下的应用。

### 面试精简表达

按职责分层、专业的做专业的（如 LlamaIndex 检索 + PydanticAI 结构化输出），层间只用不依赖框架的纯数据结构通信、绝不互相引用私有类型，外部工具走 MCP 复用。这样每层可独立替换、不叠加退出成本。
