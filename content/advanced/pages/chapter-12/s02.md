## 真实问题

报销团队返工后，技术负责人要求写一份"框架选型备忘录"，供全公司后续项目复用。第一版备忘录写成了八段"框架介绍"，每段罗列一堆 API 名字和特性 bullet，读的人越读越晕——因为它没有回答真正的问题："**这八个框架彼此差在哪、我该拿什么维度去比它们？**"一份好的全景对比，不是八段独立简介的拼接，而是一张能横向对齐的表，让你一眼看出"同一维度下谁强谁弱、代表什么权衡"。

这一节给出这张表，并教你**怎么读**它——每一列在选型时代表什么权衡，比记住某个框架的 Star 数重要得多。

## 原理：一张表，八个框架，六个维度

下面这张表是 2026 年 8 月检索的量级快照。Star 数、生产就绪度会随时间变化，请把它当作"量级与趋势"的证据，精确数字以各仓库实时页面为准。

|---|---|---|---|---|---|---|---|

## 现象与输入：怎么读这张表——六个维度的含义

这张表信息密度很高，直接背没有意义。真正要学会的是**每一列在选型时代表什么权衡**：

- **核心范式**：最重要的一列。范式决定了你"用这个框架时的思维方式"。范式不匹配业务，其他优点都白搭——一个 RAG-first 的框架硬拿去做长时状态机，会处处别扭；反过来，一个多 Agent 对话框架硬拿去做单 Agent 结构化输出（开头报销案例），同样别扭。
- **学习曲线**：直接影响团队上手成本和交付速度。原型期权重高，长期项目权重低（一次性成本会被摊薄）。
- **生产就绪度**：包含稳定性、文档、社区问答、企业级特性（鉴权、审计、持久化）。做玩具可以忽略，做线上系统它是硬门槛。注意 AutoGen 这一列已变成"维护模式"——这是一个否决级信号。
- **许可**：Apache-2.0 / MIT 都属宽松许可，商用友好；但仍需留意依赖链里是否混入限制性更强的许可。
- **Star 量级**：只反映"人气量级"，**不反映"是否适合你"**（第 5 节专门批判这一点）。它唯一的正当用途是粗略判断社区活跃度和踩坑资料的丰富度。开头故障的教训就是——AutoGen 的 Star 量级最高，却是最不该被新项目选中的那个。
- **一句话点评**：帮你快速建立第一印象，但不能替代你自己的场景验证。

## 最小可运行演示

下面用一段纯 Python 把上表编码成结构化数据，并模拟"用不同维度权重给候选框架打分"的选型器。它演示了一个关键点：**换一组权重，排名就变**——所以"最好的框架"这个说法本身不成立，只有"对你这组权重最优的框架"。
```python
FRAMEWORKS = {
    ## 五个维度打分（1-5，5 最好），仅为教学示例，非官方评级
    "smolagents":  {"透明度": 5, "生产就绪": 3, "学习易度": 5, "生态": 3, "活跃度": 4},
    "PydanticAI":  {"透明度": 4, "生产就绪": 5, "学习易度": 4, "生态": 4, "活跃度": 5},
    "LangGraph":   {"透明度": 3, "生产就绪": 5, "学习易度": 2, "生态": 5, "活跃度": 5},
    "CrewAI":      {"透明度": 3, "生产就绪": 3, "学习易度": 5, "生态": 4, "活跃度": 4},
    "AutoGen":     {"透明度": 3, "生产就绪": 1, "学习易度": 3, "生态": 4, "活跃度": 1},
}


def score(weights: dict) -> list[tuple[str, float]]:
    ranked = []
    for name, dims in FRAMEWORKS.items():
        total = sum(dims[k] * w for k, w in weights.items())
        ranked.append((name, round(total, 1)))
    return sorted(ranked, key=lambda x: -x[1])


def run() -> None:
    ## 场景A：教学原型（看重透明度与学习易度）
    a = {"透明度": 0.4, "学习易度": 0.4, "生产就绪": 0.1, "生态": 0.05, "活跃度": 0.05}
    ## 场景B：上生产（看重生产就绪与活跃度）
    b = {"生产就绪": 0.4, "活跃度": 0.3, "生态": 0.2, "透明度": 0.05, "学习易度": 0.05}
    print("场景A 教学原型排名：", score(a)[:3])
    print("场景B 上生产排名：  ", score(b)[:3])
    print("结论：换权重就换排名，不存在脱离场景的『最好框架』")


if __name__ == "__main__":
    run()
```
保存为 `select.py`，运行 `python select.py`。完整预期输出：
```text
场景A 教学原型排名： [('smolagents', 4.6), ('CrewAI', 4.4), ('PydanticAI', 4.05)]
场景B 上生产排名：   [('PydanticAI', 4.75), ('LangGraph', 4.65), ('CrewAI', 3.45)]
```
看这两行的对比：教学原型场景 smolagents 夺冠，上生产场景 PydanticAI 反超、smolagents 甚至掉出前三；AutoGen 因为"活跃度=1、生产就绪=1"，在两个场景里都排不进前三。这就是本节最想让你记住的结论——**选型是"给你的权重找最优解"，不是"找一个绝对最强者"。**

## 真实系统对应

**官方公开机制**：表中每个框架的范式与定位均可在其官方仓库/文档核验——smolagents 的 CodeAgent（让模型写 Python 作为动作）[来源](https://github.com/huggingface/smolagents)、PydanticAI 的类型安全与结构化输出 [来源](https://github.com/pydantic/pydantic-ai)、LangGraph v1 的持久化执行与检查点 [来源](https://docs.langchain.com/oss/python/releases/langgraph-v1)、OpenAI Agents SDK 的 Agents/Handoffs/Guardrails/Sessions/Tracing 原语 [来源](https://github.com/openai/openai-agents-python)、CrewAI 的 Crews 与 Flows [来源](https://github.com/crewAIInc/crewAI)、LlamaIndex 的数据连接器与 AgentWorkflow [来源](https://github.com/run-llama/llama_index)、AutoGen 的维护模式声明 [来源](https://github.com/microsoft/autogen)。**通用工程模式**：用"多维度加权打分 + 换权重看排名变化"来做选型，是可迁移的决策方法。**教学参考实现**：上面的打分值是本书为演示"权重决定排名"而构造的，不是任何机构的官方评级，请勿引用为客观数据。

需要点明边界：这张表是"量级快照"，不是"实时榜单"。Star 数、生产就绪度、甚至归属机构都会变（AutoGen 就从"顶流"变成了"维护模式"）。**表的价值不在数字本身，而在它教你用一组稳定的维度去横向对齐——数字会过期，维度不会。**

## 生产踩坑

| 症状 | 根因 | 如何观测与复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| 备忘录写成八段独立简介 | 没用统一维度横向对齐 | 让别人读完仍答不出"谁强谁弱" | 固定六维度做成一张可对齐的表 | 只面向单一框架的教程不需要横比 |
| 引用了过期的 Star/就绪度数字 | 把快照当实时榜单 | 对照仓库实时页面发现数字已变 | 标注检索日期，用"量级"而非精确值 | 论文引用需精确时另注版本 |
| 选出"绝对最强"框架 | 忽略了权重随场景变化 | 换一组权重发现排名翻转 | 先定业务权重，再据权重排名 | 团队已有强绑定框架时约束不同 |
| 忽略许可链里的限制性依赖 | 只看主框架许可 | 扫描依赖树发现 GPL 类传染许可 | 上线前做许可合规扫描 | 纯内部工具风险较低 |
| 把 MCP 当成"第八个框架"来比 | 没理解它是正交标准层 | 试图在"范式"列给 MCP 归类 | 把 MCP 单列为横向标准（见第6节） | — |

## 思考：为什么给八个框架配"一句话记忆锚点"，比记它们的 API 更有用？

### 回答

因为 API 会变、会忘，而"锚点"抓住的是框架的**不变本质**，能让你在任何技术讨论里迅速定位对方在说哪一类东西。给八个框架各配一句最凝练的锚点：**smolagents** =「让模型直接写 Python 当动作」的透明教具；**PydanticAI** =「给 Agent 装上类型安全的骨架」的工程化框架；**LangGraph** =「把流程画成可回溯的状态图」的导演级工具；**AutoGen** =「多个 Agent 围坐对话」，但已进入维护模式、新项目慎选；**CrewAI** =「像填人事表一样声明一支团队」；**OpenAI Agents SDK** =「几个官方原语开箱即用」（Agents/Handoffs/Guardrails/Sessions/Tracing）；**LlamaIndex** =「把一切数据喂给 Agent 的 RAG 管道」；**MCP** =「不是框架，是所有框架都能插的通用工具插座」。记住这八句，你听到任何一个框架名，脑子里立刻能定位它的范式与适用边界——这比背下它某个版本的函数签名有用得多，因为函数签名明年可能就变了，而"它是干什么用的一类东西"不会变。

### 面试精简表达

锚点抓的是不变的范式本质，API 抓的是易变的语法细节。记锚点让你能在讨论里秒定位框架类别与边界，记 API 只会随版本贬值。

## 深入：为什么 AutoGen 是"高 Star、低推荐"的典型反例

把开头故障放进这张表看，格外清楚。AutoGen 的 Star 量级在八个框架里数一数二，单看"人气"列它是顶流；但把视线移到"生产就绪度"列，它已变成"维护模式"——微软把 AutoGen 与 Semantic Kernel 合并为 Microsoft Agent Framework（MAF），并在 AutoGen 官方 README 引导新项目迁移 [来源](https://github.com/microsoft/autogen) [来源](https://github.com/microsoft/agent-framework)。这就是"高 Star 不等于该选"的活教材：Star 是历史累积的人气存量，反映不了当下的项目生命力。

由此可以提炼一条读表纪律：**遇到 Star 量级特别高的框架，反而要多问一句"它现在还在积极开发吗、官方有没有迁移动向"。** 因为高 Star 往往意味着这是一个"存在已久"的项目，而存在越久，越有可能正处在生命周期的后半段。第 5 节会把这条纪律展开成一套完整的"活跃度体检"清单。这一节你只需记住：**这张全景表里，"生产就绪度"列里的"维护模式"三个字，是比任何 Star 数都优先的否决信号。**
