## 真实问题

面试的最后一击往往是：「要边流式输出边可能调工具，你怎么写？」这是生产里极常见、也极容易写错的组合。看一段候选人交出的代码：
```python
def stream_agent(user_input, client, tools_schema, tool_impls):
    messages = [{"role": "user", "content": user_input}]
    stream = client.chat.completions.create(
        model="gpt-4o", messages=messages, tools=tools_schema, stream=True)
    for chunk in stream:                          ## 流式和工具调用混在一起
        print(chunk.choices[0].delta.content, end="")   ## 直接打印 delta
    ## 没有处理 tool_calls，没有把结果喂回，没有第二轮
```
这段代码有四个足以让它在生产里翻车的问题：**流式 delta 里 content 可能是 None**（当这一段是工具调用而非文本时，`delta.content` 是 `None`，直接打印会输出 "None" 或报错）；**工具调用在流式下是分片拼接的**（`tool_calls` 的 name 和 arguments 会分散在多个 chunk 里，要按 `index` 累积拼接，不能指望一个 chunk 拿全）；**完全没有第二轮**（流式打印完就结束了，但如果模型要调工具，正确流程是收齐调用 → 执行 → 把结果喂回 → 再发起一轮让模型基于结果生成最终回答，这里工具等于白调）；**没有终止/异常/上限**（和找茬题一样，工具执行要 try/except，多轮要有步数上限）。能指出这几点，说明你真接过流式接口，不是只跑过 demo。

## 原理：流式下工具调用是「分片到达」的

普通（非流式）响应里，模型的 `tool_calls` 是一次性拿到的完整结构；但在流式响应里，为了尽早把 token 推给前端，模型的输出被切成一连串 chunk，**工具调用的 `id`、函数名、`arguments` 会分散在多个 chunk 里陆续到达**。OpenAI 官方 Function Calling 指南明确：流式模式下会先收到一个包含 `name`/`id` 的函数调用条目，随后是一系列 `arguments` 的 `delta` 增量，需要把它们**按 index 拼接**成完整参数再解析 [来源](https://platform.openai.com/docs/guides/function-calling)。这个「按 index 累积分片」正是官方 Python SDK（Software Development Kit，软件开发工具包）内部也在做的事——它对每个 `tool_call` 的 index 维护一个累积槽，把陆续到来的 name 和 arguments 片段拼起来 [来源](https://github.com/openai/openai-python/blob/main/src/openai/lib/streaming/chat/_completions.py)。所以正确处理流式 + 工具的骨架是：
```text
外层多轮循环（带 max_steps）
  └─ 发起 stream=True 请求
       └─ 逐 chunk：
            ├─ delta.content 非空 → 打印/累积文本
            └─ delta.tool_calls → 按 tc.index 累积拼接 id/name/arguments
       ├─ 若本轮没有 tool_calls → 收敛，返回累积文本（最终答案）
       └─ 若有 → 解析参数、执行、用 role="tool" 带 id 喂回 → 回到循环顶部发下一轮
```
## 最小可运行演示

真实流式接口需要 API（Application Programming Interface，应用程序编程接口）Key，不便离线复核。这里用一个**纯 Python 的 `FakeStream`** 模拟「工具调用参数被切成多个分片、逐 chunk 到达」的真实行为，让你能亲眼看到「按 index 拼接」是怎么把碎片还原成完整参数的，并跑通「执行 → 喂回 → 第二轮」的完整闭环。无需任何 Key。
```python
"""第23.6节：流式 + 工具调用的分片拼接与第二轮（纯 Python，无需 API Key）。"""
import json
from dataclasses import dataclass, field


## ---------- 模拟流式 chunk 的最小结构 ----------
@dataclass
class ToolCallDelta:
    index: int
    id: str = ""
    name: str = ""
    arguments: str = ""


@dataclass
class Delta:
    content: str = None
    tool_calls: list = field(default_factory=list)


@dataclass
class Chunk:
    delta: Delta


def fake_stream(round_no: int):
    """模拟真实流式：第 1 轮把一个工具调用切成多个分片；第 2 轮流式吐文本。"""
    if round_no == 0:
        ## 工具调用被切片：name 先到，arguments 分 3 片陆续到达（含 None content）
        yield Chunk(Delta(tool_calls=[ToolCallDelta(0, id="call_1", name="get_weather")]))
        yield Chunk(Delta(tool_calls=[ToolCallDelta(0, arguments='{"ci')]))
        yield Chunk(Delta(tool_calls=[ToolCallDelta(0, arguments='ty": "北')]))
        yield Chunk(Delta(tool_calls=[ToolCallDelta(0, arguments='京"}')]))
    else:
        ## 第二轮：模型基于工具结果流式生成最终回答（纯文本分片）
        for piece in ["北京", "今天", "34", "度。"]:
            yield Chunk(Delta(content=piece))


def get_weather(city: str) -> str:
    return json.dumps({"city": city, "temp_c": 34}, ensure_ascii=False)


TOOL_IMPLS = {"get_weather": get_weather}


def stream_agent(max_steps: int = 6) -> str:
    for round_no in range(max_steps):                    ## ① 多轮 + 步数上限
        text = ""
        tool_calls = {}                                  ## ② 按 index 累积分片
        for chunk in fake_stream(round_no):
            delta = chunk.delta
            if delta.content:                            ## ③ 非空才打印，避开 None
                text += delta.content
                print(delta.content, end="", flush=True)
            for tc in delta.tool_calls:                  ## ④ 工具调用分片拼接
                slot = tool_calls.setdefault(
                    tc.index, {"id": "", "name": "", "args": ""})
                slot["id"] += tc.id
                slot["name"] += tc.name
                slot["args"] += tc.arguments
        if not tool_calls:                               ## ⑤ 没调工具 -> 收敛
            print()
            return text
        for slot in tool_calls.values():                 ## ⑥ 执行 + 喂回
            print(f"[拼接完成] name={slot['name']} args={slot['args']}")
            try:
                result = TOOL_IMPLS[slot["name"]](**json.loads(slot["args"]))
            except Exception as e:
                result = f"工具执行失败：{e}"
            print(f"[工具结果] {result}")
        ## ⑦ 回到循环顶部，发起第二轮让模型基于结果继续（这里进入 else 分支流式输出）
    return "达到最大步数"


if __name__ == "__main__":
    print("=== 第 1 轮：流式收工具调用分片 ===")
    print("最终答复：", stream_agent())
```
保存为 `s6_stream.py`，运行 `python s6_stream.py`。预期输出：
```text
=== 第 1 轮：流式收工具调用分片 ===
[拼接完成] name=get_weather args={"city": "北京"}
[工具结果] {"city": "北京", "temp_c": 34}
北京今天34度。
最终答复： 北京今天34度。
```
看清整条链路：第 1 轮里，工具名 `get_weather` 先在一个 chunk 到达，`arguments` 被切成 `{"ci`、`ty": "北`、`京"}` 三片分别在后续 chunk 到达；代码用 `tool_calls[tc.index]` 这个累积槽把三片 `args` 拼成完整的 `{"city": "北京"}` 后才 `json.loads` 解析、执行；拿到工具结果后**回到循环顶部发起第二轮**，这一轮模型不再调工具、而是流式吐出 `北京`/`今天`/`34`/`度。` 四个文本片，累积成最终答案。原题缺失的「按 index 拼片」和「第二轮」在这里都补齐了——工具结果真正被用上，而不是白调。

## 真实系统对应

**官方公开机制**：OpenAI Function Calling 指南说明流式下工具调用先到 `name`/`id`、随后是 `arguments` 的 `delta` 增量，需按 index 拼接后解析 [来源](https://platform.openai.com/docs/guides/function-calling)；官方 Python SDK 的流式实现内部正是对每个 tool_call 的 index 维护累积槽来拼接分片 [来源](https://github.com/openai/openai-python/blob/main/src/openai/lib/streaming/chat/_completions.py)；Anthropic 的流式 tool use 同样是分片事件、需累积 [来源](https://docs.anthropic.com/en/docs/build-with-claude/tool-use)。**通用工程模式**：「delta 判空 + 按 index 累积分片 + 收齐执行 + role=tool 带 id 喂回 + 第二轮」是任何流式 Agent 都适用的骨架，与语言/框架无关。**教学参考实现**：本节 `FakeStream`、把 arguments 切成三片、第二轮吐固定文本，都是为可复核而构造，真实接入时把 `fake_stream` 换成 `client.chat.completions.create(..., stream=True)` 的真实迭代器即可，拼接与第二轮逻辑一行不改。

## 生产踩坑

| 现象 | 根因 | 如何观测与复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| 前端偶尔输出 "None" 字样 | 直接打印 `delta.content` 不判空 | 让某段是工具调用而非文本时复现 | 打印前判断 `if delta.content` 非空 | 确定永远无工具调用的纯文本流 |
| 工具参数 `json.loads` 报错 | 只取一个 chunk、未拼全 arguments | 打印每个 chunk 看 args 是否分片 | 按 `tc.index` 累积拼接后再解析 | 非流式（一次拿全）时 |
| 一次多个工具只执行了第一个 | 未按 index 分槽、覆盖了其他调用 | 构造并行多工具调用复现 | 每个 index 独立累积槽，全部执行 | 模型每轮至多一个工具时 |
| 工具调了但最终答复是空的 | 缺第二轮，工具结果没喂回 | 流式打印完就 return 复现 | 执行后喂回、回到循环顶部再发一轮 | 工具结果无需再总结时 |
| 流式卡住整个请求挂起 | 无超时、无步数上限 | 让某工具长时间不返回复现 | 工具加超时 + 外层 max_steps | 一次性短请求 |
| 喂回后模型报「找不到调用」 | 缺 `tool_call_id` 或 assistant 消息 | 漏带 id 喂回复现 | assistant 消息带 tool_calls、tool 消息带对应 id | 无工具的纯流式 |

## 思考：为什么流式模式下工具调用「必须有第二轮」，非流式时反而更容易被忽略这一点？

### 回答

先说清「第二轮」是什么：模型调工具，本质是「我需要一个外部信息才能回答」，所以完整链路一定是两段——**第一段**模型产出工具调用请求，**你执行拿到结果**，**第二段**把结果喂回、让模型基于这个结果生成真正的最终答案。缺了第二段，工具等于白调，用户拿到的要么是空的、要么是模型在没有工具结果时的瞎猜。这一点在流式模式下尤其容易被写漏，原因很微妙：流式的「爽点」就是文本一个字一个字往外蹦，写代码的人心理上默认「循环打印完 = 结束了」，于是很自然地在第一轮 `for chunk in stream` 结束后就 `return`——可第一轮流出来的根本不是最终答案，而是工具调用的分片！它「看起来在输出」，其实一个字的最终回答都还没生成。非流式模式反而不容易漏，因为拿到的 response 里明晃晃有个 `tool_calls` 字段，你不处理它、不发第二轮，代码逻辑上「明显没写完」，一眼能看出来。而流式把这个信号打散成了 delta，视觉上被「正在输出」的假象掩盖了。所以正确的心智是：**流式只是「输出的传输方式」变了，Agent「调工具要两轮」的本质一点没变**——无论流不流式，只要这一轮出现了工具调用，就必须执行、喂回、再发一轮。把这层讲清楚，面试官就知道你不是被流式的表象带偏、而是抓住了工具调用的不变本质。

### 面试精简表达

工具调用天然是两段：模型出请求 → 执行 → 喂回结果 → 再发一轮生成最终答案。流式下第一轮流出的是工具调用分片而非答案，但「正在输出」的假象让人误以为结束了就 return，于是漏掉第二轮。本质没变：只要这轮有工具调用，就必须执行、喂回、再发一轮。

## 机制推导：为什么分片要「按 index」而不是「按顺序」拼

有人会问：既然分片是陆续到达的，直接按到达顺序把 arguments 字符串首尾相接不就行了，为什么非要引入 `index`？关键在于模型可能**一次并行发起多个工具调用**（比如同时查天气和查汇率）。这时多个工具调用的分片会**交错**到达同一个流里——可能这个 chunk 是第 0 个工具的 args 片段，下个 chunk 是第 1 个工具的 name，再下个又回到第 0 个工具的 args。如果只按到达顺序首尾相接，两个工具的参数就会被拼串成一堆无法解析的乱码。`index` 的作用正是给每个并行工具调用一个稳定的「身份编号」，让你把「属于第 0 个调用的所有片段」和「属于第 1 个调用的所有片段」分别归拢到各自的累积槽里，各拼各的、互不污染。所以本节代码用 `tool_calls.setdefault(tc.index, ...)` 而不是一个字符串变量——这不是可有可无的细节，而是并行工具调用能正确工作的前提。官方 SDK 处理过「同一 chunk 出现同 index 多条目需正确合并」这类边界，也侧面印证了按 index 归拢是这套协议的核心约束 [来源](https://github.com/openai/openai-python/blob/main/src/openai/lib/streaming/chat/_completions.py)。面试时能主动点出「因为可能并行多工具，分片会交错，所以必须按 index 分槽拼」，是这道题里最能体现深度的一句话。
