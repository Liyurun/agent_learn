## 真实问题

「Agent 要支持多轮对话（用户可能连续追问），你怎么管理对话状态？」很多人写 Agent 只会单轮，一问多轮就露馅。有位候选人的实现是每轮都只把当前这句话发给模型，面试官追问「用户第二句说『那退货呢』，模型怎么知道『那』指的是上一句提到的订单」，他才意识到自己的 Agent 根本没有「记忆」。另一种常见翻车是反过来：把整段越来越长的历史每轮全量重发，跑了几十轮后上下文撑爆、变慢、账单飙升，还发现模型「注意力被稀释」——早期的关键信息被淹没在一大堆闲聊里。**这道题考的是你对「记忆/上下文」落地的理解**：多轮之所以能「记住」，靠的是 history 累积；而 history 不能无限长，必须裁剪与压缩；生产里还得按用户隔离，否则会串话。

## 原理：多轮的三件事——累积、裁剪、隔离

多轮对话状态管理有三个必答要点：

- **累积**：会话状态的核心是一份**累积的 history**。多轮能「记住」，就是因为每轮都把新消息（user 说的、assistant 答的、tool 返回的）追加进去，下一轮连同历史一起发给模型。**只存 user 不存 assistant/tool，模型下一轮就失忆了**。
- **裁剪与压缩**：history 不能无限增长。要用**滑动窗口**只保留最近 N 条，防止撑爆上下文、烧钱、注意力稀释；对被截掉的旧历史做**摘要压缩**，用一条摘要保住关键信息，而不是粗暴丢弃。这就是「每轮真正喂给模型的 messages 是临时组装的，而非把 history 原样全发」——即上下文工程。
- **隔离**：每个用户/会话要有独立状态，别共用一份 history。生产里状态要按 `session_id` 隔离并外置存储（如 Redis）。

## 最小可运行演示

下面这段代码实现一个带滑动窗口 + 摘要压缩的 `Conversation` 类，用一个不联网的 `EchoModel` 模拟多轮问答，演示：连续追问时上下文如何累积、超过窗口后旧历史如何被摘要压缩。它纯 Python、无需 API（Application Programming Interface，应用程序编程接口）Key。
```python
"""第23.5节：多轮对话状态管理（纯 Python，无需 API Key）。"""
from dataclasses import dataclass, field


def summarize(msgs: list) -> str:
    """教学用摘要器：把旧消息压成一句话，真实场景可用模型做摘要。"""
    users = [m["content"] for m in msgs if m["role"] == "user"]
    return f"用户先后问过：{'；'.join(users)}"


class EchoModel:
    """假模型：回答里带上它当前能看到的历史长度，便于观察上下文。"""
    def reply(self, messages: list) -> str:
        visible = len(messages)
        last_user = [m for m in messages if m["role"] == "user"][-1]["content"]
        return f"（我看到{visible}条上下文）已收到：{last_user}"


@dataclass
class Conversation:
    system_prompt: str
    max_context_msgs: int = 4                 ## 滑动窗口：最多保留最近 N 条
    history: list = field(default_factory=list)

    def add(self, role: str, content: str):
        self.history.append({"role": role, "content": content})

    def build_messages(self) -> list:
        """每轮临时组装：系统提示 + （必要时）旧历史摘要 + 最近窗口。"""
        system = {"role": "system", "content": self.system_prompt}
        recent = self.history[-self.max_context_msgs:]
        if len(self.history) > self.max_context_msgs:
            old = self.history[:-self.max_context_msgs]
            summary = {"role": "system", "content": f"早前对话摘要：{summarize(old)}"}
            return [system, summary] + recent
        return [system] + recent

    def turn(self, user_input: str, model) -> str:
        self.add("user", user_input)              ## ① 存 user
        messages = self.build_messages()          ## ② 临时组装上下文
        answer = model.reply(messages)
        self.add("assistant", answer)             ## ③ 别忘了存 assistant
        return answer


if __name__ == "__main__":
    conv = Conversation(system_prompt="你是客服助手", max_context_msgs=4)
    model = EchoModel()
    for q in ["我的订单到哪了", "那退货呢", "运费谁承担", "要多久到账"]:
        print(f"用户：{q}")
        print(f"助手：{conv.turn(q, model)}")
    print("--- 第 4 轮实际喂给模型的上下文 ---")
    for m in conv.build_messages():
        print(f"  [{m['role']}] {m['content']}")
```
保存为 `s5_memory.py`，运行 `python s5_memory.py`。预期输出：
```text
用户：我的订单到哪了
助手：（我看到2条上下文）已收到：我的订单到哪了
用户：那退货呢
助手：（我看到4条上下文）已收到：那退货呢
用户：运费谁承担
助手：（我看到6条上下文）已收到：运费谁承担
用户：要多久到账
助手：（我看到6条上下文）已收到：要多久到账
--- 第 4 轮实际喂给模型的上下文 ---
  [system] 你是客服助手
  [system] 早前对话摘要：用户先后问过：我的订单到哪了；那退货呢
  [user] 运费谁承担
  [assistant] （我看到6条上下文）已收到：运费谁承担
  [user] 要多久到账
  [assistant] （我看到6条上下文）已收到：要多久到账
```
从第 3 轮起，`history` 一旦超过窗口 4 条，`build_messages` 就自动把最早的两条（「订单到哪了」「那退货呢」这两轮的 user 部分）压成一条「早前对话摘要」，只保留最近 4 条原文 + 系统提示。所以模型每轮看到的上下文长度稳定在「系统提示 + 一条摘要 + 最近窗口」，从第 3 轮起都是 6 条，不再随对话增长——**既不撑爆，又不丢关键信息**。注意 `turn` 里既存了 user 又存了 assistant——漏掉后者，模型下一轮就看不到自己上轮说过什么。

## 真实系统对应

**官方公开机制**：OpenAI Function Calling / Chat 接口要求把每轮消息（含 user、assistant、tool 角色）累积进 `messages` 传入，多轮的「记忆」正是靠这份累积实现的 [来源](https://platform.openai.com/docs/guides/function-calling)；Anthropic 的多轮同样要求回填历史消息 [来源](https://docs.anthropic.com/en/docs/build-with-claude/tool-use)。**通用工程模式**：「累积 history + 每轮临时组装 + 滑动窗口 + 摘要压缩 + 按 session 隔离外置存储」是任何多轮 Agent 都适用的上下文工程手法，与框架无关。**教学参考实现**：本节 `EchoModel`、字符串拼接式 `summarize`、内存里的 `history` 都是为可复核而构造，真实系统的摘要应由模型生成、状态应按 `session_id` 外置到 Redis 等存储、并对 tool 角色消息一并保存。

## 生产踩坑

| 现象 | 根因 | 如何观测与复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| 用户追问「那……呢」模型答非所问 | 每轮只发当前句，无历史 | 连续追问带指代词复现 | 累积 history，每轮组装上下文 | 真正无状态的单轮问答 |
| 模型看不到自己上轮说过的话 | 只存 user，漏存 assistant | 让模型回顾上一轮回答复现 | user/assistant 都存回 history | 无 |
| 长对话变慢、变贵、答偏 | history 无限拼接全量重发 | 跑几十轮看 token 和延迟增长 | 滑动窗口 + 旧历史摘要压缩 | 步数天然极少的任务 |
| 多轮 + 工具时模型对不上调用 | 漏存 tool 角色的中间消息 | 多轮里穿插工具调用复现 | tool 消息（带 id）也存进历史 | 纯文本无工具的对话 |
| 甲用户看到乙用户的对话 | 所有用户共用一份 history | 并发两个会话看是否串话 | 按 session_id 隔离 + 外置存储 | 单用户本地脚本 |
| 服务重启后对话记忆全丢 | 状态只在内存、无持久化 | 重启进程看历史是否还在 | 状态外置到 Redis/数据库 | 允许无记忆的一次性会话 |

## 思考：为什么「每轮真正喂给模型的 messages 要临时组装」，而不是直接把 history 全发过去？

### 回答

因为「累积的 history」和「本轮该给模型看的上下文」是两回事，把它们混为一谈是多轮翻车的根源。history 是**完整的档案**，为了可追溯、可持久化，它应该尽量全；但每轮真正塞进模型的 messages 是**本轮的工作台**，受三重现实约束：其一是**上下文窗口有限**，history 迟早会超过模型能吃下的长度，全发直接报错；其二是**成本与延迟**，输入 token 越多越贵越慢，把几十轮闲聊每次全发是巨大的浪费；其三是**注意力稀释**，上下文越长，早期真正关键的信息越容易被淹没，模型反而抓不住重点。所以正确的架构是把二者分离：history 尽量完整地留档，而每轮通过一个 `build_messages` 这样的函数**临时组装**——放系统提示、放被截掉旧历史的摘要、放最近窗口的原文，甚至可以按当前问题动态检索相关的历史片段放进去。这就是第 21 章讲的「上下文工程」：决定每一轮到底放什么进上下文，是一个主动的工程决策，而不是「把有的全倒进去」。理解了这层分离，你才能回答「历史很长怎么办」——答案不是「想办法塞下」，而是「本来就不该全塞，该组装」。所以面试时可以说：「history 是完整档案要尽量留全，但每轮喂给模型的是临时组装的工作台，受窗口、成本、注意力三重约束，靠滑动窗口和摘要来组装，这就是上下文工程。」

### 面试精简表达

history 是完整档案（要留全、可持久化），每轮喂给模型的 messages 是临时组装的工作台（受窗口、成本、注意力三重约束）。二者分离，用滑动窗口 + 摘要组装——这就是上下文工程，不是「想办法把历史全塞进去」。

## 优化前后对比：从「全量重发」到「临时组装」

优化前的多轮实现常是 `messages = system + self.history`——把累积历史原样全发。短对话看不出问题，一旦对话变长就三宗罪齐发：**撑爆**（超过上下文窗口直接报错）、**变贵变慢**（每轮输入 token 随轮数线性增长）、**答偏**（早期关键信息被大量后续闲聊淹没，注意力稀释）。而且这种实现完全不可观测——你不知道模型每轮到底看到了什么。优化后引入 `build_messages` 临时组装：每轮的上下文长度被稳定控制在「系统提示 + 一条摘要 + 最近窗口」，无论对话跑到第几十轮都不撑爆、成本可控；被截掉的旧信息不是丢弃而是摘要保留，关键信息不丢；而且组装逻辑是显式的，你能清楚知道并调节每轮放了什么。从「无脑全发」到「主动组装」，正是作业级多轮与生产级多轮的分水岭。
