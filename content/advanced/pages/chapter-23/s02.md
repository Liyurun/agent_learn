## 真实问题

找茬题是面试官最省力、区分度最高的一类考法：他贴出一段「随手写」的 Agent 循环，问「这段有几个问题」。有位候选人只看出「死循环」一个问题就停了，面试官不动声色地问「还有吗」，他答「加个 `try/except` 应该就行」——结果这道满分十条的题他只拿了两条。**找茬题的评分逻辑是「能指出几个」**：面试官心里有一张缺陷清单，你说中的越多分越高。更关键的是，这张清单几乎是所有 Agent 生产事故的浓缩——死循环、轻信模型、工具无防护、幻觉工具名、参数不校验、上下文不裁剪、无超时、无可观测、无预算、校验本身不可靠。能一眼看穿，说明你有实战意识；只看出一条，说明你只跑过 Demo。

## 现象与输入：这段「坏代码」错在哪

这就是贯穿全章的那段坏代码，也是面试里最经典的找茬样本：
```python
def agent_loop(task):
    while True:                                    ## 缺陷 1
        action = model.decide(task)
        if action.is_done:                         ## 缺陷 2
            return action.answer
        result = tools[action.tool](**action.args) ## 缺陷 3、4、5、7
```
三个最致命的问题先点出来，再补七条隐藏隐患：

| 编号 | 缺陷 | 后果 | 修复 |
|---|---|---|---|
| 1 | `while True` 无终止上限 | 模型陷入循环，无限烧 token | 加 `max_iters` 步数上限 |
| 2 | 完全轻信模型说「完成」 | 模型虚假声称完成，任务实际没做完 | 加 `verify_completion` 客观校验 |
| 3 | 工具调用无异常处理 | 一次报错整个程序崩溃 | 包 `try/except`，异常当观察喂回 |
| 4 | `tools[action.tool]` 无存在性检查 | 模型编造工具名直接抛 `KeyError`（行动幻觉） | 先判断 `action.tool in tools` |
| 5 | 参数不校验就 `**action.args` | 类型错、缺字段、恶意内容直接执行 | 执行前用 schema 校验（见第 4 节） |
| 6 | 历史/上下文不累积也不裁剪 | 模型失忆，或上下文无限增长撑爆 | 累积 history + 滑动窗口（见第 5 节） |
| 7 | 工具调用无超时 | 网络请求卡住让整个循环挂起 | 给工具调用加 timeout |
| 8 | 全程无可观测 | 线上出问题无从排查 | 记录每轮 Thought/Action/Observation |
| 9 | 只有步数上限、无 token/成本预算 | 单步超长上下文也可能极贵 | 再加一个 token 预算上限 |
| 10 | 越权/幂等/审批全缺 | 可能越权访问或重复执行副作用 | 权限校验 + 幂等键 + 高危动作人工审批 |

## 最小可运行演示

把上面十条缺陷全部修好，得到一个可离线跑通的「加固版」循环。它不联网、无需 API（Application Programming Interface，应用程序编程接口）Key，用 mock 模型和工具演示每一处防护如何生效：包括制造一次工具异常、一次幻觉工具名、一次高危动作触发审批。
```python
"""第23.2节：找茬题的加固版循环（纯 Python，无需 API Key）。"""
import json
from dataclasses import dataclass, field


@dataclass
class Action:
    is_done: bool = False
    answer: str = ""
    tool: str = ""
    args: dict = field(default_factory=dict)


RESTRICTED = {"refund"}                 ## 高危工具：需人工审批
LOG = []                                ## 可观测：记录每一步


def tool_search(q): return f"检索到关于「{q}」的资料"
def tool_divide(a, b): return a / b     ## 故意可能除零，演示异常防护
def tool_refund(order): return f"已退款 {order}"
TOOLS = {"search": tool_search, "divide": tool_divide, "refund": tool_refund}


def verify_completion(answer, task) -> bool:
    ## 客观校验：这里用“答案非空且含关键词”模拟，真实应尽量用测试等客观信号
    return bool(answer) and "资料" in answer


class ScriptedModel:
    """按脚本产出决策，覆盖正常/异常/幻觉/高危四种情况。"""
    def __init__(self): self.i = -1
    def decide(self, task, history):
        self.i += 1
        script = [
            Action(tool="search", args={"q": "退货政策"}),      ## 正常
            Action(tool="divide", args={"a": 1, "b": 0}),        ## 触发异常
            Action(tool="ghost_tool", args={}),                  ## 幻觉工具名
            Action(tool="refund", args={"order": "O-77"}),       ## 高危需审批
            Action(is_done=True, answer="检索到关于退货政策的资料，已处理完毕"),
        ]
        return script[min(self.i, len(script) - 1)]


def agent_loop(task, model, tools, max_iters=10, token_budget=8000):
    used_tokens = 0
    for step in range(max_iters):                       ## 修1：步数上限
        if used_tokens >= token_budget:                 ## 修9：token 预算上限
            return "达到 token 预算上限，转人工"
        action = model.decide(task, LOG)
        used_tokens += 100                              ## 模拟每轮 token 消耗
        if action.is_done and verify_completion(action.answer, task):  ## 修2：客观校验
            LOG.append(("final", action.answer))
            return action.answer
        if action.tool in RESTRICTED:                   ## 修10：高危动作人工审批
            LOG.append(("await_human", action.tool))
            return f"动作 {action.tool} 需人工审批，已挂起"
        if action.tool not in tools:                    ## 修4：工具存在性检查
            obs = f"没有名为 {action.tool} 的工具"
        else:
            try:
                obs = tools[action.tool](**action.args) ## 修3/7：异常防护（生产再加超时）
            except Exception as e:
                obs = f"工具执行失败：{e}"
        LOG.append((action.tool, str(obs)))             ## 修8：可观测，逐步记录
    return "达到最大迭代次数"


if __name__ == "__main__":
    result = agent_loop("处理退货咨询", ScriptedModel(), TOOLS)
    print("最终结果：", result)
    print("--- 全链路 trace ---")
    for i, (step, detail) in enumerate(LOG, 1):
        print(f"{i}. [{step}] {detail}")
```
保存为 `s2_debug.py`，运行 `python s2_debug.py`。预期输出：
```text
最终结果： 动作 refund 需人工审批，已挂起
--- 全链路 trace ---
1. [search] 检索到关于「退货政策」的资料
2. [divide] 工具执行失败：division by zero
3. [ghost_tool] 没有名为 ghost_tool 的工具
4. [await_human] refund
```
逐条看防护如何生效：第 1 步正常检索；第 2 步 `divide(1, 0)` 本会抛 `ZeroDivisionError`，被 `try/except` 转成一条可读观察，程序不崩；第 3 步模型编了个 `ghost_tool`，存在性检查把它挡下当观察喂回，而不是 `KeyError` 崩溃；第 4 步模型要调高危的 `refund`，被审批闸拦下挂起。这四步恰好演示了找茬清单里最容易被忽视的「异常、幻觉工具名、高危审批」三类隐患都被兜住了。

## 真实系统对应

**官方公开机制**：OpenAI 把「副作用动作前暂停等人工审批（human-in-the-loop）」「输入/输出/工具三类护栏」列为构建 Agent 的官方控制手段 [来源](https://platform.openai.com/docs/guides/function-calling)；工具调用的 `arguments` 是需要解析的字符串，解析失败要能兜住，这也是官方协议的一部分。**通用工程模式**：死循环上限、客观校验完成、异常即观察、工具存在性检查、参数校验、上下文裁剪、超时、可观测、预算、幂等/审批——这十条是任何自建 Agent 都适用的加固清单，与框架无关。**教学参考实现**：`ScriptedModel` 按固定脚本产出四种情况、`LOG` 作为内存 trace、`verify_completion` 用关键词模拟校验，都是为可复核而构造，真实系统请把校验换成客观信号（如测试是否通过）、把 `LOG` 换成真正的 tracing。

## 生产踩坑

| 现象 | 根因 | 如何观测与复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| 会话偶发不收敛、账单飙升 | `while True` 无上限 | 构造模型反复要求调工具的输入 | `max_iters` + token/成本预算双上限 | 一次性问答无循环 |
| 任务显示「完成」但结果是空的 | 轻信 `is_done`，无客观校验 | 让模型对未完成任务声称完成 | 用测试/规则等客观信号 verify | 低风险纯咨询 |
| 偶发 `KeyError` 导致 500 | 工具名未做存在性检查 | 诱导模型输出不存在的工具名 | `tool in tools` 判断后当观察喂回 | 输出被严格约束为固定枚举时 |
| 退款/删除被模型「自主」执行 | 高危动作无审批闸 | 让模型直接调副作用工具 | 高危工具白名单 + 人工审批中断 | 纯只读查询工具 |
| 同一操作被重复执行多次 | 重试无幂等键 | 在工具执行后模拟超时重试 | 幂等键去重 + 记录已执行动作 | 天然幂等的只读操作 |
| 线上报错无法定位到具体步骤 | 全程无 trace | 制造一次失败看能否还原过程 | 逐步记录 Thought/Action/Observation | 一次性脚本、无需追溯 |

## 思考：为什么「轻信模型说完成」比「死循环」更隐蔽、更危险？

### 回答

死循环虽然致命，但它「吵」——监控上一定表现为调用量异常、账单飙升，很快会被告警发现并掐断，属于「响亮的失败」。而「轻信模型说完成」是一种「安静的失败」：程序正常返回、没有报错、监控一切正常，用户却拿到了一个「声称完成实则没做」的结果。比如让 Agent「把这三份报告合并并发邮件」，模型可能只合并了两份就自信地回「已完成并发送」，程序照常返回成功，直到收件人反馈「怎么少一份」才暴露——这时污染可能已经扩散。它的危险正在于**不触发任何技术告警，只在业务结果上出错**，排查成本极高。根因是把「模型的自我声称」当成了「任务的客观完成」，而大模型有讨好倾向，倾向于说「我做完了」。正确做法是尽量用**客观信号**验证完成：能跑测试就跑测试、能查数据库状态就查状态、能对比预期产出就对比，而不是问模型「你做完了吗」。当校验本身也不得不用模型时（第 10 条隐患），要意识到它同样可能误判，关键任务应尽量降低对模型自评的依赖。所以面试时可以这样收尾：「死循环是响亮的失败，会被监控抓到；轻信模型是安静的失败，只在业务上出错，反而更该防——校验完成要用客观信号，不能问模型自己。」

### 面试精简表达

死循环是「响亮的失败」，监控会抓到；轻信模型是「安静的失败」，程序正常返回却在业务上出错，排查成本更高。修法是用客观信号（测试/状态/预期产出）验证完成，而非问模型「你做完了吗」。

## 答题节奏：先致命后隐藏的「一口气」打法

找茬题拼的是覆盖度与节奏。推荐这样答：先用一句话框住三大致命——「这段最要命的是三点：`while True` 会死循环烧钱、直接信 `is_done` 会被模型骗、工具裸调用一报错就崩」——干净利落点完；然后换一口气说「除此之外还有几个更细的隐患」，把七条隐藏一条一条快速列出，每条一句后果加一句修法。这样面试官会明显感到你「不是背了三条，而是脑子里真有一张完整清单」。切忌只答一条就停，也切忌把七条掰碎成长篇大论——**先密后疏、先致命后细节**，是找茬题拿高分的表达节奏。练习时可以自己故意写一段有 bug 的 Agent 代码，计时找茬，把这十条练到脱口而出。
