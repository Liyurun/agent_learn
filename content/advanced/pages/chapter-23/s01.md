## 真实问题

白板题「不用任何框架，写一个 ReAct（Reasoning and Acting，推理与行动）Agent 的核心循环」几乎是所有 Agent 岗位的第一道门槛。一位候选人上来写了 `while True: answer = model(task); return answer`，面试官只问了一句「模型要查天气才能回答，你这段怎么查」，他就卡住了——因为他脑子里的 Agent 还停留在「问一次答一次」，没有「模型决定调工具 → 代码执行 → 结果喂回 → 再决定」的循环概念。另一位候选人写出了循环，却用 `while True` 没有上限，被追问「模型如果反复调工具不停会怎样」，才意识到线上会无限烧 token 直到账单爆炸。**这道题考的不是语法，是你对 Agent 本质的理解**：去掉框架的糖衣，Agent 的骨架到底是什么。

## 原理：Agent 的骨架就是一个带工具的循环

ReAct 论文把「推理（Reasoning）」与「行动（Acting）」交替进行的范式讲得很清楚：模型先产生一段思考（Thought），再决定一个动作（Action），环境返回观察（Observation），如此循环直到给出最终答案 [来源](https://arxiv.org/abs/2210.03629)。落到代码，它就是一个循环，每一轮做四件事：
```text
      ┌─────────────────────────────────────────────┐
      │  ① 终止条件：步数是否到上限 / 模型是否说完成      │
      ▼                                               │
用户任务 ──▶ ② 模型决策（Thought+Action）：调哪个工具、传什么参数
      │                                               ▲
      ▼                                               │
   ③ 代码执行工具（Action），拿到 Observation ─────────┘
      │
      └─▶ ④ 把 (决策, 观察) 记入历史，进入下一轮
```
四个拿分点缺一不可：**循环上限**（否则无限烧钱）、**决策与执行分离**（模型只「决定」，代码来「执行」）、**异常即观察**（工具报错不崩溃，而是把错误喂回让模型应对）、**兜底返回**（到上限要优雅退出，不能悬挂）。

## 最小可运行演示

下面这段代码不依赖任何框架、不联网、无需 API（Application Programming Interface，应用程序编程接口）Key，用一个 `MockModel` 模拟「会决策的大模型」，把上面四个点全部落地。它能真正跑通贯穿全章的那条任务——「查北京气温，超过 30 度就算 25+5」。
```python
"""第23.1节：完全可运行的最小 ReAct Agent（纯 Python，无需 API Key）。"""
from dataclasses import dataclass, field


## ---------- 工具箱：真正干活的函数，由代码执行，而非模型 ----------
def look_up_weather(city: str) -> dict:
    fake_db = {"北京": 34, "上海": 28}         ## 教学假数据，确定性可复核
    return {"city": city, "temp_c": fake_db.get(city, 20)}


def add(a: int, b: int) -> int:
    return a + b


TOOLS = {"look_up_weather": look_up_weather, "add": add}


## ---------- 决策对象：模型每一步的输出结构 ----------
@dataclass
class Decision:
    kind: str                 ## "tool" 调工具 / "final" 给最终答案
    tool: str = ""
    args: dict = field(default_factory=dict)
    answer: str = ""


## ---------- 教学用假模型：按“历史长度”决定下一步，绝不联网 ----------
class MockModel:
    def decide(self, task: str, history: list) -> Decision:
        step = len(history)
        if step == 0:
            return Decision("tool", tool="look_up_weather", args={"city": "北京"})
        if step == 1:
            temp = history[-1][1]["temp_c"]        ## 读上一步观察
            if temp > 30:
                return Decision("tool", tool="add", args={"a": 25, "b": 5})
            return Decision("final", answer=f"北京 {temp} 度，未超过 30，无需备用金")
        total = history[-1][1]
        temp = history[0][1]["temp_c"]
        return Decision("final", answer=f"北京 {temp} 度已超 30，备用金 25+5={total}")


## ---------- 核心循环：Agent 的骨架 ----------
def react_agent(task: str, tools: dict, model, max_steps: int = 10) -> str:
    history = []
    for step in range(max_steps):                  ## ① 终止条件：步数上限
        decision = model.decide(task, history)      ## ② 模型只“决定”
        if decision.kind == "final":                ## ③ 模型认为完成
            return decision.answer
        if decision.tool not in tools:              ## 存在性检查：挡住“行动幻觉”
            observation = f"没有名为 {decision.tool} 的工具"
        else:
            try:
                observation = tools[decision.tool](**decision.args)  ## 代码执行
            except Exception as e:                  ## ④ 异常即观察，不崩溃
                observation = f"工具执行出错：{e}"
        history.append((decision, observation))      ## 记入历史，进入下一轮
    return "达到最大步数，任务未完成"                  ## ⑤ 兜底返回


if __name__ == "__main__":
    task = "北京今天多少度？超过30度就算25+5的备用金"
    print("最终答复：", react_agent(task, TOOLS, MockModel()))
```
保存为 `s1_react.py`，运行 `python s1_react.py`。预期输出：
```text
最终答复： 北京 34 度已超 30，备用金 25+5=30
```
这段代码的每个编号都是一个可以讲出来的设计点：**①** `max_steps` 是硬性终止条件，没有它一旦模型反复调工具就会烧到破产；**②** 模型的 `decide` 只返回一个 `Decision` 对象，它自己**不执行任何工具**；**③** 收敛信号是模型主动给出 `kind="final"`；**④** 工具报错被 `try/except` 转成一条可读观察喂回，模型可据此换参重试；**⑤** 到上限优雅返回。把「查天气→判断→算术→汇总」这条链走通，就证明你理解了 Agent 不是「问答」而是「带工具的循环」。

## 从伪代码到真 API：Function Calling 骨架

如果面试官允许你写得更接近真实接口，可把 `MockModel.decide` 换成一次真实的 Function Calling 调用。其协议骨架（以 OpenAI 官方指南为准 [来源](https://platform.openai.com/docs/guides/function-calling)）是：把工具的 JSON（JavaScript Object Notation）Schema 传给模型 → 模型返回一个或多个 `tool_calls`（每个含 `id`、函数名、`arguments` 字符串）→ 你 `json.loads` 解析参数、执行、把结果用 `role="tool"` 且带 `tool_call_id` 追加回 `messages` → 再发一轮，直到模型不再要求调工具。四个最容易写错的细节：`arguments` 是**字符串**要解析、一次可能返回**多个** `tool_calls` 要循环、结果必须带对应 `tool_call_id`、把模型每轮输出**原样追加**进 `messages` 才能保持上下文。跨供应商可对照 Anthropic 的 tool use 文档，其循环范式一致，只是字段名不同 [来源](https://docs.anthropic.com/en/docs/build-with-claude/tool-use)。

## 真实系统对应

**官方公开机制**：OpenAI Function Calling 的 `tool_calls` 结构、`arguments` 为 JSON 字符串、以 `role="tool"` 带 `tool_call_id` 回填的协议，均见官方指南 [来源](https://platform.openai.com/docs/guides/function-calling)；ReAct 的「思考—行动—观察」交替循环出自原论文 [来源](https://arxiv.org/abs/2210.03629)。**通用工程模式**：循环上限、决策与执行分离、异常即观察、兜底返回，这四点可迁移到任何自建 Agent，不依赖特定框架。**教学参考实现**：本节 `MockModel`、`look_up_weather` 的假数据、按历史长度决策的逻辑，都是为可复核而构造，真实接入时把 `decide` 换成真实模型调用即可，循环骨架一行不改。

## 生产踩坑

| 现象 | 根因 | 如何观测与复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| Agent 偶尔无限循环烧 token | 循环无步数上限（`while True`） | 让模型反复调同一工具即可复现 | `for step in range(max_steps)` 硬上限 + token 预算 | 一次性单步问答，无循环 |
| 模型编造不存在的工具名后崩溃 | 未做工具存在性检查 | 提示词里诱导模型调一个假工具名 | 先判断 `tool in tools`，否则把「无此工具」当观察喂回 | 工具集合极小且强约束输出时 |
| 一个工具报错整个程序挂掉 | 工具调用未包 `try/except` | 让工具抛异常（如除零）观察是否崩溃 | 异常转成可读观察喂回，让模型自愈 | 关键写操作，需 fail-fast 而非续跑 |
| 模型说「完成了」但其实没做完 | 完全轻信模型的 final 信号 | 构造模型虚假声称完成的样本 | 关键任务用客观信号（测试/校验）验证 | 低风险纯咨询问答 |
| 上下文越滚越长、变慢变贵 | 历史无裁剪，每轮全量重发 | 让对话跑很多轮看 token 增长 | 滑动窗口 + 摘要压缩（见第 5 节） | 步数天然很短的任务 |

## 思考：为什么一定要强调「模型只决策、代码来执行」，直接让模型执行不行吗？

### 回答

因为大模型本质上是一个「文本生成器」，它没有真正执行代码、访问数据库、调用网络的能力——它能做的只是**生成「我想调用某工具、参数是这些」这段文本**。真正把这段文本变成一次数据库查询或一次转账的，永远是你的代码。这不是实现细节，而是 Agent 架构的第一性原理，带来三个直接好处。其一是**安全**：执行权在代码手里，你才能在执行前插入权限校验、参数校验、人工审批等护栏；如果「让模型执行」，模型一句话就能触发副作用，等于把方向盘交给了一个会一本正经胡说的乘客。其二是**可控与可观测**：因为执行由代码做，你能精确记录每一次工具调用的入参、耗时、结果，出了问题能定位到具体某一步；模型「黑箱执行」则完全无从排查。其三是**可测试**：决策与执行分离后，工具就是普通函数，可以脱离模型单独做单元测试，而模型层可以用 mock 替换——本节的 `MockModel` 正是靠这个分离才能离线跑通。所以面试时被追问，标准表达是：「模型负责决定调什么工具、传什么参数，我的代码负责校验、执行、把结果喂回，二者严格分离，安全、可控、可测试都建立在这条边界上。」

### 面试精简表达

模型只会「生成调用请求」这段文本，真正执行的是代码。分离带来安全（执行前可加护栏）、可观测（每步可记录）、可测试（工具可单测、模型可 mock）三大收益，是 Agent 架构的第一性原理。

## 事故回放：一次「循环上限」缺失的线上烧钱

某团队上线初期把内测时的 `while True` 直接带到了生产，只在本地测过「一两步就收敛」的顺利样本。上线后遇到一个边界输入：模型每轮都坚持「还需要再查一次」，工具每次返回的数据又不足以让它判定完成，于是循环停不下来。因为没有步数上限、也没有 token 预算上限，单个会话在十几分钟里发起了上千次模型调用，直到监控告警「单会话调用量异常」才被人工掐断，事后核算这一个会话的花费顶得上平时几百个正常会话。复盘的修复只有两行——加 `max_steps` 与单会话 token 预算——但教训是：**Demo 顺利不代表生产安全，任何循环都必须先有硬上限，再谈优化**。这也是找茬题（第 2 节）里「死循环」永远排第一的原因。

## 思考：白板上时间只够写一版，是先写伪代码还是先写「能跑」的完整版？

### 回答

答案取决于面试官的信号，但有一套稳妥的通用打法：**先用能跑的结构把骨架写出来，再口头补全细节**。很多人纠结「写伪代码显得不够扎实、写完整版又怕时间不够、还容易在语法上卡壳」，其实这是个假两难。正确做法是分三步走。第一步，先写一个「结构完整、细节留白」的版本——`for step in range(max_steps)` 的主循环、决策与执行分离的两个分支、`try/except` 的异常位置、兜底 return 全都摆出来，但工具的具体实现、模型的具体调用可以先用一个函数名占位。这样面试官第一眼看到的就是一个「结构对、要点全」的骨架，比一段能编译但没有护栏的代码分高得多。第二步，边写边讲，把「这里为什么要有上限、这里为什么要分离、这里为什么把异常当观察」同步说出来——**讲解本身就是在为你可能写不完的部分兜底**，即使代码没写完，面试官也已经知道你懂。第三步，如果时间和面试官的兴趣都允许，再把占位的部分填成真能跑的实现（比如本节的 `MockModel`），或者主动说「如果接真实 API，这里就是一次 Function Calling 调用，返回 tool_calls 我解析执行再喂回」。这套打法的核心是：**结构优先于细节、讲解优先于补全、能跑是加分项而非及格线**。所以别在「伪代码还是完整版」上纠结，先把结构和要点稳稳拿下，剩下的用嘴补、有时间再用手补。这样即使铃声响起你只写了一半，那一半也是「一看就懂行」的一半。

### 面试精简表达

先写「结构完整、细节留白」的骨架（主循环、分离、异常位置、兜底都摆出来），边写边讲要点，有时间再把占位填成能跑的实现。结构优先于细节、讲解优先于补全、能跑是加分项不是及格线——这样即使没写完，写出的部分也是「一看就懂行」的。
