## 真实问题

「给你一个『查询订单』的需求，请定义一个工具，并说明如何保证模型传参不出错。」有位候选人的工具定义只写了一行 docstring「查订单」，参数说明只写了个类型 `order_id: str`。面试官问「模型如果不给订单号、或者给了个格式明显不对的值，会怎样」，他答「那就报错呗」——于是这道题基本判负。**因为这道题考的正是两件生产里天天出问题的事**：工具的 description 决定模型「用不用得对」，schema 校验决定「传错了怎么兜住」。第 6 章反复强调：模型完全依赖 description 判断何时用、怎么用，写不好是工具调用失败的头号原因；而参数错了直接抛异常崩溃，是新手 Agent 最常见的线上事故。

## 原理：description 管「用对」，schema 管「兜住」

一个生产级工具定义有两层防线：

- **第一层 description（给模型看）**：要说清三件事——这个工具是干嘛的、什么时候该用、缺参数时怎么办（向用户要，别臆造）。给参数写清描述和**示例格式**，能显著降低模型传错的概率。这是「用对」的前提。
- **第二层 schema 校验（给运行时用）**：即便 description 写得好，模型偶尔仍会传错——类型不对、缺字段、格式看似对实则非法。这时要在执行前用 schema（如 Pydantic）校验，非法就返回一条**可读的错误信息**喂回模型让它自己修正，而不是抛异常崩溃。这是「兜住」的保障。

Pydantic 的 `Field(description=...)` 一举两得：它既是给模型看的参数说明，又是运行时的校验器；配合 `field_validator` 还能做业务级校验 [来源](https://docs.pydantic.dev/latest/concepts/validators/)。这与 OpenAI Function Calling 用 JSON（JavaScript Object Notation）Schema 描述工具、要求把 `arguments` 字符串解析后校验的机制一致 [来源](https://platform.openai.com/docs/guides/function-calling)。

## 最小可运行演示

下面用**纯标准库**实现一个「查订单」工具的完整两层防线：不依赖 Pydantic（避免安装依赖，无需 API Key 即可运行），用一个手写的 `validate` 函数模拟 schema 校验，演示合法、格式非法、缺字段三种输入分别如何被处理。文末会说明真实项目里如何用 Pydantic 一行替换。
```python
"""第23.4节：工具定义 + 参数校验双保险（纯标准库，无需 API Key）。"""
import json


## ---------- 工具的 JSON Schema：既是给模型的说明，也是校验依据 ----------
GET_ORDER_SCHEMA = {
    "name": "get_order",
    "description": (
        "查询指定订单的状态与信息。"
        "当用户询问某个具体订单的状态、金额、时间时使用；"
        "需要用户提供订单号；若用户没给订单号，先向用户询问，不要臆造。"
    ),
    "parameters": {
        "order_id": {
            "type": "str", "required": True,
            "description": "订单号，形如 'ORD' 开头加 8 位数字，例如 ORD12345678",
        },
        "include_items": {
            "type": "bool", "required": False, "default": False,
            "description": "是否返回订单内的商品明细，默认不返回",
        },
    },
}


def validate(raw: dict, schema: dict):
    """模拟 schema 校验：类型 + 必填 + 业务格式，任一不过就返回可读错误。"""
    params = schema["parameters"]
    cleaned = {}
    for key, spec in params.items():
        if key not in raw:
            if spec.get("required"):
                return None, f"缺少必填参数 {key}"
            cleaned[key] = spec.get("default")
            continue
        val = raw[key]
        if spec["type"] == "str" and not isinstance(val, str):
            return None, f"参数 {key} 类型应为 str"
        if spec["type"] == "bool" and not isinstance(val, bool):
            return None, f"参数 {key} 类型应为 bool"
        cleaned[key] = val
    ## 业务级校验：订单号格式
    oid = cleaned.get("order_id", "")
    if not (oid.startswith("ORD") and oid[3:].isdigit() and len(oid) == 11):
        return None, "order_id 格式非法，应为 ORD + 8 位数字，例如 ORD12345678"
    return cleaned, None


def get_order(order_id: str, include_items: bool = False) -> dict:
    ## ... 真实场景在这里查数据库 ...
    return {"order_id": order_id, "status": "已发货",
            "items": ["3C 数码配件"] if include_items else []}


def call_get_order(raw_args: dict):
    """执行入口：先校验再执行，非法参数转成可读错误喂回模型。"""
    cleaned, err = validate(raw_args, GET_ORDER_SCHEMA)
    if err:
        return f"参数校验失败：{err}。请修正后重试。"    ## 让模型自己改
    return get_order(**cleaned)


if __name__ == "__main__":
    cases = [
        {"order_id": "ORD12345678"},                 ## 合法
        {"order_id": "ORD12345678", "include_items": True},
        {"order_id": "123"},                          ## 格式非法
        {"include_items": True},                      ## 缺必填字段
    ]
    for raw in cases:
        print(f"输入 {raw}")
        result = call_get_order(raw)
        if isinstance(result, dict):
            print(f"  -> {json.dumps(result, ensure_ascii=False)}")
        else:
            print(f"  -> {result}")
```
保存为 `s4_tool.py`，运行 `python s4_tool.py`。预期输出：
```text
输入 {'order_id': 'ORD12345678'}
  -> {"order_id": "ORD12345678", "status": "已发货", "items": []}
输入 {'order_id': 'ORD12345678', 'include_items': True}
  -> {"order_id": "ORD12345678", "status": "已发货", "items": ["3C 数码配件"]}
输入 {'order_id': '123'}
  -> 参数校验失败：order_id 格式非法，应为 ORD + 8 位数字，例如 ORD12345678。请修正后重试。
输入 {'include_items': True}
  -> 参数校验失败：缺少必填参数 order_id。请修正后重试。
```
三种非法输入都**没有让程序崩溃**，而是转成一条可读错误——这正是「传错怎么兜住」的答案：把错误喂回模型，让它读懂后修正参数重试，而不是抛异常中断整个 Agent。

## 上一步输入与下一步输出：错误如何喂回让模型自愈

这个工具在真实 Agent 里是一个闭环。给出示例的上一步输入与预期下一步输出，帮助理解「喂回—修正」链路：
```text
【上一步】模型第一次调用（传了非法订单号）：
  {"tool": "get_order", "args": {"order_id": "12345678"}}

【工具返回（作为观察喂回模型）】：
  "参数校验失败：order_id 格式非法，应为 ORD + 8 位数字，例如 ORD12345678。请修正后重试。"

【预期下一步】模型读到错误后自我修正，重新调用：
  {"tool": "get_order", "args": {"order_id": "ORD12345678"}}
  -> {"order_id": "ORD12345678", "status": "已发货", "items": []}
```
关键在于错误信息要**可读、可操作**（写清「应为什么格式、给个例子」），模型才能据此改对；如果只返回一个 `ValueError` 堆栈，模型往往修不对。

## 真实系统对应

**官方公开机制**：OpenAI Function Calling 用 JSON Schema 描述工具与参数，模型返回的 `arguments` 是字符串需解析后校验 [来源](https://platform.openai.com/docs/guides/function-calling)；Pydantic 官方文档说明 `field_validator` 可做自定义校验、`Field` 承载描述 [来源](https://docs.pydantic.dev/latest/concepts/validators/)；Anthropic 的 tool use 同样以 schema 定义输入并要求处理校验 [来源](https://docs.anthropic.com/en/docs/build-with-claude/tool-use)。**通用工程模式**：「description 说清用途/何时用/缺参怎么办 + schema 校验 + 失败喂回让模型修正」这条链路可迁移到任何工具定义，与是否用 Pydantic 无关。**教学参考实现**：本节手写的 `validate` 只为免依赖、可离线运行而构造，真实项目建议直接用 Pydantic——把 `GetOrderArgs(BaseModel)` 定义好后，`GetOrderArgs(**raw_args)` 一行就完成类型 + 业务校验，异常里带的正是可读错误信息。

## 生产踩坑

| 现象 | 根因 | 如何观测与复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| 模型频繁不调该调的工具 | description 太简（如「查订单」三字） | 看模型是否绕过工具直接编答案 | 写清用途 + 何时用 + 缺参向用户要 | 工具极少且强制调用时 |
| 模型总传错参数格式 | 参数只写类型、没给示例 | 统计校验失败里的格式错误占比 | 参数描述加示例格式（ORD12345678） | 参数是自由文本无固定格式 |
| 非法参数直接抛异常崩溃 | 执行前不校验 | 传一个类型错误的参数看是否崩 | 执行前 schema 校验，失败喂回 | 参数来源完全可信时 |
| 模型缺参数时臆造一个假值 | description 没说「缺参向用户要」 | 不提供必填参数看模型行为 | 明确写「没给就问用户，别臆造」 | 参数有安全默认值时 |
| 校验通过但业务上非法 | 只校验类型、没做业务校验 | 传一个类型对但格式非法的值 | 加 `field_validator` 业务级校验 | 无业务约束的纯技术参数 |
| 工具太复杂模型总用错 | 一个工具塞了太多职责 | 看单个工具的参数是否过多 | 拆分成多个单一职责的小工具 | 职责天然内聚不可拆时 |

## 思考：模型老是传错某个工具的参数，你的排查和修复顺序是什么？

### 回答

标准答案是一条从「反思自己」到「兜住模型」再到「重构工具」的链路，顺序不能乱。**第一步，先反思 description 写清了没有**——模型传错，八成是因为它没读懂这个工具该怎么用。检查描述是否说清了用途、何时用、参数含义，很多「模型太笨」其实是「说明书太烂」。**第二步，给参数加类型和示例**——只写 `order_id: str` 远不如写「订单号，形如 ORD 加 8 位数字，例如 ORD12345678」，一个具体示例能极大降低传错率。**第三步，加 schema 校验**——即便前两步做好，模型仍会偶尔出错，所以执行前必须用 schema 兜一道，非法就拦下。**第四步，校验失败把可读错误喂回让模型修正**——错误信息要写清「应该是什么、给个例子」，模型才能据此改对，而不是抛一个它读不懂的堆栈。**第五步，如果以上都做了还频繁出错，考虑工具是不是太复杂该拆分**——一个塞了七八个参数的工具，模型很难每次都填对，拆成几个单一职责的小工具往往立竿见影。整条链路的精神是「先反思自己的工具定义，再去兜模型的错，最后才怀疑是不是设计本身有问题」，而不是一上来就抱怨「模型不行」。这个排查顺序本身就体现了成熟工程师「先向内归因」的习惯。

### 面试精简表达

顺序是：先反思 description 写清没有 → 参数加类型和示例 → 加 schema 校验 → 失败把可读错误喂回让模型修正 → 还不行就考虑工具太复杂该拆分。精神是「先向内归因」，别一上来怪模型。

## 归因训练：把「模型太笨」翻译成可改进项

很多人遇到工具调用出错的第一反应是「模型不够聪明」，这是最没有产出的归因——因为它指向一个你无法改变的对象。资深工程师会把这句抱怨**翻译成具体的可改进项**：模型没调该调的工具 → 我的 description 是不是没说清「何时用」；模型传了错格式 → 我是不是没给示例；模型缺参数时瞎编 → 我是不是没写「缺了就问用户」；模型对复杂工具总填错 → 这个工具是不是该拆。你会发现，几乎每一个「模型的错」背后，都藏着一个「我的工具定义可以更好」的改进点。把归因从「模型」转向「我的定义」，你才拿回了改进的主动权——这也是工具定义题真正想筛出来的思维方式。
