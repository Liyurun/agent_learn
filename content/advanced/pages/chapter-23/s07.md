## 真实问题

同一道白板题，两位候选人写出的代码几乎一样，得分却差了一档。差在哪？高分那位从动笔前就说「我先搭主循环，再补终止条件、异常、护栏」，写到工具调用时顺口点出「这里模型只出请求、参数要校验」，写完还做了一次自我 review「终止条件有了、异常有了，还差可观测和 token 预算，生产要补上」；低分那位闷头写完、一言不发，代码对了却让面试官无从判断他到底懂多少。**实操题筛的从来不是「你背没背过语法」，而是三样东西**：你脑子里有没有 Agent 的骨架结构、你有没有踩过生产的坑（终止/异常/护栏/可观测）、你会不会一边写一边把设计意图讲清楚。这一节把前六节的散点收敛成一套可复用的方法论，并给出一个能帮你养成「自我 review」习惯的可运行清单脚本。

## 原理：实操题的四条通用技巧

无论哪种考法，下面四条都适用：

- **边写边讲**：白板写代码时同步说出每一行的设计意图，让面试官看到你的思路，而不是等他猜。
- **先骨架后细节**：先把主循环/主流程搭出来，再补异常、护栏、可观测，体现结构化思维——这也正是第 1 到 6 节每段代码的写法。
- **主动补 Demo 与生产的差距**：写完最小版，主动说「生产还要加 X、Y、Z」，一句话就体现你知道 Demo 和生产的距离。
- **不确定就说不确定**：某个 API（Application Programming Interface，应用程序编程接口）记不清，就说「具体 API 名我记不准，但逻辑是……」，别硬编一个错字段——逻辑对了远比字段名对了重要。

## 最小可运行演示

把「自我 review」从一句口头禅变成一个**可运行的检查清单脚本**：给它一段（简化表示的）Agent 代码具备哪些防护，它逐项核对「生产就绪清单」并打出得分与缺口。你可以把它当成练习白板题后的自查工具。它纯 Python、无需 API Key。
```python
"""第23.7节：实操题自我 review 清单（纯 Python，无需 API Key）。"""
from dataclasses import dataclass, field


## 生产就绪清单：每一项对应本章某一节强调的防护
CHECKLIST = {
    "has_step_limit":   "循环有步数上限（防死循环烧 token）—— 第 1/2 节",
    "sep_decide_exec":  "决策与执行分离（模型只出请求，代码执行）—— 第 1 节",
    "exception_as_obs": "工具异常转观察喂回（不崩溃）—— 第 1/2 节",
    "tool_exists_check":"工具存在性检查（挡行动幻觉）—— 第 2 节",
    "arg_validation":   "参数 schema 校验 + 失败喂回 —— 第 4 节",
    "verify_done":      "用客观信号校验完成（不轻信模型）—— 第 2 节",
    "context_trim":     "多轮上下文滑动窗口 + 摘要 —— 第 5 节",
    "session_isolation":"按 session 隔离 + 外置存储 —— 第 5 节",
    "stream_second_round":"流式下有第二轮、按 index 拼片 —— 第 6 节",
    "observability":    "全链路可观测（逐步记录）—— 第 2 节",
    "token_budget":     "token/成本预算上限 —— 第 2 节",
    "hitl_approval":    "高危动作人工审批 —— 第 2 节",
}


@dataclass
class Review:
    have: set = field(default_factory=set)   ## 这段代码已具备的防护项

    def run(self):
        got = [k for k in CHECKLIST if k in self.have]
        missing = [k for k in CHECKLIST if k not in self.have]
        score = round(100 * len(got) / len(CHECKLIST))
        print(f"生产就绪度：{score} 分（{len(got)}/{len(CHECKLIST)} 项）")
        print("已具备：")
        for k in got:
            print(f"  [√] {CHECKLIST[k]}")
        print("仍缺（面试时主动说“生产还要补”）：")
        for k in missing:
            print(f"  [ ] {CHECKLIST[k]}")


if __name__ == "__main__":
    ## 模拟“第 1 节最小 Agent”写完后的自查：它具备哪些、还缺哪些
    demo = Review(have={
        "has_step_limit", "sep_decide_exec", "exception_as_obs", "tool_exists_check",
    })
    demo.run()
```
保存为 `s7_review.py`，运行 `python s7_review.py`。预期输出：
```text
生产就绪度：33 分（4/12 项）
已具备：
  [√] 循环有步数上限（防死循环烧 token）—— 第 1/2 节
  [√] 决策与执行分离（模型只出请求，代码执行）—— 第 1 节
  [√] 工具异常转观察喂回（不崩溃）—— 第 1/2 节
  [√] 工具存在性检查（挡行动幻觉）—— 第 2 节
仍缺（面试时主动说“生产还要补”）：
  [ ] 参数 schema 校验 + 失败喂回 —— 第 4 节
  [ ] 用客观信号校验完成（不轻信模型）—— 第 2 节
  [ ] 多轮上下文滑动窗口 + 摘要 —— 第 5 节
  [ ] 按 session 隔离 + 外置存储 —— 第 5 节
  [ ] 流式下有第二轮、按 index 拼片 —— 第 6 节
  [ ] 全链路可观测（逐步记录）—— 第 2 节
  [ ] token/成本预算上限 —— 第 2 节
  [ ] 高危动作人工审批 —— 第 2 节
```
这个脚本的价值不在代码本身，而在那份 12 项清单：它把「Demo 与生产的差距」量化成可勾选的项。白板写完最小 Agent，你只需照着念缺口——「我这个最小版有步数上限、决策执行分离、异常处理和存在性检查，但还缺参数校验、可观测、token 预算、人工审批，生产要补上」——一句话就把「知道差距」演示给了面试官。这正是「主动补 Demo 与生产差距」这条技巧的落地形态。

## 真实系统对应

**官方公开机制**：清单里的「高危动作人工审批」「输入/输出/工具护栏」对应 OpenAI 构建 Agent 的官方控制手段 [来源](https://platform.openai.com/docs/guides/function-calling)；「从简单起步、按需增复杂度」呼应 Anthropic《Building Effective Agents》与 OpenAI 实践指南的核心主张 [来源](https://www.anthropic.com/engineering/building-effective-agents) [来源](https://cdn.openai.com/business-guides-and-resources/a-practical-guide-to-building-agents.pdf)。**通用工程模式**：这份 12 项清单是从前六节归纳的通用加固项，可作为任何 Agent 代码评审（code review）的检查表，与框架无关。**教学参考实现**：`Review` 类、打分方式是为把「自省」变成可操作动作而构造，真实评审可把它扩成 CI（Continuous Integration，持续集成）里的静态检查或评审模板。

## 生产踩坑

| 现象 | 根因 | 如何观测与复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| 代码写对了却被判「不够深」 | 闷头写、不讲设计意图 | 回放面试录音看讲解占比 | 边写边讲每行意图，先说结构再动手 | 明确要求「只写不说」的笔试 |
| 卡在某个 API 名上僵住 | 试图硬憋精确语法 | 计时看卡壳时长 | 讲清「我需要一个能做 X 的调用」，别硬编 | 开卷可查文档时 |
| 最小版被当成「不懂生产」 | 没说 Demo 与生产的差距 | 看是否主动补「生产还要加」 | 写完主动列缺口清单 | 题目明确只要玩具 demo |
| 一上来就写复杂框架代码 | 未从骨架起步 | 看首行是否直接堆细节 | 先搭主循环，再逐层加固 | 题目指定用某框架 API |
| 硬编错字段暴露没写过 | 不懂装懂报精确参数 | 核对字段名是否真实存在 | 逻辑优先，硬数据坦承不确定 | 无 |
| 写完不检查、带着 bug 交卷 | 缺自我 review 习惯 | 提交前是否复盘缺口 | 用清单做一次自查再收尾 | 时间极紧的抢答 |

## 思考：面试官出白板实操题，真正想筛的到底是什么？

### 回答

不是「你能不能写出一份能编译通过的完美代码」，而是三样很难靠背诵伪装的东西。**第一样是脑中有没有 Agent 的骨架结构**——你能不能不假思索地说出「给工具、模型决策、代码执行、结果喂回、循环到收敛」这个内核，并在此之上加终止条件、异常、护栏。有骨架的人写代码是「往结构里填」，没骨架的人是「东拼一句西凑一句」，一眼能看出来。**第二样是有没有踩过生产的坑**——终止条件、异常处理、参数校验、可观测、token 预算、人工审批，这些不是读文档能读来的，是被线上事故教育过才会条件反射地想到；面试官贴一段坏代码让你找茬，就是在测这个。**第三样是表达能力**——你会不会一边写一边把「为什么这么写」讲清楚。这一样常被忽视，却极其关键：Agent 工程是团队协作，一个能把设计意图讲明白的人，评审、带人、跨团队沟通都更高效；反过来，代码再对、讲不清楚，协作成本就高。这三样任何一样过硬都能加分，三样都有基本就是「一看就是真写过 Agent 的人」。所以练习实操题时，别只练「把代码写对」，更要练「把代码讲明白」——把每一行为什么这么写都能脱口而出，把 Demo 与生产的每一处差距都能随口列出，把不确定的地方诚实标出来。**能写、能讲、知边界，这才是实操题的最高境界。**

### 面试精简表达

筛三样：脑中有没有 Agent 骨架结构、有没有生产坑意识（终止/异常/护栏/可观测）、会不会边写边讲设计意图。任一过硬都加分，三样都有就是「一看就真写过」。所以要练的不只是写对，还有讲明白和知边界。

## 完整实践

把本章七节的能力连成一条可自测的练习链，建议按顺序过一遍：

1. 不看书，白板手写第 1 节的最小 ReAct（Reasoning and Acting，推理与行动）循环，说出四个关键设计点，再升级成 Function Calling 版本，边写边讲。
2. 把第 2 节找茬题的十条缺陷（三大致命 + 七条隐藏）默写到脱口而出，找一段自己故意写错的代码计时找茬。
3. 用第 3 节的决策树，针对「实时股价问答」「批量文档审核」两个新场景各做一次口头选型，讲清理由与共性内核。
4. 用第 4 节的思路为「查天气」「发邮件」各写一个带 description 和校验的工具定义，测试传错参数时是否被可读错误兜住。
5. 写一个支持多轮 + 工具调用的 `Conversation` 类（第 5 节），验证连续追问时上下文正确累积、超窗后被摘要压缩。
6. 把第 6 节流式骨架跑通，改一版「并行两个工具调用」的分片，验证按 index 拼接是否正确。
7. 用第 7 节的清单脚本给自己写的每段代码打分，念出缺口，练成收尾时的条件反射。

## 本章小结

- 实操题七大关卡：**手写最小 Agent、代码找茬、框架选型、工具定义与校验、多轮状态管理、流式 + 工具调用、通用技巧**，一场白板面试常把它们串起来逐层加难。
- 手写最小 Agent 的骨架：**循环上限、决策与执行分离、异常即观察、兜底返回**；升级到 Function Calling 还要注意 `json.loads` 解析、多 `tool_calls` 循环、`role="tool"` 带 id 喂回。
- 代码找茬：先点三大致命（**死循环、轻信模型、工具无防护**），再补七条隐藏（幻觉工具名、参数不校验、上下文不裁剪、无超时、无可观测、无预算、校验本身不可靠）。
- 框架选型没有标准答案，要**给场景、给理由**，并讲清「框架内核都是同一个循环，差异在封装了什么」。
- 工具定义：**description 说清用途/何时用/缺参怎么办 + schema 校验 + 失败喂回让模型修正**，排查传错要「先向内归因」。
- 多轮状态：**累积 history + 每轮临时组装 + 滑动窗口/摘要 + 按 session 隔离外置存储**，history 是档案、messages 是工作台。
- 流式 + 工具：**delta 判空 + 按 index 累积分片 + 收齐执行 + role=tool 带 id 喂回 + 必须有第二轮**，本质仍是「调工具要两轮」。
- 通用技巧：**边写边讲、先骨架后细节、主动补 Demo 与生产的差距、不懂就说不懂、写完自我 review**——能写、能讲、知边界。
