## 真实问题

导读故障定位后，团队决定「以后不能再靠肉眼翻日志了」，要给退款 Agent 接可观测性。有人主张直接上商用平台，但技术负责人拍板：先让每个工程师用不到 60 行代码手搓一个能跑的 tracer（追踪器），理解 trace（追踪）/ span（跨度）到底是什么数据结构——**因为你不理解它的数据模型，就永远只是在平台 UI（User Interface，用户界面）上瞎点，看不懂火焰图为什么长那样，也不知道该往 span 里记什么**。这一节就带你手搓这个 tracer，它的心智模型和 Langfuse、LangSmith 这类平台底层是一致的。

关键问题有三个：一条 trace 到底是什么结构？为什么要用「树」而不是「列表」组织 span？父子关系靠什么字段维护、又怎么保证「即使代码崩了也能记下耗时」？把这三个问题搞清楚，你就掌握了整个可观测性大厦的地基。

## 原理：Trace / Span / 父子关系

**Trace** 是 Agent 一次完整运行的结构化记录，它把「思考—行动—观察」的每一环都记下来。一条好的 trace 通常长这样：
```text
Trace (一次完整运行)
 ├─ Span: LLM 调用 1      → prompt、输出、token 数、耗时、成本
 ├─ Span: 工具调用 search → 参数、返回结果、耗时、是否成功
 ├─ Span: LLM 调用 2      → ...
 ├─ Span: 工具调用 calc   → ...
 └─ Span: 最终输出        → 结束原因（自然终止 / 强制停止）
```
其中每个 **Span** 是一个可计时、可嵌套的步骤。关键要记录的字段：

| 类别 | 应记录的内容 |
|---|---|
| 模型调用 | 输入 prompt、输出、使用的模型、token 数、耗时、成本 |
| 工具调用 | 工具名、参数、返回结果、耗时、成功/失败 |
| 循环控制 | 第几轮、终止原因（自然/强制）、是否触发上限 |
| 上下文 | 关键的上下文快照（便于复现问题） |

有了这些，你就能回答「它到底经历了什么」。

### Trace / Span 的父子结构从哪来

「Trace 由 Span 组成」这个模型不是 Agent 领域发明的，它直接借用了分布式系统里的 **OpenTelemetry** 标准（第 4 节详述）。核心概念只有三个：

- **Trace**：一次完整请求的唯一标识（`trace_id`），像一根主干。
- **Span**：主干上的一个工作单元，有自己的 `span_id`、开始/结束时间。
- **父子关系**：每个 Span 记录一个 `parent_span_id`，从而拼成一棵**调用树**（而不只是一条平铺的列表）。

为什么需要「树」而不是「列表」？因为 Agent 会嵌套：一个「规划 Span」下面可能挂着三个「子任务 Span」，每个子任务下面又各自挂着若干「LLM（Large Language Model，大语言模型）调用 Span」和「工具调用 Span」。树形结构能让你在任意一层「折叠/展开」，先看全局再钻进细节。这正是 Langfuse、LangSmith 这类平台 UI 背后的数据模型——LangSmith 明确把「一次操作触发的所有 run 绑定到同一条 trace，由唯一 trace ID 关联」[来源](https://docs.langchain.com/langsmith/observability-concepts)。
```text
trace_id=abc (整次运行)
└─ span: plan (parent=root)
   ├─ span: subtask_1 (parent=plan)
   │  ├─ span: llm_call   (parent=subtask_1)
   │  └─ span: tool.search(parent=subtask_1)
   └─ span: subtask_2 (parent=plan)
      └─ span: tool.calc  (parent=subtask_2)
```
平铺列表丢掉的恰恰是「谁触发了谁」这层因果。导读故障里「某次 llm_call 触发了 get_order，get_order 空返回又触发下一次 llm_call」——如果只有平铺列表，你看到的是一堆孤立的 span；只有在树里，你才能顺着父子边把这条因果链走出来。

## 最小可运行演示

理解 trace 最好的方式是自己写一个。下面用不到 60 行 Python 实现一个能嵌套、能计时、能算成本的极简 tracer，它不联网、不需要 API Key（Application Programming Interface Key，接口密钥），心智模型和商用平台一致。
```python
"""极简 Tracer(纯 Python):能嵌套、能计时、能算成本、崩溃也落 span。"""
import time
import uuid
from contextlib import contextmanager
from dataclasses import dataclass, field


@dataclass
class Span:
    name: str
    span_id: str
    parent_id: str | None
    start: float
    end: float | None = None
    attrs: dict = field(default_factory=dict)   # 存 tokens/成本/参数/结果/异常等

    @property
    def duration_ms(self) -> float:
        return round((self.end - self.start) * 1000, 1) if self.end else -1.0


class Tracer:
    def __init__(self) -> None:
        self.spans: list[Span] = []
        self._stack: list[str] = []              # 当前 span 栈,用来维护父子关系
        self._clock = 0.0                         # 教学用逻辑时钟,保证输出可复现

    def _now(self) -> float:
        self._clock += 0.001                      # 真实代码用 time.time();此处固定步进
        return self._clock

    @contextmanager
    def span(self, name: str, **attrs):
        sp = Span(name=name, span_id=uuid.uuid4().hex[:8],
                  parent_id=self._stack[-1] if self._stack else None,
                  start=self._now(), attrs=dict(attrs))
        self.spans.append(sp)
        self._stack.append(sp.span_id)
        try:
            yield sp                              # 允许调用方往 sp.attrs 里补记结果
        except Exception as exc:                  # 关键:崩溃也要落 span
            sp.attrs["error"] = type(exc).__name__
            raise
        finally:
            sp.end = self._now()
            self._stack.pop()

    def _depth(self, sp: Span) -> int:
        by_id = {s.span_id: s for s in self.spans}
        d, pid = 0, sp.parent_id
        while pid:
            d += 1
            pid = by_id[pid].parent_id
        return d

    def dump(self) -> None:
        for sp in self.spans:
            indent = "  " * self._depth(sp)
            print(f"{indent}{sp.name:16s} {sp.attrs}")


def simulate(sec: float) -> None:
    """教学替身:不真的 sleep,让 duration 由逻辑时钟决定,输出可逐字复现。"""
    _ = sec


if __name__ == "__main__":
    tracer = Tracer()
    with tracer.span("agent_run", task="退款订单A-2026"):
        with tracer.span("llm_call", model="strong") as s:
            simulate(0.05)
            s.attrs.update(tokens=1200, cost=0.0040)     # 事后补记 token 和成本
        with tracer.span("tool.get_order", args={"order_id": "A-2026"}) as s:
            simulate(0.09)
            s.attrs.update(ok=False, rows=0)             # 故障当晚的空返回
    tracer.dump()
```
保存为 `mini_tracer.py`，运行 `python mini_tracer.py`。完整预期输出：
```text
agent_run        {'task': '退款订单A-2026'}
  llm_call         {'model': 'strong', 'tokens': 1200, 'cost': 0.004}
  tool.get_order   {'args': {'order_id': 'A-2026'}, 'ok': False, 'rows': 0}
```
逐行讲解设计要点：

- **`@contextmanager` + `with` 语法**是关键设计。用 `with tracer.span(...)` 包住任意代码块，进入时开始计时、压栈，退出时（哪怕抛异常）在 `finally` 里结束计时、出栈。这保证了**即使代码报错，span 的耗时也会被正确记录**——这点对排查「在哪一步崩的」至关重要。
- **`_stack` 维护父子关系**：压栈时把当前栈顶作为新 span 的 `parent_id`，于是嵌套的 `with` 自然形成父子树，不需要手动传父节点。缩进打印时靠 `_depth` 顺着 `parent_id` 往上数层级。
- **`yield sp` 把 span 交回调用方**：这样你能在工具跑完后往 `s.attrs` 里补记真实结果（`tokens`、`cost`、`ok`、`rows`），而不用在开始时就知道这些值。
- **`except` 分支记异常再 `raise`**：这是「崩溃也落 span」的落地——把异常类型记进 `attrs["error"]` 后再抛出，既不吞掉异常，又留下了「哪一步崩了」的证据。

这里用逻辑时钟 `_now` 代替真实 `time.time()`，纯粹是为了让教学输出可逐字复现；生产代码直接用 `time.time()` 即可。真实平台无非是把这个 `dump` 换成了带火焰图的 Web UI，底层的 span 数据结构和这里一模一样。

> **常见误区**：只在「成功路径」上记 trace，异常时直接 `raise` 跳过记录。结果线上一崩，你手里恰恰没有那次失败的 trace，等于最需要证据时证据没了。正确做法就是上面 `finally` 里那样——**无论成功失败都落一条 span**，并把异常信息也记进 `attrs`。

### Trace 该记多细？粒度的权衡

写 tracer 时一个绕不开的问题是：到底记多细？记太粗（只记「跑了一次、耗时 5 秒」）等于没记，出了问题还是抓瞎；记太细（连模型每个中间 token、每次内存分配都记）则会拖慢系统、撑爆存储，反而淹没关键信息。经验上的「黄金粒度」是：**以一次「模型调用」或一次「工具调用」为一个 span**——这个粒度既能定位到「哪一步」，又不会细到失去焦点。这也正好对齐 OpenTelemetry GenAI 语义约定里「一次推理调用是一个 span」的设计 [来源](https://github.com/open-telemetry/semantic-conventions/blob/main/docs/gen-ai/gen-ai-spans.md)。

在 span 内部，字段的取舍也有讲究。有几类信息几乎总是值得记：输入 prompt（或其摘要/哈希）、输出、token 数、耗时、成功与否。有几类要谨慎：完整的原始 prompt 可能很长且含敏感信息（第 3、8 节的 PII 问题），可以只存摘要或做脱敏；工具返回如果是大 JSON，可以只记结构和关键字段，而非整个 blob。判断标准很简单：**问自己「排查问题时我会需要看这个字段吗」**，会就记，不会就省。

还有一个容易忽略的点：**span 之间要能关联输入输出**。也就是说，光记录「LLM span 输出了什么」不够，你还要能看出「这个输出被当作下一个工具 span 的哪个参数」。这种「数据流向」的可追溯性，是定位「脏数据传播」这类跨步骤故障的关键——你得能顺着数据一路看它是怎么从一个正确的输入，一步步变成最终那个错误输出的。

## 真实系统对应

**官方公开机制**：LangSmith 用 `trace` / `run` 两级概念，一条 trace 由多个 run 组成、共享 trace ID，且单条 trace 有 25000 个 run 的上限 [来源](https://docs.langchain.com/langsmith/observability-concepts)；Langfuse 用 `trace` / `observation`（其中 `generation` 是记录 LLM 调用的特化 observation），并按 observation 记录用量与成本 [来源](https://langfuse.com/docs/api-and-data-platform/features/observations-api)；OpenTelemetry 则用 `trace_id` / `span_id` / `parent_span_id` 三字段拼调用树 [来源](https://github.com/open-telemetry/semantic-conventions/blob/main/docs/gen-ai/gen-ai-spans.md)。名字不同，父子树的心智模型完全一致。**通用工程模式**：用上下文管理器 + 栈维护父子关系、用 `finally` 保证崩溃也落 span、以「一次调用」为粒度，是可迁移到任何语言与框架的写法。**教学参考实现**：上面的 `Tracer` 用逻辑时钟仅为输出可复现，不代表任何平台的采样、批量导出或持久化机制。

需要点明边界：商用平台在这个数据模型之上还做了大量本 tracer 没有的事——持久化存储、跨进程上下文传播、采样、批量异步导出、UI 检索。手搓 tracer 是为了理解**数据模型**，不是为了替代平台（第 7 节讲选型）。

## 生产踩坑

| 症状 | 根因 | 如何观测与复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| 线上崩溃后没有那次的 trace | 只在成功路径记 span | 让工具抛异常看是否留痕 | try/except/finally 保证崩溃也落 span | 进程被 kill -9 时确实无法保证 |
| span 全平铺、看不出因果 | 没记 parent_id,当成日志列表 | 去掉 parent_id 建树复现 | 用栈维护 parent_id 拼调用树 | 单 span 任务树退化为点属正常 |
| 存储爆炸、查询变慢 | 粒度过细,记了中间 token/内存 | 把粒度调到每 token 一 span 复现 | 以「一次调用」为 span 黄金粒度 | 深度调试单步时可临时细化 |
| trace 里存了用户手机号 | 原样记录 prompt/返回未脱敏 | 用含 PII 的输入跑一遍看落库 | 落库前脱敏/只存摘要哈希 | 完全内部无敏感数据场景较轻 |
| 补记不到工具真实结果 | 开始时就固化 attrs,没留补记口 | 工具跑完发现无处写 rows | yield span 出去,允许事后 update | 无返回值的工具无需补记 |
| 深层嵌套缩进算错 | 手动传层级而非顺 parent 数 | 三层嵌套看缩进是否错位 | 靠 parent_id 递归求 depth | 扁平结构无嵌套时无此问题 |

## 思考：为什么要用「树」而不是「列表」来组织 Span？父子关系靠什么字段维护？

### 回答

用树而不是列表，核心是为了**保留「谁触发了谁」的因果结构，并支持按层折叠/展开**。Agent 的执行天然是嵌套的：一个规划步骤下面挂着多个子任务，每个子任务下面又挂着若干 LLM 调用和工具调用。如果用平铺列表存 span，你只能看到「先后发生了什么」，却看不出「这个工具调用是哪次规划触发的、它的结果又被哪次模型调用读走」——而这恰恰是定位跨步骤故障（如脏数据传播）最需要的信息。树形结构还带来一个实用价值：可以在任意一层折叠，先看全局耗时分布，再展开某个可疑子树钻进细节，这正是所有商用平台火焰图 UI 的交互基础。父子关系靠每个 span 记录一个 `parent_span_id`（本章代码里的 `parent_id`）来维护：根 span 的 `parent_id` 为空，其余每个 span 指向它的直接父节点，整棵树就靠这一个字段递归还原出来；同一次运行的所有 span 再共享一个 `trace_id` 归到一条 trace 下。实现上，用一个「span 栈」在进入 `with` 时把当前栈顶设为新 span 的父、退出时出栈，就能让嵌套的代码块自动形成正确的父子树，无需手动传递父节点。

### 面试精简表达

树保留了 span 之间「谁触发谁」的因果、支持折叠展开钻取,列表丢掉了这层因果;父子关系靠每个 span 记 parent_span_id 维护,根节点为空,同一次运行共享 trace_id,用一个 span 栈在进出 with 时压栈出栈就能自动建树。

## 思考：为什么 tracer 一定要保证「崩溃也落 span」？

### 回答

因为**最需要 trace 的时刻恰恰是崩溃发生的时刻**，而如果只在成功路径上记 span、异常时直接把错误抛出去，你就会在最该有证据的时候两手空空。设想线上某个工具偶发超时抛异常，如果 tracer 没有在异常路径落 span，那么这次失败运行不会留下任何 trace，你连「它崩在第几步、崩之前的输入是什么、前面几步耗时多少」都无从得知，只能等下次复现——但偶发故障往往很难复现。正确做法是用 `try/except/finally` 包住 span 的生命周期：在 `finally` 里无条件结束计时、出栈（保证耗时和层级一定被记下），在 `except` 里把异常类型记进 span 的属性再重新 `raise`（既留下「哪一步崩了、崩于何种异常」的证据，又不吞掉异常、不改变原有的错误传播行为）。这样无论成功还是失败，每一步都留痕，事故复盘时才有完整现场。唯一无法保证的极端情况是进程被强制杀死（如 `kill -9` 或 OOM），此时连 `finally` 都来不及跑，需要靠异步批量导出或落盘缓冲来兜底。

### 面试精简表达

因为崩溃时才最需要证据,只记成功路径等于最需要时没数据;用 try/except/finally——finally 保证耗时和层级一定落、except 记下异常类型再 raise(不吞异常),就能崩溃也留痕;唯一兜不住的是 kill -9 这类连 finally 都跑不到的情况。
