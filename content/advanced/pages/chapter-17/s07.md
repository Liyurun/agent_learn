## 真实问题

退款 Agent 手搓 tracer（追踪器）用了三个月后，团队撞上了自建的天花板：trace（追踪）越存越多，自己搭的存储撑不住检索；产品经理想看一条 trace 却打不开链接（没有 Web UI，User Interface，用户界面）；接入的搜索 Agent、对话 Agent 各写各的 tracer，数据格式不一致无法汇总；有人想复用开源的自动埋点省去手动打点，却不知道选哪个。技术负责人这才意识到：**手搓 tracer 是用来「理解原理」的，跑生产得上平台**。可是市面上 OpenLLMetry、LangSmith、Langfuse、Arize Phoenix、OpenLIT 一大堆，到底怎么选？开源还是托管？会不会被锁死？

这一节做两件事：先讲清「自建 vs 平台」的决策边界，再横向梳理 2026 年主流的几个 LLM（Large Language Model，大语言模型）可观测性平台各自的定位、机制与选型考量，并明确标注它们的公开机制边界——不臆造任何未公开的内部实现。

## 原理：自建 vs 平台，以及平台生态的两条路线

### 自建 vs 用平台：一张决策表

到底手搓 tracer 还是直接上平台？取决于阶段和规模：

| 维度 | 自建（如第 2 节的极简 tracer） | 用平台（LangSmith/Langfuse/OpenLLMetry 生态等） |
|---|---|---|
| 上手成本 | 低，几十行代码 | 中，需接 SDK（Software Development Kit，软件开发工具包）/配置后端 |
| 存储与查询 | 自己搞，很快撑不住 | 内置持久化、检索、聚合 |
| 可视化 | 靠 print | 火焰图、时间线、对比视图 |
| 团队协作 | 难共享 | 链接即可分享一条 trace |
| 适用阶段 | 学习/原型/理解原理 | 团队协作/生产规模 |

结论：**用自建 tracer 理解原理，用平台跑生产**。二者不冲突——很多平台底层就是 OpenTelemetry（第 4 节），你自建时若也遵循 OTel 语义，未来迁移几乎零成本。

### 平台生态的两条路线：标准埋点层 vs 一体化平台

2026 年的 LLM 可观测性生态大致分两层，理解这个分层是选型的关键：

**第一层：基于 OpenTelemetry 的标准埋点库（instrumentation）。** 代表是 **OpenLLMetry**（由 Traceloop 维护，Apache 2.0 许可）。它是一组建在 OpenTelemetry 之上的扩展，为主流 LLM 提供方和向量数据库做自动埋点，把每次调用变成标准 OTel span，因此能连到你已有的任意可观测后端（Datadog、Honeycomb 等）[来源](https://github.com/traceloop/openllmetry)。同类还有 Arize 维护的 **OpenInference**（原生对接 Phoenix）、以及 OTel 兼容、支持 50+ 提供方的 **OpenLIT** [来源](https://futureagi.com/blog/best-otel-instrumentation-tools-llm-2026)。这一层的价值是「**只加几行初始化代码，框架代码不改**，就把 LangChain/LlamaIndex 的每次链执行、检索、LLM 调用捕获成 span」[来源](https://openobserve.ai/blog/langchain-llamaindex-openobserve/)。

**第二层：一体化可观测/评估平台。** 代表是 **LangSmith**（LangChain 官方，托管为主）和 **Langfuse**（开源、可自托管）。它们不只做埋点，还提供 trace 存储、Web UI、成本 dashboard、评估（evaluation）、数据集管理、prompt 管理等一整套能力。LangSmith 用 trace/run 模型（一条 trace 最多 25000 个 run）[来源](https://docs.langchain.com/langsmith/observability-concepts)；Langfuse 用 trace/observation 模型，按 observation 记录 usage 与 cost，并支持 OTLP（OpenTelemetry Protocol）接入 [来源](https://langfuse.com/docs/observability/features/token-and-cost-tracking)。

两层不是对立的：常见组合是「用 OpenLLMetry 这类标准埋点采集数据，再导入 Langfuse 或任意 OTLP 后端可视化」。这也是为什么第 4 节强调「对齐 OTel 语义」——它让这两层能自由拼接。

## 最小可运行演示

平台大多需要 API Key（Application Programming Interface Key，接口密钥）和联网，不适合离线演示。但**平台的核心抽象是可以离线复刻的**：一个能「导出到不同后端」的 tracer。下面用纯 Python 演示这个关键设计——同一份 span 数据，通过不同的 Exporter（导出器）适配到「本地控制台 / OTLP 后端 / 一体化平台」三种目标，这正是所有平台 SDK 的架构骨架。
```python
"""可插拔 Exporter 架构(纯 Python):同一份 span,导出到不同后端。

这是 OpenLLMetry / LangSmith / Langfuse 等 SDK 的共同骨架:
采集(instrumentation) 与 导出(exporter) 解耦,所以能'埋点一次,后端随意换'。
"""
from __future__ import annotations

from abc import ABC, abstractmethod


class Exporter(ABC):
    @abstractmethod
    def export(self, spans: list[dict]) -> None: ...


class ConsoleExporter(Exporter):
    """自建阶段:打到控制台,像第 2 节的 dump。"""
    def export(self, spans: list[dict]) -> None:
        for sp in spans:
            print(f"[console] {sp['name']:16s} tokens={sp.get('tokens', 0)} "
                  f"cost=${sp.get('cost', 0.0)}")


class OTLPExporter(Exporter):
    """标准埋点层:转成 OTel GenAI 语义约定字段,可发往任意 OTLP 后端。"""
    def export(self, spans: list[dict]) -> None:
        for sp in spans:
            otel = {"gen_ai.request.model": sp.get("model", "unknown"),
                    "gen_ai.usage.input_tokens": sp.get("tokens", 0)}
            print(f"[otlp->Datadog/Jaeger] span='chat {otel['gen_ai.request.model']}' "
                  f"{otel}")


class PlatformExporter(Exporter):
    """一体化平台:生成可分享的 trace 链接 + 聚合成本。"""
    def __init__(self, project: str) -> None:
        self.project = project

    def export(self, spans: list[dict]) -> None:
        total = round(sum(sp.get("cost", 0.0) for sp in spans), 4)
        trace_id = "req-9f3a"
        print(f"[platform] 项目={self.project} 共 {len(spans)} span 总成本=${total}")
        print(f"[platform] 可分享链接: https://example-obs/{self.project}/trace/{trace_id}")


class Tracer:
    """采集与导出解耦:换后端只需换 exporter,埋点代码一行不改。"""
    def __init__(self, exporter: Exporter) -> None:
        self.exporter = exporter
        self.spans: list[dict] = []

    def record(self, name: str, **attrs) -> None:
        self.spans.append({"name": name, **attrs})

    def flush(self) -> None:
        self.exporter.export(self.spans)


def run_agent(tracer: Tracer) -> None:
    """同一段埋点代码,喂给任何 exporter 都不用改。"""
    tracer.record("llm_call", model="gpt-4o", tokens=1200, cost=0.0040)
    tracer.record("tool.get_order", ok=False, rows=0)
    tracer.record("llm_call", model="gpt-4o", tokens=2100, cost=0.0071)


if __name__ == "__main__":
    for label, exp in [("自建/控制台", ConsoleExporter()),
                       ("标准埋点/OTLP", OTLPExporter()),
                       ("一体化平台", PlatformExporter(project="refund-agent"))]:
        print(f"=== 导出目标: {label} ===")
        tracer = Tracer(exp)
        run_agent(tracer)       # 埋点代码完全相同
        tracer.flush()
        print()
```
保存为 `exporters.py`，运行 `python exporters.py`。完整预期输出：
```text
=== 导出目标: 自建/控制台 ===
[console] llm_call         tokens=1200 cost=$0.004
[console] tool.get_order   tokens=0 cost=$0.0
[console] llm_call         tokens=2100 cost=$0.0071

=== 导出目标: 标准埋点/OTLP ===
[otlp->Datadog/Jaeger] span='chat gpt-4o' {'gen_ai.request.model': 'gpt-4o', 'gen_ai.usage.input_tokens': 1200}
[otlp->Datadog/Jaeger] span='chat unknown' {'gen_ai.request.model': 'unknown', 'gen_ai.usage.input_tokens': 0}
[otlp->Datadog/Jaeger] span='chat gpt-4o' {'gen_ai.request.model': 'gpt-4o', 'gen_ai.usage.input_tokens': 2100}

=== 导出目标: 一体化平台 ===
[platform] 项目=refund-agent 共 3 span 总成本=$0.0111
[platform] 可分享链接: https://example-obs/refund-agent/trace/req-9f3a
```
看清这个架构的价值：`run_agent` 里的埋点代码**一行都没变**，只换了 exporter，就能在「控制台调试 / 导入 OTLP 后端 / 一体化平台分享链接」之间自由切换。这正是「采集与导出解耦」的威力，也是为什么遵循 OTel 语义后迁移成本几乎为零——你换的是 exporter，不是埋点。

## 真实系统对应

**官方公开机制**：OpenLLMetry 是 Traceloop 维护、基于 OpenTelemetry 的开源库（Apache 2.0），为 LLM 提供方和向量库做标准 OTel 埋点，可连 Datadog、Honeycomb 等既有后端 [来源](https://github.com/traceloop/openllmetry)；它只需几行初始化、不改框架代码即可捕获 LangChain/LlamaIndex 的链执行与检索为 span [来源](https://openobserve.ai/blog/langchain-llamaindex-openobserve/)。LangSmith 用 trace/run 模型（单 trace ≤25000 run）、要求 usage_metadata + ls_model_name 才能算成本 [来源](https://docs.langchain.com/langsmith/observability-concepts) [来源](https://docs.langchain.com/langsmith/log-llm-trace)。Langfuse 开源、支持自托管与 OTLP 接入，按 observation 记录 usage/cost details（含 cached_tokens）[来源](https://langfuse.com/docs/observability/features/token-and-cost-tracking)。**通用工程模式**：采集与导出解耦的可插拔 Exporter 架构，是各家 SDK 的共同骨架，也是可迁移的设计。**教学参考实现**：上面的 `Exporter`、`PlatformExporter` 链接仅演示架构，不代表任何产品的真实 SDK 接口、字段或 URL 结构。

需要点明边界：各平台的具体功能、定价、开源/托管边界、数据驻留策略会随版本变化，选型时务必以各自当前官方文档为准；本节只梳理公开的定位与机制，不对比未公开的性能数字，也不臆造哪家「更好」——选型取决于你的技术栈、合规要求（能否自托管）、团队规模和预算。

## 生产踩坑

| 症状 | 根因 | 如何观测与复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| 自建 trace 存储很快撑不住 | 原型 tracer 无持久化/检索 | trace 量涨到十万级看查询变慢 | 生产上平台或 OTLP 后端 | 学习/原型阶段自建足够 |
| 换平台要重写大量埋点 | 埋点与导出耦合、非 OTel | 尝试从 A 平台迁到 B 复现 | 采集/导出解耦 + 对齐 OTel | 确定长期单一平台可弱化 |
| 合规要求数据不出境却用了纯托管 | 选型没考虑数据驻留 | 审计发现 trace 存在境外后端 | 选可自托管方案(如 Langfuse OSS) | 无合规约束的内部工具较轻 |
| 成本 dashboard 一直是空的 | 没传 usage_metadata/model 名 | 不传 token 元数据看成本为 0 | 按平台要求补齐用量与模型字段 | 只看 trace 不算成本时不涉及 |
| 自动埋点重复计数或缺失 | 手动埋点与自动埋点并存冲突 | 同时开两套埋点看 span 翻倍 | 二选一或明确分层 | 仅用一套时无此问题 |
| 单条 trace 触顶 run 上限被拒 | 循环失控产生海量 run | 造超长循环看是否触 25000 上限 | 加轮次上限(第 6 章)、拆分 trace | 正常短运行远不触顶 |
| 被单一厂商锁死难以迁移 | 用了私有格式非 OTLP | 评估迁移成本时发现绑定 | 优先 OTLP 兼容、语义对齐 | 短期验证期可接受锁定 |

TTL（Time To Live，生存时间）在平台侧对应数据保留策略，异常/高成本 trace 应配置更长保留。PII（Personally Identifiable Information，个人可识别信息）在发往任何第三方托管平台前必须先脱敏。

## 思考：什么时候该从自建 tracer 迁移到可观测性平台？迁移成本怎么降到最低？

### 回答

迁移的触发信号是「自建开始成为瓶颈」，主要有五个：其一，**存储与检索撑不住**——trace 量涨到几万几十万条后，自己搭的存储查询变慢，这是最常见的信号；其二，**需要协作**——产品、测试、其他工程师需要打开一条 trace 一起看，而自建没有可分享的 Web UI；其三，**需要聚合视图**——要看跨请求的成本 dashboard、成功率趋势，而不只是单条 trace；其四，**多个 Agent/团队要统一**——各自的自建 tracer 格式不一无法汇总；其五，**需要评估闭环**——想把 bad case 直接沉淀成数据集跑回归（第 6 章）。反过来，在学习、原型、单人验证阶段，自建的几十行 tracer 完全够用，上平台反而是过度工程。把迁移成本降到最低的关键，是从第一天就**遵循 OpenTelemetry 语义约定并做「采集与导出解耦」**：埋点代码只负责产出符合 `gen_ai.*` 命名的 span，导出通过可替换的 Exporter 完成。这样迁移时你换的只是 exporter（从控制台换成 OTLP 或某平台 SDK），成百上千处埋点代码一行都不用动。如果一开始就用了私有格式、把埋点和导出耦死，迁移就会变成一次痛苦的大重写——这也是第 4 节反复强调「对齐标准命名」的现实价值。

### 面试精简表达

触发信号:自建存储/检索撑不住、需要协作分享 trace、需要跨请求聚合 dashboard、多团队要统一、要评估闭环;原型/单人阶段自建够用别过度工程。降低迁移成本靠两点:第一天就对齐 OTel gen_ai 语义命名、并把采集与导出解耦,迁移时只换 Exporter、埋点代码不动;用私有格式耦死则迁移=大重写。

## 思考：OpenLLMetry 这类「标准埋点层」和 LangSmith/Langfuse 这类「一体化平台」是什么关系，会不会二选一？

### 回答

它们是**互补的两层，通常不是二选一，而是可以叠加使用**。标准埋点层（OpenLLMetry、OpenInference、OpenLIT）解决的是「**数据怎么产生**」——它建在 OpenTelemetry 之上，只需几行初始化、不改框架代码，就能把 LangChain、LlamaIndex 等框架的每次 LLM 调用、检索、链执行自动捕获成符合 `gen_ai.*` 语义约定的标准 span，然后通过 OTLP 发往任意兼容后端。它的定位是「厂商中立的采集器」，本身不提供存储和 UI。一体化平台（LangSmith、Langfuse）解决的是「**数据怎么消费**」——提供 trace 持久化、Web UI、成本 dashboard、评估、数据集与 prompt 管理等一整套面向团队的能力。二者的典型组合是：用 OpenLLMetry 做自动埋点采集，把标准 span 导入 Langfuse（Langfuse 支持 OTLP 接入）或任意 OTLP 后端做可视化与分析——采集和消费各司其职。当然也有「一站式」路径：LangSmith 与 LangChain 生态深度集成、开箱即用，你可以直接用它自带的埋点而不引入 OpenLLMetry。所以是否叠加取决于你的诉求：想要厂商中立、后端可换、和现有 Datadog/Jaeger 打通，就用「标准埋点层 + 任意后端」；想要开箱即用、深度集成某框架、少配置，就用一体化平台自带的采集。关键判断标准是「会不会被锁死」——只要采集层对齐了 OTel，消费层就能随时替换。

### 面试精简表达

互补两层、通常叠加而非二选一:标准埋点层(OpenLLMetry 等)负责'数据怎么产生'——基于 OTel、不改框架代码自动产出标准 span、厂商中立;一体化平台(LangSmith/Langfuse)负责'数据怎么消费'——存储、UI、成本 dashboard、评估。典型组合是 OpenLLMetry 采集→导入 Langfuse/任意 OTLP 后端;也可直接用 LangSmith 自带埋点一站式。判断核心是别被锁死:采集对齐 OTel,消费层就能随时换。
