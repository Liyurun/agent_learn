## 真实问题

回到导读里那次「凌晨账单翻 40 倍」。事后复盘会上，一位后端工程师提出质疑：「我们后端服务跑了这么多年，靠日志和堆栈从没这么狼狈过，为什么一个 Agent 就让我们查了两个小时？」这句话问到了点子上。同样是「线上出问题」，传统微服务的排查是有章可循的：错误码 500 指向某个接口，异常堆栈精确到「UserService.java 第 213 行空指针」，你顺着调用链往上看,十分钟内多半能定位。但退款 Agent 这次的故障从头到尾**没有抛任何异常**、错误率曲线**没有明显上升**、每一次请求单独看**都返回了通顺的自然语言回复**。它不是「崩了」，而是「跑通了却在悄悄烧钱」。

这一节要把「Agent 为什么天生更难排查」这件事讲透。不是因为 Agent 技术更新、工具不成熟，而是因为 Agent 的失败形态和传统程序**有本质区别**——它的错误往往是静默的、跨步骤累积的、藏在一连串模型决策和工具调用里的。理解这个区别，才能理解为什么后面所有小节要围绕「trace（追踪）」而不是「log（日志）」来组织。

## 原理：Agent 的失败为什么是「静默」且「跨步骤累积」的

传统程序出错，你有两大证据：**日志**和**堆栈**。程序崩溃时，异常堆栈会精确指向出错行，你顺着调用链往上就能定位。但 Agent 的「行为」藏在一连串模型决策和工具调用里，一个 Agent 回答错了或变贵了，原因可能是：模型推理错了？选错了工具？工具返回了脏数据？上下文被污染了？还是循环失控了?**没有可观测性，你无法区分这些原因**，也就无法修复。

可观测性把 Agent 从「黑箱」变成「玻璃箱」——这也呼应 Anthropic 在《构建高效 Agent》里强调的**透明性（transparency）**设计原则：显式展示 Agent 的规划步骤，让人能看懂它「打算怎么做」[来源](https://www.anthropic.com/engineering/building-effective-agents)。把这条原则落到工程上，就是「每一步都要留下可回放的痕迹」。

Agent 失败有两个传统程序少见的特征，它们共同决定了「堆栈 + print 不够用」。

**第一个特征：静默错误（silent failure）。** 普通程序崩了会抛异常，异常是「响亮」的信号；但 Agent 的失败往往不是崩溃，而是「跑通了却做错了」——它没抛异常，只是选了个不该选的工具、或者把工具返回的脏数据当真了。导读故障就是典型：`get_order` 返回空 JSON（JavaScript Object Notation，一种数据交换格式），从 HTTP（HyperText Transfer Protocol，超文本传输协议）层面看是一次成功的 200 响应，代码里没有任何 `raise`，Agent 把「空」理解成「还没查到」继续重试。这种「静默的错误」在堆栈里根本不会留下痕迹，因为压根没有异常被抛出。

**第二个特征：跨步骤累积（cross-step accumulation）。** Agent 的错误常常不是「当场出错」，而是**在多步之间累积传播**：第 2 步一个措辞不当的搜索，导致第 3 步检索到无关文档，进而让第 5 步的答案跑偏。等你在第 5 步看到错误输出时，真正的病根在第 2 步。传统的 `print` 调试是「点状」的，你事先不知道该在哪一步打点；而 trace 是「链状」的，它把整条因果链完整记录下来，让你能回溯到最初的偏差点。

用一句话概括这个差异：
```text
传统程序：错误 = 崩溃，堆栈直接指向出错行（点状定位，往上追调用栈）
Agent   ：错误 = 决策偏差，需回放整条决策链才能找到病根（链状定位，往前追时间线）
```
这两个特征叠加，就解释了导读里那两个小时为什么被浪费：没有 trace 时，工程师手里只有「点状」的 `print`，而故障是「链状」且「静默」的，两者根本对不上——他不得不用肉眼去做本该由结构化 trace 自动完成的「回放因果链」这件事。

## 最小可运行演示

抽象的「静默」「累积」不如跑一段代码直观。下面用一个不联网、不需要 API Key（Application Programming Interface Key，接口密钥）的确定性脚本，对比「只有 print 的点状调试」和「有 trace 的链状回放」在同一个故障上的差别：同一次退款 Agent 运行，工具在第 2 步返回了空数据，看看两种手段各能看到什么。
```python
"""对比:point-state print 调试 vs chain-state trace 回放（纯 Python，无需 API Key）。"""
from __future__ import annotations


def fake_get_order(order_id: str) -> dict:
    """模拟故障当晚的上游:订单接口返回空 JSON(200 成功,但内容为空)。"""
    return {}  # 注意:没有抛异常,这是一次"成功"的空返回


def run_agent_with_print() -> None:
    """传统 print 调试:只在'觉得重要'的地方打点,点状、无关联。"""
    print("[print] 开始处理退款请求")
    order = fake_get_order("A-2026")
    # 空 dict 被当成 falsy,进入'再查一次'分支——但 print 里看不出这是第几次、为什么
    if not order:
        print("[print] 订单为空,重试")          # 这行会重复出现 N 次,混在并发日志里
    print("[print] 已生成回复")                  # 最终'看起来正常'


def run_agent_with_trace() -> list[dict]:
    """链状 trace:每步落一条带因果关系的结构化记录。"""
    trace: list[dict] = []
    tokens = 1200
    for turn in range(1, 6):
        order = fake_get_order("A-2026")
        ok = bool(order)
        trace.append({
            "turn": turn, "step": "tool.get_order",
            "ok": ok, "rows": len(order),
            "note": "空返回被当成未查到->触发重试" if not ok else "正常",
        })
        trace.append({
            "turn": turn, "step": "llm_call",
            "tokens": tokens, "note": "历史累积->token 单调上升",
        })
        tokens = int(tokens * 1.6)  # 每轮把更长历史重新喂进模型,近似平方级增长
        if not ok:
            continue  # 静默地重试,不报错
    return trace


def diagnose(trace: list[dict]) -> str:
    tool_fails = [t for t in trace if t["step"] == "tool.get_order" and not t["ok"]]
    token_series = [t["tokens"] for t in trace if t["step"] == "llm_call"]
    growing = all(b > a for a, b in zip(token_series, token_series[1:]))
    return (f"病根定位:tool.get_order 连续 {len(tool_fails)} 次空返回(静默,未报错);"
            f"token 序列 {token_series} {'单调爬升(成本累积)' if growing else '平稳'}")


if __name__ == "__main__":
    print("=== 只有 print ===")
    run_agent_with_print()
    print("\n=== 有 trace(可回放整条因果链) ===")
    tr = run_agent_with_trace()
    for row in tr:
        print(row)
    print("\n=== 自动诊断 ===")
    print(diagnose(tr))
```
保存为 `silent_failure.py`，运行 `python silent_failure.py`。完整预期输出：
```text
=== 只有 print ===
[print] 开始处理退款请求
[print] 订单为空,重试
[print] 已生成回复

=== 有 trace(可回放整条因果链) ===
{'turn': 1, 'step': 'tool.get_order', 'ok': False, 'rows': 0, 'note': '空返回被当成未查到->触发重试'}
{'turn': 1, 'step': 'llm_call', 'tokens': 1200, 'note': '历史累积->token 单调上升'}
{'turn': 2, 'step': 'tool.get_order', 'ok': False, 'rows': 0, 'note': '空返回被当成未查到->触发重试'}
{'turn': 2, 'step': 'llm_call', 'tokens': 1920, 'note': '历史累积->token 单调上升'}
{'turn': 3, 'step': 'tool.get_order', 'ok': False, 'rows': 0, 'note': '空返回被当成未查到->触发重试'}
{'turn': 3, 'step': 'llm_call', 'tokens': 3072, 'note': '历史累积->token 单调上升'}
{'turn': 4, 'step': 'tool.get_order', 'ok': False, 'rows': 0, 'note': '空返回被当成未查到->触发重试'}
{'turn': 4, 'step': 'llm_call', 'tokens': 4915, 'note': '历史累积->token 单调上升'}
{'turn': 5, 'step': 'tool.get_order', 'ok': False, 'rows': 0, 'note': '空返回被当成未查到->触发重试'}
{'turn': 5, 'step': 'llm_call', 'tokens': 7864, 'note': '历史累积->token 单调上升'}

=== 自动诊断 ===
病根定位:tool.get_order 连续 5 次空返回(静默,未报错);token 序列 [1200, 1920, 3072, 4915, 7864] 单调爬升(成本累积)
```
对比很刺眼：`print` 版本一共只打了三行，最后一行还是「已生成回复」——**从日志上看一切正常**，你根本看不出重试了几次、token 涨没涨。而 trace 版本把每一轮的工具结果和 token 数完整记下来，`diagnose` 函数一眼就能自动报出「连续 5 次空返回 + token 单调爬升」。这就是「静默错误」和「跨步骤累积」为什么必须靠链状 trace 而非点状 print 才能抓住。

## 真实系统对应

**官方公开机制**：Anthropic 在《构建高效 Agent》中把「透明性」列为设计原则之一，主张显式展示 Agent 的规划步骤，让行为可审视 [来源](https://www.anthropic.com/engineering/building-effective-agents)；LangSmith 的可观测性文档明确定义了「一次操作触发的 agent 调模型、跑工具、再调模型的所有 run 属于同一条 trace，由唯一 trace ID 绑定」——这正是「链状回放」在商用平台里的落地 [来源](https://docs.langchain.com/langsmith/observability-concepts)。**通用工程模式**：把「每一步的输入输出 + 因果关系」结构化记录、支持事后回放，是可迁移到任意 Agent 框架的做法，与用哪家模型无关。**教学参考实现**：上面的 `fake_get_order`、`diagnose` 只为对比两种排查手段而构造，真实系统的空返回处理逻辑、token 增长曲线会因实现而不同，不代表任何产品的内部行为。

需要点明一个边界：并非所有 Agent 错误都是静默的——参数解析失败、工具抛异常这类「响亮」错误传统手段也能抓到。可观测性的价值恰恰在于覆盖那些**传统手段抓不到的静默、累积型故障**，而不是替代异常处理。两者是互补关系。

## 生产踩坑

| 症状 | 根因 | 如何观测与复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| 日志显示「一切正常」但账单飙升 | 静默错误不抛异常,日志抓不到 | 让工具返回空但不 raise 即复现 | 记录每步 ok/rows/tokens,而非只记异常 | 会抛异常的响亮错误无需额外手段 |
| 在错误的那一步反复打 print 也查不出 | 病根在上游步骤,错误是跨步骤累积 | 让第 2 步污染数据、第 5 步才显错 | 用链状 trace 从终点往前回放 | 单步无状态任务不存在累积 |
| 并发下日志混成一团无法归属 | print 无请求级关联 id | 并发跑多请求看日志交错 | 每条记录带 trace_id | 单并发调试影响可忽略 |
| 误把成本问题当模型太贵 | 没观测 token 随轮次的曲线 | 画 token 序列看是否单调爬升 | 按轮次/按 span 归因 token | 单轮对话 token 天然平坦 |
| 事故复盘拿不出「运行时做了什么」的证据 | 只记了模型输出,没记工具执行 | 关掉工具侧日志复现举证难 | 模型侧与工具侧都要落痕 | 纯问答无工具调用时较轻 |

## 思考：为什么 Agent 比传统程序更需要可观测性？「静默错误」和「跨步骤累积」各是什么意思？

### 回答

因为 Agent 的失败形态和传统程序有本质区别，导致传统的「日志 + 堆栈」抓不住它。传统程序的错误多是「崩溃」——响亮、当场、有堆栈精确指向出错行，属于点状定位。而 Agent 有两类传统程序少见的失败：其一是**静默错误**，指 Agent 没有抛任何异常、每次响应看起来都通顺，却在悄悄做错事（比如把工具返回的空数据当成「还没查到」继续重试），这种错误在堆栈里不留痕迹，因为压根没有异常；其二是**跨步骤累积**，指错误不是当场出现，而是在多步之间传播放大——第 2 步的偏差导致第 5 步的错误输出，你看到错误时病根已在几步之前，必须回放整条因果链才能追到。这两个特征叠加，决定了必须用「链状」的 trace（完整记录每步输入输出与因果关系、支持事后回放）而不是「点状」的 print 来排查。一条好的 trace 应包含每次模型调用的输入输出 / token / 成本 / 耗时、每次工具调用的参数 / 返回 / 成功与否 / 耗时、循环控制信息（第几轮、终止原因），以及能把这些串起来的 `trace_id`。

### 面试精简表达

传统程序错误是「响亮的崩溃」,靠堆栈点状定位;Agent 错误常是「静默的、跨步骤累积的」——不报错、跑通了却做错了,病根在几步之前,只能靠链状 trace 回放整条因果链才能抓住,这是 print 和堆栈做不到的。

## 深挖：为什么「加日志」不等于「有可观测性」

复盘会上有人提议「那我们多加点日志不就行了」。这是个常见误解。日志（logs）和可观测性（observability）不是一回事，多打日志往往只会让「翻日志」更痛苦。区别在三点。

第一，**关联性**。散落的 `print` 是一条条孤立的字符串，没有 `trace_id` 就无法把「这一行日志」归属到「哪一次用户请求的哪一步」。并发一上来，几十个请求的日志交错在一起，你连「这次故障到底是哪次请求」都分不清。可观测性的第一要义是**可关联**——所有信号都能顺着 `trace_id` 串回同一次运行。

第二，**结构化**。`print("订单为空，重试")` 是给人读的自由文本，机器无法聚合、无法计算「空返回率是多少」「token 涨了几倍」。结构化记录（如上面演示里的 dict）才能被程序消费，才能算指标、扫指纹、做告警。这是从「事后人肉翻」到「事前自动报」的分水岭。

第三，**因果结构**。日志是「离散事件」的平铺列表，而 trace 是有父子关系的调用树，它保留了「谁触发了谁」的因果。导读故障里「空返回→重试→历史膨胀→成本爆炸」这条链，只有在保留了因果结构的 trace 里才看得出来；在平铺日志里，它就是几百行毫无关系的「订单为空」。

所以正确的说法不是「加日志」，而是「加**带 trace_id 的结构化、有因果结构的**记录」。这三点会在后面几节逐一落地：第 2 节讲怎么用父子关系建调用树，第 3 节讲结构化日志与三支柱如何用 `trace_id` 关联，第 4 节讲怎么让这套记录对齐 OpenTelemetry 的行业标准。理解「日志 ≠ 可观测性」，是从第一级「靠 print」爬升到更高成熟度的第一步。
