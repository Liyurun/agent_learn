## 真实问题

退款 Agent 的 tracer 用了两个月，团队又踩了个新坑：他们自建 tracer 里把 token 数记成 `attrs["tokens"]`，把模型名记成 `attrs["model"]`；隔壁搜索 Agent 团队记成 `attrs["token_count"]` 和 `attrs["llm"]`；后来接入的一个第三方 RAG（Retrieval-Augmented Generation，检索增强生成）服务又记成 `usage.total`。等公司想搭一个统一的成本 dashboard、把所有 Agent 的花费汇总时，发现**三套字段名对不上，只能写三份解析代码**，而且哪天某个团队改了字段名，dashboard 就悄悄漏统计。更麻烦的是，他们想把 trace 导到公司已有的 Datadog / Jaeger 后端，却发现自建格式和这些后端根本不兼容，要么重写导出层、要么被平台锁死。

这一节要回答一个工程问题：**既然人人都要记 token / 模型 / 延迟，为什么不用一套行业标准的字段名？** 这套标准就是 OpenTelemetry（简称 OTel）的 GenAI（Generative AI，生成式人工智能）语义约定。理解它，你自建 tracer 时若也遵循这套命名，未来迁移到任何平台几乎零成本——因为大多数平台底层就是 OpenTelemetry。

## 原理：OpenTelemetry 与 GenAI 语义约定

**OpenTelemetry** 是云原生计算基金会（Cloud Native Computing Foundation，CNCF）下的可观测性标准，定义了 traces、metrics、logs 三大信号的数据模型和跨语言 SDK（Software Development Kit，软件开发工具包）。它的核心价值是**厂商中立**：你按 OTel 规范埋点，数据就能导到任何支持 OTLP（OpenTelemetry Protocol，OpenTelemetry 协议）的后端（Jaeger、Datadog、Grafana Tempo 等），不被任何单一平台锁定。

在通用 trace/span 模型之上，OpenTelemetry 社区专门为大模型应用定义了一套 **GenAI 语义约定（GenAI Semantic Conventions）**——它规定了「记录一次模型调用的 span，应该用哪些标准属性名」。核心约定包括 [来源](https://github.com/open-telemetry/semantic-conventions/blob/main/docs/gen-ai/gen-ai-spans.md) [来源](https://opentelemetry.io/docs/specs/semconv/gen-ai/)：

- **span 命名**：推理调用的 span 名建议为 `{gen_ai.operation.name} {gen_ai.request.model}`，例如 `chat gpt-4o`；span kind（种类）为 `CLIENT`（客户端调用）。
- **操作属性**：`gen_ai.operation.name`（操作类型，如 `chat`、`generate_content`、`text_completion`、`invoke_agent`）、`gen_ai.provider.name`（提供方，如 `openai`、`anthropic`）、`gen_ai.request.model` / `gen_ai.response.model`（请求/响应模型名）。
- **用量属性**：`gen_ai.usage.input_tokens`、`gen_ai.usage.output_tokens`（输入/输出 token 数）。
- **请求参数**：`gen_ai.request.temperature`、`gen_ai.request.max_tokens` 等。

一个关键提醒：这套 GenAI 约定的大部分内容目前仍处于 **development（开发中）/ experimental（实验性）** 稳定性级别，属性名和结构还在演进 [来源](https://opentelemetry.io/docs/specs/semconv/registry/attributes/gen-ai/)。社区也在讨论新增 `gen_ai.workflow`、`gen_ai.agent`、`gen_ai.task` 等 span 类型来覆盖多 Agent 编排 [来源](https://github.com/open-telemetry/semantic-conventions-genai/issues/55)。所以正确姿势是：**对齐它的命名习惯以获得互操作性，但不把某个具体拼写当成永久稳定的承诺**——以当前官方文档为准。

### 为什么「对齐标准命名」值得

对齐 OTel GenAI 命名有三重收益。第一是**互操作**：所有 Agent 用同一套字段名，一份 dashboard 解析代码就能汇总全公司成本，不必为每个团队写一份适配。第二是**可移植**：数据符合 OTLP，就能在 Jaeger、Datadog、Grafana、Langfuse（Langfuse 也支持 OTLP 接入）之间自由切换后端，不被锁定。第三是**生态复用**：OpenLLMetry、OpenInference、OpenLIT 等开源库已经按这套约定为主流框架做了自动埋点（第 7 节），你遵循同一套语义，就能和它们的数据无缝拼接。

## 最小可运行演示

下面用纯 Python 演示：把第 2 节自建 tracer 里那种「随便起名」的 span 属性，**映射到 OpenTelemetry GenAI 语义约定的标准字段名**，并给 span 起一个符合规范的名字。这段代码不安装 OTel SDK（避免联网依赖），而是用一个纯函数演示「语义约定」这层映射逻辑本身——这正是各家自动埋点库在做的事。
```python
"""把自建 span 属性映射到 OpenTelemetry GenAI 语义约定(纯 Python,无需安装 SDK)。

注意:GenAI 语义约定多数属性仍处 development 级别,字段名以官方当前文档为准。
本示例演示'映射'这层逻辑,不代表任何 SDK 的内部实现。
"""
from __future__ import annotations


    # 自建 tracer 里五花八门的属性名 -> OTel GenAI 标准属性名
GENAI_ATTR_MAP = {
    "model": "gen_ai.request.model",
    "llm": "gen_ai.request.model",
    "provider": "gen_ai.provider.name",
    "op": "gen_ai.operation.name",
    "input_tokens": "gen_ai.usage.input_tokens",
    "output_tokens": "gen_ai.usage.output_tokens",
    "temp": "gen_ai.request.temperature",
}


def to_otel_span(raw_name: str, raw_attrs: dict) -> dict:
    """把一个'随便起名'的 span 归一化成符合 GenAI 约定的 span。"""
    attrs = {}
    for k, v in raw_attrs.items():
        attrs[GENAI_ATTR_MAP.get(k, k)] = v  # 命中标准名则替换,否则原样保留
    # span 名规范: {gen_ai.operation.name} {gen_ai.request.model}
    op = attrs.get("gen_ai.operation.name", "chat")
    model = attrs.get("gen_ai.request.model", "unknown")
    return {"span_name": f"{op} {model}", "span_kind": "CLIENT", "attributes": attrs}


if __name__ == "__main__":
    # 三个团队各记各的,字段名不一致
    team_a = {"model": "gpt-4o", "provider": "openai", "op": "chat",
              "input_tokens": 1200, "output_tokens": 180, "temp": 0.2}
    team_b = {"llm": "claude-sonnet", "provider": "anthropic", "op": "chat",
              "input_tokens": 2100, "output_tokens": 90}

    for name, raw in [("团队A", team_a), ("团队B", team_b)]:
        span = to_otel_span("llm_call", raw)
        print(f"=== {name} 归一化后 ===")
        print("span_name :", span["span_name"])
        print("span_kind :", span["span_kind"])
        for k in sorted(span["attributes"]):
            print(f"  {k} = {span['attributes'][k]}")
        print()

    # 归一化后,一份聚合代码就能统一统计 token(不管上游用什么字段名)
    spans = [to_otel_span("llm_call", team_a), to_otel_span("llm_call", team_b)]
    total_in = sum(s["attributes"]["gen_ai.usage.input_tokens"] for s in spans)
    total_out = sum(s["attributes"]["gen_ai.usage.output_tokens"] for s in spans)
    print(f"统一聚合: 总输入 token={total_in}, 总输出 token={total_out}")
```
保存为 `otel_semconv.py`，运行 `python otel_semconv.py`。完整预期输出：
```text
=== 团队A 归一化后 ===
span_name : chat gpt-4o
span_kind : CLIENT
  gen_ai.operation.name = chat
  gen_ai.provider.name = openai
  gen_ai.request.model = gpt-4o
  gen_ai.request.temperature = 0.2
  gen_ai.usage.input_tokens = 1200
  gen_ai.usage.output_tokens = 180

=== 团队B 归一化后 ===
span_name : chat claude-sonnet
span_kind : CLIENT
  gen_ai.operation.name = chat
  gen_ai.provider.name = anthropic
  gen_ai.request.model = claude-sonnet
  gen_ai.usage.input_tokens = 2100
  gen_ai.usage.output_tokens = 90

统一聚合: 总输入 token=3300, 总输出 token=270
```
看清价值：团队 A 用 `model`、团队 B 用 `llm`，归一化到 `gen_ai.request.model` 之后，**同一份聚合代码就能跨团队统计 token**，不必写两份解析。span 名也统一成 `chat gpt-4o` 这种规范格式，在任何 OTel 后端里都能被正确识别和聚合。这就是「语义约定」的全部意义——**约定的不是数据本身，而是数据的名字**。

## 真实系统对应

**官方公开机制**：OpenTelemetry GenAI Spans 文档明确规定推理 span 名为 `{gen_ai.operation.name} {gen_ai.request.model}`、span kind 为 `CLIENT`，并定义了 `gen_ai.operation.name`、`gen_ai.provider.name`、`gen_ai.request.model`、`gen_ai.usage.input_tokens/output_tokens` 等属性 [来源](https://github.com/open-telemetry/semantic-conventions/blob/main/docs/gen-ai/gen-ai-spans.md)；这些属性在 GenAI 属性注册表里列出，且多数标记为 development 稳定性 [来源](https://opentelemetry.io/docs/specs/semconv/registry/attributes/gen-ai/)；社区正讨论把 workflow / agent / task 纳入约定以覆盖编排场景 [来源](https://github.com/open-telemetry/semantic-conventions-genai/issues/55)。**通用工程模式**：把自建属性映射到标准命名以获得互操作与可移植，是任何团队都能采用的做法。**教学参考实现**：上面的 `GENAI_ATTR_MAP`、`to_otel_span` 仅演示映射思路，真实的 OTel SDK 埋点、上下文传播、OTLP 导出远比这复杂，本示例不代表其内部实现。

需要点明边界：语义约定解决的是「字段叫什么名」，不解决「数据存哪、留多久、谁能看」——那些是后端与治理决策。而且约定仍在演进，把某次检索到的属性拼写写死进代码是有风险的；工程上应把映射表集中管理、随官方文档更新，而不是散落在各处。

## 生产踩坑

| 症状 | 根因 | 如何观测与复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| 跨团队成本 dashboard 要写多份解析 | 各团队 span 属性名不统一 | 让两个 Agent 用不同字段名复现 | 统一对齐 gen_ai.* 语义约定 | 单团队单一 Agent 时影响小 |
| 换 trace 后端要重写导出层 | 自建格式非 OTLP,被平台锁死 | 尝试把自建 trace 导入 Jaeger | 按 OTel 埋点、走 OTLP 导出 | 短期原型不追求可移植时可缓 |
| 升级依赖后属性名对不上 | 把 development 级属性拼写写死 | 跟随版本升级看字段是否变 | 集中管理映射表、跟官方文档 | 已 stable 的属性相对安全 |
| 多 Agent 编排的 trace 无法表达层级 | 只有 llm span,缺 workflow/agent span | 跑一个多 Agent 任务看 trace 扁平 | 用 workflow/agent span 分层(约定演进中) | 单 Agent 单步任务无需分层 |
| span 名五花八门无法聚合 | 未按 {op} {model} 规范命名 | 用随意 span 名在后端搜索复现 | 统一 span 命名规范 | 内部调试临时 span 可放宽 |
| 误以为 OTel 会自动脱敏 | 把语义约定当治理方案 | 记录含 PII 的 prompt 看是否落库 | 脱敏在埋点层自己做 | 无敏感数据场景风险较低 |

## 思考：为什么自建 tracer 也应该对齐 OpenTelemetry 的 GenAI 语义约定？

### 回答

因为对齐标准命名能几乎零成本地换来「互操作、可移植、生态复用」三重收益，而代价只是「起名时用规定的字段名」。第一，**互操作**：当公司里多个 Agent、多个团队都记 token、模型、延迟时，如果各起各的名（一个叫 `model`、一个叫 `llm`、一个叫 `usage.total`），想搭统一的成本或健康度 dashboard 就得为每种命名写一份解析代码，且谁改个名就悄悄漏统计；统一到 `gen_ai.request.model`、`gen_ai.usage.input_tokens` 这类标准名后，一份聚合逻辑就能汇总所有来源。第二，**可移植**：OpenTelemetry 是厂商中立标准，数据符合 OTLP 就能在 Jaeger、Datadog、Grafana、Langfuse 等任意支持 OTLP 的后端之间自由切换，不被单一平台锁死；反之自建私有格式往往要为每个后端重写导出层。第三，**生态复用**：OpenLLMetry、OpenInference 等开源自动埋点库已经按这套约定为主流框架埋好点，你遵循同一语义就能和它们的数据无缝拼接。需要注意的边界是，这套 GenAI 约定目前多数属性仍处于 development 级别、还在演进，所以应「对齐它的命名习惯」但不要「把某次检索到的拼写写死」，最好把映射表集中管理、随官方文档更新。

### 面试精简表达

对齐 OTel GenAI 命名的收益是互操作(一份解析汇总全公司)、可移植(OTLP 后端随意切换不锁定)、生态复用(自动埋点库开箱兼容),代价只是按标准字段名起名;但约定多数还是 development 级、在演进,所以对齐命名习惯即可、别把具体拼写写死,映射表集中管理跟着官方文档更新。

## 思考：OpenTelemetry 的「语义约定」到底约定了什么、又没约定什么？

### 回答

语义约定约定的是**数据的「名字」和「语义」，而不是数据本身，也不是数据的存储与治理**。具体说，它约定了：一个记录模型调用的 span 应该叫什么名（`{gen_ai.operation.name} {gen_ai.request.model}`，如 `chat gpt-4o`）、应该是什么 span kind（`CLIENT`）、应该带哪些标准属性以及这些属性各自的含义和取值范围（如 `gen_ai.operation.name` 取 `chat`/`text_completion`，`gen_ai.usage.input_tokens` 是输入 token 数）。它的目的是让不同厂商、不同团队产出的遥测数据「说同一种语言」，从而可被统一解析、聚合、跨后端搬运。但它**不约定**几件事：不约定这些数据存到哪个后端、用什么存储引擎；不约定数据保留多久、谁有权限查看；不约定要不要脱敏、怎么采样——这些都是团队的工程与治理决策，语义约定不会替你做，也不会自动帮你脱敏。此外它还有个现实边界：GenAI 部分的约定大量条目仍是 development/experimental 级别，在持续演进（比如正在讨论新增 workflow/agent/task span 类型来表达多 Agent 编排），所以它约定的「名字」本身也不是一成不变的，落地时要以当前官方文档为准。

### 面试精简表达

它约定的是数据的名字与语义——span 怎么命名、该带哪些标准属性、各属性什么含义,让不同来源的遥测'说同一种语言'可被统一处理;它不约定存储、保留期、权限、脱敏、采样这些治理决策,也不会自动脱敏;而且 GenAI 约定多数还在 development 级演进,名字本身也会变,要以官方当前文档为准。
