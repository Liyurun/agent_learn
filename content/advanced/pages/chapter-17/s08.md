## 真实问题

导读故障结案三个月后，退款 Agent 团队想把这一路踩过的坑沉淀成一份「可观测性上线检查清单」，却发现最痛的教训不是「不知道要记 trace（追踪）」，而是**接入时机和治理没做好**：第一版上线时为了赶进度没接 tracer，结果导读那次事故发生时手里没数据，白查两小时；后来补上了 tracer，又因为原样记录 prompt 把用户手机号写进了日志，被合规部门通报；再后来为了「记全一点」全量采集高流量请求，存储成本一个月涨了三倍。三件事都不是「不懂原理」，而是**把可观测性当成事后补丁而非一等公民**。

这一节做两件事：先给出一张覆盖 Agent 可观测性各层的生产建议矩阵（含接入时机、隐私、采样、成熟度四大治理维度），再用多道「思考+回答」把全章方法论收口，直接对齐高频面试题。

## 可观测性成熟度：团队会经历的四个阶段

可观测性不是「有」或「没有」的二元开关，而是一条团队会逐步爬升的阶梯。认清自己处在哪一级，能帮你判断下一步该补什么。

**第一级「靠 print」**。刚起步的项目往往就是在关键处打几行 `print`，出了问题就翻控制台。原型阶段够用，但 print 是点状的、非结构化的、跑完就没了，一旦上了生产、有了并发，日志混成一团根本没法追踪单次运行。绝大多数「Agent 上线后没法排查」的团队，都卡在这一级。

**第二级「有结构化 trace」**。也就是第 2 节手搓的那种——每次运行落一条结构化记录，能回放单次运行的完整调用链。到了这一级，你终于能回答「这一次它到底经历了什么」，排查从「猜」变成了「看」。这是从玩具走向生产的最关键一跃。

**第三级「trace + metrics + 关联」**。在结构化 trace 之上，聚合出成功率、P95 延迟、成本等指标 dashboard，并用 `trace_id` 把三支柱串起来（第 3 节）。到这一级，你不仅能排查单次问题，还能**主动发现**趋势性问题——「这周退款类请求的强停率悄悄涨了」，在用户投诉之前就介入。

**第四级「自动化 + 告警」**。把第 6 节那些「故障指纹检测」做成自动化规则，异常自动告警、可疑 trace 自动标红，甚至把高频 bad case 自动回流进评估集（第 16 章）。到这一级，可观测性从「事后翻查的工具」升级成了「事前预警的系统」，团队精力从「救火」转向「防火」。

大多数团队会长期停在第二、三级，这完全没问题——**关键是别停在第一级**。面试时如果被问到「你们的可观测性做到什么程度」，能清晰说出自己在哪一级、下一步准备补什么，比空谈「我们很重视可观测性」有说服力得多。

## 生产建议：Agent 可观测性症状矩阵

下面把全章各层的坑汇成一张矩阵，每行都是一个真实会发生、可观测、有修复、也有不适用边界的条目。它是这份清单的主体。

| 症状 | 根因 | 如何观测与复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| 事故发生时手里没有那次 trace | 上线时没接 tracer,想着以后补 | 关掉 tracer 制造一次故障 | 第一版就接入最简 tracer | 一次性脚本可不接 |
| 日志显示正常但账单飙升 | 静默错误不抛异常 | 让工具返回空但不 raise | 记 ok/rows/tokens 而非只记异常 | 会抛异常的响亮错误无需 |
| 病根在上游步骤却对着终点查 | 错误跨步骤累积传播 | 让第 2 步污染、第 5 步显错 | 从终点往前回放整条链 | 单步无状态任务无累积 |
| 并发下日志无法归属到某次请求 | 记录缺 trace_id 关联 | 并发跑多请求看日志交错 | 每条记录带 trace_id/span_id | 单并发调试影响小 |
| 崩溃后没有那次失败的 trace | 只在成功路径落 span | 让工具抛异常看是否留痕 | try/except/finally 崩溃也落 span | kill -9 无法保证 |
| span 全平铺看不出因果 | 没记 parent_id 当日志列表 | 去掉 parent_id 建树 | 用 parent_id 拼调用树 | 单 span 任务退化为点 |
| 成本翻倍很晚才发现 | 没把 token 当一等指标 | 只监控错误率不监控 token | 每次调用记 input/output token | 单轮任务成本平稳时轻 |
| 平方级膨胀没被提前预警 | 未监控每轮输入 token 曲线 | 造循环让历史累积 | 监控每轮 token,等差递增即告警 | 短对话膨胀不明显 |
| 一看慢就换小模型没效果 | 没做时间归因误优化模型 | 造慢工具看模型占比很低 | 先归因再优化,盯占比最大项 | 模型确是大头时才优化模型 |
| trace 海里逐条点开找不到北 | 靠肉眼而非指纹自动扫 | 面对上千 trace 手动排查 | 故障模式写成指纹自动标红 | trace 极少时人工可覆盖 |
| 修好的 bug 过阵子又复发 | 未把 bad case 固化进评估集 | 修完不加回归样本 | trace 定位后进 held-out 集跑回归 | 一次性临时脚本可不固化 |
| trace 里存了用户手机号被合规通报 | 原样记录 prompt 未脱敏 | 用含 PII 输入跑一遍看落库 | 落库前脱敏/掩码/只存摘要哈希 | 完全内部无敏感数据场景轻 |
| 全量采集导致存储成本暴涨 | 高流量未做采样 | 压测高 QPS 看存储写入量 | 头部采样 + 异常全采 | 低流量原型可全量 |
| 跨团队成本 dashboard 要写多份解析 | span 属性名不统一 | 两个 Agent 用不同字段名 | 对齐 gen_ai.* 语义约定 | 单团队单 Agent 时轻 |
| 换 trace 后端要重写导出层 | 自建格式非 OTLP 被锁死 | 尝试把自建 trace 导入 Jaeger | 采集/导出解耦 + 对齐 OTel | 短期原型不追求可移植可缓 |
| 合规要求数据不出境却用纯托管 | 选型没考虑数据驻留 | 审计发现 trace 存境外后端 | 选可自托管方案 | 无合规约束内部工具轻 |
| 单条 trace 触顶平台 run 上限 | 循环失控产生海量 run | 造超长循环触 25000 上限 | 加轮次上限、拆分 trace | 正常短运行远不触顶 |
| 采集与评估两张皮、闭环断裂 | trace 定位后没回流评估集 | 定位 bug 后不进数据集 | bad case 自动回流 held-out 集 | 无评估体系的早期项目 |

TTL（Time To Live，生存时间）适用于可过期的调试采样样本，但异常/高成本请求的证据应延长保留期，不应过早清除。PII（Personally Identifiable Information，个人可识别信息）在写入日志、追踪或发往任何第三方托管平台前都应先最小化与脱敏。RBAC（Role-Based Access Control，基于角色的访问控制）应用于可观测性平台本身——谁能看含敏感内容的 trace 也需要权限治理。

## 最小可运行演示：上线前的可观测性自检器

把全章的治理要点固化成一个自检清单器：输入一套「当前可观测性配置」，输出「距离生产就绪还差哪几项 + 当前处于成熟度第几级」。纯 Python，不联网、不需要 API Key（Application Programming Interface Key，接口密钥）。
```python
"""可观测性上线自检器(纯 Python):检查配置,给出缺口与成熟度等级。"""
from __future__ import annotations


CHECKS = [
    ("has_structured_trace", "已接结构化 tracer(每次运行落 span)"),
    ("span_has_trace_id", "span/日志带 trace_id 关联三支柱"),
    ("record_on_error", "崩溃路径也落 span(try/except/finally)"),
    ("track_tokens_cost", "采集 input/output token 与成本"),
    ("pii_masked", "落库前对 PII 脱敏/掩码"),
    ("sampling_policy", "有采样策略(头部采样+异常全采)"),
    ("failure_fingerprints", "有故障指纹自动检测"),
    ("badcase_to_evalset", "bad case 回流评估集"),
]


def maturity_level(cfg: dict) -> int:
    if cfg.get("failure_fingerprints") and cfg.get("badcase_to_evalset"):
        return 4
    if cfg.get("span_has_trace_id") and cfg.get("track_tokens_cost"):
        return 3
    if cfg.get("has_structured_trace"):
        return 2
    return 1


def audit(cfg: dict) -> None:
    missing = [desc for key, desc in CHECKS if not cfg.get(key)]
    level = maturity_level(cfg)
    print(f"当前可观测性成熟度: 第 {level} 级 / 共 4 级")
    if missing:
        print(f"距离'生产就绪'还差 {len(missing)} 项:")
        for m in missing:
            print("  - " + m)
    else:
        print("全部通过:已达生产就绪")


if __name__ == "__main__":
    # 导读故障当晚的配置:只有 print,几乎裸奔
    incident_night = {"has_structured_trace": False}
    print("=== 事故当晚的配置 ===")
    audit(incident_night)

    print("\n=== 整改三个月后的配置 ===")
    after = {
        "has_structured_trace": True, "span_has_trace_id": True,
        "record_on_error": True, "track_tokens_cost": True,
        "pii_masked": True, "sampling_policy": True,
        "failure_fingerprints": True, "badcase_to_evalset": True,
    }
    audit(after)
```
保存为 `readiness_audit.py`，运行 `python readiness_audit.py`。完整预期输出：
```text
=== 事故当晚的配置 ===
当前可观测性成熟度: 第 1 级 / 共 4 级
距离'生产就绪'还差 8 项:
  - 已接结构化 tracer(每次运行落 span)
  - span/日志带 trace_id 关联三支柱
  - 崩溃路径也落 span(try/except/finally)
  - 采集 input/output token 与成本
  - 落库前对 PII 脱敏/掩码
  - 有采样策略(头部采样+异常全采)
  - 有故障指纹自动检测
  - bad case 回流评估集

=== 整改三个月后的配置 ===
当前可观测性成熟度: 第 4 级 / 共 4 级
全部通过:已达生产就绪
```
这个自检器只用于**上线前对照**，不替代真实的压测与演练：它告诉你「缺哪几项、大致在第几级」，具体每项做到什么质量仍要结合业务。事故当晚 8 项全缺、卡在第一级，正是那两小时排查噩梦的根源。

## 真实系统对应

**官方公开机制**：Langfuse 开源可自托管、支持 OTLP（OpenTelemetry Protocol）接入并按 observation 记录 usage/cost（利于合规团队把数据留在自己环境）[来源](https://langfuse.com/docs/observability/features/token-and-cost-tracking)；LangSmith 提供 dashboard 与 dataset、把 bad case 固化为评估样本 [来源](https://docs.langchain.com/langsmith/observability-concepts)；OpenTelemetry 三大信号可通过 trace context 关联、GenAI 指标提供 token/duration [来源](https://opentelemetry.io/docs/specs/semconv/gen-ai/)；Anthropic 的透明性原则主张显式展示规划步骤 [来源](https://www.anthropic.com/engineering/building-effective-agents)。**通用工程模式**：早期接入、PII 脱敏、头部采样+异常全采、四级成熟度、bad case 回流评估集，是可迁移到任意团队的治理框架。**教学参考实现**：上面的自检器 `CHECKS`、`maturity_level` 阈值仅为教学示意，真实的上线检查项与分级标准应按团队风险模型定制。

需要点明边界：具体的采样率、脱敏策略、日志保留期、告警阈值、谁有权查看敏感 trace，都是团队按风险设计的工程决策；本章不声称任何平台会自动完成这些治理。平台提供的是能力，怎么用、留多久、谁能看，都要团队自己拍板。

## 思考：为什么可观测性必须在开发早期接入，而不是等出了事故再补？生产接入还需注意哪些现实约束？

### 回答

因为**最需要可观测性的时刻，恰恰是事故发生的那一刻，而「事后再补」的 trace 在事故当下还没上线**。这是个时间悖论：你想着「等出问题再加 trace」，但问题出现时，能帮你还原现场的那套 trace 还不存在，于是你只能像导读故障里那样，对着满屏 `print` 白查两小时。可观测性的价值不体现在平时——平时一切正常，它看起来是「没用的开销」；它的全部价值都压在事故那一瞬间能不能帮你把现场还原出来。就像开车要先装仪表盘和行车记录仪，而不是撞了车才想装。所以务必在第一版就把 tracer 接进去，哪怕只是第 2 节那种最简版本。生产接入还有三个容易被忽略的现实约束。其一是 **PII 脱敏**：trace 会原样记录 prompt 和工具返回，里面可能有用户手机号、订单、地址等敏感信息，必须在落库前脱敏/掩码，否则可观测性系统本身就成了数据泄露的重灾区。其二是**采样策略**：全量记录高流量系统的完整 prompt/response 成本高得吓人，常见做法是「头部采样 + 异常全采」——正常请求按比例（如 1%）采样，但失败、超时、高成本的请求 100% 记录，因为出问题的那些才是你最需要的证据。其三是**访问治理（RBAC，Role-Based Access Control，基于角色的访问控制）**：含敏感内容的 trace 谁能看，也需要权限控制。这三点加上「早期接入」，构成生产可观测性的四条治理底线。

### 面试精简表达

因为事故发生那一刻才最需要 trace,而'事后补'的 trace 那时还没上线,等于最需要证据时两手空空(导读白查两小时);可观测性的价值全压在事故瞬间能否还原现场,所以第一版就要接、哪怕最简版。三个现实约束:PII 落库前脱敏(否则可观测系统自身成泄露源)、头部采样+异常全采(正常按比例、失败/超时/高成本 100% 采)、RBAC 治理谁能看敏感 trace。

## 思考：面试官问「你们的可观测性做到什么程度」，怎么答得有说服力？

### 回答

用「四级成熟度」框架来答，能清晰说出自己在哪一级、下一步补什么，比空谈「我们很重视」有力得多。第一级「靠 print」——关键处打几行 print，原型够用但点状、非结构化、并发即混乱，绝大多数「上线后没法排查」的团队卡在这里，这一级是要坚决离开的。第二级「有结构化 trace」——每次运行落一条结构化记录、能回放单次完整调用链，排查从「猜」变成「看」，这是从玩具走向生产最关键的一跃。第三级「trace + metrics + 关联」——在 trace 之上聚合出成功率、P95、成本 dashboard，用 trace_id 串起三支柱，从而能主动发现趋势性问题（如「本周强停率悄悄涨了」），在用户投诉前介入。第四级「自动化 + 告警」——把故障指纹检测做成自动规则、异常自动告警、可疑 trace 自动标红、高频 bad case 自动回流评估集，团队从「救火」转向「防火」。回答时的加分项是：诚实说明自己团队在第几级（大多数成熟团队在第二、三级完全正常）、为什么停在这一级（成本/收益权衡）、以及下一步计划补什么（比如「我们在第二级，正在补 trace_id 关联和成本 dashboard 向第三级走」）。这种「知道阶梯、知道自己的位置、知道下一步」的回答，展示的是工程判断力，而不是口号。

### 面试精简表达

用四级成熟度框架:①靠 print(点状、要坚决离开)→②结构化 trace(能回放单次链、最关键一跃)→③trace+metrics+trace_id 关联(有 dashboard、能主动发现趋势)→④故障指纹自动化+告警+bad case 回流(从救火到防火);诚实说自己在第几级、为何停在这、下一步补什么(如'在第二级,正补 trace_id 关联和成本看板向三级走'),展示工程判断而非口号。

## 思考：把可观测性引入一个已有的 Agent 系统，落地顺序应该怎么排？

### 回答

先能看见，再堵会赔钱的洞，最后才追求规模化和自动化，具体分四步。第一步**加最简结构化 trace**（对齐第 2、3 节）：给每次运行落一条带 `trace_id`、`span_id`、`parent_id` 的结构化记录，记下每步的输入摘要、输出、token、耗时、成功与否，并保证崩溃路径也落 span。这一步的目标是「从看不见到看得见」，是后面一切的地基——别一上来就想着上大平台。第二步**锁三条治理底线**：落库前对 PII 脱敏、对高流量做「头部采样+异常全采」、给含敏感内容的 trace 加访问控制。这一步防的是「可观测性系统自己变成事故源」（数据泄露、存储爆炸）。第三步**接指标与关联**（第 3、5 节）：从结构化日志聚合出成功率、P95 延迟、成本 dashboard，用 `trace_id` 把 metrics、traces、logs 串成漏斗，能主动发现趋势问题；同时把 span 属性对齐 OpenTelemetry 的 `gen_ai.*` 语义约定，为将来上平台或换后端留好接口。第四步**做自动化闭环**（第 6 节）：把循环失控、重复调用、脏数据、成本平方膨胀等故障指纹写成自动检测规则，异常告警、可疑 trace 标红，并把定位到的 bad case 回流进 held-out 评估集（第 16 章）跑回归。每一步都要用真实故障样本验证、保留回滚开关。这个顺序的底层逻辑就是「metrics→traces→logs 漏斗」在建设层面的映射——先有能回放的线，再铺能报警的面，最后装能自动挑针的雷达。

### 面试精简表达

四步、先看见再堵洞最后自动化:①加最简结构化 trace(带 trace_id/span_id/parent_id、崩溃也落 span),从看不见到看得见,别急着上大平台;②锁治理底线(PII 脱敏、头部采样+异常全采、RBAC),防可观测系统自己变事故源;③接 metrics 与关联(成功率/P95/成本 dashboard、trace_id 串三支柱、对齐 gen_ai.* 语义为迁移留口);④自动化闭环(故障指纹告警+bad case 回流评估集跑回归);每步用真实故障验证、留回滚开关。
