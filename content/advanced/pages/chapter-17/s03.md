## 真实问题

退款 Agent 接上了第 2 节的 tracer 之后，团队很快发现新问题：trace（追踪）确实能回放单次运行了，但当运营同学问「最近退款成功率是不是下降了」「昨天一整天的总成本多少」这类**聚合问题**时，trace 一条条看根本答不了；反过来，当值班工程师想看「那次失败请求里，上游订单接口到底返回了什么原始报文」这类**细节问题**时，trace 里只记了「ok=False」也不够。更糟的是，有人在 trace、有人在 print、有人在 dashboard，三套数据各说各话，出事时对不上——同一次故障，dashboard 上是一条异常曲线，日志里是几百行文本，trace 里是一棵树，但**没有任何 id 能把它们串起来**。

这一节要讲清可观测性的三大支柱（Traces / Metrics / Logs）各自回答什么问题、按什么顺序配合排障，以及最关键的一点：**怎么用 `trace_id` 把三者串成一条线，而不是三座孤岛**。同时把「结构化日志」这个从「靠 print」爬升的第一步讲透。

## 原理：三大支柱与「面→线→点」漏斗

借用通用可观测性理论，Agent 可观测性可分三层：

- **Traces（追踪）**：单次运行的完整调用链——回答「这一次为什么这样」；
- **Metrics（指标）**：聚合的量化数据，如成功率、平均步数、P95 延迟、日均成本——回答「整体健康度如何」；
- **Logs（日志）**：离散事件记录——补充细节，回答「那一步具体发生了什么」。

三者不是并列摆着好看，它们有明确的**使用顺序**，构成一条从「面」到「线」到「点」的漏斗：
```text
       [面] Metrics        [线] Traces          [点] Logs
   ┌────────────────┐  ┌────────────────┐  ┌────────────────┐
   │ 成功率↓、P95↑   │→ │ 抽出异常那批     │→ │ 看具体报错栈、  │
   │ 成本突增        │  │ 运行的调用链     │  │ 原始返回值      │
   │ (发现有问题)    │  │ (定位哪一步)     │  │ (看清细节)      │
   └────────────────┘  └────────────────┘  └────────────────┘
        报警器              定位器              显微镜
```
顺序反了会很痛苦：如果你一上来就翻 logs（显微镜），面对海量离散日志根本不知道该看哪条——这正是导读故障里工程师踩的坑，他两个小时都耗在「显微镜」阶段。正确姿势永远是**先看 metrics 确认「有没有问题、影响多大」，再用 trace 定位「问题在哪一步」，最后用 log 看清「那一步的细节」**。

| 支柱 | 数据形态 | 回答的问题 | 典型工具/落地 |
|---|---|---|---|
| Metrics | 聚合的数值时间序列 | 整体健康度如何？ | 成功率/P95/成本 dashboard |
| Traces | 单次运行的调用树 | 这一次为什么这样？ | Span 树、火焰图 |
| Logs | 离散的事件文本 | 那一步具体发生了什么？ | 结构化日志 + 关联 trace_id |

### 结构化日志：从「给人读」到「给机器读」

从「靠 print」爬升的第一步，是把自由文本日志换成**结构化日志（structured logging）**。区别在于：`print("订单为空，重试")` 是给人读的字符串，机器无法聚合、无法关联；而结构化日志是一条带固定字段的记录（通常是 JSON，JavaScript Object Notation，一种数据交换格式），每条都带 `trace_id`、`span_id`、`timestamp`、`level`、`event` 以及事件相关的字段。

结构化的三大好处直接对应上面的三支柱：其一，带了 `trace_id`，日志才能和 trace、metric **关联**；其二，字段化之后，日志才能被聚合成 metric（比如「统计 `event=tool_empty` 的条数」就得到空返回率）；其三，机器可读的日志才能被自动扫描、告警。**没有结构化，三支柱就退化成三堆各自为政的文本。**

## 最小可运行演示

下面用一段纯 Python 演示：给退款 Agent 的每一步打**带 `trace_id` 的结构化日志**，然后从同一批日志里既聚合出 metrics、又能按 `trace_id` 筛出某次运行的完整 logs——一份数据、三种视角，全靠 `trace_id` 串联。不联网、不需要 API Key（Application Programming Interface Key，接口密钥）。
```python
"""结构化日志 + 三支柱关联(纯 Python):一份日志,既出 metrics 又出单次 logs。"""
from __future__ import annotations

import json
from collections import Counter


def make_logs() -> list[dict]:
    """模拟两次请求的结构化日志:req-A 正常,req-B 命中导读的空返回故障。"""
    return [
        {"trace_id": "req-A", "span": "tool.get_order", "event": "tool_ok", "ok": True, "cost": 0.0, "latency_ms": 88},
        {"trace_id": "req-A", "span": "llm_call", "event": "llm_ok", "ok": True, "cost": 0.0040, "latency_ms": 520},
        {"trace_id": "req-A", "span": "tool.issue_refund", "event": "tool_ok", "ok": True, "cost": 0.0, "latency_ms": 130},
        {"trace_id": "req-B", "span": "tool.get_order", "event": "tool_empty", "ok": False, "cost": 0.0, "latency_ms": 90},
        {"trace_id": "req-B", "span": "llm_call", "event": "llm_ok", "ok": True, "cost": 0.0071, "latency_ms": 610},
        {"trace_id": "req-B", "span": "tool.get_order", "event": "tool_empty", "ok": False, "cost": 0.0, "latency_ms": 88},
        {"trace_id": "req-B", "span": "llm_call", "event": "llm_ok", "ok": True, "cost": 0.0116, "latency_ms": 700},
    ]


def metrics_view(logs: list[dict]) -> dict:
    """[面] 聚合成 metrics:回答'整体健康度如何'。"""
    llm = [x for x in logs if x["span"] == "llm_call"]
    tools = [x for x in logs if x["span"].startswith("tool")]
    empty = [x for x in tools if x["event"] == "tool_empty"]
    total_cost = round(sum(x["cost"] for x in logs), 4)
    return {
        "请求数": len({x["trace_id"] for x in logs}),
        "工具空返回率": f"{len(empty)}/{len(tools)}",
        "总成本": f"${total_cost}",
        "事件分布": dict(Counter(x["event"] for x in logs)),
    }


def trace_view(logs: list[dict], trace_id: str) -> list[dict]:
    """[线] 按 trace_id 抽出单次运行:回答'这一次为什么这样'。"""
    return [x for x in logs if x["trace_id"] == trace_id]


def log_detail(logs: list[dict], trace_id: str, span: str) -> list[str]:
    """[点] 钻到某次运行的某一步:回答'那一步具体发生了什么'。"""
    return [json.dumps(x, ensure_ascii=False)
            for x in logs if x["trace_id"] == trace_id and x["span"] == span]


if __name__ == "__main__":
    logs = make_logs()
    print("=== [面] Metrics 发现问题 ===")
    print(metrics_view(logs))
    print("\n=== [线] Trace 定位:req-B 这次经历了什么 ===")
    for row in trace_view(logs, "req-B"):
        print(row)
    print("\n=== [点] Log 看清:req-B 的 get_order 那一步原始记录 ===")
    for line in log_detail(logs, "req-B", "tool.get_order"):
        print(line)
```
保存为 `three_pillars.py`，运行 `python three_pillars.py`。完整预期输出：
```text
=== [面] Metrics 发现问题 ===
{'请求数': 2, '工具空返回率': '2/4', '总成本': '$0.0227', '事件分布': {'tool_ok': 2, 'llm_ok': 3, 'tool_empty': 2}}

=== [线] Trace 定位:req-B 这次经历了什么 ===
{'trace_id': 'req-B', 'span': 'tool.get_order', 'event': 'tool_empty', 'ok': False, 'cost': 0.0, 'latency_ms': 90}
{'trace_id': 'req-B', 'span': 'llm_call', 'event': 'llm_ok', 'ok': True, 'cost': 0.0071, 'latency_ms': 610}
{'trace_id': 'req-B', 'span': 'tool.get_order', 'event': 'tool_empty', 'ok': False, 'cost': 0.0, 'latency_ms': 88}
{'trace_id': 'req-B', 'span': 'llm_call', 'event': 'llm_ok', 'ok': True, 'cost': 0.0116, 'latency_ms': 700}

=== [点] Log 看清:req-B 的 get_order 那一步原始记录 ===
{"trace_id": "req-B", "span": "tool.get_order", "event": "tool_empty", "ok": false, "cost": 0.0, "latency_ms": 90}
{"trace_id": "req-B", "span": "tool.get_order", "event": "tool_empty", "ok": false, "cost": 0.0, "latency_ms": 88}
```
看清这条动线：先从 metrics 发现「工具空返回率 2/4、总成本在涨」——**知道有问题**；再用 `trace_id="req-B"` 抽出这次运行，看到它 get_order 空返回后又调了两次 llm——**定位到哪一步**；最后钻到 get_order 那一步的原始日志——**看清细节**。三个视角来自**同一份带 `trace_id` 的结构化日志**，这就是「用 `trace_id` 串起三支柱」的具体含义。

> **经验**：三支柱要用 `trace_id` 串起来。日志里一定要带上当前的 `trace_id`，这样你在 dashboard 上发现一条异常曲线后，能顺着 `trace_id` 从 metric 跳到具体 trace，再跳到那条 log。**没有关联 id 的三支柱，是三座孤岛。**

## 真实系统对应

**官方公开机制**：LangSmith 把 run 组织成 trace 并提供 dashboard 聚合视图，同时支持按 metadata（如 `ls_provider`、`ls_model_name`）过滤与成本统计 [来源](https://docs.langchain.com/langsmith/log-llm-trace)；Langfuse 的 observation 记录 latency、timeToFirstToken 等 metrics 字段，又保留 input/output 原始内容供钻取，天然对应「线」与「点」[来源](https://langfuse.com/docs/api-and-data-platform/features/observations-api)；OpenTelemetry 的三大信号（traces / metrics / logs）本就设计为可通过 trace context 关联，日志可携带 `trace_id`、`span_id` 与 trace 关联 [来源](https://opentelemetry.io/docs/specs/semconv/gen-ai/)。**通用工程模式**：结构化日志携带 `trace_id`、按「metrics→traces→logs」漏斗排障、一份数据出三种视角，是可迁移到任意技术栈的做法。**教学参考实现**：上面的 `make_logs` 数据、`metrics_view` 聚合逻辑仅为演示三支柱关联而构造，真实系统的指标口径与日志字段以团队与平台约定为准。

需要点明边界：三支柱在真实系统里往往落在不同存储（metrics 进时序库、traces 进 trace 后端、logs 进日志系统），本节把它们放进同一个列表只为演示关联逻辑；跨存储关联的前提仍是「三者都带同一个 `trace_id`」。

## 生产踩坑

| 症状 | 根因 | 如何观测与复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| dashboard、日志、trace 对不上 | 三支柱没有共享 trace_id | 去掉日志里的 trace_id 复现孤岛 | 所有信号统一带 trace_id/span_id | 单一数据源时不涉及关联 |
| 运营问「昨天总成本」答不上 | 只有 trace 没有聚合 metrics | 只留单条 trace 尝试回答复现 | 从结构化日志聚合出成本指标 | 一次性调试无需长期指标 |
| 一上来翻海量日志找不到北 | 排障顺序反了,先点后面 | 直接从 logs 起手复现低效 | 严格按 metrics→traces→logs | 已知具体 trace_id 时可直达 |
| 空返回率算不出来 | 日志是自由文本无法聚合 | 用 print 文本尝试统计复现 | 改结构化字段 event/ok | 极小规模人工可数时较轻 |
| 日志里混入用户手机号被合规通报 | 结构化日志未脱敏原样落库 | 用含 PII 输入跑一遍看落库 | 落库前对敏感字段掩码/哈希 | 完全内部脱敏数据场景较轻 |
| 高流量下日志量暴涨拖垮系统 | 全量记录未采样 | 压测高 QPS 看日志写入瓶颈 | 头部采样 + 异常全采 | 低流量原型阶段可全量 |

TTL（Time To Live，生存时间）适用于可过期的调试日志与采样样本，但异常/高成本请求的证据应延长保留期。PII（Personally Identifiable Information，个人可识别信息）在写入日志与追踪前应最小化与脱敏。

## 思考：三大支柱应按什么顺序使用来排障？为什么说「没有关联 id 的三支柱是三座孤岛」？

### 回答

应按「metrics → traces → logs」这条从面到线到点的漏斗顺序使用，对应「报警器 → 定位器 → 显微镜」。先看 **metrics** 确认「到底有没有问题、影响面多大」——比如成功率下滑、P95 延迟上翘、成本突增，这一步决定「要不要查、优先级多高」；再用 **traces** 从异常那批请求里抽出完整调用链，定位「问题出在哪一步」——是某个工具空返回，还是循环失控；最后用 **logs** 钻到那一步的原始记录，看清「具体细节」——原始返回报文、完整报错栈。顺序不能反：如果一上来就翻海量离散日志（直接上显微镜），根本不知道该看哪一条，这正是很多人排障低效的根源。之所以说「没有关联 id 的三支柱是三座孤岛」，是因为三者分别回答不同粒度的问题、往往还存在不同的后端系统，如果它们不共享同一个 `trace_id`，你在 dashboard 上看到一条异常曲线时，就无法顺着它跳到对应的那条 trace，更无法再跳到那一步的原始日志——三份数据各自为政、无法相互印证，排障就退化成在三个系统里分别大海捞针。只有让 metrics、traces、logs 都带上同一个 `trace_id`，它们才连成一条可以顺藤摸瓜的线。

### 面试精简表达

顺序是 metrics→traces→logs,即报警器发现问题→定位器找到哪一步→显微镜看清细节,反过来先翻日志会淹死;三支柱必须共享 trace_id 才能相互跳转印证,否则就是三座各自为政的孤岛,dashboard 上的异常曲线跳不到对应 trace 和 log。

## 思考：为什么「结构化日志」是从「靠 print」爬升的第一步，它比多打 print 强在哪？

### 回答

因为可观测性的价值不在「记了多少」，而在「记的东西能不能被关联、聚合、自动处理」，而自由文本的 `print` 三样都做不到。结构化日志把每条记录变成带固定字段的对象（通常是 JSON），至少包含 `trace_id`、`span_id`、`timestamp`、`event` 和事件相关字段，这带来三个 `print` 给不了的能力。第一是**可关联**：带了 `trace_id`，一条日志才能归属到「哪次请求的哪一步」，才能和 trace、metric 串起来，并发场景下也不会混淆；`print("重试")` 则完全无法归属。第二是**可聚合**：字段化之后，「统计 event=tool_empty 的条数」就直接得到空返回率、「对 cost 字段求和」就得到总成本，日志能被算成指标；自由文本无法被机器统计。第三是**可自动化**：结构化记录能被程序扫描、匹配故障指纹、触发告警，而 `print` 只能靠人肉去读。所以「多打 print」只是让「翻日志」这件苦差事更苦，而换成结构化日志，才真正打开了从「事后人肉翻」到「事前自动报」的升级通道——这也是可观测性成熟度从第一级「靠 print」迈向更高级别的必经一步。

### 面试精简表达

print 是给人读的自由文本,不能关联、不能聚合、不能自动处理;结构化日志带 trace_id 等固定字段,能归属到具体请求(可关联)、能求和计数出指标(可聚合)、能被程序扫描告警(可自动化),这三点让排查从人肉翻日志升级为自动发现,所以它是脱离'靠 print'的第一步。
