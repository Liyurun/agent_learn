## 真实问题

有了 trace（追踪）、结构化日志、指标之后，退款 Agent 团队又遇到一个「有了数据却不会用」的尴尬：某天下午客服反馈「退款 Agent 变慢了，有的要等十几秒」，值班工程师打开 trace 平台，面对成百上千条 trace 一条条点开看，看了半小时也没得出结论——**有数据不等于会定位**。技术负责人看不下去，问了三个问题就锁定了病根：「慢的是模型还是工具？」（工具，某次数据库查询 12 秒）「同一个查询是不是被重复调了？」（是，同参数调了两次）「这个 bad case 进评估集了吗？」（没有）。三个问题背后，是一套可复用的系统化根因定位方法。

这一节把这套方法讲透，它分三步：**① 时间归因**（模型时间 vs 工具时间，回答「谁慢」）→ **② 故障指纹**（用可编程规则从 trace 里自动扫出循环失控、重复调用、脏数据等已知故障模式）→ **③ 评估集固化**（把定位到的 bad case 变成永久回归样本）。掌握它，你就能像技术负责人那样「三个问题锁定病根」，而不是在 trace 海里大海捞针。这也是「Agent 出故障如何排查」这道面试题的核心答案。

## 原理：三步定位法

### 第一步：时间归因——分离「模型时间」与「工具时间」

当 Agent 变慢，不要瞎猜，先把一次运行的时间**按类别拆开**。有一句实战箴言：

> **「慢 Agent 往往是慢工具」** —— 很多时候 Agent 慢不是模型慢，而是某个工具（数据库查询、外部 API，Application Programming Interface，应用程序接口）拖了后腿。

分离 trace 能立刻告诉你时间花在哪，避免「误优化模型」——很多人一看慢就想换更小更快的模型，结果模型时间本来就只占 10%，白忙一场。归因的第一步永远是**分类聚合**，而不是逐条盯着看。注意这里和第 5 节的对照：第 5 节按「成本」归因，大头在模型（token 贵）；本节按「延迟」归因，大头可能在工具（查询慢）——**同一批 span，看不同指标会得出不同大头，所以要明确「你在优化哪个指标」**。

### 第二步：故障指纹——把已知故障模式变成可编程检测

Agent 生产故障有几个高频模式，每一类都有可编程识别的「指纹」：

| 故障模式 | 表现 | 排查线索（指纹） |
|---|---|---|
| **循环失控（stall）** | 步数爆炸、迟迟不终止 | 工具调用次数超上限、后半段 span 高度相似 |
| **重复调用** | 同参数反复调同一工具 | (工具名, 参数) 组合出现 ≥3 次 |
| **幻觉调用** | 调用不存在的工具 / 伪造参数 | 出现工具注册表外的 name、参数解析失败 |
| **成本爆炸** | token / 费用异常 | 每轮输入 token 单调爬升（第 5 节） |
| **Prompt Drift（提示漂移）** | 改了 prompt 后行为退化 | 无单条指纹，靠评估基线对比 |
| **脏数据传播** | 工具返回错误数据被当真 | 有 span 返回 ok=False 却继续跑 |

关键理念：**排障不该靠肉眼盯 trace，而该把这些「指纹检测」沉淀成自动化规则**，让系统在你看之前就把可疑点标出来。这是从「手动 debug」进化到「可观测性平台」的本质。

### 第三步：评估集固化——让 bad case 不再复发

定位问题后，把这个 case 加入评估集（回扣第 16 章），修复后跑评估确认「修好了且没引入回归」。这一步把第 16、17 章闭环了起来：**trace 负责「发现并定位」一个 bad case，评估集负责「固化并防止它复发」**。一个成熟团队的排障不会停在「我把这个 bug 修了」，而是「我把这个 bug 变成了一条永久的评估样本，以后任何改动都得先过它这一关」。

## 最小可运行演示

下面用纯 Python 把「时间归因 + 故障指纹」两步做成一个自动根因定位器，喂给它导读故障那次运行的 trace，让它自动报出「谁慢、命中了哪些故障指纹」。不联网、不需要 API Key（Application Programming Interface Key，接口密钥）。
```python
"""自动根因定位器(纯 Python):时间归因 + 故障指纹扫描。"""
from __future__ import annotations

import json
from collections import defaultdict


def build_trace() -> list[dict]:
    """导读故障那次运行:get_order 空返回 + 同参数重复调用 + 循环失控。"""
    spans = []
    for turn in range(1, 9):
        spans.append({"name": "llm_call", "kind": "model", "latency_ms": 600})
        spans.append({"name": "tool.get_order", "kind": "tool",
                      "args": {"order_id": "A-2026"}, "ok": False, "rows": 0,
                      "latency_ms": 3000})  # 慢工具:数据库查询 3 秒
    return spans


def attribute_latency(spans: list[dict]) -> dict:
    """[归因] 把总延迟按 kind 拆开,找出大头。"""
    buckets = defaultdict(float)
    for sp in spans:
        buckets[sp["kind"]] += sp["latency_ms"]
    total = sum(buckets.values())
    return {k: f"{v:.0f}ms ({v / total:.0%})"
            for k, v in sorted(buckets.items(), key=lambda x: -x[1])}


def detect_failures(spans: list[dict], max_steps: int = 6) -> list[str]:
    """[指纹] 从一条 trace 自动扫出常见故障。"""
    alerts = []
    tool_spans = [s for s in spans if s["kind"] == "tool"]

    # 指纹1:循环失控——工具调用次数超上限
    if len(tool_spans) > max_steps:
        alerts.append(f"循环失控:工具调用 {len(tool_spans)} 次 > 上限 {max_steps}")

    # 指纹2:重复调用——(工具名,参数)反复出现
    seen = defaultdict(int)
    for s in tool_spans:
        key = (s["name"], json.dumps(s.get("args"), sort_keys=True, ensure_ascii=False))
        seen[key] += 1
        if seen[key] == 3:
            alerts.append(f"重复调用:{s['name']} 用相同参数已调 {seen[key]} 次")

    # 指纹3:脏数据/失败工具——返回 ok=False 却继续跑
    fails = [s for s in tool_spans if s.get("ok") is False]
    if fails:
        alerts.append(f"脏数据/失败未处理:{fails[0]['name']} 返回 ok=False 但流程继续({len(fails)} 次)")
    return alerts


if __name__ == "__main__":
    trace = build_trace()
    print("=== 第一步:时间归因(谁慢?) ===")
    print(attribute_latency(trace))
    print("\n=== 第二步:故障指纹扫描(为什么?) ===")
    for a in detect_failures(trace):
        print(" -", a)
    print("\n=== 第三步:固化(下一步做什么?) ===")
    print(" - 把本次输入固化为评估样本进 held-out 集,修复后跑回归确认无副作用")
```
保存为 `root_cause.py`，运行 `python root_cause.py`。完整预期输出：
```text
=== 第一步:时间归因(谁慢?) ===
{'tool': '24000ms (83%)', 'model': '4800ms (17%)'}

=== 第二步:故障指纹扫描(为什么?) ===
 - 循环失控:工具调用 8 次 > 上限 6
 - 重复调用:tool.get_order 用相同参数已调 3 次
 - 脏数据/失败未处理:tool.get_order 返回 ok=False 但流程继续(8 次)
```
```text
=== 第三步:固化(下一步做什么?) ===
 - 把本次输入固化为评估样本进 held-out 集,修复后跑回归确认无副作用
```
逐行讲解：

- **时间归因** 一眼给出 `tool: 83%`——结论立刻清晰：**该去优化工具，而不是折腾模型**。这就是「慢 Agent 是慢工具」的量化版本，也正是技术负责人第一个问题的答案。
- **重复调用指纹** 把 `(工具名, 参数)` 作为 key 计数，命中「同参数调了 3 次」——对应第二个问题，说明 Agent 陷入了「同一个坑里反复横跳」。
- **脏数据指纹** 抓到「工具返回 ok=False 却继续跑」——这类问题不查 trace 根本发现不了，因为最终输出可能「看起来正常」。三条指纹同时命中，正好复现导读故障的复合成因。

## 真实系统对应

**官方公开机制**：LangSmith 支持按 trace 查看每个 run 的耗时、按 metadata 过滤、并把 bad case 加入 dataset 做评估回归 [来源](https://docs.langchain.com/langsmith/observability-concepts)；OpenTelemetry GenAI 指标里 `gen_ai.client.operation.duration` 的 `error.type` 标签可用于区分失败调用 [来源](https://docs.nvidia.com/nemo/guardrails/latest/observability/metrics/reference.html)；Anthropic 的 `stop_reason`（如 `max_tokens`、`tool_use`）可用于观测循环是否因工具而继续或因长度截断（第 8 章）。**通用工程模式**：时间归因、故障指纹自动检测、bad case 固化进评估集，是可迁移到任意框架的排障框架。**教学参考实现**：上面的 `detect_failures` 阈值（如 `max_steps=6`、重复 3 次）需按业务实测校准，不是普适常数；指纹规则也远不止这三条。

需要点明边界：故障指纹只能识别**已知模式**，对全新的故障形态无能为力——它是「缩小范围」的加速器，不是「取代人」的自动驾驶。最终的根因确认仍要回到实际请求快照与轨迹回放（第 5 节），人来做判断。此外，阈值设置是个权衡：太松漏报、太紧误报，需要用历史数据持续校准。

## 生产踩坑

| 症状 | 根因 | 如何观测与复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| 一看慢就换小模型结果没用 | 没做时间归因,误优化模型 | 造慢工具场景看模型占比很低 | 先归因再优化,盯占比最大项 | 确认模型确实是大头时才优化模型 |
| trace 海里逐条点开找不到北 | 靠肉眼而非指纹自动扫 | 面对上千 trace 手动排查复现低效 | 把故障模式写成指纹自动标红 | trace 极少时人工可覆盖 |
| 重复调用没被发现 | 未按(工具,参数)去重计数 | 让 Agent 同参数反复调复现 | 指纹检测 (name,args) 出现次数 | 合理的多次调用不应误报 |
| 工具失败却继续跑出错答案 | 未检测 ok=False 继续的情况 | 让工具返回失败但不停复现 | 指纹扫 ok=False 且流程未中断 | 有意的降级继续需白名单 |
| 修好的 bug 过阵子又复发 | 没把 bad case 固化进评估集 | 修完不加回归样本复现回归 | trace 定位后固化进 held-out 集 | 一次性临时脚本可不固化 |
| 指纹规则误报刷屏 | 阈值太紧未按数据校准 | 用正常流量跑指纹看误报率 | 用历史数据校准阈值 | 高危场景宁可误报不可漏报 |
| 全新故障指纹抓不到 | 指纹只覆盖已知模式 | 造一个没见过的故障复现漏检 | 指纹加速定位,人工兜底确认 | 已知模式占多数时收益仍高 |

## 思考：面试官问「Agent 在生产上出了故障你怎么排查」，怎么答得有条理？

### 回答

分三步走，从「谁」到「为什么」到「怎么防复发」。第一步**时间/成本归因**：先看 metrics 确认有没有问题、影响多大，再把出问题那批运行的 trace 按类别拆开——如果是「慢」，分离模型时间和工具时间，记住「慢 Agent 往往是慢工具」，别一上来就换模型；如果是「贵」，把每轮输入 token 拆出来看是否平方级膨胀。归因的意义是先锁定「大头在哪」，避免误优化。第二步**对照故障指纹**：不要肉眼一条条翻 trace，而是用可编程规则扫已知故障模式——循环失控（工具调用超上限、后段 span 相似）、重复调用（同工具同参数出现 ≥3 次）、幻觉调用（调了注册表外的工具）、脏数据传播（工具返回 ok=False 却继续跑）、成本爆炸（输入 token 单调爬升）、prompt drift（靠评估基线对比）。把这些指纹沉淀成自动化规则，系统能在你看之前就标红可疑点。第三步**固化进评估集**：定位并修复后，把这次的输入固化成一条评估样本进 held-out 集，跑回归确认「修好了且没引入副作用」，让这个 bug 永不复发。最后用一个真实故障收尾（如导读的「空返回→重试→平方级烧钱」），证明你不只背流程还踩过坑。这套「归因→指纹→固化」比「加 print 看看」有条理得多。

### 面试精简表达

三步:①时间/成本归因——先看指标再拆 trace,慢就分模型/工具时间(慢 Agent 常是慢工具),贵就看每轮 token 是否平方膨胀,先锁大头别误优化;②故障指纹——用规则自动扫循环失控/重复调用/幻觉/脏数据/成本爆炸,不靠肉眼翻;③固化——bad case 进 held-out 评估集跑回归防复发;最后拿一个真实故障收口。

## 思考：为什么说「故障指纹检测」是从手动 debug 进化到可观测性平台的本质？

### 回答

因为它把「人肉在 trace 里找可疑点」这件不可规模化的事，变成了「系统自动扫描并标红」这件可规模化的事，这正是「工具」和「平台」的分水岭。手动 debug 的问题在于：它依赖工程师的经验和精力，一次只能看一条 trace，面对生产规模成百上千条运行根本看不过来，而且换个人、或者同一个人累了，就容易漏掉。故障指纹的思路是反过来的——把每一类已知故障模式（循环失控、重复调用、脏数据等）用可编程的规则表达出来（比如「(工具名,参数) 出现 ≥3 次就是重复调用」），让系统在数据落库时就自动跑这些规则，把命中的可疑 trace 提前标红、甚至触发告警。这样工程师不再是「大海捞针」，而是「系统把针挑出来给你确认」，精力从「找问题」转向「判断和修复」。这也是可观测性成熟度爬升的标志：第二级是「有结构化 trace 能人肉回放」，第四级才是「故障指纹自动化 + 告警」，团队从「事后救火」转向「事前预警」。当然指纹只能覆盖已知模式，全新故障仍需人工兜底，所以它是「加速器」而非「自动驾驶」——但对占多数的重复性故障，收益巨大。

### 面试精简表达

手动 debug 靠人肉逐条看 trace,不可规模化、会累会漏;故障指纹把已知故障模式写成可编程规则,让系统在数据落库时自动扫描标红甚至告警,工程师从'大海捞针'变成'确认系统挑出的针',精力从找问题转向修问题——这就是从工具到平台、从事后救火到事前预警的本质;局限是只覆盖已知模式,全新故障仍需人工兜底。
