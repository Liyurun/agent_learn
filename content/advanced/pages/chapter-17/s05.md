## 真实问题

导读那次「凌晨账单翻 40 倍」结案后，团队复盘出一个尖锐的事实：**成本是最晚被发现、也最贵的信号**。当晚 02:47 上游接口就开始返回空 JSON（JavaScript Object Notation，一种数据交换格式），但成本告警到 02:50 才响、工程师 04:50 才定位——**三个小时里账单一直在涨**。为什么这么晚？因为团队当时只监控了「错误率」和「延迟」，唯独没把「每次运行的 token（词元）消耗」当成一等公民来采集。而 Agent 的成本恰恰藏在 token 里：一次运行调了几次模型、每次输入输出多少 token、单价多少——这些不采集，成本就是个黑洞。

这一节要解决两件事：一是把 token / 延迟 / 成本这三个 Agent 最核心的量化指标**采集并归因到 span（跨度）**，让「哪一步花了多少钱、耗了多久」一目了然；二是实现**轨迹回放（trace replay）**——把一次运行的完整 trace（追踪）存下来，事后能逐帧「重播」，看清成本曲线是怎么一步步爬上去的。这两件事合起来，就能让「凌晨翻 40 倍」这类故障在告警响起的第一时间被解释清楚，而不是靠三小时肉眼翻日志。

## 原理：三个核心指标与它们的采集口径

Agent 可观测性里，有三个指标几乎决定了「生产健康度」的下限：

- **token 用量**：分输入（input / prompt）和输出（output / completion）两类，二者单价通常不同。OpenTelemetry GenAI（Generative AI，生成式人工智能）语义约定里用 `gen_ai.client.token.usage` 这个 Histogram（直方图）指标记录，并用 `gen_ai.token.type`（`input` / `output`）标签区分——每次调用记两条观测 [来源](https://docs.nvidia.com/nemo/guardrails/latest/observability/metrics/reference.html)。
- **延迟（latency）**：一次模型调用的墙钟耗时，OTel 用 `gen_ai.client.operation.duration`（单位秒的 Histogram）记录 [来源](http://raw.githubusercontent.com/open-telemetry/semantic-conventions-genai/main/docs/gen-ai/gen-ai-metrics.md)。流式（streaming）场景还关心 TTFT（Time To First Token，首 token 延迟），Langfuse 用 `timeToFirstToken` 字段记录 [来源](https://langfuse.com/docs/api-and-data-platform/features/observations-api)。
- **成本（cost）**：由 token 用量乘以模型单价算出。Langfuse 明确「为每次生成记录 usage details（各类型 token 数）与 cost details（各类型成本），并支持 cached_tokens 等更细的用量类型」[来源](https://langfuse.com/docs/observability/features/token-and-cost-tracking)。LangSmith 也强调必须提供 `usage_metadata` 与 `ls_model_name` 才能算出成本 [来源](https://docs.langchain.com/langsmith/log-llm-trace)。

一个关键洞察：**Agent 的成本随对话轮数往往不是线性、而是接近平方级增长**。因为模型无状态，每一轮都要把之前所有轮的对话历史重新喂进去（第 8 章讲过这个成本结构），所以第 N 轮的输入 token 约正比于 N，累加 N 轮后总 token 约正比于 N²。导读故障里循环失控跑了 40 多轮，成本就是这么被平方级放大的。**只有把每轮的 token 采集下来画成曲线，才能一眼识别这种膨胀。**

### 轨迹回放：把 trace 当「录像」而非「快照」

轨迹回放的核心思想是：一次运行的 trace 不只是「出事后查一眼的快照」，而是一段可以逐帧重播的「录像」。把所有 span 按时间顺序存下来，事后你能：逐帧看每一步的输入输出、累加成本看它怎么爬升、对比正常运行和故障运行的差异。这比「只看最终结果对不对」强大得多——它让你看到**过程**，而不只是**结果**。商用平台（LangSmith、Langfuse）的「trace 详情页」本质就是一个轨迹回放器。

## 最小可运行演示

下面用纯 Python 实现一个「指标采集 + 轨迹回放」的最小系统：给导读故障那次运行的每个 span 记录 token / 延迟 / 成本，按类别归因总开销，逐帧回放看成本怎么爬升，并自动判断是否是「平方级膨胀」。不联网、不需要 API Key（Application Programming Interface Key，接口密钥）。
```python
"""指标采集 + 轨迹回放(纯 Python):按 span 归因 token/延迟/成本,回放成本曲线。"""
from __future__ import annotations

from collections import defaultdict

    # 模型单价(美元/1K token),教学构造值,真实价格以官方文档为准
PRICE = {"strong": {"in": 0.003, "out": 0.015}}


def cost_of(model: str, in_tok: int, out_tok: int) -> float:
    p = PRICE[model]
    return round(in_tok / 1000 * p["in"] + out_tok / 1000 * p["out"], 6)


def build_incident_trace() -> list[dict]:
    """重建导读'凌晨翻 40 倍'那次运行:每轮历史累积,输入 token 线性增长。"""
    spans = [{"name": "agent_run", "kind": "root", "in": 0, "out": 0, "latency_ms": 0}]
    base_in = 800
    for turn in range(1, 7):
        in_tok = base_in * turn          # 无状态->每轮重发历史->输入随轮数线性增长
        out_tok = 120
        spans.append({"name": "llm_call", "kind": "model", "turn": turn,
                      "in": in_tok, "out": out_tok,
                      "cost": cost_of("strong", in_tok, out_tok),
                      "latency_ms": 500 + turn * 30})
        spans.append({"name": "tool.get_order", "kind": "tool", "turn": turn,
                      "in": 0, "out": 0, "ok": False, "rows": 0, "latency_ms": 90})
    return spans


def attribute(spans: list[dict]) -> dict:
    """按 kind 归因 token/成本/延迟,找出大头。"""
    tok = defaultdict(int)
    cost = defaultdict(float)
    lat = defaultdict(float)
    for sp in spans:
        if sp["kind"] == "root":
            continue
        tok[sp["kind"]] += sp["in"] + sp["out"]
        cost[sp["kind"]] += sp.get("cost", 0.0)
        lat[sp["kind"]] += sp["latency_ms"]
    return {"token": dict(tok), "cost": {k: round(v, 4) for k, v in cost.items()},
            "latency_ms": dict(lat)}


def replay(spans: list[dict]) -> None:
    """轨迹回放:逐帧累加成本,看曲线怎么爬升。"""
    running = 0.0
    for sp in spans:
        if sp["kind"] != "model":
            continue
        running += sp["cost"]
        bar = "#" * int(sp["in"] / 200)
        print(f"  T{sp['turn']} in={sp['in']:5d}tok cost=${sp['cost']:.5f} "
              f"累计=${running:.5f} |{bar}")


def is_quadratic(spans: list[dict]) -> bool:
    """判断输入 token 是否随轮数近似线性增长(=> 累计成本近似平方级)。"""
    ins = [sp["in"] for sp in spans if sp["kind"] == "model"]
    diffs = [b - a for a, b in zip(ins, ins[1:])]
    return len(set(diffs)) == 1 and diffs[0] > 0  # 等差递增 => 平方级累计


if __name__ == "__main__":
    trace = build_incident_trace()
    print("=== 按类别归因(token / 成本 / 延迟) ===")
    print(attribute(trace))
    print("\n=== 轨迹回放:成本曲线逐帧爬升 ===")
    replay(trace)
    print("\n=== 自动判定 ===")
    total = round(sum(s.get("cost", 0.0) for s in trace), 4)
    print(f"本次总成本=${total};输入 token 每轮等差递增(平方级累计)={is_quadratic(trace)}")
```
保存为 `metrics_replay.py`，运行 `python metrics_replay.py`。完整预期输出：
```text
=== 按类别归因(token / 成本 / 延迟) ===
{'token': {'model': 17520, 'tool': 0}, 'cost': {'model': 0.0612, 'tool': 0.0}, 'latency_ms': {'model': 3630.0, 'tool': 540.0}}

=== 轨迹回放:成本曲线逐帧爬升 ===
  T1 in=  800tok cost=$0.00420 累计=$0.00420 |####
  T2 in= 1600tok cost=$0.00660 累计=$0.01080 |########
  T3 in= 2400tok cost=$0.00900 累计=$0.01980 |############
  T4 in= 3200tok cost=$0.01140 累计=$0.03120 |################
  T5 in= 4000tok cost=$0.01380 累计=$0.04500 |####################
  T6 in= 4800tok cost=$0.01620 累计=$0.06120 |########################
```
```text
=== 自动判定 ===
本次总成本=$0.0612;输入 token 每轮等差递增(平方级累计)=True
```
逐行看清价值：

- **归因** 一眼看出成本几乎全在 `model`（工具不花 token），且延迟大头也在模型——但注意这是「成本视角」，跟第 6 节「延迟视角」会得出不同大头，说明**归因要看你关心哪个指标**。
- **回放** 那条逐帧爬升的柱状条，把「平方级膨胀」画得清清楚楚：输入 token 每轮 +800（等差），累计成本越涨越快。这正是导读故障的成本引擎。
- **自动判定** 用「输入 token 是否等差递增」判断平方级累计——真实系统里，这个判定可以做成告警规则，在成本还没翻 40 倍时就预警。

## 真实系统对应

**官方公开机制**：OpenTelemetry GenAI 指标定义了 `gen_ai.client.token.usage`（Histogram，`{token}` 单位，用 `gen_ai.token.type` 区分 input/output）与 `gen_ai.client.operation.duration`（Histogram，秒）[来源](http://raw.githubusercontent.com/open-telemetry/semantic-conventions-genai/main/docs/gen-ai/gen-ai-metrics.md) [来源](https://docs.nvidia.com/nemo/guardrails/latest/observability/metrics/reference.html)，社区还在提议补充 `gen_ai.client.time_to_first_token` 等指标 [来源](https://github.com/open-telemetry/semantic-conventions-genai/issues/101)；Langfuse 按 generation 记录 usage details 与 cost details（含 cached_tokens 等类型）并提供 latency / timeToFirstToken [来源](https://langfuse.com/docs/observability/features/token-and-cost-tracking) [来源](https://langfuse.com/docs/api-and-data-platform/features/observations-api)；LangSmith 要求提供 usage_metadata 与 ls_model_name 才能计算成本 [来源](https://docs.langchain.com/langsmith/log-llm-trace)。**通用工程模式**：按 span 归因指标、把 trace 当录像逐帧回放、用「token 等差递增」识别平方级成本，是可迁移到任意框架的做法。**教学参考实现**：`PRICE` 单价、`build_incident_trace` 的增长曲线均为教学构造，真实价格与增长形态以官方文档和实测为准。

需要点明边界：真实的 token 计费还涉及缓存 token（prompt caching）、批量折扣、不同模型混用等复杂情况，本节演示的「输入线性→累计平方」是简化模型，用于说明机制而非精确报价。缓存命中会显著改变这条曲线——这也是为什么 Langfuse 专门记 `cached_tokens`。

## 生产踩坑

| 症状 | 根因 | 如何观测与复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| 成本翻倍很晚才发现 | 没把 token 当一等指标采集 | 只监控错误率不监控 token 复现 | 每次调用记 input/output token 与成本 | 固定单轮任务成本平稳时较轻 |
| 成本涨了却不知涨在哪 | 未按 span 归因成本 | 只有总账单无分解复现 | 按 span/按轮归因 token 与成本 | 单次单调用无需归因 |
| 平方级膨胀没被预警 | 未监控 token 随轮次的曲线 | 造循环让历史累积复现膨胀 | 监控每轮输入 token,等差递增即告警 | 短对话轮数少时膨胀不明显 |
| 只看结果对错、看不到过程 | 把 trace 当快照而非录像 | 只存最终输出复现无法回放 | 存全量 span 支持逐帧回放 | 极简任务无中间步骤 |
| 输入输出 token 混算导致成本错 | 未区分 in/out 单价 | 用统一单价算成本复现偏差 | 分 gen_ai.token.type 记两条 | 输入输出同价的模型可合并 |
| 缓存命中后成本估算偏高 | 未记录 cached_tokens | 开 prompt caching 后对不上账单 | 记录缓存 token 类型单独计价 | 未用缓存时无此项 |
| 流式场景首字慢但总延迟正常 | 只测总 latency 没测 TTFT | 流式响应下测感知延迟复现 | 额外记 time_to_first_token | 非流式场景无 TTFT 概念 |

## 思考：为什么 Agent 的成本常随对话轮数近似平方级增长？如何用可观测性提前预警？

### 回答

根源在于模型是**无状态**的：它不记得上一轮，每一轮都必须把之前所有轮的对话历史（系统提示、工具定义、历次问答）重新完整喂进去。于是第 N 轮的输入 token 大致正比于已累积的历史长度，也就是正比于 N；把 N 轮的输入 token 累加起来，总量就近似正比于 1+2+...+N，即 N²/2 量级——这就是「单轮输入线性增长、累计成本平方级增长」的由来。导读那次循环失控跑了 40 多轮，成本正是被这个平方关系放大到翻 40 倍。用可观测性提前预警的做法是：把**每一轮 LLM（Large Language Model，大语言模型）调用的输入 token 单独采集**成一条时间序列，然后监控这条序列的形状——如果发现它在单调、近似等差地爬升（而不是围绕一个稳定值波动），就说明历史在无节制累积，几乎必然伴随成本平方级膨胀，此时应在「翻几倍」而不是「翻 40 倍」时就触发告警。更进一步，可以设每次运行的 token / 成本预算上限，触顶即强停并告警（第 6 章、第 18 章的护栏）。关键是**别只监控总账单**——总账单是滞后的结果，每轮输入 token 曲线才是提前量。

### 面试精简表达

模型无状态、每轮重发全部历史,所以单轮输入 token 随轮数 N 线性增长,累加 N 轮后总成本约正比 N²,呈平方级;预警靠把每轮输入 token 采成时间序列,发现它单调等差爬升就说明历史在膨胀,在翻几倍时就告警,并设单次 token/成本预算上限触顶强停,而不是只盯滞后的总账单。

## 思考：「轨迹回放」比「只看最终结果对不对」强在哪？

### 回答

强在它让你看到**过程**而不只是**结果**，从而能定位「静默的、跨步骤累积的」故障。只看最终结果对不对，本质是把一次运行当成一个「黑箱快照」——输出对就算过、错就算挂，但当输出「看起来正常」却在背后烧钱（如导读故障），或者输出错了但你不知道错在哪一步时，快照就无能为力。轨迹回放把这次运行的所有 span 按时间存成一段「录像」，让你能做三件快照做不到的事：其一，**逐帧看中间态**，看清每一步的输入输出，找到最初偏离的那一步（比如第 2 步工具就空返回了）；其二，**累加过程量**，把成本、token 沿时间轴累加画成曲线，看出「平方级膨胀」这类只有在过程里才显现的问题；其三，**对比回放**，把一次正常运行和一次故障运行并排逐帧对比，差异点往往就是病根。商用平台的 trace 详情页本质就是这样一个回放器。一句话，结果视角只能回答「对不对」，回放视角能回答「为什么、从哪一步开始、怎么演变的」——而 Agent 的多数生产故障，答案都在「过程」里。

### 面试精简表达

只看结果是黑箱快照,只能判对错;轨迹回放把全部 span 存成录像,能逐帧看中间态找到最初偏离步、能沿时间轴累加成本看出平方级膨胀、能正常与故障运行对比找差异,专治'输出看似正常却在烧钱'和'跨步骤累积'这类快照抓不到的故障,平台的 trace 详情页就是回放器。
