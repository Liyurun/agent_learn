## 真实问题

前四小节讲清了「工具在模型眼里是什么」「怎么写描述」「怎么路由和兜错」，但很多人到真正动手时仍卡在同一处：**「模型提议、运行时执行、结果回传」到底怎么在一个循环里串起来？** 一个数据平台团队 2026 年初就栽在这上面——他们把每个工具调用都写成一段独立的 `if/else`，用户问一句就手写一次「解析→执行→再拼 prompt」，代码里散落着二十多个几乎一样的分支。任务一复杂（要先换算再落库再回读），分支就互相打架，某个环节忘了把结果写回记忆，模型下一轮就「失忆」，最终答案里凭空出现一个没算过的数。

问题不在模型，而在**没有一个统一的调用循环**：状态（每个工具的返回值）散落各处，停止条件（什么时候算完）没有明确信号，失败处理（某步报错怎么办）各写各的。本小节把这些收敛成一个完全可运行、无需 API（Application Programming Interface，应用程序编程接口）Key 的调用循环——用一个确定性的「模型替身」驱动，让你能亲眼看到一条完整轨迹如何一步步收敛到最终答案，也能亲眼看到它如何从一次工具名幻觉中自愈。

## 原理：一个最小调用循环的五个部件

抛开框架的糖衣，一个能跑起来的工具调用循环只需要五个部件，缺一不可：
```text
部件              职责                              对应本章前文
──────────       ──────────────────────────      ────────────────
① 工具注册表      name -> (可执行体, 必填参数)       第 3 小节的 Schema/校验
② 模型（替身）    看着记忆，提议下一步 {tool,args}   第 2 小节的「模型提议」
③ 执行闸门        白名单+必填校验+异常兜底           第 3/4 小节的校验与错误处理
④ 记忆           把每步结果存下，供后续步骤引用      第 5 章的短期记忆
⑤ 主循环         提议→执行→写记忆→再提议，直到 final 第 2 小节的「多轮收敛」
```
其中最容易被忽视的是**部件 ④ 记忆**和**部件 ⑤ 的停止信号**。开头团队的 bug 正是漏了 ④——某步结果没写回记忆，下一步引用时拿到空值。而停止信号（本例用 `type == "final"`）必须由模型明确给出、由运行时明确识别，否则循环要么提前结束、要么无限打转。真实的 OpenAI/Anthropic SDK 用 `stop_reason`/是否还有 `tool_calls` 承担这个信号，这里我们用一个显式的 `type` 字段替代，本质完全一致。

## 现象与输入：一条可复核的成功轨迹

沿用 README 里的贯穿案例——「把 100 美元按汇率 7.2 折算成人民币，四舍五入到两位小数，写进键值存储，再回读确认」。这条链条特意混了纯计算工具（`convert_currency`、`round_number`，无副作用）和有副作用工具（`kv_set` 写库、`kv_get` 读库），因为它们的安全等级不同，正好演示执行闸门的价值。期望轨迹是：
```text
[1] CALL convert_currency {amount:100, rate:7.2} -> 720.0
[2] CALL round_number {value:720.0, ndigits:2} -> 720.0
[3] CALL kv_set {key:"cny", value:720.0} -> {ok:true}
[4] CALL kv_get {key:"cny"} -> {value:720.0}
[5] FINAL 100 美元约合 720.0 人民币（已存入 key=cny）
```
注意第 2 步到第 3 步的衔接：`round_number` 的结果 `720.0` 必须被写进记忆，`kv_set` 才能引用它。这就是「部件 ④」的意义——每一步的产出是下一步的输入，循环靠记忆把它们串成一条链。

## 最小可运行演示：完整调用循环

下面这段纯标准库代码把五个部件全部实现出来。`MockProvider` 是「确定性模型替身」：它按已完成的轮数返回下一步提议，不访问网络、不需要任何 API Key，因此每次运行轨迹完全一致、可写进单元测试。真实项目里把 `MockProvider.propose` 换成一次真正的模型调用即可，循环骨架完全不用改。
```python
import json


class KVStore:
    """教学用内存键值存储，模拟一个有副作用的真实系统。"""

    def __init__(self) -> None:
        self._data: dict = {}

    def set(self, key: str, value) -> dict:
        self._data[key] = value
        return {"ok": True, "key": key}

    def get(self, key: str) -> dict:
        if key not in self._data:
            return {"ok": False, "error": f"key 不存在: {key}"}
        return {"ok": True, "key": key, "value": self._data[key]}


def convert_currency(amount: float, rate: float) -> float:
    return amount * rate


def round_number(value: float, ndigits: int = 0) -> float:
    return round(value, ndigits)


STORE = KVStore()

TOOLS = {  # 部件①：工具注册表。name -> {可执行体 fn, 必填参数 required}
    "convert_currency": {"fn": lambda amount, rate: convert_currency(amount, rate),
                         "required": ["amount", "rate"]},
    "round_number": {"fn": lambda value, ndigits=0: round_number(value, ndigits),
                     "required": ["value"]},
    "kv_set": {"fn": lambda key, value: STORE.set(key, value), "required": ["key", "value"]},
    "kv_get": {"fn": lambda key: STORE.get(key), "required": ["key"]},
}


def execute(step: dict) -> dict:
    """部件③：执行闸门。白名单校验->必填校验->真正执行->结构化结果。副作用只在这里发生。"""
    name = step["tool"]
    args = step.get("args", {})
    if name not in TOOLS:                                  # 白名单：挡住幻觉工具名
        return {"ok": False, "error": f"未知工具: {name}"}
    for key in TOOLS[name]["required"]:                    # 必填校验：挡住漏传参数
        if key not in args:
            return {"ok": False, "error": f"缺少必填参数: {key}"}
    try:
        value = TOOLS[name]["fn"](**args)                  # 真正执行，副作用发生在此
    except Exception as exc:                               # 兜底：任何异常都结构化，不甩裸栈
        return {"ok": False, "error": f"{type(exc).__name__}: {exc}"}
    return {"ok": True, "value": value}


class MockProvider:
    """部件②：确定性模型替身。按已完成轮数提议下一步；换成真实模型调用即可上线。"""

    def __init__(self) -> None:
        self.step = 0

    def propose(self, memory: dict) -> dict:
        self.step += 1
        if self.step == 1:
            return {"type": "tool_use", "tool": "convert_currency",
                    "args": {"amount": 100, "rate": 7.2}}
        if self.step == 2:
            return {"type": "tool_use", "tool": "round_number",
                    "args": {"value": memory["convert_currency"], "ndigits": 2}}
        if self.step == 3:
            return {"type": "tool_use", "tool": "kv_set",
                    "args": {"key": "cny", "value": memory["round_number"]}}
        if self.step == 4:
            return {"type": "tool_use", "tool": "kv_get", "args": {"key": "cny"}}
        readback = memory["kv_get"]["value"]
        return {"type": "final",
                "text": f"100 美元约合 {readback} 人民币（已存入 key=cny）"}


def run_agent(max_turns: int = 8):
    """部件⑤：主循环。提议->执行->写记忆->再提议，直到 final 或触顶。"""
    provider = MockProvider()
    memory: dict = {}                                      # 部件④：记忆，串起每步结果
    trace: list = []
    for turn in range(1, max_turns + 1):
        step = provider.propose(memory)
        if step["type"] == "final":                        # 停止信号：模型明确宣告收尾
            trace.append(f"[{turn}] FINAL {step['text']}")
            return trace, step["text"]
        result = execute(step)
        if not result.get("ok"):                           # 失败即结构化终止，不静默吞掉
            trace.append(f"[{turn}] ERROR {step['tool']} -> {result['error']}")
            return trace, f"失败终止：{result['error']}"
        memory[step["tool"]] = result["value"]             # 关键：把结果写回记忆
        trace.append(f"[{turn}] CALL {step['tool']} "
                     f"{json.dumps(step['args'], ensure_ascii=False)} -> {result['value']}")
    return trace, "达到最大轮数仍未完成"                    # 轮数上限：防止无限打转烧钱


def main() -> None:
    trace, answer = run_agent()
    for line in trace:
        print(line)
    print("ANSWER:", answer)


if __name__ == "__main__":
    main()
```
保存为 `tool_loop.py`，运行 `python tool_loop.py`。预期输出：
```text
[1] CALL convert_currency {"amount": 100, "rate": 7.2} -> 720.0
[2] CALL round_number {"value": 720.0, "ndigits": 2} -> 720.0
[3] CALL kv_set {"key": "cny", "value": 720.0} -> {'ok': True, 'key': 'cny'}
[4] CALL kv_get {"key": "cny"} -> {'ok': True, 'key': 'cny', 'value': 720.0}
[5] FINAL 100 美元约合 720.0 人民币（已存入 key=cny）
ANSWER: 100 美元约合 720.0 人民币（已存入 key=cny）
```
这段代码值得反复读三遍，因为它就是所有工具 Agent 的骨架。**把 `MockProvider` 换成真实模型**：`propose` 里改成「拼 prompt→调 API→解析返回的 `tool_use`/`function_call`」，其余四个部件——注册表、执行闸门、记忆、主循环——一行都不用动。这正是「掌握机制比记住字段名重要」的实证：机制稳定，SDK 只是把这套骨架包了层糖。特别留意 `run_agent` 里两处兜底：`max_turns` 防无限循环，`not result.ok` 时结构化终止而非静默吞错——这两处是把玩具循环变成能上生产的关键。

## 让循环自愈：从一次工具名幻觉中恢复

上面的轨迹一帆风顺，但真实模型会犯错。下面这段演示模型第一轮把 `multiply` 幻觉成 `multiplly`（多打一个字母），执行闸门结构化拒绝并回传候选，模型据此在第二轮改用正确工具——这就是第 4 小节「结构化错误让模型自愈」在完整循环里的样子：
```python
import difflib
import json

REGISTRY = {
    "add": lambda a, b: a + b,
    "multiply": lambda a, b: a * b,
}


def execute(tool: str, args: dict) -> dict:
    if tool not in REGISTRY:
        near = difflib.get_close_matches(tool, list(REGISTRY), n=1, cutoff=0.5)
        hint = f"未知工具 {tool}，是否想用 {near[0]}？" if near else f"未知工具 {tool}"
        return {"ok": False, "error": hint, "candidates": list(REGISTRY)}
    return {"ok": True, "value": REGISTRY[tool](**args)}


class SelfHealProvider:
    """先提议错的工具名，收到结构化错误后改用正确工具。"""

    def __init__(self) -> None:
        self.step = 0

    def propose(self, last_error: str | None) -> dict:
        self.step += 1
        if self.step == 1:
            return {"type": "tool_use", "tool": "multiplly", "args": {"a": 6, "b": 7}}
        if self.step == 2:                                 # 读到 error 里的候选，纠正为 multiply
            return {"type": "tool_use", "tool": "multiply", "args": {"a": 6, "b": 7}}
        return {"type": "final", "text": "6 乘 7 等于 42"}


def run(max_turns: int = 5):
    provider = SelfHealProvider()
    trace, last_error = [], None
    for turn in range(1, max_turns + 1):
        step = provider.propose(last_error)
        if step["type"] == "final":
            trace.append(f"[{turn}] FINAL {step['text']}")
            return trace
        result = execute(step["tool"], step["args"])
        if not result["ok"]:                               # 拒绝但不终止：把错误喂回，给模型改错机会
            last_error = result["error"]
            trace.append(f"[{turn}] REJECT {step['tool']} -> {result['error']}")
            continue
        last_error = None
        trace.append(f"[{turn}] CALL {step['tool']} "
                     f"{json.dumps(step['args'], ensure_ascii=False)} -> {result['value']}")
    return trace


def main() -> None:
    for line in run():
        print(line)


if __name__ == "__main__":
    main()
```
保存为 `self_heal_loop.py`，运行 `python self_heal_loop.py`。预期输出：
```text
[1] REJECT multiplly -> 未知工具 multiplly，是否想用 multiply？
[2] CALL multiply {"a": 6, "b": 7} -> 42
[3] FINAL 6 乘 7 等于 42
```
对比第一个循环里「失败即终止」和这里「拒绝但不终止、把错误喂回」的区别——这是一个重要的设计选择：**幻觉工具名、参数写错这类「可自愈」的失败，应该把结构化错误回传给模型让它重试**（但要设重试上限，防止它反复犯同样的错）；而权限不足、资源不存在这类「不可恢复」的失败，则应像第一个循环那样直接结构化终止。两种策略没有优劣，只有适用场景，取舍标准就是第 4 小节讲的「失败的可恢复性」。

## 真实系统对应

**官方公开机制**：OpenAI Function Calling 指南把工具调用画成「发请求→模型返回 `function_call`→运行时执行→回传 `function_call_output`→模型据此继续或收尾」的循环，并说明可多轮往返直到模型不再提议工具 [来源](https://platform.openai.com/docs/guides/function-calling)。Anthropic Tool use 文档用 `stop_reason: "tool_use"` 标识「还要继续执行工具」，用 `tool_result`（带 `tool_use_id`）把结果按 id 对应回传，模型据此继续到 `end_turn` [来源](https://docs.anthropic.com/en/docs/agents-and-tools/tool-use/overview)。本例的 `type` 字段和 `memory` 字典，就是对这套官方循环机制的最小化教学复刻。

**通用工程模式**：五部件拆分、记忆串联、轮数上限兜底、失败按「可恢复性」分流，都是可迁移到任意 SDK 的做法。**教学参考实现**：`MockProvider`/`SelfHealProvider` 用固定序列替代真实模型，只为让轨迹可复现、可测试；生产中它们会被真实模型调用取代，而其余部件保持不变。

## 生产踩坑

| 症状 | 根因 | 如何观测与复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| 最终答案引用了没算过的值 | 某步结果没写回记忆 | 打印每轮 memory 快照复现 | 循环里强制「执行成功即写记忆」 | 无状态依赖的单步调用无需记忆 |
| Agent 陷入无限调用同一工具 | 没有轮数上限或停止信号 | 让替身永远返回 tool_use 复现 | 设 `max_turns`，识别明确 final 信号 | 长任务可调高上限但不能取消 |
| 某步报错整个 Agent 崩溃 | 执行未捕获异常，裸栈上抛 | 传入非法参数触发异常 | 执行闸门 try/except 返回结构化 | 启动期配置错误应快速失败 |
| 模型反复犯同一个传参错 | 把可自愈失败也直接终止 | 回放失败轮，看是否给了重试机会 | 可恢复失败回传 hint 让其重试 | 不可恢复失败应直接终止上报 |
| 换真实模型后循环要重写 | 业务逻辑和模型调用耦合 | 检查 propose 是否混入执行逻辑 | 严守五部件边界，只换 propose | 极简单场景可不做严格分层 |

## 思考：为什么要用「确定性模型替身」而不是直接连真实模型来讲这个循环？

### 回答

三个原因。第一是**可复现**：真实模型每次输出可能不同，轨迹不稳定，读者跑出来的结果和文档对不上，无法判断是自己写错了还是模型飘了；替身返回固定序列，轨迹字字可复核。第二是**可测试**：替身让整个循环可以写单元测试——断言「第 3 步一定调用 kv_set、最终答案一定是 720.0」，这是真实模型给不了的确定性。第三是**聚焦机制**：本小节要讲的是「循环骨架怎么搭」，不是「模型怎么决策」，用替身能把注意力集中在注册表、执行闸门、记忆、停止信号这些工程部件上。更重要的是，这个替身和真实模型在接口上完全一致（都返回 `{type, tool, args}`），所以把 `propose` 换成真实调用即可上线，循环骨架零改动——这本身就证明了「机制与模型解耦」的价值。

### 面试精简表达

替身让轨迹可复现、可写测试、聚焦骨架；接口和真实模型一致，换上去就能跑。这是「机制与模型解耦」的最好证明。

## 思考：这个最小循环距离生产级 Agent 还差哪些东西？

### 回答

差不少，但骨架是对的。至少还要补五块。一是**并发与超时**：真实工具会阻塞，需要给每次执行加超时和取消。二是**可观测性**：每轮的提议、参数、结果、耗时、Token 都要落 Trace（追踪），否则线上出问题无法定位（第 7 小节展开）。三是**成本与预算控制**：要统计每轮 Token 消耗，设总预算上限，避免一个任务烧掉不合理的钱。四是**安全闸门增强**：有副作用的工具（如 `kv_set`）要接入权限校验和危险操作二次确认（第 6 小节展开），本例的执行闸门只做了白名单和必填校验，还不够。五是**记忆管理**：本例用一个无限增长的字典存所有结果，长任务下会撑爆上下文，需要第 5 章讲的压缩和裁剪。但这些都是在「五部件骨架」之上叠加的，骨架本身不变——先把骨架跑对，再逐块加固，是比「一上来就上重型框架」更稳的路径。

### 反例

有人一开始就套一个几千行的 Agent 框架，结果连「结果没写回记忆」这种基础 bug 都定位不了，因为框架把循环藏起来了。先手写一遍这个五部件循环，理解每个部件的职责，再去用框架，才知道框架帮你做了什么、哪里能改。

## 机制推导：为什么「执行闸门」必须独立于「模型提议」和「工具实现」

这个循环最容易被写崩的地方，是把三件本该分开的事揉在一起：模型怎么决策（`propose`）、参数合不合法（`execute` 里的校验）、工具具体怎么干活（`fn` 的函数体）。开头团队的散乱 `if/else` 就是三者耦合的产物——校验逻辑抄在每个分支里，改一处要改二十处，漏一处就出事故。

把执行闸门抽成独立的 `execute` 函数，带来三个可验证的好处。第一，**校验只写一遍**：所有工具调用都走同一道闸门，白名单、必填、异常兜底的逻辑集中在一处，不会因为漏抄而出现「有的工具校验了、有的没校验」的窟窿。第二，**安全边界清晰**：所有副作用都发生在 `execute` 内部、且都在校验之后，审计时只需盯住这一个函数，就能回答「什么条件下会真正写库」。第三，**可独立测试**：可以单独给 `execute` 喂各种非法输入（未知工具、缺参数、会抛异常的参数），断言它永远返回结构化结果而非崩溃——这种测试在耦合的 `if/else` 里根本没法写。

再往深一层，这三者的分离对应三种不同的「不可信程度」：`propose`（模型）是**完全不可信**的概率输出，`execute`（闸门）是**你能完全信任**的确定性代码，`fn`（工具）是**部分可信**的外部依赖（会超时、会报错）。把不同信任级别的代码物理隔开，让最不可信的输出必须穿过最可信的闸门才能触达外部依赖——这正是 README 里那道「玻璃墙」在代码层面的落地。理解了这一层，你就明白为什么本书反复强调「护栏必须落在执行层」：因为执行层是这条链上唯一你能 100% 控制的环节。
