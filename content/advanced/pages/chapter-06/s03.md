## 真实问题

一个差旅报销 Agent 上线后，客服后台每天都收到同一类投诉：「我只是想查有哪些航班，它怎么直接把票订了、还扣了款？」复盘发现，罪魁祸首是一个叫 `handle` 的工具，描述写着「处理航班相关」。模型看到「处理航班相关」，在用户说「看看明天去上海的航班」时，就把这个既能查、又能订的工具调了出来，并按自己的理解「顺手」订了票。工程师最初以为是模型太激进，想在系统提示里加一句「查询时不要订票」——治标不治本，模型仍会偶发误触。

真正的修复是把工具描述重写：拆成 `search_flights`（只查询、不预订、不产生费用）和 `book_flight`（真实扣款、不可逆、需二次确认），每个都写清「做什么、何时用、边界是什么、返回什么」。重写后，误订投诉归零。这个事故说明一件事：**工具描述不是文档注释，而是直接决定模型行为的控制信号。** 描述里的每一个字，模型都会当作决策依据。本小节讲怎么把这份「给模型看的说明书」写好。

## 原理：好描述的五个要素

从上面的对照能提炼出「好描述」的五个要素，缺一个模型就可能出错：
```text
要素            坏描述 ❌                    好描述 ✅
──────         ──────────────            ────────────────────────────
① 做什么        「处理航班相关」            「查询可预订航班列表」
② 何时用        （没写）                  「用户想比较航班/看价格时用」
③ 边界          （没写，最危险）           「只查询不预订，不产生任何费用」
④ 参数格式      「date: 日期」             「date: 出发日期，格式 YYYY-MM-DD，须为今天或未来」
⑤ 返回什么      （没写）                  「返回航班号/起飞时间/价格列表，无结果返回空列表」
```
其中**第 ③ 项「边界」最容易被忽略，却最重要**：明确告诉模型「这个工具不做什么」，能有效防止误用。开头的事故正是缺了这一项——没人告诉模型 `handle` 不该订票。第 ④ 项「参数格式」则是把第 2 小节的 `enum`、格式约束落到每个参数的描述里，让模型不用猜。

## 现象与输入：同一个工具，好坏描述差多远

把开头的对照具体化，看模型面对同一个查询请求时的两种反应：
```text
用户输入：「帮我看看明天从北京去上海的航班」

坏描述工具 handle「处理航班相关」：
  模型困惑：查询还是预订？→ 概率性地选择「顺手订票」→ 扣款投诉

好描述工具 search_flights「按出发地/目的地/日期查询，只查不订，不产生费用」：
  模型明确：这是查询请求 → 调用 search_flights → 返回航班列表，零副作用
```
描述从「模糊」变「精确」，模型行为就从「不可预测」变「可预测」。这不是玄学，而是因为模型的选择完全基于描述文本——你把边界说清了，它的选择空间就被收窄了。

## 最小可运行演示：一个工具描述「体检器」

好描述的要素可以被程序化检查。下面这个纯标准库的「体检器」按五要素给工具定义打分，帮你在上线前发现「像 `handle` 那样的坏描述」：
```python
import re


def lint_tool_desc(tool: dict) -> dict:
    """给一份工具定义打分：检查工具名、描述长度、边界声明和参数说明。"""
    name = tool.get("name", "")
    desc = tool.get("description", "")
    issues = []
    if len(name) < 3 or name in {"handle", "do", "run", "func"}:
        issues.append("工具名过短或含糊，模型难以据名选择")
    if len(desc) < 20:
        issues.append("描述过短，未说清何时用、返回什么")
    if not re.search(r"(不|仅|只|限|禁止|不会)", desc):
        issues.append("缺少边界声明，模型可能越权误用")
    props = tool.get("parameters", {}).get("properties", {})
    if any("description" not in spec for spec in props.values()):
        issues.append("存在无描述参数，模型易传错格式")
    score = max(0, 100 - 25 * len(issues))
    return {"name": name, "score": score, "issues": issues}


def main() -> None:
    bad = {
        "name": "handle",
        "description": "处理航班相关",
        "parameters": {"properties": {"date": {"type": "string"}}},
    }
    good = {
        "name": "search_flights",
        "description": "按出发地、目的地、日期查询可预订航班列表；只查询不预订，不产生费用。",
        "parameters": {"properties": {"date": {"type": "string", "description": "出发日期 YYYY-MM-DD"}}},
    }
    for tool in (bad, good):
        print(lint_tool_desc(tool))


if __name__ == "__main__":
    main()
```
保存为 `desc_linter.py`，运行 `python desc_linter.py`。预期输出：
```text
{'name': 'handle', 'score': 0, 'issues': ['工具名过短或含糊，模型难以据名选择', '描述过短，未说清何时用、返回什么', '缺少边界声明，模型可能越权误用', '存在无描述参数，模型易传错格式']}
{'name': 'search_flights', 'score': 100, 'issues': []}
```
这个体检器用的是最朴素的启发式规则（关键词、长度），生产里可以扩展成 CI（Continuous Integration，持续集成）检查，在工具合入代码库前自动拦下 0 分的坏描述。它不能替代人工评审，但能挡住「工具名叫 `handle`、描述只有五个字、参数没说明」这类低级错误——而开头的事故恰恰就是这类低级错误引发的真金白银损失。

## 参数校验：不止查「漏没漏」，还要查「对不对」

工具描述约束的是「模型该怎么传」，但描述是软约束——模型大概率遵守，不保证遵守。运行时还必须做硬校验，把「类型不对、枚举越界、数值超范围」的参数逐一拦下。下面把校验升级成「必填 + 类型 + 枚举 + 范围」四重检查，纯标准库、可直接运行：
```python
def validate_args(args: dict, spec: dict) -> str | None:
    """按参数规格 spec 校验 args。返回 None 表示通过，否则返回错误信息。"""
    for key, rule in spec.items():
        if rule.get("required") and key not in args:          # 必填检查
            return f"缺少必填参数: {key}"
        if key not in args:
            continue
        val = args[key]
        if not isinstance(val, rule["type"]):                 # 类型检查
            return f"参数 {key} 类型应为 {rule['type'].__name__}，实际 {type(val).__name__}"
        if "enum" in rule and val not in rule["enum"]:         # 枚举检查
            return f"参数 {key}={val!r} 不在允许值 {rule['enum']} 内"
        if "min" in rule and val < rule["min"]:               # 范围下界
            return f"参数 {key}={val} 小于最小值 {rule['min']}"
        if "max" in rule and val > rule["max"]:               # 范围上界
            return f"参数 {key}={val} 大于最大值 {rule['max']}"
    return None


SPEC = {
    "city": {"type": str, "required": True},
    "unit": {"type": str, "enum": ["celsius", "fahrenheit"]},
    "days": {"type": int, "min": 1, "max": 15},
}
print(validate_args({"city": "北京", "unit": "celsius", "days": 3}, SPEC))   # None（通过）
print(validate_args({"unit": "celsius"}, SPEC))                              # 缺 city
print(validate_args({"city": "北京", "unit": "kelvin"}, SPEC))               # 枚举越界
print(validate_args({"city": "北京", "days": 99}, SPEC))                     # 超范围
print(validate_args({"city": 123}, SPEC))                                    # 类型不对
```
保存为 `validate_args.py`，运行 `python validate_args.py`。预期输出：
```text
None
缺少必填参数: city
参数 unit='kelvin' 不在允许值 ['celsius', 'fahrenheit'] 内
参数 days=99 大于最大值 15
参数 city 类型应为 str，实际 int
```
这四道关卡对应模型「乱传参」的四种典型翻车姿势。一个关键心态：**这份校验不是为了「防呆用户」，而是为了「防呆模型」。** 模型的输出是概率采样的结果，再好的模型也有一定概率给出「格式合法但业务非法」的参数（比如 `days=99`）。真实项目建议直接用 `jsonschema` 或 `pydantic`，它们能一次覆盖类型、枚举、范围、正则、嵌套对象；这里手写一遍，是为了让你看清校验器内部在做什么。

## 真实系统对应

**官方公开机制**：OpenAI Function Calling 指南明确 `description` 字段用于「说明何时以及如何使用该函数」，并支持用 JSON Schema 的 `enum`、嵌套对象、递归对象等特性精确约束参数；开启 `strict: true` 会让生成的参数严格符合 Schema [来源](https://platform.openai.com/docs/guides/function-calling)。OpenAI 还提供 `namespace`（命名空间）把相关工具按 `crm`、`billing`、`shipping` 等域分组，尤其适合模型需要在服务不同系统的近义工具间做选择的场景 [来源](https://platform.openai.com/docs/guides/function-calling)。Anthropic 同样强调工具描述质量，并提供严格工具使用保证 `tool_use` 完全匹配 Schema [来源](https://docs.anthropic.com/en/docs/agents-and-tools/tool-use/overview)。

**通用工程模式**：把「好描述五要素」和「四重参数校验」当成工具上线的检查清单。**教学参考实现**：`lint_tool_desc` 的关键词启发式和 `validate_args` 的手写校验都是演示，生产应换成成熟 Schema 库并结合真实评测。

## 生产踩坑

| 症状 | 根因 | 如何观测与复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| 查询类请求被误当成写操作 | 工具描述未声明「只读/不产生副作用」边界 | 用纯查询输入，统计误触写工具比例 | 描述显式写边界；查改拆成两个工具 | 确需读写一体的工具要在执行层加确认 |
| 参数格式五花八门 | 参数缺描述与格式约束 | 打印模型 `arguments`，看格式分布 | 每个参数写格式示例，用 `enum` 收紧 | 自由文本字段不宜强约束 |
| 近义工具频繁选错 | 描述雷同，职责边界不清 | 记录候选与实际调用做混淆矩阵 | 用命名空间分组、重写差异化描述 | 功能高度重叠的工具应考虑合并 |
| 业务非法值进入下游 | 只查必填，没查范围/枚举 | 注入 `days=99` 等越界值复现 | 补类型/枚举/范围校验 | 无业务上限的字段无需范围检查 |

## 思考：工具粒度该拆还是该合？给个判断法则。

### 回答

判断法则是**按「用户心智里的一个动作」来切工具**。「查天气」是一个动作，就是一个工具；「查天气 + 顺便改闹钟」是两个动作，就拆成两个工具。拆分的好处是语义清晰、模型好选、权限可细粒度控制、失败影响面小；代价是可能多轮调用、工具列表变长。合并的好处是减少调用轮次，但描述会变复杂、模型易混淆、权限只能一刀切、还违反单一职责难以测试。关键的安全维度是：**读操作和写操作、可逆和不可逆操作一定要拆开**，因为它们的权限和确认策略完全不同——开头的 `handle` 事故就是把「查询」和「预订扣款」合在一个工具里酿成的。

### 面试精简表达

按用户心智的一个动作切；读写必分家，可逆和不可逆必分家。拆到「模型不会因为选错而产生意外副作用」为止。

## 思考：描述写得越详细越好吗？

### 回答

不是，存在明显的边际递减甚至反效果。描述是 prompt 的一部分，每个字都消耗输入 Token，工具一多，冗长描述会显著抬高每轮成本；过长的描述还可能稀释关键信息，让模型抓不住重点。好的描述追求「信息密度」而非「字数」：用最少的字说清做什么、何时用、边界、参数格式、返回什么。经验做法是把「模型选择和传参必需的信息」放进 description，把「实现细节、内部逻辑、运维说明」留在代码注释里——后者模型根本看不到，写进描述纯属浪费 Token。

### 反例

把「本函数先查 Redis 缓存、命中率约 80%、未命中回源气象局、超时重试三次」写进 description 毫无意义：这些是实现细节，模型既用不上、又白烧 Token。模型只需要知道「查实时天气、只读、传城市名和单位枚举」。

## 命名空间与工具分组：当工具变多时

当一个 Agent 需要接入几十个工具时，扁平地平铺所有描述会带来两个问题：模型在近义工具间选错的概率上升，输入 Token 也随工具数线性增长。OpenAI 公开的 `namespace` 机制正是为此设计——把工具按业务域分组（如 `crm` 下放 `get_customer_profile`、`list_open_orders`），帮助模型在「服务不同系统的近义工具」之间做区分 [来源](https://platform.openai.com/docs/guides/function-calling)。这背后的通用工程直觉是：**先让模型在粗粒度的「域」上收敛，再在域内选具体工具**，类似人类先想「这是查客户还是查订单的事」，再选具体接口。

分组只是「组织与选择」层面的优化，不改变权限边界。即使某个高权限工具和低权限工具被放在同一个命名空间里，执行层仍必须对每个工具单独鉴权——命名空间让描述更好组织、让模型更好选择，但它不是授权机制。第 4 小节会进一步讨论「工具太多」时的动态裁剪与路由策略，第 6 小节则讲清「可见工具」和「可执行能力」为什么必须分开记录。

## 事故回放：一次「参数描述缺失」导致的批量退款

某票务平台的 `refund_order`（退款）工具，参数里有个 `amount`（退款金额），描述只写了「退款金额」，没写单位，也没写「不能超过原订单金额」。一次促销后，用户对一张 199 元的票申请「退我 1.99」——他想说的是「退 1.99 元的手续费差额」，模型却把 `amount` 理解成「退 1.99」并按「元」传了 `1.99`，结果只退了 1 元 9 角 9 分，用户投诉；另一个用户说「全退」，模型传了 `amount=19900`（误按「分」为单位），触发了超额退款拦截才没酿成资损。两个方向的错，根因都是同一个：`amount` 的描述没说清单位和上下界。

修复方式是把参数描述改成「退款金额，单位：元，最多两位小数，不得超过原订单实付金额」，并在执行层补一道范围校验：`0 < amount <= order.paid_amount`。改完之后，模型传参的歧义消失，执行层还兜住了万一模型仍传错的情况。这个案例把本小节两个主题连了起来——**描述负责减少模型出错的概率，执行层校验负责在模型仍然出错时兜底**，两者缺一不可。只把希望寄托在「把描述写清模型就不会错」上，仍然会在小概率事件里翻车；只做执行层校验而描述含糊，则会让模型频繁触发校验失败、反复重试、体验和成本双输。
