## 真实问题

一位后端工程师第一次接 Function Calling（函数调用）时踩了个典型的坑：他给模型注册了一个 `get_weather` 函数，函数体里写了详尽的中文注释解释「这个函数会先查缓存、缓存没有再调气象局接口、超时重试三次」，然后满心期待模型能「理解」这些逻辑并聪明地调用。结果模型频繁把 `unit` 参数传成 `"摄氏度"` 而不是接口要的 `"c"`，还偶尔编造出一个根本不存在的 `region` 参数。他百思不得其解：「注释写得那么清楚，模型怎么还不懂？」

答案戳破了一个普遍误解：**模型从来看不到你的函数体，也看不到你的注释。** 框架发给模型的，只是一份由「函数名 + 描述 + 参数 JSON（JavaScript Object Notation）Schema」组成的「说明书」。模型对这个工具的全部认知都来自这份说明书；函数体写得再优雅、注释再详尽，模型也一无所知。他写的中文注释在函数体里，压根没进 Schema，自然形同虚设。理解「模型到底看到了什么」，是用对 Function Calling 的第一步。

## 原理：一个工具在模型眼里的三要素

对模型而言，一个工具由三部分定义，缺一不可：
```text
┌──────────────────────────────────────────────┐
│  ① 名称     get_weather                        │
│  ② 描述     查询指定城市的实时天气；只读，不产生费用 │
│  ③ 参数 Schema (JSON):                          │
│     {                                          │
│       "city": {"type": "string"},              │
│       "unit": {"type": "string",               │
│                "enum": ["celsius","fahrenheit"]}│
│     }, "required": ["city"]                     │
└──────────────────────────────────────────────┘
```
三者各司其职：**名称**是模型选工具的第一依据；**描述**决定模型判断「什么情况下该用它」，写得好不好直接影响用得对不对；**参数 Schema** 约束模型传参的结构，让输出可被程序稳定解析。这三部分合起来就是一份「给模型看的 API 文档」。Anthropic 在《Building effective agents》里把「精心设计 Agent-Computer Interface（ACI，智能体-计算机接口）」列为核心原则，主张像打磨 prompt 一样反复打磨工具的文档与描述 [来源](https://www.anthropic.com/engineering/building-effective-agents)。

关键结论一句话：**工具描述本身就是 prompt 的一部分，会消耗输入 Token（词元），也会影响模型的选择准确率。** Anthropic 官方甚至公开了不同模型开启工具后额外注入的「工具使用系统提示」Token 数（随模型版本变化，以当前文档为准），从侧面印证工具定义确实进入了模型的输入 [来源](https://docs.anthropic.com/en/docs/agents-and-tools/tool-use/overview)。

## 从函数到 Schema：模型实际收到的是什么

框架把你的函数签名、文档字符串（docstring）和类型注解，自动翻译成一份 JSON Schema，再塞进发给模型的请求里。模型看到的从来不是函数体，而是这份说明书：
```text
你写的 Python 函数                     模型实际收到的 JSON Schema
──────────────────                    ──────────────────────────────
def get_weather(                       {
    city: str,          ──翻译──▶        "name": "get_weather",
    unit=... ):                          "description": "查询城市实时天气",
    """查询城市实时天气"""                  "parameters": {
    return ...  ← 函数体不可见              "type": "object",
                                          "properties": {
    # 你的中文注释                          "city": {"type": "string"},
    # 也不可见                             "unit": {"enum": ["celsius","fahrenheit"]}
                                          },
                                          "required": ["city"] } }
```
这解释了开头工程师的困惑：他的中文注释在函数体里，没进 Schema，模型看不见；他没给 `unit` 加 `enum` 约束，模型就自由发挥传了「摄氏度」。**函数名和 docstring 会一字不差地暴露给模型**，所以别用 `func1`、`do_stuff` 这种名字，也别把 docstring 留空——第 3 小节会专门讲怎么写好这份说明书。

## 最小可运行演示：手写「函数 → Schema」翻译器

下面用纯标准库实现「从带类型注解和 docstring 的函数自动生成 Schema」的最小逻辑，帮你看清框架背后到底在做什么。它还支持 `typing.Literal` 生成 `enum`，并对齐 OpenAI 官方示例里 `strict: true` + `additionalProperties: false` 的写法 [来源](https://platform.openai.com/docs/guides/function-calling)。
```python
import inspect
import json
import typing


def get_weather(city: str, unit: typing.Literal["celsius", "fahrenheit"] = "celsius") -> str:
    """查询指定城市的实时天气；只读查询，不产生任何费用。"""
    return f"{city} 15 度 晴"


TYPE_MAP = {str: "string", int: "integer", float: "number", bool: "boolean"}


def build_schema(func) -> dict:
    """把带类型注解和文档字符串的函数，翻译成模型可见的工具 Schema。"""
    sig = inspect.signature(func)
    props: dict = {}
    required: list = []
    for name, param in sig.parameters.items():
        ann = param.annotation
        if typing.get_origin(ann) is typing.Literal:      # 标注A：Literal -> enum
            props[name] = {"type": "string", "enum": list(typing.get_args(ann))}
        else:
            props[name] = {"type": TYPE_MAP.get(ann, "string")}
        if param.default is inspect.Parameter.empty:       # 标注B：无默认值 -> 必填
            required.append(name)
    return {
        "type": "function",
        "name": func.__name__,                             # 标注C：函数名 -> 工具名
        "description": (func.__doc__ or "").strip(),       # 标注D：docstring -> 描述
        "parameters": {
            "type": "object",
            "properties": props,
            "required": required,
            "additionalProperties": False,                 # 标注E：strict 模式要求
        },
        "strict": True,
    }


def main() -> None:
    print(json.dumps(build_schema(get_weather), ensure_ascii=False, indent=2))


if __name__ == "__main__":
    main()
```
保存为 `func_to_schema.py`，运行 `python func_to_schema.py`。预期输出：
```text
{
  "type": "function",
  "name": "get_weather",
  "description": "查询指定城市的实时天气；只读查询，不产生任何费用。",
  "parameters": {
    "type": "object",
    "properties": {
      "city": {
        "type": "string"
      },
      "unit": {
        "type": "string",
        "enum": [
          "celsius",
          "fahrenheit"
        ]
      }
    },
    "required": [
      "city"
    ],
    "additionalProperties": false
  },
  "strict": true
}
```
逐点讲解：**标注 A** 把 `Literal["celsius","fahrenheit"]` 翻译成 `enum`——这是给模型最强的取值约束，开头那个「摄氏度」的坑就是因为没加它。**标注 B** 判断参数有没有默认值，没有的进 `required`。**标注 C/D** 印证「函数名和 docstring 会一字不差暴露给模型」。**标注 E** 的 `additionalProperties: false` 是 OpenAI `strict` 模式的硬性要求之一，它禁止模型塞进 Schema 之外的字段（比如开头那个幻觉出来的 `region`）。这份输出正是 OpenAI SDK（Software Development Kit，软件开发工具包）、PydanticAI 等框架在背后帮你自动生成的东西。

## 黄金原则：模型提议，运行时处置

这是整章、乃至整本书最重要的一条原则：

> **模型不会、也不能真正执行工具。它只是「提议」调用哪个工具、传什么参数；真正的执行发生在你的代码（运行时）里。所有副作用——网络请求、数据库写入、扣款——都在你这一侧发生。**

OpenAI 把这条原则显式画成了五步流程 [来源](https://platform.openai.com/docs/guides/function-calling)：
```text
1. 你把工具定义（名称+描述+Schema）连同用户问题发给模型
2. 模型判断需要用工具，返回一个「调用请求」：
      { "name": "get_weather", "arguments": {"city": "北京", "unit": "celsius"} }
   —— 注意：此时什么都还没发生，模型只是「提议」
3. 你的运行时代码：解析 arguments → 校验 → 真正调用 get_weather(...) → 得到结果
4. 你把工具结果（tool call output）回传给模型
5. 模型基于结果生成最终回答，或继续提议下一个工具调用
```
Anthropic 的机制在字段命名上不同但内核一致：模型返回 `stop_reason: "tool_use"` 和一个或多个 `tool_use` 块，你的代码执行后，把结果放进 `tool_result` 块发回，模型据此继续 [来源](https://docs.anthropic.com/en/docs/agents-and-tools/tool-use/overview)。无论字段怎么叫，「模型提议、运行时执行」这条边界都不变。

## 真实系统对应

**官方公开机制**：OpenAI 用 `tools`（含 `type/name/description/parameters/strict`）声明函数，模型回传 `function_call`（含 `name` 与 `arguments` 字符串），你执行后以 `function_call_output`（带 `call_id`）回传 [来源](https://platform.openai.com/docs/guides/function-calling)。Anthropic 用带 `input_schema` 的 `tools` 声明，模型回 `tool_use`（带 `id`、`name`、`input`），你回 `tool_result`（带 `tool_use_id`）；`tool_choice` 默认 `auto`，可设为强制调用 [来源](https://docs.anthropic.com/en/docs/agents-and-tools/tool-use/overview)。两家都提供 `strict`/严格工具使用来保证参数严格符合 Schema。

**通用工程模式**：无论用哪家 SDK，都建议在解析 `arguments` 后、真正执行前插入一层「白名单 + 参数校验」，因为模型返回的 `arguments` 是概率生成的字符串，可能是非法 JSON 或越界值。**教学参考实现**：上面的 `build_schema` 只演示翻译逻辑，真实项目应直接用 `pydantic`/`jsonschema` 或框架自带的 Schema 生成，覆盖嵌套对象、正则、递归等复杂情形。

## 生产踩坑

| 症状 | 根因 | 如何观测与复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| 模型传参格式对不上接口 | 参数缺 `enum`/描述，靠自由发挥 | 打印模型返回的 `arguments` 原文 | 用 `enum` 收紧取值，加参数描述 | 天然自由文本字段不宜强枚举 |
| 模型编造 Schema 外的参数 | 未开严格模式 | 注入含额外字段的场景复现 | 开 `strict`/`additionalProperties:false` | 需要开放字段的极少数场景除外 |
| `arguments` 解析报错 | 模型偶发返回非法 JSON | 记录原始字符串，重放解析 | 用容错解析 + 失败重试/回退 | 结构化输出稳定后可简化 |
| 改了函数体模型行为没变 | 误以为模型能看到函数体 | 只改函数体不改描述，观察无变化 | 把关键信息写进 description 与 Schema | 函数体只影响执行，不影响模型认知 |

## 思考：为什么说「工具描述是 prompt 的一部分」？写不好会怎样？

### 回答

因为框架把工具的名称、描述和参数 Schema 一起拼进了发给模型的请求，它们和系统提示、用户消息一样占据输入上下文、消耗 Token，并直接参与模型的决策。模型对工具的全部认知都来自这份文本说明书——它看不到函数体。写不好有三个后果：一是**选错工具**（描述含糊，模型分不清两个近义工具）；二是**传错参数**（缺 `enum`/描述，模型自由发挥出非法值）；三是**成本上升**（描述冗长、工具过多，每轮都白白消耗大量输入 Token）。所以工具描述要像 prompt 一样反复打磨，这也是 Anthropic ACI 原则的核心。

### 面试精简表达

模型看到的是「说明书」不是「函数体」。说明书就是 prompt，字字都在影响模型选哪个、怎么传参、花多少 Token。

## 思考：OpenAI 和 Anthropic 的工具调用机制，本质差别大吗？

### 回答

字段命名不同，内核一致。OpenAI 用 `tools`/`function_call`/`function_call_output`，Anthropic 用 `tools(input_schema)`/`tool_use`/`tool_result`；OpenAI 用 `stop`/`tool_calls` 分辨是否要执行工具，Anthropic 用 `stop_reason: "tool_use"`。但两家都遵循同一条黄金原则——模型只返回结构化的「提议」，执行由你的代码完成，结果再回传。两家也都提供了严格模式（`strict`）来保证参数符合 Schema。因此掌握机制远比记住字段名重要：换 SDK 时，只需把「提议解析、执行、结果回传」这三个接缝对上新字段即可，中间的校验闸门完全复用。

### 反例

有人以为「换厂商要重写整个 Agent」，其实需要改的只是适配层的字段映射；如果连黄金原则都要重新理解，说明当初就没真正理解机制，只是记住了某一家的字段拼写。

## 机制推导：多轮调用如何收敛

单次调用只是骨架，真实 Agent 往往需要多轮：模型提议工具 A，拿到结果后可能再提议工具 B，直到它认为信息足够、不再需要工具，才输出最终文本。这个循环靠一个明确的「停止信号」收敛——OpenAI 看本轮响应里是否还有 `tool_calls`/`function_call`，Anthropic 看 `stop_reason` 是否仍为 `tool_use`。只要还有提议，运行时就继续「执行→回传」；一旦模型返回普通文本（`stop_reason` 变为 `end_turn` 之类），循环结束。

这个收敛逻辑有两个必须由运行时守住的边界。第一是**轮数上限**：模型可能陷入「反复调用同一个工具」的死循环，运行时必须设最大轮数，超过就强制停止并返回结构化失败，而不是无限烧钱。第二是**结果回传的完整性**：每个 `tool_result`/`function_call_output` 必须带上对应的 `id`/`call_id`，把结果和提议一一对应；漏传或错配会让模型「找不到自己刚才的提议对应什么结果」，从而胡乱作答。第 5 小节会把这套多轮循环用纯 Python 完整实现出来，你能亲眼看到它一步步收敛到最终答案，也能看到轮数上限如何兜底。

Anthropic 还公开了并行工具调用与 `disable_parallel_tool_use` 开关：默认模型可能在一轮里同时提议多个工具，若你希望「每轮至多一个工具调用」以简化执行和调试，可显式关闭并行 [来源](https://docs.anthropic.com/en/docs/agents-and-tools/tool-use/overview)。是否并行是工程权衡：并行省往返、提吞吐，但让执行顺序和错误归因变复杂；串行慢一点，却更好观测和复现。
