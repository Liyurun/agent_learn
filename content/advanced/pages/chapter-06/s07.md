## 真实问题

线上工单写着「Agent 工具用不好」，但这句话无法行动。它可能是选错工具、可能是传参非法、可能是工具本身超时、可能是重试造成了重复副作用，也可能是被提示注入诱导做了越权操作。工具层的生产诊断，第一步永远是**把模糊现象拆成可观测、可复现的具体故障**——保存那一轮真实的请求快照（暴露了哪些工具、模型提议了什么、传了什么参、执行返回了什么、停止原因是什么），再按类别分层排查，而不是一上来就「换个更强的模型」或「把 prompt 再改改」。

本小节把前六节的知识收敛成一张可操作的诊断流程、两张覆盖十余种典型故障的生产建议表，以及一组高频「思考+回答」。它是全章的落地页：读完前面理解了机制，这里给你上生产时真正会用到的排查手册。

## 诊断顺序

面对一个工具层故障，按这个顺序走，能最快把范围收敛到根因：

1. **复现**：固定任务、模型版本、温度、本轮暴露的工具集快照、数据版本，先让故障可稳定重放。
2. **看提议**：模型提议的工具名在白名单里吗？（幻觉工具名）选的是不是该选的那个？（选错工具）
3. **看传参**：`arguments` 是合法 JSON（JavaScript Object Notation）吗？类型、枚举、范围合规吗？（传参非法）
4. **看执行**：工具执行是成功、超时、还是抛异常？返回的错误信息模型读得懂吗？（执行失败与反馈质量）
5. **看副作用**：写操作实际执行了几次？和预期一致吗？（重复副作用/幂等）
6. **看循环**：是否有轮数上限？是否陷入反复调用同一工具？（不收敛）
7. **看安全**：这次调用有没有越权？是否可能被上下文里的不可信内容诱导？（注入与权限）
8. **比基线**：同一输入在固定模型上多次运行，选择和传参稳定吗？（区分「设计问题」与「模型抖动」）

## 最小可运行演示：工具层故障诊断路由器

把上面的诊断顺序写成一个确定性的路由器，输入可观测信号，输出首要动作。它不替代基于 Trace（追踪）的根因分析，但能在值班时快速缩小范围：
```python
def diagnose(signals: dict) -> str:
    """按可观测信号把「工具层出问题」路由到具体故障类别与首要动作。"""
    if signals.get("unknown_tool_name"):
        return "幻觉工具名：执行层加白名单，低置信不自动纠正，回传候选让模型重选"
    if signals.get("arg_schema_invalid"):
        return "传参非法：补 enum/类型/范围校验，返回结构化 hint 让模型改参"
    if signals.get("side_effect_count", 0) > signals.get("expected_side_effect", 0):
        return "重复副作用：非幂等写操作引入幂等键，重试前先去重"
    if signals.get("retry_no_limit"):
        return "重试失控：设 max_retry + 指数退避 + 超时"
    if signals.get("tool_selected") != signals.get("tool_expected"):
        return "工具选错：重写差异化描述、命名空间分组、动态裁剪工具集"
    return "未命中已知模式：保存请求快照与 Trace，做固定输入消融"


def main() -> None:
    print(diagnose({"unknown_tool_name": True}))
    print(diagnose({"arg_schema_invalid": True}))
    print(diagnose({"side_effect_count": 7, "expected_side_effect": 1}))
    print(diagnose({"retry_no_limit": True}))
    print(diagnose({"tool_selected": "search_reports", "tool_expected": "get_refund_status"}))
    print(diagnose({"tool_selected": "x", "tool_expected": "x"}))


if __name__ == "__main__":
    main()
```
保存为 `tool_diagnose.py`，运行 `python tool_diagnose.py`。预期输出：
```text
幻觉工具名：执行层加白名单，低置信不自动纠正，回传候选让模型重选
传参非法：补 enum/类型/范围校验，返回结构化 hint 让模型改参
重复副作用：非幂等写操作引入幂等键，重试前先去重
重试失控：设 max_retry + 指数退避 + 超时
工具选错：重写差异化描述、命名空间分组、动态裁剪工具集
未命中已知模式：保存请求快照与 Trace，做固定输入消融
```
规则的顺序有讲究：先查「幻觉/传参」这类每轮都能拦下的确定性问题，再查「重复副作用」这类会造成资损的高危问题，最后才落到「选错工具」这类需要重写描述的软问题；全都不命中，才进入基于 Trace 的消融实验。这个路由器是把「诊断顺序」代码化，方便在值班脚本里复用。

## 生产建议表（一）：调用正确性与错误处理

| 症状 | 根因 | 如何观测与复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| 模型调用不存在的工具致崩溃 | 运行时未做白名单，裸 `KeyError` 上抛 | 注入幻觉工具名，观察是否崩溃 | 执行前查注册表，低置信不自动纠正，回传候选 | 白名单外一律拒绝，不猜测 |
| 传参格式对不上接口 | 参数缺 `enum`/描述，模型自由发挥 | 打印模型 `arguments` 原文看分布 | 用 `enum`/类型/范围收紧，加参数描述 | 天然自由文本字段不宜强枚举 |
| 业务非法值进入下游 | 只查必填，没查范围与枚举 | 注入 `days=99` 等越界值复现 | 执行层补类型/枚举/范围四重校验 | 无业务上限字段无需范围检查 |
| 工具失败后模型反复犯同样错 | 错误信息是裸栈，无修复建议 | 回放失败轮，看模型是否纠正 | 返回结构化 `{ok:false, error, hint}` | 不可恢复错误应直接终止上报 |
| 改了函数体模型行为没变 | 误以为模型能看到函数体 | 只改函数体不改描述，观察无变化 | 关键信息写进 description 与 Schema | 函数体只影响执行不影响模型认知 |
| `arguments` 偶发解析报错 | 模型偶发返回非法 JSON | 记录原始字符串重放解析 | 容错解析 + 失败重试/回退 | 严格模式稳定后可简化 |
| 近义工具频繁选错 | 工具过多、描述雷同 | 记录候选与实际调用做混淆矩阵 | 差异化描述、命名空间分组、动态裁剪 | 功能重叠工具应合并而非硬分 |

## 生产建议表（二）：循环、副作用、安全与可观测

| 症状 | 根因 | 如何观测与复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| 最终答案引用了没算过的值 | 某步结果没写回记忆 | 打印每轮 memory 快照复现 | 循环里强制「执行成功即写记忆」 | 无状态依赖的单步调用无需记忆 |
| Agent 陷入无限调用同一工具 | 缺轮数上限或明确停止信号 | 让替身永远返回 tool_use 复现 | 设 `max_turns`，识别明确 final 信号 | 长任务可调高上限但不能取消 |
| 重试导致重复扣款/发消息 | 非幂等写操作直接重试 | 注入超时后统计副作用次数 | 写操作引入幂等键 + 提交检查点 | 幂等只读操作重试安全 |
| 重试把成本和延迟拖爆 | 无重试上限或退避 | 注入持续失败依赖看调用次数 | `max_retry` + 指数退避 + 超时 | 非幂等写重试前必须去重 |
| 系统提示护栏被注入绕过 | 权限寄托在 prompt 软约束 | 用「忽略指令」类注入复现 | 权限/鉴权/确认改为执行层硬编码 | prompt 提示可作第二道防线 |
| 外部内容诱导 Agent 泄露数据 | 踩中致命三要素三项齐备 | 在可读文档植入注入指令复现 | 打破任一环：隔离外发或限私有数据 | 纯本地可信数据场景风险较低 |
| 高危操作被静默执行 | 缺执行层二次确认 | 直接调用 danger 级工具复现 | danger 级强制 confirmed 才放行 | 只读工具无需确认避免打扰 |
| 查询工具持有过大权限令牌 | 未按最小 scope 签发凭据 | 审计工具实际使用权限范围 | 按工具最小 scope 单独签发密钥 | 确需宽权限运维工具单独审批 |
| 换更大模型工具还是用不好 | 把「设计问题」当「模型能力问题」 | 固定输入对比不同模型选择分布 | 先修描述/路由/校验，再谈换模型 | 极端复杂域可能确需更强模型 |
| 线上出问题无法定位 | 只存最终答案，不存工具轨迹 | 复盘时发现没有中间记录 | 每轮落 Trace：提议/参数/结果/耗时/Token | 隐私要求可能限制原文留存需脱敏 |

两张表合计 17 行，覆盖了从「调用正确性」到「安全与可观测」的主要故障面。它们共享同一个方法论：每个故障都要能被**观测**（有指标或日志）、能被**复现**（有明确输入）、有**执行层的修复**（而非只靠调 prompt），并且清楚它的**不适用边界**（避免把修复当银弹到处套）。

## 思考：面试官问「你怎么保证工具调用的可靠性」，怎么答？

### 回答

分四层答，每层都落到可验证的机制上。第一层**输入可信化**：工具描述写清做什么/何时用/边界/参数格式/返回什么，用 `enum` 和严格模式收紧参数，让模型少犯错。第二层**执行层硬校验**：白名单挡幻觉工具名，四重参数校验（必填/类型/枚举/范围）挡非法值，所有副作用只在通过校验后发生。第三层**失败可恢复**：工具失败返回结构化 `{ok, error, hint}` 而非裸栈，让模型能自愈；重试带上限和退避；非幂等写操作用幂等键。第四层**安全兜底**：权限和危险操作确认写在执行层而非 prompt，按最小权限签发凭据，用致命三要素审计工具组合。最后强调**可观测**：每轮落 Trace，出问题能按诊断顺序快速定位。核心一句话——可靠性不是靠更强的模型，而是靠「把模型输出当不可信输入，用确定性代码兜住每一种失败」。

### 面试精简表达

描述收紧输入，执行层硬校验挡住非法调用，结构化错误让模型自愈，安全护栏落在代码，全程可观测。可靠性来自工程而非模型。

## 思考：工具调用出问题，第一反应该是调 prompt 还是查代码？

### 回答

先查代码和数据，最后才考虑调 prompt。原因是：工具层的多数故障——幻觉工具名崩溃、传参越界、重复扣款、越权执行——都是**运行时没兜住**造成的，改 prompt 治标不治本，且 prompt 改动难以回归、容易按下葫芦浮起瓢。正确顺序是先保存请求快照按诊断流程定位：如果是崩溃或资损，几乎一定是执行层缺校验/缺幂等/缺鉴权，该补代码；如果是「选错近义工具」，才可能需要重写描述（这也算「代码」层面的工具定义，而非系统 prompt）；只有当确认是「模型在信息充分、工具设计合理时仍频繁误判」，才轮到考虑调整提示或换模型。把「调 prompt」当第一反应，是很多团队在工具层反复踩坑的根源——它让确定性问题被非确定性手段掩盖。

### 反例

线上出现「重复扣款」时去系统提示里加一句「不要重复扣款」，是典型的错误第一反应——重复扣款是重试逻辑和幂等缺失造成的，与模型是否「想」重复扣款无关，加 prompt 完全无效。

## 思考：怎么判断该给 Agent 加工具，还是该优化现有工具？

### 回答

先诊断当前故障属于「能力缺失」还是「能力用不好」。如果任务本就需要一个现在没有的动作（比如需要查实时汇率但没有汇率工具），那是能力缺失，该加工具。如果工具已经有、但模型选错/传错/用错，那是能力用不好，加工具只会让工具列表更长、选择更难，是反向操作——该做的是优化：重写差异化描述、拆分职责不清的工具、补参数校验、做命名空间分组。一个常见误区是「模型没做好某件事，就再加一个工具去补」，结果工具越加越多，选择困难和 Token 成本双双上升。判断法则：**先让现有工具的每一个都「描述清晰、职责单一、校验完备」，再考虑是否真的缺一个新动作。** 加工具是扩展能力边界，优化工具是提升现有能力的可用性，二者解决的是不同问题。

### 面试精简表达

缺动作才加工具，用不好则优化工具。别用「加工具」去修「用不好」，那只会让选择更难、成本更高。

## 思考：本章的工具工程方法，怎么和第 5 章记忆、第 7 章反思衔接？

### 回答

三者是一条链。**工具（第 6 章）**负责让 Agent 能感知和改变外部世界，产出结构化的观测结果；**记忆（第 5 章）**负责把这些工具调用的结果、状态、历史串起来，让多轮调用不「失忆」——本章调用循环里的 `memory` 字典就是最小的短期记忆；**反思（第 7 章）**则依赖工具返回的结构化错误信号来评价「上一步做得对不对、下一步怎么改」——本章反复强调的「结构化 error + hint」正是反思的输入前提，没有好的反馈信号，反思就是闭门造车。所以工具工程做得好不好，直接决定了记忆里存的是不是干净可用的状态、反思拿到的是不是可操作的信号。三章合起来，才构成一个「能感知、能记住、能改进」的完整 Agent 内核。

### 面试精简表达

工具产出观测与结构化反馈，记忆把它们串成状态，反思据反馈改进。工具是这条链的起点，反馈质量决定后两者的上限。

## 生产落地清单：从 Demo 到上线要补的十件事

把前面所有小节的要点收敛成一张上线前的检查清单，逐项核对能避开绝大多数工具层事故：

第一，**每个工具描述过一遍五要素体检**（做什么/何时用/边界/参数格式/返回什么），坏描述在合入代码库前就拦下。第二，**执行层白名单 + 四重参数校验**全覆盖，任何工具调用都必须穿过这道闸门。第三，**所有工具失败返回结构化结果**（`{ok, error, hint}`），杜绝裸 traceback 回传上下文。第四，**调用循环设轮数上限**，识别明确的停止信号，防止无限打转。第五，**非幂等写操作全部引入幂等键**，重试前去重，重试带上限和指数退避。第六，**危险操作在执行层强制二次确认**，权限用 RBAC 按最小权限控制，绝不把护栏只写在 prompt 里。第七，**用致命三要素审计每个 Agent 的工具组合**，处理不可信内容的 Agent 不给无限制外发能力。第八，**工具用的凭据按最小 scope 单独签发**，查询工具不持有写权限令牌。第九，**每轮落 Trace**：本轮暴露的工具集、模型提议、传参原文、执行结果与错误、副作用次数、停止原因、Token 与延迟，出问题能按诊断顺序定位。第十，**建端到端评估集**：用真实失败样本做回归，衡量「任务成功率、工具选对率、传参合规率、越权拦截率」，而不只看「调用了几次工具」。

这十件事没有一件依赖「更强的模型」，全都是确定性的工程动作。它们的共同哲学贯穿全章——**把模型的每一个输出都当作不可信输入，用你能 100% 控制的执行层代码，兜住每一种可预见的失败。** 这就是从「能跑的 Demo」到「敢上生产的 Agent」之间，那段最不性感、却最决定成败的距离。
