## 真实问题

某跨境电商的客服 Agent 在 2026 年春节大促期间上线，第一周就收到一条投诉：用户问「我这笔 89.9 美元的订单，按今天汇率折合多少人民币？我要不要现在付」，Agent 回答「大约 640 元人民币，建议尽快支付」。用户照做，结果实际扣款 647 元。差的这 7 元，来自模型的「心算」——它没有调用任何汇率接口，而是凭训练时的模糊印象「估」了一个数。更糟的是，当天汇率其实是 7.23，模型记得的却是几个月前的旧数。

问题不在于「模型不够聪明」，而在于它被要求做两件它天生做不好的事：一是获取「训练截止之后才存在」的实时汇率，二是做「必须精确」的乘法。这两件事都应该外包给工具，而不是让模型「猜」。团队后来接入了一个 `get_fx_rate` 工具和一个 `multiply` 工具，同样的问题再没出现——不是换了模型，而是让模型「只负责决定用哪个工具」，把「取数」和「算数」交给确定性的代码。

## 原理：纯 LLM 的三块短板

要理解工具的价值，先要看清纯大语言模型（Large Language Model，LLM）天生缺什么。Lilian Weng 在《LLM Powered Autonomous Agents》中把 Tool Use（工具使用）列为自主 Agent 的三大核心组件之一，指出工具使用极大扩展了模型的能力边界，让模型可以调用外部 API 获取训练数据里没有的、实时或专有的信息 [来源](https://lilianweng.github.io/posts/2023-06-23-agent/)。把这层价值拆开，工具恰好补上三块短板：
```text
纯 LLM 的三块短板              工具如何补齐                    案例中的体现
────────────────            ────────────────────         ─────────────────
① 知识冻结在训练时刻    →    联网 / 查库，取实时信息        汇率是训练后才变的
② 不会精确计算          →    调用计算器 / 代码，杜绝算错    89.9 × 7.23 必须精确
③ 只能输出文字，无副作用 →   调用 API 执行动作             真正下单、扣款、发货
```
这三块短板可以归成两大类。前两者是**认知增强**：让答案更准、更新、更专有；第三者是**行动赋能**：让 Agent 能真正改变外部世界的状态。给 Agent 设计工具前，先想清楚你要补的是哪一块——很多人一上来就想给模型「联网」，却忽略了「精确计算」这块更隐蔽、也更容易出事的短板。

## 现象与输入：为什么「心算」一定会翻车

模型生成数字的本质是「按概率采样下一个 token（词元）」，它没有一个内置的算术单元。位数少、进位简单时，训练语料里见过的组合足够多，蒙对的概率很高；位数一多、进位一复杂，它就会给出一个「长度对、前几位也像、但中间某几位错」的数字。这类错误极其隐蔽，因为它看起来非常「合理」，不像随机乱码那样一眼可辨。
```text
输入：请计算 9137 × 7823
纯模型可能输出：71458751   （长度 8 位，看着很对）
确定性工具输出：71478751   （真实答案）
差异：中间第 4 位 5→7，静默出错，无任何报警
```
这就是为什么「需要精确、确定性结果」的任务必须外包给工具：不是模型「偶尔」会错，而是它从原理上就无法保证精确。

## 最小可运行演示

下面用一段纯标准库代码，把「模型口算」和「工具计算」的差异摆在一起。为避免真的调用大模型，这里用一张固定表模拟模型那种「确定性地算错」的行为——关键在于对照，而非制造随机性。
```python
def model_guess_multiply(a: int, b: int) -> str:
    """模拟纯语言模型对大数乘法的概率式作答：会生成一个看似合理、位数也对，
    但某几位是错的数字。这里用一张固定表模拟这种确定性的错误。"""
    table = {(9137, 7823): "71458751"}
    return table.get((a, b), "无预置样本")


def calculator_multiply(a: int, b: int) -> int:
    """确定性工具：调用真实运算，结果永远精确。"""
    return a * b


def main() -> None:
    a, b = 9137, 7823
    guess = model_guess_multiply(a, b)
    truth = calculator_multiply(a, b)
    print("模型口算：", guess)
    print("工具计算：", truth)
    print("是否一致：", guess == str(truth))
    print("结论：口算是概率生成，工具是确定性执行")


if __name__ == "__main__":
    main()
```
保存为 `only_talk.py`，运行 `python only_talk.py`。预期输出：
```text
模型口算： 71458751
工具计算： 71478751
是否一致： False
结论：口算是概率生成，工具是确定性执行
```
这段代码的意义不在于「证明模型会算错」——真实模型未必每次错在这一位——而在于说明一个工程决策：**凡是要求精确、可复现、可审计的计算，都不该让模型直接产出，而应交给确定性工具。** 把「决定何时算、算什么」留给模型，把「怎么算得对」交给代码，这就是工具分工的核心思想。

## 真实系统对应

**官方公开机制**：OpenAI 的 Function Calling 指南把工具能力举例为「获取某地天气」「按用户 ID 查账户」「为丢失的订单发起退款」等——全都是模型无法凭训练数据独立完成、必须借助外部系统的动作 [来源](https://platform.openai.com/docs/guides/function-calling)。Anthropic 的 Tool use 文档也明确：默认 `tool_choice` 为 `auto` 时，模型在「请求映射到某工具能力，且答案不在上下文里」时才调用工具，对稳定知识、创意任务和闲聊则直接回答 [来源](https://docs.anthropic.com/en/docs/agents-and-tools/tool-use/overview)。这条边界说明厂商也认同「不是所有问题都要用工具」。

**通用工程模式**：把任务先分类——「取实时/专有数据」「做精确计算」「产生副作用」三类交给工具，「常识问答/改写/总结」留给模型。**教学参考实现**：上面的 `model_guess_multiply` 只是演示，不代表任何真实模型某次一定会算出 `71458751`。

## 生产踩坑

| 症状 | 根因 | 如何观测与复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| 数字答案偶发偏差 | 模型心算代替工具计算 | 抽样比对模型输出与工具真值 | 精确计算强制走工具，模型只解释结果 | 粗略估算场景可容忍近似 |
| 引用了过期的实时数据 | 用训练记忆冒充实时信息 | 问「今天」类问题，核对时效 | 时效数据必须现查，禁止凭记忆作答 | 稳定常识无需每次现查 |
| 该动手时只给了建议 | 未注册可执行工具 | 检查 `tools` 是否为空 | 为「动作类」需求定义并接入工具 | 纯咨询场景无需赋予执行能力 |

## 思考：模型自己也会算数，为什么还要给它计算器工具？

### 回答

因为模型的「算数」是概率生成，本质是在「猜」一个看起来对的数字，位数一多、进位一复杂就会静默出错，且错误看起来非常合理，难以察觉。而计算器是确定性执行，永远精确、可复现、可审计。把「需要精确、确定性结果」的任务外包给工具，让模型专注于「决定何时用、用哪个、怎么传参」，这正是工具分工的核心。更深一层：这样做还让系统可测试——工具的输出可以写单元测试，模型的心算不能。

### 面试精简表达

模型擅长「决定做什么」，不擅长「保证算得对」。精确计算走工具，是把不确定性挡在确定性代码之外。

## 思考：是不是所有问题都应该让 Agent 去调工具？

### 回答

不是。滥用工具会带来两类代价：一是延迟和成本，每次工具调用都多一轮模型往返和外部请求；二是误调用面扩大，工具越多，模型选错、传错、被注入诱导的风险越高。判断法则是看这个问题是否落入「实时/专有数据、精确计算、产生副作用」三类之一；若答案本就是稳定常识（如「水的沸点」）、创意生成（如「写首诗」）或对已在上下文中的信息做加工，直接让模型回答更快更省。Anthropic 文档也明确模型对稳定知识和闲聊会直接作答，这与「工具是补短板，不是万能钥匙」的判断一致。

### 反例

若把「1+1 等于几」也强制走计算器工具，只会徒增一轮往返延迟；但「9137×7823」这种大数乘法就必须走工具。区分点是「模型能否稳定给出精确结果」，而不是「这是不是一道算术题」。

## 事故回放：一次「凭记忆报价」引发的连锁退款

把开头的汇率事故完整拆开，可以看到「只会说」的模型如何在四个环节层层放大误差。第一环，用户问的是「今天汇率」，属于典型的时效数据，但系统没有配汇率工具，模型只能调用训练记忆里的旧值 7.18。第二环，模型把 89.9 × 7.18 心算成「约 640」，既用了错的汇率，又做了不精确的乘法，两个误差叠加。第三环，模型在回答里加了一句「建议尽快支付」，把一个不确定的估算包装成了确定的建议，诱导用户立刻行动。第四环，真实扣款走的是支付网关的实时汇率 7.23，算出 649.9，四舍五入 647，与模型报价差 7 元。

单看每一环，模型的措辞都「没毛病」，但结果是真金白银的投诉。修复方案不是「让模型报价时更谨慎」——那是软约束，靠不住；而是从架构上拆分职责：`get_fx_rate` 现查实时汇率，`multiply` 做精确计算，模型只负责「决定调用顺序、把结果解释成人话、并明确提示『最终以支付时汇率为准』」。上线后,报价与实际扣款的偏差被压到零，因为报价用的就是同一个实时汇率源。这印证了本章的起点：Agent 可靠性的第一步，不是换更强的模型，而是认清模型「只能说」，把「能做」的部分交给工具。

## 机制推导：从「语言模型」到「会用工具的 Agent」

一个纯语言模型的输入是文本、输出也是文本，它与世界之间隔着一层「只能读写字符串」的玻璃墙。工具的作用，是在这堵墙上开一扇门：模型仍然只输出文本，但这段文本被约定为一种「结构化的调用意图」（比如一段 JSON），运行时代码读到它，就代模型去敲真实系统的门，再把结果以文本形式塞回模型的下一轮输入。整个过程里，模型自始至终没有碰过真实系统——它发出的永远只是「提议」。

这个抽象解释了两件事。第一，为什么工具定义（名称、描述、参数结构）必须以文本形式发给模型：因为模型只认文本，它对工具的全部认知都来自这份「说明书」，这一点第 2 小节会展开。第二，为什么所有副作用都发生在运行时而非模型内部：因为门是运行时代码开的，模型只是隔着玻璃墙「指」了一下。理解了这层玻璃墙，你就理解了工具机制的全部安全性来源——玻璃墙本身就是一道天然的隔离，而运行时代码是这道墙上唯一的、可控的门。

Toolformer 论文进一步说明，模型甚至可以在预训练中「学会」在合适位置插入工具调用（如调用计算器、检索、翻译接口），并用调用结果提升下游任务表现 [来源](https://arxiv.org/abs/2302.04761)。这说明「何时该调工具」既可以由外部提示引导，也可以内化为模型能力，但「谁去真正执行」始终在模型之外——这条边界不会因为模型更强而消失。
