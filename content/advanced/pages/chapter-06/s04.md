## 真实问题

一个企业内部助手 Agent 接入了 60 多个工具——查考勤、订会议室、发通知、查报销、拉数据报表……上线两周后，两类故障反复出现。第一类：用户说「帮我查下这个月的报销进度」，模型却调用了 `search_reports`（查数据报表），因为两个工具的描述都含「报表/报告」字样，模型选混了。第二类更离谱：用户问「订个明天下午的会议室」，模型提议调用一个叫 `reserve_meeting_room` 的工具——可注册表里根本没有这个工具，正确的叫 `book_room`，模型「幻觉」出了一个不存在的工具名，运行时直接抛 `KeyError` 崩溃。

这两类故障——**选错工具**和**幻觉工具名**——是多工具 Agent 最典型的两个坑。它们的共同根源是：工具一多，模型的选择空间爆炸，出错概率随之上升；而运行时如果没有「白名单校验 + 错误处理」这层防护，模型的每一次失误都会变成一次线上事故。本小节讲清楚：工具多了怎么帮模型选对（路由），选错/传错/调用失败时怎么优雅兜底（错误处理与重试）。

## 原理：工具变多带来的三类失效

工具数量上升，会同时放大三类失效，必须分别应对：
```text
失效类型        表现                          应对手段
──────────     ──────────────────────      ────────────────────────
① 选择困难      近义工具选错、漏选           分组/命名空间、动态裁剪、重写差异化描述
② 幻觉工具名    调用注册表里不存在的工具      白名单校验 + 近邻纠正 + 结构化拒绝
③ 调用失败      工具执行抛异常/超时/返回错误  分类捕获 + 修复建议 + 带上限重试
```
第 ① 类是「上下文与描述」问题：工具定义都塞进 prompt，60 个工具的描述既挤占 Token，又让近义工具互相干扰。第 ② 类是「输出不可信」问题：模型返回的工具名是概率生成的字符串，可能拼错、可能凭空造。第 ③ 类是「外部世界不可靠」问题：真实工具会超时、会报错、会返回意料之外的数据。这三类都不能靠「让模型更小心」解决，只能靠运行时的确定性代码兜住。

## 现象与输入：一次「选错 + 幻觉」的双重翻车
```text
可用工具（部分）：get_weather, search_flights, book_flight, convert_currency

场景A（选错）：用户「查报销进度」→ 模型调 search_reports（想查报表）
场景B（幻觉）：用户「订会议室」→ 模型调 reserve_meeting_room（注册表里叫 book_room）

没有防护时：
  场景B 直接 KeyError 崩溃，整个 Agent 挂掉，用户看到 500 错误

有防护时：
  路由器发现 reserve_meeting_room 不在白名单 → 近邻匹配到 book_room → 纠正或提示
```
关键差别在于：有没有一层「把模型输出当不可信输入」的路由与校验。有了它，幻觉工具名就从「崩溃事故」降级成「一次可恢复的提示」。

## 最小可运行演示：工具路由 + 带上限重试

下面这段纯标准库代码，把「白名单路由 + 近邻纠正 + 带上限重试」三件事做出来。`route` 用 `difflib` 做近似匹配，把模型拼错的工具名纠正回白名单里的真实工具；`call_with_retry` 给不稳定的工具调用加一个明确的重试上限，避免无限重试烧钱：
```python
import difflib

REGISTRY = ["get_weather", "search_flights", "book_flight", "convert_currency"]


def route(proposed: str) -> dict:
    """把模型提议的工具名路由到白名单：命中直通，近似则纠正，都不中则拒绝并给提示。"""
    if proposed in REGISTRY:
        return {"status": "ok", "tool": proposed}
    near = difflib.get_close_matches(proposed, REGISTRY, n=1, cutoff=0.6)
    if near:
        return {"status": "corrected", "tool": near[0], "from": proposed}
    return {"status": "reject", "from": proposed, "hint": f"未知工具，请从 {REGISTRY} 中选择"}


def call_with_retry(fn, max_retry: int = 2) -> dict:
    """带上限的重试：成功即返回，超过次数返回结构化失败。"""
    attempt = 0
    for attempt in range(1, max_retry + 2):
        result = fn(attempt)
        if result.get("ok"):
            return {"ok": True, "attempt": attempt, "value": result["value"]}
    return {"ok": False, "attempt": attempt, "error": "重试次数用尽"}


def flaky(attempt: int) -> dict:
    """模拟前一次失败、第二次成功的抖动依赖。"""
    return {"ok": True, "value": "第二次成功"} if attempt >= 2 else {"ok": False}


def main() -> None:
    print(route("get_weather"))
    print(route("serch_flights"))
    print(route("fly_to_moon"))
    print(call_with_retry(flaky))


if __name__ == "__main__":
    main()
```
保存为 `router_retry.py`，运行 `python router_retry.py`。预期输出：
```text
{'status': 'ok', 'tool': 'get_weather'}
{'status': 'corrected', 'tool': 'search_flights', 'from': 'serch_flights'}
{'status': 'reject', 'from': 'fly_to_moon', 'hint': "未知工具，请从 ['get_weather', 'search_flights', 'book_flight', 'convert_currency'] 中选择"}
{'ok': True, 'attempt': 2, 'value': '第二次成功'}
```
三个路由结果对应三种情况：拼对了直通、拼错了（`serch_flights`）被近邻纠正回 `search_flights`、彻底幻觉（`fly_to_moon`）被拒绝并附带「从这些工具里选」的提示。**近邻纠正要谨慎使用**：它适合修正明显的拼写抖动，但如果两个真实工具名本身很接近，自动纠正可能纠错到错误的工具上——所以生产里更稳妥的做法是「低置信度时不自动纠正，而是把候选列表连同拒绝原因回传给模型，让它重选」。重试部分则演示了「第一次失败、第二次成功」的抖动如何被 `max_retry` 兜住，且失败时返回结构化信息而非崩溃。

## 让工具「自我描述」错误：给模型可自愈的反馈

工具执行失败时返回什么，直接决定模型能不能自我纠错。一条常被忽视的原则：**错误信息不是给人看的日志，而是给模型看的「下一步提示」。** 对比两种返回：
```text
坏的错误返回（模型无从下手）        好的错误返回（模型能自愈）
────────────────────────         ──────────────────────────────
"Error: 500"                     "查询失败：城市名 'Beijingg' 未找到，
"Traceback (most recent...)"      是否想查 'Beijing'？请用正确城市名重试"
"KeyError: 'city'"               "缺少必填参数 city，请补充城市名后重试"
      ↓                                  ↓
模型看不懂，重复犯错或放弃         模型读懂原因，下一轮自动修正
```
用代码把这个理念落地——让执行在失败时返回「结构化、可读、含修复建议」的结果，而不是把裸异常甩给模型：
```python
def safe_run(fn, args: dict) -> dict:
    """执行工具，无论成功失败都返回结构化结果（给模型看的字典）。"""
    try:
        return {"ok": True, "result": fn(**args)}
    except KeyError as exc:                                # 已知错误 -> 针对性提示
        return {"ok": False, "error": f"缺少字段 {exc}", "hint": "请检查并补全参数后重试"}
    except ValueError as exc:
        return {"ok": False, "error": str(exc), "hint": "参数值非法，请修正取值范围后重试"}
    except Exception as exc:                               # 兜底：未知异常也要结构化
        return {"ok": False, "error": f"{type(exc).__name__}: {exc}", "hint": "换一种方式或换个工具重试"}


def parse_price(text: str) -> float:
    return float(text)


print(safe_run(parse_price, {"text": "199.9"}))
print(safe_run(parse_price, {"text": "免费"}))
```
保存为 `safe_run.py`，运行 `python safe_run.py`。预期输出：
```text
{'ok': True, 'result': 199.9}
{'ok': False, 'error': "could not convert string to float: '免费'", 'hint': '参数值非法，请修正取值范围后重试'}
```
不同异常类型对应不同的 `hint`，模型读到 `hint` 就知道下一步该怎么办——这正是第 7 章「反思」的前提：没有好的反馈信号，反思就是闭门造车。哪怕是意料之外的异常，也要包成 `{"ok": False, ...}`，而不是让裸 traceback 塞回上下文——裸 traceback 既浪费 Token，模型也读不出可操作的信息。

## 真实系统对应

**官方公开机制**：Anthropic 的 Tool use 文档说明，当所需必填参数缺失时有专门的处理路径；`tool_result` 块可以携带执行结果或错误信号回传给模型，模型据此继续或纠错 [来源](https://docs.anthropic.com/en/docs/agents-and-tools/tool-use/overview)。面对「工具数量巨大」的场景，OpenAI 提供 `tool_search`，允许延迟加载很少使用的工具、按需检索再载入上下文（仅特定模型及以上版本支持，以当前文档为准）[来源](https://platform.openai.com/docs/guides/function-calling)；Anthropic 也提供服务端的 Tool search tool，用于「在成千上万工具中按需发现和加载」[来源](https://docs.anthropic.com/en/docs/agents-and-tools/tool-use/overview)。这些都印证了「工具太多需要按需裁剪」是厂商也在解决的真实问题。

**通用工程模式**：白名单校验、近邻纠正、结构化错误、带上限重试、动态裁剪工具集，都是可迁移的做法。**教学参考实现**：`difflib` 近邻匹配和固定的 `flaky` 抖动都是演示，生产的重试应带指数退避与超时，路由应结合语义检索而非纯字符串相似度。

## 生产踩坑

| 症状 | 根因 | 如何观测与复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| 近义工具频繁选错 | 工具过多、描述雷同 | 记录候选与实际调用做混淆矩阵 | 分组/命名空间、动态裁剪、差异化描述 | 功能重叠工具应合并而非硬分 |
| 调用不存在的工具致崩溃 | 运行时未做白名单 | 注入幻觉工具名复现 | 执行前查注册表，低置信不自动纠正 | 白名单外一律拒绝，不猜测 |
| 工具失败后模型反复犯同样错 | 错误信息无修复建议 | 回放失败轮次，看模型是否纠正 | 返回结构化错误 + `hint` | 不可恢复错误应直接终止并上报 |
| 重试把成本和延迟拖爆 | 无重试上限或退避 | 注入持续失败依赖，看调用次数 | 设 `max_retry` + 指数退避 + 超时 | 非幂等写操作重试前必须去重 |
| 换更大模型选择仍不稳 | 把「工具设计问题」当「模型能力问题」 | 固定输入对比不同模型选择分布 | 先修描述与路由，再谈换模型 | 极端复杂域可能确需更强模型 |

## 思考：工具太多导致模型选择困难，怎么系统性缓解？

### 回答

分三个层次。第一层是**描述层**：重写近义工具的描述，突出差异，用命名空间/分组让模型先在「域」上收敛再选具体工具。第二层是**上下文层**：不要每轮都把全部工具塞进 prompt，而是根据当前任务意图动态裁剪，只暴露相关的那几个——OpenAI 的 `tool_search` 和 Anthropic 的 Tool search tool 正是这个思路的官方实现。第三层是**执行层**：无论前两层怎么优化，都要用白名单兜底，把模型偶发的选错/幻觉挡在执行之外。三层各司其职：描述层减少选错概率，上下文层降低 Token 成本和干扰，执行层保证选错也不出事故。

### 面试精简表达

选对靠描述和分组，选少靠动态裁剪，选错兜底靠执行层白名单。三层叠加，而不是指望换个更强的模型。

## 思考：工具调用失败时，该重试、换工具，还是直接放弃？

### 回答

取决于失败的性质，判断维度是「可恢复性」和「幂等性」。**瞬时性失败**（超时、限流、`overloaded`）适合带指数退避的有限重试，因为再试一次很可能就成功。**参数性失败**（缺字段、取值非法）不该盲目重试，而应把结构化错误和 `hint` 回传给模型，让它修正参数后重试——同样的错参再试一百次也不会成功。**能力性失败**（这个工具根本做不了这件事）应换工具或换路径。**不可恢复失败**（权限不足、资源不存在）应直接返回结构化失败并上报，不要假装还能救。最关键的安全约束是：**非幂等的写操作（下单、扣款、发消息）在重试前必须先做幂等去重**，否则一次网络抖动的重试可能造成重复扣款——这一点第 6 小节会展开。

### 反例

对「参数缺失」类错误做无脑重试是典型反模式：模型每次都传同样的错参，重试只是把同一个错误重复 N 次，白白消耗成本和延迟，最后还是失败。正确做法是把错误讲清楚让模型改参。

## 事故回放：一次无上限重试引发的「重复扣款雪崩」

某支付 Agent 的 `charge`（扣款）工具在一次下游网关抖动时返回超时。系统的重试逻辑写得很「勇敢」：只要失败就重试，没有上限，也没有退避。结果那几分钟里，网关一直半死不活，每次 `charge` 都超时——但其中一部分「超时」其实扣款已经成功，只是响应没回来。Agent 不知道，继续重试，同一笔订单被扣了 7 次。等监控发现异常人工熔断时，已经产生了一批重复扣款，客服和财务花了整整两天对账退款。

这个事故有两个叠加的根因。第一是**无上限、无退避的重试**：抖动期间的疯狂重试既加重了网关负担，又放大了副作用。第二、也是更致命的——**对非幂等的写操作直接重试**：`charge` 没有幂等键，运行时无法区分「这次超时是没扣成功」还是「扣成功了但响应丢了」，于是把「可能已经成功」的操作又执行了一遍。修复方案是两条一起上：给重试加 `max_retry=3` 和指数退避；给 `charge` 引入幂等键（同一订单同一幂等键只扣一次，重复请求直接返回首次结果）。这印证了本小节的核心边界——**重试是对付瞬时失败的利器，但对非幂等写操作，必须先有幂等保护，重试才安全。** 错误处理不只是「捕获异常」，更是「理解这个操作能不能安全地再来一次」。
