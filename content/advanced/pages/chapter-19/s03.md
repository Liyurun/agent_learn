## 真实问题

一个内部知识助理上线后，用户投诉「问天气它去算数、问算数它去搜网页」。工程师第一反应是「模型不够强，换个更大的」，换完花了双倍推理成本，选错率只从 22% 降到 18%，几乎没救。后来一位老工程师看了一眼工具定义，发现三个工具的 docstring 分别是 `"""搜索。"""`、`"""计算。"""`、`"""读取。"""`——全是两个字，模型根本分不清「搜索」是搜网络还是搜本地、「读取」读什么、「计算」和「搜索」在「查一个数值」时该用哪个。把描述改清楚后，选错率从 22% 直接降到 3%，成本还降回原来的一半。

这个故事的教训是：**到了阶梯 2，多个工具摆在面前，真正的挑战从「能不能调用工具」变成了「模型如何在多个工具间选对那一个」，而这件事 90% 取决于你的工具描述写得好不好**。工具描述是写给模型看的 API（Application Programming Interface，应用程序接口）文档，模糊的文档人都会用错，何况模型。

## 原理：工具选择是一次「读文档做决策」

阶梯 1 只有一个工具，模型没得选，`Action` 永远是那一个。到阶梯 2，模型每一步都要先做一个**分类决策**：当前这一步，该用三四个工具里的哪一个？模型做这个决策的唯一依据，就是每个工具的**名字 + 描述 + 参数说明**。它不会运行你的代码，也看不到你的实现——它只能「读文档猜用途」。

因此，工具描述必须回答模型三个问题：**这个工具是干什么的、什么时候用它（以及什么时候不要用）、要传什么参数**。看一组对比，同一个搜索工具，两种描述：

| 写法 | docstring | 后果 |
|---|---|---|
| 模糊（反例） | `"""搜索。"""` | 模型不知道搜的是网络还是本地、该传关键词还是自然语言，经常选错或不选 |
| 清晰（正例） | `"""联网搜索实时信息（新闻、天气、股价等）。当问题涉及你不知道的最新事实时使用。参数 query 为搜索关键词。"""` | 模型知道「何时用、传什么」，选择准确率大幅提升 |

清晰版多写的那几句，本质是给模型补上了「用途 + 触发条件 + 参数语义」三块信息。尤其是**负向边界**（「什么时候不要用」），在语义相近的工具间特别值钱——比如给 `calculator` 补一句「只做纯数值计算，不要用它查实时数据」，就能挡住「问股价时误用计算器」。

## 最小可运行演示

下面这段代码把「工具描述质量决定选对率」这件事量化演示出来。它用一个确定性的关键词路由器**模拟**模型的语义匹配：描述清晰（关键词丰富）就能选对，描述模糊（关键词塌缩成同一个词）就只能盲选。这是教学参考实现——真实模型用的是语义向量而非关键词，但「描述越清晰越好选」这条结论完全一致。
```python
"""阶梯2：多工具选择（纯 Python，无需 API Key）。
用一个确定性路由器演示"工具描述质量决定选对率"，并展示选错工具的对照。"""
from dataclasses import dataclass


@dataclass
class Tool:
    name: str
    desc: str          # 写给模型看的"API 文档"
    keywords: tuple    # 教学用：把 docstring 的语义压成关键词，模拟模型的语义匹配


def calculator(expr: str) -> str:
    return str(eval(expr))  # 教学演示


def read_file(path: str) -> str:
    return f"（此处返回 {path} 的前 2000 字，示例略）"


def web_search(query: str) -> str:
    return f"（联网搜索『{query}』的实时结果，示例略）"


CLEAR_TOOLS = [  # 清晰描述：把"何时用/传什么"写进关键词，模型能对上号
    Tool("calculator", "计算数学表达式，如 12*8。", ("计算", "算", "多少", "乘", "加")),
    Tool("read_file", "读取本地文本文件内容，参数 path 为文件路径。", ("读取", "文件", "本地", "打开")),
    Tool("web_search", "联网搜索实时信息（新闻/天气/股价）。", ("搜索", "天气", "新闻", "股价", "最新")),
]

VAGUE_TOOLS = [  # 模糊描述：全写"搜索/查询"，语义塌缩，模型无从区分
    Tool("calculator", "计算。", ("查询",)),
    Tool("read_file", "读取。", ("查询",)),
    Tool("web_search", "搜索。", ("查询",)),
]


def route(question: str, tools) -> str:
    """教学版路由：按关键词命中数选工具，模拟"描述越清晰越好选"。"""
    best, best_hits = None, 0
    for t in tools:
        hits = sum(1 for kw in t.keywords if kw in question)
        if hits > best_hits:
            best, best_hits = t.name, hits
    return best or tools[0].name  # 无命中时只能盲选第一个（暴露模糊描述的后果）


def run() -> None:
    questions = [
        "北京今天的天气怎么样？",
        "帮我算一下 12*8 等于多少？",
        "读取本地文件 notes.txt 的内容。",
    ]
    print("== 清晰描述（每个工具写清何时用/传什么）==")
    for q in questions:
        print(f"  问题：{q}  -> 选中：{route(q, CLEAR_TOOLS)}")
    print("== 模糊描述（全写『查询』，语义塌缩）==")
    for q in questions:
        print(f"  问题：{q}  -> 选中：{route(q, VAGUE_TOOLS)}（盲选，多半错）")


if __name__ == "__main__":
    run()
```
保存为 `ladder2_multitool.py`，运行 `python ladder2_multitool.py`。完整预期输出：
```text
== 清晰描述（每个工具写清何时用/传什么）==
  问题：北京今天的天气怎么样？  -> 选中：web_search
  问题：帮我算一下 12*8 等于多少？  -> 选中：calculator
  问题：读取本地文件 notes.txt 的内容。  -> 选中：read_file
== 模糊描述（全写『查询』，语义塌缩）==
  问题：北京今天的天气怎么样？  -> 选中：calculator（盲选，多半错）
  问题：帮我算一下 12*8 等于多少？  -> 选中：calculator（盲选，多半错）
  问题：读取本地文件 notes.txt 的内容。  -> 选中：calculator（盲选，多半错）
```
对照两段输出：清晰描述下三道题全选对；模糊描述下三道题全塌缩到 `calculator`（因为关键词都命中不了、只能盲选列表第一个）。**这就是「工具描述即 API 文档」最直观的证据**——同样的三个工具、同样的三道题，只改描述，选对率从 100% 掉到 33%。

## 逐行讲解

- `Tool` 用 `keywords` 字段把 docstring 的语义「压缩」成关键词，是为了在纯 Python、无模型的环境里**可复现地**模拟语义匹配。真实系统里，这一步由模型读取 docstring 后的语义理解完成，你写的描述越清晰，模型内部的「语义关键词」就越丰富准确。
- `CLEAR_TOOLS` 的每个工具都覆盖了「用途词 + 触发词」：`web_search` 不只写「搜索」，还写了「天气/新闻/股价/最新」这些触发场景，这样问天气时才命中。
- `VAGUE_TOOLS` 把三个工具的关键词全塌缩成 `("查询",)`，模拟「描述太笼统、语义区分不开」。此时任何问题都命中不了（问句里没有「查询」二字），`route` 只能 `return tools[0].name` 盲选第一个——对应真实模型「分不清就随便选一个」的失败模式。
- `route` 里 `best or tools[0].name` 这行兜底，正是「无信息可依据时的盲选」，它让「描述模糊 → 盲选 → 选错」这条因果链在输出里看得见。

## 真实系统对应

**官方公开机制**：主流模型接口都要求为每个工具提供 `name`、`description` 与参数 schema，模型据此选择工具——这在函数调用文档里是明确机制（详见第 8 章）。**通用工程模式**：「工具描述要写清用途 + 触发条件 + 负向边界 + 参数语义」是可迁移到任何厂商的做法；NirDiamant/GenAI_Agents 里 40+ 个案例反复示范了多工具协作时清晰描述的重要性，可从中复现 3 个案例做练习 [来源](https://github.com/NirDiamant/GenAI_Agents)。**教学参考实现**：上面的关键词路由器仅用于让「描述质量→选对率」的因果可离线复核，不代表任何真实模型的选择算法——真实模型用的是语义向量，不是字符串包含。

要点明一个边界：当工具数量很多（十几个以上）且语义重叠时，光靠改描述也压不住选错率，此时要用**两阶段路由**——先让模型粗选一个类别，再只把该类别下的少数工具暴露给它。这与「工具不是越多越好」的结论一致：同时暴露的工具越多，选择准确率越低、每轮重发的 token 越多（详见第 8 章）。

## 生产踩坑

| 症状 | 根因 | 如何观测与复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| 问 A 却调了 B 工具 | 工具描述模糊、语义区分不开 | 记录「问题类型→实际调用工具」分布 | 描述写清用途+触发+负向边界 | 单工具场景不涉及 |
| 换更大模型选错率仍高 | 病根在描述不在模型能力 | 固定模型、只改描述看变化 | 先修描述再谈换模型 | 描述已清晰仍错才考虑换模型 |
| 语义相近工具反复混用 | 缺「什么时候不要用」负向边界 | 构造两工具都沾边的问题复现 | 给每个工具补负向边界说明 | 工具语义完全正交时较少见 |
| 工具一多选择准确率骤降 | 同时暴露工具过多且重叠 | 逐步增加工具数观测准确率 | 收敛工具集、两阶段路由 | 领域确需大量工具时另设路由 |
| 参数传错类型/单位 | 参数语义没写清（单位、格式） | 观测参数校验失败率 | docstring 标明单位、格式、示例 | 参数极简时影响小 |
| 每轮 token 随工具数线性涨 | 工具定义每轮随历史重发 | 统计各轮 input token | 精简工具集、按需暴露 | 短对话影响可忽略 |

## 思考：多工具 Agent 选错工具时，为什么应该先检查工具描述，而不是急着换更强的模型？

### 回答

因为选错工具的主要矛盾通常在「信息供给」而非「模型能力」。模型选工具的唯一依据是你给的名字、描述和参数说明，它看不到你的实现。如果描述模糊（比如三个工具都只写两个字）、语义重叠、缺少「什么时候不要用」的负向边界，那么再强的模型也没有足够信息做出正确区分——就像给人一份只写「搜索/计算/读取」的 API 文档，人也会用错。此时换更大的模型，付出双倍推理成本，选错率往往只降几个百分点，因为病根没动。正确的第一步是把描述写清「用途 + 触发条件 + 负向边界 + 参数语义」，很多时候选错率会断崖式下降，成本还不变。只有当描述已经写得很清晰、工具语义也正交，选错率仍高，才轮到考虑换模型或上两阶段路由。一句话：先修「写给模型看的文档」，再谈「换更聪明的读者」。

### 面试精简表达

模型选工具只能靠描述，描述模糊/重叠/缺负向边界时再强的模型也分不清；先把描述写清（用途+触发+负向边界+参数），通常选错率断崖下降且不增成本，描述已清晰仍错才考虑换模型或两阶段路由。

### 反例

如果工具描述已经非常清晰、参数语义明确、也做了负向边界，但模型在明显该用 A 时仍频繁选 B，且换一个更强的模型后立刻正常，那这确实是模型能力问题（小模型的指令遵循或工具理解上限）。此时换模型或对小模型做工具选择的少样本示例，才是对的。判据是：**先确认描述无懈可击，再归因到模型**，顺序不能反。

## 优化前后对比：一次把选错率从 22% 打到 3% 的复盘

回到开头那个知识助理。优化前的工具定义是三个两字 docstring，线上选错率 22%，团队第一反应是换模型，换完 18%、成本翻倍。老工程师介入后，做了三件事，每件都对应一条可观测指标：

第一，给每个工具补全「用途 + 触发条件 + 参数语义」，例如 `web_search` 从「搜索」扩写成「联网搜索实时信息（新闻/天气/股价），当问题涉及你不知道的最新事实时使用，参数 query 为搜索关键词」。这一步把选错率从 22% 降到 9%。第二，给语义相近的 `calculator` 和 `web_search` 各补一句负向边界（「calculator 只做纯数值计算，不查实时数据」「web_search 不做数学运算」），选错率降到 5%。第三，把不常用的两个工具收进二级路由、默认只暴露三个高频工具，选错率降到 3%，每轮 input token 也少了近三成。

复盘的关键结论有两条：其一，**换模型是最贵、收益最低的一招**，应该排在最后；其二，**每一步优化都要绑一个可观测指标**（选错率、token 数），否则你不知道是哪招起了作用。这与阶梯 1 的教训一脉相承——看得见（草稿纸、指标），才修得动。
