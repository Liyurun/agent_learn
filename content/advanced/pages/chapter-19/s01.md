## 真实问题

再把开头小林的故障拉近看一组数字。他的第一版「多 Agent 客服系统」在三天里改了 47 次仍跑不通，git 提交记录显示他反复在四个文件间来回改：工具定义、ReAct 循环、向量记忆写入、路由分诊。每次报错，他都无法回答一个最基本的问题——「这次是哪一层坏了？」因为四层是同一天写的，任何一个报错都可能来自任意一层，甚至来自它们的交互。他花在「定位是哪层」上的时间，是花在「修复」上的三倍。

对照另一位工程师小周：她第一周只写一个单工具 ReAct，46 行代码，第二天就跑通并换了一个自定义工具；第二周在此基础上加第二、第三个工具和一层记忆；第三周才做 Agentic RAG。她每次报错都能立刻锁定「新增的那一层最可疑」，三周下来产出了五个能跑、能讲的小项目。两人智商相当、投入时间相同，差别只在**是否隔离了学习变量**。这一节要把这个差别背后的原理讲透，让你相信「按阶梯」不是鸡汤，而是有认知科学依据的高效路径。

## 原理：工作记忆的容量与「块」

认知科学有一个稳定的结论：人的**工作记忆**（working memory，负责临时保持并操作信息的心理系统）容量非常有限，一次大约只能同时把玩 4±1 个「块」（chunk）。「块」不是固定大小的信息量，而是「已经被你打包成一个整体、可以当一个单位来调用」的知识单元。对新手，「ReAct 循环」是五六个散块（Thought 是什么、Action 怎么解析、Observation 怎么拼回、循环怎么终止……）；对熟手，「ReAct 循环」被打包成一个块，一句话就能调用。

阶梯法的本质，就是**每一级只让一个新块进入工作记忆**，其余部分都是你上一级已经「自动化」了的熟练动作。这和学开车先在空场练离合、再上路练变道是一个道理：空场练离合时，你不用同时操心红绿灯、后视镜、变道时机；等离合成了肌肉记忆（一个块），上路时它就不再占用工作记忆，你才腾得出脑子处理路况。

把「按阶梯」与「一步到位」放在一起，差异一目了然：

| 维度 | 一步到位挑战大项目 | 阶梯式逐级练习 |
|---|---|---|
| 每次新增概念数 | 5~6 个，工作记忆过载 | 1~2 个，可控 |
| 卡住时的定位 | 不知道是哪一层出问题 | 新增的那一层最可疑，易定位 |
| 中途放弃概率 | 高（挫败感强） | 低（每级都有正反馈） |
| 沉淀产出 | 一个跑不通的半成品 | 5~6 个可展示的小项目 |
| 面试可讲性 | 「做过但讲不清细节」 | 每级都能讲清设计权衡 |

## 现象与输入：把「阶梯」翻译成能力增量

把六级阶梯「翻译」成一句话的能力增量，你会看得更清楚——注意每一行只描述「新增的那一个变量」：
```text
阶梯1 → 阶梯2 : 新增「工具从 1 个变多个」，难点从"能调"变"选对"
阶梯2 → 阶梯3 : 新增「一层跨会话的长期记忆」，学会分短期/长期/工具观测
阶梯3 → 阶梯4 : 新增「先出计划再执行」，把多跳任务拆成有序子任务
阶梯4 → 阶梯5 : 新增「检索时机/次数由模型决定，而非代码写死」
阶梯5 → 阶梯6 : 新增「用回归评估集给质量装上刻度尺」
```
阶梯 4 → 阶梯 5 这一跃最关键：它表面看只是「检索多做几次」，实质却是**控制权从代码转移到了模型**——这正是第 1、2 章反复强调的「工作流（workflow）与 Agent 的分界线」。在阶梯 5 之前，是你的 `for` 循环在决定流程；到了 Agentic RAG，是模型在决定「要不要再查一次」。Anthropic 在《Building Effective Agents》里把这条线作为核心区分：workflow 是用预定义代码路径编排大模型，agent 是让大模型动态决定自身流程与工具使用 [来源](https://www.anthropic.com/engineering/building-effective-agents)。这条分界线，本章会在阶梯 5 里活生生地跑给你看。

## 最小可运行演示

「隔离变量」这件事本身也能用代码演示：下面这段脚本把六级阶梯的「新增能力」映射成一张清单，帮你在动手前先把顺序在脑子里排好。它不联网、不需要 API Key，是本章所有阶梯的「导航图」。
```python
import sys


def ladder_gain(level: int) -> str:
    table = {
        1: "单工具：跑通 ReAct 循环",
        2: "多工具：从能调到选对",
        3: "记忆：短期/长期/工具观测分层",
        4: "规划：先拆解再执行",
        5: "RAG：从固定检索到自主检索",
        6: "评估：用回归集守住质量",
    }
    return table.get(level, "未知阶梯")


def run() -> None:
    print(f"Python={sys.version_info.major}.{sys.version_info.minor}")
    for lv in range(1, 7):
        print(f"Level {lv} 新增能力：{ladder_gain(lv)}")
    print("热身通过：环境可用，可以开始逐级练习")


if __name__ == "__main__":
    run()
```
保存为 `warmup.py`，运行 `python warmup.py`。预期输出：
```text
Python=3.10
Level 1 新增能力：单工具：跑通 ReAct 循环
Level 2 新增能力：多工具：从能调到选对
Level 3 新增能力：记忆：短期/长期/工具观测分层
Level 4 新增能力：规划：先拆解再执行
Level 5 新增能力：RAG：从固定检索到自主检索
Level 6 新增能力：评估：用回归集守住质量
热身通过：环境可用，可以开始逐级练习
```
这段代码刻意写得极简，因为它的价值不在代码本身，而在「先建立一张能力地图」这个动作。真正开始爬阶梯前，你应该能不看这张表，说出每一级新增了什么。

## 真实系统对应

**官方公开机制**：ReAct 范式出自 ICLR 2023 论文，作者明确指出「推理（reasoning）与行动（acting）交织」能让模型的决策过程外显、可解释、可干预 [来源](https://arxiv.org/abs/2210.03629)——这正是阶梯 1 要你亲手看清 Thought/Action/Observation 的理论依据。Anthropic《Building Effective Agents》给出的「从最简单的方案起步、只在必要时才增加复杂度」的原则，与阶梯法「每级只加一个变量」的思路完全一致 [来源](https://www.anthropic.com/engineering/building-effective-agents)。**通用工程模式**：把大能力拆成「依赖有序的小能力、逐级点亮」，是可迁移到任何学习路径的方法，不限于 Agent。**教学参考实现**：上面的清单脚本仅用于建立导航，不代表任何框架的分层方式。

要点明一个边界：阶梯的「级数」和「顺序」不是唯一真理。本章按「单工具→多工具→记忆→规划→RAG→评估」排，是因为后一级大多依赖前一级的能力；但真实项目里，记忆和 RAG 常常同时出现，规划和多工具也可能合并。阶梯是**学习脚手架**，不是生产架构的强制模板。

## 生产踩坑

| 症状 | 根因 | 如何观测与复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| 反复在多个文件间改仍跑不通 | 多层能力同一天引入、变量未隔离 | 统计一次报错可能来自几层 | 一次只加一层，留可运行快照 | 单文件玩具脚本无需分层 |
| 跳过阶梯 1 直冲 Agentic RAG | 误以为「阶梯=低级」跳基础 | 让其解释模型为何再检索一次，答不出 | 补回手写 ReAct，看懂每步再上 | 已能默画 ReAct 者可跳 |
| 每级都换全新场景、学得散 | 没有贯穿案例、能力增量对不上 | 检查各级是否复用同一条数据链 | 用一条贯穿数据链串六级 | 教学演示允许换场景举例 |
| 「学完」却没有产出 | 只跑通、未沉淀作品 | 面试时拿不出可讲的项目 | 每级写 README、放进作品集 | 纯自娱自乐可从简 |

## 思考：为什么建议按阶梯练，而不是一上来就挑战大项目？

### 回答

从两个角度回答最有说服力。第一是**工作记忆容量**：人一次只能同时操作 4±1 个「块」，一步到位挑战大项目会让工具、循环、记忆、路由、护栏五六个陌生概念同时涌进工作记忆，直接过载，表现为「每个词都懂、连起来就懵」；阶梯法每级只让一个新块进入工作记忆，其余是已自动化的熟练动作，大脑不过载。第二是**依赖顺序与可定位性**：后一级能力大多依赖前一级（Agentic RAG 的「模型自主检索」依赖你先看懂 ReAct 的每一步），逐级练时一旦卡住，「新增的那一层」最可疑，定位成本极低；一步到位时多层同时引入，任何报错都可能来自任意一层或它们的交互，定位成本三倍于修复成本。附带的收益是：阶梯法每级都有正反馈、降低放弃率，还能沉淀出多个可展示、能讲清权衡的作品。

### 面试精简表达

阶梯法隔离学习变量：每级只加一个新「块」不让工作记忆过载，且后级依赖前级、卡住时新增那层最可疑，定位成本低；一步到位则多层同时上，过载又难定位，易半途而废。

### 反例

如果你已经能不看代码默画出 ReAct 循环、说清短期/长期记忆的区别，那么阶梯 1、3 对你就是「已自动化的旧块」，此时逐级慢练反而低效——阶梯是给「新块」用的脚手架，对已掌握的部分应当直接跳级。判断标准不是「级数高低」，而是「这一级对你是不是新块」。

## 机制推导：为什么「后级依赖前级」不是随意排序

有人质疑：阶梯顺序是不是作者拍脑袋定的？其实每一级的「新增变量」都在消费前一级已经稳定下来的能力，形成一条依赖链。阶梯 2 的「多工具选对」依赖阶梯 1 的「模型能按格式提议一个工具调用」——连一个工具都调不稳，谈何在多个里选对。阶梯 5 的「模型自主决定检索几次」依赖阶梯 1 的「你能读懂 Thought/Action/Observation」——看不懂单步循环，就看不懂模型「为什么决定再查一次」，只能对着框架黑盒调参。阶梯 6 的「评估回归」依赖阶梯 5 有一个能对照的「传统 vs Agentic」双版本——没有两个版本，指标就没有对照对象。

由此推出一条实用结论：**当你在某一级卡住时，先回头检查它依赖的下一级是否真的稳固**。很多人卡在 Agentic RAG「看不懂模型的检索决策」，根因往往在阶梯 1 没吃透——ReAct 的单步循环还没成为一个「块」，自然读不懂多轮决策。修复方式不是在阶梯 5 硬调 prompt，而是回到阶梯 2 页把手写 ReAct 再跑一遍。这条「往回一级找根因」的习惯，会在后面每一节反复用到。
