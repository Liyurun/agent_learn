## 真实问题

一个差旅助理 Agent 接到任务：「我下周要去埃菲尔铁塔所在的国家出差，帮我看看当地用什么货币、需不需要转换。」它直接调了一个 `get_currency` 工具、参数填「埃菲尔铁塔」，工具返回「未知」——因为货币表里根本没有「埃菲尔铁塔」这个键，它只认国家名。Agent 于是回答「查不到该地区的货币」，任务失败。而正确的解法需要三跳：埃菲尔铁塔 → 巴黎（城市）→ 法国（国家）→ 欧元（货币）。模型一步到位，跳过了中间两步，自然撞墙。

这类**多跳任务**是阶梯 4 要攻克的：单靠「想到哪调到哪」的即兴反应会漏掉中间步骤。解法是引入**规划（planning）**——先让模型把大任务拆成一串有序的子任务，再逐步执行、每一步的输入来自上一步的产出。这就是 plan-and-execute（先规划再执行）范式，也是 Anthropic《Building Effective Agents》里「用工作流分解复杂任务」思想的直接应用 [来源](https://www.anthropic.com/engineering/building-effective-agents)。

## 原理：从「即兴反应」到「先规划再执行」

阶梯 1~3 的 Agent 都是「反应式」的：看到问题，立刻决定下一个动作，走一步看一步。这对单跳、依赖浅的任务够用；但对「A 的 B 的 C」这种需要串联多个中间结果的多跳任务，反应式容易在中途迷失——它可能忘了自己要干嘛、可能跳过必需的中间查询、可能在子任务间来回打转。

规划范式把这件事拆成两个阶段：

- **规划阶段（Plan）**：模型先读懂任务，输出一个**有序子任务列表**（计划），每个子任务是一个明确的、可执行的小步骤。此时还不执行任何工具，只是「想清楚要分几步、每步干什么」。
- **执行阶段（Execute）**：按计划逐步执行，**每一步的输入来自上一步的产出**，形成一条依赖链。若某步失败（返回「未知」或异常），触发**重规划（re-plan）**——回到规划阶段，根据已知信息调整剩余计划。

Anthropic 把这类模式归入「工作流」：当任务能被清晰拆成固定子步骤时，用预定义的编排（如 prompt chaining，提示链）比让模型完全自主更可靠、更可控 [来源](https://www.anthropic.com/engineering/building-effective-agents)。规划的价值就在于：**把「模型脑子里一团乱麻的多跳」显式化成一张可检查、可回退的计划表**。

## 最小可运行演示

下面这段代码对照「无规划的一步到位」与「先规划再执行」。规划器用确定性逻辑把多跳问题拆成 `城市→国家→货币` 三步（真实项目由模型生成计划），执行器逐步执行、把上一步产出喂给下一步，并在结果为「未知」时触发重规划信号。纯 Python，无需 API Key。
```python
"""阶梯4：规划——先拆解再执行（plan-and-execute），纯 Python 无需 API Key。
对照"无规划的一步到位"与"先出计划再逐步执行、失败可重规划"。"""
from dataclasses import dataclass, field


@dataclass
class State:
    known: dict = field(default_factory=dict)  # 已知事实
    log: list = field(default_factory=list)


def tool_lookup_city(state: State, name: str) -> str:
    table = {"埃菲尔铁塔": "巴黎", "自由女神像": "纽约"}
    return table.get(name, "未知")


def tool_lookup_country(state: State, city: str) -> str:
    table = {"巴黎": "法国", "纽约": "美国"}
    return table.get(city, "未知")


def tool_lookup_currency(state: State, country: str) -> str:
    table = {"法国": "欧元", "美国": "美元"}
    return table.get(country, "未知")


class Planner:
    """确定性规划器：把多跳问题拆成有序子任务（真实项目由 LLM 生成计划）。"""

    def plan(self, question: str):
        # 问题："埃菲尔铁塔所在国家用什么货币？" 需要 城市->国家->货币 三跳
        return [
            ("lookup_city", "landmark"),
            ("lookup_country", "city"),
            ("lookup_currency", "country"),
        ]


TOOLS = {
    "lookup_city": tool_lookup_city,
    "lookup_country": tool_lookup_country,
    "lookup_currency": tool_lookup_currency,
}


def execute(plan, seed: str, state: State):
    """逐步执行计划：每一步的输入来自上一步的产出（依赖链）。"""
    cur = seed
    out_of = {"lookup_city": "city", "lookup_country": "country",
              "lookup_currency": "currency"}
    for i, (step, _slot) in enumerate(plan, 1):
        result = TOOLS[step](state, cur)
        state.known[out_of[step]] = result
        state.log.append(f"[计划步{i}] {step}({cur}) -> {result}")
        if result == "未知":                     # 失败 -> 触发重规划信号
            state.log.append(f"[计划步{i}] 结果未知，触发重规划")
            return None
        cur = result
    return state.known.get("currency")


def naive_one_shot(question: str) -> str:
    """无规划：想一步到位直接查货币，但缺中间事实，答不出。"""
    return "无法直接回答：不知道该地标在哪个国家（缺中间步骤）"


def run() -> None:
    q = "埃菲尔铁塔所在国家用什么货币？"
    print("== 无规划（一步到位）==")
    print("  ", naive_one_shot(q))

    print("== 先规划再执行 ==")
    state = State()
    plan = Planner().plan(q)
    print("  生成计划：", " -> ".join(s for s, _ in plan))
    ans = execute(plan, seed="埃菲尔铁塔", state=state)
    for line in state.log:
        print("  ", line)
    print("  最终答案：", ans)


if __name__ == "__main__":
    run()
```
保存为 `ladder4_planning.py`，运行 `python ladder4_planning.py`。完整预期输出：
```text
== 无规划（一步到位）==
   无法直接回答：不知道该地标在哪个国家（缺中间步骤）
== 先规划再执行 ==
  生成计划： lookup_city -> lookup_country -> lookup_currency
   [计划步1] lookup_city(埃菲尔铁塔) -> 巴黎
   [计划步2] lookup_country(巴黎) -> 法国
   [计划步3] lookup_currency(法国) -> 欧元
  最终答案： 欧元
```
对照两段：无规划直接撞墙（缺中间步骤）；先规划再执行，把任务显式拆成三步，每步的输出（巴黎→法国→欧元）正好是下一步的输入，一条依赖链稳稳走到「欧元」。**这就是规划的威力——它不是让模型更聪明，而是让模型「把要走的路先画出来」，从而不漏步、可检查、可回退**。

## 逐行讲解

- `Planner.plan` 是规划阶段的核心：输入任务，输出一个有序的 `(工具, 输入槽)` 列表。这里用确定性逻辑写死了三步，是为了让输出可复核；真实项目里这一步由模型完成——你给它任务和工具清单，让它先输出一个 JSON 计划。
- `execute` 是执行阶段：`cur` 变量像接力棒，第一步的输出（巴黎）成为第二步的输入，第二步的输出（法国）成为第三步的输入。这条「上一步产出喂下一步」的依赖链，正是多跳任务的本质。
- `if result == "未知"` 是**重规划触发点**：一旦某步失败，执行中止并记录「触发重规划」。真实系统会在这里回到规划阶段，根据「已经查到城市但查不到国家」的现状调整剩余计划（比如换一个数据源）。本例为聚焦主线，用返回 `None` 表示需要重规划。
- `State` 把「已知事实」和「执行日志」分开存：`known` 累积中间结果供后续步骤使用，`log` 记录完整轨迹供复盘。这与阶梯 1 的草稿纸一脉相承——**执行过程要可观测**。

## 真实系统对应

**官方公开机制**：Anthropic《Building Effective Agents》明确提出，复杂任务应优先用工作流分解（如 prompt chaining 把任务拆成前后依赖的步骤、在步骤间加程序化 gate 检查），只在任务无法预先拆解时才用完全自主的 agent [来源](https://www.anthropic.com/engineering/building-effective-agents)。**通用工程模式**：plan-and-execute（先出完整计划再逐步执行）是可迁移到任何框架的范式，LangGraph 等把它实现为「先规划节点、再循环执行节点、失败回到规划节点」的状态图；Lilian Weng 的综述也把「任务分解 / 规划」列为自主 Agent 的核心组件之一 [来源](https://lilianweng.github.io/posts/2023-06-23-agent/)。**教学参考实现**：上面的确定性 `Planner` 和查表工具仅为离线复核，真实规划由模型生成、可能出错、需重规划兜底。

要点明一个边界：规划不是万能的，它和「反应式」各有适用面。任务步骤清晰、依赖固定时，规划（工作流）更可靠；任务开放、每步依赖上一步的不确定结果、无法预先拆解时，反应式或让模型动态决策（下一节的 Agentic RAG 就是一例）更合适。过度规划会让简单任务变复杂——「先拆解」本身也有成本。

## 生产踩坑

| 症状 | 根因 | 如何观测与复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| 多跳任务跳过中间步骤 | 反应式一步到位、无规划 | 给「A 的 B 的 C」型问题看是否漏步 | 引入 plan-and-execute 显式拆步 | 单跳任务无需规划 |
| 某步失败后整条计划崩掉 | 无重规划、失败即终止 | 让中间某步返回「未知」复现 | 失败触发重规划、调整剩余步骤 | 致命错误确需整体中止时例外 |
| 计划步骤间数据传错 | 上一步产出与下一步入参不匹配 | 打印每步的 `(输入, 输出)` 复现错配 | 明确每步输入来源、加类型/存在性校验 | 步骤独立无依赖时较少见 |
| 简单任务被过度拆解 | 对什么都先规划、成本上升 | 统计简单题的计划步数与延迟 | 先判断复杂度，简单走反应式 | 需强可控/可审计的流程另算 |
| 计划本身就是错的 | 模型对任务理解偏差 | 检查生成的计划是否合理 | 计划出来先做一致性检查再执行 | 计划固定写死时不涉及 |
| 重规划陷入死循环 | 无重规划次数上限 | 让某步永远失败复现 | 给重规划设次数上限、触顶转人工 | 明确可无限重试的场景另算 |

## 思考：什么样的任务需要「先规划再执行」，什么样的任务反而不该规划？

### 回答

判断的核心是**任务能否被预先清晰拆解、步骤依赖是否固定**。适合规划的是「多跳、依赖链清晰」的任务：比如「A 的负责人在 B 部门的职位」「某地标所在国家的货币」，这类任务能预先看出「要分几步、每步依赖上一步的什么产出」，用 plan-and-execute 显式拆步能避免漏步、便于检查和失败重规划，比反应式即兴反应可靠得多。不适合规划、反而该用反应式或动态决策的是两类：一类是「单跳、依赖浅」的简单任务，先拆解纯属过度设计，增加延迟和成本；另一类是「开放式、每步依赖上一步的不确定结果、无法预先拆解」的任务——比如探索式文档问答，你事先不知道要查几次、查什么，这时应该让模型每步动态决定（就是下一级 Agentic RAG 做的事），硬套固定计划反而束手束脚。所以规划和反应式不是谁取代谁，而是按「任务是否可预先拆解」分流：可拆解、依赖固定就规划；不可拆解、依赖动态就让模型动态决策。

### 面试精简表达

多跳、依赖链可预先拆清的任务用 plan-and-execute（不漏步、可检查、可重规划）；单跳简单任务规划是过度设计，开放式、依赖上一步不确定结果、无法预拆的任务该让模型动态决策。按「能否预先清晰拆解」分流。

### 反例

有人会说「那我全部任务都先规划，最保险」。这恰恰是反模式：对「北京今天天气如何」这种单跳问题，先让模型生成一个只有一步的计划、再执行，白白多了一次「规划」的模型调用，延迟和成本翻倍，收益为零。更糟的是开放式任务——你无法预先知道文档问答要检索几次，硬生成一个固定步数的计划，模型要么计划太短漏查、要么太长空跑。规划的成本必须与任务复杂度匹配：**简单任务的规划开销可能大于收益**。

## 优化前后对比：给多跳客服 Agent 加规划层

某工单系统的客服 Agent 处理「我上次报修的那台设备，保修到什么时候」这类问题时，通过率只有 55%。日志显示，失败几乎都发生在多跳问题上——Agent 想一步查「保修期」，但保修期挂在「设备型号」上，而设备型号要先从「用户上次工单」里查出来，它跳过了中间两跳。

优化方案是加一个轻量规划层：收到问题后，先让模型判断「这是单跳还是多跳」；多跳则输出一个有序计划（查上次工单→取设备型号→查该型号保修期），再逐步执行、每步产出喂下一步，某步查空则重规划换数据源。上线后多跳问题通过率从 41% 升到 83%，整体通过率从 55% 升到 79%。代价是多跳问题平均多了一次「规划」调用、延迟增加约 0.6 秒——但团队评估认为「答对」远比「快 0.6 秒」重要，且对判定为单跳的问题不加规划、延迟不受影响。这个案例再次印证阶梯 4 的核心：**规划不提升模型智商，但能把多跳任务从『撞运气』变成『按图施工』，并让失败可定位、可重规划**。
