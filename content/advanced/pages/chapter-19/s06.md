## 真实问题

一个企业内部文档问答系统，用的是标准 RAG（Retrieval-Augmented Generation，检索增强生成）：每次提问都用原问题检索一次、拼上下文、让模型作答。上线后单跳问题（「请假流程是什么」）表现很好，通过率 90%；但一遇到多跳问题就崩——比如「张三负责的系统用了什么数据库」，通过率只有 30%。原因是：用原问题检索一次，只能召回「张三负责风控系统」这个片段，却召回不到「风控系统用 PostgreSQL」这个片段——因为后者根本不含「张三」二字，语义上离原问题很远。流程写死了只查一次，模型再聪明也补不回缺失的证据。

这是本章的重点，也是理解「Agentic（自主）」精髓的最佳练习。解法是 **Agentic RAG**：让模型**自主决定**是否检索、检索什么、检索几次——而不是每次都固定检索一次。当模型发现第一次检索缺了关键证据，它能**改写查询、再检索一次**，逐步逼近答案。这一跃，正是全书最核心的分界线——**控制权从代码转移到模型**——活生生地体现。

## 原理：从「固定检索」到「模型决定检索」

先看传统 RAG，它是一条**写死的三步流水线**：
```python
def naive_rag(question: str) -> str:
    docs = vector_store.search(question, k=4)   # 1. 固定用原问题检索一次
    context = "\n".join(docs)                    # 2. 拼接检索结果
    prompt = f"根据以下资料回答问题。\n资料：{context}\n问题：{question}"
    return llm(prompt)                           # 3. 一次性作答
```
检索几次、用什么查，全由这几行代码决定，模型无权干预。它的天花板对多跳问题一目了然：证据分散在两个几乎没有词面重叠的片段里，一次检索捞不全。

Agentic RAG 把「检索决策权」交给模型：每一步，模型输出一个结构化决策——要么「继续检索（并给出这次要查的查询词，可以改写）」，要么「资料够了，作答」。这正是主流的 CRAG（Corrective RAG，纠错型 RAG）/ Self-RAG（自反思 RAG）范式的核心：在检索与生成之间插入「文档是否相关」的评估，不相关就改写查询重试 [来源](https://docs.langchain.com/oss/javascript/langgraph/agentic-rag)。对比两者：

| | 传统 RAG | Agentic RAG |
|---|---|---|
| 检索时机 | 固定：每次提问都检索一次 | 由模型决定：可能不检索、检索一次或多次 |
| 检索内容 | 固定用原始问题检索 | 模型可改写查询、多轮迭代检索 |
| 控制方 | 代码（写死流程） | 模型（动态决策） |
| 面对复杂问题 | 一次检索可能不够，答不全 | 能追加检索、逐步逼近答案 |
| 延迟与成本 | 低（一次检索一次生成） | 高（每步多一次决策调用，2~4 倍） |

## 最小可运行演示

下面用极简向量库 + 确定性假模型，跑出「传统一次检索答不全、Agentic 改写多轮补齐」的对照轨迹。关键设计：答案证据（Doc B「风控系统的存储层基于 PostgreSQL」）与原始问题几乎无词面重叠，只能靠「张三→风控系统→PostgreSQL」这条桥接链两跳串起来。纯 Python，无需 API Key。
```python
"""阶梯5：传统 RAG vs Agentic RAG（纯 Python，无需 API Key）。
用极简向量库 + 确定性假模型，跑出"传统一次检索答不全、Agentic 改写多轮补齐"的对照轨迹。
关键：答案证据（Doc B）与原始问题几乎无词面重叠，只能靠"桥接实体"两跳串起来。"""
import math
import re
from collections import Counter


DOCS = [  # ---------- 极简向量库（词袋 + 余弦）----------
    "张三是风控系统的负责人。",              # Doc A：桥接实体（张三 <-> 风控系统）
    "风控系统的存储层基于 PostgreSQL 构建。",  # Doc B：答案证据，几乎不含问题词
    "李四是推荐系统的负责人。",              # 干扰项
    "推荐系统使用 Redis 做缓存。",           # 干扰项
]


def embed(text: str) -> Counter:
    return Counter(re.findall(r"[a-zA-Z]+|[\u4e00-\u9fff]", text.lower()))


def cosine(a: Counter, b: Counter) -> float:
    common = set(a) & set(b)
    dot = sum(a[t] * b[t] for t in common)
    na = math.sqrt(sum(v * v for v in a.values()))
    nb = math.sqrt(sum(v * v for v in b.values()))
    return dot / (na * nb) if na and nb else 0.0


class VectorStore:
    def __init__(self, docs):
        self.docs = [(d, embed(d)) for d in docs]

    def search(self, query: str, k: int = 2):
        q = embed(query)
        ranked = sorted(self.docs, key=lambda d: cosine(q, d[1]), reverse=True)
        return [d for d, e in ranked[:k] if cosine(q, e) > 0]


STORE = VectorStore(DOCS)


def naive_rag(question: str) -> str:  # 传统 RAG：固定用原问题检索一次
    docs = STORE.search(question, k=2)
    ctx = " | ".join(docs)
    print(f"  [传统RAG] 用原问题检索(1次) k=2 -> {docs}")
    if "PostgreSQL" in ctx:
        return "风控系统使用 PostgreSQL。"
    return "抱歉，资料中未提到该系统使用的数据库。"


class AgenticModel:  # Agentic RAG：模型决定检索几次、每次查什么
    """确定性假模型：先查负责人->拿到系统名->改写查询补数据库信息。"""

    def __init__(self):
        self.round = 0

    def decide(self, context: list) -> dict:
        self.round += 1
        joined = " ".join(context)
        if self.round == 1:
            return {"action": "search", "query": "张三 负责 系统"}
        if "风控系统" in joined and "PostgreSQL" not in joined:
            return {"action": "search", "query": "风控系统 存储 数据库"}
        if "PostgreSQL" in joined:
            return {"action": "answer",
                    "answer": "张三负责的风控系统使用 PostgreSQL。"}
        return {"action": "answer", "answer": "资料不足以回答。"}


def agentic_rag(question: str, max_search: int = 4) -> str:
    model = AgenticModel()
    context = []
    for step in range(1, max_search + 1):
        decision = model.decide(context)
        if decision["action"] == "answer":
            print(f"  [AgenticRAG] step{step} 决策=answer")
            return decision["answer"]
        docs = STORE.search(decision["query"], k=1)
        context += docs
        print(f"  [AgenticRAG] step{step} 决策=search "
              f"query={decision['query']!r} -> {docs}")
    return "多轮检索仍无足够依据，需人工确认。"


def run() -> None:
    q = "张三负责的系统用了什么数据库？"
    print("== 传统 RAG ==")
    print("  最终答案：", naive_rag(q))
    print("== Agentic RAG（自主改写多轮检索）==")
    print("  最终答案：", agentic_rag(q))


if __name__ == "__main__":
    run()
```
保存为 `ladder5_agentic_rag.py`，运行 `python ladder5_agentic_rag.py`。完整预期输出：
```text
== 传统 RAG ==
  [传统RAG] 用原问题检索(1次) k=2 -> ['张三是风控系统的负责人。', '李四是推荐系统的负责人。']
  最终答案： 抱歉，资料中未提到该系统使用的数据库。
== Agentic RAG（自主改写多轮检索）==
  [AgenticRAG] step1 决策=search query='张三 负责 系统' -> ['张三是风控系统的负责人。']
  [AgenticRAG] step2 决策=search query='风控系统 存储 数据库' -> ['风控系统的存储层基于 PostgreSQL 构建。']
  [AgenticRAG] step3 决策=answer
  最终答案： 张三负责的风控系统使用 PostgreSQL。
```
**看懂这段对比，你就抓住了本章、乃至全书最核心的一条分界线**。传统 RAG 用原问题检索一次，召回的是两条「负责人」片段，压根没碰到 PostgreSQL，只能如实回答「未提到」——它不是不聪明，是流程写死只查一次。Agentic RAG 第一步查到「张三→风控系统」，发现还缺数据库信息，**自主改写查询**成「风控系统 存储 数据库」，第二步精准补上 PostgreSQL，第三步才作答。次数不是写死的，是问题难度决定的。

## 逐行讲解——注意「控制权」的转移

- `AgenticModel.decide` 是整个设计的心脏：它每一步都输出一个 `search` 或 `answer` 的结构化决策。这就是把「要不要再检索」的决定权，从代码交给了模型。
- `for step in range(max_search)` 依然是**硬性上限**——即便控制权给了模型，代码仍握着「最多查 4 次」的最终否决权。**自主 ≠ 失控**，这是第 18 章的铁律，也和阶梯 1 的「步数上限」、阶梯 4 的「重规划次数上限」一脉相承。
- 第二步检索用的是改写后的 `"风控系统 存储 数据库"`，而**非原始 question**。这是关键：模型可以改写查询，第一轮查「张三负责哪个系统」，拿到「风控系统」后，第二轮改写成「风控系统 存储 数据库」，精准补上缺失证据。这正是 CRAG/Self-RAG 里「检索不佳则改写查询重试」的核心动作 [来源](https://docs.langchain.com/oss/javascript/langgraph/agentic-rag)。
- `answer` 分支由模型自己判断「证据够了」。对简单问题它可能第一轮就 answer（相当于不检索或检索一次），对多跳问题它会连查几轮——**这就是「模型决定流程」与「代码决定流程」的分水岭**。

用一张图钉死这条分界线：
```text
┌────────────────────────────────────────────────────────────┐
│  传统 RAG：流程由【代码】决定  →  这是"工作流(workflow)"       │
│  Agentic RAG：流程由【模型】决定 →  这才是"Agent"             │
│                                                            │
│  分界线：谁在决定"下一步做什么"？                             │
└────────────────────────────────────────────────────────────┘
```
## 真实系统对应

**官方公开机制**：Anthropic《Building Effective Agents》把「workflow 是预定义代码路径编排 LLM、agent 是 LLM 动态决定自身流程」作为核心区分 [来源](https://www.anthropic.com/engineering/building-effective-agents)；LangGraph 的 Agentic RAG 教程给出了可复现的实现——在检索后加一个「文档相关性打分」节点，相关就去生成、不相关就改写问题重试 [来源](https://docs.langchain.com/oss/javascript/langgraph/agentic-rag)。业界把 Self-RAG、CRAG、Adaptive RAG 都视为「同一个自主循环」的变体：重检索、给自己的检索打分、检索差就改写查询、作答前再自评。**通用工程模式**：「模型输出结构化 search/answer 决策 + 代码握硬性上限 + 改写查询」是可迁移到任何厂商的骨架。**教学参考实现**：上面的 `AgenticModel` 和词袋向量库仅为让对照轨迹可逐字复核，真实模型的决策每次可能不同、也可能出错。

要点明一个边界：**Agentic RAG 不是「更好」，而是「更贵但更强」**。业界的经验是，它比单次 RAG 多消耗 2~4 倍的 token 和延迟，只在「可度量的一部分多跳/复杂问题」上值这个价，对简单单跳问题完全不值 [来源](https://docs.langchain.com/oss/javascript/langgraph/agentic-rag)。正确姿势是**分流**：简单问题走传统 RAG（快、省），检测到多跳/复杂才升级到 Agentic RAG。

## 生产踩坑

| 症状 | 根因 | 如何观测与复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| 多跳问题答不全 | 传统 RAG 固定只检索一次 | 用「A 的 B」型无词面重叠问题复现 | 升级 Agentic RAG、改写查询多轮检索 | 单跳问题一次检索够 |
| 简单问题也变慢变贵 | 一刀切全用 Agentic RAG | 统计单跳题的延迟与 token | 按问题分流，简单走传统 RAG | 全是复杂多跳场景另算 |
| 模型无限改写检索烧钱 | 无检索次数上限 | 让证据永远召回不到复现 | `max_search` 硬上限、触顶转人工 | 明确可长检索的离线任务另算 |
| 模型不输出合法决策 JSON | 结构化输出不稳 | 让模型返回非 JSON 文本复现 | 用函数调用/强约束、解析失败重试 | 支持严格结构化输出时较少见 |
| 改写后的查询越改越偏 | 缺相关性打分、盲目改写 | 观测每轮召回相关性 | 加检索结果打分、无关才改写 | 语料小、召回稳定时影响小 |
| 检索结果过长撑爆上下文 | 每轮把全部召回并入上下文 | 让召回返回大段文本复现 | 每条截断、只取 top-k、去重 | 结果本就短小时无需处理 |

## 思考：你怎么判断一个问题该用传统 RAG 还是 Agentic RAG？「控制权」到底从谁转移到了谁？

### 回答

先说控制权：从**代码**转移到了**模型**。传统 RAG 里，检索几次、用什么查，全写死在代码里，模型只是最后拿着固定检索结果作答，无权决定流程；Agentic RAG 里，模型每一步都输出「继续检索还是作答」的结构化决策，是模型在决定「下一步做什么」——这正是 workflow（代码编排）与 agent（模型自主）的分界。再说怎么判断用哪个：核心是**成本/收益权衡**，默认走传统 RAG，因为它一次检索一次生成、又快又省，对 80% 的单跳事实型问题足够；当出现「多跳信号」时才升级 Agentic RAG。多跳信号包括：问题里有「的那个/它的/相比之下」等指代或比较词，或第一次检索的结果相关性置信度很低（召回的片段答不上问题）。Agentic RAG 每步多一次决策调用，延迟和成本是传统的 2~4 倍，只在「可度量的那部分复杂问题」上值这个价，绝不该一刀切全面替换。所以正确姿势是分流：简单问题传统 RAG，检测到多跳/低置信才动态升级，用评估集验证这条分流线值不值。

### 面试精简表达

控制权从代码转移到模型（谁决定下一步：代码=工作流，模型=Agent）。判断用哪个靠成本收益：默认传统 RAG（快省，够应付单跳）；出现指代/比较词等多跳信号或首检索置信度低时升级 Agentic RAG（贵 2~4 倍，只在复杂问题上值）。别一刀切，按问题分流并用评估集验证。

### 反例

如果你的场景全是复杂多跳、且对准确率极度敏感、对延迟不敏感（比如离线的尽调报告生成、法律条文交叉核验），那么默认就上 Agentic RAG、甚至更激进的多轮自反思，是合理的——此时「贵 2~4 倍」换来的准确率提升完全值得，分流反而多余。反过来，如果全是「今天星期几」式单跳问题，连传统 RAG 都嫌重，直接让模型回答或做一次简单检索即可。判据始终是问题分布与延迟/成本约束，不存在「Agentic RAG 永远更好」。

## 机制推导：为什么「改写查询」是 Agentic RAG 的灵魂

很多人以为 Agentic RAG 的关键是「多检索几次」，其实多检索几次只是表象，**灵魂是「每次检索用的查询可以不同」**。回看演示：如果第二次检索还是用原问题「张三负责的系统用了什么数据库」，召回的仍是那两条「负责人」片段，查一百次也捞不到 PostgreSQL——因为 Doc B 与原问题没有词面/语义重叠。真正解决问题的是第二步把查询**改写**成「风控系统 存储 数据库」，用第一步查到的桥接实体（风控系统）作为新查询的锚点，才对上了 Doc B。

由此推出两条工程结论。其一，**查询改写的质量决定 Agentic RAG 的上限**：改写得准（抓住缺失的那部分信息、用上已知的桥接实体），两跳就能补齐；改写得偏（还是围着原问题打转），加多少轮都白搭。所以 CRAG/Self-RAG 都强调在改写前先给「已召回文档是否相关/是否够用」打分，让改写有的放矢 [来源](https://docs.langchain.com/oss/javascript/langgraph/agentic-rag)。其二，**改写要有锚点**：好的改写不是把原问题换几个同义词，而是「把上一轮拿到的中间实体嵌进去」——这和阶梯 4 规划里「上一步产出喂下一步」是同一个思想，只不过阶梯 4 由代码显式串联，阶梯 5 由模型自主串联。这条从「代码串联」到「模型串联」的演进，正是阶梯 4 通向阶梯 5 的内在逻辑。
