## 真实问题

三周结束，小林把六级阶梯全跑通了。可当他准备把这些写进简历时，又卡住了：六个脚本散落在六个文件夹里，`ladder1_react.py`、`ladder5_agentic_rag.py`……除了他自己，没人知道它们各自证明了什么、彼此是什么关系。他试着在简历上写「熟悉 Agent 开发，做过 ReAct、RAG、多智能体」，结果面试官追问「你这几个项目之间是什么关系？你在阶梯 5 遇到的最大权衡是什么？」他答不上来——因为他跑通了代码，却没沉淀「设计权衡」这层认知。

这就是学习的最后一公里：**跑通不等于会讲，会讲不等于能上生产**。这一节做三件事：先给一个可运行的「作品集收口器」，把六级成果登记成一份能讲清关系与权衡的清单；再讲清从「本章六级」到「下一章生产化」之间那条必须跨越的鸿沟；最后用多道「思考 + 回答」把全章方法论收口，直接对齐高频面试题。

## 原理：作品集的价值不在代码量，在「可讲清的权衡」

一个 Agent 作品集，面试官真正在意的从来不是「你写了多少行代码」或「你用了多少框架」，而是三个可讲清的东西：

- **能力增量**：每一级相比上一级「新增了哪一个变量」。这条线证明你理解「Agent 的复杂度是逐层叠加的」，而不是一上来就堆一个大杂烩。
- **设计权衡**：每一级你做了什么取舍、为什么。比如阶梯 4「规划让多跳可控，但代价是多一次模型调用」，阶梯 5「控制权从代码转移到模型，灵活但更难约束」。能讲清权衡，才证明你不是抄教程，而是真懂。
- **数字证据**：每一级用什么可复核的数字证明它有效。阶梯 6 的忠实度从 0 到 0.916、回归从 FAILED 到 PASSED，就是最有说服力的证据。

把这三条对每一级都答得出来，六个零散脚本就串成了一条**成长故事线**：从「只会调一个工具」到「能让模型自主决策检索、还能用指标守住质量」。这条线，正是简历上「Agent 开发能力」四个字背后真正值钱的东西。

## 最小可运行演示

下面的「作品集收口器」把六级阶梯登记成结构化卡片，并按一条硬标准——**有演示、有沉淀踩坑的 README、能讲清权衡、有数字证据**——判断每一级是否达到「可写进简历」。它不联网、不需要 API Key（Application Programming Interface Key，接口密钥），是本章最后一段可执行代码。
```python
"""作品集收口器（纯 Python，离线可运行）：
把阶梯 1~6 的成果登记成一份可展示、可自检的作品集清单，
并按「能不能讲清设计权衡」这条硬标准，判断每一级是否达到「可写进简历」。"""
from __future__ import annotations

from dataclasses import dataclass


@dataclass
class LadderCard:
    level: int
    name: str
    new_variable: str      # 本级新增的那一个变量
    tradeoff: str          # 能不能讲清的设计权衡
    metric: str            # 用什么数字证明它有效
    has_demo: bool         # 是否有可运行演示
    has_readme: bool       # 是否沉淀了含踩坑的 README


PORTFOLIO = [
    LadderCard(1, "单工具 ReAct Agent", "跑通 Thought/Action/Observation 循环",
               "为何要显式循环而非一次问答：多步任务需要观测反馈再决策",
               "两步内算出 210.0，轮次上限兜底不空转", True, True),
    LadderCard(2, "多工具路由", "在多个工具间选对",
               "选对靠工具描述而非模型更聪明：清晰描述命中率显著高于模糊描述",
               "清晰描述选对、模糊描述盲选第一个", True, True),
    LadderCard(3, "分层记忆", "跨会话长期记忆",
               "短期/长期/工具观测三层各司其职，长期记忆要过滤噪声",
               "跨会话召回『素食+邮件通知』偏好", True, True),
    LadderCard(4, "先规划再执行", "把多跳任务先拆解成有序子任务",
               "规划让多跳可控、失败可重规划，代价是多一次模型调用",
               "城市→国家→货币三跳按序完成", True, True),
    LadderCard(5, "Agentic RAG", "检索时机与查询由模型决定",
               "控制权从代码转移到模型：这是工作流与 Agent 的分界线",
               "传统一次检索答不出、Agentic 两跳查到 PostgreSQL", True, True),
    LadderCard(6, "评估与回归", "用指标守住质量、防止退化",
               "没有回归集就同时失去『判断好坏』与『防退化』两种能力",
               "忠实度/相关性/召回三指标出数字，FAILED→PASSED", True, True),
]


def is_resume_ready(card: LadderCard) -> bool:
    """可写进简历的硬标准：有演示、有沉淀踩坑的 README、能讲清权衡、有数字。"""
    return card.has_demo and card.has_readme and bool(card.tradeoff) and bool(card.metric)


def run() -> None:
    ready = 0
    print("== 六级项目阶梯 · 作品集自检 ==")
    for c in PORTFOLIO:
        ok = is_resume_ready(c)
        ready += ok
        flag = "可展示" if ok else "待补齐"
        print(f"阶梯{c.level} {c.name}[{flag}]  新增变量：{c.new_variable}")
        print(f"        能讲清的权衡：{c.tradeoff}")
        print(f"        数字证据：{c.metric}")
    print("-" * 40)
    print(f"作品集完成度：{ready}/{len(PORTFOLIO)} 级达到『可写进简历』标准")
    if ready == len(PORTFOLIO):
        print("结论：六级齐备，可作为一条完整的成长故事线讲给面试官")
    else:
        print("结论：仍有阶梯缺演示/README/权衡/数字，先补齐再展示")


if __name__ == "__main__":
    run()
```

这段收口器的意义在于：它把「跑通六个脚本」这件事，翻译成了面试官能听懂的语言——每一级新增什么变量、做了什么权衡、有什么数字。当你能对着这份清单把六级串成一条故事线，你才真正「学会」了，而不只是「跑过」。

## 从六级阶梯到生产：那条还没跨过的鸿沟

必须诚实地划清边界：本章练的阶梯 1~6，全部是**离线、单机、教学参考实现**——确定性假模型、词袋向量库、内存里的记忆。它证明你「懂原理、能手写」，但它离「能上线服务真实用户」还差一整层。Anthropic 在《Building Effective Agents》里反复强调：能用简单工作流解决就别上 Agent，且任何自主系统上线前都要有充分的护栏、测试与可观测 [来源](https://www.anthropic.com/engineering/building-effective-agents)。这条「生产化鸿沟」至少包含四块本章没有覆盖的内容：

- **护栏（Guardrails）**：输入输出的安全过滤、权限校验、危险动作的人工审批。本章的工具直接执行，生产里有副作用的动作必须有闸门。
- **可观测（Observability）**：结构化日志、Trace（追踪）、指标看板、告警。本章靠 `print` 看输出，生产里要能事后回放每一次决策。
- **持久化与并发**：本章记忆在内存里、进程一关就没；生产要落库、要支持多用户并发、要处理会话隔离。
- **部署与成本**：真实模型有延迟、有 Token（令牌）成本、有限流；本章的假模型零成本零延迟，生产要做缓存、批处理、降级与预算控制。

GenAI_Agents 与 agents-towards-production 两个开源教程集，正是分别覆盖「从基础到高级的案例」与「生产级的护栏、评估、监控、部署」 [来源](https://github.com/NirDiamant/GenAI_Agents) [来源](https://github.com/NirDiamant/agents-towards-production)。本章帮你造好了六个零件、把每个零件的原理讲透；把它们组装成一个带护栏、可观测、能部署的完整系统，是下一章综合实战要做的事。看清这条鸿沟，你才不会把「Demo 跑通」误当成「可以上线」——这本身就是一种成熟。

## 真实系统对应

**官方公开机制 / 权威资料**：Anthropic《Building Effective Agents》给出了「优先用简单方案、Agent 需充分测试与护栏」的工程原则，以及工作流与 Agent 的分界 [来源](https://www.anthropic.com/engineering/building-effective-agents)；Lilian Weng 的《LLM Powered Autonomous Agents》把规划、记忆、工具使用作为自主 Agent 的三大支柱系统综述 [来源](https://lilianweng.github.io/posts/2023-06-23-agent/)，恰好对应本章阶梯 4、3、1~2。**通用工程模式**：「按阶梯逐级隔离变量、每级沉淀含权衡的作品、看清 Demo 与生产的鸿沟」是可迁移到任何技能学习的方法论。**教学参考实现**：本章六级全部离线可运行，是为讲清原理构造的最小骨架，不等同于任何生产系统架构；从 Demo 到生产还需护栏、可观测、持久化、部署四层，见下一章。

需要点明边界：本章不声称跑通六级就具备生产能力，也不把任何开源教程集里的具体实现当作唯一正确答案；框架 API、模型能力、成本数字都会变化，落地时以当前官方文档与你的真实业务数据为准。

## 思考：面试官让你「讲一个你做过的 Agent 项目」，用本章六级阶梯怎么答出层次？

### 回答

用「一条成长故事线」来答，而不是罗列孤立的技术点。开头先给主线：「我用阶梯法练 Agent，每一级只新增一个变量，最后攒成一条从单工具到 Agentic RAG 的能力曲线。」然后逐级点出「新增变量 + 权衡 + 数字」三件套：阶梯 1 手写 ReAct 循环，理解了「模型只提议、运行时才执行」和「多步任务要观测反馈再决策」；阶梯 2 加多工具，踩到的坑是「选不对」，我把成败定位到工具描述，用清晰描述和模糊描述做了对照实验；阶梯 3 加分层记忆，权衡是「长期记忆要过滤噪声，否则全是『好的谢谢』」；阶梯 4 加规划，权衡是「先拆解让多跳可控，代价是多一次模型调用」；阶梯 5 上 Agentic RAG，这是最关键的一跳——「控制权从代码转移到模型」，我亲手对比了传统一次检索答不出、Agentic 两跳查到答案；阶梯 6 建评估回归集，用忠实度/相关性/召回三个指标，让「升级值不值」变成 FAILED→PASSED 的数字。最后收口一句诚实的边界：「这六级是离线 Demo，证明我懂原理、能手写；真上生产还需护栏、可观测、持久化、部署四层。」这样从主线到逐级权衡到诚实边界，层次和成熟度就都出来了。

### 面试精简表达

用一条成长故事线：阶梯法逐级只加一个变量，每级讲「新增变量+权衡+数字」，重点讲阶梯 5「控制权从代码转移到模型」，收口点明「Demo 懂原理、生产还差护栏/可观测/持久化/部署四层」。

## 思考：为什么说阶梯 4 到阶梯 5 之间那条线，是全章最重要的分界线？

### 回答

因为它就是「工作流（Workflow）」与「Agent」的本质分界，也是 Anthropic《Building Effective Agents》反复强调的那条线 [来源](https://www.anthropic.com/engineering/building-effective-agents)。阶梯 4 及以下，无论多工具、记忆还是规划，**流程的控制权始终在你写的代码手里**：是你决定先调哪个工具、按什么顺序执行子任务，模型只是在你划定的轨道上填空。这叫工作流——路径由代码预先编排，可预测、好调试、成本可控。而到了阶梯 5 的 Agentic RAG，**控制权发生了转移：检索几次、每次查什么、什么时候停下来作答，都由模型在运行时自己决定**，你的代码只提供工具和循环骨架。这就是 Agent——模型自主决定流程。这条线之所以最重要，是因为它决定了两件事的走向：一是能力上限，Agent 能处理你事先无法穷举路径的开放任务；二是工程代价，控制权交出去后，可预测性下降、调试变难、成本和安全都更难约束。所以真正的工程判断不是「越自主越好」，而是「能用工作流解决的就别上 Agent」——先看任务是否真的需要模型自主决策，需要才跨过这条线。理解这条线，你才不会盲目追求「全自主」，也不会在简单场景里为一次单跳问答上多轮自主检索。

### 面试精简表达

阶梯 4 及以下流程由代码编排（工作流，可预测好调试），阶梯 5 流程由模型自主决定（Agent，能处理开放任务但更难约束）；这条线就是工作流与 Agent 的分界，工程判断是「能用工作流就别上 Agent」。

## 思考：学完本章六级，接下来该怎么把「离线 Demo」推进到「能上线」？

### 回答

按「先看得见、再堵住会赔钱的洞、最后组装上线」的顺序推进，而不是急着把假模型换成真模型就部署。第一步，把假模型换成真模型时先加**可观测**：给每一级的每一步打结构化日志（哪一级、调了什么工具、传了什么参数、耗时多少、模型说了什么),这样真实模型的不确定性一旦出问题，你有 Trace 可回放。第二步，补**护栏**：有副作用的工具（下单、删除、扣款）加权限校验和人工审批闸门，输入输出加安全过滤——本章工具直接执行是教学简化，生产绝不能裸奔。第三步，做**持久化与并发**：把内存里的记忆落库、做会话隔离、支持多用户并发，否则进程一重启用户偏好全没。第四步，做**成本与部署**：真实模型有延迟、有 Token 成本、有限流，要上缓存、降级、预算上限，再考虑部署形态。贯穿这四步的是本章阶梯 6 的评估回归集——每推进一步都重跑它，掉分就拦截。这个顺序的逻辑和「学习要隔离变量」一脉相承：一次只推进一层，出问题时新推进的那层最可疑。把这四层补齐，六个离线零件才真正组装成一个能服务真实用户的系统，这也正是下一章综合实战的主线。

### 面试精简表达

顺序是可观测（打 Trace）→护栏（危险动作加审批与过滤）→持久化并发（记忆落库、会话隔离）→成本与部署（缓存/降级/预算），每步都用阶梯 6 的回归集守住；一次只推进一层，出问题时新层最可疑。
