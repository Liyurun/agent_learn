## 真实问题

一位学员在群里贴出他的第一个 Agent：用了某框架，三行代码 `agent.run(...)` 就能回答带计算的问题。他很得意，直到面试官问：「你的 Agent 每一步在做什么？Observation 特别长会怎样？」他答不上来——框架把 ReAct（Reasoning and Acting，推理与行动）循环藏进了黑盒，他只学会了调 API（Application Programming Interface，应用程序接口），没看清里面到底发生了什么。面试官的评语是：「会用框架，但不理解原理，遇到框架不支持的定制需求就抓瞎。」

这一节要解决的正是这个问题：**阶梯 1 的真正价值，不是用框架跑通一个 Demo，而是先脱离框架、用几十行代码把 ReAct 循环的骨架亲手写一遍**，让你对框架「到底帮你做了什么」心里有数。看得懂草稿纸上 Thought/Action/Observation 的流动，就是本级的验收线。

## 原理：ReAct 循环的四个动作与两条终止

ReAct 出自 ICLR 2023 论文，核心思想是让模型把**推理轨迹（reasoning trace）**和**行动（action）**交织输出：模型先写一段 Thought（我该怎么办），再决定一个 Action（用哪个工具、传什么参数），运行时执行后返回 Observation（工具给了什么），模型据此再写下一段 Thought，如此循环，直到给出最终答案 [来源](https://arxiv.org/abs/2210.03629)。这套「让推理外显」的格式之所以关键，是因为它让模型的决策过程变得**可解析、可观测、可干预**——代码能读到 Thought/Action，才能执行工具、才能在出错时纠偏。

把循环压成必须刻进脑子的要点：

- **四个动作**：Thought（推理）→ Action（决定用哪个工具）→ Action Input（参数）→ Observation（工具返回），后者拼回草稿纸，进入下一轮 Thought。
- **两条终止条件，缺一不可**：一是**模型主导**——模型认为信息够了，输出 `Final Answer` 自然终止；二是**代码主导**——`for step in range(max_steps)` 的硬性步数上限，防止模型陷入「反复调用工具却不收敛」而无限烧 token（Token，模型处理文本的最小计费单位）。
```text
      ┌─────────────────────── ReAct 循环 ───────────────────────┐
      │                                                          │
   Question ──▶ [LLM] ──Thought──▶ 需要工具？                     │
      ▲            │                  │是                        │
      │            │否                ▼                          │
      │       Final Answer      Action + Input ──▶ [工具执行]      │
      │            │                             │                │
    (结束)◀────────┘              Observation ◀───┘                │
                                    │                            │
                                    └──── 拼回草稿纸，回到 LLM ─────┘
```
## 最小可运行演示

下面用一个确定性的 `ScriptedModel` 代替真实大模型，把 Thought → Action → Observation → 再 Thought 的完整闭环跑一遍。它只依赖标准库，不联网、不需要 API Key，是 ReAct 循环的「可执行版时序图」。工具是一个带正则防御的计算器——工具三要素（名字、说明用途与参数的 docstring、可执行函数体）的最小实现。
```python
"""阶梯1：不依赖框架、手写一个完整 ReAct 循环（纯 Python，无需 API Key）。"""
import re


def calculator(expression: str) -> str:
    """计算一个数学表达式，如 '320 * 0.75'。"""
    if not re.fullmatch(r"[\d\s+\-*/().]+", expression or ""):
        return "错误：表达式含非法字符"
    try:
        return str(eval(expression))  # 教学演示；生产应换安全求值库
    except Exception as exc:  # noqa: BLE001
        return f"计算错误：{exc}"


TOOLS = {"calculator": calculator}


class ScriptedModel:
    """确定性假模型：按 ReAct 格式逐步返回 Thought/Action，最后给 Final Answer。"""

    def __init__(self) -> None:
        self.step = 0
        self.script = [
            "Thought: 先算七五折，即 320 * 0.75\nAction: calculator\nAction Input: 320 * 0.75",
            "Thought: 再减 30\nAction: calculator\nAction Input: 240.0 - 30",
            "Thought: 我知道答案了\nFinal Answer: 实付 210.0 元。",
        ]

    def __call__(self, prompt: str) -> str:
        out = self.script[min(self.step, len(self.script) - 1)]
        self.step += 1
        return out


llm = ScriptedModel()

SYSTEM = """你是一个会用工具的助手。请严格按以下格式逐步思考：
Thought: 你的推理
Action: 工具名
Action Input: 传给工具的参数
当你能回答时，输出：
Thought: 我知道答案了
Final Answer: 最终答案
可用工具：calculator(expression) —— 计算数学表达式。"""


def _parse(text: str, tag: str) -> str:
    for line in text.splitlines():
        if line.strip().startswith(tag):
            return line.split(tag, 1)[1].strip()
    return ""


def react(question: str, max_steps: int = 5) -> str:
    scratchpad = f"Question: {question}\n"
    for step in range(1, max_steps + 1):
        raw = llm(SYSTEM + "\n" + scratchpad)
        scratchpad += raw + "\n"
        thought = _parse(raw, "Thought:")
        if "Final Answer:" in raw:
            print(f"[step {step}] Thought: {thought}")
            return raw.split("Final Answer:")[-1].strip()
        action = _parse(raw, "Action:")
        action_input = _parse(raw, "Action Input:")
        print(f"[step {step}] Thought: {thought}")
        print(f"[step {step}] Action: {action}({action_input})")
        if action in TOOLS:
            obs = TOOLS[action](action_input)
        else:
            obs = f"错误：没有名为 {action} 的工具"
        print(f"[step {step}] Observation: {obs}")
        scratchpad += f"Observation: {obs}\n"
    return "已达最大步数，未能得出答案。"


if __name__ == "__main__":
    ans = react("一件商品原价 320 元，打七五折后再减 30，实付多少？")
    print("FINAL:", ans)
```
保存为 `ladder1_react.py`，运行 `python ladder1_react.py`。完整预期输出：
```text
[step 1] Thought: 先算七五折，即 320 * 0.75
[step 1] Action: calculator(320 * 0.75)
[step 1] Observation: 240.0
[step 2] Thought: 再减 30
[step 2] Action: calculator(240.0 - 30)
[step 2] Observation: 210.0
[step 3] Thought: 我知道答案了
FINAL: 实付 210.0 元。
```
**看懂这段轨迹，就是阶梯 1 的验收线**。你要能指着每一行说出：step 1 的 Thought 是推理、Action 是决定用计算器、Observation 是工具返回的 `240.0`；step 2 把 `240.0` 拿来继续算；step 3 模型宣布 `Final Answer`，两条终止条件里的「模型主导」这条生效。这四个词不再是理论名词，而是你亲眼看它们在草稿纸上流动。

## 逐行讲解（对照第 4、6 章）

- `calculator` 是**工具三要素**的最小实现：清晰的**名字**、一段说明**用途和参数**的 docstring、一个**可执行函数体**。第一行的正则校验是「工具内部自己做防御」的雏形——不要指望模型永远传合法输入。
- `SYSTEM` 提示把 ReAct 的**输出格式**用自然语言「教」给模型。ReAct 之所以有效，就是靠这套 `Thought/Action/Observation` 的固定格式让推理外显，代码才能解析和干预 [来源](https://arxiv.org/abs/2210.03629)。
- `react` 里的 `scratchpad`（草稿纸）是灵魂：它把**历史推理 + 工具观测**不断累加，作为下一次调模型的上下文。所谓「循环」，就是「把上一步的观测拼回提示，再问一次模型」。
- `for step in range(max_steps)` 是**硬性终止条件**。这一行看似不起眼，却是把 Demo 和事故分开的关键——没有它，一旦模型陷入反复调用工具却不收敛，就会无限烧 token。
- `if "Final Answer:" in raw` 是**模型主导的终止条件**。两种终止条件缺一不可：只靠模型宣布可能永不收敛，只靠步数上限则正常问题也会被硬截断。

## 真实系统对应

**官方公开机制**：ReAct 的「推理—行动交织」范式与两种终止的思路来自 ICLR 2023 论文 [来源](https://arxiv.org/abs/2210.03629)。真实框架把这套循环封装好了：smolagents 用 `@tool` 装饰器注册工具、`CodeAgent` 接管循环 [来源](https://github.com/NirDiamant/GenAI_Agents) 里也有大量单工具起步的案例。以 smolagents 为例，等价逻辑被压缩成几行：
```python
from smolagents import CodeAgent, tool


@tool
def calculator(expression: str) -> str:
    """计算数学表达式。
    Args:
        expression: 形如 '320 * 0.75' 的表达式
    """
    return str(eval(expression))


agent = CodeAgent(tools=[calculator], model=your_model)
agent.run("原价 320 打七五折再减 30，实付多少？")
```
同样是 ReAct，框架把「草稿纸拼接、格式解析、步数控制」全接管了。**通用工程模式**：「先手写、再用框架」这个顺序不能反——反过来你只学会了 API，没学会原理。**教学参考实现**：上面的 `ScriptedModel` 只为让输出可逐字复核，不代表任何真实模型的推理逻辑；真实模型的 Thought 文本每次都会不同。

要点明一个边界：现代模型接口大多提供**函数调用（function calling）**能力，能强制结构化输出工具名与参数，比让模型「按文本格式吐 Thought/Action」更稳。手写文本版 ReAct 是为了让你看清循环骨架；生产里若模型支持函数调用，应优先用它来避免格式解析失败（详见第 8 章）。

## 生产踩坑

| 症状 | 根因 | 如何观测与复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| `_parse` 取空、工具调不到 | 模型偶尔不按 `Action:` 格式输出 | 让假模型返回一行不含 `Action:` 复现 | 用函数调用强制结构化，或解析失败回喂「请重按格式」 | 模型支持严格结构化输出时较少见 |
| 循环永不终止、token 烧光 | 只靠 `Final Answer` 无步数上限 | 让工具总返回「查无结果」复现 | `for step in range(max_steps)` 兜底 | 明确单步任务可不设循环 |
| Observation 特别长撑爆上下文 | 工具原样回传大段 JSON | 让工具返回上万字符复现 | 工具内先裁剪/摘要、只回字段子集、超长落盘回引用 ID | 结果本就短小的工具无需裁剪 |
| 计算器被注入任意代码 | 直接 `eval` 用户/模型输入 | 传入 `__import__('os')` 复现 | 正则白名单 + 换安全求值库 | 完全可信内部输入风险较低 |
| 换个模型就跑不通 | 提示词格式与该模型习惯不合 | 换模型后观测格式偏差 | 用函数调用抹平差异、或按模型微调格式提示 | 固定单一模型时影响小 |

## 思考：为什么必须「先手写 ReAct，再用框架」，顺序反过来会怎样？

### 回答

因为原理和 API 是两层不同的知识，顺序反了会让你误以为学会了、实则只学到表层。先手写，你会亲手实现草稿纸拼接、格式解析、步数控制、工具执行这四件事，从而对「循环到底怎么转、在哪里可能坏」有肌肉级的理解；之后再用框架，你会立刻看出框架帮你省掉了哪几件事，遇到框架不支持的定制需求（比如自定义终止条件、在某步插入人工审核）也知道从哪下手。反过来先用框架，`agent.run()` 三行就出结果，你会跳过所有细节，形成「我会做 Agent」的错觉；一旦面试官问「Observation 太长怎么办」「模型不按格式输出怎么办」，或者业务要求定制循环，你就抓瞎，因为这些细节都被黑盒吞了。手写付出的是几十行代码的成本，换来的是「看得懂黑盒、改得动黑盒」的能力，非常划算。

### 面试精简表达

先手写掌握循环骨架（草稿纸/解析/步数/执行）与故障点，再用框架就知道它省了什么、定制时从哪改；反过来只会调 API，遇到定制或追问就露怯。

### 反例

如果你的任务就是「快速验证一个想法能不能用 LLM 做出来」，且团队已有成熟框架封装，那么直接用框架起步、验证通过后再回头补原理，也是合理的——此时目标是「验证可行性」而非「学习原理」。判断标准是你的目标：学习就先手写，赶交付就先框架。但简历上要写「精通 Agent 开发」，手写这关躲不过去。

## 事故回放：一次「解析失败」如何拖垮整个循环

回到手写 ReAct 最常见的 bug。某学员的 Agent 在 100 次运行里有 7 次直接返回「已达最大步数」，却查不出原因。打印草稿纸后真相大白：这 7 次里，模型把 `Action Input` 写成了两行（第二行是补充说明），而 `_parse` 只取第一行含标签的内容，导致参数被截断，工具执行返回错误，模型看到错误又重试、再次两行输出，如此循环直到步数耗尽。

根因是**解析器对模型输出的格式波动没有容错**。修复有三条路，按优先级排：其一，若模型支持函数调用，直接换成结构化输出，从根上消灭文本解析；其二，若必须用文本格式，把「格式错了，请严格按单行 `Action Input:` 重新输出」作为 Observation 回喂给模型，让它自我修正；其三，`_parse` 做多行合并的兜底解析。优化前只有一条「偶发达到最大步数」的模糊现象；优化后，通过打印草稿纸把它精确定位到「多行 Action Input 解析截断」，并用函数调用彻底根治，7% 的失败率降到 0。这个案例再次印证阶梯 1 的核心价值——**看得见草稿纸，才修得了循环**。
