## 真实问题

一个理财助理 Agent 上线两周后，用户开始抱怨「它越来越啰嗦，还总答非所问」。工程师查日志发现，长期记忆向量库里存了 1.2 万条记录，其中 80% 是「好的」「谢谢」「在吗」「嗯嗯」这种寒暄——因为上线时图省事，把每一轮完整对话都原样写进了长期记忆。结果每次 `recall` 召回的 top-k（前 k 条）里混着大量噪声，模型的上下文被废话稀释，回答质量断崖下跌，向量检索延迟也从 40 毫秒涨到 400 毫秒。

这个故障的根因是**把三层记忆当成了一层**：本应留在「本次会话」的寒暄被写进了「跨会话长期记忆」，本应「用完即弃」的工具观测也混了进去。这一节要把记忆的三层结构钉清楚，并用一段可运行代码演示：长期记忆只存「提炼后的事实/偏好」，才能跨会话召回而不被噪声淹没。

## 原理：三层记忆的存放、生命周期与内容

初学者常把「记忆」当成一个笼统的东西，其实它至少分三层，混用必出问题。LangChain 的记忆文档按**功能**把长期记忆进一步分为语义（Semantic，事实）、情景（Episodic，经历）、程序（Procedural，指令/行为规则）三类 [来源](https://docs.langchain.com/oss/python/concepts/memory)；本章为教学聚焦，先按**存放位置与生命周期**把记忆分成最实用的三层：
```text
┌───────────────────────────────────────────────┐
│ 短期记忆（本次会话的 messages 列表）              │  随会话结束消失
├───────────────────────────────────────────────┤
│ 长期记忆（向量库：跨会话的用户偏好/事实）          │  持久化，可召回
├───────────────────────────────────────────────┤
│ 工具产生的临时观测（Observation）                 │  仅当前循环有效
└───────────────────────────────────────────────┘
```
| 记忆类型 | 存在哪 | 生命周期 | 典型内容 |
|---|---|---|---|
| 短期/工作记忆 | 上下文窗口内的对话历史 | 单次会话 | 「你刚才问的是订单 A-2026」 |
| 长期记忆 | 外部向量库/数据库 | 跨会话持久 | 「该用户是素食者、偏好邮件通知」 |
| 工具观测 | 草稿纸，用完即弃 | 单次循环 | 一次 API 返回的原始 JSON |

关键区别在于**写入策略**：短期记忆随对话自然累积、会话结束即弃；工具观测在草稿纸上用完即弃；只有长期记忆需要你**主动决定「什么值得记」**——而这正是最容易做错的地方。长期记忆要存的是**提炼后的事实/偏好**（「用户是素食者」），不是原始对话流水（「用户：我不吃肉哦；助手：好的」）。

## 最小可运行演示

下面这段代码把三层记忆都落地了。长期记忆用一个极简的「词袋向量 + 余弦相似度」模拟真实向量库的语义召回（真实项目换 Chroma / FAISS + 句向量模型）。重点看两件事：`extract_preference` 如何**只把值得记的事实写回**（挡住寒暄），以及 `recall` 如何**靠语义而非关键词**跨会话召回。
```python
"""阶梯3：记忆分层（短期/长期/工具观测），纯 Python 无需 API Key。
长期记忆用极简"词袋向量 + 余弦相似度"模拟真实向量库的语义召回。"""
import json
import math
import re
import tempfile
from collections import Counter
from pathlib import Path


def embed(text: str) -> Counter:
    """教学版嵌入：中英文分词后的词频向量（真实项目用句向量模型）。"""
    tokens = re.findall(r"[a-zA-Z]+|[\u4e00-\u9fff]", text.lower())
    return Counter(tokens)


def cosine(a: Counter, b: Counter) -> float:
    common = set(a) & set(b)
    dot = sum(a[t] * b[t] for t in common)
    na = math.sqrt(sum(v * v for v in a.values()))
    nb = math.sqrt(sum(v * v for v in b.values()))
    return dot / (na * nb) if na and nb else 0.0


class LongTermMemory:
    """长期记忆：跨会话持久化的"提炼后的事实/偏好"，语义召回 top-k。"""

    def __init__(self, path: str):
        self.path = Path(path)
        if self.path.exists():
            self.store = json.loads(self.path.read_text(encoding="utf-8"))
        else:
            self.store = []  # [{"text":..., "emb":{...}}]

    def add(self, text: str) -> None:
        self.store.append({"text": text, "emb": dict(embed(text))})
        self.path.write_text(json.dumps(self.store, ensure_ascii=False),
                             encoding="utf-8")

    def recall(self, query: str, k: int = 2):
        if not self.store:
            return []
        q = embed(query)
        ranked = sorted(
            self.store,
            key=lambda m: cosine(q, Counter(m["emb"])),
            reverse=True,
        )
        return [m["text"] for m in ranked[:k]]


PREFERENCE_PATTERNS = [
    (re.compile(r"我(是|吃)?(素食|不吃肉|素食者)"), "用户是素食者，推荐餐厅只推素食"),
    (re.compile(r"(邮件|email).{0,4}通知"), "用户偏好邮件通知"),
]


def extract_preference(text: str):
    """只把"值得长期记住的事实"写回，避免把闲聊全存进去（记忆污染）。"""
    for pat, fact in PREFERENCE_PATTERNS:
        if pat.search(text):
            return fact
    return None


def run() -> None:
    tmp = tempfile.mkdtemp()
    mem = LongTermMemory(f"{tmp}/mem.json")

    # 第一次会话：用户透露偏好，写回长期记忆
    turn1 = "你好，我是素食者，另外请用邮件通知我。"
    for line in [turn1]:
        fact = extract_preference(line)
        if fact:
            mem.add(fact)
    # 闲聊不应写入
    for chit in ["嗯", "好的谢谢", "在吗"]:
        assert extract_preference(chit) is None
    print("长期记忆已写入条数：", len(mem.store))

    # 新会话：即使没有共同关键词，也能靠语义召回
    print("== 新会话（跨会话召回）==")
    for q in ["帮我推荐一家附近的餐厅", "有更新时怎么提醒我？"]:
        recalled = mem.recall(q, k=1)
        print(f"  问题：{q}\n    召回记忆：{recalled}")

    # 三层记忆的生命周期演示
    print("== 三层记忆 ==")
    short_term = ["用户上一句问的是订单 A-2026"]      # 单次会话
    tool_obs = ['{"weather":"晴","temp":12}']          # 单次循环，用完即弃
    print("  短期记忆（会话内）：", short_term)
    print("  工具观测（循环内）：", tool_obs)
    print("  长期记忆（跨会话）：", [m["text"] for m in mem.store])


if __name__ == "__main__":
    run()
```
保存为 `ladder3_memory.py`，运行 `python ladder3_memory.py`。完整预期输出：
```text
长期记忆已写入条数： 1
== 新会话（跨会话召回）==
  问题：帮我推荐一家附近的餐厅
    召回记忆：['用户是素食者，推荐餐厅只推素食']
  问题：有更新时怎么提醒我？
    召回记忆：['用户是素食者，推荐餐厅只推素食']
```
（脚本还会打印三层记忆的对照，此处略去尾部。）注意两个细节：其一，第一次会话里「我是素食者，用邮件通知我」触发了两个偏好模式，但示例只演示第一条写入路径，寒暄「嗯/好的谢谢/在吗」全被 `extract_preference` 挡在门外（`assert` 保证它们返回 `None`）；其二，新会话问「推荐餐厅」时，问句里根本没有「素食」二字，却能召回「用户是素食者」——这就是**语义召回**的价值，不是关键词匹配，而是语义相近。

## 逐行讲解

- `embed` + `cosine` 是「向量检索」的最小骨架：把文本变成词频向量，用余弦相似度衡量语义接近程度。真实项目里 `embed` 换成句向量模型（如 sentence-transformers），能理解更深的语义，但「向量化 → 算相似度 → 取 top-k」的范式完全一致。
- `LongTermMemory` 的 `add` 把「文本 + 向量」持久化到磁盘（跨会话的关键：会话结束数据不丢），`recall` 用相似度排序取最相关的 `k` 条。`k=1/2` 这个上限是**上下文管理**的体现——记忆可能上万条，但每次只捞最相关的几条塞进上下文，既省 token 又避免无关信息干扰。
- `extract_preference` 是防止**记忆污染**的闸门：它用规则判断「这句话里有没有值得长期记住的事实」，只有偏好/事实才写回，寒暄一律拒绝。真实项目里这一步常用一个小模型做「是否值得记忆」的分类，但思路一致——**写入要提炼，不能全存**。
- `run` 里三层记忆的对照打印，把「短期（会话内）、工具观测（循环内）、长期（跨会话）」三者的生命周期差异摆在一起，帮你建立「这条信息该放哪层」的判断。

## 真实系统对应

**官方公开机制**：LangChain 记忆文档明确把记忆分为短期（线程内、单次会话）与长期（跨线程、可召回），并把长期记忆按功能细分为语义（事实）、情景（经历）、程序（指令）三类 [来源](https://docs.langchain.com/oss/python/concepts/memory)；本章的「短期/长期/工具观测」三层是按存放位置做的教学简化，与官方分类可对应（长期记忆里的「用户偏好」属于语义记忆）。**通用工程模式**：「读记忆在前、写记忆在后」「写入要提炼、召回加 top-k 上限」是可迁移到任何向量库的做法，GenAI_Agents 里有多个记忆型 Agent 案例可复现 [来源](https://github.com/NirDiamant/GenAI_Agents)。**教学参考实现**：词袋 `embed` 和规则版 `extract_preference` 仅为离线可复现，真实系统用句向量模型和分类器。

要点明一个边界：记忆的「召回」不是越多越好。召回太多会稀释上下文、增加成本；召回太少可能漏掉关键偏好。真实系统还会给记忆条目加**元数据**（时间、来源、重要性）做过滤，加**时间衰减**让旧偏好权重下降，并定期做**记忆压缩/摘要**。这些治理手段本章不展开，但要知道「记忆需要治理，不是只管存」。

## 生产踩坑

| 症状 | 根因 | 如何观测与复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| 记忆越存越多、召回全是废话 | 把整段对话原样写进长期记忆 | 统计记忆库里寒暄占比 | 写入前做提炼，只存事实/偏好 | 需完整审计留存的场景另设归档库 |
| 向量检索越来越慢 | 记忆条数无上限增长 | 观测检索延迟随条数变化 | 加 top-k、定期压缩/去重 | 条数很少时影响小 |
| 召回不到明显相关的偏好 | 用关键词匹配而非语义向量 | 用无共同词的同义问句复现 | 换句向量模型做语义召回 | 精确 ID 查询用关键词更准 |
| 过期偏好一直生效 | 记忆无时间衰减/失效 | 让旧偏好与新偏好冲突复现 | 加时间戳、时间衰减、可覆盖 | 永久性事实（如生日）无需衰减 |
| 短期与长期混为一谈 | 会话内临时信息写进长期库 | 检查「订单号」类临时信息是否被持久化 | 明确分层，临时信息只留短期 | 确需跨会话追踪的事务另算 |
| 工具观测被反复重发 | 未及时清理草稿纸里的旧观测 | 统计各轮 input token 增长 | 用完即弃、必要时摘要后保留 | 需完整轨迹回放时保留 |

## 思考：长期记忆为什么不能把整段对话原样存进去？记忆的三层结构各是什么？

### 回答

不能原样存的核心原因是**信噪比与成本**。原始对话里充斥「嗯/好的/谢谢/在吗」这类零信息量的寒暄，如果全塞进长期记忆向量库，会造成三重伤害：一是召回污染，每次 `recall` 的 top-k 里混着大量废话，稀释了真正有用的偏好，模型回答质量下降；二是检索变慢、存储膨胀，条数无节制增长；三是难以治理，你分不清哪条是有价值的事实、哪条是噪声。正确做法是**写入前先提炼**——只把「用户是素食者」「偏好邮件通知」这类稳定的事实/偏好存进去，而不是对话流水。三层结构是：短期/工作记忆，存在上下文窗口内的对话历史，生命周期是单次会话，内容如「你刚才问的订单号」；长期记忆，存在外部向量库/数据库，跨会话持久，内容是提炼后的用户偏好/事实；工具观测，存在草稿纸上，仅当前循环有效，内容是一次工具调用返回的原始结果。三者写入策略不同——短期随对话累积、工具观测用完即弃、长期需主动提炼后写入，混层就会出问题。

### 面试精简表达

原样存会让寒暄噪声污染召回、拖慢检索、难治理；长期记忆要存提炼后的事实/偏好。三层：短期（会话内 messages，会话结束消失）、长期（向量库，跨会话持久、语义召回）、工具观测（草稿纸，单次循环用完即弃），写入策略各不相同。

### 反例

有一类场景确实需要「原样留存对话」——比如合规审计、纠纷取证、训练数据采集。但要分清：这是把原始对话存进**审计日志/归档库**（另一套存储，按合规要求保留、脱敏、设保留期），而不是存进**用于召回的长期记忆向量库**。两者目的不同：审计库要「全、可追溯」，召回库要「精、高信噪比」。把二者混为一谈，正是开头故障的根源。

## 事故回放：1.2 万条噪声记忆是怎么攒出来的

回到开头的理财助理。上线时为了「快」，工程师在每轮对话结束后直接 `memory.add(user_msg + assistant_msg)`，没有任何提炼。前几天没事——记忆少，召回还算准。到第二周，记忆涨到 1.2 万条，其中约 9600 条是纯寒暄或与偏好无关的过程性对话。此时问「帮我看看理财建议」，`recall` 召回的 top-5 里往往有三四条是「好的谢谢」「稍等」，模型上下文被废话占据，回答开始跑偏；同时向量检索延迟从 40 毫秒涨到 400 毫秒。

修复分三步：其一，**止血**——在写入口加一个 `extract_preference` 式的闸门，只有判定为「事实/偏好」才写入，寒暄一律拒绝，新增噪声归零；其二，**清历史**——对已有 1.2 万条跑一遍分类，把 9600 条噪声归档到审计库、从召回库删除，检索延迟回落到 45 毫秒；其三，**加治理**——给每条记忆加时间戳和来源，召回时按时间衰减，并每周做一次去重压缩。优化后，召回 top-5 的偏好命中率从 40% 回到 92%，回答质量投诉清零。这个案例的教训一句话能记住：**长期记忆的入口必须有闸门，出口必须有上限，中间必须有治理**。
