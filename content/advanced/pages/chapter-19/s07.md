## 真实问题

阶梯 5 做完，团队兴奋地把 Agentic RAG（Retrieval-Augmented Generation，检索增强生成）上线，替换了旧的传统 RAG。一周后运营找上门：「怎么感觉答得还不如以前？」工程师懵了——他凭「感觉」觉得 Agentic 更强，却拿不出任何数字。更糟的是，他上周为了修一个 bug 改了检索的 `k` 值，改完只手动试了两三个问题觉得「没问题」，结果那次改动其实让另外一批问题的召回全崩了，无人察觉。

这两个问题——**「升级到底值不值」说不清**、**「改动有没有搞坏别的」不知道**——都指向同一个缺失：**没有评估回归集**。阶梯 6 要补上这最后一块，也是把 Demo 推向生产最关键的一步：用一套固定的测试集和量化指标，让「质量」从「拍脑袋的感觉」变成「可对照的数字」。没有这把刻度尺，前五级练得再好，也守不住质量、不敢改代码。

## 原理：RAG 评估的三个核心指标

评估 RAG 系统，业界有一个成熟的四指标诊断框架，本节聚焦最核心的三个（第四个「上下文精确率」思路类似，从略）[来源](https://docs.ragas.io/en/stable/concepts/metrics/available_metrics/)。这三个指标分别盯住 RAG 链路的不同环节：

- **忠实度（Faithfulness）**：答案里的每个论断，是否都能在检索到的上下文里找到支撑？它对抗的是「幻觉」——模型编造了上下文里没有的内容。忠实度低，说明模型在「瞎编」。
- **答案相关性（Answer Relevancy）**：答案是否真的回答了用户的问题？它对抗的是「答非所问」——模型说了一堆正确但无关的话。相关性低，说明模型「跑题」。
- **上下文召回（Context Recall）**：回答问题所需的关键信息，是否都被检索到了？它对抗的是「检索缺失」——该召回的证据没召回。召回低，说明「检索环节漏了料」，再强的模型也巧妇难为无米之炊。

三个指标定位不同故障：**召回低是检索的锅，忠实度低是生成瞎编，相关性低是生成跑题**。把它们分开测，才能知道「答不好」到底坏在哪一环。真实项目常用 RAGAS 等框架、以「大模型当裁判」（LLM-as-a-judge）来打分；本节用纯启发式近似，让你在无 API Key 环境下也能跑通整套回归流程，理解每个指标在测什么。

## 最小可运行演示

下面这段代码实现三个指标的启发式近似，并用一个迷你评估集，对「传统 RAG（一次检索）」与「Agentic RAG（多轮改写）」两个版本跑一次回归对照，输出每个指标是否过门槛、以及最终 PASSED/FAILED。纯 Python，无需 API Key。
```python
"""阶梯6：评估与回归——用测试集守住质量（纯 Python，无需 API Key）。
实现 RAG 三个核心指标的启发式近似：忠实度/答案相关性/上下文召回，并跑一次回归对照。"""
import re


def tokens(text: str):
    return set(re.findall(r"[a-zA-Z]+|[\u4e00-\u9fff]", text.lower()))


def faithfulness(answer: str, contexts) -> float:
    """忠实度：答案中的实义词有多少能在检索上下文里找到（近似"claim 是否被支撑"）。"""
    ans_t = tokens(answer)
    ctx_t = set().union(*[tokens(c) for c in contexts]) if contexts else set()
    if not ans_t:
        return 0.0
    supported = len(ans_t & ctx_t)
    return round(supported / len(ans_t), 3)


def answer_relevancy(answer: str, question: str) -> float:
    """答案相关性：答案与问题的词重叠占问题的比例（近似"是否答到点上"）。"""
    q_t, a_t = tokens(question), tokens(answer)
    if not q_t:
        return 0.0
    return round(len(q_t & a_t) / len(q_t), 3)


def context_recall(contexts, gold_facts) -> float:
    """上下文召回：标准答案要点里，有多少被检索上下文覆盖。"""
    ctx_t = set().union(*[tokens(c) for c in contexts]) if contexts else set()
    hit = sum(1 for f in gold_facts if tokens(f) & ctx_t)
    return round(hit / len(gold_facts), 3) if gold_facts else 0.0


EVAL_SET = [  # 一个 3 条的迷你评估集：question / answer / contexts / gold_facts
    {
        "q": "张三负责的项目用什么数据库？",
        "a_bad": "抱歉，资料未提到数据库。",
        "a_good": "张三负责的风控项目使用 PostgreSQL。",
        "ctx_bad": ["张三负责风控项目。"],
        "ctx_good": ["张三负责风控项目。", "风控项目采用 PostgreSQL 作为主数据库。"],
        "gold": ["风控项目使用 PostgreSQL"],
    },
    {
        "q": "推荐项目用什么缓存？",
        "a_bad": "不清楚。",
        "a_good": "推荐项目使用 Redis 做缓存。",
        "ctx_bad": ["李四负责推荐项目。"],
        "ctx_good": ["推荐项目使用 Redis 做缓存。"],
        "gold": ["推荐项目使用 Redis"],
    },
]

PASS_LINE = {"faithfulness": 0.5, "answer_relevancy": 0.3, "context_recall": 0.9}


def score_variant(variant: str):
    rows = []
    for case in EVAL_SET:
        a = case[f"a_{variant}"]
        ctx = case[f"ctx_{variant}"]
        rows.append({
            "faithfulness": faithfulness(a, ctx),
            "answer_relevancy": answer_relevancy(a, case["q"]),
            "context_recall": context_recall(ctx, case["gold"]),
        })
    avg = {m: round(sum(r[m] for r in rows) / len(rows), 3) for m in PASS_LINE}
    passed = all(avg[m] >= PASS_LINE[m] for m in PASS_LINE)
    return avg, passed


def run() -> None:
    for variant, label in [("bad", "传统RAG(一次检索)"), ("good", "AgenticRAG(多轮改写)")]:
        avg, passed = score_variant(variant)
        print(f"== {label} ==")
        for m in ["faithfulness", "answer_relevancy", "context_recall"]:
            print(f"   {m}={avg[m]}  (门槛 {PASS_LINE[m]})")
        print(f"   回归结论：{'PASSED' if passed else 'FAILED'}")


if __name__ == "__main__":
    run()
```
保存为 `ladder6_eval.py`，运行 `python ladder6_eval.py`。完整预期输出：
```text
== 传统RAG(一次检索) ==
   faithfulness=0.0  (门槛 0.5)
   answer_relevancy=0.116  (门槛 0.3)
   context_recall=1.0  (门槛 0.9)
   回归结论：FAILED
== AgenticRAG(多轮改写) ==
   faithfulness=0.916  (门槛 0.5)
   answer_relevancy=0.697  (门槛 0.3)
   context_recall=1.0  (门槛 0.9)
   回归结论：PASSED
```
读这张对照表，胜过一切「我感觉更好」的空谈：传统 RAG 版本的忠实度是 0（因为它答的是「资料未提到」这种回避句，跟检索上下文毫无支撑关系）、相关性也很低（0.116，几乎没答到点上），回归 FAILED；Agentic RAG 版本忠实度 0.916、相关性 0.697，全部过门槛，回归 PASSED。**现在「升级值不值」有了数字答案：值。**

## 逐行讲解

- 三个指标函数都用 `tokens`（分词集合）做启发式近似：`faithfulness` 看答案词有多少被上下文覆盖（近似「论断是否被支撑」），`answer_relevancy` 看答案与问题的词重叠（近似「有没有答到点上」），`context_recall` 看标准答案要点是否被上下文命中（近似「该召回的有没有召回」）。真实项目里这三步换成「大模型当裁判」的语义判断，更准，但「三个指标分别盯不同环节」的框架完全一致。
- `EVAL_SET` 是评估的地基：每条包含问题、两个版本的答案、两个版本的检索上下文、以及**标准答案要点 `gold`**。`gold` 是人工标注的「回答这题必须覆盖的关键事实」，是 `context_recall` 的判分依据——**没有标注的评估集，评估无从谈起**。
- `PASS_LINE` 是**门槛线**：每个指标设一个最低分，全部达标才算 PASSED。门槛不是普适常数，要按业务实测校准（本例的 0.5/0.3/0.9 是教学取值）。
- `score_variant` 把评估集里每条跑一遍、取平均、比门槛，输出「平均分 + 是否通过」。这就是一次**回归**的最小骨架：任何代码改动后重跑它，分数掉了就说明改坏了，分数稳住才敢合并。

## 真实系统对应

**官方公开机制 / 权威框架**：RAG 评估的「忠实度 / 答案相关性 / 上下文召回 / 上下文精确率」四指标框架是业界共识，RAGAS 等开源框架把它们标准化并用大模型裁判打分 [来源](https://docs.ragas.io/en/stable/concepts/metrics/available_metrics/)；检索评估需要带标注的语料、查询与相关性判断，且「相关文档排得太靠后模型可能用不上」是公认的经验。**通用工程模式**：「固定评估集 + 量化指标 + 门槛线 + 每次改动重跑回归」是可迁移到任何 Agent 系统的质量守护流程，agents-towards-production 的生产级教程里评估与监控是核心一环 [来源](https://github.com/NirDiamant/agents-towards-production)。**教学参考实现**：上面的启发式打分（词集合重叠）只为离线可复核，会高估或低估语义层面的正确性，真实项目务必换成语义裁判并人工抽检。

要点明一个边界：**指标是缩小范围的工具，不是真理**。词重叠近似会误判——比如答案换了同义词、上下文表述不同，词集合对不上但语义正确，会被低估；反之堆砌关键词也可能虚高。所以真实评估要「大模型裁判 + 人工抽检 + 多指标交叉」，且门槛线要用真实数据校准。指标的作用是让你「先看哪一环」，最终判断仍要回到样本本身。

## 生产踩坑

| 症状 | 根因 | 如何观测与复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| 说不清升级到底值不值 | 只凭感觉、无量化评估 | 让两人对同一改动给相反结论 | 建评估集，用指标出数字对照 | 一次性原型可从简 |
| 改一处悄悄搞坏另一批 | 改动后只手动试几个问题 | 改 k 值后跑全量回归看掉分 | 每次改动重跑回归集才合并 | 无回归集时先补集 |
| 三指标混着看、定位不到环 | 不区分召回/忠实度/相关性 | 只看一个总分找不到病根 | 三指标分开测，按环定位 | 单指标够用的简单场景 |
| 评估集没有标注 | 缺 gold 标准答案要点 | context_recall 无从计算 | 人工标注每题的关键事实 | 纯主观题另设评审 |
| 词重叠指标误判语义 | 启发式近似不懂同义/改写 | 同义答案被判低分复现 | 换大模型裁判、人工抽检 | 精确匹配类任务影响小 |
| 门槛线拍脑袋定 | 阈值未用真实数据校准 | 门槛过松/过严都放行或误杀 | 用历史数据分布校准门槛 | 教学演示可用固定取值 |
| 评估集长期不更新 | 新故障没进回归集 | 老 bug 修了新 bug 反复出 | 每个线上故障补一条回归用例 | 需求冻结的封版期另算 |

## 思考：为什么说「没有评估回归集，前五级练得再好也守不住质量」？

### 回答

因为没有评估回归集，你就同时失去了「判断好坏」和「防止退化」两种能力，而这两种能力是质量的全部依托。第一，判断好坏：Agent 的输出是自然语言、带随机性，靠人「感觉」根本无法稳定判断哪个版本更好——开头那个团队就是凭感觉上线 Agentic RAG，结果还不如旧版还浑然不觉。有了评估集和忠实度/相关性/召回三个指标，「哪个版本好」变成一张可对照的数字表，升级值不值一目了然。第二，防止退化（回归）：Agent 系统改一处常常牵动全局——改个检索 k 值、换个 prompt、调个记忆策略，都可能让原本答对的一批问题突然答错。没有回归集，你改完只能手动试几个问题，抽样太小必然漏掉退化；有了回归集，每次改动重跑全量，掉分就拦截、稳住才合并，退化无处遁形。更进一步，评估集还能定位「答不好坏在哪一环」——召回低是检索的锅、忠实度低是生成瞎编、相关性低是跑题，三指标分开测就能对症下药。所以评估回归集不是锦上添花，而是把前五级的能力「锁住、守住、还能持续改进」的地基；没有它，前五级只是一次性的 Demo，经不起任何改动和上线。

### 面试精简表达

没有评估集就同时失去「判断好坏」（Agent 输出随机、靠感觉不可靠）和「防止退化」（改一处常搞坏另一批、手动抽样必漏）两种能力；有了固定评估集+忠实度/相关性/召回三指标+门槛线，升级值不值有数字、每次改动重跑回归拦截退化、还能按指标定位坏在哪一环。它是把 Demo 变生产的地基。

### 反例

对一个「跑完就扔」的一次性探索脚本（比如临时验证「这个想法能不能用 LLM 做」），建一整套评估回归集确实是过度投入——目标只是验证可行性，不需要长期守护质量。但要清醒：一旦这个脚本要给别人用、要持续迭代、要上线，评估集就从「可选」变成「必需」。判据是**生命周期**：一次性用完即弃可以省，长期迭代上线绝不能省。开头故障的教训正是——他们把一个需要长期守护的系统，当成一次性脚本来对待，跳过了评估。

## 机制推导：从「三指标」到「一条可持续改进的回归飞轮」

评估的价值不止于「上线前测一次」，它能转成一个持续改进的飞轮。推导如下：每当线上出现一个「答错」的真实案例，你把它连同「正确答案要点（gold）」补进评估集——这一步把「一次故障」变成「一条永久的回归用例」。下次任何人改动代码，回归集都会重跑这条用例，确保这个 bug 不再复发。日积月累，评估集从最初的三五条长成几百条，覆盖越来越多的边界情况，系统质量在「改动→回归→补用例」的循环里螺旋上升。

由此推出两条工程结论。其一，**评估集要「活」**：它不是上线前写死的一次性资产，而是随每个线上故障持续生长的活文档——「每个故障补一条用例」应该成为团队铁律。其二，**评估集是团队协作的护栏**：有了它，新人也敢改代码（改坏了回归会拦），因为质量的判断标准从「资深工程师的感觉」外化成了「所有人都能重跑的数字」。这正是从「一个人的 Demo」走向「一个团队维护的生产系统」的关键一跃——它把阶梯 1~5 造好的零件，用一套可重复、可协作、可持续的质量流程锁死。下一节，我们就把这六级零件组装成作品集，并望向通往生产的最后一跃。
