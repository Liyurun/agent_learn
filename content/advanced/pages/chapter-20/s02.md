## 真实问题

架构选定为中心化编排后，第一个要落地的就是那个「中心」——supervisor（监督者/编排 Agent）。3 月 15 日事故复盘时，团队发现代码里根本没有一个统一的主循环：分诊逻辑写在一个函数里，护栏检查散落在各专家 Agent 内部，会话预算上限压根没实现。结果凌晨那通对话没有任何一处「总闸」能拦住它——高风险意图没被强制转人工、输出没过护栏、轮次没上限。**没有一个清晰的编排主循环，就没有地方安放这些横切的安全能力**。这一节要把 supervisor 编排写成一个可运行、可打印每一步 trace 的主循环，让分诊、专家、护栏、预算上限、可观测在一个会话里有序协作。

## 原理：一个会话就是一次有限状态机的运转

把中心化编排的主循环抽象成有限状态机，是理解它的关键。一次用户输入进来，会依次经过这些状态：
```text
  用户输入
     │
     ▼
 [BUDGET_CHECK] 会话预算上限？超限 ──▶ 强制转人工（FINISH）
     │ 未超限
     ▼
 [TRIAGE] 分诊：高风险词兜底 / 意图分类 / 置信度
     │
     ├─ order ─────▶ 订单专家 ┐
     ├─ logistics ─▶ 物流专家 │
     ├─ knowledge ─▶ 知识专家 ├─▶ [OUTPUT_GUARD] 输出护栏
     └─ human ─────▶ 转人工   ┘        │
                                       ▼
                               返回答复（FINISH）
   全程：Session 共享对象读写 + Tracing 落每一步事件
```
三个要点必须刻进脑子。**其一，supervisor 始终持有对话所有权**——它不是把控制权永久交给专家，而是「调用专家拿到答复后收回控制权」，这正是 OpenAI Agents SDK 里 manager/agents-as-tools 模式的核心：manager 保留答复的所有权 [来源](https://github.com/openai/openai-agents-python/blob/main/docs/agents.md)。**其二，横切能力（预算上限、输出护栏、trace）落在主循环里而非专家内部**，这样任何专家、任何分支都逃不过它们。**其三，上下文靠共享 Session 对象传递，而非字符串接力**——结构化字段（user_id、订单号）走 Session，自然语言只用于给用户看的最终回复。

## 现象与输入：为什么不能做「字符串接力」

多 Agent 最容易踩的坑之一是上下文丢失：分诊 Agent 知道 user_id，传给专家时如果只传自然语言输出，结构化信息就在文本里被稀释甚至丢失，专家只好再问一遍，体验断裂。正确做法是维护一个贯穿全程的 Session 对象，各 Agent 都从它读写：
```text
        ┌────────── Session（全程共享）──────────┐
        │ session_id / user_id(系统注入)        │
        │ messages / turn_count / token_used    │
        │ route_history / trace                 │
        └───────────────────┬───────────────────┘
              读/写           │           读/写
     supervisor   订单Agent  物流Agent  知识Agent  转人工Agent
```
## 最小可运行演示

下面是 supervisor 编排的主循环。专家子 agent 先用最简 mock（后续 3–6 节各自展开），重点展示**主循环如何把分诊、路由、输出护栏、会话预算上限、trace 串起来**。完全离线、无需 API Key。
```python
"""第20.2节：supervisor 编排主循环（纯 Python mock，无需 API Key）。"""
from dataclasses import dataclass, field
import re

MAX_TURNS, MAX_TOKENS = 10, 8000
RISK_WORDS = ["投诉", "12315", "起诉", "赔偿", "曝光"]
RISKY_OUTPUT = [r"(全额|立即|马上|一定).{0,6}(退款|赔偿)", r"退\s*\d+\s*元"]


@dataclass
class Session:
    session_id: str
    user_id: str
    messages: list = field(default_factory=list)
    turn_count: int = 0
    token_used: int = 0
    route_history: list = field(default_factory=list)
    trace: list = field(default_factory=list)


## ---- mock 子 agent（后续小节各自展开）----
def order_agent(s, q):
    return "您的订单 O-20260315-77 当前状态：已发货。"


def logistics_agent(s, q):
    return "订单 O-20260315-77 快递已到达【上海转运中心】，预计明天送达。"


def knowledge_agent(s, q):
    return "依据3C数码退换货政策：支持签收后7天无理由退货（依据文档 KB-RETURN-3C）。"


def escalate(s, reason):
    tid = f"T-{s.session_id[-3:]}-01"
    s.trace.append(f"escalate ticket={tid} reason={reason}")
    return f"已为您转接人工客服（工单号 {tid}），请稍候。"


## ---- mock 分诊：确定性关键词分类 + 伪置信度 ----
def triage(s, q):
    if any(w in q for w in RISK_WORDS):
        return "human", "命中高风险关键词", 1.0
    if "到哪" in q or "物流" in q or "快递" in q:
        return "logistics", "", 0.93
    if "退" in q or "政策" in q or "无理由" in q:
        return "knowledge", "", 0.88
    if "订单" in q or "金额" in q:
        return "order", "", 0.90
    return "human", "无法分类，兜底转人工", 0.4


## ---- 输出护栏：拦截未授权承诺 ----
def check_output(ans, s):
    for pat in RISKY_OUTPUT:
        if re.search(pat, ans):
            s.trace.append(f"guardrail_block pattern={pat}")
            return "关于退款/赔偿的具体处理，需人工客服为您核实，正在转接。"
    return ans


HANDLERS = {"order": order_agent, "logistics": logistics_agent,
            "knowledge": knowledge_agent}


def customer_service(s, q):
    s.messages.append(("user", q))
    if s.turn_count >= MAX_TURNS or s.token_used >= MAX_TOKENS:
        return escalate(s, "达到会话上限")
    label, reason, score = triage(s, q)
    s.route_history.append(label)
    s.trace.append(f"triage route={label} score={score:.2f}")
    try:
        handler = HANDLERS.get(label)
        ans = handler(s, q) if handler else escalate(s, reason)
    except Exception as e:
        s.trace.append(f"agent_crash {type(e).__name__}")
        ans = escalate(s, "系统异常降级")
    ans = check_output(ans, s)
    s.messages.append(("assistant", ans))
    s.turn_count += 1
    s.token_used += 200
    return ans


def run():
    s = Session(session_id="S-0315-001", user_id="U-8821")
    queries = [
        "我的订单 O-20260315-77 到哪了？",
        "七天无理由退货怎么操作？",
        "你们必须立刻全额退我 328 元，不然我打 12315 投诉！",
    ]
    for q in queries:
        ans = customer_service(s, q)
        print(f"USER: {q}")
        print(f"BOT : {ans}")
        print("-" * 42)
    print("=== 会话轨迹 trace ===")
    print("\n".join(s.trace))
    print(f"route_history={s.route_history}")


if __name__ == "__main__":
    run()
```
保存为 `s2_supervisor.py`，运行 `python s2_supervisor.py`。完整预期输出：
```text
USER: 我的订单 O-20260315-77 到哪了？
BOT : 订单 O-20260315-77 快递已到达【上海转运中心】，预计明天送达。
------------------------------------------
USER: 七天无理由退货怎么操作？
BOT : 依据3C数码退换货政策：支持签收后7天无理由退货（依据文档 KB-RETURN-3C）。
------------------------------------------
USER: 你们必须立刻全额退我 328 元，不然我打 12315 投诉！
BOT : 已为您转接人工客服（工单号 T-001-01），请稍候。
------------------------------------------
=== 会话轨迹 trace ===
triage route=logistics score=0.93
triage route=knowledge score=0.88
triage route=human score=1.00
escalate ticket=T-001-01 reason=命中高风险关键词
route_history=['logistics', 'knowledge', 'human']
```
第三轮就是事故那句话。注意它**在 triage 阶段就被高风险词拦下强制转人工**（`score=1.00 reason=命中高风险关键词`），根本没机会走到专家 Agent 去「承诺退款」。这就是把安全能力落在主循环的价值：一处兜底，全局生效。

## 防御性编排：用字典分发替代 if-elif 长链

上面已经用 `HANDLERS.get(label)` 字典分发替代了冗长的 `if-elif`。这不是炫技，而是**防御性编排**：路由标签到处理函数的映射一目了然，新增专家 Agent 只需加一行，且 `try/except Exception` 把任一专家/工具的异常统一降级为转人工——生产系统第一信条是「可以答不好，但绝不能崩」。异常写进 `trace` 而非静默吞掉：**降级不等于沉默**，用户体验降级了，工程上必须留痕才能被告警和复盘。

## 真实系统对应

**官方公开机制**：中心化编排对应 OpenAI Agents SDK 的 manager/agents-as-tools 模式，面向用户的 Agent 持有对话所有权、把专家当有边界的工具调用 [来源](https://github.com/openai/openai-agents-python/blob/main/docs/agents.md)；LangGraph 把这类拓扑称为 supervisor——一个中心协调者接收每条消息、分类意图、路由到专家，专家答完控制权回到 supervisor 决定是否再路由或结束 [来源](https://langchain-ai.github.io/langgraph/concepts/multi_agent/)。**通用工程模式**：把编排写成带预算上限的主循环、横切能力（护栏/trace）落在循环里、上下文走共享 Session 对象，是可迁移到任何框架的骨架。**教学参考实现**：本节的 `triage` 用关键词而非真实模型分类，`token_used += 200` 是模拟计数，仅为让输出可逐字复核。

值得点明边界：真实的 LangGraph supervisor 会用 `Command` 对象在图节点间转移控制、用 checkpointer 持久化状态；OpenAI SDK 的 manager 会把子 agent 包成 tool。本节为讲清状态转移把这些简化成函数调用与列表 trace，把 `triage` 换成真实模型、把 `trace` 换成结构化日志与 span（第 7 节），主循环骨架一行不改。

## 生产踩坑

| 症状 | 根因 | 如何观测与复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| 专家 Agent 反复追问已知信息 | 上下文做成字符串接力，结构化字段丢失 | 打印传给专家的 payload，看有无 user_id | 结构化字段走共享 Session，自然语言仅给用户看 | 单 Agent 无交接时不涉及 |
| 高风险话术溜到专家层被「承诺」 | 护栏写在专家内部而非主循环 | 构造带「赔偿」的输入看是否直达专家 | 输入护栏与高风险兜底前置到 supervisor | 无敏感动作的只读场景风险低 |
| 某专家崩溃拖垮整通会话 | 主循环无异常兜底 | 让某专家抛异常，观察是否 500 | try/except 统一降级转人工并写 trace | 明确要求 fail-fast 的内部工具链 |
| 会话无限循环烧 token | 主循环无预算上限 | 让模型总要求继续，观察轮次是否封顶 | 主循环入口做 turn/token 上限检查 | 单步问答无多轮循环 |
| 新增专家要改动多处 | 路由用 if-elif 长链散落 | 统计新增一个专家改了几个文件 | 用字典分发表集中管理路由 | 专家极少且永不新增 |

## 思考：为什么横切的安全能力必须落在主循环，而不是各专家内部？

### 回答

因为落在专家内部无法保证覆盖所有路径，而客服系统的安全底线要求「零漏网」。设想把「拦截未授权承诺」写在每个专家 Agent 内部：新增一个专家时如果忘了加这段检查，就出现一条没有护栏的路径；某个专家因为异常提前返回，也可能绕过检查；四个专家各写一份护栏逻辑，还会出现实现不一致、修一处漏三处的问题。把它落在主循环的出口处（`check_output`），则任何专家、任何分支、甚至异常降级返回的消息，都必须经过这唯一一道闸——这正是 3 月 15 日事故的教训：护栏当时散落在专家里，而那句话走的恰好是没护栏的分支。同理，会话预算上限落在主循环入口，才能保证不管走哪个专家都逃不过轮次/token 上限；trace 落在主循环，才能保证每一步都被记录、100% 会话可还原。一句话：横切关注点（安全、预算、可观测）的本质就是「与具体业务分支正交」，落在正交的主循环上才能做到无死角，落在业务分支里必然有缝。

### 面试精简表达

安全底线要零漏网，而专家内部的护栏一旦新增分支或异常返回就会有缝。把护栏、预算、trace 落在主循环这条所有路径的必经之地，一处兜底、全局生效；这正是横切关注点该在的位置。

## 机制推导：为什么 supervisor 要「收回控制权」而不是永久 handoff

中心化编排和去中心化 handoff 的分水岭，就在「专家答完之后控制权归谁」。去中心化里，分诊把控制权永久交给专家，专家再交给下一个专家，形成链式接力；中心化里，专家只是被「调用」，答完控制权立刻回到 supervisor。对客服场景，收回控制权带来三个关键收益。第一，**输出护栏有统一出口**：无论哪个专家答的，控制权都回到 supervisor，由它统一过 `check_output`；若永久 handoff，护栏就得在每个专家出口各写一遍。第二，**多轮上下文归属清晰**：下一轮用户输入仍进 supervisor，由它带着完整 Session 重新分诊，而不是「上一个专家继续接管」——这避免了「用户已经转到新话题，却还被上一个专家纠缠」的体验断裂。第三，**权限收在一处**：只有 supervisor 和转人工 Agent 能触发「升级」，专家无此权限，符合最小权限原则。代价是每轮多一跳路由延迟和一次分诊调用——但对「安全边界必须清晰」的客服场景，这个代价值得。这也解释了为什么 OpenAI 文档把 handoffs 归为「专家应当拥有下一次答复的所有权」时才用，而 manager 模式用于「manager 应保持控制、把专家当有边界的能力调用」 [来源](https://github.com/openai/openai-agents-python/blob/main/docs/agents.md)。
