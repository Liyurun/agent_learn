## 真实问题

3 月 15 日事故里，模型「承诺」退款只是第一层问题；更深的一层是：**假如当时真有一个 `create_refund` 工具，模型的这句承诺会不会真的触发扣款？** 复盘时团队捏了把汗——早期版本的退款工具既没有人工审批，也没有幂等键。这意味着：模型一句话就能触发真实退款；如果因为网络抖动重试，同一笔退款可能执行两次。还有一个更隐蔽的坑：订单查询工具的 `user_id` 是从对话上下文里取的，而非系统会话注入的，理论上能被诱导查询他人订单（越权）。这一节要把工具层做成生产级：**越权校验、超时降级、重试退避、幂等键、缓存**，并讲清哪些数据能缓存、哪些绝不能。

## 原理：工具是信任边界，安全防线落在工具内

工具是 Agent 与真实世界的接口，也是**信任边界**——模型给的参数全部当成不可信输入。四条铁律：

1. **参数区分「可信」与「不可信」**：`user_id` 可信（系统会话注入），`order_id` 不可信（来自用户输入或模型），所以要做归属校验，防越权。
2. **失败返回结构化错误，而非抛异常**：`{"error": ...}` 让上层 Agent 能读懂并优雅处理；直接 raise 会让整个循环崩溃。
3. **一切外部调用都要超时 + 有限重试**：没有超时的外部调用是生产事故头号来源，一个卡住的物流 API 能拖垮整条会话；重试要用指数退避（backoff），立刻重试往往还是失败。
4. **有副作用的动作要幂等**：退款、扣款、发信这类非幂等操作，必须用幂等键保证「重试不产生重复副作用」。

缓存是第五条工程手段，但有严格边界：**只缓存低频变更的数据（政策、FAQ），高频变更的业务数据（订单、物流）绝不缓存**，否则用户会看到过期状态（明明已发货却显示待发货）。

## 现象与输入：退款为什么必须幂等

设想没有幂等键的退款工具。用户申请退 328 元，工具发起扣款请求，但因网络抖动客户端没收到响应，重试机制又发了一次——如果服务端把两次请求当成两笔独立退款，用户就被退了 656 元。幂等键（idempotency key）解决这个问题：每笔退款带一个唯一键，服务端记录「这个键处理过没有」，重复请求直接返回首次结果而不再执行。这与有副作用工具「必须走人工审批」是两条独立防线：审批防「不该退的退了」，幂等防「该退一次的退了两次」。

## 最小可运行演示
```python
"""第20.5节：工单/退款工具层 —— 权限校验、超时降级、幂等键、缓存（mock）。"""
import time
from functools import lru_cache


## ---- mock 数据 ----
ORDERS = {
    "O-20260315-77": {"user_id": "U-8821", "status": "已发货", "amount": 328.0},
    "O-20260310-05": {"user_id": "U-9999", "status": "已签收", "amount": 59.9},
}
_REFUND_LOG = {}         ## 幂等键 -> 结果，模拟幂等表


def get_order(user_id: str, order_id: str) -> dict:
    """查询订单，仅允许查本人订单（越权校验落在工具内）。"""
    order = ORDERS.get(order_id)
    if order is None:
        return {"error": "订单不存在"}
    if order["user_id"] != user_id:                    ## 越权拦截
        return {"error": "无权查询该订单"}
    return {"status": order["status"], "amount": order["amount"]}


def _with_retry(fn, retries=2, backoff=0.0):
    for i in range(retries + 1):
        try:
            return fn()
        except (TimeoutError, ConnectionError) as e:
            if i == retries:
                return {"error": f"服务暂不可用：{e}"}
            time.sleep(backoff * (2 ** i))


@lru_cache(maxsize=256)
def get_return_policy(category: str) -> str:
    """高频少变，适合缓存。"""
    table = {"3C": "签收后7天无理由退货", "生鲜": "不支持无理由退货"}
    return table.get(category, "该品类需人工确认")


def create_refund(user_id: str, order_id: str, amount: float,
                  idempotency_key: str, approved: bool) -> dict:
    """退款有副作用：必须人工审批 + 幂等键防重复退款。"""
    if not approved:
        return {"status": "pending_approval", "msg": "退款需人工审批，已挂起"}
    if idempotency_key in _REFUND_LOG:                 ## 幂等：重复请求返回同一结果
        return {**_REFUND_LOG[idempotency_key], "replayed": True}
    order = ORDERS.get(order_id)
    if order is None or order["user_id"] != user_id:
        return {"error": "订单无效或越权"}
    result = {"status": "refunded", "amount": amount, "order_id": order_id}
    _REFUND_LOG[idempotency_key] = result
    return result


def run():
    print("=== 越权校验 ===")
    print("本人查:", get_order("U-8821", "O-20260315-77"))
    print("越权查:", get_order("U-8821", "O-20260310-05"))
    print("=== 缓存（第二次命中 lru_cache）===")
    print("政策查询:", get_return_policy("3C"), "| 缓存信息:", get_return_policy.cache_info())
    get_return_policy("3C")
    print("再次查询后缓存:", get_return_policy.cache_info())
    print("=== 退款审批 + 幂等 ===")
    print("未审批:", create_refund("U-8821", "O-20260315-77", 328.0, "IK-1", approved=False))
    r1 = create_refund("U-8821", "O-20260315-77", 328.0, "IK-1", approved=True)
    r2 = create_refund("U-8821", "O-20260315-77", 328.0, "IK-1", approved=True)
    print("首次退款:", r1)
    print("重复请求(同幂等键):", r2)


if __name__ == "__main__":
    run()
```
保存为 `s5_tools.py`，运行 `python s5_tools.py`。完整预期输出：
```text
=== 越权校验 ===
本人查: {'status': '已发货', 'amount': 328.0}
越权查: {'error': '无权查询该订单'}
=== 缓存（第二次命中 lru_cache）===
政策查询: 签收后7天无理由退货 | 缓存信息: CacheInfo(hits=0, misses=1, maxsize=256, currsize=1)
再次查询后缓存: CacheInfo(hits=1, misses=1, maxsize=256, currsize=1)
=== 退款审批 + 幂等 ===
未审批: {'status': 'pending_approval', 'msg': '退款需人工审批，已挂起'}
首次退款: {'status': 'refunded', 'amount': 328.0, 'order_id': 'O-20260315-77'}
```

逐段看三道防线：**越权校验**——U-8821 查自己的 O-20260315-77 正常返回，查属于 U-9999 的订单被工具内部拦下返回「无权查询」，哪怕模型被诱导传了别人的 order_id 也没用；**缓存**——第一次查政策 `misses=1`，第二次 `hits=1`，命中缓存零成本返回（政策是低频变更数据，适合缓存）；**审批 + 幂等**——未审批时退款挂起不执行，审批后首次执行 `refunded`，用同一幂等键 `IK-1` 重复请求时返回 `replayed=True` 的同一结果而不再扣款。这三道防线，正是事故里缺失的那几环。

## 真实系统对应

**官方公开机制**：OpenAI 官方把「围绕函数工具调用检查参数或结果」归为 tool guardrails、把「在取消/编辑/敏感 MCP（Model Context Protocol，模型上下文协议）等副作用动作前暂停」归为 human-in-the-loop approvals，并给出明确的选择表 [来源](https://developers.openai.com/api/docs/guides/agents/guardrails-approvals.md)；退款正属于「副作用动作」，应走审批（第 6 节展开）。**通用工程模式**：越权校验落在工具内、外部调用套超时与指数退避重试、非幂等动作用幂等键、按数据变更频率决定是否缓存，是可迁移到任何工具层的做法。**教学参考实现**：`ORDERS`/`_REFUND_LOG` 是内存字典模拟数据库与幂等表，`lru_cache` 是演示用的进程内缓存，真实生产请用带 TTL 的分布式缓存（如 Redis）和持久化幂等表。

一个边界要点：`lru_cache` 是进程内、无过期时间的缓存，只适合演示。真实政策也会更新，所以生产缓存要带 TTL（Time To Live，存活时间）或主动失效机制；而订单状态这类高频变更数据，要么不缓存、要么设极短 TTL（几秒），否则「已发货显示待发货」的投诉会接踵而来。

## 生产踩坑

| 症状 | 根因 | 如何观测与复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| 用户查到他人订单（越权） | user_id 取自模型/用户输入而非系统会话 | 诱导模型传他人 order_id 复现 | user_id 由系统会话注入，工具内做归属校验 | 内部管理后台有意跨用户查询 |
| 同一笔退款被扣两次 | 非幂等动作无幂等键，重试重复执行 | 对同一退款请求重试观察是否双扣 | 每笔退款带幂等键，服务端去重 | 天然幂等的只读查询 |
| 一个卡住的 API 拖垮整通会话 | 外部调用无超时 | 让物流 API 永久 hang 观察会话是否卡死 | 所有外部调用设超时 + 有限重试退避 | 本地纯计算无外部依赖 |
| 用户看到过期订单状态 | 给高频变更数据加了缓存 | 发货后立即查询看是否仍显示待发货 | 高频变更数据不缓存或设极短 TTL | 政策/FAQ 等低频数据适合缓存 |
| 立刻重试仍失败、雪崩 | 重试无退避，瞬间打爆对端 | 对端过载时观察重试是否加剧拥塞 | 指数退避（0.5s,1s,2s…）+ 上限 | 明确对端可承受的高频轮询 |

## 思考：退款既然已经走人工审批，为什么还要幂等键？两者是不是重复了？

### 回答

不重复，因为它们防的是两类完全不同的故障，缺一不可。人工审批防的是「不该退的退了」——它是一道**授权关**，确保退款这个有副作用的动作在执行前有人（或策略）确认过，模型一句话不能直接触发扣款。但审批只解决「要不要退」，不解决「退几次」。幂等键防的是「该退一次的退了两次」——它是一道**去重关**，应对的是分布式系统里无法避免的重试：客户端发出退款请求后没收到响应（可能是响应丢了、也可能是超时），重试机制再发一次，如果服务端没有幂等去重，同一笔审批通过的退款就会被执行两次，用户被双倍退款。注意这个场景里审批是通过的、金额也是对的，审批关一点问题没有，出问题的纯粹是「同一个已授权动作被重复投递」——这正是幂等键的战场。把两者放在时间线上看更清楚：审批发生在执行之前（授权阶段），幂等发生在执行之时（投递阶段）；一个管准入，一个管次数。生产里还有第三道相关防线是对账（事后核对退款笔数与金额），三者构成「事前授权 + 事中去重 + 事后对账」的完整链条。所以面试时如果只答「有审批就够了」，会漏掉分布式重试这个最常见的双扣根因。

### 面试精简表达

审批管「要不要退」（授权，执行前），幂等管「退几次」（去重，执行时）。分布式重试会让已授权的同一笔退款被重复投递，审批拦不住，必须靠幂等键去重；两者加事后对账构成完整链条，缺一不可。

## 深入：结构化错误如何让上层 Agent 优雅决策

工具的第二条铁律「失败返回结构化错误而非抛异常」值得展开，因为它直接决定了整个系统的健壮性。设想 `get_order` 遇到「订单不存在」时直接 `raise ValueError`：这个异常会一路冒泡，如果主循环没接住就是 500 崩溃，接住了也只能笼统降级转人工。而返回 `{"error": "订单不存在"}` 时，上层 Agent 能读懂这个语义，做出更细的决策——比如提示用户「请核对订单号」而不是转人工，或者建议用户换个订单号重试。更关键的是，结构化错误让「可恢复失败」和「不可恢复失败」得以分流：网络超时、连接错误这类可恢复失败，在工具内部重试（Agent 不该关心网络抖动）；「订单不存在」「无权查询」这类业务语义失败，直接返回结构化错误交给 Agent 决策。这条分界线（职责边界）是面试高频追问点：可恢复的网络类失败在工具内部消化，业务语义失败上抛给 Agent。把两类失败混在一起——要么全靠 Agent 重试（浪费，业务错误重试没意义），要么全靠工具兜底（Agent 失去决策信息）——都是错的。结构化错误是让这条分界线得以存在的前提。
