## 真实问题

事故平息后，运营抽查历史对话又发现一类隐患：一位用户问「生鲜产品能七天无理由退货吗」，知识 Agent 回答「可以的，七天无理由退货」——但这是错的，生鲜类因易腐**不支持**无理由退货。追查发现，当时知识 Agent 的 prompt 里明明写了「只依据检索文档作答、不要编造」，可它还是编了。原因有两个：一是它检索到的是「退换货总则」这类宽泛文档，证据根本不足以回答生鲜的具体政策，但它没有再检索就硬答了；二是**prompt 里的「不要编造」是软约束，降低概率但不能杜绝**。这一节要把知识子 agent 做成「Agentic RAG（Retrieval-Augmented Generation，检索增强生成）+ 引用溯源 + grounded 硬标记」，让答案要么有据可依、要么明确转人工，绝不硬编。

## 原理：Agentic RAG 与「有据可依」的硬标记

传统 RAG 是「一次检索 + 一次作答」，问题是如果第一次检索不到位，答案质量就完全取决于那一次召回。Agentic RAG 让模型**自主决定检索几次、如何改写查询**：证据不足时改写查询再检索，直到足够或达上限。这段代码同时落地三个知识点：Agentic RAG 的自主检索循环、防幻觉的 prompt 约束（软护栏）、循环上限的终止条件。

但真正的防线是**结构化的 grounded 标记**：
```text
  问题 ──▶ [模型决策] ──answer?──▶ 有据可依(grounded=True)？──是──▶ 带引用作答 ✅
              │            │                          └─否──▶ grounded=False，输出护栏拦截
              │         retrieve?
              ▼            │
        达检索上限?──是──▶转人工   ▼
              │           改写查询 → 向量检索 → 证据入 context ──┐
              └─────────────────────────────────────────────────┘
```
`grounded` 标记「这条回答是否有文档支撑」。若 `grounded=False` 却给了肯定答复，就是幻觉信号，可被输出护栏（第 6 节）拦下。这是硬防线，prompt 约束是软防线，软硬结合才靠谱。同时给每条答案附上 `sources`（引用了哪些文档），因为客服场景里「你凭什么这么说」必须能回溯——用户投诉时，客服主管要能看到 Agent 引用的原文。

## 现象与输入：为什么要「改写再检索」

看贯穿案例里的知识库三篇文档，注意它们的关键词标签：
```text
KB-RETURN-GENERAL  退换货总则   tags=[退货, 退换, 政策]
KB-RETURN-3C       3C 7天无理由 tags=[3C, 数码, 7天, 无理由]
KB-REFUND-FLOW     退款流程     tags=[退款, 到账, 流程]
```
用户问「3C 数码怎么 7 天无理由退货」，如果模型第一次用宽泛查询「退货 政策」去检索，只会命中 `KB-RETURN-GENERAL`（总则），证据不足以回答具体的 3C 政策。Agentic RAG 的关键就在这里：模型判断「证据不够具体」，**把查询改写成「3C 数码 7天 无理由」再检索一次**，这次精确命中 `KB-RETURN-3C`，才能有据作答。下面的演示就复现这个「宽泛→不足→改写→命中」的自主循环。

## 最小可运行演示
```python
"""第20.4节：知识库检索子 agent —— Agentic RAG + 引用溯源 + grounded 标记（mock）。"""
from dataclasses import dataclass


## ---- mock 向量库：每篇文档带关键词标签，检索按标签命中数打分 ----
KB = {
    "KB-RETURN-GENERAL": {
        "text": "退换货总则：不同品类政策不同，请按具体品类查询。",
        "tags": ["退货", "退换", "政策"],
    },
    "KB-RETURN-3C": {
        "text": "3C数码类商品支持签收后7天无理由退货，商品需不影响二次销售。",
        "tags": ["3C", "数码", "7天", "无理由"],
    },
    "KB-REFUND-FLOW": {
        "text": "退款审核通过后原路退回，到账时间1-7个工作日。",
        "tags": ["退款", "到账", "流程"],
    },
}


def vector_search(query_tags, k=2):
    scored = []
    for doc_id, doc in KB.items():
        hit = len(set(query_tags) & set(doc["tags"]))
        if hit:
            scored.append((hit, doc_id, doc["text"]))
    scored.sort(key=lambda x: (-x[0], x[1]))
    return [(doc_id, text) for _, doc_id, text in scored[:k]]


@dataclass
class Decision:
    action: str          ## "retrieve" | "answer"
    query_tags: tuple = ()
    answer: str = ""
    source: str = ""


class ScriptedRAGModel:
    """确定性假模型：首轮宽泛检索证据不足 -> 改写为精确查询 -> 命中后作答。"""
    def __init__(self):
        self.step = 0

    def decide(self, question, context):
        self.step += 1
        if self.step == 1:
            return Decision("retrieve", query_tags=("退货", "政策"))     ## 宽泛
        ## 判断证据是否“足够具体”：是否检索到含 7天/无理由 的 3C 文档
        hit = [c for c in context if "7天" in c[1]]
        if not hit:
            return Decision("retrieve", query_tags=("3C", "数码", "7天", "无理由"))  ## 改写
        return Decision("answer", answer=f"依据官方政策：{hit[0][1]}", source=hit[0][0])


def knowledge_agent(question, max_retrieval=3):
    model, context, tries, trace = ScriptedRAGModel(), [], 0, []
    while tries < max_retrieval:
        d = model.decide(question, context)
        if d.action == "answer":
            return {"answer": d.answer, "sources": [d.source],
                    "grounded": True, "trace": trace}
        tries += 1
        context = vector_search(d.query_tags, k=2)
        trace.append(f"retrieve#{tries} tags={list(d.query_tags)} "
                     f"-> {[c[0] for c in context]}")
    return {"answer": "该问题需人工确认，正在为您转接。",
            "sources": [], "grounded": False, "trace": trace}


def run():
    res = knowledge_agent("3C数码怎么7天无理由退货")
    print("=== Agentic RAG 检索轨迹 ===")
    print("\n".join(res["trace"]))
    print("=== 结构化输出 ===")
    print(f"answer  : {res['answer']}")
    print(f"sources : {res['sources']}")
    print(f"grounded: {res['grounded']}")


if __name__ == "__main__":
    run()
```
保存为 `s4_rag.py`，运行 `python s4_rag.py`。完整预期输出：
```text
=== Agentic RAG 检索轨迹 ===
retrieve#1 tags=['退货', '政策'] -> ['KB-RETURN-GENERAL']
retrieve#2 tags=['3C', '数码', '7天', '无理由'] -> ['KB-RETURN-3C']
=== 结构化输出 ===
answer  : 依据官方政策：3C数码类商品支持签收后7天无理由退货，商品需不影响二次销售。
sources : ['KB-RETURN-3C']
grounded: True
```
逐帧读这段轨迹：`retrieve#1` 用宽泛查询只召回总则，模型判断「不含 7天/无理由，证据不足」，于是 `retrieve#2` 改写成精确查询命中 `KB-RETURN-3C`，这才作答。最终输出带 `sources=['KB-RETURN-3C']` 和 `grounded=True`——**答案可回溯、有据可依**。如果三次检索都拿不到含关键信息的文档，函数会返回 `grounded=False` 并转人工，绝不硬编。这正是开头那个「生鲜能否无理由退货」隐患的正解：证据不足就转人工，而不是软约束下硬答。

## 真实系统对应

**官方公开机制**：Anthropic《Building Effective Agents》把「检索—评估—再检索」这类模型自主决定工具使用的循环归为 agentic 模式，并强调应从最简单的可组合方案起步、按需增加自治度 [来源](https://www.anthropic.com/engineering/building-effective-agents)。真实生产客服如 Intercom Fin 的公开材料反复强调「解析率高度依赖知识库质量」——知识库不全或不新，检索就召回不到证据，答案质量随之下降 [来源](https://www.intercom.com/blog/videos/meet-fin-2-ai-agent-keynote/)。**通用工程模式**：Agentic RAG 的「证据不足→改写→再检索→达上限兜底」循环、以及给答案附 `sources`/`grounded` 结构化字段，是可迁移到任何 RAG 系统的做法。**教学参考实现**：`vector_search` 用关键词标签命中数模拟向量相似度、`ScriptedRAGModel` 是确定性假模型，仅为让输出可逐字复核；真实系统请用嵌入向量检索与真实 LLM 决策。

一个边界要说清：真实的向量检索是稠密语义相似度，能召回「表述不同但语义相近」的文档，而本节的关键词标签匹配做不到这点——它只是为了让「宽泛查询召回不足、精确查询命中」这个教学现象可复现。落地时召回质量取决于嵌入模型、切分策略、索引方式，这些属于第 19 章 RAG 的范畴，本节聚焦「检索循环 + 有据可依」这一层。

## 生产踩坑

| 症状 | 根因 | 如何观测与复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| prompt 写了不编造，仍幻觉 | 只有软约束，无 grounded 硬标记 | 问知识库没有的问题看是否硬答 | grounded=False 时输出护栏拦截肯定答复 | 闲聊类无需据可依的问题 |
| 证据不足却硬答 | 传统单次检索，召回不足不重试 | 用需多跳的问题看是否只检索一次 | Agentic RAG：证据不足改写再检索 | 简单问题单次检索足够，别过度 |
| 用户投诉「凭什么这么说」无法回溯 | 答案未附引用来源 | 抽查答案是否带 sources | 每条答案附 sources 文档 id | 无合规回溯要求的内部问答 |
| 检索死循环烧 token | 无检索次数上限 | 让每次检索都召回空看是否无限重试 | max_retrieval 上限，达上限转人工 | 明确单次检索的简单场景 |
| 知识库过期导致答错 | 文档未随政策更新 | 对比答案与最新政策原文 | 建立知识库更新与失效检查流程 | 政策极稳定、几乎不变的领域 |

## 思考：为什么说「prompt 里写了不要编造」不足以防幻觉，必须有 grounded 硬标记？

### 回答

因为 prompt 约束作用于「生成阶段的概率」，而 grounded 标记作用于「放行阶段的事实」，二者的强制力完全不同。prompt 里写「只依据文档、不要编造」，本质是往模型的条件分布里加了一个偏置，让它更倾向于据实回答——但它只是「更倾向」，不是「保证」。当检索证据不足、而用户问得又很肯定时，模型仍可能顺着语言习惯给出一个听起来合理的肯定答复，这就是幻觉，开头「生鲜可以无理由退货」就是活例子。grounded 标记则是一道结构化的、与模型生成无关的检查：它由代码判定「本次回答到底有没有检索到的文档支撑」（`len(context) > 0` 且证据相关），如果 `grounded=False` 却给了肯定答复，输出护栏直接拦截、改为转人工。这道检查不依赖模型「自觉」，而是代码强制，所以能杜绝而非仅降低。更深一层，二者是纵深防御的两层：软护栏（prompt）在前，把大部分幻觉概率压下去；硬护栏（grounded + 输出拦截）在后，兜住漏网的那部分。客服场景对「答错政策」零容忍，必须软硬都有——只靠 prompt 是把安全底线寄托在概率上，而底线不能是概率。

### 面试精简表达

prompt 约束改变的是生成概率（更倾向不编造，但不保证），grounded 标记是代码层的事实检查（无据可依就不放行肯定答复）。前者软、后者硬，客服对答错政策零容忍，必须软硬双防线，不能把底线寄托在概率上。

## 深入：引用溯源如何反哺评估与合规

引用溯源（`sources` 字段）不只是给用户看的「凭据」，它还是评估和合规的抓手。评估上，有了 sources，就能在评估集里加一条自动检查：「答案引用的文档是否真的包含答案所述的政策」——这比人工逐条读答案高效得多，也能捕捉「引用了 A 文档却说了 B 内容」这种「假溯源」幻觉。合规上，金融、电商等受监管场景常要求「AI 给出的政策解释必须可追溯到官方文档版本」，sources 里带上文档 id 甚至版本号，就能在审计时还原「这条答复当时依据的是哪一版政策」。这也解释了为什么 Intercom Fin 这类产品把知识库质量当作解析率的生命线 [来源](https://www.intercom.com/blog/videos/meet-fin-2-ai-agent-keynote/)：溯源链的两端——检索到的文档、以及文档本身的准确与新鲜——共同决定了答案能否既「答得出」又「可追责」。把 grounded 与 sources 一起做进结构化输出，知识 Agent 就从「一个会说话的黑箱」升级成「每句话都有出处、可评估、可审计」的可信组件。
