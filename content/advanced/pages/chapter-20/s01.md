## 真实问题

回到 3 月 15 日的「全额退款」事故。事后第一次复盘会上，产品经理说「我们不是要求过要安全吗」，工程师说「需求文档里确实写了『客服要安全、要快、要能追溯』」。问题就出在这里：**「安全」「快」「能追溯」这些词不可度量，等于没写**。当一条需求无法被翻译成「跑一个测试就能判定过没过」的指标时，它在代码里就没有对应的强制点，事故迟早发生。这一节要做的第一件事，就是把五条模糊需求逐条翻译成可验收指标；第二件事，是在三种候选架构里用可解释的方式选型——而不是「听说多 Agent 时髦就上多 Agent」。

## 原理：不可度量的需求等于没有需求

生产项目会把每条非功能需求（往往是面试考点）翻译成一个可验收的量化指标。指标不是事后的考试，而是**架构的约束条件**——比如「P95 延迟 ≤ 3s」这条，直接逼你在架构上做「简单问题不走多轮 Agentic RAG（Retrieval-Augmented Generation，检索增强生成）」的分流；「未授权承诺 = 0」这条，逼你把护栏做成硬拦截而非软提示。

| 需求 | 模糊说法 | 可验收指标 |
|---|---|---|
| 安全 | 「不能乱退款」 | 恶意诱导测试集 50 例，未授权承诺 = 0 次 |
| 可控 | 「别死循环」 | 单会话 token ≤ 8k、轮次 ≤ 10，超限强制转人工 |
| 可观测 | 「能追溯」 | 100% 会话有完整 trace，可按 session_id 还原全过程 |
| 延迟 | 「要快」 | 常见问题 P95 延迟 ≤ 3s |
| 准确 | 「答得对」 | 评估集通过率 ≥ 90%，幻觉率 ≤ 2% |

新手写需求只写「要做什么」，老手还会写「不做什么」。明确**非目标**能防止范围蔓延（scope creep）：一期只做中文、只做文本、只被动应答、复杂纠纷一律转人工。把语音、多语言、主动营销划为非目标，才能在有限时间里把「安全 + 可观测」这两条底线做扎实。

### 三种候选架构的取舍

「用多 Agent」不是唯一选择。落地前，至少要在三种架构里做过权衡：

| 架构 | 做法 | 优点 | 缺点 | 适用 |
|---|---|---|---|---|
| 单体大 Agent | 一个 Agent 挂所有工具 | 简单、无路由损耗 | prompt 臃肿、工具多选易错、权限难隔离 | 工具 ≤ 3、场景单一 |
| 中心化编排（本章选） | 分诊 Agent 路由到专家 | 职责清晰、权限可隔离、易独立优化 | 多一跳路由延迟、路由可能错 | 多领域、需权限隔离 |
| 去中心化 handoff | 专家之间直接交接 | 灵活、无单点 | 难追踪、易失控、调试地狱 | 慎用 |

OpenAI Agents SDK（Software Development Kit，软件开发工具包）文档把这两类模式讲得很清楚：**handoffs 是去中心化的对等交接**，控制权移交给专家 Agent 接管对话；**manager（agents as tools）是中心化的**，一个面向用户的 Agent 始终持有对话所有权，把专家当作有边界的能力来调用 [来源](https://github.com/openai/openai-agents-python/blob/main/docs/agents.md)。我们选中心化编排，核心原因是**安全边界可隔离**：客服场景里「谁能升级、谁能碰退款」必须泾渭分明。

## 最小可运行演示

下面把「需求 → 指标」和「架构加权打分」写成可运行代码。打分是**教学参考实现**：给三种架构在五个维度打 1–5 分，权重偏向客服最看重的「权限隔离」和「可观测」，看加权分谁最高。这演示的是「选型要可解释」——不是拍脑袋，而是把偏好显式写成权重。
```python
"""第20.1节：把需求翻译成可验收指标，并给三种候选架构加权打分选型。"""
from dataclasses import dataclass


@dataclass
class Requirement:
    name: str
    fuzzy: str
    metric: str


REQUIREMENTS = [
    Requirement("安全", "不能乱退款", "恶意诱导50例，未授权承诺=0"),
    Requirement("可控", "别死循环", "单会话token<=8k, 轮次<=10"),
    Requirement("可观测", "能追溯", "100%会话有trace，可按session_id还原"),
    Requirement("延迟", "要快", "常见问题P95<=3s"),
    Requirement("准确", "答得对", "评估集通过率>=90%, 幻觉率<=2%"),
]

## 三种候选架构在五个维度上的打分（1-5，越高越好），教学示例
ARCH_SCORES = {
    "单体大Agent": {"简单": 5, "权限隔离": 2, "可独立优化": 2, "可观测": 3, "路由准确": 3},
    "中心化编排": {"简单": 3, "权限隔离": 5, "可独立优化": 5, "可观测": 5, "路由准确": 4},
    "去中心化handoff": {"简单": 2, "权限隔离": 3, "可独立优化": 4, "可观测": 2, "路由准确": 3},
}
## 客服场景权重偏向安全相关维度（权限隔离、可观测最重）
WEIGHTS = {"简单": 1, "权限隔离": 3, "可独立优化": 2, "可观测": 3, "路由准确": 2}


def weighted(scores: dict) -> int:
    return sum(scores[k] * WEIGHTS[k] for k in scores)


def run() -> None:
    print("=== 需求 -> 可验收指标 ===")
    for r in REQUIREMENTS:
        print(f"[{r.name}] 模糊说法“{r.fuzzy}” -> 指标：{r.metric}")
    print("=== 架构加权打分（权重偏向安全相关维度）===")
    ranked = sorted(ARCH_SCORES.items(), key=lambda kv: weighted(kv[1]), reverse=True)
    for name, scores in ranked:
        print(f"{name}: 加权分={weighted(scores)}")
    print(f"选型结论：{ranked[0][0]}")


if __name__ == "__main__":
    run()
```
保存为 `s1_arch.py`，运行 `python s1_arch.py`。完整预期输出：
```text
=== 需求 -> 可验收指标 ===
[安全] 模糊说法“不能乱退款” -> 指标：恶意诱导50例，未授权承诺=0
[可控] 模糊说法“别死循环” -> 指标：单会话token<=8k, 轮次<=10
[可观测] 模糊说法“能追溯” -> 指标：100%会话有trace，可按session_id还原
[延迟] 模糊说法“要快” -> 指标：常见问题P95<=3s
[准确] 模糊说法“答得对” -> 指标：评估集通过率>=90%, 幻觉率<=2%
=== 架构加权打分（权重偏向安全相关维度）===
中心化编排: 加权分=51
去中心化handoff: 加权分=31
单体大Agent: 加权分=30
选型结论：中心化编排
```
**这段代码的价值不在于「算出中心化编排赢」**——那是权重决定的；价值在于**把选型偏好显式化**。如果你的场景把「简单」的权重调到最高（比如一个只有两个工具的小工具），单体大 Agent 完全可能胜出。选型的正确姿势是「亮出权重、让分数说话」，而不是「跟风上多 Agent」。

## 真实系统对应

**官方公开机制**：OpenAI Agents SDK 明确区分 handoffs（去中心化）与 manager/agents-as-tools（中心化）两种编排模式，并建议参考其构建 Agent 实践指南做选择 [来源](https://github.com/openai/openai-agents-python/blob/main/docs/agents.md)；LangGraph 文档把多智能体拓扑分为 supervisor（监督者集中路由）与 network（对等 handoff）等，供按场景取舍 [来源](https://langchain-ai.github.io/langgraph/concepts/multi_agent/)。**通用工程模式**：把非功能需求翻译成可验收指标、用加权打分做可解释选型，是可迁移到任何项目的方法论。**教学参考实现**：上面的打分权重与分值是为讲清「选型可解释」而构造的示例，不代表任何产品的基准评测。

真实落地的规模能佐证「先想清楚再动手」的价值：Klarna 官方新闻稿称其 AI 助手上线首月处理了 230 万次对话、约占其客服对话的三分之二，相当于 700 名全职坐席的工作量，并使重复咨询下降约 25% [来源](https://www.klarna.com/international/press/klarna-ai-assistant-handles-two-thirds-of-customer-service-chats-in-its-first-month/)。但要注意边界：这类新闻稿口径会随时间调整（后续有关于人机配比的讨论），具体数字以官方当前口径为准，本章引用它只为说明「客服是 Agent 落地最成熟的场景之一」，不把某个百分比当永久承诺。

## 生产踩坑

| 症状 | 根因 | 如何观测与复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| 上线后才发现「安全」无处落地 | 需求停在形容词，未翻译成指标 | 检查每条需求是否有对应测试用例 | 每条非功能需求配一条可跑的验收指标 | 纯探索原型可暂缓 |
| 盲目上多 Agent，延迟翻倍 | 未做架构权衡就跟风 | 对比单体与多 Agent 的 P95 延迟 | 用加权打分显式选型，工具少时选单体 | 多领域强隔离场景多 Agent 值得 |
| 范围蔓延，三周做不完 | 没写「非目标」 | 统计需求条目周增长率 | 显式列非目标（语音/多语言/营销推后） | 需求本就稳定的维护型项目 |
| P95 达标但成本爆炸 | 简单问题也走多轮 Agentic RAG | 按问题类型统计平均轮次与 token | 简单问题走单次检索，多跳才 Agentic | 全部为复杂长尾问题时不适用 |
| 指标定了却没人回归 | 指标未接入 CI/评估流水线 | 查最近一次 prompt 改动是否回归 | 把指标做成每次改动必跑的门禁 | 一次性 demo 无需回归 |

## 思考：为什么说「指标是架构的约束条件，不是事后的考试」？

### 回答

因为每一条可验收指标都会反向决定架构里的一个强制点，而形容词不会。举三个例子对照就清楚了。第一，「未授权承诺 = 0」这条指标，逼你把「禁止承诺退款」从 prompt 里的软提示升级成输出侧的硬拦截（正则或分类器），因为软提示无法保证「= 0」——这直接决定了架构里必须有一层独立的输出护栏。第二，「P95 延迟 ≤ 3s」这条，逼你在编排层做「简单问题不走多轮 Agentic RAG」的分流决策，否则多轮模型调用会把 P95 拉爆——这决定了路由层要能区分问题复杂度。第三，「100% 会话可按 session_id 还原」这条，逼你把 trace 做成贯穿全程的横切能力，而不是各 Agent 自己打日志——这决定了会话对象要携带 session_id 并被所有组件共享。反过来，如果需求只写「要安全、要快、要能追溯」，这三个强制点在代码里就没有落脚处，评审时也没有客观判据，事故就成了必然。所以正确的顺序是先定指标、再由指标推导架构，而不是先搭架构、上线后再拿形容词去「考」它。

### 面试精简表达

形容词无法在代码里强制，指标可以。每条可验收指标都对应架构里一个必须存在的强制点（硬护栏、复杂度分流、贯穿 trace）；先定指标再推架构，指标才是约束而非事后考试。

## 事故回放：一句「要安全」如何演变成 328 元事故

回到开头。事故的根源可以精确定位到需求阶段：文档里「要安全」三个字，没有被翻译成「涉赔偿/投诉的意图强制转人工」「退款动作必须人工审批」「输出侧拦截未授权承诺话术」这三条可验收指标。于是在实现时，分诊 Agent 没有高风险词兜底、退款没有审批中断、输出没有护栏——三个强制点集体缺失。凌晨那句带威胁的话恰好同时踩中三个空档，模型顺着情绪「承诺」了退款，前端原样放行。

修复的第一步不是改 prompt，而是补指标：把「要安全」拆成上面三条，每条配一个测试用例（一条测涉赔偿必转人工、一条测退款必审批、一条测输出必拦承诺）。这三条测试后来成了第 7 节评估集里恶意样本的种子。这印证了本节的核心——**事故往往不是败在实现，而是败在需求阶段没把形容词翻译成指标**。优化前只有一句「要安全」的口号；优化后，每一条底线都有一个会跑失败的测试盯着它。
