## 真实问题

3 月 15 日事故之后，团队补了一版分诊逻辑，但很快又踩了新坑：一位用户说「订单金额不对，是不是多扣了钱，我要投诉」，纯模型分类器把它判成了 `order`（订单查询），因为「订单」「金额」这些词的权重压过了「投诉」。结果它被路由到订单专家，只是查了下订单状态就回复「金额无误」，用户情绪进一步升级。**问题不在模型不够强，而在路由策略太单薄**：只靠一个分类器，既没有「涉投诉无条件转人工」的规则红线，也没有「模型自己拿不准就转人工」的置信度兜底。这一节要把意图路由做成「模型分类 + 置信度/规则双兜底」的三层防线，并用代码把「兜底」真正写出来。

## 原理：纯规则不灵活、纯模型不可靠，二者叠加才稳

意图路由有三种典型策略，各有致命短板：

| 路由策略 | 覆盖率 | 可靠性 | 问题 |
|---|---|---|---|
| 纯 if-else 规则 | 低（长尾覆盖不全） | 高（确定性） | 意图稍变就漏 |
| 纯模型分类 | 高 | 中（会误判） | 高风险问题也可能误判 |
| 模型分类 + 置信度/规则双兜底（本章选） | 高 | 高 | 实现稍复杂，值得 |

双兜底的核心思想是**让规则守红线、让模型覆盖长尾、让置信度兜住模型的不确定**。三层的优先级是：
```text
用户输入
   │
   ▼
① 规则红线（最高优先）：命中高风险词（投诉/赔偿/起诉/12315）─▶ 无条件转人工
   │ 未命中
   ▼
② 模型分类 + 置信度：分类器给 (label, score)
   │
   ├─ score < 阈值(0.6) ─▶ 模型自己拿不准 ─▶ 转人工兜底
   │
   └─ score >= 阈值 ─▶ 采信模型，路由到对应专家
```
规则放最前，是因为**它守的是「绝不能放过」的红线**——涉钱、涉投诉的话，哪怕模型 99% 确信是普通咨询，也必须转人工，因为错误分类（把投诉当咨询）的代价远高于多转一次人工。这与 OpenAI Agents SDK 里「input guardrail 在 Agent 运行前检查输入、可短路整个运行」的定位一致：护栏是与主流程并行的独立校验，可以在早期拦截违规输入 [来源](https://developers.openai.com/api/docs/guides/agents/guardrails-approvals.md)。

## 现象与输入：置信度从哪来

真实系统里，「置信度」可以来自分类模型的输出概率、结构化输出里的一个 `confidence` 字段、或多次采样的一致性。本节的 mock 用一个可复核的替代：**用意图关键词的命中数模拟置信度**——命中越多越「自信」。这不代表真实模型的打分方式，只为让演示确定性、可逐字复核。真实接入时把 `classify_with_score` 换成真实分类器即可，兜底逻辑一行不改。

## 最小可运行演示
```python
"""第20.3节：意图路由子 agent —— 模型分类 + 置信度/规则双兜底（mock）。"""
from dataclasses import dataclass

RISK_WORDS = ["投诉", "12315", "起诉", "赔偿", "曝光", "3·15"]
CONF_THRESHOLD = 0.6


@dataclass
class RouteResult:
    label: str
    reason: str
    score: float


## mock 分类器：用关键词命中数模拟“置信度”，确定性可复核
INTENT_KEYWORDS = {
    "order":     ["订单", "金额", "支付", "付款"],
    "logistics": ["快递", "物流", "发货", "到哪", "签收"],
    "knowledge": ["退货", "退换", "政策", "无理由", "保修", "怎么"],
}


def classify_with_score(q: str) -> RouteResult:
    best_label, best_hits = "human", 0
    for label, kws in INTENT_KEYWORDS.items():
        hits = sum(1 for k in kws if k in q)
        if hits > best_hits:
            best_label, best_hits = label, hits
    ## 命中越多“越自信”，最高封顶 0.95；零命中给 0.4
    score = min(0.4 + 0.2 * best_hits, 0.95) if best_hits else 0.4
    return RouteResult(best_label, "", score)


def route(q: str) -> RouteResult:
    ## 规则兜底优先：高风险词无条件转人工（不信任模型）
    if any(w in q for w in RISK_WORDS):
        return RouteResult("human", "命中高风险关键词", 1.0)
    r = classify_with_score(q)
    if r.score < CONF_THRESHOLD:                      ## 低置信兜底
        return RouteResult("human", f"路由置信度低({r.score:.2f})", r.score)
    return r


CASES = [
    "我的订单到哪了",
    "七天无理由退货政策是什么",
    "订单金额不对，是不是多扣了",
    "你们必须赔偿我，否则去12315投诉",
    "呃这个那个我也说不清楚",              ## 零命中 -> 低置信兜底人工
]


def run():
    for q in CASES:
        r = route(q)
        tag = f"score={r.score:.2f}"
        extra = f" reason={r.reason}" if r.reason else ""
        print(f"[{r.label:9}] {tag}{extra}  <- {q}")


if __name__ == "__main__":
    run()
```
保存为 `s3_router.py`，运行 `python s3_router.py`。完整预期输出：
```text
[order    ] score=0.60  <- 我的订单到哪了
[knowledge] score=0.95  <- 七天无理由退货政策是什么
[order    ] score=0.80  <- 订单金额不对，是不是多扣了
[human    ] score=1.00 reason=命中高风险关键词  <- 你们必须赔偿我，否则去12315投诉
[human    ] score=0.40 reason=路由置信度低(0.40)  <- 呃这个那个我也说不清楚
```
逐条看三层防线如何生效：第一条「订单到哪了」命中 `订单`+`到哪`，但「到哪」属 logistics、「订单」属 order，这里演示了**边界模糊时靠命中权重决策**（结果 order，score 0.60 恰好达阈值）；第四条带「赔偿/12315/投诉」，**规则红线直接拦下转人工**（score 1.00），哪怕它也含「订单」类词也不采信模型；第五条语义含糊、零命中，**低置信兜底转人工**（score 0.40）。第四条正是事故那类输入——现在它连模型分类都不用等，规则第一时间就兜住了。

## 真实系统对应

**官方公开机制**：OpenAI 把 input guardrail 定义为在 Agent 运行前检查输入、可短路运行的独立校验，并明确「校验或改写输入」是 guardrail 的典型用途 [来源](https://developers.openai.com/api/docs/guides/agents/guardrails-approvals.md)；一份社区整理的 SDK 指南也点明 guardrail 常常「本身就是一个小而快的 Agent，返回结构化裁决（是否触发 + 原因）」 [来源](https://openai.github.io/openai-agents-python/guardrails/)。LangGraph 的 supervisor 拓扑里，中心协调者「接收每条消息、分类意图、路由到专家」，正是本节路由子 agent 的位置 [来源](https://langchain-ai.github.io/langgraph/concepts/multi_agent/)。**通用工程模式**：规则守红线 + 模型覆盖长尾 + 置信度兜底的三层结构，可迁移到任何路由/分诊场景。**教学参考实现**：用关键词命中数模拟置信度是为可复核而构造，真实系统请用分类器概率或结构化输出的 confidence 字段。

一个必须澄清的边界：真实模型给出的「置信度」并不总是可靠的概率（存在过度自信问题），所以生产上常用「多信号」而非单一分数——比如置信度 + 是否命中敏感词 + 历史该用户是否已投诉。本节为讲清机制只用了单一模拟分数，落地时应结合业务信号做更稳的兜底。

## 生产踩坑

| 症状 | 根因 | 如何观测与复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| 投诉被当普通咨询处理 | 只有模型分类，无规则红线 | 用「订单+投诉」混合句复现误判 | 高风险词规则前置、无条件转人工 | 无敏感/投诉语义的场景 |
| 含糊问题被强行归到某专家 | 无低置信兜底，取 argmax 硬分 | 输入语义含糊句看是否仍被硬分 | score < 阈值时转人工兜底 | 意图空间极小且互斥时 |
| 阈值拍脑袋定 0.6 导致误转/漏转 | 未用评估集校准阈值 | 在评估集上扫阈值看准确率曲线 | 用标注数据网格搜索最优阈值 | 无评估集的早期原型 |
| 过度自信的分数骗过兜底 | 单一依赖模型概率，未加业务信号 | 找模型高分但实际错分的样本 | 多信号兜底（分数+敏感词+历史） | 分类任务简单、模型校准良好时 |
| 新意图上线后长期误路由 | 关键词/类别表长期不更新 | 统计 human 兜底里的高频真实意图 | 定期从低置信日志挖新意图补类别 | 意图集合稳定不变的封闭域 |

## 思考：为什么规则红线要放在模型分类之前，而不是之后做「二次校验」？

### 回答

因为红线的语义是「无条件」，而放在模型之后会给「模型误判 + 校验遗漏」留出叠加出错的窗口。设想把顺序反过来：先让模型分类，再用规则做二次校验。这时有两个隐患。其一，如果模型把「订单金额不对我要投诉」判成 order 并且分类流程里有某个提前返回（比如高置信直接执行），规则校验可能根本没机会跑——顺序上「先执行后校验」天然有竞态。其二，即便每次都校验，逻辑也变成「模型说了算，除非规则否决」，这在心智模型上是错的：涉投诉/赔偿的输入，我们的立场是「默认不信任任何自动处理」，而不是「先信任模型、再看要不要否决」。把规则放最前，语义就变成「先过红线，红线放行了才轮到模型」，这与业务立场一致——红线是准入条件，不是事后补丁。此外，规则前置还有性能与成本收益：命中红线的输入直接转人工，省掉一次模型分类调用；对高频的投诉/催单场景，这笔省下的调用量不小。所以正确顺序是规则红线 → 模型分类 → 置信度兜底，三层从「最不信任」到「较信任」递进。

### 面试精简表达

红线是准入条件不是事后补丁。放模型之后会有「先执行后校验」的竞态，且心智变成「默认信任模型再否决」，与「涉钱涉投诉默认不信任」的业务立场相悖；前置还能省掉一次分类调用。

## 优化前后对比：从单分类器到三层防线

优化前的路由是一行 `label = classifier(q)`，直接取模型的 argmax。它的问题在事故复盘里暴露无遗：一是**没有红线**，涉投诉/赔偿的输入完全交给模型判断，模型被「订单」「金额」等词带偏就误路由；二是**没有兜底**，含糊输入被强行归到某个专家，专家答非所问；三是**不可解释**，出了错只能看到一个 label，不知道模型有多确信、为什么这么分。

优化后引入三层防线，可观测性也随之提升：每次路由都产出 `(label, score, reason)` 三元组，写进 trace 后，运营能统计「有多少比例走了规则红线、多少走了低置信兜底、模型平均置信度多高」。这些数字反过来指导优化——比如低置信兜底里如果反复出现「保修相关」的问题，说明该新增一个「售后保修」专家类别（这正是第 7 节数据飞轮里「从低置信日志挖新意图」的来源）。路由从「一个黑箱 label」变成「可解释、可统计、可迭代的决策」，这才是生产级路由与作业级路由的差距。
