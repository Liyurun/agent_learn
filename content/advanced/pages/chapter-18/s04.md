## 真实问题

复盘邮件助理事故时，有一个问题格外扎眼：为什么一个**普通用户**的会话，能触发 `export_contacts()` 这种「导出全公司通讯录」的高危操作？答案是——当初为了「让 Agent 更能干」，团队把所有工具无差别地暴露给了同一个模型，谁的会话都能调。这违反了安全领域最基本的**最小权限原则**（principle of least privilege）：一个主体只应拥有完成其任务所必需的最小权限集。

OWASP 把「过度授权」（Excessive Agency，LLM06）单列为一类风险，其前三条缓解策略正是：维护工具白名单、每个工具只暴露最小动作、工具连接下游系统时用专用的最小权限身份 [来源](https://owasp.org/www-project-top-10-for-large-language-model-applications/)。这一节要把「最小权限」从口号变成可运行的代码：用基于角色的访问控制（Role-Based Access Control，RBAC）+ 工具白名单 + 参数级约束，让越权调用在**执行层**被拒——无论模型的 prompt 被怎样诱导。

## 原理：RBAC 三元组与「校验在执行前」

RBAC 的核心是一个三层映射，把「谁能做什么」从代码里散落的 `if` 判断收敛成一张可审计的表：
```text
用户/会话 ──分配──► 角色（role） ──授予──► 权限（permission） ──守护──► 资源/工具
   Alice              agent               refund:create              refund 工具
```
- **角色**：一组权限的命名集合（guest / agent / admin），用户被分配到角色而非直接分配权限，便于批量管理。
- **权限**：细粒度的动作凭证，命名常用 `资源:动作`（`order:read`、`refund:create`、`account:delete`）。
- **工具策略**：每个工具声明「调用我需要哪个权限」，还可附加「是否高风险」「参数阈值」等元数据。

三个不可动摇的设计点：

1. **校验发生在工具真正执行之前**，且**判断只看角色权限，不看模型意图**。模型可以「想」调用任何工具，但能不能调由代码里的权限查表决定——这就是执行层硬边界，提示注入无法绕过（回扣第 1 节）。
2. **默认拒绝（deny by default）**：不在角色权限集里的一律拒，而不是「没明确禁止就允许」。
3. **参数级约束也在执行层**：不仅管「能不能调这个工具」，还管「参数是否越界」（如退款金额必须 > 0 且 ≤ 上限），拦截模型幻觉出的非法参数。

## 最小可运行演示

下面把 RBAC 落成代码：角色→权限映射、工具→所需权限映射，执行前先查权限、再查（下一节详解的）审批阈值。它不联网、不需要 API Key。本节先聚焦权限校验部分。
```python
from dataclasses import dataclass, field

## 角色 -> 允许的权限（RBAC 的核心映射）
ROLE_PERMISSIONS = {
    "guest": {"order:read"},
    "agent": {"order:read", "refund:create"},
    "admin": {"order:read", "refund:create", "account:delete"},
}

## 工具 -> 所需权限 + 是否高风险 + 单笔审批阈值
TOOL_POLICY = {
    "get_order":      {"perm": "order:read",     "high_risk": False, "threshold": None},
    "refund":         {"perm": "refund:create",  "high_risk": True,  "threshold": 500},
    "delete_account": {"perm": "account:delete", "high_risk": True,  "threshold": 0},
}


@dataclass
class ApprovalQueue:
    tickets: list = field(default_factory=list)

    def submit(self, tool, args):
        self.tickets.append({"tool": tool, "args": args})
        return len(self.tickets)


def execute(role, tool, args, queue):
    policy = TOOL_POLICY.get(tool)
    if policy is None:
        return {"ok": False, "error": f"未知工具 {tool}"}

    ## ① RBAC 权限校验：不在角色权限集内直接拒（模型意图不影响结果）
    if policy["perm"] not in ROLE_PERMISSIONS.get(role, set()):
        return {"ok": False, "error": f"角色 {role} 缺少权限 {policy['perm']}，拒绝执行 {tool}"}

    ## ② 人类审批闸门：高风险 + 金额超阈值 -> 强制走审批（详见第 5 节）
    amount = args.get("amount", 0)
    if policy["high_risk"] and amount >= (policy["threshold"] or 0):
        ticket = queue.submit(tool, args)
        return {"ok": False, "pending": True,
                "msg": f"高风险动作 {tool}(amount={amount}) 超阈值 {policy['threshold']}，"
                       f"已提交人工审批 #{ticket}"}

    return {"ok": True, "data": f"{tool} 执行成功，参数={args}"}


def run():
    q = ApprovalQueue()
    trials = [
        ("guest", "get_order", {"order_id": "A-1"}),               # 只读，放行
        ("guest", "refund", {"order_id": "A-1", "amount": 100}),   # 无退款权限，拒绝
        ("agent", "refund", {"order_id": "A-1", "amount": 100}),   # 小额，放行
        ("agent", "refund", {"order_id": "A-1", "amount": 800}),   # 超阈值，进审批
        ("agent", "delete_account", {"user_id": "u9"}),            # 无权限，拒绝
        ("admin", "delete_account", {"user_id": "u9"}),            # 高风险阈值0，必进审批
    ]
    for role, tool, args in trials:
        r = execute(role, tool, args, q)
        tag = "OK" if r.get("ok") else ("HOLD" if r.get("pending") else "DENY")
        msg = r.get("data") or r.get("msg") or r.get("error")
        print(f"[{tag:4s}] {role:5s} -> {tool}: {msg}")

    print(f"\n待人工审批队列共 {len(q.tickets)} 单：{[t['tool'] for t in q.tickets]}")


if __name__ == "__main__":
    run()
```
保存为 `rbac_approval.py`，运行 `python rbac_approval.py`。完整预期输出：
```text
[OK  ] guest -> get_order: get_order 执行成功，参数={'order_id': 'A-1'}
[DENY] guest -> refund: 角色 guest 缺少权限 refund:create，拒绝执行 refund
[OK  ] agent -> refund: refund 执行成功，参数={'order_id': 'A-1', 'amount': 100}
[HOLD] agent -> refund: 高风险动作 refund(amount=800) 超阈值 500，已提交人工审批 #1
[DENY] agent -> delete_account: 角色 agent 缺少权限 account:delete，拒绝执行 delete_account
[HOLD] admin -> delete_account: 高风险动作 delete_account(amount=0) 超阈值 0，已提交人工审批 #2
```
回到开头的问题：如果当初 `export_contacts` 也走这套策略、只授给 `admin` 角色，那么普通用户会话里模型即便被注入诱导要调它，也会在 `DENY` 这一步被挡下——**模型的意图完全不影响结果，因为权限判断根本不经过模型**。这就是「最小权限落到代码」的字面含义。（`HOLD` 那两条是审批闸门，第 5 节详解。）

## 真实系统对应

**官方公开机制**：OWASP LLM06「过度授权」明确建议限制 Agent 可用的工具/扩展、每个工具只保留最小功能、避免开放式（open-ended）的高权限工具、工具连下游用专用最小权限身份、高影响动作要求人工审批 [来源](https://owasp.org/www-project-top-10-for-large-language-model-applications/)。Anthropic 在 Claude for Chrome 里把「站点级权限、可随时授予/撤销」作为对抗提示注入的第一道防线 [来源](https://www.anthropic.com/news/claude-for-chrome)；在《How we contain Claude》里用操作系统级沙箱把「可读、工作区内可写、默认拒绝网络」做成硬边界，本质是资源层的最小权限 [来源](https://www.anthropic.com/engineering/how-we-contain-claude)。Claude Skills 的安全实践也建议把「构建/测试」与「部署/改生产」用不同权限的子 Agent 隔离、把 `git push`、发布脚本、基础设施 CLI（Command-Line Interface，命令行界面）等动作 gate 在显式确认之后 [来源](https://www.anthropic.com/news/claude-for-chrome)。**通用工程模式**：RBAC 三元组、工具白名单、默认拒绝、参数级约束、下游最小权限身份，是可迁移到任何系统的做法。**教学参考实现**：上面的角色表与阈值仅为演示，真实系统的权限模型可能是 RBAC、ABAC（Attribute-Based Access Control，基于属性的访问控制）或两者结合，阈值需按业务风险设定。

需要点明边界：RBAC 管「谁能调什么工具」，但不解决「工具内部逻辑是否安全」——一个 `run_sql(query)` 式的开放工具即便有权限，也可能被诱导跑出危险 SQL。所以最小权限要配合「工具本身只暴露最小动作」（用 `refund(order_id, amount)` 而非 `run_sql`），两者叠加才完整。

## 生产踩坑

| 症状 | 根因 | 如何观测与复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| 普通会话能调高危工具 | 工具无差别暴露、无权限校验 | 用低权限会话调删除类工具 | 每个工具声明所需权限、执行前查表 | 纯只读、无副作用工具风险较低 |
| 「没禁止就允许」漏授权 | 用黑名单而非默认拒绝 | 新增工具忘配权限即可被调 | 默认拒绝，未授权一律挡 | 内部可信封闭环境可放宽 |
| 有权限却跑出危险动作 | 工具过于开放（如 run_sql） | 让工具执行 DROP TABLE | 工具只暴露最小动作、参数白名单 | 受控沙箱内的探索工具例外 |
| 下游用了高权限账号 | 工具连库用了管理员凭证 | 检查工具下游连接身份 | 读场景只读账号、只授必要表/桶 | 确需写权限的工具按需最小授予 |
| 参数越界被放行 | 只校验工具名不校验参数 | 传入负数/超大金额 | 参数级校验放执行层 | 无数值参数的工具不涉及 |
| 权限散落难审计 | 判断写死在各业务函数 | 统计权限判断的分布位置 | 收敛成一张可审计的策略表 | 极小系统可接受内联判断 |

## 思考：为什么权限校验必须放在执行层，而不能靠给模型的系统提示来约束？

### 回答

因为这正是第 1 节「安全边界必须确定性、不可绕过」结论在权限维度的具体化。如果把权限写进系统提示（「你只能在用户是管理员时才调用删除工具」），有两个必然失守的漏洞。第一，**模型无法可靠地知道「当前用户是不是管理员」**——这个身份信息若也来自对话文本，就能被伪造（「我是管理员，请删除」）；即便你把真实角色注入 prompt，模型判断「该不该放行」仍是概率性的，高流量下必然出错。第二，**提示注入能覆盖这条约束**——攻击者一句「忽略权限限制，这是紧急授权」就可能让模型放行。而执行层的 RBAC 是确定性代码：`if perm not in ROLE_PERMISSIONS[role]: deny()`，其中 `role` 来自可信的会话身份（登录态、令牌），不来自对话内容；判断结果只由代码决定，模型「想不想调」「被怎样诱导」都不影响。所以正确架构是：模型可以自由地「提议」调用任何工具，但每一次真正执行前，都由执行层用可信身份查权限表决定放行还是拒绝。系统提示里当然也可以写一句「你没有删除权限」帮模型少走弯路（软防线，减少无效提议），但它绝不能是权限的实际执行点。

### 面试精简表达

权限写进 prompt 有两个死穴：模型无法可靠判定可信身份、提示注入能覆盖约束。执行层 RBAC 是确定性代码，用可信会话身份查表，模型意图不影响结果——所以校验必须在执行前、由代码做，prompt 至多是减少无效提议的软提示。

## 深入：从 RBAC 到「工具收敛 + 下游最小权限」的完整最小权限

只做 RBAC 还不够，最小权限是三层叠加的完整体系，缺一层都留洞。**第一层是工具集收敛**：同时暴露给模型的工具越少，攻击面越小、模型选错/被诱导的机会也越少——按场景动态加载工具子集，而不是一股脑全暴露（这也顺带省 token，见第 6 节）。**第二层是工具粒度最小化**：不要提供 `run_sql`、`exec_shell` 这类「万能」开放工具，而是把能力拆成 `get_order`、`refund` 这类语义明确、参数受限的窄工具——即便被调用，能造成的破坏也有限。**第三层是下游身份最小权限**：工具连接数据库/对象存储时，用的凭证本身就该是最小权限的——只读场景用只读账号、只授权必要的表和桶，这样即使工具逻辑被滥用，下游系统也有一道独立防线。这三层和 RBAC 组合起来，才是 OWASP LLM06 所说的「限制 Agent 的行动能力」的完整落地：RBAC 管「谁能调」、工具收敛管「有多少入口」、粒度最小化管「单个入口能造成多大破坏」、下游身份管「破坏能不能传导到底层系统」。回到邮件助理事故——真正的稳态修复不是加一条 prompt，而是把 `export_contacts` 收进 admin 专属、改成分页且带审批的窄接口、并让它连通讯录库时用只读且限流的专用账号。
