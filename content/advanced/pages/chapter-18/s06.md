## 真实问题

安全问题止血后，账单问题浮出水面：邮件助理上线第一个月的模型调用费是预算的 7 倍。财务追问「钱花哪了」，团队一开始以为是「答案太长」，去压缩输出长度，收效甚微。真正拉出用量明细才发现两个大头：其一，**所有请求都用最强、最贵的模型跑**——哪怕只是「订单什么时候发货」这种一句话就能答的简单问题；其二，一个长达 4,000 token 的系统提示 + 工具定义，**每一轮都完整重发**给模型。前者是「杀鸡用牛刀」，后者是「重复付费」。

这一节先解决第一个大头——**模型分层路由**（也叫 model routing / cascading）：用便宜的小模型处理简单请求，只在真正需要复杂推理时才动用昂贵的强模型。OpenAI 和 Anthropic 都提供从小到大的多档模型，单价常相差一个数量级，路由得当能省下大头。（第二个大头「重复重发前缀」由第 7 节的 prompt caching 解决。）

## 原理：成本的乘式，与分层路由为何「性价比最高」

先把 Agent 成本拆成一个乘式，理解了它就不用死记优化清单：
```text
Agent 成本 ≈ 轮次 × 每轮 token 单价
            其中每轮 token = (稳定前缀 + 累积历史 + 新增) × 模型单价
```
这个乘式有三个可下手的因子：**轮次**（减少步数、第 13 章的代码即动作）、**每轮 token 量**（上下文压缩、缓存前缀）、**单价**（分层路由）。分层路由动的是「单价」这个因子，而它之所以**性价比最高**，是因为一个反直觉的事实：**一个 Agent 任务里的绝大多数步骤，其实是简单决策**——判断意图、决定下一步调哪个工具、格式化输出——这些用小模型完全够用；只有少数真正需要多步推理、代码生成的步骤才值得动用强模型。

分层路由的关键设计是「**用廉价手段分诊，再决定要不要请强模型出场**」：
```text
请求 ──► 廉价分诊（规则 or 极小模型）──► 判定复杂度
                                          │
                    ┌─────────────────────┼─────────────────────┐
                 simple                  mid                    hard
                    │                     │                      │
              小模型（便宜）          中模型              强模型（贵，仅少数）
```
分诊本身很便宜（一条规则或一次极小模型调用），但它能把大量简单请求挡在强模型之外——**一次廉价的判断，省下大量昂贵的调用**，这就是「性价比最高」的来源。代价是分诊可能出错（把复杂问题误判为简单），所以分诊要偏保守：拿不准就往上走一档，宁可偶尔多花一点，也别让复杂问题被小模型做砸而降质。

## 最小可运行演示

下面用纯 Python 实现一个分诊 + 路由器，并对比「全用强模型」与「分层路由」两种策略的总成本。价格为教学示例常数，真实单价以官方定价页为准。它不联网、不需要 API Key。
```python
from dataclasses import dataclass

## 教学用示例价格（美元 / 1M input token），真实价格以官方文档为准
PRICE_PER_MTOK = {"small": 0.15, "large": 3.00}


@dataclass
class Query:
    text: str
    input_tokens: int


def triage(q):
    ## 廉价分诊：短、无多步推理关键词 -> simple；否则 hard
    hard_kw = ["分析", "推理", "生成代码", "多步", "为什么", "设计方案"]
    if q.input_tokens < 400 and not any(k in q.text for k in hard_kw):
        return "simple"
    return "hard"


def route(q):
    return "small" if triage(q) == "simple" else "large"


def cost(tier, tokens):
    return PRICE_PER_MTOK[tier] * tokens / 1_000_000


def run():
    workload = [
        Query("今天几号", 20),
        Query("查一下订单状态", 60),
        Query("把这句话翻译成英文", 80),
        Query("帮我改个收货地址", 70),
        Query("订单什么时候发货", 50),
        Query("确认一下我的会员等级", 90),
        Query("这个优惠券怎么用", 85),
        Query("请分析这段日志为什么会出现死循环并给出修复方案", 1200),
        Query("生成代码实现一个带重试的下单接口", 900),
    ]

    all_large = sum(cost("large", q.input_tokens) for q in workload)

    routed_total = 0.0
    print("=== 分层路由决策 ===")
    for q in workload:
        tier = route(q)
        c = cost(tier, q.input_tokens)
        routed_total += c
        print(f"  {q.text[:16]:<18} tokens={q.input_tokens:>5} -> {tier:<5} 成本=${c:.6f}")

    saved = all_large - routed_total
    print(f"\n全部用强模型总成本：   ${all_large:.6f}")
    print(f"分层路由总成本：       ${routed_total:.6f}")
    print(f"节省：                 ${saved:.6f}（{saved / all_large:.1%}）")


if __name__ == "__main__":
    run()
```
保存为 `model_routing.py`，运行 `python model_routing.py`。完整预期输出：
```text
=== 分层路由决策 ===
  今天几号               tokens=   20 -> small 成本=$0.000003
  查一下订单状态            tokens=   60 -> small 成本=$0.000009
  把这句话翻译成英文          tokens=   80 -> small 成本=$0.000012
  帮我改个收货地址           tokens=   70 -> small 成本=$0.000010
  订单什么时候发货           tokens=   50 -> small 成本=$0.000008
  确认一下我的会员等级         tokens=   90 -> small 成本=$0.000013
  这个优惠券怎么用           tokens=   85 -> small 成本=$0.000013
  请分析这段日志为什么会出现死循环   tokens= 1200 -> large 成本=$0.003600
  生成代码实现一个带重试的下单接口   tokens=  900 -> large 成本=$0.002700

全部用强模型总成本：   $0.007665
分层路由总成本：       $0.006368
节省：                 $0.001297（16.9%）
```
这个 16.9% 的节省看似不高，是因为示例负载里两条 hard 请求的 token 量特别大（1200、900），单价高的它们主导了总成本。**这恰恰揭示了分层路由的真实收益规律**：省下的钱正比于「被路由到小模型的请求占比 × 强弱模型单价差」。如果你的负载像真实客服那样 80%+ 是简单短请求，节省会显著得多；如果负载几乎全是重推理任务，路由收益就有限——这时该转向压缩和缓存（第 7 节）。**关键不是背下某个百分比，而是理解「路由省的是单价，收益取决于简单请求的占比」**。

## 真实系统对应

**官方公开机制**：OpenAI 与 Anthropic 都提供分档的模型家族（从轻量到旗舰），官方定价页公开各档单价，且明确「更小的模型更便宜、更快」，适合简单任务 [来源](https://platform.openai.com/docs/guides/prompt-caching)。OpenAI《A Practical Guide to Building Agents》建议「先用最强模型建立质量基线，再逐步用小模型替换能胜任的环节」，这正是分层路由的落地方法论 [来源](https://cdn.openai.com/business-guides-and-resources/a-practical-guide-to-building-agents.pdf)。**通用工程模式**：用廉价分诊（规则或小模型）决定复杂度、再路由到对应档位模型，是可迁移到任何厂商的做法；分诊器本身也可以是一个被路由的小模型。**教学参考实现**：上面的关键词分诊与示例价格仅用于演示原理，真实系统的复杂度分诊常用小模型 + 特征（长度、是否需工具、历史轮次），价格必须以当前官方定价为准。

需要点明边界：分层路由的收益高度依赖负载分布和模型单价差，不存在「一定省 X%」的普适数字；分诊错误会带来降质，需用评估集（第 16 章）监控路由后的质量回归。此外，「先建质量基线再降档」的顺序不能反——没有基线就直接用小模型，你无法判断是省了钱还是悄悄降了质。

## 生产踩坑

| 症状 | 根因 | 如何观测与复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| 路由后质量悄悄下降 | 分诊把复杂问题误判为简单 | 抽样对比 small/large 答案质量 | 分诊保守、复杂信号触发升级、评估监控 | 全简单任务时降质风险低 |
| 路由几乎没省钱 | 负载几乎全是重推理任务 | 统计各档命中占比 | 转向压缩/缓存，或优化任务分解 | 简单请求占比高时收益自然大 |
| 分诊本身成了新成本 | 分诊用了较大模型 | 测量分诊调用的费用占比 | 分诊用规则或极小模型 | 分诊必须用模型时权衡其成本 |
| 降档后无法判断得失 | 没先建强模型质量基线 | 直接上小模型无对照 | 先建基线再逐环节降档 | 一次性任务可不建基线 |
| 强模型仍被简单请求占用 | 路由规则过于宽松 | 看强模型调用里简单请求占比 | 收紧 simple 判定、加长度/关键词特征 | 高价值场景宁可多用强模型 |
| 上下文膨胀抵消路由收益 | 只优化单价忽略 token 量 | 统计各轮 input token 增长 | 叠加压缩与缓存（乘式的另一因子） | 短对话膨胀影响可忽略 |

## 思考：模型分层路由为什么被称为「性价比最高」的成本优化？它的收益取决于什么？

### 回答

「性价比最高」指的是**投入产出比**：分层路由的实现成本很低（加一个廉价分诊器和一张路由表），但撬动的是单价这个最大的成本杠杆——强弱模型单价常差一个数量级，把本可以用小模型处理的请求从强模型上挪走，等于直接按数量级省钱。它的底层依据是一个经验事实：Agent 任务里绝大多数步骤是简单决策（判断意图、选工具、格式化），只有少数需要强推理，所以「大部分请求本就不需要强模型」。但收益不是恒定的，它精确地取决于两个量的乘积——**被路由到便宜档位的请求占比 × 强弱模型的单价差**。这解释了两个现象：一是像客服这种简单请求占大头的负载，路由能省很多；二是像代码智能体这种几乎全是重推理的负载，路由收益有限（该转向压缩和缓存）。所以回答这个问题不能只说「便宜模型省钱」，而要点出「省的是单价、收益随简单请求占比放大」，并主动说明它的代价——分诊误判会降质，需要先建强模型质量基线、再逐环节降档，并用评估集持续监控路由后的质量，防止「省了钱却悄悄降了质」。

### 面试精简表达

它用极低的实现成本（分诊器+路由表）撬动最大的杠杆——单价（强弱模型差一个数量级）。收益 = 简单请求占比 × 单价差，所以客服类负载收益大、纯重推理负载收益小。代价是分诊误判降质，需先建基线再降档、用评估集监控。

## 深入：把分层路由放进乘式，看清它与其他手段的分工

很多人把成本优化手段当成一份并列的清单去背，其实它们各自作用在乘式的不同因子上，理解分工才能对症下药。**分层路由**动的是「单价」——它不改变你发了多少 token、跑了多少轮，只是让每个 token 用更便宜的模型算。**上下文压缩**动的是「每轮 token 量」——定期把冗长历史摘要成关键信息、裁剪臃肿的工具返回，让每一轮塞进去的 token 变少；代价是摘要有损，压过头会让 Agent「失忆」，所以要保守。**减少步数**动的是「轮次」——用代码即动作（第 13 章）把「一次调一个工具、来回好几轮」变成「一段代码一次完成多个操作」，轮次少了，那个随上下文累积的「平方级」token 账自然就小了（回扣第 8 章：模型无状态，每轮重发历史，token 随轮数增长）；代价是需要更强的模型生成可靠代码和一个安全沙箱。**控制工具数量**动的是「每轮的固定 token」——每暴露一个工具，它的名字、描述、参数 schema 都要塞进每一轮 prompt，工具太多既费 token 又让模型挑花眼。把这四条放回乘式就一目了然：想省钱，要么降单价（路由）、要么压每轮量（压缩/控工具）、要么减轮次（减步数）——**没有银弹，只有针对当前瓶颈因子的对症下药**。而下一节的 prompt caching，动的则是乘式里最隐蔽的一项：那个「每轮都重发的稳定前缀」，它既不减轮次也不换模型，而是让重复的前缀部分按折扣计费。
