## 真实问题

邮件助理的账单事故，最刺痛人的不是「贵」，而是**没有任何东西在花钱失控时踩刹车**。分层路由（第 6 节）和 prompt caching（第 7 节）都在「让每次调用更便宜」，但它们都有一个共同的盲区：**它们不设上限**。真实压垮预算的往往不是「单次调用贵」，而是三类失控叠加——其一，一个循环 Agent 陷入「查无结果→再查→再查」的重试风暴，几分钟内烧掉一天的额度（回扣第 8 章的循环控制）；其二，某个上游脚本 bug 或恶意用户在一秒内打进上千个请求，把并发和费用同时顶爆；其三，月底促销流量翻十倍，谁都没设一个「花到这里就停」的硬线。事故当天的复盘结论只有一句话：**降低单价治不了失控，失控要靠硬闸门。**

这一节给成本装上两道确定性的硬闸门——**限流**（rate limiting，控制「单位时间能发多少请求」）与**预算熔断**（budget circuit breaker，控制「累计能花多少钱」）——并把全章收口到一个绕不开的工程判断：**成本、延迟、质量（cost / latency / quality）三者不可兼得的三角权衡**。前面所有手段（护栏、路由、缓存、限流）本质上都是在这个三角里选一个适合当前业务的落点。

## 原理：两道硬闸门 + 一个三角

### 硬闸门一：令牌桶限流，既压峰又容突发

限流最朴素的做法是「固定窗口计数」（每秒最多 N 个），但它有个硬伤——**边界突刺**：在窗口交界处（如第 0.99 秒和第 1.01 秒）可能瞬间放进 2N 个请求。**令牌桶（token bucket）** 是更平滑的经典算法，它的模型只有两个参数：
```text
容量 capacity：桶最多装多少令牌（决定"允许多大的突发"）
补充速率 refill_rate：每秒往桶里加多少令牌（决定"长期平均速率"）

每来一个请求：先按流逝时间补令牌（不超过容量）→ 桶里够就扣减放行，不够就拒绝(429)
```
它的妙处在于同时兼顾两个看似矛盾的目标：**长期平均速率**被 `refill_rate` 卡死（防止持续过载），但**短时突发**又被 `capacity` 允许（桶里攒着的令牌可以一次性放出，不误伤正常的流量尖峰）。这正是 OpenAI、Anthropic 等 API 限流的通用思路——它们的 429（Too Many Requests）配合 `Retry-After` 头，就是在告诉你「桶空了，等这么久再来」[来源](https://platform.openai.com/docs/guides/rate-limits)。

### 硬闸门二：预算熔断，fail-closed 而非 fail-open

预算闸门比限流更「狠」：它不管速率，只管**累计花费**。核心设计原则是 **fail-closed（失败即关闭）**——一旦累计成本触及预算上限，立即停止发起新调用并告警，而不是「先放过去再说」（fail-open）。这个方向选择在安全和成本领域是铁律：**宁可停机，不可失控**。因为 Agent 的成本是「先花后知道」的——等你看到账单时钱已经花了，所以闸门必须在**每次调用前**用「已花 + 本次预估 > 预算？」来判断，超了就熔断。

预算可以分层设置形成纵深：单次请求预算（防单个任务失控）、单用户/单会话预算（防单点滥用）、全局日/月预算（防整体超支）。任一层触顶都熔断对应范围。

### 三角权衡：为什么没有「既快又好又便宜」

把全章手段放在一起看，会发现它们都在同一个三角里做取舍——**成本、延迟、质量三者最多同时优化两个**：
```text
              质量（Quality）
                  ▲
                 ╱ ╲
                ╱   ╲   强模型 = 高质量高成本高延迟
               ╱     ╲
              ╱       ╲
   成本 ◀────────────────▶ 延迟
  (Cost)                (Latency)

- 想要"低成本+低延迟" → 用小模型，牺牲质量（分层路由的 simple 档）
- 想要"高质量+低延迟" → 用强模型不压缩，牺牲成本
- 想要"高质量+低成本" → 强模型 + 缓存/压缩，牺牲延迟（首轮写缓存更慢）
```
这个三角不是让你「找到最优解」，而是逼你**先明确当前业务把哪个角当成硬约束**：金融风控把质量当硬约束（错一次代价极高，宁可慢、贵）、高并发客服把延迟和成本当硬约束（可以牺牲一点质量换秒回和低价）、离线批处理把成本当硬约束（可以很慢，用最便宜的档跑）。**所有护栏与优化手段，本质都是在这个三角里为特定业务选定一个落点，并用限流和预算给这个落点上锁。**

## 最小可运行演示

下面用纯 Python 实现令牌桶限流 + 预算熔断两道硬闸门。它不联网、不需要 API Key，用固定时间戳让输出可逐字复核。
```python
"""预算与限流演示（纯 Python，无需 API Key）。"""
from __future__ import annotations

from dataclasses import dataclass


class TokenBucket:
    ## 经典令牌桶：容量 capacity，每秒补 refill_rate 个令牌
    def __init__(self, capacity, refill_rate, now=0.0):
        self.capacity = capacity
        self.refill_rate = refill_rate
        self.tokens = capacity
        self.last = now

    def allow(self, cost, now):
        ## 先按流逝时间补令牌（不超过容量），再尝试扣减
        elapsed = now - self.last
        self.tokens = min(self.capacity, self.tokens + elapsed * self.refill_rate)
        self.last = now
        if self.tokens >= cost:
            self.tokens -= cost
            return True
        return False


@dataclass
class BudgetGuard:
    ## 成本硬闸门：累计花费不得超过 budget，超了就熔断（fail-closed）
    budget: float
    spent: float = 0.0

    def try_spend(self, amount):
        if self.spent + amount > self.budget:
            return False
        self.spent += amount
        return True


def run():
    print("=== 令牌桶限流：容量5、每秒补1，突发6次请求 ===")
    bucket = TokenBucket(capacity=5, refill_rate=1.0, now=0.0)
    for i in range(6):
        ok = bucket.allow(cost=1, now=0.0)   # 同一时刻的突发
        print(f"  请求{i + 1}: {'放行' if ok else '限流(429)'} 剩余令牌={bucket.tokens:.1f}")
    ok = bucket.allow(cost=1, now=2.0)       # 等待 2 秒后补回令牌
    print(f"  2秒后再请求: {'放行' if ok else '限流(429)'} 剩余令牌={bucket.tokens:.1f}")

    print("\n=== 成本预算熔断：预算 $0.010，每轮花 $0.003 ===")
    guard = BudgetGuard(budget=0.010)
    for turn in range(1, 6):
        if not guard.try_spend(0.003):
            print(f"  第{turn}轮: 预算耗尽（已花 ${guard.spent:.3f}）-> 熔断停机、告警")
            break
        print(f"  第{turn}轮: 放行，累计花费 ${guard.spent:.3f}")


if __name__ == "__main__":
    run()
```
保存为 `budget_ratelimit.py`，运行 `python budget_ratelimit.py`。完整预期输出：
```text
=== 令牌桶限流：容量5、每秒补1，突发6次请求 ===
  请求1: 放行 剩余令牌=4.0
  请求2: 放行 剩余令牌=3.0
  请求3: 放行 剩余令牌=2.0
  请求4: 放行 剩余令牌=1.0
  请求5: 放行 剩余令牌=0.0
  请求6: 限流(429) 剩余令牌=0.0
  2秒后再请求: 放行 剩余令牌=1.0

=== 成本预算熔断：预算 $0.010，每轮花 $0.003 ===
  第1轮: 放行，累计花费 $0.003
  第2轮: 放行，累计花费 $0.006
  第3轮: 放行，累计花费 $0.009
  第4轮: 预算耗尽（已花 $0.009）-> 熔断停机、告警
```
两段输出对应两道闸门的确定性行为。令牌桶：容量 5 的桶在同一时刻放行前 5 个、第 6 个因桶空被限流；2 秒后补回 2 个令牌（每秒 1 个），再请求即放行——**长期平均被 refill_rate 卡住，突发被 capacity 允许**。预算熔断：每轮花 $0.003，第 4 轮之前「已花 $0.009 + 本次 $0.003 = $0.012 > $0.010」触发熔断，**注意它是在花之前判断、超了就停，而不是花超了才发现**。这就是 fail-closed：钱还没花出去，闸门已经落下。

## 真实系统对应

**官方公开机制**：OpenAI 的 Rate limits 文档说明限流按 RPM（Requests Per Minute，每分钟请求数）/TPM（Tokens Per Minute，每分钟 token 数）等维度施加，超限返回 429 并建议指数退避、尊重 `Retry-After` [来源](https://platform.openai.com/docs/guides/rate-limits)；Error codes 文档把 429 单列为限流类错误 [来源](https://platform.openai.com/docs/guides/error-codes)。OpenAI《A Practical Guide to Building Agents》把「设置护栏、预算与人工审核」列为把 Agent 投产的必要条件，强调要为高风险和高成本动作设硬约束 [来源](https://cdn.openai.com/business-guides-and-resources/a-practical-guide-to-building-agents.pdf)。Anthropic《Building Effective Agents》则从「简单性与可控性」角度提醒：能力越强的 Agent 越需要显式的停止条件与成本约束，而不是放任其自主循环 [来源](https://www.anthropic.com/engineering/building-effective-agents)。**通用工程模式**：令牌桶限流、分层预算、fail-closed 熔断、429 + 指数退避 + `Retry-After`，都是可迁移到任何系统的成熟做法，与 LLM 无关，源自经典的分布式系统流控。**教学参考实现**：上面的桶容量、补充速率、预算数值均为演示常数，真实系统要按 SLO（Service Level Objective，服务等级目标）、并发能力和财务预算来定，并接入监控告警（第 17 章的可观测性）。

需要点明边界：限流管「速率」、预算管「总量」，两者互补但都不管「单次调用是否值得」——一个在预算内、速率内但把复杂任务派给了小模型导致答错的调用，这两道闸门都拦不住，那是分层路由和评估（第 16 章）的职责。硬闸门解决的是「失控」，不是「不划算」。

## 生产踩坑

| 症状 | 根因 | 如何观测与复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| 固定窗口边界瞬间放行 2 倍 | 用固定窗口而非令牌桶 | 在窗口交界处集中打请求 | 换令牌桶/滑动窗口平滑限流 | 低流量场景边界突刺影响小 |
| 预算超了才发现停不下来 | 熔断做成 fail-open | 让循环持续烧钱观察是否自停 | 每次调用前判断、fail-closed 熔断 | 无成本上限的内部实验环境 |
| 循环重试风暴烧光额度 | 无轮次上限 + 无预算闸门 | 让工具持续返回"查无结果" | 轮次上限 + 单任务预算双保险 | 明确单步任务不涉及循环 |
| 把 429 当程序 bug 排查 | 未区分限流与逻辑错误 | 观察错误是否集中在高峰 | 识别 429、指数退避、尊重 Retry-After | 持续 429 需申请更高配额 |
| 只设全局预算被单用户打爆 | 缺分层预算 | 用单账号狂发请求观察全局额度 | 单请求/单用户/全局分层预算 | 单租户内部系统可只设全局 |
| 熔断后无告警、静默失败 | 只停未通知 | 触发熔断看是否有人知道 | 熔断即告警 + 记录审计 | 有独立监控兜底时可弱化 |
| 为省成本一律用小模型致降质 | 三角里只盯成本一个角 | 抽样对比关键任务质量 | 按业务定三角落点、关键任务保质量 | 纯低风险任务可偏向省成本 |
| 重试退避无上限拖垮延迟 | 指数退避未设封顶 | 持续 429 时观察等待时长 | 退避设最大间隔 + 最大重试次数 | 离线批处理可容忍长退避 |

## 思考：为什么已经有了分层路由和 prompt caching 来降成本，还必须单独设限流和预算熔断？

### 回答

因为**降单价和设上限解决的是两类完全不同的问题，前者无法替代后者**。分层路由和 prompt caching 优化的是「每次调用的单价」——让同样的工作花更少的钱，它们的作用是让成本曲线的**斜率**变缓。但它们对「调用次数」和「总花费」没有任何约束：一个陷入死循环的 Agent，哪怕每次调用都用了最便宜的小模型、命中了缓存，只要它循环一万次，账单照样爆炸；一个被恶意刷量的接口，单价再低也架不住每秒上千次请求。换句话说，路由和缓存让「每一步」更便宜，但**失控是「步数」或「总量」维度的问题**，需要的是一条水平的硬上限来截断，而不是一条更缓的斜线。这就是限流（截断速率）和预算熔断（截断总量）存在的意义——它们是 fail-closed 的确定性闸门，和第 1 节「安全边界必须落在执行层」是同一个道理：你不能指望「让 Agent 自己少花点」，就像不能指望「让模型自己别越权」一样，必须由代码在每次调用前用「速率够不够、预算超没超」硬性判断。一句话总结：**优化手段让你走得更省，硬闸门保证你不会走到悬崖下面去；一个管效率，一个管安全，缺一不可。**

### 面试精简表达

路由和缓存降的是「每次调用的单价」（让成本曲线斜率变缓），但对「调用次数/总花费」无约束——死循环或刷量下单价再低也会爆。限流截断速率、预算熔断截断总量，是 fail-closed 的水平硬上限，和「安全边界必须在执行层」同理：不能指望 Agent 自觉，必须代码在每次调用前硬判断。优化管效率、闸门管安全，缺一不可。

## 思考：成本、延迟、质量三角权衡，在不同业务里应该怎么选落点？

### 回答

关键是**先识别当前业务把三角的哪个角当成不可妥协的硬约束，再在剩下两个角之间做平衡**，而不是幻想三个都拉满。可以按业务的「错误代价」和「时延敏感度」两个维度来定：**质量当硬约束**的场景——金融风控、医疗辅助、法律文书审核，错一次的代价极高（可能是资损或合规事故），所以宁可慢、宁可贵，也要上强模型、不激进压缩、加人类审批（第 5 节），落点靠近「质量」顶点；**延迟当硬约束**的场景——实时客服、语音助手、搜索补全，用户等超过一两秒就流失，所以要用小模型 + 缓存把响应压到毫秒级，可以接受在简单问题上牺牲一点质量深度，落点靠近「延迟」角，并用分层路由把少数难题才升级到强模型；**成本当硬约束**的场景——离线的批量文档处理、日报生成、数据清洗，没人实时等结果，所以可以用最便宜的档、跑很慢也无所谓，落点靠近「成本」角。选定落点后，本章的每个手段就各归其位：路由和缓存帮你在保住硬约束的前提下省成本，限流和预算给这个落点上锁防失控，护栏和审批在质量敏感场景加确定性防线。**所以正确的问法不是「怎么做到又快又好又便宜」，而是「这个业务错了会怎样、用户等得起吗」——答案决定你放弃哪个角。**

### 面试精简表达

三角最多同时优化两个，先定哪个角是硬约束：金融/医疗把质量当硬约束（宁可慢贵，上强模型+审批）、实时客服把延迟当硬约束（小模型+缓存,容许小降质）、离线批处理把成本当硬约束（最便宜档、慢无妨）。选定落点后路由/缓存省成本、限流/预算上锁、护栏/审批保质量。核心问题是「错了会怎样、等得起吗」，答案决定放弃哪个角。

## 深入：把全章串成一条「投产检查线」

回到开头「被一封邮件掏空」的故障，现在可以用全章的手段把它从头到尾封死，同时给出一份可迁移的投产检查线。**先过安全四关**：①输入到达前，注入检测 + spotlighting 隔离，让「忽略以上指令」被标记并被当作纯数据（第 1、2 节）；②任何工具执行前，RBAC 查表 + 工具白名单，`export_contacts` 因缺权限被拒（第 4 节）；③即便有权限，高风险 + 批量 PII 触发人类审批闸门，暂停等人（第 5 节）；④输出返回用户前，输出护栏拦截外发到可疑地址、拦截 PII 泄露（第 2、3 节）。**再过成本三关**：⑤请求进来先分诊，简单请求走小模型（第 6 节）；⑥稳定前缀走缓存、按 write/hit/新增三段计费（第 7 节）；⑦每次调用前过限流和预算熔断，任何失控在花钱之前被截断（本节）。**最后一条贯穿线**：所有这些关卡的决策、拦截、放行、熔断都要落到可观测的 trace 和指标里（第 16、17 章），否则你既不知道护栏有没有生效，也不知道钱花在了哪。这七关加一条观测线，本质上是同一条铁律的七次应用——**凡是关乎安全和钱的判断，都必须是执行层的确定性代码，绝不能寄希望于「模型/流量/预算自己会克制」**。这就是本章、也是整卷「工程化与生产」想让你带走的核心工程直觉：把 Agent 当成一个强大但不可完全信任的执行体，在它周围用确定性的闸门筑起纵深，让它能干活、干不了坏事、也花不超钱。
