## 真实问题

事故复盘还揪出一个「平时没人注意、出事就致命」的隐患：邮件助理为了排障，把每一轮的完整上下文（含用户来信原文）都打进了日志，日志又被同步到一个第三方可观测平台。而用户来信里满是个人可识别信息（Personally Identifiable Information，PII）——手机号、邮箱、身份证号、银行卡号。也就是说，就算没有那次外发事故，这些 PII 也早已随日志流到了系统外。更糟的是，团队还把用户原文直接拼进 prompt 送给第三方模型 API——PII 就这样离开了本方可控边界。

OWASP 把「敏感信息泄露」列为 LLM02，是 2025 版清单里上移的高风险项，并特别强调对 PII 的深度关注 [来源](https://owasp.org/www-project-top-10-for-large-language-model-applications/)。这一节要解决的问题很具体：**在把文本写入日志、送入模型、跨系统传输之前，如何自动识别其中的 PII 并按策略脱敏，同时保留必要场景下的可逆还原能力**。

## 原理：识别与匿名化两段式，算子决定可逆性

主流做法（以 Microsoft Presidio 为代表）把 PII 处理拆成解耦的两段 [来源](https://microsoft.github.io/presidio/)：

- **识别（analyze）**：用命名实体识别、正则、校验规则、上下文词等多种识别器（recognizer）在文本中定位 PII 实体，输出每个实体的类型（PHONE、EMAIL、ID 等）和字符区间（span）。
- **匿名化（anonymize）**：对识别出的每个实体套用一个**算子（operator）**做变换。Presidio 内置多种算子，各自的可逆性不同：

| 算子 | 做什么 | 可逆性 | 典型场景 |
|---|---|---|---|
| redact / replace | 替换成占位符（如 `<EMAIL>`）或固定值 | 需外部保存映射才可逆 | 通用遮蔽、送模型前脱敏 |
| mask | 遮蔽一部分（如 `138****8000`） | 不可逆（信息已丢） | 展示给客服的部分脱敏 |
| hash | 替换成密码学哈希 | 不可逆但可比对 | 分析/去重友好的匿名化 |
| encrypt | 用密钥加密 | 可逆（凭密钥） | 需还原的受控场景 |

理解「可逆性」是这一节的关键：**mask 和 hash 是单向的，脱敏后原值就找不回来了**（适合日志、分析这种不需要还原的场景）；**redact + 外部保管映射、或 encrypt，才能在受控场景下还原**（适合「送模型时脱敏、拿回结果后填回真实值」的流程）。选错算子，要么该保护的没保护住，要么该还原的还原不了。

## 最小可运行演示

下面用纯 Python（不依赖第三方库）复刻 Presidio 的两段式：`analyze` 用正则识别四类 PII，`anonymize` 按策略对不同类型套不同算子，并演示 redact 的可逆还原。它不联网、不需要 API Key。
```python
import hashlib
import re
from dataclasses import dataclass

RECOGNIZERS = {
    "PHONE": r"1[3-9]\d{9}",
    "EMAIL": r"[A-Za-z0-9._%+-]+@[A-Za-z0-9.-]+\.[A-Za-z]{2,}",
    "ID_CARD": r"\d{17}[\dXx]",
    "BANK_CARD": r"\b\d{16,19}\b",
}


@dataclass
class Entity:
    kind: str
    start: int
    end: int
    text: str


def analyze(text):
    ## 识别 PII，先匹配更长/更具体的实体，避免 18 位身份证正则误吃 19 位银行卡
    ents = []
    order = ["BANK_CARD", "ID_CARD", "PHONE", "EMAIL"]
    taken = [False] * len(text)
    for kind in order:
        for m in re.finditer(RECOGNIZERS[kind], text):
            if any(taken[m.start():m.end()]):
                continue
            for i in range(m.start(), m.end()):
                taken[i] = True
            ents.append(Entity(kind, m.start(), m.end(), m.group()))
    return sorted(ents, key=lambda e: e.start)


def _mask(value):
    if len(value) <= 4:
        return "*" * len(value)
    return value[:3] + "*" * (len(value) - 7) + value[-4:]


def _hash(value):
    return "HASH_" + hashlib.sha256(value.encode()).hexdigest()[:8]


def anonymize(text, policy):
    ## 按策略脱敏；返回脱敏文本与"占位->原值"映射（可逆场景用）
    ents = analyze(text)
    vault = {}
    out = text
    for idx, ent in enumerate(reversed(ents)):  # 从后往前替换，保持前面 span 不偏移
        op = policy.get(ent.kind, "redact")
        if op == "redact":
            token = f"<{ent.kind}_{len(ents) - 1 - idx}>"
            vault[token] = ent.text
            repl = token
        elif op == "mask":
            repl = _mask(ent.text)
        elif op == "hash":
            repl = _hash(ent.text)
        else:
            repl = ent.text
        out = out[:ent.start] + repl + out[ent.end:]
    return out, vault


def deanonymize(text, vault):
    for token, original in vault.items():
        text = text.replace(token, original)
    return text


def run():
    raw = ("客户张三 手机 13800138000，邮箱 zhang@example.com，"
           "身份证 11010119900307561X，银行卡 6222021234567890123。")
    print("原文：", raw)

    print("\n识别到的 PII 实体：")
    for e in analyze(raw):
        print(f"  {e.kind:9s} [{e.start:>3},{e.end:>3}) = {e.text}")

    policy = {"PHONE": "mask", "EMAIL": "redact", "ID_CARD": "redact", "BANK_CARD": "hash"}
    masked, vault = anonymize(raw, policy)
    print("\n脱敏后（入日志/送模型用此版本）：")
    print("  ", masked)

    print("\n可逆还原（仅限内部受控场景，凭 vault）：")
    print("  ", deanonymize(masked, vault))


if __name__ == "__main__":
    run()
```
保存为 `pii_redact.py`，运行 `python pii_redact.py`。完整预期输出：
```text
原文： 客户张三 手机 13800138000，邮箱 zhang@example.com，身份证 11010119900307561X，银行卡 6222021234567890123。

识别到的 PII 实体：
  PHONE     [  8, 19) = 13800138000
  EMAIL     [ 23, 40) = zhang@example.com
  ID_CARD   [ 45, 63) = 11010119900307561X
  BANK_CARD [ 68, 87) = 6222021234567890123

脱敏后（入日志/送模型用此版本）：
   客户张三 手机 138****8000，邮箱 <EMAIL_1>，身份证 <ID_CARD_2>，银行卡 HASH_92b6fedb。

可逆还原（仅限内部受控场景，凭 vault）：
   客户张三 手机 138****8000，邮箱 zhang@example.com，身份证 11010119900307561X，银行卡 HASH_92b6fedb。
```
看还原那一行就能理解算子的可逆性差异：EMAIL 和 ID_CARD 用了 redact（占位符进了 vault），能完整还原；PHONE 用了 mask、BANK_CARD 用了 hash，**这两个还原不回来**（`138****8000` 和 `HASH_92b6fedb` 保持原样）——因为遮蔽和哈希是单向的，原始信息已经丢弃。这正是「按场景选算子」的意义：日志和分析用 mask/hash（无需还原、更安全），需要拿模型结果填回真实值的流程用 redact + vault。

## 真实系统对应

**官方公开机制**：Microsoft Presidio 是开源的 PII 检测与去标识化 SDK，明确分为 `presidio-analyzer`（检测实体 span）与 `presidio-anonymizer`（对实体套算子），内置 redact / replace / mask / hash / encrypt 等算子，并支持通过自定义识别器扩展实体类型 [来源](https://microsoft.github.io/presidio/)。OWASP LLM02 把敏感信息泄露列为高风险，缓解措施包括数据脱敏、输入清洗、限制模型对敏感数据的访问 [来源](https://owasp.org/www-project-top-10-for-large-language-model-applications/)。**通用工程模式**：「识别—匿名化」两段式、按实体类型配算子策略、在写日志/送模型/跨系统前统一过一道脱敏，是可迁移到任何栈的做法；输出护栏（第 2 节）也常调用同一套脱敏。**教学参考实现**：上面的正则识别器只覆盖四类中国常见 PII 且未做校验位验证，真实系统应用 Presidio 或等价工具，配合命名实体识别模型与上下文增强，正则单打独斗漏检率高。

需要点明边界：脱敏不是「一劳永逸」。识别器有漏检（自由文本里的地址、姓名尤其难）；哈希虽单向但对低熵字段（如手机号）可被彩虹表/暴力枚举反推，敏感场景需加盐；可逆还原用的 vault 本身就是高价值目标，必须严格访问控制。TTL（Time To Live，生存时间）适用于可过期的缓存与脱敏映射，但不应用于删除法律要求保留的数据。

## 生产踩坑

| 症状 | 根因 | 如何观测与复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| 日志里仍有明文 PII | 只脱敏了展示层没脱敏日志 | grep 日志中的手机号/邮箱模式 | 在写日志的统一入口强制脱敏 | 已在采集端脱敏的字段不重复处理 |
| 长实体被短正则切碎 | 识别器顺序不当（先短后长） | 用 19 位卡号触发 18 位身份证误配 | 先匹配长/具体实体并标记占位 | 实体长度互不重叠时无此问题 |
| 该还原的还原不回来 | 对需还原字段用了 mask/hash | 脱敏后尝试 deanonymize 失败 | 需还原用 redact+vault 或 encrypt | 纯日志/分析场景本就不需还原 |
| 哈希 PII 被反推 | 低熵字段直接哈希无盐 | 对手机号哈希做枚举比对 | 加盐/加密，或直接 mask 不保留 | 高熵、无需比对的字段可接受 |
| 自由文本 PII 漏检 | 只用正则、无 NER 模型 | 塞入口语化地址与姓名 | 叠加命名实体识别 + 上下文词 | 结构化字段可用规则精确覆盖 |
| vault 泄露导致批量还原 | 映射库未做访问控制 | 检查谁能读取 vault | 严格权限 + 加密存储 + 审计 | 无可逆需求时可不建 vault |

## 思考：脱敏时如何在「保护」与「可用」之间选算子？举例说明。

### 回答

核心判断是「这个字段脱敏后，下游还需不需要它、需不需要还原」，据此在四类算子里选。第一种情况，**下游完全不需要原值、只需知道'这里有个 PII'**：用 redact 替换成占位符（`<EMAIL>`），语义位置保留、原值不带出去，最通用。第二种，**下游要做去重或关联分析、但不能看到原值**：用 hash，同一个原值哈希结果一致（可比对、可 group by），但不可反推——不过对手机号这类低熵字段要加盐防枚举。第三种，**要展示给人看、需要保留部分可辨识度**：用 mask（`138****8000`），客服能核对尾号但看不到完整号码，信息已部分丢失、不可逆。第四种，**流程上必须还原**（比如送模型时脱敏、拿回答案后要填回真实手机号发短信）：用 redact + 外部 vault 保存映射，或用 encrypt 凭密钥还原——但要清醒地认识到，vault/密钥本身成了高价值攻击目标，得严格管控。一句话总结：**不需要还原就优先选不可逆的（mask/hash，更安全）；必须还原才用可逆的（redact+vault/encrypt），并为可逆能力付出额外的管控成本**。选错的典型后果是：该还原的用了 hash 结果填不回，或该保护的用了可逆算子扩大了泄露面。

### 面试精简表达

按「下游是否需要原值/还原」选算子：不需还原优先 mask/hash（不可逆更安全，hash 低熵字段要加盐）；需展示用 mask；需还原用 redact+vault 或 encrypt，并严格管控映射库这个高价值目标。

## 机制推导：为什么脱敏要放在「统一出口」而非各处手写

开头事故的根因之一是「脱敏逻辑散落各处、日志入口漏了」。推导一下正确的落位：PII 会从三个出口离开可控边界——写日志、送模型 API、跨系统传输。如果在每个业务函数里各写各的脱敏，必然出现「A 处脱了、B 处忘了」的漏网，而且规则不一致（有人 mask、有人 redact）。正确做法是把脱敏收敛成一个**统一的中间件/出口层**：所有要写日志的内容先过 `anonymize`、所有要拼进 prompt 的用户文本先过 `anonymize`、所有对外传输先过 `anonymize`，用同一套策略表驱动。这样新增一个 PII 类型只改一处策略、不会遗漏出口。它和第 2 节的输出护栏是同一种思想的两个应用面——**把安全变换放在数据流的收口处，而不是指望每个调用点都记得做**。这也呼应全章主线：安全不能依赖「每个人都自觉」，要靠架构上的强制收口。
