## 真实问题

第 6 节解决了「杀鸡用牛刀」，现在处理成本的第二个大头——**重复重发前缀**。邮件助理的每次请求都带着一段 4,000 token 的稳定内容：系统提示（角色设定、安全规则）+ 四个工具的完整定义（名字、描述、参数 schema）。一次对话往往有 6 轮，这 4,000 token 就被**原封不动地重发了 6 次**，每次都按 input token 全价计费。用量明细里，这部分「重复的前缀」占了输入成本的一多半——它们内容完全一样，却付了 6 次钱。

这正是 **prompt caching（提示缓存）** 要治的病：把请求里稳定不变的前缀缓存起来，后续请求命中缓存时，这部分按大幅折扣计费（而非全价重算）。OpenAI 称其「可降低最多 80% 延迟和 90% 输入成本」[来源](https://platform.openai.com/docs/guides/prompt-caching)；Anthropic 的 prompt caching 也提供类似的写入/命中计费模型 [来源](https://docs.anthropic.com/en/docs/build-with-claude/prompt-caching)。

## 原理：前缀缓存的计费模型与「稳定前缀放最前」

prompt caching 的机制建立在一个约束上：**缓存匹配的是请求的前缀（prefix）**。系统按初始前缀的哈希路由请求，只有当新请求的前缀与已缓存内容逐字节一致时，才算命中（cache hit）[来源](https://platform.openai.com/docs/guides/prompt-caching)。由此推出计费的三段结构：
```text
一次请求的 input = [稳定前缀（可缓存）] + [本轮新增（不可缓存）]

- 首次请求：前缀未缓存 → 按"写入"计费（Anthropic 5分钟缓存写入约 1.25× 基础价）
- 后续命中：前缀已缓存 → 按"命中读取"计费（大幅折扣，可低至基础价的约 1/10）
- 每轮新增的用户消息：始终按原价（因为它每轮都变，不可缓存）
```
两个必须记住的工程要点：

1. **把稳定的东西放最前面。** 因为缓存匹配前缀，你要把「多轮不变」的内容（系统提示、工具定义、长文档）放在请求最前端，把「每轮都变」的内容（本轮用户消息）放后面。顺序反了——比如把变动的时间戳放开头——会让整个前缀失配，缓存形同虚设。
2. **缓存有生存时间（TTL）。** Anthropic 默认 5 分钟 TTL，每次命中会刷新（keep-alive），也提供 1 小时 TTL 选项（写入溢价更高，约 2×）[来源](https://docs.anthropic.com/en/docs/build-with-claude/prompt-caching)。选 5 分钟还是 1 小时，几乎只看一个指标：**请求间隔**——交互式对话/Agent 工具循环几分钟内多次命中用 5 分钟档，定时批处理/日报这种跨几十分钟复用同一上下文用 1 小时档。OpenAI 的自动缓存则要求前缀至少 1,024 token 才生效 [来源](https://platform.openai.com/docs/guides/prompt-caching)。

## 最小可运行演示

下面用纯 Python 模拟前缀缓存的计费模型，对比「不缓存」与「缓存」在 6 轮对话下的累计成本。价格与折扣为教学示例，真实值以官方定价为准。它不联网、不需要 API Key。
```python
## 教学示例：每 1M input token 基础价、缓存写入溢价、缓存命中折扣
BASE = 3.00
WRITE_MULTIPLIER = 1.25   # 首次写入 1.25x（示例）
HIT_MULTIPLIER = 0.10     # 命中读取 0.1x（约 90% 折扣，示例）


def price(tokens, multiplier):
    return BASE * tokens / 1_000_000 * multiplier


class PrefixCache:
    ## 极简前缀缓存：以"稳定前缀内容"为 key，用调用计数模拟 TTL
    def __init__(self, ttl_calls=5):
        self.store = {}            # key -> 剩余可命中次数
        self.ttl = ttl_calls

    def charge(self, prefix_key, prefix_tokens, fresh_tokens):
        ## 前缀部分：命中走折扣，未命中/过期走写入溢价
        if self.store.get(prefix_key, 0) > 0:
            self.store[prefix_key] -= 1
            prefix_cost = price(prefix_tokens, HIT_MULTIPLIER)
            kind = "HIT "
        else:
            self.store[prefix_key] = self.ttl - 1
            prefix_cost = price(prefix_tokens, WRITE_MULTIPLIER)
            kind = "WRITE"
        ## 每轮新增的用户消息按原价（不可缓存）
        fresh_cost = price(fresh_tokens, 1.0)
        print(f"  [{kind}] 前缀{prefix_tokens}tok 成本=${prefix_cost:.6f} "
              f"+ 新增{fresh_tokens}tok 成本=${fresh_cost:.6f}")
        return prefix_cost + fresh_cost


def run():
    # 稳定前缀（system+工具定义）4000 token/轮；每轮新增用户消息 200 token
    prefix_tokens, fresh_tokens, rounds = 4000, 200, 6

    print("=== 不使用缓存：每轮前缀都按原价重发 ===")
    no_cache = 0.0
    for i in range(rounds):
        c = price(prefix_tokens, 1.0) + price(fresh_tokens, 1.0)
        no_cache += c
        print(f"  第{i + 1}轮 成本=${c:.6f}")
    print(f"不缓存累计：${no_cache:.6f}")

    print("\n=== 使用前缀缓存：首轮写入溢价，后续命中折扣 ===")
    cache = PrefixCache(ttl_calls=rounds)
    with_cache = 0.0
    for i in range(rounds):
        print(f"  第{i + 1}轮", end=" ")
        with_cache += cache.charge("sys_v1", prefix_tokens, fresh_tokens)
    print(f"缓存累计：${with_cache:.6f}")

    saved = no_cache - with_cache
    print(f"\n节省：${saved:.6f}（{saved / no_cache:.1%}）")


if __name__ == "__main__":
    run()
```
保存为 `prompt_caching.py`，运行 `python prompt_caching.py`。完整预期输出：
```text
=== 不使用缓存：每轮前缀都按原价重发 ===
  第1轮 成本=$0.012600
  第2轮 成本=$0.012600
  第3轮 成本=$0.012600
  第4轮 成本=$0.012600
  第5轮 成本=$0.012600
  第6轮 成本=$0.012600
不缓存累计：$0.075600

=== 使用前缀缓存：首轮写入溢价，后续命中折扣 ===
  第1轮 [WRITE] 前缀4000tok 成本=$0.015000 + 新增200tok 成本=$0.000600
  第2轮 [HIT ] 前缀4000tok 成本=$0.001200 + 新增200tok 成本=$0.000600
  第3轮 [HIT ] 前缀4000tok 成本=$0.001200 + 新增200tok 成本=$0.000600
  第4轮 [HIT ] 前缀4000tok 成本=$0.001200 + 新增200tok 成本=$0.000600
  第5轮 [HIT ] 前缀4000tok 成本=$0.001200 + 新增200tok 成本=$0.000600
  第6轮 [HIT ] 前缀4000tok 成本=$0.001200 + 新增200tok 成本=$0.000600
缓存累计：$0.024600

节省：$0.051000（67.5%）
```
看清收益结构：第 1 轮因为要写入缓存反而**更贵**（1.25× 溢价），但从第 2 轮起前缀按 0.1× 折扣计费，5 轮命中把这个溢价赚回来还大赚。整体从 $0.0756 降到 $0.0246，省了 67.5%。**这也暴露了缓存的两个前提**：一是必须有足够多的命中来摊平首次写入的溢价（只跑一轮的请求用缓存反而亏）；二是前缀必须真的稳定（`prefix_key` 每轮相同才命中）——如果前缀里混进了每轮都变的内容（时间戳、随机 ID），就会次次 WRITE、次次溢价，比不缓存还贵。

## 真实系统对应

**官方公开机制**：OpenAI Prompt caching 文档说明其对所有 gpt-4o 及更新模型自动生效、无需改代码、无额外费用，缓存命中可降低最多 80% 延迟与 90% 输入成本，要求前缀至少约 1,024 token、按前缀哈希路由 [来源](https://platform.openai.com/docs/guides/prompt-caching)；新一代模型支持在显式缓存断点（cache breakpoint）处精确匹配，并可能收取 1.25× 的缓存写入费 [来源](https://developers.openai.com/api/docs/guides/prompt-caching)。Anthropic Prompt caching 文档说明用 `cache_control: {"type": "ephemeral"}` 标记可缓存内容，默认 5 分钟 TTL（命中刷新），可选 `"ttl": "1h"` 的 1 小时缓存（写入约 2× 基础价），并明确缓存需为账户启用 [来源](https://docs.anthropic.com/en/docs/build-with-claude/prompt-caching)。**通用工程模式**：把稳定前缀放最前、按 write/hit/新增三段核算、按请求间隔选 TTL 档位，是可迁移的做法；prompt caching 之外还有「请求级缓存」（相同问题直接返回上次答案，适合 FAQ）和「工具结果缓存」（相同参数短时间内复用，治第 17 章重复搜索的病）。**教学参考实现**：上面的倍率（1.25×/0.1×）与 TTL 计数是示例，真实折扣、写入费、最小前缀长度务必以当前官方定价为准。

需要点明边界：缓存折扣只作用于**可缓存的前缀部分**，不是「总成本省 90%」——每轮新增的用户消息、模型输出都按原价（本节演示里新增部分就没打折）。所以「省了多少」取决于前缀占总 token 的比例：前缀越大越稳定、命中越多，收益越大；前缀频繁变动或对话极短时，缓存几乎不省甚至倒亏。

## 生产踩坑

| 症状 | 根因 | 如何观测与复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| 缓存几乎不命中 | 变动内容混进了前缀 | 在前缀里放时间戳/随机ID复现 | 稳定内容放最前、变动内容放后 | 前缀本就每次不同的场景无法缓存 |
| 用了缓存反而更贵 | 命中次数不足以摊平写入溢价 | 只跑一轮就结束的请求 | 只对高复用前缀开缓存 | 一次性请求不该开缓存 |
| 以为省了 90% 总成本 | 把前缀折扣当成总成本折扣 | 拆开前缀与新增分别计费 | 按 write/hit/新增三段核算 | 前缀占比极高时接近该比例 |
| 命中率随对话变长下降 | 历史增长使前缀边界后移 | 长对话中统计命中 token 占比 | 固定可缓存段 + 显式断点 | 短对话影响可忽略 |
| 缓存过期后批量回落全价 | TTL 档位与请求间隔不匹配 | 请求间隔超 5 分钟观察 miss | 按间隔选 5min/1h 档 | 高频命中场景默认档即可 |
| 脏读：缓存内容已过期失效 | 对时效敏感数据做了结果缓存 | 缓存订单状态后状态变更 | 时效数据设短 TTL 或不缓存 | 静态文档/FAQ 可长缓存 |

## 思考：prompt caching 为什么要求「稳定内容放最前」？前缀里混进一个时间戳会怎样？

### 回答

因为缓存匹配的是请求的**前缀**，而且是逐字节（严格前缀）匹配的。系统为了快速判断「这个请求能不能复用之前的计算」，会对请求开头的一段内容做哈希，只有当新请求的前缀与已缓存前缀完全一致时才算命中。这个机制决定了内容的摆放顺序至关重要：你要把「多轮之间完全不变」的内容——系统提示、工具定义、长文档——放在最前面，让它们构成一个稳定的、可被反复命中的前缀；把「每轮都变」的内容——本轮用户消息——放在后面。如果反过来，在前缀开头混进一个时间戳（或随机请求 ID、当前时间、每次不同的会话摘要），那么每一轮请求的前缀开头都不一样，哈希对不上，**整个前缀都会失配**——不仅命中不了，还因为系统认为这是全新前缀而每轮都走「写入」路径，若开了写入溢价，成本比完全不缓存还高。这就是「稳定内容放最前」的硬约束：缓存不是「内容一样就行」，而是「前缀逐字节一样才行」。工程上要做的是把请求结构化地分层——不可变前缀段、可变消息段严格分开，绝不让任何每轮变动的东西污染前缀开头。

### 面试精简表达

缓存按前缀逐字节匹配、按前缀哈希路由，所以稳定内容必须放最前构成可复用前缀。前缀开头混进时间戳会让每轮前缀都不同、整体失配，不仅命中不了还次次走写入，比不缓存更贵。

## 深入：三种缓存的分工，与「缓存一切」的陷阱

「缓存」在 Agent 里其实有三个层次，各治不同的病，别混为一谈。**第一层是 prompt caching（前缀缓存）**，就是本节主角——省的是「每轮重发的稳定前缀」的重复计费，由模型厂商在推理层提供，你只需把稳定内容放前面（Anthropic 还需显式 `cache_control` 标记）。**第二层是请求级缓存（response cache）**——完全相同的用户问题直接返回上次的最终答案，适合 FAQ、帮助文档这类高重复、答案稳定的场景，省的是「整次模型调用」。**第三层是工具结果缓存**——相同参数的工具调用在短时间内直接复用结果，这正好治第 17 章那个「Agent 反复用相同参数调同一搜索」的病，省的是「重复的工具执行开销」。三者叠加能显著降本，但都共享同一个风险——**脏读（stale read）**：被缓存的数据可能已经过期。前缀缓存里如果缓存了「今天的日期」，第二天就错了；请求级缓存里如果缓存了「我的订单状态」，状态一变答案就错了；工具结果缓存里如果缓存了「实时库存」，库存一动就误导决策。所以「缓存一切」是陷阱，正确姿势是**按时效性分级**：静态内容（系统提示、产品手册、历史文档）大胆长缓存；半静态内容（用户偏好）设中等 TTL；强时效内容（订单状态、库存、价格）设极短 TTL 或干脆不缓存。判断标准就一句话——**这份数据在缓存有效期内会不会变、变了会不会造成错误决策**。这也和第 3 节的 TTL 讨论一脉相承：TTL 适用于可过期的缓存，但会变化且一变就出错的强时效数据，宁可每次实时取。
