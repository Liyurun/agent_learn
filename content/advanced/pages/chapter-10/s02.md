## 真实问题

某 SaaS（Software as a Service，软件即服务）公司的客服机器人用一个「万能提示」处理所有咨询：退款、技术报错、售前咨询、闲聊全塞进同一个系统提示，提示写到 1200 字。上线一个月，数据难看：退款场景误触发工具（模型把「我想了解退款政策」当成「立即发起退款」）、技术问题答得像营销话术、简单的「你们几点上班」也走了最贵的强模型。团队复盘发现两个病根：一是**一个提示同时服务四类意图，指令互相干扰**，模型注意力被稀释，每类都做不好；二是**所有请求不分难易都走同一个模型**，简单问题白白花强模型的钱。

改造方式是路由（Routing）：先用一个便宜的小模型判断意图，再把请求分派给「只懂这一类问题、提示精简、工具聚焦」的专门处理器；同时把简单问题留在小模型、只把高风险或难题升级给强模型。改造后退款误触发降为零（退款处理器强制走「查询→确认→再执行」），平均单请求成本下降约一半（大量简单问答不再触碰强模型）。

## 原理：为什么「专门处理」胜过「大一统提示」

Anthropic 对路由的定义是：对输入分类，并把它导向一个专门的后续任务；这个工作流实现了**关注点分离（separation of concerns）**，能构建更专门化的提示——没有它，为一种输入优化提示往往会拖累另一种输入的表现 [来源](https://www.anthropic.com/engineering/building-effective-agents)。文档给的适用条件是：任务存在**可被清晰区分的类别**，且分类可以由 LLM 或传统分类模型/算法准确完成；给的例子正是「把不同类型的客服咨询（通用问题、退款请求、技术支持）导向不同的下游流程、提示与工具」，以及「把简单/常见问题路由给更小更省的模型（如 Claude Haiku）、把困难/罕见问题路由给更强的模型（如 Claude Sonnet）以优化性能」。

一个想同时处理退款、技术、闲聊的巨型提示会陷入「样样通样样松」：指令越多越互相干扰，模型注意力被稀释。路由的思路是**分而治之**——先判断意图，再交给一个只需专注单类问题的处理器。这既提升单类质量，又让每个处理器独立可测、可优化。而它最高价值的衍生用途是**成本分层（cost tiering）**：用便宜小模型做分类、把简单问题也交给小模型省钱，只把难题升级给昂贵强模型，这在高流量系统里能省下可观成本。
```text
大一统：所有输入 ─▶ [巨型提示 + 强模型 + 全套工具] ─▶ 质量参差、成本高
路由：  输入 ─▶ [小模型分类器] ─┬─ refund   ─▶ [退款处理器：强模型+退款工具]
                                 ├─ technical─▶ [技术处理器：排障工具]
                                 └─ general  ─▶ [通用处理器：小模型，省钱]
```
## 最小可运行演示

下面用确定性的关键词分类替代小模型（真实系统里换成一次小模型调用即可），演示「分类 → 分派 → 成本分层 + 兜底类别」。纯 Python，无需 API Key。
```python
CATEGORIES = ["refund", "technical", "general"]
KEYWORDS = {
    "refund": ["退款", "退货", "发票", "扣款"],
    "technical": ["报错", "无法登录", "崩溃", "超时", "bug"],
}


def classify(msg: str) -> str:
    """小模型分类的确定性替身：命中关键词即归类，否则走兜底 general。"""
    for category, words in KEYWORDS.items():
        if any(word in msg for word in words):
            return category
    return "general"                                  # 兜底类别，避免误分派到高风险处理器


def handle_refund(msg: str) -> str:
    return f"[强模型+退款工具] 已按退款政策受理：{msg}"


def handle_technical(msg: str) -> str:
    return f"[排障工具] 已生成排障步骤：{msg}"


def handle_general(msg: str) -> str:
    return f"[小模型] 直接回答：{msg}"


def route(msg: str) -> dict:
    category = classify(msg)
    handler = {
        "refund": handle_refund,
        "technical": handle_technical,
        "general": handle_general,
    }[category]
    return {"category": category, "reply": handler(msg)}


def main() -> None:
    samples = ["我要申请退款", "登录一直报错超时", "你们几点上班"]
    for s in samples:
        r = route(s)
        print(f"输入={s} -> 类别={r['category']}")
    counts = {c: 0 for c in CATEGORIES}
    for s in samples:
        counts[route(s)["category"]] += 1
    print("分派统计:", counts)


if __name__ == "__main__":
    main()
```
保存为 `demo02_routing.py`，运行 `python demo02_routing.py`。预期输出：
```text
输入=我要申请退款 -> 类别=refund
输入=登录一直报错超时 -> 类别=technical
输入=你们几点上班 -> 类别=general
分派统计: {'refund': 1, 'technical': 1, 'general': 1}
```
关键点：分支是**预先枚举**好的（refund/technical/general），这是路由与编排者-工作者的分水岭——后者的分支运行时才确定。每个处理器有独立的提示、工具集、甚至模型：退款走强模型 + 退款工具，通用问答走小模型省钱。`return "general"` 的兜底分支是生产安全网——分不清就走最保守的通用处理，绝不把模糊输入误分派到高风险的退款处理器。

## 示例的上一步输入与下一步输出

路由的调试关键是把「分类结果」变成可审计的结构，而不是让分类和分派糊在一起：
```text
上一步输入（进入路由的原始请求）：
{"user_id": "u-88", "text": "登录一直报错超时", "channel": "app"}

分类器输出（可审计的中间信号）：
{"category": "technical", "confidence": 0.91, "fallback_used": false}

下一步输出（专门处理器的入参）：
{"handler": "handle_technical", "tools": ["log_search", "restart_hint"], "model": "small"}
```
把 `confidence` 与 `fallback_used` 显式记录，能回答两个生产必答问题：这次分类有多大把握？是否落到了兜底类别？很多路由事故不是「分错了」，而是「分错了却没人知道」——因为分类信号从未被记录。

## 真实系统对应

**官方公开机制**：Anthropic 文档明确把路由用于「不同客服意图导向不同下游流程/提示/工具」，并把「简单问题→小模型、难题→强模型」作为路由的官方示例，指名 Haiku 与 Sonnet 两档模型 [来源](https://www.anthropic.com/engineering/building-effective-agents)。LangGraph 官方文档的 `Routing` 小节用 `with_structured_output(Route)` 让模型输出一个受限的枚举字段（story/joke/poem），再用条件边分派到对应节点，正是「用结构化输出做路由逻辑」的公开实现 [来源](https://docs.langchain.com/oss/python/langgraph/workflows-agents)。

**通用工程模式**：「先分类、再用专门处理器、加兜底类别、按难度分层用不同模型」是可迁移到任何栈的做法，分类器既可以是 LLM，也可以是传统文本分类模型（成本更低、更稳定）。

**教学参考实现**：本页用关键词匹配替代分类模型，只为可复现；真实系统的分类器要处理歧义、多意图、对抗输入，通常需要小模型 + 结构化输出 + 置信度阈值。

## 生产踩坑

| 症状 | 根因 | 如何观测与复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| 技术问题被分到退款处理器 | 分类器误分类，无兜底 | 记录每次 category 与 confidence；用歧义样本复现 | 设兜底类别；高风险类加二次确认 | 类别本就极清晰时可简化 |
| 一个请求同时属多类 | 类别定义不互斥 | 统计多关键词命中冲突的比例 | 允许多标签或定优先级；重划类别边界 | 严格单意图场景无需多标签 |
| 分错了却无人察觉 | 分类信号未落日志 | 抽查线上请求是否留有分类记录 | 记录 category/confidence/fallback | 无审计要求的玩具项目 |
| 简单问题也走强模型 | 未做成本分层 | 统计各处理器的模型与调用占比 | 简单类走小模型，仅难题升级强模型 | 全部为高风险请求时不宜省 |
| 分类器成瓶颈拖慢全链 | 分类用了过大的模型 | 测分类步骤单独耗时 | 分类用小模型/传统分类器 | 分类本身极难需强模型时例外 |
| 新类别出现后一直漏判 | 类别集合僵化不更新 | 监控兜底类别命中率突增 | 定期用兜底流量挖掘新类别 | 类别天然封闭的场景 |

## 思考：路由模式怎么帮你省钱？它有哪些失败模式？

### 回答

路由省钱靠**成本分层**：用便宜的小模型（或传统分类器）做意图分类，把简单/常见问题也交给小模型直接回答，只把高风险或困难问题升级给昂贵的强模型。在高流量下，简单问题往往占大头，这一层就能显著拉低平均成本，同时不牺牲难题质量。它的失败模式主要有三类：一是**误分类**（把技术问题分到退款），缓解办法是设兜底类别、对高风险类别加二次确认或用更强分类器；二是**类别不互斥**（一个请求同属多类），要么允许多标签路由、要么定义优先级、要么重划类别边界；三是**分类信号不可观测**（分错了没人知道），必须把 category、confidence、是否走兜底都落日志。

### 面试精简表达

路由=先分类再分派，靠关注点分离提质量、靠成本分层降成本；三大坑是误分类、类别不互斥、分类不可观测，对应加兜底、定优先级、留日志。

## 事故回放：一次「政策问答」引发的误退款

某平台的退款处理器同时挂了两个工具：`lookup_order`（查订单）和 `issue_refund`（发起退款）。分类器把「请问你们的七天无理由退款政策是什么」这句**政策问答**误分类为 `refund` 意图，请求进入退款处理器。由于处理器提示里没有强制「先确认用户是否真的要退款」，模型看到 `issue_refund` 工具就直接调用，给一位只是随口问政策的用户发起了真实退款。虽然金额不大，但触发了对账异常与用户投诉。

复盘定位到两层问题：分类层把「政策咨询」和「退款申请」混为一类；处理器层把「查询类工具」和「执行类工具」不加保护地放在一起。修复分两步：其一，在分类层拆出 `refund_policy_qa`（只读）与 `refund_request`（可执行）两个子类，政策问答走只读处理器；其二，在退款处理器内部把 `issue_refund` 设为「必须先经过一次显式确认 gate 才能调用」的高风险动作。这个案例说明：路由的类别粒度直接决定安全边界——**把「问政策」和「要退款」归为一类，等于把只读和写操作交给同一个处理器，风险由此而生**。

## 优化前后对比

| 维度 | 优化前（大一统提示） | 优化后（路由 + 分层） | 验证方式 |
|---|---|---|---|
| 单类质量 | 指令互相干扰，参差 | 专门处理器，聚焦 | 各类别分别评测 |
| 成本 | 全走强模型 | 简单问题走小模型 | 统计各模型调用占比 |
| 高风险控制 | 工具不分读写 | 只读/可执行分类 + gate | 用政策问答做故障注入 |
| 可观测性 | 无分类记录 | category/confidence 落日志 | 抽查线上分类记录 |
| 可扩展性 | 加需求就改巨型提示 | 加处理器不动其他分支 | 新增类别的回归影响面 |

路由的正确心法是：**类别边界即安全边界**。分类粒度太粗会把不同风险等级的请求混在一起，粒度太细又会推高分类难度与维护成本。工程上通常先按「读 vs 写、风险高 vs 低」这两条轴切出最小够用的类别集，再随线上兜底流量的暴露逐步细化。
