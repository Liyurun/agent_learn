## 真实问题

某出版团队用大模型做文学翻译。单次翻译的初稿总差一口气：意思对，但语气生硬、个别术语不地道。让译者反复手改成本太高。团队起初想用「更强的模型 + 更长的提示」一次翻好，效果依旧不稳定——因为「什么叫好翻译」这件事，模型**自己写的时候意识不到问题，别人指出来却能改好**。这正是评估-优化（Evaluator-Optimizer）的用武之地：一个 LLM 负责**生成**，另一个 LLM 在循环中**评估并给出反馈**，生成者据此迭代精炼，直到评估者满意。

改造后，生成者出初稿，评估者按「准确性、流畅度、术语一致」三条明确标准打分并给出可操作的修改建议，生成者据此改，通常 2-3 轮就达标。关键收益不是「模型变强」，而是**引入了一个独立的评估视角，跳出生成者自己的思维定式**。但团队也踩了两个坑：一次因为评估标准写得含糊（只说「翻得更好一点」），循环空转到上限也没进步；一次因为忘了设终止条件，评估者永不满意，生成者无限改，一夜烧掉大量 Token。这两个坑对应本模式两个不可或缺的前提。

## 原理：为什么拆成「生成者」和「评估者」两个角色

Anthropic 对评估-优化的定义是：一个 LLM 调用生成响应，另一个提供评估与反馈，两者在循环中协作 [来源](https://www.anthropic.com/engineering/building-effective-agents)。文档给出的适用条件是「**我们有明确的评估标准，且迭代精炼能带来可衡量的价值**」，并给出「好契合」的两个信号：其一，当人类清晰表达反馈时，LLM 的响应能被明显改进；其二，LLM 自己能提供这样的反馈。文档把它类比为「人类作者打磨一篇文稿的迭代写作过程」，给的例子是「文学翻译（译者 LLM 可能一开始抓不住的细微差别，评估者 LLM 能给出有用批评）」和「需要多轮搜索与分析的复杂搜索任务（评估者决定是否需要进一步搜索）」。

背后的认知规律是「**评判比创作更容易**」——发现一篇译文哪里别扭，比一次写出完美译文简单。把生成和评估拆成两个角色（甚至两个不同的提示/模型），让评估者专注挑毛病、给可操作反馈，生成者专注据反馈改进。这种分工比让一个模型「自己写自己改」更有效，因为**独立的评估视角能跳出生成者的思维定式**。
```text
[生成者] ─產出草稿─▶ [评估者] ─PASS?─▶ 达标退出
    ▲                    │
    └──── REVISE + 具体反馈 ┘   （反馈必须回流到下一轮生成，循环才有意义）
                              受 max_rounds 硬上限保护
```
但这个模式有两个前提，缺一不可：其一，**评估标准必须明确**——连「什么是好」都说不清，评估者给不出有效反馈，循环就空转；其二，**迭代必须真能带来提升**——若改来改去质量不再上升，就是在浪费 Token。

## 最小可运行演示

下面用确定性的生成者与评估者模拟一次「翻译初稿 → 评估 → 改进」的循环，评估标准显式写死（术语必须含 connection pool、句式需简洁），并设 `max_rounds` 硬上限。纯 Python，无需 API Key。
```python
def generator(task: str, feedback: str = "") -> str:
    """生成者：初稿粗糙，收到反馈后逐步改进（确定性模拟）。"""
    base = "The pool timeout is caused by concurrency."
    if "术语" in feedback:
        base = "The connection pool timeout is caused by concurrency limits."
    if "流畅" in feedback:
        base = "Connection pool timeouts are caused by exceeding concurrency limits."
    return base


def evaluator(draft: str) -> tuple[str, str]:
    """评估者：按明确标准打分，返回 PASS/REVISE + 可操作反馈。"""
    low = draft.lower()
    if "connection pool" not in low:
        return "REVISE", "术语不完整：应使用 connection pool"
    if draft.startswith("The connection pool timeout is caused"):
        return "REVISE", "流畅度不足：改为主动、简洁的句式"
    return "PASS", "达标"


def evaluator_optimizer(task: str, max_rounds: int = 4) -> dict:
    feedback = ""
    draft = generator(task)
    for round_i in range(1, max_rounds + 1):           # ★ 硬上限防死循环
        verdict, feedback = evaluator(draft)
        if verdict == "PASS":
            return {"result": draft, "rounds": round_i, "status": "passed"}
        draft = generator(task, feedback)              # 反馈回流到下一轮
    return {"result": draft, "rounds": max_rounds, "status": "max_rounds"}


def main() -> None:
    r = evaluator_optimizer("翻译连接池超时说明")
    print("状态:", r["status"])
    print("轮数:", r["rounds"])
    print("终稿:", r["result"])


if __name__ == "__main__":
    main()
```
保存为 `demo05_evaluator.py`，运行 `python demo05_evaluator.py`。预期输出：
```text
状态: passed
轮数: 3
终稿: Connection pool timeouts are caused by exceeding concurrency limits.
```
逐轮追踪：第 1 轮初稿缺术语 → 评估者返回「术语不完整」→ 第 2 轮补上术语但句式生硬 → 评估者返回「流畅度不足」→ 第 3 轮改成简洁主动句 → 评估者 PASS。三处关键设计：评估者提示里**显式写明评估标准**（术语、流畅度），标准越明确反馈越有用；达标就**自然终止**；`for round_i in range(max_rounds)` 是**硬性上限**，即使评估者永不满意也不会无限循环——这与开放式 Agent 循环必须设停止条件同理。

## 终止条件的三种形态

评估-优化最大的风险是死循环，因此终止条件不能只靠「评估者说 PASS」。生产上通常同时设三道闸：
```text
自然终止：评估者返回 PASS —— 正常路径
硬上限终止：round 达到 max_rounds —— 兜底，返回当前最佳版本 + 未达标标记
增量终止：连续 N 轮质量不再提升 —— 防「改来改去原地打转」，提前止损
```
Anthropic 明确指出这个模式的适用前提之一是「迭代精炼能带来**可衡量**的价值」[来源](https://www.anthropic.com/engineering/building-effective-agents)。「可衡量」意味着每轮都应能读出质量增量；一旦增量趋近于零，继续循环就是纯浪费。把「增量终止」显式实现（记录每轮评估分，连续无提升即停），能在评估者「嘴硬」时保护预算。

## 真实系统对应

**官方公开机制**：Anthropic 文档把评估-优化用于文学翻译与需多轮搜索的复杂任务，并强调其两个契合信号（人类反馈能改进响应、LLM 能给出这种反馈）与「明确评估标准」前提 [来源](https://www.anthropic.com/engineering/building-effective-agents)。LangGraph 官方文档的 `Evaluator-optimizer` 小节用两个节点（generator 与 evaluator）加一条条件边实现循环：evaluator 返回结构化的 `grade`（如 funny/not funny），据此决定回到 generator 继续改还是结束 [来源](https://docs.langchain.com/oss/python/langgraph/workflows-agents)。

**通用工程模式**：「生成与评估分角色、反馈显式回流、多重终止条件」是可迁移做法；评估者可以是同等或更强的模型，也可以是确定性的规则/测试（如代码场景用「跑测试」当评估者）。

**教学参考实现**：本页生成者与评估者都是确定性替身，只为可复现地展示循环收敛；真实评估者需要给出结构化、可操作的反馈，且要防「评估者比生成者还弱导致越改越差」。

## 生产踩坑

| 症状 | 根因 | 如何观测与复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| 循环空转，改到上限也没进步 | 评估标准含糊 | 检查评估者提示是否有明确维度 | 把评估维度写进评估者提示 | 标准本就清晰时无此问题 |
| 死循环无限烧 Token | 无终止条件 | 观察是否有请求 round 无上限 | 设 max_rounds 硬上限 | 一次即达标的任务不涉及 |
| 改来改去原地打转 | 无增量终止 | 记录每轮评估分是否停滞 | 连续 N 轮无提升即停 | 每轮都有明显提升时可放宽 |
| 越改越差 | 评估者比生成者弱 | 对比评估者与生成者能力 | 评估者用同等或更强模型 | 评估可用确定性规则时更稳 |
| 反馈没真正回流 | 只把反馈打印却没喂回生成 | 检查下一轮提示是否含反馈 | 把反馈拼进下一轮生成输入 | 无迭代的单次任务 |
| 对简单任务硬套循环 | 过度设计 | 对比单次调用与循环的质量差 | 单次够好就别上循环 | 高打磨要求时循环值得 |

## 思考：评估-优化模式在什么情况下会失效？

### 回答

两种典型失效，恰好对应它的两个前提被违反。其一，**没有明确的评估标准**：评估者说不清「什么是好」，只能给出「再好一点」这类空洞反馈，生成者无从改起，循环变成空转，改到上限也不进步——修复是把评估维度（如准确性、流畅度、术语一致）显式写进评估者提示，让反馈可操作。其二，**没有终止条件**：评估者永不满意、生成者永远在改，形成死循环无限烧 Token——修复是设 `max_rounds` 硬上限，并加「连续 N 轮无质量提升即停」的增量终止。此外还有两个次要失效：评估者比生成者弱导致「越改越差」（评估者应用同等或更强模型，或用确定性规则/测试当评估者），以及反馈没真正回流到下一轮生成（循环形同虚设）。所以用这个模式必须同时满足「标准明确」和「设终止条件」两个硬前提。

### 面试精简表达

失效有二：一是评估标准不明→反馈空洞→空转；二是无终止条件→死循环烧钱。前提是「标准明确 + 设 max_rounds」，附加防「评估者太弱」和「反馈没回流」。

### 反例

给「把一句话翻译成英文」这种一次就能翻好的任务套评估-优化循环，是过度设计——迭代带不来可衡量的提升，只增加延迟与成本，违反简单性原则。评估-优化只在「初稿明显有提升空间、且好坏可清晰评判」时才划算。

## 事故回放：一个「嘴硬评估者」的通宵账单

某团队用评估-优化做营销文案打磨，评估者提示写的是「如果文案还不够吸引人，就返回 REVISE 并给建议」。问题在于「够不够吸引人」是主观且无上界的标准——评估者几乎总能挑出「还能更好」的地方，于是每一轮都返回 REVISE。更糟的是，这个循环当时没有设 `max_rounds`，只依赖评估者说 PASS 才停。一条测试文案在无人值守的夜里循环了数百轮，生成者反复微调同一句话，评估者反复说「还能更吸引人」，直到第二天早上有人发现调用账单异常才手动杀掉进程。

复盘定位到三个叠加问题：评估标准无上界（主观、永远能更好）、无硬上限（唯一出口是 PASS）、无增量监测（早已原地打转却无人察觉）。修复是三管齐下：把「吸引人」拆成可判定的子标准（是否含行动号召、长度是否达标、是否含核心卖点），达到即 PASS；加 `max_rounds=4` 硬上限；记录每轮评估分，连续 2 轮无提升就停并返回当前最佳版本。这个事故是评估-优化的经典教训——**评估标准的「可判定性」和终止条件的「硬性」，比模型本身的能力更决定这个循环是否安全**。

## 优化前后对比

| 维度 | 优化前 | 优化后 | 验证方式 |
|---|---|---|---|
| 评估标准 | 主观、无上界 | 拆成可判定子标准 | 检查评估者提示维度 |
| 终止条件 | 仅靠评估者 PASS | PASS + 硬上限 + 增量终止 | 注入「嘴硬评估者」复现 |
| 反馈回流 | 反馈未喂回生成 | 反馈拼进下一轮输入 | 检查下一轮提示内容 |
| 评估者能力 | 可能弱于生成者 | 同等/更强，或用规则 | 对比评估与生成模型 |
| 成本 | 可能无限循环 | 有界，可预估上限 | 记录每请求轮数分布 |

评估-优化的正确心法是：**它的收益来自「独立评估视角」，它的安全来自「标准可判定 + 终止条件硬」。** 先确认任务满足两个前提（好坏可清晰评判、迭代确有提升），再确认三道终止闸齐备，最后才让它上生产。缺任何一环，这个循环要么空转、要么烧钱。
