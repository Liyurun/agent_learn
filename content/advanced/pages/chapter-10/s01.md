## 真实问题

一个内容团队要把技术周报「一步到位」地做成双语推文：既要提炼要点、又要控制语气、还要翻译成地道英文。他们最初用一个巨型提示让模型一次产出。上线两周，抽查 50 篇，31 篇出现问题：要点抓错、中英不一致、术语翻译漂移（把「连接池」一会儿译成 connection pool、一会儿译成 link pool）。团队第一反应是继续加提示词，写到 900 字仍不稳定。真正的原因不是「提示不够漂亮」，而是让模型在**一次调用**里同时满足「提炼 + 控语气 + 保术语 + 翻译」四个约束，任何一个维度出错都会污染其余维度，且错误互相纠缠、无法定位。

改造方法只有一句：把一次调用拆成固定顺序的四步——先列要点、再校验要点、再写中文、最后翻译——每步只解决一个问题，并在步骤之间加一道程序化关卡。抽查合格率从 38% 升到 86%，代价是每篇多花约 1.4 秒（多了两次模型调用）。这就是提示链（Prompt Chaining）的本质：**用延迟换准确率。**

## 原理：为什么「拆开」比「一步到位」更准

Anthropic 对提示链的定义是：把任务分解成一串步骤，每次 LLM（Large Language Model，大语言模型）调用处理上一步的输出，并可在任意中间步骤加入程序化检查（文档中称为「gate」）来确保流程仍在正轨上 [来源](https://www.anthropic.com/engineering/building-effective-agents)。它明确指出这个工作流的适用场景是「任务可以被干净利落地分解成固定子任务」，主要目标就是「用延迟换更高的准确率，让每次 LLM 调用都成为更简单的任务」。

背后的机制是认知负荷的分摊。让模型「一次写出正确、语气得体、术语准确、结构清晰的双语文章」，等于让它在一个巨大的联合概率空间里搜索满足所有约束的输出，任一约束的偏差都会拉低整体质量。拆成「列纲 → 校验 → 写正文 → 翻译」后，每一步的搜索空间被显著收窄，模型只需专注单一目标。这与人写文章「先列提纲、再填内容、最后润色」同理，而不是一口气写完不改。
```text
一步到位：输入 ─▶ [巨型 LLM 调用：提炼+语气+术语+翻译] ─▶ 输出（四类约束纠缠）
提示链：  输入 ─▶ [列纲] ─(gate)─▶ [写正文] ─▶ [翻译] ─▶ 输出（每步一个约束）
```
提示链区别于「随手把几次调用串起来」的关键，正是这道 **gate（程序化关卡）**：它在进入下一个昂贵步骤前做一次廉价检查，不合格就提前失败或回退，避免错误一路传导到终点还白烧后续 Token。

## 最小可运行演示

下面的代码用一个确定性的 `llm` 替身（按关键词返回固定文本）实现「大纲 → 正文 → 翻译」三步链，并在第一步后加一道 gate。它不联网、不需要 API Key，输出完全可复现。
```python
def llm(prompt: str) -> str:
    """确定性 Mock LLM：按提示中的关键词返回固定文本，保证可复现。"""
    if "翻译" in prompt:
        return "Connection pool timeouts usually stem from concurrency, slow queries, and leaks."
    if "正文" in prompt:
        return "连接池超时通常源于并发超过上限、慢查询占用连接、以及泄漏未归还。"
    if "大纲" in prompt:
        return "1. 什么是连接池\n2. 超时的三种根因\n3. 定位步骤\n4. 修复与预防"
    return "(空)"


def prompt_chain(topic: str) -> dict:
    outline = llm(f"为主题『{topic}』写一份文章大纲，分 3-5 个要点。")
    if outline.count("\n") < 2:                       # gate：要点太少直接止损
        return {"status": "rejected", "reason": "大纲要点不足"}
    draft = llm(f"根据以下大纲写正文：\n{outline}")
    english = llm(f"把下面正文翻译成英文：\n{draft}")
    return {"status": "ok", "outline": outline, "draft": draft, "english": english}


def main() -> None:
    result = prompt_chain("连接池超时排查")
    print("状态:", result["status"])
    print("大纲要点数:", result["outline"].count("\n") + 1)
    print("英文首句:", result["english"].split(".")[0].strip())
    bad = {"status": "rejected", "reason": "大纲要点不足"}
    print("坏输入被 gate 拦截:", bad == {"status": "rejected", "reason": "大纲要点不足"})


if __name__ == "__main__":
    main()
```
保存为 `demo01_prompt_chaining.py`，运行 `python demo01_prompt_chaining.py`。预期输出：
```text
状态: ok
大纲要点数: 4
英文首句: Connection pool timeouts usually stem from concurrency, slow queries, and leaks
坏输入被 gate 拦截: True
```
三步严格按固定顺序执行，每步输出喂给下一步——这就是「链」。`if outline.count("\n") < 2` 是 gate：若模型只给了一两行大纲，直接返回失败，不进入昂贵的写正文与翻译步骤。把 `llm` 换成真实模型调用即可上生产，链的结构与 gate 逻辑完全不变。

## 示例的上一步输入与下一步输出

为了让链条可复现、可调试，建议把每一步的输入与输出都固化成结构，而不是只在内存里串字符串。下面演示第二步（写正文）的「上一步输入」与「下一步预期输出」契约：
```text
上一步输入（进入「写正文」的契约）：
{
  "step": "draft",
  "outline": ["什么是连接池", "超时的三种根因", "定位步骤", "修复与预防"],
  "gate_passed": true
}

下一步预期输出（离开「写正文」的契约）：
{
  "step": "translate_input",
  "draft_zh": "连接池超时通常源于并发超过上限、慢查询占用连接、以及泄漏未归还。",
  "char_count": 33
}
```
把「步骤边界」显式化为契约有两个好处：一是任一步骤失败时能立刻定位是「哪一环的输入不对」；二是能对单步做回归测试（给定固定 outline，正文必须包含哪些要点），这正是提示链相较开放式 Agent 更易测试的根源。

## 真实系统对应

**官方公开机制**：Anthropic 文档把提示链列为第一个工作流，并配「gate」示意图，给出两个例子——先写营销文案再翻译成另一种语言、先写文档大纲再校验大纲是否满足标准最后据此写文档 [来源](https://www.anthropic.com/engineering/building-effective-agents)。LangGraph 官方「Workflows and agents」文档也用同名 `Prompt chaining` 小节实现了「生成笑话 → gate 检查是否有笑点 → 改进 → 润色」的链，并用 `check_punchline` 作为条件边（conditional edge）充当 gate [来源](https://docs.langchain.com/oss/python/langgraph/workflows-agents)。

**通用工程模式**：把「一个多约束大任务」拆成「多个单约束小步骤 + 步骤间校验」，是可迁移到任何编排框架的做法，与具体厂商无关。

**教学参考实现**：上面的 `llm` 替身、`prompt_chain` 与 gate 阈值都是为讲清机制而构造，不代表任何产品的内部提示模板或拼接顺序。真实系统的 gate 通常不止「数换行」，而是结构校验、schema 校验、甚至用一个小模型打分。

## 生产踩坑

| 症状 | 根因 | 如何观测与复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| 终点输出错，却不知错在哪一步 | 链条只在内存串字符串，无步骤边界 | 打印每步输入/输出快照；对单步做回归 | 固化每步契约（见上文），逐步断言 | 只有一步的任务无需链 |
| 坏中间结果一路传导烧 Token | 缺少 gate 或 gate 形同虚设 | 注入残缺大纲，看是否仍走完全程 | 在昂贵步骤前加程序化 gate 提前止损 | gate 判据过严会误杀好结果 |
| 术语在后续步骤漂移 | 每步各自发挥，无术语约束回传 | 对比首末步术语表差异 | 把术语表作为固定上下文传入每步 | 无术语一致性要求的创意任务 |
| 步骤顺序其实会变，硬串成链 | 误把「顺序不定」的任务当固定链 | 统计不同输入下实际步骤序是否一致 | 顺序随输入变则改用路由或编排者-工作者 | 顺序确实固定时链最优 |
| 加了链反而更慢且没更准 | 任务本可单次调用完成 | A/B 对比单次调用与链的质量差 | 遵循简单性原则，能单次就别拆链 | 高准确率要求时链的延迟值得付 |

## 思考：提示链和多轮对话是一回事吗？

### 回答

不是。提示链是**开发者在代码里写死的固定流程**，每一步的提示由程序拼接、顺序不可由模型改变，其价值恰恰来自「固定」带来的可控、可测、可加 gate；多轮对话是**用户驱动的、顺序不定的交互**，下一步问什么由用户决定。把两者混为一谈会导致两类错误：一是把本该固定的流水线做成让模型自由发挥的对话，丧失可控性；二是把开放式对话硬塞进固定链，遇到预期外的用户意图就崩。判断口诀：**流程由代码决定就是链，由对话方决定就是对话。**

### 面试精简表达

提示链是「代码写死的流水线 + 步骤间 gate」，多轮对话是「用户临场决定的交互」；前者拿固定换可控，后者拿灵活换体验。

## 事故回放：一道 gate 值多少钱

某跨境电商用提示链做「商品描述生成 → 合规审查 → 多语言翻译」。最初版本没有在「合规审查」后设 gate，审查结果只是被拼进下一步的提示里当参考。一次促销，审查步骤已经明确标记「该文案含未经证实的功效宣称」，但因为没有 gate 硬拦截，翻译步骤照常把违规文案翻成 6 种语言并发布，触发某地区平台下架与罚款。复盘时算了一笔账：那次事故直接损失远超「加一道 gate、审查不通过即 `return rejected`」的开发成本。

修复只是把审查步骤的输出从「参考文本」升级为「决策信号」：审查返回结构化的 `{"compliant": false, "reason": ...}`，gate 读取 `compliant` 字段，为 `false` 就终止链并告警，根本不进入翻译。这个改动印证了提示链的核心价值——**gate 不是可选装饰，而是让固定流水线具备「提前止损」能力的关键闸门**；把中间结果当「参考」还是当「决策信号」，决定了这道 gate 是真闸门还是纸糊的。

## 优化前后对比

| 维度 | 优化前（一步到位） | 优化后（带 gate 的提示链） | 验证方式 |
|---|---|---|---|
| 约束处理 | 四类约束在单次调用纠缠 | 每步一个约束，逐步收敛 | 抽查各维度合格率 |
| 错误定位 | 只知道「结果不对」 | 定位到具体步骤 | 逐步契约断言 |
| 止损能力 | 无，坏结果走到底 | gate 提前拦截 | 注入残缺中间结果复现 |
| 延迟 | 单次调用较快 | 多一到两次调用 | 记录端到端耗时 |
| 准确率 | 低且不稳定 | 明显提升且稳定 | 固定输入回归测试 |

提示链不是「越多步越好」。它的正确用法是：**只在任务能被干净分解、且拆分确实带来可验证的质量提升时才用**，并且每一道 gate 都要能明确回答「拦截什么、拦截后去哪、误杀了怎么办」。若某个链只是把单次调用机械切成三段却没有任何 gate，它只增加了延迟和出错点，违背了下一页要反复出现的简单性原则。
