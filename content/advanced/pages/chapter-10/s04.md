## 真实问题

某团队做一个「自动修 bug」助手。缺陷描述五花八门：有的只需改一个文件，有的要连改前端、后端、迁移脚本、测试共八个文件。他们先用并行化（分段）实现：在代码里**硬编码**「改 A.py、B.py、C.py 三个文件」的三个并行任务。结果可想而知——遇到只需改一个文件的 bug，多跑了两个空任务；遇到要改八个文件的 bug，漏改了五个，测试全绿却没真正修好。问题的本质是：**要改哪些文件，事先根本不知道，它取决于具体的缺陷。** 把「拆成几份、每份做什么」写死在代码里，天然无法应对这种任务。

正确的模式是编排者-工作者（Orchestrator-Workers）：让一个中心的编排者（Orchestrator）LLM**在运行时**先分析「这个 bug 要动哪些文件」，动态返回一个文件列表，再为每个文件派一个工作者（Worker）去改，最后由编排者综合所有改动。改造后，一个文件的 bug 只派一个 worker，八个文件的 bug 派八个，不多不少。这就是它与并行化的唯一本质区别——**子任务不是预先定义的，而是编排者根据具体输入运行时决定的。**

## 原理：「运行时动态决定」到底动态在哪

Anthropic 对编排者-工作者的定义是：一个中心 LLM **动态地分解任务、把子任务委派给工作者 LLM、并综合它们的结果** [来源](https://www.anthropic.com/engineering/building-effective-agents)。文档给出的适用条件是「复杂任务且你**无法预测所需的子任务**（例如编码时，需要改的文件数量以及每个文件改动的性质都取决于任务）」，并特别强调：它在拓扑上与并行化相似，但**关键区别在于灵活性——子任务不是预先定义的，而是由编排者基于具体输入决定的**。文档给的例子正是「每次都要对多个文件做复杂改动的编码产品」和「需要从多个来源收集并分析信息的搜索任务」。

这是本章最容易混淆的点，值得掰开揉碎。对比并行化和编排者-工作者面对「改代码」的差别：
```text
并行化（分段）：          编排者-工作者：
任务                       任务
 │                          │
[开发者硬编码拆成 3 份]     [Orchestrator LLM 分析]  ← 运行时才知道拆几份
 ├─ A.py（写死）            │
 ├─ B.py（写死）            ├─ ? 个 worker（运行时定）
 └─ C.py（写死）            └─ 每个做什么也运行时定
```
一句话记忆：**并行化是「我（开发者）来拆」，编排者-工作者是「让模型来拆」。** 正因为「拆」这个决策交给了模型，它的自主性更高、更靠近自主性光谱的右端——也因此更需要护栏（比如给 worker 数量设上限，防止分解爆炸）。

## 最小可运行演示

下面用确定性的 `orchestrator_plan` 替代编排者 LLM（真实系统里换成一次强模型调用 + 结构化输出）：不同任务返回不同长度的文件列表，直观体现「运行时决定拆几个」。纯 Python，无需 API Key。
```python
def orchestrator_plan(task: str) -> list[dict]:
    """编排者：运行时根据任务内容动态生成子任务列表（数量不固定）。"""
    files = []
    if "登录" in task:
        files = ["auth/login.py", "auth/session.py"]
    if "结算" in task:
        files = ["billing/checkout.py", "billing/coupon.py", "billing/tax.py"]
    return [{"id": i + 1, "desc": f"修改 {f}"} for i, f in enumerate(files)]


def worker(subtask: dict) -> dict:
    return {"id": subtask["id"], "output": f"已完成：{subtask['desc']}"}


def orchestrator_synthesize(results: list[dict]) -> str:
    lines = [f"- #{r['id']} {r['output']}" for r in results]
    return "最终报告：共处理 {} 个文件\n".format(len(results)) + "\n".join(lines)


def orchestrator_workers(task: str, max_workers: int = 8) -> str:
    subtasks = orchestrator_plan(task)                 # ★ 运行时决定拆几个
    if len(subtasks) > max_workers:                    # 上限护栏，防止分解爆炸
        subtasks = subtasks[:max_workers]
    results = [worker(st) for st in subtasks]
    return orchestrator_synthesize(results)


def main() -> None:
    print("任务A（登录）:")
    print(orchestrator_workers("修复登录会话过期问题"))
    print("\n任务B（结算）:")
    print(orchestrator_workers("修复结算优惠券少减金额"))


if __name__ == "__main__":
    main()
```
保存为 `demo04_orchestrator.py`，运行 `python demo04_orchestrator.py`。预期输出：
```text
任务A（登录）:
最终报告：共处理 2 个文件
- #1 已完成：修改 auth/login.py
- #2 已完成：修改 auth/session.py

任务B（结算）:
最终报告：共处理 3 个文件
- #1 已完成：修改 billing/checkout.py
- #2 已完成：修改 billing/coupon.py
- #3 已完成：修改 billing/tax.py
```
同一个 `orchestrator_workers` 函数，任务 A 拆出 2 个子任务、任务 B 拆出 3 个——**代码里没有任何地方写死「2」或「3」，数量完全由 `orchestrator_plan` 在运行时根据任务内容决定**。这正是编排者-工作者的灵魂。`max_workers` 上限是必备护栏：编排者可能被诱导拆出几十个子任务，护栏防止分解爆炸导致成本失控。演示里 worker 用串行循环，实际生产中若子任务独立可用线程池并行执行（这就是编排者-工作者与并行化的组合）。

## 「分解—执行—综合」三段式与结构化契约

编排者-工作者的标准形态是三段式，其中「分解」和「综合」都由编排者担纲，中间的「执行」交给工作者。为了让分解结果可解析、可校验，编排者应输出结构化的计划，而不是自由文本：
```text
编排者「分解」输出（结构化计划，运行时生成）：
{
  "subtasks": [
    {"id": 1, "file": "billing/checkout.py", "change": "修正优惠券金额计算"},
    {"id": 2, "file": "billing/coupon.py",   "change": "校验满减门槛"},
    {"id": 3, "file": "billing/tax.py",       "change": "重算税基"}
  ],
  "count": 3
}

每个 worker「执行」的入参与出参：
入参：{"id": 1, "file": "billing/checkout.py", "change": "..."}
出参：{"id": 1, "status": "done", "diff": "- old\n+ new"}

编排者「综合」输出：
{"summary": "共修改 3 个文件，全部通过", "files": ["checkout.py", "coupon.py", "tax.py"]}
```
结构化的好处是：分解阶段能对 `count` 设上限、对 `file` 做白名单校验（防止编排者要求改不该动的文件）；综合阶段能逐条核对每个 worker 是否真的完成。**把「模型的自由发挥」约束在一个可校验的 schema 里，是驾驭高自主性模式的关键手段。**

## 真实系统对应

**官方公开机制**：Anthropic 文档把编排者-工作者用于「每次都对多个文件做复杂改动的编码产品」，并明确其与并行化的区别在「子任务由编排者运行时决定而非预定义」[来源](https://www.anthropic.com/engineering/building-effective-agents)。这与 Anthropic 后续公开的多智能体研究系统思路一致：一个主导 Agent 分解研究问题、派多个子 Agent 并行搜集，再综合。LangGraph 官方文档的 `Orchestrator-worker` 小节也指出：当子任务无法像并行化那样预定义时，用编排者-工作者提供更高灵活性，并用 `Send` API 动态派发运行时才知道数量的 worker [来源](https://docs.langchain.com/oss/python/langgraph/workflows-agents)。

**通用工程模式**：「先让模型规划、再按规划派工、最后综合」是可迁移的做法；核心工程约束是给分解结果加 schema 校验和数量上限。

**教学参考实现**：本页 `orchestrator_plan` 用关键词返回固定文件列表，只为可复现地展示「数量运行时可变」；真实编排者是一次强模型调用，其输出需要严格解析与校验，且可能出错（拆漏、拆错、拆过头）。

## 生产踩坑

| 症状 | 根因 | 如何观测与复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| 编排者拆出几十个子任务，成本爆炸 | 无 worker 数量上限 | 记录每次分解的子任务数分布 | 设 max_workers 上限 + 超限告警 | 任务天然子项少时风险低 |
| 编排者要求改不该动的文件 | 分解结果无白名单校验 | 检查计划中的 file 是否越界 | 对 file 做白名单/权限校验 | 沙箱内可放宽 |
| 子任务漏拆，测试绿但没修好 | 编排者分解不全 | 对已知多文件 bug 回归 | 综合阶段核对覆盖面 + 人工抽检 | 单文件任务不涉及 |
| 综合阶段丢失部分 worker 结果 | 综合只看部分输出 | 对比 worker 数与综合引用数 | 逐条核对每个 id 是否被综合 | 无需综合的独立产出 |
| 分解结果无法解析 | 编排者返回自由文本 | 统计 JSON 解析失败率 | 用结构化输出/函数调用约束格式 | 简单场景可宽松 |
| 明明子任务固定却上编排者 | 过度设计 | 对比并行化与编排者的必要性 | 子任务能预定义就用并行化 | 子任务确实不定时才用本模式 |

## 思考：并行化和编排者-工作者到底有什么区别？

### 回答

这是必考混淆题，核心答案只有一句：**子任务是不是预先定义的。** 并行化（分段）的子任务在**编码时**就固定了——开发者在代码里写死「拆成摘要、情感、关键词三份」，运行时数量与内容都不变；编排者-工作者的子任务由编排者 LLM 在**运行时**根据具体输入动态分解——事先不知道会拆成几个、拆成什么。用「改代码」讲最清楚：并行化适用于「我知道要改 A、B、C 三个文件」，编排者-工作者适用于「要改哪些文件取决于这个 bug，可能 1 个也可能 8 个，让模型先分析再派工」。正因为「拆」的决策权从开发者转移到模型，编排者-工作者自主性更高、更靠右，也更需要 worker 数量上限、文件白名单等护栏。

### 面试精简表达

唯一本质区别：子任务预定义（并行化，我来拆）还是运行时由编排者决定（编排者-工作者，模型来拆）。前者分支固定成本可控，后者分支不定需设上限护栏。

### 反例

给「把用户输入翻译成英文」这种子任务完全确定的任务上编排者-工作者，是典型过度设计——翻译根本不需要运行时分解，一次调用或轻量提示链就够，硬上编排者只会徒增成本、延迟与出错点。

## 事故回放：一次分解爆炸烧掉的预算

某研究助手用编排者-工作者做「文献综述」：编排者读用户问题，分解成若干「检索 + 精读」子任务派给 worker。一次用户输入了一个极其宽泛的问题（「总结人工智能的所有进展」），编排者被诱导拆出 60 多个子任务，每个 worker 又各自触发多次检索与长文本精读。因为当时没有设 worker 数量上限，系统一口气派出 60 多个 worker 并发跑，单次请求的 Token 消耗是正常请求的几十倍，几分钟内就把当天的调用预算烧掉一大截，还触发了模型提供方的速率限制导致后续请求全部失败。

复盘的修复有三层：其一，给 `max_workers` 设硬上限（如 8），超限则要求编排者「聚焦最相关的 N 个方向」重新分解；其二，在分解阶段就估算成本，超预算先向用户确认；其三，把「问题过宽」本身作为一种要拒绝或澄清的输入，而不是照单全收地分解。这个事故印证了编排者-工作者的核心风险——**把分解权交给模型，就必须同时把「分解规模」的控制权留在代码里**。自主性越高的模式，越依赖代码侧的硬护栏兜底。

## 优化前后对比

| 维度 | 优化前（硬编码并行化） | 优化后（编排者-工作者） | 验证方式 |
|---|---|---|---|
| 子任务数量 | 编码时写死 | 运行时由编排者决定 | 不同任务对比拆分数 |
| 覆盖面 | 多文件 bug 漏改 | 按实际动态覆盖 | 已知多文件 bug 回归 |
| 成本控制 | 分支固定，成本恒定 | 分支不定，需上限护栏 | 记录子任务数分布 |
| 越权风险 | 不涉及 | 需文件白名单校验 | 注入越界文件请求 |
| 适用性 | 子任务固定时最优 | 子任务不定时才该用 | 对比两模式必要性 |

编排者-工作者的正确心法是：**它的强大来自「把拆分交给模型」，它的风险也来自这里。** 只有当子任务数量与内容确实无法预先确定时才用它；一旦用了，就必须在代码侧配齐三道护栏——数量上限、结果 schema 校验、以及综合阶段的覆盖核对。
