## 真实问题

一支团队在半年里踩遍了模式选择的坑：给「翻译一句话」上了编排者-工作者 + 评估-优化的多 Agent 系统（过度设计，成本翻十倍）；给「必须先审查再发布」的固定流程用了开放循环 Agent（模型自主决定顺序，导致违规内容先发后审）；给「三类客服意图」用一个巨型提示（关注点不分离，样样松）。这些错误的共同根源不是不懂某个模式，而是**没有一套「面对新需求，如何快速选对模式」的判断框架，以及一份「选完之后如何在生产里活下来」的踩坑清单**。

本页把两件事讲透：其一，五种模式 + 开放 Agent 的**选择决策流**与速查表；其二，一张覆盖全部模式、可直接对照排查的**生产建议表**；最后落到 Anthropic 的三大设计原则——它们是区分「玩具 Agent」与「生产级 Agent」的分水岭。

## 原理：先定自主性，再选模式

一切选择都从一个判断开始：**这个需求能不能用固定路径搞定？** Anthropic 的建议是「找到尽可能简单的方案，只在需要时才增加复杂度；很多应用其实只要优化单次 LLM 调用配合检索和示例就够了」，并明确「工作流为定义良好的任务提供可预测性与一致性，Agent 则在需要大规模灵活性与模型驱动决策时更合适」[来源](https://www.anthropic.com/engineering/building-effective-agents)。

把这句话落成决策流：
```text
需求来了
  │
  ├─ 单次 LLM 调用 + 检索/示例就够? ───────────▶ 别上工作流（最省）
  │
  ├─ 步骤固定、有先后依赖? ────────────────────▶ 提示链（步骤间加 gate）
  │
  ├─ 要先按类型分流到不同处理? ─────────────────▶ 路由（加兜底类别 + 成本分层）
  │
  ├─ 子任务独立、能同时做? ─────────────────────▶ 并行化·分段（各算分片再合并）
  │     └─ 想靠冗余提高可靠性? ─────────────────▶ 并行化·投票（按代价定聚合阈值）
  │
  ├─ 子任务数量/内容运行时才知道? ──────────────▶ 编排者-工作者（设 worker 上限）
  │
  ├─ 有明确评分标准、迭代确有提升? ─────────────▶ 评估-优化（标准可判定 + 终止条件）
  │
  └─ 步骤数无法预测、需模型全权决策且环境可信? ──▶ 开放循环 Agent（沙箱 + 停止条件）
```
这条决策流的排序不是随意的：**越往下自主性越高、越贵、越难调试**。工程判断永远是「从上往下找第一个能满足需求的」，而不是「从下往上炫技」。

## 五种模式速查表

| 模式 | 一句话本质 | 子任务是否预定义 | 头号风险 | 典型场景 |
|---|---|---|---|---|
| Prompt Chaining 提示链 | 固定顺序分步，延迟换准确率 | 是（固定顺序） | 缺 gate，坏结果传导到底 | 先写文案再翻译、先大纲再正文 |
| Routing 路由 | 分类后导向专门处理 | 是（分支枚举） | 误分类、类别不互斥 | 客服分流、模型成本分层 |
| Parallelization 并行化 | 分段并行 / 多次投票 | 是（独立子任务） | 并行写共享状态、慢实例 | 处理+审查并行、多实例查漏洞 |
| Orchestrator-Workers 编排者-工作者 | 动态分解委派再综合 | 否（运行时决定） | 分解爆炸、越权改文件 | 多文件编码、开放式研究 |
| Evaluator-Optimizer 评估-优化 | 生成-评估循环精炼 | 循环迭代 | 空转、死循环 | 文学翻译、多轮复杂搜索 |

## 组合才是常态：把模式当积木

Anthropic 强调这些构建块「不是规定动作，而是开发者可以塑形与组合以适配不同用例的常见模式」，成功的关键是「度量表现并迭代实现，只有当复杂度确实能改善结果时才增加它」[来源](https://www.anthropic.com/engineering/building-effective-agents)。真实系统几乎都是混搭。以本章开头的「客服审核 + 生成」系统为例：
```text
用户提交文本
  │
[路由] 按内容类型分流（投诉/咨询/闲聊）
  │
  ├─ 每个分支内部：
  │    [并行化·分段] 同时跑「合规审查」与「回复生成」（审查不过则丢弃生成）
  │        └─ 合规审查内部用 [并行化·投票]：多实例判断，一票否决
  │    [提示链] 固定步骤：脱敏 → 生成 → 格式化
  │    [评估-优化] 对生成的回复做质量打磨（标准明确 + max_rounds）
  │
最终响应
```
这个例子里五种模式全用上了，但每一处都遵循「用满足需求的最低自主性」：分流用路由而非让模型自由决定、审查用确定性投票而非单次判断、打磨用有界的评估-优化而非无限循环。**掌握单个模式是基础，会按简单性原则组合才是高手**。

## 真实系统对应

**官方公开机制**：Anthropic 明确「框架能帮你快速起步，但走向生产时不要犹豫去减少抽象层、用基础组件构建」，并给出三大原则（简单性、透明性、精心打磨 ACI）[来源](https://www.anthropic.com/engineering/building-effective-agents)。OpenAI 的实践指南同样建议「先用单 Agent 把能力做扎实，只有当单 Agent 的提示与工具变得臃肿难维护时，才升级到多 Agent 编排」[来源](https://cdn.openai.com/business-guides-and-resources/a-practical-guide-to-building-agents.pdf)。Chip Huyen 的《Agents》则从工程角度反复强调「规划与执行分离、给循环设预算」的重要性 [来源](https://huyenchip.com/2025/01/07/agents.html)。

**通用工程模式**：「先定自主性档位、再选最低够用的模式、组合时给整体设预算」是可迁移到任何栈的选择方法论。

**教学参考实现**：本页决策流与组合示例是为讲清选择逻辑而构造的教学框架，不对应任何产品的内部编排；真实系统的模式边界往往更模糊，需要用度量（成本、延迟、质量）来验证选择是否正确。

## 真实系统对应：三大真实平台如何落地这些模式

除了本书的教学骨架，公开资料显示主流平台都以自己的原语承载同一套模式，边界如下（只陈述公开机制，不臆造内部实现）：

- **Anthropic Claude（API + Cookbook）**：官方 Cookbook 直接提供 prompt chaining、routing、parallelization、orchestrator-workers、evaluator-optimizer 的示例实现，主张「用 API 几行代码即可」[来源](https://platform.claude.com/cookbook/patterns-agents-basic-workflows)。这是「模式 = 代码编排」而非「模式 = 框架特性」的最直接证据。
- **LangGraph（LangChain）**：用 `StateGraph`（图 API）或 `entrypoint/task`（函数 API）承载五种模式，提示链用普通边、路由用条件边 + 结构化输出、并行化用多入边汇聚、编排者-工作者用 `Send` 动态派发、评估-优化用带条件边的循环，并配 LangSmith 做轨迹追踪 [来源](https://docs.langchain.com/oss/python/langgraph/workflows-agents)。
- **通用 LLM API 直调**：不引入任何框架，仅用一个统一的 `call()` 入口 + 普通 Python 控制流即可实现全部五种（见第 6 页）。这是 Anthropic「先直接用 API」建议的最小化落地。

三者的共同点印证了本章的核心论断：**这五种模式是编排范式，不绑定任何框架**；框架只是让起步更快，边界是「别让抽象层遮蔽底层的提示与响应」。

## 生产建议表（覆盖全部模式，可直接对照排查）

| 症状 | 根因 | 如何观测与复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| 简单需求上了多 Agent，成本翻十倍 | 违反简单性，过度设计 | 对比单次调用与复杂方案的质量差 | 从最低自主性起步，无收益不升级 | 高价值高难度任务值得复杂 |
| 固定流程用了开放 Agent，顺序失控 | 该用工作流却用 Agent | 观察模型是否自主改变步骤序 | 顺序固定就用提示链写死 | 顺序确实不定时才用 Agent |
| 提示链坏结果一路传导烧 Token | 缺 gate 或 gate 形同虚设 | 注入残缺中间结果看是否走完 | 昂贵步骤前加程序化 gate 止损 | 单步任务无需 gate |
| 路由把高风险请求误分派 | 分类器误分类、无兜底 | 用歧义样本复现；查分类日志 | 设兜底类别 + 高风险类二次确认 | 类别极清晰时可简化 |
| 简单问题也走强模型，成本高 | 未做成本分层 | 统计各处理器模型调用占比 | 简单类走小模型，仅难题升级 | 全高风险请求时不宜省 |
| 本可并行的步骤排成串行，延迟高 | 误把独立任务当有依赖 | 画依赖图找无依赖边 | 无依赖子任务改分段并行 | 真有先后依赖必须串行 |
| 并行分支写同一状态出现脏数据 | 并行写共享状态 | 高并发注入复现竞态 | 各算分片，末尾统一合并 | 无共享写时无此问题 |
| 投票成本翻倍却没更准 | 对稳定任务滥用投票 | 对比单次与多次一致率 | 只对不稳定高风险判断投票 | 判断本就稳定时不投票 |
| 编排者拆出几十个子任务烧预算 | 无 worker 数量上限 | 记录每次分解的子任务数 | 设 max_workers + 超限重分解 | 子项天然少时风险低 |
| 编排者要求改不该动的文件 | 分解结果无白名单校验 | 检查计划 file 是否越界 | 对 file 做白名单/权限校验 | 沙箱内可放宽 |
| 评估-优化循环空转不达标 | 评估标准含糊 | 查评估者提示是否有明确维度 | 把评估维度写进提示，标准可判定 | 标准本清晰时无此问题 |
| 评估-优化死循环无限烧钱 | 无终止条件 | 观察是否有请求 round 无上限 | 设 max_rounds + 增量终止 | 一次即达标不涉及 |
| 组合模式后调用次数相乘失控 | 模式嵌套无总预算 | 统计端到端调用/Token 分布 | 给整体设调用与 Token 预算上限 | 单模式且分支少时风险低 |
| 出错无从排查，黑盒 Agent | 未展示规划步骤，缺透明性 | 检查是否记录规划与轨迹 | 显式打印规划、反馈、调用轨迹 | 纯确定性流程可简化 |
| 模型频繁用错工具 | ACI 差，工具描述含糊 | 统计工具调用错误率 | 像打磨提示一样打磨工具文档与测试 | 无工具的纯文本任务 |

## 三大设计原则（Anthropic）

无论用哪种模式，Anthropic 给出三条贯穿始终的原则 [来源](https://www.anthropic.com/engineering/building-effective-agents)：

1. **保持简单性（Simplicity）**：优先最简方案，只有确证不足才加复杂度。
2. **优先透明性（Transparency）**：显式展示 Agent 的规划步骤，让人看懂它在想什么、做什么。
3. **精心设计 ACI（Agent-Computer Interface，智能体-计算机接口）**：把工具的文档和测试当成提示一样打磨。

| 原则 | 一句话 | 操作方法 | 反面教材 |
|---|---|---|---|
| 简单性 | 能简单就别复杂 | 从单次调用起步，无可见收益不升级自主性 | 翻译一句话却上多 Agent |
| 透明性 | 让人看懂它在想什么 | 打印规划、反馈、调用轨迹（见第 6 页） | 黑盒 Agent 出错无从排查 |
| 精心设计 ACI | 工具接口像提示一样打磨 | 打磨工具名/描述/参数/返回/错误信息并写测试 | 工具描述含糊导致频繁用错 |

**为什么简单性排第一？** 因为复杂度是万恶之源——越复杂越难调试、越贵、越容易出错。它的操作方法是：先用最简单的方案（能单次调用就别上工作流，能工作流就别上 Agent），只有当它确实不够用、且你能证明加复杂度带来了可见收益时才升级。透明性解决「概率系统必然出错、看不见就没法调试」的问题；ACI 则是最容易被忽视却最影响成败的一条——工具的名字、描述、参数、返回、错误信息本质是「写给模型看的 API 文档」，一个描述模糊的工具会让再聪明的模型也频频出错。

## 思考：工作流和 Agent 有什么区别？什么时候该用哪个？

### 回答

Anthropic 把二者都归为「Agentic 系统」，但做了关键架构区分：**工作流是 LLM 与工具通过预定义代码路径编排的系统，流程写死、可预测、可控；Agent 是 LLM 动态自主决定流程与工具使用、自己掌控如何完成任务的系统，灵活但不可预测**。判断准则是「能用工作流满足需求就别用 Agent」——因为自主性是成本：更难调试、更贵、更不可复现、可能有复合错误。只有当任务的步骤数无法预测、无法硬编码固定路径、且你能在可信环境里对模型的决策有一定信任时，才用 Agent（并且要配沙箱测试与停止条件）。本章前四种模式（提示链、路由、并行化、编排者-工作者）本质是工作流，评估-优化介于两者之间，完全开放的循环 Agent 在光谱最右端。

### 面试精简表达

工作流=代码写死路径（可控），Agent=模型动态决策（灵活）；能用工作流就别用 Agent，因为自主性=成本；只有步骤不可预测、无法硬编码时才上 Agent，且必配沙箱与停止条件。

## 思考：面对一个新需求，你的选型思考顺序是什么？

### 回答

按自主性从低到高「找第一个够用的」：第一步先问「单次 LLM 调用 + 检索/示例够不够」，够就不上工作流；不够再问「步骤是否固定有依赖」（是→提示链）、「是否要按类型分流」（是→路由）、「子任务是否独立可并行」（是→并行化分段，要冗余则投票）、「子任务是否运行时才确定」（是→编排者-工作者）、「是否有明确评分且迭代有提升」（是→评估-优化）；只有当步骤数完全无法预测、必须让模型全权决策时，才上开放循环 Agent。选完还要用度量（成本、延迟、质量）验证选择，并记住模式可组合——顶层路由、分支内链、某步并行、末尾评估-优化是常见搭配。核心是「从上往下找够用的，而不是从下往上炫技」。

### 反例

反面做法是「一上来就想用最强大最自主的方案」，结果给固定流程套开放 Agent、给一句话翻译套多 Agent，徒增成本、延迟与出错点。

## 思考：这五种模式能一起用吗？举一个组合例子。

### 回答

能，而且生产系统几乎都是组合使用——Anthropic 明确说这些是可塑形、可组合的构建块。举例一个「智能客服审核 + 生成」系统：顶层用**路由**按内容类型分流（投诉/咨询/闲聊）；每个分支内部用**并行化·分段**同时跑「合规审查」和「回复生成」，审查不过就丢弃生成结果以降延迟；合规审查内部再用**并行化·投票**多实例判断、一票否决以降漏报；回复的固定加工步骤（脱敏→生成→格式化）用**提示链**并在步骤间加 gate；最后对生成的回复用**评估-优化**做有界的质量打磨。整套系统五种模式都用上了，但每一处都遵循「用满足需求的最低自主性」，并给端到端设了调用与 Token 预算上限，防止模式嵌套导致调用次数相乘失控。

### 面试精简表达

能组合，且是常态：路由做顶层分流、链做固定步骤、并行做加速与冗余、编排者-工作者做动态分解、评估-优化做质量把关；关键是组合时仍守简单性并设总预算。

## 事故复盘合集：三个「选错模式」的真实教训

- **过度设计**：给「翻译一句话」上编排者-工作者 + 评估-优化。根因是违反简单性原则。翻译大多数情况一次调用就够，要求高时最多加「翻译→校对」的轻量提示链。上多 Agent 纯属徒增成本、延迟与出错点。修复：砍到单次调用 + 可选轻量校对。
- **该用工作流却用 Agent**：给「必须先审查再发布」的固定流程用开放循环 Agent，模型自主决定顺序，某次先生成后审查导致违规内容被发出。根因是把可预测流程交给了不可预测的模型。修复：改成工作流，审查作为确定性前置 gate，不通过就绝不进入发布。
- **该分层却大一统**：给退款/技术/通用三类客服用一个巨型提示。根因是关注点不分离，指令互相干扰。修复：改用路由 + 专门处理器 + 成本分层，退款处理器还要把只读工具与可执行工具分开并加确认 gate。

三个案例的共同教训可以浓缩成一句话，也是本章的落点：**先选对自主性档位（工作流还是 Agent），再选最低够用的模式，最后用度量验证并配齐护栏**。掌握五种模式是入门，会按简单性、透明性、精心设计 ACI 三大原则做取舍与组合，才是生产级工程师与「会背名词的人」的分水岭。
