## 真实问题

某社区平台的内容管道原本是一条提示链：用户发帖后，先「审查是否违规」，通过再「生成推荐标签」，最后「情感分析入库」。三步串行，端到端 P95 延迟 3.6 秒。用户抱怨发帖卡顿。工程师起初想换更快的模型，但压测发现瓶颈不在模型速度，而在**把三件互不依赖的事排成了串行**——审查、打标签、情感分析根本不需要等彼此的结果。改成并行后，三步同时跑，端到端延迟压到约 1.3 秒，接近「一次调用」的耗时。

与此同时，另一个更隐蔽的问题浮现：安全审查用单次模型判断，偶尔漏判（模型某次「心情好」放过了辱骂）。团队又叠加了第二种并行——对同一段内容让三个实例独立判断，只要一票说违规就升级人工。漏判率显著下降。这两个改造对应并行化（Parallelization）的两种子形态：**Sectioning（分段）**解决「不同的事同时做」，**Voting（投票）**解决「同一件事做多遍以提高可靠性」。

## 原理：分段与投票是两种截然不同的目的

Anthropic 把并行化定义为「LLM 有时能同时处理一个任务，并把它们的输出以程序化方式聚合」，并明确拆成两种变体 [来源](https://www.anthropic.com/engineering/building-effective-agents)：

- **Sectioning（分段）**：把任务拆成**相互独立的子任务并行运行**。文档的例子是「一个模型实例处理用户查询，同时另一个实例审查内容是否违规」——这比让同一次 LLM 调用既当护栏又出主答效果更好；以及「自动化评测，每个 LLM 调用评估模型在某个提示上的不同方面」。
- **Voting（投票）**：**对同一个任务运行多次以获得多样化输出**。文档的例子是「用多个不同提示审查同一段代码有无漏洞，任一发现问题就标记」，以及「用多个提示或不同投票阈值评估内容是否违规，以平衡误报与漏报」。

初学者极易混淆二者，但目的完全不同：
```text
分段：一个任务 ─▶ 切成不同子任务 ─▶ 各做各的 ─▶ 拼装   （做不同的事，为了「快 + 分工」）
投票：一个任务 ─▶ 重复做很多遍   ─▶ 综合/多数/一票否决  （做同一件事，为了「准 + 全」）
```
一句话记忆：**分段是「把一件大事切成几件小事」，投票是「把同一件事做很多遍」。** 两者的共同前提各不相同——分段要求子任务**相互独立**（能打乱顺序同时做），投票要求任务**值得用冗余换可靠**（单次判断不够稳）。

## 最小可运行演示

下面用线程池演示两种子形态。`llm_section` 是三个不同子任务（分段），`llm_vote` 对同一问题多次判断（投票）。纯 Python，无需 API Key，LLM 调用是 I/O（Input/Output，输入/输出）密集型，用线程池并发即可显著提速。
```python
from concurrent.futures import ThreadPoolExecutor


def llm_section(kind: str, review: str) -> str:
    """分段：三个不同子任务，各返回确定性结果。"""
    if kind == "summary":
        return "用户抱怨发货慢但客服态度好。"
    if kind == "sentiment":
        return "中性偏负"
    if kind == "keywords":
        return "发货, 慢, 客服"
    return "(未知)"


def analyze_review(review: str) -> dict:
    kinds = ["summary", "sentiment", "keywords"]
    with ThreadPoolExecutor(max_workers=3) as pool:
        futures = {k: pool.submit(llm_section, k, review) for k in kinds}
        return {k: f.result() for k, f in futures.items()}


def llm_vote(code: str, seed: int) -> str:
    """投票：对同一问题多次判断，模拟不同实例的分歧。"""
    verdicts = ["no", "yes", "no"]                     # 第二个实例发现了漏洞
    return verdicts[seed % len(verdicts)]


def vote_is_safe(code: str, n: int = 3) -> str:
    with ThreadPoolExecutor(max_workers=n) as pool:
        votes = [f.result() for f in [pool.submit(llm_vote, code, i) for i in range(n)]]
    return "unsafe" if "yes" in votes else "safe"      # 保守聚合：一票否决


def main() -> None:
    sect = analyze_review("发货太慢了，不过客服态度不错。")
    print("分段结果:", sect)
    print("投票判定:", vote_is_safe("eval(user_input)"))


if __name__ == "__main__":
    main()
```
保存为 `demo03_parallelization.py`，运行 `python demo03_parallelization.py`。预期输出：
```text
分段结果: {'summary': '用户抱怨发货慢但客服态度好。', 'sentiment': '中性偏负', 'keywords': '发货, 慢, 客服'}
投票判定: unsafe
```
分段部分：三个子任务用线程池同时提交，因互不依赖，总耗时从「三次相加」压到「约一次」，最后汇总成一个字典。投票部分：对同一段代码跑 3 次，`return "unsafe" if "yes" in votes` 用的是**保守聚合（一票否决）**——安全审查宁可误报不可漏报，只要一票说有漏洞就升级人工。换成「多数表决」只需把聚合逻辑改成 `votes.count("yes") > n // 2`，这体现了投票的灵活性：**聚合策略由场景的误报/漏报代价决定**。

## 聚合策略：投票的灵魂在「怎么合票」

投票的价值不只在「跑多遍」，更在「怎么把多个结果合成一个决定」。三种常见聚合策略对应不同的代价权衡：
```text
一票否决（保守）：任一实例报警即升级 —— 用于安全审查，漏报代价极高
多数表决（均衡）：过半即采纳       —— 用于一般判断，平衡误报与漏报
全票通过（激进）：全部同意才放行   —— 用于放行高风险动作，宁可卡住也不放错
```
Anthropic 特别指出投票可以「用不同的投票阈值来平衡误报与漏报」[来源](https://www.anthropic.com/engineering/building-effective-agents)。这意味着阈值不是拍脑袋，而应由业务代价决定：审查违规内容漏一条的代价远高于误拦一条，就该用一票否决；而放行一笔高价值转账，则可能需要全票通过。

## 真实系统对应

**官方公开机制**：Anthropic 文档给出分段的护栏例子（一个实例出主答、另一个实例审查）和投票的代码审查例子（多提示查漏洞，任一发现即标记），并明确投票可调阈值平衡误报漏报 [来源](https://www.anthropic.com/engineering/building-effective-agents)。LangGraph 官方文档的 `Parallelization` 小节用 `START` 同时连到三个节点（生成笑话/故事/诗），再汇入 `aggregator` 节点，正是分段的图实现 [来源](https://docs.langchain.com/oss/python/langgraph/workflows-agents)。

**通用工程模式**：「独立子任务并发以降延迟」和「同任务多实例以换可靠」是与厂商无关的经典做法；线程池适合 I/O 密集的模型调用，CPU 密集才需进程池。

**教学参考实现**：本页用确定性替身固定了分段结果与投票分歧，只为可复现；真实系统的投票需要处理实例间真实随机性、成本翻倍与延迟取决于最慢实例等问题。

## 生产踩坑

| 症状 | 根因 | 如何观测与复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| 本可并行的步骤排成串行，延迟高 | 误把独立任务当有依赖 | 画任务依赖图；标出无依赖边 | 无依赖的子任务改为分段并行 | 真有先后依赖时必须串行 |
| 并行任务写同一份状态出现竞态 | 并行写共享状态 | 高并发下结果不确定、偶发脏数据 | 各分支只读或写各自分片，最后合并 | 无共享写时无此问题 |
| 投票成本翻倍却没更准 | 对稳定任务滥用投票 | 对比单次与多次判断的一致率 | 只对不稳定的高风险判断用投票 | 判断本就稳定时不必投票 |
| 投票聚合策略选错 | 未按误报/漏报代价定阈值 | 分别统计误报率与漏报率 | 安全用一票否决，一般用多数表决 | 无明显代价差异时可简化 |
| 并行延迟由最慢实例决定 | 无超时，个别慢实例拖垮整体 | 记录各实例耗时分布 | 设单实例超时 + 降级默认值 | 必须等齐所有结果的场景 |
| 分段结果拼装时字段冲突 | 各子任务输出结构不统一 | 检查汇总字典键是否碰撞 | 约定各子任务输出 schema | 单一输出无需拼装 |

## 思考：并行化的「分段」和「投票」目的有何不同？各举一例。

### 回答

两者结构相似（都是分叉并行再聚合），但目的相反。**分段（Sectioning）**是把一件大任务切成**若干不同的小任务**并行做，目的是**加速 + 关注点分离**；例子：对同一段评论同时做「摘要 / 情感分析 / 关键词提取」，三件不同的事互不依赖，并行后总耗时约等于单次。**投票（Voting）**是对**同一件事**做很多遍再综合，目的是**提高可靠性 / 覆盖多样性**；例子：让三个实例独立判断「这段代码有没有安全漏洞」，用一票否决聚合——只要一次说有就升级人工。判断口诀：分段问「能不能拆成不同的事同时做」，投票问「要不要把同一件事做多遍换可靠」。

### 面试精简表达

分段=切成不同子任务并行（为快+分工，如评论多角度分析）；投票=同任务跑多遍再合票（为准+全，如多实例查漏洞一票否决）。

### 反例

把「先审查再生成」做成提示链是常见反例：审查和生成其实互相独立，本应分段并行（同时跑，审查不过就丢弃生成结果），却被排成串行，白白多等一轮延迟。识别「哪些步骤其实可以并行」是优化 Agent 延迟的重要手段。

## 事故回放：一次「并行写库」引发的脏数据

某团队做用户画像，用分段并行同时跑「兴趣标签」「消费等级」「活跃度」三个子任务，本意是提速。问题出在三个子任务都往同一条 `user_profile` 记录里写字段，且用了「读取整条记录→改一个字段→写回整条」的模式。高并发下三个线程读到的是同一份旧记录，各改各的字段后依次写回，后写的覆盖了先写的——最终只有一个子任务的结果留存，另两个被静默丢弃。测试环境并发低没复现，线上高并发才暴露，表现为「画像字段偶尔莫名为空」。

根因是违反了并行化的铁律：**并行写共享状态是设计异味，会产生竞态。** 修复是让三个子任务各自返回自己的分片（只算不写），由汇总步骤在所有分支结束后统一合并成一条记录再写库。这与提示链「步骤间加 gate」是不同的教训：提示链管的是「顺序与止损」，并行化管的是「独立与合并」。判断能不能并行的口诀始终是——**能不能打乱顺序同时做且不互相踩踏？能，才可并行。**

## 优化前后对比

| 维度 | 优化前 | 优化后 | 验证方式 |
|---|---|---|---|
| 独立步骤 | 串行执行，延迟叠加 | 分段并行，总耗时≈单次 | 压测端到端 P95 |
| 共享状态 | 并行读改写同一记录 | 各算分片，末尾统一合并 | 高并发注入复现竞态 |
| 高风险判断 | 单次判断偶发漏判 | 多实例投票 + 一票否决 | 统计漏报率下降 |
| 聚合策略 | 拍脑袋定 | 按误报/漏报代价选阈值 | 分别度量误报与漏报 |
| 慢实例 | 无超时拖垮整体 | 单实例超时 + 降级 | 记录实例耗时分布 |

并行化的正确心法是分清两条独立的判断线：**要不要并行**看子任务是否独立（分段）；**要不要冗余**看单次判断是否够稳、以及漏报代价有多高（投票）。两者可以叠加使用，但都要为「共享状态」和「最慢实例」这两个隐形成本买单。
