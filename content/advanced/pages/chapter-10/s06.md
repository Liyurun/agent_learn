## 真实问题

前五页各讲一种模式，但面试与真实工程里最考验人的是**横向对比**：五种模式的代码「形状」到底差在哪？为什么说提示链是「一条线」、路由是「一个岔路口」、并行化是「一次分叉汇合」、编排者-工作者是「运行时才知道几条分叉」、评估-优化是「一个带出口的回环」？

一位候选人能背出五种模式的定义，却在白板上写不出它们的骨架，也说不清「同样是分叉，并行化和编排者-工作者的分叉数量为什么一个固定一个不定」。本页用**同一套确定性框架**把五种模式各实现一遍，并打印每种模式的**调用次数**与**调用轨迹**，让差异一眼可见。全部纯 Python、无需 API Key、输出可复现——你可以直接抄到白板上或本地跑。

## 设计：唯一的模型入口 + 可观测的调用轨迹

统一约定只有两条：其一，所有模式都通过同一个 `MockProvider.call(role, prompt)` 访问「模型」，用确定性规则替代真实 LLM（Large Language Model，大语言模型），保证结果可复现；其二，每次调用都追加到 `trace` 列表，于是每种模式跑完就能打印它的调用形状。这样「五种模式的区别」被降维成一个可观测指标——**调用次数与调用序列的形状**。
```text
统一入口：provider.call(role, prompt)  # role ∈ {planner, classifier, evaluator, generator, section, voter, worker}
可观测量：len(trace)（调用次数）+ trace（调用序列）

预期的调用形状：
提示链        线性：worker → worker → worker            （3 次，一条线）
路由          岔路：classifier → 某个 worker            （2 次，选一条）
并行化        分叉汇合：3×section + 3×voter             （6 次，分叉再合）
编排者-工作者  1×planner + N×worker（N 运行时定）        （1+N 次，分叉数不定）
评估-优化      回环：generator↔evaluator 交替直到 PASS   （交替，带出口）
```
## 完整可运行代码
```python
"""五种 Agentic 工作流模式最小骨架统一实现 + 运行轨迹（纯 Python，无需 API Key）。"""
from __future__ import annotations

from concurrent.futures import ThreadPoolExecutor
from dataclasses import dataclass, field


@dataclass
class MockProvider:
    """确定性模型替身：记录每一次调用，按角色+关键词返回稳定文本。"""

    trace: list[str] = field(default_factory=list)

    def call(self, role: str, prompt: str) -> str:
        self.trace.append(f"{role}<-{prompt[:24]}")
        if role == "planner":
            return "checkout.py|coupon.py|tax.py"
        if role == "classifier":
            if "退款" in prompt:
                return "refund"
            if "报错" in prompt or "超时" in prompt:
                return "technical"
            return "general"
        if role == "evaluator":
            return "PASS" if "connection pool" in prompt else "REVISE:补全术语 connection pool"
        if role == "generator":
            return ("connection pool timeout" if "REVISE" in prompt
                    else "pool timeout")
        if role == "section":
            head = prompt.split("::", 1)[0]
            return {"summary": "发货慢但客服好", "sentiment": "中性偏负",
                    "keywords": "发货,慢,客服"}.get(head, "?")
        if role == "voter":
            return prompt.rsplit("#", 1)[-1]           # 用编号模拟不同实例的分歧
        if role == "worker":
            kind = prompt.split("::", 1)[0]
            return {"大纲": "1.根因 2.定位 3.修复",
                    "正文": "连接池超时源于并发、慢查询与泄漏",
                    "翻译": "pool timeout: concurrency/slow-query/leak",
                    "handle": "已受理", "改": "已修改"}.get(kind, "done")
        return "(worker done:" + prompt[:12] + ")"


def prompt_chaining(p: MockProvider, topic: str) -> str:
    outline = p.call("worker", f"大纲::{topic}")
    if len(outline) < 3:                               # gate
        return "rejected"
    draft = p.call("worker", f"正文::{outline}")
    return p.call("worker", f"翻译::{draft}")


def routing(p: MockProvider, msg: str) -> str:
    category = p.call("classifier", msg)
    return f"{category}:" + p.call("worker", f"handle::{category}")


def parallelization(p: MockProvider, review: str) -> dict:
    kinds = ["summary", "sentiment", "keywords"]
    with ThreadPoolExecutor(max_workers=3) as pool:
        sec = {k: pool.submit(p.call, "section", f"{k}::{review}") for k in kinds}
        sectioning = {k: f.result() for k, f in sec.items()}
    with ThreadPoolExecutor(max_workers=3) as pool:
        votes = [f.result() for f in
                 [pool.submit(p.call, "voter", f"code#{v}") for v in ["no", "yes", "no"]]]
    return {"sectioning": sectioning, "vote": "unsafe" if "yes" in votes else "safe"}


def orchestrator_workers(p: MockProvider, task: str) -> str:
    plan = p.call("planner", task).split("|")          # 运行时动态分解
    outs = [p.call("worker", f"改::{f}") for f in plan]
    return f"综合 {len(outs)} 个 worker 结果"


def evaluator_optimizer(p: MockProvider, task: str, max_rounds: int = 4) -> str:
    draft = p.call("generator", task)
    for i in range(1, max_rounds + 1):
        verdict = p.call("evaluator", draft)
        if verdict == "PASS":
            return f"passed@round{i}:{draft}"
        draft = p.call("generator", verdict)           # 反馈回流
    return f"max_rounds:{draft}"


def main() -> None:
    for name, fn in [
        ("prompt_chaining", lambda p: prompt_chaining(p, "连接池超时")),
        ("routing", lambda p: routing(p, "登录报错超时")),
        ("parallelization", lambda p: parallelization(p, "发货慢")),
        ("orchestrator_workers", lambda p: orchestrator_workers(p, "修复结算")),
        ("evaluator_optimizer", lambda p: evaluator_optimizer(p, "翻译说明")),
    ]:
        p = MockProvider()
        out = fn(p)
        print(f"[{name}] 调用次数={len(p.trace)} 结果={out}")
        print(f"    轨迹={p.trace}")


if __name__ == "__main__":
    main()
```
保存为 `workflow_patterns.py`，运行 `python workflow_patterns.py`。

## 运行轨迹与逐行解读

实际运行输出如下（可复现）：
```text
[prompt_chaining] 调用次数=3 结果=pool timeout: concurrency/slow-query/leak
    轨迹=['worker<-大纲::连接池超时', 'worker<-正文::1.根因 2.定位 3.修复', 'worker<-翻译::连接池超时源于并发、慢查询与泄漏']
[routing] 调用次数=2 结果=technical:已受理
    轨迹=['classifier<-登录报错超时', 'worker<-handle::technical']
[parallelization] 调用次数=6 结果={'sectioning': {'summary': '发货慢但客服好', 'sentiment': '中性偏负', 'keywords': '发货,慢,客服'}, 'vote': 'unsafe'}
    轨迹=['section<-summary::发货慢', 'section<-sentiment::发货慢', 'section<-keywords::发货慢', 'voter<-code#no', 'voter<-code#yes', 'voter<-code#no']
[orchestrator_workers] 调用次数=4 结果=综合 3 个 worker 结果
    轨迹=['planner<-修复结算', 'worker<-改::checkout.py', 'worker<-改::coupon.py', 'worker<-改::tax.py']
[evaluator_optimizer] 调用次数=4 结果=passed@round2:connection pool timeout
    轨迹=['generator<-翻译说明', 'evaluator<-pool timeout', 'generator<-REVISE:补全术语 connection p', 'evaluator<-connection pool timeout']
```
逐条读懂这五行轨迹，就等于读懂了五种模式的本质区别：

- **提示链（3 次，线性）**：`worker → worker → worker`，每次的输入是上一次的输出（第二次的 `正文::` 里带着第一次产出的大纲），是一条不分叉的直线。gate 在这里体现为 `if len(outline) < 3: return "rejected"`——大纲太短就不会有后两次调用。
- **路由（2 次，选一条）**：先 `classifier` 判出 `technical`，再只调用**一个** worker。注意它只走了三条分支里的一条，其余分支的处理器根本没被调用——这就是「关注点分离」的代价与收益。
- **并行化（6 次，分叉再汇合）**：前三次是 `section` 的三个**不同**子任务（分段），后三次是 `voter` 的三个**相同**判断（投票，一票 `yes` 触发 `unsafe`）。同样是「多次调用」，分段是横向拼装、投票是纵向合票。
- **编排者-工作者（1+3 次，分叉数运行时定）**：先 1 次 `planner` 动态返回 `checkout.py|coupon.py|tax.py`，再按这个**运行时**结果派 3 个 worker。把任务换成别的，`planner` 返回不同长度的列表，worker 数量随之变化——这正是它与并行化「6 次固定」的分水岭。
- **评估-优化（4 次，回环带出口）**：`generator → evaluator → generator → evaluator`，第 1 轮初稿缺术语被 REVISE，第 2 轮补上后 evaluator 返回 PASS，`passed@round2` 说明它在第 2 轮自然终止，没有走到 `max_rounds=4` 的兜底出口。

## 把三件套跑起来：保存、运行、核对

这份代码就是一份可交付的「三件套」示例：
```text
1) 保存：把上面的完整代码存为 workflow_patterns.py
2) 运行：python workflow_patterns.py（Python 3.8+，无需联网、无需 API Key）
3) 核对：五行输出的「调用次数」应分别为 3 / 2 / 6 / 4 / 4；
        parallelization 的 vote 应为 unsafe（一票否决）；
        evaluator_optimizer 应为 passed@round2（第 2 轮达标）。
```
若你把 `MockProvider.call` 换成真实模型调用（例如接入 Anthropic 或 OpenAI 的 API，Application Programming Interface，应用程序编程接口），五个函数的**结构完全不用改**——变的只是 `call` 内部从「查表」变成「发请求」。这印证了 Anthropic 的核心建议：这些模式可以直接用 LLM API 几行代码实现，不必依赖复杂框架 [来源](https://www.anthropic.com/engineering/building-effective-agents)。

## 真实系统对应

**官方公开机制**：Anthropic 明确建议开发者「先直接用 LLM API，很多模式几行代码就能实现」，并提供 Cookbook 示例实现供参考 [来源](https://platform.claude.com/cookbook/patterns-agents-basic-workflows)。本页「一个统一入口 + 五种编排」正是这一建议的最小化落地。LangGraph 官方文档同样把五种模式用同一套 `StateGraph`/`entrypoint` 原语实现，区别只在节点如何连边 [来源](https://docs.langchain.com/oss/python/langgraph/workflows-agents)。

**通用工程模式**：「把模型访问收敛到唯一入口 + 全程记录调用轨迹」是可迁移的可观测性做法；无论用哪个框架，能打印「谁在什么时候调用了模型、输入是什么」都是调试 Agent 的第一手段。

**教学参考实现**：`MockProvider` 的查表逻辑纯为可复现，不代表任何真实模型行为；真实系统的调用次数会因模型随机性、重试、并发而波动，`trace` 也应携带耗时、Token 用量、请求 ID 等字段。

## 生产踩坑

| 症状 | 根因 | 如何观测与复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| 换真实模型后结构大改 | 模型访问散落各处，无统一入口 | 搜索代码里直接发请求的位置 | 收敛到唯一 provider.call 入口 | 单次脚本可不抽象 |
| 线上无法复盘调用序列 | 未记录调用轨迹 | 检查是否有 trace/日志 | 每次调用记录 role/输入/耗时/Token | 一次性实验可省 |
| 并行分支异常被吞 | future 未取异常 | 制造一个分支抛错观察 | 对每个 future 显式取结果并捕获 | 无并行时不涉及 |
| 组合模式后调用次数失控 | 模式嵌套无预算 | 统计端到端调用次数分布 | 给整体设调用/Token 预算上限 | 单模式且分支少时风险低 |
| Mock 与真实行为差异被忽视 | 把教学替身当真实基准 | 对比 Mock 与真实调用的分布 | 明确标注 Mock 仅为可复现 | 纯教学演示可接受 |

## 思考：为什么用「调用轨迹」而不是「定义」来区分五种模式更靠谱？

### 回答

因为定义容易背、容易混，而调用轨迹是**可观测、可验证、不会骗人**的事实。同样一句「多次调用模型」，并行化和编排者-工作者听起来都符合，但看轨迹立刻分清：并行化是「开发者写死的固定分叉」（本例恒为 6 次），编排者-工作者是「先一次 planner 再按其运行时结果派 N 个 worker」（换个任务次数就变）。同样一句「分叉并行」，分段和投票听起来一样，但轨迹显示分段是三个**不同角色/子任务**、投票是三个**相同角色**。工程上，能打印「谁在何时用什么输入调用了模型」是调试 Agent 的第一手段——出问题时，先看轨迹里「该调用的没调用」还是「不该调用的调用了」，比空想定义高效得多。

### 面试精简表达

定义会混，轨迹不会：看「调用次数是否固定、是不是先规划再派工、分叉的角色相同还是不同」，三个问题就能把五种模式区分开，还顺带给了可观测的调试抓手。

## 从可复现 Mock 到真实系统的迁移清单

本页的 Mock 版本适合讲清结构，但要上生产还需补齐五件事，每一件都对应前面某页的踩坑表：

- **把 `call` 换成真实模型调用**，但保持唯一入口，方便统一加重试、超时、限流。
- **给 `trace` 加真实字段**：耗时、输入/输出 Token 数、请求 ID，才能做成本与延迟分析。
- **对并行分支显式取异常**：`future.result()` 要包在 try 里，避免一个分支静默失败拖垮汇总。
- **给组合模式设总预算**：模式嵌套（如路由里套提示链、其中一步并行）会让调用次数相乘，必须有端到端的调用/Token 上限。
- **区分 Mock 与真实基准**：Mock 的调用次数是确定的，真实系统会因随机性、重试而波动，不能把 Mock 数字当性能承诺。

这套骨架的价值不在代码本身，而在它把「五种抽象模式」压成了「五种可运行、可观测、可对比的调用形状」。掌握它，你既能在白板上手写任意一种，也能在真实系统里通过看轨迹快速判断「这段编排到底是哪种模式、哪里出了问题」。
