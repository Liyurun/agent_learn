## 真实问题

回到本章开头那个「越改越错」的代码修复 Agent：它 40 分钟提交 11 个版本，根源之一是它拿到的反馈只有一句 `AssertionError`。这句反馈**能证明「失败了」，但不能告诉它「哪里失败、为什么失败、往哪改」**。于是它只能瞎猜。

对比一下，如果 CI（Continuous Integration，持续集成）返回的是这样一条反馈：
```text
FAILED test_digit_sum::solve(99)
  期望: 18
  实际: 9
  失败断言在第 3 行: assert solve(99) == 18
```
Agent 立刻就能定位：「99 应该得 18，我却算出 9——我只取了个位数。」这条反馈是**可定位、可操作**的。同一个模型、同一个反思机制，喂给它一句 `AssertionError` 和喂给它这条结构化反馈，改错效率天差地别。

这就引出本章最重要的一句话：**反思的质量天花板，由反馈信号的质量决定。反思是上层建筑，反馈信号是地基。** 本节回答一个工程问题：反馈信号到底从哪来，各种来源可靠到什么程度。

## 原理：四类评价信号，可靠度递增

Agent 的评价信号大致有四类来源，可靠度和适用面各不相同：
```text
① 模型自评（LLM 自己判断"我写得对吗"）
   可靠度：最低。生成时的盲区在评估时依然存在（一起瞎）。
   适用：表面可判断的质量（风格、格式、明显缺项）。

② 外部工具校验（用工具交叉验证）
   可靠度：较高。搜索引擎查事实、代码解释器跑代码、计算器验算术。
   适用：能被工具客观验证的方面（事实、可执行性、数值）。

③ 单元测试 / 可执行判分（有明确对错的自动判分）
   可靠度：高。测试通过与否是二元、客观、可复现的。
   适用：代码、算术、结构化输出等"有标准答案"的任务。

④ 人类反馈（人来评判或给偏好）
   可靠度：高但昂贵、慢、不可实时。
   适用：主观质量、价值对齐、高风险决策的最终把关。
```
一个核心判断原则：**能用客观信号就别用主观自评。** 能跑测试就跑测试，能查事实就查事实，能验算就验算。只有在拿不到客观信号时（比如「这段文案够不够吸引人」），才退而依赖模型自评，且要清楚它的局限。

CRITIC 论文（arXiv:2305.11738）正是这个思路的代表：它让 LLM 像人类一样借助外部工具（搜索引擎查事实、代码解释器调试代码）来交叉验证并逐步修正自己的输出，而不是纯靠模型「黑箱」自我判断 [来源](https://arxiv.org/abs/2305.11738)。它的动机很直白——人类修改初稿时也会用搜索引擎核实、用调试器排错，而不是闭着眼睛改。

## 现象与输入：好信号 vs 坏信号

同一个失败，反馈信号的好坏决定了反思能不能落地：
```text
好的反馈信号                         坏的反馈信号
────────────────────                 ────────────────────
"文件不存在: /data/report.txt"        "操作失败"（不知为何失败）
"第3行语法错误: 缺少冒号"              "代码有问题"（不知哪里、什么问题）
"测试 solve(99): 期望18 实际9"         "结果不对"（无从下手）
"搜索结果: 最新稳定版是 2.4.1"         "查一下"（没有实际结果）
        ↓                                    ↓
反思能精准定位、有效改进              反思只能瞎猜，甚至越改越错
```
好信号的三个特征：**可定位**（指出哪里）、**可操作**（暗示怎么改）、**客观可复现**（不依赖评判者主观）。这解释了为什么第 6 章反复强调「工具失败要返回结构化错误」——那正是为反思提供好信号的地基工程。

## 最小可运行演示

下面这段代码把「模型自评」和「单元测试判分」两种信号放在一起对比：对一个算术任务，自评可能给出「虚假自信」，而单元测试给出客观真相。完全可运行、不依赖模型或网络：
```python
def unit_test_signal(func, cases):
    """③ 单元测试信号：客观、可定位、可复现。"""
    failures = []
    for args, expected in cases:
        got = func(*args)
        if got != expected:
            failures.append(f"输入{args}: 期望{expected} 实际{got}")
    return (len(failures) == 0), failures


def self_eval_signal(func, cases):
    """① 模型自评信号（模拟）：这里模拟一个"过度自信"的自评——
    它只看'函数能跑不报错'就说'看起来对'，不做真值比对。"""
    try:
        for args, _ in cases:
            func(*args)          # 只要不抛异常就"觉得对"
        return True, "自评：代码能运行，看起来是对的"
    except Exception as e:
        return False, f"自评：运行报错 {e}"


def buggy_digit_sum(n):
    return n % 10                # bug：只取个位


if __name__ == "__main__":
    cases = [((7,), 7), ((99,), 18), ((123,), 6)]
    ok1, msg1 = self_eval_signal(buggy_digit_sum, cases)
    ok2, fails = unit_test_signal(buggy_digit_sum, cases)
    print(f"模型自评 -> 通过={ok1}; {msg1}")
    print(f"单元测试 -> 通过={ok2}; 失败明细={fails}")
```
保存为 `signal_compare.py`，运行 `python signal_compare.py`，预期输出：
```text
模型自评 -> 通过=True; 自评：代码能运行，看起来是对的
单元测试 -> 通过=False; 失败明细=['输入(99,): 期望18 实际9', '输入(123,): 期望6 实际3']
```
对比刺眼：这段有 bug 的代码「能运行不报错」，于是自评信号给出「看起来对」的**虚假自信**；而单元测试信号直接给出「99 期望 18 实际 9」的客观失败明细。如果 Agent 信了自评，就会把 bug 当成正确交卷；只有单元测试信号才能触发有效反思。这就是「能用客观信号就别用自评」的实证。

真实的模型自评当然比这个 `try/except` 复杂，但**它的根本局限一样**：生成代码时没想到「多位数」的模型，评估时通常也想不到。盲区在生成和评估时同时存在。

## 深入：为什么「自评」会一起瞎，以及怎么缓解

「同一个模型自评」为什么不可靠？机制根源在于**盲区的同源性**：
```text
自评（同一模型生成 + 评估）：
    生成时的"思路惯性"会带进评估——
    模型倾向于认为自己写的是对的，
    生成时没考虑到的情况，评估时同样考虑不到（盲区同源，一起瞎）。

缓解手段（按有效性递增）：
    a. 换视角：给评估者一套不同的 prompt 人设（"挑刺者"）、明确的 rubric。
    b. 换角色：用独立的评估者（另一次调用/另一个模型），打破单一视角。
    c. 换信号：直接引入外部客观信号（工具/测试/真值），绕开"模型判断"。
```
三种缓解手段有效性递增：换视角是「同一个人换个角度看」，聊胜于无；换角色是「找另一个人 code review」，能发现一部分盲区；换信号是「直接跑测试」，最彻底——因为它把「对错判断」从模型手里拿走，交给客观事实。

这解释了三篇论文的递进关系：Self-Refine 用「换视角/换角色」在表面可判断任务上自我精炼 [来源](https://arxiv.org/abs/2303.17651)；CRITIC 用「换信号」（外部工具）处理需要客观验证的任务 [来源](https://arxiv.org/abs/2305.11738)；DeepMind 则给出反证——在纯推理任务上、没有外部信号时，光靠自评（哪怕换视角）自我纠正往往无效甚至有害 [来源](https://arxiv.org/abs/2310.01798)。三者拼起来就是一句话：**信号越客观，反思越可信；纯自评的边界很窄。**

## 人类反馈：最贵但最终的信号

第四类信号——人类反馈——值得单独说。它是训练与运行两个层面的「终审」：

- **训练层面**：RLHF（Reinforcement Learning from Human Feedback，基于人类反馈的强化学习）用人类对模型输出的偏好排序训练奖励模型，再用强化学习优化模型，代表工作是 InstructGPT [来源](https://arxiv.org/abs/2203.02155)。这是把「人类偏好」这个信号固化进模型权重的过程，塑造了模型的底层倾向。
- **运行层面**：在具体任务里，人类可以充当最终评估者（比如高风险决策的人工审批），或提供即时反馈（点赞/点踩、修改建议）。

人类反馈的特点是**可靠度高但代价高、速度慢、无法实时大规模**。所以工程上的典型做法是「分层」：绝大多数评价用自动信号（测试、工具）快速完成，只把少数高风险、主观或有争议的决策上升到人类反馈。把人类反馈用在刀刃上，而不是每一步都等人。

要区分清楚：RLHF 是**训练阶段改权重**的方法，本章其余部分（Reflexion / Self-Refine / CRITIC）是**推理阶段不改权重**的方法。面试里把 RLHF 说成「一种反思机制」是概念错误——它是用人类信号塑造模型，不是运行时的自我审视循环。

## 真实系统对应

**官方公开机制**：CRITIC 论文公开了「用外部工具（搜索、代码解释器）交叉验证并修正输出」的框架与实验 [来源](https://arxiv.org/abs/2305.11738)；InstructGPT 论文公开了 RLHF 的三步流程（监督微调 → 训练奖励模型 → 强化学习优化）[来源](https://arxiv.org/abs/2203.02155)；Anthropic 的 Evaluator-Optimizer 模式描述了「独立评估者给反馈」的工作流 [来源](https://www.anthropic.com/engineering/building-effective-agents)。**通用工程模式**：按「客观 > 自评」的优先级选择评价信号，并把人类反馈分层用在高风险处。**教学参考实现**：上面的 `self_eval_signal` 用 `try/except` 模拟「过度自信」，是为了直观演示盲区，不代表真实模型自评的实现方式。

边界声明：不能说「用了工具反馈就一定对」——工具本身也可能返回过期或错误结果（比如查到过期镜像站，见第 02 节）。信号可靠度是相对的：客观信号通常比自评可靠，但仍需校验工具输出本身是否可信。

## 生产踩坑

| 症状 | 根因 | 如何观测与复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| 模型自评「虚假自信」把错的判成对 | 生成与评估盲区同源 | 对比自评结论与客观真值的一致率 | 优先用测试/工具等客观信号，自评仅作辅助 | 纯主观质量（文案美感）只能靠人评 |
| 有测试却仍靠模型自评 | 没把可执行判分接进反思循环 | 检查反思的输入是不是测试结果 | 把单元测试/工具输出作为反思的反馈源 | 无法编写测试的任务除外 |
| 工具返回了错的反馈，反思跟着错 | 默认信任工具输出，未校验来源 | 记录工具返回与真值的偏差 | 校验工具结果来源/时效，多源交叉 | 权威且实时的工具可降低校验频率 |
| 每步都等人工反馈拖慢全流程 | 没有把人类反馈分层 | 统计人工介入次数与平均等待时长 | 自动信号兜底，人工只审高风险 | 强合规场景可能要求逐步人工 |
| 把 RLHF 当成「运行时反思」 | 混淆训练阶段与推理阶段 | 审查设计文档中的概念表述 | 明确区分「改权重训练」与「不改权重推理」 | 无 |

## 思考：为什么说「反馈信号是反思的地基」？

### 回答

因为反思是「基于反馈做改进」的过程，它本身不产生真相，只加工反馈。如果反馈是错的、模糊的或干脆没有，反思加工出来的结论必然不可靠——垃圾进，垃圾出。反馈准确且可定位，反思才能精准纠错；反馈是一句「操作失败」，反思只能瞎猜；反馈是错的，反思会「自信地改错」。所以当你发现 Agent「越反思越糊涂」，第一个要排查的不是反思逻辑，而是它拿到的反馈到底准不准、够不够具体。

这也是本章和第 6 章的呼应点：第 6 章要求「工具失败返回结构化错误」，本质就是在为反思打地基。地基不牢，反思盖得越高塌得越惨。

### 面试精简表达

反思只加工反馈、不产生真相。反馈是地基，反思是上层建筑。Agent 越反思越错时，先查反馈信号准不准，而不是先改反思逻辑。

## 思考：什么时候该用外部工具信号，什么时候模型自评就够？

### 回答

看**错误是否「表面可判断」**。如果错误藏在深层推理里（一道模型本来就不会做的数学题），模型自评会和自生成犯同一个错，必须引入外部客观信号（求解器、单元测试、真值比对）——这正是 CRITIC 的思路 [来源](https://arxiv.org/abs/2305.11738)。如果错误是表面可判断的（缺字段、不合格式、太口语），模型自评通常够用，因为「缺什么」一眼能看出来，不需要深层推理。

一个实操判据：**问自己「这个对错，能不能写成一个自动化检查？」** 能（跑测试、查事实、验格式）就优先用那个客观检查当信号；不能（美感、说服力）才退回模型自评或人类评判。越靠近「能自动检查」，越该用客观信号。

### 反例

不要走极端认为「工具信号永远对」。工具也会返回过期、错误或不完整的结果（第 02 节的过期镜像站就是例子）。客观信号更可靠是统计意义上的，具体使用时仍要校验工具输出本身——尤其是外部检索类工具。
