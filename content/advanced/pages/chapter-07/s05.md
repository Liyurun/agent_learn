## 真实问题

前面几节的代码都为讲清单个机制而做了简化。本节要回答一个更工程的问题：**把「生成候选代码 → 用单元测试自动判分 → 把失败用例转成语言反思 → 带着反思生成改进版」这一整套端到端拼起来，到底长什么样？** 而且要满足两个硬约束：完全可运行、不需要任何 API Key（Application Programming Interface Key，接口密钥）；评价信号必须客观（用真实运行的单元测试判分，而不是模型拍脑袋）。

我们用本章贯穿数据里的「数字和（digit sum）」任务：实现 `solve(n)` 返回整数各位数字之和。这个任务的好处是——它有**可自动判分的评价信号**（一组单元测试），错误是**可定位的**（哪个用例期望什么、实际什么），修订效果是**客观可验证的**（测试全过就是真过）。这正是第 04 节强调的「能用客观信号就别用自评」的落地。

为了让代码在无模型环境下也能真实运行，我们把「LLM 生成候选代码」这一步用一个**确定性的候选序列**替代（模拟模型在反思驱动下逐步逼近正确解）。但判分、反思生成、终止控制这些**机制部分都是真实的、可迁移到接真实模型的版本**——把 `propose_candidate` 换成一次真实的模型调用即可。

## 原理：五个部件如何拼成闭环

端到端反思循环由五个部件组成，缺一不可：
```text
① 任务与测试（评价信号的载体）
   solve(n) 的规格 + 一组 (输入, 期望) 单元测试。

② 判分器（Evaluator）
   把候选源码 exec 出来，逐用例运行，返回"哪些用例失败、期望/实际"。
   —— 这是客观信号，不是模型自评。

③ 反思器（Self-Reflection）
   把失败用例转成一句可定位、可操作的语言反思。

④ 生成器（Actor/Generator）
   读入"任务 + 历史反思"，产出下一版候选代码。
   （本节用确定性序列模拟；接真实模型时替换为一次 LLM 调用）

⑤ 控制器（终止 + 防打转）
   组合三重终止（达标/硬上限/改进停滞）与"重复失败检测"。
```
这五个部件恰好对应前面各节：② 是第 04 节的客观信号，③ 是第 02 节的语言化反馈，④⑤ 融合了第 02/03 节的记忆与终止。本节把它们缝成一个能真正跑起来、能自动判分的工程。

## 最小可运行演示（完整工程）

下面是完整、可直接运行的实现。它会打印每一轮的候选源码摘要、失败用例、生成的语言反思，直到测试全过或触发终止：
```python
"""反思循环实战：生成-判分-反思-修订，用单元测试做客观评价信号。
纯 Python，无需 API Key、无需网络。接真实模型时只需替换 propose_candidate。

部件①任务与测试 TESTS：可自动判分的评价信号。
部件④候选序列 CANDIDATES：模拟模型在反思驱动下逐步逼近正确解——
    第 1 版误用 max（2 个用例失败）；第 2 版只取个位（反而更差，3 个失败）；
    第 3 版正确遍历每位（全过）。"""

TESTS = [((7,), 7), ((10,), 1), ((99,), 18), ((123,), 6), ((0,), 0)]

CANDIDATES = [
    "def solve(n):\n    return max(int(c) for c in str(n))\n",
    "def solve(n):\n    return n % 10\n",
    "def solve(n):\n    total = 0\n    for c in str(n):\n        total += int(c)\n    return total\n",
]


def evaluate(source_code, tests):
    """② 判分器：exec 候选源码并逐用例判分，返回失败明细列表。"""
    namespace = {}
    try:
        exec(source_code, namespace)
    except Exception as exc:                       # 语法/运行期错误也是一种反馈
        return [("EXEC_ERROR", str(exc), None)]
    solve = namespace.get("solve")
    if solve is None:
        return [("NO_FUNC", "未定义 solve", None)]
    failures = []
    for args, expected in tests:
        try:
            got = solve(*args)
        except Exception as exc:
            got = f"异常:{exc}"
        if got != expected:
            failures.append((args, expected, got))
    return failures


def reflect(failures):
    """③ 反思器：把失败用例转成一句可定位、可操作的语言反思。"""
    if not failures:
        return "全部用例通过，无需反思"
    # 取第一个失败用例做诊断（真实场景可综合多个）
    args, expected, got = failures[0]
    if args in ("EXEC_ERROR", "NO_FUNC"):
        return f"代码无法运行（{expected}），先保证能定义并执行 solve"
    # 基于"期望 vs 实际"给出方向性诊断
    if isinstance(got, int) and isinstance(expected, int) and got < expected:
        return (f"输入 {args} 期望 {expected} 实际 {got}：结果偏小，"
                f"可能只累加了部分数位，应遍历每一位相加")
    return f"输入 {args} 期望 {expected} 实际 {got}：逻辑与规格不符，需修订"


def propose_candidate(round_idx, memory):
    """④ 生成器：读入历史反思，产出下一版候选。
    本节用确定性序列模拟；接真实模型时改为一次 LLM 调用，
    把 memory（历史反思）拼进提示即可。"""
    idx = min(round_idx, len(CANDIDATES) - 1)
    return CANDIDATES[idx]


def run_reflection_loop(max_rounds=5):
    """⑤ 控制器：三重终止 + 重复失败检测，串起整个闭环。"""
    memory = []                                    # 语言反思记忆
    fail_counts = []                               # 每轮失败数，用于改进停滞检测
    prev_source = None
    for rnd in range(max_rounds):
        source = propose_candidate(rnd, memory)
        # 重复失败检测：与上一版完全相同且上一版失败过 → 强制换策略
        if source == prev_source and fail_counts and fail_counts[-1] > 0:
            print(f"第{rnd + 1}轮: 候选与上一版相同且曾失败，强制中断以防原地打转")
            return "STOP_REPEAT", memory
        failures = evaluate(source, TESTS)
        n_fail = len(failures)
        fail_counts.append(n_fail)
        head = source.splitlines()[0] + " ...(共%d行)" % len(source.splitlines())
        print(f"第{rnd + 1}轮 候选: {head}")
        print(f"        失败用例数: {n_fail} -> {failures}")
        if n_fail == 0:                            # 终止一：达标
            print(f"        全部通过，在第 {rnd + 1} 轮达标")
            return "PASS", memory
        lesson = reflect(failures)
        memory.append(lesson)
        print(f"        语言反思: {lesson}")
        # 终止三：改进停滞（连续两轮失败数没减少，且候选已换过）
        if len(fail_counts) >= 2 and fail_counts[-1] >= fail_counts[-2] and rnd >= 1:
            # 仅提示，不立即停（本任务下一版会改好），真实系统可在此收敛退出
            pass
        prev_source = source
    print("达到最大轮次（终止二：硬上限）")          # 终止二：硬上限
    return "MAX_ROUNDS", memory


if __name__ == "__main__":
    status, memory = run_reflection_loop()
    print("-" * 50)
    print("最终状态:", status)
    print("累计语言反思:")
    for i, m in enumerate(memory, 1):
        print(f"  {i}. {m}")
```
保存为 `reflect_loop.py`，运行 `python reflect_loop.py`，预期输出：
```text
第1轮 候选: def solve(n): ...(共2行)
        失败用例数: 2 -> [((99,), 18, 9), ((123,), 6, 3)]
        语言反思: 输入 (99,) 期望 18 实际 9：结果偏小，可能只累加了部分数位，应遍历每一位相加
第2轮 候选: def solve(n): ...(共2行)
        失败用例数: 3 -> [((10,), 1, 0), ((99,), 18, 9), ((123,), 6, 3)]
        语言反思: 输入 (10,) 期望 1 实际 0：结果偏小，可能只累加了部分数位，应遍历每一位相加
第3轮 候选: def solve(n): ...(共5行)
        失败用例数: 0 -> []
        全部通过，在第 3 轮达标
--------------------------------------------------
最终状态: PASS
累计语言反思:
  1. 输入 (99,) 期望 18 实际 9：结果偏小，可能只累加了部分数位，应遍历每一位相加
  2. 输入 (10,) 期望 1 实际 0：结果偏小，可能只累加了部分数位，应遍历每一位相加
```
第 2 轮很值得注意：失败用例数从第 1 轮的 2 涨到了 3——第 2 版（只取个位 `n % 10`）比第 1 版（`max`）还差。这就是一个「改坏了」的信号：`max` 版至少对个位数和「最大位恰好是和」的少数情况碰巧对，而 `n % 10` 版连 `solve(10)` 都从 1 掉到 0。这说明**候选之间的失败数不是单调下降的，反思驱动的修订完全可能一时走岔**。也正因如此，「改动后失败数不降反升」是一个强烈的回滚信号——真实系统应在此回滚到历史最优版并调整反思方向，而不是盲目相信「下一版一定更好」。本例第 3 版恰好改对了，所以没有触发回滚，但这只是这条确定性序列的巧合，不能当成普遍规律。

## 从模拟到接真实模型：只改一个函数

上面的 `propose_candidate` 用确定性序列模拟了「模型在反思驱动下改代码」。要接真实模型，**只需替换这一个函数**，其余部件（判分、反思、终止、防打转）完全不变。伪代码如下（不可直接运行，因为需要模型接口，仅示意接口位置）：
```python
def propose_candidate_real(round_idx, memory, task_spec, client):
    """接真实模型的版本：把任务规格 + 历史反思拼进提示。"""
    reflections = "\n".join(f"- 上次教训：{m}" for m in memory)
    prompt = (
        f"任务：{task_spec}\n"
        f"{reflections}\n"
        f"请根据以上教训给出改进后的 Python 函数 solve，只返回代码。"
    )
    resp = client.complete(prompt)     # 一次模型调用
    return extract_code_block(resp)    # 从回复中抽取代码块
```
这段之所以不作为可运行三件套，是因为它依赖具体模型客户端；但它清楚地标出了「机制与模型解耦」的设计——判分器、反思器、控制器是稳定的工程骨架，模型只在 `propose_candidate` 这一个点接入。这样做的工程价值是：**你可以先用确定性序列把整个闭环调通、测好，再换上真实模型**，避免一上来就在「模型不稳定」和「循环逻辑有 bug」两个变量里同时打转。

## 深入：三重终止与防打转在这个工程里如何生效

把第 03 节的三重终止和第 01 节的防打转，落到这个具体工程里：
```text
达标即停（终止一）：evaluate 返回空失败列表 → return "PASS"。
    这是最理想的退出，本例在第 3 轮触发。

硬上限（终止二）：rnd 跑满 max_rounds → return "MAX_ROUNDS"。
    防止候选序列永远修不好时无限烧钱。

改进停滞（终止三）：fail_counts 连续两轮不下降。
    本例第 2 轮失败数(3) > 第 1 轮(2)，说明第 2 版是"改坏了"——
    真实系统可在此回滚到上一版或强制换大方向。

重复失败检测（防打转）：候选源码与上一版完全相同且曾失败 → STOP_REPEAT。
    对应开头事故里"补丁 A 和补丁 B 几乎一样都失败"的场景。
```
特别看第 2 轮：失败数从 2 涨到 3，这是一个「改坏了」的信号。本例因为第 3 版会改好，所以没有在此强制停；但在真实系统里，**「改动后失败数不降反升」是一个强烈的回滚信号**——它意味着当前反思方向可能是错的。把它接进控制器（比如「连续两轮失败数不降就回滚到历史最优版并换反思策略」），就能避免在错误方向上继续消耗。

## 真实系统对应

**官方公开机制**：用「可执行的自动判分」作为 Agent 的评价信号，与 CRITIC「用代码解释器等工具验证并修正输出」的思路一致 [来源](https://arxiv.org/abs/2305.11738)；「生成-评估-修订」的循环结构对应 Anthropic 公开的 Evaluator-Optimizer 工作流 [来源](https://www.anthropic.com/engineering/building-effective-agents)。**通用工程模式**：把「模型生成」与「机制骨架」解耦，模型只在单一接入点介入，骨架用确定性数据先行调通。**教学参考实现**：`CANDIDATES` 确定性序列、`reflect` 的诊断规则、`run_reflection_loop` 的控制逻辑都是为可运行与可测试构造的，不复刻任何产品的重试/纠错内核。

安全边界必须强调：这里用 `exec` 运行候选代码是**教学演示**。生产环境中运行模型生成的代码有严重安全风险（任意代码执行），必须在沙箱、容器或受限子进程中隔离，限制资源与权限，绝不能在有生产数据或密钥的进程里直接 `exec`。本节代码只处理无害的算术函数，仅供理解机制。

## 生产踩坑

| 症状 | 根因 | 如何观测与复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| 单个用例过了就当通过 | 测试覆盖不足，「碰巧对」被当成正确 | 增加边界用例（0、多位数、负数）重跑 | 用多样化、覆盖边界的测试集判分 | 探索性任务允许部分通过 |
| 直接 exec 模型生成代码被攻击 | 未隔离，任意代码执行风险 | 用恶意样本（读文件/联网）测试是否被拦 | 沙箱/容器/受限子进程隔离，限权限与资源 | 无——生产必须隔离 |
| 改动后失败数上升仍继续 | 控制器没有「改坏了就回滚」 | 记录每轮失败数曲线，注入一版更差的候选 | 保留历史最优版，失败数不降则回滚并换策略 | 允许探索性劣化的搜索任务除外 |
| 循环调不通分不清是模型还是逻辑错 | 模型与循环逻辑两个变量同时变动 | 先用确定性候选序列跑通骨架 | 机制与模型解耦，骨架先行用固定数据验证 | 无 |
| 判分器吞掉异常导致「假通过」 | 异常被 try 吃掉未计入失败 | 注入会抛异常的候选，检查是否记为失败 | 异常显式记为失败反馈，不静默忽略 | 无 |
| 反思文本无法定位问题 | reflect 只说「不对」没带期望/实际 | 抽查反思是否含具体用例与期望值 | 反思必须带「输入/期望/实际」三元组 | 无客观真值时退化为定性描述 |

## 思考：为什么要把「机制骨架」和「模型调用」解耦？

### 回答

因为它把一个「双变量难题」拆成两个「单变量问题」。如果一上来就用真实模型跑整个反思循环，当结果不对时你分不清是**模型生成得差**还是**循环逻辑有 bug**——两个变量同时在变，无法定位。先用确定性候选序列（`CANDIDATES`）把判分、反思、终止、防打转这套骨架跑通、测好，此时骨架的每一步输出都是可预期、可断言的；确认骨架无误后，再把 `propose_candidate` 换成真实模型调用，这时若出问题，几乎可以肯定在模型侧。

这也带来一个额外好处：骨架可以写单元测试（用固定候选序列断言循环走向），从而让「反思循环」本身变成可回归测试的工程，而不是一个只能靠肉眼看日志的黑箱。

### 面试精简表达

解耦是为了把「模型不稳定」和「逻辑有 bug」两个变量分开。先用固定数据把循环骨架测通，再接模型，出了问题好定位；骨架还能写回归测试。

## 思考：这个例子里，为什么「单个用例通过」不能作为终止条件？

### 回答

因为「单个用例通过」可能是「碰巧对」。本例第 1 版用 `max` 时，对输入 10 恰好得到正确的 1（`max(1,0)=1`），如果只看这一个用例就会误判为「修好了」，但它对 99 仍然错（`max(9,9)` 得 9 而非 18）。只有**全量、覆盖边界的测试集都通过**，才是可靠的达标信号。这背后是一个更普遍的原则：评价信号的可靠度取决于它的**覆盖度**——测试越能覆盖边界情况（0、多位数、进位等），「碰巧对」的假象就越难蒙混过关。

推广到所有反思循环：终止条件的严格程度，不能低于任务对正确性的要求。用一个宽松的信号当终止条件，等于给循环装了个失灵的刹车——它会在「假达标」处停下，交付一个带 bug 的结果。

### 反例

也不能走到另一个极端，认为「测试必须 100% 覆盖所有可能输入才能停」——那对多数任务不现实且成本极高。合理做法是覆盖**有代表性的边界与典型情形**，让「碰巧全过」的概率低到可接受，而不是追求绝对完备。工程是权衡，不是极端。
