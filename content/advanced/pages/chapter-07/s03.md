## 真实问题

一个把用户口语化需求改写成「正式工单描述」的 Agent，收到输入「赶紧把登录崩溃这事搞定，急」。它一次性输出：「请尽快处理登录崩溃问题。」看起来还行，但工单系统要求正式描述必须包含「模块、现象、影响范围、优先级」四要素，这一版一个都没有。下游工程师收到后一头雾水，反过来追问三轮才补齐信息，比人工写还慢。

问题不是模型「不会写正式工单」，而是它**一次成型就交卷，中间没有「先自己检查一遍缺什么、再补」的环节**。如果让它「生成初稿 → 对照要素清单挑毛病 → 针对毛病修订」，它完全有能力自己补齐这四要素。这个「生成-批评-修订」的循环，就是 Self-Refine。

## 原理：同一个模型，扮演生成者和批评者

Self-Refine 论文（arXiv:2303.17651）的核心思想是：用**同一个 LLM**，不额外训练，通过「生成初稿 → 自我给出反馈 → 根据反馈修订」的迭代循环来提升输出质量 [来源](https://arxiv.org/abs/2303.17651)。论文报告，在多项任务上，Self-Refine 的输出在人类评价和自动指标上都优于同一模型的一次性生成，平均绝对提升约 20% [来源](https://arxiv.org/abs/2303.17651)。它的一个重要卖点是「无需训练、即插即用」——连 GPT-4 这样接近当时最强水平的模型，也能在测试时（test-time）靠这个简单循环进一步改善 [来源](https://arxiv.org/abs/2303.17651)。

它和第 02 节 Reflexion 的关系值得先厘清：
```text
Reflexion（跨"尝试"积累经验）：
    多次独立尝试同一任务，每次失败把教训存进记忆，带到"下一次尝试"。
    关注点：跨 episode 的语言记忆积累。

Self-Refine（单次任务内的迭代打磨）：
    一次任务内，对"同一个输出"反复 生成→批评→修订，直到满意。
    关注点：单个输出的质量精炼，不一定涉及跨任务记忆。
```
两者不是对立的，实际系统常常组合：用 Self-Refine 打磨单次输出，用 Reflexion 在多次尝试间积累经验。本节聚焦 Self-Refine 的「单次任务内三步循环」。

三步是：
```text
1. 生成（Generate）：产出一版草稿
2. 批评（Feedback/Critique）：同一模型对草稿给出"具体、可操作"的反馈
3. 修订（Refine）：同一模型根据反馈产出改进版
   → 回到步骤 2，直到反馈说"够好了"或达到轮次上限
```
关键在于步骤 2 的反馈必须**具体可操作**。论文强调反馈要 actionable（可执行）——不是「不够好」，而是「缺少优先级字段」这种能直接指导下一步修改的反馈 [来源](https://arxiv.org/abs/2303.17651)。反馈越具体，修订越有效。

## 最小可运行演示

下面把「口语需求改写成正式工单」的 Self-Refine 循环落地。批评者按一个明确的要素清单（rubric，评分标准）逐条挑毛病，生成者据此补齐，直到达标或到上限。完全可运行、不需要模型或网络：
```python
REQUIRED = ["模块", "现象", "影响范围", "优先级"]


def generate(draft, feedback=""):
    """生成/修订一版。真实场景是调 LLM，这里用规则模拟"根据反馈补齐要素"。"""
    if not feedback:
        return {"模块": "", "现象": "登录崩溃", "影响范围": "", "优先级": ""}
    # 根据反馈补上被指出缺失的字段
    fixes = {
        "缺少模块": ("模块", "用户登录"),
        "缺少影响范围": ("影响范围", "全部用户无法登录"),
        "缺少优先级": ("优先级", "P0"),
    }
    for problem, (key, value) in fixes.items():
        if problem in feedback:
            draft[key] = value
    return draft


def critique(draft):
    """批评者：按 rubric 逐条检查，返回 (是否达标, 具体可操作的反馈)。"""
    problems = [f"缺少{field}" for field in REQUIRED if not draft.get(field)]
    if not problems:
        return True, "达标：四要素齐全"
    return False, "、".join(problems)               # 具体反馈，非笼统"不够好"


def self_refine(max_rounds=5):
    draft, feedback = generate(""), ""
    for rnd in range(1, max_rounds + 1):
        ok, feedback = critique(draft)              # ① 批评
        shown = {k: v for k, v in draft.items() if v}
        print(f"第{rnd}轮: {shown} -> {'达标' if ok else '待改：' + feedback}")
        if ok:                                      # ② 自然终止
            return draft
        draft = generate(draft, feedback)           # ③ 据反馈修订
    print("达到最大轮次，返回当前最好版本（强制终止）")
    return draft


if __name__ == "__main__":
    result = self_refine()
    print("最终工单:", result)
```
保存为 `self_refine_ticket.py`，运行 `python self_refine_ticket.py`，预期输出：
```text
第1轮: {'现象': '登录崩溃'} -> 待改：缺少模块、缺少影响范围、缺少优先级
第2轮: {'现象': '登录崩溃', '模块': '用户登录', '影响范围': '全部用户无法登录', '优先级': 'P0'} -> 达标：四要素齐全
最终工单: {'模块': '用户登录', '现象': '登录崩溃', '影响范围': '全部用户无法登录', '优先级': 'P0'}
```
逐点讲解：

- **标注 ①（批评者用 rubric）**：`critique` 按明确清单逐条检查，返回**结构化、可操作**的反馈（「缺少模块、缺少影响范围」），而不是「不够好」。这直接决定修订能否命中要点。
- **标注 ②（自然终止）**：`if ok: return` —— 批评者满意就停，不画蛇添足。
- **标注 ③（据反馈修订）**：`generate(draft, feedback)` 只针对被指出的缺陷改，不推倒重来。真实 LLM 里这一步是把「上一版 + 反馈」一起给模型，让它产出改进版。

注意这里生成者和批评者是**同一套逻辑扮演的两个角色**——这正是 Self-Refine 的定义（同一个模型自我反馈）。第 04、06 节会讨论「同一个模型自评」的风险（自评虚假自信），以及何时该换成「独立评估者」。

## 三重终止：给循环装上刹车

Self-Refine 循环最危险的失败模式是「永远还能更好」地转下去，烧钱且不收敛。成熟的循环要组合三种终止条件：
```text
终止条件一：达标即停（自然终止）
    批评者判定"已满足要求" → 立刻停，别画蛇添足。

终止条件二：硬上限（强制终止）
    轮次达到 max_rounds → 无论好坏都停，防死循环、控成本。

终止条件三：改进停滞（收敛检测）
    连续两轮质量提升 < 阈值 → 说明"榨不出更多提升了"，停。
    （避免为了 1% 的提升多花好几轮的钱）
```
把三种刹车合成一个可运行的判定函数：
```python
def should_stop(scores, max_rounds, min_gain=0.02):
    """综合判断是否该停，返回停止原因或 None（继续）。"""
    if scores and scores[-1] >= 0.95:                       # 条件一：达标
        return "已达标"
    if len(scores) >= max_rounds:                           # 条件二：硬上限
        return "达到最大轮次"
    if len(scores) >= 2 and scores[-1] - scores[-2] < min_gain:  # 条件三：停滞
        return "改进已停滞，继续投入不划算"
    return None


def demo():
    scores = [0.60, 0.82, 0.90, 0.905]   # 模拟四轮质量分：后期提升趋缓
    for i in range(1, len(scores) + 1):
        reason = should_stop(scores[:i], max_rounds=6)
        print(f"看到前{i}轮分数 {scores[:i]} -> {reason or '继续'}")


if __name__ == "__main__":
    demo()
```
保存为 `should_stop.py`，运行 `python should_stop.py`，预期输出：
```text
看到前1轮分数 [0.6] -> 继续
看到前2轮分数 [0.6, 0.82] -> 继续
看到前3轮分数 [0.6, 0.82, 0.9] -> 继续
看到前4轮分数 [0.6, 0.82, 0.9, 0.905] -> 改进已停滞，继续投入不划算
```
第 4 轮分数从 0.90 只涨到 0.905，增量 0.005 < 阈值 0.02，触发「改进停滞」终止。这体现了成本意识：当边际提升已经很小时，继续投入是浪费。这和第 4 章 ToT（Tree of Thoughts，思维树）的剪枝、第 3 章「自主性是成本」是同一套工程哲学——**任何「还能更好」的循环都必须有明确的、多重的退出机制。**

## 深入：Self-Refine 在哪些任务上有效、哪些上无效

Self-Refine 不是万能的，它的有效性高度依赖任务类型。综合论文报告与后续研究，一个清晰的规律是：
```text
效果好的任务（有明确、可自评的质量维度）：
    对话回复生成、约束满足类改写、风格/礼貌度调整、代码可读性优化……
    共性：质量维度是"表面可判断"的，模型容易看出"缺了什么、哪里不合规范"。

效果差甚至变差的任务（深层推理正确性）：
    复杂数学推理、多步逻辑证明……
    共性：错误藏在推理链深处，模型自己既发现不了、也判断不了对错，
          "自评"往往和"自生成"犯同一个错（一起瞎）。
```
论文本身就观察到：在开放式、有明确约束的任务上提升明显，而在逻辑/数学类任务上提升有限，因为模型难以自行识别推理错误 [来源](https://arxiv.org/abs/2303.17651)。这条规律是理解「反思边界」的关键伏笔——它解释了为什么第 06 节 DeepMind 的研究会得出「纯推理任务上、无外部反馈时自我纠正无效」的结论 [来源](https://arxiv.org/abs/2310.01798)。**能否自评，取决于「错误是否表面可判断」**：工单缺字段是表面可判断的，一道你不会做的数学题对错是深层不可判断的。

推论到工程上：当任务的正确性无法靠模型自评判断时，不要用「模型自评式」的 Self-Refine，而要引入**外部客观信号**（单元测试、工具校验、真值比对）——这就是第 04 节要展开的「评价信号从哪来」，也是 CRITIC 论文用工具替代纯自评的动机 [来源](https://arxiv.org/abs/2305.11738)。

## 真实系统对应

**官方公开机制**：Anthropic 在《Building Effective Agents》里把「Evaluator-Optimizer」列为五种工作流模式之一——一个 LLM 生成、另一个 LLM 评估并给反馈、生成者据此迭代，并指出它适合「有明确评估标准且迭代能带来明显提升」的任务，如文学翻译润色、需要多轮检索的复杂问答 [来源](https://www.anthropic.com/engineering/building-effective-agents)。Self-Refine 论文本身则是公开可复现的方法 [来源](https://arxiv.org/abs/2303.17651)。**通用工程模式**：把「生成」与「批评」显式分成两个可替换的角色（可以是同一模型的两次调用，也可以是两个不同模型）。**教学参考实现**：上面的工单改写和 `should_stop` 是为讲清机制构造的，其阈值（0.95、0.02）是示意值，真实系统应按任务校准。

一个重要的区分：Self-Refine 论文里生成者和批评者是**同一个模型**（自我反馈）；Anthropic 的 Evaluator-Optimizer 描述里更强调**两个角色**（可以是不同 prompt 甚至不同模型）。「同一模型自评」和「独立评估者」是一个连续谱，选哪端取决于任务能否被模型可靠自评——这正是下一节的主题。

## 生产踩坑

| 症状 | 根因 | 如何观测与复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| 循环永不停止、成本失控 | 只有「还能更好」没有终止条件 | 统计平均轮次与每轮质量增量 | 装三重刹车：达标/硬上限/改进停滞 | 高价值任务可适当放宽硬上限 |
| 修订后反而变差 | 批评反馈不可操作或本身是错的 | 记录每轮质量分，观察是否单调上升 | 反馈须具体可操作；对推理类任务改用外部信号 | 表面质量类任务风险较低 |
| 数学/逻辑题「越改越错」 | 用模型自评判断深层推理正确性 | 对比自评结论与真值 | 换外部客观信号（测试/求解器/真值） | 表面约束类任务可继续自评 |
| 批评永远说「不够好」不收敛 | rubric 没有明确的「达标」定义 | 检查批评是否能输出「达标」态 | 给 rubric 明确的通过条件 | 开放创作类可容忍主观停止 |

## 思考：Self-Refine 和 Reflexion 到底有什么区别？

### 回答

一句话：**Reflexion 是「跨尝试」积累经验，Self-Refine 是「单次任务内」迭代打磨。** Reflexion 关注多次独立尝试之间的语言记忆积累——每次失败把教训存进记忆，带到下一次尝试；它的价值在跨 episode 的经验沉淀。Self-Refine 关注一次任务内对同一个输出的反复精炼——生成、批评、修订、再批评，直到满意；它不一定涉及跨任务记忆。

更细的区别：Reflexion 强调「真实结果反馈 + 持久化记忆」，通常用在能拿到成功/失败信号的任务；Self-Refine 强调「同一模型自我批评」，在表面可判断质量的任务上即插即用。工程里常组合——外层用 Reflexion 跨尝试学，内层用 Self-Refine 单次打磨。

### 面试精简表达

Reflexion 是「多次尝试之间记笔记」，Self-Refine 是「一次输出内反复改稿」。前者跨 episode 攒记忆，后者单 episode 内精炼。

## 思考：为什么「批评反馈要具体可操作」如此关键？

### 回答

因为**修订的质量上限由反馈的具体程度决定**。如果批评只说「不够好」，生成者不知道往哪改，只能整体重写，很可能改出新问题、甚至丢掉原本对的部分；如果批评说「缺少优先级字段」，生成者能精准补上那一处，其余不动。可操作的反馈把「重写」变成「定点修补」，既提升命中率又降低破坏性。

这一条和第 6 章「工具失败要返回结构化错误」是同一个道理：反馈信号越结构化、越可定位，下游的纠错就越有效。反过来，当你发现 Self-Refine「越改越乱」，第一个要查的往往不是修订逻辑，而是批评反馈够不够具体、准不准。

### 反例

「反馈越详细越好」也有边界：如果批评者把不存在的问题也「挑」出来（幻觉式批评），反馈再详细也是误导，会把对的改错。所以「具体」的前提是「准确」——这又回到了「批评者本身是否可信」，即评价信号的可靠度问题。
