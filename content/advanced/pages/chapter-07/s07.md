## 真实问题

反思机制上线三个月后，团队收到一条模糊反馈：「那个会自我改进的 Agent 好像越来越不靠谱，有时候答得还不如不反思。」这句话无法直接行动——「不靠谱」可能出在信号层（没有客观评价信号，纯自评瞎改）、反馈层（反馈不可定位，只有一句 `AssertionError`）、记忆层（反思没被存下来，下一轮读不到）、控制层（没有终止与回滚，改坏了还继续）或预算层（循环烧钱却不收敛）。生产诊断的第一步不是猜，而是**保存一次完整的反思轨迹**：每轮的候选、评价信号、失败明细、生成的语言反思、终止判定，再按层定位「反思在哪一层第一次没帮上忙」。这一节把本章前六节的机制沉淀成一张大表、一个可运行的分层诊断器，和一组面试级的思考回答。

## 反思故障诊断顺序

排查一个「反思不起作用」的故障，按下面的顺序逐层缩小范围，每一步都对应本章的一节：

1. **复现**：固定任务、输入、模型版本、随机种子，确认「反思后变差 / 原地打转 / 烧钱不收敛」能稳定重现。
2. **查信号层**：这个任务能接上客观信号吗？还是让模型自评一道它本就不会的深层推理题？（第 04、06 节）
3. **查反馈层**：失败反馈是否可定位（有输入/期望/实际），还是只有一句 `AssertionError` 让模型瞎猜？（第 04 节）
4. **查记忆层**：上一轮的反思是否被写进记忆并带回了下一轮，还是每轮从零开始？（第 02 节）
5. **查控制层**：有没有三重终止（达标/硬上限/停滞）和「重复失败就换策略」的防打转？改坏了会不会回滚？（第 03、05 节）
6. **查预算层**：反思成本是否与出错代价成正比？简单任务是不是被无脑加了多轮反思？（第 01、06 节）

这个顺序不是随意排的：信号和反馈是地基，地基不牢，上面的记忆、控制、预算做得再好也是空转——所以先查地基，再查上层。

## 生产建议表：信号与反馈层

第一张表聚焦「反思加工的是不是可信反馈」这个地基问题。信号错、反馈糊，是反思失效最常见也最隐蔽的根因：

| 症状 | 根因 | 如何观测与复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| 自我检查把对的答案改错 | 无客观信号却让模型自评深层推理 | 对一批已知正确答案的题开关自查，比对准确率 | 只在能接客观信号时反思；纯推理接求解器/真值 | 表面可判断任务（缺字段/格式）自查风险低 |
| 反馈只有一句报错无法定位 | 评价器只返回布尔或 `AssertionError` | 抽查反思文本是否含具体用例与期望/实际 | 反馈必须带「输入/期望/实际」三元组 | 无客观真值时退化为定性描述 |
| 越反思越笃定地错 | 反馈信号本身错误（如工具返回过期数据） | 注入错误反馈，观察反思是否沿错误方向精进 | 校验反馈来源与时效，多源交叉验证 | 权威实时信号可降低校验频率 |
| 自评分数虚高、全部「通过」 | 用模型自评当验收，盲区与生成同源 | 用人工标注的金标准集比对自评通过率 | 高风险验收改用外部工具/单元测试 | 低风险草稿可容忍自评 |
| 单个用例过了就当整体通过 | 测试覆盖不足，「碰巧对」被当正确 | 补边界用例（0、多位、进位、负数）重跑 | 用覆盖边界的测试集判分 | 探索性任务允许部分通过 |

这里 API Key（Application Programming Interface Key，接口密钥）不应硬编码进反思脚本；接外部工具做校验时，工具返回的时效与可信度本身也要被校验，否则副作用三「越反思越自信地错」就会出现。

## 生产建议表：记忆与控制层

第二张表聚焦「反思有没有被记住、循环有没有刹车」。开头那次 40 分钟 11 版的事故，根因几乎全在这一层：

| 症状 | 根因 | 如何观测与复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| 每轮重复同一个错误动作 | 反思没写进记忆，下一轮读不到 | 打印每轮传入模型的上下文，查是否含历史反思 | 反思写入记忆并拼进下一轮提示 | 单轮任务无需跨轮记忆 |
| 提交近乎相同的补丁反复失败 | 缺重复失败检测 | 记录相邻候选的 diff 相似度与失败状态 | 候选与上一版高度相似且曾失败即中断换策略 | 允许微调重试的搜索任务放宽 |
| 改动后失败数上升仍继续 | 控制器没有「改坏了就回滚」 | 记录每轮失败数曲线，注入一版更差候选 | 保留历史最优版，失败数不降则回滚 | 允许探索性劣化的搜索任务除外 |
| 反思循环长期不收敛烧钱 | 无终止条件或终止条件失灵 | 统计平均轮次与超限比例 | 三重终止（达标/硬上限/停滞）+重复检测 | 探索性研究任务可放宽上限 |
| 反思攒太多撑爆上下文窗口 | 只追加不淘汰，反思无限增长 | 监控反思条数与输入 token 随轮数变化 | 保留近 N 条+摘要更早反思为策略手册 | 短任务反思少无需压缩 |
| 循环调不通分不清模型还是逻辑错 | 模型与循环逻辑两个变量同时变动 | 先用确定性候选序列跑通骨架 | 机制与模型解耦，骨架先行用固定数据验证 | 无 |
| 判分器吞异常导致「假通过」 | 异常被 try 吃掉未计入失败 | 注入会抛异常的候选，检查是否记为失败 | 异常显式记为失败反馈，不静默忽略 | 无 |

CoT（Chain-of-Thought，思维链）在这里只是候选的生成方式，不能替代客观判分；把 CoT 的「看起来很有道理」当成正确性证据，正是自评虚高的温床。

## 生产建议表：预算与安全层

第三张表聚焦「反思值不值得上、以及绝不能靠反思兜底的安全边界」：

| 症状 | 根因 | 如何观测与复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| 反思让成本翻倍、成功率不变 | 给简单任务/每一步都无脑加反思 | 统计反思调用的边际成功率增量 | 反思成本与出错代价成正比，简单任务不加 | 高价值不可逆任务值得每步反思 |
| 高风险动作靠反思兜底出事 | 把反思当成安全闸门 | 注入错误模型输出看是否被拦 | 安全边界用模型外确定性代码强制 | 无 |
| 直接 exec 模型生成代码被攻击 | 未隔离，任意代码执行风险 | 用恶意样本（读文件/联网）测试是否被拦 | 沙箱/容器/受限子进程隔离，限权限与资源 | 无——生产必须隔离 |
| 把「反思无用论」当结论 | 误读 DeepMind「无外部反馈」设定 | 复核论文实验前提是否含外部信号 | 结论应为「反思要接信号」而非「没用」 | 无 |
| 延迟被多轮反思拖垮用户体验 | 同步串行反思阻塞响应 | 监控 P95 延迟随反思轮数变化 | 设轮数上限；低风险场景先出结果后台再优化 | 离线批处理可放宽延迟 |
| 反思日志泄露敏感输入 | 轨迹落盘含未脱敏原文 | 审计轨迹管道里的字段 | 落盘前最小化并脱敏敏感字段 | 合规要求可能限制原文留存 |
| 指标正常但用户仍说变差 | 只量轮次/延迟，缺端到端质量 | 增加「反思带来的净质量增量」指标 | 建含反思相关用例的端到端评估集 | 指标不取代人工复核 |

三张表合计 19 行，覆盖信号、反馈、记忆、控制、预算、安全六个面。RLHF（Reinforcement Learning from Human Feedback，基于人类反馈的强化学习）是训练阶段固化人类偏好的手段，与这里推理阶段的反思是两条不同的线，排查生产反思故障时不要把二者混为一谈。

## 最小可运行演示

把上面的诊断顺序落成一个可运行的分层诊断器，纯标准库、无需 API Key。它读入一次反思轨迹的关键指标，输出「第一次偏离在哪一层」：
```python
"""反思系统生产诊断器：把「反思没起作用」的模糊投诉按层定位到具体失败点。
纯标准库，无需 API Key、无需网络。"""


def diagnose_reflection(trace):
    findings = []
    if not trace["has_objective_signal"]:
        findings.append("信号层：无客观评价信号，纯自评推理不可靠")
    if not trace["feedback_locatable"]:
        findings.append("反馈层：反馈不可定位（如仅 AssertionError），无法指导修订")
    if not trace["reflection_persisted"]:
        findings.append("记忆层：反思未写入记忆，下一轮读不到，注定重复")
    if trace["repeated_identical_patch"]:
        findings.append("控制层：连续提交近乎相同且失败的候选，缺重复失败检测")
    series = trace["fail_count_series"]
    if len(series) >= 2 and series[-1] >= series[0] and max(series) > 0:
        findings.append("控制层：失败数未随反思下降，疑似改坏，应回滚到历史最优版")
    if trace["rounds"] >= trace["max_rounds"] and not trace["passed"]:
        findings.append("预算层：耗尽最大轮次仍未达标，应停并上报人工")
    return findings or ["各层正常：反思闭环健康"]


def main():
    incident = {
        "has_objective_signal": True,
        "feedback_locatable": False,
        "reflection_persisted": False,
        "repeated_identical_patch": True,
        "fail_count_series": [3, 3, 3, 3, 3],
        "rounds": 11,
        "max_rounds": 5,
        "passed": False,
    }
    for line in diagnose_reflection(incident):
        print(line)


if __name__ == "__main__":
    main()
```
保存为 `diagnose_reflection.py`，运行 `python diagnose_reflection.py`，预期输出（对应开头那次 40 分钟 11 版事故的指标）：
```text
反馈层：反馈不可定位（如仅 AssertionError），无法指导修订
记忆层：反思未写入记忆，下一轮读不到，注定重复
控制层：连续提交近乎相同且失败的候选，缺重复失败检测
控制层：失败数未随反思下降，疑似改坏，应回滚到历史最优版
预算层：耗尽最大轮次仍未达标，应停并上报人工
```
把 `feedback_locatable` 改成 `True`、`reflection_persisted` 改成 `True`，输出里对应两行就会消失。这个诊断器只负责缩小范围，不自动改阈值或停循环；每个判断在生产里都应连到可打开的反思轨迹快照。它体现了反思诊断的核心原则：**先定位「哪一层第一次偏离预期」，而不是笼统归因为「反思不行」。** 注意它一次性列出所有命中层，而不是只报第一层——因为一次事故常是多层同时塌方，只修一层往往不够。

## 值班现场：从「反思变差」到可复现故障

一个真实的排查过程。用户反馈「让 Agent 自我检查后，一道数学题反而答错了」。值班人员先取该会话 ID、任务和模型版本，导出反思轨迹：首答 69（正确），自查后改成 72（错误），而这道题**没有接任何外部求解器或真值**——纯让模型自评推理对错。这一眼就落在信号层：无客观信号的纯推理自评，正是 DeepMind 论文界定的「内在自我纠正」失效区间。它不是模型「退化」了，而是这类任务本就不该开无信号自查。

修复方向随之明确：对这类「纯推理、无外部信号」的任务关闭强制自查，或接入一个确定性求解器/校验器提供客观信号，只有信号判定为错时才允许修订。上线后用这条投诉做回归验证：接入求解器后，同样的题首答正确就不再被「改错」，真错的题才被纠正。整个过程从「模糊反馈」到「定位在信号层」只花了十几分钟——不是因为日志多，而是因为轨迹能回答「反思加工的信号到底可不可信」。

## 六类常见误诊

「反思不行」常被当成通用解释，但它可能只是某一层的问题。**误诊一**：把「无信号自评改错」当「模型能力退化」——模型没退化，是这类任务不该开无信号反思，该接客观信号或关掉自查。**误诊二**：把「原地打转」当「模型太笨」——模型不笨，是反思没被存下来、缺重复失败检测，补记忆和防打转即可。**误诊三**：把「改坏了还继续」当「反思方向错」——方向可能没错，是控制器缺回滚，保留历史最优版就能兜住。**误诊四**：把「烧钱不收敛」当「任务太难」——难是一方面，但没有硬上限和停滞终止才是直接原因。**误诊五**：把「越反思越自信地错」当「模型幻觉」——模型忠实地用了错误反馈，问题在反馈信号本身没被校验。**误诊六**：把「反思无用」当普适结论——那是误读了 DeepMind「无外部反馈」的实验设定，正确结论是「反思要接信号」。每一类误诊的共同教训是：**先看证据落在哪一层，再动手，别用一个笼统结论掩盖具体的失败点。**

## 优化前后对照

以历史投诉构成固定回归集，每次只改一个环节并对照，避免把随机波动当收益：

| 优化 | 基线问题 | 单一改动 | 成功判据 | 回滚信号 |
|---|---|---|---|---|
| 接客观信号 | 无信号自评把对的改错 | 纯推理任务接求解器/真值 | 已知正确题不再被改错 | 求解器误判引入新错 |
| 反馈结构化 | 反馈只有 AssertionError | 返回输入/期望/实际三元组 | 反思能定位到具体用例 | 反馈冗长拖高 token |
| 反思写入记忆 | 每轮重复同一错误 | 反思拼进下一轮提示 | 重复动作显著下降 | 记忆过长撑爆窗口 |
| 加重复失败检测 | 提交近乎相同的补丁 | 相似且曾失败即换策略 | 原地打转被及时中断 | 误杀正常的微调重试 |
| 加回滚到最优版 | 改坏了还继续覆盖 | 失败数不降则回滚 | 交付不劣于历史最优 | 卡在局部最优不再探索 |
| 反思成本分级 | 简单任务被无脑反思 | 按出错代价决定是否反思 | 成本降而成功率不变 | 高风险任务被误省略 |

没有对照，成功率上升可能来自数据变化，成本下降可能只是答案变短。每个优化都要能回答「改善了哪个指标、代价是什么、什么时候该回滚」。这张表 6 行，与上文三张表合计 25 行生产经验。

## 真实系统对应

**官方公开机制**：Anthropic 在《Building Effective Agents》里公开的 Evaluator-Optimizer 工作流，明确适用于「有明确评估标准、迭代能带来明显提升」的任务——这正是「反思要接可信信号」的工程背书，也隐含「没有明确评估标准时收益有限」的边界 [来源](https://www.anthropic.com/engineering/building-effective-agents)。CRITIC 用外部工具（搜索、代码解释器）替代纯自评做校验，是「接对信号」的论文范例 [来源](https://arxiv.org/abs/2305.11738)。**通用工程模式**：分层诊断、机制与模型解耦、保留历史最优版、端到端质量评估、安全边界外置。**教学参考实现**：上面诊断器的字段和判断顺序是示例，真实系统的指标集、阈值和告警由团队按风险设计，本书不声称任何平台自动完成这些治理。

## 思考：面试时被问「你们的反思循环怎么防止无限烧钱」，怎么答？

### 回答

用「三重终止 + 防打转 + 回滚」四件套回答，每一件都对应一个具体失效模式。第一，**达标即停**：评价器返回零失败就立刻退出，这是最理想的出口。第二，**硬上限**：设 `max_rounds`，跑满就停并上报，防止候选永远修不好时无限循环——这是烧钱的最后一道闸。第三，**改进停滞终止**：连续两轮失败数不下降就判定收敛乏力，停下或换大方向，而不是傻等硬上限。第四，**重复失败检测**：相邻候选 diff 高度相似且都失败，说明模型在原地打转（对应开头事故里补丁 A、B 几乎一样都失败），强制中断换策略。再加一条兜底：**保留历史最优版**，改坏了就回滚，保证即使循环走岔也不会交付比原来更差的结果。这套组合的核心思想是：反思循环必须默认「可能永远修不好」，所以先把刹车装好，再谈提升。

### 面试精简表达

三重终止（达标/硬上限/停滞）+ 重复失败检测防打转 + 保留历史最优版可回滚。默认循环可能修不好，先装刹车再谈提升。

## 思考：怎么向非技术的产品经理解释「为什么不能给所有功能都加自我反思」？

### 回答

用一个类比：反思像「请人复核」，复核有用的前提是复核者手里得有「标准答案或检查清单」。如果这个功能有客观标准（能跑测试、能查数据库、能对照规则），复核就靠谱，值得加。如果这个功能是让模型评判一件它本来就没把握的事（比如判断一段开放式推理对不对），那「复核」就等于让同一个人把自己的答案再猜一遍——不但不会更准，还可能把本来蒙对的改错（这有 DeepMind 的研究支撑）。再加上成本：每次反思都要多花一次模型调用和等待时间，给简单功能无脑加反思，用户体验变慢、账单变贵，成功率却几乎不动。所以决策标准很简单两句话：**这个功能能不能接上客观检查？错了代价高不高？** 两个都「是」才加反思，否则不加，或者换成「找外部工具、找人确认」。

### 面试精简表达

反思=请人复核，复核要有标准答案才有用。能接客观检查、且出错代价高的功能才加反思；纯主观判断加了反而可能改错，还费钱费时。

## 思考：上线一个新的反思策略前，最少要准备哪些东西？

### 回答

至少四样，缺一不可。第一，**一个固定回归集**：用历史真实案例（尤其是那些「越改越错」「原地打转」的事故）构成，新策略必须在这批样本上不倒退。第二，**可开关的对照**：反思能力要能一键开/关，方便做 A/B 对照，把「反思带来的净质量增量」和随机波动区分开。第三，**完整的反思轨迹落盘**：每轮候选、评价信号、失败明细、语言反思、终止判定都要能回放，否则出了问题无法定位在哪一层。第四，**回滚开关和历史最优版**：新策略改坏了要能立刻回退，且循环内部保留历史最优版，保证下行风险被封住。有这四样，你才敢说「上线可控」——而不是把一个只在少数样例上看起来更聪明的策略直接推给全量用户。

### 面试精简表达

固定回归集（含历史事故）、可开关的对照、完整轨迹落盘、回滚开关+历史最优版。四样齐了才敢上，缺一样都是在赌。
