## 一个「越改越错」的真实任务

某团队让一个代码评审 Agent 自动修复线上告警：`结算金额偶尔多减 1 分`。时间线是这样的：

- 09:12，Agent 读取结算函数，判断是浮点数四舍五入问题，提交补丁 A（把 `round(x, 2)` 换成另一种写法）。
- 09:15，CI（Continuous Integration，持续集成）跑单元测试，3 个用例失败，返回一条日志：`AssertionError`。
- 09:16，Agent「反思」后说「我需要再仔细检查一下四舍五入」，提交了几乎一样的补丁 B。
- 09:19、09:23、09:28……接下来 40 分钟里，它一共提交了 11 个版本，每次都在同一处小改，每次都失败，CI 队列被它塞满。
- 10:04，值班同学手动介入，才发现真正的根因在另一个函数：金额用了 `int(x * 100)` 截断而不是四舍五入。Agent 从头到尾没看那个函数。

事故复盘时最刺眼的一句话是：「它明明每一轮都在『反思』，为什么越反思越错？」答案不在模型大小，而在于它的反思缺了三样东西：没有拿到能定位问题的真实反馈（只有一句 `AssertionError`），没有把「补丁 B 和补丁 A 几乎一样且都失败」这条教训存下来，也没有任何终止与换策略的机制。这三样，正是本章要逐一补上的。

这个故障会贯穿全章：第 01 节讲「为什么会崩」，第 02 节讲 Reflexion 如何把失败写成语言记忆，第 03 节讲 Self-Refine 的生成-批评-修订循环，第 04 节讲反馈信号从哪来（为什么一句 `AssertionError` 不够），第 05 节把它做成一个完全可运行、能自动判分的工程，第 06 节讲反思的边界（含 DeepMind「模型还不能靠自己纠正推理」的反证），第 07 节讲生产落地与面试回答。

## 章节贯穿数据

后续小节共用同一条可复核的数据链，取自开头那次「越改越错」的事故，抽象成一个可自动判分的小任务：
```text
任务：实现 solve(n)，返回整数 n 各位数字之和（digit sum）
单元测试（可自动判分的评价信号）：
  solve(7)   == 7
  solve(10)  == 1
  solve(99)  == 18
  solve(123) == 6
  solve(0)   == 0

首版候选（有 bug）：只取个位数
  def solve(n): return n % 10
失败反馈（真实、可定位）：
  solve(10) 期望 1  实际 0
  solve(99) 期望 18 实际 9
  solve(123) 期望 6 实际 3
语言反思：
  "只取了个位，应该遍历每一位相加"
修订后候选（通过全部用例）：
  def solve(n):
      total = 0
      for ch in str(n):
          total += int(ch)
      return total
```
各小节会抽取这条链的一个侧面：02 节用它演示「反思写进记忆」，03 节用它演示「生成-批评-修订」，05 节把它做成端到端可运行、能真正 `exec` 判分的工程。用同一条数据的好处是：你可以把不同小节的代码拼起来对照，验证「输入变了什么、反思改了什么、结果好在哪」。

## 最小环境核验程序

导读页先给一段不依赖任何模型、不需要 API Key（Application Programming Interface Key，接口密钥）的核验程序，确认解释器可用、能 `exec` 运行候选代码、能自动判分。它就是全章方法的「最小内核」。
```python
def run_tests(source_code, tests):
    """把候选源码 exec 出来，逐个用例判分，返回失败列表。"""
    namespace = {}
    exec(source_code, namespace)
    solve = namespace["solve"]
    failures = []
    for args, expected in tests:
        got = solve(*args)
        if got != expected:
            failures.append((args, expected, got))
    return failures


def main():
    tests = [((7,), 7), ((10,), 1), ((99,), 18), ((123,), 6), ((0,), 0)]
    buggy = "def solve(n):\n    return n % 10\n"
    fixed = "def solve(n):\n    return sum(int(c) for c in str(n))\n"
    print("首版失败用例:", run_tests(buggy, tests))
    print("修订后失败用例:", run_tests(fixed, tests))


if __name__ == "__main__":
    main()
```
从章节目录保存为 `verify_chapter7.py`，运行 `python verify_chapter7.py`，预期输出：
```text
首版失败用例: [((10,), 1, 0), ((99,), 18, 9), ((123,), 6, 3)]
修订后失败用例: []
```
这段程序体现了本章最核心的一个观点：**反思要有效，先得有一个能自动、客观判分的评价信号**。这里的评价信号就是单元测试；`run_tests` 返回的失败用例，就是喂给下一轮反思的「真实反馈」。如果连这个都没有，后面所有反思都是闭门造车。若运行报 `KeyError: 'solve'`，说明候选源码里函数没定义好，先检查源码字符串，而不是怀疑判分逻辑。

## 从「越改越错」看反思的完整生命周期

回到开头那次 40 分钟、11 个版本的事故。用本章的框架把它拆开，每一个「本可以早点止损」的环节都对应一节内容。第一处：Agent 拿到的反馈只有 `AssertionError`，没有「哪个用例、期望什么、实际什么」，于是它只能瞎猜——这是第 04 节「评价信号」的问题。第二处：补丁 B 和补丁 A 几乎一样却都失败，这条「重复动作」的教训从未被记录下来，于是第 3、4、5……版继续重复——这是第 02 节「语言化记忆」的缺失。第三处：循环没有任何「改进停滞就停」或「重复失败就换策略」的刹车——这是第 03、06 节「终止条件」的缺失。第四处：它始终没跳出「补丁在这个函数」的假设去看别处——这是第 06 节要讲的「过度反思反而强化了错误方向」。

优化后的同一任务应该长这样：CI 返回结构化失败（哪个用例、期望/实际、失败断言所在行）；Agent 把「补丁 A 改动点 X 未能修复用例 Y」写成一条语言反思存进记忆；下一轮读到这条反思，发现「已经在 X 处试过且失败」，于是主动扩大搜索范围去看别的函数；循环设了「连续两版 diff 高度相似且都失败 → 停下并上报人工」的刹车。同样的模型、同样的窗口，只是把「反思」从一句空话变成了「有真实反馈、被记住、会换策略、知道何时停」的闭环——事故就能在第 3 版而不是第 11 版被拦住。
