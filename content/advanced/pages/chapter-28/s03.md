## 真实问题

电商客服 Agent 迭代到第三版，团队想知道：v3 到底比 v2 好不好？用第 2 节的 rubric 打分试了一下，结果很尴尬——v2 平均 4.31 分，v3 平均 4.34 分，差 0.03 分。这 0.03 分是「v3 真的更好」，还是「裁判绝对打分的抖动」？没人敢下结论。团队又重跑一次，这次 v2 反而高了 0.02 分。**绝对分数在版本选型这种「细微差异」的场景下，方差大到淹没了真实差距。**

问题的根子在于：让裁判说「这个回答值几分」，是在要求它凭空拿出一把绝对的尺子——而这把尺子本身在漂移。换个问法就稳得多：不问「几分」，只问「A 和 B 哪个更好」。这一节讲成对比较（Pairwise Comparison）为什么更稳、怎么汇总成胜率（win rate），以及它和 rubric 打分的分工。

## 原理：比较比打分更符合人类直觉

人类天生**更擅长比较而非绝对打分**——很难说清一杯咖啡是 7 分还是 8 分，但一口就能尝出哪杯更好。成对比较利用了这一点：���裁判在同一个问题下，看 A、B 两个回答，只判「谁更好」（或平局）。它有三个好处：

1. **方差更小、更稳定**：相对判断不需要维持一把绝对尺子，裁判只需比较，结论在重复实验里更一致，特别适合**模型/prompt 版本 PK**。
2. **对齐真实选型场景**：版本选型、模型选型的本质问题就是「换不换」，而不是「打几分」，成对比较直接回答这个问题。
3. **可汇总成有统计含义的胜率**：在 N 条样本上让新版对旧版逐条比较，赢的比例就是胜率；胜率显著高于 50% 才算真的更好（显著性检验见第 6 节）。

成对比较也有它的软肋——**位置偏差（Position Bias）**：裁判会倾向于选放在前面的那个。这是它的主要偏差，必须用「双向评测取一致」去偏（第 4 节详解）。所以完整的成对比较 = 比较范式 + 位置去偏 + 胜率汇总。

## 最小可运行演示：成对比较、位置去偏与胜率汇总

下面这段代码做三件事：一个 prompt 模板（显式声明忽略长度以对抗长度偏差）、一个双向一致的成对比较器、以及把逐条结论汇总成胜率。用确定性 mock 裁判，无需 API Key。
```python
"""教学参考实现:成对比较 + 位置去偏(双向取一致) + 胜率汇总。"""
from __future__ import annotations


def pairwise_judge_prompt(question: str, ans_a: str, ans_b: str) -> str:
    """成对比较 prompt:显式声明忽略长度,对抗长度偏差。"""
    return f"""你是严格的评审。针对同一问题的两个回答,判断哪个更好。
评判标准(按优先级):正确性 > 是否真正解决问题 > 简洁清晰。
注意:回答更长不代表更好;请忽略长度,只看质量。
问题:{question}
回答A:{ans_a}
回答B:{ans_b}
只输出 JSON:{{"winner":"A"或"B"或"TIE","reason":"一句话理由"}}"""


class MockJudge:
    """确定性假裁判:按预设质量分比较,质量接近时暴露位置偏差(选前面)。"""

    def __init__(self, quality: dict):
        self.quality = quality

    def __call__(self, q: str, first: str, second: str) -> str:
        q1, q2 = self.quality[first], self.quality[second]
        if abs(q1 - q2) > 1:
            return "A" if q1 > q2 else "B"
        return "A"  # 位置偏差:质量接近时无脑选前面


def debiased_compare(judge, q, ans_a, ans_b) -> str:
    """双向评测取一致:交换顺序问两次,把第二次视角翻回来再比。"""
    first = judge(q, ans_a, ans_b)                  # 'A' 指 ans_a
    second = judge(q, ans_b, ans_a)                 # 'A' 现在指 ans_b
    second_mapped = "A" if second == "B" else "B"   # 翻回原视角
    return first if first == second_mapped else "TIE"


def win_rate(judge, question, pairs) -> dict:
    """在多条 (v_new, v_old) 样本上汇总新版胜率。"""
    wins = ties = losses = 0
    for new_ans, old_ans in pairs:
        r = debiased_compare(judge, question, new_ans, old_ans)  # A=new, B=old
        if r == "A":
            wins += 1
        elif r == "TIE":
            ties += 1
        else:
            losses += 1
    n = len(pairs)
    return {"wins": wins, "ties": ties, "losses": losses,
            "win_rate": round(wins / n, 3)}


def run() -> None:
    q = "如何重置密码?"
    # 4 条样本:新版质量普遍不低于旧版,但有 1 条质量接近
    quality = {"n1": 5, "o1": 3, "n2": 5, "o2": 3,
               "n3": 4, "o3": 4, "n4": 5, "o4": 3}  # n3/o3 接近 -> TIE
    judge = MockJudge(quality)
    pairs = [("n1", "o1"), ("n2", "o2"), ("n3", "o3"), ("n4", "o4")]
    print("单条示例(质量接近->TIE):", debiased_compare(judge, q, "n3", "o3"))
    print("胜率汇总:", win_rate(judge, q, pairs))


if __name__ == "__main__":
    run()
```
保存为 `demo03_winrate.py`，运行 `python demo03_winrate.py`。完整预期输出：
```text
单条示例(质量接近->TIE): TIE
胜率汇总: {'wins': 3, 'ties': 1, 'losses': 0, 'win_rate': 0.75}
```
看这个结果：4 条样本里新版赢 3 平 1 负 0，胜率 0.75。那条质量接近的 `n3/o3` 被双向去偏判成了 TIE——**这正是想要的行为**：与其被位置偏差污染成一个假的胜负，不如诚实地判平局。胜率 0.75 只是点估计，它到底显著不显著、值不值得上线，还要过第 6 节的显著性检验；但比起 rubric 打分那 0.03 分的绝对差，「4 条赢 3 条」这个相对结论稳定得多、也好解释得多。

## 成对比较 vs Rubric 打分：分工而非替代

两种范式回答的是不同问题，不该二选一，而应按场景分工：

| 维度 | 成对比较 | Rubric 打分 |
|---|---|---|
| 回答的问题 | 谁更好（相对） | 好到什么程度、达标没（绝对） |
| 稳定性 | 高（人类擅长比较、方差小） | 中（绝对分易漂移） |
| 能否设达标线 | 不能（只有相对名次） | 能（如「≥4 分才上线」） |
| 典型用途 | 版本 PK、模型选型 | 上线门槛、质量监控、回归 |
| 主要偏差 | 位置偏差（双向去偏） | 长度偏差（rubric 声明+去偏） |

一句话:**选优用比较（稳），定级用打分（能设线）**。版本 A/B 谁上线用成对比较，「这条回答能不能发给用户」用 rubric 达标线。成熟系统常常两者都用——先用 rubric 卡住绝对达标线，再用成对比较在达标的多个版本里选最优。

## 真实系统对应

**官方公开机制**：LangSmith 提供专门的成对评估（pairwise evaluation）能力，接收两个实验作为对比目标，并提供 `randomize_order`（随机化顺序）选项来缓解位置偏差；文档明确指出「位置偏差主要应通过 prompt 工程解决，随机化顺序是额外的缓解手段」 [来源](https://docs.smith.langchain.com/evaluation/how_to_guides/evaluate_pairwise)。这与本节「prompt 显式声明 + 双向/随机去偏」双管齐下的做法一致。**通用工程模式**：成对比较汇总成胜率、以 50% 为基线判断优劣，是可迁移到任何裁判实现的做法。**教学参考实现**：上面的 `MockJudge` 用硬编码质量分模拟位置偏差，不代表任何真实模型行为；真实场景里 `judge` 要换成对大模型的调用，并解析其 JSON 输出。

## 生产踩坑

| 症状 | 根因 | 如何观测与复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| 版本 PK 用绝对分选、结论反复 | 绝对打分方差淹没细微差距 | 同两版重跑多次看排名是否翻转 | 改用成对比较看胜率 | 需绝对达标线时仍用 rubric |
| 成对结论随 A/B 顺序翻转 | 位置偏差未去偏 | 交换顺序各问一次看是否一致 | 双向取一致或 randomize_order | 质量差距悬殊时偏差影响小 |
| 胜率 51% 就宣布新版更好 | 未做显著性检验 | 小样本重复实验看波动 | 双比例 z 检验 + 足够样本 | 差距悬殊(如 90% vs 10%)时较稳 |
| 成对比较想设上线门槛却设不出 | 用错范式:比较只有相对名次 | 试图从胜率反推「几分算达标」 | 达标线改用 rubric 绝对分 | 纯选型场景无需达标线 |
| TIE 太多、区分不出版本 | 两版本质量确实接近或 prompt 太笼统 | 统计 TIE 占比 | 加大样本或细化评判标准 | 版本本就等价时 TIE 多是对的 |

## 思考：什么时候该用成对比较、什么时候该用 rubric 打分？

### 回答

按「你要回答的是相对问题还是绝对问题」来分。要回答相对问题——「v3 比 v2 好吗、该不该换」——用成对比较：人类天生擅长比较、不擅长绝对打分，所以让裁判只判「谁更好」比让它报「几分」方差小得多，在版本选型这种细微差异场景尤其明显；结论汇总成胜率，过 50% 且统计显著才算真更好。要回答绝对问题——「这条回答能不能发给用户、达没达到上线线」——用 rubric 打分：因为成对比较只给相对名次，没法设「≥4 分才上线」这种绝对达标线，而 rubric 能把「好」拆成带锚点的维度并汇总出绝对分。两者主要偏差也不同：成对比较怕位置偏差，靠双向取一致或随机化顺序去偏；rubric 怕长度偏差，靠 prompt 声明「简洁也可满分」加长度去偏。成熟系统往往两者叠用——先用 rubric 卡住绝对达标线，再在达标的候选里用成对比较选最优。能说清「选优用比较、定级用打分」以及各自主要偏差，就是高分答案。

### 面试精简表达

相对问题(选优、版本 PK)用成对比较,稳、看胜率、怕位置偏差;绝对问题(能否上线、设达标线)用 rubric 打分,能设线、怕长度偏差;成熟系统先用 rubric 卡线再用比较选优。
