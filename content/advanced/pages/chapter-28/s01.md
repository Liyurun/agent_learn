## 真实问题

回到开头那个「离线 95、线上 71」的电商客服 Agent。上线第二周,一条真实投诉炸了出来:用户说「订单 A123 想退款」,Agent 直接回复「已为您登记退款」,可财务侧发现这笔订单根本不在可退款政策内——Agent **先承诺了退款,才去查政策,查完发现不能退,却已经把话说出去了**。翻离线评估记录,这条样本当时是「通过」的,因为离线只看最后那句「已为您登记退款」,措辞礼貌、信息完整,裁判给了满分。

问题就出在这:**结果评估只审最后一句话,而这次事故的病根在中间的调用顺序**。`do_refund` 早于 `check_policy`,这个危险顺序在只看结果的评估里完全隐形。一次 Agent 运行产生的不是一句话,而是一条**轨迹(trajectory)**:一串带因果的思考、工具调用与观察。要把这类事故在离线拦下,就必须把评估粒度从「结果」下沉到「轨迹」,并且细到能写成断言、能进持续集成(Continuous Integration,CI)的快检。

## 原理:轨迹的四个可断言维度

一次 Agent 运行的轨迹形如:
```text
用户输入「订单 A123 想退款」
  → [思考1] → [工具调用1: query_order(A123)] → [观察1: {status:"shipped"}]
  → [思考2] → [工具调用2: check_policy(A123)] → [观察2: {refundable:true}]
  → [思考3] → [工具调用3: do_refund(A123, 88)] → [观察3: {ok:true}]
  → [最终回复:「已为您登记退款,预计 3 个工作日到账。」]
```
结果评估只看最后那句;轨迹评估要审视中间每一个 `[工具调用]` 及其**顺序、参数、必要性**。为什么中间过程值得单独评?因为在 Agent 里,「对的答案」和「对的过程」是两个独立的随机变量——可能同时对、同时错,也可能一对一错(答案对但过程危险,正是开头那次事故)。把「轨迹好不好」拆成能写进代码的四个维度:

| 维度 | 它回答什么问题 | 判定方式 |
|---|---|---|
| 工具选择正确性 | 该用的工具用了吗、不该用的碰了吗 | 集合运算:必用工具查全、红线工具查漏 |
| 参数正确性 | 工具的关键入参对吗 | 只结构化比对关键参数,不苛求全部 |
| 顺序合理性 | 有先后依赖的步骤顺序对吗 | 拓扑约束检查(A 必须早于 B) |
| 步数效率 | 有没有绕路、重复、空转 | 理想步数 / 实际步数 |

四个维度里,**工具选择要分「查全」和「红线」两组**:查全是能力问题(漏调该调的),红线是安全问题(碰了绝不该碰的),严重程度不同,报告里必须分开列。**参数只比对关键参数**——退款的 `id` 必须对,`trace_id` 之类无所谓;苛求全部参数一字不差是新手常犯的过严错误。

## 最小可运行演示

下面这段代码把四个维度落成一个纯规则的轨迹评估器,不依赖任何大模型,适合做 CI 里的第一道快检。它同时评一条「正确轨迹」和一条「先退款后查单、还重复空转」的问题轨迹。
```python
"""教学参考实现:轨迹级评估(trajectory-level evaluation)。"""
from __future__ import annotations
from dataclasses import dataclass, field


@dataclass
class ToolCall:
    name: str
    args: dict
    ok: bool = True  # 执行是否成功


@dataclass
class Trajectory:
    calls: list
    final_answer: str


@dataclass
class TrajectorySpec:
    must_call: set = field(default_factory=set)
    must_not_call: set = field(default_factory=set)
    ordered_pairs: list = field(default_factory=list)  # (A, B): A 必须早于 B
    key_args: dict = field(default_factory=dict)
    ideal_steps: int = 0


def eval_trajectory(traj: Trajectory, spec: TrajectorySpec) -> dict:
    called = [c.name for c in traj.calls]
    called_set = set(called)
    report = {}
    # 维度1:工具选择——查全(该调的调了没)与红线(不该调的调了没)
    report["missing_tools"] = sorted(spec.must_call - called_set)
    report["forbidden_hit"] = sorted(spec.must_not_call & called_set)
    # 维度2:参数正确性——只查关键参数
    arg_errors = []
    for c in traj.calls:
        if c.name in spec.key_args:
            for k, expected in spec.key_args[c.name].items():
                if c.args.get(k) != expected:
                    arg_errors.append((c.name, k, c.args.get(k), expected))
    report["arg_errors"] = arg_errors
    # 维度3:顺序合理性——只在两个工具都出现时检查先后
    order_violations = []
    for a, b in spec.ordered_pairs:
        if a in called and b in called and called.index(a) > called.index(b):
            order_violations.append((a, b))
    report["order_violations"] = order_violations
    # 维度4:步数效率——理想/实际,<1 说明绕路
    report["step_efficiency"] = round(
        spec.ideal_steps / len(traj.calls), 3) if traj.calls else 0.0
    report["passed"] = not (report["missing_tools"] or report["forbidden_hit"]
                            or report["arg_errors"] or report["order_violations"])
    return report


def run() -> None:
    good = Trajectory(
        calls=[ToolCall("query_order", {"id": "A123"}),
               ToolCall("check_policy", {"id": "A123"}),
               ToolCall("do_refund", {"id": "A123", "amount": 88})],
        final_answer="已登记退款")
    bad = Trajectory(  # 先退款、漏查政策、还重复空转
        calls=[ToolCall("do_refund", {"id": "A123", "amount": 88}),
               ToolCall("query_order", {"id": "A123"}),
               ToolCall("query_order", {"id": "A123"}),
               ToolCall("query_order", {"id": "A123"})],
        final_answer="已退款")
    spec = TrajectorySpec(
        must_call={"query_order", "check_policy"},
        must_not_call={"delete_order"},
        ordered_pairs=[("query_order", "do_refund"), ("check_policy", "do_refund")],
        key_args={"do_refund": {"id": "A123"}},
        ideal_steps=3)
    for tag, traj in [("good", good), ("bad", bad)]:
        r = eval_trajectory(traj, spec)
        print(f"[{tag}] passed={r['passed']} missing={r['missing_tools']} "
              f"order_violations={r['order_violations']} eff={r['step_efficiency']}")


if __name__ == "__main__":
    run()
```
保存为 `demo06_trajectory.py`,运行 `python demo06_trajectory.py`。完整预期输出:
```text
[good] passed=True missing=[] order_violations=[] eff=1.0
[bad] passed=False missing=['check_policy'] order_violations=[('query_order', 'do_refund')] eff=0.75
```
逐行看这段输出的价值:`good` 轨迹四维全过、效率 1.0;`bad` 轨迹一眼暴露三处病——漏了 `check_policy`(能力问题)、`query_order` 竟晚于 `do_refund`(正是开头事故的危险顺序)、效率 0.75(4 步做了 3 步的活,重复空转)。这条断言若在离线 CI 里跑过,开头那次「先承诺后查政策」的事故根本上不了线。把 `ordered_pairs` 里的顺序约束写清,是这类事故最便宜的防线。

## 轨迹评估的严格度怎么选

不是所有任务都该做同粒度的轨迹精评。粒度选错,要么漏报(太松)、要么误杀合理路径(太严)。给一张决策依据表:

| 任务特征 | 推荐粒度 | 理由 |
|---|---|---|
| 路径唯一、有强安全序(先鉴权后操作) | 序列 + 顺序约束 | 顺序本身就是正确性的一部分 |
| 子任务可并行、无先后依赖 | 集合匹配(in-any-order) | 强求顺序会误杀合理路径 |
| 允许探索、只关心关键动作 | 关键步骤查准查全率 | 容忍额外调用,抓住核心动作 |
| 开放推理、路径本就发散 | 只评结果 + 步数上限 | 轨迹无「标准答案」,评了也是噪声 |

最后一行常被忽略:**有些任务根本不该做轨迹精评**。开放式研究 Agent 的路径千变万化,比对「黄金轨迹」纯属自找麻烦,此时只该管结果对不对、别超步数上限。

## 真实系统对应

**官方公开机制**:LangSmith 支持对「中间步骤(intermediate steps)」评估,并提供 run 级与 thread 级两种粒度——run 级评单次运行、thread 级评一整条会话里的所有轨迹 [来源](https://docs.langchain.com/langsmith/online-evaluations)。Anthropic 在其工具开发方法里明确建议「让 Agent 跑完整的工具调用循环,记录时间、调用次数、token 消耗与错误类型」,用准确率之外的多维指标辅助决策 [来源](https://www.anthropic.com/engineering/writing-tools-for-agents)。**通用工程模式**:把轨迹拆成工具选择、参数、顺序、步数四个可断言维度,用集合运算与拓扑约束判定,是可迁移到任何框架的做法。**教学参考实现**:上面的 `TrajectorySpec` 与 `eval_trajectory` 只为讲清四维判定,阈值与字段命名不代表任何产品内部结构。

一个边界要点:轨迹里若含有副作用工具(如 `do_refund`),离线评估时必须 mock 掉它——评估不能真扣款、真发货。这与第 6 节「影子流量对有副作用工具要 mock」是同一条原则的两个位置。

## 生产踩坑

| 症状 | 根因 | 如何观测与复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| 答案对但过程危险却判通过 | 只评结果、未评轨迹 | 回放「先退款后查政策」看是否通过 | 加顺序约束断言进 CI 快检 | 无先后依赖的任务不设顺序约束 |
| 合理并行路径被误判失败 | 对无依赖子任务强求顺序 | 把可并行工具打乱顺序即误报 | 改用集合匹配 in-any-order | 有强安全序的任务仍需顺序 |
| 参数比对全红、噪声淹没真问题 | 苛求全部参数一字不差 | 比对 trace_id 等无关字段即误报 | 只比对 key_args 点名的关键参数 | 关键金额/ID 字段必须严格 |
| 开放研究 Agent 轨迹评估全失败 | 对发散路径强求黄金轨迹 | 同问题跑两次得两条不同合理轨迹 | 只评结果 + 步数上限 | 有唯一正确路径的任务另算 |

## 思考:为什么「答案对」不等于「过程对」,轨迹评估到底在防什么?

### 回答

因为在 Agent 里,答案的正确性和过程的正确性是两个独立的随机变量,只看其一会漏掉一整类事故。开头那次事故就是活证据:最终回复「已为您登记退款」措辞完美、信息完整,任何只看结果的裁判都会给满分——但它是在 `check_policy` 之前就 `do_refund`,是「先斩后奏」的危险顺序,一旦政策不允许退款,承诺已经泼出去了。轨迹评估防的正是这类「结果侥幸正确、过程本质危险」的情况,以及三类隐患:调错工具或漏调必用工具(能力问题)、碰了红线工具(安全问题)、绕路重复空转(成本问题)。落地时要把四维拆开:工具选择分查全与红线两组、参数只比关键项、顺序用拓扑约束、步数算效率;并且要按任务特征选粒度——有强安全序的任务必须评顺序,开放发散任务则只评结果加步数上限,否则评了也是噪声。能把轨迹讲到「可写成断言、可进 CI」的粒度,说明你真在生产里评过 Agent,而不只是背概念。

### 面试精简表达

答案对与过程对是两个独立变量;轨迹评估用工具选择(查全+红线分开)、关键参数、顺序拓扑、步数效率四维断言,专防「结果侥幸对、过程实则危险」,并按任务是否有唯一路径决定评多细。
