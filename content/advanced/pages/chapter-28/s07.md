## 真实问题

电商客服 Agent 上线后，团队发现一个诡异现象：每次底层模型供应商发布新版本，离线评估分就「莫名其妙地变好」——从 4.34 涨到 4.51，团队一度以为新模型真的更强，准备直接切换。可线上业务指标纹丝不动。深挖之后真相大白：新模型的训练数据里，很可能已经包含了团队评估集所用的一些公开客服对话——**评估集被污染了，模型不是「更会答」，而是「见过这些题」**。更基础的问题还在前面：团队最初的评估集只有 80 条，全是「用户礼貌提问」的合作型样本，而线上真正出问题的是那些「不耐烦、要挟差评、话说一半」的对抗型用户——评估集根本没覆盖到最要命的失败模式。

这一节解决两个问题：**怎么高效合成覆盖面足够广（含对抗样本）的评估集**，以及**怎么用版本与污染追踪，识破「模型升级导致评估分虚假变好」的假象**。

## 原理：合成生成 + 污染追踪

真实评估样本贵、慢、覆盖窄，**合成评估集（synthetic evaluation set）**用程序化或大模型的方式批量生成多样化样本。2026 年的业界实践强调两点 [来源](https://futureagi.com/blog/synthetic-test-data-llm-evaluation-2026/)：

1. **persona（用户画像）覆盖生产分布 + 对抗样本**：persona 库不能只有合作型用户，必须包含不耐烦、对抗、边界试探等最容易触发失败的画像——「只含合作型用户的评估集会漏掉最要命的失败模式」。
2. **版本化 + 污染追踪**：每个合成测试集都要有**版本号、创建日期、生成模型 id、内容 hash**。没有这些，你就无法判断「模型升级后评估分变好」到底是真的能力提升，还是评估集被新模型的训练数据污染了。

污染追踪的核心机制很简单：给每条样本算一个内容 hash，与训练/已知数据集的 hash 集合比对，命中的就是重叠样本，必须剔除或标记——这保证评估集与训练集不重叠，评估分才诚实。

Anthropic 的工具开发方法也走同一条路：用真实数据与复杂任务生成评估集、让 Agent 跑完整工具调用循环、记录时间/调用数/token/错误类型，再让模型分析失败样本、批量改进 [来源](https://www.anthropic.com/engineering/writing-tools-for-agents)。

## 最小可运行演示：合成生成 + persona 覆盖 + 污染检查

下面这段代码用「模板 × persona」组合批量合成评估样本，给每条打上版本/创建日期/生成器/hash，再做污染检查（剔除与训练集重叠的样本）和 persona 覆盖统计。纯 Python，无需大模型（真实场景可把模板换成大模型生成的 persona 与任务）。
```python
"""教学参考实现:合成评估集生成 + 污染追踪。"""
from __future__ import annotations
import hashlib
import itertools

TEMPLATES = [
    "我的订单 {oid} 想退款,可以吗?",
    "订单 {oid} 迟迟没发货,帮我催一下。",
    "{oid} 这个单我要改收货地址。",
]
PERSONAS = ["cooperative", "impatient", "adversarial"]  # 含对抗型


def make_hash(text: str) -> str:
    return hashlib.sha256(text.encode()).hexdigest()[:12]


def gen_cases(generator_id: str, version: str, created: str) -> list:
    cases = []
    for (tmpl, persona) in itertools.product(TEMPLATES, PERSONAS):
        oid = f"A{1000 + len(cases)}"
        text = tmpl.format(oid=oid)
        cases.append({
            "input": text, "persona": persona, "version": version,
            "created": created, "generator": generator_id,
            "hash": make_hash(text + persona),
        })
    return cases


def contamination_check(new_cases: list, train_hashes: set) -> list:
    """污染检查:若合成样本 hash 命中训练集,剔除,防评估集与训练集重叠。"""
    return [c for c in new_cases if c["hash"] not in train_hashes]


def run() -> None:
    cases = gen_cases(generator_id="mock-gen-v1",
                      version="evalset-2026.08", created="2026-08-24")
    print(f"生成样本数={len(cases)}(模板 {len(TEMPLATES)} x persona {len(PERSONAS)})")
    print("样例:", cases[0]["input"], "| persona=", cases[0]["persona"],
          "| hash=", cases[0]["hash"])
    # 假设训练集里已包含前两条的 hash(模拟污染)
    train_hashes = {cases[0]["hash"], cases[1]["hash"]}
    clean = contamination_check(cases, train_hashes)
    print(f"污染检查后剩余={len(clean)}(剔除 {len(cases) - len(clean)} 条与训练集重叠)")
    # persona 覆盖统计:确保对抗样本没缺席
    cover = {p: sum(c["persona"] == p for c in clean) for p in PERSONAS}
    print("persona 覆盖:", cover)


if __name__ == "__main__":
    run()
```
保存为 `demo08_synthetic.py`，运行 `python demo08_synthetic.py`。完整预期输出：
```text
生成样本数=9(模板 3 x persona 3)
样例: 我的订单 A1000 想退款,可以吗? | persona= cooperative | hash= b1ab4fad2202
污染检查后剩余=7(剔除 2 条与训练集重叠)
persona 覆盖: {'cooperative': 2, 'impatient': 2, 'adversarial': 3}
```
三处要点：第一，3 个模板 × 3 个 persona 组合出 9 条样本，且每条都带 `version`、`created`、`generator`、`hash`——**这套元数据是识破「模型升级导致评估分虚假变好」的唯一凭据**：下次评估分变了，先比对 hash 看评估集有没有被新模型见过。第二，污染检查剔除了 2 条与训练集 hash 重叠的样本，剩 7 条——评估集与训练集不重叠，分数才诚实。第三，`persona 覆盖` 显示对抗型（adversarial）样本占了 3 条，没有缺席——这正是开头那个「评估集只有合作型用户」问题的修复：**主动保证最容易触发失败的对抗画像被覆盖到**。

## 真实系统对应

**官方公开机制**：业界合成测试数据实践明确要求「每个合成测试集要有版本、创建日期、生成模型 id 与 hash，否则无法区分模型是真变好还是评估集被污染」，并强调 persona 库要覆盖生产分布加对抗样本 [来源](https://futureagi.com/blog/synthetic-test-data-llm-evaluation-2026/)。Anthropic 的工具开发方法建议用真实数据生成评估集、跑完整工具循环、用模型分析失败样本迭代改进 [来源](https://www.anthropic.com/engineering/writing-tools-for-agents)。「黄金数据集」的通行做法是先用合成数据做「银标」、再经领域专家评审升级为「金标」 [来源](https://www.getmaxim.ai/articles/building-a-golden-dataset-for-ai-evaluation-a-step-by-step-guide/)。**通用工程模式**：模板×persona 组合生成、内容 hash 污染检查、覆盖统计，都是可迁移的做法。**教学参考实现**：上面的模板与 persona 是固定示例，真实场景应用大模型生成更自然多样的样本，并让人工把「银标」升级为「金标」；hash 只截取前 12 位是为演示简洁，生产中应用完整 hash 或专门的去重/近重复检测。

一个边界：合成数据能扩覆盖、降成本，但**不能完全替代真实数据**——合成样本可能带上生成模型自身的分布偏好，与真实用户分布有系统性差异。稳妥做法是「合成打底 + 真实校准」：用合成集扩大覆盖，用真实失败样本校准分布、并作为最终验收的 held-out。

## 生产踩坑

| 症状 | 根因 | 如何观测与复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| 模型升级评估分「变好」但线上没变 | 评估集被新模型训练数据污染 | 比对评估集 hash 与已知公开数据 | 版本化 + 污染检查 + 用私有样本 | 全新能力确有提升属真改善 |
| 评估集只覆盖合作型用户 | persona 单一、缺对抗样本 | 统计 persona 分布看是否失衡 | 主动补对抗/边界试探 persona | 业务确实只有单一用户群时另说 |
| 合成集分数高、线上分数低 | 合成分布带生成模型偏好 | 对比合成集与真实集分数差 | 合成打底 + 真实校准 held-out | 纯覆盖性冒烟测试可容忍 |
| 无法复现某次评估结果 | 评估集无版本、被随意改动 | 试图重跑历史评估对不上 | 版本号 + 创建日期 + 冻结快照 | 一次性探索实验可不冻结 |
| 近似重复样本虚增覆盖假象 | 只做精确 hash 去重 | 造仅标点不同的近重复样本 | 近重复检测(如 MinHash/语义去重) | 样本天然差异大时精确去重够用 |

## 思考：为什么「模型升级后评估分变好」不一定是好事?怎么识破它?

### 回答

因为「评估分变好」有两种截然不同的成因，一种是真喜讯，一种是假象，而且假象往往更常见。真喜讯是新模型能力确实提升，在它从没见过的题上也答得更好。假象是**评估集污染**：新模型的训练数据里恰好包含了你评估集所用的样本（尤其是来自公开数据集的样本），于是它不是「更会答」，而是「见过这些题」——评估分涨了，但这些样本代表的真实场景它并没有变强，所以线上业务指标纹丝不动。识破它的唯一凭据是给评估集做版本化与污染追踪：每条样本记录版本号、创建日期、生成模型 id 和内容 hash；当评估分变化时，先拿评估集的 hash 去比对新模型可能的训练数据、或至少比对自己的训练/调优集，命中的样本要剔除或标记。更稳的做法是评估集尽量用**私有的、未公开的真实样本**做最终验收 held-out，这类样本不太可能进入公开训练语料，污染风险最低。此外这个问题还牵出评估集覆盖面：如果评估集只有合作型用户，就算没污染，它也测不出对抗型用户下的失败——所以 persona 要主动覆盖不耐烦、对抗、边界试探等最易触发失败的画像。能把「污染导致虚假变好、用版本+hash+私有 held-out 识破、外加 persona 覆盖」讲清，就说明你懂评估集本身也是需要治理的资产。

### 面试精简表达

评估分变好可能是真提升,也可能是评估集被新模型训练数据污染(见过题而非更会答),后者线上指标不动。识破靠版本化+内容 hash 比对+尽量用私有未公开样本做 held-out;同时 persona 要覆盖对抗型,否则测不出最要命的失败。
