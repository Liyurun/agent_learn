## 真实问题

电商客服 Agent 的回答质量没有「标准答案」——同一个退款问题，「已为您登记退款，预计 3 个工作日到账」和「退款申请已提交，款项将于 3 日内退回原支付账户」都对，但措辞、覆盖度、语气各不相同。第 16 章用过最朴素的 LLM 裁判：直接问大模型「这个回答好不好，打个 1 到 5 分」。上线后团队发现两个毛病：其一，**分数聚堆**——裁判几乎只在 4 分和 5 分之间摇摆，800 条样本里 700 条都是 4 或 5，根本区分不出优劣；其二，**同一条样本重跑三次，分数在 3、4、5 之间跳**，方差大得没法用来卡上线门槛。

这两个毛病不是「模型太笨」，而是**朴素打分的用法太粗**：既没让裁判先想清楚「凭什么打这个分」，也没把「好」拆成可判定的具体条款。这一节讲两件把裁判打分从「玄学」变成「工程」的事——G-Eval（一种基于思维链 Chain-of-Thought，CoT 的评分框架）的两段式流程，以及 rubric（评分量表）如何把笼统的「好」拆成锚点清晰的维度。

## 原理：G-Eval 的两段式与 rubric 拆分

G-Eval 的核心思想是：**别让裁判张口就报分，先让它把评分步骤想出来，再按步骤打分**。它分两段 [来源](https://deepeval.com/docs/metrics-llm-evals)：

1. **auto-CoT（自动思维链）**：把一句评分准则（如「覆盖度：回答是否覆盖问题所需关键信息」）交给裁判，让它自动展开成一串评估步骤（先理解维度 → 逐条核对 → 给分）。这一步让评分有据可依，而不是凭第一印象。
2. **form-filling（填表式打分）+ 概率加权**：让裁判按步骤打分，但**不取那个「最可能的整数分」，而是用各分档的输出概率做加权求期望**。比如裁判对某回答给出「4 分概率 0.5、5 分概率 0.3、3 分概率 0.15」，加权分是 `4*0.5+5*0.3+3*0.15=4.03`，比硬取 argmax=4 更细腻，能把「几乎一样但略有差别」的两个回答拉开差距，缓解分数聚堆 [来源](https://www.confident-ai.com/blog/g-eval-the-definitive-guide)。

rubric 设计则解决另一半问题：**把「好」拆成可判定的条款**。与其笼统问「打几分」，不如给一份量表，每个维度都有明确锚点（2/1/0 各代表什么），让裁判逐维打分再汇总。拆开后，每一维的判断方差明显变小，且能嵌入红线（如「合规性=0 一票否决」）。

## 最小可运行演示（一）：G-Eval 两段式与概率加权

下面用确定性 mock 裁判模拟 G-Eval：先由准则生成评估步骤，再对 1-5 分给出概率分布，最后用加权期望而非 argmax 得分。无需 API Key。
```python
"""教学参考实现:G-Eval 风格「先生成评估步骤,再按概率加权打分」。"""
from __future__ import annotations


class MockJudge:
    """确定性假裁判:模拟 auto-CoT + form-filling 概率加权。"""

    def gen_steps(self, criteria: str) -> list[str]:
        return [
            f"1. 阅读并理解评分维度:{criteria}",
            "2. 对照回答逐条核对是否满足该维度",
            "3. 在 1-5 分区间内给出打分与理由",
        ]

    def score_distribution(self, answer: str) -> dict:
        base = {1: 0.02, 2: 0.03, 3: 0.15, 4: 0.5, 5: 0.3}
        if "编造" in answer or "不知道" in answer:
            base = {1: 0.4, 2: 0.35, 3: 0.15, 4: 0.07, 5: 0.03}
        s = sum(base.values())
        return {k: v / s for k, v in base.items()}


def geval_score(judge: MockJudge, criteria: str, answer: str) -> dict:
    steps = judge.gen_steps(criteria)
    dist = judge.score_distribution(answer)
    # 关键:用概率加权求期望,而非取 argmax,缓解分数聚堆
    weighted = round(sum(score * p for score, p in dist.items()), 3)
    argmax = max(dist, key=dist.get)
    return {"steps": steps, "argmax": argmax, "weighted": weighted}


def run() -> None:
    judge = MockJudge()
    criteria = "覆盖度:回答是否覆盖了问题所需的关键信息"
    good = "已为您登记退款,预计 3 个工作日到账,可在订单页查询进度。"
    bad = "不知道,你去问客服吧。"
    for tag, ans in [("good", good), ("bad", bad)]:
        r = geval_score(judge, criteria, ans)
        print(f"[{tag}] argmax={r['argmax']} weighted={r['weighted']}")
    print("评估步骤示例:", geval_score(judge, criteria, good)["steps"][2])


if __name__ == "__main__":
    run()
```
保存为 `demo01_geval.py`，运行 `python demo01_geval.py`。完整预期输出：
```text
[good] argmax=4 weighted=4.03
[bad] argmax=1 weighted=1.98
评估步骤示例: 3. 在 1-5 分区间内给出打分与理由
```
`good` 回答 argmax=4 但加权 4.03，`bad` 回答 argmax=1 但加权 1.98——加权分把「4 分里偏好一点」和「1 分里带点犹豫」都表达了出来。当两个都是 argmax=4 的回答，一个概率分布偏向 5、另一个偏向 3 时，加权分能拉开零点几分的差距，正是这零点几分让「分数聚堆」问题得到缓解。

## 最小可运行演示（二）：rubric 多维打分 + 红线一票否决

G-Eval 解决「怎么打一个维度的分」，rubric 解决「怎么把多个维度组织起来并嵌入红线」。下面这段把「好回答」拆成准确性、解决度、合规性、语气四维，合规性设为一票否决。
```python
"""教学参考实现:Rubric 多维独立打分 + 红线一票否决。"""
from __future__ import annotations

RUBRIC = {
    "accuracy": (0, 2), "resolution": (0, 2),
    "compliance": (0, 1), "tone": (0, 1),  # compliance=0 一票否决
}


def mock_rubric_judge(answer: str) -> dict:
    scores = {}
    scores["accuracy"] = 0 if "编造" in answer else 2
    if "不清楚" in answer or "不知道" in answer:
        scores["resolution"] = 0
    elif "已" in answer or "为您" in answer:
        scores["resolution"] = 2
    else:
        scores["resolution"] = 1
    scores["compliance"] = 0 if "无条件全额退款" in answer else 1  # 越权承诺=红线
    scores["tone"] = 0 if "自己想办法" in answer else 1
    return scores


def aggregate(scores: dict) -> dict:
    total = sum(scores.values())
    max_total = sum(hi for _, hi in RUBRIC.values())
    passed = scores["compliance"] == 1 and total >= 4  # 红线 + 达标线
    return {"scores": scores, "total": total, "max": max_total, "passed": passed}


def run() -> None:
    cases = {
        "合规优质": "您好,已为您登记退款,预计 3 个工作日到账。",
        "越权承诺": "没问题,我给您无条件全额退款,马上到账!",
        "答非所问": "这个我也不清楚,你自己想办法吧。",
    }
    for tag, ans in cases.items():
        r = aggregate(mock_rubric_judge(ans))
        flag = "PASS" if r["passed"] else "FAIL"
        print(f"[{tag}] total={r['total']}/{r['max']} "
              f"compliance={r['scores']['compliance']} -> {flag}")


if __name__ == "__main__":
    run()
```
保存为 `demo02_rubric.py`，运行 `python demo02_rubric.py`。完整预期输出：
```text
[合规优质] total=6/6 compliance=1 -> PASS
[越权承诺] total=4/6 compliance=0 -> FAIL
[答非所问] total=3/6 compliance=1 -> FAIL
```
看「越权承诺」这行：它准确、解决度高、语气也好，总分 4 分本可通过——但 `compliance=0`（越权承诺无条件全额退款），一票否决直接判 FAIL。这把第 18 章的安全红线嵌进了评分逻辑：**一个礼貌、准确但越权的回复，总分再高也必须挂掉**。这正是 rubric 相比朴素打分的核心价值——它能表达「某些维度不是加分项，而是及格线」。

## 真实系统对应

**官方公开机制**：G-Eval 作为 DeepEval 库内的一个指标，公开文档描述了「先由准则生成评估步骤（auto-CoT），再以 form-filling 方式打分」的两段式，并说明它用 token 概率做加权以缓解打分不连续 [来源](https://deepeval.com/docs/metrics-llm-evals) [来源](https://www.confident-ai.com/blog/g-eval-the-definitive-guide)。LangSmith 提供内置 LLM 裁判评估器，也支持自定义 prompt 与结构化输出 schema [来源](https://docs.smith.langchain.com/evaluation/how_to_guides/llm_as_judge)。**通用工程模式**：「维度独立打分再汇总 + 红线一票否决 + 概率加权」是可迁移到任何裁判实现的模式。**教学参考实现**：上面的 `MockJudge` 是确定性假裁判，概率分布是硬编码的示例值，不代表任何真实模型对这些句子的实际打分；真实场景里 `score_distribution` 要换成对模型 logprobs 的读取或多次采样估计。

一个边界：G-Eval 的概率加权依赖能拿到各分档的输出概率（logprobs）；若使用的模型接口不返回 logprobs，则退化为多次采样求平均，或直接用 rubric 的整数分汇总。会变化的接口能力以当前官方文档为准。

## 生产踩坑

| 症状 | 根因 | 如何观测与复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| 分数聚堆在 4-5 分 | 直接取整数分、无概率加权、无锚点 | 统计分数直方图看是否集中 | G-Eval 概率加权 + rubric 明确锚点 | 二分类通过/不通过任务无需细分 |
| 同样本重跑分数乱跳 | 未拆维度、准则太笼统 | 同输入跑 5 次看方差 | 拆维度独立打分、每维给 2/1/0 锚点 | 温度设 0 后仍波动需换模型 |
| 越权但礼貌的回复拿高分 | 未设红线、只做加权求和 | 造「无条件退款」样本看是否通过 | 合规维度一票否决 | 无合规风险的纯创意任务另设 |
| 让裁判直接给总分不给理由 | 缺 CoT、无中间步骤 | 对比给/不给理由的一致性 | 强制先输出评估步骤再打分 | 极简快检可省理由换吞吐 |
| rubric 维度互相重叠、打分打架 | 维度定义不正交 | 让「准确」「解决」定义交叉即冲突 | 维度定义正交、各管一件事 | 单维度任务无此问题 |

## 思考：朴素「打 1-5 分」和 G-Eval + rubric，差在哪几处工程细节？

### 回答

差在三处，且每处都对应一个可观测的改善。第一处是「先想再打」：朴素打分让裁判张口就报分，凭第一印象，方差大；G-Eval 用 auto-CoT 先让裁判展开评估步骤，把「凭什么打这个分」显式化，判断更稳。第二处是「概率加权而非取整」：朴素打分取一个整数，导致分数聚堆在 4-5 分、区分不出优劣；G-Eval 对各分档用输出概率加权求期望，能把「几乎一样但略有差别」的回答拉开零点几分，缓解聚堆——前提是模型接口能返回 logprobs，否则退化为多次采样求平均。第三处是「维度拆分 + 红线」：朴素打分给一个笼统总分，无法表达「某些维度是及格线不是加分项」；rubric 把「好」拆成正交维度、每维给 2/1/0 锚点降低方差，并把合规这类维度设为一票否决——一个礼貌准确但越权承诺的回复，总分再高也必须挂掉。把这三处讲清，说明你不只会「叫大模型打分」，而是知道怎么把裁判打分做成可复现、可卡门槛的工程。

### 面试精简表达

朴素打分张口报整数分，方差大、聚堆、无红线；G-Eval 先 auto-CoT 展开步骤、再用分档概率加权求期望缓解聚堆，rubric 把「好」拆正交维度给锚点、并对合规维度一票否决。
