## 真实问题

「离线 95、线上 71」这个落差里，有两条病根属于「管线」层面。其一是**优化泄漏**：团队在调 prompt、选 few-shot 时反复用评估集里的样本试效果，等于 Agent 提前看了考题，离线分虚高。其二是**离线到线上没有过渡带**：离线过了就直接全量上线，中间没有任何在真实分布上验证的环节，于是长尾输入、真实用户偏好这些离线集覆盖不到的东西，全在上线后才暴露。

这一节把评估从「离线跑个分」升级成一条贯穿「离线 held-out → 影子流量 → A/B → 灰度」的完整管线。核心两件事：离线怎么**防数据泄漏**、在线怎么**分层推进**把风险逐级释放。

## 原理（一）：数据泄漏的三种形态与切分

「泄漏（leakage）」不止「把评估样本塞进 few-shot」这一种，生产里有三种更隐蔽的形态：

1. **优化泄漏**：拿评估集样本去调 prompt、选 few-shot、甚至微调。Agent 相当于提前看了考题，评估分虚高。
2. **切分泄漏**：同一个真实事件被拆成多条样本，一部分进训练/调优集、一部分进评估集。看似不同，实则同源，评估等于「考做过的题」。
3. **时间泄漏**：用「未来」的数据评「过去」的决策。比如评估选股 Agent 时，评估样本里混入了决策时点之后才发生的信息。

堵住它们的做法是**按事件（而非样本）切分 + 按时间切分**：先按事件分组，同一事件的所有样本整组分到某一侧；涉及时序则严格按时间点切开。而 held-out（留出）评估集要**从创建起就锁死、只在最终验收看一次**，任何优化动作都不许碰它。

## 原理（二）：在线评估分层推进

离线评估集再好，也只是「你以为的真实分布」。唯一的真相在线上。在线评估分三层，风险逐级释放：

- **影子流量（shadow traffic）**：新版 Agent 并行处理真实线上请求，但结果不返回给用户，只记录下来和线上版本对比。用户毫无感知，零风险，能暴露长尾输入。代价是双倍推理成本，且对有副作用的动作（真扣款、真发货）不适用，必须 mock 掉。
- **A/B 测试**：把用户分组给不同版本，用**业务指标**（转化率、解决率、人工转接率）做裁判，看统计显著性。
- **灰度发布**：逐步放量，盯稳定性与异常率，保留一键回滚。

LangSmith 明确区分离线评估（在数据集上跑）与在线评估（在生产 trace 上实时跑），并指出在线评估器可用于给输入分类、进而回流成离线数据集——这正是「失败样本回流成评估集」的闭环 [来源](https://docs.smith.langchain.com/evaluation/concepts) [来源](https://docs.langchain.com/langsmith/online-evaluations)。

## 最小可运行演示：切分防泄漏 + A/B 显著性

下面这段代码把「按事件哈希切分、按时间切分、A/B 双比例 z 检验」三件事落地。重点看：同一事件的样本一定同侧；同样涨 3 个点，小样本不显著、大样本才显著。
```python
"""教学参考实现:离线切分防泄漏 + 在线 A/B 双比例 z 检验。"""
from __future__ import annotations
import hashlib
from math import sqrt


def assign_split(event_id: str, holdout_ratio: float = 0.2) -> str:
    """按 event_id 哈希切分:同一事件所有样本必同侧,杜绝切分泄漏。"""
    h = int(hashlib.md5(event_id.encode()).hexdigest(), 16)
    return "holdout" if (h % 100) < holdout_ratio * 100 else "dev"


def time_based_split(cases: list, cutoff: str):
    """时序任务按时间切:cutoff 之前开发、之后评估,防时间泄漏。"""
    dev = [c for c in cases if c["date"] < cutoff]
    test = [c for c in cases if c["date"] >= cutoff]
    return dev, test


def ab_significant(conv_a, n_a, conv_b, n_b, z=1.96) -> dict:
    """双比例 z 检验:B 相对 A 的提升是否统计显著(z=1.96 对应 95%)。"""
    p_a, p_b = conv_a / n_a, conv_b / n_b
    p_pool = (conv_a + conv_b) / (n_a + n_b)
    se = sqrt(p_pool * (1 - p_pool) * (1 / n_a + 1 / n_b))
    if se == 0:
        return {"lift": 0.0, "significant": False}
    z_score = (p_b - p_a) / se
    return {"rate_a": round(p_a, 4), "rate_b": round(p_b, 4),
            "lift": round(p_b - p_a, 4), "z": round(z_score, 3),
            "significant": abs(z_score) > z}


def run() -> None:
    # 1) 事件哈希切分:同一事件两条样本一定同侧
    print("split(incident_20260421) 两次:",
          assign_split("incident_20260421"), assign_split("incident_20260421"))
    # 2) 时间切分:cutoff 之前开发,之后评估
    cases = [{"date": "2026-03"}, {"date": "2026-05"}, {"date": "2026-08"}]
    dev, test = time_based_split(cases, "2026-06")
    print(f"时间切分 dev={len(dev)} test={len(test)}")
    # 3) A/B:同样涨 3 个点,小样本 vs 大样本显著性不同
    small = ab_significant(72, 100, 75, 100)
    large = ab_significant(2160, 3000, 2250, 3000)
    print(f"A/B 小样本 lift={small['lift']} z={small['z']} sig={small['significant']}")
    print(f"A/B 大样本 lift={large['lift']} z={large['z']} sig={large['significant']}")


if __name__ == "__main__":
    run()
```
保存为 `demo07_pipeline.py`，运行 `python demo07_pipeline.py`。完整预期输出：
```text
split(incident_20260421) 两次: dev dev
时间切分 dev=2 test=1
A/B 小样本 lift=0.03 z=0.481 sig=False
A/B 大样本 lift=0.03 z=2.633 sig=True
```
三处要点：第一，同一 `event_id` 两次都得到 `dev`——确定性哈希保证「同一事件的所有样本永远同侧」，切分泄漏被从根上堵死。第二，时间切分把 6 月前的 2 条给开发、6 月后的 1 条给评估，保证评估时「只能看到决策时点之前的信息」。第三，也是最反直觉的：**同样是涨 3 个百分点，各 100 样本时 z=0.481 不显著、各 3000 样本时 z=2.633 才显著**——`lift` 一模一样，但小样本那 3 个点很可能只是噪声。这就是为什么「看着涨了 3 个点就上线」是危险的，必须过显著性这一关。

## 真实系统对应

**官方公开机制**：LangSmith 把评估分为离线（在 dataset 上跑，用于开发迭代）与在线（在生产 trace 上实时跑，支持 run 级与 thread 级粒度），并说明在线评估器可把输入分类后回流成离线数据集 [来源](https://docs.smith.langchain.com/evaluation/concepts) [来源](https://docs.langchain.com/langsmith/online-evaluations)。合成测试数据的业界实践也强调「每个测试集要有版本、创建日期、生成模型 id 与 hash，否则无法判断模型升级到底是真变好还是评估集被污染」 [来源](https://futureagi.com/blog/synthetic-test-data-llm-evaluation-2026/)（详见第 7 节）。**通用工程模式**：事件哈希切分、时间切分、held-out 锁死、影子流量、A/B 双比例 z 检验、灰度回滚，都是可迁移到任何平台的做法。**教学参考实现**：上面的 z 检验是最基础的双比例检验，未处理多重比较、序贯检验等复杂情况；`holdout_ratio`、`cutoff` 是示例值，真实场景需按业务与样本量设计。

一个重要边界：A/B 测试**不能偷看中途结果就提前下结论**——反复看、一显著就停，会大幅抬高假阳性率（这是序贯检验问题，需用专门方法如 always-valid p-value）。此外要设最小样本量、关注真实业务指标而非离线代理指标。

## 生产踩坑

| 症状 | 根因 | 如何观测与复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| 离线分虚高、线上崩 | 优化泄漏:评估集被反复用来调 prompt | 对比 held-out 与开发集分数差 | held-out 锁死、只验收看一次 | 分布剧变时需重建评估集 |
| 随机切分仍泄漏 | 同源样本被切到两侧(切分泄漏) | 按样本 id 随机切看同事件是否分家 | 按 event_id 哈希整组切分 | 样本间确实独立时随机切可用 |
| 时序任务评估分好、上线亏钱 | 时间泄漏:用未来信息评过去决策 | 检查评估样本是否含决策后信息 | 按时间点严格切分 | 无时序依赖的任务不涉及 |
| 涨 3 个点就上线、后来回落 | 未做显著性检验、样本量不足 | 小样本重复实验看波动 | 双比例 z 检验 + 最小样本量 | 差距悬殊时较稳 |
| A/B 反复偷看、一显著就停 | 序贯检验假阳性 | 每小时看一次、见显著就停 | 预设样本量或用序贯检验方法 | 一次性固定样本实验不涉及 |
| 影子版真扣了款 | 有副作用工具未 mock | 影子版直接调用真实支付 | 副作用工具在影子环境 mock | 纯只读工具影子执行安全 |

## 思考：离线评估都通过了，怎么保证线上不出问题？

### 回答

答案是分层推进、逐级释放风险，绝不从「离线通过」直接跳到「全量上线」。第一层先把离线做干净：评估集必须防三种泄漏——优化泄漏(拿评估集调 prompt/选 few-shot，等于提前看考题)、切分泄漏(同源样本被切到训练和评估两侧，等于考做过的题)、时间泄漏(用未来信息评过去决策)；做法是按 event_id 哈希整组切分、按时间点切分、held-out 从创建起锁死只在验收看一次。离线门禁里的裁判还必须是过了 Kappa 校准的(第 5 节)。第二层影子流量:新版并行处理真实线上请求但结果不返回用户，零风险地在真实分布上验证，能暴露离线集覆盖不到的长尾输入——注意有副作用的工具(扣款、发货)必须 mock，否则影子版会真的执行。第三层小流量 A/B:用真实业务指标(解决率、转化率)做裁判，且必须做统计显著性检验——同样涨 3 个点，样本量不够时可能只是噪声，z 值过 1.96 才算 95% 置信下的真差异，而且不能反复偷看中途结果一显著就停。第四层灰度放量并保留一键回滚。能把「三种泄漏 + 影子流量对副作用要 mock + A/B 要看显著性且别偷看」这几个细节讲出来，就非常专业了。

### 面试精简表达

分层推进:离线先防三种泄漏(优化/切分/时间)、held-out 锁死、裁判过 Kappa;再影子流量在真实分布零风险验证(副作用工具须 mock);再小流量 A/B 看业务指标显著性(z>1.96、别偷看);最后灰度放量可一键回滚。
