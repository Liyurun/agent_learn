## 真实问题

回到贯穿全章的客服 Agent。它上线前做过成本估算：工程师测了几个 demo 请求，发现单次模型调用大约花 $0.03，于是按「日活 2 万请求 × $0.03 ≈ $600/天」报了预算。上线第 4 天，财务把实际账单甩了过来：**日消耗接近 $6,600，是预估的 11 倍**。团队第一反应是「被攻击了」或「有 bug 在疯狂调用」，排查半天却发现请求量完全正常，就是 2 万出头。真正的问题是估算方式错了：他们用「单次调用花多少钱」乘以「请求数」做线性外推，而 Agent 的成本**根本不是线性的**。demo 里那些问题两三步就答完了，真实用户的问题平均要走 12 步，而 12 步的成本不是 3 步的 4 倍，而是十几倍。

这一节把账算对。它是全章的地基——如果你对成本的心智模型是线性的，后面所有优化手段的优先级你都会排错。

## 原理：为什么是平方级，不是线性

回顾第 4 章的 ReAct（Reasoning and Acting，推理与行动）循环：Agent 每一步都要把**到目前为止的全部历史**（原始任务 + 所有思考 + 所有工具调用 + 所有观察结果）再喂给模型一次。因为大模型本身是**无状态**的——它不记得上一轮说过什么，你每一轮都得把完整对话重新发一遍。关键就在这里：**上下文是只增不减地累积的**。

我们来推导。假设每一步新增的内容大致是 `k` 个 token（一次思考 + 一次工具结果），那么第几步读入多少：
```text
第 1 步，模型读入 ≈ 1k
第 2 步，读入 ≈ 2k    （第 1 步的历史 + 新的一步）
第 3 步，读入 ≈ 3k
...
第 n 步，读入 ≈ nk

总输入 token = k + 2k + 3k + ... + nk
            = k · (1 + 2 + 3 + ... + n)
            = k · n(n+1)/2
            ≈ O(n²)
```
看到那个 `n(n+1)/2` 了吗？这是等差数列求和，结果是 **n 的平方级**。也就是说，**任务步数翻倍，token 成本不是翻倍，而是变成约 4 倍**。这就是「平方级增长」的由来，也是 Agent 成本失控最常见、最隐蔽的坑。demo 三步、线上十二步，`12²/3² = 16` 倍——加上真实请求上下文本身更长，11 倍的账单差距就完全解释得通了。

这里要区分两层，别混淆：
- **单轮内部**：把一段长上下文喂给模型，输入费用是随 token 数**线性**的（10 万 token 就按 10 万计费）。
- **多轮之间**：因为每轮都要把不断变长的历史重发，各轮读入量本身在线性增长，各轮加总就变成了**平方级**。平方级说的是「整个任务的累计输入」，不是「单次调用」。

## 最小可运行演示

下面这段纯 Python 把平方级累积算出来，同时对照「线性直觉」的误估，让你直观看到差距。
```python
def estimate_agent_cost(n_steps, tokens_per_step=500, price_per_1k_input=0.003):
    """估算 n 步 Agent 任务的累计输入 token 与成本。
    第 step 步读入的上下文 ~= 前面所有步的累积 = step * tokens_per_step。"""
    total_input_tokens = 0
    for step in range(1, n_steps + 1):
        context_this_step = step * tokens_per_step  # 重读历史
        total_input_tokens += context_this_step
    cost = total_input_tokens / 1000 * price_per_1k_input
    # 闭式解校验：k * n(n+1)/2
    closed_form = tokens_per_step * n_steps * (n_steps + 1) // 2
    assert total_input_tokens == closed_form, "求和应等于 k*n(n+1)/2"
    return {"steps": n_steps, "total_input_tokens": total_input_tokens,
            "cost_usd": round(cost, 4)}


def linear_baseline(n_steps, tokens_per_step=500, price_per_1k_input=0.003):
    """错误的线性直觉：以为每步只花固定 token（不累积历史）。"""
    total = n_steps * tokens_per_step
    return round(total / 1000 * price_per_1k_input, 4)


def main():
    base = estimate_agent_cost(5)["cost_usd"]
    print("步数 | 累计输入token | 平方级成本$ | 相对5步倍数 | 线性直觉误估$")
    for n in [5, 10, 20, 40]:
        r = estimate_agent_cost(n)
        ratio = round(r["cost_usd"] / base, 1)
        lin = linear_baseline(n)
        print(f"{n:>4} | {r['total_input_tokens']:>12} | {r['cost_usd']:>10} "
              f"| {ratio:>10}x | {lin:>12}")
    n, agents = 20, 4
    single = estimate_agent_cost(n)["cost_usd"]
    print(f"\n多智能体：{n}步 x {agents}个Agent → 约 ${round(single*agents,4)}"
          f"（单Agent ${single} 的 {agents} 倍）")


if __name__ == "__main__":
    main()
```
保存为 `quadratic.py`，运行 `python quadratic.py`。完整预期输出：
```text
步数 | 累计输入token | 平方级成本$ | 相对5步倍数 | 线性直觉误估$
   5 |         7500 |     0.0225 |        1.0x |       0.0075
  10 |        27500 |     0.0825 |        3.7x |        0.015
  20 |       105000 |      0.315 |       14.0x |         0.03
  40 |       410000 |       1.23 |       54.7x |         0.06

多智能体：20步 x 4个Agent → 约 $1.26（单Agent $0.315 的 4 倍）
```
逐行讲解：

- 循环里 `context_this_step = step * tokens_per_step` 是关键：第 `step` 步读入的上下文，约等于前面累积的所有内容——这就是「重读历史」。`assert` 用闭式解 `k·n(n+1)/2` 校验求和，运行不报错就证明了公式。
- 看「相对 5 步倍数」这一列：5→10 步（步数翻倍），成本从 1.0x 到 3.7x（近 4 倍）；10→20 又近 4 倍（3.7→14）；40 步已是 54.7 倍。而「线性直觉误估」那一列几乎不动（0.0075→0.06 只涨 8 倍且是线性的），**两列的鸿沟就是很多人算错账的地方**。
- 最后一行提醒：这只算了**输入** token，真实还要叠加输出 token；而多智能体系统是**平方级之上再乘 Agent 数**，成本更凶猛（回扣第 11 章「多智能体很贵」的告诫）。

## 平方级增长意味着什么

把上面这张表翻译成工程直觉：

| 步数 n | 累计输入 token | 相对 5 步 | 直觉 |
|---|---|---|---|
| 5 | 7,500 | 1× | 基线 |
| 10 | 27,500 | ≈3.7× | 步数翻倍，成本近 4 倍 |
| 20 | 105,000 | ≈14× | 再翻倍，又近 4 倍 |
| 40 | 410,000 | ≈55× | 失控 |

这张表给出一个极重要的结论：**控制 Agent 成本，第一优先级不是「换便宜模型」，而是「减少步数、压缩上下文」**。因为成本对步数是平方敏感的，砍掉一半步数（12→6），成本降到约四分之一；而换一个便宜 20% 的模型，成本只降 20%。同样的工程投入，前者的回报是后者的好几倍。这条优先级贯穿全章：第 2 节的分层路由动的是「单价」因子，第 6 节的上下文压缩动的是「每步 token」因子，而减步数动的是那个被平方放大的「步数」因子——**动被平方的那个因子，杠杆最大**。

## 真实系统对应

**官方公开机制**：两家厂商都按 token 计费、都要求多轮对话每轮重发完整消息历史（无状态），这是平方级累积的直接来源；Anthropic 与 OpenAI 都公开 `usage` 字段（输入/输出 token 计数），可用于逐轮观测累积量 [来源](https://platform.openai.com/docs/guides/prompt-caching)。**通用工程模式**：用「平均步数 × 平均上下文长度」而非「调用次数」来估算与监控成本，是可迁移到任何厂商的做法。**教学参考实现**：上面的 `tokens_per_step=500`、`price_per_1k=0.003` 都是示例常数，真实值随模型与定价页变化，以官方文档为准；这段代码只为把平方级的**形状**讲清楚，不代表任何具体账单。

一个来自公开工程经验的推论：正因为累积，第 3 节的 prompt caching 才这么值钱——它让那段每轮重发的稳定前缀只在第一次全价、后续大幅打折，相当于把平方级里「不变的那部分」摊平。而第 6 节的上下文压缩，则是直接砍掉累积历史里的冗余，从源头降低每一步的 `k`。

## 生产踩坑

| 症状 | 根因 | 如何观测与复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| 上线后账单是预估的数倍 | 用单次调用成本做线性外推 | 对比压测平均步数与线上平均步数 | 按平方级模型重估，监控平均步数 | 单步问答型应用近似线性 |
| Agent 没死循环但每次都很贵 | 平均步数远超预期，磨蹭绕路 | 打点记录每请求实际步数分布 | 优化 prompt 减绕路、工作流固化路径 | 本就需要多步的复杂任务另设预算 |
| 只监控调用次数，漏掉成本异常 | 调用数正常但单请求 token 暴涨 | 对比调用次数曲线与 token 曲线 | 监控"平均上下文长度"与"平均步数" | 固定长度请求波动可忽略 |
| 换了便宜模型仍降不下来 | 动错因子，没碰被平方的步数 | 对比砍半步数 vs 换模型的降幅 | 优先减步数、压上下文 | 单价差达数量级时换模型也显著 |
| 多智能体成本爆炸 | 平方级之上再乘 Agent 数 | 统计每个子 Agent 的累计 token | 减少子 Agent 数、共享上下文 | 任务确需并行专家时权衡 |

## 思考：为什么 Agent 的 token 成本是平方级而非线性？为什么「减步数」比「换便宜模型」更该优先？

### 回答

分两问答。第一问，平方级的根源是「无状态模型 + 只增不减的上下文累积」：模型不记得上一轮，每一步都要把到目前为止的全部历史重发一次，所以第 n 步读入约 `nk` token，n 步加总是 `k·(1+2+…+n) = k·n(n+1)/2`，即 O(n²)。直观后果是步数翻倍、成本近 4 倍。注意平方级说的是「整个任务的累计输入」，单次调用内部仍是按 token 线性计费——别把两层混了。第二问，因为成本对步数是**平方敏感**、对单价是**线性敏感**：砍掉一半步数，成本降到约 1/4；换个便宜 20% 的模型，成本只降 20%。同样的工程投入，动「被平方放大的那个因子（步数）」的杠杆远大于动单价。所以降本第一优先级是减步数、压上下文，其次才是分层路由换单价。多智能体还要在平方级之上再乘 Agent 数，更要先从「能不能少几个 Agent、少几步」入手。

### 面试精简表达

模型无状态、每轮重发累积历史，输入 token 是 k·n(n+1)/2 即 O(n²)，步数翻倍成本近 4 倍；成本对步数平方敏感、对单价线性敏感，所以减步数/压上下文的杠杆远大于换便宜模型。

## 机制推导：单请求内部线性、任务整体平方，两个视角别打架

有人会质疑：「模型按 token 线性计费，怎么会是平方级？」这是把两个视角搞混了。把它拆开看就清楚了。

设第 i 步读入 `L_i` token，单价 `p`。**单步成本** `= p · L_i`，对该步的上下文长度是**线性**的——这没错，把 10 万 token 喂进去就按 10 万算。但在多轮任务里，`L_i` 本身随 i 增长（`L_i ≈ i·k`），于是**任务总成本** `= p · Σ L_i = p · Σ i·k = p·k·n(n+1)/2`，对**步数 n** 是**平方**的。两个视角都对，只是自变量不同：固定一次调用看 token，是线性；沿着整个任务看步数，是平方。

这个推导还解释了两件事。其一，为什么 prompt caching 能大幅削平账单：那段每轮重发的稳定前缀，在累积里是一个「每步都出现的常数块」，把它从全价降到 0.1x，等于把平方级三角形里最厚的一层几乎抹平。其二，为什么「上下文窗口够大」不等于「用得起」：窗口是能力上限，费用却随你实际塞进去的 token 平方级累积——能塞 100 万 token 不代表你负担得起每轮都塞满。工程上真正该守的不是「别超窗口」，而是「让每一步只带它真正需要的上下文」，这正是第 6 节上下文压缩要解决的。
