## 真实问题

客服 Agent 上线后有一类投诉最让人头疼：「有时候快，有时候要等十几秒，没个准。」团队想优化，却卡在第一步——**「太慢」是个没法直接下手的抽象抱怨**。有人拍脑袋说「肯定是模型推理慢，换个快模型」，换了之后 P50（中位数延迟）没什么改善，那些「偶尔十几秒」的请求照样十几秒。真正一测才发现，慢的根源根本不在模型：**某个外部物流查询 API 偶尔会卡 3 秒以上（P99），而这类慢请求恰好集中在复杂订单——也就是最重要的那批用户**。同时，随着对话变长，每一步重读的历史越堆越厚，把每步的推理时间也拖长了。

这一节讲两件事：怎么把「太慢」拆成可测量的环节做**延迟预算分解**（先量化再优化，且要看 P95/P99 尾延迟而非平均值）；以及怎么用**上下文压缩**从源头砍掉每一步重读的冗余历史——它同时降延迟（每步 token 少了）和降成本（呼应第 1 节的平方级）。

## 原理：延迟预算分解与尾延迟

一次 Agent 请求的延迟，可以拆成一串可测量的环节：
```text
总延迟 = Σ(每一步的延迟)，而每一步 =
   ┌─ 网络往返               ~50ms
   ├─ 排队 / 冷启动          0 ~ 数百 ms
   ├─ 模型推理(TTFT + 生成)   数百 ms ~ 数秒   ← 通常大头
   ├─ 工具执行(可能调外部API)  0 ~ 数秒        ← 可能是隐藏大头
   └─ 框架开销(序列化等)       ~几十 ms
```
分解的价值在于**对症下药**：瓶颈在模型推理，就换更快的模型、缩短输出、用流式降感知延迟；瓶颈在工具执行（某外部 API 慢），就加缓存、并行、超时降级；瓶颈在步数太多，就优化 prompt 减少绕路，或用工作流固化路径（回扣第 10 章）。**没有分环节的计时，「太慢」就是一句无法行动的抱怨；有了它，你能一眼看出时间花在哪。**

还有一个比「先测量」更反直觉、也更重要的点：**看 P95/P99 尾延迟，而不是平均值**。平均延迟会被大量快请求拉低，掩盖掉少数极慢的请求；而那少数极慢的请求（P99）往往正是你最复杂、最重要的那批。一个平均 1 秒的系统，P99 可能高达 15 秒——那 1% 的用户体验极差，且他们常常是付费大客户。

## 原理：上下文压缩为什么同时降本又降延迟

第 1 节讲过，输入 token 随步数平方级累积，源头是「每一步都重读全部历史」。上下文压缩就是从源头动手：**在把历史喂给模型前，砍掉其中的冗余，只保留关键信息**。因为这段历史每一步都要重发，压缩的收益会被多轮**放大**——每步少 30% token，在十轮对话里就是持续少 30%。

压缩的核心原则是**「删冗余不删证据」**：寒暄、重复确认、已被后续覆盖的中间过程可以删；但关键实体（订单号、金额、物流单号）、关键结论、当前意图必须保留。常见做法有几类：保留最近 N 轮 + 摘要更早的历史（滑动窗口 + 摘要）、只保留结构化的关键事实、用小模型或专门的压缩模型（如 Microsoft 的 LLMLingua，宣称最高约 20x 压缩）判定每个 token 的去留 [来源](https://github.com/microsoft/LLMLingua)。

## 最小可运行演示

分两段。第一段是延迟预算分解 + 尾延迟；第二段是上下文压缩。都是纯 Python，不联网、不需要 API Key。
```python
import time
from contextlib import contextmanager


class LatencyTracker:
    def __init__(self):
        self.spans = {}

    @contextmanager
    def track(self, name):
        start = time.perf_counter()
        yield
        self.spans[name] = self.spans.get(name, 0.0) + (time.perf_counter() - start)

    def report(self):
        total = sum(self.spans.values())
        print("环节            耗时      占比")
        for name, t in sorted(self.spans.items(), key=lambda x: -x[1]):
            print(f"{name:<14} {t*1000:>6.0f}ms   {t/total*100:>5.1f}%")


def percentile(sorted_vals, p):
    k = max(1, -(-p * len(sorted_vals) // 100))  # 向上取整的最近秩法
    return sorted_vals[k - 1]


def main():
    tracker = LatencyTracker()
    with tracker.track("网络往返"):
        time.sleep(0.05)
    with tracker.track("模型推理"):
        time.sleep(0.30)
    with tracker.track("工具执行"):
        time.sleep(0.12)
    with tracker.track("框架开销"):
        time.sleep(0.02)
    tracker.report()
    print("→ 瓶颈一目了然：模型推理占大头，先优化它\n")

    samples = [1.0] * 99 + [15.0]   # 99 个 1s + 1 个 15s 长尾
    avg = sum(samples) / len(samples)
    s = sorted(samples)
    print(f"延迟样本(100次): 平均 {avg:.2f}s, P50 {percentile(s,50):.2f}s, "
          f"P95 {percentile(s,95):.2f}s, P99 {percentile(s,99):.2f}s")
    print("→ 平均 1.14s 看着漂亮，但 P99 高达 15s：只看平均会漏掉尾延迟。")


if __name__ == "__main__":
    main()
```
保存为 `latency.py`，运行 `python latency.py`。完整预期输出：
```text
环节            耗时      占比
模型推理              300ms    61.2%
工具执行              120ms    24.5%
网络往返               50ms    10.2%
框架开销               20ms     4.1%
→ 瓶颈一目了然：模型推理占大头，先优化它

延迟样本(100次): 平均 1.14s, P50 1.00s, P95 1.00s, P99 15.00s
→ 平均 1.14s 看着漂亮，但 P99 高达 15s：只看平均会漏掉尾延迟。
```
第二段，上下文压缩：
```python
## 模拟一段较长的 Agent 历史：(角色, 文本, token 数, 是否关键结论)
HISTORY = [
    ("system", "你是客服助手，遵守以下规则……", 1200, True),
    ("user", "我想查一下我的订单", 30, False),
    ("assistant", "好的，请提供订单号", 20, False),
    ("user", "订单号 A123", 15, True),                          # 关键实体
    ("tool", "订单A123：已发货，预计3天到达，物流单号SF888", 60, True),
    ("assistant", "您的订单已发货，物流单号 SF888", 40, False),
    ("user", "那我上次退货的进度呢", 25, True),                  # 新关键意图
    ("assistant", "让我查一下……（大段寒暄与重复确认）", 300, False),
    ("tool", "退货RMA-77：退款已到账 ¥199", 50, True),          # 关键事实
    ("user", "好的谢谢", 10, False),
]
PRICE_PER_1K = 0.003


def raw_tokens(h):
    return sum(tk for _, _, tk, _ in h)


def compress(h, keep_recent=2):
    """保留 system + 所有关键结论 + 最近 keep_recent 条。"""
    n = len(h)
    return [(r, t, tk, k) for i, (r, t, tk, k) in enumerate(h)
            if r == "system" or k or i >= n - keep_recent]


def cost(tokens):
    return tokens / 1000 * PRICE_PER_1K


def main():
    raw, comp = raw_tokens(HISTORY), raw_tokens(compress(HISTORY))
    print(f"压缩前：{len(HISTORY)} 条，{raw} tokens，单轮 ${cost(raw):.5f}")
    print(f"压缩后：{len(compress(HISTORY))} 条，{comp} tokens，单轮 ${cost(comp):.5f}")
    ratio = comp / raw
    print(f"压缩比：{ratio*100:.0f}%（省 {(1-ratio)*100:.0f}% 输入 token）")
    turns = 10
    print(f"\n{turns} 轮对话（历史每轮重发）累计：未压缩 ${cost(raw*turns):.4f} "
          f"→ 压缩后 ${cost(comp*turns):.4f}（省 {(1-ratio)*100:.0f}%）")
    print("被删的是寒暄与重复确认，保留了订单号/物流单号/退款等关键事实——"
          "压缩的关键是'删冗余不删证据'。")


if __name__ == "__main__":
    main()
```
保存为 `compression.py`，运行 `python compression.py`。完整预期输出：
```text
压缩前：10 条，1750 tokens，单轮 $0.00525
压缩后：6 条，1360 tokens，单轮 $0.00408
压缩比：78%（省 22% 输入 token）

10 轮对话（历史每轮重发）累计：未压缩 $0.0525 → 压缩后 $0.0408（省 22%）
被删的是寒暄与重复确认，保留了订单号/物流单号/退款等关键事实——压缩的关键是'删冗余不删证据'。
```
逐行讲解：

- `LatencyTracker` 用上下文管理器给每个环节计时，`report` 按耗时降序打印占比——**这正是第 17 章 tracing（追踪）在延迟优化上的具体应用**。本例模型推理占 61%，那就先优化推理，而不是瞎调网络或框架。
- `percentile` 用向上取整的最近秩法算分位数：99 个 1s + 1 个 15s 的样本，平均 1.14s、P50/P95 都是 1s 很漂亮，但 P99 是 15s。**这就是「关注 P95/P99 而非平均」的量化理由**——那 1% 的极慢请求被平均值完全掩盖了。
- 压缩演示里 `compress` 保留了 system、所有标 `key=True` 的关键条目、以及最近 2 条，删掉了「你好/请提供订单号/大段寒暄」等冗余，省 22% token。在 10 轮对话里这 22% 会被持续放大——注意被删的都是冗余，订单号、物流单号、退款金额这些**证据**一个没丢。

## 真实系统对应

**官方公开机制**：TTFT/TPOT/尾延迟是推理服务基准测试的标准指标 [来源](https://arxiv.org/abs/2309.06180)；两家 API 的 `usage` 字段可用于逐轮统计上下文 token 量。Microsoft LLMLingua 是有论文与开源实现的提示压缩方法 [来源](https://github.com/microsoft/LLMLingua)。**通用工程模式**：延迟预算分解、P95/P99 监控、滑动窗口 + 摘要压缩、只保留结构化关键事实，都是可迁移到任何系统的做法，LangSmith 等追踪平台能把各环节耗时可视化。**教学参考实现**：上面的计时用 `sleep` 模拟，压缩用「关键字标记」这种启发式；真实系统的压缩要么用小模型/LLMLingua 判定去留，要么用结构化状态（第 6 章）替代原始对话，阈值与策略需按业务校准。

一条边界：上下文压缩是**有损**的——删错了会丢失后续需要的信息，导致模型答错或反复追问。所以压缩要保守，宁可多留一点关键上下文，也别为了省 token 把证据删了；高风险场景应保留原始历史的可追溯副本（哪怕不喂给模型），以备审计与回溯。

## 生产踩坑

| 症状 | 根因 | 如何观测与复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| 换快模型后慢请求依旧 | 瓶颈不在推理而在某外部工具 | 分环节计时看占比 | 先测量定位再对症下药 | 推理确是瓶颈时换模型有效 |
| 平均延迟漂亮但投诉不断 | 只看平均、忽略 P99 尾延迟 | 画 P50/P95/P99 分布 | 监控并优化尾延迟 | 负载极均匀时尾部不突出 |
| 复杂订单请求特别慢 | 慢集中在最重要的那批请求 | 按请求类型分桶看延迟 | 对慢桶单独加缓存/并行 | 简单请求快不代表整体好 |
| 压缩后模型答错/反复追问 | 压缩删掉了后续需要的信息 | 对比压缩前后回答质量 | 保守压缩、保留关键实体 | 无时效的静态背景可多压 |
| 压缩省不了多少 | 只删了短寒暄、没动大块冗余 | 统计各类内容 token 占比 | 摘要长历史、去重工具结果 | 历史本就精简则收益小 |
| 上下文越滚越长直到超窗口 | 从不压缩、无限累积 | 监控每轮上下文长度曲线 | 滑动窗口 + 摘要封顶 | 短对话不会触顶 |

## 思考：怎么做延迟预算分解？为什么优化前要先测量、且要看 P95/P99 而非平均值？

### 回答

延迟预算分解就是把一次请求的总延迟拆成可测量的环节——网络往返、排队/冷启动、模型推理（TTFT + 生成）、工具执行、框架开销——给每个环节打点计时、算出占比，从而定位瓶颈。之所以要**先测量再优化**，是因为「太慢」是抽象抱怨、无法直接行动，且人的直觉经常错：很多人以为慢在模型推理，一测才发现是某个外部工具 API 偶尔卡几秒。测出瓶颈才能对症下药——瓶颈在推理就换快模型/缩输出/流式，在工具就加缓存/并行/超时，在步数就减绕路。之所以要看 **P95/P99 而非平均**，是因为平均值会被大量快请求拉低、掩盖掉少数极慢请求：一个平均 1 秒的系统 P99 可能高达 15 秒，那 1% 的用户体验极差，而这 1% 往往是你最复杂、最重要（甚至最付费）的请求。只盯平均值，你会对最该救的那批用户视而不见。配套地，上下文压缩能从源头降低每步 token，因历史每轮重发、收益被多轮放大，但压缩有损、要「删冗余不删证据」。

### 面试精简表达

延迟预算分解=把总延迟拆到网络/推理/工具/框架各环节计时找瓶颈；先测量因直觉常错（以为推理慢其实是外部工具卡），对症下药；看 P95/P99 因平均值掩盖尾延迟，而极慢的 1% 往往是最重要的请求；上下文压缩从源头降每步 token、收益被多轮放大，但要删冗余不删证据。

### 反例

「优化前先换个更强更快的模型」是常见反例：没测量就动手，结果瓶颈在外部物流 API，换模型对那些「偶尔十几秒」的请求毫无帮助，白花钱还耽误时间。正确顺序永远是先分环节测量、看尾延迟、定位瓶颈，再动手。
