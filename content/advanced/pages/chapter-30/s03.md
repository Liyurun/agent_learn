## 真实问题

客服 Agent 的第二个成本大头，是**为重复的东西反复付钱**。拉用量明细看到两处触目惊心的重复：其一，一段 4,000 token 的稳定内容——系统提示（角色、安全规则）+ 四个工具的完整定义 + 几条 few-shot 示例——在一次六轮对话里被**原封不动重发了六次**，每次按输入 token 全价计费，这段「每轮都一样」的内容占了输入成本的一多半；其二，客服场景里大量问题是**高度重复**的——「怎么退货」「运费多少」「营业时间」，同一个问题一天被不同用户问几百遍，每一遍都完整跑一次模型。前者是「重复传、重复收费」，后者是「重复算、重复收费」。

这一节讲缓存——本质就是「算过的别再算、传过的别再收全价」。但缓存有三种层次完全不同的机制，很多人混为一谈，面试一问就露馅。本节把三者彻底讲清：它们分别省什么、匹配方式有何不同、各自在什么情况下失效。

## 原理：三层缓存，各管一段

### KV Cache：推理引擎内部的加速器

先厘清一个底层概念。Transformer 生成每个 token 时，需要用到前面所有 token 的 Key、Value 向量做注意力计算。**KV Cache（Key-Value Cache，键值缓存）** 就是把这些算过的 K、V 向量存起来，生成下一个 token 时直接复用，不必重算整段前缀。它是模型推理引擎（如 vLLM）内部的机制，**主要加速的是「输出阶段」——即逐 token 生成的速度**。这里的核心工程挑战是显存管理：朴素实现要给每条序列预留连续显存、浪费严重，vLLM 的 **PagedAttention** 把 KV 缓存像操作系统的分页内存一样切成固定大小的块（block）管理，实现近零浪费并支持前缀共享，是现代高吞吐推理引擎的基础 [来源](https://arxiv.org/abs/2309.06180)。作为应用层开发者你通常不用手动管 KV Cache，但理解它是理解 prompt caching 的基础——prompt caching 本质就是把 KV Cache 的复用暴露成一个你能主动用的、跨请求的省钱功能。

### Prompt Caching：把长前缀的钱省掉

**Prompt Caching（提示缓存）** 是供应商提供的、你能主动利用的省钱功能：如果多次请求共享**相同的前缀**（比如都带同一段几千 token 的系统提示、工具定义、few-shot），供应商可以缓存这段前缀的计算结果，后续请求命中缓存的部分**大幅降价**。

两家的公开机制与计费（以当前官方文档为准）：
- **OpenAI**：自动生效、无需改代码，对 gpt-4o 及更新模型开启；前缀需**至少 1,024 token** 才可能命中；缓存输入相对全价打折，常见约 50%，更新的模型家族折扣更高（可达约 90%）[来源](https://platform.openai.com/docs/guides/prompt-caching)。
- **Anthropic**：用 `cache_control` 断点显式声明缓存哪段；计费倍率清晰——**5 分钟 TTL（Time To Live，生存时间）写入 1.25x、1 小时 TTL 写入 2x、命中读取 0.1x**（即命中后约九折优惠）；命中会刷新 TTL [来源](https://docs.anthropic.com/en/docs/build-with-claude/prompt-caching)。

关键在于：**缓存匹配的是「前缀」，且要逐字节相同**。这决定了 prompt 的组织铁律——**把稳定不变的内容放前面，把每次都变的内容放后面**：
```text
✅ 缓存友好的 prompt 结构：
   ┌──────────────────────────┐
   │ [稳定前缀 · 可缓存]       │  系统指令 + 工具定义 + few-shot
   │   每轮逐字节相同          │  ← 命中缓存，按 0.1x（或折扣价）计费
   ├──────────────────────────┤
   │ [动态后缀 · 不缓存]       │  当前对话历史 + 用户新问题
   │   每轮都变                │  ← 正常全价计费
   └──────────────────────────┘

❌ 缓存不友好：把"当前时间/用户名"这种每次都变的东西放最前面
   → 前缀一变，整段缓存全部失效，一分钱没省到，还白交写入溢价
```
### 语义缓存：连模型都不用调

前两种缓存都还要调模型（prompt caching 只是让输入前缀便宜）。**语义缓存（Semantic Cache）** 更狠——如果一个新问题和之前问过的某个问题**语义足够接近**，直接返回上次的答案，**根本不调模型，成本趋近于零、延迟趋近于零**。

它和普通缓存的区别是匹配方式：普通缓存要求 key **完全相等**（「北京天气」≠「北京的天气」），语义缓存用**向量相似度**匹配（「北京天气」≈「北京的天气怎么样」，相似度够高就命中）。实现上就是把问题过一个 embedding 模型转成向量，在向量库里找最相似的历史问题（回扣第 5 章的向量检索），相似度超过阈值就复用其答案。

## 最小可运行演示

分两段。第一段模拟 prompt caching 的前缀计费，对比「缓存友好」「不缓存」「时间戳污染前缀」三种结构在 6 轮对话下的累计成本（计费倍率参考 Anthropic 公开值，价格为示例）：
```python
BASE = 3.00               # 基础输入价：$/1M token（示例）
WRITE_MULT = 1.25         # 5 分钟缓存写入 1.25x（Anthropic 公开倍率）
HIT_MULT = 0.10           # 命中读取 0.1x（约 90% 折扣）
STABLE_PREFIX_TOKENS = 4000
NEW_TOKENS_PER_TURN = 300
TURNS = 6


def price(tokens, mult):
    return BASE * tokens / 1_000_000 * mult


def cost_no_cache():        # 前缀每轮全价重发
    return sum(price(STABLE_PREFIX_TOKENS, 1.0) + price(NEW_TOKENS_PER_TURN, 1.0)
               for _ in range(TURNS))


def cost_cache_friendly():  # 首轮写入 1.25x，后续命中 0.1x
    total = 0.0
    for turn in range(1, TURNS + 1):
        total += price(STABLE_PREFIX_TOKENS, WRITE_MULT if turn == 1 else HIT_MULT)
        total += price(NEW_TOKENS_PER_TURN, 1.0)
    return total


def cost_prefix_poisoned():  # 时间戳污染：每轮当新前缀写入，从不命中
    return sum(price(STABLE_PREFIX_TOKENS, WRITE_MULT) + price(NEW_TOKENS_PER_TURN, 1.0)
               for _ in range(TURNS))


def main():
    a, b, c = cost_no_cache(), cost_cache_friendly(), cost_prefix_poisoned()
    print(f"不用缓存            6轮累计 ${a:.5f}  (基线)")
    print(f"缓存友好(稳定前缀在前) 6轮累计 ${b:.5f}  省 {(1-b/a)*100:.0f}%")
    print(f"时间戳污染前缀      6轮累计 ${c:.5f}  "
          f"比不缓存还贵 {(c/a-1)*100:.0f}%（写入溢价白交，从不命中）")


if __name__ == "__main__":
    main()
```
保存为 `promptcache.py`，运行 `python promptcache.py`。完整预期输出：
```text
不用缓存            6轮累计 $0.07740  (基线)
缓存友好(稳定前缀在前) 6轮累计 $0.02640  省 66%
时间戳污染前缀      6轮累计 $0.09540  比不缓存还贵 23%（写入溢价白交，从不命中）
```
第二段演示语义缓存与「阈值是把双刃剑」（用确定性玩具 embedding，不需真实模型）：
```python
import math

VOCAB = ["北京", "上海", "天气", "怎么样", "如何", "订单", "状态", "查询", "余额"]


def embed(text):
    return [float(text.count(w)) for w in VOCAB]  # 玩具词袋向量


def cosine(a, b):
    dot = sum(x * y for x, y in zip(a, b))
    na, nb = math.sqrt(sum(x*x for x in a)), math.sqrt(sum(y*y for y in b))
    return dot / (na * nb + 1e-9)


class SemanticCache:
    def __init__(self, threshold=0.92):
        self.threshold, self.store = threshold, []

    def get(self, q):
        qv = embed(q)
        best_ans, best_q, best_sim = None, None, 0.0
        for vec, oq, ans in self.store:
            sim = cosine(qv, vec)
            if sim > best_sim:
                best_ans, best_q, best_sim = ans, oq, sim
        if best_sim >= self.threshold:
            return {"hit": True, "answer": best_ans, "matched": best_q,
                    "sim": round(best_sim, 3)}
        return {"hit": False, "sim": round(best_sim, 3)}

    def put(self, q, ans):
        self.store.append((embed(q), q, ans))


def main():
    cache = SemanticCache(threshold=0.92)
    cache.put("北京天气怎么样", "北京今天晴，12 度")
    for q in ["北京天气怎么样", "北京的天气怎么样", "上海天气怎么样", "查询我的订单状态"]:
        r = cache.get(q)
        if r["hit"]:
            print(f"[命中 sim={r['sim']}] '{q}' → 复用『{r['matched']}』，0 次模型调用")
        else:
            print(f"[未命中 sim={r['sim']}] '{q}' → 需真调模型")
    print("\n--- 把阈值下调到 0.5（危险演示）---")
    loose = SemanticCache(threshold=0.5)
    loose.put("北京天气怎么样", "北京今天晴，12 度")
    r = loose.get("上海天气怎么样")
    print(f"'上海天气怎么样' → hit={r['hit']} sim={r['sim']}"
          f"（阈值太低把不同城市误判为同一问题，返回过时/错误答案）")


if __name__ == "__main__":
    main()
```
保存为 `semantic.py`，运行 `python semantic.py`。完整预期输出：
```text
[命中 sim=1.0] '北京天气怎么样' → 复用『北京天气怎么样』，0 次模型调用
[命中 sim=1.0] '北京的天气怎么样' → 复用『北京天气怎么样』，0 次模型调用
[未命中 sim=0.667] '上海天气怎么样' → 需真调模型
[未命中 sim=0.0] '查询我的订单状态' → 需真调模型

--- 把阈值下调到 0.5（危险演示）---
'上海天气怎么样' → hit=True sim=0.667（阈值太低把不同城市误判为同一问题，返回过时/错误答案）
```
逐行讲解：

- prompt caching 演示里，「缓存友好」省 66%——首轮花了 1.25x 写入溢价，后续五轮的前缀都按 0.1x 命中，把那段 4,000 token 的重复几乎抹平。「时间戳污染」则是经典事故：把每轮都变的时间戳放前缀最前，导致前缀逐轮不同，**每轮都当新前缀写入、从不命中，不但没省钱还比不缓存贵 23%**（白交了写入溢价）。这就是「把当前时间放 prompt 最前面会击穿缓存」的量化证明。
- 语义缓存演示里，`threshold=0.92` 时，「北京天气怎么样」和「北京的天气怎么样」都命中（0 次模型调用），而「上海天气怎么样」（sim=0.667）正确地不命中——**否则会把上海的问题返回北京的答案，这是灾难**。危险演示把阈值降到 0.5，「上海天气」立刻误命中「北京天气」，返回错答案。这说明阈值**宁可偏高（保守）**：偏低会返回错答案，偏高只是少省点钱。

## 三种缓存对比

| 缓存 | 匹配方式 | 省什么 | 适用场景 | 主要风险/失效条件 |
|---|---|---|---|---|
| KV Cache | 引擎内部前缀（分块显存） | 输出阶段算力与延迟 | 自动，几乎总有效 | 应用层基本无需操心 |
| Prompt Caching | 前缀逐字节相等 | 输入 token 费用（大幅折扣） | 长而稳定的系统提示/工具定义 | 前缀被污染（时间戳等）则全失效 |
| 语义缓存 | 向量相似度超阈值 | 整次模型调用（成本≈0） | 答案稳定的重复问题（FAQ） | 阈值过低返回错答案；答案时效性 |

## 真实系统对应

**官方公开机制**：OpenAI 自动 prompt caching（1024 token 起、约 50%~90% 折扣）与 Anthropic `cache_control`（5 分钟/1 小时 TTL、写入 1.25x/2x、命中 0.1x）都是有文档支撑的产品功能 [来源](https://platform.openai.com/docs/guides/prompt-caching) [来源](https://docs.anthropic.com/en/docs/build-with-claude/prompt-caching)；KV Cache 与 PagedAttention 是 vLLM 论文明确描述的推理引擎机制 [来源](https://arxiv.org/abs/2309.06180)。**通用工程模式**：语义缓存（embedding + 向量库 + 阈值 + 时效控制）是可迁移到任何厂商的应用层设计，开源的 GPTCache 等就是这类实现。**教学参考实现**：上面的价格、倍率、玩具 embedding 都是示例；真实系统用真实 embedding 模型与向量库做近似最近邻检索，而非线性遍历。TTL 具体值、折扣具体数会随官方定价变化，以当前文档为准。

一条容易忽略的边界：语义缓存**只适合答案相对稳定的问题**（政策类 FAQ、知识问答）。像「我最新一笔订单的状态」这种答案随时间变的，**绝对不能语义缓存**——会返回过期的旧状态。缓存什么、不缓存什么，是语义缓存最关键、也最容易出事的设计决策。

## 生产踩坑

| 症状 | 根因 | 如何观测与复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| prompt cache 命中率≈0 | 时间戳/随机值污染了前缀 | 把动态内容放前缀最前复现 | 稳定内容放前、动态放后 | 无重复前缀的一次性请求 |
| 缓存启用后反而更贵 | 频繁写入但很少命中（间隔超 TTL） | 统计写入次数 vs 命中次数 | 请求间隔长选 1 小时 TTL | 命中远多于写入时才划算 |
| 语义缓存返回错答案 | 相似度阈值调得太低 | 用近义不同义问题对测 | 阈值宁高勿低、用真实数据校准 | 完全精确匹配场景无此风险 |
| 语义缓存返回过期状态 | 缓存了时效性强的答案 | 缓存"订单状态"后改状态复现 | 只缓存答案稳定的问题 | 静态知识 FAQ 可放心缓存 |
| 前缀差一个空格就不命中 | 未意识到需逐字节相同 | 改动前缀一个字符对比 | 固化前缀模板、版本化管理 | 前缀本就每次不同则不适用 |
| 缓存命中率骤降没人知道 | 未监控命中率指标 | 上线改动后看命中率曲线 | 把缓存命中率纳入监控告警 | 无缓存的系统不涉及 |

## 思考：KV Cache、prompt caching、语义缓存分别省什么？为什么把时间戳放 prompt 最前面会击穿缓存？

### 回答

三者是完全不同的三层，分别省不同的东西。**KV Cache** 是推理引擎内部机制，缓存前面 token 的 K、V 向量、加速逐 token 生成，省的是**输出阶段的算力与延迟**，应用层通常自动享受、无需操心（vLLM 用 PagedAttention 分块管理显存来支撑它）。**Prompt caching** 是供应商给你的功能，缓存请求里**逐字节相同的稳定前缀**，命中后这段前缀大幅打折，省的是**输入 token 费用**（Anthropic 命中约 0.1x、OpenAI 约五到九折）。**语义缓存**是应用层设计，用**向量相似度**判断新问题是否与历史问题足够像，够像就直接返回旧答案，省的是**整次模型调用**（成本、延迟都趋近于零）。至于时间戳击穿：prompt caching 命中的前提是前缀**逐字节相同**，缓存系统按前缀哈希路由；把「当前时间」这种每轮都变的内容放在 prompt 最前面，会让每一轮的前缀都不同，于是永远无法命中已有缓存，每轮都被当成新前缀重新写入——不但没省钱，反而白交了写入溢价，比不用缓存还贵。正确做法是把不变的（系统提示、工具定义）放前面，把变的（时间、用户输入）放后面。

### 面试精简表达

KV Cache 省输出算力（引擎内部）、prompt caching 省输入费（缓存逐字节相同的前缀）、语义缓存省整次调用（向量相似度匹配）；时间戳放前缀最前会让前缀逐轮不同、永不命中，击穿缓存还白交写入溢价，所以稳定内容放前、动态内容放后。

### 反例

「给每条用户消息都开语义缓存」是危险反例：对「我的订单到哪了」这类时效性答案，语义缓存会把上次的旧状态返回给这次的用户，造成信息错误。语义缓存只适合答案稳定的问题，且阈值要保守。
