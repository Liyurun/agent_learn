## 真实问题

客服 Agent 团队还有两条业务线在烧钱和拖慢，方向截然不同。第一条是**离线**的：每晚要给当天新增的一万条用户评论做情感标注和分类，用来生成运营日报。工程师一开始用在线接口一条条实时调，跑一晚上不说，还按实时价全额付费——可这活儿**根本不急**，明早看到结果就行。第二条是**在线**的：Agent 回答「帮我核对一下这笔订单」时，要同时查订单系统、查物流、查退货政策三个相互独立的接口，工程师写成了串行——查完订单再查物流再查政策，每个约 0.2 秒，一轮下来 0.6 秒白白耗在「排队等待」上，用户嫌卡。

这两条线对应两种不同的优化：能等的任务用**批处理**换极致便宜；在线的独立调用用**并行**抢回墙上时间。这一节讲清它们各自的适用边界——**判据是一句话：结果是现在就要，还是可以等？**

## 原理：批处理省钱、并行省时间

### 批处理（Batching）：吞吐换延迟

如果你有大量**不要求实时**的任务，可以把它们**打包成批**一次性提交给供应商的批处理 API。它在后台错峰调度、异步处理，因此价格显著更低，代价是**不保证即时返回**。两家的公开机制：
- **OpenAI Batch API**：异步提交、**50% 折扣**、独立且更高的限流额度、**24 小时**周转承诺 [来源](https://developers.openai.com/api/docs/guides/batch)。
- **Anthropic Message Batches API**：对**输入和输出都打 50% 折扣**，用于大批量异步处理；同样有明确的批处理窗口 [来源](https://platform.claude.com/docs/en/build-with-claude/batch-processing)。

批处理的适用判断很简单：**结果用户是现在就要，还是可以等？** 能等的（离线评估、数据标注、批量摘要、日报生成）走批处理省一半；不能等的（在线对话）就老实实时调。

### 并发吞吐：区分「墙上时间」与「吞吐量」

在线场景要抢的是**墙上时间（wall-clock time，也叫端到端延迟）**——用户从发问到拿到答案的真实秒数。一个 Agent 一步里如果要调用多个**相互独立**的工具，串行执行是「等完一个再等下一个」，墙上时间是各者之和；**并行执行**让它们同时跑，墙上时间约等于**最慢的那一个**。
```text
串行（慢）：查订单(0.2s) ─▶ 查物流(0.2s) ─▶ 查政策(0.2s)   墙上时间 0.6s
                                                    ▲
并行（快）：查订单(0.2s) ┐
           查物流(0.2s) ├─ 同时进行                墙上时间 ≈ 0.2s（最慢那个）
           查政策(0.2s) ┘
```
这里要和第 5 节的两个推理引擎指标区分开，别混淆：
- **TTFT（Time To First Token，首 token 延迟）**：请求发出到吐出第一个字的时间。
- **TPOT（Time Per Output Token，每输出 token 时间，也叫 ITL 令牌间延迟）**：生成后续每个 token 的平均间隔，决定流式输出「顺不顺」。
- 而在推理引擎服务端，**吞吐量（throughput）**指单位时间处理的总 token 数——服务端靠「连续批处理（continuous batching）」把多个用户请求动态拼进同一批来提吞吐（vLLM 的做法），这是**服务端**的省钱手段；本节的「并行工具调用」是**应用层**降单请求墙上时间的手段。两者都叫「批/并行」，但一个提服务端吞吐、一个降单请求延迟，方向不同。

## 最小可运行演示

下面用纯 Python 演示：上半用 asyncio 对比串行与并行三个独立工具的墙上时间；下半算一笔批处理省钱账（折扣为示例，真实以官方为准）。不联网、不需要 API Key。
```python
import asyncio
import time


async def call_tool(name, delay):
    await asyncio.sleep(delay)
    return f"{name} 完成"


async def run_serial(tasks):
    start = time.perf_counter()
    results = []
    for name, delay in tasks:
        results.append(await call_tool(name, delay))
    return results, time.perf_counter() - start


async def run_parallel(tasks):
    start = time.perf_counter()
    results = await asyncio.gather(*(call_tool(n, d) for n, d in tasks))
    return results, time.perf_counter() - start


def batch_vs_realtime(n_tasks=10000, tokens_each=500,
                      price_per_1k=0.003, batch_discount=0.5):
    realtime = n_tasks * tokens_each / 1000 * price_per_1k
    return realtime, realtime * batch_discount


async def amain():
    tasks = [("查订单", 0.2), ("查物流", 0.2), ("查政策", 0.2)]
    _, t_serial = await run_serial(tasks)
    _, t_parallel = await run_parallel(tasks)
    print(f"串行执行 3 个独立工具：墙上时间 {t_serial:.2f}s（≈三者之和）")
    print(f"并行执行 3 个独立工具：墙上时间 {t_parallel:.2f}s（≈最慢一个）")
    print(f"并行提速约 {t_serial / t_parallel:.1f}x，且不额外花钱（该调的还是调）\n")
    rt, bt = batch_vs_realtime()
    print(f"批处理省钱（1 万条离线标注任务，示例价）：")
    print(f"  实时调用总成本 ${rt:.2f} → 批处理 API ${bt:.2f}，"
          f"省 50%（代价：不保证即时返回）")


if __name__ == "__main__":
    asyncio.run(amain())
```
保存为 `parallel_batch.py`，运行 `python parallel_batch.py`。完整预期输出：
```text
串行执行 3 个独立工具：墙上时间 0.60s（≈三者之和）
并行执行 3 个独立工具：墙上时间 0.20s（≈最慢一个）
并行提速约 3.0x，且不额外花钱（该调的还是调）

批处理省钱（1 万条离线标注任务，示例价）：
  实时调用总成本 $15.00 → 批处理 API $7.50，省 50%（代价：不保证即时返回）
```
逐行讲解：

- `asyncio.gather` 把三个协程同时调度，它们的等待时间**重叠**在一起，所以总耗时约等于最慢的一个（0.2s）而非三者之和（0.6s），实测提速约 3 倍。**前提是三个工具相互独立**——如果查物流依赖查订单的结果（有数据依赖），就不能并行，只能串行。
- 并行是「几乎免费的午餐」：它**不花额外的钱**（该调的接口还是调那么多次），只是把等待时间叠起来，省的是墙上时间。这和批处理正相反——批处理省钱但更慢，并行省时间但不省钱。
- 批处理演示：1 万条离线任务实时调 $15，走批处理 API 打五折到 $7.5。代价是不即时返回（可能几小时后才出结果），所以只适合离线场景。

## 真实系统对应

**官方公开机制**：OpenAI Batch API（50% 折扣、24 小时周转、独立限流池）与 Anthropic Message Batches API（输入输出各 50% 折扣）都是文档明确的产品 [来源](https://developers.openai.com/api/docs/guides/batch) [来源](https://platform.claude.com/docs/en/build-with-claude/batch-processing)；推理引擎侧的连续批处理是 vLLM 论文描述的机制 [来源](https://arxiv.org/abs/2309.06180)。**通用工程模式**：应用层用线程池/`asyncio.gather` 并行独立工具、按依赖关系决定串并行，是可迁移到任何框架的做法；现代编排框架（如第 15 章 LangGraph）能自动识别无依赖节点并并行执行。**教学参考实现**：上面的 `sleep` 只为模拟 I/O 耗时，真实系统用真正的网络/数据库客户端并要加超时；折扣数字是示例，真实以官方为准。

需要点明边界：批处理的「24 小时周转」是承诺上限，实际常更快，但你不能依赖它即时返回；两家的批量大小、限流额度、结果拉取方式各有细节，以官方文档为准。并行工具调用则要处理好其中某个工具失败的情况（第 8 章讲过部分失败降级：一个挂了别拖垮全部，用超时和降级兜底）。

## 生产踩坑

| 症状 | 根因 | 如何观测与复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| 在线接口跑离线大批量、又慢又贵 | 该走批处理却用实时调用 | 统计任务是否需即时返回 | 能等的任务改批处理 API 省 50% | 强实时任务必须在线调 |
| 并行没变快 | 工具间有数据依赖，被迫串行 | 画工具依赖图看能否并行 | 只对无依赖工具并行 | 有依赖时并行本就不适用 |
| 并行写共享状态丢更新 | 对非独立操作强行并行 | 同时写同一份状态复现竞态 | 写冲突调用串行或加锁 | 独立只读查询天然可并行 |
| 一个工具卡死拖垮整轮 | 并行未设单调用超时 | 注入一个卡死工具复现 | 每调用超时罩，超时转降级 | 明确允许长任务另设 |
| 批处理任务迟迟不返回还在等 | 误把批处理当同步接口用 | 提交后同步阻塞等待复现 | 异步提交+轮询/回调取结果 | 无 |
| 以为并行也能省钱 | 混淆"省时间"与"省钱" | 对比并行前后 token 用量 | 明确并行省墙上时间不省 token | 批处理才省钱 |

## 思考：批处理和并行工具调用分别解决什么问题？为什么并行能降延迟却不降成本？

### 回答

两者解决方向相反的问题，判据是「结果是现在就要还是可以等」。**批处理**面向**能等的离线任务**（数据标注、批量摘要、日报）：把大量请求打包异步提交，供应商错峰调度，换来约 50% 折扣，代价是不保证即时返回（可能几小时）。它的收益是**省钱**，牺牲的是即时性。**并行工具调用**面向**在线场景里的独立工具**（同时查订单、物流、政策）：用 `asyncio.gather` 或线程池让它们同时跑，墙上时间从「各者之和」压到「最慢的一个」。它的收益是**省墙上时间（降延迟）**。至于为什么并行不降成本：并行改变的只是这些调用在时间轴上的**排布方式**（从依次排队变成重叠进行），并没有减少调用次数或 token 量——该调的接口还是调那么多次、该花的 token 还是花，只是等待时间叠在了一起。所以它是「几乎免费的午餐」：不花额外的钱就把延迟砍掉一截。前提是工具**相互独立**（无数据依赖、不写同一份共享状态），且要给每个调用配超时，一个失败别拖垮整轮。

### 面试精简表达

批处理省钱不即时（离线任务打包异步、约五折）；并行降墙上时间不省钱（独立工具同时跑、墙上时间取最慢者，调用次数不变所以不省 token）。判据：结果现在要还是可以等；并行前提是工具独立且配超时。

### 反例

「把并行当省钱手段」是常见误解。有人以为「三个工具并行了成本就降三分之一」，其实并行只是让三次调用的等待重叠，三次调用一次没少、token 一个没省，账单分文不降。真正省钱的是缓存（省调用/输入费）和批处理（打折），并行省的是时间。
