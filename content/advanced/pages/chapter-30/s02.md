## 真实问题

客服 Agent 的成本大头之一，是**用最贵的模型回答最简单的问题**。拉出真实流量分布后团队傻眼了：约 75% 的请求是「你们几点下班」「订单到哪了」「怎么退货」这种一句话能答清的简单问题，只有不到 5% 是「我这笔跨境订单被海关扣了，退款政策怎么算」这种真需要多步推理的硬骨头。可上线时图省事，**所有请求一律走最强、最贵的大模型**。用最强模型去回答「你好」，就像派主任医师去给人量体温——不是不行，是浪费到离谱。当大模型和小模型单价能差**一个数量级**（50 倍并不夸张）时，这种浪费直接把账单撑大了好几倍。

这一节讲降本的第一大杀器：**别用一个模型干所有活**。把请求按难度分诊，简单的下沉到便宜小模型，复杂的才动用昂贵大模型。这与第 18 章第 6 节讲的分层路由是同一思想，本节把它推到更细的机制（前置分诊 vs 级联）、更真实的流量分布和更完整的成本对比。

## 原理：成本乘式与分诊为何「性价比最高」

先把 Agent 成本拆成一个乘式，理解它就不用死记优化清单：
```text
Agent 成本 ≈ 步数 × 每步 token 量 × 模型单价
             │           │              │
          减步数      压上下文        分层路由
        (第1、6节)    (第6节)         (本节)
```
分层路由动的是「单价」这个因子。它之所以**性价比高**，源于一个反直觉事实：**一个 Agent 任务里的绝大多数决策其实是简单的**——判断意图、决定下一步调哪个工具、格式化输出——这些用小模型完全够用；只有少数真正需要长链推理、代码生成的步骤才值得动用大模型。既然真实流量里简单请求占大头，把它们从大模型上卸下来，省的就是大头。

核心设计是「**用廉价手段分诊，再决定要不要请大模型出场**」，借鉴医院的分诊（triage）机制：
```text
用户请求
   │
   ▼
┌─────────────┐   简单(问候/查状态/FAQ)
│ 廉价分诊台   │──────────────────────────▶ 小模型直接答（便宜、快）
│(规则 or 极小模型)│
└─────────────┘   复杂(推理/多步/高风险)
   │        └───────────────────────────▶ 大模型攻坚（贵、强）
   ▼
 (拿不准) → 中档模型兜底
```
分诊本身很便宜（一条规则或一次几十毫秒的极小模型调用），但它能把大量简单请求挡在大模型之外——**一次廉价判断，省下大量昂贵调用**，这就是性价比的来源。

## 前置分诊 vs 级联升级：两条路线

分层路由有两种实现路线，权衡点不同：

- **前置分诊（routing）**：先分类再选模型，只调一次目标模型。优点是不浪费调用；缺点是**分诊错了就用错模型**——把复杂问题误判成简单，用小模型硬答会得到低质答案。
- **级联升级（cascade）**：先用小模型试，如果小模型表示「我不确定/超出能力」，再自动转给大模型。优点是**质量有保底**；缺点是升级时调了两次（小 + 大），延迟和这部分成本增加。

| 策略 | 做法 | 优点 | 缺点 | 适用 |
|---|---|---|---|---|
| 前置分诊 | 先分类再选一档模型 | 只调一次，省调用 | 分诊错→用错模型→掉质量 | 分诊准、误判代价可控 |
| 级联升级 | 小模型先试，不行再升级 | 质量有保底 | 难请求多调一次，延迟增 | 误判代价高、质量敏感 |

一条重要原则：**分诊要偏保守**。拿不准时宁可往上升一档，宁可偶尔多花一点，也别让复杂问题被小模型做砸——因为「答错」的代价（用户投诉、二次人工介入）通常远高于「多花几分钱」。误判代价高的场景，甚至可以让小模型答完后由大模型做一次快速质检。

## 最小可运行演示

下面用纯 Python 在一个贴近真实的流量分布（简单请求占 75%）上，对比三种策略的总成本。价格为教学示例常数，真实单价以官方定价页为准。不联网、不需要 API Key。
```python
## 教学示例价格：美元 / 1k token（把输入+输出合并近似为一个单价）
PRICE = {"small": 0.0002, "medium": 0.001, "large": 0.01}

## 模拟真实流量：(文本, token 量, 真实难度, 出现次数) —— 简单请求占大多数
TRAFFIC = [
    ("你好", 20, "small", 300),
    ("查一下订单 A123 的状态", 40, "small", 250),
    ("今天天气怎么样", 30, "small", 200),
    ("帮我把这段话翻译成英文", 120, "medium", 120),
    ("总结这封邮件的要点", 200, "medium", 80),
    ("帮我分析这份合同的违约风险并给出方案", 800, "large", 30),
    ("为什么这段代码会内存泄漏，怎么修", 600, "large", 20),
]


def classify(text):
    """分诊：关键词启发式。生产里常用一个小模型来做这步。"""
    if any(k in text for k in ("分析", "方案", "为什么", "合同", "诊断", "修")):
        return "large"
    if any(k in text for k in ("你好", "查", "状态", "天气", "谢谢")):
        return "small"
    return "medium"


def unit(tier, tokens):
    return PRICE[tier] * tokens


def main():
    total_reqs = sum(cnt for *_, cnt in TRAFFIC)
    all_large = sum(unit("large", tk) * cnt for _, tk, _, cnt in TRAFFIC)

    triage_cost, wrong = 0.0, 0
    for text, tk, truth, cnt in TRAFFIC:
        tier = classify(text)
        triage_cost += unit(tier, tk) * cnt
        if tier != truth:
            wrong += cnt

    cascade_cost = 0.0
    for text, tk, truth, cnt in TRAFFIC:
        cascade_cost += unit("small", tk) * cnt        # 先花一次小模型
        if truth != "small":                            # 小模型自评搞不定 → 升级
            cascade_cost += unit("large", tk) * cnt     # 再花一次大模型

    print(f"总请求量 {total_reqs} 次（简单请求占约 "
          f"{sum(c for _,_,t,c in TRAFFIC if t=='small')/total_reqs*100:.0f}%）")
    print(f"全用大模型      总成本 ${all_large:8.2f}  (基线)")
    print(f"前置分诊路由    总成本 ${triage_cost:8.2f}  "
          f"省 {(1-triage_cost/all_large)*100:.0f}%  分诊误判 {wrong} 次")
    print(f"级联升级        总成本 ${cascade_cost:8.2f}  "
          f"省 {(1-cascade_cost/all_large)*100:.0f}%  (质量有保底，难请求多花一次小模型)")


if __name__ == "__main__":
    main()
```
保存为 `routing.py`，运行 `python routing.py`。完整预期输出：
```text
总请求量 1000 次（简单请求占约 75%）
全用大模型      总成本 $  884.00  (基线)
前置分诊路由    总成本 $  394.80  省 55%  分诊误判 0 次
级联升级        总成本 $  681.68  省 23%  (质量有保底，难请求多花一次小模型)
```
逐行讲解：

- `TRAFFIC` 刻意做成「简单请求占 75%」的真实分布——这正是分层路由能省大钱的前提。如果你的流量全是硬骨头，分层路由就省不了多少。
- 前置分诊省了 **55%**：把 75% 的简单请求下沉小模型（单价差 50 倍），大头被卸掉；本例分诊规则和真实难度对齐，所以误判 0 次。**真实系统里误判不会是 0**，这也是为什么下面要讨论误判代价。
- 级联升级只省 **23%**，比前置分诊省得少——因为它对每个难请求都先花了一次小模型再升级（多调一次）。但它换来的是**质量保底**：难请求最终一定由大模型作答，不会被小模型做砸。省得少一点，买的是「不会因分诊错误而掉质量」的保险。

## 真实系统对应

**官方公开机制**：OpenAI 与 Anthropic 都提供从小到大的多档模型（如各自的轻量档与旗舰档），单价常相差一个数量级，具体型号与价格以官方定价页为准 [来源](https://platform.claude.com/docs/en/about-claude/pricing)。OpenAI 的《A practical guide to building agents》明确建议「从最强模型建立基线，再尝试用更小模型替换以省成本」的选型方法 [来源](https://cdn.openai.com/business-guides-and-resources/a-practical-guide-to-building-agents.pdf)。**通用工程模式**：前置分诊、级联升级、保守升档、小模型做分诊器，都是可迁移到任何厂商的路由骨架，主流框架（如第 15 章 LangGraph）里也能用条件边实现按难度分流。**教学参考实现**：上面的关键词 `classify` 只为演示，生产里更常用一个小模型或轻量分类器来做分诊——它比死板关键词鲁棒得多，且几乎不花钱（几十毫秒、几百 token）。价格常数同样是示例。

需要点明边界：厂商不会公开「什么请求该走哪档」的判定逻辑，那是你的业务决策；也没有普适的分诊阈值——必须用你自己的真实流量校准。分层路由的收益完全取决于你的**流量难度分布**，别把本例的「省 55%」当成任何场景都成立的常数。

## 生产踩坑

| 症状 | 根因 | 如何观测与复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| 分层路由后投诉变多 | 分诊把复杂问题误判为简单 | 抽查被判 small 的低分答案 | 分诊偏保守、拿不准升档 | 误判代价极低的场景可激进 |
| 省钱不明显 | 流量里简单请求占比低 | 统计真实难度分布 | 先量分布再决定是否值得路由 | 全是硬骨头则收益有限 |
| 级联反而更贵更慢 | 难请求占比高，几乎都在升级 | 统计升级率 | 高难流量直接前置走大模型 | 简单占多数时级联划算 |
| 关键词分诊频繁误判 | 死板规则覆盖不了自然语言 | 记录分诊分布与错判样本 | 换小模型/分类器做分诊 | 领域词固定时规则够用 |
| 小模型答错无人发现 | 未对下沉请求做质量抽检 | 对 small 档做离线评估抽样 | 小模型答完大模型质检高风险项 | 低风险 FAQ 可不质检 |
| 分诊器成了新瓶颈 | 分诊模型太大或串行阻塞 | 测分诊环节延迟占比 | 用极小模型、异步/缓存分诊结果 | 规则分诊几乎无开销 |

## 思考：怎么在不牺牲质量的前提下降低 Agent 成本？分诊该偏激进还是偏保守？

### 回答

首推模型分层路由：用便宜小模型处理占大多数的简单请求，只在真正需要复杂推理时才动用昂贵大模型；因为一个 Agent 任务里绝大多数决策是简单的，且真实流量里简单请求常占大头，把它们从大模型卸下来省的就是大头。要「不牺牲质量」，关键在两点。第一，**分诊偏保守**：拿不准时往上升一档，因为答错的代价（投诉、返工、二次人工）通常远高于多花几分钱；对高风险请求可让小模型答完后由大模型快速质检。第二，用**级联而非纯前置分诊**来给质量兜底——小模型先试、自评搞不定再升级到大模型，这样难请求最终一定由强模型作答，代价只是难请求多调一次小模型、省得比前置分诊少一些。所以选择是：误判代价低、追求极致省钱→前置分诊 + 激进下沉；误判代价高、质量敏感→级联 + 保守升档。切忌一句「换个便宜模型」了事——那会全局掉质量，是把「路由」误解成了「降配」。

### 面试精简表达

分层路由：简单请求下沉小模型、复杂请求上大模型；分诊要偏保守（拿不准升档，答错代价远高于多花钱），质量敏感时用级联升级给兜底；前置分诊省得多但赌分诊准，级联省得少但质量有保底。

### 反例

「为了省钱把所有请求都换成小模型」是典型反例：它省的是钱，赔的是质量——复杂请求被小模型做砸，引发投诉与人工返工，综合成本反而更高。分层路由的精髓是「按难度分流」，不是「一刀切降配」。

## 优化前后对比：客服 Agent 的路由改造

回到贯穿案例。改造前，客服 Agent 对所有请求走大模型，按前面演示的口径估算，1000 次请求约 $884。团队分两步改造：第一步先量流量，确认简单请求占约 75%，判断路由值得做；第二步不用关键词而是训了一个极小的意图分类器做分诊（几十毫秒、几乎不花钱），把「查状态/问营业时间/查退货政策」这类下沉到小模型，把「投诉、跨境退款、复杂纠纷」留给大模型，并对判为「投诉/纠纷」的高风险项加一道大模型质检。上线后模型费用降约一半，而抽样评估显示简单请求的答案质量没有可感知下降——因为它们本就不需要大模型的能力。

这里有个容易忽略的收益：分层路由不只省钱，还**顺带降了延迟**。小模型不仅便宜，通常也更快，简单请求下沉后，占大多数的请求响应更快了，P50 延迟明显改善。这也预告了第 8 节的主题——降本的手段常常和降延迟同向，但和「提质量」相互拉扯，三者构成一个不可能三角。
