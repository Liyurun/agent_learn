## 真实问题

回到贯穿全章的那个客服 Agent。前六节把成本和延迟一项项压下来了，但第 30 章开头那个「一天烧掉三个月预算」的故障，根子其实不在「哪个环节贵」，而在**发现得太晚**。复盘时间线是这样的：傍晚一次 prompt 改动引入 bug，让 Agent 对部分请求疯狂重试工具，单请求 token 从 5.5 万飙到 20 万；异常从当晚八点就开始了，可团队只在监控面板上挂了一个「当日累计花费」的粗指标，而且要到第二天早上九点看日报才有人核对——**足足 13 个小时里，钱在以正常速度的几十倍流失，却没有任何人、任何系统喊停**。等看到日报时，一夜之间多烧了几万块，已经无法挽回。

事后大家都说「早知道就好了」，但「早知道」不是靠人盯,而是靠系统。这一节要解决的就是**成本可观测（cost observability）与预算告警（budget alerting）**：不是等出事后复盘，而是在账单爆炸前几分钟就自动拦住它。核心要回答三个问题——钱花在哪个粒度上能看清（可观测）、花到多少该提醒人（告警）、花到多少该自动叫停（熔断）。

## 原理：从「日总花费」到 per-request 粒度可观测

前六节反复用到一个词：**per-request（单请求）粒度**。它是这一节的地基。「日总花费」这类聚合指标的致命缺陷是**延迟高、颗粒粗**：它要等一整天的数据攒齐才有意义，且被海量正常请求平均掉，一个疯狂重试的异常请求淹没在其中根本看不出来。要想「几分钟就发现」，就必须把观测粒度下沉到**每一次请求**：这次请求用了哪个模型、输入/输出各多少 token、命中缓存没有、走了几步循环、花了多少钱、耗时多久。

有了 per-request 记录，可观测就能建立在三个层次上，逐层收窄：
```text
① 单请求指标（最细）：model / input_tokens / output_tokens
                     / cached / steps / cost_usd / latency_ms
      ↓ 聚合
② 维度切片（中）：按模型、按用户、按请求类型、按时间窗分组
                 → 回答"钱到底花在谁身上、哪类请求最贵"
      ↓ 聚合
③ 预算与趋势（粗）：小时/日预算消耗曲线、环比、预测何时耗尽
```
关键洞察是：**异常几乎总是先在①层暴露**。那个 bug 导致的 20 万 token 请求，在①层是一根扎眼的尖刺，在③层的日总曲线上却只是一个不起眼的小凸起。所以「发现得早」的前提，是你留存了足够细的单请求记录，并且**对单请求本身设了阈值**——而不只是对总量设阈值。两家 API 的响应里都带 `usage` 字段（`input_tokens`/`output_tokens`，以及缓存相关的读写 token 计数），是最可靠的计费口径来源 [来源](https://docs.anthropic.com/en/docs/build-with-claude/prompt-caching)；不要用「字符数除以 4」这类估算来记账，误差会在高频调用下累积成大偏差。

## 原理：告警与熔断——两级保险丝

可观测只是「看得见」，要「拦得住」还需要主动的控制机制。这里有两个必须分清的动作：

- **告警（alert）**：花费达到预算的某个比例（比如 80%）时，通知人去关注。它是**软**的——不阻断请求，只是提醒。作用是「留出人工干预的窗口」，让你在真正撞墙前有时间判断：是正常的流量高峰，还是异常？
- **熔断（circuit break）**：花费即将超过硬上限时，**直接拒绝**后续请求。它是**硬**的——不给人反应时间，自动叫停。作用是「兜底」，在无人值守的深夜也能保住钱包。

这两级的关系是**先软后硬**：80% 告警给人机会,100% 熔断兜最后的底。但只有「总量」这一维的保险丝还不够——回到那个故障，它的问题是**单请求异常**（一个请求就烧 20 万 token），如果只有「小时总预算」熔断，得等到很多个这样的异常累积到撞穿小时预算才触发，可能已经是几十分钟后了。所以熔断要做成**两个粒度**：
```text
熔断粒度一（总量）：本次请求会让"累计花费 > 小时预算"？→ 拒绝
熔断粒度二（单请求）：本次请求预估 token > 单请求阈值？→ 拒绝（疑似长循环/死循环）
```
粒度二是那次故障真正需要的保险丝：一个请求正常 6,000 token，突然要 20 万，几乎必然是循环失控或 prompt bug——在它执行前就拦下，比等日报早了 13 个小时。

## 最小可运行演示

下面用纯 Python 实现一个 `CostGuard`：它在每个请求执行**前**做两级熔断预检（总量 + 单请求 token），在花费越过 80% 时**告警**一次，并模拟一个「单请求 token 飙升」的异常来展示单请求粒度检测的价值。它不联网、不需要 API Key。
```python
class CostGuard:
    def __init__(self, hourly_budget_usd=100.0, alert_ratio=0.8,
                 per_request_token_limit=50000):
        self.hourly_budget = hourly_budget_usd
        self.alert_ratio = alert_ratio
        self.per_request_token_limit = per_request_token_limit
        self.spent = 0.0
        self.alerted = False

    def check_request(self, estimated_cost, est_tokens):
        ## 单请求粒度异常：token 飙升（可能陷入长循环）
        if est_tokens > self.per_request_token_limit:
            return {"allow": False,
                    "reason": f"单请求 token {est_tokens} 超阈值 "
                              f"{self.per_request_token_limit}（疑似长循环）"}
        ## 预算熔断：本次会超小时预算就拒绝
        if self.spent + estimated_cost > self.hourly_budget:
            return {"allow": False, "reason": "小时预算耗尽，触发熔断"}
        return {"allow": True, "reason": "放行"}

    def record(self, actual_cost):
        self.spent += actual_cost
        if not self.alerted and self.spent > self.hourly_budget * self.alert_ratio:
            self.alerted = True
            print(f"[告警] 已用 ${self.spent:.1f}/{self.hourly_budget:.0f}"
                  f"（>{self.alert_ratio*100:.0f}%），请人工关注")


def main():
    guard = CostGuard(hourly_budget_usd=10.0)  # 小额度便于演示熔断
    ## 正常请求流：每个约 $1.2
    normal = [(1.2, 6000)] * 12
    served, blocked = 0, 0
    for i, (cost, tokens) in enumerate(normal, 1):
        verdict = guard.check_request(cost, tokens)
        if verdict["allow"]:
            guard.record(cost)
            served += 1
        else:
            blocked += 1
            print(f"请求#{i} 被拒：{verdict['reason']}（已花 ${guard.spent:.1f}）")
    print(f"正常流：放行 {served}，熔断拒绝 {blocked}\n")

    ## 异常请求：单请求 token 从 6k 飙到 200k（prompt bug 导致疯狂重试）
    print("--- 单请求 token 飙升异常 ---")
    guard2 = CostGuard(hourly_budget_usd=1000.0)  # 预算充足，但单请求异常
    verdict = guard2.check_request(estimated_cost=0.6, est_tokens=200000)
    print(f"疑似长循环请求：allow={verdict['allow']}  {verdict['reason']}")
    print("→ 只看'总花费'会等到日报才发现；单请求 token 告警几分钟就能拦下。")


if __name__ == "__main__":
    main()
```
保存为 `cost_guard.py`，运行 `python cost_guard.py`。完整预期输出：
```text
[告警] 已用 $8.4/10（>80%），请人工关注
请求#9 被拒：小时预算耗尽，触发熔断（已花 $9.6）
请求#10 被拒：小时预算耗尽，触发熔断（已花 $9.6）
请求#11 被拒：小时预算耗尽，触发熔断（已花 $9.6）
请求#12 被拒：小时预算耗尽，触发熔断（已花 $9.6）
正常流：放行 8，熔断拒绝 4

--- 单请求 token 飙升异常 ---
疑似长循环请求：allow=False  单请求 token 200000 超阈值 50000（疑似长循环）
→ 只看'总花费'会等到日报才发现；单请求 token 告警几分钟就能拦下。
```
逐行讲解：

- `check_request` 在请求执行**前**做预检，且**先查单请求阈值再查总量**——这个顺序不能反：单请求异常（疑似长循环）比总量超支更危险，应该优先拦截。
- 正常流里第 8 个请求刚好让累计花费越过 80%（$8.4 > $8），触发一次**告警**（`alerted` 标志保证只提醒一次，不刷屏）；到第 9 个请求，$9.6 + $1.2 > $10 触发**熔断**，后续全部拒绝。告警和熔断是两个不同的动作，前者提醒、后者阻断。
- 第二段是全章那个故障的核心：`guard2` 预算充足（$1000），单看总量根本拦不住那个 20 万 token 的请求；但**单请求 token 阈值**（5 万）一眼就把它挡下。这正是「per-request 粒度」的价值——只看总量的系统会等到日报，单请求粒度的系统几分钟就拦住。

## 真实系统对应

**官方公开机制**：两家 API 的响应都返回 `usage`（输入/输出 token、缓存读写 token），这是最可靠的计费口径 [来源](https://docs.anthropic.com/en/docs/build-with-claude/prompt-caching)；OpenAI 后台也提供用量与限额（usage limits）设置，可在账户级别配置软/硬限额并邮件告警 [来源](https://platform.openai.com/docs/guides/rate-limits)。**通用工程模式**：per-request 埋点、按维度切片、软告警 + 硬熔断两级机制、单请求 token 阈值检测长循环——这些都是可迁移到任何自建系统的做法，通常落在网关层或中间件里，配合 Prometheus/Grafana 这类可观测栈做曲线与告警规则，用 LangSmith 等追踪平台把每次调用的 token 与成本可视化。**教学参考实现**：上面的 `CostGuard` 用内存计数器模拟，真实系统要考虑分布式一致性（多实例共享预算，通常放 Redis 原子计数器）、时间窗滚动（小时/日预算的滑动重置）、以及「拒绝后给用户什么降级体验」（返回排队提示、切更便宜模型、还是直接报错）。

三条边界值得强调。其一，**熔断阈值要留安全边际**：如果掐在 100% 才熔断，等你发现时可能已经因为并发请求穿透了预算，实践中常把硬熔断设在 95% 或更早。其二，**告警要防「狼来了」**：阈值设太低会频繁误报，人就会开始忽略告警，反而在真出事时麻木——告警要少而准。其三，**熔断是最后防线不是常态**：如果系统经常触发熔断，说明预算规划或路由策略本身有问题，该回头优化前六节的手段，而不是把熔断当日常限流器用。

## 生产踩坑

| 症状 | 根因 | 如何观测与复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| 一夜烧穿预算无人察觉 | 只监控日总花费、粒度太粗 | 回放异常请求看它在日曲线里几乎不显 | 下沉到 per-request 记录 + 单请求阈值 | 单请求量恒定的简单场景 |
| 单请求 token 飙升未被拦 | 只对总量熔断、没有单请求阈值 | 构造一个超大 token 请求跑 CostGuard | 加单请求 token/步数上限熔断 | 确需超长上下文的批任务需单独放行 |
| 告警太频繁被无视 | 阈值过低或未去重 | 统计一天触发告警次数 | 提高阈值 + 只首次告警 + 分级 | 真高峰期的告警不算误报 |
| 熔断掐在 100% 仍超支 | 无安全边际 + 并发穿透 | 高并发下压测撞线 | 熔断设 95%、用原子计数 | 单实例低并发时穿透概率低 |
| 记账与账单对不上 | 用字符估算而非 usage 字段 | 对比自记成本与官方账单 | 一律以 API usage 为准 | 完全离线的本地模型另算口径 |
| 多实例各记各的超支 | 预算计数器没共享 | 起多副本并发跑观察总额 | 预算放 Redis 原子自增 | 单实例部署无此问题 |
| 熔断后用户体验崩了 | 直接报错无降级 | 触发熔断看客户端表现 | 降级到排队/更便宜模型/缓存兜底 | 内部批处理任务可直接拒绝 |

## 思考：为什么「只监控日总花费」会漏掉那次故障？可观测和熔断该做到什么粒度？

### 回答

「只监控日总花费」漏掉故障，是因为这个指标**延迟高、颗粒粗**：它要等一整天数据攒齐才有意义，且被海量正常请求平均掉——那个疯狂重试、单请求烧 20 万 token 的异常，在日总曲线上只是一个不起眼的小凸起，直到第二天看日报才被人核对到，中间足足 13 小时无人喊停。要「几分钟就发现」，可观测必须下沉到 **per-request（单请求）粒度**：记录每次请求的模型、输入/输出 token、是否命中缓存、循环步数、成本、耗时，因为异常几乎总是先在单请求层暴露成一根尖刺。熔断则要做**两个粒度**：一是总量熔断（本次会让累计超小时预算就拒绝），二是**单请求熔断**（预估 token 超阈值就当场拒绝，识别疑似长循环/死循环）——后者才是那次故障真正需要的保险丝，因为只靠总量熔断得等很多异常累积撞穿小时预算才触发，可能已过去几十分钟。配套原则：告警（软，80% 提醒人、留干预窗口）先于熔断（硬，95%~100% 直接阻断、兜底），且熔断要留安全边际、告警要少而准防「狼来了」，计费口径一律以 API 的 `usage` 字段为准而非字符估算。

### 面试精简表达

日总花费颗粒太粗、延迟太高，异常请求被平均掉，等日报才发现（该故障漏了 13 小时）；可观测要下沉到 per-request（模型/token/缓存/步数/成本/延迟），异常先在单请求层暴露；熔断做两级——总量熔断 + 单请求 token 阈值熔断（拦长循环），后者是关键；告警（软, 80%）先于熔断（硬, 95%~100%），熔断留安全边际、告警要少而准，记账以 API usage 字段为准。

### 反例

「把熔断阈值精确掐在 100%、只对小时总量设一道熔断」是常见反例：一来 100% 无安全边际，高并发下多个请求同时穿透就超支了；二来只对总量熔断，那个单请求烧 20 万 token 的异常得等累积撞穿小时预算才被拦，早已过去几十分钟。正确做法是熔断设 95% 留边际、并额外加一道单请求 token 阈值当场拦异常。
