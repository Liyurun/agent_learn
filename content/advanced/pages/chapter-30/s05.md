## 真实问题

客服 Agent 优化到这一步，模型费用降了、独立工具并行了，但用户满意度调研里还是有一条高频抱怨：「一问问题，屏幕卡在那不动，等好几秒才'唰'地蹦出一大段，还以为死机了。」团队查了日志，发现这些请求的端到端延迟其实并不算离谱（多在 6~8 秒），问题出在**交互方式**：Agent 用的是非流式模式——模型把整段回答**全部生成完**才一次性返回，用户在这几秒里面对的是**完全空白、毫无反馈的屏幕**。人对「无反馈的等待」极度敏感，8 秒的空白足以让一部分用户以为出故障、刷新或离开。

这一节讲一种性价比极高的「障眼法」：**流式输出**。它降的不是真实延迟，而是**感知延迟**——总生成时间一分没变，用户体验却能从「卡死」变「秒回」。这背后要理解两个推理引擎指标：TTFT 和 TPOT。

## 原理：真实延迟 vs 感知延迟，与两个关键指标

普通（非流式）模式下，用户要等模型把整段回答全部生成完才能看到第一个字；**流式（streaming）模式**则是**生成一个 token 就吐一个**，用户几乎立刻看到文字开始往外冒。虽然**总生成时间没变**，但等待体验天差地别。

衡量这件事有两个关键指标（也是第 4 节提到、需与吞吐量区分的那两个）：

- **TTFT（Time To First Token，首 token 延迟）**：从发出请求到看到**第一个字**的时间。它直接决定「用户等多久才看到反应」，是感知延迟的核心。非流式的 TTFT 等于「整段生成完」的时间；流式的 TTFT 只是「第一个 token 生成好」的时间，通常小一个量级。
- **TPOT（Time Per Output Token，每输出 token 时间，又称 ITL，Inter-Token Latency，令牌间延迟）**：生成后续每个 token 的平均间隔，决定流式输出「顺不顺、卡不卡顿」。TPOT 稳定，字就均匀地冒；TPOT 忽快忽慢，就会一顿一顿的。

一个常用的近似关系：**端到端延迟 ≈ TTFT + (输出 token 数 × TPOT)**。这个拆分很有用——它告诉你，短回答的延迟主要由 TTFT 主导，长回答则由 TPOT × 长度主导，优化重点不同。
```text
非流式：[──────等待全部生成 8s──────] 一次性显示 8s 的内容
        用户盯着空白屏幕 8 秒 → 焦虑，以为卡死了
        TTFT = 8s（要等到全部完成）

流式：  [首字0.5s]字·字·字·字·字...持续输出到 8s
        用户 0.5s 就看到开始输出 → 感觉"秒回"，愿意等
        TTFT = 0.5s，之后每字间隔 = TPOT
```
对 Agent 尤其重要：多步 Agent 本身就慢（要走好几轮工具调用），如果全程无反馈，用户更容易以为它死了。把每一步的进展**流式暴露**出来——「正在查询订单…」「正在核对物流…」「正在生成回复…」——本质都是在管理感知延迟，让用户看到「它在动」。

## 最小可运行演示

下面用纯 Python 模拟逐 token 生成，对比非流式与流式的 TTFT。总生成时间一致，但首字延迟差一个量级。不联网、不需要 API Key。
```python
import time


def generate_tokens(n=20, per_token=0.05):
    """模拟模型逐 token 生成，每个 token 花 per_token 秒（即 TPOT=50ms）。"""
    for i in range(n):
        time.sleep(per_token)
        yield f"字{i}"


def non_streaming():
    """非流式：全部生成完再一次性返回，用户全程看空白。"""
    start = time.perf_counter()
    buf = []
    for tok in generate_tokens():
        buf.append(tok)
    ttft = time.perf_counter() - start        # 首次可见 = 全部完成时
    return ttft, ttft, len(buf)


def streaming():
    """流式：生成一个就吐一个，首 token 一到用户即可见。"""
    start = time.perf_counter()
    first_visible, count = None, 0
    for tok in generate_tokens():
        if first_visible is None:
            first_visible = time.perf_counter() - start  # 记录 TTFT
        count += 1
    total = time.perf_counter() - start
    return first_visible, total, count


def main():
    ns_ttft, ns_total, _ = non_streaming()
    s_ttft, s_total, _ = streaming()
    print(f"非流式：TTFT {ns_ttft*1000:.0f}ms（=全部生成完），总时间 {ns_total*1000:.0f}ms")
    print(f"流式：  TTFT {s_ttft*1000:.0f}ms（=第一个字），  总时间 {s_total*1000:.0f}ms")
    print(f"\n总生成时间几乎一样，但流式的首字延迟只有非流式的约 "
          f"1/{ns_ttft/s_ttft:.0f}——感知延迟从'卡死'变'秒回'。")


if __name__ == "__main__":
    main()
```
保存为 `streaming.py`，运行 `python streaming.py`。完整预期输出：
```text
非流式：TTFT 1001ms（=全部生成完），总时间 1001ms
流式：  TTFT 50ms（=第一个字），  总时间 1001ms

总生成时间几乎一样，但流式的首字延迟只有非流式的约 1/20——感知延迟从'卡死'变'秒回'。
```
逐行讲解：

- `generate_tokens` 每个 token 睡 50ms，即 TPOT=50ms、共 20 个 token，总生成时间约 1 秒。这是两种模式**共同的、无法回避的真实生成时间**。
- 非流式的 TTFT = 1001ms：因为它要等最后一个 token 生成完才一次性返回，首字可见时间就等于总时间。流式的 TTFT = 50ms：第一个 token 一生成好就立刻可见，只花了一个 TPOT。**两者总时间几乎相同，但 TTFT 差了约 20 倍**——这就是流式的全部价值：不改变真实延迟，只把「用户看到反应」的时刻大幅提前。
- 注意这段演示里流式并没有让任务更快完成（总时间还是 1 秒）。它优化的是**感知**，不是真实吞吐。这也是它「划算」的原因——几乎零成本、零副作用，纯赚体验。

## 真实系统对应

**官方公开机制**：OpenAI 与 Anthropic 都提供流式接口（`stream=True` / SSE 事件流），逐块返回增量内容；Anthropic 的 Streaming Messages 文档描述了 `message_start`→内容块增量→`message_stop` 的事件结构（第 8 章第 4 节详述过增量解析）[来源](https://docs.anthropic.com/en/docs/build-with-claude/streaming)。TTFT、TPOT/ITL、吞吐量是推理服务基准测试（如 vLLM、NVIDIA 基准工具）的标准指标 [来源](https://arxiv.org/abs/2309.06180)。**通用工程模式**：前端打字机效果、工具调用的中间状态提示、进度指示，都是可迁移到任何产品的感知延迟管理手段。**教学参考实现**：上面的 `sleep` 模拟 TPOT，真实 TPOT 取决于模型、硬件、并发负载，且流式还要处理网络分块、半截 JSON（第 8 章讲过工具参数流式时不能对半截 JSON 提前解析）等工程细节。

一条边界：流式降的是**感知**延迟，不解决**真实**延迟。如果你的 Agent 真的要 40 秒才出结果，流式能让用户愿意多等一会儿、不至于以为卡死，但它治标不治本——真实延迟还得靠第 6 节的延迟预算分解找瓶颈、靠第 2 节的小模型、靠第 4 节的并行来降。流式和这些手段是互补的：流式改善「等待的体验」，其余改善「等待的长度」。

## 生产踩坑

| 症状 | 根因 | 如何观测与复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| 用户以为卡死、刷新或离开 | 非流式下长时间空白无反馈 | 测非流式 TTFT（=总时长） | 开启流式 + 中间进展提示 | 极短回答无感知问题 |
| 流式仍感觉一顿一顿 | TPOT 不稳定或前端缓冲过大 | 记录相邻 token 到达间隔 | 减小前端缓冲、稳定后端负载 | 网络抖动导致的偶发例外 |
| 多步 Agent 中途长时间无反应 | 只在最终答案流式，工具阶段静默 | 观察工具执行期前端状态 | 每步推送"正在查询…"状态 | 单步任务无中间态 |
| 前端过早解析半截内容出错 | 对未完成的流式分片提前处理 | 在增量回调里立即解析复现 | 累积到块结束再解析 | SDK 通常已封装 |
| 以为开了流式就变快了 | 混淆感知延迟与真实延迟 | 对比流式前后总时长 | 明确流式治标、真实延迟另治 | 无 |
| 流式下计费/用量统计错乱 | 未在流结束正确汇总 usage | 对比流式与非流式 usage | 在 message_stop 汇总用量 | 非流式不涉及 |

## 思考：Agent 响应慢，除了让它真的变快，还能怎么优化体验？TTFT 和 TPOT 各是什么？

### 回答

关键是区分「真实延迟」和「感知延迟」，前者是任务真正花的秒数，后者是用户主观觉得等了多久，而人对「无反馈的等待」极度敏感、对「有进展的等待」相当宽容。所以在不改变真实延迟的前提下，**流式输出 + 中间进展提示**能大幅降低感知延迟：流式让模型生成一个字就吐一个字，用户几乎立刻看到反应，而不是盯着空白屏幕等整段生成完；对多步 Agent，还要把每一步的进展（「正在查询订单…」）推送出去，让用户看到「它在动」。衡量这件事的核心指标是 **TTFT（Time To First Token，首 token 延迟）**——从发请求到看到第一个字的时间，流式能把它从「整段生成完」压到「第一个 token 生成好」，通常小一个量级。与之配套的是 **TPOT（Time Per Output Token，每输出 token 时间，又称 ITL 令牌间延迟）**——后续每个字的平均间隔，决定输出顺不顺；端到端延迟约等于 `TTFT + 输出token数 × TPOT`。要强调的是流式治标不治本：它改善「等待的体验」，真实延迟还得靠找瓶颈、换快模型、并行来降，二者互补。

### 面试精简表达

区分真实延迟与感知延迟：流式输出 + 中间进展提示大幅降感知延迟（核心指标 TTFT 首 token 延迟，从"整段生成完"降到"第一个字"），TPOT 是后续每字间隔决定流畅度，端到端≈TTFT+token数×TPOT；流式治标、真实延迟另靠换模型/并行/找瓶颈。

### 反例

「把流式当性能优化来汇报'延迟降了 90%'」是误导性反例：流式把 TTFT 从 8s 降到 0.5s 是真的，但任务总时长一分没变，真实吞吐、真实成本都没改善。如果下游还有严格的端到端 SLO（Service Level Objective，服务级目标）要求整个响应在 3 秒内完成，流式救不了你，必须真降延迟。
