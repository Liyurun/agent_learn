## 真实问题

一个团队在 2025 年初写了一个远程 MCP Server，用的是当时文档里的「HTTP + SSE（Server-Sent Events，服务器发送事件）」两端点方案：一个 GET 端点开 SSE 长连接推消息，一个 POST 端点收客户端消息。半年后他们升级客户端 SDK（Software Development Kit，软件开发工具包），发现新客户端默认用「Streamable HTTP」单端点方案，握手直接 400 失败。排查半天才明白：**MCP 的传输层在 2025-03-26 版本换代了**，旧的 HTTP+SSE 被 Streamable HTTP 取代，而他们的 Server 没有做向后兼容。传输层不是「随便挑一个能通信的方式」，它的版本演进会实打实地影响生产系统的兼容性。

## 原理：两种标准传输

MCP 用 JSON-RPC 编码消息，规范当前定义了两种标准传输机制 [来源](https://modelcontextprotocol.io/specification/2025-11-25/basic/transports)：

| 传输方式 | 适用场景 | 核心特征 |
|---|---|---|
| stdio（标准输入输出） | Server 作为本地子进程运行 | Host 把 Server 当子进程拉起，通过 stdin/stdout 收发换行分隔的 JSON-RPC 消息；无网络暴露面 |
| Streamable HTTP | Server 作为独立进程，处理多客户端 | 单一 HTTP 端点同时支持 POST 与 GET，可选用 SSE 流式推送多条服务端消息 |

规范明确建议「客户端应尽可能支持 stdio」[来源](https://modelcontextprotocol.io/specification/2025-11-25/basic/transports)。两种传输的示意：
```text
stdio 传输（本地）                      Streamable HTTP 传输（远程）
┌──────┐  拉起子进程   ┌────────┐      ┌──────┐  POST/GET   ┌────────┐
│ Host │─────────────▶│ Server │      │ Host │────────────▶│ Server │
│      │◀─stdin/stdout│(子进程) │      │      │◀─可选SSE流──│ (独立)  │
└──────┘              └────────┘      └──────┘             └────────┘
本地文件系统/脚本                       远程 API / 多租户服务
```
### stdio 的规则与边界

规范对 stdio 有几条严格约束，很多手写 Server 的 bug 都源于违反它们 [来源](https://modelcontextprotocol.io/specification/2025-11-25/basic/transports)：

- 消息以换行分隔，且**消息内不得含嵌入的换行符**。
- Server **不得**向 stdout 写任何不是有效 MCP 消息的内容（所以调试用的 `print` 会污染协议流，是新手最常见的坑）。
- Server **可以**向 stderr 写日志；Client 可捕获、转发或忽略 stderr，且**不应**把 stderr 有输出当成错误信号。

这几条解释了本章第 5 节手写 Server 时为什么坚持「日志走 stderr、只有 JSON-RPC 走 stdout」——一旦把 `print("debug")` 写到 stdout，客户端解析就会因为多出一行非法 JSON 而失败。

### Streamable HTTP 的关键机制

Streamable HTTP 在 2025-03-26 版本引入，替代 2024-11-05 的 HTTP+SSE 传输 [来源](https://modelcontextprotocol.io/specification/2025-11-25/basic/transports)。它的要点：

- Server 提供**单一** MCP 端点路径（如 `https://example.com/mcp`），同时支持 POST 和 GET。
- 客户端每条 JSON-RPC 消息都用一个新的 HTTP POST 发到该端点，`Accept` 头须同时列出 `application/json` 和 `text/event-stream`。
- 对于 JSON-RPC 请求，Server 可以选择返回 `application/json`（单个 JSON 对象）或 `text/event-stream`（开一条 SSE 流，逐步推送多条消息，最终包含该请求的响应）。
- 若输入是通知或响应（不需要回包），Server 接受后返回 `202 Accepted` 且无 body。
- 可用 `MCP-Session-Id` 响应头建立有状态会话，客户端后续请求须带上它。
- 支持断线重连：SSE 事件可带 `id`，客户端用 `Last-Event-ID` 头请求重放丢失的消息。

## 传输层版本演进时间线

传输层是 MCP 里演进最频繁的部分，理解这条时间线能帮你判断兼容性问题 [来源](https://modelcontextprotocol.io/specification/2025-11-25/basic/transports)：
```text
2024-11-05  首版：stdio + HTTP+SSE（两端点：GET 开 SSE，POST 收消息）
2025-03-26  引入 Streamable HTTP（单端点 POST/GET，可选 SSE），取代 HTTP+SSE
2025-06-18  elicitation 提升为一等原语（属原语层，非传输层）
2025-11-25  传输层维持 stdio + Streamable HTTP 两种；补充协议版本头等细节
2026-07-28  标注为 latest；对 Streamable HTTP 行为再做调整（以官方页面为准）
```
那个团队的兼容性事故，正好卡在 2024-11-05 → 2025-03-26 这次换代上。规范也给出了向后兼容的迁移路径：想支持老客户端的 Server 应同时保留旧的 SSE 与 POST 端点、以及新的 MCP 端点；想支持老 Server 的客户端应先尝试 POST `InitializeRequest`，若失败（400/404/405）再回退到旧的 GET+SSE `endpoint` 事件方案 [来源](https://modelcontextprotocol.io/specification/2025-11-25/basic/transports)。

## 传输层的安全警告

规范对 Streamable HTTP 给出了明确的安全要求，这不是可选建议 [来源](https://modelcontextprotocol.io/specification/2025-11-25/basic/transports)：

- Server **必须**校验所有连接的 `Origin` 头，以防 DNS（Domain Name System，域名系统）重绑定攻击；`Origin` 非法应返回 `403 Forbidden`。
- 本地运行时，Server **应当**只绑定 localhost（127.0.0.1），而非所有网络接口（0.0.0.0）。
- Server **应当**对所有连接实现恰当的身份认证。

没有这些保护，攻击者可以用 DNS 重绑定从远程网站与本地 MCP Server 交互。这解释了为什么「本地工具优先用 stdio」——stdio 没有网络监听端口，天然不存在这类攻击面。

## 最小可运行演示

stdio 传输的本质是「换行分隔的 JSON-RPC 帧」。下面用纯标准库写一个「帧编解码器」，演示 stdio 传输层如何把多条消息切分、且拒绝含嵌入换行的非法消息：
```python
import json

def encode_frame(message: dict) -> str:
    line = json.dumps(message, ensure_ascii=False)
    if "\n" in line:  # 规范：单条消息不得含嵌入换行
        raise ValueError("消息含嵌入换行，违反 stdio 传输约定")
    return line + "\n"

def decode_stream(raw: str) -> list:
    messages = []
    for line in raw.split("\n"):
        line = line.strip()
        if line:
            messages.append(json.loads(line))
    return messages

def main() -> None:
    stream = ""
    stream += encode_frame({"jsonrpc": "2.0", "id": 1, "method": "initialize"})
    stream += encode_frame({"jsonrpc": "2.0", "method": "notifications/initialized"})
    stream += encode_frame({"jsonrpc": "2.0", "id": 2, "method": "tools/list"})
    decoded = decode_stream(stream)
    print(f"帧数: {len(decoded)}")
    for m in decoded:
        kind = "通知" if "id" not in m else "请求"
        print(f"  [{kind}] method={m['method']}")

if __name__ == "__main__":
    main()
```
保存为 `stdio_frames.py`，运行 `python stdio_frames.py`。预期输出：
```text
帧数: 3
  [请求] method=initialize
  [通知] method=notifications/initialized
  [请求] method=tools/list
```
三条消息被换行正确切分，含 `id` 的是请求、无 `id` 的是通知。这正是第 5 节完整 Server 的 stdio 收发底座——真实 Server 只是把这个编解码器接到 `sys.stdin` / `sys.stdout` 上。

## 真实系统对应

**官方公开机制**：stdio 与 Streamable HTTP 是规范定义的两种标准传输，换行分隔、stdout 只放合法消息、stderr 可放日志、Streamable HTTP 单端点与安全警告、以及从 HTTP+SSE 的演进与向后兼容路径，均有规范文档支撑 [来源](https://modelcontextprotocol.io/specification/2025-11-25/basic/transports)。**通用工程模式**：「本地用 stdio、远程用 HTTP」的选择准则，以及把版本演进与兼容性事故关联，是可迁移推导。**教学参考实现**：上面的帧编解码器是本书构造的最小骨架，不代表官方 SDK 的传输实现。

## 生产踩坑

| 症状 | 根因 | 如何观测与复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| 客户端解析协议流失败 | Server 把调试 print 写进了 stdout | 在 Server 里加一行 print 到 stdout 复现 | 所有日志改走 stderr，stdout 只放 JSON-RPC | 非 stdio 传输不受此限 |
| 升级客户端后握手 400 | 依赖已废弃的 HTTP+SSE 两端点 | 用新客户端连旧 Server 复现 | 迁移到 Streamable HTTP 或做双端点兼容 | 内网封闭且两端同步升级时可暂缓 |
| 本地 Server 被远程网页调用 | HTTP Server 绑定 0.0.0.0 且不校验 Origin | 从外部主机尝试连接本地端口 | 绑定 127.0.0.1，校验 Origin，加认证 | 受控内网+网关鉴权场景可放宽绑定 |
| 长任务中途断连丢消息 | 未启用 SSE 事件 id 与重放 | 中途断网观察是否丢结果 | 给 SSE 事件带 id，用 Last-Event-ID 重放 | 短请求无需可恢复流 |
| 会话状态丢失需重新初始化 | 客户端未携带 MCP-Session-Id | 去掉会话头发请求看是否 400 | 保存并回传 MCP-Session-Id | 无状态 Server 无需会话 |

## 思考：为什么本地工具优先用 stdio 而不是 HTTP？

### 回答

主要是安全面与复杂度两方面。安全上，stdio 没有网络监听端口，Host 把 Server 当子进程直接拉起、通过 stdin/stdout 通信，天然不存在 DNS 重绑定、未授权远程调用、中间人这类网络攻击面；而 HTTP Server 一旦绑定到网络接口，就必须额外处理 Origin 校验、localhost 绑定、身份认证、传输加密等一整套防护。复杂度上，stdio 无需部署、无需端口管理、无需鉴权，进程退出连接即清理，非常适合文件系统、本地脚本这类个人化工具。规范也明确建议客户端尽可能支持 stdio。反过来，当 Server 需要被多个远程用户共享、需要独立部署和水平扩展时，才用 Streamable HTTP，并补齐鉴权与加密。

### 面试精简表达

stdio 是本地子进程 + 标准输入输出，无网络端口所以无网络攻击面、无需鉴权部署；远程多租户才用 Streamable HTTP，代价是要自己补齐 Origin 校验、认证与加密。

## 事故回放：一个 print 引发的协议流崩溃

一个开发者手写了 stdio MCP Server，功能都对，但客户端总在第二条消息报「JSON 解析失败」。他反复检查工具逻辑无果。真相是：他在 `tools/call` 处理函数里加了一行 `print(f"收到调用: {name}")` 用于调试。这行 `print` 默认输出到 stdout——而 stdout 正是 MCP 协议流所在。于是客户端读到的流变成了「一行合法 JSON-RPC 响应 + 一行 `收到调用: add` 的非法文本」，解析器在后者上崩溃。

规范对此写得很清楚：Server **不得**向 stdout 写任何不是有效 MCP 消息的内容，但**可以**向 stderr 写日志 [来源](https://modelcontextprotocol.io/specification/2025-11-25/basic/transports)。修复只需把 `print(...)` 改成 `print(..., file=sys.stderr)`，或用 `logging` 配置到 stderr。这个坑之所以高频，是因为 Python 的 `print` 默认走 stdout，而单机测试脚本时 stdout 和 stderr 混在一个终端里看不出区别，只有接上真正的 stdio 客户端才暴露。本章第 5 节的 Server 从一开始就遵守这条规则，你可以把它作为「正确姿势」的参照。

## 官方案例边界

两种标准传输、stdio 的收发规则、Streamable HTTP 的单端点与会话机制、安全警告、以及传输层的版本演进与向后兼容路径，都有官方规范支撑 [来源](https://modelcontextprotocol.io/specification/2025-11-25/basic/transports)。但「升级 SDK 后握手 400」和「print 污染 stdout」这两个事故是本书构造的教学案例，用于说明规范条款的现实后果；具体某个 SDK 版本的默认传输、某次换代的精确行为差异，以官方 changelog 与规范当前页面为准。
