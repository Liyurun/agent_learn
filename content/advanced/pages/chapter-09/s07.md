## 真实问题

一个团队把手写的 MCP（Model Context Protocol，模型上下文协议）Server 从本地 stdio 调试环境迁到生产的远程部署后，线上开始零星报「Agent 偶发无响应」。这个告警和第 27 章那条「回答质量下降」一样无法直接行动——问题可能在传输层、握手、错误分类、版本协商、权限或后端任意一环。值班人员若凭直觉去「重启 Server」或「换更大模型」，往往治标不治本。生产环境的 MCP 故障诊断，必须先固定输入、保存一条完整的 `initialize → tools/list → tools/call` 轨迹，再按协议分层逐一排查，而不是把一切归结为「MCP 不稳定」。本节汇总一张覆盖全链路的症状矩阵，并给出面试高频的思考回答。

## 诊断顺序

一条可行动的 MCP 诊断路径，应严格按协议分层自底向上排查：

1. **传输层**：stdout 是否混入了非 JSON-RPC 内容（`print` 污染）；stdio 消息是否含嵌入换行；远程 HTTP 是否校验了 `Origin`、绑定了正确接口。
2. **握手层**：是否完成了 `initialize → notifications/initialized` 才开始调用；协议版本是否协商成功、有无回退。
3. **语义层**：无 `id` 的通知是否被错误地当请求等回复；请求响应是否严格按 `id` 配对。
4. **错误分类层**：业务失败是否被错回成协议级 `error`；结构错误是否被错回成 `isError`。
5. **原语归属层**：只读数据是否被误做成 Tool（模型乱读）；用户工作流是否被误做成 Tool（擅自触发）。
6. **信任层**：接入的公共 Server 是否可信、是否锁版本；工具描述是否被当成不可信输入审计。
7. **后端层**：真正的 API（Application Programming Interface，应用程序接口）/ 数据库 / 文件访问是否正常，权限与幂等是否正确。

## 症状矩阵

下表是本章各小节踩坑的汇总，覆盖从传输到后端的全链路。每一行都对齐「症状 → 根因 → 观测与复现 → 修复与预防 → 不适用边界」，可直接用作值班手册：

| 症状 | 根因 | 如何观测与复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| 客户端解析协议流失败 | Server 往 stdout 写了调试 print | 在处理函数加一行 print 到 stdout 复现 | 日志全走 stderr，stdout 只放 JSON-RPC | 非 stdio 传输不受此限 |
| stdio 消息被截断或粘连 | 单条消息含嵌入换行，破坏分帧 | 构造含 \n 的字段序列化后发送 | 序列化后校验无嵌入换行再发 | 长度前缀分帧的实现另行处理 |
| 升级客户端后握手 400 | 依赖已废弃的 HTTP+SSE 两端点 | 用新客户端连旧 Server 复现 | 迁移 Streamable HTTP 或做双端点兼容 | 两端同步升级的封闭内网可暂缓 |
| 本地 Server 被远程网页调用 | HTTP 绑 0.0.0.0 且不校验 Origin | 从外部主机尝试连接本地端口 | 绑 127.0.0.1、校验 Origin、加认证 | 受控内网加网关鉴权可放宽 |
| 握手前直接调用工具报错 | 跳过 initialize，Server 未就绪 | 不发 initialize 直接 tools/call | 严格按 initialize→initialized→调用 | 复用已建立会话无需重握手 |
| 客户端对通知一直等回复挂起 | 对无 id 的通知也调了 readline | 发一条无 id 通知后立即 readline | 通知不读回复，只有 request 才等 | 某些实现要求对特定通知回 ACK |
| 请求与响应对不上号 | 忽略 id 配对，按顺序假设回包 | 并发发两个请求交换返回顺序 | 严格用 id 匹配，维护 pending 表 | 纯同步一问一答风险较低 |
| 中文结果变成 uXXXX 转义 | json.dumps 未设 ensure_ascii=False | 打印含中文的结果观察 | 序列化统一加 ensure_ascii=False | 纯 ASCII 场景无影响 |
| 合法业务失败被当协议错误 | 业务异常也回成 JSON-RPC error | 查一个不存在的工单看返回类型 | 业务失败回 isError=true 供模型纠正 | 请求结构错误仍回协议 error |
| 模型乱读一堆不相关文档 | 只读数据被做成 Tool 让模型自主调用 | 记录工具调用序列看是否高频读无关数据 | 只读数据改 Resource，由应用按策略加载 | 确需按需检索时可保留检索型 Tool |
| 模型擅自触发用户流程 | 用户工作流被做成 Tool | 观察无用户请求时是否有该工具调用 | 改为 Prompt，仅用户主动触发 | 明确授权的自动化可用 Tool |
| 危险动作无人确认直接执行 | Tool 缺少人在回路确认 | 注入一个删除类工具看是否直接执行 | 敏感 Tool 加确认与审计、展示参数 | 幂等只读操作确认可从简 |
| 接入的公共 Server 悄改行为 | 依赖不可信来源且未锁版本 | 对比不同时间拉取的 tools/list | 锁版本、接入前审计、沙箱隔离 | 自建可信内网 server 风险低 |
| 恶意工具描述诱导模型越权 | 未把工具描述当不可信输入 | 注入含隐藏指令的工具描述复现 | 审计工具描述，敏感动作人在回路 | 仅内部可信 server 可放宽 |
| 不同应用协议版本不一致 | 客户端 SDK 版本参差未协商 | 用旧版客户端连新 server 观察握手 | 严格实现版本协商与回退 | 全栈同步升级可暂缓 |
| 子进程退出后管道报错 | 未正确关闭 stdin 并 wait | 不调 close 直接结束进程复现 | finally 关 stdin 并 wait 超时 | 长驻服务用不同生命周期管理 |
| 工具很多时 tools/list 卡顿或超限 | 未分页，一次返回全部工具 | 注册大量工具后拉全量清单 | 用规范的 cursor 分页按需拉取 | 工具数很少时无需分页 |

SDK（Software Development Kit，软件开发工具包）会替你处理其中很多细节，但生产中你仍要能读懂这些症状背后的协议语义——否则出问题时无法定位是 SDK、传输还是后端的责任。

## 最小可运行演示

把上面的诊断顺序固化成一棵规则树，就能把「MCP 接入出问题了」这句模糊描述，映射到最优先排查的方向。它不替代基于轨迹的根因分析，但能在值班时快速缩小范围：
```python
from __future__ import annotations


def diagnose(signals: dict) -> str:
    """一棵最小诊断规则树：把模糊的「MCP 接入出问题了」拆成可行动的方向。
    输入是一组可观测信号，输出最先应排查的方向；顺序即优先级。
    """
    if signals["stdout_has_non_json"]:
        return "传输：Server 往 stdout 写了非 JSON-RPC 内容，改走 stderr"
    if not signals["initialized"]:
        return "握手：未完成 initialize/initialized 就调用，先补握手"
    if signals["waiting_reply_for_notification"]:
        return "语义：对无 id 的通知在等回复，通知不读回复"
    if signals["protocol_error_code"] == -32601:
        return "协议：方法名不存在(-32601)，核对 method 拼写与版本"
    if signals["business_failed"] and not signals["is_error_flag"]:
        return "错误分类：业务失败被回成协议 error，应回 isError=true"
    return "进入基于轨迹的复现：固定输入重放 initialize→list→call"


def main() -> None:
    sample = {
        "stdout_has_non_json": False,
        "initialized": True,
        "waiting_reply_for_notification": False,
        "protocol_error_code": 0,
        "business_failed": True,
        "is_error_flag": False,
    }
    print(diagnose(sample))


if __name__ == "__main__":
    main()
```
保存为 `mcp_diagnose.py`，运行 `python mcp_diagnose.py`。预期输出：
```text
错误分类：业务失败被回成协议 error，应回 isError=true
```
这个样例信号里，传输、握手、语义都正常，但「业务失败了却没标 isError」，规则树精确指向了错误分类层。把你的真实告警信号填进这个字典，就能得到第一排查方向。规则树用于缩小范围，真正定位仍要靠第 5 节那套可复现的轨迹重放。

## 真实系统对应

**官方公开机制**：症状矩阵里涉及的传输规则、错误分类、版本协商、tools/list 分页、安全要求，均对齐官方规范 [来源](https://modelcontextprotocol.io/specification/2025-11-25/basic/transports) [来源](https://modelcontextprotocol.io/specification/2025-11-25/server/tools)。官方也提供了跨主流语言的 SDK 与调试工具，生产应优先使用它们而非手写传输 [来源](https://www.anthropic.com/news/donating-the-model-context-protocol-and-establishing-of-the-agentic-ai-foundation)。**通用工程模式**：把诊断拆成「传输→握手→语义→错误→原语→信任→后端」七层、用规则树缩小范围，是从可观测信号提炼的可迁移做法。**教学参考实现**：`mcp_diagnose.py` 的规则与信号字段是本书构造，真实平台的告警字段、采样、脱敏与阈值由团队按风险设计，本节不声称任何平台自动完成这些治理。

## 生产建议清单

除了症状矩阵，生产接入 MCP 还应遵循几条通用工程约束：其一，能用官方 SDK 就不手写传输——手写骨架适合学习，生产要用维护良好的 SDK 以获得分页、并发、取消、认证的完整实现。其二，把每次 `tools/call` 的输入、输出、耗时、错误类型（协议级还是执行级）都记进可观测系统，关联一个 trace_id，事故时才能重放。其三，对接入的每个 Server 做来源审计与版本锁定，像对待第三方依赖一样管理供应链。其四，敏感 Tool 一律走人在回路确认，把「是否放行」的控制权留在模型之外。其五，本地工具默认 stdio、远程服务默认 Streamable HTTP，且远程务必补齐 Origin 校验、绑定与认证。

## 思考：手写 MCP Server 和用官方 SDK，生产上到底该选哪个？

### 回答

学习阶段手写、生产阶段用 SDK，两者目的不同。手写一个最小 MCP-like server（如第 5 节）的价值在于「透视」——它让你看清 `initialize/tools/list/tools/call` 三条消息、两类错误、stdio 收发规则在底层到底是什么，之后用任何 SDK 都不再是黑盒。但手写骨架刻意省略了分页、能力协商完整字段、Resources/Prompts 原语、并发、请求取消、超时、认证与 Streamable HTTP——这些恰恰是生产必需的。官方 SDK 覆盖所有主流语言、月下载量以千万计、由社区持续维护，替你正确实现了这些。所以生产结论是：用官方 SDK，并遵循其安全建议；手写只用于学习和调试透视。把手写骨架直接上生产，等于放弃了 SDK 已经踩平的所有坑。

### 面试精简表达

手写是透视镜（看懂协议底层），SDK 是生产工具（分页/并发/取消/认证/HTTP 全都替你实现好）。学习手写、生产用 SDK，别拿教学骨架上线。

## 思考：MCP 出故障时，如何快速判断责任在协议层还是后端？

### 回答

靠「两类错误」和「分层轨迹」定位。先看返回：如果是 JSON-RPC 的 `error` 对象（如 -32601 方法不存在、-32602 未知工具），责任在协议层——请求结构、方法名或工具名不对，与后端无关；如果是带 `isError: true` 的 `result`，责任在后端或业务逻辑——工具执行了但失败了，错误文本里通常有可行动信息。再看轨迹：固定输入重放 `initialize → tools/list → tools/call`，看握手是否成功、工具是否被发现、调用是否发出。握手失败是协议/版本问题，发现不到工具是注册问题，调用发出但结果错是后端问题。把每次调用的输入、输出、错误类型、耗时记进可观测系统，关联 trace_id，就能在协议层和后端层之间快速切分责任，而不是笼统地说「MCP 挂了」。

### 面试精简表达

看错误类型：协议 error 归协议层（结构/方法/工具名），isError 归后端/业务；再用固定输入重放握手-发现-调用三段轨迹,定位卡在哪一层。

## 思考：MCP 和 Function Calling 的关系，为什么是面试高频陷阱？

### 回答

因为很多人误以为二者是「二选一」的竞争关系，实则是不同层的互补关系。Function Calling 是「模型和运行时之间的语言」——解决「模型如何提议调用某个工具、生成什么参数」；MCP 是「运行时和工具提供方之间的语言」——解决「工具方如何以标准方式被任意应用发现和接入」。一次真实调用里两者协作：模型通过 Function Calling 提议调 `get_ticket`，运行时通过 MCP 把这个调用标准化地发给工单 Server，Server 返回结果，运行时再回灌给模型。MCP 不替代 Function Calling，而是让 Function Calling 能调用的工具「来源标准化、可跨应用复用」。陷阱就在于问「MCP 是不是取代了 Function Calling」——正确答案是「不是，它们在不同层，MCP 在 Function Calling 的下一层，二者互补」。

### 面试精简表达

Function Calling 管「模型↔运行时」（怎么提议调用），MCP 管「运行时↔工具方」（怎么标准接入）；不同层、互补而非替代，MCP 让可被调用的工具跨应用复用。

## 事故回放：从「偶发无响应」到定位一个 print

把本节开头那个「Agent 偶发无响应」的告警按诊断顺序拆开，能看到手写 Server 迁到生产后最典型的一类故障。值班人员先固定输入、重放握手轨迹，发现 `initialize` 正常、`tools/list` 正常，但某些 `tools/call` 之后客户端就再也读不到下一条响应——表现为「偶发无响应」而非「报错」。这排除了握手和版本问题，把嫌疑集中到「协议流被污染」上。

进一步排查发现，是某个工具的处理分支里残留了一行调试用的 `print(f"processing {name}")`，默认输出到 stdout。本地 stdio 调试时 stdout 和 stderr 混在一个终端里看不出问题；一旦接上严格解析的生产客户端，这行非法文本就插进了协议流，客户端解析器在它上面卡住，后续响应全被阻塞——于是表现为「偶发无响应」（只有走到那个分支才触发）。修复只是把 `print` 改成 `print(..., file=sys.stderr)`。

这次事故的教训有三：第一，手写 Server 的 stdout 纪律在生产环境是硬约束，而它恰恰最容易在「本地能跑」时被忽视；第二，「偶发」往往意味着「只有特定分支触发」，用固定输入覆盖全部分支就能稳定复现；第三，可观测性要记录「客户端在哪条消息后卡住」，而不只是「有没有报错」——无响应和报错是两种完全不同的故障信号。这也再次印证了第 4 节的结论：日志走 stderr、stdout 只放合法 JSON-RPC，不是可选建议，而是生产铁律。
