## 真实问题

一个团队第一次接 MCP，把「Host」和「Client」当成同一个东西，于是写了一个大类，让它同时管理三个后端 Server 的连接、共享一份读写缓冲区。结果某天数据库 Server 卡住不返回，整个大类的事件循环被这一个慢连接拖住，桌面助手连带无法调用本来正常的 GitHub Server 和文件系统 Server——一个下游超时，拖垮了全部能力。他们困惑：「不就是一个应用连三个工具吗，为什么要分这么多层？」这个困惑恰恰是 MCP 三方架构存在的理由。

## 原理：三方角色各管一段

MCP 定义了清晰的三角色架构，官方文档与生态资料反复强调 Client 与 Server 之间是**一对一**关系 [来源](https://modelcontextprotocol.io/)：
```text
   ┌──────────────┐        ┌──────────────┐        ┌──────────────┐
   │    Host      │        │    Client    │        │    Server    │
   │  (宿主应用)   │◀──────▶│  (协议连接器) │◀──────▶│  (工具提供方) │
   │ Claude Desktop│        │  一对一连接   │        │  GitHub 等   │
   └──────────────┘        └──────────────┘        └──────────────┘
```
| 角色 | 职责 | 一句话定位 |
|---|---|---|
| Host（宿主） | 用户直接交互的 AI 应用，管理模型、聚合能力、做最终决策 | 「谁在跟用户对话」 |
| Client（客户端） | 宿主内部的协议连接器，与某个 Server 建立并维护一对一连接 | 「谁在管这条连接」 |
| Server（服务端） | 对外暴露 Tools / Resources / Prompts 的工具提供方 | 「谁提供能力」 |

关键约束是：**每个 Client 只和一个 Server 保持一对一连接**。当 Host 要同时接入 GitHub、文件系统、数据库三个 Server 时，它在内部创建三个独立的 Client，各自维护一条连接：
```text
        ┌───────────── Host（Claude Desktop）──────────────┐
        │                                                  │
        │   Client A ──一对一──▶  GitHub Server            │
        │   Client B ──一对一──▶  Filesystem Server        │
        │   Client C ──一对一──▶  Database Server          │
        │                                                  │
        └──────────────────────────────────────────────────┘
```
上面那个团队的 bug 根因就在这里：他们把三条连接塞进了一个共享事件循环，破坏了「一对一 + 隔离」的设计意图。正确做法是每个 Server 对应一个独立 Client，某个 Server 崩了、超时了、返回垃圾数据，只影响对应的那个 Client，不会污染其他连接。这是典型的「故障隔离」——和微服务里「一个下游挂了不拖垮整体」是同一个思想。Host 负责聚合与决策（把哪些能力交给模型看），Client 负责协议细节与连接生命周期，职责清晰、互不干扰。

## 为什么底层选 JSON-RPC 2.0

MCP 用 JSON-RPC（JSON Remote Procedure Call，JSON 远程过程调用）2.0 作为消息格式 [来源](https://modelcontextprotocol.io/specification/2025-11-25/basic/transports)。一条请求长这样：
```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "tools/call",
  "params": { "name": "get_ticket", "arguments": { "ticket_id": "TICKET-101" } }
}
```
对应的成功响应用相同的 `id` 配对：
```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "result": { "content": [{ "type": "text", "text": "登录超时，负责人 alice" }] }
}
```
选它的理由有三，都可从 JSON-RPC 2.0 规范核验 [来源](https://www.jsonrpc.org/specification)：

- **极简且语言无关**：本质就是 JSON，任何语言都能轻松收发，天然适合「Python 写 Server、TypeScript 写 Client」这种跨语言场景。
- **请求-响应用 `id` 配对**：`id` 让请求和响应能对上号，支持异步、乱序、批量——这与第 8 章 Function Calling 的调用 id 是同一个思路。
- **支持通知（notification）**：没有 `id` 的消息就是「通知」，发出去不等回复，适合「工具列表变了」（`notifications/tools/list_changed`）这类服务端主动推送的事件，或客户端的 `notifications/initialized` 握手确认。

## MCP 在技术栈中的位置

把 MCP 放进整个调用栈，它的分层定位就清楚了：
```text
┌─────────────────────────────────────────────┐
│  用户 / 业务逻辑                                │
├─────────────────────────────────────────────┤
│  模型推理层：LLM 通过 Function Calling 提议调用  │ ← 第 8 章
├─────────────────────────────────────────────┤
│  MCP 协议层：标准化「发现 / 调用工具、读资源」     │ ← 本章
│  （JSON-RPC 2.0 消息 + stdio / HTTP 传输）      │
├─────────────────────────────────────────────┤
│  工具实现层：真实的 API / DB / 文件系统           │
└─────────────────────────────────────────────┘
```
**Function Calling 是「模型和运行时之间的语言」，MCP 是「运行时和工具提供方之间的语言」**。两者在不同的层，各管一段，所以是互补而非替代——这是本章最重要的一句话，也是面试高频陷阱题的答案。模型仍然通过 Function Calling 机制提议调用工具；MCP 负责把工具以标准化的方式暴露给应用，让同一个工具服务能被不同应用复用。

## 最小可运行演示

下面用一段纯标准库代码，模拟「一个 Host 内的三个 Client 各连一个 Server」，并演示故障隔离：当 database Server 抛错时，其他两个 Client 仍能正常工作。
```python
class FakeServer:
    def __init__(self, name: str, healthy: bool = True) -> None:
        self.name = name
        self.healthy = healthy

    def call(self, method: str) -> dict:
        if not self.healthy:
            raise TimeoutError(f"{self.name} 无响应")
        return {"server": self.name, "method": method, "ok": True}

class Client:
    """一对一连接器：只负责它自己那台 Server。"""
    def __init__(self, server: FakeServer) -> None:
        self.server = server

    def call(self, method: str) -> dict:
        try:
            return self.server.call(method)
        except TimeoutError as exc:
            return {"server": self.server.name, "ok": False, "error": str(exc)}

class Host:
    def __init__(self, servers: list[FakeServer]) -> None:
        self.clients = [Client(s) for s in servers]  # 每个 Server 一个独立 Client

    def broadcast(self, method: str) -> list[dict]:
        return [c.call(method) for c in self.clients]

def main() -> None:
    servers = [
        FakeServer("github"),
        FakeServer("filesystem"),
        FakeServer("database", healthy=False),  # 故意让它坏掉
    ]
    host = Host(servers)
    for result in host.broadcast("tools/list"):
        state = "OK" if result["ok"] else f"FAIL({result['error']})"
        print(f"{result['server']:>10}: {state}")

if __name__ == "__main__":
    main()
```
保存为 `isolation.py`，运行 `python isolation.py`。预期输出：
```text
    github: OK
filesystem: OK
  database: FAIL(database 无响应)
```
database 的故障被限制在它自己的 Client 里，github 和 filesystem 不受影响。这就是「一对一连接 + 故障隔离」在代码层的体现——如果三条连接共享一个会抛异常的循环，一台坏掉会让整个 `broadcast` 崩溃。

## 真实系统对应

**官方公开机制**：MCP 官方规范明确使用 JSON-RPC 编码消息，且 `initialize`、`tools/list`、`tools/call` 等方法名与消息结构均有文档定义 [来源](https://modelcontextprotocol.io/specification/2025-11-25/server/tools)；生态资料明确 Host 内的 Client 与 Server 是一对一关系，Host 是用户交互的 AI 应用（如 Claude Desktop、Cursor、ChatGPT、自研 app）[来源](https://www.linuxfoundation.org/press/linux-foundation-announces-the-formation-of-the-agentic-ai-foundation)。**通用工程模式**：把「一对一连接」解释为「故障隔离」，把三角色类比为「宿主/连接器/提供方」，是可迁移的工程推导。**教学参考实现**：上面的 `Host`/`Client`/`FakeServer` 类只演示隔离思想，不代表任何产品的进程模型或线程模型。

## 生产踩坑

| 症状 | 根因 | 如何观测与复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| 一个 Server 超时，全部能力不可用 | 多条连接共享同一阻塞循环，破坏一对一隔离 | 让一台 Server 故意 sleep，观察其他工具是否也卡 | 每个 Server 一个独立 Client，加独立超时 | 单 Server 场景无需强隔离 |
| 请求与响应对不上号 | 忽略 JSON-RPC 的 `id` 配对，按顺序假设回包 | 并发发两个请求，交换返回顺序复现 | 严格用 `id` 匹配，维护 pending 表 | 纯同步一问一答时风险较低 |
| 通知被当成请求等回复 | 没区分有无 `id`，对通知也阻塞等待 | 发一条无 id 的 notification 看是否挂起 | 无 id 消息不读回复，只有 request 才等 | 某些实现要求对特定通知回 ACK |
| 握手前直接调用工具报错 | 跳过 initialize，Server 未进入就绪态 | 不发 initialize 直接 tools/call 复现 | 严格按 initialize → initialized → 调用 | 复用已建立会话时无需重握手 |

## 思考：为什么要把 Client 从 Host 里单独拆出来？

### 回答

因为 MCP 规定 Client 与 Server 是一对一连接，把连接管理从 Host 中抽象成独立的 Client，能获得三重好处。第一是故障隔离：某个 Server 崩溃、超时或返回垃圾数据，只影响它对应的那个 Client，不会拖垮 Host 里其他连接。第二是职责单一：Host 专注聚合能力与决策（把哪些工具交给模型看、如何解释结果），Client 专注协议细节与连接生命周期（握手、发现、重连、超时）。第三是可扩展：Host 要接入第 N 个 Server 时，只需再实例化一个 Client，不需要改动已有连接的逻辑。很多人只能背出三者是什么，答不出「为什么」，加分点正是「一对一连接 + 故障隔离」。

### 面试精简表达

Host 是跟用户对话的应用，Client 是一对一连接某个 Server 的连接器，Server 是能力提供方；拆出 Client 是为了故障隔离与职责单一——一个下游挂了不拖垮整体。

## 机制推导：一条请求从 Host 到 Server 再回来的完整路径

设想用户在桌面助手里问「TICKET-101 现在谁负责」。这句话先进入 Host 的模型推理层，模型通过 Function Calling 判断需要调用 `get_ticket` 工具并生成参数 `{"ticket_id": "TICKET-101"}`。Host 把这个意图交给「连着工单 Server 的那个 Client」。Client 把它封装成一条 JSON-RPC 请求 `{"jsonrpc":"2.0","id":7,"method":"tools/call","params":{"name":"get_ticket","arguments":{"ticket_id":"TICKET-101"}}}`，通过传输层（stdio 或 HTTP）发给 Server。

Server 收到后，根据 `method` 分派到 `tools/call` 处理逻辑，执行真正的后端查询（这里是查内存字典），把结果包成 `{"jsonrpc":"2.0","id":7,"result":{"content":[...],"structuredContent":{...}}}` 回传。Client 依据 `id=7` 把这条响应匹配回原来的请求，交还给 Host。Host 再把结构化结果回灌给模型，模型据此生成人类可读的回答。

这条路径里，每一层的边界都很清晰：模型只负责「决定调什么」，MCP 协议层负责「标准化地传递调用与结果」，Server 负责「真正访问后端」。任何一层出问题，都能通过它的日志定位——模型选错工具是推理层问题，请求发不出去是传输层问题，后端查不到数据是 Server 实现问题。三层各自可观测，这正是分层架构的价值。

## 官方案例边界

MCP 官方规范以 JSON-RPC 编码消息、定义 `initialize` / `tools/list` / `tools/call` 等方法，这些是可核验的官方公开机制 [来源](https://modelcontextprotocol.io/specification/2025-11-25/server/tools)。Host、Client、Server 三方角色与一对一连接约束，也是官方与生态文档明确描述的 [来源](https://www.linuxfoundation.org/press/linux-foundation-announces-the-formation-of-the-agentic-ai-foundation)。但「三个 Client 共享循环导致连带故障」这个 bug、以及故障隔离的类比，是本书构造的教学案例，不对应任何产品的真实事故；具体某个 Host 内部如何实现连接池、线程模型、超时策略，官方并未公开，正文不做臆测。
