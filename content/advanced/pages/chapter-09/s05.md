## 真实问题

很多人学完 MCP 概念，却在「亲手写一个 Server」这一步卡住：官方 SDK（Software Development Kit，软件开发工具包）封装了太多细节，装依赖、配环境本身就是门槛，反而看不清协议底层到底在传什么。本节反其道而行——**不用任何第三方库，只用 Python 标准库，手写一个最小的 MCP-like server**，让你亲眼看到 `initialize`、`tools/list`、`tools/call` 这三条 JSON-RPC（JSON Remote Procedure Call，JSON 远程过程调用）消息在 stdio 上一来一回的完整轨迹。它不是官方 SDK 的替代品，而是「透视镜」：看懂它，你再用任何 SDK 都知道底层发生了什么。

这个 Server 复用本章的贯穿案例——一个内存里的工单系统，暴露 `list_tickets`、`get_ticket`、`add_number` 三个工具。全部代码无需网络、无需 API（Application Programming Interface，应用程序接口）Key，只依赖 Python 3.8+ 标准库。

## 原理：一个 Server 只需要处理三类消息

一个能跑通的最小 MCP-like server，本质只需正确响应三个方法，外加对「通知」与「错误」的处理：
```text
initialize                能力协商握手：告诉 Client 我是谁、支持什么
tools/list                动态发现：返回工具名 + 描述 + inputSchema
tools/call                调用工具：执行并返回结果，区分两类错误
notifications/initialized 通知（无 id）：Client 确认握手完成，无需回复

错误分两类（对齐官方规范）：
  协议级错误（JSON-RPC error）：未知方法、未知工具 -> 返回 error 对象
  工具执行错误（isError: true）：参数不合法、业务失败 -> 返回 result 但标 isError
```
官方规范对这两类错误的区分很关键：工具执行错误（`isError: true`）包含可供模型自我纠正的反馈，Client 应把它交给模型；而协议级错误（如未知工具的 `-32602`）表示请求结构本身有问题，模型较难修复 [来源](https://modelcontextprotocol.io/specification/2025-11-25/server/tools)。我们的 Server 会精确地体现这一区分。

## 最小可运行演示：Server 端（保存为 `ticket_mcp_server.py`）

第一件套是 Server。它逐行读取 stdin 上的 JSON-RPC 消息，分派处理，把响应写回 stdout；所有日志走 stderr，绝不污染协议流（这正是第 4 节强调的 stdio 铁律）：
```python
from __future__ import annotations

import json
import sys

PROTOCOL_VERSION = "2025-11-25"

TICKETS = {
    "TICKET-101": {"title": "登录超时", "owner": "alice", "status": "open"},
    "TICKET-102": {"title": "报表导出乱码", "owner": "bob", "status": "closed"},
}


def _tool_list_tickets() -> dict:
    """列出全部工单的 id 与标题（只读）。"""
    return {"tickets": [{"id": k, "title": v["title"]} for k, v in TICKETS.items()]}


def _tool_get_ticket(ticket_id: str) -> dict:
    """按 id 查单个工单（只读）。"""
    item = TICKETS.get(ticket_id)
    if item is None:
        raise ValueError(f"未找到工单：{ticket_id}")
    return {"id": ticket_id, **item}


def _tool_add_number(a: float, b: float) -> dict:
    """两数相加，纯计算无副作用。"""
    return {"sum": a + b}


TOOLS = {
    "list_tickets": {
        "name": "list_tickets",
        "title": "列出工单",
        "description": "列出全部工单的编号与标题，只读、无副作用。",
        "inputSchema": {"type": "object", "additionalProperties": False},
        "handler": _tool_list_tickets,
    },
    "get_ticket": {
        "name": "get_ticket",
        "title": "查询工单",
        "description": "根据工单编号返回标题、负责人与状态，只读。",
        "inputSchema": {
            "type": "object",
            "properties": {"ticket_id": {"type": "string", "description": "工单编号，如 TICKET-101"}},
            "required": ["ticket_id"],
        },
        "handler": _tool_get_ticket,
    },
    "add_number": {
        "name": "add_number",
        "title": "两数相加",
        "description": "把两个数字相加返回其和，用于演示模型控制的动作。",
        "inputSchema": {
            "type": "object",
            "properties": {
                "a": {"type": "number", "description": "第一个加数"},
                "b": {"type": "number", "description": "第二个加数"},
            },
            "required": ["a", "b"],
        },
        "handler": _tool_add_number,
    },
}


def log(message: str) -> None:
    """日志只走 stderr，绝不污染 stdout 的协议流。"""
    print(f"[server] {message}", file=sys.stderr)


def make_error(req_id, code: int, message: str) -> dict:
    return {"jsonrpc": "2.0", "id": req_id, "error": {"code": code, "message": message}}


def make_result(req_id, result: dict) -> dict:
    return {"jsonrpc": "2.0", "id": req_id, "result": result}


def handle(request: dict):
    """把一条 JSON-RPC 请求分派到对应方法；通知（无 id）返回 None。"""
    req_id = request.get("id")
    method = request.get("method")
    params = request.get("params") or {}

    if req_id is None:
        log(f"收到通知 {method}，无需回复")
        return None

    if method == "initialize":
        return make_result(req_id, {
            "protocolVersion": PROTOCOL_VERSION,
            "capabilities": {"tools": {"listChanged": False}},
            "serverInfo": {"name": "ticket-mcp", "version": "0.1.0"},
        })

    if method == "tools/list":
        tools = [
            {k: spec[k] for k in ("name", "title", "description", "inputSchema")}
            for spec in TOOLS.values()
        ]
        return make_result(req_id, {"tools": tools})

    if method == "tools/call":
        name = params.get("name")
        arguments = params.get("arguments") or {}
        spec = TOOLS.get(name)
        if spec is None:
            return make_error(req_id, -32602, f"Unknown tool: {name}")
        try:
            payload = spec["handler"](**arguments)
        except TypeError as exc:
            return make_result(req_id, {
                "content": [{"type": "text", "text": f"参数错误：{exc}"}],
                "isError": True,
            })
        except ValueError as exc:
            return make_result(req_id, {
                "content": [{"type": "text", "text": str(exc)}],
                "isError": True,
            })
        return make_result(req_id, {
            "content": [{"type": "text", "text": json.dumps(payload, ensure_ascii=False)}],
            "structuredContent": payload,
            "isError": False,
        })

    return make_error(req_id, -32601, f"Method not found: {method}")


def main() -> None:
    log("ticket-mcp 启动，等待 stdin 上的 JSON-RPC 消息")
    for line in sys.stdin:
        line = line.strip()
        if not line:
            continue
        try:
            request = json.loads(line)
        except json.JSONDecodeError:
            sys.stdout.write(json.dumps(make_error(None, -32700, "Parse error")) + "\n")
            sys.stdout.flush()
            continue
        response = handle(request)
        if response is not None:
            sys.stdout.write(json.dumps(response, ensure_ascii=False) + "\n")
            sys.stdout.flush()


if __name__ == "__main__":
    main()
```
**逐块讲解**：

- `TOOLS` 注册表：每个工具带 `name`、`title`、`description`、`inputSchema`（一个 JSON Schema）和 `handler`（真正的实现）。`tools/list` 只暴露前四项，`handler` 留在 Server 内部——这对应官方规范里 Tool 定义的字段结构 [来源](https://modelcontextprotocol.io/specification/2025-11-25/server/tools)。
- `handle()`：按 `method` 分派。`initialize` 回 `serverInfo` 与 `capabilities`；`tools/list` 回工具清单；`tools/call` 查表、调用、包装结果。
- **两类错误的精确区分**：未知工具（`spec is None`）返回 JSON-RPC `error`（协议级，code `-32602`）；参数类型不对（`TypeError`）或业务失败（`ValueError`，如工单不存在）返回带 `isError: true` 的 `result`（工具执行错误）。这与官方规范完全一致。
- `log()` 走 stderr：把「收到通知」这类调试信息写到 stderr，stdout 只放合法 JSON-RPC，避免第 4 节讲的「print 污染协议流」事故。

## 最小可运行演示：Client 端（保存为 `ticket_mcp_client.py`）

第二件套是 Client。它用标准库 `subprocess` 把 Server 当子进程拉起（这就是 stdio 传输），依次发送握手、通知、发现、调用消息，并按 `id` 匹配响应：
```python
from __future__ import annotations

import json
import subprocess
import sys
from pathlib import Path

SERVER = Path(__file__).with_name("ticket_mcp_server.py")


class StdioClient:
    def __init__(self, server_path: Path) -> None:
        self.proc = subprocess.Popen(
            [sys.executable, str(server_path)],
            stdin=subprocess.PIPE,
            stdout=subprocess.PIPE,
            stderr=subprocess.DEVNULL,
            text=True,
            bufsize=1,
        )
        self._id = 0

    def _next_id(self) -> int:
        self._id += 1
        return self._id

    def request(self, method: str, params: dict | None = None) -> dict:
        req_id = self._next_id()
        msg = {"jsonrpc": "2.0", "id": req_id, "method": method}
        if params is not None:
            msg["params"] = params
        self._send(msg)
        return json.loads(self.proc.stdout.readline())

    def notify(self, method: str, params: dict | None = None) -> None:
        msg = {"jsonrpc": "2.0", "method": method}
        if params is not None:
            msg["params"] = params
        self._send(msg)

    def _send(self, msg: dict) -> None:
        self.proc.stdin.write(json.dumps(msg, ensure_ascii=False) + "\n")
        self.proc.stdin.flush()

    def close(self) -> None:
        self.proc.stdin.close()
        self.proc.wait(timeout=5)


def show(title: str, payload) -> None:
    print(f"[{title}] {json.dumps(payload, ensure_ascii=False)}")


def main() -> None:
    client = StdioClient(SERVER)
    try:
        init = client.request("initialize", {
            "protocolVersion": "2025-11-25",
            "capabilities": {},
            "clientInfo": {"name": "ticket-client", "version": "0.1.0"},
        })
        show("initialize", init["result"]["serverInfo"])

        client.notify("notifications/initialized")

        listed = client.request("tools/list")
        show("tools/list", [t["name"] for t in listed["result"]["tools"]])

        got = client.request("tools/call", {"name": "get_ticket", "arguments": {"ticket_id": "TICKET-101"}})
        show("call get_ticket", got["result"]["structuredContent"])

        added = client.request("tools/call", {"name": "add_number", "arguments": {"a": 2, "b": 3}})
        show("call add_number", added["result"]["structuredContent"])

        unknown = client.request("tools/call", {"name": "drop_table", "arguments": {}})
        show("protocol error", unknown["error"])

        missing = client.request("tools/call", {"name": "get_ticket", "arguments": {"ticket_id": "TICKET-999"}})
        show("tool error", {"isError": missing["result"]["isError"],
                             "text": missing["result"]["content"][0]["text"]})
    finally:
        client.close()


if __name__ == "__main__":
    main()
```
**逐块讲解**：

- `subprocess.Popen([...], stdin=PIPE, stdout=PIPE)`：以子进程方式拉起 Server，这正是 stdio 传输——Host 与 Server 通过管道通信，无网络端口。`stderr=DEVNULL` 表示忽略 Server 的日志（Client 不应把 stderr 当错误信号）。
- `request()`：分配自增 `id`，发送后用 `readline()` 读一行响应并按 JSON 解析——一问一答，靠 `id` 配对。
- `notify()`：发送无 `id` 的通知，**不读回复**（这对应第 2 节踩坑表里「通知被当请求等回复」的正确姿势）。
- `main()` 里六次交互，覆盖了握手、发现、正常调用、协议级错误、工具执行错误的全部路径。

## 真实系统对应

**官方公开机制**：`initialize` / `tools/list` / `tools/call` 的消息结构、Tool 定义字段（`name`/`title`/`description`/`inputSchema`）、以及「协议级错误 vs 工具执行错误」的区分，均严格对齐官方规范 [来源](https://modelcontextprotocol.io/specification/2025-11-25/server/tools)；stdio 的收发规则对齐传输层规范 [来源](https://modelcontextprotocol.io/specification/2025-11-25/basic/transports)。**通用工程模式**：用 subprocess + 管道模拟 stdio、用 `id` 配对请求响应，是可迁移的实现方式。**教学参考实现**：这套 Server/Client/测试是本书构造的最小骨架，**不是官方 SDK**——它省略了分页、能力协商的完整字段、Resources/Prompts 原语、以及并发处理，只保留能说明「握手 + 发现 + 调用」闭环的核心。真实生产应使用官方 SDK 并遵循其安全建议。

## 生产踩坑

| 症状 | 根因 | 如何观测与复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| 客户端读不到响应一直挂起 | 对通知也调了 readline 等回复 | 发一条无 id 通知后立即 readline 复现 | 通知不读回复，只有 request 才 readline | 某些实现要求对特定通知回 ACK |
| 中文结果变成 \uXXXX 转义 | json.dumps 未设 ensure_ascii=False | 打印含中文的结果观察 | 序列化统一加 ensure_ascii=False | 纯 ASCII 场景无影响 |
| 未知工具让 Server 崩溃 | 未先查表就直接调用 handler | 调用不存在的工具名复现 | 先查 TOOLS，未命中返回 -32602 | 受信内部调用可简化校验 |
| 合法业务失败被当成协议错误 | 把业务异常也回成 JSON-RPC error | 查一个不存在的工单看返回类型 | 业务失败回 isError=true 供模型纠正 | 请求结构错误仍应回协议 error |
| 子进程退出后管道报错 | 未正确关闭 stdin 与 wait | 不调 close 直接结束进程复现 | finally 里关 stdin 并 wait 超时 | 长驻服务用不同生命周期管理 |

## 思考：为什么要区分「协议级错误」和「工具执行错误」？

### 回答

因为这两类错误的「可恢复性」和「应交给谁处理」完全不同。协议级错误（JSON-RPC 的 `error` 对象，如未知工具 `-32602`、方法不存在 `-32601`）表示请求的结构本身有问题——模型即使重试也很难修复，因为它不知道该改哪里，所以这类错误主要交给开发者排查。工具执行错误（`result` 里 `isError: true`，如参数越界、工单不存在）则包含可操作的反馈，模型读到「未找到工单：TICKET-999」后，有机会用正确的工单号重试，所以规范建议 Client 把这类错误交给模型以支持自我纠正。把业务失败错误地回成协议级 error，会剥夺模型自我纠正的机会；把结构错误回成 `isError`，又会让模型在无法修复的地方空转。本节的 Server 用「未知工具 → error，工单不存在 → isError」精确地体现了这个区分。

### 面试精简表达

协议级错误是「请求结构不对」，模型改不了，给开发者；工具执行错误是「业务失败」，含可纠正反馈，给模型重试。规范明确 Client 应把工具执行错误交给模型。

## 机制推导：从这个最小 Server 到官方 SDK 还差什么

这个 40 余行核心逻辑的 Server 已经能跑通完整闭环，但离生产级官方 SDK 还有明确的差距，理解这些差距能帮你判断何时该用 SDK。第一，它只实现了 Tools，没实现 Resources 和 Prompts 原语，也没实现 sampling/elicitation 这类客户端能力。第二，`tools/list` 没做分页（规范支持 `cursor` 分页），工具很多时会有问题。第三，`initialize` 的能力协商是简化的——真实握手要协商协议版本、声明双方 capabilities，并处理版本不兼容。第四，它是单线程一问一答，没有并发、没有请求取消（`CancelledNotification`）、没有超时。第五，它只支持 stdio，没有 Streamable HTTP，因此不能远程多租户部署。

但这些「缺失」恰恰反衬出这个骨架的教学价值：它把协议最核心的「握手 → 发现 → 调用 → 错误分类」这条主干剥离出来，让你看清 SDK 在底层到底替你做了什么。当你之后用官方 Python 或 TypeScript SDK 时，`@tool` 装饰器背后就是「往 `tools/list` 注册一条带 inputSchema 的记录」，`session.call_tool()` 背后就是「发一条 `tools/call` 并按 id 等响应」。看懂了骨架，SDK 对你就不再是黑盒。

## 官方案例边界

本节代码严格对齐官方规范的消息结构与错误语义 [来源](https://modelcontextprotocol.io/specification/2025-11-25/server/tools) [来源](https://modelcontextprotocol.io/specification/2025-11-25/basic/transports)，但它是本书构造的教学最小实现，**不是官方 SDK，也不声称覆盖完整规范**。工单数据是固定的内存字典，纯计算工具无任何副作用，全程不访问网络、不需要凭证。把它用于生产是不合适的——生产应使用官方维护的 SDK，并遵循其对认证、并发、分页、传输安全的完整实现与建议。
