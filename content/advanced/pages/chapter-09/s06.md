## 真实问题

一位架构师在 2025 年底给管理层做技术选型汇报，被问了一个尖锐的问题：「MCP（Model Context Protocol，模型上下文协议）会不会是某一家厂商的私有协议？我们押注它，会不会被单一供应商绑架？」他当时只能含糊回答「Anthropic 主导」，没能给出治理层面的确证。三个月后，答案变得清晰：MCP 被正式捐赠给 Linux 基金会下的一个中立基金，OpenAI、Google、微软等竞争对手同时成为采纳方与支持方。这个「协议归属」问题，恰恰是评估一个标准能否长期押注的关键——技术再好，若治理被单一厂商掌控，企业就要承担被绑架的风险。本节把 MCP 的采纳版图、治理结构和安全考量讲清楚，让你能回答「凭什么相信 MCP 是中立标准」。

## 现象与输入：MCP 的采纳版图

评估一个协议是否值得押注，先看「谁在用」。MCP 于 2024 年 11 月由 Anthropic 发布 [来源](https://www.anthropic.com/news/model-context-protocol)，一年内的采纳数据可从官方公告核验 [来源](https://www.anthropic.com/news/donating-the-model-context-protocol-and-establishing-of-the-agentic-ai-foundation)：
```text
采纳维度              可核验事实（截至 2025-12 官方公告）
─────────────────────────────────────────────────────────
公共 Server 数量      超过 10,000 个活跃的公共 MCP server
应用端采纳            ChatGPT、Cursor、Gemini、Microsoft Copilot、VS Code 等
基础设施部署          AWS、Cloudflare、Google Cloud、Microsoft Azure 提供部署支持
官方 SDK              覆盖所有主流语言；Python + TypeScript 月下载量 97M+
官方注册中心          社区驱动的 Registry，用于发现可用 server
Claude 连接器目录     75+ 个由 MCP 驱动的 connector
```
这里最值得注意的一点是：**采纳方里包含 Anthropic 的直接竞争对手**。OpenAI 不只是采纳者，还是核心贡献者——它把 MCP 作为 ChatGPT 里 connectors 与 apps 的基础，并早在 2025 年 3 月就在 ChatGPT 桌面应用、Agents SDK（Software Development Kit，软件开发工具包）与 Responses API（Application Programming Interface，应用程序接口）中采纳 [来源](https://openai.com/index/agentic-ai-foundation/)。Google 的 Gemini、微软的 Copilot 与 Visual Studio Code 也在采纳名单中。一个协议能让相互竞争的头部厂商都采纳，本身就是它「中立且好用」的最强信号——如果 MCP 只是 Anthropic 的私有格式，竞争对手没有理由采纳它。

## 原理：为什么捐给 Linux 基金会是「去厂商化」的关键一步

2025 年 12 月 9 日，Anthropic 正式把 MCP 捐赠给 **Agentic AI Foundation（AAIF，智能体 AI 基金会）**——一个隶属于 Linux 基金会的定向基金，由 Anthropic、Block、OpenAI 共同发起，并得到 Google、微软、AWS、Cloudflare、Bloomberg 的支持 [来源](https://www.anthropic.com/news/donating-the-model-context-protocol-and-establishing-of-the-agentic-ai-foundation)。理解这一步为什么重要，要看 Linux 基金会的角色：它是一个非营利组织，以中立托管、社区建设、共享基础设施著称，数十年间托管过 Linux 内核、Kubernetes、Node.js、PyTorch 等全球关键开源项目，有维持「厂商中立」的成熟记录 [来源](https://www.linuxfoundation.org/press/linux-foundation-announces-the-formation-of-the-agentic-ai-foundation)。

把协议交给这样一个中立基金，直接回应了本节开头那个「会不会被单一供应商绑架」的疑虑：

- **所有权中立化**：MCP 不再由 Anthropic 单独拥有，而是与 Block 的 goose、OpenAI 的 AGENTS.md 一起成为 AAIF 的创始项目，未来的演进由社区与多方共同推动。
- **治理模型不变**：官方明确捐赠后 MCP 的治理模型保持不变，维护者继续以社区意见和透明决策为优先 [来源](https://www.anthropic.com/news/donating-the-model-context-protocol-and-establishing-of-the-agentic-ai-foundation)。这意味着捐赠不是「换个老板」，而是给已有的开放治理加了一层制度保障。
- **规范持续演进**：2025-11-25 的规范发布引入了异步操作、无状态化、服务端身份、官方扩展机制等特性，说明协议在多方参与下仍在快速迭代 [来源](https://blog.modelcontextprotocol.io/posts/2025-11-25-first-mcp-anniversary/)。

对做技术选型的人来说，这条链路把「押注 MCP 的风险」从「赌一家公司的商业意图」降级为「跟随一个 Linux 基金会托管的开放标准」——这与当年押注 Linux、Kubernetes 的风险性质相同，是可承受的。

## 最小可运行演示

生态繁荣带来一个现实问题：不同应用、不同 SDK 可能停留在不同的协议版本上。规范用 `initialize` 里的版本协商来处理这种异构。下面用纯标准库模拟这套协商逻辑——客户端请求一个版本，Server 要么精确匹配、要么回退到自己支持的最新版，让客户端决定是否继续：
```python
from __future__ import annotations

SERVER_SUPPORTED = ["2024-11-05", "2025-03-26", "2025-06-18", "2025-11-25"]


def negotiate(client_requested: str, server_supported: list[str]) -> dict:
    """模拟 initialize 里的协议版本协商：
    - 若 Server 支持客户端请求的版本，则回该版本；
    - 否则回 Server 支持的最新版本，让客户端决定是否继续。
    """
    if client_requested in server_supported:
        return {"agreed": client_requested, "fallback": False}
    latest = sorted(server_supported)[-1]
    return {"agreed": latest, "fallback": True}


def main() -> None:
    cases = ["2025-11-25", "2025-03-26", "2099-01-01"]
    for requested in cases:
        result = negotiate(requested, SERVER_SUPPORTED)
        tag = "回退到最新" if result["fallback"] else "精确匹配"
        print(f"客户端请求 {requested} -> 协商结果 {result['agreed']} ({tag})")


if __name__ == "__main__":
    main()
```
保存为 `version_negotiate.py`，运行 `python version_negotiate.py`。预期输出：
```text
客户端请求 2025-11-25 -> 协商结果 2025-11-25 (精确匹配)
客户端请求 2025-03-26 -> 协商结果 2025-03-26 (精确匹配)
客户端请求 2099-01-01 -> 协商结果 2025-11-25 (回退到最新)
```
前两行说明只要 Server 支持客户端请求的版本就精确匹配；第三行说明客户端请求一个 Server 不认识的未来版本时，Server 回退到自己支持的最新版本，把「是否继续」的决定权交还客户端。真实握手远比这复杂（还要协商能力、处理不兼容），但这段骨架点出了「异构生态靠版本协商而非强制统一」的核心思路。

## 安全考量：开放生态的另一面

生态越大，攻击面越大。学术界已系统梳理过 MCP 的安全威胁面，指出 server 的安装、运行、更新各阶段都可能引入风险，如工具描述里的提示注入、被投毒的 server、过度授权、凭证泄露等 [来源](https://arxiv.org/abs/2503.23278)。规范本身也把安全写进了强制条款而非可选建议 [来源](https://modelcontextprotocol.io/specification/2025-11-25/basic/transports)：

- **传输层**：远程 Server 必须校验 `Origin` 头以防 DNS（Domain Name System，域名系统）重绑定，本地应只绑 127.0.0.1，并实现身份认证。
- **信任边界**：不要盲目信任任意公共 server；一个恶意 server 可以在工具描述里嵌入提示注入，诱导模型执行非预期动作。这正是「10,000+ 公共 server」繁荣背后的隐忧——数量不等于可信。
- **人在回路**：规范要求对敏感工具调用做可见提示与确认，把「是否放行」的最终控制权留在模型之外（见第 3 节）。
- **权限最小化**：Server 应遵循最小权限原则，只暴露必要能力；企业接入公共 server 前应做来源审计与沙箱隔离。

一句话概括：MCP 把「接入」标准化了，但没有、也不可能把「信任」自动化。选用任何公共 server，都要像引入第三方依赖一样做供应链审计。

## 真实系统对应

**官方公开机制**：采纳数据（10,000+ 公共 server、97M+ SDK 月下载、75+ Claude 连接器）、采纳方名单（ChatGPT、Cursor、Gemini、Microsoft Copilot、VS Code）、基础设施支持方（AWS、Cloudflare、Google Cloud、Azure）、以及捐赠给 AAIF 与治理模型不变，均来自 Anthropic 与 Linux 基金会的官方公告 [来源](https://www.anthropic.com/news/donating-the-model-context-protocol-and-establishing-of-the-agentic-ai-foundation) [来源](https://openai.com/index/agentic-ai-foundation/) [来源](https://www.linuxfoundation.org/press/linux-foundation-announces-the-formation-of-the-agentic-ai-foundation)。**通用工程模式**：把「协议捐给中立基金 = 降低厂商绑架风险」类比到 Linux/Kubernetes 的治理经验，是可迁移推导。**教学参考实现**：版本协商代码是本书构造的最小骨架，不代表任何 SDK 的真实协商实现；具体数字会随官方页面更新，本节不把某次检索值写成永久承诺。

## 生产踩坑

| 症状 | 根因 | 如何观测与复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| 接入的公共 Server 悄悄改了工具行为 | 依赖不可信来源的第三方 server，无版本锁定 | 对比不同时间拉取的 tools/list 定义 | 锁定 server 版本，接入前做来源审计与沙箱 | 自建可信内网 server 风险较低 |
| 不同应用连同一 Server 协议版本不一致 | 客户端 SDK 版本参差，未做协商 | 用旧版客户端连新 server 观察握手 | 严格实现 initialize 版本协商与回退 | 全栈同步升级时可暂缓 |
| 恶意工具描述诱导模型越权 | 未把工具描述当成不可信输入 | 注入含隐藏指令的工具描述复现 | 对工具描述做审计，敏感动作人在回路确认 | 仅内部可信 server 可放宽 |
| 押注协议却担心被单厂商绑架 | 未核实治理结构 | 查治理文档与基金会归属 | 确认由 Linux 基金会 AAIF 中立托管 | 私有内部协议不适用此判断 |

## 思考：企业该如何评估「要不要押注 MCP」？

### 回答

从三个层面评估，而不是只看「技术好不好」。第一是治理层：MCP 已捐给 Linux 基金会下的 AAIF，由多家竞争厂商共同支持、治理模型保持社区驱动，这把「被单一供应商绑架」的风险降到与押注 Linux、Kubernetes 同级。第二是采纳层：ChatGPT、Cursor、Gemini、Microsoft Copilot、VS Code 都已采纳，10,000+ 公共 server 与 97M+ SDK 月下载说明生态已过临界点，不是小众实验。第三是安全层：开放生态意味着更大的攻击面，接入公共 server 必须做供应链审计、版本锁定、权限最小化和人在回路。结论是：MCP 在治理与采纳上已具备长期押注的条件，但接入策略上要像对待任何第三方依赖一样谨慎。押注协议本身低风险，盲目接入不可信 server 高风险，二者不能混为一谈。

### 面试精简表达

看治理（Linux 基金会 AAIF 中立托管、多厂商支持、治理不变）、看采纳（竞争对手都在用、万级 server、亿级 SDK 下载）、看安全（开放生态攻击面大，要审计与最小权限）。协议可押注，接入需谨慎。

## 思考：竞争对手 OpenAI 也采纳 MCP，说明了什么？

### 回答

说明 MCP 已经跨过了「私有格式」与「开放标准」的分界线。一个协议若只服务于发明者的商业利益，竞争对手没有动机采纳它；而 OpenAI 不仅采纳，还是核心贡献者，把 MCP 作为 ChatGPT 里 connectors 与 apps 的基础，并与 Anthropic 合作推进 MCP Apps。竞争对手的深度参与产生了两个效果：一是增强了协议的中立性可信度——多方博弈使任何单一厂商都难以把协议改造成对自己有利的私有分支；二是扩大了网络效应——为一个应用写的 MCP server，能同时被 ChatGPT、Claude、Gemini 等多个宿主复用，这正是第 1 节「M+N」价值的生态级兑现。从历史看，能让竞争对手共同采纳与治理的标准（如 HTTP、SQL、USB），往往才是能穿越周期的标准。

### 面试精简表达

竞争对手采纳且贡献，是「开放标准 vs 私有格式」的分水岭；它同时提升中立可信度、扩大网络效应，让同一个 server 被多个宿主复用，兑现 M+N 的生态价值。

## 机制推导：从「一家发布」到「多方治理」的演进逻辑

MCP 的一年演进，暗含一条开源标准成熟的典型路径，理解它能帮你判断其他新协议的成熟度。第一阶段是「单方发布 + 完整规范 + 官方 SDK」：Anthropic 2024 年 11 月发布协议、开源 SDK、给出参考实现，降低了采纳门槛。第二阶段是「竞争对手采纳」：OpenAI 2025 年 3 月、Google 2025 年 4 月相继采纳，协议从「一家的方案」变成「行业的候选标准」。第三阶段是「基础设施跟进」：AWS、Cloudflare、Azure、Google Cloud 提供部署支持，公共 server 突破万级，生态过临界点。第四阶段是「治理去中心化」：2025 年 12 月捐给 Linux 基金会 AAIF，所有权中立化，治理制度化。

这条路径的每一步都在解决采纳者的一个顾虑：SDK 解决「上手难」，竞争对手采纳解决「会不会小众」，基础设施跟进解决「能不能规模化部署」，捐给基金会解决「会不会被绑架」。当你评估任何新兴 Agent 协议时，可以用同一把尺子去量它走到了哪一步——只发了规范但无人采纳的，风险最高；已经完成治理去中心化的，才具备长期押注的条件。
