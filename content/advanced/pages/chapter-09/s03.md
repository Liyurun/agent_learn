## 真实问题

一个团队给内部知识库写了 MCP Server，把所有能力都做成了 Tool：「读取某篇文档」是 Tool、「列出所有文档」是 Tool、「一键生成周报」也是 Tool。上线后出现两个怪现象：一是模型经常「自作主张」去读一堆不相关的文档，把上下文塞满噪声，因为「读文档」被暴露成了模型可自主调用的动作；二是本该由用户主动触发的「生成周报」，模型有时在用户没要求时也擅自调用了。团队困惑：「不都是能力吗，为什么要分类？」这正是 MCP 把 Server 能力刻意分成三种原语的原因——**不同能力的控制权本就该归属不同角色**。

## 原理：三种原语与控制权光谱

MCP Server 可以向应用暴露三类原语，它们的核心差异不在「能做什么」，而在「谁说了算」[来源](https://modelcontextprotocol.io/specification/2025-11-25/server/tools)：

| 原语 | 是什么 | 控制方 | 典型例子 |
|---|---|---|---|
| Tools（工具） | 可执行的动作，可能有副作用 | 模型控制——由 LLM 判断是否调用 | 创建 issue、发送消息 |
| Resources（资源） | 可读取的数据，只读无副作用 | 应用控制——由宿主决定加载什么 | 文件内容、数据库记录 |
| Prompts（提示） | 预定义的提示词模板 / 工作流 | 用户控制——由用户主动选择触发 | 「一键生成周报」模板 |

把三者按「谁说了算」排在一条线上，就能看到 MCP 刻意设计的自主性梯度：
```text
用户控制 ◀──────────────────────────────────▶ 模型控制
   │                    │                        │
Prompts              Resources                Tools
用户主动选           应用决定加载什么           模型自主决定调不调
「生成周报」模板      「读这个 README」          「要不要创建 issue」
   │                    │                        │
自主性最低          自主性居中                 自主性最高
（最可控）                                    （最需护栏）
```
回到那个团队的 bug：把「读文档」做成 Tool，等于把「加载哪些数据进上下文」这个本该由应用把关的决策，交给了模型自主发挥，于是模型漫无目的地乱读；把「生成周报」做成 Tool，等于把「用户意图的显式表达」交给了模型，于是模型擅自触发。正确的归类是：**读文档 → Resource（应用控制加载），生成周报 → Prompt（用户主动触发），只有真正有副作用的动作（如「归档文档」）才做成 Tool**。

官方规范对 Tools 的定位写得很直白：Tools 被设计为「模型控制」（model-controlled），语言模型可基于上下文自动发现并调用；但出于信任与安全，规范强调应「始终有人在回路中，有能力拒绝工具调用」，应用应清晰展示暴露了哪些工具、在调用时给出可见指示、对敏感操作弹出确认 [来源](https://modelcontextprotocol.io/specification/2025-11-25/server/tools)。这套划分正是「自主性是成本，能不给模型的权力就不给」理念在协议层的落地——它不是技术限制，而是一种深思熟虑的安全哲学。

## 2025 年规范新增：sampling、elicitation、roots

除了三种「服务端原语」，2025 年的规范还明确了几个「客户端能力」，它们让协议从「Server 单向暴露能力」变成「双向协作」[来源](https://modelcontextprotocol.io/docs/learn/client-concepts)：

- **Sampling（采样）**：Server 反过来请求 Client 帮它做一次 LLM 补全。这样 Server 无需自己集成或付费接入模型——它借用 Client 已有的模型访问权，且由 Client 完全掌控用户许可与安全边界。例如一个「研究型」Server 可以在处理任务途中，请 Client 帮它总结一段中间结果。
- **Elicitation（信息征询）**：Server 在工具执行途中暂停，向用户请求结构化输入（如「确认预订吗？」「选择座位偏好」）。Server 提供一个描述期望结构的 JSON Schema，Host 渲染相应 UI 并把用户填的值返回。它在 2025-06-18 版本被提升为一等原语 [来源](https://modelcontextprotocol.io/docs/learn/client-concepts)。规范建议：绝不通过 elicitation 索取敏感密钥，提示要具体并说明数据用途。
- **Roots（根）**：Host 告诉 Server「哪些文件系统路径或 URI 在作用域内」，为 Server 的访问划定边界。

2025-11-25 版本还在 sampling 上补充了能力：sampling 请求里可以包含工具定义并指定工具选择行为、支持服务端多步推理循环与并行工具调用，同时把含义模糊的 `includeContext` 参数软性弃用，改为显式的能力声明 [来源](https://blog.modelcontextprotocol.io/posts/2025-11-25-first-mcp-anniversary/)。这些细节会随版本演进，以官方规范当前值为准。

## 最小可运行演示

下面用纯标准库写一个「原语分类器」，输入一个能力的属性（是否有副作用、是否由用户主动触发），输出它应该归为哪种原语。它把上面那套判断准则变成可执行的规则：
```python
def classify(name: str, has_side_effect: bool, user_triggered: bool, read_only_data: bool) -> str:
    if user_triggered:
        return "Prompt（用户控制：预定义工作流，由用户主动触发）"
    if has_side_effect:
        return "Tool（模型控制：有副作用的动作，最需护栏）"
    if read_only_data:
        return "Resource（应用控制：只读数据，由应用决定是否加载）"
    return "需澄清：无副作用、非用户触发、又不是纯数据，重新界定能力边界"

CASES = [
    ("发送 Slack 消息", True, False, False),
    ("读取项目 README", False, False, True),
    ("一键生成周报模板", False, True, False),
    ("归档一篇文档", True, False, False),
    ("列出全部工单", False, False, True),
]

def main() -> None:
    for name, side, user, read in CASES:
        print(f"{name} -> {classify(name, side, user, read)}")

if __name__ == "__main__":
    main()
```
保存为 `classify_primitives.py`，运行 `python classify_primitives.py`。预期输出：
```text
发送 Slack 消息 -> Tool（模型控制：有副作用的动作，最需护栏）
读取项目 README -> Resource（应用控制：只读数据，由应用决定是否加载）
一键生成周报模板 -> Prompt（用户控制：预定义工作流，由用户主动触发）
归档一篇文档 -> Tool（模型控制：有副作用的动作，最需护栏）
列出全部工单 -> Resource（应用控制：只读数据，由应用决定是否加载）
```
这段代码把「有副作用 → Tool，只读数据 → Resource，用户主动触发 → Prompt」的准则固化成规则。真实系统里，分类还要结合权限与风险评估，但这个骨架能帮你在设计 Server 时先想清楚每个能力的控制权归属。

## 真实系统对应

**官方公开机制**：规范明确 Tools 为「模型控制」、要求人在回路可拒绝调用、应展示工具并对敏感操作确认 [来源](https://modelcontextprotocol.io/specification/2025-11-25/server/tools)；客户端概念文档定义了 sampling、elicitation、roots 的语义 [来源](https://modelcontextprotocol.io/docs/learn/client-concepts)；周年博客说明了 2025-11-25 对 sampling 的增强 [来源](https://blog.modelcontextprotocol.io/posts/2025-11-25-first-mcp-anniversary/)。**通用工程模式**：把三种原语解释为「自主性光谱」并映射到「自主性是成本」的理念，是可迁移推导。**教学参考实现**：上面的 `classify` 分类器是本书构造的启发式，不代表任何 Server 框架的内部注册逻辑。

## 生产踩坑

| 症状 | 根因 | 如何观测与复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| 模型乱读一堆不相关文档 | 把「只读数据」做成 Tool 让模型自主调用 | 记录模型的工具调用序列，看是否高频读无关数据 | 只读数据改为 Resource，由应用按策略加载 | 确需模型按需检索时可保留检索型 Tool |
| 模型擅自触发本该用户发起的流程 | 把「用户工作流」做成 Tool | 观察无用户请求时是否有该工具调用 | 改为 Prompt，仅用户主动选择时触发 | 明确授权的自动化流程可用 Tool |
| 危险动作无人确认直接执行 | Tool 缺少人在回路的确认 | 注入一个删除类工具看是否直接执行 | 敏感 Tool 增加确认与审计，展示参数 | 幂等只读操作确认可从简 |
| Server 想调模型却自己接了一套 LLM | 未使用 sampling，重复集成与付费 | 检查 Server 是否内置模型密钥 | 用 sampling 让 Client 代为补全并控权限 | Client 不支持 sampling 时需降级 |
| 参数缺失时工具直接报错崩溃 | 未用 elicitation 向用户补齐输入 | 用缺参数请求复现崩溃 | 用 elicitation 请求结构化输入 | 不得用它索取敏感密钥 |

## 思考：三种原语分错类别会有什么后果？

### 回答

分错类别会同时损害安全性和可用性。把只读数据（该是 Resource）做成 Tool，模型会漫无目的地自主调用它，既浪费注意力污染上下文，又丧失了「应用按策略控制加载」的把关能力。把用户工作流（该是 Prompt）做成 Tool，模型可能在用户没要求时擅自触发，违背了「用户意图应显式表达」的原则。把有副作用的动作（该是 Tool）做成 Resource，则会绕过「模型控制 + 人在回路确认」的护栏。判断准则很简单：有副作用的动作 → Tool；只读数据 → Resource；用户主动触发的工作流 → Prompt。控制权归属错了，Server 就既不安全也不好用。

### 面试精简表达

Tools 归模型（有副作用、最需护栏），Resources 归应用（只读数据、按策略加载），Prompts 归用户（工作流、主动触发）；分错类别会让模型越权乱读或擅自触发。

## 机制推导：为什么「模型控制」的 Tools 反而最需要人在回路

直觉上，「交给模型自主决定」听起来像是把最大的信任给了模型，但规范恰恰在 Tools 这一层最强调「人在回路可拒绝」。原因在于责任与风险的错配：Tools 是唯一可能产生真实副作用的原语（创建、修改、删除、发送），而模型的判断是概率性的、可被工具描述里的提示注入误导的。把「是否调用」交给模型是为了让 Agent 能动态适应对话，这是价值所在；但「调用是否被允许执行」必须由模型之外的机制兜底。

因此规范建议应用做三件事：清晰展示暴露了哪些工具（让用户知情）、在工具被调用时给出可见指示（让用户可感知）、对敏感操作弹出确认（让用户可拦截）[来源](https://modelcontextprotocol.io/specification/2025-11-25/server/tools)。这三件事共同构成「人在回路」。它不与「模型控制」矛盾：模型控制的是「提议调什么」，人在回路控制的是「是否放行」。把这两件事混为一谈，是很多人误以为「Agent 就该全自动」的根源。

## 完整输入输出与运行说明

上面的分类器可以扩展成一个「Server 设计检查表」，在你真正写 Server 前，先把每个待暴露的能力过一遍。判断逻辑不变，但增加对「危险动作是否需确认」的提示：
```python
def classify(name, has_side_effect, user_triggered, read_only_data):
    if user_triggered:
        return "Prompt", "用户控制"
    if has_side_effect:
        note = "，且属危险动作，需人在回路确认" if name.startswith(("删除", "归档", "发送")) else ""
        return "Tool", "模型控制" + note
    if read_only_data:
        return "Resource", "应用控制"
    return "待澄清", "边界不清"

def main():
    for name, s, u, r in [
        ("删除数据库记录", True, False, False),
        ("读取配置文件", False, False, True),
    ]:
        kind, control = classify(name, s, u, r)
        print(f"{name}: {kind} / {control}")

if __name__ == "__main__":
    main()
```
保存为 `design_checklist.py`，运行 `python design_checklist.py`。预期输出：
```text
删除数据库记录: Tool / 模型控制，且属危险动作，需人在回路确认
读取配置文件: Resource / 应用控制
```
「读取配置文件」被正确识别为 Resource，避免了本节开头那个团队「把只读数据做成 Tool」的错误；「删除数据库记录」被标记为需人在回路确认的危险 Tool。这个检查表不替代真正的权限系统，但能在设计早期就把控制权归属想清楚。
