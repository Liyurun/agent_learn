## 真实问题

面试进入中高级岗的深水区。面试官问：「你的 Agent 要完成『帮我订一趟从北京到上海的高铁，选靠窗、下午出发、报销价位以内的』，它是怎么把这个模糊目标变成一步步动作的？这个能力叫什么？」候选人答「靠推理啊，让它想一想」。面试官追问：「那它是先想好完整计划再执行，还是走一步看一步？这两种有什么区别？」候选人答不上来。接着面试官又问：「你反复提到要给模型『喂对上下文』，这和写 prompt 有什么不一样？」候选人答「不就是把 prompt 写好吗」——把上下文工程窄化成了写提示词。**这两问，一个考对『规划』范式的理解（ReAct vs Plan-and-Execute），一个考对『上下文工程』这个新热点的认知边界，都是中高级岗的高频分水岭题。** 这一节把它们讲透。

## 原理：规划的两种范式，上下文工程的系统视角

### 规划：把模糊目标拆成有序子步骤

Planning（规划）是指 Agent 把一个复杂目标拆解成有序的子步骤，并决定按什么顺序执行的能力。它是把「一个大而模糊的目标」变成「一串可执行的小动作」的关键环节。Lilian Weng 在自主 Agent 综述里就把 Planning（含子目标分解与反思）列为 Agent 的核心组件之一 [来源](https://lilianweng.github.io/posts/2023-06-23-agent/)。规划有两种典型范式：
```text
ReAct（边做边规划）：            Plan-and-Execute（先规划后执行）：
 想→做→看→想→做→看→...           先想出完整计划：[A, B, C, D]
 每步都重新决策                   然后 A→B→C→D 逐个执行
 适应变化强，但调用多             调用少、结构清晰，但对变化僵硬
                                 （常配 Re-planning 重规划兜底）
```
- **ReAct（Reasoning and Acting，推理与行动，边做边规划）**：不预先制定完整计划，走一步看一步——每一步根据当前观察决定下一步。灵活、适应变化，但调用次数多、可能绕路。
- **Plan-and-Execute（先规划后执行）**：先让模型一次性产出完整计划（第 1 步做 A、第 2 步做 B……），再按计划逐步执行。调用次数少、结构清晰，但计划一旦定死，遇到中途变化不好调整（通常配一个「重规划 / re-planning」机制来补救）。

现实里两者常融合——先做一个粗规划（Plan），执行中用 ReAct 式的观察来触发「重规划」。这样既有整体方向，又能应对意外。

### 上下文工程：设计每一步喂给模型的信息组合

上下文工程（Context Engineering）指的是**系统性地设计「每一步喂给模型的上下文里到底该有什么」**——包括 system prompt、可用工具、检索到的知识、历史记忆、当前状态等，让模型在有限的上下文窗口里拿到「恰好够用且不冗余」的信息。Anthropic 在《Effective context engineering for AI agents》里给了一个精准的对照：Prompt Engineering（提示工程）是「编写和组织 LLM 指令以获得最佳结果的方法」，而 Context Engineering 是「在 LLM 推理过程中，策划和维护那组最优 token（信息）的策略集合，涵盖 prompt 之外可能进入上下文的所有信息」[来源](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)。
```text
一次 Agent 调用的上下文 =
   [System Prompt: 角色/规则/边界]
 + [工具定义: 有哪些工具可用]
 + [检索知识: RAG 召回的片段]
 + [记忆: 长期记忆召回 + 短期对话历史]
 + [当前状态: 已做过哪些步骤、观察到什么]
 + [用户当前输入]
上下文工程 = 决定以上每一块「放什么、放多少、怎么排、什么时候裁剪」
```
区别在于范围：Prompt Engineering 更偏「怎么把一句话/一个指令写好」，是上下文工程的一个子集；上下文工程是更宏观的「在一个多步、有记忆、有工具的 Agent 系统里，怎么动态地组装每一步的完整上下文」。对单轮问答，Prompt Engineering 够用；对多步 Agent，必须上升到上下文工程。

## 最小可运行演示

下面这段代码一次演示两件事：一个「规划范式选择器」（按任务特征推荐 ReAct 还是 Plan-and-Execute），和一个「上下文预算装配器」（在有限 token 预算内按优先级装配上下文，超预算时裁剪低优先级块）。不联网、不需要 API Key。
```python
"""第21.5节：规划范式选择 + 上下文预算装配（纯 Python，无需 API Key）。"""
from dataclasses import dataclass


def choose_planning(env_volatile: bool, steps_predictable: bool, cost_sensitive: bool) -> str:
    ## 环境多变 -> 需要边走边看 -> ReAct；步骤可预期且省调用 -> Plan-and-Execute
    if env_volatile and not steps_predictable:
        return "ReAct（边做边规划，适应变化，代价是调用多）"
    if steps_predictable and cost_sensitive:
        return "Plan-and-Execute（先规划后执行，省调用，配重规划兜底）"
    return "混合：先粗规划，执行中用观察触发重规划"


@dataclass
class Block:
    name: str
    priority: int      ## 数字越小越重要
    tokens: int


def assemble_context(blocks: list, budget: int) -> tuple:
    ## 上下文工程核心：有限预算内，按优先级保留，超预算裁掉最不重要的
    kept, used = [], 0
    for b in sorted(blocks, key=lambda x: x.priority):
        if used + b.tokens <= budget:
            kept.append(b.name)
            used += b.tokens
    dropped = [b.name for b in blocks if b.name not in kept]
    return kept, dropped, used


def run():
    print(choose_planning(True, False, False))
    print(choose_planning(False, True, True))
    print("---")
    blocks = [
        Block("System Prompt(规则/边界)", 1, 500),
        Block("当前状态(已做步骤)", 2, 400),
        Block("RAG 召回知识", 3, 1200),
        Block("长期记忆(用户偏好)", 4, 300),
        Block("完整历史对话", 5, 3000),   ## 最不重要且最长，超预算先裁它
    ]
    kept, dropped, used = assemble_context(blocks, budget=2500)
    print(f"预算2500 用了{used} 保留={kept}")
    print(f"裁剪={dropped}")


if __name__ == "__main__":
    run()
```
保存为 `s5_plan_context.py`，运行 `python s5_plan_context.py`。预期输出：
```text
ReAct（边做边规划，适应变化，代价是调用多）
Plan-and-Execute（先规划后执行，省调用，配重规划兜底）
---
预算2500 用了2400 保留=['System Prompt(规则/边界)', '当前状态(已做步骤)', 'RAG 召回知识', '长期记忆(用户偏好)']
裁剪=['完整历史对话']
```
注意上下文装配部分：预算 2500 token 装不下所有块时，装配器优先保住「规则/状态/知识/偏好」，把最长且优先级最低的「完整历史对话」裁掉——**这就是上下文工程的核心动作：不是塞得越满越好，而是在有限预算里按优先级取舍。** 这一步正是 Prompt Engineering 覆盖不到的系统级决策。

## 真实系统对应

**官方公开机制**：Anthropic 明确把 Context Engineering 定义为「策划和维护推理时那组最优 token 的策略集合」，并把它与 Prompt Engineering 作对比——后者只是「编写指令」，前者涵盖 prompt 之外进入上下文的所有信息；文章还强调因注意力预算有限、上下文越长越会「腐烂」，所以要做压缩（compaction）、结构化裁剪等 [来源](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)。Planning 作为 Agent 核心组件、含子目标分解与反思，见 Lilian Weng 综述 [来源](https://lilianweng.github.io/posts/2023-06-23-agent/)；ReAct 这种「边推理边行动」的范式源自 Yao 等人论文 [来源](https://arxiv.org/abs/2210.03629)。**通用工程模式**：ReAct/Plan-and-Execute 的取舍、「按优先级在预算内装配上下文」是可迁移到任意框架的工程共识。**教学参考实现**：上面的选择器与装配器是为讲清判据而构造，真实系统的 token 计数、优先级排序会更复杂。

一个必须澄清的边界：**上下文不是「塞得越满越好」，也不是「越省越好」**。太少会缺关键信息导致模型答不好；太多会注意力稀释、成本飙升、还容易被无关内容带偏（甚至夹带提示注入）。上下文工程追求的是「恰好够用且不冗余」的那个平衡点，而这个平衡点会随任务、随步骤动态变化——这正是它比一次性写好 prompt 更难、也更关键的地方。

## 生产踩坑

| 现场表现 | 根因 | 如何观测复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| 复杂任务步骤遗漏、目标漂移 | 规划能力弱、无子目标分解 | 用多步任务看是否漏步 | 显式规划 + 清晰目标约束 + 关键计划人工审核 | 单步简单任务无需规划 |
| Plan 定死后中途变化答错 | 无重规划机制 | 执行中注入变化看是否死磕原计划 | 加 re-planning：偏差就更新计划 | 步骤完全确定的封闭流程 |
| ReAct 调用次数爆炸、又慢又贵 | 全程边走边看、无粗规划 | 统计单任务平均步数 | 先粗规划定方向，减少无谓探索 | 环境高度不可预测时 |
| 把上下文工程当成写 prompt | 认知窄化 | 追问「多步系统里怎么动态组装」 | 明确它是系统级信息装配、含记忆检索状态 | 纯单轮问答场景 |
| 上下文塞满导致注意力稀释 | 「越多越好」误区 | 对比精简前后回答质量 | 按优先级裁剪、摘要压缩旧对话 | 上下文天然很短的任务 |
| 关键信息缺失导致模型乱答 | 该给的没给、裁过头 | 检查缺失块是否影响答案 | 保住高优先级块，宁裁历史不裁规则 | 信息本就极少的场景 |

## 思考：上下文工程和 Prompt Engineering 到底是什么关系？为什么对 Agent 来说前者更决定成败？

### 回答

它们是「包含关系」：Prompt Engineering 是上下文工程的一个子集。Prompt Engineering 关注「怎么把一条指令 / 一段 system prompt 写好」——措辞、结构、示例、角色设定，它的对象是「你手写的那段文字」。上下文工程关注的范围大得多——它管的是「每一步进入模型上下文的**全部信息**」，Anthropic 的定义里特别点出这包括「prompt 之外可能进入上下文的所有信息」[来源](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)：检索召回的知识、长期记忆、工具定义、当前任务状态、历史对话……这些大多不是你手写的，而是系统在运行时动态拼进去的。所以 Prompt Engineering 是「写好那句话」，上下文工程是「决定这一步到底该带哪些信息、各带多少、怎么排、什么时候裁」。

为什么对 Agent 来说后者更决定成败？因为 Agent 是**多步、有记忆、有工具**的系统，它每一步的上下文都在变，而且大部分内容不是人手写的、是动态组装的。一个单轮问答，你把 prompt 打磨到极致就基本决定了效果；但一个跑十几步的 Agent，就算每一步的 system prompt 都完美，只要某一步该召回的知识没召回、或者历史塞太多把关键状态淹没了，模型照样答错。换句话说，**Agent 的失败往往不是「话没写好」，而是「该看到的没看到、不该看的看了一堆」**——这恰恰是上下文工程要解决的问题，Prompt Engineering 够不着。Anthropic 也正是基于「注意力预算有限、上下文会腐烂」这个事实，才强调要主动做压缩和裁剪，而不是把窗口填满。所以对 Agent 工程师而言，「给模型喂对上下文」这门手艺，比单纯打磨措辞更接近成败的核心。

### 面试精简表达

包含关系：Prompt Engineering 是写好「你手写的那段指令」，上下文工程是管「每一步进入上下文的全部信息」（含检索、记忆、状态等动态内容）。Agent 是多步动态系统，失败常因「该看到的没看到、不该看的看一堆」，这正是上下文工程管的，措辞打磨够不着。

### 反例

有人说「那我把所有可能有用的信息都塞进上下文，不就不会漏了吗」——这恰恰是上下文工程最反对的做法。塞满会导致注意力稀释（context rot）、成本飙升、还可能夹带提示注入。上下文工程的精髓不是「多」，而是「准」——在有限预算里放「恰好够用且不冗余」的信息，这需要主动裁剪，而不是无脑堆料。
