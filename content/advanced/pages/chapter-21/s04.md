## 真实问题

面试进入到近两年的热点区。面试官问：「你简历里写了用 MCP（Model Context Protocol，模型上下文协议），说说它是什么，为什么有人叫它『AI 应用的 USB-C』？」候选人答「MCP 是 Anthropic 出的一个工具，用来连接各种数据源」。面试官不满意：「你说它是『工具』还是『协议』？这俩差别很大。」候选人含糊过去。接着面试官又问：「你这个客服系统，为什么用了三个 Agent 而不是一个？」候选人答「多 Agent 更强大、更专业」——又踩了「多 Agent 更高级」的坑。**这两问，一个考对『标准化协议』的理解深度，一个考『架构克制』的设计判断力，都是最能暴露『是不是真做过』的题。** 这一节把它们讲透。

## 原理：MCP 的复杂度本质与多 Agent 的取舍

### MCP 为什么是「USB-C」：M×N → M+N

MCP 是一个**开放标准协议**，用于统一 AI 应用与外部工具、数据源的连接方式。「USB-C」这个比喻的精髓在于**标准化带来的复杂度下降**。在 MCP 之前，每个 Agent 接每个工具都要写一套定制对接代码，是 M×N 的复杂度；有了 MCP 这个统一接口，工具方只要实现一次 MCP Server，任何支持 MCP 的应用都能即插即用，复杂度降到 M+N：
```text
没有 MCP（M 个应用 × N 个工具，每对都要定制对接）：
   App1 ─┬─ ToolA        对接数量 = M × N
   App2 ─┼─ ToolB        新增一个工具，M 个应用都要各接一遍
   App3 ─┴─ ToolC
有了 MCP（统一协议做中间层）：
   App1 ─┐            ┌─ ToolA(MCP Server)
   App2 ─┼─ MCP 协议 ─┼─ ToolB(MCP Server)   对接数量 = M + N
   App3 ─┘            └─ ToolC(MCP Server)   工具实现一次，所有应用即插即用
```
MCP 官方规范采用 **Host / Client / Server** 三层架构：Host 是发起连接的 LLM 应用（协调并管理一个或多个 Client），Client 是 Host 内维护与单个 Server 连接的组件，Server 是对外提供上下文与能力的程序；底层基于 JSON-RPC 消息格式，是一个有状态的会话协议 [来源](https://modelcontextprotocol.io/specification/2025-06-18/architecture)。Server 对外暴露三类东西：Tools（可调用的操作）、Resources（可读取的数据）、Prompts（可复用的提示模板）。要强调它和 Function Calling（函数调用）不是竞争关系而是**不同层次**：Function Calling 是「模型怎么表达要调工具」，MCP 是「工具怎么被标准化地暴露和发现」，MCP 底层往往就靠模型的 Function Calling 来触发。

### 单 Agent 还是多 Agent：默认单，能单就别多

这道题考的是「设计判断力」，最忌讳「多 Agent 更高级」的直觉。默认优先单 Agent——**能用单 Agent 解决就别上多 Agent**。多 Agent 只在以下情况才有必要：
```text
拿到一个任务
   │
   ├─ 单 Agent + 好的工具能搞定吗？ ──是──▶ 用单 Agent（默认选择）
   │
   └─ 否，具体是什么原因？
          ├─ 上下文/工具太多，选择困难 ──▶ 先想能不能精简工具，不行再拆
          ├─ 有明确的多领域边界        ──▶ 按领域拆专门 Agent
          └─ 需要权限隔离/职责分离      ──▶ 拆 Agent 做隔离
                     │
                     └─▶ 但要接受代价：路由错误、上下文传递丢失、延迟成本上升、调试变难
```
判断标准始终是「**多 Agent 带来的收益是否大于这些额外复杂度**」。这与 Anthropic《Building Effective Agents》的主张一致——能用简单可组合的模式就不要上复杂自治架构，多 Agent 的复杂度必须由收益证明 [来源](https://www.anthropic.com/engineering/building-effective-agents)；也呼应 OpenAI 建议的「先从单 Agent 起步，真正需要时再引入多 Agent 编排」[来源](https://cdn.openai.com/business-guides-and-resources/a-practical-guide-to-building-agents.pdf)。

## 最小可运行演示

下面这段代码一次演示两件事：一个「对接复杂度计算器」（直观算出 M×N vs M+N 的差距），和一个「单/多 Agent 决策器」（按信号判断该不该拆）。不联网、不需要 API Key。
```python
"""第21.4节：MCP 复杂度计算 + 单/多 Agent 决策（纯 Python，无需 API Key）。"""
from dataclasses import dataclass


def integration_cost(m_apps: int, n_tools: int) -> tuple:
    ## 没有 MCP：每个应用对每个工具都要定制对接 -> M×N
    ## 有 MCP：每个应用接一次协议、每个工具实现一次 Server -> M+N
    return m_apps * n_tools, m_apps + n_tools


@dataclass
class Task:
    name: str
    single_agent_can_do: bool
    clear_domain_split: bool
    needs_permission_isolation: bool
    too_many_tools: bool


def decide_architecture(t: Task) -> str:
    if t.single_agent_can_do and not t.needs_permission_isolation:
        return "单 Agent（默认，收益不足以支撑多 Agent 复杂度）"
    reasons = []
    if t.clear_domain_split:
        reasons.append("多领域边界")
    if t.needs_permission_isolation:
        reasons.append("权限隔离")
    if t.too_many_tools:
        reasons.append("工具过载(先试精简)")
    return f"多 Agent（触发信号：{', '.join(reasons) or '需复核'}），代价：路由/上下文/延迟/调试"


def run():
    for m, n in [(3, 4), (10, 20)]:
        no_mcp, with_mcp = integration_cost(m, n)
        print(f"{m}应用×{n}工具: 无MCP={no_mcp} 有MCP={with_mcp} 省下={no_mcp - with_mcp}")
    print("---")
    tasks = [
        Task("简单FAQ问答", True, False, False, False),
        Task("客服(订单/物流/售后+退款权限隔离)", False, True, True, True),
    ]
    for t in tasks:
        print(f"[{decide_architecture(t)}] <- {t.name}")


if __name__ == "__main__":
    run()
```
保存为 `s4_mcp_multiagent.py`，运行 `python s4_mcp_multiagent.py`。预期输出：
```text
3应用×4工具: 无MCP=12 有MCP=7 省下=5
10应用×20工具: 无MCP=200 有MCP=30 省下=170
---
[单 Agent（默认，收益不足以支撑多 Agent 复杂度）] <- 简单FAQ问答
[多 Agent（触发信号：多领域边界, 权限隔离, 工具过载(先试精简)），代价：路由/上下文/延迟/调试] <- 客服(订单/物流/售后+退款权限隔离)
```
注意 `10应用×20工具` 那行：无 MCP 要 200 次定制对接、有 MCP 只要 30 次——**这就是「USB-C」比喻的数学本质，随规模增大差距越拉越开（网络效应）。** 决策器则示范：简单 FAQ 走单 Agent，只有当「多领域 + 权限隔离 + 工具过载」多个信号叠加时才拆多 Agent。

## 真实系统对应

**官方公开机制**：MCP 规范明确 Host/Client/Server 三层架构与基于 JSON-RPC 的有状态会话协议，Host 协调多个 Client、每个 Client 与一个 Server 通信并维护安全边界 [来源](https://modelcontextprotocol.io/specification/2025-06-18/architecture)。Claude Code（Anthropic 的命令行编码 Agent）的 Subagents（子代理）文档提供了一个真实的多 Agent 边界样本——「每个 subagent 在自己独立的上下文窗口里运行，有自定义 system prompt、特定的工具访问权限和独立的权限」，当遇到匹配其描述的任务时才委派给它 [来源](https://docs.anthropic.com/en/docs/claude-code/sub-agents)。这恰好印证了「多 Agent 的价值点之一是上下文隔离与权限隔离」，也印证了「按明确的角色/任务边界来拆」这一原则。**通用工程模式**：M×N→M+N 的复杂度分析、「默认单 Agent、按信号才拆」的决策路径，可迁移到任何集成与架构设计。**教学参考实现**：上面的成本计算与决策器是为讲清判据而构造。

一个必须澄清的边界：引入第三方 MCP Server 相当于**引入外部代码与权限**，要注意来源可信、权限最小化、对 Server 返回的内容做校验（存在提示注入风险）。MCP 降低了「对接成本」，但没有降低「信任成本」——反而因为「即插即用」太方便，更容易让人忽视安全审查。面试里能主动补一句这个边界，会显得你不只懂它的好处，也懂它的风险。

## 生产踩坑

| 现场表现 | 根因 | 如何观测复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| 把 MCP 说成某公司的产品 | 混淆协议与产品 | 追问「它是协议还是产品」 | 明确 MCP 是开放标准协议、可多方实现 | 口语泛指生态时可不较真 |
| 分不清 MCP 与 Function Calling | 以为二者竞争 | 追问「它俩什么关系」 | 明确不同层：FC 是模型层、MCP 是连接层 | 只讲高层价值不涉及分层 |
| 接入第三方 Server 后被注入攻击 | 未审查来源、未校验返回 | 用恶意 Server 返回注入指令复现 | 来源可信 + 权限最小化 + 返回内容校验 | 全内部自建、可信域内 |
| 「多 Agent 更高级」硬拆 | 迷信多 Agent | 统计拆分后是否真提升 | 默认单 Agent，收益证明才拆 | 确有多领域/权限隔离刚需 |
| 两个 Agent 总被路由混淆 | 职责边界重叠 | 统计路由准确率、看混淆矩阵 | 边界重叠就合并，别硬拆 | 意图空间大且天然可分 |
| 跨 Agent 上下文传递丢关键信息 | handoff 未打包必要上下文 | 复盘转交后信息是否完整 | handoff 时显式打包上下文与身份 | 单 Agent 无跨 Agent 传递 |

## 思考：MCP 和 Function Calling 到底是什么关系？为什么说它们不冲突？

### 回答

它们处在**不同的抽象层次**，解决的是不同的问题，所以不冲突，而是互补协作。Function Calling 是**模型层**的能力——它回答「模型如何表达『我想调用某个工具、参数是什么』」，产出的是一个结构化的调用请求。MCP 是**应用层 / 连接层**的协议——它回答「一个工具如何被标准化地描述、暴露、发现和连接」，让任何支持 MCP 的宿主都能即插即用地接入任何 MCP Server。

把它们串起来看一次真实调用就清楚了：宿主应用通过 MCP Client 连接到一个 MCP Server，Server 按协议声明了它有哪些 Tools（这一步是 MCP 在做「标准化暴露」）；宿主把这些 Tools 的定义转换成模型能理解的工具 schema，发给模型；模型用 **Function Calling** 的能力返回「我要调用其中某个工具、参数是 X」（这一步是 Function Calling 在做「模型层表达」）；宿主拿到请求后，通过 MCP Client 把调用转发给对应的 Server 执行。**可以说 MCP 底层往往就靠模型的 Function Calling 来触发——Function Calling 是『怎么调』的机制，MCP 是『调什么、从哪发现』的标准。** 所以当有人问「有了 MCP 是不是就不用 Function Calling 了」，答案是否定的：没有 Function Calling，模型根本没法表达它要调哪个工具；没有 MCP，工具的接入就退回到 M×N 的定制泥潭。二者一个管模型侧的表达、一个管生态侧的互操作，是配合而非替代。

### 面试精简表达

不同层次、互补协作。Function Calling 是模型层「怎么表达要调工具」的能力，MCP 是连接层「工具怎么被标准化暴露和发现」的协议；MCP 底层往往靠 Function Calling 触发。一个管表达、一个管互操作，配合而非替代。

### 反例

有人说「MCP 就是 Function Calling 的升级版」——错。它们不在同一维度上，谈不上谁升级谁。这就像说「USB-C 接口是电流的升级版」一样类别错误：电流（Function Calling）是物理层的东西，USB-C（MCP）是接口标准，一个是「怎么传」、一个是「用什么口传」，各司其职。

## 思考：怎么判断一个多 Agent 系统「拆得对不对」？

### 回答

看两个可观测的信号：**每个 Agent 的职责是否清晰不重叠，以及 Agent 之间的路由准确率高不高。** 这两个信号背后，其实是「拆分边界选得好不好」这一件事的两面。

先说职责不重叠。一个拆得好的多 Agent 系统，每个 Agent 都应该有一个清晰、互斥的领域——订单 Agent 只管订单、物流 Agent 只管物流，它们的职责边界不应该模糊到「一个问题既像订单又像物流」。判断方法很直接：拿真实流量做混淆分析，如果发现某两个 Agent 频繁被「抢」同一类问题、或者一类问题在两个 Agent 之间反复横跳，那几乎可以断定**这两个 Agent 的拆分边界本身有问题**——它们承担的职责有重叠，正确的做法往往不是继续调路由，而是把这两个 Agent 合并成一个。这呼应了导读里反复强调的克制原则：拆分不是越细越好，边界重叠的拆分是负资产。

再说路由准确率。多 Agent 相比单 Agent，多出来的最大新增失败模式就是「路由到错误的 Agent」。所以一个健康的多 Agent 系统，必须能观测「有多少比例的请求被路由对了、错的都错在哪」。如果路由准确率长期上不去，要么是边界重叠（回到上一点），要么是路由器本身信息不足。反过来，如果职责清晰、路由准确率高、且每个 Agent 单独看都能把自己领域内的事做好，那这个拆分大概率是对的。这也正是 Claude Code 子代理文档强调「给子代理清晰且相对专门的角色、明确的工具访问权限和完成标准」的原因 [来源](https://docs.anthropic.com/en/docs/claude-code/sub-agents)——**边界清晰是多 Agent 能协作的前提，边界模糊则一切都会在路由层塌方。**

### 面试精简表达

看两点：职责是否清晰不重叠、路由准确率高不高。若两个 Agent 总被路由混淆，说明拆分边界重叠，该合并而非硬调路由；职责清晰 + 路由准 + 各自领域内做得好，才说明拆对了。拆分不是越细越好。

## 优化前后对比：从「M 家各建私有集成」到「统一协议生态」

MCP 的价值，在一个「工具方视角」的对比里最能看清。设想一家提供「企业知识库检索」能力的服务商，在没有 MCP 的世界里，它要想让自己的能力被各种 AI 应用用上，就得为每一个宿主单独做集成——给 A 编辑器做一个插件、给 B 聊天应用做一套适配、给 C 自研 Agent 平台再写一遍对接。每多一个宿主，就多一份维护负担；宿主升级了接口，所有集成还得跟着改。这就是 M×N 里那个「N 侧」的真实痛苦。

有了 MCP 之后，这家服务商只需要做一件事：**把能力实现成一个符合 MCP 规范的 Server**。此后任何支持 MCP 的宿主——无论是编辑器、聊天应用还是自研平台——都能通过标准的 MCP Client 即插即用地接入，服务商不用再为每个宿主单独适配。反过来，宿主方也一样受益：接一次 MCP Client，就能接入整个 MCP Server 生态，而不用为每个工具各写一遍集成。这就是「网络效应」的来源——**协议的价值随着接入方的增多而指数级放大**，越多工具实现 MCP、宿主接入 MCP 的动力就越强，越多宿主支持 MCP、工具方实现 MCP 的动力也越强。这也是为什么面试里能把 MCP 的价值从「接工具方便」讲到「网络效应与生态互操作」，会比只会背「USB-C 比喻」高出一个层次：**你讲的不是一个接口好不好用，而是一个标准如何改变整个行业的集成经济学。**
