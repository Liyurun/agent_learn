## 真实问题

面试进行到第三问，面试官换了个方向：「你的客服 Agent 上线后，用户抱怨『每次都要重新自我介绍，它根本记不住我是 VIP』。你会怎么设计记忆？」候选人答「把历史对话都存下来，每次拼进 prompt 就行」。面试官追问：「那用户聊了三个月、几千条消息，你也全塞进去？」候选人卡住了。**这暴露了记忆题最常见的误区——把「记忆」等同于「把所有历史塞进上下文」，没意识到上下文窗口是有限且昂贵的资源。** 紧接着面试官又问 Function Calling（函数调用）：「模型决定调用退款接口，这个退款是模型自己执行的，还是你的代码执行的？」这两问，一个考记忆的分层，一个考工具调用的边界，都是极高频的「一问就露馅」题。这一节把它们讲透。

## 原理：记忆为什么要分层，Function Calling 里谁执行函数

### 记忆的三层与核心约束

Agent 的记忆通常分三类，最好的记忆方式是与「人类记忆」做类比，同时点出**记忆的本质约束是上下文窗口有限**：

1. **短期记忆**：当前对话的上下文（context window），靠把历史消息拼进 prompt 实现，受限于模型上下文长度。类比人类「刚才聊了啥」。
2. **长期记忆**：跨会话持久化的信息（用户偏好、历史事实），常用向量数据库存储，需要时通过语义检索召回。类比人类「我记得这个用户是 VIP」。
3. **工作记忆 / 临时状态**：任务执行过程中的中间结果，如已调用过哪些工具、当前计划到哪一步。类比人类「我正在做这道题、算到第三步」。
```text
                ┌──────── 短期记忆（上下文窗口内的对话历史）
用户请求 ──▶ 组装 Prompt ◀── 工作记忆（本次任务的中间状态：调过哪些工具、计划到哪步）
                └──────── 长期记忆（向量库检索召回：用户偏好、历史事实）
                                    ▲
                          写入：重要信息 embedding 后存库
```
为什么要分层？因为**上下文窗口是有限且昂贵的资源**。不可能把所有历史都塞进去——既超长度，也烧钱，还会因信息太多而「注意力稀释」（Anthropic 在《Effective context engineering for AI agents》里把这种现象称为「上下文腐烂 / context rot」——上下文越长，模型越难保持专注、越难准确回忆细节 [来源](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)）。所以要区分「哪些必须在当前上下文里（短期/工作）、哪些可以存在外部按需召回（长期）」。长期记忆的工程难点全在「写入什么、怎么检索准」：写入要判断「什么信息值得记」，检索要解决「召回相关而不召回噪音」——靠 chunk 策略、元数据过滤、rerank（重排序）二次排序等手段。

### Function Calling 的端到端流程与命门

Function Calling 是让 LLM 以结构化方式请求调用外部函数的机制。**命门只有一句话：模型本身并不执行函数，它只输出「想调用哪个函数、参数是什么」的结构化请求，真正的执行由外部代码完成。** OpenAI 的 Function calling 文档把这个定位说得很直白——你把函数定义（名称、描述、参数的 JSON schema）连同问题发给模型，模型「智能地返回需要被调用的函数及其参数」，而非自己执行 [来源](https://developers.openai.com/api/docs/guides/function-calling)。端到端流程分五步：
```text
应用            模型              工具/外部系统
 │ tools schema+问题 │                  │
 │──────────────────▶│                  │
 │  {name,args} 请求  │                  │   ← 模型只「说要调什么」，不执行
 │◀──────────────────│                  │
 │ 真正执行 func(args) │                  │
 │───────────────────┼─────────────────▶│
 │       result       │                  │
 │◀───────────────────┼──────────────────│
 │  把 result 喂回     │                  │
 │──────────────────▶│                  │
 │  最终回答/下一次调用 │                  │
 │◀──────────────────│                  │
```
1. 开发者把可用工具的 schema（名称、描述、参数）连同用户问题发给模型；
2. 模型判断需要调用某工具，返回结构化调用请求（函数名 + 参数）；
3. **应用代码解析请求并真正执行**该函数；
4. 把执行结果作为一条新消息喂回给模型；
5. 模型根据结果生成最终回答（或决定再调下一个工具）。

## 最小可运行演示

下面这段代码一次演示两件事：一个「分层记忆」路由器（判断一条信息该放短期/长期/工作记忆、以及长期记忆如何按相关性召回），和一个「Function Calling 两段式」mock（模型只返回请求、应用才执行，并做参数校验）。不联网、不需要 API Key。
```python
"""第21.3节：分层记忆路由 + Function Calling 两段式（纯 Python，无需 API Key）。"""
from dataclasses import dataclass, field


## ---------- 分层记忆 ----------
def classify_memory(info: str) -> str:
    if any(k in info for k in ["VIP", "偏好", "会员等级"]):
        return "long"     ## 稳定可复用 -> 长期记忆
    if any(k in info for k in ["已调用", "当前步骤", "中间结果"]):
        return "work"     ## 任务中间态 -> 工作记忆
    return "short"        ## 本轮对话 -> 短期记忆


LONG_TERM = {"用户U-8821是VIP会员": ["VIP", "会员"], "偏好顺丰快递": ["快递", "偏好"]}


def recall(query: str, top_k: int = 1) -> list:
    ## 极简语义召回 mock：按关键词命中数排序，模拟向量相似度
    scored = [(sum(1 for kw in kws if kw in query), doc) for doc, kws in LONG_TERM.items()]
    scored = [(s, d) for s, d in scored if s > 0]
    scored.sort(reverse=True)
    return [d for _, d in scored[:top_k]]


## ---------- Function Calling 两段式 ----------
@dataclass
class ToolCall:
    name: str
    args: dict


def model_propose(question: str) -> ToolCall:
    ## 模型「只提出请求」，不执行
    if "退款" in question:
        return ToolCall("refund", {"order_id": "O-77", "amount": 328.0})
    return ToolCall("noop", {})


def app_execute(call: ToolCall) -> str:
    ## 应用「真正执行」，先做参数校验（模型可能给非法参数）
    if call.name == "refund":
        amount = call.args.get("amount")
        if not isinstance(amount, (int, float)) or amount <= 0:
            return "拒绝执行：非法金额"
        return f"已受理退款请求 order={call.args['order_id']} amount={amount}（待人工审批）"
    return "无需调用工具"


def run():
    print("--- 分层记忆 ---")
    for info in ["用户是VIP会员", "已调用查询订单工具", "你好我想问下"]:
        print(f"{classify_memory(info):5} <- {info}")
    print("召回:", recall("这个VIP会员用什么快递"))
    print("--- Function Calling ---")
    call = model_propose("我要退款")
    print(f"模型提出请求: {call.name}{call.args}")
    print(f"应用执行结果: {app_execute(call)}")


if __name__ == "__main__":
    run()
```
保存为 `s3_memory_fc.py`，运行 `python s3_memory_fc.py`。预期输出：
```text
--- 分层记忆 ---
long  <- 用户是VIP会员
work  <- 已调用查询订单工具
short <- 你好我想问下
召回: ['用户U-8821是VIP会员']
--- Function Calling ---
模型提出请求: refund{'order_id': 'O-77', 'amount': 328.0}
应用执行结果: 已受理退款请求 order=O-77 amount=328.0（待人工审批）
```
注意 Function Calling 部分：`model_propose` 只返回一个 `ToolCall` 数据对象（模型「说要调什么」），真正跑 `refund` 逻辑、做金额校验、加「待人工审批」的是 `app_execute`（应用代码）。**这两个函数的分工，就是这道题的命门可视化——模型永远只到「提出请求」为止。**

## 真实系统对应

**官方公开机制**：OpenAI Function calling 文档明确函数定义由 `name`、`description`、`parameters`（JSON schema）、`strict` 等字段组成，模型返回的是「需要调用的函数及参数」，执行在应用侧 [来源](https://developers.openai.com/api/docs/guides/function-calling)；`strict` 模式用于强制模型输出严格符合 schema 的参数，这正对应「参数校验」的工程需求。Anthropic 在《Effective context engineering for AI agents》里把「上下文腐烂」和「注意力预算有限」作为记忆分层与压缩的根本动因，并讨论了 compaction（压缩）、sub-agents（子代理）等管理长程上下文的策略 [来源](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)。**通用工程模式**：短期/长期/工作三层记忆、长期记忆的「写入 + 语义检索 + rerank」、Function Calling 的「模型提出 + 应用执行 + 结果喂回」两段式，都是可迁移到任意框架的工程共识。**教学参考实现**：上面的关键词召回和 mock 工具是为可复核而构造，真实系统请用向量数据库与真实模型的结构化输出。

一个必须澄清的边界：**长期记忆和 RAG（Retrieval-Augmented Generation，检索增强生成）技术手段高度重合（都靠向量检索），但目的不同**——RAG 是检索「外部知识」来回答问题，长期记忆是检索「关于用户/历史交互的信息」来保持连续性和个性化。面试里能主动区分这两者的目的差异，是一个加分点；混为一谈则说明只记住了「都用向量库」这个表层。

## 生产踩坑

| 现场表现 | 根因 | 如何观测复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| 上下文越拼越长直到超限报错 | 把全部历史塞进 prompt | 用长会话复现 token 超限 | 摘要压缩 + 滑动窗口 + 只留关键结论 | 会话极短、天然不会超限 |
| 长期记忆召回一堆无关内容 | chunk 粗、无元数据过滤 | 用含歧义词的查询看召回 | 优化 chunk、加元数据过滤、rerank 二次排序 | 知识极少、直接全量注入更简单 |
| 记忆库越用越脏 | 什么都往长期记忆写 | 统计长期库里一次性中间结果占比 | 只写稳定可复用信息，临时结果不入库 | 需完整审计留痕的合规场景 |
| 误以为模型自己执行了函数 | 混淆「请求」与「执行」 | 追问「谁真正跑了这个函数」 | 明确模型只提出请求、应用才执行 | 讲高层概念不涉及实现时 |
| 模型给的参数非法导致崩溃 | 未做 schema 校验就执行 | 构造缺字段/类型错的参数 | 用 JSON schema/strict 校验，非法则拒绝或让模型修正 | 参数空间极小且已枚举校验 |
| 工具多时模型频繁选错 | 同时暴露太多工具、description 含糊 | 统计误调用率 | 减少同时暴露数量、合并相近工具、写清 description | 工具极少且职责互斥 |

## 思考：为什么说「模型不执行函数」是 Function Calling 这道题的命门？

### 回答

因为这一点决定了你对「安全边界在哪」的全部理解，答错它，后面所有工程设计都会跟着错。很多人下意识以为「模型调用了退款接口 = 模型执行了退款」，这个误解一旦成立，就会得出「模型很危险，它能直接动钱」的错误结论，进而在设计上要么过度恐慌、要么防错了地方。真相是：**模型的输出永远只是文本 / 结构化请求，它没有任何执行能力。** 它说「我要调 refund(order_id='O-77', amount=328)」，就像你写下一张便条——真正跑去执行退款、扣减库存、发送邮件的，是你的应用代码。OpenAI 文档也把这一点讲得很清楚：模型「返回需要调用的函数及参数」，执行由你的程序完成 [来源](https://developers.openai.com/api/docs/guides/function-calling)。

理解了这一点，工程上的安全边界就一目了然：既然「执行」这道关卡完全在应用侧，那么**所有的校验、鉴权、审批、幂等、护栏，都应该、也只能加在应用侧的执行环节**，而不是指望模型「自觉」。具体来说有两件必做的防护：其一是**参数校验**——模型可能给出不合法参数（金额为负、订单号不存在、缺字段），应用必须用 JSON schema 或 `strict` 模式校验后再执行；其二是**执行安全**——高危动作（退款、删除、发消息）要加审批、要幂等、要 try/except 兜住失败。这也正是为什么导读那场「全额退款」事故的正确修复不是「让模型别乱承诺」，而是「退款执行环节强制走人工审批」——因为执行权本来就在应用手里，护栏就该加在这里。把「谁执行」这件事想反了，护栏就会加错位置，防了个寂寞。

### 面试精简表达

模型只输出「想调什么」的结构化请求，执行在应用代码。这决定了所有校验、鉴权、审批、幂等都必须加在应用侧执行环节，而不是指望模型自觉。答错这点，安全护栏就会加错位置。

### 反例

有人说「那我在 prompt 里写清楚『退款前必须确认金额合法』，模型不就自己校验了吗」——不可靠。prompt 约束只是「建议」，模型可能忽略、可能被绕过，而且就算模型「打算」校验，它也没有能力去查订单是否真实存在（那需要执行一次数据库查询，还是得应用来做）。真正的校验只能是应用侧执行前的一道硬关卡。

## 机制推导：长期记忆的「写入判断」为什么比「检索」更难

大多数人讨论长期记忆时，注意力都在「检索准不准」（chunk、rerank、过滤），但实践里更难、也更被低估的是**写入判断**——决定「一条信息到底值不值得记进长期库」。检索的难点是技术性的，有成熟的量化指标（召回率、准确率）和成熟的手段可优化；而写入判断的难点是**语义性和时效性的**，很难一刀切。

举个具体的两难：用户说「我下周要搬家到杭州」。这条信息该不该写进长期记忆？写，那么两周后用户搬完家了，这条「要搬家到杭州」就成了过时的脏数据，可能误导后续对话（比如还在推荐杭州的搬家服务）；不写，那用户下次问「我上次说要搬去哪来着」，Agent 又答不上来，个性化就断了。这类「暂时有用、之后会过期」的信息，恰恰是写入判断最棘手的部分。工程上的应对通常是给长期记忆加**时效标签和衰减机制**——重要且稳定的事实（VIP 身份、长期偏好）长期保留，带时效的信息（临时计划、一次性诉求）设过期时间或定期复核。这也是为什么面试里能主动说出「什么该写、什么不该写、怎么防止记忆库变脏」的人，比只会说「存向量库」的人显得成熟得多：**他考虑的不是「怎么记住」，而是「怎么记得干净、记得不误导未来」。**
