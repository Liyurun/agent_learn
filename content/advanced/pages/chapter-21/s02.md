## 真实问题

接着导读那场面试。面试官抛出第一问「什么是 AI Agent，和普通 LLM 调用有什么区别」，候选人答「Agent 更智能、能调工具」。面试官立刻用一段代码反将一军：「我写死一条链路——先让模型总结文档、再调翻译接口、最后发邮件，全程调了三个工具，这算 Agent 吗？」候选人答「算」，当场失分。**问题不在他不知道 Agent，而在他把「有没有工具」当成了判据，没抓住真正的分水岭——控制权归属。** 那段代码调了三个工具，但调用顺序是代码写死的，模型无权决定「下一步做什么」，所以它是 Workflow（工作流）而非 Agent。这一节要把 Agent 与普通 LLM 调用、Agent 与 Workflow、ReAct（Reasoning and Acting，推理与行动）与 Chain-of-Thought（思维链，缩写 CoT）三组关系讲透，核心只有一个词：**谁决定下一步**。

## 原理：从纯 LLM 调用到自主 Agent 的控制权光谱

回答「Agent 和普通 LLM 调用的区别」，最能拉开差距的地方，是你能不能把「区别」讲成一条**光谱**，而不是非黑即白的二分。Anthropic 在《Building Effective Agents》里就明确区分了 Workflow 和 Agent：Workflow 是「通过预定义代码路径编排 LLM 和工具」，Agent 是「LLM 动态地决定自己的流程和工具用法」[来源](https://www.anthropic.com/engineering/building-effective-agents)。把从「纯 LLM 调用」到「完全自主 Agent」画成一条控制权逐渐让渡给模型的光谱：
```text
控制权在人 ←──────────────────────────────────────→ 控制权在模型
 纯 LLM 调用  →  固定链路(Chain)  →  带分支路由  →  Workflow 编排  →  Agent
 (问答一次)     (Prompt 串起来)    (if/else)      (代码编排工具)    (模型自主决策+循环)
```
沿着这条光谱，回答时分三层递进：

1. **第一层·现象**：普通 LLM 调用是单轮的「输入 → 输出」，Agent 是多轮的「感知 → 决策 → 行动 → 观察」循环。
2. **第二层·本质**：区别不在「有没有工具」，而在「谁决定下一步」。哪怕一个 Workflow 调了很多工具，只要调用顺序是代码写死的，它就不是 Agent；反过来，哪怕只有一个工具，只要是模型自己判断「要不要调、什么时候调、调完看结果再决定下一步」，它就有了 Agent 的内核。
3. **第三层·代价与取舍**：自主性不是免费的。模型掌握控制权意味着更灵活，但也更不可控——可能多绕路、多花钱、甚至陷入循环。所以「是不是 Agent」从来不是「高不高级」的问题，而是「这个场景需不需要把控制权交给模型」的问题。

而 ReAct 正是让模型「掌握控制权」的最经典范式。ReAct = Reasoning + Acting，让 Agent 交替进行「推理」和「行动」：Thought（想下一步做什么）→ Action（调用工具）→ Observation（观察结果），带着观察结果再进入下一轮 Thought。ReAct 论文的原话是——它「以交错的方式生成推理轨迹和任务相关动作」，让推理轨迹帮助模型归纳、追踪和更新行动计划并处理异常，让动作使模型能与外部信息源交互 [来源](https://arxiv.org/abs/2210.03629)。它解决的核心问题是：纯推理（如 CoT）无法获取外部实时信息、容易一本正经地胡说；纯行动又缺乏规划、容易乱调工具。ReAct 把两者结合——**用推理指导行动，用行动结果修正推理**，形成自我纠错的闭环。
```text
纯推理 (CoT):   Thought → Thought → Thought → Answer
                └─ 问题：链条越长越容易跑偏，且无法接触外部世界，错了没人纠正
纯行动:         Action → Action → Action
                └─ 问题：没有「想一想」，容易乱调工具、目标漂移
ReAct:          Thought → Action → Observation ──┐
                   ↑______________________________|  带着真实反馈再想下一步
```
## 最小可运行演示

下面这段代码用一个「判断系统属于光谱哪一档」的分类器，把「谁决定下一步」这个抽象判据变成可运行的检查；同时跑一个极简的 ReAct 循环 mock，展示「想—做—看」如何交替。它不联网、不需要 API Key。
```python
"""第21.2节：控制权光谱分类器 + 极简 ReAct 循环（纯 Python，无需 API Key）。"""
from dataclasses import dataclass


@dataclass
class System:
    name: str
    uses_tools: bool
    model_decides_next_step: bool      ## 关键判据：下一步由谁决定
    has_loop: bool                     ## 有无「观察后再决策」的循环


def classify(s: System) -> str:
    ## 分水岭不是「有没有工具」，而是「模型是否决定下一步 + 有无循环」
    if s.model_decides_next_step and s.has_loop:
        return "Agent（模型掌握控制权）"
    if s.uses_tools:
        return "Workflow（工具由代码编排）"
    return "纯 LLM 调用（单轮问答）"


## 极简 ReAct：模型「想」出该调哪个工具，执行后拿观察，再决定停不停
def fake_weather(city: str) -> str:
    return f"{city}今天晴，26℃"


def react_once(question: str) -> list:
    trace = []
    trace.append(("Thought", "问的是实时天气，我的训练知识答不了，应该调天气工具"))
    trace.append(("Action", "get_weather(city='北京')"))
    trace.append(("Observation", fake_weather("北京")))
    trace.append(("Thought", "已拿到实时结果，可以回答了"))
    trace.append(("Answer", "北京今天晴，26℃"))
    return trace


SYSTEMS = [
    System("单次问答", uses_tools=False, model_decides_next_step=False, has_loop=False),
    System("写死三步流水线", uses_tools=True, model_decides_next_step=False, has_loop=False),
    System("模型自主调工具并循环", uses_tools=True, model_decides_next_step=True, has_loop=True),
]


def run():
    for s in SYSTEMS:
        print(f"[{classify(s):22}] <- {s.name}")
    print("--- ReAct 循环 ---")
    for step, content in react_once("今天北京天气如何"):
        print(f"{step:11}: {content}")


if __name__ == "__main__":
    run()
```
保存为 `s2_agent.py`，运行 `python s2_agent.py`。预期输出：
```text
[纯 LLM 调用（单轮问答）  ] <- 单次问答
[Workflow（工具由代码编排）] <- 写死三步流水线
[Agent（模型掌握控制权）  ] <- 模型自主调工具并循环
--- ReAct 循环 ---
Thought    : 问的是实时天气，我的训练知识答不了，应该调天气工具
Action     : get_weather(city='北京')
Observation: 北京今天晴，26℃
Thought    : 已拿到实时结果，可以回答了
Answer     : 北京今天晴，26℃
```
注意第二行「写死三步流水线」——它 `uses_tools=True` 却被判为 Workflow，因为 `model_decides_next_step=False`。这精确复现了导读里面试官的反问：**调了三个工具不等于 Agent，判据是模型有没有权决定下一步。**

## 真实系统对应

**官方公开机制**：Anthropic 明确把 Workflow（预定义代码路径编排）和 Agent（LLM 动态决定流程与工具）分开定义，并给出边界建议「追求简单，能用 Workflow 就别上 Agent；只有当任务的灵活性和模型驱动的决策确实带来价值时，才引入 Agent」[来源](https://www.anthropic.com/engineering/building-effective-agents)。ReAct 的「推理与行动交错」范式来自 Yao 等人的原始论文 [来源](https://arxiv.org/abs/2210.03629)；而 CoT「用中间推理步骤提升多步推理」则来自 Wei 等人的论文 [来源](https://arxiv.org/abs/2201.11903)——两者的关系是「ReAct 在 CoT 的纯推理上加了与环境交互的行动」。Lilian Weng 的综述把 Planning（规划）、与环境交互、反思归纳为自主 Agent 的核心组件，可作为「Agent 内核」的权威参照 [来源](https://lilianweng.github.io/posts/2023-06-23-agent/)。**通用工程模式**：用「控制权归属 + 有无循环」判断一个系统是不是 Agent，可迁移到任何架构评审。**教学参考实现**：上面的分类器与 ReAct trace 是为讲清判据而构造，真实 ReAct 每一步 Thought 都是一次真实模型调用。

一个必须澄清的边界：光谱不是「越靠右越好」。很多面试者有个错觉——把「Agent」当褒义、「Workflow」当贬义。事实恰恰相反：**在能用 Workflow 解决的场景硬上 Agent，是典型的过度设计**，会白白付出自主性带来的不可控与成本。判断从来是「这个场景需不需要把控制权交给模型」，而不是「哪个更高级」。

## 生产踩坑

| 现场表现 | 根因 | 如何观测复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| 把「能调 API」当成 Agent | 用工具有无当判据 | 举「写死流水线也调三个工具」反问 | 改用「模型是否决定下一步」判据 | 概念科普场合无需较真时 |
| 该用 Workflow 却上了 Agent | 迷信「Agent 更高级」 | 统计任务是否真需要动态决策 | 固定流程能解决就用 Workflow | 任务确实高度动态开放时 |
| ReAct 循环停不下来 | 无步数上限与收敛判断 | 构造无解问题看是否无限循环 | 设 max_turns + 无进展则终止 | 有明确外部终止信号的任务 |
| ReAct 延迟成本高到不可接受 | 每步一次模型调用累积 | 统计单任务平均 Thought 轮数 | 精简工具让每步一次到位、简单意图走规则短路 | 对延迟不敏感的离线批处理 |
| 把 ReAct 说成某个框架/库 | 混淆范式与实现 | 追问「它是范式还是库」 | 明确 ReAct 是范式、可用任意框架实现 | 特指某库实现细节的语境 |

## 思考：ReAct 和 Chain-of-Thought 到底是什么关系？为什么不能只用 CoT？

### 回答

CoT 和 ReAct 是「包含与扩展」的关系：CoT 只有推理没有行动，ReAct 在 CoT 的推理之上，加了「与外部环境交互」的行动能力。CoT 让模型在给出答案前先生成一串中间推理步骤（Wei 等人的论文证明这能显著提升多步推理任务的表现 [来源](https://arxiv.org/abs/2201.11903)），它的价值是「把一步到位的猜答案，变成分步推导」。但 CoT 有一个根本局限——**它全程在模型脑内进行，接触不到外部世界**。链条越长越容易跑偏，而一旦某一步推错，后面全建立在错误之上，且没有任何外部信号能纠正它。这就是「一本正经地胡说」的温床：推理看起来很有条理，结论却与现实脱节。

ReAct 解决的正是这个局限。它在推理之间插入「行动」和「观察」——模型想到「我需要某个信息」时，不是继续脑补，而是真的去调工具、查数据库、访问网页，拿到真实的 Observation 再继续想。这样「脑内的规划」和「世界的反馈」不断对齐，推错了会被真实结果拉回来。ReAct 论文把这个协同总结为：推理帮助模型创建、维护和调整行动计划并处理异常，行动让模型接入外部信息源 [来源](https://arxiv.org/abs/2210.03629)。所以「为什么不能只用 CoT」的答案是：**只用 CoT 时，模型没有获取外部实时信息的手段，也没有校正错误推理的锚点；需要与外部世界交互、需要实时数据、需要自我纠错的任务，必须用 ReAct 这种能行动的范式。** 当然，代价是 ReAct 每一步 Thought 都是一次模型调用，延迟和成本都高于一次性的 CoT，所以生产里要配步数上限和收敛判断。

### 面试精简表达

CoT 只推理、ReAct 在推理上加行动。CoT 全程在脑内、接触不到外部世界、错了没锚点纠正；ReAct 用真实 Observation 校正推理，适合需要实时数据与自我纠错的任务，代价是每步一次模型调用、延迟成本更高。

### 反例

有人说「那我把 CoT 的推理写得足够详细，是不是就不需要 ReAct 了」——不行。再详细的推理也变不出模型没有的实时信息（比如今天的股价、某订单的真实状态），也无法验证自己推理的中间结论是否符合现实。信息缺口和校正锚点这两件事，只能靠「行动」补，不能靠「想得更细」补。

## 事故回放：一个「假 Agent」如何在评审里被识破

某团队上线了一个号称「智能报告 Agent」的系统，架构评审时被一句话问倒。系统流程是：接收用户请求 → 固定调用「数据查询」→ 固定调用「图表生成」→ 固定调用「摘要撰写」→ 返回。评审专家问：「如果数据查询返回空，它会怎么办？」团队答「还是会继续走图表生成，只是图表是空的」。专家又问：「模型有没有可能根据查询结果，决定跳过图表、直接说数据不足？」团队答「没有，流程是写死的」。

评审结论很清晰：**这是一个包装成 Agent 的 Workflow。** 它调了工具、有多个步骤、输出也「看起来智能」，但模型全程没有任何决策权——每一步做什么、下一步是什么，都由代码写死。它连「观察结果后改变计划」这个 Agent 最基本的能力都没有。这个案例的价值在于：它把导读里「调三个工具算不算 Agent」的抽象问题，落到了一个可操作的检验动作上——**问一句「当中间结果异常时，谁来决定下一步」**。如果答案永远是「代码」，那它就是 Workflow；只有当答案是「模型看情况定」时，它才是 Agent。这个检验动作，比任何定义都更能帮你在面试和评审里一秒看穿一个系统的本质。
