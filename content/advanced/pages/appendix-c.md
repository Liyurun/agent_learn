> 本附录汇总全书核心术语，按主题分组，每个术语提供三样东西——**一句话定义**（建立直觉）、**常见误解**（面试最容易答偏的地方）、**面试怎么用**（被问到时怎么答才到位）。面试前快速扫一遍，确保关键术语能脱口而出、不混淆。加 ⭐ 的为高频面试术语。

> **怎么用这张表**：不要死背英文缩写。正确用法是——先看"一句话定义"建立直觉，再看"常见误解"避雷，最后看"面试怎么用"预演被问的角度，需要细节时回到正文对应章节。能把"常见误解"和"面试怎么用"讲清楚，才算真的掌握。缩写在正文首次出现时给出英文全称：CoT(Chain-of-Thought)、KV Cache(Key-Value Cache)、CLI(Command-Line Interface)、SDK(Software Development Kit)、RBAC(Role-Based Access Control)、SLO(Service Level Objective)、PII(Personally Identifiable Information)、HITL(Human-in-the-Loop)、RAG(Retrieval-Augmented Generation)、MCP(Model Context Protocol)。

## C.1 基础概念

| 术语（中/英） | 一句话定义 | 常见误解 | 面试怎么用 |
|---|---|---|---|
| 智能体 ⭐ Agent | 以 LLM(Large Language Model) 为大脑，能自主决策、调用工具、迭代完成目标的系统 | 以为"调了个大模型 API 就是 Agent" | 答区别抓一句"谁控制流程——模型动态决定下一步就是 Agent，代码写死就是工作流" |
| 工作流 ⭐ Workflow | 由代码固定编排流程、每步走向可预知的系统 | 以为工作流比 Agent"低级" | 答"流程可预知、要稳定可控时优先工作流，它更省更稳，不是低级" |
| 大语言模型 LLM | Agent 的推理内核，基于海量文本训练的生成模型 | 以为模型什么都能干、能直接执行动作 | 答"它的局限（上下文有限、会幻觉、知识过时、不能真执行动作）恰恰决定了 Agent 要配记忆、工具、护栏" |
| 自主性 Autonomy | Agent 自行决定下一步做什么的程度 | 以为自主性越高越好 | 答"不是，自主性越高越难控，要按场景在'灵活'和'可控'间权衡" |
| 智能体循环 ⭐ Agent Loop | 感知→决策→行动→观察反复迭代，直到达成目标或触发终止 | 忘了写退出条件，导致死循环 | 常要求"手写最小 Agent 循环"，要说清循环体和退出条件（步数/token/完成判定） |
| 系统提示 System Prompt | 设定 Agent 角色、能力边界与行为规则的顶层指令 | 以为系统提示能被用户输入随便覆盖 | 答"它定义角色和护栏，应与不可信的用户输入隔离，关键约束别只写在这里、还要有代码兜底" |
| 涌现能力 Emergent Ability | 模型规模到一定程度才显现的能力（如少样本推理） | 以为所有能力都随规模线性增长 | 当背景概念用，回答"为什么大模型才适合做 Agent" |
| 少样本/零样本 Few-shot / Zero-shot | 提示里给几个示例（few）或不给示例（zero）让模型完成任务 | 以为示例越多越好 | 答"few-shot 用示例对齐格式与风格，但占 token；格式简单时 zero-shot 更省，复杂输出才值得给例子" |
| 智能体工程 Agentic | 形容"让模型自主决策驱动流程"的一类系统与做法 | 把任何用到 LLM 的系统都叫 agentic | 答"agentic 强调决策权在模型手里，程度有高有低，不是二选一的标签" |

## C.2 推理与规划

| 术语（中/英） | 一句话定义 | 常见误解 | 面试怎么用 |
|---|---|---|---|
| 思维链 ⭐ CoT (Chain-of-Thought) | 引导模型一步步写出中间推理再给答案 | 以为对所有任务都该开 CoT | 答"CoT 有效是因为拆小步降难度；但它增加 token 和延迟，简单任务不必用" |
| 思维树 ToT (Tree of Thoughts) | 把推理扩展为可探索多分支并回溯的树 | 以为它总比 CoT 好 | 答"更准但更贵——用成倍的模型调用换探索能力，要权衡" |
| 推理+行动 ⭐ ReAct | Thought→Action→Observation 交替循环，推理与行动相互增强 | 把 ReAct 讲成"只是加了工具" | 必考，常要求"画出并口述 ReAct 循环"，强调行动的真实反馈纠正推理、防幻觉 |
| 任务分解 Task Decomposition | 把复杂目标拆成可执行的子任务 | 以为只能一次性拆好 | 答"可由规划步一次性拆，也可边做边拆，取决于任务是否可预知" |
| 规划 Planning | Agent 制定完成目标的步骤序列 | 以为一定要先完整规划再执行 | 答"先规划再执行更可控，边走边看更抗变，看任务不确定性选" |
| 自洽性 Self-Consistency | 采样多条推理链、对答案投票取多数 | 以为它能修复模型根本不会的题 | 答"多链投票用冗余换稳健，但只在模型本就有一定正确率时有效" |
| 重规划 Re-planning | 执行中发现计划失效时重新规划 | 以为计划定了就得硬跑到底 | 答"发现偏离就触发重规划，别把错误计划执行到底" |

## C.3 记忆与上下文

| 术语（中/英） | 一句话定义 | 常见误解 | 面试怎么用 |
|---|---|---|---|
| 短期记忆 ⭐ Short-term Memory | 当前对话上下文，靠上下文窗口承载 | 以为它能无限累积 | 答"受上下文窗口限制，长了要截断或摘要，否则爆窗且变贵" |
| 长期记忆 ⭐ Long-term Memory | 跨会话持久化的信息，常用向量库存取 | 以为把所有历史都存下来就好 | 答"只存关键事实/偏好，按相关性检索回填，不是全量堆积" |
| 上下文窗口 Context Window | 模型单次能处理的最大 token 范围 | 以为窗口越大越好 | 答"更大不等于更好，有'中间迷失'和成本/延迟问题" |
| 向量数据库 ⭐ Vector Database | 存 embedding 并支持语义相似度检索的库 | 以为它能替代关系库做精确查询 | 答"它做语义相似检索，不做精确匹配；两者各司其职" |
| 嵌入 Embedding | 把文本映射为向量以支持语义检索 | 以为不同模型的向量能混用 | 答"相似度常用余弦；不同 embedding 模型的向量空间不通用，不能混检索" |
| 检索增强生成 ⭐ RAG | 先检索外部知识、再据此生成，缓解陈旧与幻觉 | 以为 RAG 能彻底消除幻觉 | 答"RAG 大幅降幻觉但不清零，还要引用校验；RAG vs 微调看'知识常变需溯源'还是'改风格内化稳定知识'" |
| 智能体式 RAG ⭐ Agentic RAG | 由 Agent 自主决定是否/如何/检索几次的 RAG | 以为只是"多检索几次" | 答"关键是检索的决策权从固定流程交给了 Agent，能按需检索、改写查询、判断是否够" |
| 假设文档嵌入 HyDE (Hypothetical Document Embeddings) | 先让模型对问题生成一个"假设答案"，再用它的向量去检索 | 以为它总能提升召回 | 答"用假设答案对齐文档的语言空间、提升召回，但假设跑偏时会引入噪声，属于查询改写的一种" |
| 重排序 ⭐ Rerank | 对初步召回的候选用更强模型重新打分排序 | 以为向量召回一步到位、不用重排 | 答"两阶段检索——先向量快速召回一批，再用 cross-encoder 精排取 top-k，用少量算力换准确率" |
| 双编码/交叉编码 Bi-encoder / Cross-encoder | 双编码分别编码查询与文档（快，用于召回），交叉编码把两者拼一起联合打分（准，用于精排） | 以为召回和精排能用同一个模型 | 答"召回用 bi-encoder 快而糙、精排用 cross-encoder 慢而准，分工正对应两阶段检索" |
| 上下文工程 ⭐ Context Engineering | 精心策划进入上下文窗口的内容以提升效果 | 以为等同于写好 prompt | 答"它比 prompt 工程更宽，是对推理时全部 token 的治理——只放当前决策必需的，控噪声控成本" |
| 中间迷失 Lost in the Middle | 长上下文中模型对中间位置信息利用率下降 | 以为信息塞进去就一定被用上 | 答"关键信息别埋中间，放首尾更易被利用" |
| 分块 Chunking | 把长文档切成适合检索的片段 | 以为切得越碎越好 | 答"块太大稀释相关性、太小丢上下文，要按语义边界切并考虑重叠" |
| 记忆流 Memory Stream | 带时间戳的记忆记录，按近因/重要/相关性检索 | 以为长期记忆就是按时间倒序取 | 答"综合近因性、重要性、相关性三项打分检索，不是单看时间" |

## C.4 工具与协议

| 术语（中/英） | 一句话定义 | 常见误解 | 面试怎么用 |
|---|---|---|---|
| 工具使用 ⭐ Tool Use | Agent 调用外部函数/API 与真实世界交互 | 以为工具只是"查资料" | 答"工具让 Agent 突破纯文本，能获取实时信息、执行真实动作（下单、退款）" |
| 函数调用 ⭐ Function Calling | 模型以结构化方式请求调用函数（模型只输出请求，不执行） | 以为模型自己执行了函数 | 必考，答"模型只输出结构化调用请求，执行由应用侧完成，结果再回填给模型" |
| 工具描述 Tool Schema | 名称+描述+参数，模型据此决定何时怎样调用 | 以为工具描述随便写 | 答"工具描述即 prompt，写不清模型会选错/漏用工具" |
| 模型上下文协议 ⭐ MCP (Model Context Protocol) | 统一 AI 应用与外部工具连接的开放标准，"AI 的 USB-C" | 把 MCP 和 Function Calling 混为一谈 | 答"MCP 是应用层的标准化连接协议，把 N×M 的对接变成 N+M；Function Calling 是模型层的调用能力，两者不同层" |
| MCP 三原语 Resources / Tools / Prompts | MCP 定义的三类能力：资源、工具、提示模板 | 只记得"工具"一类 | 答"资源（读数据）、工具（执行动作）、提示（复用模板）三类" |
| 结构化输出 Structured Output | 让模型输出符合 schema 的结构化数据（如 JSON） | 以为在 prompt 里写"输出 JSON"就够 | 答"要 schema 约束 + 校验重试，别只靠 prompt 祈祷" |
| 并行工具调用 Parallel Tool Calls | 模型一次请求多个相互独立的工具调用 | 以为所有工具都能并行 | 答"相互独立的可并行，有依赖的必须串行" |
| 工具执行沙盒 Sandbox | 隔离环境中执行工具/代码，限制副作用 | 以为让模型执行代码只要"信任它" | 答"放沙盒里跑，限制权限、网络与资源，防止误删/越权/失控" |
| 工具幻觉 Tool Hallucination | 模型编造不存在的工具名或非法参数去调用 | 以为工具描述写了模型就一定调对 | 答"要做参数校验 + 白名单，非法调用直接拦截并让模型带错误重试，别把非法调用真执行" |
| 幂等键 Idempotency Key | 让同一操作重复执行只生效一次的唯一标识 | 以为重试无害 | 答"退款/下单这类有副作用的动作要带幂等键，重试或超时重发才不会重复扣款" |

## C.5 编排与多智能体

| 术语（中/英） | 一句话定义 | 常见误解 | 面试怎么用 |
|---|---|---|---|
| 提示链 Prompt Chaining | 把任务拆成串联的多个 LLM 调用 | 以为它和 Agent 一回事 | 答"步骤固定、可线性拆解、每步可校验的任务用提示链，它是工作流不是 Agent" |
| 路由 ⭐ Routing | 根据输入把请求分派到不同处理路径/Agent | 以为分类器一定分得对 | 答"用分类器/LLM 分派，必须加兜底默认路径和低置信度转人工" |
| 并行化 Parallelization | 同时执行多个子任务再汇总 | 以为什么任务都能并行 | 答"子任务相互独立、可分别完成再聚合时才并行" |
| 编排者-工作者 Orchestrator-Workers | 中心 Agent 动态拆分任务分派给工作 Agent | 和并行化分不清 | 答"区别在任务由中心动态拆分，而非预先固定切好" |
| 评估者-优化者 Evaluator-Optimizer | 生成→评估→改进的迭代循环 | 以为对任何输出都值得多轮打磨 | 答"有明确评判标准、值得多轮打磨的输出才用，否则白烧 token" |
| 多智能体 ⭐ Multi-Agent | 多个专门化 Agent 协作完成复杂任务 | 以为多 Agent 更高级、更强 | 高频陷阱题，答"能拆成弱耦合子任务且单 Agent 搞不定时才用，要接受成本高、易发散、难调试" |
| 交接 ⭐ Handoff | 一个 Agent 把任务及上下文移交给另一个 Agent | 以为交接只传一句话 | 答"要传任务目标 + 必要上下文，避免信息丢失导致接手方重复提问" |
| 中心化/去中心化 Centralized / Decentralized | Manager 统一路由 vs Agent 间对等协作 | 以为去中心化更先进 | 答"中心化好控好调试，去中心化更灵活但易发散，多数生产系统选中心化" |
| 反思 Reflection | Agent 对自身行为/结果回顾以改进 | 以为反思一定提升质量 | 答"反思是自评改进的一种，可无外部评判；但判断力不够时会自我强化错误" |
| 监督者 Supervisor | 负责分诊、路由、编排子 Agent 的中心节点 | 以为它也直接干活 | 答"supervisor 只负责编排与前置护栏，具体执行下放给专家子 Agent" |

## C.6 工程化与生产

| 术语（中/英） | 一句话定义 | 常见误解 | 面试怎么用 |
|---|---|---|---|
| 评估 ⭐ Evaluation | 系统衡量 Agent 效果（成功率、幻觉率、轨迹合理性） | 以为只看最终答案对错 | 必考，答"不仅看结果，还要看轨迹/工具调用是否合理，这是 Agent 评估和普通模型评估的关键差异" |
| 轨迹评估 ⭐ Trajectory Evaluation | 评估 Agent 完成任务的中间步骤序列是否合理 | 以为答案对了过程就对 | 答"答案对但路径绕/乱调工具也是问题；轨迹评估看每步 thought/action/observation 是否该发生、顺序对不对" |
| 模型即评委 ⭐ LLM-as-a-judge | 用另一个 LLM 给输出质量打分 | 以为"另一个模型打分就客观" | 答"有位置偏好、冗长偏好等偏差且不稳定，要固定 rubric、做对齐校准、必要时人工抽检" |
| 可观测性 ⭐ Observability | 记录 Agent 每步决策/工具调用，便于排查 | 以为打几行日志就够 | 答"Agent 难调试，要把每步 thought/action/observation、入参出参、耗时 token 都记下来能回放" |
| 追踪 ⭐ Tracing | 完整记录一次执行的全链路轨迹（span 树） | 把 trace 和普通日志等同 | 答"trace 是一次执行的结构化全链路轨迹，能按 session_id 还原谁在何时做了什么，日志是零散记录" |
| 护栏 ⭐ Guardrails | 对输入/输出的安全与合规约束 | 以为在 prompt 里写"别乱说"就是护栏 | 答"护栏要软硬结合、多层：输入侧过滤、输出侧校验、工具调用前权限校验，不能只靠 prompt 自觉" |
| 提示注入 Prompt Injection | 通过恶意输入劫持 Agent 行为的攻击 | 以为加一条"忽略恶意指令"就能防住 | 答"没有银弹，只能分层缓解：隔离不可信输入、最小权限、关键动作人工确认" |
| 人在回路 ⭐ HITL (Human-in-the-Loop) | 关键/高危操作需人工确认（可中断-恢复） | 以为所有动作都要人工审 | 答"只对不可逆/高成本/高风险动作（支付、退款、删库、外发）加 HITL，其余放行以免拖慢体验" |
| 幻觉 ⭐ Hallucination | 模型编造不真实内容 | 以为能被彻底根除 | 答"只能压不能清零：RAG 溯源、结构化校验、工具核实、允许它说'不知道'" |
| 护栏软硬之分 Soft/Hard Guardrail | 软护栏靠提示引导，硬护栏靠代码强制拦截 | 以为软硬二选一 | 答"软护栏可被绕过，关键动作（如未授权承诺退款）必须上硬护栏代码拦截" |
| 令牌 Token | 模型处理文本的最小单位，计费与上下文的度量 | 以为一个汉字=一个 token | 答"按 token 计费，控成本靠缩短上下文、缓存、选小模型；中英文分词比例不同" |
| KV Cache ⭐ (Key-Value Cache) | 缓存注意力层已算过的 Key/Value，避免重复计算 | 和 Prompt Caching 混为一谈 | 答"KV Cache 是推理时省重复计算、加速生成的机制，作用在单次生成内部" |
| 提示缓存 ⭐ Prompt Caching | 缓存重复的提示前缀，跨请求复用以省成本降延迟 | 以为它和 KV Cache 是一回事 | 答"Prompt Caching 面向重复的长系统提示/文档前缀跨请求复用，把稳定前缀放最前面命中率最高，省钱又降延迟" |
| 延迟 Latency | 从请求到响应的耗时 | 只想着换更快的模型 | 答"减少循环步数、并行独立工具、流式输出、缓存，比单纯换模型更有效" |
| 温度 Temperature | 控制采样随机性的参数 | 以为越高越"聪明" | 答"要确定性/结构化输出调低，要多样性/探索调高" |
| 缓存 Caching | 复用重复请求的结果以省成本降延迟 | 以为什么都能缓存 | 答"稳定的系统提示、重复的检索/工具结果可缓存；带时效或个性化的要谨慎" |
| 回退/降级 Fallback | 主路径失败时切换到备用方案 | 以为工具挂了就直接报错 | 答"设兜底：换模型、返回安全默认、转人工，别让单点故障击穿整条链路" |
| 终止条件 ⭐ Termination Condition | 强制结束循环的规则（步数/token/完成校验） | 以为模型会自己知道停 | 答"设最大步数/token 上限 + 完成判定 + 无进展检测，防死循环烧钱" |
| 会话预算 Session Budget | 单会话的轮次/token 上限，超限强制干预 | 忽略单会话累计成本 | 答"给会话设轮次和 token 上限，超限强制转人工或结束，防单会话失控" |

## C.7 安全、权限与合规

| 术语（中/英） | 一句话定义 | 常见误解 | 面试怎么用 |
|---|---|---|---|
| 越狱 Jailbreak | 直接诱导模型突破自身安全限制 | 和提示注入混为一谈 | 答"越狱是直接攻击模型的安全对齐，提示注入是借外部输入劫持已部署 Agent，攻击面不同" |
| 最小权限 Least Privilege | 只给 Agent/工具完成任务所必需的最小权限 | 以为给全权限方便就好 | 答"权限越小爆炸半径越小，敏感工具按需授权，别给 Agent 万能钥匙" |
| 基于角色的访问控制 RBAC (Role-Based Access Control) | 按角色分配可执行的操作与可访问的数据 | 以为身份能从用户输入里解析 | 答"身份来自系统会话注入，绝不来自模型或用户可控的自然语言，否则埋越权隐患" |
| 个人身份信息 PII (Personally Identifiable Information) | 能识别到个人的敏感信息（姓名、电话、身份证等） | 以为输出不检查也没事 | 答"输出侧要做 PII 脱敏，日志/trace 里也要脱敏，避免敏感信息泄漏" |
| 服务级目标 SLO (Service Level Objective) | 对服务质量（如延迟、成功率）设定的量化目标 | 把模糊需求当指标 | 答"把'快、准、稳'翻译成可验收的 SLO，如 P95 延迟<3s、成功率>95%，才能验收和监控" |
| 接地/有据 Grounding | 让生成内容有可核验的外部证据支撑 | 以为 prompt 写'别编造'就有据 | 答"要给答案标引用来源、做 grounded 标记，让每句结论可回溯到证据，光靠 prompt 约束不够" |

## C.8 最易混淆的术语辨析

| 易混对 | 关键区别（记这一句） |
|---|---|
| Agent vs Workflow ⭐ | 谁控制流程：模型动态决定=Agent；代码写死=Workflow |
| Function Calling vs MCP ⭐ | 模型层的调用能力 vs 应用层的标准化连接协议 |
| RAG vs Agentic RAG ⭐ | 固定检索一次 vs 模型自主决定是否/如何/检索几次 |
| CoT vs ReAct | 只推理 vs 推理+行动（与环境交互） |
| 短期 vs 长期记忆 | 当前上下文 vs 跨会话持久化 |
| KV Cache vs Prompt Caching ⭐ | 单次生成内省重复计算 vs 跨请求复用重复提示前缀 |
| Rerank vs 向量召回 | 精排（cross-encoder 慢而准）vs 粗召（向量快而糙），两阶段配合 |
| HyDE vs 普通检索 | 先造假设答案再检索 vs 直接用原问题检索 |
| 编排者-工作者 vs 并行化 | 任务动态拆分下发 vs 预先固定切好并行 |
| 反思 vs 评估者-优化者 | 自评改进（可无外部评判）vs 有独立评估者的生成-评估循环 |
| 提示注入 vs 越狱 | 借外部输入劫持已部署 Agent vs 直接诱导模型突破自身安全限制 |
| 追踪 vs 日志 | 一次执行的全链路结构化轨迹 vs 零散的运行时记录 |
| 软护栏 vs 硬护栏 | 提示引导（可被绕过）vs 代码强制拦截（不可绕过） |

## C.9 高频追问与"错误答案"对照（避雷）

术语背得再熟，面试栽在"看似会、实则答偏"上也很常见。下面列出高频追问、正确方向和一个典型错误答案，专门避雷。

| 追问 | 正确方向 | 典型错误答案（别这么答） |
|---|---|---|
| Agent 一定比工作流好吗？ | 不是，流程可预知时工作流更稳更省，Agent 是需要动态决策时才用 | "Agent 更智能，所以更好" |
| 上下文窗口越大越好吗？ | 不是，还有"中间迷失"、成本和延迟问题，关键信息要放首尾 | "越大越好，能塞更多信息" |
| 模型会自己执行函数吗？ | 不会，模型只输出结构化调用请求，执行在应用侧 | "模型调用 API 拿到结果" |
| 多 Agent 是不是更高级？ | 不是，它成本高、易发散、难调试，是最后手段 | "多 Agent 更强，能力更全" |
| RAG 和微调怎么选？ | 知识常变/需溯源用 RAG，改风格/内化稳定知识用微调，可结合 | "微调更彻底，能就用微调" |
| RAG 能彻底消除幻觉吗？ | 不能，只能大幅降低，还要引用校验和 grounded 标记 | "上了 RAG 就不会幻觉了" |
| 用 LLM 当评委可靠吗？ | 有偏好偏差、不够稳定，要固定 rubric 并做校准，不能全信 | "另一个模型打分，肯定客观" |
| 提示注入能彻底防住吗？ | 没有银弹，只能分层缓解：隔离输入、最小权限、关键动作人工确认 | "加一条'忽略恶意指令'的提示就行" |
| 自我反思一定能提升质量吗？ | 不一定，当模型判断力不强于生成力时，自评无增益甚至强化错误 | "让它自己再检查一遍肯定更好" |
| 身份信息能从用户输入里取吗？ | 不能，身份必须由系统会话注入，否则埋越权隐患 | "从用户说的账号里解析就行" |

> **经验**：面试官问这些"是不是更好/能不能彻底"的问题，十有八九在设陷阱——他想听的是"看情况 + 权衡 + 代价"，而不是非黑即白的断言。养成"先给结论，再补条件与代价"的答题习惯，能避开绝大多数坑。

## C.10 术语记忆法（面试速记）

背术语不是目标，会用才是。推荐四个记忆技巧：

- **按"演进线"记推理类**：CoT（会想）→ Self-Consistency（想多次投票）→ ToT（想成树）→ ReAct（边想边做）。一条线拎起来，比孤立背四个词牢得多。
- **按"两阶段"记检索类**：查询改写（HyDE）→ 向量粗召 → Rerank 精排 → 塞进上下文（受"中间迷失"约束）。整条检索链串起来，RAG 相关术语就全挂上了。
- **按"三层防线"记工程类**：护栏（拦）→ 可观测/追踪（看）→ 终止条件/回退（兜）。任何生产化问题都能挂到这三层上回答。
- **按"一句话对比"记易混对**：每对易混术语只记一句核心区别（见 C.8），被追问时先甩这句，再展开。

> **面试会怎么问（元问题）**：面试官有时不直接问定义，而是给一个场景让你判断该用哪个概念。例如"用户问题有时要查库有时不用查，你怎么设计检索"——这在考 Agentic RAG；"这个客服流程很固定"——在暗示用 Workflow。**训练方法**：看到每个术语，反过来想"什么样的场景描述会指向它"，才能在场景题里对号入座。
