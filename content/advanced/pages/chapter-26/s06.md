## 真实问题

一个团队花了三周给 RAG 系统做优化：换了更强的 embedding、加了 rerank、上了查询改写，每一步都「感觉更好了」。上线后老板问「到底好了多少」，团队答不上来——他们从头到尾没有一个**评估集**，所有判断都基于「随手试几个问题，看着顺眼」。更尴尬的是，某次改动其实让「精确型号查询」这类问题**变差了**，但因为随手试的恰好都是通用问题，没人发现，直到大客户投诉「查错误码全错」才暴露。

这暴露了 RAG 工程最致命的盲区：**没有量化，优化就是玄学。** 你不知道当前系统好在哪、坏在哪；不知道某次改动是净收益还是拆东墙补西墙；更不知道换了模型 / 调了参数后，会不会在你没测到的那类问题上悄悄退化。这一节讲清 RAG 评估的四个核心指标、怎么攒一个能回归的评估集，以及为什么它是所有优化的**前置条件**而不是「有空再做」。

## 原理：把「好不好」拆成可测的四个指标

RAG 系统的质量不是一个笼统的「准确率」，而要拆到**检索**和**生成**两个环节分别度量。业界最常用的一套是 Ragas（RAG Assessment，一个开源 RAG 评估框架）提出的四个指标 [来源](https://docs.ragas.io/)，它们把「一次问答做得好不好」拆成四个正交的问题：

| 指标 | 度量环节 | 回答的问题 | 低分意味着 |
|---|---|---|---|
| 上下文召回率 context recall | 检索 | 标准答案需要的事实，检索到的上下文里有几成？ | 检索**漏了**关键信息（该召的没召回） |
| 上下文精度 context precision | 检索 | 检索到的块里，真正相关的占几成、排得靠前吗？ | 检索**掺了噪声**（召回一堆无关块） |
| 忠实度 faithfulness | 生成 | 答案里的每个声明，都能被检索上下文支撑吗？ | 模型在**编**（幻觉，脱离原文瞎说） |
| 答案相关性 answer relevancy | 生成 | 答案切题吗，还是答非所问 / 啰嗦跑题？ | 答案**没回应**问题本身 |

这四个指标的正交性是关键——它们**分别定位不同环节的病**：
```text
一次 RAG 问答的四个诊断维度：

用户问题 ──▶ [检索] ──▶ 上下文 ──▶ [生成] ──▶ 答案
              │                        │
    上下文召回率↑：该召的召回了吗          忠实度↑：答案有没有脱离原文瞎编
    上下文精度↑：召回的干净吗、排得对吗     答案相关性↑：答案切不切题

诊断逻辑：
  召回率低 → 修检索（混合检索 / 分块 / 查询改写）
  精度低   → 加 rerank、收窄 top-k
  忠实度低 → 加 prompt 约束「只依据原文」、降温度、加引用
  相关性低 → 修 prompt、修查询理解
```
- **忠实度（faithfulness）**：把答案拆成一个个「声明」，逐个检查能不能从检索到的上下文里推出来。全能推出=1.0，有编造=扣分。这是防幻觉最直接的指标 [来源](https://docs.ragas.io/en/stable/concepts/metrics/available_metrics/faithfulness/)。
- **上下文召回率（context recall）**：把标准答案拆成事实点，看有多少能在检索到的上下文里找到。它衡量「检索有没有漏」[来源](https://docs.ragas.io/)。
- **上下文精度（context precision）**：检索回来的块里，相关的占比多高、是否排在前面。它衡量「检索有没有掺噪声」。
- **答案相关性（answer relevancy）**：答案是否直接回应了问题。真实 Ragas 的做法是让 LLM 根据答案反向生成几个问题，再比它们和原问题的相似度——切题的答案反推出的问题会和原问题很像。

## 最小可运行演示

下面用零依赖代码实现这四个指标的**简化版**（真实 Ragas 用 LLM 做「声明抽取」和「事实核对」，这里用字符串包含与字频相似度模拟，让输出可逐字复核），对同一个问题跑「朴素 RAG」和「混合 + rerank RAG」两条管线，看四个指标如何把「哪条管线好、好在哪个环节」量化出来。
```python
from collections import Counter
import math

docs = {  # 贯穿数据：知识库，仅 d2 含答案
    "d0": "A100 是英伟达数据中心 GPU",
    "d1": "显卡功耗需要认真管理",
    "d2": "A100 的最大功耗为 400 瓦",
    "d3": "深度学习训练消耗大量电力",
}
question = "A100 功耗多少瓦"
ground_truth_docs = {"d2"}                     # 人工标注：应命中的文档
reference_facts = ["A100 最大功耗", "400 瓦"]   # 标准答案拆成的事实点


def embed(t):
    return Counter(t)


def cosine(a, b):
    c = set(a) & set(b)
    d = sum(a[t] * b[t] for t in c)
    na = math.sqrt(sum(v * v for v in a.values()))
    nb = math.sqrt(sum(v * v for v in b.values()))
    return d / (na * nb) if na and nb else 0.0


def context_precision(retrieved):  # 检索到的块里，相关块的比例
    if not retrieved:
        return 0.0
    return sum(1 for d in retrieved if d in ground_truth_docs) / len(retrieved)


def context_recall(retrieved):  # 标准答案的事实点，上下文覆盖了几成
    ctx = "".join(docs[d] for d in retrieved)
    covered = sum(1 for f in reference_facts if all(p in ctx for p in f.split()))
    return covered / len(reference_facts)


def faithfulness(answer, retrieved):  # 答案的声明有几成被上下文支撑
    ctx = "".join(docs[d] for d in retrieved)
    claims = [c for c in answer.replace("。", " ").split() if c]
    return sum(1 for c in claims if c in ctx) / len(claims) if claims else 0.0


def answer_relevancy(answer):  # 答案与问题的相关度（简化版）
    return round(cosine(embed(answer), embed(question)), 3)


def evaluate(name, retrieved, answer):
    print(f"[{name}]")
    print(f"  上下文精度={context_precision(retrieved):.2f} "
          f"上下文召回={context_recall(retrieved):.2f} "
          f"忠实度={faithfulness(answer, retrieved):.2f} "
          f"答案相关性={answer_relevancy(answer)}")


evaluate("朴素 RAG", ["d1", "d3", "d0"], "A100 功耗大约 300 瓦")   # 召回全噪声+编数字
evaluate("混合+rerank", ["d2"], "A100 最大功耗 400 瓦")           # 精准召回+忠实作答
```
保存为 `eval_metrics.py`，运行 `python eval_metrics.py`。预期输出：
```text
[朴素 RAG]
  上下文精度=0.00 上下文召回=0.00 忠实度=0.25 答案相关性=0.804
[混合+rerank]
  上下文精度=1.00 上下文召回=1.00 忠实度=1.00 答案相关性=0.804
```
逐行讲解：

- **朴素 RAG**：召回的 `d1/d3/d0` 全是噪声，`d2` 没进来——**上下文精度和召回率都是 0**，检索环节彻底失败；答案「300 瓦」是编的，只有「A100」「功耗」等词能对上上下文，**忠实度仅 0.25**，暴露幻觉。
- **混合 + rerank**：精准召回 `d2`，**上下文精度、召回率、忠实度全 1.0**，答案完全有据可依。
- **关键观察**：两条管线的**答案相关性都是 0.804**——因为两个答案都「在谈 A100 功耗」，看起来都切题。这恰恰说明**单看一个指标会骗人**：答案相关性高不代表答案对（朴素 RAG 切题但答错）。必须四个指标一起看，才能定位到「病在检索（精度 / 召回为 0）而非答非所问」。这就是把「感觉变好了」换成「四个数字」的价值。

## 深入：评估集怎么攒，为什么它是优化的前置条件

有了指标还不够，你需要一个**评估集（evaluation set）**：一组「问题 + 标准答案 + 应命中的文档」的样本，覆盖你线上真实会遇到的各类查询。它是把「玄学调参」变成「可回归工程」的地基。
```text
评估集的一条样本长这样：

{
  "question": "A100 功耗多少瓦",
  "reference_answer": "A100 的最大功耗为 400 瓦",
  "ground_truth_docs": ["d2"],          # 人工标注：这题应该命中哪些文档
}

评估集要覆盖各类查询（这是防"拆东墙补西墙"的关键）：
  · 通用语义类："怎么给显卡降功耗"
  · 精确匹配类："错误码 ERR_5012 是什么"   ← 只有这类才测得出缺 BM25 的坑
  · 多跳 / 对比类："对比 A100 和 H100 功耗"
  · 库里没有答案类："A100 支持量子计算吗"   ← 测系统会不会老实说"不知道"
```
为什么它是**前置条件**而非「有空再做」？因为**没有评估集，你无法判断任何一次改动是净收益还是净亏损**。开头那个团队的悲剧就是典型：他们的每次改动都「感觉更好」，但因为没有覆盖「精确匹配类」的评估样本，某次改动让错误码查询退化了却毫无察觉。有了评估集，每次改动前后各跑一遍、对比四个指标在**各类查询**上的变化，才能看清「这次改动让通用问题涨了 5 分，但让精确匹配跌了 20 分」这种拆东墙补西墙。攒评估集的务实起点：从线上真实日志里捞几十条高频问题，人工标注标准答案和应命中文档，先跑起来，再持续扩充。50 条精心标注的样本，胜过 5000 条没标注的。

一个常见的进阶做法是用强 LLM 辅助**合成评估集**（给它文档片段，让它生成「这段能回答的问题」），快速冷启动;但合成样本必须人工抽检校正，否则评估集本身就带偏。无论人工还是合成，核心原则不变：**评估集要像线上流量，优化才不会在没测到的地方翻车。**

## 真实系统对应

**官方公开机制**：Ragas 是开源的 RAG 评估框架，明确定义了忠实度、答案相关性、上下文精度、上下文召回率等指标及其计算方式（多数指标用 LLM 做「声明抽取 + 事实核对」）[来源](https://docs.ragas.io/)；其忠实度定义为「答案中被上下文支撑的声明数 / 答案总声明数」[来源](https://docs.ragas.io/en/stable/concepts/metrics/available_metrics/faithfulness/)。LangSmith、TruLens、Phoenix 等也提供 RAG 评估与追踪能力（具体功能以各自当前文档为准）。**通用工程模式**：分「检索指标 vs 生成指标」度量、攒覆盖多类查询的评估集、每次改动跑回归对比、用强 LLM 合成 + 人工抽检冷启动，都是可迁移到任何系统的做法。**教学参考实现**：上面的四个指标是字符串 / 字频简化版，只为让输出可复核；真实 Ragas 用 LLM 做声明级核对，分数更细腻，也更贵、更慢。

需要点明边界：LLM 做裁判（LLM-as-judge）本身有噪声和偏差，同一样本多次评分可能有波动，需要固定裁判模型、多次取均值、并定期人工校准；评估指标是「参考信号」不是「绝对真理」，最终还要结合线上真实反馈。价格、指标口径、SDK（Software Development Kit，软件开发工具包）方法名都会变，以 Ragas 当前官方文档为准。

## 生产踩坑

| 症状 | 根因 | 如何观测与复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| 优化全凭「感觉变好」 | 没有评估集与量化指标 | 问「好了多少」答不出数字 | 先攒评估集再优化 | 一次性 Demo 可豁免 |
| 改动拆东墙补西墙没发现 | 评估集不覆盖某类查询 | 精确匹配类退化却没测到 | 评估集覆盖通用/精确/多跳/无答案 | 场景极单一时风险低 |
| 答案相关性高但答案是错的 | 只看单一指标 | 切题但事实错仍高分 | 四指标联合看，重点盯忠实度 | 只需切题不需正确的闲聊 |
| 检索没漏但答案还是编 | 忠实度低、prompt 无约束 | 忠实度分低于阈值 | prompt 加「只依据原文」+降温度 | 允许创造性生成的场景 |
| 召回率低但一直调 prompt | 病在检索却治生成 | 上下文召回率持续为 0 | 先修检索（混合/分块）再谈生成 | 检索已达标时才调生成 |
| LLM 裁判分数忽高忽低 | 裁判模型有噪声 | 同样本多次评分方差大 | 固定裁判、多次取均值、人工校准 | 规则类硬指标无此问题 |
| 合成评估集本身带偏 | 合成样本没人工抽检 | 指标虚高但线上翻车 | 合成后人工抽检校正 | 高质量人工标注集除外 |
| 线上退化上线才发现 | 缺少回归门禁 | 每次发版靠人工试 | 把评估集接入 CI 做回归门禁 | 无自动化流水线的早期项目 |

## 思考：只用「答案看起来对不对」来评估 RAG 有什么问题？为什么要拆成四个指标？

### 回答

「答案看起来对不对」是一个笼统的整体判断，它有两个致命问题。第一，**它会骗人**：一个答案可以「切题、通顺、看起来很专业」却在**事实上是错的**——比如朴素 RAG 答「A100 功耗大约 300 瓦」，语气笃定、切中问题，但数字是编的。只看「像不像答案」根本发现不了这种幻觉。第二，**它无法定位病灶**：就算你判断出「这次答错了」，你也不知道该修哪里——是检索没召回到答案（检索的锅）、还是召回了但模型没用上反而瞎编（生成的锅）？不知道病因就无法对症下药。拆成四个指标正是为了解决这两点。忠实度专门抓「答案有没有脱离原文瞎编」，直接戳破「看起来对其实是编的」；上下文召回率和精度度量检索环节「有没有漏、有没有掺噪声」；答案相关性度量「切不切题」。四个指标正交，分别对应管线的不同环节，于是当系统答错时，看四个数字就能定位：召回率为 0 就是检索漏了、忠实度低就是模型在编、相关性低就是答非所问。这样优化才有方向，而不是对着一个笼统的「感觉」瞎调。

### 面试精简表达

单看「答案像不像」既会被「切题但编造」的幻觉骗过，又无法定位病灶；拆成上下文召回/精度（检索）+ 忠实度/答案相关性（生成）四个正交指标，才能既戳破幻觉又按环节对症下药。

## 思考：为什么说「评估集是 RAG 优化的前置条件，而不是有空再做」？

### 回答

因为没有评估集，你做的每一次「优化」都是一次**没有仪表的盲飞**——你不知道改动到底是净收益还是净亏损，甚至可能在拆东墙补西墙而毫不知情。这不是理论担忧：现实里最常见的翻车就是「换了个更强的组件，通用问题涨了，但某类没测到的查询（比如精确型号 / 错误码）悄悄退化了」，直到线上大客户投诉才暴露。评估集之所以是**前置**条件，是因为它定义了「什么叫更好」——只有先有一组覆盖各类真实查询的「问题+标准答案+应命中文档」，你才能在每次改动前后各跑一遍、对比四个指标在**每一类查询**上的变化，看清「这次改动在通用问题上 +5、在精确匹配上 -20」这种真相。反过来，如果等「优化完了有空再补评估」，你根本无法回溯判断之前哪次改动是对的、哪次埋了雷。务实的做法是先从线上日志捞几十条高频问题、人工标注，哪怕只有 50 条也能立刻把玄学调参变成可回归工程——50 条标注样本的价值远超 5000 条没标注的。更进一步，把评估集接进 CI 做回归门禁，就能在退化上线**之前**拦住它。一句话：先量化，再优化；先有仪表，再飞行。

### 面试精简表达

没有评估集的优化是盲飞，无法判断净收益还是拆东墙补西墙，尤其漏测某类查询会让它悄悄退化；先攒覆盖多类查询的「问题+标准答案+应命中文档」评估集、每次改动跑回归、接入 CI 门禁，才能把玄学调参变成可回归工程。
