## 真实问题

一个多轮客服 RAG，前面聊得好好的，一到追问就崩。用户先问「A100 是什么？」，系统答得不错；接着用户问「它的功耗呢？」——系统召回的却是一篇「它的相关说明请查阅产品手册」的废话页，因为直接拿「它的功耗呢」去检索，「它」指代谁完全丢失，反倒和另一篇同样含「它」的页面撞上了。更糟的是用户问「对比 A100 和 H100 的功耗」，系统只召回了 A100 那篇，H100 的数字压根没进上下文，于是答了个「只说了一半」的对比。

前面几节优化的都是「文档侧」（分块、embedding）和「检索算法」（混合、rerank），但还有一大类问题出在**查询本身**：口语化、有指代、太短、和文档用词对不上。查询侧优化就是在检索**之前**先「修一修」查询。这一节讲三招：**查询改写（补指代）、查询分解（拆复杂问题）、HyDE（补语义鸿沟）。**

## 原理：三类查询问题，三招对应

| 查询问题 | 典型例子 | 解药 |
|---|---|---|
| 多轮指代 | 「它的功耗呢？」（「它」= 前文 A100） | 查询改写 query rewriting |
| 一问多意 | 「对比 A100 和 H100 的功耗」 | 查询分解 query decomposition |
| 语义鸿沟 | 问句「怎么降低显卡功耗？」vs 陈述句文档 | HyDE |

**问题一：多轮对话里的指代。** 「它的功耗呢」里的「它」指代前文的 A100，但直接拿这句去检索什么都召不回，甚至被别的含「它」的页面带偏。解药是**查询改写（query rewriting）**：用 LLM 结合对话历史，把查询补全成「A100 的功耗是多少」再去检索。

**问题二：一个复杂查询要拆成多个。** 「对比 A100 和 H100 的功耗」在向量空间里是「一个混合语义」，一次检索往往只召回其中一边。应该拆成两个子查询分别检索，再把结果合并。这叫**查询分解（query decomposition）**。

**问题三：查询和答案的「语义鸿沟」。** 用户用问句提问（「怎么降低显卡功耗？」），而文档是陈述句（「限制功率上限可降低功耗」）。问句和陈述句在向量空间里可能离得远。这就是 **HyDE（Hypothetical Document Embeddings，假设性文档嵌入）**要解决的。

## 最小可运行演示（一）：查询改写与查询分解

先演示查询改写（治指代）和查询分解（治一问多意）。对照本章贯穿数据，你会看到：原始追问「它的功耗呢」被含「它」的干扰页带偏，改写后精准锁定 A100；复合问题只召回一边，分解后两边都召回。
```python
from collections import Counter
import math

docs = {
    "d_a100": "A100 的最大功耗为 400 瓦",
    "d_h100": "H100 的最大功耗为 700 瓦",
    "d_faq": "它的相关说明请查阅产品手册的对应章节",
}


def embed(t):
    return Counter(t)


def cosine(a, b):
    c = set(a) & set(b)
    d = sum(a[t] * b[t] for t in c)
    na = math.sqrt(sum(v * v for v in a.values()))
    nb = math.sqrt(sum(v * v for v in b.values()))
    return d / (na * nb) if na and nb else 0.0


def retrieve(q):
    best = max(docs, key=lambda k: cosine(embed(q), embed(docs[k])))
    return best, round(cosine(embed(q), embed(docs[best])), 3)


history = "用户: A100 是什么？ 助手: 它是英伟达数据中心 GPU。"  # 场景一：多轮对话指代消解（查询改写）
followup = "它的功耗呢"


def fake_llm_rewrite(history, q):
    """真实场景调 LLM 结合历史补全指代，这里用模板模拟。"""
    return "A100 的功耗是多少"


rewritten = fake_llm_rewrite(history, followup)
print("== 查询改写（指代消解）==")
print(f"原始追问『{followup}』-> 命中 {retrieve(followup)}（被含『它』的干扰句带偏）")
print(f"改写后『{rewritten}』-> 命中 {retrieve(rewritten)}（精准锁定 A100）")

compound = "对比 A100 和 H100 的功耗"  # 场景二：复杂查询分解


def fake_llm_decompose(q):
    return ["A100 的功耗是多少", "H100 的功耗是多少"]


print("\n== 查询分解（复杂问题拆子查询）==")
print(f"复合问题『{compound}』-> 命中 {retrieve(compound)}（一次只能召回一个，另一个漏了）")
for s in fake_llm_decompose(compound):
    print(f"子查询『{s}』-> 命中 {retrieve(s)}")
```
保存为 `query_rewrite.py`，运行 `python query_rewrite.py`。预期输出：
```text
== 查询改写（指代消解）==
原始追问『它的功耗呢』-> 命中 ('d_faq', 0.3)（被含『它』的干扰句带偏）
改写后『A100 的功耗是多少』-> 命中 ('d_a100', 0.75)（精准锁定 A100）

== 查询分解（复杂问题拆子查询）==
复合问题『对比 A100 和 H100 的功耗』-> 命中 ('d_a100', 0.866)（一次只能召回一个，另一个漏了）
子查询『A100 的功耗是多少』-> 命中 ('d_a100', 0.75)
子查询『H100 的功耗是多少』-> 命中 ('d_h100', 0.75)
```
逐行讲解：

- **查询改写**：原始追问「它的功耗呢」和含「它」的废话页 `d_faq` 相似度 0.3，反而高于真答案，命中被带偏；LLM 结合历史把它补成「A100 的功耗是多少」，相似度 0.75 精准命中 `d_a100`。真实场景 `fake_llm_rewrite` 是一次 LLM 调用（输入对话历史 + 当前问，输出补全指代的独立问题）。
- **查询分解**：复合问题「对比 A100 和 H100 的功耗」虽然和 `d_a100` 相似度高达 0.866，但**一次检索只能返回一个 top-1**，H100 那篇就漏了；拆成两个子查询后，A100 和 H100 各自被精准召回，合并才能支撑「对比」。

## 最小可运行演示（二）：HyDE

HyDE 的核心思路是：**先让 LLM 根据问句「编」一个假想答案，再用这个假想答案的向量去检索。** 因为「答案找答案」比「问句找答案」在向量空间里对齐得更好。
```text
HyDE 的核心思路：

朴素做法：  用"问句"的向量去检索"答案句"  ← 问句和答案句语义空间有鸿沟
                │
HyDE 做法： 先让 LLM 根据问句"编"一个假想答案
           "怎么降低显卡功耗？"──LLM──▶"可以通过限制功率上限、降低核心频率来降低功耗……"
                │
           用这个"假想答案"的向量去检索  ← 答案对答案，语义空间对齐！
                │
           假想答案可能有事实错误没关系——只用它的向量去"找相似的真答案"
```
```python
from collections import Counter
import math

docs = [
    "限制功率上限并降低核心频率可以有效降低显卡功耗",
    "显卡的散热风扇转速可以手动调节",
    "深度学习框架支持多卡并行训练",
]


def embed(t):
    return Counter(t)


def cosine(a, b):
    c = set(a) & set(b)
    d = sum(a[t] * b[t] for t in c)
    na = math.sqrt(sum(v * v for v in a.values()))
    nb = math.sqrt(sum(v * v for v in b.values()))
    return d / (na * nb) if na and nb else 0.0


query = "怎么降低显卡功耗"

naive_top = max(docs, key=lambda d: cosine(embed(query), embed(d)))  # ① 朴素：直接用问句检索


def fake_llm_hypothetical_answer(q):  # ② HyDE：先让 LLM 生成一个"假想答案"（这里用模板模拟）
    return "降低显卡功耗可以通过限制功率上限、降低核心频率等方式实现"


hyde_doc = fake_llm_hypothetical_answer(query)
hyde_top = max(docs, key=lambda d: cosine(embed(hyde_doc), embed(d)))  # ③ 用假想答案检索

print("问句直接检索命中:", naive_top)
print("HyDE 假想答案检索命中:", hyde_top)
print("问句 vs 答案句相似度:", round(cosine(embed(query), embed(docs[0])), 3))
print("假想答案 vs 答案句相似度:", round(cosine(embed(hyde_doc), embed(docs[0])), 3))
```
保存为 `hyde.py`，运行 `python hyde.py`。预期输出：
```text
问句直接检索命中: 限制功率上限并降低核心频率可以有效降低显卡功耗
HyDE 假想答案检索命中: 限制功率上限并降低核心频率可以有效降低显卡功耗
问句 vs 答案句相似度: 0.554
假想答案 vs 答案句相似度: 0.847
```
逐行讲解：

- **标注 ①**：朴素做法用问句「怎么降低显卡功耗」直接检索。这个例子里它也命中了正确文档，但注意最后两行——**问句和答案句的相似度只有 0.554**。
- **标注 ②③**：HyDE 先调 LLM 生成假想答案（陈述句形态，和文档同构），再用它的向量检索。**假想答案和答案句的相似度飙到 0.847**。

**关键观察**：HyDE 的价值不在于「改变命中了谁」（本例两者都命中对了），而在于**把相关度的「区分度」从 0.554 拉高到 0.847**。在真实的百万级库里，0.554 的相似度可能被一堆 0.5+ 的噪声淹没、排不进 top-k；而 0.847 能让真答案在候选里显著突出、稳定进 top-k。这就是「答案找答案」相比「问句找答案」的对齐优势——它把真答案在向量空间里「拉近」了。

## 深入：HyDE 的假想答案编错了会不会带偏检索？

HyDE 最反直觉、面试最爱问的一点：**假想答案是 LLM 现编的，万一它编错了数字（比如说「显卡功耗 50 瓦」），检索不会被带偏吗？**

答案是不会，因为 **HyDE 用的是假想答案的「向量」，不是假想答案的「内容」**。HyDE 原论文《Precise Zero-Shot Dense Retrieval without Relevance Labels》的核心洞察就是：假想答案哪怕事实错误，它在向量空间里的**落点**大致是对的（都是「关于降低功耗的陈述」），用这个落点去找语义相近的**真实文档**，照样能召回正确的原文 [来源](https://arxiv.org/abs/2212.10496)。最终塞给生成模型的是**检索回来的真实原文**，不是那个假想答案——假想答案在召回完成后就被丢弃了。所以：
```text
HyDE 的"用向量不用内容"：

假想答案(可能数字编错) ──▶ 只取它的向量 ──▶ 找相似的真实文档
                              │                    │
                        内容被丢弃            真实文档进 prompt
                        (不进 prompt)         (事实以真实文档为准)
```
这也划定了 HyDE 的适用边界：它救的是「问句和文档语义鸿沟大」的召回问题；如果你的库里**根本没有**相关真实文档，HyDE 编得再像也召不回不存在的东西。而且 HyDE 的代价是**每次查询多一次 LLM 调用**（生成假想答案），延迟和成本上升。所以它适合「语义鸿沟大、且对召回质量要求高」的场景，不是无脑全用。

## 真实系统对应

**官方公开机制**：HyDE 出自 CMU / 滑铁卢大学的论文，是有正式发表、被广泛复现的方法 [来源](https://arxiv.org/abs/2212.10496)；LangChain、LlamaIndex 都提供了 HyDE、查询改写、查询分解（sub-question / multi-query）的现成组件 [来源](https://python.langchain.com/docs/how_to/#query-analysis)。2026 年的实践里，查询改写在多轮对话 RAG 里几乎是标配。**通用工程模式**：结合历史补指代、把复合问题拆子查询分别检索再合并、用假想答案对齐「答案找答案」，都是可迁移到任何系统的做法。**教学参考实现**：上面的 `fake_llm_rewrite` / `fake_llm_decompose` / `fake_llm_hypothetical_answer` 都用确定性模板模拟 LLM，真实场景各是一次 LLM 调用。

需要点明边界：查询改写 / 分解 / HyDE 都要多花 LLM 调用（延迟 + 成本），且改写本身可能出错（把指代补错、把问题拆歪）。这些优化都要用评估集（见 26.6）验证净收益，而不是无脑叠加——叠得越多，延迟越高、出错环节越多。

## 生产踩坑

| 症状 | 根因 | 如何观测与复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|

## 思考：HyDE 让 LLM 编的假想答案如果事实错误，为什么不会把最终答案带偏？

### 回答

因为 HyDE 只用假想答案的**向量**去找相似的**真实文档**，最终塞给生成模型的是检索回来的真实原文，不是那个假想答案。关键在于「用向量、不用内容」：假想答案哪怕把数字编错了（比如说「功耗 50 瓦」），它在向量空间里的**落点**大致还是对的——都是「一段关于降低显卡功耗的陈述句」，和真答案「限制功率上限降低功耗」在语义空间里靠得很近。用这个落点去检索，照样能召回正确的真实文档。而假想答案在召回完成的那一刻就被丢弃了，它从不进入生成 prompt，所以它的事实错误影响不到最终答案的正确性——最终答案的事实依据完全来自检索回来的真实原文。HyDE 的整个价值就是「借假想答案在向量空间里的位置，实现答案对答案的对齐」，因为「答案找答案」比「问句找答案」对齐得好，能把真答案在候选里的区分度显著拉高。当然它有边界：如果库里根本没有相关真实文档，HyDE 编得再像也召不回不存在的东西。

### 面试精简表达

HyDE 只用假想答案的向量去找相似真实文档，真原文才进 prompt，假想答案召回后即丢弃；数字编错只影响向量落点、落点大致仍对，故不带偏最终答案。

## 思考：查询改写、查询分解、HyDE 三者分别治什么病？该怎么选？

### 回答

三者对应三类不同的查询问题。查询改写治**多轮指代**：追问里「它 / 这个 / 上面那个」这类指代词，直接拿去检索会丢失指代对象甚至被别的含指代词的页面带偏，用 LLM 结合对话历史把指代补全成完整实体名（「它的功耗呢」→「A100 的功耗是多少」）再检索。查询分解治**一问多意**：像「对比 A 和 B」这种复合问题，在向量空间里是一个混合语义，一次检索往往只召回一边，要拆成多个子查询分别检索再合并结果。HyDE 治**语义鸿沟**：用户用问句提问、文档是陈述句，两者在向量空间里离得远，用 LLM 先生成一个陈述句形态的假想答案，用它的向量实现「答案找答案」的对齐。怎么选？看你的失败模式——多轮对话场景优先上查询改写（几乎是标配）；有大量对比 / 多跳问题就加查询分解；问句和文档用词差异大、召回区分度低就上 HyDE。三者可以叠加，但每一招都多一次 LLM 调用（增延迟和成本），也各自有出错风险，所以要用评估集测净收益、按需启用，而不是无脑全上——简单问题直接检索就好，别为它套三层优化。

### 面试精简表达

改写治多轮指代、分解治一问多意、HyDE 治问句-文档语义鸿沟；按失败模式选，多轮必上改写，对比问上分解，鸿沟大上 HyDE，每招多一次 LLM 调用，需评估集验证净收益、按需启用。
