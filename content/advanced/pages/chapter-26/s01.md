## 真实问题

一家做技术文档问答的团队上线两周后收到大量投诉：问「A100 的最大功耗」，系统召回的块是「……适合大规模训练。A100 的最大功耗为」——正好在「为」字后面被切断了，「400 瓦」这三个字落在了下一个块里，而下一个块的开头是「400 瓦。此外 A100 还支持……」。检索命中了前半句，模型看到的却是「A100 的最大功耗为」这个没有数字的残句，于是照旧编了个数。

排查发现根因在**分块**：他们用最朴素的「按 500 字硬切」，把一句完整的「A100 的最大功耗为 400 瓦」拦腰截成两段。更糟的是知识库里的规格表格也被机械切断，检索到的永远是「半张表」。这一节要讲清：分块不是「把长文切短」这么简单，它决定了检索管线的下限——**切坏了，后面 embedding 再强、rerank 再准都白搭。**

## 原理：让检索粒度和生成粒度解耦

第 5 章讲过「固定大小 + 重叠」的基础分块。生产环境里的进阶策略，核心目标只有一个：**让「用来检索的粒度」和「喂给生成的粒度」解耦。** 为什么要解耦？因为这两者的最优粒度天然冲突：

- **检索想要小块**：块越小，语义越聚焦，「A100 功耗多少瓦」这类查询越容易精准命中「A100 的最大功耗为 400 瓦」这一句，不会被整段的其他信息稀释。
- **生成想要大块**：模型作答需要完整上下文——只给它「400 瓦」这一句，它不知道这是谁的功耗、是最大值还是典型值。

| 分块策略 | 做法 | 适合场景 | 代价 |
|---|---|---|---|
| 固定大小 + 重叠 | 按字数硬切，相邻块留重叠 | 通用、实现最简单 | 可能切断语义单元、腰斩表格 |
| 语义分块 | 按标题 / 段落 / 句子边界切 | 结构化文档（Markdown、法条） | 需解析文档结构 |
| 父子块 small-to-big | 小块检索，命中后返回所属大块 | 既要命中准又要上下文全 | 存储与实现更复杂 |
| 句子窗口 | 按句检索，返回命中句 ± N 句 | 问答精度要求极高 | 需维护句子位置索引 |
| Contextual Retrieval | 入库前给每块 prepend 一段 LLM 生成的上下文 | 块脱离原文就丢失指代的长文档 | 每块多一次 LLM 调用（可缓存） |

其中**父子块（parent-document retrieval，又称 small-to-big）**是解决「检索精度 vs 上下文完整」这对矛盾的经典招式。它的直觉是：
```text
父子块检索的直觉：

离线：大块(父) ──切成──▶ 小块(子)，子块单独 embedding 入库
                          子块记录「我属于哪个父块」

在线：用查询检索 ──▶ 命中某个小块(精准) ──▶ 返回它所属的大块(完整)
      └─ 小块保证「命中准」，大块保证「上下文全」
```
## 最小可运行演示

下面用零依赖的玩具 embedding 演示父子块的核心逻辑：子块负责精准命中，父块负责完整上下文。对照本章贯穿数据——查询「A100 功耗多少瓦」应精准命中「A100 的最大功耗为 400 瓦」那句子块，但返回的是它所属的整个父块。
```python
from collections import Counter
import math


def embed(text: str) -> Counter:
    """玩具 embedding：字频向量（零依赖可跑，演示用）。"""
    return Counter(text)


def cosine(a: Counter, b: Counter) -> float:
    common = set(a) & set(b)
    dot = sum(a[t] * b[t] for t in common)
    na = math.sqrt(sum(v * v for v in a.values()))
    nb = math.sqrt(sum(v * v for v in b.values()))
    return dot / (na * nb) if na and nb else 0.0


parent_docs = {  # ① 父文档，切成子块，子块记住 parent_id
    "p1": "A100 是英伟达数据中心 GPU。A100 的最大功耗为 400 瓦。A100 适合大规模训练。",
    "p2": "H100 是新一代 GPU。H100 的最大功耗为 700 瓦。H100 带宽显著提升。",
}
children = []  # [(child_text, parent_id, 向量), ...]
for pid, doc in parent_docs.items():
    for sent in doc.split("。"):
        sent = sent.strip()
        if sent:
            children.append((sent, pid, embed(sent)))  # ② 子块单独 embedding


def parent_retrieve(query: str):
    q = embed(query)
    # ③ 先用子块检索，找最相关的子块
    scored = [(cosine(q, vec), text, pid) for text, pid, vec in children]
    scored.sort(reverse=True)
    best_score, best_child, best_parent = scored[0]
    # ④ 返回命中子块所属的完整父块
    return best_child, parent_docs[best_parent], best_score


child, parent, score = parent_retrieve("A100 功耗多少瓦")
print(f"命中子块（精准）: {child}")
print(f"返回父块（完整）: {parent}")
print(f"相似度: {score:.3f}")
```
保存为 `parent_child.py`，运行 `python parent_child.py`。预期输出：
```text
命中子块（精准）: A100 的最大功耗为 400 瓦
返回父块（完整）: A100 是英伟达数据中心 GPU。A100 的最大功耗为 400 瓦。A100 适合大规模训练。
相似度: 0.781
```
逐行讲解：

- **标注 ①②**：父文档按句切成子块，每个子块记住自己的 `parent_id` 并单独 embedding 入库。子块短、语义聚焦，检索命中更准。
- **标注 ③**：查询只和「子块」比相似度。子块短，「A100 功耗多少瓦」能精准命中「A100 的最大功耗为 400 瓦」，不会被整段其他信息稀释。
- **标注 ④**：命中子块后，返回的不是这一句，而是它所属的**整个父块**——模型既拿到精准命中，又拿到「A100 是数据中心 GPU + 400 瓦 + 适合训练」的完整上下文。

这就是父子块的威力：**检索粒度和生成粒度各自最优。** 运行结果里，查询精准命中了「400 瓦」那句，但返回的是 p1 的完整三句。

## 深入：Contextual Retrieval——给每块补回它丢掉的上下文

父子块解决的是「返回时补上下文」，但还有一个更隐蔽的问题：**块在 embedding 那一刻就已经丢了上下文。** 一个块写着「它的最大功耗为 400 瓦」，「它」指代谁？脱离原文，这个块连自己在讲 A100 都不知道，embedding 自然编不出正确语义。

Anthropic 在 2024 年提出的 **Contextual Retrieval（上下文检索）**正是治这个病 [来源](https://www.anthropic.com/news/contextual-retrieval)：**在给每个块做 embedding 之前，先用 LLM 生成一段 50–100 token 的「上下文前缀」**，说明「这个块出自哪篇文档、在讲什么」，把前缀拼到块前面再 embedding 和建 BM25 索引。它包含两个子技术——Contextual Embeddings（上下文嵌入）和 Contextual BM25（上下文关键词索引）。据 Anthropic 官方 cookbook 的实验，这个方法把 top-20 召回失败率降低了约 49%，**再叠加 rerank 后最多降低 67%** [来源](https://platform.claude.com/cookbook/capabilities-contextual-embeddings-guide)。
```text
Contextual Retrieval 的核心动作：

原始块：  "它的最大功耗为 400 瓦"          ← "它"指代谁？脱离原文丢失语义
              │
              ▼ 离线：用 LLM 生成上下文前缀（可 prompt 缓存降本）
上下文块："本段出自英伟达 A100 数据中心 GPU 规格手册的功耗章节。它的最大功耗为 400 瓦"
              │
              ▼ 用「上下文块」做 embedding + 建 BM25 索引
        检索时「A100 功耗」既能语义命中也能关键词命中
```
下面用规则模板模拟「LLM 生成上下文前缀」，演示加前缀前后检索命中的差异（真实场景是一次 LLM 调用，这里用确定性模板让输出可复核）：
```python
from collections import Counter
import math


def embed(t):
    return Counter(t)


def cosine(a, b):
    c = set(a) & set(b)
    d = sum(a[t] * b[t] for t in c)
    na = math.sqrt(sum(v * v for v in a.values()))
    nb = math.sqrt(sum(v * v for v in b.values()))
    return d / (na * nb) if na and nb else 0.0


raw_chunks = ["它的最大功耗为 400 瓦", "它带宽显著提升适合大模型训练"]
context_prefix = {  # ① 模拟「LLM 根据全文给每块生成上下文前缀」，真实场景是一次 LLM 调用
    "它的最大功耗为 400 瓦": "本段出自英伟达 A100 数据中心 GPU 规格手册。",
    "它带宽显著提升适合大模型训练": "本段出自英伟达 H100 数据中心 GPU 规格手册。",
}
contextual_chunks = [context_prefix[c] + c for c in raw_chunks]  # ② 上下文块=前缀+原块，用它 embedding

query = "A100 功耗多少瓦"
q = embed(query)
naive = max(raw_chunks, key=lambda c: cosine(q, embed(c)))
contextual = max(contextual_chunks, key=lambda c: cosine(q, embed(c)))
print("朴素块检索命中：", naive)
print("上下文块检索命中：", contextual)
```
保存为 `contextual_retrieval.py`，运行 `python contextual_retrieval.py`。预期输出：
```text
朴素块检索命中： 它的最大功耗为 400 瓦
上下文块检索命中： 本段出自英伟达 A100 数据中心 GPU 规格手册。它的最大功耗为 400 瓦
```
逐行讲解：

- **标注 ①**：真实做法是把「整篇文档 + 这个块」一起发给 LLM，让它写一句「这个块在讲什么、出自哪」。Anthropic 建议把整篇文档放进 prompt 缓存（prompt cache）里复用，这样给同一文档的几十个块生成前缀时，文档部分只算一次输入成本 [来源](https://www.anthropic.com/news/contextual-retrieval)。
- **标注 ②**：注意朴素块里根本没有「A100」三个字（只有「它」），query 里的「A100」在朴素块上无从匹配；加了上下文前缀后，「A100」进了块，无论走向量还是 BM25 都能命中。这就是 Contextual Retrieval 把召回失败率大幅降低的机制来源。

## 真实系统对应

**官方公开机制**：Anthropic 的 Contextual Retrieval 是有官方博客与 cookbook 支撑的具体方法，明确给出「Contextual Embeddings + Contextual BM25 + Rerank」的组合与量化收益 [来源](https://www.anthropic.com/news/contextual-retrieval) [来源](https://platform.claude.com/cookbook/capabilities-contextual-embeddings-guide)。LangChain 公开了 `ParentDocumentRetriever` 实现父子块检索，思路与本节一致：小块索引、大块返回 [来源](https://python.langchain.com/docs/how_to/parent_document_retriever/)。**通用工程模式**：语义分块（按 Markdown 标题、句子边界切）、句子窗口、对表格 / 代码块整段保留，都是可迁移到任何向量库的做法。**教学参考实现**：上面的字频 embedding 和模板生成的上下文前缀仅为让输出可逐字复核，真实系统请用专业 embedding 模型和真实 LLM。

需要点明边界：Contextual Retrieval 的收益依赖「文档确实存在跨块指代 / 上下文丢失」这个前提。如果你的文档本身每块就语义自洽（如 FAQ 一问一答），加上下文前缀收益有限，还白白多花 LLM 成本。任何优化都要用评估集（见第 26.6 节）验证，而不是无脑全上。

## 生产踩坑

| 症状 | 根因 | 如何观测与复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| 召回块缺头少尾看不懂 | 按固定字数硬切断句 | 打印召回块看是否半句 | 语义分块 / 句子边界切 / 加重叠 | 纯流水线日志等无语义结构文本 |
| 检索到「半张表」「半段代码」 | 表格 / 代码块被机械切断 | 对含表格文档切分后目视检查 | 表格代码整段保留或按结构切 | 无结构化内容的纯散文 |
| 块脱离原文丢失指代 | 块里全是「它 / 该产品」等指代词 | 单独读块无法判断在讲谁 | Contextual Retrieval 加上下文前缀 | 每块本就自洽的 FAQ |
| 命中准但上下文不全 | 只返回命中的小块 | 模型答「缺少背景无法回答」 | 父子块：小块检索大块返回 | 答案就是一句话的场景 |
| Contextual 前缀成本爆炸 | 每块单独把全文发给 LLM | 统计 embedding 阶段 token 消耗 | 全文放 prompt 缓存复用 | 文档极短时提升不明显 |
| 块太大触发中间遗忘 | 父块设得过大塞满窗口 | 观测长上下文下答案质量下降 | 父块大小设上限、配合压缩 | 短文档不受影响 |

## 思考：父子块检索是怎么同时兼顾「检索精准」和「上下文完整」的？

### 回答

它把「检索」和「返回」拆成了两个不同粒度的对象。检索阶段用**小块（子块）**：小块短、语义单一，查询和它比相似度时不会被无关信息稀释，所以命中率高、噪声小——这解决「精准」。返回阶段用小块所属的**大块（父块）**：父块保留了完整的背景、指代对象、前后文，模型据此作答不会「只见树木不见森林」——这解决「完整」。关键在于「子块记录 parent_id」这条映射，让系统能从「命中的小块」一步跳到「它所属的大块」。本质上这是「解耦」思想：检索粒度和生成粒度本来最优值就不同，硬用一个粒度必然顾此失彼，父子块用两套粒度 + 一条映射同时吃到两头的好处。

### 面试精简表达

小块索引保证命中准、大块返回保证上下文全，靠 `parent_id` 映射把两者连起来——检索粒度和生成粒度各自最优。

## 思考：为什么说「换更强的 embedding 都救不了坏分块」？

### 回答

因为分块是检索管线的**输入端**，它决定了「向量库里到底存了什么」。如果一句「A100 的最大功耗为 400 瓦」被切成「A100 的最大功耗为」和「400 瓦。此外……」两个块，那么无论 embedding 模型多强，它能编码的也只是这两个残缺块——「400 瓦」这个数字所在的块开头是「400 瓦」这个孤立数字，缺少「A100 功耗」的语境，语义落点会很奇怪；而含「A100 的最大功耗为」的块又没有数字。embedding 再强也无法把「本不在同一个块里的信息」拼回来。这就是「天花板由最短的板决定」在分块环节的体现：坏分块直接压低了整条管线的上限，后面所有优化都是在这个被压低的上限之下修修补补。正确顺序是先保证分块把语义单元、表格、代码完整保留，再谈 embedding 选型。

### 面试精简表达

分块决定向量库里存的是完整语义还是残句，embedding 无法还原本就被切断的信息；坏分块压低整条管线上限，必须先修分块再换模型。
