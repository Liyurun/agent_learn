## 真实问题

回到本章开头「A100 功耗 400 瓦」那次故障。团队把前六节的优化全上了——分块修好、换了合适 embedding、混合检索 + rerank、查询改写、评估集也攒起来了，通用问答准确率从 60% 提到 90%。但一类问题始终答不好：**多跳、对比、需要多轮检索**的复杂问题。比如「A100 和 H100 哪个更省电，省多少？」——这需要先分别查到两者功耗、再做减法比较，而传统 RAG 是「一次检索、一次生成」的**单趟流水线**，它拿原始问题去检索，往往只召回一边，然后基于半份资料硬答。

问题的本质是：**传统 RAG 把检索当成一次性的、被动的动作**——用户问什么就检索什么，检索完就必须生成，中间没有「我信息够不够、要不要再查一次、换个查法」的判断。**Agentic RAG（智能体检索增强生成）**正是把检索从「一次性动作」升级成「Agent 可以反复决策、迭代执行的工具」。这一节讲清 Agentic RAG 相比传统 RAG 强在哪、代价是什么、怎么防它陷入无限检索烧钱，并给出一张覆盖全章的生产建议清单收口。

## 原理：从「单趟流水线」到「带自检的检索循环」

传统 RAG 和 Agentic RAG 的根本差异，在于**检索是不是一个可以被反复决策的动作**：
```text
传统 RAG（单趟、被动）：
  问题 ──▶ 检索一次 ──▶ 拿到上下文 ──▶ 生成 ──▶ 结束
         （问什么查什么，查完必须答，没有"够不够"的判断）

Agentic RAG（循环、主动）：
  问题 ──▶ [Agent 决策]──▶ 检索 ──▶ 自检：信息够吗？
             ▲                          │
             │            不够：改写/分解/换库，再检索一次
             └──────────────────────────┘
                          够了 ──▶ 生成 ──▶ 结束
             （检索是 Agent 手里的工具，可反复调用、动态换策略）
```
对照第 9 章讲过的 Agent 循环，你会发现 Agentic RAG 本质上就是**把「检索」做成 Agent 的一个工具**，让第 8-9 章的「工具调用 + 循环 + 终止判断」那套机制作用在检索上。它带来三个传统 RAG 没有的能力 [来源](https://arxiv.org/abs/2501.09136)：

- **迭代检索**：一次不够就再查。第一次召回不理想，Agent 可以改写查询、换个说法、换个库再查一次，而不是拿着半份资料硬答。
- **查询分解与规划**：面对「对比 A 和 B」这类复杂问题，Agent 先把它拆成子问题分别检索，再综合（呼应第 26.5 节的查询分解，只是这里由 Agent 自主决定）。
- **充分性自检**：每次检索后，Agent 判断「现在的信息够不够回答」，不够就继续，够了才生成。这是传统 RAG 完全没有的一环。

代价也很实在：**每多一次检索 / 决策就多一次（甚至多次）LLM 调用**，延迟和成本成倍上升；而且循环一旦没设好终止条件，Agent 可能陷入「查了又查、永远觉得不够」的无限检索，把 token 预算烧光。所以 Agentic RAG 的工程重点，除了「让它会迭代」，更在于「**给循环上兜底**」——这正好复用第 8 章「循环必须有 max_turns 兜底」的铁律。

## 最小可运行演示

下面用零依赖代码对比「传统 RAG 一次到位」和「Agentic RAG 迭代检索 + 充分性自检」。对照本章贯穿数据，复杂问题「对比 A100 和 H100 的功耗」在传统 RAG 下只召回一边，在 Agentic RAG 下被自主分解、迭代检索补齐两边——同时用 `max_steps` 兜底，演示「绝不无限检索」。
```python
from collections import Counter
import math

docs = {
    "d_a100": "A100 的最大功耗为 400 瓦",
    "d_h100": "H100 的最大功耗为 700 瓦",
    "d_noise": "显卡的散热与功耗管理很重要",
}


def embed(t):
    return Counter(t)


def cosine(a, b):
    c = set(a) & set(b)
    d = sum(a[t] * b[t] for t in c)
    na = math.sqrt(sum(v * v for v in a.values()))
    nb = math.sqrt(sum(v * v for v in b.values()))
    return d / (na * nb) if na and nb else 0.0


def retrieve(q, k=1):
    ranked = sorted(docs, key=lambda i: cosine(embed(q), embed(docs[i])), reverse=True)
    return ranked[:k]


def has_number(doc_ids):
    return any(any(c.isdigit() for c in docs[d]) for d in doc_ids)


def agentic_rag(question, max_steps=3):
    """迭代检索 + 充分性自检 + 分解，带 max_steps 兜底防死循环。"""
    collected, step, plan = [], 0, [question]
    while plan and step < max_steps:                 # 循环必须有上限（第 8 章铁律）
        step += 1
        sub = plan.pop(0)
        hit = retrieve(sub, k=1)
        collected += hit
        print(f"  第{step}步 子问题『{sub}』-> 检索 {hit}")
        if question.startswith("对比") and step == 1:  # 自检：对比类信息不足则分解补检
            plan += ["A100 功耗多少瓦", "H100 功耗多少瓦"]
            print("    自检：对比类问题信息不足 -> 分解为子查询继续检索")
    collected = list(dict.fromkeys(collected))       # 去重保序
    return collected, has_number(collected), step


q = "对比 A100 和 H100 的功耗"
print("== 传统 RAG（一次到位）==")
print(f"  检索 {retrieve(q, k=1)} -> 只拿到一边，无法完成对比\n")

print("== Agentic RAG（迭代检索 + 自检）==")
ctx, enough, steps = agentic_rag(q, max_steps=3)
print(f"  收集到的上下文: {ctx}")
print(f"  信息是否充分: {enough}（两型号数字齐全）")
print(f"  实际检索步数: {steps}（max_steps=3 兜底，绝不无限检索）")
```
保存为 `agentic_rag.py`，运行 `python agentic_rag.py`。预期输出：
```text
== 传统 RAG（一次到位）==
  检索 ['d_a100'] -> 只拿到一边，无法完成对比

== Agentic RAG（迭代检索 + 自检）==
  第1步 子问题『对比 A100 和 H100 的功耗』-> 检索 ['d_a100']
    自检：对比类问题信息不足 -> 分解为子查询继续检索
  第2步 子问题『A100 功耗多少瓦』-> 检索 ['d_a100']
  第3步 子问题『H100 功耗多少瓦』-> 检索 ['d_h100']
  收集到的上下文: ['d_a100', 'd_h100']
  信息是否充分: True（两型号数字齐全）
  实际检索步数: 3（max_steps=3 兜底，绝不无限检索）
```
逐行讲解：

- **传统 RAG**：拿原始复合问题「对比 A100 和 H100 的功耗」一次检索，只召回 `d_a100`——H100 那份压根没进上下文，模型只能基于半份资料硬答，这就是它答不好对比 / 多跳问题的结构性原因。
- **Agentic RAG**：第 1 步先直接检索，然后**自检发现「对比类问题只拿到一边、信息不足」**，于是自主把问题分解成两个子查询，第 2、3 步分别把 A100 和 H100 的数字补齐，最终两型号数字齐全、可以完成对比。
- **关键的兜底**：`while plan and step < max_steps` 里的 `max_steps=3` 是命门。真实 Agent 判断「信息够不够」靠的是 LLM，而 LLM 可能永远觉得「还能再查查」，若没有这个硬上限，就会陷入无限检索烧光预算。**会迭代是能力，能停下来是工程**——这正是第 8 章「循环必须有 max_turns 兜底」在检索场景的复用。

## 深入：Agentic RAG 不是银弹，别为简单问题套复杂流程

Agentic RAG 强大，但它的每一份强大都用**延迟和成本**买单。一个只需要一次检索就能答的简单事实问题（「A100 功耗多少瓦」），如果也走「决策→检索→自检→再决策」的完整循环，就是拿三五次 LLM 调用去做本该一次搞定的事——用户多等好几秒、成本翻几倍，质量却没提升。

所以 2026 年的务实架构不是「全都上 Agentic」，而是**分层路由**：先用一个轻量判断（甚至规则）识别问题复杂度，简单事实问题走「传统 RAG 快路」（一次检索一次生成），只有多跳 / 对比 / 需要澄清的复杂问题才走「Agentic 慢路」（迭代检索）。这和第 8 章「简单单步任务可不设循环」、以及「工具越加越多选择准确率越差、要收敛」的思路一脉相承——**复杂度要和问题匹配，不是越复杂越好**。
```text
分层路由（务实架构）：

问题 ──▶ [复杂度判断]
            │
   ├─ 简单事实类 ──▶ 传统 RAG 快路（一次检索→生成）  快、便宜
   └─ 多跳/对比/需澄清 ──▶ Agentic 慢路（迭代检索+自检）  慢、贵、能力强
```
同时，Agentic RAG 引入了传统 RAG 没有的新失败模式：迭代检索让每一步的错误会**累积传播**（第一步查歪，后面越走越偏）、上下文随迭代**膨胀**（呼应第 5 章「中间遗忘」和第 27 章「上下文工程」——查得越多塞得越满，反而稀释注意力）、以及循环控制不当的**成本失控**。这些都要靠评估集（第 26.6 节）量化「Agentic 相比传统到底净赚多少」，而不是因为「Agentic 听起来更先进」就无脑上。

## 真实系统对应

**官方公开机制**：Agentic RAG 有正式的综述论文系统梳理其范式（Naïve / Advanced / Modular / Agentic RAG）与迭代检索、规划、自检等特征 [来源](https://arxiv.org/abs/2501.09136)；LangGraph 等编排框架公开支持把「检索」做成图中的一个节点、配合条件边实现「检索→评估→再检索」的循环（具体 API 以当前官方文档为准）[来源](https://langchain-ai.github.io/langgraph/)；Anthropic《Building Effective Agents》强调「用最简单能work的方案，只在复杂度确有必要时才加 Agent」，与本节「分层路由、别为简单问题套复杂流程」一致 [来源](https://www.anthropic.com/engineering/building-effective-agents)。**通用工程模式**：把检索当工具、迭代 + 自检 + 分解、`max_steps` 兜底、简单快路 / 复杂慢路分层路由，都是可迁移到任何编排框架的做法。**教学参考实现**：上面的 `agentic_rag` 用规则模拟「自检与分解」，真实系统里这些判断由 LLM 做；「信息够不够」的自检也远比「有没有数字」复杂。

需要点明边界：Agentic RAG 的收益高度依赖问题类型——对简单事实问题它是净亏损（增延迟成本、不增质量）；它的迭代能力也不能凭空创造知识，库里没有的答案查多少次都查不到。是否值得上、慢路占比多少，必须用评估集在你自己的真实流量上量化。

## 思考：Agentic RAG 相比传统 RAG，本质区别是什么？它强在哪、代价是什么？

### 回答

本质区别是**检索是不是一个可以被反复决策的动作**。传统 RAG 是「单趟、被动」的流水线：拿原始问题检索一次，检索完就必须基于拿到的上下文生成，中间没有「信息够不够、要不要再查、换个查法」的判断——问什么查什么，查完必须答。Agentic RAG 把检索从「一次性动作」升级成「Agent 手里可以反复调用的工具」，于是多出三个能力：迭代检索（一次不够就改写 / 换库再查）、查询分解与规划（把「对比 A 和 B」这类复杂问题拆成子问题分别检索再综合）、充分性自检（每次检索后判断「够不够回答」，不够就继续、够了才生成）。它本质上就是把第 8-9 章的「工具调用 + 循环 + 终止判断」那套机制作用到检索上。强在能处理传统 RAG 搞不定的多跳、对比、需要多轮澄清的复杂问题。代价也很实在：每多一次检索 / 决策就多一次甚至多次 LLM 调用，延迟和成本成倍上升；还引入了新的失败模式——错误会随迭代累积传播、上下文随迭代膨胀稀释注意力、以及循环控制不当导致的无限检索烧钱。所以它不是银弹，简单事实问题用它反而是净亏损，务实做法是分层路由：简单问题走传统 RAG 快路，只有复杂问题才走 Agentic 慢路，并且必须用评估集量化慢路到底净赚多少。

### 面试精简表达

传统 RAG 是单趟被动的「查一次必须答」，Agentic RAG 把检索做成 Agent 可反复调用的工具，多出迭代检索、查询分解、充分性自检三能力；强在多跳 / 对比复杂问题，代价是成倍的延迟成本和错误累积 / 上下文膨胀 / 无限检索等新风险，因此要分层路由 + max_steps 兜底 + 评估集量化净收益。

## 思考：Agentic RAG 的检索循环怎么防止「查了又查、永远不停」把预算烧光？

### 回答

核心是记住第 8 章那条铁律——**会迭代是能力，能停下来才是工程**——并给循环上多重兜底。第一层也是最硬的一层：**设 `max_steps`（最大检索步数）硬上限**，无论 Agent 觉得「够不够」，到了上限就必须停下用现有信息作答。这是必须有的兜底，因为判断「信息够不够」靠的是 LLM，而 LLM 完全可能永远觉得「还能再查查」，没有硬上限就会无限循环。第二层是**成本 / token 预算上限**：累计消耗到阈值就中止，防止单个复杂查询拖垮整体成本。第三层是**进展检测**：如果连续几步检索都没带来新信息（召回的还是已有的文档、或自检状态没改善），就判定「陷入原地打转」，提前终止而不是耗到上限。第四层是**充分性判据要具体**：别让自检问一个笼统的「够了吗」，而是给出可判定的条件（比如「对比类问题需要集齐所有被比较对象的关键数字」），条件满足即停，避免因判据模糊而反复纠结。此外还要做好**分层路由**——简单问题根本不进循环（走传统 RAG 快路），从源头减少不必要的迭代。最后，所有这些参数（max_steps、预算、判据）都要用评估集调，找到「质量够用、成本可控」的平衡点，而不是拍脑袋设一个很大的上限了事。

### 面试精简表达

靠多重兜底：max_steps 硬上限（LLM 可能永远觉得不够，必须有硬闸）、token / 成本预算上限、连续无新信息就提前终止的进展检测、具体可判定的充分性判据，再加分层路由让简单问题不进循环，所有阈值用评估集调——会迭代是能力，能停下来是工程。
