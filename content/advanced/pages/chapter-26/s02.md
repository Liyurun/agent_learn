## 真实问题

一个团队想给 RAG 系统「升级」：把用了一年的旧 embedding 模型换成 MTEB（Massive Text Embedding Benchmark，大规模文本嵌入基准）榜单上分更高的新模型。他们改了配置、重启服务，只把「查询」这一侧换成了新模型，向量库里存量的几百万条向量没动。上线当晚，检索质量断崖式下跌，召回的结果「像随机抽的」，客服问答准确率从 82% 掉到 31%。回滚后一切正常。

事后定位：向量库里存的还是**旧模型**空间里的坐标，查询用**新模型**编码，两个模型的向量空间根本不可比——就像一个用经度纬度、一个用平面直角坐标，硬算「距离」得到的全是噪声。这一节讲 embedding 选型的四个维度、两个高频认知陷阱（对称 vs 非对称、维度不是越高越好），以及一条铁律：**换 embedding 模型必须全量重建索引。**

## 原理：选型看四个维度

embedding 模型把文本编码成向量，是检索质量的地基。选型别只盯着「参数量大 / 榜单分高」，要看四个维度：

| 维度 | 说明 | 实践建议 |
|---|---|---|
| 语言支持 | 中文 / 多语言场景需专门优化 | 中文场景选中文或多语言 embedding，别用纯英文模型 |
| 维度 dim | 向量维度，影响存储与检索速度 | 高维更能表达语义但更占空间；权衡召回与成本 |
| 最大输入长度 | 单次能编码的最长文本 | 必须 ≥ 你的块大小，否则超出部分被截断 |
| 领域适配 | 通用 vs 领域微调 | 专业领域（医疗 / 法律）可考虑领域微调或强通用模型 |

截至 2026 年，主流选择大致分三档（**具体名次与价格以当前官方文档和 MTEB 榜单为准**，会频繁变动）：OpenAI 的 `text-embedding-3-small`（1536 维，便宜）/ `text-embedding-3-large`（3072 维，质量更高）都支持用 `dimensions` 参数裁剪维度 [来源](https://platform.openai.com/docs/guides/embeddings)；Voyage、Cohere Embed v4、Qwen3-Embedding、Gemini-embedding 等在 MTEB 上互有高低 [来源](https://huggingface.co/spaces/mteb/leaderboard)。榜单只是起点——真正靠谱的做法是在**你自己的评估集**（见 26.6）上测，而不是照搬别人的榜单名次。

### 认知一：对称 vs 非对称检索，别用错类型

有的 embedding 模型是为「句子对句子」的**对称相似**训练的（判断两句话是不是一个意思），有的是为「短查询对长文档」的**非对称检索**训练的。RAG 属于后者——查询短、文档长，两者形态天然不对称。用错类型会明显掉点。很多模型为此要求给查询和文档**加不同的指令前缀**，例如查询加 `query:`、文档加 `passage:`（不同模型前缀不同，以其文档为准），漏加或加反都会掉分。
```text
非对称检索的前缀约定（示意，具体前缀以模型文档为准）：

入库： embed("passage: A100 的最大功耗为 400 瓦")  ──▶ 存进向量库
查询： embed("query: A100 功耗多少瓦")            ──▶ 拿去比相似度
       └─ 前缀让模型知道"这是查询 vs 这是文档"，用对齐的方式编码
```
### 认知二：维度不是越高越好，Matryoshka 让你滑动取舍

高维向量表达力强，但**存储成本和检索延迟都随维度近似线性上升**。100 万条向量，3072 维要存的浮点数是 768 维的 4 倍。现代很多 embedding 支持**套娃表示学习（Matryoshka Representation Learning，MRL）**：训练时让「前 N 维」自身就是一个可用的低维向量，于是你可以**截取前 N 维**在精度和成本之间平滑滑动——OpenAI 的 text-embedding-3 系列就用 `dimensions` 参数暴露了这个能力 [来源](https://platform.openai.com/docs/guides/embeddings)。

## 最小可运行演示

下面演示两件事：一是 Matryoshka 式「截断维度」——高维向量截短后重新归一化，检索排序基本不变但存储减半；二是「换模型必须重建索引」的坑——用不一致的编码方式查询，相似度彻底失真。为了零依赖、可复核，这里用一个确定性的哈希 embedding 模拟真实高维向量。
```python
import hashlib
import math


def embed(text: str, dim: int = 32) -> list[float]:
    """确定性哈希 embedding：把文本映射到 dim 维向量（教学用，模拟高维稠密向量）。"""
    vec = [0.0] * dim
    for token in text:
        h = int(hashlib.md5(token.encode()).hexdigest(), 16)
        vec[h % dim] += 1.0
    norm = math.sqrt(sum(v * v for v in vec))
    return [v / norm for v in vec] if norm else vec


def cosine(a: list[float], b: list[float]) -> float:
    n = min(len(a), len(b))
    dot = sum(a[i] * b[i] for i in range(n))
    na = math.sqrt(sum(a[i] * a[i] for i in range(n)))
    nb = math.sqrt(sum(b[i] * b[i] for i in range(n)))
    return dot / (na * nb) if na and nb else 0.0


docs = {
    "d0": "A100 是很热门的数据中心显卡型号",
    "d2": "A100 的最大功耗为 400 瓦",
    "d3": "深度学习训练会消耗大量电力",
}
query = "A100 功耗多少瓦"

full = {k: embed(query, 32) and cosine(embed(query, 32), embed(v, 32)) for k, v in docs.items()}  # ① 全维度(32)检索
rank_full = sorted(full, key=full.get, reverse=True)


def truncate(vec, n):  # ② Matryoshka：只用前 16 维（存储减半），重新算相似度
    head = vec[:n]
    norm = math.sqrt(sum(x * x for x in head))
    return [x / norm for x in head] if norm else head


q16 = truncate(embed(query, 32), 16)
half = {k: cosine(q16, truncate(embed(v, 32), 16)) for k, v in docs.items()}
rank_half = sorted(half, key=half.get, reverse=True)

print("全维度(32)排名:", rank_full)
print("截断到16维排名:", rank_half, "（存储减半，Top1 是否保持一致）")

mismatch = cosine(embed(query, 16), embed(docs["d2"], 32))  # ③ 换模型没重建索引：维度错配=空间不可比
print(f"维度错配时 d2 相似度: {mismatch:.3f}（对不齐，检索失真）")
```
保存为 `embedding_dim.py`，运行 `python embedding_dim.py`。预期输出（哈希稳定，可逐字复核）：
```text
全维度(32)排名: ['d2', 'd0', 'd3']
截断到16维排名: ['d2', 'd3', 'd0'] （存储减半，Top1 是否保持一致）
维度错配时 d2 相似度: 0.535（对不齐，检索失真）
```
逐行讲解：

- **标注 ①**：全 32 维检索，标准答案 d2 排第一。
- **标注 ②**：Matryoshka 截断到前 16 维、重新归一化后，**Top1 仍是 d2**——最关心的「命中答案」保持住了；但尾部 d0、d3 的次序发生了交换。这恰好演示了降维的真实取舍：**用一半存储换来的往往是「头部稳、尾部略抖」**，能不能接受要用评估集量化（真实 MRL 模型在这个截断上比玩具哈希向量稳定得多）。
- **标注 ③**：维度错配（库里 32 维、查询 16 维）时，`cosine` 只能比前 16 维，相似度被算成一个「看似有值其实无意义」的数——这正是「换模型 / 换维度没重建索引」时最危险的地方：**它不报错，只是悄悄给出错误的相似度**，让你误以为系统在正常工作。

## 深入：为什么「换模型必须重建索引」是硬约束

不同 embedding 模型（甚至同模型不同版本）学到的是**不同的向量空间**。同一句「A100 400 瓦」在模型 A 里可能落在坐标 `(0.1, 0.8, ...)`，在模型 B 里落在 `(0.7, -0.3, ...)`——两个坐标系的「轴」含义完全不同。相似度（余弦距离）只有在**同一个空间内**比较才有意义。
```text
换 embedding 模型的坑：

写入时用模型 A ──▶ 向量库里全是 A 空间的坐标
查询时用模型 B ──▶ B 空间的坐标
                    └─▶ 两个空间不可比！相似度计算完全失真
                        表现为"检索结果像随机的"，而且不报错
```
所以：**换 embedding 模型 = 整个向量库必须全量重新 embedding 重建。** 这不是「建议」，是数学上的硬约束。工程上要把「模型标识 + 版本 + 前缀策略」作为索引的元数据记录下来，查询时校验一致，避免开头那种「只换查询侧、不重建库」的事故。同理，前缀策略（`query:` / `passage:`）也必须写入和查询两侧完全一致。

## 真实系统对应

**官方公开机制**：OpenAI 文档明确 `text-embedding-3-small/large` 支持 `dimensions` 参数缩短向量维度，并说明缩短后仍保留语义能力（Matryoshka 特性）[来源](https://platform.openai.com/docs/guides/embeddings)；MTEB 是社区公认的 embedding 评测基准，榜单持续更新 [来源](https://huggingface.co/spaces/mteb/leaderboard)。**通用工程模式**：非对称检索的查询 / 文档前缀、把模型标识写进索引元数据、换模型全量重建、在自有评估集上选型，都是可迁移到任何厂商的做法。**教学参考实现**：上面的哈希 embedding 只为让输出可复核，不代表任何真实模型的语义能力；真实向量维度是几百到几千维。

需要点明边界：具体哪个模型「最好」高度依赖你的语言、领域、块大小和预算，没有普适答案；MTEB 榜单名次只反映平均表现，不保证在你的数据上最优。价格、维度上限、最大输入长度都会变，务必以当前官方文档为准。

## 生产踩坑

| 症状 | 根因 | 如何观测与复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| 换模型后检索像随机 | 换 embedding 没重建索引 | 新模型查询旧向量库比相似度 | 换模型全量重新 embedding 重建 | 同版本兼容升级厂商保证时例外 |
| 中文检索普遍偏差 | 用了纯英文 embedding | 对中文查询看召回相关性 | 选中文 / 多语言 embedding | 纯英文语料无此问题 |
| 长块被静默截断 | 块长超过模型最大输入 | 打印被编码文本长度对比上限 | 块大小 ≤ 模型最大输入长度 | 短块场景不触发 |
| 掉分找不到原因 | 漏加 / 加反查询文档前缀 | 对比加前缀前后召回质量 | 严格按模型文档统一前缀策略 | 不要求前缀的模型除外 |
| 存储与延迟暴涨 | 盲目用最高维度 | 统计向量库体积与检索 P99 | Matryoshka 截断到够用维度 | 召回质量对维度敏感时慎降 |
| 选型照搬别人榜单翻车 | 未在自有数据上评测 | 榜单第一在你数据上反而差 | 用自有评估集选型 | 与榜单数据分布高度一致时可参考 |

## 思考：换了个 MTEB 榜单更高的 embedding 模型后线上崩了，最可能的原因是什么？

### 回答

十有八九是**没重建索引**。老向量库里存的还是旧模型编码出来的向量，你只把「查询」这一侧换成了新模型，于是查询向量在新模型空间、库里向量在旧模型空间，两个空间的坐标轴含义完全不同，余弦相似度算出来是无意义的噪声，表现就是「检索结果像随机抽的」。而且这个错误最阴险的地方在于**它不报错**——相似度还是能算出一个 0 到 1 的数，系统看起来在正常运行，只是结果全错。正确做法是：换 embedding 模型必须把知识库里所有文本用新模型全量重新 embedding、重建向量索引，并把「模型标识 + 版本 + 前缀策略」作为索引元数据记录，查询时校验一致。次要可能性还有：新模型要求的查询 / 文档前缀没加或加反、新模型是对称相似而非非对称检索训练的、最大输入长度变短导致长块被截断——但「没重建索引」是最常见、最致命的那个。

### 面试精简表达

换 embedding 没重建索引：新查询在新空间、旧向量在旧空间，两空间不可比，相似度变噪声且不报错；换模型必须全量重建并校验索引元数据。

## 思考：向量维度是不是越高越好？什么时候该主动降维？

### 回答

不是越高越好，要在「表达力」和「存储 / 延迟成本」之间权衡。高维向量确实能承载更细的语义差别，但存储成本和检索延迟都随维度近似线性上升——100 万条向量，3072 维要存的浮点数是 768 维的 4 倍，ANN（Approximate Nearest Neighbor，近似最近邻）索引的内存和查询耗时也相应变大。什么时候该主动降维？当你的召回质量对维度不敏感（用评估集测出「截到一半维度，召回率几乎不掉」）、而存储 / 延迟 / 成本压力大时，就该降。现代 Matryoshka 表示学习让这件事变得平滑安全：模型训练时保证「前 N 维自身就是可用向量」，你可以直接截取前 N 维、重新归一化，在精度和成本之间滑动，而不用换模型或重训。务实的流程是：先用完整维度建一版基线，再用评估集测「截到 1/2、1/4 维度时召回率掉多少」，找到「质量可接受、成本最低」的那个点。切记降维也是「改变了向量」，同样要保证写入和查询两侧维度一致。

### 面试精简表达

不是越高越好，高维换来的表达力要用线性增长的存储和延迟买单；用评估集测降维后召回掉多少，Matryoshka 可安全截断前 N 维在精度与成本间滑动，写入查询维度必须一致。
