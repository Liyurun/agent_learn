## 真实问题

一个法律文书 RAG 系统，把召回 top-k 从 3 调到 10 想「多召点、别漏」，结果准确率不升反降。抽样一看：召回的 10 个块里，真正相关的往往只有 2~3 个，其余是「和查询字面高度重合但没有真正答案」的块——比如查「合同解除的法定条件」，召回一堆**复述了「合同解除」四个字但内容是讲别的**的段落。这些噪声块塞进 prompt 后稀释了模型注意力，模型反而抓不住真答案（回顾第 5 章「中间遗忘」）。

问题的本质是：**召回阶段用的相似度是「粗筛」**，它能保证「相关的大概率被捞进来」，却不能保证「最相关的排在最前」。解药是加一个**重排（rerank）**阶段：召回可以广（宁滥勿缺），但送进 prompt 前用一个更精细的模型把候选重新精排，只留真正最相关的几个。这一节讲清「双塔召回 + 交叉编码器精排」的两阶段架构，以及它为什么收益常常大于换 embedding。

## 原理：召回要广，精排要准

检索阶段有个策略性权衡：**召回（recall）要广，精排（precision）要准。** 具体做法是分两阶段：
```text
两阶段检索：

阶段一（召回）：向量 / BM25 / 混合检索 快速捞出 top-50  ← 追求"不漏"，宁滥勿缺
                   │
阶段二（精排）：rerank 模型对这 50 个逐一精排          ← 追求"准"，把最相关的顶上来
                   │
                取 rerank 后的 top-5 给 LLM
```
为什么召回和精排要用**不同**的模型？关键在两种模型结构的取舍——**双塔 vs 交叉编码器**：
```text
双塔(bi-encoder)：  查询─▶[编码]─▶向量 ┐
                                       ├─▶ 算距离   快，文档向量可离线预先算好
                    文档─▶[编码]─▶向量 ┘             精度有限（查询与文档没交互）

交叉编码器(cross-encoder)： [查询+文档]─▶[模型]─▶ 相关度分
                            慢，每对都要现算       精度高（查询文档充分交互）
```
- **双塔（bi-encoder）**：查询和文档**各自独立**编码成向量，再比距离。好处是文档向量可以**离线预先算好**存进库，在线只编码查询、算距离，快到毫秒级，能在百万级库里召回。代价是查询和文档「从没见过面」，精度有限。
- **交叉编码器（cross-encoder）**：把「查询 + 文档」**拼在一起**送进模型，让两者在模型内部充分交互，直接输出一个相关度分。精度高得多，但**每个「查询-文档」对都要现算一次**，慢，只能对少量候选跑。

所以标准架构是：**双塔负责在海量库里快速召回 top-50（便宜的粗筛），交叉编码器负责在这 50 个里精排出 top-5（昂贵的精排）。** 用「便宜粗筛 + 昂贵精排」的组合，兼顾速度和精度。

## 最小可运行演示

下面用可运行代码模拟这个两阶段流程。对照本章贯穿数据，你会看到一个典型问题：召回阶段把「只复述问题、没有答案」的干扰块顶到了第一，而 rerank 阶段把「真正含 400 瓦答案」的块救回第一。
```python
from collections import Counter
import math

docs = [
    "A100 功耗多少和负载多少及温度多少有关",   # 复述问题、没有答案（干扰）
    "限制功率上限可以让 A100 稳定在 400 瓦",   # 真正含数字答案
    "A100 支持多实例 GPU 技术提升利用率",
    "深度学习训练消耗大量电力",
]


def embed(t):
    return Counter(t)


def cosine(a, b):
    c = set(a) & set(b)
    d = sum(a[t] * b[t] for t in c)
    na = math.sqrt(sum(v * v for v in a.values()))
    nb = math.sqrt(sum(v * v for v in b.values()))
    return d / (na * nb) if na and nb else 0.0


query = "A100 功耗多少瓦"

recall = sorted(docs, key=lambda d: cosine(embed(query), embed(d)), reverse=True)  # ① 阶段一：双塔快速召回，取 top-N 粗筛
top_recall = recall[:3]
print("召回 top-3（粗筛）:")
for d in top_recall:
    print("  ", d)


def cross_encoder_score(query, doc):  # ② 阶段二：交叉编码器精排（模拟 query+doc 深度交互）
    """模拟交叉编码器：既看词重合，也奖励『含功率/功耗 + 单位瓦 + 具体数字』的块。"""
    base = cosine(embed(query), embed(doc))
    has_answer = ("瓦" in doc and ("功率" in doc or "功耗" in doc)
                  and any(c.isdigit() for c in doc))
    return base + (0.5 if has_answer else 0)     # 模拟深度交互识别出"真答案"


reranked = sorted(top_recall, key=lambda d: cross_encoder_score(query, d), reverse=True)
print("\nrerank 后 top-3（精排）:")
for d in reranked:
    print("  ", d)
```
保存为 `rerank.py`，运行 `python rerank.py`。预期输出：
```text
召回 top-3（粗筛）:
   A100 功耗多少和负载多少及温度多少有关
   限制功率上限可以让 A100 稳定在 400 瓦
   A100 支持多实例 GPU 技术提升利用率

rerank 后 top-3（精排）:
   限制功率上限可以让 A100 稳定在 400 瓦
   A100 功耗多少和负载多少及温度多少有关
   A100 支持多实例 GPU 技术提升利用率
```
逐行讲解：

- **标注 ①**：阶段一用双塔（玩具向量）快速召回。注意这里出了典型问题——「A100 功耗多少和负载多少及温度多少有关」这句**只是复述问题、没有答案**，却因为和查询字面高度重合被排到了第一；真正含答案「400 瓦」的块反而屈居第二。这正是双塔召回「粗」的体现：字面重合 ≠ 含答案。
- **标注 ②**：阶段二用交叉编码器精排。真实 rerank 模型会把 query 和 doc 拼接后深度交互，判断「这段到底有没有真正回答问题」；这里用「奖励同时含『功率 / 功耗』+ 单位『瓦』+ 具体数字的块」来模拟这种深度理解。结果「限制功率上限可以让 A100 稳定在 400 瓦」被顶到第一，干扰块被压下去。

这就是 rerank 的价值：**召回负责把答案捞进候选池，rerank 负责把答案顶到最前。** 前者靠混合检索保证「不漏」，后者靠交叉编码器保证「不乱」。

## 深入：为什么 rerank 收益常大于换 embedding

很多团队 RAG 效果差，第一反应是「换个更强的 embedding」。但实践中，**加一层 rerank 的收益往往比换 embedding 更大、更省事**，原因有三：

1. **rerank 直接治「排序」这个痛点。** embedding 决定「谁能进候选池」，rerank 决定「候选池里谁排前面」。而 RAG 最终塞进 prompt 的就是 top 几个，排序错了，答案再好也没进 prompt。rerank 精准打击这个环节。
2. **交叉编码器的精度天花板高于双塔。** 双塔为了「可预先算向量」牺牲了查询-文档交互，这是结构性限制；交叉编码器没有这个限制，同等参数量下精度更高。Anthropic 的实验里，「Contextual Retrieval + rerank」比不加 rerank 又把失败率显著降低（从 49% 降到 67% 的那部分增量主要来自 rerank）[来源](https://www.anthropic.com/news/contextual-retrieval)。
3. **rerank 是「加一层」，不用动存量索引。** 换 embedding 要全量重建索引（见 26.2），成本高、风险大；加 rerank 只是在召回后多一次调用，不碰向量库。

**代价当然有**：rerank 多一次模型调用，**增加延迟和成本**。所以它只对召回的**少量候选**（几十个）做，绝不对全库做。而且召回 k 不能无脑放大——k 越大，rerank 要打分的候选越多，延迟成本越高；极端情况下真答案被埋在几百个候选里，rerank 也未必救得回。合理做法是「召回几十个、rerank 出几个」，具体数值用评估集调。

## 真实系统对应

**官方公开机制**：Anthropic Contextual Retrieval 明确把 reranking 作为最后一步，用交叉编码器对合并后的候选精排，并给出量化收益 [来源](https://www.anthropic.com/news/contextual-retrieval)；Cohere、Voyage、Jina 等厂商都提供专门的 rerank API（模型名与价格以当前官方文档为准）。**通用工程模式**：两阶段「双塔召回 + 交叉编码器精排」、召回放大 + rerank 收窄、只对候选跑 rerank，是可迁移到任何系统的标准架构。**教学参考实现**：上面的 `cross_encoder_score` 是规则模拟，真实 rerank 用训练好的交叉编码器模型；这里只为演示「精排能把双塔召回的排序错误纠正过来」的机制。

需要点明边界：rerank 模型本身也会错，它不是「绝对正确的裁判」；对延迟敏感的场景要权衡 rerank 带来的额外耗时；召回质量太差（真答案根本没进候选池）时，rerank 无力回天——它只能重排「已召回的」，不能凭空找回「没召回的」。

## 生产踩坑

| 症状 | 根因 | 如何观测与复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| 复述问题的块排在答案前 | 双塔召回只看字面重合 | 打印召回 top-k 看是否是答案 | 加交叉编码器 rerank 精排 | 召回本就精准的简单场景 |
| 召回 k 调大反而更差 | 噪声块稀释注意力 | 对比 k=3 与 k=10 答案质量 | rerank 后截断到 top-3~5 | 有 rerank 兜底时可适当放大召回 |
| rerank 后延迟飙升 | 召回 k 太大、候选过多 | 观测 rerank 阶段耗时随 k 变化 | 召回收敛到几十、只对候选 rerank | 离线批处理对延迟不敏感 |
| 加了 rerank 没效果 | 真答案根本没进候选池 | 检查召回阶段是否已漏 | 先修召回（混合检索）再谈 rerank | 召回已含答案时 rerank 有效 |
| 对全库跑 rerank 成本爆炸 | 误把 rerank 当召回用 | 统计 rerank 调用次数 | rerank 只对召回候选做 | 库极小可例外 |
| 换 embedding 折腾半天收益小 | 痛点在排序不在召回池 | 分别测召回率与精度 | 先加 rerank 再考虑换模型 | 召回率本身就低时需先修召回 |
| rerank 模型也判错 | 把 rerank 当绝对正确 | 用评估集看 rerank 后精度 | 评估集回归、必要时换 rerank 模型 | 无绝对可靠的裁判 |

## 思考：rerank 用的交叉编码器和召回用的双塔，各自的取舍是什么？为什么要两阶段？

### 回答

取舍的核心是「速度 vs 精度」。双塔（bi-encoder）把查询和文档**各自独立**编码成向量再比距离，最大好处是文档向量可以**离线预先算好**存进库，在线只需编码查询、算距离，快到毫秒级，能在百万级库里做召回；代价是查询和文档在编码时「从没交互过」，精度有结构性上限。交叉编码器（cross-encoder）把「查询 + 文档」**拼在一起**送进模型，让两者在内部充分交互再输出相关度分，精度高得多；但每个「查询-文档」对都要现算一次，慢，无法对全库跑。正因为一个「快但粗」、一个「准但慢」，才要两阶段：**双塔在海量库里快速召回 top-50（便宜粗筛），交叉编码器在这 50 个里精排出 top-5（昂贵精排）**。这样既有召回的速度和广度，又有精排的准度。单用双塔排序会乱（字面重合的噪声顶到前面），单用交叉编码器又跑不动全库——组合起来才兼顾速度和精度。

### 面试精简表达

双塔各自编码可离线预算、快但精度有限，交叉编码器拼接交互、准但每对现算跑不动全库；两阶段=双塔召回广 + 交叉编码器精排准，兼顾速度与精度。

## 思考：为什么说「加 rerank 的收益常常大于换 embedding」？什么时候这句话不成立？

### 回答

因为 RAG 最终塞进 prompt 的只是 top 几个块，**排序**直接决定模型看到什么。embedding 决定「谁能进候选池」，rerank 决定「候选池里谁排最前」——很多系统的痛点其实在后者：答案已经被召回进来了，只是被字面重合的噪声块压在后面没进 prompt。这种情况下加 rerank 直接命中痛点，而且交叉编码器的精度天花板高于双塔（有查询-文档交互），再加上 rerank 只是「加一层调用、不动存量索引」，比换 embedding 要全量重建索引省事得多、风险小得多。这就是为什么它常是性价比最高的一步。但这句话有前提，不成立的情况主要是：**如果真答案根本没被召回进候选池**（召回率本身就低，比如缺 BM25 导致精确词漏召），那 rerank 无力回天——它只能重排「已召回的」，不能凭空找回「没召回的」。这时该先修召回（上混合检索、修分块、换或调 embedding），再谈 rerank。所以正确的诊断顺序是：先用评估集看是「召回率低」还是「精度低」——召回率低先修召回，精度低才优先上 rerank。

### 面试精简表达

RAG 只把 top 几个入 prompt，排序是痛点，rerank 直接治排序且不动索引，性价比高；但若真答案没进候选池（召回率低），rerank 救不了，须先修召回——用评估集区分召回率低还是精度低。
