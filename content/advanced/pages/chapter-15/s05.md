## 真实问题

一位刚接手审核 Agent 的新同事，学了两周 LangGraph，能照着文档拼节点和边，但一到「自己设计一张图」就卡壳。他问了个很典型的问题：「LangGraph 是不是又是一套要从头学的新东西？路由、多智能体、反思……这些是不是 LangGraph 发明的新概念？」团队里的老人给了他一句点破的话——「你在卷三学的那些工作流模式，LangGraph 一个都没发明，它只是给每一种模式配了一套『用图来画』的通用语言。你已经懂『意义』了，现在只是学怎么把它画成图。」

这一节要把这句话坐实。我们把卷三讲过的四种核心工作流模式——ReAct（Reasoning and Acting，推理并行动）循环、Routing（路由）、编排者-工作者（Orchestrator-Worker）、反思（Reflection）循环——**逐一画成 LangGraph 的图结构**，并给出一段能同时跑通它们的最小代码。学完你会确信：**LangGraph 没有新原理，只有把旧原理显式化的图语言。** 这也是「原理不变、换框架只是换语法」最有力的证明。这些工作流模式的权威梳理见 Anthropic 的《Building Effective Agents》[来源](https://www.anthropic.com/engineering/building-effective-agents)。

## 原理：四种模式各对应一种图结构

每一种工作流模式，在 LangGraph 里都有一个几乎一一对应的图形结构：
```text
① ReAct 循环（第 4 章）= 带条件边回环的两节点图：
   [调模型] ──▶ [调工具] ──条件边(还要继续吗?)
      ▲                          │否
      └──────────是──────────────┘──▶ END
   条件边读「模型是否还要调工具」，是则回到调模型，否则 END

② Routing 路由（第 10 章）= 一个分诊节点 + 条件边多分叉：
              ┌─条件边:退款──▶ [退款节点]
   [分诊节点]──┼─条件边:技术──▶ [技术节点]
              └─条件边:通用──▶ [通用节点]
   条件边读「问题类型」，返回对应节点名

③ 编排者-工作者 / Manager（第 10、11 章）= 中心节点向多工作节点分发 + 汇总：
   [编排节点] ──派发──▶ [工作节点1] ─┐
        │      ──派发──▶ [工作节点2] ─┼─▶ [汇总节点] ──▶ END
        └──────派发──▶ [工作节点3] ─┘
   工作节点并行、各写增量到 State（用 operator.add 合并，见第 2 节）

④ 评估-优化 / 反思循环（第 7 章）= 生成→评估→不合格回环：
   [生成节点] ──▶ [评估节点] ──条件边:不合格──▶ 回到[生成节点]
                                └─合格──▶ END
   条件边读「评估是否通过」，不过则回环重生成（配轮次上限防死循环）
```
看出规律了吗？**四种模式的差别，全落在「边」怎么画上**：ReAct 和反思是「条件边回环」，路由是「条件边多分叉」，编排者-工作者是「一个节点多出边分发 + 汇总节点收口」。节点做的事（调模型、调工具、评估）是卷一到卷三讲透的原理；图只是把「这些事之间怎么走」显式画出来。**LangGraph 提供的是画法，不是原理。**

## 现象与输入

用一句话对照，把「模式」翻译成「图元素」：
```text
工作流模式（卷三的"意义"）        LangGraph 图元素（"语法"）
────────────────────────────    ──────────────────────────────
ReAct：想→做→再想→做直到够      两节点 + 条件边回环（还要工具吗）
Routing：按类型分派              分诊节点 + add_conditional_edges 多分叉
Orchestrator-Worker：拆分-并行-合  中心节点多出边 + 并行工作节点 + 汇总节点
Reflection：生成-批判-改进        生成/评估两节点 + 条件边回环（合格没）
共享状态记忆（第 5 章）          State 通道（第 2 节的 reducer）
高风险动作人工审核（第 2、11 章） review 节点 + interrupt（第 4 节）
```
这张对照表就是新同事困惑的解药：**他不需要学「新模式」，只需要学「把已知模式翻译成图元素」这一层映射。** 会了这层翻译，任何工作流模式他都能画成图。

## 最小可运行演示

下面用纯 Python 复刻「路由」和「反思循环」两种模式的图（其余两种结构同理），跑通它们、打印走向轨迹。它无需安装 LangGraph、不需要 API Key。真实 LangGraph 里，这两张图分别靠 `add_conditional_edges` 的多分叉与回环实现，语义一致 [来源](https://langchain-ai.github.io/langgraph/concepts/low_level/)。
```python
"""教学参考实现：把「路由」与「反思循环」两种工作流模式画成图并跑通。"""
from __future__ import annotations

START, END = "__start__", "__end__"


class Graph:
    def __init__(self):
        self.nodes, self.edges, self.cond = {}, {}, {}

    def node(self, name, fn): self.nodes[name] = fn; return self
    def edge(self, a, b): self.edges[a] = b; return self
    def cedge(self, a, router): self.cond[a] = router; return self

    def run(self, state, entry, max_steps=25):
        node, trace = entry, []
        for _ in range(max_steps):
            if node == END:
                break
            state = {**state, **(self.nodes[node](state) or {})}
            trace.append(node)
            node = self.cond[node](state) if node in self.cond else self.edges.get(node, END)
        return state, trace


## ===== 模式②：Routing 路由 =====
def triage(state):                       ## 分诊节点：给问题打个类型标签
    text = state["question"]
    kind = "退款" if "退款" in text else ("技术" if "报错" in text else "通用")
    return {"kind": kind}

def refund(state): return {"answer": "已转退款专席处理"}
def tech(state): return {"answer": "已转技术支持处理"}
def general(state): return {"answer": "已由通用客服回答"}

def route(state):                        ## 条件边：读 kind，多分叉
    return {"退款": "refund", "技术": "tech", "通用": "general"}[state["kind"]]

def build_routing():
    g = Graph()
    g.node("triage", triage).node("refund", refund).node("tech", tech).node("general", general)
    g.edge(START, "triage").cedge("triage", route)
    for n in ("refund", "tech", "general"):
        g.edge(n, END)
    return g


## ===== 模式④：反思（评估-优化）循环 =====
def generate(state):                     ## 生成节点：每轮把草稿变长一点（模拟改进）
    draft = state.get("draft", "") + "改"
    return {"draft": draft, "rounds": state.get("rounds", 0) + 1}

def evaluate(state):                     ## 评估节点：长度达标即合格
    return {"pass": len(state["draft"]) >= 3}

def reflect_route(state):                ## 条件边：不合格回生成，合格且防超轮则 END
    if state["pass"] or state["rounds"] >= 5:
        return END
    return "generate"

def build_reflection():
    g = Graph()
    g.node("generate", generate).node("evaluate", evaluate)
    g.edge(START, "generate").edge("generate", "evaluate")
    g.cedge("evaluate", reflect_route)   ## 回环就画在这条条件边上
    return g


if __name__ == "__main__":
    r = build_routing()
    for q in ["我要退款", "登录报错怎么办", "你们几点上班"]:
        _, trace = r.run({"question": q}, entry="triage")
        print(f"路由 [{q}] -> 走向 {trace}")

    print()
    g = build_reflection()
    final, trace = g.run({}, entry="generate")
    print(f"反思循环走向 {trace}")
    print(f"最终草稿={final['draft']} 轮数={final['rounds']} 合格={final['pass']}")
```
保存为 `patterns.py`，运行 `python patterns.py`。完整预期输出：
```text
路由 [我要退款] -> 走向 ['triage', 'refund']
路由 [登录报错怎么办] -> 走向 ['triage', 'tech']
路由 [你们几点上班] -> 走向 ['triage', 'general']

反思循环走向 ['generate', 'evaluate', 'generate', 'evaluate', 'generate', 'evaluate']
最终草稿=改改改 轮数=3 合格=True
```
路由图里，同一个 `triage` 节点因问题不同，条件边把它导向三个不同后继——这就是「路由=条件边多分叉」。反思图里，`generate→evaluate` 走了三轮才达标，靠的是 `evaluate` 上那条「不合格回 generate」的条件边回环——这就是「反思=生成评估回环」。两种看似不同的模式，本质都是**条件边**的不同画法。

## 真实系统对应

**官方公开机制**：LangGraph 用 `add_conditional_edges(node, router)` 支持「按状态返回下一节点名」的动态路由（含回到已访问节点形成循环）、支持路由函数返回节点名列表实现向多个节点的并行分发（配合 reducer 合并结果），这些都是官方 Low Level 文档描述的能力 [来源](https://langchain-ai.github.io/langgraph/concepts/low_level/)。LangGraph 官方也提供了 supervisor（编排者-工作者）等多智能体范式的现成实现 [来源](https://docs.langchain.com/oss/python/langgraph/overview)。**通用工程模式**：「四种工作流模式 ↔ 四种图结构」的映射本身是可迁移的建模心法——换任何图/流程引擎，路由都是「分叉」、反思都是「回环」、编排都是「分发+汇总」。Anthropic《Building Effective Agents》对这些模式（prompt chaining、routing、orchestrator-workers、evaluator-optimizer）做了权威梳理，可与本节图映射对照阅读 [来源](https://www.anthropic.com/engineering/building-effective-agents)。**教学参考实现**：上面的 `Graph` 只演示路由与回环语义，不复刻 LangGraph 的并行超步与真实调度。

需要点明边界：把模式画成图很直观，但「回环」类图（ReAct、反思）**必须配轮次/步数上限**，否则条件边一直返回「继续」就成了死循环、烧 token——这也是演示里 `max_steps` 和 `rounds >= 5` 的作用，回扣第 8 章「循环要有硬上限」。

## 生产踩坑

| 症状 | 根因 | 如何观测与复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| 反思/ReAct 图无限回环 | 条件边总返回「继续」、无上限 | 让评估永不通过复现死循环 | 加 rounds/步数上限，触顶降级 | 明确会收敛的流程风险低 |
| 路由分支漏了「兜底」类 | router 未覆盖未知类型 | 输入一个新类型看是否 KeyError | router 加 default 兜底分支 | 类型封闭且穷举时无碍 |
| 编排并行结果互相覆盖 | 汇总通道用了默认覆盖 | 多工作节点写同键看是否丢 | 汇总通道用 operator.add（第 2 节） | 单工作节点无并发问题 |
| 把简单直线流程硬画成回环 | 过度套用「反思」模式 | 数一下是否真需要多轮 | 不需迭代就用直线普通边 | 确需迭代改进的任务除外 |
| 多智能体图节点爆炸难维护 | 一张图塞进过多子逻辑 | 统计节点数与耦合度 | 拆子图（subgraph）分层组织 | 小图不必过早拆分 |
| 分发后无汇总、结果散落 | 只分发没画汇总节点 | 并行节点各写各的、无收口 | 加汇总节点收敛再 END | 无需合并的独立任务除外 |

## 思考：面试官问「你用过 LangGraph 吗？它和你理解的工作流模式什么关系？」怎么答出段位？

### 回答

关键是**做映射**，而不是罗列 API。可以这样答：「LangGraph 没有发明新的 Agent 模式，它只是给我在卷三学过的每一种工作流模式配了一套用图来画的通用语言。具体来说——ReAct 循环是『调模型、调工具』两个节点加一条『还要工具吗』的条件边回环；Routing 路由是一个分诊节点加 `add_conditional_edges` 的多分叉；编排者-工作者是一个中心节点向多个工作节点分发、再用一个汇总节点收口（并行结果靠 reducer 合并）；反思循环是『生成、评估』两节点加一条『不合格就回生成』的条件边回环，还得配轮次上限防死循环。你会发现四种模式的差别全在『边怎么画』上，节点做的事还是那些老原理。」这样回答，面试官立刻知道你不是只会拼节点，而是理解了「模式的本质是意义、图是语法」——**能做映射的人和只会背框架名的人，段位一眼可辨。** 最后可以补一句：正因为原理相通，我学 LangGraph 很快，换任何新框架也不怕。

### 面试精简表达

答「LangGraph 没发明新模式，只是给旧模式配了图语言」：ReAct/反思=条件边回环，路由=条件边多分叉，编排者-工作者=中心节点分发+汇总。差别全在边怎么画，节点还是老原理——能做这层映射就是段位。

## 思考：为什么说「理解了卷三，学 LangGraph 会很快」不是一句鼓励的空话？

### 回答

因为它是可以被本节的映射直接证明的事实，不是打气。学一个框架，真正难的从来不是记 API（`add_node`、`add_edge` 半天就熟），而是理解「这些 API 组合起来能表达什么、该怎么组合去解决问题」——而这一层，恰恰是卷三已经教给你的。卷三讲的路由、编排、反思、ReAct，是「在什么场景、用什么结构去组织 Agent 的行为」这一层的知识（意义）；LangGraph 的节点和边，是把这些结构落地的工具（语法）。当你已经懂「反思就是生成-评估-不合格回环」这个意义，再看 LangGraph，你要做的只是把它翻译成「两节点 + 一条回环条件边」——翻译远比从零理解快。反过来,如果一个人没学过卷三、直接啃 LangGraph，他会淹没在「什么时候用条件边、状态该放什么、要不要检查点」的问题里，因为他缺的不是语法，是意义。所以「理解了卷三学 LangGraph 会很快」的底层逻辑是：**框架学习的瓶颈在『意义』不在『语法』，而卷三已经把意义给足了。**

### 面试精简表达

框架学习的难点在「用它能表达什么」（意义）而非记 API（语法）。卷三已把路由/编排/反思等模式的意义讲透，学 LangGraph 只是把已懂的意义翻译成节点和边——翻译比从零理解快得多，所以确实很快。

## 深入：为什么「共享状态 + 图」能优雅表达多智能体协作？

编排者-工作者模式（第 11 章）在 LangGraph 里之所以画起来自然，关键在于它把「多智能体协作」拆成了两个正交的部分：**协作结构**交给图（谁分发给谁、谁汇总），**协作数据**交给共享状态（各工作节点把结果写进同一个 State，用 reducer 合并）。

对比一下没有这两样东西时怎么做多智能体：你得手写一个调度器，维护「哪个 agent 该跑了」的队列，再手写各 agent 之间传数据的管道，还得处理并发写的竞态——协作结构和协作数据搅在一起，代码很快失控。而在 LangGraph 里，编排节点用条件边（返回工作节点名列表）声明「分发给谁」，工作节点各自返回增量、由 `operator.add` 通道安全合并，汇总节点读合并后的状态收口。结构是图、数据是状态，两者解耦，所以「加一个工作节点」只是多注册一个 node 和一条分发边，不用碰调度和合并逻辑。这正是第 11 章多智能体协作在图上的优雅落地，也再次印证：LangGraph 的价值不在发明协作模式，而在**给协作模式提供了一套「结构与数据解耦」的清晰表达**。
