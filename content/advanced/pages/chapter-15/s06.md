## 真实问题

审核 Agent 项目成了，团队被拉去评审另外三个新需求：A 团队要「一个由研究员+写手+审稿人组成的内容生产团队」；B 团队在 OpenAI 生态，要「现成的多 Agent 交接和输入输出护栏」；C 团队有「几万份历史合同 PDF，想让 Agent 基于它们答疑」。三个团队的第一反应都是「那也用 LangGraph 吧，你们不是搞成了吗」。技术评审时被否了——**这三个需求各有更省心的框架，硬套 LangGraph 是拿最重的兵器打最不对口的仗**。这次评审暴露了一个普遍误区：把「我熟的那个框架」当成万能锤，看什么都像钉子。

这一节横向对照 LangGraph 之外的三个主流框架——CrewAI、OpenAI Agents SDK、LlamaIndex——讲清它们各自的核心范式、最强场景与边界，帮你建立「遇到什么需求该翻哪把兵器」的完整版图。核心结论先给：**它们背后是同一套原理的不同表达，各自在某一维度做到最省心；选型不是找最强，是找最对口。**

## 原理：三个框架各自的定位

### CrewAI：像组建团队一样声明角色

CrewAI 的范式是**角色制（Crews）+ 流程编排（Flows）**：用声明式的方式定义每个 Agent 的角色（role）、目标（goal）、背景故事（backstory）和工具，再让它们像一支团队一样按顺序、层级或混合流程协作；Flows 则提供带状态管理、条件分支与人工介入触发的事件驱动编排 [来源](https://docs.crewai.com/)。

- **心智模型**：像「填一张组织架构表」——给每个 Agent 写清「你是谁、你的目标、你有哪些工具」，CrewAI 让这支团队协作。
- **最强场景**：角色分工清晰、协作流程相对固定的多 Agent 任务，如「研究员+写手+审稿人」的内容生产流水线。上手最快、声明式直观。
- **边界**：当协作逻辑高度动态、需要精细控制每一步走向时，声明式的表达力不如 LangGraph 的图；CrewAI 官方也用 Flows 来补足复杂编排 [来源](https://docs.crewai.com/)。对应第 11 章的多 Agent 协作。

### OpenAI Agents SDK：清晰的原语 + 内置追踪护栏

OpenAI Agents SDK 提供一组清晰、Python 优先的原语 [来源](https://openai.github.io/openai-agents-python/)：

| 原语 | 官方语义 | 本书对应概念 | 章节 |
|---|---|---|---|
| **Agents** | 配了指令与工具的 LLM | 智能体本身 | 全书 |
| **Handoffs** | 让一个 Agent 把任务委派/交接给另一个 | 去中心化的 Agent 交接 | 第 11 章多 Agent |
| **Guardrails** | 与 Agent 执行并行地跑输入/输出校验，不过则 fail fast | 输入输出护栏 | 第 18 章安全护栏 |
| **Tracing** | 内置执行追踪，可视化/调试/评估 | 可观测性 / 追踪 | 第 17 章可观测性 |
| **Sessions** | 跨轮次自动维护对话历史 | 会话记忆 | 第 5 章记忆 |

- **心智模型**：四五个原语几乎和本书概念一一对应，学起来毫无隔阂——「它把我学过的概念直接做成了 API」。
- **最强场景**：OpenAI 生态、想要现成的多 Agent handoff、护栏与追踪能力，且偏好轻量、Python 原生的编排（用语言本身的控制流而非学新抽象）[来源](https://openai.github.io/openai-agents-python/)。
- **边界**：它的编排偏「代码即流程」，对「长时可暂停、图级检查点、时间旅行」这类需求，不如 LangGraph 专门；护栏是「并行校验 + fail fast」，与业务级审批流是两回事。

### LlamaIndex：数据与 RAG 的王者

LlamaIndex 是 **RAG-first（Retrieval-Augmented Generation，检索增强生成）** 框架：核心强项是把海量异构数据（PDF、数据库、网页、API）接入并索引，提供丰富的数据连接器与检索能力，并在其上提供 AgentWorkflow 等 Agent 编排 [来源](https://docs.llamaindex.ai/en/stable/)。

- **根本差异**：别的框架首先关心「怎么组织 Agent 逻辑」，LlamaIndex 首先关心「怎么把数据喂进来、检索好」。
- **最强场景**：文档密集、知识库问答——「我有一大堆文档/数据，想让 Agent 基于它们回答问题」。回扣第 5 章记忆/检索、第 19 章 Agentic RAG。
- **边界**：如果核心痛点是复杂控制流而非数据接入，LlamaIndex 的 Agent 编排不是它最锋利的地方；但作为「数据层」，它常和别的框架组合使用（见第 7 节）。

## 现象与输入

用同一个需求「客服助手」分别落到四个框架，最省心的写法长什么样，一眼看出定位差异：
```text
需求：一个能查订单、必要时转人工的客服助手

LangGraph   ── 画图：triage→(条件边)→refund/tech/general，refund 前插 interrupt 人工节点
              适合：流程复杂、要暂停/审计/人工关口
CrewAI      ── 声明：客服Agent(role=客服,goal=解答,tools=[查订单]) + 人工审核触发
              适合：多角色团队、协作流程相对固定
OpenAI SDK  ── 定义：Agent(客服) --handoff--> Agent(退款专席)，输入挂 Guardrail 防注入
              适合：OpenAI 生态、要现成 handoff/guardrail/tracing
LlamaIndex  ── 索引：把订单FAQ/政策文档建索引，QueryEngine 检索后作答
              适合：答案主要来自文档/知识库
```
同一个「客服」需求，四个框架的「最省心写法」完全不同——因为它们优化的维度不同：LangGraph 优化控制粒度，CrewAI 优化角色声明，OpenAI SDK 优化原语现成，LlamaIndex 优化数据接入。**选型的本质，是把需求和框架优化的那个维度对上。**

## 最小可运行演示

下面用纯 Python 复刻四个框架各自的「心智模型骨架」——不是真实 SDK（真实 API 以各自官方文档为准），而是把「CrewAI 靠角色声明、OpenAI SDK 靠 handoff+guardrail、LlamaIndex 靠检索、LangGraph 靠图路由」这四种范式的**思路**用最小代码摆在一起对照。它无需任何第三方库、不需要 API Key。
```python
"""教学参考实现：四种框架范式的"心智模型骨架"对照（非真实 SDK）。"""
from __future__ import annotations
from dataclasses import dataclass, field


## ① CrewAI 范式：声明角色，团队按序协作
@dataclass
class Agent:
    role: str
    goal: str
    tools: list[str] = field(default_factory=list)

def crewai_style(question: str) -> str:
    crew = [
        Agent("研究员", "检索资料", ["search"]),
        Agent("写手", "整理成稿", []),
        Agent("审稿人", "校对润色", []),
    ]
    steps = [f"{a.role}({a.goal})" for a in crew]     ## 按声明顺序流水线协作
    return "CrewAI: " + " -> ".join(steps) + f" => 回答「{question}」"


## ② OpenAI Agents SDK 范式：handoff 交接 + guardrail 护栏
def guardrail(text: str) -> bool:                     ## 输入护栏：并行校验、不过 fail fast
    return "忽略以上指令" not in text

def openai_sdk_style(question: str) -> str:
    if not guardrail(question):
        return "OpenAI SDK: Guardrail 拦截（疑似提示注入），fail fast"
    agent = "客服Agent"
    if "退款" in question:                             ## handoff：交接给专席
        agent = "客服Agent --handoff--> 退款专席Agent"
    return f"OpenAI SDK: {agent}（Tracing 已记录本次执行）=> 回答「{question}」"


## ③ LlamaIndex 范式：先检索文档，再基于检索结果作答
KB = {"退款政策": "7 天无理由退款", "营业时间": "9:00-21:00"}

def llamaindex_style(question: str) -> str:
    hit = next((v for k, v in KB.items() if k[:2] in question or k in question), None)
    if hit is None:
        hit = next((v for k, v in KB.items() if any(c in question for c in k)), "未检索到")
    return f"LlamaIndex: 检索知识库命中「{hit}」=> 基于文档回答「{question}」"


## ④ LangGraph 范式：图 + 条件边路由（可插 interrupt 人工节点）
def langgraph_style(question: str) -> str:
    kind = "退款" if "退款" in question else "通用"
    path = "triage -(退款)-> [interrupt 人工审核] -> refund" if kind == "退款" \
        else "triage -(通用)-> general"
    return f"LangGraph: 图路由 {path} => 回答「{question}」"


if __name__ == "__main__":
    for q in ["我要退款", "你们几点营业"]:
        print(f"\n问题：{q}")
        for fn in (crewai_style, openai_sdk_style, llamaindex_style, langgraph_style):
            print("  " + fn(q))
```
保存为 `four_frameworks.py`，运行 `python four_frameworks.py`。完整预期输出：
```text
问题：我要退款
  CrewAI: 研究员(检索资料) -> 写手(整理成稿) -> 审稿人(校对润色) => 回答「我要退款」
  OpenAI SDK: 客服Agent --handoff--> 退款专席Agent（Tracing 已记录本次执行）=> 回答「我要退款」
  LlamaIndex: 检索知识库命中「7 天无理由退款」=> 基于文档回答「我要退款」
  LangGraph: 图路由 triage -(退款)-> [interrupt 人工审核] -> refund => 回答「我要退款」

问题：你们几点营业
  CrewAI: 研究员(检索资料) -> 写手(整理成稿) -> 审稿人(校对润色) => 回答「你们几点营业」
  OpenAI SDK: 客服Agent（Tracing 已记录本次执行）=> 回答「你们几点营业」
  LlamaIndex: 检索知识库命中「9:00-21:00」=> 基于文档回答「你们几点营业」
  LangGraph: 图路由 triage -(通用)-> general => 回答「你们几点营业」
```
同一个问题，四种范式各自的「重心」跃然纸上：CrewAI 重角色流水线、OpenAI SDK 重交接与护栏、LlamaIndex 重检索命中、LangGraph 重图路由与人工关口。**这段代码不是要你记 API，而是让你记住四种范式的『味道』**——遇到需求时，能立刻想到「这更像谁的味道」。

## 真实系统对应

**官方公开机制**：CrewAI 文档描述 Crews（角色/目标/工具的声明式团队）与 Flows（带状态、条件、人工介入触发的事件驱动编排）[来源](https://docs.crewai.com/)；OpenAI Agents SDK 文档列出 Agents、Handoffs、Guardrails（与执行并行、fail fast）、Tracing、Sessions、Function tools（Pydantic 自动 schema）、MCP（Model Context Protocol，模型上下文协议）服务器工具调用等原语 [来源](https://openai.github.io/openai-agents-python/)；LlamaIndex 文档强调数据连接器、索引/检索与 AgentWorkflow [来源](https://docs.llamaindex.ai/en/stable/)。**通用工程模式**：「按框架优化的维度做选型」「用同一需求横向试写找味道」是可迁移的选型方法。**教学参考实现**：上面四段骨架只演示范式思路，**不是任何 SDK 的真实调用**，真实类名、参数、能力边界一律以各自官方文档为准。

需要点明边界：框架都在快速演进，本节讲的是「相对稳定的定位与范式」，不是「功能清单」。比如 CrewAI 也能做条件编排、OpenAI SDK 也在扩展能力、LlamaIndex 也有 Agent——「谁能做什么」会变，但「谁在哪个维度最省心」这个定位相对稳定。选型时先按定位缩小范围，再查当前官方文档确认具体能力。

## 生产踩坑

| 症状 | 根因 | 如何观测与复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| 用 LangGraph 搭简单角色团队、样板爆炸 | 需求是「声明角色」却选了「画图」 | 数真业务逻辑占代码比例 | 角色分工固定的用 CrewAI | 需精细控制时图是值得的 |
| 文档问答效果差、检索是自己拼的 | 该用 RAG 框架却手写检索 | 对比召回率与连接器覆盖 | 数据密集用 LlamaIndex 连接器 | 数据极少可自己拼 |
| 把 Guardrail 当业务审批流 | 混淆「并行校验」与「人工审批」 | 看是否需要人参与决策 | 业务审批用 interrupt/Flows | 纯自动校验用 Guardrail 即可 |
| 离开 OpenAI 生态后能力打折 | 选型只看「现在用 OpenAI」 | 评估换模型/厂商的迁移成本 | 跨厂商需求评估可移植性 | 长期锁定 OpenAI 生态无碍 |
| 多角色协作逻辑一动态就失控 | CrewAI 声明式表达不了动态走向 | 加一个条件分支看是否别扭 | 动态复杂编排改用图/Flows | 流程固定时声明式最省心 |
| 追踪/护栏重复造轮子 | 没用 SDK 现成的 Tracing/Guardrails | 看是否手写了追踪埋点 | OpenAI 生态直接用内置能力 | 已有成熟可观测栈时另算 |

## 思考：什么场景应该选 LlamaIndex 而非 LangGraph 或 PydanticAI？为什么说它定位有根本差异？

### 回答

当你的**核心痛点是「数据接入与检索」而非「控制流」**时，选 LlamaIndex。典型场景：手里有几万份合同 PDF、一堆数据库表、若干内部 API，想让 Agent 基于这些异构数据回答问题——这里最难、最耗时的不是「Agent 怎么走流程」，而是「怎么把这些数据可靠地接进来、切好块、建好索引、检索得准」。LlamaIndex 的根本差异就在这里：别的框架（LangGraph、PydanticAI、CrewAI）首先回答「怎么组织 Agent 的逻辑」，而 LlamaIndex 首先回答「怎么把数据喂进来、检索好」，它把 300+ 数据连接器和成熟的 RAG（检索增强生成）能力做成了第一公民。所以如果你用 LangGraph 做这件事，你会发现自己在图之外还得手写一大堆数据加载、切块、embedding、检索的代码——那部分恰恰是 LlamaIndex 的主场。反过来，如果你的痛点是「多步骤、要暂停、要人工审核」的复杂控制流，那 LlamaIndex 的 Agent 编排就不是它最锋利的地方，该选 LangGraph。一句话——**按「你最难的那件事是数据还是控制流」来选。**

### 面试精简表达

痛点是「海量异构数据的接入与检索」时选 LlamaIndex——它以 RAG 和数据连接器为第一公民，而其他框架先关心 Agent 逻辑组织。痛点是复杂控制流则选 LangGraph。按「最难的是数据还是控制流」来分。

## 思考：OpenAI Agents SDK 的原语为什么让「学过本书的人」格外亲切？这说明了什么？

### 回答

因为它的核心原语几乎和本书讲的概念一一对应：Handoffs 就是第 11 章讲的去中心化 Agent 交接，Guardrails 就是第 18 章的输入输出护栏，Tracing 就是第 17 章的可观测性/追踪，Sessions 就是第 5 章的会话记忆，Function tools 就是第 8 章的 Function Calling（配 Pydantic 自动生成 schema）。也就是说，你学完本书的原理再看这个 SDK，会有一种「它把我学过的概念直接做成了 API」的通透感——不需要先理解一堆新抽象，直接把已知概念对号入座即可。这恰恰再次印证了本书反复强调的「原理是共同底座」：同一批概念（交接、护栏、追踪、记忆、工具调用），不同框架只是用不同的名字和包装去实现。理解了底层原理，你看任何框架都像在看「原理的一种方言」——OpenAI SDK 只是把方言说得特别贴近本书的术语而已。这也说明：**框架的价值在于把原理工程化、开箱即用，而不在于发明原理；所以吃透原理的人，换框架的成本极低。**

### 面试精简表达

它的 Handoffs/Guardrails/Tracing/Sessions/Function tools 分别对应本书的交接、护栏、可观测、记忆、Function Calling，几乎一一对号入座。这说明原理是共同底座，框架只是原理的不同包装——吃透原理，换框架成本极低。
