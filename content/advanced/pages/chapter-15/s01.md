## 真实问题

「合规资料审核」故障复盘的第一现场，是一段被反复引用的代码。上一版流程是这么写的：一个几百行的 `run()` 函数，里头一个大 `while` 循环，循环里用 `if/elif` 判断「现在该做抽取还是打分还是等人」，中间状态全塞在几个散落的局部变量里（`fields`、`score`、`waiting_human`）。这段代码能跑，但没人敢改——因为「下一步走哪」的逻辑和「每一步做什么」的逻辑搅在一起，藏在层层缩进里。更要命的是，当合规同事问「为什么这单进了人工复核、上一单没进」时，团队翻了半小时代码才找到那个决定分叉的 `if score > 60`，而且没有任何一处地方能一眼看出「整条流程长什么样」。

这一节要把这团「隐式控制流」拆开，钉死 LangGraph 的核心心智：**把流程显式地画成一张有向图**——处理逻辑放进节点、走向逻辑放进边、数据放进状态。画清楚这三者的分工，你不仅能修好这个故障，还能回答「LangGraph 到底解决了什么、凭什么」。

## 原理：三个概念与一条铁律

LangGraph 出自 LangChain 团队，核心思想是把 Agent 的执行流程建模为一张**图（Graph）**——由**节点（Node）**和**边（Edge）**组成的状态机 [来源](https://github.com/langchain-ai/langgraph)。官方 Low Level 概念文档把它拆成三件东西 [来源](https://langchain-ai.github.io/langgraph/concepts/low_level/)：

| 概念 | 官方语义 | 一句话理解 |
|---|---|---|
| **状态（State）** | 一个共享的数据结构（常用 `TypedDict` 或 Pydantic 模型），定义图运行期间流转的数据 schema | 「在图里流动的共享数据包」，节点唯一的通信方式 |
| **节点（Node）** | 一个普通函数（或可调用对象），入参是当前 State，返回要更新的字段字典 | 「一个处理步骤」，只管做事、不管跳转 |
| **边（Edge）** | 决定「当前节点执行完，下一步走哪」的路由逻辑，分普通边与条件边 | 「走向规则」，其中条件边按状态动态选路 |

再加上两个特殊锚点 `START` 与 `END`：`START` 是虚拟入口（用户输入从这里进入图），`END` 是虚拟出口（到达即终止）[来源](https://langchain-ai.github.io/langgraph/concepts/low_level/)。

由此提炼一条必须刻进脑子的铁律：

> **铁律：处理逻辑归节点，走向逻辑归边，通信数据归状态——三者严格分离。** 节点是纯函数，它不知道也不关心「下一步去哪」；跳转完全由边决定；节点之间从不互相传参，只通过读写共享状态来协作。正是这条分离，让「整条流程长什么样」可以一眼看清、可以单独审计。
```text
    START
      │  add_edge(START, "load")
      ▼
  ┌────────┐   节点=纯函数：读 State.docs，写 State.fields
  │ extract │──────────────────────────────────────────▶ 只做事
  └───┬────┘
      │  add_edge("extract", "score")
      ▼
  ┌────────┐   写 State.risk_score
  │ score  │
  └───┬────┘
      │  add_conditional_edges("score", route)  ← 走向逻辑在这里
      │
   route(state) 读 State.risk_score，返回下一个节点名
      │                          │
  risk>60│                       │risk≤60
      ▼                          ▼
  ┌────────┐                 ┌────────┐
  │ review │                 │ ingest │──▶ END
  └────────┘                 └────────┘
```
## 现象与输入

把开头那团 `if/elif` 和 LangGraph 的图并排看，差别一目了然：
```text
【隐式控制流（旧代码）】              【显式图（LangGraph）】
def run(docs):                       g = StateGraph(State)
  fields, score = {}, 0              g.add_node("extract", extract)
  stage = "extract"                  g.add_node("score", score)
  while True:                        g.add_node("review", review)
    if stage == "extract":           g.add_node("ingest", ingest)
      fields = ...; stage="score"    g.add_edge(START, "extract")
    elif stage == "score":           g.add_edge("extract", "score")
      score = ...                    g.add_conditional_edges("score", route)
      stage = "review" if score>60   g.add_edge("review", "ingest")
              else "ingest"          g.add_edge("ingest", END)
    elif ...                         app = g.compile()
  ↑ 走向和做事搅在一起、藏在缩进里     ↑ 每条边、每个节点、每个分叉都显式可见
```
左边「下一步走哪」写死在 `stage = ...` 的赋值里，散落在各分支；右边「走向」全部收拢到 `add_edge` / `add_conditional_edges` 这几行，**流程结构从代码里浮出水面**。这就是「把 Agent 建模成图」最直接的收益——结构可见、可审计、可改。

## 最小可运行演示

下面用纯 Python 复刻 LangGraph 的 `StateGraph`、`add_node`、`add_edge`、`add_conditional_edges`、`compile`、`invoke` 六个核心接口，跑通贯穿案例的图（省略人工介入，留到第 4 节）。它不联网、不需要 API Key、也不依赖安装 LangGraph，是本节图模型的「可执行版」。真实 LangGraph 的 API 形状与此一致，字段名以官方文档为准 [来源](https://langchain-ai.github.io/langgraph/concepts/low_level/)。
```python
"""教学参考实现：用纯 Python 复刻 LangGraph 的图执行语义（无需安装 langgraph）。"""
from __future__ import annotations
from typing import Callable

START, END = "__start__", "__end__"


class MiniStateGraph:
    def __init__(self) -> None:
        self.nodes: dict[str, Callable[[dict], dict]] = {}
        self.edges: dict[str, str] = {}                  ## 普通边：A -> B
        self.cond: dict[str, Callable[[dict], str]] = {}  ## 条件边：A -> route(state)

    def add_node(self, name: str, fn: Callable[[dict], dict]) -> "MiniStateGraph":
        self.nodes[name] = fn
        return self

    def add_edge(self, src: str, dst: str) -> "MiniStateGraph":
        self.edges[src] = dst
        return self

    def add_conditional_edges(self, src: str, router: Callable[[dict], str]):
        self.cond[src] = router
        return self

    def compile(self) -> "CompiledGraph":
        return CompiledGraph(self)


class CompiledGraph:
    def __init__(self, g: MiniStateGraph) -> None:
        self.g = g

    def invoke(self, state: dict, max_steps: int = 20) -> dict:
        node = self.g.edges[START]            ## 从 START 指向的第一个真实节点开始
        for _ in range(max_steps):            ## 硬性步数上限，防死循环
            if node == END:
                break
            fn = self.g.nodes[node]
            update = fn(state) or {}          ## 节点只返回"要更新的字段"
            state = {**state, **update}       ## 框架把返回值合并回全局 State
            if node in self.g.cond:           ## 条件边：按 router 返回值动态选路
                node = self.g.cond[node](state)
            else:                             ## 普通边：无脑走下一个
                node = self.g.edges.get(node, END)
        return state


## ---- 贯穿案例的四个节点：都是纯函数，只读写 State，不管跳转 ----
def extract(state: dict) -> dict:
    return {"fields": {"amount": 120000, "party": "甲公司"}}

def score(state: dict) -> dict:
    amount = state["fields"]["amount"]
    return {"risk_score": 82 if amount >= 100000 else 30}

def review(state: dict) -> dict:
    return {"approved": True, "route_taken": "人工复核"}   ## 第 4 节改成 interrupt

def ingest(state: dict) -> dict:
    return {"result": f"已入库：{state['fields']['party']}"}

def route(state: dict) -> str:                             ## 条件边：读状态、选路
    return "review" if state["risk_score"] > 60 else "ingest"


def build():
    g = MiniStateGraph()
    g.add_node("extract", extract).add_node("score", score)
    g.add_node("review", review).add_node("ingest", ingest)
    g.add_edge(START, "extract")
    g.add_edge("extract", "score")
    g.add_conditional_edges("score", route)   ## 分叉就画在这里
    g.add_edge("review", "ingest")
    g.add_edge("ingest", END)
    return g.compile()


if __name__ == "__main__":
    app = build()
    out = app.invoke({"docs": ["尽调材料#1"], "fields": {}, "risk_score": 0})
    print("最终状态：")
    for k, v in out.items():
        print(f"  {k} = {v}")
```
保存为 `mini_graph.py`，运行 `python mini_graph.py`。完整预期输出：
```text
最终状态：
  docs = ['尽调材料#1']
  fields = {'amount': 120000, 'party': '甲公司'}
  risk_score = 82
  route_taken = 人工复核
  approved = True
  result = 已入库：甲公司
```
因为金额 120000 ≥ 100000，`score` 写入 `risk_score=82`，条件边 `route` 读到 82>60，选路进 `review`，再走 `ingest` 到 `END`。把金额改成 50000，你会看到 `risk_score=30`、路由直接跳 `ingest`、结果里没有 `route_taken`——**分叉完全由运行时状态决定**，这就是条件边的价值。把 `MiniStateGraph` 换成真实 `from langgraph.graph import StateGraph, START, END`，节点函数与 `build()` 骨架几乎一行不用改。

## 真实系统对应

**官方公开机制**：LangGraph 官方 Low Level 文档明确 `StateGraph` 以状态 schema 初始化，`add_node` 注册节点函数、`add_edge` 加普通边、`add_conditional_edges` 加条件边（第二个参数是读状态返回下一节点名或名列表的路由函数），`START`/`END` 是保留的虚拟入口/出口，`compile()` 返回可 `invoke`/`stream` 的对象 [来源](https://langchain-ai.github.io/langgraph/concepts/low_level/)。节点返回「要更新的字段字典」、由框架合并回全局状态，也是官方语义。**通用工程模式**：「处理归节点、走向归边、通信归状态」的三分离，是可迁移到任何图/流程引擎的建模纪律；步数上限防死循环同理。**教学参考实现**：上面的 `MiniStateGraph` 只为演示执行语义，不复刻 LangGraph 的超步（superstep）并行调度、Pregel 消息传递、通道 reducer 等真实机制（并行与 reducer 见第 2、5 节），也不代表其源码结构。

需要点明一个边界：真实 LangGraph 的执行模型基于 **Pregel/BSP（Bulk Synchronous Parallel，整体同步并行）超步**——同一超步内被激活的多个节点可以并行执行，超步之间做状态合并 [来源](https://langchain-ai.github.io/langgraph/concepts/low_level/)。上面的教学实现是单节点顺序执行的简化版，足以讲清「节点/边/状态」的分工，但不要据此以为 LangGraph 只能串行。

## 生产踩坑

| 症状 | 根因 | 如何观测与复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| 改一处走向牵动整块逻辑 | 走向写死在节点内的赋值里 | 搜索 `stage=`/`next=` 散落数量 | 走向全收拢到条件边的 router 函数 | 只有一条直线的流程无需拆 |
| 图跑不动、卡在某节点 | 忘了给某节点加出边、成孤岛 | 打印每个节点的出边覆盖 | 编译前校验每个非 END 节点都有出边 | 有意的终止节点直连 END |
| 节点间靠全局变量传值 | 没用 State，用了模块级变量 | 并发跑两个请求看串数据 | 一切共享数据放进 State schema | 无状态的纯计算节点例外 |
| 条件边返回了不存在的节点名 | router 拼错节点名或漏分支 | 让 router 返回一个错名复现 KeyError | router 返回值限定在 Literal 枚举里 | 动态生成节点名的高级用法另设 |

## 思考：LangGraph 和普通 Agent 循环（smolagents / PydanticAI）最本质的区别是什么？

### 回答

很多人会答「一个用图、一个用循环」，这只说对了表面。更本质的答案是：**LangGraph 把「流程走向」从模型的隐式决策，变成了开发者用图和状态显式定义的确定性结构**。smolagents、PydanticAI 的循环是隐式的——框架内部有个 `while`，下一步走哪基本由模型在循环里自己决定，你看不到也难以精细干预；而 LangGraph 让你亲手画出每个节点、每条边、每个分叉条件，模型仍然在**节点内部**做决策（比如「抽取哪些字段」），但**节点之间怎么跳转**由你画的边和共享状态说了算。一句话——它把控制权从模型手里，部分收回到了开发者手里。这正是「精细控制」和「可审计」的根源：因为走向是你显式定义的确定性结构，所以能画出来、能审计、能在特定节点插入检查点和人工关口（第 3、4 节）。

### 面试精简表达

隐式循环里「下一步走哪」由模型决定、藏在框架内部；LangGraph 里走向由开发者用边和状态显式定义，模型只在节点内决策——控制权部分从模型收回到开发者，换来可控与可审计。

## 思考：`add_edge` 和 `add_conditional_edges` 有什么区别？什么时候必须用条件边？

### 回答

`add_edge(A, B)` 是**静态固定连接**：执行完 A 必然去 B，跳转与运行时状态无关。`add_conditional_edges(A, router)` 绑定一个**读状态的路由函数**：执行完 A 后，调用 `router(state)`，用它的返回值（下一个节点名，或一个名字列表表示并行分发）动态决定去哪。判断依据是：**下一步走哪，是否取决于「这一步跑出来的结果」？** 如果取决于（金额高走人工、低走直接入库；问题类型走不同处理节点；反思结果合格与否决定要不要回环），就必须用条件边；如果无论如何都走同一个后继（抽取完必然去打分），用普通边即可。一句话——普通边画「固定流程」，条件边画「分支决策」，后者才是图状态机表达复杂逻辑的关键。

### 面试精简表达

普通边是「执行完 A 必去 B」的静态连接；条件边绑定读状态的 router、按运行时结果动态选下一节点。走向依赖上一步结果时用条件边，否则用普通边。

## 机制推导：为什么「节点是纯函数、只返回增量」是个好设计？

回到贯穿案例。`score` 节点只返回 `{"risk_score": 82}`，而不是返回整个新状态；框架负责把这个增量合并回全局 State。这个「只返回增量、由框架合并」的约定，看似只是语法糖，实则解决了三个真实问题。

其一，**解耦**：节点不需要知道 State 里还有哪些别的字段，它只关心自己产出的那几个键。这让节点可以独立编写、独立测试——给 `score` 喂一个含 `fields` 的字典，断言它返回 `{"risk_score": 82}`，无需构造完整状态。

其二，**为并发合并铺路**：真实 LangGraph 在一个超步里可能并行跑多个节点，每个节点各自返回增量，框架再按通道的 reducer 规则把这些增量合并（第 2 节详述）。如果节点直接改全局状态，并发写就会互相覆盖、丢更新——「只返回增量、由框架合并」正是安全并发的前提。

其三，**为检查点铺路**：因为每个超步后状态是一个明确、完整、可序列化的数据包，框架才能在超步边界干净地存一次检查点（第 3 节）。如果状态散落在一堆局部变量里，就没有一个「干净的存档点」。所以这三个词——纯函数、返回增量、框架合并——不是随便定的约定，而是并发、持久化、可测试性共同的地基。
