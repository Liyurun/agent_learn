## 真实问题

开头故障里最刺眼的一行代码，是「人工复核」节点的实现：
```python
def human_review(state):
    while state["approved"] is None:
        time.sleep(30)          ## 每 30 秒轮询一次数据库，看人审了没
        state["approved"] = poll_review_db(state["case_id"])
    return state
```
它有三宗罪。其一，**占着进程死等**：合规同事可能几小时后才处理，这几小时里进程线程一直阻塞在 `sleep` 里，什么也干不了。其二，**进程一死全丢**：这正是那次崩溃的直接原因——等人期间机器重启，`while` 循环连同内存里的中间状态一起没了。其三，**没有一个「干净的暂停点」**：状态散在内存，无法存档、无法在别处（比如一个审批 Web 页面）展示待办、也无法「人在另一台机器上批准后，图在原处续跑」。

这一节讲 LangGraph 怎么把「等人」这件事做对——用 `interrupt` 把审核节点变成一个**可存档的断点**：图执行到这里主动暂停、把待办抛给外部、状态存进检查点；人在任意时间、任意进程给出结论后，用 `Command(resume=...)` 从断点原地续跑。

## 原理：interrupt 暂停 + Command(resume) 续跑

LangGraph 的人工介入（Human-in-the-Loop，HITL）建立在检查点之上。官方 Human-in-the-loop 文档描述了两种主要方式 [来源](https://langchain-ai.github.io/langgraph/concepts/human_in_the_loop/)：

**方式一：节点内调用 `interrupt`（推荐、动态）**。在节点函数里调用 `interrupt(payload)`：

- 图**当场暂停**，`payload`（任意可 JSON 序列化的值，如「请复核这段摘要」）被抛给调用方；
- 当前状态**存进检查点**——所以暂停期间进程可以退出、可以崩溃，状态稳稳在库里；
- 调用方拿到 `payload`、展示给人、收集人的输入后，用 `graph.invoke(Command(resume=人的输入), config)` 恢复；
- 恢复时，`interrupt(...)` 这个调用会**返回**人给的值，节点从中断处**继续往下执行**（注意：节点会从头重跑到 `interrupt` 处，`interrupt` 之前的代码要幂等或轻量）[来源](https://langchain-ai.github.io/langgraph/concepts/human_in_the_loop/)。

**方式二：编译时设断点 `interrupt_before` / `interrupt_after`（静态）**。`compile(checkpointer=..., interrupt_before=["human_node"])` 让图在进入某节点前停下，检查、甚至用 `update_state` 改写状态后再 `invoke(None, config)` 继续 [来源](https://langchain-ai.github.io/langgraph/concepts/human_in_the_loop/)。

两种方式都**必须挂 checkpointer**——因为「暂停后能恢复」的前提是「状态被存下来了」。这就把第 3 节的检查点和本节的人工介入串成了一条线：**检查点是人工介入的地基。**
```text
   ┌──────────────┐
   │ score:82>60  │ 条件边判定进人工
   └──────┬───────┘
          ▼
   ┌──────────────┐   node 内 interrupt({"待办":"复核摘要", "摘要":...})
   │ review 节点   │──① 图暂停，payload 抛给调用方
   └──────┬───────┘──② 当前状态存进检查点 c4（暂停态）
          │              进程可退出/崩溃，状态不丢
          │        ……（几分钟或几小时后）……
          │        人在审批页点"批准" -> invoke(Command(resume=True), config=T1)
          ▼        ③ interrupt(...) 返回 True，review 从断点继续
   ┌──────────────┐
   │ approved=True │──▶ ingest ──▶ END
   └──────────────┘
```
## 现象与输入

把「sleep 硬等」和「interrupt 断点」并排看，差别在「暂停期间进程的状态」：
```text
【sleep 硬等（旧代码）】                   【interrupt 断点（LangGraph）】
def review(state):                        def review(state):
  while approved is None:                   decision = interrupt(
    time.sleep(30)  # 占着进程死等             {"task":"复核","summary":state["fields"]})
    approved = poll_db()                     return {"approved": decision}
  ...                                       ↑ 图暂停、状态存检查点、进程可退出
  ↑ 进程阻塞数小时                          人在别处批准 -> Command(resume=True) 续跑
  ↑ 崩溃则 while 与状态全丢                 ↑ 崩溃也不怕，状态在 c4
```
左边把「等待」变成「阻塞」，右边把「等待」变成「一次可存档的暂停」。**同样是等人，右边不占进程、不怕崩溃、待办可展示、可跨进程恢复**——这才是把人优雅嵌进自动化流程的正确姿势。

## 最小可运行演示

下面用纯 Python 复刻 `interrupt` + `Command(resume=...)` 的核心语义：节点抛出一个「中断信号」让图暂停并存档，外部收集人类输入后用 `resume` 恢复、图从暂停节点继续。它无需安装 LangGraph、不需要 API Key。真实 LangGraph 的 `interrupt` / `Command(resume=...)` 语义与此一致 [来源](https://langchain-ai.github.io/langgraph/concepts/human_in_the_loop/)。
```python
"""教学参考实现：复刻 interrupt 暂停 + Command(resume) 恢复（无需安装 langgraph）。"""
from __future__ import annotations
import copy

START, END = "__start__", "__end__"


class Interrupt(Exception):
    """节点内 interrupt(payload) 抛出的信号：携带待办、触发图暂停。"""
    def __init__(self, payload: dict) -> None:
        self.payload = payload


def interrupt(payload: dict, resume=None):
    """暂停点：无 resume 值时抛出信号让图停下；有则直接返回人给的值。"""
    if resume is None:
        raise Interrupt(payload)
    return resume


class Graph:
    def __init__(self) -> None:
        self.checkpoints: dict[str, dict] = {}     ## thread_id -> 暂停态快照

    def _nodes(self):
        return ["extract", "score", "review", "ingest"]

    def run(self, state: dict, tid: str, resume=None) -> dict:
        nodes = self._nodes()
        ## 若是恢复：从检查点取回暂停态，跳到 review 继续
        if resume is not None and tid in self.checkpoints:
            snap = self.checkpoints[tid]
            state = copy.deepcopy(snap["state"])
            start_idx = nodes.index(snap["at"])
            print(f"[恢复] thread={tid} 从检查点续跑，resume={resume}")
        else:
            start_idx = 0
        for node in nodes[start_idx:]:
            if node == "extract":
                state = {**state, "fields": {"amount": 120000, "party": "甲公司"}}
            elif node == "score":
                state = {**state, "risk_score": 82}
                if state["risk_score"] <= 60:        ## 条件边：低风险跳过人工
                    print("[路由] 低风险，直接入库")
                    node_seq_skip = True
            elif node == "review":
                try:
                    decision = interrupt(            ## 暂停点
                        {"task": "请复核并批准/驳回", "fields": state["fields"],
                         "risk_score": state["risk_score"]},
                        resume=resume)
                except Interrupt as it:
                    self.checkpoints[tid] = {"at": "review", "state": copy.deepcopy(state)}
                    print(f"[暂停] 图在 review 暂停，待办抛给人：{it.payload['task']}")
                    print(f"[暂停] 状态已存检查点（thread={tid}），进程现在可安全退出")
                    return {"__status__": "interrupted", "payload": it.payload}
                state = {**state, "approved": decision}
                print(f"[续跑] 人给出结论 approved={decision}")
                resume = None                        ## 用掉 resume，后续正常跑
            elif node == "ingest":
                if not state.get("approved", True):
                    state = {**state, "result": "已驳回，未入库"}
                else:
                    state = {**state, "result": f"已入库：{state['fields']['party']}"}
        return state


def main() -> None:
    g = Graph()
    print("=== 第一次调用：跑到人工复核处暂停 ===")
    r1 = g.run({"docs": ["材料#1"]}, tid="T1")
    print("返回给调用方：", r1["payload"])

    print("\n=== （几小时后，可能换了台机器）人点了批准，恢复 ===")
    r2 = g.run({}, tid="T1", resume=True)
    print("最终状态：", {k: v for k, v in r2.items() if not k.startswith("__")})


if __name__ == "__main__":
    main()
```
保存为 `human_in_loop.py`，运行 `python human_in_loop.py`。完整预期输出：
```text
=== 第一次调用：跑到人工复核处暂停 ===
[暂停] 图在 review 暂停，待办抛给人：请复核并批准/驳回
[暂停] 状态已存检查点（thread=T1），进程现在可安全退出
返回给调用方： {'task': '请复核并批准/驳回', 'fields': {'amount': 120000, 'party': '甲公司'}, 'risk_score': 82}

=== （几小时后，可能换了台机器）人点了批准，恢复 ===
[恢复] thread=T1 从检查点续跑，resume=True
[续跑] 人给出结论 approved=True
最终状态： {'docs': ['材料#1'], 'fields': {'amount': 120000, 'party': '甲公司'}, 'risk_score': 82, 'approved': True, 'result': '已入库：甲公司'}
```
第一次调用跑到 `review` 就暂停、把待办 `payload` 返回给调用方，此时**进程可以安全退出**——状态在检查点 T1 里。几小时后（甚至在另一台机器上）用 `resume=True` 恢复，`interrupt` 返回 `True`、`review` 写入 `approved=True`、继续走 `ingest` 入库。把 `resume=True` 改成 `resume=False`，你会看到结果变成「已驳回，未入库」——**人的决定真正左右了图的走向**。

## 真实系统对应

**官方公开机制**：LangGraph HITL 文档明确 `interrupt(value)` 在节点内暂停图、把 `value` 抛给客户端、状态存入检查点，用 `Command(resume=...)` 恢复且 `interrupt` 返回该值；也支持编译时 `interrupt_before` / `interrupt_after` 设静态断点，配合 `update_state` 在恢复前改写状态；两者都要求编译时提供 checkpointer [来源](https://langchain-ai.github.io/langgraph/concepts/human_in_the_loop/)。官方还提示：含 `interrupt` 的节点在 resume 时会**从头重跑到 interrupt 处**，因此 interrupt 之前不要放不可重复的副作用 [来源](https://langchain-ai.github.io/langgraph/concepts/human_in_the_loop/)。**通用工程模式**：「把审批做成可存档断点、待办外抛、跨进程恢复」是可迁移到任何长流程审批的模式，回扣第 2、11 章「高风险动作必须有人工关口」。**教学参考实现**：上面的 `Interrupt` 异常与 `resume` 参数只演示语义，不复刻 LangGraph 真实的中断实现（它基于检查点与节点重放，而非简单异常）。

需要点明两个边界。其一，因为 resume 时节点会重放到 `interrupt`，**`interrupt` 之前的代码必须幂等或无副作用**——别在 `interrupt` 前扣款。其二，`interrupt` 解决的是「暂停/收人类输入/恢复」的机制，**它不替你做权限与审计**：谁能批、批的动作要不要留痕、驳回后走什么补偿流程，都是你在节点和 State 里要设计的业务逻辑。

## 生产踩坑

| 症状 | 根因 | 如何观测与复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| 等人期间进程被占死 | 用 sleep 轮询而非 interrupt | 看审批节点是否阻塞线程 | 改用 interrupt，暂停即释放进程 | 秒级同步确认可不暂停 |
| 等人时崩溃、审批状态全丢 | 暂停靠内存 while、无检查点 | 审批期间 kill 进程复现 | interrupt + checkpointer 存暂停态 | 无需等待的自动流程不涉及 |
| resume 后 interrupt 前的动作重复执行 | 在 interrupt 前放了副作用 | interrupt 前扣款、resume 看是否重扣 | 副作用移到 interrupt 之后或加幂等键 | interrupt 前纯计算无碍 |
| 恢复时报「找不到线程」 | resume 用了错的 thread_id | 换个 thread_id resume 复现 | resume 与暂停用同一 thread_id | 新会话本就无暂停态 |
| 待办无法在审批页展示 | interrupt 的 payload 没抛全信息 | 前端拿不到复核所需字段 | payload 带齐人决策所需上下文 | 无外部 UI 的场景另设 |
| 人驳回后仍继续入库 | 未按 resume 值分支处理 | resume=False 看是否仍入库 | 依 approved 走条件分支/补偿 | 只有批准一种结局时无碍 |

## 思考：判断一个业务「要不要上 LangGraph」，最灵的一条标准是什么？

### 回答

最灵的一条标准是问：**「这个流程里，有没有『必须停下来等人、或等外部事件，之后再从断点继续』的环节？」** 如果有——比如高额退款要人批准、合规材料要人复核、要等第三方回调才能继续——那几乎就是 LangGraph 的主场，因为它的 `interrupt` + 检查点能把「等待」做成可存档、不占进程、可跨进程恢复的断点，这是轻量框架用 `sleep` 硬做会非常别扭、且一崩就丢的地方。如果没有——流程一口气跑完、无需暂停无需审计——那 PydanticAI 或 smolagents 往往更简单够用，硬上 LangGraph 反而是杀鸡用牛刀，得写一堆图结构的样板。这条标准比「流程复不复杂」更好用，因为「复杂」很主观，而「有没有暂停/等待/人工关口」是个能一眼判定的客观特征。它背后的道理是：LangGraph 最不可替代的能力，恰恰长在「暂停与恢复」上（检查点 + interrupt），所以有这个需求时它的价值最大化，没有时它的成本最突出。

### 面试精简表达

看流程里有没有「必须停下等人/等外部事件、之后从断点继续」的环节。有就上 LangGraph（interrupt + 检查点是它最不可替代的能力）；没有就用更轻的框架，硬上是杀鸡用牛刀。

## 思考：为什么说「interrupt 必须配 checkpointer」？没有检查点会怎样？

### 回答

因为 `interrupt` 的本质是「暂停 + 之后恢复」，而「恢复」的前提是「暂停那一刻的状态被存下来了」——存状态这件事，正是 checkpointer 干的。没有 checkpointer，图暂停时状态只在内存里，一旦调用返回、进程去处理别的请求甚至退出，这份内存状态就没了，之后拿着 `Command(resume=...)` 来恢复时，根本找不到「从哪个状态、哪个节点接着跑」，恢复无从谈起。这也解释了为什么第 3 章的检查点是本章人工介入的地基：检查点先把「状态可持久、可按 thread_id 恢复」这件事做实，`interrupt` 才能在它之上实现「优雅暂停、跨进程恢复」。反过来看开头故障里的 `sleep` 硬等，正是「没有检查点的暂停」——它靠占着进程和内存来维持「暂停」，所以既占资源又怕崩溃。一句话——checkpointer 提供「可恢复的状态」，interrupt 提供「暂停与续跑的控制流」，二者缺一不可。

### 面试精简表达

interrupt 是「暂停+恢复」，恢复必须有「暂停时的状态」，而存状态正是 checkpointer 的职责。没有它，暂停态只在内存、进程一走就丢，resume 找不到从哪续跑——所以二者缺一不可。
