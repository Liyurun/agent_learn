## 真实问题

审核 Agent 上线两周后，出了一个诡异的 bug：同一份材料，有时抽取出 3 条风险点，有时只剩 1 条，且总是「最后一个节点写的那条」。团队一开始怀疑模型不稳定，换了温度、加了重试，没用。翻日志才发现真相：为了加速，他们把「合同风险」「财务风险」「合规风险」三个抽取节点改成了并行，三个节点都往状态里写同一个键 `risks`——每个节点返回 `{"risks": [自己那条]}`。而框架默认的合并规则是**覆盖（overwrite）**：三个节点的返回值合并时，后写的直接盖掉先写的，于是三条风险只活下来一条。这个 bug 的根因既不是模型、也不是并行本身，而是**没有给「需要累加的字段」配一个正确的 reducer**。

这一节要讲清 LangGraph 里最容易被轻视、其实最关键的东西——**状态（State）与通道（channel）reducer**。理解它，你就理解了「多个节点往同一个键写值时，到底发生了什么」，也就能避开上面这类「悄悄丢数据」的坑。

## 原理：状态是 schema，通道有 reducer

在 LangGraph 里，状态不是一个随手传的字典，而是一个**声明了字段与类型的 schema**，通常用 `TypedDict`、`dataclass` 或 Pydantic 模型定义 [来源](https://langchain-ai.github.io/langgraph/concepts/low_level/)。状态里的每一个键，官方称为一个**通道（channel）**。关键机制在于：**每个通道可以绑定一个 reducer 函数，决定「当一个超步里有新值写入这个通道时，如何与旧值合并」** [来源](https://langchain-ai.github.io/langgraph/concepts/low_level/)。

- **不指定 reducer（默认）**：新值**覆盖（overwrite）**旧值。适合「单一值、单一写者」的字段，如 `risk_score`、`approved`。
- **指定 reducer（如 `operator.add`）**：新值与旧值按 reducer 规则**合并**。用 `Annotated[list, operator.add]` 声明的列表通道，节点返回的增量会被**追加**而非覆盖。
- **`add_messages`**：LangGraph 内置的、专为对话消息设计的 reducer，能按消息 `id` 做「id-aware 归并」（同 id 更新、不同 id 追加），还支持用 `RemoveMessage` 删除 [来源](https://langchain-ai.github.io/langgraph/concepts/low_level/)。
```python
import operator
from typing import Annotated, TypedDict

class AuditState(TypedDict):
    docs: list[str]                          ## 只读输入，默认覆盖即可
    risk_score: int                          ## 单一值、单一写者 -> 默认覆盖
    approved: bool | None                    ## 单一结论 -> 默认覆盖
    risks: Annotated[list, operator.add]     ## 多节点并行写 -> 必须用追加型 reducer
    log: Annotated[list, operator.add]       ## 事件轨迹 -> 追加
```
一句话记住：**「这个字段会不会被多个节点、或在多个超步里写？如果会、且你想保留每次写入，就必须给它配 reducer；否则默认覆盖会悄悄丢数据。」**

## 现象与输入

把开头的 bug 用状态视角拆开，就能看清「覆盖」和「追加」的分水岭：
```text
三个抽取节点在同一超步并行，各自返回增量：
  contract_node -> {"risks": ["合同缺违约条款"]}
  finance_node  -> {"risks": ["应收账款异常"]}
  compliance_node -> {"risks": ["缺环评批复"]}

【risks 通道用默认覆盖（错误）】
  合并顺序不确定，最终 risks = ["缺环评批复"]   ← 另外两条被盖掉，悄悄丢数据

【risks 通道用 Annotated[list, operator.add]（正确）】
  三个增量依次追加，最终 risks =
    ["合同缺违约条款", "应收账款异常", "缺环评批复"]  ← 三条都在
```
问题的隐蔽性在于：**用默认覆盖时程序不报错、也能跑，只是数据悄悄少了。** 这类「静默丢失」比崩溃更难查——所以状态设计要在动手前想清楚「每个字段的合并语义」。

## 最小可运行演示

下面用纯 Python 复刻「通道 + reducer」的合并语义：一个超步里收集多个节点的增量，按每个通道声明的 reducer 合并回状态。它直观展示「覆盖」和「追加」的差别，无需安装 LangGraph、不需要 API Key。真实 LangGraph 用 `Annotated[type, reducer]` 声明，语义与此一致 [来源](https://langchain-ai.github.io/langgraph/concepts/low_level/)。
```python
"""教学参考实现：复刻 LangGraph 的通道 reducer 合并语义（无需安装 langgraph）。"""
from __future__ import annotations
import operator
from typing import Callable

## 通道 reducer 表：键 -> 合并函数；未登记的键默认"覆盖"
REDUCERS: dict[str, Callable] = {
    "risks": operator.add,   ## 列表追加
    "log": operator.add,
}


def overwrite(old, new):
    return new


def apply_updates(state: dict, updates: list[dict]) -> dict:
    """把同一超步里多个节点返回的增量，按各通道 reducer 依次合并。"""
    merged = dict(state)
    for update in updates:                       ## 遍历每个节点的返回增量
        for key, new_val in update.items():
            reducer = REDUCERS.get(key, overwrite)
            if key not in merged:
                merged[key] = new_val
            else:
                merged[key] = reducer(merged[key], new_val)
    return merged


def run() -> None:
    init = {"risks": [], "risk_score": 0, "log": []}

    ## 场景 A：三个并行节点都写 risks（追加型 reducer）
    parallel_updates = [
        {"risks": ["合同缺违约条款"], "log": ["contract done"]},
        {"risks": ["应收账款异常"], "log": ["finance done"]},
        {"risks": ["缺环评批复"], "log": ["compliance done"]},
    ]
    a = apply_updates(init, parallel_updates)
    print("risks（operator.add 追加）:", a["risks"])
    print("log:", a["log"])

    ## 场景 B：risk_score 是单一写者，默认覆盖
    b = apply_updates(a, [{"risk_score": 30}, {"risk_score": 82}])
    print("risk_score（默认覆盖，保留最后写入）:", b["risk_score"])

    ## 场景 C：演示"如果 risks 也用默认覆盖会怎样"
    global REDUCERS
    REDUCERS = {"log": operator.add}   ## 故意去掉 risks 的 reducer
    c = apply_updates(init, parallel_updates)
    print("risks（错误地用默认覆盖）:", c["risks"], "  <- 丢了两条！")


if __name__ == "__main__":
    run()
```
保存为 `channels.py`，运行 `python channels.py`。完整预期输出：
```text
risks（operator.add 追加）: ['合同缺违约条款', '应收账款异常', '缺环评批复']
log: ['contract done', 'finance done', 'compliance done']
risk_score（默认覆盖，保留最后写入）: 82
risks（错误地用默认覆盖）: ['缺环评批复']   <- 丢了两条！
```
场景 A 与场景 C 的对比就是开头那个 bug 的最小复现：同样三条增量，配了 `operator.add` 就三条都在，用默认覆盖就只剩最后一条。这也解释了为什么「状态是图的灵魂」——**通道的 reducer 决定了数据的去留，选错了，数据会静默丢失。**

## 真实系统对应

**官方公开机制**：LangGraph Low Level 文档明确「状态 schema 的每个键是一个通道，可用 `Annotated[type, reducer]` 为该通道指定 reducer；未指定时默认覆盖」，并把 `add_messages` 列为内置的消息专用 reducer（按 `id` 归并、支持 `RemoveMessage`）[来源](https://langchain-ai.github.io/langgraph/concepts/low_level/)。多个节点在一个超步里写同一通道时，reducer 决定合并方式，这也是官方描述的语义。**通用工程模式**：「为需要累加/去重/求极值的字段显式声明合并语义」是可迁移到任何状态合并场景的纪律；社区总结的 reducer 选择表（覆盖 / `operator.add` 追加 / `operator.or_` 并集 / `add_messages` id 归并 / 自定义 callable）是实用参考 [来源](https://langchain-ai.github.io/langgraph/concepts/low_level/)。**教学参考实现**：上面的 `apply_updates` 只演示合并语义，不复刻 LangGraph 真实的通道类型系统、超步调度与并行执行。

需要点明边界：真实 LangGraph 里，reducer 的意义在**并发写入**时最关键——同一超步内多个节点写同一通道，靠 reducer 安全合并；而跨超步的单写者字段，默认覆盖通常就够。选 reducer 的原则是「用能满足需求的最克制选项」：能覆盖就别追加，能追加就别写复杂自定义 [来源](https://langchain-ai.github.io/langgraph/concepts/low_level/)。

## 生产踩坑

| 症状 | 根因 | 如何观测与复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| 并行节点写同一键、数据只剩一条 | 该通道用了默认覆盖 | 三节点并行写 list、看最终长度 | 给累加通道声明 `operator.add` | 单一写者字段本就该覆盖 |
| 消息历史越滚越重复/错乱 | 用 `operator.add` 而非 `add_messages` | 同 id 消息更新后看是否变两条 | 消息通道用 `add_messages` 按 id 归并 | 非对话的普通列表用 add 即可 |
| 想删历史消息却删不掉 | 不知道有 `RemoveMessage` | 尝试用赋值删消息看是否生效 | 用 `add_messages` + `RemoveMessage` | 无需删除的场景不涉及 |
| 状态字段越加越多、难维护 | 把不该进状态的临时值也塞进去 | 统计 State 字段数与使用范围 | 只放「跨节点要共享」的数据 | 确需全程携带的上下文除外 |
| 自定义 reducer 偶发报错 | reducer 未处理旧值为 None/初值 | 首次写入时旧值缺失即复现 | reducer 兼容空初值、写单测 | 有默认初值的通道风险低 |
| 并发写非独立数据仍冲突 | reducer 只解决合并、不解决业务竞态 | 两节点并行改同一账户余额 | 非独立写改串行或加锁 | 天然独立的分片写可并行 |

## 思考：为什么说「状态是图的灵魂」？状态设计不好会怎样？

### 回答

因为状态承担了图里两件最关键的事，二者都绕不开它。第一，**节点之间的全部通信都靠状态**——节点是纯函数、彼此不传参，A 节点的产出要给 B 用，只能写进状态、B 再读出来。所以状态 schema 实际上定义了「图里有哪些信息在流动」。第二，**条件边的判断依据也是状态**——「下一步走哪」由 `router(state)` 读状态决定，这正是「状态机」三个字的由来。状态设计不好，两头都出问题：字段缺了，节点拿不到需要的上下文；合并语义错了（该追加的用了覆盖），数据会像开头 bug 那样静默丢失；字段冗余，图会变得难维护、检查点也变大。所以动手写图之前，第一件事不是写节点，而是**把 State 的字段和每个字段的合并语义想清楚**——这是图的地基。

### 面试精简表达

状态是节点唯一的通信方式，也是条件边选路的依据；schema 定义了「图里流动什么信息」。设计不好会导致上下文缺失、数据静默丢失（reducer 选错）、图难维护——所以先设计 State 再写节点。

## 思考：什么时候必须用 reducer？`operator.add` 和 `add_messages` 怎么选？

### 回答

判断标准只有一个：**这个通道会不会「在一个超步里被多个节点写」或「跨超步累积」，且你想保留每次写入？** 如果是——比如并行的多个抽取节点都往 `risks` 写、每轮对话都往 `messages` 追加——就必须配 reducer，否则默认覆盖会让你只剩最后一次写入。至于 `operator.add` 和 `add_messages` 的取舍：普通列表（风险点、日志、检索片段）用 `operator.add` 做简单拼接即可；但**对话消息**要用 `add_messages`，因为它是「id-aware」的——同一条消息被更新时按 `id` 归并而不是变成两条，还支持 `RemoveMessage` 删除消息。如果对消息也用 `operator.add`，更新一条消息就会追加成重复的两条，历史很快就乱。一句话——非消息的累加用 `operator.add`，对话消息一律用 `add_messages`。

### 面试精简表达

多写者或需累积且要保留每次写入时必须配 reducer。普通列表用 `operator.add` 拼接；对话消息用 `add_messages`，它按 id 归并、支持 RemoveMessage，避免更新变重复。

## 事故回放：一次「静默丢风险点」的复盘

回到开头的 bug。团队把三个抽取节点并行化时，只想着「并行更快」，没意识到三个节点写的是同一个通道 `risks`，而这个通道当时是默认覆盖。上线后症状是「风险点数量不稳定」，但因为程序不报错、总能给出一个「看起来合理」的结果，所以两周才被一个细心的合规同事发现——她记得某份材料明明该有三条风险，系统只报了一条。

修复只有一行：把 `risks: list` 改成 `risks: Annotated[list, operator.add]`。但复盘留下的教训比这行代码重要：**并行化不是「把串行改成并行」这么简单，一旦多个节点写同一个通道，就必须回答「这些写入该怎么合并」。** 团队后来立了一条规矩——任何要并行的节点，评审时必须列出「它写哪些通道、这些通道的 reducer 是什么、会不会和别的并行节点写冲突」。这条规矩之后，再没出过静默丢数据的事。这也印证了本节的主线：状态和它的合并语义，是图的灵魂，不是可有可无的配角。
