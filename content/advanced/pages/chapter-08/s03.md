## 真实问题

“少减五元”修复后期，Agent 要在一屏内给运营出一份对账：同时查订单、查当前优惠券规则、查支付网关流水。一开始工程师写成串行：查订单 300 毫秒、查规则 250 毫秒、查流水 400 毫秒，一轮下来近一秒，运营嫌慢。更糟的是有一次支付网关抖动，`get_payment` 抛异常，整个 `for` 循环直接崩溃，另外两个本已成功的结果也丢了，模型收到的是一条“Internal Error”，只能重来。问题有两层：独立的只读查询本可并发却串行；一个失败拖垮了整批。

这一节讲并行工具调用：现代模型能在一轮里同时提议多个调用，运行时该如何并发执行、按 `id` 乱序配对、以及“五个里一个失败”如何做部分降级而不是整批崩溃。

## 原理：一轮多调用、并发执行、id 配对、部分降级

官方明确支持“一轮多调用”。OpenAI 指出模型可能在一轮里调用多个函数，可用 `parallel_tool_calls=false` 关闭；在从 GPT-5 起的部分模型上，函数还能与内置工具并行（但内置工具不能进同一并行批）[来源](https://platform.openai.com/docs/guides/function-calling)。Anthropic 有专门的 Parallel tool use 文档，默认允许并行，可用 `tool_choice={"type":"auto","disable_parallel_tool_use":True}` 要求“每轮至多一个调用” [来源](https://platform.claude.com/docs/en/agents-and-tools/tool-use/overview) [来源](https://docs.anthropic.com/en/docs/agents-and-tools/tool-use/parallel-tool-use)。

运行时侧的四条原则：

1. **只对相互独立的操作并行**。同时查天气和查汇率是独立的；同时写同一份共享状态不是（后文详述）。
2. **用线程池并发**。工具多为 I/O 密集（网络、数据库），线程池能把总耗时从“各步之和”压到“最慢一步”。
3. **按 id 配对，不按顺序**。`as_completed` 让结果乱序到达，每个结果带 `tool_use_id`/`tool_call_id`，回传前按原始提议顺序重排即可稳定。
4. **部分失败降级**。每个调用独立捕获异常、转成带 `is_error` 的结果；一个失败不影响其余，把成功结果与错误一起回传，由模型决定重试还是降级作答。
```text
一轮三提议                     并发执行(耗时=最慢一步)          乱序完成 -> 按 id 重排
call_001 get_weather ┐        ┌ get_fx    最先(0.01s) ┐        call_001 [OK]
call_002 get_fx      ┼──并发──┤ get_weather (0.02s)   ┼──▶    call_002 [OK]
call_003 get_stock   ┘        └ get_stock  抛异常      ┘        call_003 [ERROR]
                                                              成功 2/3，部分降级
```
## 现象与输入

把对账场景的一轮拆成可观测字段：
```text
模型 -> 运行时（一轮三个独立调用）
  call_001 get_weather(city="北京")   ## 只读
  call_002 get_fx(pair="USDCNY")      ## 只读
  call_003 get_stock(code="600000")   ## 只读，但行情源此刻不可用

运行时并发执行，返回（乱序到达，按 id 重排后）：
  call_001 [OK]    晴 12C
  call_002 [OK]    7.10
  call_003 [ERROR] RuntimeError: 行情源不可用

回填给模型的一批结果里，成功与失败并存；模型可基于两项已知信息先作答，
或对 call_003 单独重试，而不是整批推倒重来。
```
## 最小可运行演示

下面用线程池模拟三个独立的 I/O 工具，其中 `get_stock` 故意抛异常。代码演示并发执行、`as_completed` 乱序完成、按 `id` 重排、以及部分失败降级。
```python
import time
from concurrent.futures import ThreadPoolExecutor, as_completed


def get_weather(city: str) -> str:
    time.sleep(0.02)
    return "晴 12C"


def get_fx(pair: str) -> str:
    time.sleep(0.01)
    return "7.10"


def get_stock(code: str) -> str:
    time.sleep(0.03)
    raise RuntimeError("行情源不可用")


REGISTRY = {"get_weather": get_weather, "get_fx": get_fx, "get_stock": get_stock}


def execute_one(call: dict) -> dict:
    cid, name, args = call["id"], call["name"], call["args"]
    try:
        out = REGISTRY[name](**args)
        return {"tool_use_id": cid, "content": out, "is_error": False}
    except Exception as exc:  ## 单个失败不影响整批
        return {"tool_use_id": cid, "content": f"{type(exc).__name__}: {exc}",
                "is_error": True}


def run_parallel(calls: list[dict]) -> list[dict]:
    results: list[dict] = []
    with ThreadPoolExecutor(max_workers=5) as pool:
        future_map = {pool.submit(execute_one, c): c for c in calls}
        for fut in as_completed(future_map):  ## 谁先完成谁先回，顺序被打乱
            results.append(fut.result())
    ## 靠 id 而非顺序做配对：按原始提议顺序重新排列，保证输出稳定
    order = {c["id"]: i for i, c in enumerate(calls)}
    results.sort(key=lambda r: order[r["tool_use_id"]])
    return results


def run() -> None:
    calls = [
        {"id": "call_001", "name": "get_weather", "args": {"city": "北京"}},
        {"id": "call_002", "name": "get_fx", "args": {"pair": "USDCNY"}},
        {"id": "call_003", "name": "get_stock", "args": {"code": "600000"}},
    ]
    results = run_parallel(calls)
    ok = sum(1 for r in results if not r["is_error"])
    for r in results:
        flag = "ERROR" if r["is_error"] else "OK"
        print(f"{r['tool_use_id']} [{flag}] {r['content']}")
    print(f"成功 {ok}/{len(results)}，部分失败降级：把已成功结果与错误一并回传模型")


if __name__ == "__main__":
    run()
```
保存为 `parallel.py`，运行 `python parallel.py`。完整预期输出：
```text
call_001 [OK] 晴 12C
call_002 [OK] 7.10
call_003 [ERROR] RuntimeError: 行情源不可用
成功 2/3，部分失败降级：把已成功结果与错误一并回传模型
```
注意：尽管 `get_fx` 最先完成、`get_stock` 最后完成，最终输出仍按 `call_001/002/003` 稳定排列——因为我们用 `id` 而非到达顺序重排。这就是 `id` 配对在并行下的价值，也是输出可复核的原因。

## 真实系统对应

**官方公开机制**：OpenAI 用 `parallel_tool_calls` 控制是否允许一轮多调用，并说明内置工具不能进并行批 [来源](https://platform.openai.com/docs/guides/function-calling)；Anthropic 默认允许并行，可用 `disable_parallel_tool_use` 关闭 [来源](https://platform.claude.com/docs/en/agents-and-tools/tool-use/overview)。两家都要求回填时把**同一轮所有调用的结果**一并带回，且各自引用对应 `id`。**通用工程模式**：线程池并发 + `as_completed` + `id` 重排 + 部分降级，是可迁移到任何厂商的执行骨架。**教学参考实现**：上面的 `time.sleep` 只为模拟 I/O 耗时，真实系统用真正的网络/数据库客户端，并要加超时（见第 6 节）。

一个官方顺序约束的推论：Anthropic 要求含结果的 user 消息里 `tool_result` 块紧跟 `tool_use` 且排在文本前 [来源](https://platform.claude.com/docs/en/agents-and-tools/tool-use/handle-tool-calls)。因此并行的多个结果必须**在同一条 user 消息里**成组回填，而不是拆成多条消息——这也是“按 id 重排后一次性回填”的协议依据。

## 生产踩坑

| 症状 | 根因 | 如何观测与复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| 一个工具异常整批崩溃 | 未在单调用内捕获异常 | 让一个工具抛异常复现 | 每个调用独立 try，转 is_error | 致命错误确需整体中止时例外 |
| 并发写共享状态丢更新 | 对非独立操作强行并行 | 同时写同一购物车复现竞态 | 有写冲突的调用串行或加锁 | 独立分片写可并行 |
| 结果错配到别的问题 | 按到达顺序拼结果 | 让快慢工具并存复现错配 | 按 id 重排后回填 | 单调用顺序恰好一致会掩盖 |
| 并行没有变快 | 工具是 CPU 密集，GIL 限制 | 对比串并行耗时 | CPU 密集改用进程池或异步下沉 | I/O 密集用线程池即可 |
| 少数慢工具拖住整轮 | 未设单调用超时 | 注入一个卡死工具复现 | 每调用超时罩，超时转 is_error | 明确允许长任务的场景另设 |
| 部分失败被当全部失败 | 未把成功结果一起回传 | 只回传错误复现模型重来 | 成功与错误一并回传由模型决策 | 关键调用失败需整体降级时例外 |

## 思考：五个并行工具调用中一个失败了，应该怎么办？

### 回答

三步。第一，失败的那个调用返回结构化错误（带 `is_error=true`），绝不让它的异常冒泡到主循环导致整批崩溃。第二，把四个成功结果与这一个错误**一起**回填给模型——同一轮的结果要成组回传，各自带 `id`。第三，把决策权交给模型：它可以基于四项已知信息先给出部分答案并说明第五项缺失，也可以只对失败项单独重试（若该工具幂等或只读，重试安全）。核心是“部分失败降级”：一个失败只损失一个数据点，而不是让整轮归零。运行时的职责是保证“失败被隔离、信息不丢、决策可继续”。

### 面试精简表达

隔离失败、成组回传、把重试还是降级的决策交给模型；一个失败只塌一格，不塌整批。

## 事故回放：并发写购物车丢失的那一单

另一个真实反例：一个导购 Agent 在一轮里同时提议 `add_to_cart(A)` 和 `add_to_cart(B)`，工程师图快把两者并行。购物车服务端用“读取-修改-写回”更新，没有加锁：两个线程几乎同时读到同一份空车，各自加入一件商品后写回，后写的覆盖了先写的，结果只剩一件。用户投诉“明明加了两件只剩一件”，日志里两个调用都返回成功，排查一度陷入僵局。

根因是把**非独立操作**当独立操作并行了：两个调用写同一份共享状态（购物车），存在竞态。修复有两条路：要么让写同一资源的调用串行执行；要么让服务端用原子操作或乐观锁（带版本号的 compare-and-set）。团队选了后者，并把“是否写同一资源”作为并行前的判定条件写进执行器。教训很直接：**并行的前提永远是“操作相互独立”**，只读查询天然独立，写操作要先问“会不会撞同一份状态”。

## 机制推导：并行度、超时与成本的三角

并行不是免费的。它引入三个要相互权衡的量。其一，并行度（线程池大小）：太小则退化为串行，太大则可能压垮下游服务或触发限流，通常按下游承载能力设上限。其二，单调用超时：并行时一个慢工具会拖住整轮的回填时机（要等所有 future 完成或超时），因此每个调用都要有独立超时，超时即转 `is_error`，不阻塞其余（详见第 6 节）。其三，成本：一轮多调用会让这一轮的输出 token 变多，且每个结果都要在下一轮随历史重发——并行省了墙钟时间，但没省 token，反而可能因结果更多而增加后续轮次的输入量。

因此工程上的常见姿势是：只读、独立、幂等的调用尽量并行以降延迟；有副作用或写共享状态的调用串行并配幂等键；并对并行批设一个合理的并行度与统一超时。把这三角想清楚，才不会为了“看起来并发”而引入竞态和限流。
