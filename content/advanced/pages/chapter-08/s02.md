## 真实问题

“少减五元”项目里有两个后端：一个走 OpenAI 兼容接口，一个走 Anthropic Messages。同一套结算工具，团队复制粘贴了两份几乎一样的处理代码，结果 Bug 只在其中一个后端出现：Anthropic 分支里，工程师把工具结果写成了 `{"role": "tool", "content": ...}`——这是 OpenAI 的形状；Anthropic 需要的是一条 `role=user` 的消息，内部放一个 `tool_result` 块，并带 `tool_use_id`。请求直接被 API 以 400 拒绝，报错说“找不到与 tool_use 对应的 tool_result 块”。这类问题不是逻辑错，而是**协议形状**记混了。

这一节把两家的工具 Schema 与消息协议摆在一起对照，抽出三个稳定共性：工具定义都用 JSON Schema（JavaScript Object Notation Schema，一种用 JSON 描述数据结构与约束的规范）；调用里都带一个 `id`；结果回填都要引用这个 `id`。看清共性与差异，就能用一个归一化层把两套折叠成同一份内部代码。

## 原理：三种消息角色与两家的字段映射

一次工具调用往返涉及三种“消息角色/块”：

1. **工具定义**：随请求发给模型，是 input token 的一部分。OpenAI Chat Completions 放在 `tools[i].function.{name, description, parameters}`；OpenAI Responses API 放在 `tools[i].{type:"function", name, description, parameters, strict}`；Anthropic 放在顶层 `{name, description, input_schema}` [来源](https://platform.openai.com/docs/guides/function-calling) [来源](https://platform.claude.com/docs/en/agents-and-tools/tool-use/overview)。
2. **工具调用（模型 → 你）**：OpenAI 是 assistant 消息里的 `tool_calls[i] = {id, function:{name, arguments}}`，其中 `arguments` 是**字符串化的 JSON**；Anthropic 是 assistant 内容里的 `{type:"tool_use", id, name, input}`，其中 `input` 已是**对象**。
3. **工具结果（你 → 模型）**：OpenAI 用一条 `{role:"tool", tool_call_id, content}`（Responses API 用 `{type:"function_call_output", call_id, output}`）；Anthropic 用一条 `{role:"user", content:[{type:"tool_result", tool_use_id, content, is_error?}]}` [来源](https://platform.claude.com/docs/en/agents-and-tools/tool-use/handle-tool-calls)。

一张对照表钉住差异：

| 环节 | OpenAI Chat Completions | OpenAI Responses | Anthropic Messages |
|---|---|---|---|
| 工具定义键 | tools[].function.parameters | tools[].parameters | input_schema |
| 严格模式 | function.strict=true | strict=true | strict=true（自定义工具） |
| 调用容器 | message.tool_calls[] | output 里的 function_call | content 里的 tool_use 块 |
| 调用 id 字段 | tool_calls[].id | function_call.call_id | tool_use.id |
| 参数字段 | function.arguments（字符串） | arguments（字符串） | input（对象） |
| 回填消息角色 | role=tool | function_call_output | role=user + tool_result 块 |
| 回填引用 id | tool_call_id | call_id | tool_use_id |
| 错误标记 | 约定放进 content | 约定放进 output | is_error=true 字段 |

三个不变的共性：工具定义都是 JSON Schema；调用都带 `id`；结果都靠 `id` 配对。差异集中在“参数是字符串还是对象”“回填用什么角色”。

## 为什么工具定义统一选 JSON Schema

这里值得深挖一个“为什么”：为什么两家不约而同用 JSON Schema 描述参数，而不是自然语言或自造 DSL（Domain-Specific Language，领域特定语言）？

- **模型见过海量 JSON Schema**。预训练语料里充斥 OpenAPI 与 JSON Schema 文档，模型对这种格式的“填空”能力极强，生成合法 JSON 的概率远高于自造格式。
- **可机器校验**。Schema 天生可被程序逐字段校验（类型、枚举、必填、嵌套），运行时能在执行前挡下非法参数——这正是第 1 节阶段③的核心工作。
- **可约束解码与严格模式**。OpenAI 提供 `strict: true` 让函数调用严格贴合 Schema，Anthropic 也提供 strict tool use 保证调用与 Schema 完全一致 [来源](https://platform.openai.com/docs/guides/function-calling) [来源](https://platform.claude.com/docs/en/agents-and-tools/tool-use/overview)。这把“合规”从事后清洗前移到了生成阶段。

一个把每个字段“说人话”的工具定义示例（以 Anthropic 形状为例，OpenAI 只是外层包装不同）：
```text
{
  "name": "get_coupon_rule",
  "description": "按优惠券 id 查询当前生效的满减规则；仅用于读取，不修改任何订单；不要用于下单或扣款。",
  "input_schema": {
    "type": "object",
    "properties": {
      "coupon_id": {"type": "string", "description": "优惠券编号，如 C-88"}
    },
    "required": ["coupon_id"]
  }
}
```
`description` 是**写给模型的 prompt**：它不仅说“能做什么”，还划清“不要用于下单或扣款”这条负向边界，显著降低模型在近义工具间选错的概率。

## 最小可运行演示

下面这段代码把两家的工具定义各构造一份，再用一个 `normalize_call` 归一化函数把两家的工具调用折叠成同一内部结构 `{id, name, args}`，最后按各自协议生成回填消息。核心是证明：**内部逻辑只需一套，差异隔离在归一化层**。
```python
import json


def openai_tool(name, desc, schema):
    ## OpenAI Chat Completions：tools[i].function.{name,description,parameters}
    return {"type": "function",
            "function": {"name": name, "description": desc, "parameters": schema}}


def anthropic_tool(name, desc, schema):
    ## Anthropic Messages：顶层 name/description/input_schema
    return {"name": name, "description": desc, "input_schema": schema}


def normalize_call(vendor: str, raw: dict) -> dict:
    """把两家的工具调用折叠成统一内部结构：{id, name, args}。"""
    if vendor == "openai":
        ## assistant.message.tool_calls[i] = {id, function:{name, arguments(str)}}
        return {"id": raw["id"], "name": raw["function"]["name"],
                "args": json.loads(raw["function"]["arguments"])}
    if vendor == "anthropic":
        ## assistant.content[i] = {type:tool_use, id, name, input(dict)}
        return {"id": raw["id"], "name": raw["name"], "args": raw["input"]}
    raise ValueError(f"未知厂商 {vendor}")


def result_message(vendor: str, call_id: str, content: str) -> dict:
    """回填结果时的消息形状差异：OpenAI 用 role=tool，Anthropic 用 tool_result 块。"""
    if vendor == "openai":
        return {"role": "tool", "tool_call_id": call_id, "content": content}
    return {"role": "user",
            "content": [{"type": "tool_result", "tool_use_id": call_id,
                         "content": content}]}


def run() -> None:
    schema = {"type": "object",
              "properties": {"city": {"type": "string"}},
              "required": ["city"]}
    print("OpenAI 工具定义:", json.dumps(openai_tool("get_weather", "查天气", schema),
                                     ensure_ascii=False))
    print("Anthropic 工具定义:", json.dumps(anthropic_tool("get_weather", "查天气", schema),
                                        ensure_ascii=False))

    oai_call = {"id": "call_a", "function": {"name": "get_weather",
                                             "arguments": '{"city": "北京"}'}}
    ant_call = {"type": "tool_use", "id": "toolu_b", "name": "get_weather",
                "input": {"city": "北京"}}
    n1 = normalize_call("openai", oai_call)
    n2 = normalize_call("anthropic", ant_call)
    print("归一化(OpenAI):", n1)
    print("归一化(Anthropic):", n2)
    print("两家结构一致:", n1["name"] == n2["name"] and n1["args"] == n2["args"])
    print("回填(OpenAI):", result_message("openai", n1["id"], "晴 12C"))
    print("回填(Anthropic):", result_message("anthropic", n2["id"], "晴 12C"))


if __name__ == "__main__":
    run()
```
保存为 `protocol.py`，运行 `python protocol.py`。完整预期输出：
```text
OpenAI 工具定义: {"type": "function", "function": {"name": "get_weather", "description": "查天气", "parameters": {"type": "object", "properties": {"city": {"type": "string"}}, "required": ["city"]}}}
Anthropic 工具定义: {"name": "get_weather", "description": "查天气", "input_schema": {"type": "object", "properties": {"city": {"type": "string"}}, "required": ["city"]}}
归一化(OpenAI): {'id': 'call_a', 'name': 'get_weather', 'args': {'city': '北京'}}
归一化(Anthropic): {'id': 'toolu_b', 'name': 'get_weather', 'args': {'city': '北京'}}
两家结构一致: True
回填(OpenAI): {'role': 'tool', 'tool_call_id': 'call_a', 'content': '晴 12C'}
回填(Anthropic): {'role': 'user', 'content': [{'type': 'tool_result', 'tool_use_id': 'toolu_b', 'content': '晴 12C'}]}
```
“两家结构一致: True”是这段代码的立意：归一化后，你的执行器、校验器、并行调度器都只面向 `{id, name, args}`，与厂商无关。要接第三家，只需再加一个归一化分支。

## 真实系统对应

**官方公开机制**：OpenAI 明确 `arguments` 是字符串、需要 `json.loads`，且回填用 `role="tool"` + `tool_call_id`（Chat Completions）或 `function_call_output` + `call_id`（Responses）[来源](https://platform.openai.com/docs/guides/function-calling)；Anthropic 明确 `tool_result` 块必须紧跟对应 `tool_use`、且在含结果的 user 消息里 `tool_result` 块必须排在任何文本之前，否则报 400 [来源](https://platform.claude.com/docs/en/agents-and-tools/tool-use/handle-tool-calls)。Anthropic 还特意指出：与用 `tool`/`function` 特殊角色的 API 不同，它把工具直接嵌进 `user`/`assistant` 消息结构 [来源](https://platform.claude.com/docs/en/agents-and-tools/tool-use/handle-tool-calls)。**通用工程模式**：用归一化层把厂商差异折叠成单一内部表示，是可迁移的多后端设计。**教学参考实现**：上面的 `normalize_call` 只覆盖两家最常见形状，不含流式增量、思考块、服务端工具等细节。

一个务必记住的官方硬约束：Anthropic 要求 `tool_result` 紧跟 `tool_use`，中间不能插入其它消息；含结果的 user 消息里 `tool_result` 必须在文本前面。开头那个 400 错误，一半是角色写错，一半就是顺序约束没遵守。

## 生产踩坑

| 症状 | 根因 | 如何观测与复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| Anthropic 400：找不到 tool_result | 用了 role=tool 的 OpenAI 形状 | 直接回放被拒请求体 | 用 tool_result 块 + tool_use_id | OpenAI 后端本就用 role=tool |
| 400：文本在 tool_result 之前 | 违反“结果块在前”顺序约束 | 在结果前加一句文本即复现 | 结果块排最前，文本置后 | 无文本时不触发 |
| json.loads 报错 | 忘了 OpenAI arguments 是字符串 | 直接把 arguments 当 dict 用 | 归一化层统一解析 | Anthropic input 已是对象 |
| 两个后端行为漂移 | 复制粘贴两份处理代码 | diff 两分支逻辑 | 归一化到单一内部结构 | 厂商独有能力需单独分支 |
| 模型频繁选错近义工具 | 描述缺少负向边界 | 记录候选与实际调用 | 描述写清“何时不要用” | 工具本就语义重叠需重设计 |
| 严格模式仍出非法值 | 误以为 strict 覆盖业务约束 | 构造越业务界但合 Schema 的值 | 业务校验独立于 Schema | strict 只保证结构合规 |

## 思考：为什么工具调用要携带 id，而不能用返回顺序配对？

### 回答

因为一轮可能包含多个工具调用，它们并发执行、返回顺序不可预测。若用“第 k 个返回配第 k 个提议”，只要有一个调用比另一个先完成，配对就全乱：模型会把汇率数字当成天气、把股价当成库存。`id` 是每次调用的身份证，回填时原样带回（OpenAI 的 `tool_call_id`、Anthropic 的 `tool_use_id`），无论结果乱序到什么程度都能精确配回。更重要的是，`id` 让“配对”从一个脆弱的时序假设，变成一个稳定的显式契约——这也是并行调用（第 3 节）能安全落地的前提。

### 反例

有团队为省事，在并行执行后按 `as_completed` 的到达顺序直接拼结果，测试时只有一个工具、顺序恰好一致，上线后并发两个工具立刻错配。教训：任何时候都用 `id` 配对，哪怕当前只有一个调用。

## 机制推导：从“参数是字符串”看解析风险

OpenAI 把 `arguments` 设计成字符串化 JSON，是为了让流式传输时能逐段拼接（第 4 节详述），但这给非流式使用者埋了两个坑。其一，必须 `json.loads` 后才是对象，忘记解析会在后续 `**args` 展开时炸掉。其二，字符串可能是**不完整或非法的 JSON**——尤其在流式未收齐、或模型偶发截断时。因此归一化层的正确姿势是：解析失败不抛裸异常，而是转成一条带错误标记的结果回传模型，让它重新生成（这与第 6 节的错误恢复一致）。

Anthropic 把 `input` 直接给成对象，省去了解析步骤，但流式时它同样是分片累积、到 `content_block_stop` 才成为完整对象 [来源](https://docs.anthropic.com/en/docs/build-with-claude/streaming)。可见“字符串 vs 对象”只是最终形态的差异，底层都要面对“增量拼接、收齐才可用”的现实。理解这一点，就不会在流式场景里对半截参数贸然执行——那正是第 4 节要解决的问题。
