## 真实问题

“少减五元”故障的第一现场，是运维截出的一段请求日志。上午九点零七分，结算 Agent 向模型发出请求，附带四个工具定义与用户消息“修复订单 A-2026 的优惠券少减五元”。模型返回的不是文本，而是一个结构化调用 `get_coupon_rule(coupon_id="C-88")`。运维当时的第一反应是“模型自己去查规则库了”，于是去规则库排查连接。这个判断错得离谱：模型从没碰过规则库，它只是**输出了一张想调用的申请单**，真正的查询是运行时代码在九点零七分零三秒发起的。方向错了，前二十分钟全白排。

这一节要把这条“模型只说、运行时才做”的边界钉死，并给出一次工具调用从请求到回填再到终止的完整、可观测生命周期。它是后面所有小节的地基：把生命周期看清楚，参数校验、并行、流式、错误恢复才有位置可挂。

## 原理：五个阶段与两条铁律

OpenAI 官方把工具调用流程明确概括为五步 [来源](https://platform.openai.com/docs/guides/function-calling)：（1）带着可用工具向模型发请求；（2）从模型收到一个工具调用；（3）在应用侧用工具调用里的输入执行代码；（4）带着工具输出发第二次请求；（5）从模型收到最终回复（或更多工具调用）。Anthropic 的 Tool use 概览描述的是同一趟往返：传入带 `input_schema` 的工具，模型以 `stop_reason: "tool_use"` 和一个或多个 `tool_use` 块回应，你的代码执行后用 `tool_result` 把结果送回，模型再据此作答 [来源](https://platform.claude.com/docs/en/agents-and-tools/tool-use/overview)。措辞不同，机制一致。

把五步压成两条必须刻进脑子的铁律：

- **铁律一：模型只“说”，不“做”。** 模型输出的是描述“想调什么、传什么参数”的结构化块，网络请求、数据库写入、文件操作全部由运行时执行。因此安全防线必须建在运行时，而不能寄希望于“让模型别乱来”。
- **铁律二：阶段③④之间会循环，且模型无状态。** 一次提问可能触发多轮“提议—执行—回填”，直到模型给出纯文本才终止。而模型不记得上一轮，上下文全靠你每轮重新携带——轮次越多，token 消耗越大。
```text
用户            你的运行时(Runtime)            大模型(LLM)            外部世界(API/DB)
 │                    │                           │                       │
 │──提问────────────▶ │                           │                       │
 │                    │──①工具定义 + 消息─────────▶│                       │
 │                    │                           │──②推理:需要工具──      │
 │                    │◀──tool_calls(id,name,args)─│                       │
 │                    │──③存在性/参数/权限校验──    │                       │
 │                    │──③真正执行──────────────────────────────────────▶ │
 │                    │◀──返回结果 / 抛异常────────────────────────────────│
 │                    │──④tool_result(id, 内容)──▶│                       │
 │                    │                           │──推理:够了吗?──         │
 │                    │◀──(不够)再来一个 tool_use ─│  ↺ 回到第③步           │
 │                    │◀──(够了)⑤纯文本答案────────│                       │
 │◀──最终答案─────────│                           │                       │
```
## 现象与输入

把“少减五元”的第一轮拆成可观测字段，就能看清模型到底“说”了什么、运行时又“做”了什么：
```text
① 运行时 -> 模型（第一次请求）
   tools = [get_order, get_coupon_rule, apply_discount, charge_customer]
   messages = [{"role":"user","content":"修复订单 A-2026 的优惠券少减五元"}]

② 模型 -> 运行时（结构化申请单，无任何副作用）
   {"type":"tool_use","id":"call_002","name":"get_coupon_rule",
    "input":{"coupon_id":"C-88"}}

③ 运行时执行（副作用/查询在此刻才真正发生）
   get_coupon_rule("C-88") -> "满100减5，rule_version=v3"

④ 运行时 -> 模型（第二次请求，回填结果，带 id）
   {"type":"tool_result","tool_use_id":"call_002","content":"满100减5，rule_version=v3"}

⑤ 模型 -> 运行时（信息够了，纯文本，自然终止）
```
关键点在②与③之间那道缝：模型在②只是填了申请单，`id=call_002` 是这次调用的“身份证”；真正的查询发生在③。运维把②误当成③，才排错了方向。

## 最小可运行演示

下面用一个确定性的 `FakeModel` 代替真实大模型，走完请求→返回 tool_calls→执行→回填→再请求→终止的完整闭环，并打印每一步事件。它不联网、不需要 API Key，是本章生命周期的“可执行版时序图”。
```python
import json


class FakeModel:
    """确定性假模型：第 1 轮返回一个工具调用，拿到结果后第 2 轮给纯文本。"""

    def __init__(self) -> None:
        self.round = 0

    def create(self, messages: list[dict]) -> dict:
        self.round += 1
        if self.round == 1:
            ## 模型只是"填一张申请单"，没有任何副作用
            return {
                "role": "assistant",
                "content": [
                    {"type": "text", "text": "我需要查一下北京的天气。"},
                    {"type": "tool_use", "id": "call_001",
                     "name": "get_weather", "input": {"city": "北京"}},
                ],
            }
        ## 第 2 轮：看到 tool result 后收敛为纯文本，无 tool_use = 自然终止
        last = messages[-1]["content"][0]["content"]
        return {"role": "assistant",
                "content": [{"type": "text", "text": f"北京现在{last}。"}]}


def get_weather(city: str) -> str:
    table = {"北京": "晴，12 摄氏度", "上海": "多云，15 摄氏度"}
    return table.get(city, "未知城市")


def run() -> None:
    model = FakeModel()
    registry = {"get_weather": get_weather}
    messages: list[dict] = [{"role": "user", "content": "北京天气怎么样？"}]
    trace: list[str] = []

    for turn in range(1, 6):  ## 硬性轮次上限，防死循环
        resp = model.create(messages)
        messages.append(resp)
        calls = [b for b in resp["content"] if b.get("type") == "tool_use"]
        if not calls:  ## 无工具调用 = 自然终止
            trace.append(f"[T{turn}] 模型给出最终答案，循环结束")
            print("\n".join(trace))
            text = next(b["text"] for b in resp["content"] if b["type"] == "text")
            print("FINAL:", text)
            return
        results = []
        for call in calls:
            trace.append(f"[T{turn}] 模型提议 {call['name']}({call['input']}) id={call['id']}")
            fn = registry[call["name"]]           ## 真正执行发生在运行时
            out = fn(**call["input"])
            trace.append(f"[T{turn}] 运行时执行完成 -> {out}")
            results.append({"type": "tool_result", "tool_use_id": call["id"],
                            "content": out})
        messages.append({"role": "user", "content": results})  ## 回填结果，带 id


if __name__ == "__main__":
    run()
```
保存为 `lifecycle.py`，运行 `python lifecycle.py`。完整预期输出：
```text
[T1] 模型提议 get_weather({'city': '北京'}) id=call_001
[T1] 运行时执行完成 -> 晴，12 摄氏度
[T2] 模型给出最终答案，循环结束
FINAL: 北京现在晴，12 摄氏度。
```
这段轨迹逐字对应五个阶段：T1 的“提议”是②，“执行完成”是③，追加 `tool_result` 是④，T2 的纯文本是⑤。把 `FakeModel` 换成真实客户端、把 `get_weather` 换成真实函数，主循环骨架一行都不用改——这正是生命周期抽象的价值。

## 真实系统对应

**官方公开机制**：OpenAI 文档给出的五步流程与本节完全一致，并在 Chat Completions 里用 `role="tool"` + `tool_call_id` 回填结果，在 Responses API 里用 `function_call_output` + `call_id` 回填 [来源](https://platform.openai.com/docs/guides/function-calling)；Anthropic 文档明确“客户端工具由你的应用执行，模型返回 `tool_use`、你返回 `tool_result`”，并强调 `tool_result` 必须紧跟对应的 `tool_use` [来源](https://platform.claude.com/docs/en/agents-and-tools/tool-use/handle-tool-calls)。**通用工程模式**：把“提议—执行—回填—再请求”抽象成一个带轮次上限的主循环，是可迁移到任何厂商的骨架。**教学参考实现**：上面的 `FakeModel` 只为演示时序，不代表任何产品的推理逻辑或消息拼接顺序。

需要点明一个边界：Anthropic 还有“服务端工具”（如 web_search、code_execution），由 Anthropic 基础设施执行，你直接拿到结果、无需回填 [来源](https://platform.claude.com/docs/en/agents-and-tools/tool-use/overview)。本章聚焦“客户端工具”这条主线——因为它才是“模型只说、运行时才做”这条铁律的舞台；服务端工具属于另一类执行位置，不要混为一谈。

## 生产踩坑

| 症状 | 根因 | 如何观测与复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| 排错方向对准“模型直连外部” | 误把“提议”当“执行” | 打印②③两个时间戳，看副作用发生在运行时 | 把安全与重试逻辑全落在运行时 | 服务端内置工具确实由厂商执行 |
| 循环永不终止、token 烧光 | 只靠自然终止、无轮次上限 | 让工具总返回“查无结果”即可复现 | for turn in range(max_turns) 兜底 | 明确单步任务可不设循环 |
| 第二轮模型“失忆” | 未把历史重新发给无状态模型 | 只发最后一条消息即复现 | 每轮携带完整 messages | 服务端会话托管场景另算 |
| 结果配错调用 | 回填时丢了 id 或按顺序配对 | 打乱结果顺序复现错配 | 回填务必带 tool_use_id/tool_call_id | 单调用时顺序恰好一致会掩盖 |

## 思考：为什么说“模型只说不做”是整个 Function Calling 的地基？

### 回答

因为它决定了安全、可靠、可观测三件事各自的归属。安全：模型的输出必须当成不可信输入来校验，防线只能建在运行时；如果误以为模型“亲自”执行，就会去给模型加“请不要乱调”的提示词，而这毫无强制力。可靠：副作用（扣款、发信、删文件）只发生在运行时的一行代码里，幂等、重试、超时都要在那一行周围做，而不是指望模型不重复提议。可观测：要复盘一次故障，必须分别抓“模型说了什么（tool_use）”和“运行时做了什么（真实执行 + 返回）”两份证据；把二者混为一谈，就会像开头运维那样排错方向。

### 面试精简表达

模型输出的是意图，运行时执行的是动作；把意图当动作，安全、幂等、审计三者的落点就全错了。

## 事故回放：二十分钟排错方向为何全错

回到“少减五元”。运维看到模型返回 `get_coupon_rule` 调用，就断定“模型连了规则库”，于是查规则库的连接池、慢查询、超时——全部正常，因为模型压根没连过规则库。真正的调用发生在运行时那一行 `registry["get_coupon_rule"](coupon_id="C-88")`，而当时运行时日志级别是 WARNING，这行 INFO 级执行日志没落盘，于是“运行时做了什么”这份证据缺失，排查只能对着“模型说了什么”空转。

把生命周期补全后，修复很直接：运行时对每次执行打一条结构化日志，字段包含 `turn`、`tool_use_id`、`name`、`args_digest`、`latency_ms`、`exit`。这样再遇到问题，第一眼就能回答“模型提议了什么、运行时是否执行、执行结果与耗时”。这不是“日志越多越好”，而是让日志能回答“②和③哪一步先偏离预期”。优化前只有一条“Agent 出错”的告警；优化后，每一轮都有可追溯的提议与执行配对证据。

## 机制推导：从无状态到“每轮重发历史”的成本结构

模型是无状态的：它不记得上一轮发生了什么，第 N 轮的输入必须包含前 N-1 轮的全部消息。这意味着一次三轮的工具调用，工具定义与早期消息会被重复发送三次，input token 随轮数近似线性增长。开头故障里，四个工具定义加起来上千 token，模型每轮都要重读一遍——这就是 Function Calling 成本的主要来源，也是“工具不是越多越好”的根因（详见第 2 节的 Schema 成本讨论）。

由此推出两条工程结论。其一，控制“同时暴露的工具数量”既是选择准确率问题，也是成本问题：轮次越多，冗余工具定义被重发的次数越多。其二，轮次上限不仅防死循环，也是成本闸门：把 `max_turns` 设为业务能接受的上界，触顶就降级返回，避免“模型换着关键词无限重试”把预算烧光。这两条会在第 5、第 7 节被反复用到。
