## 真实问题

对账 Agent 上了流式（streaming）后，前端能边生成边显示，体验好了很多。但灰度第二天出现一个诡异 Bug：某些请求偶发报 `JSONDecodeError`，且总在长参数工具上。定位发现，工程师为了“更快执行”，在流式回调里每收到一段工具参数分片就尝试 `json.loads` 并立即执行——而流式下工具参数是**一段段的部分 JSON 字符串**，收到 `{"location":` 时就解析，当然报错。更危险的是有一次半截参数恰好是合法 JSON 的前缀，被解析成了残缺对象直接执行，查了错误的城市。

这一节讲流式场景下如何正确解析工具参数：官方为什么用“部分 JSON 增量”传输、如何累积分片、以及为什么必须等收齐（`content_block_stop`）才能执行。

## 原理：input_json_delta 与“收齐才可用”

Anthropic Streaming 文档把机制说得很清楚：`tool_use` 内容块的 delta 对应 `input` 字段的更新；为支持最大粒度，这些 delta 是**部分 JSON 字符串**（`input_json_delta` 的 `partial_json`），而最终的 `tool_use.input` 始终是一个对象。官方建议：累积这些字符串分片，等收到 `content_block_stop` 事件后再解析 JSON，或用支持部分解析的库、或直接用 SDK 提供的增量取值 helper [来源](https://docs.anthropic.com/en/docs/build-with-claude/streaming)。

一条流的事件流结构是：`message_start` → 若干内容块（每块 `content_block_start` → 一个或多个 `content_block_delta` → `content_block_stop`）→ 若干 `message_delta` → `message_stop`；其间可能穿插 `ping` 事件 [来源](https://docs.anthropic.com/en/docs/build-with-claude/streaming)。每个内容块有一个 `index`，对应它在最终消息 `content` 数组里的位置——**增量累积必须按 index 归桶**，否则并行多工具的分片会串味。
```text
event: content_block_start   {index:1, content_block:{type:tool_use, id, name, input:{}}}
event: content_block_delta   {index:1, delta:{type:input_json_delta, partial_json:'{"location":'}}
event: content_block_delta   {index:1, delta:{type:input_json_delta, partial_json:' "San'}}
event: content_block_delta   {index:1, delta:{type:input_json_delta, partial_json:' Francisco, CA"}'}}
event: content_block_stop    {index:1}          ## 此刻才拼成完整对象，才可解析、才可执行
```
一个官方补充细节：当前模型一次只发出 `input` 里的一个完整键值对，因此工具调用的流式事件之间可能有停顿；键值累积完才作为多个分片 `content_block_delta` 发出 [来源](https://docs.anthropic.com/en/docs/build-with-claude/streaming)。这解释了为什么流式工具参数看起来是“一顿一顿”出现的。

## 现象与输入

把开头 Bug 的输入拆开，就能看清“半截 JSON”长什么样：
```text
累积过程（每步尝试 json.loads）：
'{"location":'                       -> 半截，解析失败（这就是那次 JSONDecodeError）
'{"location": "San'                  -> 半截，解析失败
'{"location": "San Francisco,'       -> 半截，解析失败
'{"location": "San Francisco, CA"}'  -> 收齐，解析成功 -> {'location': 'San Francisco, CA'}

错误做法：在任一半截步骤就执行工具。
正确做法：只在 content_block_stop 后、用收齐的完整对象执行。
```
## 最小可运行演示

下面模拟一段带工具调用的事件序列（字段名对齐官方文档），增量累积后在 `content_block_stop` 时解析成对象，并在每一步演示“半截 JSON 不可解析”。
```python
import json


def make_event_stream():
    """模拟一段带工具调用的 SSE 事件序列（字段名对齐官方文档）。"""
    return [
        {"type": "content_block_start", "index": 1,
         "content_block": {"type": "tool_use", "id": "toolu_01",
                           "name": "get_weather", "input": {}}},
        {"type": "content_block_delta", "index": 1,
         "delta": {"type": "input_json_delta", "partial_json": '{"location":'}},
        {"type": "content_block_delta", "index": 1,
         "delta": {"type": "input_json_delta", "partial_json": ' "San'}},
        {"type": "content_block_delta", "index": 1,
         "delta": {"type": "input_json_delta", "partial_json": ' Francisco,'}},
        {"type": "content_block_delta", "index": 1,
         "delta": {"type": "input_json_delta", "partial_json": ' CA"}'}},
        {"type": "content_block_stop", "index": 1},
    ]


def try_parse(buffer: str):
    try:
        return json.loads(buffer)
    except json.JSONDecodeError:
        return None


def run() -> None:
    buffers: dict[int, str] = {}
    names: dict[int, str] = {}
    for ev in make_event_stream():
        idx = ev["index"]
        if ev["type"] == "content_block_start":
            names[idx] = ev["content_block"]["name"]
            buffers[idx] = ""
            print(f"[start] 工具={names[idx]} index={idx}")
        elif ev["type"] == "content_block_delta":
            piece = ev["delta"]["partial_json"]
            buffers[idx] += piece
            parsed = try_parse(buffers[idx])
            state = "可解析" if parsed is not None else "半截JSON不可解析"
            print(f"[delta] 累积={buffers[idx]!r} -> {state}")
        elif ev["type"] == "content_block_stop":
            final = json.loads(buffers[idx])   ## 收齐后一次性解析
            print(f"[stop]  最终 input 对象={final}")
            print(f"现在才能安全执行 {names[idx]}(**{final})")


if __name__ == "__main__":
    run()
```
保存为 `streaming.py`，运行 `python streaming.py`。完整预期输出：
```text
[start] 工具=get_weather index=1
[delta] 累积='{"location":' -> 半截JSON不可解析
[delta] 累积='{"location": "San' -> 半截JSON不可解析
[delta] 累积='{"location": "San Francisco,' -> 半截JSON不可解析
[delta] 累积='{"location": "San Francisco, CA"}' -> 可解析
[stop]  最终 input 对象={'location': 'San Francisco, CA'}
现在才能安全执行 get_weather(**{'location': 'San Francisco, CA'})
```
前三行都是“半截JSON不可解析”，只有收齐后的第四行才可解析——这正是开头 Bug 的根源与修复：**按 index 归桶累积，`content_block_stop` 后再解析再执行**。

## 真实系统对应

**官方公开机制**：Anthropic 明确工具参数流式是 `input_json_delta` 的部分 JSON，最终 `input` 才是对象，并建议累积到 `content_block_stop` 再解析；SDK 提供增量取值 helper [来源](https://docs.anthropic.com/en/docs/build-with-claude/streaming)。Anthropic 另有“细粒度工具流式”（fine-grained tool streaming，需 beta 头或 `eager_input_streaming`），可不缓冲、不做 JSON 校验地直接流出参数，代价是**可能收到非法或部分 JSON**，需自行处理这些边界 [来源](https://docs.anthropic.com/en/docs/build-with-claude/streaming)。OpenAI 侧，流式下工具调用的 `arguments` 同样是增量拼接的字符串，开启 `parallel_tool_calls` 时多个调用的分片会交错，需按调用索引分别累积 [来源](https://platform.openai.com/docs/guides/function-calling)。**通用工程模式**：按 index/调用索引归桶累积、收齐再解析。**教学参考实现**：上面的事件流是手写模拟，真实 SDK 会替你做大部分累积工作。

一条重要边界：SDK 通常已封装好累积逻辑，直接给你解析后的对象。只有当你做**直接的 API 集成**（自己处理 SSE）时，才需要亲手累积。文档也建议流式模式优先用 SDK，别重复造轮子 [来源](https://docs.anthropic.com/en/docs/build-with-claude/streaming)。

## 生产踩坑

| 症状 | 根因 | 如何观测与复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| 偶发 JSONDecodeError | 对半截 partial_json 提前解析 | 在 delta 回调里 json.loads 复现 | 累积到 content_block_stop 再解析 | 用 SDK 时通常已封装 |
| 半截参数被误执行 | 半截恰是合法 JSON 前缀 | 构造 {"city":"北 这类前缀 | 只用收齐对象执行 | 细粒度流式需显式容错 |
| 并行多工具参数串味 | 未按 index 归桶累积 | 两个 tool_use 交错分片复现 | 按 index/调用索引分桶 | 单工具场景不触发 |
| 前端显示卡顿一顿一顿 | 误以为异常 | 观察键值对逐个到达 | 属正常：一次发一个完整键值 | 非工具文本块更连续 |
| ping/未知事件导致崩溃 | 未优雅处理未知事件 | 注入 ping 或新事件类型 | 忽略未知事件、不崩溃 | 需要新事件语义时另处理 |
| 细粒度流式收到非法 JSON | 关闭了缓冲与校验 | 开 eager 流式发长参数 | 自行做部分解析与兜底 | 不追求低延迟时别开 |

## 思考：流式下能不能边收参数边执行工具，以降低延迟？

### 回答

对绝大多数工具，不能。工具参数在流式下是分片到达的部分 JSON，半截参数要么无法解析、要么是合法前缀但语义残缺，据此执行会查错对象、传错值，甚至对有副作用的工具造成错误写入。正确姿势是累积到 `content_block_stop`（或对应的“调用完成”信号）拿到完整对象再执行。唯一的例外是 Anthropic 的“细粒度工具流式”这类场景：它为超长参数的首字节延迟而设计，明确告诉你可能收到非法/部分 JSON，你必须自己承担部分解析与容错的责任，且通常只对“可安全增量消费”的场景有意义。也就是说，降低延迟的收益要和“对半截参数执行”的风险严格权衡，默认应当收齐再执行。

### 面试精简表达

参数是流式拼出来的，半截不能用；默认收齐再执行，除非用官方细粒度流式并自己兜底非法 JSON。

## 事故回放：一个合法前缀引发的错城市查询

回到开头的对账 Agent。某次流式里，模型要查的城市是“北京市海淀区”，参数流是 `{"city": "北京市海` → `淀区"}`。工程师的旧代码在每个 delta 后 `json.loads`，第一段 `{"city": "北京市海` 解析失败被 `try/except` 静默吞掉，但有另一个更短的工具 `{"city": "北"}` 的分片在某次恰好先收齐成 `{"city": "北"}`——一个合法但残缺的对象，被立即执行，查了不存在的“北”市，返回“未知城市”。前端于是显示了错误结果，而日志里没有任何异常（因为解析成功了）。

复盘后修复三处：一是移除“边收边解析执行”，改为按 `index` 归桶、`content_block_stop` 后统一执行；二是把“解析失败”从静默 `except` 改为记录 `debug` 日志，避免掩盖问题；三是加一条断言——执行前校验参数已收齐（当前块已 stop）。优化前，流式带来的是“更快但偶发错值”；优化后，流式只影响“何时显示”，不影响“执行什么”。这印证了本节的核心：**流式改变的是展示时机，不应改变执行语义**。

## 机制推导：为什么官方选“部分 JSON”而不是“整块发送”

一个自然的疑问：既然半截不能用，为什么不等参数完全生成好再一次性发出？官方给了两层理由的线索。其一是**最大粒度**：把 `input` 的更新拆成尽量细的分片，能让 SDK 与未来模型支持更细的增量消费，而不必改协议 [来源](https://docs.anthropic.com/en/docs/build-with-claude/streaming)。其二是**首字节延迟**：对超长参数（比如一大段代码或文档），等全部生成完再发，用户要干等；边生成边发分片，配合细粒度流式，能更早开始传输。

代价是把“何时可用”的判断责任交给了消费者：普通模式下靠 `content_block_stop` 兜底，细粒度模式下则可能拿到非法 JSON。理解这个取舍，就能解释为什么协议要区分“分片是字符串、最终是对象”——它是在“低延迟传输”和“可靠解析”之间做的工程折中，而不是设计疏漏。作为使用者，默认走“收齐再执行”，只有在明确需要压低首字节延迟时才启用细粒度流式并自己兜底。
