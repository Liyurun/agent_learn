## 真实问题

“少减五元”结案后，团队想把教训沉淀成一份能防复发的清单，却发现难点不在“知道要幂等”，而在**告警太模糊**。线上告警只有一句“结算 Agent 成功率下降”，无法行动：根因可能在工具定义（模型选错工具）、参数校验（伪造字段被放行）、并行执行（一个失败拖垮整批）、循环控制（无限重试烧预算）、错误处理（异常崩溃而非回传）、副作用（重复扣款）任意一层。把一句模糊告警拆成可定位的层，再给每层配上“症状—根因—观测—修复—边界”，才是这份清单的价值。

这一节做两件事：先给出一张覆盖 Function Calling 端到端各层的生产建议表与一个可运行的分层诊断器；再用多道“思考+回答”把全章方法论收口，直接对齐高频面试题。

## 诊断顺序：先分层，再归因

遇到“Agent 又出错了”，不要先归结为“模型不行”或“上下文太长”，而是按数据流分层排查，每层都有可观测证据：

1. **复现**：固定模型标识、温度、工具 Schema 快照、数据版本与请求输入。不能复现就先把这五个变量钉死。
2. **定义层**：模型是否编造了不存在的工具名、是否在近义工具间反复选错。观测“未知工具调用数”与“工具选择分布”。
3. **校验层**：参数非法率是否偏高。观测 Schema 拒绝率，检查工具描述与枚举约束是否清晰。
4. **并行层**：一轮多调用里是否有部分失败未降级、是否并发写了共享状态。观测部分失败率与是否启用降级。
5. **循环层**：是否频繁触顶轮次上限、是否有重试风暴。观测平均轮次与触顶率。
6. **错误层**：错误是抛了裸异常崩溃，还是转成 `is_error` 回传。观测崩溃率与错误分类分布。
7. **副作用层**：有副作用的工具是否重复执行。观测幂等键命中率与重复动作数。
8. **对照**：同一输入在固定模型上多次运行的结果，与离线评估集比较。

## 生产建议：Function Calling 端到端症状矩阵

下面把全章各层的坑汇成一张矩阵，每行都是一个真实会发生、可观测、有修复、也有不适用边界的条目。它是这份清单的主体。

| 症状 | 根因 | 如何观测与复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| 排错方向对准“模型直连外部” | 误把“提议”当“执行” | 打印②③时间戳看副作用发生处 | 安全与重试全落运行时 | 服务端内置工具确由厂商执行 |
| 循环永不终止、token 烧光 | 只靠自然终止无轮次上限 | 让工具总返回“查无结果” | for turn in range(max_turns) 兜底 | 明确单步任务可不设循环 |
| 第二轮模型“失忆” | 未把历史重发给无状态模型 | 只发最后一条消息复现 | 每轮携带完整 messages | 服务端会话托管场景另算 |
| Anthropic 400 找不到 tool_result | 用了 role=tool 的 OpenAI 形状 | 回放被拒请求体 | 用 tool_result 块 + tool_use_id | OpenAI 后端本就用 role=tool |
| 400 文本排在 tool_result 之前 | 违反“结果块在前”约束 | 结果前加文本复现 | 结果块最前、文本置后 | 无文本时不触发 |
| 结果错配到别的问题 | 按到达顺序拼结果 | 让快慢工具并存复现 | 一律按 id 重排后回填 | 单调用顺序恰好一致会掩盖 |
| 一个工具异常整批崩溃 | 单调用未捕获异常 | 让一个工具抛异常 | 每调用独立 try 转 is_error | 致命错误确需整体中止时例外 |
| 并发写共享状态丢更新 | 对非独立操作强行并行 | 同时写同一购物车复现竞态 | 写冲突调用串行或加锁 | 独立分片写可并行 |
| 偶发 JSONDecodeError | 对半截 partial_json 提前解析 | delta 回调里 json.loads | 累积到 content_block_stop 再解析 | 用 SDK 时通常已封装 |
| 半截参数被误执行 | 半截恰是合法 JSON 前缀 | 构造合法前缀分片 | 只用收齐对象执行 | 细粒度流式需显式容错 |
| 超时后重试重复扣款 | 非幂等写无幂等键 | 首次成功但响应超时后重试 | 绑定业务意图的幂等键 | 只读工具重试本就安全 |
| 慢工具拖垮整轮延迟 | 未设单调用超时 | 注入 sleep 工具 | future.result(timeout) 罩超时 | 允许长任务的场景另设 |
| 模型反复用同样非法参数 | 错误文案含糊 | 回传“参数错误”无细节 | 文案写清字段与期望值 | 模型能力上限仍需换路径 |
| 把限流当程序 Bug 排查 | 未区分 429 与逻辑错 | 观察是否集中在高峰 | 指数退避 + 尊重 Retry-After | 持续 429 需申请配额 |
| 工具结果里的指令被当命令执行 | 未隔离不可信内容 | 结果里塞“忽略以上指令” | 放 tool_result、做注入防护 | 完全可信内部工具风险较低 |
| 工具越加越多、选择准确率下降 | 同时暴露工具过多且语义重叠 | 记录候选与实际调用分布 | 收敛工具集、两阶段路由 | 领域本就需要大量工具时另设 |
| 每轮 input token 线性膨胀 | 工具定义与历史每轮重发 | 统计各轮 input token | 精简工具、压缩历史 | 短对话影响可忽略 |
| strict 模式仍出越业务界的值 | 误以为 strict 覆盖业务约束 | 构造合 Schema 但越业务界的值 | 业务校验独立于结构校验 | strict 只保证结构合规 |

TTL（Time To Live，生存时间）适用于可过期的缓存与偏好，不应用于删除法律保留或未完成事务。PII（Personally Identifiable Information，个人可识别信息）在写入日志与追踪前应最小化与脱敏。

## 最小可运行演示：分层诊断器

把上面的诊断顺序固化成一个规则树，输入一组指标，输出首要嫌疑层，避免“一切归结为模型不行”。
```python
"""生产诊断器（纯 Python）：把"工具调用循环质量下降"拆到可行动的层。"""
from __future__ import annotations


def diagnose(m: dict) -> list[str]:
    findings = []
    if m["schema_reject_rate"] > 0.1:
        findings.append("校验层：参数非法率过高，检查工具描述与枚举约束")
    if m["unknown_tool_calls"] > 0:
        findings.append("定义层：模型编造工具名，收敛工具集或重写描述")
    if m["avg_turns"] >= m["max_turns"]:
        findings.append("循环层：频繁触顶轮次上限，检查终止条件与重试风暴")
    if m["parallel_partial_fail"] and not m["degrade_enabled"]:
        findings.append("并行层：部分失败未降级，补齐 is_error 与降级策略")
    if m["duplicate_side_effect"]:
        findings.append("副作用层：疑似重复执行，检查幂等键")
    return findings or ["指标正常，用固定输入做回归对照"]


def run() -> None:
    metrics = {
        "schema_reject_rate": 0.02,
        "unknown_tool_calls": 0,
        "avg_turns": 8,
        "max_turns": 8,
        "parallel_partial_fail": True,
        "degrade_enabled": False,
        "duplicate_side_effect": True,
    }
    for line in diagnose(metrics):
        print(line)


if __name__ == "__main__":
    run()
```
保存为 `diagnose.py`，运行 `python diagnose.py`。完整预期输出：
```text
循环层：频繁触顶轮次上限，检查终止条件与重试风暴
并行层：部分失败未降级，补齐 is_error 与降级策略
副作用层：疑似重复执行，检查幂等键
```
这个规则树只用于**缩小范围**，不替代基于 Trace（追踪）的根因分析：它告诉你先看哪一层，具体归因仍要回到实际请求快照与运行轨迹。示例里三条同时命中，说明这套结算 Agent 在循环、并行、副作用三层都有隐患——恰好对应“少减五元”故障的复合成因。

## 真实系统对应

**官方公开机制**：OpenAI 公开了错误码与限流指南，可用于区分限流（`429`）、服务端错误（`5xx`）与逻辑错误，并建议指数退避与幂等键 [来源](https://platform.openai.com/docs/guides/error-codes) [来源](https://platform.openai.com/docs/guides/rate-limits)；Anthropic 公开了 `stop_reason`（如 `tool_use`、`max_tokens`）与 `usage` 字段，可用于观测循环是否因工具而继续、是否因长度截断 [来源](https://platform.claude.com/docs/en/agents-and-tools/tool-use/overview)。**通用工程模式**：分层诊断、症状矩阵、固定输入回归对照，是可迁移到任何厂商的排障框架。**教学参考实现**：上面的规则树仅用于教学，阈值（如 `0.1` 的拒绝率）需按业务实测校准，不是普适常数。

需要点明边界：具体的采样率、脱敏策略、日志保留期与告警阈值由团队按风险设计；本文不声称任何平台会自动完成这些治理。可观测平台（如厂商用量字段、Trace 工具）提供的是能力，怎么用、留多久、谁能看，都是团队的工程决策。

## 思考：面试官问“讲一下 Function Calling 端到端是怎么工作的”，怎么答得有层次？

### 回答

分三层递进。第一层给骨架：一次工具调用是“运行时带工具定义发请求→模型返回结构化 tool_use（只说不做）→运行时执行并回填 tool_result（带 id）→模型据此再请求或给纯文本终止”，这是 OpenAI 五步、Anthropic 一趟往返的共性。第二层点两条铁律：模型只“说”不“做”，副作用全在运行时，所以安全防线建在运行时；模型无状态，每轮重发历史，所以 token 随轮数增长、要设轮次上限。第三层展开四个工程细节，正好覆盖本章：并行调用要按 id 乱序配对、部分失败降级；流式下参数是部分 JSON、要收齐再执行；错误统一成 is_error 回传当信号；有副作用的工具要幂等。最后用“少减五元”这类具体故障收尾——伪造参数没校验、部分失败没降级、扣款没幂等——证明你不只背流程，还踩过坑。这样从骨架到铁律到细节到实战，层次就出来了。

### 面试精简表达

先讲四步骨架，再点“只说不做 + 无状态重发历史”两条铁律，最后展开并行、流式、错误、幂等四个工程细节，用一个真实故障收口。

## 思考：为什么说“工具越多越好”是错觉？

### 回答

有三重代价。第一是选择准确率：工具越多、语义越接近，模型越容易在近义工具间选错，尤其当描述没写清“何时不要用”这类负向边界时。第二是成本：工具定义是 input token 的一部分，而模型无状态、每轮重发历史，工具越多，每轮被重复发送的 token 越多，多轮下来成本线性放大。第三是维护与安全面：每个工具都是一处潜在的副作用入口和攻击面，数量越多越难做权限、审计和注入防护。正确姿势是收敛到“当前任务真正需要”的最小工具集，语义重叠的工具要么合并要么用两阶段路由（先粗选类别再暴露子集），并给每个工具写清正反用途边界。这与第 27 章“工具不是越多越好、要按任务动态选择”的结论一致：上下文预算和选择准确率都要求节制。

### 面试精简表达

工具多了选择准确率下降、每轮重发推高成本、攻击面变大；应收敛到最小集、写清负向边界、必要时两阶段路由。

## 思考：Function Calling 与 MCP（Model Context Protocol，模型上下文协议）是什么关系？

### 回答

两者是不同层次、互补的东西。Function Calling 解决的是“模型如何在一次对话里提议调用工具、运行时如何执行并回填”的**协议机制**，它是模型与运行时之间的交互约定。MCP 解决的是“工具和数据源如何被标准化地暴露给各种 Agent”的**集成标准**，它是运行时与外部工具服务之间的连接约定，目标是缓解 N×M 的集成爆炸。落到代码里：MCP Server 把一个工具的名字、描述、input_schema 标准化地暴露出来，运行时（MCP Host/Client）拿到这些定义后，仍然是通过 Function Calling 的机制把它们放进请求、接收模型的 tool_use、执行、回填。也就是说 MCP 负责“工具从哪来、长什么样”，Function Calling 负责“模型怎么提议、运行时怎么执行”。理解这层关系，就不会把两者对立起来问“用哪个”——实际系统里常常是 MCP 提供工具、Function Calling 驱动调用，二者叠加使用（MCP 细节见第 9 章）。

### 面试精简表达

Function Calling 是模型与运行时的调用协议，MCP 是运行时与外部工具的集成标准；MCP 供给工具定义，Function Calling 驱动调用，二者互补叠加。

## 思考：把本章方法引入一个已有的工具调用系统，落地顺序应该怎么排？

### 回答

先观测，后改造，最后优化。第一步加观测而非急着重写：给每轮打结构化日志（turn、tool_use_id、name、args_digest、latency_ms、exit、stop_reason），把“模型说了什么”和“运行时做了什么”分别落盘，这样才有证据分层归因。第二步锁三条安全底线：给主循环加轮次上限防死循环烧钱、给每个工具执行套 try 转 is_error 防崩溃、给有副作用的工具加幂等键防重复。第三步做协议归一化：如果对接多家厂商，用归一化层把 tool_calls/tool_use 折叠成统一内部结构，避免复制粘贴两份漂移的处理代码。第四步才是性能优化：对独立只读工具并行并配统一超时、精简工具集降 token、必要时上流式改善首字节延迟。每一步都用失败样本建回归集、做对照实验、保留回滚开关。这个顺序的逻辑是——先能看见问题，再堵住会赔钱的洞，最后才追求快和省。

### 面试精简表达

顺序是观测→安全底线（轮次上限/is_error/幂等）→协议归一化→性能优化（并行/精简/流式）；每步配回归集与回滚开关，先看得见再堵洞最后提速。
