## 真实问题

“少减五元”故障最贵的一笔损失，来自 `charge_customer` 被调了两次。当时的现场是：中午重试高峰，网络抖动让运行时对第一次扣款的响应超时，代码于是“重试”了一次；可第一次其实已经扣款成功，只是响应没回来。结果同一订单扣了两笔，客服工单堆到晚上。复盘时工程师的第一反应是“加重试次数限制”——这治标不治本。真正的三个缺陷是：超时没有被当成一种**结构化错误**处理，而是抛了裸异常；无效参数（那个 `rule_version="v0"`）没有转成给模型的纠错信号；有副作用的扣款工具没有幂等键，导致重试就是重复扣款。

这一节把工具调用里的错误分成三类——超时、无效参数、拒绝——讲清每类如何统一成带 `is_error` 的结构化结果回传模型，让“错误变成模型能纠错的信号”；再对照 OpenAI 与 Anthropic 的公开错误处理机制，最后用一个幂等键演示把“重试即重复扣款”这个坑堵死。

## 原理：错误是给模型的信号，不是崩溃的理由

Function Calling 的错误处理有一条与传统后端不同的核心心智：**工具执行失败通常不应该让主循环崩溃，而应该把失败本身作为一条结果回传给模型，由模型决定纠错还是降级。** Anthropic 的 Handle tool calls 文档明确了这一点：`tool_result` 块有一个可选的 `is_error` 字段，设为 `true` 即告知模型该次工具执行出错；文档还列出三类典型错误——工具执行错误、无效工具名、服务端工具错误 [来源](https://platform.claude.com/docs/en/agents-and-tools/tool-use/handle-tool-calls)。

把生产里的错误归成三类，处理方式各不相同：

| 错误类别 | 典型触发 | 运行时动作 | 回传给模型的内容 | 模型的合理反应 |
|---|---|---|---|---|
| 超时类 | 下游慢、网络抖动 | 超时罩中断，转 is_error | “工具执行超时（>Ns）” | 重试（若幂等）或降级作答 |
| 无效参数类 | 模型伪造/写错参数 | Schema 校验拦下，转 is_error | “参数非法：具体原因” | 用合法参数重新提议 |
| 拒绝类 | 高风险动作未获批 | 权限关口拒绝，转 is_error | “需人工审核，已拒绝” | 改走安全路径或请求授权 |

三类共性是：**都不抛裸异常，都带 `is_error=True`，都携带可读原因**。差异在于模型的合理反应不同：超时可重试，无效参数要改参数，拒绝要换路径。好的错误文案能显著提升模型的自我纠错率——把“参数非法”写成“参数 unit 取值须在 ['c','f'] 内”，模型立刻知道该怎么改（第 5 节 T2→T3 就是实证）。

## 现象与输入

把三类错误 + 一个正常case摆在一起，就能看清“统一结构化”的价值：
```text
输入四个工具调用：
e1 slow_tool()                 下游慢 2 秒，运行时超时罩设 0.2 秒 -> 超时类
e2 parse_date(text="2026/08/24") 分隔符错，函数抛 ValueError    -> 无效参数类
e3 parse_date(text="2026-08-24") 合法                          -> 正常
e4 (删库类高风险动作)             未获批                          -> 拒绝类

统一回传结构（每条都带 is_error）：
e1 [ERROR] 工具执行超时（>0.2s）
e2 [ERROR] ValueError: 非法日期：2026/08/24
e3 [OK]    已解析 2026-08-24
e4 [ERROR] 该操作涉及删库，需人工审核，已拒绝
```
关键在于：四条结果形状一致，模型无需区分“系统崩了”还是“我参数写错了”，它只看 `is_error` 与原因文本，就能决定下一步。这就是“错误即信号”。

## 最小可运行演示（一）：三类错误的结构化处理

下面用线程池给工具套一个超时罩，把超时、无效参数、拒绝三类错误统一成带 `is_error` 的结构化结果。
```python
"""错误恢复：超时/无效参数/拒绝三类错误的结构化处理（纯 Python）。"""
from __future__ import annotations
import time
from concurrent.futures import ThreadPoolExecutor, TimeoutError as FutureTimeout

_POOL = ThreadPoolExecutor(max_workers=4)


def slow_tool() -> str:
    time.sleep(2.0)   ## 故意慢，触发超时
    return "never"


def parse_date(text: str) -> str:
    ## 只接受 YYYY-MM-DD
    parts = text.split("-")
    if len(parts) != 3 or not all(p.isdigit() for p in parts):
        raise ValueError(f"非法日期：{text}")
    return f"已解析 {text}"


def make_result(cid, content, is_error=False):
    return {"tool_use_id": cid, "content": content, "is_error": is_error}


def execute_with_timeout(cid, fn, kwargs, timeout=0.2):
    fut = _POOL.submit(fn, **kwargs)
    try:
        out = fut.result(timeout=timeout)
        return make_result(cid, out)
    except FutureTimeout:                        ## 超时类
        fut.cancel()
        return make_result(cid, f"工具执行超时（>{timeout}s）", is_error=True)
    except Exception as exc:                      ## 无效参数类（函数抛异常）
        return make_result(cid, f"{type(exc).__name__}: {exc}", is_error=True)


def run() -> None:
    cases = [
        ("e1", slow_tool, {}, "超时类"),
        ("e2", parse_date, {"text": "2026/08/24"}, "无效参数类"),
        ("e3", parse_date, {"text": "2026-08-24"}, "正常"),
    ]
    for cid, fn, kwargs, label in cases:
        r = execute_with_timeout(cid, fn, kwargs)
        tag = "ERROR" if r["is_error"] else "OK"
        print(f"{cid} [{label}] -> [{tag}] {r['content']}")

    ## 拒绝类：高风险动作未获批，直接返回结构化拒绝
    reject = make_result("e4", "该操作涉及删库，需人工审核，已拒绝", is_error=True)
    print(f"e4 [拒绝类] -> [ERROR] {reject['content']}")
    print("三类错误都带 is_error=True：模型据此纠错或降级，而非把错误当有效数据")
    _POOL.shutdown(wait=False)


if __name__ == "__main__":
    run()
```
保存为 `error_recovery.py`，运行 `python error_recovery.py`。完整预期输出：
```text
e1 [超时类] -> [ERROR] 工具执行超时（>0.2s）
e2 [无效参数类] -> [ERROR] ValueError: 非法日期：2026/08/24
e3 [正常] -> [OK] 已解析 2026-08-24
e4 [拒绝类] -> [ERROR] 该操作涉及删库，需人工审核，已拒绝
三类错误都带 is_error=True：模型据此纠错或降级，而非把错误当有效数据
```
`e1` 的下游要跑 2 秒，但超时罩设在 0.2 秒，于是运行时不会干等，立刻转成超时错误回传。这就是“慢工具不能拖住整轮”的落地（与第 3 节并行的超时讨论一致）。

## 最小可运行演示（二）：幂等键堵死“重试即重复扣款”

超时最危险的衍生问题是：超时后重试，但上一次其实已成功。对**非幂等**的写操作（如扣款），重试就是重复副作用。解法是幂等键——同一次业务动作用同一把键，服务端据此去重。下面演示重试三次但只扣一次。
```python
"""幂等键演示：重试非幂等的扣款工具，靠幂等键保证只扣一次（纯 Python）。"""
from __future__ import annotations


class PaymentService:
    """模拟支付服务端：用幂等键去重，重复请求返回同一结果，不重复扣款。"""

    def __init__(self) -> None:
        self._seen: dict[str, dict] = {}   ## idempotency_key -> 结果
        self.charge_count = 0              ## 真实扣款发生次数

    def charge(self, order_id: str, amount: float, idempotency_key: str) -> dict:
        if idempotency_key in self._seen:
            ## 命中幂等键：直接返回上次结果，不再真正扣款
            return {**self._seen[idempotency_key], "replayed": True}
        self.charge_count += 1             ## 只有首次才真正扣款
        result = {"order_id": order_id, "amount": amount,
                  "txn_id": f"T-{idempotency_key}", "replayed": False}
        self._seen[idempotency_key] = result
        return result


def run() -> None:
    svc = PaymentService()
    key = "order-A2026-attempt1"          ## 同一次业务动作用同一把键

    ## 模拟：首次扣款成功，但网络抖动让运行时以为失败，于是重试
    r1 = svc.charge("A-2026", 100.0, key)
    r2 = svc.charge("A-2026", 100.0, key)   ## 重试：同一幂等键
    r3 = svc.charge("A-2026", 100.0, key)   ## 再重试

    print(f"首次:   {r1}")
    print(f"重试1:  {r2}")
    print(f"重试2:  {r3}")
    print(f"真实扣款次数={svc.charge_count}（重试 3 次，只扣 1 次）")
    assert svc.charge_count == 1
    assert r1["txn_id"] == r2["txn_id"] == r3["txn_id"]
    print("幂等键保证：非幂等工具在重试下也只产生一次副作用")


if __name__ == "__main__":
    run()
```
保存为 `idempotency.py`，运行 `python idempotency.py`。完整预期输出：
```text
首次:   {'order_id': 'A-2026', 'amount': 100.0, 'txn_id': 'T-order-A2026-attempt1', 'replayed': False}
重试1:  {'order_id': 'A-2026', 'amount': 100.0, 'txn_id': 'T-order-A2026-attempt1', 'replayed': True}
重试2:  {'order_id': 'A-2026', 'amount': 100.0, 'txn_id': 'T-order-A2026-attempt1', 'replayed': True}
真实扣款次数=1（重试 3 次，只扣 1 次）
幂等键保证：非幂等工具在重试下也只产生一次副作用
```
三次调用返回同一个 `txn_id`，`charge_count` 始终为 1——这正是“少减五元”里第三个缺陷的修复。幂等键的生成要绑定“同一次业务意图”，通常用订单号 + 动作类型 + 尝试标识，而不是每次重试都换一把新键（换新键等于没有幂等）。

## 真实系统对应

**官方公开机制**：Anthropic 文档给出 `tool_result` 的 `is_error` 字段，并明确列出工具执行错误、无效工具名、服务端工具错误三类；还特别提示“工具结果常携带来自外部、你无法控制的内容（网页、邮件、用户上传、第三方 API），应当作为不可信内容处理，防范间接提示注入（indirect prompt injection）”，并建议把不可信内容放在 `tool_result` 块里而非 system 或纯 user 文本 [来源](https://platform.claude.com/docs/en/agents-and-tools/tool-use/handle-tool-calls)。OpenAI 侧，超时、限流、`5xx` 是可重试类，`4xx`（如参数错误）不可重试，官方建议结合指数退避与幂等键，并有专门的错误码与限流指南 [来源](https://platform.openai.com/docs/guides/error-codes) [来源](https://platform.openai.com/docs/guides/rate-limits)。**通用工程模式**：把三类错误统一成带 `is_error` 的结构化结果、给非幂等写操作加幂等键、超时用退避重试而非无限重试，是可迁移到任何厂商的做法。**教学参考实现**：上面的超时罩用线程池 `future.result(timeout=...)` 模拟，真实系统应优先用底层客户端自带的超时；`PaymentService` 的内存去重仅为演示，生产要用持久化存储与并发安全的去重。

一个务必分清的边界：`fut.cancel()` 对**已经开始执行**的线程池任务通常无法真正中断，它只能取消尚未开始的任务。因此“超时转错误”保护的是**主循环的响应性**（不干等），而不是“下游一定停止了工作”。对有副作用的工具，超时后能否安全重试，取决于它是否幂等——这正是演示二存在的理由：**超时处理与幂等键必须成对出现**，否则“超时重试”本身就是重复扣款的元凶。

## 生产踩坑

| 症状 | 根因 | 如何观测与复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| 一个工具异常导致主循环崩溃 | 抛裸异常未转 is_error | 让工具 raise 复现 | 统一捕获转结构化结果回传 | 致命错误确需整体中止时例外 |
| 超时后重试造成重复扣款 | 非幂等写 + 无幂等键 | 首次成功但响应超时后重试 | 绑定业务意图的幂等键去重 | 只读工具重试本就安全 |
| 慢工具拖垮整轮延迟 | 未设单调用超时 | 注入 sleep 工具复现 | future.result(timeout) 罩超时 | 明确允许长任务的场景另设 |
| 模型反复用同样非法参数 | 错误文案含糊 | 回传“参数错误”无细节复现 | 错误文案写清哪个字段、期望什么 | 模型能力上限导致的仍需换路径 |
| 把限流当程序 Bug 排查 | 未区分 429 与逻辑错 | 观察是否集中在高峰 | 指数退避 + 尊重 Retry-After | 持续 429 需申请配额 |
| 工具结果里的指令被当命令执行 | 未隔离不可信内容 | 在工具返回里塞“忽略以上指令” | 结果放 tool_result、做注入防护 | 完全可信的内部工具风险较低 |
| 无限重试烧光预算 | 只重试不设上限 | 让工具永远超时复现 | 重试次数 + 轮次双上限 | —— |
| 取消超时任务后下游仍在跑 | 误以为 cancel 能中断 | 观察下游是否仍写入 | 靠幂等而非取消保证正确性 | 支持真正中断的客户端例外 |

## 真实系统对应：OpenAI 与 Anthropic 错误机制对照

两家在“错误如何回传给模型”这件事上机制相通、字段不同，工程上值得并列记忆：

- **失败如何告知模型**：Anthropic 用 `tool_result` 的 `is_error=true` 显式标记 [来源](https://platform.claude.com/docs/en/agents-and-tools/tool-use/handle-tool-calls)；OpenAI 没有独立错误字段，约定把错误信息写进回填内容（Chat Completions 的 `role=tool` 的 `content`、Responses 的 `function_call_output`），让模型从文本理解失败 [来源](https://platform.openai.com/docs/guides/function-calling)。
- **传输层错误码**：OpenAI 公开了错误码与限流机制，`429` 表示限流、`5xx` 表示服务端错误，建议指数退避 [来源](https://platform.openai.com/docs/guides/error-codes) [来源](https://platform.openai.com/docs/guides/rate-limits)。这类错误发生在“运行时 ↔ 模型 API”这一跳，与“工具执行失败”是两个不同层面，排障时要先分清是哪一跳出错。
- **不可信结果**：Anthropic 明确把工具结果当不可信内容、防间接提示注入 [来源](https://platform.claude.com/docs/en/agents-and-tools/tool-use/handle-tool-calls)。这条对两家都适用：任何来自外部的工具返回都可能藏有企图操纵模型的文本，安全边界要建在运行时，而不是指望模型自觉。

结论：把“工具执行错误”和“API 传输错误”分层——前者转 `is_error` 交给模型纠错，后者按错误码做退避重试；再把所有外部结果当不可信输入处理。这三条拼起来，才是一个能扛住生产抖动的错误恢复回路。

## 思考：工具执行失败时，为什么通常不直接把异常抛给用户，而要回传给模型？

### 回答

因为在 Agent 架构里，模型是决策者，它比一段固定的异常处理代码更懂“下一步该怎么办”。把失败作为结构化结果（`is_error=true` + 可读原因）回传，模型能据此做三种远比“报错退出”更好的处理：一是自我纠错，比如参数越界就换合法参数重试（第 5 节实证）；二是降级作答，比如五个数据点缺一个，就用其余四个先给部分答案并说明缺失；三是换路径，比如某工具被拒绝就改用另一条安全途径。如果直接抛异常给用户，这三条智能路径全被切断，用户只看到一句冰冷的“Internal Error”。当然也有例外：致命的、无法在本轮内恢复的错误（如认证失效、配置缺失）应当快速失败并告警，而不是让模型在无望的情况下空转重试。判断标准是——这个错误模型有没有能力通过改变行为来绕过；能，就回传给它；不能，就快速失败。

### 面试精简表达

模型是决策者，失败当信号回传能触发纠错、降级、换路径三条智能路径；只有模型无力回天的致命错误才快速失败告警。

## 思考：超时和重试，为什么必须和幂等键一起设计？

### 回答

因为超时的本质是“不知道下游到底成没成”，而重试的前提是“重试安全”。对只读工具，重试无非多查一次，无害；但对有副作用的非幂等写操作（扣款、下单、发信），超时后重试就可能把一次成功的操作又做一遍——“少减五元”里的重复扣款正是这么来的。幂等键让服务端能识别“这是同一次业务动作的重试”，从而只产生一次副作用、并返回上次结果。所以正确的设计是：超时转结构化错误保证主循环不干等，退避重试应对瞬时抖动，而幂等键保证“即使重试也只做一次”。三者缺一不可：只设超时不加幂等，超时重试就是重复副作用；只加幂等不设超时，慢工具会拖垮整轮延迟。还要注意幂等键必须绑定“同一次业务意图”，每次重试换新键等于没有幂等。

### 面试精简表达

超时说明结果未知，重试要安全就得靠幂等键；三者成套：超时保响应、退避应对抖动、幂等保证只做一次，且键要绑定同一次业务意图。
