## 31.0 怎么用这份题库

在开刷之前，先建立三个"元认知"，它们决定了你刷题的效率上限。

**第一，分清"记忆题"和"理解题"。** 像"什么是 ReAct""MCP 的三个角色是什么"这类，答案相对固定，属于记忆题，卡壳了就是没记牢，多过几遍即可。而像"什么时候该上多 Agent""如何设计一个客服 Agent"这类，没有标准答案，属于理解题，考的是你的判断力和工程品味——这类题不能靠背，要靠"想清楚背后的取舍"。本章会用图标提示：记忆题重在准确，理解题重在有观点。

**第二，答案要分层，但速查时先抓第一层。** 全书反复强调"一句话定义 → 展开维度 → 边界代价"的三层结构。速查时你至少要能脱口而出**第一层（一句话）**；行有余力再补第二、第三层。本章参考答案通常已经把三层压进了 3-6 句里，你可以拆开练。

**第三，用"追问"预演压力。** 每类里我挑了部分题配了"追问/提示"，那是面试官最爱顺着问下去的方向。真实面试极少问完一题就换，几乎一定会追问。**提前把追问也想一遍，才算真正准备好。** 第九类"进阶追问加练"整类都是为这件事准备的。

下面开始。九个类别，逐类速刷。

## 31.1 一、基础概念类（Q1-Q15）

这一类是"开场必问区"，几乎每场面试的前十分钟都在这里。考点集中在：Agent 的定义、自主性、ReAct、与传统程序/工作流的区别。答不好基础题，后面讲得再花哨也会被打折扣。

### Q1：一句话定义 AI Agent，它和普通 LLM 调用的本质区别是什么？

**参考答案**：
- AI Agent 是**以 LLM 为大脑、能自主感知—决策—调用工具—根据反馈迭代**以完成目标的系统。
- 与普通 LLM 调用最本质的区别在于**由谁控制工作流**：普通调用是"问一句答一句"，流程由代码写死；Agent 是**模型自己决定下一步做什么**（调工具、继续推理、还是结束）。
- 判断依据不是"有没有调 API"，而是"**调不调、何时调、调完看结果再决定下一步**"是不是模型运行时动态决定的。
- Anthropic 在《Building Effective Agents》中把二者明确区分为 Workflow（预定义代码路径编排）与 Agent（模型动态决定流程）[来源](https://www.anthropic.com/engineering/building-effective-agents)。

> **追问/提示**：会顺着问"那 Workflow 和 Agent 的界限在哪""是不是所有场景都该上 Agent"。记住答案锚点是"控制权归属"和"能简单就别复杂"。

### Q2：Agent 的"自主性（Autonomy）"具体指什么？为什么它是把双刃剑？

**参考答案**：
- 自主性指**模型自己掌握控制流**：决定任务怎么拆、下一步调哪个工具、什么时候算完成，而不是由人写死流程。
- 好处是灵活——面对开放、多变、事前无法穷举分支的任务，模型能临场应变。
- 代价是不可控——可能多绕路、多花钱、陷入死循环、或做出你没预期的动作。
- 所以自主性是"程度问题"而非"有无问题"：工程上要通过终止条件、预算上限、人在回路（human-in-the-loop）等手段，把自主性约束在可接受的范围内。

> **追问/提示**："如何量化自主性？"可答用"人给了多少约束/模型有多少自由裁量"来定性分级，没有统一公式。

### Q3：请解释 ReAct，它解决了什么问题？

**参考答案**：
- ReAct = Reasoning + Acting，让模型在**"思考（Thought）→ 行动（Action）→ 观察（Observation）"的循环**里交替推理和调用工具。
- 它解决了纯 CoT（只推理不行动）容易**脱离现实、凭空编造**的问题：每步行动都能拿到真实观察，用外部反馈校正下一步推理。
- 同时也解决了纯 Acting（只调工具不推理）**盲目试错、没有规划**的问题。
- 它是当今绝大多数 Agent 循环的基础范式，工具调用型 Agent 本质上就是 ReAct 的工程化实现。

> **追问/提示**：常被追问"ReAct 有什么缺点"——每步都要推理导致 token 和延迟高、容易在观察噪声下跑偏、长链路里错误会累积。

### Q4：Agent 和 Workflow（工作流）到底怎么区分？

**参考答案**：
- 核心判据是**控制流由谁决定**：Workflow 的执行路径由代码预先编排（哪怕中间调了很多 LLM 和工具）；Agent 的执行路径由模型运行时动态决定。
- Workflow 可预测、可测试、成本可控，适合流程稳定、分支可穷举的任务；Agent 灵活、能应对开放任务，但更难调试、成本更高。
- 两者不是对立，而是一条**控制权从人逐渐让渡给模型的光谱**：纯 LLM 调用 → 固定链 → 带路由 → Workflow 编排 → Agent。
- 工程建议：**能用 Workflow 解决就别上 Agent**，只有当"模型驱动的动态决策确实带来价值"时才引入自主性。

> **追问/提示**：给一个真实系统让你判断是不是 Agent，看三点——控制流是否模型决定、有没有"观察后再决策"的循环、工具调用顺序是否运行时才定。

### Q5：Agent 的最小闭环由哪几部分组成？

**参考答案**：
- 最小闭环通常是四要素：**大脑（LLM 做推理决策）、工具（与外部世界交互的手脚）、记忆（保存上下文与历史）、循环控制（决定继续还是终止）**。
- 大脑负责"想"，工具负责"做"，记忆负责"记住做过什么和结果"，循环控制负责"什么时候停"。
- 缺了循环控制就退化成单轮调用；缺了工具就只能空想；缺了记忆则每步都失忆、无法完成多步任务。
- 这也是为什么很多框架把 Agent 抽象成 `while (not done): think → act → observe` 的骨架。

> **追问/提示**：可延伸到"规划（Planning）算不算独立组件"——可算作大脑的一种能力，也可外置为独立的 Planner。

### Q6：为什么说"LLM 是 Agent 的大脑，但不是 Agent 的全部"？

**参考答案**：
- LLM 提供推理、语言理解和决策能力，是 Agent 的核心，但它本身**无状态、无法执行动作、知识有截止日期、还会幻觉**。
- 要成为 Agent，必须外接：工具（执行动作、获取实时信息）、记忆（跨轮保持状态）、编排逻辑（循环、终止、错误处理）、护栏（约束行为）。
- 换句话说，Agent 的能力 = LLM 的智能 × 工程脚手架的可靠性，后者往往决定生产可用性。
- 面试里这句话能体现你"不神化模型、重视工程"的成熟度。

### Q7：Agent、Copilot、Chatbot、AutoML 这些词经常混用，你怎么区分？

**参考答案**：
- **Chatbot**：以对话为主，通常单轮问答或简单多轮，不一定有工具和自主决策。
- **Copilot**：人主导、AI 辅助，强调"人在回路"，AI 给建议但人做最终决定（如代码补全）。
- **Agent**：AI 主导执行，能自主决策、调用工具、多步完成目标，人只给目标和约束。
- 三者是"自主程度"递增的关系；AutoML 是另一维度（自动化机器学习流程），与前三者不在同一分类轴上。

> **追问/提示**："Copilot 能不能算 Agent"——取决于它是否具备自主的多步决策循环，很多"Copilot"其实是带路由的 Workflow。

### Q8：什么叫"Agentic"？它是形容词还是名词？

**参考答案**：
- "Agentic"是形容词，形容一个系统**具有多少 Agent 的特质**——自主决策、动态规划、工具使用、循环迭代。
- 它强调"程度"：一个系统可以"有点 Agentic"（有一处模型自主决策）到"高度 Agentic"（几乎全程模型驱动）。
- 用"Agentic"而不用"是不是 Agent"，是为了避免非黑即白的二分，更符合真实系统的连续光谱。
- 例如"Agentic RAG"就是指"在 RAG 流程里加入了自主决策（要不要检索、检索几次、检索什么）"。

### Q9：Agent 一定要用大模型吗？小模型能做 Agent 吗？

**参考答案**：
- 不一定非要最大的模型，但 Agent 对模型的**指令遵循、工具调用格式稳定性、多步推理**要求较高，太小的模型容易输出格式错乱、规划混乱。
- 实践中常用"分层"：简单子任务用小/快模型，复杂规划用大模型，兼顾成本与质量。
- 小模型做 Agent 的可行性正在提升（尤其针对特定领域微调后），但通用开放任务仍以中大模型为主。
- 关键不是参数量，而是**能否稳定地遵循工具调用协议并做出合理决策**。

> **追问/提示**：会延伸到"成本与性能类"的分层路由（见 Q90）。

### Q10：为什么 Agent 领域这两年才火，早年不行吗？

**参考答案**：
- 早年 LLM 的**指令遵循和工具调用能力不稳定**，难以支撑可靠的多步自主循环。
- 关键催化剂包括：模型能力跃升（更强的推理与 Function Calling）、Function Calling 的标准化、上下文窗口变长、以及 ReAct 等范式的提出。
- 生态成熟也是原因：框架（如 LangGraph、smolagents）、协议（如 MCP）、可观测工具让工程落地成本大降。
- 一句话：**不是想法新，而是"底座"够可靠了**，才让 Agent 从 demo 走向生产。

### Q11：Agent 的"目标（Goal）"和"任务（Task）"有什么区别？

**参考答案**：
- 目标是**期望达成的最终状态**（如"帮我订好去北京的机票"），通常抽象、可能需要多步。
- 任务是为达成目标而分解出的**具体可执行步骤**（查航班、比价、下单、确认）。
- Agent 的核心工作之一就是**把目标分解成任务序列**（规划），并在执行中根据反馈动态调整。
- 面试时点出"目标是终点、任务是路径，规划是二者之间的桥"，能显示你理解层次。

### Q12：什么是 Agent 的"环境（Environment）"？

**参考答案**：
- 环境是 Agent 所处、并能通过工具去感知和改变的**外部世界**：可以是文件系统、数据库、网页、API、操作系统，甚至另一个 Agent。
- Agent 通过工具"感知"环境（读数据）、通过工具"作用"于环境（写数据、发请求），再根据"观察"调整决策。
- 环境的**可观测性**和**可逆性**极大影响设计难度：不可逆的动作（如转账、删除）需要额外护栏和确认。
- 这是从强化学习借来的概念，帮助你把 Agent 看成"感知—行动"的闭环智能体。

### Q13：Agent 会"幻觉"吗？和 LLM 幻觉是一回事吗？

**参考答案**：
- Agent 幻觉根源仍是 LLM 幻觉，但**危害被放大**：模型可能编造不存在的工具、编造工具参数、或臆断工具返回结果。
- 典型表现：调用了不存在的函数、把失败的调用当成功、在没检索到证据时硬编答案。
- 缓解手段：严格的工具 schema 校验、把真实工具返回强制喂回上下文、要求"无证据就说不知道"、以及可观测追踪定位幻觉发生点。
- 关键认识：Agent 让幻觉从"说错话"升级为"做错事"，所以护栏更重要。

> **追问/提示**：可衔接到工程化类的护栏（Q80）与终止条件（Q82）。

### Q14：Agent 的"感知—决策—行动"循环和强化学习里的智能体是一回事吗？

**参考答案**：
- 概念上同源——都是"感知环境→做决策→采取行动→获得反馈"的闭环，Agent 借用了 RL 的智能体框架。
- 但实现机制不同：RL 智能体靠**奖励信号训练策略网络**，LLM Agent 靠**预训练模型的推理能力 + 提示/上下文**在推理时决策，通常不在线更新权重。
- LLM Agent 的"学习"更多发生在上下文层面（记忆、反思、few-shot），而非参数更新。
- 面试点出这个"同框架、异机制"的对比，能显示你知识面的广度。

### Q15：如果面试官问"你觉得现在的 Agent 最大的局限是什么"，怎么答？

**参考答案**：
- 可从三个层面答：**可靠性**（长链路错误累积、难以稳定复现）、**成本与延迟**（多步调用叠加，token 和时间成本高）、**评估难**（开放任务缺乏客观指标）。
- 再补一个"控制难"：自主性越高越难约束，安全和幂等成为硬约束。
- 给出你的判断：当前 Agent 在"流程较固定、可验证、有明确工具"的垂直场景最实用，通用开放自主仍不成熟。
- 这种"承认局限 + 给出适用边界"的回答，比一味吹捧更能打动面试官。

> **追问/提示**：这是典型的开放题，没有标准答案，重点是**有观点、有依据、有边界意识**。

#### 深挖专栏 A：把"控制权光谱"讲成一张图

基础概念类几乎所有题都能收敛到"控制权归属"这一个点上，所以值得单独用一张图把它钉死。很多人卡在"到底怎么算 Agent、怎么算 Workflow"，是因为脑子里是"非黑即白"的二分；一旦换成"光谱"，就豁然开朗了。
```
控制权在人  ←──────────────────────────────────────────────→  控制权在模型
   纯 LLM 调用   固定链(Chain)   带路由(Router)   Workflow 编排      Agent
   ├─────────────┼───────────────┼────────────────┼──────────────────┤
   问一次答一次   Prompt 串起来    if/else 分流     代码预定义全流程    模型运行时自主决策+循环
   完全可预测                                                        灵活但不可控
   最便宜/最快    ────────── 成本、灵活性、不可控性递增 ──────────→   最贵/最慢/最强
```
沿着这条光谱，面试里几乎所有"这算不算 Agent"的题都能就地判断：**把待判系统放到光谱上，看它的"下一步"是谁决定的。** 如果下一步永远由代码固定决定（哪怕它调了十个工具、用了三个模型），它在光谱左半边，是 Workflow；只要有一处"模型看了上一步的观察结果，自己决定接下来干什么"，它就开始向右滑，具备了 Agent 的内核。

这张图还能顺带回答"自主性越高越好吗"——显然不是。越往右，灵活性和能力上去了，但成本、延迟、不可控性也一起上去了。**工程的艺术不是"尽量往右"，而是"停在恰好够用的那个点"。** 这正是 Anthropic 反复强调的取舍：能用左边解决的，就别滑到右边[来源](https://www.anthropic.com/engineering/building-effective-agents)。

> **一个常见误区**：把"用了大模型/用了 RAG/接了很多工具"当成"更 Agent"。这些都只是"能力"，和"控制权在谁手里"是两个正交的维度。一个接了 20 个工具但调用顺序写死的系统，仍然是纯 Workflow。

#### 本类速记卡

基础概念类的所有题目，其实都在反复敲一个钉子：**Agent 的本质是"控制权交给模型"**。无论问定义、问自主性、问和 Workflow 的区别，只要你回答里能把"控制流由谁决定"这句话讲清楚，就抓住了这一类的题眼。下面这张速记表，把最容易混的几组概念一次性对齐，方便你面试前扫最后一眼。

| 对比项 | A | B | 一句话区分 |
|---|---|---|---|
| LLM 调用 vs Agent | 单轮问答，流程写死 | 多轮循环，模型决定下一步 | 看"谁决定下一步" |
| Workflow vs Agent | 代码预定义路径 | 模型运行时动态决定路径 | 看"控制流归属" |
| Chatbot vs Copilot vs Agent | 对话为主 / 人主导 AI 辅助 / AI 主导执行 | —— | 看"自主程度递增" |
| 目标 vs 任务 | 期望的最终状态 | 达成目标的具体步骤 | 规划是二者的桥 |
| LLM 幻觉 vs Agent 幻觉 | 说错话 | 做错事（编造工具/参数/结果） | Agent 把危害放大 |

**高频陷阱与红旗（本类）**：

1. 把"能调 API"直接等同于 Agent——普通函数也调 API，关键在"谁决定调不调"。
2. 只会背"感知—决策—行动"三个词，答不出与普通 LLM 调用的**本质**区别。
3. 认为"Agent 一定比 Workflow 高级、什么都该上 Agent"——答不出自主性的代价，就暴露了没有工程判断。
4. 把自主性说成"有或没有"的二分，而不是"程度"光谱。
5. 谈局限时只会说"会幻觉"，说不出可靠性、成本、评估难这些更结构化的维度。

**串题演练（模拟连环追问）**：面试官很可能这样一路问下来——"什么是 Agent？"→"那它和 Workflow 差在哪？"→"是不是都该用 Agent？"→"给你个系统你怎么判断它是不是 Agent？"→"现在 Agent 最大的局限是什么？"。你会发现这五问其实是同一根线（控制权 → 代价 → 判断 → 边界）。**准备时按这条线串一遍，比孤立背五道题高效得多。**

## 31.2 二、核心能力类（Q16-Q30）

这一类深入 Agent 的"四大原语"：**规划、记忆、工具使用、反思**。面试官通过这类题判断你是不是真的读过原理、动过手，而不是只会喊概念。答这类题最忌只说名词，要能讲清"机制"和"边界"。

### Q16：什么是 CoT（思维链）？它为什么有效？

**参考答案**：
- CoT（Chain-of-Thought）是让模型在给出最终答案前，**先输出一步步的中间推理过程**，把"直接跳到答案"变成"分步推导"。
- 它有效的直观解释是：把复杂问题分解成小步骤，每步只需较小的推理跨度，降低了单步出错概率；同时中间步骤给了模型"更多思考的 token 预算"。
- 触发方式包括"让我们一步步思考"这类提示，或提供带推理过程的 few-shot 示例。
- 局限：推理过程可能"看起来对但其实错"（伪推理），且更费 token；对简单任务反而是浪费。

> **追问/提示**：会问"CoT 和 ReAct 的关系"——ReAct 是在 CoT 的推理里插入了真实的"行动+观察"，让推理有外部依据。

### Q17：ToT（思维树）和 CoT 有什么区别？什么场景用 ToT？

**参考答案**：
- CoT 是**一条**线性推理链；ToT（Tree-of-Thought）是**探索多条**推理路径，形成一棵树，可以对不同分支评估、回溯、择优。
- ToT 适合**有多种可能解法、需要试探和比较、允许回溯**的问题（如解谜、复杂规划），用搜索换质量。
- 代价是成本大幅上升：探索多分支意味着成倍的模型调用和 token。
- 决策原则：任务解空间大、单链容易走死胡同时才用 ToT；简单任务用 CoT 甚至直接回答即可。

### Q18：Agent 的"规划（Planning）"有哪几种典型做法？

**参考答案**：
- 常见有几类：**边做边想（ReAct 式，走一步看一步）**、**先规划后执行（Plan-and-Execute，先出完整计划再依次做）**、**分解式（把大目标拆成子任务/子 Agent）**。
- Plan-and-Execute 的好处是全局视角强、减少来回摇摆，坏处是计划可能脱离实际、需要重规划机制。
- ReAct 式灵活、能随时纠偏，但缺乏全局规划，长任务容易"只见树木"。
- 生产中常混合：先粗规划出里程碑，执行中用 ReAct 处理每个里程碑的细节，遇到偏差再触发重规划。

> **追问/提示**："计划错了怎么办"——需要重规划（replanning）触发条件：子任务失败、观察与预期不符、超出预算。

### Q19：Agent 的记忆分哪几类？各自解决什么问题？

**参考答案**：
- 常见分为**短期记忆**（当前任务的上下文，通常就是对话/执行窗口）和**长期记忆**（跨会话持久保存的知识、偏好、历史）。
- 长期记忆又常细分：情景记忆（发生过什么）、语义记忆（事实知识）、程序记忆（怎么做某事的经验）。
- 短期记忆受上下文窗口限制，长期记忆通常靠外部存储 + 检索（如向量库）实现，用时再取回。
- 记忆系统解决的核心问题是：**让 Agent 在有限上下文下，跨步骤、跨会话保持连贯与个性化**。

> **追问/提示**：会问"短期记忆满了怎么办"——摘要压缩、滑动窗口、把旧内容外置到长期记忆再按需检索。

### Q20：为什么 Agent 需要长期记忆？不能全塞进上下文吗？

**参考答案**：
- 上下文窗口有限且昂贵：全塞进去会超长、变贵、变慢，还会稀释注意力（"中间迷失"效应，见 Q68）。
- 长期记忆把"用得着再取"的信息外置，只在需要时检索相关片段进上下文，兼顾成本与相关性。
- 它还带来跨会话能力：记住用户偏好、历史决策、过去的错误，实现个性化和持续改进。
- 一句话：**上下文是工作台，长期记忆是仓库**，不能把整个仓库搬上工作台。

### Q21：向量检索是记忆的唯一实现方式吗？

**参考答案**：
- 不是。向量检索擅长"语义相似"召回，但不擅长精确匹配、时间排序、结构化查询。
- 记忆可以用多种存储组合：**向量库**（语义召回）、**关系/文档数据库**（结构化事实、精确查询）、**键值缓存**（快速读写状态）、**知识图谱**（实体关系）。
- 实践中常混用：如"用户最近 5 条订单"用 SQL，而"和当前问题相关的历史对话"用向量检索。
- 关键是按**查询模式**选存储，而不是无脑上向量库。

### Q22：什么是 Function Calling？它和"工具使用"是一回事吗？

**参考答案**：
- Function Calling 是模型的一种能力：根据你提供的**函数 schema**（名字、参数、描述），模型输出一个**结构化的调用意图**（要调哪个函数、传什么参数）。
- 注意：**模型本身不执行函数**，它只是"决定并输出参数"，真正执行由你的代码完成，再把结果喂回模型。
- "工具使用"是更宽的概念，Function Calling 是当前实现工具使用最主流的机制。
- 关键点：它把"自由文本"变成"可被程序可靠解析和执行的结构化调用"，是 Agent 可靠调工具的基础。

> **追问/提示**：常追问"模型执行函数吗"——不执行，只产出调用意图，这是高频送分/送命点。

### Q23：一个工具的定义应该包含什么？怎么写好工具描述？

**参考答案**：
- 一个工具定义通常包含：**名字、功能描述、参数 schema（含类型/是否必填/取值约束）、返回说明**。
- 写好描述的要点：**站在模型视角**说清"这个工具什么时候该用、每个参数是什么意思、有什么边界"，描述本质是给模型看的"说明书"。
- 常见坑：描述含糊导致模型乱用、参数缺约束导致传错、功能重叠的工具让模型选择困难。
- 经验：工具描述质量往往比模型大小更影响调用准确率——**工具设计是 Agent 工程的核心手艺之一**。

### Q24：模型调用工具失败了，Agent 应该怎么处理？

**参考答案**：
- 首先要把**失败信息（错误码、报错文本）如实喂回模型**，让它知道"这次没成功、为什么没成功"，而不是假装成功。
- 然后可设计策略：允许模型基于错误信息**重试/换参数/换工具**，但要设**重试上限**防止死循环。
- 对不可逆或高风险动作，失败后应停下来请求人确认，而不是自动反复尝试。
- 关键认识：**工具会失败是常态**，Agent 的鲁棒性很大程度上就是错误处理设计得好不好。

> **追问/提示**：衔接工程化类的终止条件（Q82）和幂等（Q84）。

### Q25：什么是反思（Reflection）？它如何提升 Agent 表现？

**参考答案**：
- 反思是让 Agent **对自己的输出或执行过程进行审视、批评、并据此改进**的机制，本质是"自己给自己当审稿人"。
- 典型做法：生成初稿 → 用另一次调用（或另一个角色）指出问题 → 根据反馈修订，可迭代多轮。
- 它能提升复杂任务（代码、写作、多步推理）的质量，因为很多错误"生成时看不出、回看才发现"。
- 代价：多轮反思成倍增加成本和延迟，且可能"越改越差"或陷入自我肯定，需要设停止条件。

> **追问/提示**："反思一定有用吗"——不一定，简单任务反思是浪费，且反思质量受模型自评能力限制。

### Q26：Reflexion、Self-Refine 这类方法的核心思想是什么？

**参考答案**：
- 核心都是**"用反馈驱动迭代改进"**：先产出结果，再获得某种评价（自评、环境反馈、或外部信号），把评价转化为下一次尝试的改进指引。
- Self-Refine 偏"自己评自己改"；Reflexion 强调把失败的经验**以语言形式存进记忆**，下次遇到类似情况调用，实现"跨尝试学习"。
- 它们的价值在于不改模型权重，仅靠上下文和记忆就实现"经验积累"。
- 边界：依赖模型能产生有效反馈；如果自评不准，迭代可能无效甚至有害。

### Q27：Agent 如何判断"任务已经完成"？

**参考答案**：
- 完成判定通常有几种来源：**模型自己声明完成**（输出终止信号/停止调用工具）、**满足显式条件**（如结果通过校验、达到目标状态）、**外部验证器判定**（测试通过、schema 校验通过）。
- 只靠模型自称"我完成了"不可靠，容易过早或虚假宣称成功，最好配合**可验证的完成标准**。
- 同时必须有**兜底终止**：最大步数、最大时间、最大预算，防止判断不了时无限循环。
- 好的完成判定 = 模型信号 + 客观校验 + 硬性兜底，三者叠加。

> **追问/提示**：这题几乎必然连到 Q82（终止条件设计）。

### Q28：多步任务里错误会累积，怎么缓解？

**参考答案**：
- 根因是长链路里每步都有出错概率，误差逐步放大（"平方级/指数级"恶化，见 Q97）。
- 缓解手段：**缩短链路**（能一步做完不拆两步）、**每步加校验**（结构化输出 + schema 校验）、**引入反思/自检**、**关键步骤人确认**。
- 架构上可用"检查点 + 可回退"，出错时回到最近的正确状态重试，而不是从头再来。
- 更根本的是**降低单步失败率**（好的工具设计、清晰提示、约束输出），因为长链路对单步可靠性极其敏感。

### Q29：什么是"工具选择困难"？工具太多会怎样？

**参考答案**：
- 当可用工具数量多、功能重叠、描述含糊时，模型容易**选错工具、漏选、或反复纠结**，准确率下降、token 上升。
- 缓解：**精简工具集**（只暴露当前场景需要的）、**清晰互斥的命名和描述**、**按阶段/角色动态裁剪可见工具**、必要时用检索先筛出候选工具再交给模型。
- 经验：工具不是越多越好，"给模型看的选项越少越聚焦，决策越准"。
- 这也是多 Agent 分工的动因之一——每个子 Agent 只面对自己那一小撮工具。

### Q30：Agent 能自己"创造工具"吗？

**参考答案**：
- 在一定意义上可以：一些做法让 Agent **把常用的动作序列固化成新工具/新函数**（如生成代码并保存为可复用函数），下次直接调用。
- 代码型 Agent（如以代码为动作的范式）天然更容易"造工具"——它写的代码本身就是可复用的能力。
- 好处是能力随使用积累、减少重复推理；风险是自造工具的正确性和安全性需要校验。
- 这属于较前沿的方向，面试中能提出来体现你了解趋势，但要点明它的可靠性挑战。

> **追问/提示**：可衔接 smolagents 的"代码即动作"理念（见 Q49、Q52）。

#### 深挖专栏 B：一次 ReAct 循环到底长什么样

核心能力类里，ReAct 是被问得最多、也最容易"答得空"的一题。很多人能背出"Reasoning + Acting"，却说不清一次循环里到底发生了什么。下面这张时序图，把"查北京今天天气"这个最简单的例子拆到每一步，面试时能照着讲，立刻显得你"真的懂"。
```
用户: 北京今天天气怎么样？
  │
  ▼
┌─ 第 1 轮 ───────────────────────────────────────────────┐
│ Thought(推理): 我不知道实时天气，需要调天气工具            │
│ Action(行动):  get_weather(city="北京")                  │
│ Observation(观察): {"temp": 28, "cond": "晴", "date":今天} │  ← 真实工具返回，回填上下文
└──────────────────────────────────────────────────────────┘
  │  模型看到 Observation，判断"信息够了"
  ▼
┌─ 第 2 轮 ───────────────────────────────────────────────┐
│ Thought: 已拿到数据，可以回答了，无需再调工具              │
│ Final Answer: 北京今天晴，气温约 28℃                      │
└──────────────────────────────────────────────────────────┘
```
看这张图，几个"送分点"就自然浮出来了：

1. **每一轮都有"观察"回填。** 这正是 ReAct 相比纯 CoT 的关键——推理不是凭空进行的，而是每步都拿真实反馈校正（呼应 Q3、Q16）。
2. **循环的出口是模型自己判断"够了"。** 这就是终止判定的起点（呼应 Q27），也是为什么必须再加"最大步数"兜底（呼应 Q82）——万一模型判断不了呢？
3. **上下文在逐轮累积。** 第 2 轮要带着第 1 轮的 Thought/Action/Observation 一起发给模型。轮数一多，上下文就膨胀，这就是"平方级成本"的种子（呼应 Q89）。

> **生产踩坑**：曾见过一个 Agent 因为工具返回里带了一句"如需更多信息请调用 X 接口"，模型把这句"数据里的话"当成了"指令"，于是又去调 X，再又被带去调 Y……绕了七八步才停。根因是**没有把"数据"和"指令"分清**（呼应 Q81 提示注入），也**没设进展检测**（呼应 Q82）。这个坑很典型：ReAct 的每一步"观察"都是外部内容，不能无条件信任。

#### 本类速记卡

核心能力类考的是"四大原语"：规划、记忆、工具、反思。它们不是四个孤立模块，而是一个循环里的四个环节——**规划决定"做什么"，工具负责"去做"，记忆保存"做过什么和结果"，反思判断"做得好不好、要不要重来"**。下面把这一类里最常被追问的机制点浓缩成一张对照表。

| 能力 | 一句话本质 | 关键机制 | 主要代价/边界 |
|---|---|---|---|
| CoT | 先分步推理再答 | 拆解 + 更多思考 token | 可能伪推理、费 token |
| ToT | 探索多条路径择优 | 分支 + 评估 + 回溯 | 成本成倍上升 |
| Plan-and-Execute | 先出计划再执行 | 全局规划 + 重规划 | 计划可能脱离实际 |
| 记忆 | 跨步/跨会话保状态 | 短期上下文 + 长期外置检索 | 检索质量决定上限 |
| Function Calling | 模型产出结构化调用意图 | schema + 结果回填 | 模型不执行，执行在你侧 |
| 反思 | 自己给自己当审稿人 | 生成 → 批评 → 修订 | 可能越改越差、更贵 |

**高频陷阱与红旗（本类）**：

1. 说"模型自己执行了函数"——错，模型只产出调用意图，执行在你的代码侧（Q22 送命点）。
2. 认为"反思/ToT 一定更好"——它们是用成本换质量，简单任务是浪费。
3. 谈记忆只会说"上向量库"——答不出向量检索不擅长精确匹配、时间排序、结构化查询（Q21）。
4. 忽视"错误累积"，把长链路当成和短链路一样可靠（Q28、Q97 数学根据）。
5. 谈工具只讲"注册了什么工具"，讲不出"工具描述质量决定调用成功率"这个手艺活。

**串题演练**："什么是 ReAct？"→"它和 CoT 什么关系？"→"每步都推理不是很贵吗，怎么优化？"→"多步错误会累积，你怎么缓解？"→"任务什么时候算完成？"。这条线把规划、成本、可靠性、终止串到了一起，正好衔接后面的工程化与成本类。

## 31.3 三、协议与编排类（Q31-Q45）

这一类考"多个组件/多个 Agent 怎么协作"：Function Calling 的端到端机制、MCP 协议、五种工作流模式、多 Agent 拓扑。这是区分"会用框架"和"懂系统"的分水岭，也是系统设计题的基础。

### Q31：完整描述一次 Function Calling 的端到端流程。

**参考答案**：
- 一次典型流程分五步：① 你把**工具 schema + 用户问题**一起发给模型；② 模型判断需要调工具，返回**结构化调用意图**（函数名 + 参数）；③ **你的代码执行**该函数，拿到真实结果；④ 把**结果作为一条消息回填**进上下文再发给模型；⑤ 模型基于结果生成最终回答，或决定继续调下一个工具。
- 关键点：模型只"决定"，执行在你这边；结果必须回填，否则模型不知道发生了什么。
- 多步任务就是这五步的循环，直到模型不再要求调工具。
- 这套机制的可靠性依赖于 schema 清晰、参数校验、以及结果回填的正确格式。

> **追问/提示**：会问"并行工具调用怎么处理"——现代模型可一次返回多个调用，你并发执行后按 id 对应回填。

### Q32：Function Calling 里的 schema 为什么重要？写错了会怎样？

**参考答案**：
- schema 是模型和你的代码之间的"契约"，定义了函数名、参数结构、类型、约束。它决定模型能否**稳定产出可解析的调用**。
- schema 含糊/缺约束会导致：模型传错参数类型、漏必填字段、编造不存在的参数，进而执行失败或行为异常。
- 好 schema 的要点：描述清晰、参数有类型和枚举约束、必填项明确、返回结构可预期。
- 可以说 schema 质量直接决定工具调用成功率——**它是给模型的 API 文档，也是给代码的校验规则**。

### Q33：什么是 MCP？它要解决什么问题？

**参考答案**：
- MCP（Model Context Protocol）是一个**开放协议，用统一标准把 AI 应用和外部工具/数据源连接起来**，常被比喻为"AI 应用的 USB-C"[来源](https://modelcontextprotocol.io/)。
- 它要解决的核心痛点是 **M×N 集成爆炸**：M 个应用要接 N 个工具，若各写各的对接，就有 M×N 种适配；有了统一协议，变成 M+N。
- MCP 让工具/数据源的提供方只需实现一次 Server，任何支持 MCP 的应用（Client/Host）都能接入。
- 意义：把"工具接入"从一次性定制变成可复用的标准化生态。

> **追问/提示**：会追问 M×N → M+N 的具体含义，务必能画出来讲清楚。

### Q34：MCP 里的 Host、Client、Server 分别是什么？

**参考答案**：
- **Host**：用户直接交互的 AI 应用（如某个 AI 客户端/IDE），负责整体协调。
- **Client**：Host 内部为每个 Server 维护的连接器，一个 Client 对应一个 Server 连接。
- **Server**：暴露具体能力（工具、资源、提示）的一方，如一个连数据库、连文件系统的服务。
- 关系：Host 内含多个 Client，每个 Client 连一个 Server；Server 提供能力，Host 消费能力。

### Q35：MCP 主要暴露哪几类能力？

**参考答案**：
- 常见三类：**Tools（可被模型调用的函数/动作）、Resources（可读取的数据/上下文，如文件、记录）、Prompts（预定义的提示模板）**。
- Tools 偏"做动作"，Resources 偏"给上下文"，Prompts 偏"复用交互模式"。
- 这种分层让 Server 能以统一方式对外提供"能干什么、有什么数据、怎么用"。
- 理解这三类的区别，有助于设计一个清晰的 MCP Server。

### Q36：MCP 和 Function Calling 是什么关系？会冲突吗？

**参考答案**：
- 不冲突，是**不同层次**：Function Calling 是"模型如何决定调用一个工具"的模型能力；MCP 是"工具如何被标准化地发现、连接、暴露"的协议层。
- 打个比方：Function Calling 是模型"会用工具的手"，MCP 是"工具插座的统一规格"。
- 实践中二者结合：MCP Server 暴露工具 → Host 把这些工具转成模型能理解的 schema → 模型用 Function Calling 决定调用。
- 所以它们是互补的：一个解决"怎么调"，一个解决"怎么接"。

> **追问/提示**：这是高频对比题，别混为一谈，务必点出"层次不同、互补"。

### Q37：Anthropic 总结的五种 Agentic 工作流模式是哪些？

**参考答案**：
- 通常概括为：**① Prompt Chaining（提示链，按序拆步）；② Routing（路由，先分类再分流）；③ Parallelization（并行，含分片与投票）；④ Orchestrator-Workers（编排者—工作者，主控动态派活）；⑤ Evaluator-Optimizer（评估者—优化者，生成后评估再改进）**[来源](https://www.anthropic.com/engineering/building-effective-agents)。
- 前几种偏"结构可预测的 Workflow"，最后一种引入了迭代改进的循环。
- 它们的共性是"用可控结构编排 LLM"，而非放任模型完全自主。
- 记忆技巧：链、路由、并行、编排、评估—优化，对应五种典型协作形态。

> **追问/提示**：几乎必考——要能各举一个真实场景，并说清和"全自主 Agent"的区别。

### Q38：Prompt Chaining 和 Routing 分别适合什么场景？

**参考答案**：
- **Prompt Chaining** 适合任务能被**清晰拆成固定顺序的子步骤**（如"先提炼要点 → 再翻译 → 再润色"），每步产出喂给下一步，可在中间加校验门（gate）。
- **Routing** 适合输入**有明显分类**、不同类别走不同处理路径（如客服先判断"退款/技术/咨询"再分流到对应流程或模型）。
- Chaining 是"串行分解"，Routing 是"分类分流"，二者常组合使用。
- 选择依据：任务是"一条流水线"用 Chaining，是"多条岔路"用 Routing。

### Q39：Parallelization（并行）模式有哪两种典型形态？

**参考答案**：
- 一种是**分片（Sectioning）**：把任务拆成互不依赖的子任务并行跑，最后汇总（如把长文档分段并行处理）。
- 另一种是**投票/多数表决（Voting）**：让多个模型/多次采样并行产出，再聚合择优（如多次生成取一致答案，或多角度审查）。
- 并行的价值是**降低延迟**（分片）或**提升可靠性/覆盖度**（投票）。
- 代价是成本上升（并发多次调用）和汇总逻辑的复杂度。

### Q40：Orchestrator-Workers 和固定并行有什么区别？

**参考答案**：
- 固定并行的子任务是**事先确定**的；Orchestrator-Workers 里，**编排者（Orchestrator）在运行时动态决定要拆出哪些子任务**，再分派给 Worker 执行、最后综合。
- 因为子任务由模型运行时生成，这种模式**更 Agentic**，适合事前无法穷举分工的复杂任务（如"调研并写报告"）。
- 代价是更难预测和调试，成本也更高。
- 它是很多"主管 Agent + 子 Agent"多智能体系统的骨架。

### Q41：Evaluator-Optimizer 模式的核心循环是什么？

**参考答案**：
- 核心是**"生成 → 评估 → 反馈 → 再生成"**的循环：一个角色产出结果，另一个角色（评估者）依据标准打分/挑错，把反馈交回生成者改进。
- 它适合**有明确评价标准、且迭代能带来提升**的任务（如翻译润色、代码改错）。
- 与反思（Reflection）思想一致，区别是这里把"生成者"和"评估者"显式分成两个角色/两次调用。
- 停止条件很关键：达到质量阈值或最大迭代次数就停，避免无限打磨。

### Q42：什么时候该用多 Agent，而不是单 Agent？

**参考答案**：
- 当任务**需要多种差异很大的专长、工具集庞杂到单 Agent 难以驾驭、或需要并行推进多条子任务**时，多 Agent 有价值。
- 多 Agent 的好处：职责分离、每个 Agent 上下文/工具更聚焦、可并行、可独立演进。
- 代价也很实在：通信开销、协调复杂度、上下文传递损耗、整体更难调试、成本更高。
- 原则：**能用单 Agent + 好的工具设计解决，就别急着上多 Agent**；多 Agent 是解决复杂度的手段，本身也是复杂度。

> **追问/提示**：这是系统设计高频题，切忌无脑吹多 Agent，要能说出它的代价。

### Q43：多 Agent 有哪些常见的协作拓扑？

**参考答案**：
- 常见拓扑：**主管/编排式（一个 Orchestrator 派活给多个 Worker）、流水线式（Agent 依次接力）、群聊/协商式（多个 Agent 讨论达成一致）、层级式（多层主管—下属）**。
- 主管式最常用、最可控，适合"分派—汇总"型任务；流水线适合有明确阶段的流程；群聊式灵活但难控、易发散。
- 选择依据：任务是"分派汇总"用主管式，是"阶段接力"用流水线，需要"多视角碰撞"才考虑群聊式。
- 拓扑越自由，协调成本和不可控性越高。

### Q44：多 Agent 之间怎么传递信息？有什么坑？

**参考答案**：
- 常见方式：**共享状态/黑板（写到公共存储）、消息传递（结构化消息/事件）、直接把上文摘要塞进下一个 Agent 的提示**。
- 主要坑：**上下文传递损耗**（转述几手后信息失真）、**上下文膨胀**（把全部历史都传导致又贵又乱）、**职责边界不清**导致重复或遗漏。
- 缓解：传"结构化的、必要的"信息而非全部原文，定义清晰的接口契约，关键交接点做校验。
- 经验：多 Agent 系统的 bug 大多出在"交接处"，接口设计比单个 Agent 的聪明程度更重要。

### Q45：为什么有人说"多数所谓多 Agent 系统其实是 Workflow"？

**参考答案**：
- 因为很多"多 Agent"系统的 Agent 间调用顺序是**代码写死的**（先调 A 再调 B），本质是被拆成多个模块的 Workflow，而非真正由模型动态决定协作。
- 真正的多 Agent 强调**运行时动态决定"调谁、调几个、怎么协作"**，而不仅是把流程切成几块分别用 LLM。
- 这个区分呼应了 Q4 的核心判据——**控制流由谁决定**。
- 面试时点出这一点，能显示你不被"多 Agent"的营销话术带偏，看得清系统本质。

> **追问/提示**：可延伸——"那到底该追求哪种"，答案仍是"看场景需不需要动态协作，能固定编排就固定编排"。

#### 深挖专栏 C：把 MCP 的 M×N → M+N 画出来

MCP 那道题（Q33）里最容易"背了但讲不清"的，就是"M×N 集成爆炸"。这是个一画图就秒懂的东西，面试时能顺手画出来，效果远好过干背"USB-C"这个比喻。

没有统一协议时，M 个 AI 应用各自要对接 N 个工具，每一对都要写一套专属适配，连线数是 **M×N**：
```
   没有 MCP（M×N 条定制连线）              有了 MCP（M+N 条标准连线）

  App1 ─┬─ 工具A                          App1 ─┐              ┌─ 工具A
        ├─ 工具B                          App2 ─┼─  MCP 协议  ─┼─ 工具B
  App2 ─┼─ 工具A          ==>             App3 ─┘  (统一标准)   └─ 工具C
        ├─ 工具C                                    每个应用只实现一次 Client，
  App3 ─┴─ ...                                      每个工具只实现一次 Server
  （每加一个应用或工具，连线成倍增加）        （加应用只 +1，加工具也只 +1）
```
这张图把 MCP 的价值一次讲透：**它不是让某个 Agent 变聪明，而是把"工具接入"从一次性定制变成可复用的标准生态**——工具方只需实现一次 Server，任何支持 MCP 的应用都能即插即用[来源](https://modelcontextprotocol.io/)。集成的复杂度从相乘降到相加，这就是协议层的意义。

顺带把 Q36 那个高频对比也钉死：**MCP 和 Function Calling 处在不同层次，不是竞品。** 用一句话串起来就是——"MCP 负责把工具标准化地送到模型面前（协议层），Function Calling 负责让模型决定调用哪个、传什么参数（模型能力层），你的代码负责真正执行（执行层）。" 三层各司其职：
```
[协议层]  MCP：发现/连接/暴露工具  ──→  把工具转成模型能读的 schema
                                              │
[能力层]  Function Calling：模型输出"调哪个、传什么"（只决定，不执行）
                                              │
[执行层]  你的代码/MCP Server：真正跑这个动作，把结果回填
```
> **面试会怎么问**：一旦你能主动画出这三层，面试官往往会顺势追问"那如果不用 MCP，只用 Function Calling 行不行？"——答案是"完全行，MCP 是为了解决多应用多工具的规模化接入，单应用少量工具时直接写 Function Calling 的 schema 反而更简单"。这又回到全书主线：**能简单就简单，MCP 是为规模化准备的，不是默认必需品。**

#### 本类速记卡

协议与编排类有两条主线：一条是**"怎么接"**（Function Calling 的机制、MCP 的标准化），一条是**"怎么协作"**（五种工作流模式、多 Agent 拓扑）。两条线在面试里经常交叉，能把"层次"讲清楚（模型能力层 vs 协议层 vs 编排层）就赢了一半。先记住这张五种模式速查表。

| 模式 | 一句话 | 适用场景 | Agentic 程度 |
|---|---|---|---|
| Prompt Chaining | 固定顺序拆步，逐步传递 | 可清晰分解的流水线 | 低 |
| Routing | 先分类再分流 | 输入有明显类别 | 低 |
| Parallelization | 分片并行 / 多次投票 | 可拆分 / 要提可靠性 | 低-中 |
| Orchestrator-Workers | 主控运行时动态派活 | 分工事前无法穷举 | 中-高 |
| Evaluator-Optimizer | 生成→评估→再生成 | 有明确评价标准可迭代 | 中 |

**高频陷阱与红旗（本类）**：

1. 把 Function Calling 和 MCP 混为一谈——一个是"模型怎么调"，一个是"工具怎么接"，层次不同、互补（Q36）。
2. 说不清 MCP 的 M×N → M+N 价值，只会背"USB-C"这个比喻。
3. 无脑吹多 Agent，答不出通信开销、上下文损耗、协调复杂度这些代价（Q42）。
4. 把"把流程切成几块分别用 LLM"当成真正的多 Agent，其实那还是 Workflow（Q45）。
5. 五种模式记不全或分不清哪种更 Agentic，举不出对应的真实场景。

**串题演练**："完整讲一次 Function Calling 流程"→"如果一次要调多个工具怎么办？"→"这些工具怎么标准化接入（MCP）？"→"多个工具/多步之间怎么编排（五种模式）？"→"什么时候要上多 Agent？"。这条线从"单次调用"一路铺到"多 Agent 系统"，是协议编排类最典型的递进。

## 31.4 四、框架类（Q46-Q58）

这一类考"工具箱认知"：主流框架各自的定位、设计哲学、擅长与不擅长，以及"给你一个场景怎么选型"。面试官不指望你精通每个框架，但希望你**说得清差异、讲得出取舍**，而不是只会背一个框架的 API。

### Q46：为什么要用 Agent 框架？不用框架自己写不行吗？

**参考答案**：
- 完全可以不用框架——一个 Agent 循环的核心不过是"调模型 → 解析工具调用 → 执行 → 回填 → 再循环"，几十行就能写出来。
- 框架的价值在于**省掉重复的脚手架**：工具注册、消息管理、状态持久化、流式输出、错误重试、可观测集成等。
- 但框架也有代价：抽象层可能"帮倒忙"（黑盒、难调试、被框架的假设绑架）。
- 成熟的观点是：**先手写理解本质，再按需选框架**；简单场景手写更透明，复杂场景框架省力。Anthropic 也建议先理解底层再决定要不要抽象[来源](https://www.anthropic.com/engineering/building-effective-agents)。

> **追问/提示**：会问"框架的坏处"——过度抽象、黑盒、版本变动快、锁定，务必答得出。

### Q47：smolagents、PydanticAI、LangGraph 三者的定位有何不同？

**参考答案**：
- **smolagents**（Hugging Face）：极简、轻量，核心理念是"**代码即动作**（让模型直接写代码来行动）"，适合快速上手和理解 Agent 本质[来源](https://github.com/huggingface/smolagents)。
- **PydanticAI**（Pydantic 团队）：强调**类型安全和结构化输出**，把 Pydantic 的数据校验带进 Agent 开发，适合工程化、要求可靠输出的场景[来源](https://github.com/pydantic/pydantic-ai)。
- **LangGraph**（LangChain 团队）：把 Agent 建模成**图（节点+边+状态）**，擅长复杂、有状态、可控流程编排和多 Agent，适合生产级复杂系统[来源](https://github.com/langchain-ai/langgraph)。
- 一句话记忆：**smolagents 轻、PydanticAI 稳、LangGraph 强**（可控复杂流程）。

> **追问/提示**：几乎必考的选型题，务必能各说一句"最适合的场景"。

### Q48：给你一个"简单的单工具查询 Agent"，你会选哪个框架？为什么？

**参考答案**：
- 简单单工具场景，我倾向**手写或用 smolagents 这类轻量方案**——避免为小需求引入重框架的复杂度。
- 理由：单工具循环逻辑简单，重框架的状态图、编排能力用不上，反而增加学习和调试成本。
- 如果对**输出结构有强校验要求**（比如要稳定返回结构化 JSON），可以选 PydanticAI。
- 选型第一原则永远是"**匹配复杂度**"：别用牛刀杀鸡，也别用水果刀砍柴。

### Q49：smolagents 的"代码即动作（Code as Action）"是什么意思？有什么优势？

**参考答案**：
- 传统 Agent 用"JSON 工具调用"来表达动作；smolagents 让模型**直接写并执行 Python 代码**作为动作。
- 优势：一段代码里可以**组合多个操作、用变量传递中间结果、写循环和条件**，表达能力比"一次一个 JSON 调用"强得多，往往用更少的步骤完成任务。
- 它也更贴近"编程"的本质，模型对代码的掌握通常好于臆造的 JSON 格式。
- 代价与风险：执行模型生成的代码有**安全隐患**，必须放在沙箱/受限环境里运行。

> **追问/提示**：必问安全——如何隔离执行？答沙箱、白名单模块、资源限制、禁网等。

### Q50：PydanticAI 的核心卖点"类型安全"具体带来什么好处？

**参考答案**：
- 它用 Pydantic 模型定义 Agent 的**输入、输出、依赖**，模型产出会被**校验成强类型对象**，不合规就报错或重试。
- 好处：把"模型输出不可控"这个老大难，转成"要么符合 schema、要么明确失败"，大幅提升下游代码的可靠性。
- 对工程团队友好：类型提示、IDE 补全、和现有 Python 类型体系无缝衔接，降低维护成本。
- 适合把 Agent 嵌入严肃后端系统、对输出契约有硬要求的场景。

### Q51：LangGraph 把 Agent 建模成"图"，这个抽象好在哪？

**参考答案**：
- 它把流程拆成**节点（一步计算/一次调用）、边（转移，可带条件）、共享状态**，Agent 的执行就是在图上流转。
- 好处：**流程显式可见、可控、可持久化**——你能清楚看到有哪些状态和分支，方便加检查点、回溯、人在回路、断点续跑。
- 特别适合复杂、有循环和条件、需要精细控制的生产系统，以及多 Agent 编排。
- 代价是概念多、上手门槛比轻量框架高，简单任务用它是"杀鸡用牛刀"。

> **追问/提示**："图模型对比 ReAct 循环有什么优势"——把隐式循环变成显式可控的状态机，更好调试和干预。

### Q52：同样是让 Agent 行动，"写代码"和"输出 JSON 工具调用"各有什么优劣？

**参考答案**：
- **JSON 工具调用**：结构化、易校验、易加权限控制、执行安全边界清晰；但一次只表达一个调用，多步组合啰嗦、状态要靠外部管。
- **写代码（Code Action）**：表达力强，能一段里组合多操作、循环、条件、变量传递，步骤更少；但执行任意代码有安全风险，必须沙箱化，且不易做细粒度权限。
- 选择：**受控/高安全要求**场景偏 JSON 工具调用；**表达复杂逻辑、追求少步骤**且能保证沙箱安全时偏代码动作。
- 二者不是对立，有的系统混用：常规动作走工具，复杂计算交给代码。

### Q53：框架选型时你会考虑哪些维度？

**参考答案**：
- 我会看几条：**任务复杂度**（简单→轻量，复杂有状态→图式）、**输出可靠性要求**（强校验→类型安全框架）、**可观测/调试支持**、**社区与文档成熟度**、**团队技术栈契合度**、**锁定风险与可迁移性**。
- 还要看**生产诉求**：要不要持久化、断点续跑、人在回路、并发编排。
- 原则是"从需求倒推"，而不是"哪个火用哪个"。
- 最后补一句：框架会变，**核心是理解 Agent 原理**，框架只是把原理封装得更顺手。

### Q54：LangChain 和 LangGraph 是什么关系？

**参考答案**：
- 二者出自同一生态（LangChain 团队）。LangChain 早期以"链（Chain）"和大量集成组件著称，偏"把 LLM 应用的常用积木拼起来"。
- LangGraph 是更后来的、面向**有状态、可控、可循环的 Agent/多 Agent 编排**的库，用图抽象解决复杂流程控制[来源](https://github.com/langchain-ai/langgraph)。
- 可以理解为：需要复杂流程控制和状态管理时，LangGraph 提供了比早期 Chain 更合适的模型。
- 面试时不必纠结版本细节，讲清"链式拼装"到"图式编排"的演进思路即可。

### Q55：Hugging Face 的 Agents Course 覆盖了哪些内容？值得学吗？

**参考答案**：
- 它是一个系统的免费课程，覆盖 Agent 基础概念、工具使用、框架实践（含 smolagents 等）、以及动手项目[来源](https://huggingface.co/learn/agents-course)。
- 优点：结构清晰、由浅入深、带实操，适合建立体系化认知而非零散看博客。
- 对面试准备的价值：帮你把"概念—代码—项目"打通，很多面试题的底层知识都能在里面找到出处。
- 学习建议：配合动手做项目，别只看不练。

### Q56：框架频繁更新、API 变动大，怎么应对？

**参考答案**：
- 心态上接受"框架是快速演进的工具"，不把宝押在某个具体 API 上，而是**吃透背后的原理**（循环、工具、状态、编排），换框架时才能快速迁移。
- 工程上：**锁定版本**、写好抽象隔离层（把框架调用包一层自己的接口）、关注 changelog、有测试兜底。
- 选型时把"社区活跃度和向后兼容记录"也算进去。
- 一句话：**依赖原理，警惕锁定**。

### Q57：面试官问"你用过哪个框架，讲讲踩过的坑"，怎么答好？

**参考答案**：
- 结构：**先说场景 → 再说遇到的具体问题 → 然后说你怎么定位和解决 → 最后提炼出可复用的经验**。
- 好的坑要具体，比如："框架默认把全部历史塞进上下文导致 token 暴涨，我改成摘要 + 按需检索""工具描述含糊导致模型选错，我重写了描述和参数约束"。
- 避免空泛吐槽框架，要体现**你从坑里学到了什么、下次怎么避免**。
- 这类题考的是真实经验和反思能力，编不出来一问就露馅，所以准备时要基于自己真做过的项目。

> **追问/提示**：这是开放经验题，务必用自己的真实项目，切勿硬编。

### Q58：如果完全不用任何框架，手写一个最小 Agent 需要哪些部分？

**参考答案**：
- 核心循环：**构造带工具 schema 的请求 → 调模型 → 解析返回（是普通回答还是工具调用）→ 若是工具调用则执行并回填结果 → 回到循环，直到无工具调用或触发终止条件**。
- 必备配套：工具注册表（名字→函数映射）、消息历史管理、终止条件（最大步数/预算）、错误处理（工具失败回填、重试上限）。
- 可选增强：结构化输出校验、日志/追踪、并行工具调用、状态持久化。
- 亲手写一遍这个最小实现，是理解一切框架的最好方式——**框架无非是把这些部分做得更完善**。

> **追问/提示**：能当场口述这个循环骨架，比背任何框架 API 都加分。

#### 本类速记卡

框架类的最高原则只有一句：**框架服务于原理，原理决定选型**。面试官不在乎你能背几个 API，在乎你能不能"给个场景说清该用什么、为什么、代价是什么"。三个主流框架的一句话定位务必脱口而出。

| 框架 | 一句话定位 | 核心理念 | 最适合 |
|---|---|---|---|
| smolagents | 轻 | 代码即动作 | 快速上手、理解本质、少步完成 |
| PydanticAI | 稳 | 类型安全、结构化输出 | 要求可靠输出契约的工程系统 |
| LangGraph | 强 | 图（节点+边+状态） | 复杂有状态、可控流程、多 Agent |

**高频陷阱与红旗（本类）**：

1. 只会背一个框架的 API，说不出框架之间的差异和取舍。
2. 认为"用框架一定比手写好"——答不出框架的坏处（过度抽象、黑盒、锁定、版本变动）。
3. 谈"代码即动作"只说好处，不提"执行模型生成代码必须沙箱"的安全前提（Q49）。
4. 选型时"哪个火用哪个"，而不是从需求（复杂度、可靠性、可观测、锁定风险）倒推。
5. 被问"踩过什么坑"时空泛吐槽，讲不出定位过程和沉淀的经验（Q57）。

**串题演练**："你用过哪些框架？"→"它们定位有什么不同？"→"给你个简单单工具场景选哪个？"→"复杂多状态呢？"→"不用框架你能手写一个最小 Agent 吗？"。最后这一问是"照妖镜"——**能口述循环骨架的人，才是真懂框架在封装什么。**

## 31.5 五、RAG 与上下文类（Q59-Q73）

这一类考"怎么把外部知识和上下文喂好给模型"：传统 RAG 与 Agentic RAG 的区别、分块、重排、上下文工程、中间迷失。RAG 几乎是所有实用 Agent 的底座，这类题问得又细又实。

### Q59：什么是 RAG？它解决了什么问题？

**参考答案**：
- RAG（Retrieval-Augmented Generation，检索增强生成）是**先从外部知识库检索相关内容，再把它拼进提示让模型基于证据回答**的方法。
- 它解决三个痛点：**知识截止**（模型不知道训练后的新知识）、**幻觉**（有证据可依，减少瞎编）、**私域知识**（模型没见过你的内部文档）。
- 典型流程：文档切块 → 向量化入库 → 用户提问时检索 top-k 相关块 → 拼进上下文 → 模型基于检索内容生成答案。
- 一句话：**让模型"开卷考试"，而不是凭记忆硬答**。

### Q60：传统 RAG 和 Agentic RAG 有什么区别？

**参考答案**：
- **传统 RAG** 是**固定单次流程**：检索一次 → 塞进上下文 → 生成，检索时机、次数、query 都是写死的。
- **Agentic RAG** 把检索变成 Agent 可自主决策的动作：**由模型判断要不要检索、检索几次、每次用什么 query、检索到的够不够、要不要换个角度再查**。
- 因此 Agentic RAG 能处理需要多跳推理、需要迭代求证、单次检索答不了的复杂问题。
- 代价：更多模型调用、更高成本和延迟、更难预测——本质是"用自主性换能力"，呼应 Q4 的控制权光谱。

> **追问/提示**：会问"什么时候用 Agentic RAG"——简单事实查询用传统 RAG 就够，多跳/需求不明确/要求证时才升级。

### Q61：为什么要分块（Chunking）？块太大或太小分别有什么问题？

**参考答案**：
- 分块是因为文档太长无法整篇塞进上下文，也因为检索需要**粒度合适的语义单元**来匹配 query。
- **块太大**：一个块混入多个主题，检索精度下降、噪声多、还浪费上下文 token。
- **块太小**：语义被切碎、丢失上下文、一个完整答案被拆到多个块导致召回不全。
- 所以要找平衡，常见做法是按语义/结构切分并设**重叠（overlap）**保留上下文连续性。

### Q62：有哪些常见的分块策略？

**参考答案**：
- **固定长度分块**（按字符/token 数切，最简单，但可能切断语义）；
- **带重叠的滑动窗口**（相邻块共享一部分内容，保上下文连续）；
- **按结构分块**（按段落、标题、章节等自然边界切，保语义完整）；
- **语义分块**（用嵌入相似度判断在哪切，尽量让一块是一个完整语义单元）。
- 选择依据文档类型：结构化强的文档按结构切，长散文可语义切；没有万能策略，要按数据实测调。

> **追问/提示**：会追问"怎么定块大小"——没有魔法数字，要用你的真实问答集评测不同大小的召回和答案质量。

### Q63：什么是重排（Rerank）？为什么向量检索后还要 rerank？

**参考答案**：
- 向量检索（bi-encoder）为了快，把 query 和文档**分别**编码后算相似度，精度有限、可能召回"看似相关实则不准"的块。
- Rerank 用更精细的模型（如 cross-encoder，把 query 和候选块**一起**输入判相关性）对初步召回的候选**重新精排**，把最相关的排到前面。
- 典型流程是"**先粗召回一批（如 top-50）→ 再 rerank 精选出 top-5**"，兼顾速度和精度。
- 价值：显著提升进入上下文的内容质量，减少噪声，进而提升答案准确率。

### Q64：召回率和精确率在 RAG 里怎么权衡？

**参考答案**：
- 召回多（k 大）：更可能包含正确答案，但也带进更多噪声、更贵、还可能触发"中间迷失"。
- 召回少（k 小）：噪声少、便宜，但可能漏掉关键证据导致答不全。
- 常见解法：**先高召回粗筛，再用 rerank 提精确率**，最后只把少量高质量块放进上下文。
- 关键是**用真实评测集去调 k 和 rerank 阈值**，而不是拍脑袋，因为最优点随数据和场景变化。

### Q65：什么是"上下文工程（Context Engineering）"？它和提示工程有什么区别？

**参考答案**：
- 上下文工程指**系统性地设计"在每一步该把哪些信息、以什么结构、放进模型有限上下文窗口"**，是提示工程的延伸和放大。
- 区别：提示工程偏"怎么写好一句指令"；上下文工程偏"**怎么管理整个上下文的构成**"——包括系统提示、工具定义、历史、检索内容、记忆、格式，以及它们的取舍和压缩。
- 对 Agent 尤其重要：多步循环里上下文会不断累积，不管理就会膨胀、变贵、被噪声淹没。
- 一句话：**上下文是模型唯一能"看到"的东西，工程的核心就是精心决定让它看到什么**。

> **追问/提示**：会追问"具体怎么做"——按需检索、摘要压缩历史、裁剪无关工具、结构化组织、把可外置的外置。

### Q66：Agent 运行久了上下文会膨胀，有哪些压缩/管理手段？

**参考答案**：
- **摘要（Summarization）**：把旧的对话/执行历史压缩成摘要，保留结论丢弃过程细节。
- **滑动窗口**：只保留最近 N 轮，更早的外置或丢弃。
- **外置 + 按需检索**：把历史存到外部记忆，用时再检索相关片段回来。
- **结构化状态**：用一个精简的状态对象记录关键信息（当前目标、已完成、待办），而非堆原始对话。
- 通常几种组合使用，目标是"让上下文里始终是**当前这步最需要**的信息"。

### Q67：什么是"中间迷失（Lost in the Middle）"现象？

**参考答案**：
- 指模型在处理长上下文时，**对开头和结尾的信息利用得好，对放在中间的信息容易忽略/利用不足**，即使那里就是答案。
- 后果：把关键内容埋在长上下文中段，可能被"看不见"，导致回答遗漏或出错。
- 应对：**减少无关内容、把最关键的信息放在开头或结尾、用 rerank 让最相关块靠前、控制上下文长度**。
- 它是"塞得越多越好"这一误区的直接反例——**上下文不是越长越好，相关性和位置很关键**。

> **追问/提示**：这题常和"为什么不能无脑扩大上下文/无脑加大 k"连起来问。

### Q68：上下文窗口越来越大，是不是就不需要 RAG 了？

**参考答案**：
- 不是。即使窗口很大，**全塞进去仍有代价**：更贵、更慢、注意力被稀释、容易"中间迷失"。
- RAG/检索的价值在于**只挑相关的进上下文**，提升信噪比和成本效率，且知识库可实时更新、无限扩展。
- 长上下文和 RAG 是互补的：长上下文缓解了"块太碎"的问题，但"从海量知识里挑相关"仍需检索。
- 一句话：**能装下 ≠ 应该装下**；相关性管理永远有价值。

### Q69：RAG 检索不到相关内容时，Agent 应该怎么办？

**参考答案**：
- 首选是**如实承认"没有找到足够证据"**，而不是硬编答案——这是防幻觉的关键纪律。
- Agentic 做法：模型可以**改写 query 再检索、换检索源、分解问题多跳检索**，尝试补齐证据。
- 若仍无果，应明确告知用户"知识库里没有相关信息"，并可给出下一步建议或转人工。
- 工程上要在提示里显式约束"无证据不作答"，并通过评估监控"无依据回答"的比例。

### Q70：怎么评估一个 RAG 系统好不好？

**参考答案**：
- 分两段评：**检索质量**（召回率、精确率、命中率、rerank 后 top-k 是否含正确证据）和**生成质量**（答案是否忠实于检索内容 faithfulness、是否切题、是否完整）。
- 特别关注**忠实度/可归因性**：答案里的说法能不能在检索到的证据里找到出处，防止"检索对了但生成又瞎编"。
- 方法上常用带标注的问答评测集，结合人工评估和"LLM 当裁判"的自动评估。
- 还要监控端到端指标：正确率、无依据回答率、延迟、成本。

> **追问/提示**：会衔接工程化类的评估（Q74）——RAG 评估是 Agent 评估的一个子集。

### Q71：混合检索（Hybrid Search）是什么？为什么有用？

**参考答案**：
- 混合检索是**把关键词检索（如 BM25，擅长精确词匹配）和向量检索（擅长语义匹配）结合**，取长补短。
- 向量检索会漏掉"专有名词、编号、代码符号"这类需要精确匹配的场景，关键词检索正好补上；反过来关键词检索抓不住语义相似，向量补上。
- 结合方式常见是各自召回后融合排序（如 RRF 之类的融合），再交给 rerank。
- 价值：在真实混杂查询上，混合检索通常比单一方式更稳。

### Q72：元数据过滤在 RAG 里起什么作用？

**参考答案**：
- 元数据（如时间、来源、部门、文档类型、权限标签）可以在检索时**先做结构化过滤，再在过滤后的子集里做语义检索**。
- 好处：**缩小检索范围提升精度**（如只查"2024 年之后的政策文档"）、**实现权限隔离**（只检索当前用户有权看的内容）、**支持时效性**（优先近期文档）。
- 它把"纯语义相似"约束到"语义相似 + 满足业务条件"，更贴近真实需求。
- 这也是为什么记忆/知识库不能只靠向量库（呼应 Q21），常要配结构化字段。

### Q73：把整段对话历史都当作 RAG 检索源，有什么问题？

**参考答案**：
- 直接把海量历史全存全检索，会带来**噪声多、相关性差、隐私/权限风险、以及检索出无关旧内容干扰当前判断**的问题。
- 更好的做法是**分层管理记忆**：区分"当前工作上下文""结构化的关键事实""可检索的历史片段"，并对历史做摘要和筛选后再入库。
- 检索时要结合元数据（时间、会话、主题）过滤，避免召回不相关的陈年对话。
- 核心还是那句话：**检索的质量取决于"入库的是什么、怎么筛"，不是无脑全塞**。

> **追问/提示**：可衔接记忆类（Q19-Q21）和上下文工程（Q65），这几块本质是一回事的不同侧面。

#### 本类速记卡

RAG 与上下文类反复强调一个反直觉的道理：**不是喂给模型的越多越好，而是"喂对"最重要**。分块、rerank、混合检索、元数据过滤，全都是在提高"进入上下文的信噪比"；而"中间迷失""平方级成本"则从反面告诉你，塞太多不仅浪费，还会主动伤害效果。记住这条从"入库"到"进上下文"的检索质量链。
```
文档 → 分块(粒度合适) → 向量化入库(带元数据)
                                   │
用户提问 → [元数据过滤] → 混合检索(粗召回一批) → rerank(精排 top-k)
                                                        │
                                   → 拼进上下文(关键内容放首尾) → 基于证据生成(要求引用/无据不答)
```
**高频陷阱与红旗（本类）**：

1. 认为"上下文窗口够大就不需要 RAG"——忽视成本、延迟、中间迷失（Q67、Q68）。
2. 只知道向量检索，不知道要 rerank，也不知道混合检索能补精确匹配（Q63、Q71）。
3. 谈分块只会说"切成小块"，讲不出块太大太小各自的问题和 overlap 的作用（Q61）。
4. RAG 检索不到时"硬编答案"，而不是"无证据不作答"（Q69，防幻觉纪律）。
5. 把"上下文工程"和"提示工程"划等号，答不出前者管的是"整个上下文的构成与取舍"。

**串题演练**："什么是 RAG？"→"传统 RAG 和 Agentic RAG 差在哪？"→"检索质量不好怎么办（分块/rerank/混合）？"→"上下文越塞越多有什么问题（中间迷失/平方级成本）？"→"那到底怎么管理上下文？"。这条线把检索质量和上下文工程连成一体，是当下最热的一类题。

## 31.6 六、工程化类（Q74-Q87）

这一类考"怎么让 Agent 从 demo 变成生产可用"：评估、可观测、护栏、终止条件、幂等。这些是让面试官相信"你能真的把 Agent 上线并维护"的关键信号，也是很多人最薄弱的一块。

### Q74：为什么 Agent 的评估比传统软件难？

**参考答案**：
- 传统软件是确定性的，同输入同输出，可写断言；Agent 是**非确定性**的，同一输入可能走不同路径、给不同措辞，难以用精确匹配判对错。
- 任务往往是**开放式**的（"写个报告""帮我调研"），没有唯一正确答案，好坏是程度问题。
- 而且要评的不只是最终答案，还有**过程**：路径是否合理、工具用得对不对、有没有多绕路。
- 所以 Agent 评估需要新方法：轨迹评估、LLM 当裁判、基于规则的检查、以及大量真实用例。

### Q75：评估 Agent 应该评哪些维度？

**参考答案**：
- 至少四类：**最终结果质量**（对不对、完不完整）、**过程/轨迹质量**（步骤是否合理、工具调用是否正确）、**效率**（步数、token、延迟、成本）、**安全合规**（有没有越界、泄露、危险动作）。
- 对特定场景还要加**任务成功率**（端到端是否达成目标）和**鲁棒性**（异常输入、工具失败时的表现）。
- 关键是别只盯着"答案对不对"，Agent 的价值和风险很多藏在过程里。
- 好的评估体系是"结果 + 过程 + 成本 + 安全"的多维仪表盘。

### Q76："LLM 当裁判（LLM-as-a-Judge）"是什么？有什么坑？

**参考答案**：
- 就是**用一个（通常更强的）模型按给定标准去评判另一个模型/Agent 的输出**，输出打分或判定，解决开放任务没有标准答案、人工评估太贵的问题。
- 优点：可规模化、成本远低于人工、能评相对主观的质量维度。
- 坑：裁判模型自身有偏见（偏爱长答案、偏爱某种风格、位置偏见）、可能不稳定、和人类判断未必一致。
- 缓解：精心设计评分标准（rubric）、给参考答案、做人机一致性校准、关键场景仍需人工抽检。

> **追问/提示**：会追问"怎么保证裁判可靠"——用明确 rubric、小样本人工对齐、必要时多裁判投票。

### Q77：什么是可观测性（Observability）？Agent 为什么特别需要它？

**参考答案**：
- 可观测性指能**看清系统内部到底发生了什么**：每一步的输入输出、模型的推理、调了哪些工具、传了什么参数、返回什么、花了多少 token 和时间。
- Agent 特别需要，是因为它是**多步、非确定、黑盒**的——出了问题（答错、绕路、死循环、超支），没有轨迹根本无从定位。
- 核心手段是**Tracing（追踪）**：把一次运行的完整调用链记录成一棵可回放的 trace，逐步查看。
- 一句话：**没有可观测性的 Agent，等于蒙着眼开车**。

### Q78：Trace、Span 这些概念在 Agent 追踪里指什么？

**参考答案**：
- **Trace**：一次完整运行（如一次用户请求）的全过程记录，是最外层的容器。
- **Span**：Trace 里的一个子步骤/子操作（如一次模型调用、一次工具执行），带开始/结束时间、输入输出、元数据，可嵌套形成树状结构。
- 通过 Trace + Span，你能看到"这次任务一共几步、每步花了多久、在哪一步出的错、token 都花在哪"。
- 这套模型借鉴了分布式系统的链路追踪，是 Agent 调试和成本归因的基础设施。

### Q79：Agent 上线后你会监控哪些指标？

**参考答案**：
- **质量类**：任务成功率、答案正确率、无依据回答率、用户反馈/满意度。
- **效率类**：每次任务的步数、token 消耗、延迟（P50/P95）、单次成本。
- **可靠性类**：工具调用失败率、超时率、循环/超步触发率、异常率。
- **安全类**：护栏拦截次数、危险动作触发、异常访问。
- 有了这些指标做基线，才能发现回归、定位瓶颈、控制成本，把 Agent 当成一个需要持续运维的生产系统。

### Q80：什么是护栏（Guardrails）？分哪几类？

**参考答案**：
- 护栏是**在 Agent 输入、输出、动作各环节施加的安全与合规约束**，防止有害、越权、错误的行为。
- 常见分类：**输入护栏**（过滤恶意/越权请求、注入攻击）、**输出护栏**（拦截有害/敏感/不合规内容）、**行为/工具护栏**（限制能调哪些工具、危险动作需确认、权限最小化）。
- 实现方式包括规则校验、分类器、schema 约束、人在回路确认、以及模型自检。
- 关键认识：Agent 会"做事"，所以护栏不只是过滤文字，更要管住"动作"（如转账、删除、外发）。

> **追问/提示**：会追问"提示注入（prompt injection）怎么防"——输入过滤 + 最小权限 + 关键动作确认 + 不盲信外部内容里的指令。

### Q81：什么是提示注入（Prompt Injection）？为什么对 Agent 危害大？

**参考答案**：
- 提示注入是**攻击者把恶意指令藏在数据里**（如网页、文档、工具返回），诱导模型把"数据"当成"指令"执行。
- 对 Agent 危害尤其大：因为 Agent 能调用工具、执行动作，被注入后可能**外泄数据、执行危险操作、越权访问**，从"说错话"升级成"做坏事"。
- 缓解：**最小权限**（限制工具能力）、**关键动作人确认**、**区分可信指令与不可信数据**、**输出/动作护栏**、不盲目信任外部内容里的"指令"。
- 这是 Agent 安全里最现实的威胁之一，能讲清楚会显得你有安全意识。

### Q82：怎么设计 Agent 的终止条件，防止死循环和失控？

**参考答案**：
- 至少设几道"闸"：**最大步数/迭代次数、最大耗时、最大 token/成本预算**，任一触发就强制停止。
- 加**进展检测**：如果连续几步没有实质进展（重复同样的动作、观察不变），判定卡死并中止或换策略。
- 结合**明确的完成判据**（可验证的成功标准，见 Q27），有正常出口才不至于只能靠兜底强停。
- 触发兜底终止时要**优雅降级**：返回已有的部分结果、报告未完成原因、或转人工，而不是直接崩。

> **追问/提示**：这是工程化必考题，能答出"多层闸 + 进展检测 + 优雅降级"就很完整。

### Q83：什么是幂等性（Idempotency）？为什么 Agent 里很重要？

**参考答案**：
- 幂等指**同一操作执行一次和执行多次，效果相同**（如"把状态设为已支付"幂等，"余额减 100"不幂等）。
- Agent 里重要，是因为它会**重试**（工具失败重试、循环里重复调用），非幂等操作重复执行会造成重复下单、重复扣款、重复发消息等严重后果。
- 做法：给写操作加**幂等键/请求 ID**、用"设置为某值"而非"增量修改"、执行前检查是否已执行过、区分"读操作"（天然安全）和"写操作"（需保护）。
- 一句话：**只要 Agent 会重试，就必须假设动作可能被执行多次，并设计得能安全重复**。

> **追问/提示**：会举例——"如果重试机制遇到发邮件工具会怎样"，答"没有幂等保护会重复发，需要幂等键去重"。

### Q84：Agent 执行了不可逆的危险操作怎么防？

**参考答案**：
- 首选**人在回路（Human-in-the-Loop）**：对不可逆/高风险动作（转账、删除、对外发布）强制人工确认后才执行。
- 其次**权限最小化**：Agent 默认只有只读或低风险权限，高危能力单独授权、单独审计。
- 再加**预演/dry-run**：先让 Agent 输出"打算做什么"，校验通过再真正执行；以及**可回滚设计**、操作审计日志。
- 原则：**越不可逆、影响越大，越要把控制权收回给人**，自主性要为风险让步。

### Q85：怎么测试一个 Agent？有哪些层次？

**参考答案**：
- **单元层**：单独测工具函数（确定性，正常单测）、测提示模板、测 schema 校验。
- **组件层**：测单步决策（给定上下文，模型是否选对工具）、测检索质量。
- **端到端层**：用真实/构造的任务集跑完整流程，评成功率、轨迹、成本，常配 LLM 裁判。
- **回归层**：把线上出过问题的 case 沉淀成测试集，每次改动都回归，防止改好一个坏两个。
- 关键是把"非确定的整体"尽量拆出"确定可测的部分"，其余用统计化的评估兜住。

### Q86：Agent 的输出不稳定（同问不同答），工程上怎么缓解？

**参考答案**：
- 从几方面下手：**降低温度/采样随机性**（需要确定性时）、**用结构化输出 + schema 校验**约束格式、**明确而具体的提示**减少发挥空间。
- 关键决策处加**校验和重试**：输出不合规就重试或纠错，而不是直接放行。
- 对必须稳定的环节，考虑**用代码/规则替代模型**（能确定性解决的就别交给模型）。
- 接受"完全消除不确定性不现实"，工程目标是**把不确定性约束在可接受范围并可监控**。

### Q87：怎么把一个 Agent 从 Demo 推进到生产级？关键差距在哪？

**参考答案**：
- Demo 只要"跑通一次好看的路径"；生产要处理**长尾、异常、失败、并发、安全、成本、可维护**。
- 关键补齐项：**评估体系**（知道好不好、有没有回归）、**可观测**（出问题查得到）、**护栏与权限**（不出乱子）、**终止与幂等**（不失控、不重复搞破坏）、**成本/延迟控制**（用得起、够快）。
- 还要有**运维闭环**：监控指标、收集 badcase、回归测试、持续迭代。
- 一句话：**从 Demo 到生产，比拼的不是模型多聪明，而是工程有多可靠**。

> **追问/提示**：这题是工程化类的"总纲"，能系统地列出这几块，说明你有生产落地的完整认知。

#### 本类速记卡

工程化类是"从 Demo 到生产"的分水岭，也是最能区分"玩过 Agent"和"上过线"的一类题。它的关键词只有一个：**可靠**。评估让你"知道好不好"，可观测让你"出问题查得到"，护栏让你"不出大乱子"，终止与幂等让你"不失控、不重复搞破坏"。把这五块串成一张"生产就绪清单"记在心里。

| 支柱 | 解决什么 | 关键手段 |
|---|---|---|
| 评估 | 知道好不好、有没有回归 | 结果+轨迹+成本多维、LLM 裁判、回归集 |
| 可观测 | 出问题能定位 | Trace/Span、逐步回放、成本归因 |
| 护栏 | 不出有害/越权行为 | 输入/输出/动作护栏、最小权限、防注入 |
| 终止条件 | 不死循环、不失控 | 步数/时间/预算闸 + 进展检测 + 优雅降级 |
| 幂等 | 重试不重复搞破坏 | 幂等键、设值代替增量、执行前查重 |

**高频陷阱与红旗（本类）**：

1. 评估只看"最终答案对不对"，忽视过程/轨迹、成本、安全（Q75）。
2. 没有可观测就想调试非确定系统——等于蒙眼开车（Q77）。
3. 护栏只想着"过滤脏话"，忘了 Agent 会"做事"，必须管住动作（Q80、Q81）。
4. 没设终止条件，被问"死循环怎么办"答不上来（Q82）。
5. 忽视幂等，重试机制一遇到"发邮件/下单"就重复执行（Q83）。

**串题演练**："Agent 怎么评估，为什么难？"→"上线后你监控什么？"→"出了偶发错误怎么排查？"→"怎么防止它做危险/越权的事？"→"重试会不会导致重复下单？"。这一串几乎就是一次"生产 Agent 的 code review"，答得全，面试官会认定你"能对线上负责"。

## 31.7 七、成本与性能类（Q88-Q99）

这一类考"用得起、跑得快"：Agent 的成本结构、分层路由、缓存、延迟优化、"平方级成本"。很多候选人只关心"能不能做出来"，能主动谈成本和性能的人，会显得更像"要为线上负责的人"。

### Q88：Agent 的成本主要花在哪？为什么它比普通 LLM 应用贵？

**参考答案**：
- 主要成本是**模型调用的 token 费用**（输入 + 输出），而 Agent 是**多步循环**，一个任务往往要调模型很多次，每次还带着越来越长的上下文。
- 所以成本 ≈ 步数 × 每步上下文长度 × 单价，三个因子相乘，很容易远超单次问答。
- 加上工具调用、检索、可能的反思/多 Agent，成本进一步叠加。
- 一句话：**Agent 贵不是因为单次调用贵，而是因为"多步 × 长上下文"的乘法效应**。

### Q89：什么是 Agent 的"平方级/二次成本"问题？

**参考答案**：
- 在一个不断累积上下文的循环里，**每多一步，上下文就更长，而下一步又要把整段上下文再发一遍**。
- 于是随着步数增加，累计处理的 token 大致按**步数的平方级**增长（第 N 步要处理约 N 倍的历史），而不是线性。
- 后果：长任务的成本和延迟会失控性地上升，这也是"控制上下文长度"如此重要的经济原因。
- 缓解：摘要压缩、外置记忆按需检索、缩短链路、必要时清理无关历史（呼应 Q66）。

> **追问/提示**：能把"为什么是平方而不是线性"讲清楚（每步重发累积上下文），是这题的加分点。

### Q90：什么是分层路由（Model Routing / Tiered Routing）？

**参考答案**：
- 分层路由指**根据任务难度把请求分派给不同档位的模型**：简单任务用小/快/便宜的模型，复杂任务才用大/强/贵的模型。
- 好处：在保证质量的前提下大幅降本提速，因为现实中大量子任务其实很简单，用大模型是浪费。
- 实现：用一个轻量分类器/规则/小模型先判断难度或类型，再路由；也可"先小模型试，不行再升级到大模型"。
- 关键权衡：路由判断本身也有成本和出错风险，要保证"路由错了"的代价可控。

### Q91："先便宜模型试，不行再升级"这种级联（Cascade）策略怎么设计？

**参考答案**：
- 思路：**先用便宜模型处理，用一个置信度/校验判断结果是否可接受，不行再升级到更强的模型**重做。
- 关键是**判定"够不够好"的信号**：可用置信度、校验规则、或让模型自评是否有把握。
- 好处：大部分简单请求被便宜模型消化，只有少数难的才付高价，整体成本大降。
- 风险：级联多了会增加延迟（失败后要重来），判定不准会漏放低质量结果，需要监控级联命中率。

### Q92：缓存在 Agent 里怎么用？能缓存什么？

**参考答案**：
- 可缓存的层次：**结果缓存**（相同/相似请求直接返回历史答案）、**检索缓存**（相同 query 的检索结果）、**工具调用缓存**（相同参数的确定性工具结果）、以及**提示前缀缓存**（复用不变的系统提示/上下文前缀，很多平台原生支持）。
- 好处：省 token、降延迟、减少重复计算。
- 注意：**只缓存确定性、可安全复用的部分**；带时效性或副作用的调用不能乱缓存，要设失效策略。
- 语义缓存（用相似度命中近似请求）能提高命中率，但要防"看似相同实则不同"的误命中。

> **追问/提示**：会问"提示缓存和普通缓存区别"——提示缓存复用的是模型对固定前缀的计算，命中省的是首 token 计算成本。

### Q93：Agent 延迟高，从哪些角度优化？

**参考答案**：
- **减少步数**：能一步做完别拆多步，缩短循环链路。
- **并行化**：无依赖的工具调用/子任务并发执行，而不是串行等待。
- **换更快的模型/分层**：延迟敏感环节用小快模型。
- **流式输出**：先把已生成内容流给用户，降低"感知延迟"。
- **缓存 + 提示前缀复用**：减少重复计算。此外还有减小上下文长度、预取、就近部署等手段。核心是"该并行的并行、该省的步省掉、能提前给反馈就提前给"。

### Q94：延迟优化里，"实际延迟"和"感知延迟"有什么区别？

**参考答案**：
- **实际延迟**是任务真正跑完的耗时；**感知延迟**是用户"感觉等了多久"。
- 二者可以解耦：即使实际耗时不变，**流式输出、显示进度/中间步骤、先给一部分结果**都能显著降低感知延迟，改善体验。
- 例如让用户看到"正在检索…正在整理…"，比对着空白等同样时间体验好得多。
- 工程上两手抓：既压实际延迟（并行、缓存、少步），也管感知延迟（流式、进度反馈）。

### Q95：多 Agent / 反思 / ToT 这些"更强"的方法，成本上要注意什么？

**参考答案**：
- 它们本质都是**用更多模型调用换质量**：多 Agent 是多份上下文并行、反思是多轮迭代、ToT 是多分支探索，成本可能翻数倍甚至数量级。
- 所以要**先算账**：多花的成本换来的质量提升，值不值？很多场景简单方法就够了。
- 工程上给这些方法设**预算上限和迭代上限**，防止成本失控。
- 原则呼应全书主线：**先追求简单，只有当复杂方法带来的价值确实超过其成本时才用**。

### Q96：怎么在"质量、成本、延迟"这个三角里做取舍？

**参考答案**：
- 这三者通常互相牵制：想要更高质量往往更贵更慢（更大模型、更多步、反思）；想要更便宜更快往往牺牲质量。
- 做法：**先明确业务对三者的优先级**（如客服重延迟、金融报告重质量），再针对性优化，不追求"全都要"。
- 用**分层/级联 + 缓存 + 控制上下文**这些手段，在满足质量底线的前提下压成本和延迟。
- 关键是**有数据支撑的取舍**：靠评估和监控找到"质量够用、成本延迟最优"的工作点，而不是拍脑袋。

> **追问/提示**：这是很好的开放题切入口，能结合一个具体业务讲优先级取舍会很出彩。

### Q97：单步失败率对长任务成本/成功率影响有多大？

**参考答案**：
- 影响是**指数放大**的：如果每步成功率是 p，走 N 步全对的概率约是 p 的 N 次方。哪怕单步 95% 正确，20 步下来整体成功率也可能掉到很低。
- 失败还会触发重试、重规划，进一步推高成本和延迟。
- 所以长任务对单步可靠性极其敏感，**提升单步质量（好工具、清晰提示、结构化校验）和缩短链路，比事后补救更划算**。
- 这也是"能少步就少步""能确定性就别交给模型"这些工程直觉的数学依据。

### Q98：怎么给 Agent 做成本归因（知道钱花在哪）？

**参考答案**：
- 靠**可观测/Tracing**：把每次运行拆成 span，记录每一步的 token 数、模型档位、工具调用，就能算出"哪一步、哪个工具、哪个用户"最烧钱。
- 有了归因数据，才能定点优化：是某步上下文太长？某工具被反复调用？某类请求走了太多步？
- 还能按用户/功能/模型维度聚合，做成本看板和预算告警。
- 一句话：**先能测量，才能优化**；没有成本归因的降本都是盲猜。

### Q99：如果老板说"这个 Agent 太贵了，砍一半成本"，你会怎么系统地做？

**参考答案**：
- 先**测量归因**：用 trace 找出成本大头（哪些步/工具/请求类型最烧钱）。
- 再**对症下药**：能分层的分层（简单请求下沉小模型）、能缓存的缓存、压缩上下文、缩短链路、砍掉低价值的反思/多 Agent。
- 然后**验证质量不塌**：每项优化都跑评估集，确认降本没把成功率打下去，找到"质量够用、成本最低"的点。
- 最后**建立监控**：上成本看板和预算告警，防止未来悄悄反弹。这套"测量→优化→验质量→监控"的闭环，比单点省钱更能打动面试官。

> **追问/提示**：这题是成本类的综合题，展现的是"系统化解决问题"的方法论，比记住某个技巧更重要。

#### 本类速记卡

成本与性能类的底层公式只有一个：**成本 ≈ 步数 × 每步上下文长度 × 单价**。所有优化手段，本质都是在压这三个因子里的某一个——分层/级联压"单价"，缓存和减少步数压"步数"，上下文压缩压"每步长度"。而"平方级成本"提醒你：步数和上下文长度会互相放大，长任务尤其危险。

| 优化手段 | 压的是哪个因子 | 代价/风险 |
|---|---|---|
| 分层路由 | 单价（简单任务用小模型） | 路由判断本身有成本和误判 |
| 级联 Cascade | 单价（先便宜后升级） | 失败重来增加延迟 |
| 缓存/提示前缀复用 | 步数/重复计算 | 只能缓存确定性、可复用部分 |
| 上下文压缩/摘要 | 每步长度 | 摘要可能丢关键信息 |
| 并行化 | 实际延迟 | 汇总复杂、并发成本 |
| 流式输出 | 感知延迟 | 不降实际耗时 |

**高频陷阱与红旗（本类）**：

1. 说不清 Agent 为什么比普通 LLM 应用贵——答不出"多步 × 长上下文"的乘法效应（Q88）。
2. 把成本增长当成线性，讲不出"平方级"的由来（每步重发累积上下文，Q89）。
3. 只会说"换个小模型"，不知道分层/级联、缓存、上下文压缩这套组合拳。
4. 混淆"实际延迟"和"感知延迟"，不知道流式输出改善的是后者（Q94）。
5. 降本不先做成本归因就乱砍，也不验证质量是否塌方（Q98、Q99）。

**串题演练**："Agent 为什么贵？"→"成本随步数怎么增长？"→"怎么降本（分层/缓存/压上下文）？"→"降本会不会伤质量，你怎么验证？"→"延迟高怎么优化？"。把这条线走通，你就能应对"老板要砍一半成本"这类最实战的压轴题。

## 31.8 八、系统设计与开放类（Q100-Q113）

这一类是面试的"压轴区"：给你一个真实场景让你从零设计一个 Agent 系统，或问你踩坑经验、趋势判断。没有标准答案，考的是**结构化思维、工程品味、和真实经验**。答这类题的通用套路是：**先澄清需求和约束 → 给整体架构 → 逐个模块展开 → 主动谈边界/风险/取舍**。

### Q100：系统设计题的通用答题框架是什么？

**参考答案**：
- 一套稳妥的顺序：**① 澄清需求与约束**（用户是谁、要解决什么、质量/延迟/成本/安全的优先级）；**② 给高层架构**（有哪些组件、数据怎么流）；**③ 展开关键模块**（模型选型、工具、记忆/RAG、编排方式）；**④ 谈非功能项**（评估、可观测、护栏、成本、终止）；**⑤ 主动点出取舍与风险**。
- 最忌一上来就堆技术名词，要先问清楚需求再设计。
- 全程体现"能简单就简单"：先给最小可行方案，再按需加复杂度。
- 结尾主动说"如果时间/预算不同，我会怎么调整"，显示你有权衡意识。

> **追问/提示**：这是所有系统设计题的元框架，先把它刻进肌肉记忆。

### Q101：设计一个"企业内部知识库问答 Agent"，你的方案是什么？

**参考答案**：
- **核心是 RAG**：文档接入 → 清洗分块 → 向量化入库（配元数据用于权限/时效过滤）→ 检索（混合检索 + rerank）→ 基于证据生成，并**要求引用出处、无证据不作答**。
- **权限**是企业场景的硬约束：按用户身份做元数据过滤，只检索有权访问的文档。
- **是否 Agentic**：简单事实问答用传统 RAG 即可；复杂多跳问题再让模型自主多轮检索。
- **配套**：评估（检索命中率 + 答案忠实度）、可观测、缓存高频问答、监控无依据回答率。先上传统 RAG，验证效果后再考虑 Agentic 升级。

### Q102：设计一个"能查数据库并回答业务问题"的 Agent（Text-to-SQL 类），要注意什么？

**参考答案**：
- 核心链路：**理解问题 → 生成 SQL → 执行 → 把结果解释成自然语言**，可加"执行前校验 SQL"和"错误则据报错重试"。
- 安全是重中之重：**只读权限、SQL 白名单/语法校验、禁危险语句、限制返回行数、超时保护**，绝不能让模型的 SQL 直接裸跑在生产库上。
- 准确性：给模型**表结构/字段说明/示例查询**（schema 即上下文），并对生成的 SQL 做校验，必要时人确认。
- 配套评估：用带标注的"问题→正确结果"集测端到端准确率，监控错误 SQL 率。

> **追问/提示**：必问安全——"模型生成了 DELETE 怎么办"，答只读账号 + 语句白名单 + 校验拦截。

### Q103：设计一个"多智能体的软件开发/写代码 Agent 团队"，你会怎么分工？

**参考答案**：
- 一种常见分工：**规划者**（拆解需求、定方案）、**编码者**（写代码）、**测试者/评审者**（跑测试、挑问题）、**协调者/主管**（编排、汇总、决定是否返工），形成"写—测—改"的评估-优化循环。
- 关键机制：**用可执行的测试作为客观反馈**（代码能不能跑、测试过不过），比让模型互相"觉得对不对"可靠得多。
- 要设**迭代上限和预算**，防止改来改去停不下来；沙箱执行保证安全。
- 先问：这个任务真的需要多 Agent 吗？很多编码任务单 Agent + 好工具 + 测试反馈就够了，别为多 Agent 而多 Agent。

### Q104：设计一个"网页浏览/操作类 Agent"（能上网查、能点击操作），难点在哪？

**参考答案**：
- 难点一：**环境复杂多变**——网页结构千差万别、会变、有反爬和验证码，感知（解析页面）和动作（点击/填写）都不稳定。
- 难点二：**安全与不可逆**——可能触发下单、提交表单等真实操作，需要严格护栏和关键动作确认。
- 难点三：**长链路 + 高延迟 + 高成本**——多步浏览操作放大了错误累积和费用。
- 设计要点：把动作限制在安全白名单、关键操作人确认、每步校验页面状态、设终止条件、完善的追踪用于复盘失败。

### Q105：设计一个"客服 Agent"，怎么平衡自动化和人工兜底？

**参考答案**：
- 分层处理：**先路由**（判断问题类型/紧急度），常见问题用 RAG/流程自动答，复杂或高风险的**转人工或人在回路**。
- 设**升级（escalation）条件**：模型没把握、用户不满、涉及退款/投诉等敏感操作、连续答不好，就转人工。
- 护栏：敏感动作（改订单、退款）需确认或走人工，避免 Agent 擅自操作。
- 体验与信任：能引用依据、能说"这个我帮你转人工"，比硬答强；持续用真实对话评估和迭代。这也呼应本书第 20 章的综合实战。

### Q106：给你一个新需求，你怎么判断"到底该不该用 Agent"？

**参考答案**：
- 先问：**任务的流程是不是固定、可穷举分支**？如果是，用 Workflow 甚至普通代码更好，别上 Agent。
- 再问：**是否需要模型运行时动态决策、面对开放不可预测的情况、需要多步自主推理和工具组合**？是，才考虑 Agent。
- 还要看**代价能否承受**：Agent 更贵、更慢、更难控，业务能不能接受。
- 结论遵循"能简单就简单"：**Agent 是为"确实需要自主性"的场景准备的，不是默认选项**。这正是 Anthropic 反复强调的取舍[来源](https://www.anthropic.com/engineering/building-effective-agents)。

### Q107：讲一个你在 Agent 项目里踩过的坑，以及怎么解决的。

**参考答案**：
- 结构：**背景 → 现象 → 定位过程 → 解决方案 → 沉淀的经验**。要具体、要有你个人的思考。
- 示例方向（选你真做过的）：上下文膨胀导致成本飙升 → 加摘要和按需检索；工具描述含糊导致乱调 → 重写 schema；没设终止条件导致死循环烧钱 → 加多层闸和进展检测；重试无幂等导致重复下单 → 加幂等键。
- 重点不是坑本身，而是**你如何用可观测数据定位、如何权衡解决方案、以及下次怎么预防**。
- 千万别硬编——面试官一追细节就露馅，用自己真实的经历最稳。

> **追问/提示**：这是高频开放题，提前准备 2-3 个自己真实的坑，能讲出定位过程和反思。

### Q108：你怎么看"Agent 会不会取代大部分软件工程师"这类趋势问题？

**参考答案**：
- 给出有分寸的判断：Agent 正在**改变**开发方式（自动化重复劳动、加速原型、辅助调试），但当前在**可靠性、复杂系统理解、责任归属**上仍有明显局限。
- 更可能的趋势是**人机协作**——工程师从"写每一行"转向"定义目标、审查、把关、设计系统"，而不是被简单替代。
- 表达时兼顾乐观与冷静：**承认能力进步，也点明边界和不确定性**，避免极端断言。
- 面试官考的不是你预言得准不准，而是你**有没有独立、平衡、有依据的判断力**。

### Q109：面对"Agent 领域变化太快，怎么持续学习"这个问题，你怎么答？

**参考答案**：
- 方法论：**抓不变的原理**（循环、工具、记忆、编排、评估这些底层不怎么变），把新框架/新论文挂到这个知识骨架上，就不会被表面变化淹没。
- 渠道：读权威一手材料（如 Anthropic、OpenAI 的工程指南、经典博客和课程），动手复现，而不是只刷碎片资讯。
- 实践驱动：**做项目 → 遇到问题 → 针对性补知识**，比漫无目的地追新更有效。
- 展现你有**可持续的学习系统**，而不是靠一时热情，这比你现在懂多少更打动人。

### Q110：如果让你从零搭一个 Agent 团队的技术栈，你会怎么分层规划？

**参考答案**：
- 分层思路：**模型层**（选型 + 分层路由）、**编排层**（框架或自研的循环/图）、**能力层**（工具、MCP 接入、RAG/记忆）、**工程层**（评估、可观测、护栏、缓存、成本控制）、**运维层**（监控、badcase 收集、回归、迭代）。
- 原则：**先搭最小闭环跑通一个真实用例**，再逐层加固，而不是一开始就上全套重型基建。
- 选型上优先成熟、可观测友好、不过度锁定的方案，为演进留余地。
- 强调"工程层和运维层"往往是决定成败的地方，别只堆模型和框架。

### Q111：如果一个 Agent 在生产上"偶尔答错但难以复现"，你会怎么排查？

**参考答案**：
- 第一步靠**可观测**：调出出错那次的完整 trace，逐 span 看输入输出，定位是哪一步出的偏差（检索没召回？工具返回异常？模型决策错了？）。
- 第二步**找模式**：把类似 badcase 聚合，看是否集中在某类输入、某个工具、某种上下文长度，判断是偶发还是系统性。
- 第三步**复现与修复**：把该 case 固化成测试用例，针对根因改（改提示/工具/检索/加校验），再回归验证。
- 关键认知：**非确定系统靠"数据 + 追踪 + 回归测试"而非单步 debug**；没有 trace 几乎无法定位。

### Q112：怎么向非技术的业务方解释"为什么 Agent 有时会出错、不能 100% 保证"？

**参考答案**：
- 用类比：Agent 像一个**很能干但偶尔会判断失误的实习生**，不是传统那种"输入确定就输出确定"的程序，所以不能承诺 100% 正确。
- 说清应对：我们用**护栏防大错、用人工兜底管高风险、用评估和监控持续把错误率压低**，把风险控制在可接受范围。
- 管理预期：把它定位成"**大幅提效但需要监督**"的工具，在合适场景用、给关键动作留人工确认。
- 这题考的是**沟通能力和风险意识**——能把技术局限翻译成业务语言，是资深工程师的重要素质。

### Q113：如果只能给准备 Agent 面试的人一条建议，你会说什么？为什么？

**参考答案**：
- 一条建议：**亲手从零写一个不依赖框架的最小 Agent，并把它推到"能处理失败、有终止、有评估"的半生产状态。**
- 因为这个过程会逼你真正理解循环、工具、上下文、错误处理、成本这些核心，而不是停留在背概念。
- 有了这段经历，无论面试官问概念、原理、还是系统设计，你都能从"我实际做过"的角度回答，自然有细节、有取舍、有踩坑。
- 一句话总结全章：**面试考的从来不是你背了多少，而是你想得多清楚、做得多扎实。**

> **追问/提示**：这题几乎是"送分的态度题"，答出"重实践、重原理、重工程"的价值观即可收尾。

#### 本类速记卡

系统设计与开放类没有速查表能"背下来"，因为它考的是**现场把知识组织成方案的能力**。但答题的"骨架"是可以背的——那就是 Q100 那套五步框架。任何系统设计题，你都可以往这个模子里套，再填上前面七类学到的具体技术点。
```
系统设计答题骨架（万能模子）
① 澄清需求与约束  →  用户是谁？要解决什么？质量/延迟/成本/安全谁优先？
② 高层架构        →  有哪些组件？数据怎么流？（画个框图）
③ 关键模块展开    →  模型选型 / 工具 / 记忆·RAG / 编排方式
④ 非功能项        →  评估 / 可观测 / 护栏 / 成本 / 终止条件
⑤ 取舍与风险      →  主动说边界、说"如果预算不同我会怎么调"
```
**高频陷阱与红旗（本类）**：

1. 不澄清需求就开始堆技术，方案脱离实际场景。
2. 只画"美好路径"，不谈失败、异常、安全、成本、终止（生产思维缺失）。
3. 默认"上多 Agent 才显水平"，忘了"能简单就简单"（Q103、Q106）。
4. 讲踩坑经验时空洞或明显硬编，一追细节就崩（Q107）。
5. 趋势题给极端断言（"很快全被取代"/"完全没用"），显不出独立平衡的判断力（Q108）。

**串题演练**：系统设计题往往是"一道大题打到底"——"设计一个 X Agent"→"数据从哪来、怎么检索？"→"怎么保证安全和不越权？"→"怎么评估好不好、怎么控成本？"→"这个方案的边界和风险是什么？"。你会发现，**前面七类的每一个知识点，最终都要在这里被调用一次**。这也是为什么把系统设计放在压轴——它是全章的"综合考"。

## 31.9 九、进阶追问加练（Q114-Q140）

前八类是按"知识板块"切的，帮你把点铺开。但真实面试的杀伤力从来不在第一问，而在**追问**——面试官顺着你的答案往下钻，一层层逼你暴露"是真懂还是背的"。这一类专门收纳那些"第二层、第三层"的深挖题：它们大多横跨多个板块，答案没有唯一标准，考的是你能不能把散点连成体系、能不能主动谈机制与代价。

建议把这一类当作**压力测试**来刷：每题先自己讲一遍，再对照参考答案看有没有漏掉"为什么"和"边界"。能把这 27 道稳稳接住，你在真实面试里被连问四五层也不会慌。

### Q114：Agent 循环为什么会"停不下来"或"原地绕圈"？底层原因和防护分别是什么？

**参考答案**：
- 底层原因通常有三类：**没有明确的完成信号**（模型判断不了"够了"）、**工具反复失败但模型不断重试同一动作**、以及**上下文里旧的错误观察污染了后续决策**，让模型在错误路径上打转。
- 更隐蔽的一种是"**语义死循环**"：每一步看似不同，实则在两三个状态间来回横跳，因为缺少对"已尝试过什么"的记忆。
- 防护要分层：**硬性上限**（最大步数、最大 token、超时）兜底；**重复检测**（同一工具+同一参数连续调用就熔断）；**显式完成判据**（用结构化的"任务完成"标记而非靠模型自觉）。
- 最好再加一层"**进展度量**"：若连续 N 步都没让任务向前推进，就主动升级人工或换策略。

> **追问/提示**：能把"硬上限"和"进展判断"分开讲，说明你懂"防失控"和"防低效"是两件事。

### Q115：为什么说"管理上下文比调 prompt 更重要"？

**参考答案**：
- 对多轮 Agent 而言，模型每一步看到的**不是你精心写的那句 prompt，而是一路累积下来的上下文**——历史消息、工具返回、中间产物。上下文里塞了什么、按什么顺序排、有没有噪声，直接决定这一步的质量。
- 提示工程是"把一句话说好"，上下文工程是"把整个信息场组织好"，后者的杠杆在长任务里远大于前者。
- 常见翻车不是 prompt 写得不好，而是**上下文膨胀、旧错误没清理、关键信息被挤到中间**（呼应中间迷失）。
- 所以工程重心应从"改措辞"转向"决定每一步该放什么、删什么、压缩什么"[来源](https://huyenchip.com/2025/01/07/agents.html)。

> **追问/提示**：可举例——同样的 prompt，上下文干净和上下文脏，效果天差地别。

### Q116：ReAct 和模型原生的工具调用循环（如 tools/function calling）有什么异同？

**参考答案**：
- 相同点：本质都是"**推理→行动→观察→再推理**"的循环，都让模型在运行时决定调不调工具、调哪个。
- 不同点在"思考"的表达方式：经典 ReAct 用**自然语言显式写出 Thought**，靠 prompt 约定格式；原生工具调用则把"要调哪个工具、传什么参数"变成**结构化字段**，由 API 层保证格式，思考往往被隐藏或压缩。
- 工程上原生方式更稳（不用自己解析文本、schema 由平台校验），但**可解释性变弱**——你看不到那段自然语言的推理链，调试时要额外记录。
- 二者不是对立，很多框架就是"用原生工具调用做行动、再要求模型附带一段简短理由"来兼得两者。

> **追问/提示**：被问"生产里你选哪种"，答"原生为主、显式理由为辅，兼顾稳定与可调试"。

### Q117：CoT 一定要"显式输出思考过程"吗？推理模型改变了什么？

**参考答案**：
- 经典 CoT 靠"让我一步步想"把中间推理**显式写进输出**，从而提升复杂问题的正确率；但显式思考会**增加 token、拖慢延迟、也可能泄露不该给用户看的中间内容**。
- 新一代"推理模型"把这段思考**内化**了：思考在内部完成，对外只给结论（或给一段可折叠的思考摘要），相当于把 CoT 从"提示技巧"变成"模型能力"。
- 这带来的工程变化是：你不必再手写"一步步思考"的咒语，但要为**更长的思考时延和更高的思考 token 成本**做预算。
- 结论：CoT 的"要不要显式"取决于场景——需要可审计/可调试就显式，纯追求答案质量且用推理模型时可交给模型内化。

> **追问/提示**：注意别把"隐藏思考"当"没有思考"——成本和延迟还在。

### Q118：为什么工具的"返回值设计"和工具描述一样重要？

**参考答案**：
- 工具描述决定模型"**要不要调、怎么调**"，而返回值决定模型"**调完之后能不能正确理解结果、继续往下走**"——后者常被忽视，却是错误累积的高发区。
- 返回值太原始（如一大坨 JSON、堆栈报错）会淹没关键信息、撑爆上下文；太模糊（只回"成功/失败"）又让模型无从决策。
- 好的返回值应当是"**为模型阅读而设计的**"：结构清晰、只含决策所需字段、失败时给出可操作的原因而非裸异常。
- 一个经验法则：把返回值想象成"给下一步的模型看的摘要"，而不是"给日志系统看的原始数据"。

> **追问/提示**：能主动区分"给模型看的返回"和"给日志看的返回"，很加分。

### Q119：Agent 的长期记忆"写入策略"怎么设计？怎么防记忆污染？

**参考答案**：
- 关键不是"能不能存"，而是"**该不该存、存什么、什么时候失效**"。无差别把所有对话写进长期记忆，很快会积累矛盾、过时、甚至错误的信息，反过来毒害后续检索。
- 常见做法：只沉淀"**稳定且可复用**"的事实（用户偏好、长期结论），临时性/推测性内容不入库；写入前做**去重与冲突检测**，新信息与旧信息冲突时要有更新或标注机制。
- 还要给记忆加"**时效与来源**"元数据，检索时能按新鲜度、可信度过滤。
- 记忆系统要能被"遗忘/纠正"——支持删除和修订，否则错误会永久累积。

> **追问/提示**：谈到"记忆也需要 GC/失效机制"，说明你把记忆当系统而非仓库。

### Q120：多 Agent 里的"上下文隔离"到底是优点还是缺点？

**参考答案**：
- 两面都有。**优点**：每个子 Agent 只带自己那份干净上下文，避免无关信息互相干扰，也能各自并行、各用不同模型/工具。
- **缺点**：隔离意味着信息传递要靠显式"交接"，一旦交接不完整（漏了关键前提、口径不一致），就会出现"各自都对、拼起来错"的整合难题。
- 所以隔离的价值取决于任务是否**天然可分解**：能干净切分的任务隔离收益大；强耦合、需要共享大量中间状态的任务，隔离反而增加协调成本。
- 工程上要为"交接内容"设计明确契约（谁给谁、传什么字段、怎么校验），这往往比多加一个 Agent 更重要[来源](https://www.anthropic.com/engineering/building-effective-agents)。

> **追问/提示**：能说出"隔离的代价是交接成本"，就超过了只夸多 Agent 的人。

### Q121：Orchestrator 决定任务拆分粒度时，拆太细和太粗各有什么问题？

**参考答案**：
- **太粗**：单个子任务仍然复杂，子 Agent 照样容易出错、绕路，等于没真正分解，还多了一层调度开销。
- **太细**：子任务数量爆炸，每个都要一轮甚至多轮 LLM 调用，**成本和延迟成倍上升**，交接次数增多也放大了整合出错概率。
- 合理粒度的判据是"**一个子任务能被一个子 Agent 在可控步数内稳定完成，且产出能被清晰交接**"。
- 实践中往往先粗切、观察哪些子任务失败率高，再对高失败子任务二次分解，而不是一上来就切得很碎。

> **追问/提示**：能把"粒度"和"成本/失败率"挂钩，体现了工程权衡意识。

### Q122：结构化输出（JSON mode / schema 约束）能不能省掉后续校验？

**参考答案**：
- 不能。schema 约束能保证输出**格式合法**（字段齐、类型对），但保证不了**内容正确**——模型完全可能填进一个格式正确但语义错误、越界或凭空捏造的值。
- 典型如：枚举字段填了合法枚举值但选错了、ID 字段编了个格式对但不存在的 ID、数值字段给了不合业务范围的数。
- 所以正确姿势是"**schema 管格式 + 业务校验管语义**"两道关：格式层交给结构化输出/类型系统（如 PydanticAI 这类强调类型安全的框架），语义层用规则或二次检索核对[来源](https://github.com/pydantic/pydantic-ai)。
- 把"格式合法"误当"内容可信"，是生产里很常见的隐性 bug 源。

> **追问/提示**：能举"格式对但值错"的例子，说明你真踩过而不是背的。

### Q123：流式输出（streaming）给 Agent 工程带来哪些好处和复杂度？

**参考答案**：
- 好处主要在**体验**：边生成边返回能大幅降低"感知延迟"，用户很早就看到进展，即便实际总时长没变。
- 但它引入复杂度：**中途要不要触发工具**（流到一半发现要调工具怎么办）、**错误处理**（已经吐出去的内容如何撤回/纠正）、**结构化解析**（流式的 JSON 需要增量解析）。
- 对多步 Agent，还要决定"流什么"：是流最终答案，还是把中间步骤/工具调用也作为进度事件推给前端。
- 工程上通常"**最终答案流式 + 中间步骤作为状态事件**"，兼顾体验与可控。

> **追问/提示**：能把"感知延迟"和"实际延迟"接上（呼应 Q94），加分。

### Q124：为什么说"评估集比模型更值钱"？怎么构建一个好评估集？

**参考答案**：
- 模型会换、会升级，但"**判断一次改动是变好还是变坏**"的能力沉淀在评估集里——没有它，任何优化都是凭感觉，换模型/改 prompt 都不敢动。
- 好评估集的要点：**覆盖真实分布**（从线上真实 case 沉淀，而非拍脑袋编）、**含难例与边界**（易错、模糊、对抗样本）、**有明确判据**（每条能判对错，而不是"感觉还行"）。
- 要持续"喂养"：把线上新发现的失败 case 不断回灌评估集，让它随业务演进。
- 评估集要分层：既有可自动判分的客观题，也有需要 LLM-as-Judge 或人工的主观题[来源](https://cdn.openai.com/business-guides-and-resources/a-practical-guide-to-building-agents.pdf)。

> **追问/提示**：一句话点睛——"没有评估集的优化，都是许愿"。

### Q125：LLM-as-Judge 有哪些典型偏差？怎么校准？

**参考答案**：
- 常见偏差：**位置偏差**（偏爱靠前/靠后的候选）、**长度偏差**（偏爱更长更啰嗦的回答）、**自我偏好**（偏爱和自己风格相似的输出）、以及**评分漂移**（同一答案不同次打分不一致）。
- 校准手段：给裁判**明确评分标准与打分锚点**（rubric），把"好不好"拆成可判定的子项；**打乱候选顺序、多次投票取一致**来抵消位置/随机偏差。
- 关键一步是"**校验裁判本身**"：用一批有人工标注的样本核对裁判打分和人类是否一致，不一致就改 rubric。
- 高风险场景不能全交给裁判，要保留人工抽检兜底。

> **追问/提示**：能说"要评估评估者"，是很成熟的工程视角。

### Q126：Trace 全量采集太贵，怎么设计采样又不漏关键问题？

**参考答案**：
- 纯随机采样会漏掉稀有但重要的失败，纯全量又太贵，务实做法是"**分层采样**"：正常成功的请求低比例采样，**异常路径全量留存**（报错、超时、触发护栏、用户负反馈、成本超阈值的 case 必抓）。
- 对关键业务链路可临时开全量、问题定位后再降回。
- 采样要保证"**可回溯**"：每条 trace 带上足够的关联 ID（会话、用户、版本），出问题能顺藤摸瓜。
- 另一招是"**尾部采样**"：先缓冲，等一次请求跑完知道它是否异常，再决定留不留，避免为了抓异常而全量存储。

> **追问/提示**：能提"异常全量、正常抽样"，说明你懂成本和可观测的平衡。

### Q127：护栏应该放在哪一层？输入、输出、工具三道关怎么配合？

**参考答案**：
- 三道关各司其职：**输入关**拦截恶意/越权/注入类请求；**工具关**在真正执行危险动作前做权限与参数校验（尤其不可逆操作）；**输出关**过滤敏感信息、有害内容、以及不符合格式/事实的回答。
- 它们要**纵深配合**而非只设一道：输入没拦住的，工具关还能挡；工具关放过的，输出关再兜。
- 护栏本身要**可观测、可降级**：拦截了什么要记录，护栏挂了要有默认安全行为（宁可拒答不可放行危险操作）。
- 高风险动作应结合"人机协同"，让护栏在关键点把控制权交回人[来源](https://www.anthropic.com/engineering/building-effective-agents)。

> **追问/提示**：能把三道关说成"纵深防御"而非单点，体现安全思维。

### Q128：Prompt Injection 的纵深防御体系怎么搭？

**参考答案**：
- 单一手段都不够，要多层叠加。**输入侧**：对来自外部（网页、文档、工具返回）的内容做隔离与标注，明确"这是数据不是指令"，降低模型把它当命令执行的概率。
- **权限侧**：坚持最小权限——即使注入得逞，Agent 能触碰的工具和数据也有限，把爆炸半径压到最小。
- **执行侧**：危险/不可逆动作前强制人工确认或二次校验，让注入拿不到"直接执行"的通道。
- **监控侧**：对异常行为（突然要访问不相关资源、参数异常）告警。核心心法是"**假设注入一定会发生，把损失控制住**"，而不是幻想彻底杜绝。

> **追问/提示**：能说"防不住就限爆炸半径"，比只说"过滤输入"成熟得多。

### Q129：Prompt Cache（前缀缓存）省钱的原理是什么？怎么把上下文排得对缓存友好？

**参考答案**：
- 原理：很多请求共享相同的**前缀**（系统提示、工具定义、少样本示例），服务端可以缓存这段前缀的计算结果，后续命中就不必重复计算，从而省 token 成本、降延迟。
- 对缓存友好的排布关键是"**把稳定的放前面、把多变的放后面**"：系统提示/工具schema/固定示例放最前（可被反复命中），用户当轮输入、动态检索结果放最后。
- 反面教材是把随请求变化的内容（时间戳、随机 ID、检索片段）塞在最前，导致前缀每次都不同、缓存永远命中不了。
- 在多步 Agent 里，保持前缀稳定还能让整段循环持续吃到缓存红利。

> **追问/提示**：能说"变动内容后置"这条具体规则，说明你真做过成本优化。

### Q130：为什么"并行"不总是更快？并行的隐藏成本是什么？

**参考答案**：
- 并行只在子任务**真正独立**时才提速；一旦子任务间有依赖，就得等最慢的那个（受限于关键路径），并行度再高也没用。
- 隐藏成本包括：**结果聚合**（并行出来的结果要合并、去重、消解冲突，这步本身可能很贵）、**总 token 暴涨**（同时跑多路，峰值成本和限流压力都上来）、以及**调试变难**（并发下的错误更难复现）。
- 还有"长尾"问题：并行的总耗时由最慢分支决定，一个慢分支就拖垮整体感知速度。
- 所以要先判断"是不是真独立、聚合值不值",再决定并行——不是越并行越好。

> **追问/提示**：能提"关键路径"和"聚合成本"，说明你懂并行不是免费午餐。

### Q131：级联路由的"难度/置信度判断"怎么做？判断本身也要花钱怎么办？

**参考答案**：
- 判断路径通常有几种：**廉价先跑再校验**（先用小模型出答案，用规则或小裁判判断够不够好，不够再升级）、**基于特征的路由**（按输入长度、领域、是否需要工具等启发式先分流）、以及**基于历史的路由**（相似请求过去用哪档模型够用）。
- 判断本身的成本要**远小于**它能省下的成本，否则得不偿失——所以判断器要尽量轻（规则/小模型/嵌入相似度），别用大模型去判断该不该用大模型。
- 要监控"**错判代价**"：把难题错判成简单档会导致返工，反而更贵，需要在路由阈值上留安全边际。
- 本质是拿"一点判断开销"换"大头推理开销"，只有量级差够大才划算。

> **追问/提示**：能提"判断器要比被判断的便宜一个量级"，非常到位。

### Q132：为什么长任务要设计"检查点（checkpoint）/可恢复"？

**参考答案**：
- 长任务跑几十步、几分钟甚至更久，中途任何一步失败（工具挂了、超时、限流），若没有检查点就得**从头重来**——既浪费已花的成本，又可能重复执行不可逆操作。
- 检查点让任务能从最近的稳定状态**断点续跑**，只重做失败之后的部分。
- 它还是"**人机协同**"的基础：暂停等人确认、之后恢复，靠的就是能把状态存下来再取回（LangGraph 这类把 Agent 建模为带状态的图的框架，天然支持这种持久化与恢复）[来源](https://github.com/langchain-ai/langgraph)。
- 设计时要注意检查点的"**幂等恢复**"——恢复后不能把已完成的副作用再做一遍。

> **追问/提示**：能把 checkpoint 和"幂等""人机协同"串起来，体现系统观。

### Q133：Human-in-the-loop 应该在哪些节点介入？怎么设计才不打断体验？

**参考答案**：
- 该介入的典型节点：**执行不可逆/高风险动作前**（付款、删数据、对外发消息）、**置信度低或反复失败时**、以及**结果需要合规/责任确认时**。
- 设计原则是"**该拦的强拦、不该拦的别烦**"：把人工确认集中在少数关键闸口，而不是每步都打断，否则用户体验崩塌、也失去了自动化意义。
- 体验上可用"**默认建议 + 一键确认/否决**"，让人做判断题而非填空题；低风险场景用"**事后可撤销**"替代"事前必确认"。
- 关键是把"介入点"设计成产品的一部分，而非事后补丁。

> **追问/提示**：能说"确认要少而准、给用户判断题"，体现产品思维。

### Q134：为什么说"可复现性"是 Agent 工程的隐形基石？怎么提升？

**参考答案**：
- Agent 天生带随机性（采样温度、并发、外部工具返回都在变），导致"**同问不同答、出错难复现**"，而不能复现的 bug 几乎无法系统修复。
- 提升手段：**固定可控的随机源**（温度、seed）、**记录完整输入快照**（当时的 prompt、上下文、工具返回都存下来，回放时喂同样的输入）、**给外部依赖打桩**（测试时用固定的工具返回）。
- 还要做**版本化**：模型版本、prompt 版本、工具版本都要记，才能定位"是哪次改动引入的回归"。
- 有了可复现，评估、回归测试、事故排查才谈得上。

> **追问/提示**：能提"记录输入快照做回放"，是很实用的工程招。

### Q135：怎么给 Agent 设计"优雅降级（graceful degradation）"？

**参考答案**：
- 核心是"**关键路径不能因为某个部件挂了就整体崩**"。要预设当某能力不可用时的退路：检索挂了退回纯模型回答并声明不确定；工具超时给出已知信息+提示稍后重试；大模型限流则降级到小模型或缓存答案。
- 降级要"**明示而非默默**"：告诉用户当前处于降级状态、结果可能受限，避免用户误以为拿到的是完整能力。
- 要区分"**能降级**"和"**必须拒绝**"：低风险可降级服务，高风险（涉及安全/合规）宁可拒绝也不带病运行。
- 降级路径本身也要被测试和监控，否则真出事时降级逻辑也一起挂。

> **追问/提示**：能说"降级要告知用户、要被测试",说明考虑到了真实运维。

### Q136：Agent 的权限模型（最小权限）该怎么设计？

**参考答案**：
- 原则是**最小权限 + 显式授权**：Agent 默认什么都不能碰，只按任务需要开放最小的一组工具和数据范围，而不是给一个"万能账号"。
- 要按"**动作风险分级**"授权：只读类可宽松，写入/删除/对外/花钱类要收紧甚至强制人工确认。
- 权限要**可审计、可回收**：谁在什么时候用什么权限做了什么都要留痕，出问题能追责、能立即收权。
- 这直接决定了注入或失控时的"**爆炸半径**"——权限越小，最坏情况越可控（呼应 Q128）。

> **追问/提示**：能把权限和"爆炸半径"接上，安全思路就闭环了。

### Q137：为什么"日志/审计"对 Agent 不只是调试，还是合规刚需？

**参考答案**：
- Agent 会自主执行有副作用的动作（改数据、对外沟通、花钱），一旦出问题，"**它当时到底做了什么、为什么这么做**"必须能被完整还原，这在很多行业是合规和责任认定的硬要求。
- 所以要记录的不只是最终输出，而是**决策链路**：每一步的推理、工具调用及参数、返回、以及触发的护栏。
- 审计日志要**防篡改、可长期留存、可按主体检索**（按用户/会话/动作查）。
- 它和可观测性重叠但目的不同：可观测面向"改进系统"，审计面向"事后问责与合规"。

> **追问/提示**：能区分"可观测（改进）vs 审计（问责）",体现了成熟度。

### Q138：怎么理解"Agent 的能力上限，很大程度由工具和环境决定，而非只看模型"？

**参考答案**：
- 再强的模型，若没有合适的工具和可交互的环境，也只能"想"不能"做"——它够不到实时数据、改不了外部状态，能力被环境卡死。
- 反过来，给一个中等模型配上设计良好的工具、清晰的返回、可靠的环境反馈，往往比给强模型配烂工具表现更好。
- 所以工程投入的重心常常应放在"**把工具和环境做好**"（好描述、好返回、好错误处理、稳定的执行环境），而不是一味追更大的模型。
- 这也是为什么"工具设计"被反复强调是 Agent 工程的核心手艺之一[来源](https://huyenchip.com/2025/01/07/agents.html)。

> **追问/提示**：这题答好能扭转"唯模型论"，很能体现工程判断。

### Q139：给你一个模糊需求，怎么快速做出"第一版"？你的最小闭环是什么？

**参考答案**：
- 先**收敛范围**：抓一个最高频、最有价值、边界最清晰的子场景做"第一版"，而不是一上来就做全能体。
- 最小闭环：**单模型 + 少量必要工具 + 一个明确的完成判据 + 一小批真实测试 case**，先把"能端到端跑通一个真实任务"做出来。
- 刻意**先不上多 Agent、不上复杂记忆**——按"能简单就简单"的原则，把复杂度留到被数据证明确有必要时再加[来源](https://www.anthropic.com/engineering/building-effective-agents)。
- 有了第一版和评估 case，再靠"跑—看失败—针对性加复杂度"的循环迭代。

> **追问/提示**：能说"先收敛场景、先做最小闭环",完全对上大厂实践指南的建议。

### Q140：用一句话概括"做好 Agent 工程"的核心心法，你会怎么说？为什么？

**参考答案**：
- 一句话："**能简单就简单，把复杂度花在刀刃上，并让一切可评估、可观测、可控。**"
- "能简单就简单"来自主流实践的共识——先用最朴素的方案，只有当自主性和灵活性确实带来价值时才加复杂度[来源](https://www.anthropic.com/engineering/building-effective-agents)。
- "可评估、可观测、可控"是把 Agent 从 demo 送进生产的三根支柱：没有评估就不敢改，没有可观测就修不了，没有控制就不敢放。
- 之所以用这句收尾，是因为它把前面 139 道题的技术细节，压缩成了一个能指导取舍的价值观——面试时能亮出这句，说明你不只会点，还有"面"。

> **追问/提示**：这是全章的"题眼",能把它讲清楚，等于给整场面试收了个漂亮的尾。

#### 深挖专栏 D：把"真实面试的连环追问"走一遍

前面说过，面试的杀伤力在追问。这里用一道最常见的开场题，演示面试官是怎么一层层往下钻的——你会看到，接住追问靠的不是背更多题，而是每个概念都想透了"为什么"和"边界"。
```
面试官：什么是 Agent？                                    → 考「压缩」：一句话能不能说清
   │
   ├─ 你答：以 LLM 为大脑、能自主决策并循环迭代的系统
   │
面试官：那它和 Workflow 有什么区别？                        → 考「结构」：能不能抓住"控制权"这条轴
   │
   ├─ 你答：区别在控制权归属，流程写死是 Workflow，模型动态决定才是 Agent
   │
面试官：那是不是越自主越好？                                → 考「边界」：知不知道代价
   │
   ├─ 你答：不是，自主带来灵活也带来不可控，能简单就简单
   │
面试官：不可控具体指什么？你怎么在生产里控住？              → 考「工程」：能不能落到实处
   │
   ├─ 你答：可能绕路/循环/超支 → 硬上限 + 重复检测 + 显式完成判据 + 人机协同
   │
面试官：那你怎么知道改动之后是变好还是变坏？                → 考「闭环」：有没有评估意识
   │
   └─ 你答：靠评估集，把线上失败 case 回灌，任何改动先过评估再上线
```
看这条追问链：从"是什么"(Q1) → "怎么区分"(Q4) → "代价"(Q2) → "怎么控"(Q114/Q82) → "怎么评估"(Q124)，**一道开场题最终打穿了五个板块**。这正是这一类"进阶追问加练"的意义——真实面试不按板块出题，而是顺着一个点往深里钻。你要练的，是**任意一个点被追问四五层都能接住**。

#### 本类速记卡

进阶追问类没有整齐的对照表，但可以把"面试官的追问方向"归纳成一张"钻取地图"，帮你预判下一问会往哪走：
```
听到任何一个概念，面试官大概率会往这四个方向追：
  ① 为什么这样设计？   → 讲机制/原理（第二层）
  ② 它的代价/边界？    → 讲什么时候不适用、代价是什么（第三层）
  ③ 生产里怎么落地？   → 讲评估/可观测/护栏/成本（工程层）
  ④ 你自己踩过吗？     → 讲真实案例、怎么定位、怎么权衡（经验层）
```
**高频陷阱与红旗（本类）**：

1. 只能答第一层定义，一问"为什么"就卡壳——典型的"背题"信号。
2. 把"格式对"当"内容对"、把"隐藏思考"当"没有思考"、把"多 Agent"当"更高级"——概念似是而非。
3. 谈优化只说好处，答不出隐藏成本（并行的聚合成本、缓存的排布约束、判断器自身开销）。
4. 安全类只会说"过滤输入"，说不出"限爆炸半径""纵深防御""最小权限"。
5. 通篇没有一次"评估/可观测/可复现"意识——一看就是没做过生产。

**串题演练**：把 Q114-Q140 和前八类交叉着练——比如从 Q1 出发，练"被追问到 Q114（控循环）→ Q124（评估）"的链路；从 Q60（Agentic RAG）出发，练"被追问到 Q118（返回值设计）→ Q69（检索不到怎么办）→ Q135（降级）"的链路。**能自己画出这些追问链，你就从"刷题的人"变成了"懂体系的人"。**

## 31.10 动手实践：把题库变成你自己的

速查题库最怕"读完就忘"。这一节给你三个把它盘活的练法，任选其一坚持下去，效果远胜反复默读。

**练法一：自建"红黄绿"筛题表。** 拿一张纸或一个表格，把 Q1-Q140 过一遍，每题标一个颜色：绿（能脱口而出第一层定义）、黄（大概知道但讲不利索）、红（完全卡壳）。之后只复习黄和红，绿的隔几天抽查一次。这个方法的价值在于**逼你诚实面对"哪些是真会、哪些是自以为会"**——很多人栽在"以为自己懂了"的黄题上。

**练法二：给每道开放题挂一个"真实素材"。** 本章的开放/经验题（Q15、Q57、Q95、Q99、Q107、Q108 等）都没有标准答案，它们的答案要从你自己的项目里长出来。找一个你真做过的 Agent 相关的事（哪怕是课程项目、复现的 demo），围绕它准备：你遇到过什么坑、怎么定位、怎么权衡、学到什么。**把这个素材反复往不同开放题上套**，你会发现一个好素材能撑起七八道题。

**练法三：结对模拟连环追问。** 找个同伴（或对着录音自问自答），不要一题一答就停，而是照每类速记卡里的"串题演练"那条线一路追问下去。真实面试的杀伤力在追问——第一层谁都会背，第二层第三层才见真章。**练到能被连问四五层还不慌，你就真的准备好了。**

> **一个提醒**：动手写代码永远是性价比最高的复习。如果时间有限，与其把 140 题背第三遍，不如去把 Q58 说的"最小 Agent"亲手写出来、跑起来、让它失败一次再修好。写过之后回头看这些题，你会有"原来说的就是这个"的通透感。

## 31.11 本章小结

这一章我们用速刷的方式，把 Agent 面试的高频考点铺成了 140 道问答对，分九类收纳。回头看，前八类不是散的，而是有一条清晰的**由内而外、由概念到落地**的主线，第九类则把这条主线拧成"被追问也不散"的韧性：
```
基础概念（是什么·控制权）
    │
核心能力（规划·记忆·工具·反思——Agent 内部怎么运转）
    │
协议与编排（Function Calling·MCP·五模式·多 Agent——组件怎么协作）
    │
框架（用什么工具把上面这些搭起来）
    │
RAG 与上下文（怎么把知识和上下文喂对）
    │
工程化（怎么让它可靠、可观测、可控）
    │
成本与性能（怎么让它用得起、跑得快）
    │
系统设计与开放（把以上全部组织成一个真实系统）
    │
进阶追问加练（把任意一个点被连问四五层都能接住）
```
如果要把全章浓缩成几句能带进考场的"元原则"，我会挑这五条：

1. **控制权归属是一切的题眼。** 判断是不是 Agent、要不要上 Agent、是不是真多 Agent，都回到"控制流由谁决定"。
2. **能简单就简单。** 从 Anthropic 到 OpenAI，主流工程共识都是"先追求简单，只有当自主性/复杂方法确实带来价值时才引入"[来源](https://www.anthropic.com/engineering/building-effective-agents)。这句话能救你于无数"该不该上 X"的题。
3. **喂对比喂多重要。** 上下文不是越长越好，检索和上下文工程的核心是提高信噪比。
4. **可靠性是生产的分水岭。** 评估、可观测、护栏、终止、幂等——从 Demo 到生产，拼的是工程可靠，不是模型聪明。
5. **答案要有骨架，也要有血肉。** 骨架是本章给你的浓缩答案，血肉是你自己的例子、踩坑、取舍。能长出血肉，才和"背题的人"拉开差距。

最后再强调一次本章开头的话：**这些参考答案是起点不是终点。** 真正的面试准备，是把它们内化成你能用自己的语言、自己的经历讲出来的东西。当你能在被连环追问时依然从容——不是因为你背得多，而是因为你想得清、做得实——你就赢了。

## 31.12 跨题综合演练与参考解答

下面这些"跨题综合题"不对应单一某道题，而是要你把多道题的知识串起来，正是面试官最爱的问法。先自己组织一遍思路，再对照参考解答查漏——参考解答给的是"答题骨架 + 得分点"，不是唯一标准答案。

**综合题 1**：有人说"我做了个多 Agent 客服系统"，你想追问哪三个问题来判断它到底是不是真多 Agent、设计得好不好？（串联 Q4、Q42、Q45、Q105）

> **参考解答**：三问直击要害——① "各 Agent 的控制流是谁决定的？"若路由顺序是代码写死的，那本质是 Workflow 而非多 Agent（控制权归属，Q4）；② "两个 Agent 的职责边界清晰吗？路由准确率多少？"若常被路由混淆，说明拆分本身有问题，该合并（Q45）；③ "跨 Agent 传递上下文时丢信息吗？失败在哪一层定位？"考察它有没有正视多 Agent 的真实代价——路由错误、上下文丢失、调试变难（Q105）。能问出这三点，说明你不是被"多 Agent"这个词唬住，而是在查它的工程成色。

**综合题 2**：一个企业知识库问答 Agent 上线后"经常答错但难复现"，请把"排查 → 定位 → 修复 → 防复发"完整讲一遍。（串联 Q70、Q77、Q101、Q111）

> **参考解答**：**排查**先分层——是检索没召回对（retrieval），还是召回对了但模型没用好（generation）？靠 trace 把每次请求的召回片段和最终答案都记下来（Q77 可观测）。**定位**：难复现往往源于非确定性（采样温度、检索 Top-K 抖动）与"答案不附引用"，所以先把温度调低、强制答案标注引用来源，让错误可归因（Q101、Q111）。**修复**：检索侧优化 chunk 与 rerank，生成侧强制"无依据不作答"（Q70）。**防复发**：把每个复现出的坏 case 固化进回归评估集，改动后自动跑，守住不回退（Q124 思路）。一句话收口：难复现的根因通常是"没有可观测 + 有非确定性"，先让它可复现，再谈修复。

**综合题 3**：为什么"上下文窗口变大"既没有让 RAG（Retrieval-Augmented Generation，检索增强生成）过时，也没有让"平方级成本"问题消失？请从相关性、成本、注意力三个角度说。（串联 Q67、Q68、Q89）

> **参考解答**：**相关性**——窗口再大，把无关文档全塞进去只会降低信噪比，RAG 的价值是"只喂相关的"，这与窗口大小无关（Q67）。**成本**——注意力是 O(n²) 量级，上下文越长单次越贵，把全库塞进上下文在经济上不可行，检索是成本控制手段（Q89）。**注意力**——长上下文存在"中间迷失"（lost in the middle），关键信息埋在中段会被忽略，所以即便塞得下也未必答得好（Q68）。三点合起来：大窗口是"能力上限"提高，但相关性、成本、注意力三重约束决定了"检索 + 上下文工程"依然是刚需。

**综合题 4**：老板要求"质量不降的前提下把成本砍一半"，请给出一套系统化方案，并说明每一步怎么保证质量不塌。（串联 Q88-Q99）

> **参考解答**：按"先减量、再降价、后缓存"的优先级动手，每步都挂质量闸门——① **减步数**（成本随步数平方级涨，减步收益最大）：优化工具让一步拿到关键信息，质量用回归集守住；② **分层路由**：简单问题走小模型、难问题走大模型，用置信度/规则兜底防止误分级导致质量塌（Q90）；③ **prompt caching**：把稳定的系统提示与工具定义缓存，只省钱不改语义，质量零风险（Q92）；④ **语义缓存**：高频重复问题命中缓存，配相似度阈值防串答。每一步上线都先影子流量对比质量指标，达标才放量——核心原则是"降本动作必须可回滚、可度量"。

**综合题 5**：给你一个"能操作网页下单"的 Agent 需求，请从安全、幂等、终止、人在回路四个角度，列出你必须加的护栏。（串联 Q82、Q83、Q84、Q104）

> **参考解答**：**安全**——下单、支付属高危操作，权限最小化 + 操作白名单 + 对页面注入内容做校验防提示注入（Q82）；**幂等**——每笔下单带幂等键，重试/恢复时不重复扣款（Q83）；**终止**——设步数上限与超时，防止在"找不到按钮—重试"里烧钱死循环（Q84）；**人在回路**（Human-in-the-Loop，HITL）——支付金额超阈值或涉不可逆操作时中断转人工审批，通过后再续跑（Q104）。收口一句：凡"花钱、不可逆、对外可见"的动作，默认都要护栏，宁可多拦一次也不放过一次。

**综合题 6**：如果只让你问候选人一道题来判断"他是真懂 Agent 还是只会背"，你会问什么？为什么？（考的是你对"什么最本质"的判断）

> **参考解答**：这题没有唯一答案，但高分思路是问一道**逼出"权衡与边界"的题**，例如"你做过的某个 Agent，哪个设计决定你后来后悔了，为什么？"。原因：会背的人能流利复述定义，但答不出真实的取舍与踩坑；只有真正做过、想过代价的人，才能讲出"当时选 A、后来发现 B 更好、代价是什么"。本质是——**用"讲代价"来区分"记知识"和"用知识"**，这也是全书反复强调的最强信号。

**综合题 7**：一个长链路 Agent 任务跑到第 12 步时工具超时崩了，请把"为什么要有检查点、恢复时怎么保证不重复执行副作用、恢复后如何续跑"讲成一套方案。（串联 Q114、Q83、Q132）

> **参考解答**：**为什么要检查点**——长链路重跑成本高，检查点让任务能从崩溃处续跑而非从头再来（Q114）。**不重复副作用**——已执行的写操作（下单、发消息）要靠幂等键去重：恢复时先查"这步是否已成功执行过"，成功则跳过只取结果（Q83）。**怎么续跑**——把每步的状态（已完成步骤、中间产物、计划）持久化为可恢复的 state，恢复时加载 state、定位到断点、重放未完成部分（Q132）。一句话：检查点解决"从哪续"，幂等解决"续跑不重复作恶"，状态持久化解决"续跑有依据"。

**综合题 8**：面试官顺着"什么是 Agent"一路追问到"你怎么保证改动之后系统变好而不是变坏"，请把这条从概念到评估闭环的追问链，用你自己的话一口气讲完。（串联 Q1、Q4、Q2、Q114、Q124）

> **参考解答**：一口气讲法——"Agent 是以 LLM（Large Language Model，大语言模型）为大脑、能自主决策并循环迭代的系统（Q1）；它和 Workflow 的分水岭是控制权归属（Q4）；实现上靠 ReAct（Reasoning and Acting，推理与行动）这类边想边做的循环推进（Q2）；但自主循环会带来不可控和错误累积，所以工程上要有检查点、终止条件兜住（Q114）；而要保证每次改动是变好不是变坏，就必须有可回归的评估集——把坏 case 固化、改动后自动跑、指标不回退才上线（Q124）。"这条链从"是什么"讲到"怎么保证可持续变好"，正好展示了从概念到工程闭环的完整认知。

> 能把这八道综合题讲清楚，说明你已经不是在"记题"，而是在"用知识"——这正是本章想带你到达的地方。真正的高手，是能把任意两三道题的知识临时拼成一个连贯方案，而不是等着面试官恰好问到你背过的那道。
