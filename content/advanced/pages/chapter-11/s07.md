## 真实问题

线上告警写着「多智能体研究助手质量下降」，但这句话无法直接行动。根因可能在分解（编排者委派不清）、召回（子智能体搜错地方）、组装（子结论没进最终聚合）、协调（无限踢皮球）、成本（token 爆炸）或版本（多个生效结论冲突）。多智能体的生产诊断必须先保存**跨 Agent 的运行轨迹（trace）与请求快照**，再按变量分层，绝不能把一切归结为「模型不行」或「上下文太长」。这一节把全章的坑收敛成一张可查的表、一个可运行的分层诊断器，和一组能直接用于系统设计面试的思考回答。

## 诊断顺序

1. **复现**：固定任务、模型版本、温度、工具快照、数据版本与子智能体数量；Anthropic 提醒 Agent 两次运行即使提示相同也非确定性，必须先想办法稳定复现 [来源](https://www.anthropic.com/engineering/multi-agent-research-system)。
2. **看分解**：编排者是否给每个子任务写清了目标、输出格式、工具指引与边界；有没有多个子智能体重复劳动。
3. **看召回**：正确证据是否被某个子智能体搜到、并实际进入它的回传。
4. **看组装**：子结论是否真的进入了编排者的最终聚合，还是被置信度门槛误杀或悄悄丢弃。
5. **看冲突**：多个子智能体的结论是否互相矛盾、是否存在多个生效版本。
6. **看协调**：hop 数是否逼近上限、是否出现无限对话或不收敛。
7. **看成本**：单查询子智能体数与总 token 是否与任务价值匹配（对照 15× 基准）。
8. **比基线**：同一输入在固定版本上的多次结果与离线评测集对比，评「结果对不对」而非「步骤对不对」。

## 最小可运行演示：多智能体分层诊断器

把上面的诊断顺序写成一个确定性规则树，用来在拿到 trace 后快速缩小根因范围。它允许并列报告多个根因，而不是遇到第一项就停止；它只负责缩小范围，不替代基于 trace 的根因分析。
```python
def diagnose(m: dict) -> list[str]:
    findings = []
    if not m["evidence_in_final"]:
        findings.append("组装：子结论未进入最终聚合")
    if m["active_versions"] > 1:
        findings.append("冲突：存在多个生效版本")
    if m["hops"] >= m["max_hops"]:
        findings.append("编排：疑似无限踢皮球/未收敛")
    if m["subagent_token_ratio"] > 10:
        findings.append("成本：子智能体 token 膨胀，复核任务价值")
    return findings or ["需固定输入做拓扑与提示消融"]


def main() -> None:
    print("\n".join(diagnose({
        "evidence_in_final": True, "active_versions": 2,
        "hops": 3, "max_hops": 5, "subagent_token_ratio": 15,
    })))


if __name__ == "__main__":
    main()
```
保存为 `diagnose_ma.py`，运行 `python diagnose_ma.py`，预期输出：
```text
冲突：存在多个生效版本
成本：子智能体 token 膨胀，复核任务价值
```
这个例子里 `active_versions=2` 触发冲突诊断、`subagent_token_ratio=15` 触发成本诊断，两条并列输出，说明生产故障常常不止一个根因。把 `evidence_in_final` 改成 `False`，输出还会多一条「组装」故障；把 `hops` 改成等于 `max_hops`，会多一条「编排」故障。生产系统应把每条判断连接到可打开的 trace 与输入快照，而不是止步于规则树。

## 真实系统对应

**官方公开机制**：Anthropic 用全生产追踪诊断非确定性失败、只监控决策模式与交互结构以保护隐私、用 rainbow deployment 灰度、用小样本+LLM-as-judge+人工三层评测 [来源](https://www.anthropic.com/engineering/multi-agent-research-system)。LangGraph 的持久化与检查点、图递归上限用于状态恢复与防不收敛 [来源](https://langchain-ai.github.io/langgraph/concepts/persistence/)。AutoGen 的显式终止条件防无限对话 [来源](https://microsoft.github.io/autogen/stable/user-guide/agentchat-user-guide/tutorial/teams.html)。CrewAI 的 Sequential/Hierarchical 流程控制推进方式 [来源](https://docs.crewai.com/en/concepts/processes/)。**通用工程模式**：先观测再优化、按层定位根因、每次只改一个变量做对照。**教学参考实现**：`diagnose` 规则树是缩小范围的启发式，阈值需按团队风险配置。

## 思考：多智能体系统最重要的可观测性指标是什么？

### 回答

没有单一指标。多智能体的最低观测集合应包含：任务成功率（评结果而非步骤）、每个子智能体的工具调用数与 token 占比、编排的 hop 数与是否触顶、子结论进入最终聚合的比例、冲突/多版本计数、交接载荷是否完整、以及端到端延迟与总成本。关键约束是**成本指标必须与任务结果联看**——单看「省了 token」可能只是少给了证据；单看「成功率高」可能只是数据版本变了。Anthropic 的做法印证了这一点：他们监控 Agent 的决策模式与交互结构而非单条对话内容，用全链路 trace 定位「哪一步第一次偏离」[来源](https://www.anthropic.com/engineering/multi-agent-research-system)。所以最重要的不是某个数字，而是「能不能把一次失败归因到具体的 Agent 与 hop」。

### 面试精简表达

最重要的是可归因性：用贯穿全程的 trace_id 记录每个子智能体的调用、token、hop 与子结论去向，把失败定位到具体 Agent 与交接点；成本指标必须与任务成功率联看，否则省 token 可能只是少给证据。

## 思考：如何把多智能体方法引入一个现有的单 Agent 系统？

### 回答

先加观测，再谈拆分，最后才上完整多智能体。第一步是给现有单 Agent 补全链路 trace 与失败样本回归集，弄清它到底卡在哪——是工具太多选错、还是上下文装不下、还是职责纠缠。第二步做最小拆分：按第 01 节的三关（必要性/可分性/成本），先把巨型单 Agent 拆成「路由 + 两三个各管一摊的专业 Agent」，这一步直接提升每步先验准确率，成本增量小。第三步才在确实需要并行发散、且价值足够高的环节引入编排者-工作者，给每个子任务写清四要素、设置终止条件与置信度门槛。每一步都做对照实验、保留回滚开关，并复核「新增的 15× token 是否换来了值得的收益」。绝不要一上来就设计五六个 Agent 互调——那只会拉长复合错误链、让调试变成噩梦。

### 反例

不要在「明确正在发生越权写入或误退款」时还坚持「先做完整观测再动手」。如果多智能体系统里某个 Agent 正在触发不可逆的高风险动作，应先在**执行层**停用危险能力止损，再补观测。先观测适用于质量与成本优化，不意味着延迟紧急止损——护栏必须在模型之外强制执行。

## 思考：面试问「你怎么设计一个电商智能客服的多智能体系统」，怎么答？

### 回答

先讲判断再讲架构。判断层：订单查询、退款、技术故障、闲聊四类需求里，退款是高风险、需集中把关；技术故障会在「分诊→技术→资深专家」间自然流转；闲聊要轻快。所以答案是**混合拓扑**——顶层用一个只做分类的路由（或分诊 Agent）分流，普通咨询走 handoff 对话式接力、退款切到 Supervisor 集中审核。通信层：交接必须携带结构化载荷（用户身份、已确认问题、已尝试方案），防止接管者重新盘问；子结论走消息传递解耦，慎用共享黑板。可靠性层：给每个循环设 max_hops 防无限踢皮球，用复合可靠性数学（0.95ⁿ）论证「能少一个 Agent 就少一个」，关键环失败降级转人工。护栏层：退款这类不可逆动作的审核加在执行层、配 Human-in-the-Loop，与哪个 Agent 触发无关。观测层：贯穿 trace_id，记录每跳 Agent、耗时、工具调用、交接载荷，评「结果对不对」。最后点出成熟度——先证明单 Agent 不行、任务可分、价值够高，三关都过才拆。

### 面试精简表达

混合拓扑：路由分流 + 普通咨询 handoff 接力 + 退款走 Supervisor 集中把关；交接带结构化载荷、循环设 max_hops、高风险动作在执行层加人工审核、全程 trace_id 可归因；先过「必要性/可分性/成本」三关再拆。

## 思考：什么时候应该让多智能体系统「拒绝继续」并上报？

### 回答

当继续生成只会掩盖不确定性时就应拒绝。具体触发点包括：编排的 hop 数触顶仍未收敛、子智能体回传的置信度全部低于门槛、多个子结论存在无法自动调和的版本冲突、不可逆动作的执行状态未知、关键证据无权限访问、或交接载荷缺少必要字段。此时正确做法是返回**结构化失败**——包含失败阶段、缺失了什么、以及可恢复方式（如从哪个检查点重试），交由上游或人工处理，而不是硬编一段流畅但可能错误的答复。这对应第 05 节 demo 里 Supervisor 的置信度门槛——**让编排者拥有拒绝的能力**是可靠多智能体的底线。拒绝信息本身不得泄露敏感内部细节，且个人可识别信息（Personally Identifiable Information，PII）在写入 trace 前应最小化与脱敏。

### 反例

不要把「拒绝继续」当成遇到任何不确定就停摆。开放式研究任务天然允许未决项与多条并行路径，Anthropic 就用「end-state 评估」承认 Agent 可以走不同但都正确的路径 [来源](https://www.anthropic.com/engineering/multi-agent-research-system)。拒绝应保留给「继续会掩盖风险或产生不可逆后果」的场景，而不是把正常的探索性不确定也一刀切地上报。

## 值班现场：从「研究助手变笨」到可复现故障

凌晨的告警只有一句「研究助手正确率下降」，token 与延迟都没异常。值班人员若只看资源指标会误判为模型波动。抽取失败样本、按 trace_id 展开后发现：编排者把「对比 A、B 两家公司 2025 年财报」这个需要 2 到 4 个子智能体的比较型查询，只派了 1 个子智能体串行搜索——因为最近一次提示改动误删了「按复杂度缩放」的规则，导致比较型查询被当成简单事实处理，子智能体来不及覆盖两家公司就返回了。

定位过程先冻结变量：模型标识、温度、工具 schema、语料快照、请求输入与提示版本。随后按 trace 逐跳检查：hop 数只有 3（plan+1 次 search+synthesize），远低于比较型该有的规模；子智能体的搜索只覆盖了 A 公司。这证明首要故障在**分解阶段**而非召回或模型能力。恢复被删的缩放规则后，同一查询派生 3 个子智能体、覆盖两家公司，正确率回升。团队进一步在提示回归集里固定了「比较型查询必须派 ≥2 个子智能体」的断言，防止再次回归。

优化前，告警只有一个总体正确率，无法区分分解、召回、组装；优化后，每个 trace 记录 hop 数、每个子智能体的主题覆盖、token 占比与子结论去向。故障从数小时缩短到二十分钟定位。这个结果不是因为日志越多越好，而是因为轨迹能回答「哪一层第一次偏离预期」——这正是全章反复强调的：**多智能体的可观测性核心是可归因，而非堆量。**

## 六类常见误诊

「上下文太长」常被当成通用解释，但在多智能体里，输入长可能只是子结论多。若编排者委派本身就模糊，裁剪上下文不会修复重复劳动；若某个子智能体搜错了数据源，重排提示也无效。

「换更大模型」可能暂时提升成功率，却掩盖分解规则缺失、终止条件缺位、状态不可恢复等结构问题。更强模型仍然不会读取没进入聚合的子结论，也不能替代 max_hops 去阻止无限踢皮球。

「多加几个子智能体」几乎是最诱人的误诊。Anthropic 的数据恰恰相反：早期失败正是「为简单查询爆出 50 个子智能体」，解法是按复杂度缩放**减少**而非增加投入 [来源](https://www.anthropic.com/engineering/multi-agent-research-system)。子智能体越多，token 与协调复杂度越高、复合错误环数越长。

「群聊全广播最省事」忽略了 token 随 Agent 数暴涨；「共享黑板最方便」忽略了并发写竞态；「测试通过」若只覆盖单个 Agent 或 Mock，就忽略了多智能体特有的涌现交互行为——对主导 Agent 的微调可能不可预测地改变子智能体行为 [来源](https://www.anthropic.com/engineering/multi-agent-research-system)。找到第一个出现偏差的层，永远比换模型或加 Agent 更重要。

## 生产观测数据模型

一次多智能体运行至少关联 `trace_id`、任务类型、查询复杂度分类、模型版本、语料/工具版本与代码版本。**编排阶段**记录分解出的子任务数、每个子任务的目标与边界、hop 序列与是否触顶；**子智能体阶段**记录各自的主题覆盖、工具调用数、token 用量、回传的 conclusion/evidence/confidence；**交接阶段**记录 destination 与 payload 字段完整性；**聚合阶段**记录采纳/丢弃了哪些子结论及原因、冲突计数；**结果阶段**记录任务成功、约束遵循、总成本与端到端延迟。

原始提示与检索原文可能含个人信息和密钥，不能为了可观测性无界保存。Anthropic 的做法是监控决策模式与交互结构而非单条对话内容以保护隐私 [来源](https://www.anthropic.com/engineering/multi-agent-research-system)。追踪管道应在写入前脱敏，敏感正文可保存受控对象指针；访问记录与保留期独立治理。若法规禁止留存原文，就保存最小必要结构与不可逆哈希，并接受复现能力受限。

## 从告警到修复的运行过程

值班人员先选一条失败 `trace_id`，导出脱敏后的子任务分解、各子智能体回传、交接载荷与聚合决策；用相同版本离线重放，确认能稳定失败；运行分层诊断器得到候选根因层级；只修改单一环节（例如恢复缩放规则、或补一个终止条件）后重放整套回归集；指标通过再灰度发布，并保留旧路径开关。若无法固定复现，则比较失败与成功样本的数据版本、查询复杂度分类与子智能体主题覆盖，而不是直接调提示。

修复完成的证据包括：比较型查询派生了足够的子智能体、正确证据进入了某个子智能体的回传并进入最终聚合、冲突版本被过滤、hop 数在合理范围、总 token 与任务价值匹配、回归集未出现新类别退化。只有「这条查询这次答对了」远不足以关闭事故——多智能体的涌现性意味着单例通过可能只是偶然走对了一条路径。
