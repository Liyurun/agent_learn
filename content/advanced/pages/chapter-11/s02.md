## 真实问题

拆分之后，第一个绕不开的决策是：这几个 Agent 之间的**控制权**怎么流动？某团队把「分诊、检索、生成、审核」四个 Agent 拉起来，一开始让它们「谁想说话就说话」——任何 Agent 都能决定下一个调谁。结果一次退款咨询里，检索 Agent 和生成 Agent 互相调用了七八轮才收敛，日志乱成一团，根本看不出「这一步为什么是它在说话」。换成「一个中心 Agent 统一决定下一步调谁」之后，同样的查询三跳就结束，轨迹清晰可审计。

同一批 Agent，仅仅因为拓扑不同，表现天差地别。拓扑不是画在架构图上好看的装饰，它直接决定了控制权流向、可审计性、并行度和调试难度。

## 原理

LangGraph 的多智能体文档把 Agent 建模成图节点，系统性地列出了几种连接方式 [来源](https://langchain-ai.github.io/langgraph/concepts/multi_agent/)：

- **Network（对等网络）**：每个 Agent 都能和任意其他 Agent 通信，任一 Agent 都能决定下一个调谁。适合「没有清晰层级、也没有固定顺序」的问题。
- **Supervisor（编排者）**：每个 Agent 只和一个 supervisor 通信，由 supervisor 决定下一个该调哪个 Agent。
- **Supervisor(tool-calling)（工具调用式编排者）**：Supervisor 的特例——把每个子 Agent 当作「工具」，用一个会调用工具的 LLM 决定调哪个工具、传什么参数。
- **Hierarchical（层级）**：supervisor 之上再放 supervisor，是 Supervisor 架构的泛化，用于更复杂的控制流。
- **Custom workflow（自定义流水线）**：每个 Agent 只和一部分 Agent 通信，部分流程是确定性的，只有少数 Agent 能决定后继。

其中最常见的「确定性流水线」就是 **Sequential（顺序）**：Agent 串成一条线，上一个的输出是下一个的输入。CrewAI 的流程文档把它列为两大内置流程之一：Sequential「按任务列表预定义顺序执行，一个任务的输出作为下一个任务的上下文」；Hierarchical 则「指定一个 manager LLM 或自定义 manager Agent，由它规划、委派、校验」，任务不预先分配、由 manager 按能力动态分派 [来源](https://docs.crewai.com/en/concepts/processes)。

三种基础拓扑的控制权流动可以并排理解：
```text
Supervisor（中心辐射，控制权像回旋镖）：
        用户
         │
      ┌──▼──┐
      │ Sup │◀──────────┐
      └┬─┬─┬┘           │ 结论回传
   ┌───┘ │ └───┐        │
   ▼     ▼     ▼        │
 [W1]  [W2]  [W3] ──────┘   Sup 统一聚合 → 用户

Network（对等，控制权像自由传球）：
   [A]⇄[B]
    ⇅ ╳ ⇅        任一 Agent 可决定下一个调谁
   [C]⇄[D]

Sequential（流水线，控制权像单向传送带）：
   用户 → [草稿] → [审阅] → [润色] → 用户
```
## 现象与输入

同一批子任务，在不同拓扑下的调用次序完全不同。用贯穿案例的两个子任务 `a`、`b` 观察 Supervisor 拓扑的轨迹，再用「草稿→审阅→润色」观察 Sequential 拓扑：
```text
Supervisor：先 plan，再逐个 dispatch，最后 synthesize 聚合
Sequential：按固定阶段单向流动，不回中心
```
## 最小可运行演示
```python
def supervisor_order(subtasks: list[str]) -> list[str]:
    trace = ["supervisor:plan"]
    for t in subtasks:
        trace.append(f"dispatch:{t}")
    trace.append("supervisor:synthesize")
    return trace


def sequential_order(stages: list[str]) -> list[str]:
    return [f"stage:{s}" for s in stages]


def main() -> None:
    print("Supervisor:", supervisor_order(["a", "b"]))
    print("Sequential:", sequential_order(["draft", "review", "polish"]))


if __name__ == "__main__":
    main()
```
保存为 `topology.py`，运行 `python topology.py`，预期输出：
```text
Supervisor: ['supervisor:plan', 'dispatch:a', 'dispatch:b', 'supervisor:synthesize']
Sequential: ['stage:draft', 'stage:review', 'stage:polish']
```
Supervisor 的轨迹一定是「先规划、再分派、后聚合」，控制权每次都回到中心，因此天然可审计；Sequential 的轨迹是单向的，没有中心，胜在简单可预测。Network 没有在这里演示轨迹，因为它的次序由运行时决定、不固定——这正是它灵活但难审计的根源。

## 三种拓扑对比

| 维度 | Supervisor/层级 | Network/对等 | Sequential/流水线 |
|---|---|---|---|
| 控制权 | 始终回到中心（回旋镖） | 在对等 Agent 间自由传（传球） | 单向传送（传送带） |
| 下一步谁决定 | 中心 supervisor | 当前 Agent 自主决定 | 预先定义、确定性 |
| 并行能力 | 强（可 map-reduce 分派） | 中（取决于设计） | 弱（本质串行） |
| 可审计/护栏 | 易（集中把关） | 难（分散、次序不定） | 易（路径固定） |
| 适合场景 | 需统一质量把关、可并行分派 | 无清晰层级、需灵活流转 | 阶段清晰、后阶段依赖前阶段 |
| 对应真实系统 | Anthropic 研究系统、CrewAI Hierarchical、LangGraph Supervisor | LangGraph Network | CrewAI Sequential、提示链 |

现实系统常**混合使用**：LangGraph 明确指出 Hierarchical 是 Supervisor 的泛化，可以「团队里用 Supervisor、团队之间再加顶层 Supervisor」[来源](https://langchain-ai.github.io/langgraph/concepts/multi_agent/)；也可以顶层用流水线做阶段推进，某个阶段内部再用 Supervisor 并行分派。

## 真实系统对应

**官方公开机制**：LangGraph 文档给出 Network、Supervisor、Supervisor(tool-calling)、Hierarchical、Custom workflow 五类连接方式及可运行代码骨架 [来源](https://langchain-ai.github.io/langgraph/concepts/multi_agent/)；CrewAI 提供 Sequential 与 Hierarchical 两种内置流程，后者必须指定 `manager_llm` 或 `manager_agent` [来源](https://docs.crewai.com/en/concepts/processes)；Anthropic 研究系统采用 orchestrator-worker（编排者-工作者）这一 Supervisor 拓扑的具体落地 [来源](https://www.anthropic.com/engineering/multi-agent-research-system)。**通用工程模式**：用「控制权流动方式」区分三类拓扑，用「是否需集中把关、是否可并行、阶段是否固定」来选型。**教学参考实现**：上面的 `supervisor_order`/`sequential_order` 只演示调用次序，不含真实 LLM 调用。

## 层级拓扑：当一个 supervisor 也管不过来

LangGraph 特别提醒：随着 Agent 变多，单个 supervisor 会重新陷入「工具太多、上下文太复杂」的老问题——它开始在「下一个调谁」上做出糟糕决策 [来源](https://langchain-ai.github.io/langgraph/concepts/multi_agent/)。这时的解法是**层级化**：把 Agent 分成若干专业小队，每队一个 supervisor，再加一个顶层 supervisor 管理各小队。
```text
                [顶层 Supervisor]
                 ╱            ╲
        [研究队 Sup]         [写作队 Sup]
         ╱      ╲             ╱      ╲
     [检索]   [核实]      [撰写]   [校对]
```
层级化本质是「把 Supervisor 递归地套一层」，用分治来控制单个 supervisor 的认知负荷。它的代价是链路更深、复合错误环数更多，因此只在「小队数量多到单 supervisor 管不过来」时才引入——这又回到第 01 小节「能少一层就少一层」的原则。

## 生产踩坑

| 症状 | 根因 | 如何观测与复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| 对等网络里 Agent 反复互相调用 | Network 无中心、次序不定 | 回放交互图看是否有环 | 改用 Supervisor 集中决策，或给 Network 加收敛条件 | 探索型任务允许有限迭代 |
| 单 supervisor 决策质量下降 | Agent 太多、supervisor 上下文过载 | 统计 supervisor 分派准确率随 Agent 数变化 | 层级化：拆成小队+顶层 supervisor | 小队数少时不必分层 |
| 流水线中途失败全链重跑 | Sequential 无检查点 | 注入某阶段异常观察 | 每阶段存检查点，失败从该阶段恢复 | 阶段极短时重跑成本可忽略 |
| 高风险动作在对等网络里无人把关 | 控制权分散、护栏无处集中 | 审计谁触发了敏感动作 | 把高风险环节切到 Supervisor 集中审核 | 只读任务风险低 |

## 思考：Supervisor(tool-calling) 和普通 Supervisor 有什么区别？

### 回答

普通 Supervisor 把子 Agent 建模成**图节点**，用 `Command` 显式地把控制权路由到某个节点，路由逻辑可以是结构化输出里的 `next_agent` 字段；Supervisor(tool-calling) 则把每个子 Agent 包装成一个**工具**，让一个会调用工具的 LLM 在 while 循环里决定调哪个工具、传什么参数，直到它决定停止 [来源](https://langchain-ai.github.io/langgraph/concepts/multi_agent/)。前者控制流更显式、更易可视化与加护栏；后者复用了成熟的工具调用机制、实现最省事，但「子 Agent=工具」这层抽象会让控制流藏在模型的工具选择里，调试时要额外记录每次工具调用。两者都是 Supervisor 拓扑，区别只在「路由是显式的图边，还是隐式的工具调用」。

### 面试精简表达

都是中心编排：普通 Supervisor 用图边显式路由，tool-calling Supervisor 把子 Agent 当工具、用 LLM 的工具调用隐式路由。前者好审计，后者好实现。

## 机制推导：从"控制权流动"反推拓扑选型

选拓扑不必背场景表，只要回答三个关于控制权的问题就能收敛。第一，**下一步该由谁决定？** 如果必须由一个中心统一决定（为了审计、为了统一质量），选 Supervisor；如果可以让当前 Agent 自主决定、追求灵活，选 Network；如果每一步都能提前写死，选 Sequential。第二，**结果要不要集中把关？** 需要统一综合与护栏的，控制权必须回到中心，这只有 Supervisor 天然满足；Network 的结果分散在各 Agent，Sequential 的结果沿传送带流动，两者要额外加把关点。第三，**能不能并行？** Supervisor 可以一次分派多个 worker 做 map-reduce，Network 的并行取决于设计，Sequential 本质串行、并行度最低。

把三个问题的答案组合起来，选型几乎是确定的：需要审计 + 可并行 + 高价值 → Supervisor/层级；灵活流转 + 无清晰层级 → Network；阶段清晰 + 后依赖前 → Sequential。现实里最稳的往往是混合：顶层用 Sequential 或 Supervisor 做主干，某个需要并行发散的阶段内部再嵌一层 Supervisor。**拓扑的本质是控制权的形状，先想清控制权怎么流，图就画出来了。**
