## 真实问题

前三节把「何时拆、怎么连、怎么传」讲清楚了，但真正的问题是：一个生产级的编排者-工作者（orchestrator-worker）系统，从原型到上线到底要过哪些坎？Anthropic 在 2025 年 6 月公开了《How we built our multi-agent research system》，把他们做 Research 功能踩过的坑与提炼的原则完整写了出来 [来源](https://www.anthropic.com/engineering/multi-agent-research-system)。这一节就以它为主线，把编排者-工作者从「架构图」拆到「能落地的工程细节」。

需要强调本节的可信度边界：以下所有关于 Research 系统的行为，都是 Anthropic **官方公开机制**——博客明确写出的外部行为与设计原则；从中提炼的做法属于**通用工程模式**；而具体的 token 数字、subagent 数量随任务变化，会变化的部分以其当前官方页面为准。本节不反推任何未公开的内部调度算法。

## 原理：一个编排者，一群并行子智能体

Anthropic 的 Research 系统采用编排者-工作者架构：一个 LeadResearcher（主导研究 Agent）协调整个流程，把工作委派给并行运行的专业化 Subagent（子智能体）[来源](https://www.anthropic.com/engineering/multi-agent-research-system)。完整工作流可以拆成六个阶段，每一步都能对应到前几节的抽象概念：
```text
用户查询
  │
  ▼
[LeadResearcher] ①分析查询、制定策略
  │              ②把研究计划写入 Memory 持久化（防止上下文超 200k 被截断丢计划）
  │
  ├─③派生若干带明确任务的 Subagent（数量随复杂度缩放）
  │      ▼            ▼            ▼
  │  [Subagent1]  [Subagent2]  [Subagent3]   各自独立上下文、独立搜索、interleaved thinking 评估结果
  │      └────────────┼────────────┘
  │                   ▼
  ├─④LeadResearcher 综合子智能体的发现，判断是否还需要更多研究
  │      需要 → 回到 ③（再派生 subagent 或调整策略）
  │      够了 → 退出研究循环
  │                   ▼
  ├─⑤[CitationAgent] 处理文档与研究报告，定位每条主张对应的引用来源
  │                   ▼
  └─⑥带引用的最终结果返回用户
```
这张流程图里藏着四个关键设计，全部有公开出处：

第一，**主导 Agent 先规划、把计划存入 Memory**。Anthropic 明确写道：因为上下文窗口超过 20 万 token 就会被截断，而保留研究计划很重要，所以 LeadResearcher 会先把计划写进 Memory 持久化 [来源](https://www.anthropic.com/engineering/multi-agent-research-system)。这正是第 03 节「大块产物走外部存储」的具体落地——计划是必须存活的硬信息，不能任由上下文滚动冲掉。

第二，**子智能体是「并行的压缩器」**。Anthropic 把搜索的本质概括为「压缩」：从海量语料里蒸馏洞见。子智能体各自拥有独立的上下文窗口，并行探索问题的不同侧面，再把最重要的 token 浓缩后交回主导 Agent；每个子智能体还提供了关注点分离——不同的工具、提示与探索轨迹，降低路径依赖 [来源](https://www.anthropic.com/engineering/multi-agent-research-system)。这就是第 05 节 demo 里「每个 worker 把多条原文压缩成一句结论回传」的思想来源。

第三，**动态多步搜索，而非静态 RAG**。Anthropic 特别对比了传统检索增强生成（Retrieval-Augmented Generation，RAG）：RAG 是静态检索——取与查询最相似的若干块，直接生成回答；而他们的架构用多步搜索动态地发现相关信息、根据新发现调整、分析结果再形成高质量答案 [来源](https://www.anthropic.com/engineering/multi-agent-research-system)。这解释了「为什么开放式研究适合多智能体」：路径无法预先写死。

第四，**归因是独立一环**。信息够了之后，系统把全部发现交给 CitationAgent，由它定位每条主张该引用哪个来源，确保所有断言都能追溯到出处 [来源](https://www.anthropic.com/engineering/multi-agent-research-system)。把「归因」拆成独立 Agent，是把「可追溯性」做成了架构约束，而不是指望主导 Agent 顺手带上。

## 现象与输入：为什么 token 花得值

Anthropic 给了一组可核验的数字，把「多智能体为什么有效」量化了。在 BrowseComp 评测里，三个因素解释了 95% 的性能方差，其中**仅 token 用量本身就解释了 80%**，另外两个是工具调用次数与模型选择 [来源](https://www.anthropic.com/engineering/multi-agent-research-system)。这条发现验证了他们的架构选择：把工作分散到拥有独立上下文窗口的多个 Agent，能为并行推理增加容量。

代价也写得很直白：Agent 大约比对话多用 4 倍 token，多智能体系统大约比对话多用 15 倍 token [来源](https://www.anthropic.com/engineering/multi-agent-research-system)。所以经济可行性要求任务价值足够高，能为提升的性能买单。
```text
token 用量解释 80% 性能方差 → 多智能体的收益本质是"花得起更多 token 做并行推理"
Agent ≈ 4× 对话 token
多智能体 ≈ 15× 对话 token
结论：只有高价值、可并行、超单一上下文的任务才划算
```
## 最小可运行演示：把「按复杂度缩放」写成显式规则

Anthropic 记录的一个高频早期失败是：Agent 难以为不同任务判断合适的投入，会为简单查询也生成 50 个子智能体。他们的解法是**把缩放规则直接嵌进提示**：简单事实查找只用 1 个 Agent、3 到 10 次工具调用；直接比较用 2 到 4 个子智能体、每个 10 到 15 次调用；复杂研究才用 10 个以上子智能体、职责清晰划分 [来源](https://www.anthropic.com/engineering/multi-agent-research-system)。下面把这条公开的启发式复述成一个可运行的确定性函数（教学复述，非其源码）：
```python
def plan_effort(query_type: str) -> dict:
    """把 Anthropic 公开的"按复杂度缩放投入"启发式写成显式规则（教学复述，非其源码）。"""
    rules = {
        "fact": {"subagents": 1, "calls_each": (3, 10)},
        "compare": {"subagents": 3, "calls_each": (10, 15)},
        "deep": {"subagents": 10, "calls_each": (15, 30)},
    }
    return rules.get(query_type, {"subagents": 1, "calls_each": (3, 10)})


def main() -> None:
    for q in ["fact", "compare", "deep"]:
        print(q, "->", plan_effort(q))


if __name__ == "__main__":
    main()
```
保存为 `effort.py`，运行 `python effort.py`，预期输出：
```text
fact -> {'subagents': 1, 'calls_each': (3, 10)}
compare -> {'subagents': 3, 'calls_each': (10, 15)}
deep -> {'subagents': 10, 'calls_each': (15, 30)}
```
这段代码的价值不在算法，而在把「投入多少」从模型的自由发挥变成一条可审计的规则。它直接回答了第 01 节「不要过早多智能体」的落地问题：与其禁止多智能体，不如给主导 Agent 一把「按复杂度分配资源」的尺子。

## 编排者如何教会子智能体干活

Anthropic 花了大量篇幅讲「主导 Agent 怎么委派」，因为这是编排者-工作者最容易翻车的地方。他们的核心原则是：**每个子智能体都需要一个目标、一种输出格式、关于用哪些工具和来源的指引、以及清晰的任务边界**；缺少详细任务描述时，Agent 会重复劳动、留下空白、或找不到必要信息 [来源](https://www.anthropic.com/engineering/multi-agent-research-system)。

他们举了一个具体反例：早期允许主导 Agent 只给「research the semiconductor shortage（研究半导体短缺）」这类简短指令，结果指令太模糊，子智能体误解任务、或做了和其他 Agent 完全相同的搜索——一个子智能体去查 2021 年的汽车芯片危机，另外两个却重复调查 2025 年的当前供应链，缺乏有效分工 [来源](https://www.anthropic.com/engineering/multi-agent-research-system)。

把这条经验提炼成一个「子任务规格」清单，正是第 05 节 `SubTask` 数据类的设计依据：

| 子任务规格字段 | 缺失时的后果 | 对应 demo 字段 |
|---|---|---|
| 目标（objective） | 子智能体误解任务方向 | `objective` |
| 输出格式 | 主流程无法聚合、收到自由文本 | `conclusion`+`evidence`+`confidence` 契约 |
| 工具与来源指引 | 在错误的地方搜索（如去 web 找只在 Slack 的信息） | 语料主题标签 `topic` |
| 任务边界 | 多个子智能体重复劳动 | 一个 `topic` 只分派给一个 `worker` |

Anthropic 还总结了几条并行化与提示原则：主导 Agent 一次并行拉起 3 到 5 个子智能体、每个子智能体并行用 3 个以上工具，把复杂查询的研究时间最多缩短 90%；用扩展思考（extended thinking）作为可控草稿纸来规划；以及「先宽后窄」的搜索策略——先短查询铺开、评估、再逐步收窄 [来源](https://www.anthropic.com/engineering/multi-agent-research-system)。这些都指向同一件事：**编排者的提示不是一堆命令，而是一套「分工、方法、投入预算」的协作框架**。

## 真实系统对应

**官方公开机制**：Anthropic Research 采用 orchestrator-worker 架构，LeadResearcher 规划并把计划写入 Memory、并行派生 Subagent、综合结果、再交 CitationAgent 归因；公开了 token 解释 80% 方差、多智能体≈15× 对话 token、并行化最多省 90% 时间、按复杂度缩放的子智能体数与调用次数等数字 [来源](https://www.anthropic.com/engineering/multi-agent-research-system)。Anthropic 在《Building Effective Agents》里把编排者-工作者列为一种核心工作流：中心 LLM 动态分解任务、委派给工作者、再综合结果 [来源](https://www.anthropic.com/engineering/building-effective-agents)。**通用工程模式**：主导 Agent 给子任务写「目标+输出格式+工具指引+边界」四要素；按查询复杂度缩放投入；把归因、记忆做成独立环节。**教学参考实现**：`plan_effort` 只是把公开启发式写成规则，具体数字随任务变化，不代表 Claude 内部实现。

## 深入：把研究计划存进 Memory 意味着什么

很多人第一次读这套架构，会忽略「把计划写入 Memory」这一步的分量。它其实回答了一个多智能体特有的难题：**主导 Agent 自己也会上下文溢出**。研究一旦深入，主导 Agent 要综合越来越多子智能体的回传，对话历史迅速膨胀；一旦逼近上下文上限，最先被冲掉的往往是最早写下的「研究计划」——而这恰恰是整个任务的锚点。

Anthropic 的做法是把计划从「易失的对话」搬到「持久的外部记忆」：即便上下文被截断，主导 Agent 也能从 Memory 里取回计划，而不是丢掉之前的工作 [来源](https://www.anthropic.com/engineering/multi-agent-research-system)。他们在附录里进一步描述了长程对话管理：Agent 会在进入新任务前总结已完成阶段、把关键信息存入外部记忆；当上下文逼近上限，就派生带干净上下文的新子智能体，通过精心设计的交接保持连续性 [来源](https://www.anthropic.com/engineering/multi-agent-research-system)。

把这两点连起来看，编排者-工作者的「记忆层」其实承担了三件事：锚定不可丢的计划、承接跨阶段的中间结论、以及在上下文换代时充当交接介质。这也解释了为什么第 05 节的 demo 要给 Supervisor 一条显式的 `trace`——运行轨迹和外部记忆是同一个思路的两面：**让重要的东西活在对话之外**。

## 生产踩坑

| 症状 | 根因 | 如何观测与复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| 子智能体重复做同样的搜索 | 主导 Agent 委派指令太模糊、无边界 | 对比各子智能体的搜索查询是否雷同 | 给每个子任务写目标+输出格式+工具指引+边界 | 探索型任务允许少量重叠 |
| 简单查询也派生大量子智能体 | 未按复杂度缩放投入 | 统计每查询子智能体数与查询类型 | 在提示里嵌入缩放规则，简单事实用 1 个 | 高价值宽问题需要多个 |
| 主导 Agent 中途丢失研究计划 | 计划留在易失的对话里被截断 | 观察上下文接近上限后计划是否还在 | 把计划写入外部 Memory，超限时取回 | 短任务上下文充裕时可省 |
| 最终答案主张无法溯源 | 归因和生成混在一步 | 抽查断言能否对应到具体来源 | 拆出独立 CitationAgent 专做归因 | 内部草稿无需对外引用 |
| 子智能体在错误的地方搜索 | 未指定工具与来源 | 检查子任务是否声明数据源 | 明确「该用哪个工具、去哪找」 | 单一数据源任务无歧义 |

## 思考：编排者-工作者和普通的「函数调用子任务」区别在哪？

### 回答

表面上都是「一个主控调用若干下属」，但编排者-工作者的关键差异在于**子智能体是自主的、有独立上下文的 Agent，而不是一个确定性函数**。普通函数调用是「输入 X 必得输出 Y」，路径固定；而 Anthropic 强调，研究这类开放式问题无法预先写死步骤，过程本质是动态的、路径依赖的，子智能体要在多轮里自主决定搜哪里、怎么收窄 [来源](https://www.anthropic.com/engineering/multi-agent-research-system)。这带来两个工程后果：一是评测方式不同——即使起点相同，Agent 也可能走完全不同但都正确的路径，所以要评「是否达成了正确结果」而非「是否走了规定步骤」；二是分工必须显式——编排者要给每个子智能体写清目标、输出格式、工具指引和边界，否则就会重复劳动。把子智能体当自主 Agent 而非纯函数，是编排者-工作者区别于普通 map-reduce 的本质。

### 面试精简表达

编排者-工作者的下属是有独立上下文、能多轮自主决策的 Agent，不是确定性函数；因此要按「达成结果」而非「走对步骤」来评测，并且编排者必须给每个子任务写清目标、输出格式、工具与边界四要素。

## 思考：为什么 Anthropic 说「多数编码任务不适合多智能体」？

### 回答

因为编码任务与研究任务在「可并行性」和「依赖关系」上正相反。Anthropic 明确指出：需要所有 Agent 共享同一上下文、或 Agent 之间存在大量依赖的领域，目前不适合多智能体；多数编码任务包含的真正可并行子任务比研究少得多，而且 LLM Agent 目前还不擅长实时地互相协调与委派 [来源](https://www.anthropic.com/engineering/multi-agent-research-system)。研究之所以适合，是因为它天然可以「宽度优先」地并行探索多个独立方向，每个方向的中间发现互不阻塞；而写代码时，模块 A 的接口往往决定模块 B 怎么写，强依赖让并行退化成「等待+返工」。这也回扣第 01 节的判断：可分性（能切成各管一摊或可并行）是上多智能体的第二道关卡，编码任务常常卡在这一关。所以「适不适合多智能体」不看任务难度，而看任务能否被切成低耦合、可并行的子问题。

### 面试精简表达

研究可以宽度优先并行、子方向低耦合，所以适合多智能体；多数编码任务子任务强依赖、可并行度低，且 Agent 还不擅长实时协调，所以更适合共享上下文的单 Agent 或流水线。
