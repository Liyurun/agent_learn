## 真实问题

一个客服系统里，分诊 Agent 判断用户是技术故障，于是把对话转给技术 Agent，转交时只说了一句「帮这位用户看看」。技术 Agent 接手后一脸懵：用户是谁？什么设备？报错信息是什么？之前试过什么？它只好把用户已经说过三遍的信息重新问一遍。用户当场火了：「我刚才不是说过了吗？」

这次事故的根因不是模型能力，而是**通信设计**：交接时丢了上下文。多智能体系统里，「Agent 之间传什么、怎么传」和「每个 Agent 干什么」同等重要——分工定义了「谁负责什么」，通信定义了「信息如何在他们之间流动」。分工清晰但通信糟糕，照样体验崩坏。

## 原理

LangGraph 直言：**构建多智能体系统时最重要的事，就是搞清楚 Agent 之间如何通信** [来源](https://langchain-ai.github.io/langgraph/concepts/multi_agent/)。它把通信问题拆成几个关键子问题：Agent 之间是通过 handoff（交接）还是 tool call（工具调用）通信？一个 Agent 传给下一个的「载荷（payload）」是什么？如何在消息列表里表示一次交接？子 Agent 的状态怎么管理？

据此可以归纳出三种通信机制，它们是「解耦程度」和「共享便利」之间的取舍：

- **消息传递（Message Passing）**：Agent 之间直接收发结构化消息，类似 actor 模型。LangGraph 指出，最常见的通信方式就是通过一个共享的消息列表通道 [来源](https://langchain-ai.github.io/langgraph/concepts/multi_agent/)。AutoGen 的 `RoundRobinGroupChat` 走到极致：所有 Agent 共享同一份上下文、轮流发言，每个 Agent 发言都会广播给其他所有 Agent，从而保持一致的上下文 [来源](https://microsoft.github.io/autogen/stable/user-guide/agentchat-user-guide/tutorial/teams.html)。
- **共享黑板（Shared State / Blackboard）**：多个 Agent 读写同一份共享状态对象，把中间结果写到公共「黑板」，其他 Agent 从中读取。CrewAI 的 Sequential 流程正是让「一个任务的输出作为下一个任务的上下文」，通过 `context` 参数显式指定 [来源](https://docs.crewai.com/en/concepts/processes)。
- **交接（Handoff）**：一个 Agent 把控制权连同载荷移交给另一个 Agent。LangGraph 定义 handoff 需要两样东西——`destination`（目标 Agent）和 `payload`（要传递的信息，如状态更新）；在图里通过返回 `Command` 对象同时完成「控制流跳转」和「状态更新」，也可以把 handoff 包装成一个返回 `Command` 的工具 [来源](https://langchain-ai.github.io/langgraph/concepts/multi_agent/)。

## 现象与输入

交接失败的核心是「载荷太瘦」。对比两种交接载荷：
```text
坏交接：payload = "帮用户 U-9 处理问题"        → 接管者不知道问题是什么，重新盘问
好交接：payload = {用户, 已确认问题, 已尝试方案, 历史} → 接管者无缝续上
```
黑板则解决另一类问题：让多个 Agent 把各自的中间结论沉淀到一处，避免通过冗长对话「口口相传」导致失真。

## 最小可运行演示
```python
from dataclasses import dataclass, field


@dataclass
class HandoffPacket:
    user_id: str
    confirmed_problem: str = ""
    tried: list[str] = field(default_factory=list)

    def render(self) -> str:
        return (f"用户={self.user_id} 已确认问题={self.confirmed_problem} "
                f"已尝试={self.tried or '无'}")


class Blackboard:
    def __init__(self) -> None:
        self.notes: dict[str, str] = {}

    def write(self, key: str, value: str) -> None:
        self.notes[key] = value

    def read(self, key: str) -> str:
        return self.notes.get(key, "<空>")


def main() -> None:
    packet = HandoffPacket("U-9", "支付回调超时", ["重试", "换网关"])
    print("交接包:", packet.render())
    bb = Blackboard()
    bb.write("root_cause", "回调地址被防火墙拦截")
    print("黑板读取:", bb.read("root_cause"))
    print("黑板缺失:", bb.read("unknown"))


if __name__ == "__main__":
    main()
```
保存为 `comm.py`，运行 `python comm.py`，预期输出：
```text
交接包: 用户=U-9 已确认问题=支付回调超时 已尝试=['重试', '换网关']
黑板读取: 回调地址被防火墙拦截
黑板缺失: <空>
```
`HandoffPacket` 把「接管者必须知道的信息」显式列成字段——身份、已确认问题、已尝试方案。`tried` 尤其重要：它能阻止接管者「重复建议一个已试过没用的方案」，这是客服体验的高频雷区。`Blackboard` 演示了共享状态的两个基本操作：写入结论、按键读取，缺失时返回明确的 `<空>` 而不是崩溃或猜测。

## 三种通信机制的权衡

| 通信机制 | 比喻 | 优点 | 缺点 | 适合 |
|---|---|---|---|---|
| 消息传递 | 打电话/发消息 | 高度解耦、无竞态 | 要显式设计消息协议 | 职责清晰、交互点明确 |
| 共享黑板 | 共用一块白板 | 共享数据方便、结果逐步累积 | 竞态、一致性难保证 | 少量 Agent、读多写少 |
| 交接 | 接力赛交棒 | 控制权自然流转、可完整接管 | 载荷设计不当就丢上下文 | 对话式、问题在专长间流转 |

核心经验：**优先用消息传递解耦，慎用共享黑板**。共享状态越多，竞态、脏读、难复现的 bug 就越多；如果非用不可，就设计成「读多写少」并对写操作加同步。交接则要把载荷**结构化成显式契约**，而不是让接管者从一段自由文本里猜。

## 真实系统对应

**官方公开机制**：LangGraph 定义 handoff 的 `destination` + `payload`，并给出「handoff as tool」的 `Command` 代码；指出最常见通信方式是共享消息列表通道 [来源](https://langchain-ai.github.io/langgraph/concepts/multi_agent/)。AutoGen 的 `RoundRobinGroupChat` 让所有 Agent 共享上下文、轮流广播；`Swarm` 用 `HandoffMessage` 表示 Agent 间的转移 [来源](https://microsoft.github.io/autogen/stable/user-guide/agentchat-user-guide/tutorial/teams.html)。CrewAI 用 `context` 参数把上一任务输出作为下一任务上下文 [来源](https://docs.crewai.com/en/concepts/processes)。**通用工程模式**：用「解耦度 vs 共享便利」三选一，交接必须携带结构化载荷。**教学参考实现**：`HandoffPacket`/`Blackboard` 是演示，不代表任何框架内部数据结构。

## 深入：Anthropic 如何避开"传话游戏"

Anthropic 在附录里公开了一个精妙的通信优化，叫「避免传话游戏（game of telephone）」：与其要求子 Agent 把所有结果都经由主导 Agent 转述，不如让子 Agent 直接把产物写入外部文件系统，再把一个**轻量引用**传回协调者 [来源](https://www.anthropic.com/engineering/multi-agent-research-system)。这样做有两个好处：一是防止多级处理中的信息损失（每转述一次就失真一次，正是「传话游戏」的由来）；二是减少把大块输出反复复制进对话历史带来的 token 开销。对代码、报告、数据可视化这类结构化产物尤其有效，因为子 Agent 的专用提示产出的质量，往往比经过通用协调者过滤后更好。

这条经验把「消息传递」和「共享黑板」融合了：控制信令（轻量引用）走消息传递、保持解耦；大块产物走外部存储（一种持久化黑板），避免污染对话。它也解释了为什么在长对话里，Anthropic 让 Agent「先把已完成阶段总结、把关键信息存入外部记忆，再继续新任务」，并在上下文接近上限时「派生带干净上下文的新子 Agent，通过精心设计的交接保持连续性」[来源](https://www.anthropic.com/engineering/multi-agent-research-system)。

## 生产踩坑

| 症状 | 根因 | 如何观测与复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| 接管者重新盘问用户 | handoff 载荷太瘦、丢上下文 | 打印交接 payload 字段 | 用结构化交接包（身份/已确认问题/已尝试） | 全新会话本无上下文 |
| 多 Agent 写黑板互相覆盖 | 共享状态并发写、无同步 | 并发写同一键复现脏写 | 设计成读多写少、对写加锁或分键 | 单写者场景无竞态 |
| 转述几轮后结论失真 | 走"传话游戏"式层层转述 | 对比原始产物与转述版 | 子 Agent 产物写外部存储、只回传引用 | 极短结论直接回传即可 |
| 广播式群聊 token 爆炸 | 所有 Agent 共享全上下文互相广播 | 统计每轮广播消息量 | 只广播必要摘要、或改用点对点消息 | 小团队短对话可接受 |
| 接管者重复已失败方案 | 交接未带"已尝试"字段 | 检查 payload 是否含 tried | 交接包强制包含已尝试方案列表 | 首次接管无历史尝试 |

## 思考：交接（handoff）和工具调用（tool call）到底差在哪？

### 回答

差在**控制权是否转移**。工具调用是「A 调用 B、B 返回结果、A 继续主导」——控制权像回旋镖，去了还回来，B 从不直接面对用户，这也是编排者-工作者与 Supervisor(tool-calling) 的基础。交接是「A 把对话连同载荷移交给 B、A 退场、B 接管」——控制权像接力棒，交出去就不回来，B 可以直接回复用户甚至再交给 C。LangGraph 把两者统一在 `Command` 里：普通工具调用只更新状态，handoff 工具在更新状态之外还带上 `goto` 指定跳转目标 [来源](https://langchain-ai.github.io/langgraph/concepts/multi_agent/)。混淆这一点，就没真正理解去中心化——很多人以为 handoff 就是「A 调用 B」，其实前者控制权不转移、后者转移。

### 反例

不要把「整段对话历史原样塞进 payload」当成安全做法。历史太长会稀释接管者的注意力、抬高成本，还可能把过期信息带进来。更好的做法是**既给结构化摘要（confirmed_problem、tried），又保留必要的原始片段**：摘要让接管者快速抓重点，原始片段留作追溯。这也呼应上下文工程的思想——交接不是「传得越多越好」，而是「传得刚好且可追溯」。

## 角色分工的三种粒度

分工不是「越细越好」，而是要匹配任务结构。第一种是**按领域分工**：退款、技术、闲聊各一个 Agent，边界是业务域，适合职责天然可切开的场景，交接沿业务流转发生。第二种是**按能力分工**：规划者、检索者、写作者、审核者，边界是认知职能，适合流水线或编排者-工作者，一个复杂任务被拆成「想—查—写—审」四种能力。第三种是**按视角分工**：同一任务让多个 Agent 从不同角度并行处理再投票或综合，Anthropic 的并行子 Agent、AutoGen 的 primary+critic 反思模式都属于此类——AutoGen 的两 Agent 团队让 critic 反复给 primary 反馈、直到它回复 `APPROVE` 才终止 [来源](https://microsoft.github.io/autogen/stable/user-guide/agentchat-user-guide/tutorial/teams.html)。

三种粒度对应不同的通信默认值：按领域分工天然配交接（控制权随业务流转移），按能力分工天然配流水线的黑板传递（前一环产物喂给后一环），按视角分工天然配消息传递或共享上下文的群聊（多方各自发言再综合）。选错组合会别扭：给按视角分工的并行 Agent 强行套交接，就会退化成串行；给按领域分工的客服强行套全广播群聊，就会 token 爆炸。**先想清分工粒度，通信机制往往就跟着定了。**
