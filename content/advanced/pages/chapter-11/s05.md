## 真实问题

前面四节讲了「何时拆、拓扑、通信、编排者-工作者」，但读者最容易卡在一句话上：「道理我都懂，代码到底长什么样？」很多教程给的多智能体示例要么依赖某个框架、要么需要 API Key、要么输出不确定无法复核，读者跑不起来也就没法真正理解。本节给一个**完全离线、纯 Python 标准库、无需 API Key、结果确定性可复核**的编排者-工作者实现：一个 Supervisor 把宽问题分解成子任务、分派给多个 Worker、聚合结构化结论，并留下可审计的运行轨迹（trace）。

工程边界要先说清：这是**教学参考实现**，用「本地语料检索」模拟子智能体的「web 搜索」，用「独立 search_log」模拟子智能体的「独立上下文窗口」，用「离线估算」模拟 token 计数。它复刻的是 Anthropic 编排者-工作者的**公开机制**（分解、并行、压缩回传、聚合、可观测），不代表任何产品的内部源码，token 数字也不用于核对真实账单。

## 工程结构

整个 demo 是单文件、零第三方依赖，核心是三个数据类和两个角色类：
```text
multi_agent_demo.py
├── CORPUS               # 10 篇带主题标签的本地文档，2 篇标记 relevant=False（噪声）
├── estimate_tokens()    # 离线 token 估算，仅用于成本演示
├── TraceEvent           # 运行轨迹事件：trace_id/hop/agent/action/tool_calls/tokens/note
├── WorkerResult         # 子智能体回传的结构化契约：conclusion/evidence/confidence
├── SubTask              # 子任务规格：worker/topic/objective（对应第04节的四要素）
├── Worker               # 工作者：独立 search_log、按主题检索、压缩成结论
└── Supervisor           # 编排者：plan 分解 / dispatch 分派 / synthesize 聚合 + 轨迹
```
这个结构刻意对齐第 04 节从 Anthropic 提炼的设计：`SubTask` 携带目标与边界（防止重复劳动）、`WorkerResult` 是固定契约（防止主流程收到无界噪声）、`Supervisor.trace` 承担可观测性（对应「加全链路追踪才能定位失败」）。

## 安装与运行

无需安装任何依赖，Python 3.10 及以上即可：
```bash
python multi_agent_demo.py
```
预期输出的关键不变量（绝对数字随文本微调，但结构与判定必须成立）：
```text
worker_count = 5           # 5 个子任务各派一个 worker
accepted_topics = [supervisor, worker, cost, reliability]  # 4 个有效主题被采纳
dropped_topics = [noise]   # 噪声主题因命中 0 条、置信度 0.0 被自动丢弃
total_tool_calls = 50      # 5 个 worker 各扫描 10 篇文档
hops = 7                   # 1 次 plan + 5 次 search + 1 次 synthesize
```
## 阶段 1：语料与 token 估算

先定义本地语料库。10 篇短文档各带一个 `topic` 主题标签和一个 `relevant` 布尔位，其中 `noise` 主题的两篇被标记为 `relevant=False`，模拟「无关闲聊」与「过期旧版本」这两类必须被排除的干扰。`estimate_tokens` 用一个朴素规则离线估算 token：非 ASCII 字符（含中文）按 1 个计，ASCII 每 4 个约 1 个——它只用于成本演示，绝不等于真实账单。
```python
from __future__ import annotations

import json
from dataclasses import dataclass

CORPUS: dict[str, dict] = {
    "doc-01": {"topic": "supervisor", "relevant": True, "text": "编排者负责把宽问题分解成明确子任务并分派。"},
    "doc-02": {"topic": "supervisor", "relevant": True, "text": "编排者给每个子任务写清目标、输出格式与边界。"},
    "doc-03": {"topic": "worker", "relevant": True, "text": "工作者拥有独立上下文窗口，并行探索不同侧面。"},
    "doc-04": {"topic": "worker", "relevant": True, "text": "工作者把大量原文压缩成少量高价值结论回传。"},
    "doc-05": {"topic": "cost", "relevant": True, "text": "多智能体消耗的 token 显著高于单轮对话，需要价值足够高的任务。"},
    "doc-06": {"topic": "cost", "relevant": True, "text": "并行分派能把长任务的墙钟时间大幅缩短。"},
    "doc-07": {"topic": "reliability", "relevant": True, "text": "有状态的长任务错误会累积，需要检查点与重试。"},
    "doc-08": {"topic": "reliability", "relevant": True, "text": "子任务返回结构化契约，避免主流程收到无界噪声。"},
    "doc-09": {"topic": "noise", "relevant": False, "text": "无关的市场闲聊，不应进入任何子任务结论。"},
    "doc-10": {"topic": "noise", "relevant": False, "text": "过期的旧版本说明，仅供审计不应污染当前答案。"},
}


def estimate_tokens(text: str) -> int:
    """离线 token 估算：非 ASCII（含中文）按 1 个，ASCII 每 4 个约 1 个。仅用于成本演示，不等于真实账单。"""
    non_ascii = sum(1 for ch in text if ord(ch) > 127)
    ascii_count = len(text) - non_ascii
    return non_ascii + (ascii_count + 3) // 4
```
## 阶段 2：数据契约

三个数据类把「运行轨迹」「子智能体回传」「子任务规格」都变成显式结构。`WorkerResult` 是最关键的一个——它把子智能体的输出固定成 `conclusion`（结论）、`evidence`（证据）、`confidence`（置信度）三个字段，这正是第 04 节强调的「输出格式」，让主流程有稳定的聚合依据，而不是收到一段自由文本。
```python
@dataclass
class TraceEvent:
    trace_id: str
    hop: int
    agent: str
    action: str
    tool_calls: int
    tokens: int
    note: str


@dataclass
class WorkerResult:
    worker: str
    topic: str
    conclusion: str
    evidence: list[str]
    confidence: float
    tool_calls: int
    tokens: int


@dataclass
class SubTask:
    worker: str
    topic: str
    objective: str
```
## 阶段 3：Worker（工作者）

Worker 模拟一个拥有**独立上下文**的子智能体：它有自己的 `search_log`（对应独立上下文窗口），只检索分配给它的主题，并且**只采纳 `relevant=True` 的文档**——两篇噪声文档因此被自然过滤。它扫描全部 10 篇文档（`tool_calls` 累加，模拟工具调用成本），把命中的原文压缩成一句 `conclusion`，并按命中数算出 `confidence`（命中 2 条即满信心 1.0，命中 0 条则 0.0）。
```python
class Worker:
    """工作者：拥有独立 search_log（独立上下文），只按分配主题检索并压缩结论。"""

    def __init__(self, name: str) -> None:
        self.name = name
        self.search_log: list[str] = []

    def run(self, task: SubTask) -> WorkerResult:
        hits: list[str] = []
        tool_calls = 0
        for doc_id, doc in CORPUS.items():
            tool_calls += 1
            if doc["topic"] == task.topic and doc["relevant"]:
                self.search_log.append(doc_id)
                hits.append(doc["text"])
        conclusion = f"关于「{task.topic}」共命中 {len(hits)} 条要点"
        tokens = estimate_tokens(conclusion) + sum(estimate_tokens(h) for h in hits)
        confidence = round(min(1.0, len(hits) / 2.0), 2)
        return WorkerResult(self.name, task.topic, conclusion, hits, confidence, tool_calls, tokens)
```
## 阶段 4：Supervisor（编排者）

Supervisor 实现编排者-工作者的三步骨架，每一步都写入 `trace`：

- `plan`：把宽问题按显式给定的主题列表切成子任务。主题数由调用方传入而非模型自由发挥，这正是第 04 节「按复杂度缩放、不要为简单查询派生 50 个子智能体」的落地——把「派几个」变成可控参数。
- `dispatch`：逐个运行 worker，记录每一跳的工具调用数、token、置信度。这里用顺序执行模拟并行分派；真实系统会并发，但轨迹语义一致。
- `synthesize`：**只采信置信度达标（≥0.5）的子结论**，噪声主题因命中 0 条、置信度 0.0 被自动排除，并在轨迹里显式记下「采纳了谁、丢弃了谁」。
```python
class Supervisor:
    """编排者：分解问题、分派给多个 worker、聚合结构化结论、维护运行轨迹。"""

    def __init__(self, trace_id: str) -> None:
        self.trace_id = trace_id
        self.trace: list[TraceEvent] = []
        self._hop = 0

    def _record(self, agent: str, action: str, tool_calls: int, tokens: int, note: str) -> None:
        self._hop += 1
        self.trace.append(TraceEvent(self.trace_id, self._hop, agent, action, tool_calls, tokens, note))

    def plan(self, question: str, topics: list[str]) -> list[SubTask]:
        """分解：按主题把宽问题切成各管一摊的子任务，主题数由调用方显式给定，避免过度分派。"""
        tasks = [
            SubTask(f"worker-{i + 1}", topic, f"检索并压缩「{topic}」相关证据")
            for i, topic in enumerate(topics)
        ]
        self._record("supervisor", f"plan:{question}", 0,
                     estimate_tokens(question), f"分解为 {len(tasks)} 个子任务")
        return tasks

    def dispatch(self, tasks: list[SubTask]) -> list[WorkerResult]:
        results: list[WorkerResult] = []
        for task in tasks:
            result = Worker(task.worker).run(task)
            self._record(task.worker, f"search:{task.topic}", result.tool_calls,
                         result.tokens, f"confidence={result.confidence}")
            results.append(result)
        return results

    def synthesize(self, question: str, results: list[WorkerResult]) -> dict:
        """聚合：只采信可信度达标（>=0.5）的子结论，噪声主题因命中过少被自动排除。"""
        accepted = [r for r in results if r.confidence >= 0.5]
        dropped = [r.topic for r in results if r.confidence < 0.5]
        lines = [f"- {r.topic}: {r.conclusion}（置信度 {r.confidence}）" for r in accepted]
        answer = f"针对「{question}」聚合 {len(accepted)} 条可信子结论：\n" + "\n".join(lines)
        total_tokens = sum(r.tokens for r in results)
        total_calls = sum(r.tool_calls for r in results)
        self._record("supervisor", "synthesize", total_calls, estimate_tokens(answer),
                     f"采纳={len(accepted)} 丢弃={dropped}")
        return {
            "answer": answer,
            "accepted_topics": [r.topic for r in accepted],
            "dropped_topics": dropped,
            "worker_count": len(results),
            "total_tool_calls": total_calls,
            "total_worker_tokens": total_tokens,
            "hops": len(self.trace),
        }
```
## 阶段 5：编排入口与运行

`run` 把三步串起来，并把轨迹序列化进报告；`main` 打印答案、关键指标和逐跳轨迹。
```python
def run() -> dict:
    supervisor = Supervisor(trace_id="run-001")
    question = "多智能体协作的关键要点是什么"
    topics = ["supervisor", "worker", "cost", "reliability", "noise"]
    tasks = supervisor.plan(question, topics)
    results = supervisor.dispatch(tasks)
    report = supervisor.synthesize(question, results)
    report["trace"] = [
        {"hop": e.hop, "agent": e.agent, "action": e.action,
         "tool_calls": e.tool_calls, "tokens": e.tokens, "note": e.note}
        for e in supervisor.trace
    ]
    return report


def main() -> None:
    report = run()
    print(report["answer"])
    print("---")
    print(f"worker_count={report['worker_count']}")
    print(f"accepted_topics={report['accepted_topics']}")
    print(f"dropped_topics={report['dropped_topics']}")
    print(f"total_tool_calls={report['total_tool_calls']}")
    print(f"total_worker_tokens={report['total_worker_tokens']}")
    print(f"hops={report['hops']}")
    print("--- trace ---")
    for event in report["trace"]:
        print(json.dumps(event, ensure_ascii=False))


if __name__ == "__main__":
    main()
```

## 这个 demo 演示了什么，又不演示什么

它**演示**了编排者-工作者的五个可核验行为：一是**分解**——宽问题被切成 5 个各管一摊的子任务；二是**并行压缩**——每个 worker 独立扫描、把原文压缩成一句结论回传，对应 Anthropic「子智能体是并行压缩器」；三是**结构化契约**——回传固定为 `conclusion/evidence/confidence`，主流程据此聚合而非解析自由文本；四是**噪声自动排除**——`noise` 主题命中 0 条、置信度 0.0，被聚合阶段丢弃，证明「隔离+置信度门槛」能挡住无关信息；五是**可观测性**——7 跳轨迹带 `trace_id`、每跳的 agent、工具调用与 token，任何一步失败都能定位。

它**不演示**真实的 LLM 推理、真实的 web 搜索、真实的并发调度和真实 token 计费——这些在教学示例里被替换成确定性的本地逻辑，目的是让输出可复核。要接到真实系统，只需把 `Worker.run` 里的「本地检索」换成「LLM+工具调用」、把 `estimate_tokens` 换成供应商官方计数、把 `dispatch` 的顺序循环换成并发执行，骨架和轨迹语义都不用变。

## 真实系统对应

**官方公开机制**：demo 的「分解→并行子智能体→压缩回传→主导 Agent 聚合」映射 Anthropic Research 的 orchestrator-worker 流程 [来源](https://www.anthropic.com/engineering/multi-agent-research-system)；「子任务带目标与边界」「按显式主题数分派」对应其「教编排者委派」「按复杂度缩放」原则 [来源](https://www.anthropic.com/engineering/multi-agent-research-system)；编排者-工作者作为工作流模式见《Building Effective Agents》[来源](https://www.anthropic.com/engineering/building-effective-agents)。**通用工程模式**：结构化回传契约、置信度门槛过滤、全链路 trace。**教学参考实现**：`CORPUS`/`Worker`/`Supervisor` 都是为讲清机制构造的离线代码，不代表任何框架内部结构，token 数字不用于计费。

## 思考：为什么要给子智能体的回传加一个「置信度门槛」？

### 回答

因为编排者-工作者最危险的失败之一，是**主流程收到无界噪声后无法判断该不该采信**。如果 worker 只回传一段自由文本，Supervisor 就只能全盘接收，噪声主题的「无关闲聊」和「过期版本」会混进最终答案。demo 用两个机制挡住它：一是 Worker 内部只采纳 `relevant=True` 的文档（隔离），二是 Supervisor 在聚合时设 `confidence >= 0.5` 门槛（把关）。两者叠加，noise 主题命中 0 条、置信度 0.0，被自然丢弃，且轨迹里留下「丢弃=[noise]」的显式记录。这对应第 04 节从 Anthropic 提炼的「子任务返回结构化契约，避免主流程收到无界噪声」，也对应上下文工程里「宁可标注不确定，也不要把低质量信息当事实注入」。置信度门槛的本质是：**让编排者拥有拒绝的能力**，而不是被动接收一切回传。

### 面试精简表达

结构化契约让每条子结论带上置信度，编排者据此设门槛过滤低质量回传；配合子智能体内部的相关性过滤，就能在聚合阶段自动丢弃噪声，并在轨迹里留痕可审计。

## 思考：这个 demo 用顺序循环模拟并行，会不会误导对「并行」的理解？

### 回答

不会，只要说清「轨迹语义」和「墙钟时间」是两回事。demo 的 `dispatch` 用顺序 for 循环逐个跑 worker，是为了让输出确定、可复核；但它记录的轨迹语义——「5 个独立子任务、各自独立上下文、互不依赖」——和真正的并行完全一致，因为每个 worker 的结果只依赖自己的 `topic`，不依赖其他 worker，这正是「可并行」的判据。真实系统只要把顺序循环换成并发执行（线程池、异步或多进程），结果不变、但墙钟时间大幅缩短，对应 Anthropic「并行拉起 3 到 5 个子智能体、把研究时间最多缩短 90%」[来源](https://www.anthropic.com/engineering/multi-agent-research-system)。反过来说，如果 worker 之间有依赖（worker-2 要用 worker-1 的输出），那它本就不该并行，顺序循环反而是诚实的。所以判断能否并行，看的是「子任务之间有没有依赖」，而不是「代码写没写线程」。

### 面试精简表达

顺序循环只影响墙钟时间不影响结果，因为子任务互不依赖；轨迹语义已经是并行的，换成并发执行即可提速，这也正说明「可并行」取决于子任务是否解耦，而非实现细节。
