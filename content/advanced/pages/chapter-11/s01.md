## 真实问题

一个电商团队最初只有一个「全能客服 Agent」：系统提示里塞了退款政策、物流规则、技术排障手册、营销话术，工具集挂了退款、查单、重启服务、发短信、发邮件、查知识库等八个工具。上线两周后，指标很难看：退款场景里模型有时去调「重启服务」工具，技术故障里又误触「发优惠券」。团队一度以为是提示词写得不够好，反复润色到三千字，问题依旧。

回放发现，真正的瓶颈有两条。第一是**注意力稀释**：八个工具描述、四类政策手册同时进入一个上下文窗口，模型在「当前该用哪个工具」上的判断被大量无关信息干扰。第二是**职责纠缠**：退款是高风险动作需要严格审计，闲聊却要轻快自然，把两种截然不同的目标压进同一个系统提示，任何一处调整都会牵动另一处。这不是模型能力问题，而是「一个 Agent 承担了本该拆开的多种职责」。

## 原理

Anthropic 在《Building Effective Agents》里给出的第一原则是：**找到最简单的方案，只有在确有必要时才增加复杂度**；很多应用「优化单次 LLM 调用 + 检索 + 少量示例」就够了，不必上 Agent，更不必上多智能体 [来源](https://www.anthropic.com/engineering/building-effective-agents)。AutoGen 的团队教程也明确写道：**先用单 Agent，把工具和指令优化到位；只有当单 Agent 证明不够用时，再转向多 Agent 团队** [来源](https://microsoft.github.io/autogen/stable/user-guide/agentchat-user-guide/tutorial/teams.html)。LangGraph 的多智能体文档则从「症状」出发，列出三个应当考虑拆分的信号：单个 Agent 工具太多、选择困难；上下文太复杂，一个 Agent 跟不住；系统需要多个专业化领域（如规划者、研究者、数学专家）[来源](https://langchain-ai.github.io/langgraph/concepts/multi_agent/)。

把这些公开判断整理成一条可操作的决策链：
```text
需求来了
  │
  ├─ 单 Agent（精简提示 + 聚焦工具）真的搞不定吗？
  │     否 → 别拆，优化单 Agent（对齐 Anthropic/AutoGen 的"先简单"原则）
  │     是
  │     ▼
  ├─ 任务能被清晰地切成"各管一摊"的专业域或可并行子问题吗？
  │     否 → 拆了也是互相扯皮，先重新划分职责
  │     是
  │     ▼
  └─ 任务价值足够高，愿意承担"约15×token + 复合错误 + 调试变难"的代价吗？
        是 → 上多智能体
```
三道关卡对应三条核心判断：**必要性**（单 Agent 不行）、**可分性**（职责清晰或可并行）、**成本可承受**（价值高到能付代价）。Anthropic 的研究系统数据给了第三关一个硬约束：多智能体系统消耗的 token 大约是普通对话的 15 倍，因此「只有当任务价值足够高，能为提升的性能买单时，多智能体才具备经济可行性」；而且「需要所有 Agent 共享同一上下文、或 Agent 之间存在大量依赖」的领域（例如多数编码任务）并不适合多智能体 [来源](https://www.anthropic.com/engineering/multi-agent-research-system)。

## 现象与输入

把「工具越多、单 Agent 越难聚焦」这件事量化，可以用一个最朴素的均匀假设：如果一个 Agent 面前有 N 个工具、且没有任何先验偏好，那么它随机选中「正确工具」的概率是 1/N。这不是模型的真实行为（真实选择由工具描述质量与上下文决定），但它给出一个直觉下界：工具集从 2 个膨胀到 8 个，选中先验概率从 0.5 掉到 0.125。
```text
精简工具集：refund / lookup                → 正确工具先验 0.5
臃肿工具集：refund / lookup / diag / ...(8) → 正确工具先验 0.125
```
## 最小可运行演示
```python
def single_agent_focus(tools: list[str], relevant: str) -> dict:
    """单 Agent 工具越多，正确工具被选中的先验概率越低（均匀近似）。"""
    pick_prob = 1 / len(tools)
    return {"tool_count": len(tools), "relevant_tool": relevant,
            "uniform_pick_prob": round(pick_prob, 3)}


def main() -> None:
    lean = single_agent_focus(["refund", "lookup"], "refund")
    bloated = single_agent_focus(
        ["refund", "lookup", "diag", "restart", "kb", "ticket", "email", "sms"], "refund")
    print("精简:", lean)
    print("臃肿:", bloated)


if __name__ == "__main__":
    main()
```
保存为 `focus.py`，运行 `python focus.py`，预期输出：
```text
精简: {'tool_count': 2, 'relevant_tool': 'refund', 'uniform_pick_prob': 0.5}
臃肿: {'tool_count': 8, 'relevant_tool': 'refund', 'uniform_pick_prob': 0.125}
```
拆分的第一收益不是「多个大脑」，而是让每个 Agent 面对**更小的工具集与更聚焦的指令**。这也解释了为什么很多时候「把巨型单 Agent 按领域拆成两三个小 Agent」比「无脑加十个 Agent」更有效：前者直接提升了每一步的先验准确率，后者只是把复合错误链拉长。

## 真实系统对应

**官方公开机制**：Anthropic 明确指出多智能体擅长「可高度并行、信息超出单一上下文窗口、需要接入大量复杂工具」的高价值任务，而不适合强依赖、需共享同一上下文的任务（如多数编码）[来源](https://www.anthropic.com/engineering/multi-agent-research-system)。LangGraph 把「工具太多、上下文太复杂、需要多专业域」列为拆分信号 [来源](https://langchain-ai.github.io/langgraph/concepts/multi_agent/)。AutoGen 建议「先优化单 Agent 再上团队」[来源](https://microsoft.github.io/autogen/stable/user-guide/agentchat-user-guide/tutorial/teams.html)。**通用工程模式**：用「必要性/可分性/成本」三关做拆分前的守门。**教学参考实现**：上面的均匀先验只是直觉演示，不是任何模型的真实工具选择分布。

## 反面案例：不要过早多智能体

Anthropic 记录了早期版本的一个真实失败：Agent 会**为简单查询也生成 50 个子 Agent**、为不存在的信息在网上无休止搜索、彼此之间用过量更新互相干扰 [来源](https://www.anthropic.com/engineering/multi-agent-research-system)。它们后来在提示里嵌入「按查询复杂度缩放投入」的规则才收敛：简单事实查找只用 1 个 Agent、3 到 10 次工具调用；直接比较用 2 到 4 个子 Agent；复杂研究才用 10 个以上。这条经验对「过早多智能体」是当头一棒——**拆分不是免费的，过度分解会同时放大成本与协调复杂度**。

一个务实的顺序是：先把单 Agent 的工具描述、系统提示、少量示例打磨到位；再考虑「路由 + 少量专业 Agent」；只有当单一上下文确实装不下、或子问题天然可并行且价值很高时，才上完整的编排者-工作者多智能体。任何一步都要能回答「拆分带来的收益，是否盖过了 15× 的 token 成本与复合错误」。

## 生产踩坑

| 症状 | 根因 | 如何观测与复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| 单 Agent 频繁选错工具 | 工具集臃肿、注意力稀释 | 记录候选工具数与实际调用；把工具从 3 个加到 10 个复现 | 按领域拆分或做两阶段路由，缩小每步工具集 | 工具本就少时拆分无益 |
| 拆成多 Agent 后更慢更贵 | 过度分解、简单任务也并行 | 统计每查询子 Agent 数与总 token | 嵌入"按复杂度缩放投入"规则，简单查询用 1 个 | 高价值可并行任务例外 |
| 多 Agent 互相扯皮不收敛 | 职责边界模糊、可分性不足 | 回放交互看是否重复劳动 | 拆分前先把职责切成"各管一摊" | 探索型任务允许一定重叠 |

## 思考：为什么"能不用多智能体就不用"是成熟标志？

### 回答

因为多智能体的收益是「更大规模、更强并行、更清晰分工」，代价却是三重叠加的：token 成本（Anthropic 数据约 15× 对话）、复合错误（每多一环整体可靠性相乘衰减）、调试难度（控制权在多个 Agent 间跳转，需要跨 Agent 的链路追踪才能定位）。新手倾向于用架构复杂度证明自己「会」，而资深工程师先问「单 Agent 优化到位了吗、任务真能并行吗、价值撑得起成本吗」。能主动讲清「何时不该用」，说明判断力已经从「能搭多复杂」升级到「该搭多复杂」。

### 面试精简表达

多智能体不是能力勋章而是成本决策：先证明单 Agent 不行、任务可分、价值够高，三关都过才拆；否则一个精心设计的单 Agent 往往更快更稳更便宜。

## 事故回放：三千字系统提示救不了职责纠缠

回到开头的电商客服。团队第一反应是「提示词工程」，把系统提示从八百字扩到三千字，加了大量「退款时请务必先查政策」「技术故障请勿触发营销工具」之类的告诫。灰度一周，退款误触率只从 12% 降到 9%，闲聊场景的响应却因为提示太长明显变慢、变生硬。

根因分析把这次失败拆成两层。**注意力层**：三千字提示 + 八个工具描述让模型在每一步都要在大量文本里定位「当前任务相关的那一小块」，这正是长上下文里的干扰问题；**目标冲突层**：退款要「保守、可审计」，闲聊要「轻快、有人情味」，两种优化方向在同一提示里彼此拉扯，改好一个就拖垮另一个。真正的修复不是继续加字，而是**按职责拆分**：退款、技术、闲聊各自一个精简 Agent，前面加一个只做分类的路由。拆分后退款 Agent 的提示回落到六百字、只挂三个工具，误触率降到 1% 以下；闲聊 Agent 因为卸掉了政策包袱，响应又快又自然。

这个回放的价值在于：它证明「提示词润色」和「架构拆分」解决的是不同层次的问题。当失败来自职责纠缠与注意力稀释时，再漂亮的措辞也只是打补丁；把职责切开、让每个 Agent 面对更小的世界，才是根治。但要注意，这里拆的是「三个各管一摊的专业 Agent + 一个路由」，而不是「十个互相调用的 Agent」——前者提升每步先验，后者只会拉长复合错误链。这也自然引出下一节的问题：拆开之后，这些 Agent 该用什么拓扑组织起来。
