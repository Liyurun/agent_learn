## 真实问题

多智能体系统上线后，最折磨人的不是「跑不起来」，而是「跑起来了但时好时坏，出了错不知道是哪个 Agent 的锅」。Anthropic 直言：在传统软件里一个 bug 可能只是弄坏一个功能；但在 agentic 系统里，微小改动会级联成巨大的行为变化，这让「为必须长期维持状态的复杂 Agent 写代码」变得异常困难 [来源](https://www.anthropic.com/engineering/multi-agent-research-system)。本节系统梳理多智能体特有的三大失败模式——上下文丢失、无限对话、成本爆炸——并把它们对应到 AutoGen、CrewAI、LangGraph 的公开机制上，看成熟框架分别用什么手段防御。

## 原理：多智能体的失败是「相乘」的

单 Agent 的可靠性是一条时间线上的问题；多智能体的可靠性是**相乘**的。Anthropic 把这称为「错误的复合本质」：一步失败会让 Agent 探索完全不同的轨迹，导致不可预测的结果，传统软件里的小问题足以让 Agent 彻底脱轨 [来源](https://www.anthropic.com/engineering/multi-agent-research-system)。把它量化：假设每个 Agent 单独成功率 95%，串联 n 个后整体成功率是 0.95 的 n 次方。
```python
def chain_reliability(per_agent: float, n: int) -> float:
    return round(per_agent ** n, 4)


def main() -> None:
    for n in [1, 3, 5, 10, 20]:
        r = chain_reliability(0.95, n)
        print(f"n={n:>2} 整体成功率={r:.4f} 每100次失败≈{round((1 - r) * 100)}")


if __name__ == "__main__":
    main()
```
保存为 `reliability.py`，运行 `python reliability.py`，预期输出：
```text
n= 1 整体成功率=0.9500 每100次失败≈5
n= 3 整体成功率=0.8574 每100次失败≈14
n= 5 整体成功率=0.7738 每100次失败≈23
n=10 整体成功率=0.5987 每100次失败≈40
n=20 整体成功率=0.3585 每100次失败≈64
```
5 个 95% 的 Agent 串起来整体只剩 77%，10 个直接掉到 60%。这个数字解释了两件事：为什么「能少一个 Agent 就少一个」（每多一环打一次折），以及为什么多智能体「更」需要护栏与评估（要么提升单环成功率，要么减少串联环数）。缓解手段有三：**减少串联环数**（能并行别串行、能合并别拆分）、**提高单环可靠性**（每环加评估与重试）、**加护栏兜底**（关键环失败时降级或转人工）。

## 失败模式一：上下文丢失

第 03 节讲过交接丢上下文导致「接管者重新盘问」；在长程多智能体里，这个问题会升级成两种更隐蔽的形态。

第一种是**主导 Agent 自身的上下文溢出**。Anthropic 指出上下文窗口超过 20 万 token 会被截断，最先丢的往往是最早写下的研究计划；他们的防御是把计划写入 Memory 持久化，超限时再取回，而不是丢掉之前的工作 [来源](https://www.anthropic.com/engineering/multi-agent-research-system)。第二种是**跨阶段的信息失真**，即第 03 节讲过的「传话游戏（game of telephone）」：每经一次转述就失真一次。Anthropic 的解法是让子智能体把大块产物写入外部文件系统、只回传轻量引用，防止多级处理中的信息损失 [来源](https://www.anthropic.com/engineering/multi-agent-research-system)。

框架层面，LangGraph 用**持久化（persistence）与检查点（checkpoint）**系统性地解决状态存活：图的状态可以按线程持久化，随时恢复，这让长程多智能体在崩溃或换代后不丢状态 [来源](https://langchain-ai.github.io/langgraph/concepts/persistence/)。这也是为什么第 05 节的 demo 要给 Supervisor 一条显式 `trace`——运行轨迹和检查点是同一个思路：**让重要的东西活在对话之外**。

## 失败模式二：无限对话与不收敛

第二类失败是 Agent 之间「停不下来」：对等网络里两个 Agent 反复互相调用、编排里子智能体为不存在的信息无休止搜索、或对话式系统里 Agent 之间无限「踢皮球」。Anthropic 记录的早期失败正属此类：Agent 会为简单查询生成 50 个子智能体、为不存在的来源在网上无休止搜索、用过量更新互相干扰 [来源](https://www.anthropic.com/engineering/multi-agent-research-system)。

成熟框架都把「终止条件」做成一等公民。AutoGen 的团队（Team）机制要求显式指定**终止条件（termination condition）**：可以是达到最大消息数、也可以是某个 Agent 说出特定文本才停——例如它的 primary+critic 反思团队让 critic 反复给反馈，直到它回复 `APPROVE` 才终止 [来源](https://microsoft.github.io/autogen/stable/user-guide/agentchat-user-guide/tutorial/teams.html)。CrewAI 的 Hierarchical 流程由一个 manager 规划、委派、校验，任务在 manager 的控制下推进而非无序互调 [来源](https://docs.crewai.com/en/concepts/processes/)。LangGraph 的图则天然带**递归上限（recursion limit）**，超过步数会中止，防止无限循环。教学层面对应的就是每个循环都必须有的 `max_hops`/`max_turns` 上限——这在第 05 节的 Supervisor 里体现为「主题数由调用方显式给定」，从源头上限制了分派规模。

## 失败模式三：成本爆炸

第三类失败是「跑对了但太贵」。Anthropic 的数据是硬约束：多智能体系统大约比对话多用 15 倍 token，Agent 大约多用 4 倍 [来源](https://www.anthropic.com/engineering/multi-agent-research-system)。成本爆炸通常来自三处：过度分解（简单查询也派大量子智能体）、广播式群聊（所有 Agent 共享全上下文互相广播，token 随 Agent 数平方增长）、以及大块产物反复复制进对话历史。

防御手段对应三条：按复杂度缩放投入（简单事实用 1 个 Agent）、用点对点消息或摘要广播替代全量广播、大块产物走外部存储只传引用 [来源](https://www.anthropic.com/engineering/multi-agent-research-system)。关键是**把 token 成本和任务价值放在一起看**——Anthropic 反复强调多智能体只在「任务价值足够高、能为提升的性能买单」时才具备经济可行性。

## 三大框架的公开防御机制对照

| 失败模式 | AutoGen 公开机制 | CrewAI 公开机制 | LangGraph 公开机制 |
|---|---|---|---|
| 上下文丢失 | Team 共享消息上下文、Swarm 用 HandoffMessage 携带转移信息 | Sequential 用 `context` 显式把上一任务输出喂给下一任务 | 持久化+检查点按线程存取状态，支持恢复 |
| 无限对话/不收敛 | 显式终止条件（最大消息数 / 文本匹配如 APPROVE） | Hierarchical 由 manager 规划-委派-校验，受控推进 | 图的递归上限，超步数中止 |
| 成本爆炸 | 可控的团队规模与轮次上限 | 按流程选择 Sequential/Hierarchical，避免无谓并发 | 图结构显式，便于统计每节点开销 |
| 状态与协调 | AgentChat 之上的事件驱动运行时 | Crew 编排任务与 Agent、Flow 做事件驱动的确定性编排 | StateGraph 显式建模状态与转移 |

> 说明：上表只陈述各框架**公开文档描述的外部机制**，不涉及其内部实现；具体 API 名称、默认上限、参数以各自当前官方文档为准。

## 真实系统对应

**官方公开机制**：Anthropic 记录了错误复合、上下文截断、无限搜索、50 个子智能体等真实失败及其防御（Memory 持久化、外部产物引用、按复杂度缩放、全链路追踪、重试与检查点、rainbow deployment 灰度发布）[来源](https://www.anthropic.com/engineering/multi-agent-research-system)。AutoGen 提供 Team 与显式终止条件、Swarm 的 HandoffMessage [来源](https://microsoft.github.io/autogen/stable/user-guide/agentchat-user-guide/tutorial/teams.html)。CrewAI 提供 Sequential 与 Hierarchical 两种内置流程 [来源](https://docs.crewai.com/en/concepts/processes/)。LangGraph 提供持久化、检查点与图递归上限 [来源](https://langchain-ai.github.io/langgraph/concepts/persistence/)。**通用工程模式**：用复合可靠性数学决定环数、用终止条件防不收敛、用「价值 vs 15× token」守成本。**教学参考实现**：`chain_reliability` 只是概率相乘的直觉演示，真实 Agent 各环成功率并不独立同分布。

## 深入：为什么多智能体的调试要用「新方法」

Anthropic 特别指出，Agent 做动态决策、且即使提示相同，两次运行之间也是非确定性的，这让调试更难：用户报告「Agent 找不到明显信息」，但工程师看不出原因——是搜索查询差？选了差的来源？还是撞上工具失败？他们的解法是加**全生产追踪（full production tracing）**，从而系统性地诊断失败；并且他们监控 Agent 的决策模式与交互结构，而不监控单条对话的内容，以保护用户隐私 [来源](https://www.anthropic.com/engineering/multi-agent-research-system)。

这解释了第 05 节 demo 为什么坚持给每一跳打 `trace_id`、agent、tool_calls、tokens。多智能体的可观测性和单 Agent 有本质差异：单 Agent 只有一条时间线，多智能体的控制权在多个 Agent 间跳转，必须靠贯穿全程的 trace 才能回答「哪一步第一次偏离预期」。Anthropic 还提到部署要用 rainbow deployment（彩虹部署）逐步把流量从旧版本切到新版本、两版并存，避免更新打断正在运行的 Agent——因为 agentic 系统是「几乎持续运行的、由提示/工具/执行逻辑构成的高度有状态的网」，部署时 Agent 可能停在流程的任意位置 [来源](https://www.anthropic.com/engineering/multi-agent-research-system)。这是把「有状态长程运行」这个特性一路贯彻到发布流程的例子。

## 深入：同步执行的瓶颈与异步的代价

Anthropic 坦承了一个当前架构的局限：主导 Agent **同步执行**子智能体，要等一批子智能体全部完成才继续。这简化了协调，但造成信息流瓶颈——主导 Agent 无法中途引导子智能体、子智能体之间无法协调、整个系统可能因为等一个慢的子智能体而阻塞 [来源](https://www.anthropic.com/engineering/multi-agent-research-system)。异步执行能带来更多并行（Agent 并发工作、按需创建新子智能体），但会引入结果协调、状态一致性、跨子智能体错误传播的新难题；他们的判断是：随着模型能处理更长更复杂的任务，性能收益会证明这份复杂度是值得的 [来源](https://www.anthropic.com/engineering/multi-agent-research-system)。

这段话对读者的价值在于：它诚实地展示了「没有免费的午餐」。同步简单但有瓶颈，异步快但难保证一致性——这正是第 02 节「拓扑是控制权的形状」的延伸：连并行方式（同步/异步）都是一个需要权衡的工程决策，而不是「越并行越好」。

## 生产踩坑

| 症状 | 根因 | 如何观测与复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| 一步失败导致整链脱轨 | 错误复合、单环失败被放大 | 注入某环失败观察整体结果 | 减少环数+每环重试+关键环护栏兜底 | 只读探索任务容错高 |
| 主导 Agent 丢失早期计划 | 上下文超限被截断 | 观察长任务后计划是否还在 | 计划写入外部 Memory，超限取回 | 短任务上下文充裕 |
| Agent 间无限踢皮球 | 缺终止条件/递归上限 | 回放交互图找环 | 设 max_hops、终止条件或图递归上限 | 探索型允许有限迭代 |
| 子智能体为不存在信息无休搜索 | 未设投入上界 | 统计单查询工具调用数 | 按复杂度缩放，设调用次数上限 | 深研究任务上限放宽 |
| 群聊 token 随 Agent 数暴涨 | 全量广播共享上下文 | 统计每轮广播消息量 | 摘要广播或点对点消息 | 小团队短对话可接受 |
| 成本翻十几倍难解释 | 未把 token 与任务价值联看 | 分解每子智能体 token 占比 | 记录「价值 vs 15× token」，低价值不上多智能体 | 高价值可并行任务例外 |
| 部署更新打断运行中 Agent | 有状态长程运行、一次性切换 | 部署时观察在途任务失败率 | 灰度/彩虹部署，两版并存渐进切流量 | 无状态短任务可直接切 |
| 两次运行结果不一致难复现 | Agent 决策非确定性 | 相同提示多跑几次对比轨迹 | 加全链路 trace，评「达成结果」而非「走对步骤」 | 确定性纯函数环节不受影响 |
| 慢子智能体阻塞整个系统 | 同步执行、等最慢的一个 | 记录各子智能体耗时分布 | 评估异步执行，或给单个子智能体设超时 | 强依赖子任务本就该串行 |

## 思考：为什么框架都把「终止条件」做成一等公民？

### 回答

因为多智能体天然缺乏「自然终点」。单次 LLM 调用回答完就结束，但多个 Agent 互相调用/交接时，没有谁天生知道「整件事做完了」——编排里子智能体可能为不存在的信息无休搜索，对等网络里两个 Agent 可能反复互调，对话式系统里可能无限踢皮球。所以 AutoGen 要求 Team 显式指定终止条件（最大消息数或特定文本如 APPROVE）[来源](https://microsoft.github.io/autogen/stable/user-guide/agentchat-user-guide/tutorial/teams.html)，LangGraph 的图带递归上限，CrewAI 的 Hierarchical 由 manager 控制推进。教学层面就是每个循环必须有的 `max_hops`。把终止条件做成一等公民，本质是承认「Agent 不会自己停」，必须由架构强制给出停止的判据——这也呼应第 05 节「主题数由调用方显式给定」，从源头限制规模。

### 面试精简表达

多智能体没有自然终点，容易无限循环或不收敛，所以 AutoGen/LangGraph/CrewAI 都把终止条件（最大消息数、递归上限、manager 校验）做成显式机制；教学上对应每个循环必备的 max_hops 上限。

## 真实系统对应：从 Anthropic 早期失败看「涌现行为」

Anthropic 强调多智能体有**涌现行为（emergent behaviors）**：这些行为不是被专门编程出来的，例如对主导 Agent 的微小改动会不可预测地改变子智能体的行为方式；成功要求理解交互模式，而不只是单个 Agent 的行为 [来源](https://www.anthropic.com/engineering/multi-agent-research-system)。这句话对生产运维极其重要：它意味着**你不能只测单个 Agent，还要测它们的交互**。他们的应对是三管齐下——用小样本（约 20 个代表真实用法的查询）立刻开测、用 LLM-as-judge 按评分标准（事实准确、引用准确、完整性、来源质量、工具效率）规模化评估、再用人工评测抓自动化漏掉的边缘案例（比如早期 Agent 一贯偏好 SEO 内容农场而非权威但排名低的学术 PDF）[来源](https://www.anthropic.com/engineering/multi-agent-research-system)。

把这套经验落到自己的系统，就是三条可执行原则：第一，评测要评「结果对不对」而非「步骤对不对」，因为多智能体可能走不同但都正确的路径；第二，早开测、小样本足以暴露大问题（一次提示改动可能把成功率从 30% 提到 80%）；第三，自动评测与人工评测互补，前者规模化、后者抓涌现的怪异行为。这三条直接对应生产里「先建观测与评测基线、再优化」的顺序，也是下一节生产建议的前提。
