## 真实问题

回到开头故障最扎心的那一句：**「崩了才知道混进了坏数据，中间八天无人知晓。」** 团队复盘时想回答几个朴素的问题——这八天里 Agent 一共跑了多少次？平均每次重试几轮？哪些供应商触发了 `ModelRetry`？某一次具体的运行里，模型到底调用了哪些工具、每步的输入输出是什么、花了多少 token、耗时多久？结果发现全都答不上来，因为线上的 Agent 是个彻底的黑盒：进去一段文本，出来一个结果（或一个异常），中间发生了什么完全不可见。出问题时既没法快速定位是哪一层坏了，也没法度量「重试率」「工具错误率」这类健康指标。

另一个平行的痛点在测试环节：团队想写单元测试验证「遇到 `"约一万元"` 会触发重试」「供应商不在白名单会 `ModelRetry`」，但每跑一次测试就要真实调用一次模型 API——要花钱、要联网、结果还不确定（同样的输入模型可能这次这么答、下次那么答），根本没法写稳定的断言。这一节讲 PydanticAI 怎么同时解决这两件事：用 Logfire 让运行**可观测**，用 `TestModel`/`FunctionModel` 让运行**可离线、可确定地测试**。

## 原理：观测靠 Logfire，测试靠假模型

**可观测性**：PydanticAI 与 Logfire 深度集成，而 Logfire 建立在 OpenTelemetry（一套厂商中立的可观测性标准，缩写 OTel）之上 [来源](https://ai.pydantic.dev/logfire/)。核心用法极简：
```python
import logfire
logfire.configure()                    # 配置（含发送到 Logfire 平台所需信息）
logfire.instrument_pydantic_ai()       # 一行开启对 PydanticAI 的自动埋点
```
开启后，每次 Agent 运行、每次模型请求、每次工具调用都会作为一个 span（跨度，OpenTelemetry 里表示一段带时间的操作）被记录下来，形成一棵可视化的调用树：你能看到「这次运行 → 调了 check_vendor 工具（输入/输出/耗时）→ 触发了一次重试 → 产出 Invoice」的完整轨迹，以及 token 用量、时延等指标。因为底层是 OpenTelemetry，数据不绑死在 Logfire——你也可以把它接到任何兼容 OTel 的后端。

**离线测试**：PydanticAI 提供两个「假模型」用于测试 [来源](https://ai.pydantic.dev/testing/)：

- **`TestModel`**：最简单的假模型，**不调用任何真实 LLM**，会（尽量）按你的 `output_type`/工具 Schema 生成合规的假数据，用于快速验证「链路能跑通、工具被调用了」。
- **`FunctionModel`**：更可控，你传入一个 Python 函数，由它决定「模型」在每一步返回什么——想让它第一轮返回坏值、第二轮返回好值？写在函数里即可，从而**确定性地**测试重试、`ModelRetry` 等分支。

配合 `Agent.override(model=...)`（第 4 节 override 的同款机制，只是换的是 model 而非 deps），你可以在测试代码块里把真实模型临时替换成假模型。官方还提供 `models.ALLOW_MODEL_REQUESTS = False` 这个「保险丝」：把它设为 `False`，一旦测试里不小心真的发起了模型请求就会报错，防止 CI 偷偷联网烧钱 [来源](https://ai.pydantic.dev/testing/)。

画成图：
```text
              可观测（生产）                        可测试（CI）
  logfire.configure()                    with agent.override(model=TestModel()):
  logfire.instrument_pydantic_ai()           # 或 FunctionModel(自定义函数)
          │                                      │
          ▼                                      ▼
  每次运行/模型请求/工具调用 → span 树      不联网、不花钱、结果确定
  可看输入输出、token、耗时、重试次数       可断言"工具被调了""触发了重试"
          │                                 ALLOW_MODEL_REQUESTS=False 当保险丝
          ▼                                      │
  OpenTelemetry 标准，可接任意兼容后端     ← 防止测试偷偷联网真调模型
```
## 现象与输入：黑盒 vs 可观测

把「有没有可观测」两种运维状态并排看，价值就具体了：
```text
黑盒（故障前）：                              可观测（instrument 后）：
输入文本 → [ ??? ] → 结果/异常               输入文本 → span 树：
                                                ├─ agent run（总耗时/总token）
出问题：不知哪层坏、无指标、             │  ├─ model request #1（输入/输出/token）
八天混进多少坏数据无从查起               │  ├─ tool: check_vendor（入参/返回/耗时）
                                            │  ├─ retry #1（重试原因：amount 校验失败）
                                            │  └─ model request #2 → 产出 Invoice
                                            可度量：重试率、工具错误率、p95 时延
```
左边黑盒的每一个「不知道」，右边都变成了「一个 span 上的字段」。**可观测的本质是把「运行时发生了什么」从内存里的瞬时状态，固化成可查询、可聚合、可告警的数据。** 有了它，「结算 Agent 成功率下降」这种模糊告警才能被下钻到「是 check_vendor 的 ModelRetry 率突增」这种可行动的根因。

## 最小可运行演示

我们不联网、不用 API Key，用纯 Python 复刻两件事：一个极简的「span 记录器」演示可观测性的数据形态，一个「假模型」演示离线确定性测试。这让你在没装 `pydantic_ai`/`logfire` 时也能看清它们的心智模型。
```python
"""教学参考实现：复刻(1)span 记录器的可观测数据形态 (2)假模型的离线确定性测试。"""
from dataclasses import dataclass, field


## ---------- (1) 可观测：极简 span 记录器 ----------
@dataclass
class Span:
    name: str
    attrs: dict = field(default_factory=dict)


class Tracer:
    """教学替身：真实 logfire/OTel 记录嵌套 span 树，这里拍平成列表演示数据形态。"""
    def __init__(self):
        self.spans: list[Span] = []

    def record(self, span_name: str, **attrs) -> None:
        self.spans.append(Span(span_name, attrs))

    def report(self) -> None:
        retries = sum(1 for s in self.spans if s.name == "retry")
        tools = sum(1 for s in self.spans if s.name == "tool_call")
        print(f"[观测] 共 {len(self.spans)} 个 span，工具调用 {tools} 次，重试 {retries} 次")
        for s in self.spans:
            print(f"  - {s.name}: {s.attrs}")


## ---------- (2) 可测试：假模型（FunctionModel 思路）----------
def fake_model_fn(turn: int) -> dict:
    """确定性假模型：第0轮给坏值，第1轮给好值。测试据此断言重试分支。"""
    return [{"amount": "约一万元"}, {"amount": "10000"}][turn]


def run_with_tracing(tracer: Tracer, model_fn, max_retries: int = 2) -> float:
    for turn in range(max_retries):
        raw = model_fn(turn)
        tracer.record("model_request", turn=turn, output=raw)
        try:
            amount = float(raw["amount"])
            tracer.record("tool_call", tool="validate", ok=True)
            return amount
        except ValueError:
            tracer.record("retry", turn=turn, reason=f"amount={raw['amount']!r} 非数字")
    raise RuntimeError("重试耗尽")


if __name__ == "__main__":
    tracer = Tracer()
    result = run_with_tracing(tracer, fake_model_fn)
    tracer.report()
    ## 离线确定性断言：因为用假模型，结果每次都一样，可以写死断言
    assert result == 10000.0, "应在第2轮纠正为 10000.0"
    assert sum(1 for s in tracer.spans if s.name == "retry") == 1, "应恰好重试1次"
    print("测试通过：结果确定、重试次数可断言")
```
保存为 `observability_test.py`，运行 `python observability_test.py`。完整预期输出：
```text
[观测] 共 4 个 span，工具调用 1 次，重试 1 次
  - model_request: {'turn': 0, 'output': {'amount': '约一万元'}}
  - retry: {'turn': 0, 'reason': "amount='约一万元' 非数字"}
  - model_request: {'turn': 1, 'output': {'amount': '10000'}}
  - tool_call: {'tool': 'validate', 'ok': True}
测试通过：结果确定、重试次数可断言
```
这段演示同时说清了两件事。可观测那半：`Tracer` 把「模型请求、重试、工具调用」都记成 span，事后 `report()` 就能聚合出「重试 1 次、工具调用 1 次」——这正是线上 Logfire 帮你自动做的，只不过它记的是嵌套 span 树、还带 token 和耗时。可测试那半：因为 `fake_model_fn` 是**确定性**的（第 0 轮必给坏值、第 1 轮必给好值），`assert result == 10000.0` 和 `assert 重试次数 == 1` 才敢写死——**换成真实模型，同样的输入下次可能一轮就对、也可能三轮才对，断言就没法写。** 这就是 `TestModel`/`FunctionModel` 的核心价值：把不确定的模型换成确定的替身，让测试可断言、可复现、不花钱。

## 真实系统对应

**官方公开机制**：`logfire.instrument_pydantic_ai()` 一行开启对 PydanticAI 的自动埋点，Logfire 基于 OpenTelemetry，运行/模型请求/工具调用都会成为 span [来源](https://ai.pydantic.dev/logfire/)；测试侧 `TestModel` 不调真实 LLM 并按 Schema 造合规假数据、`FunctionModel` 用自定义函数精确控制每步返回、`Agent.override(model=...)` 临时替换模型、`ALLOW_MODEL_REQUESTS=False` 防止测试误发真实请求 [来源](https://ai.pydantic.dev/testing/)。**通用工程模式**：「生产埋点可观测 + 测试用确定性替身」是任何严肃 LLM 系统的双支柱，可迁移到任何框架——观测选 OpenTelemetry 生态、测试用可注入的假模型。**教学参考实现**：上面的 `Tracer`/`fake_model_fn` 是极简替身，真实 Logfire 的 span 是嵌套树且含丰富属性，真实 `FunctionModel` 的函数签名更完整。

需要点明边界：Logfire 的免费额度、数据保留期、平台功能会变化，以官方文档为准；本节讲「基于 OTel 的自动埋点」这一稳定机制，不承诺具体额度。可观测本身有成本（存储、采样），极低价值的高频任务可只采样或不接入。`TestModel` 生成的是「合规但无意义」的假数据，它验证「链路通」而非「答案对」——验证答案质量要靠评估集（第 16 章）。

## 生产踩坑

| 症状 | 根因 | 如何观测与复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| 崩了才知道、无法定位哪层坏 | 线上无埋点、Agent 是黑盒 | 关掉 instrument 复现「查不到中间态」 | `logfire.instrument_pydantic_ai()` 开 span | 极低价值一次性脚本可不接 |
| 想算重试率/工具错误率却没数据 | 未把运行固化成可聚合指标 | 试图从日志正则捞指标发现散乱 | 用 span 属性聚合成指标看板 | 无 SLO（Service Level Objective，服务等级目标）要求的内部工具可放宽 |
| 单测要真调模型、慢又花钱又不稳 | 测试直连真实 LLM | CI 里跑单测发现要 API Key 和网络 | 用 `TestModel`/`FunctionModel` + override | 少量端到端集成测试仍需真模型 |
| 测试断言时对时错 | 对不确定的真实模型写死断言 | 同输入多跑几次看结果是否漂移 | 用确定性 `FunctionModel` 固定每步返回 | 评估答案质量用评估集而非断言 |
| CI 偷偷联网真调模型烧钱 | 没设请求保险丝 | 误留一处真实 model 未 override | 设 `ALLOW_MODEL_REQUESTS=False` | 明确的集成测试阶段需允许 |
| 观测数据把 PII（Personally Identifiable Information，个人可识别信息）明文写进 span | 未脱敏就埋点 | 检查 span 里是否含身份证/手机号 | 埋点前最小化并脱敏 PII | 已合规脱敏的字段可保留 |
| 观测存储成本失控 | 全量高频任务不采样 | 统计 span 量与存储账单 | 按重要性采样、设保留期 | 低频高价值任务可全量 |

## 思考：为什么说「可观测性」不是运维的锦上添花，而是 Agent 上生产的准入条件？

### 回答

因为 Agent 的行为具有内在的不确定性，而不确定的系统若不可观测，就等于放弃了对它的控制权。展开说三点。第一，**Agent 的每次运行路径都可能不同**：同样的输入，模型可能调不同的工具、重试不同的次数、走不同的分支。传统确定性程序你读代码就能推断行为，Agent 不行——你必须靠观测「它这次实际做了什么」。没有观测，你连「刚才那次为什么错」都无法回答。第二，**故障是概率性的、间歇的**：像开头「金额写成约一万元」，八天里只有 1.9% 的坏数据，靠人肉根本发现不了，只有把每次运行固化成可聚合的指标，才能在「坏数据率」这条曲线抬头时提前告警，而不是等对账崩了才知道。第三，**优化需要度量**：想降本（减少重试）、提准（改进工具描述），前提是能量化「重试率是多少」「哪个工具错得最多」，没有观测就是盲目调参。所以对生产级 Agent，可观测性和「结构化输出」「错误处理」一样，是承重结构而非装饰——这也是 PydanticAI 把 Logfire 集成做成一等公民、一行 `instrument` 就能开的原因。它对应第 17 章会深入的可观测性主题，也是本章「三可」里「可观测」那一可的落地。

### 面试精简表达

因为 Agent 行为不确定（每次路径可能不同）、故障概率性间歇（1.9% 坏数据人肉发现不了）、优化需度量（不量化重试率就是盲调）。不可观测的不确定系统等于失控，所以它是准入条件而非锦上添花。

## 思考：TestModel 和 FunctionModel 该怎么选？它们能替代所有测试吗？

### 回答

先说怎么选：`TestModel` 用于「我只想确认链路能跑通、工具会被调用、输出结构合规」这类冒烟测试——它自动按 Schema 造合规假数据，你不用操心模型返回什么，最省事。`FunctionModel` 用于「我要精确控制模型每一步返回什么，以测试特定分支」——比如测「第一轮坏值触发重试、第二轮好值通过」，这种确定性的多轮脚本只有 `FunctionModel` 能给。一句话：**只验证「通不通」用 `TestModel`，要验证「特定分支对不对」用 `FunctionModel`。** 再说能不能替代所有测试：不能，它们替代的是「不该依赖真实模型的那部分测试」。它们验证的是你的**代码逻辑**（工具有没有被正确调用、重试分支对不对、依赖注入通不通），而**不验证模型答案的质量**——因为假模型给的是「合规但无意义」的数据。要验证「模型在真实发票上抽得准不准」，必须用真实模型跑评估集（第 16 章），并保留少量连真实 API 的端到端集成测试。所以健康的测试金字塔是：大量用假模型的快速单元测试（毫秒级、不花钱、可确定）打底，少量真实模型的集成/评估测试封顶。把「逻辑正确性」和「模型答案质量」这两件事分开测，是 LLM 应用测试的关键认知。

### 面试精简表达

TestModel 验「链路通/结构合规」最省事，FunctionModel 精确控制每步返回以测特定分支（如重试）。二者只测代码逻辑不测答案质量，替代不了评估集（第16章）和端到端集成测试。金字塔：大量假模型单测打底、少量真实模型评估封顶。
