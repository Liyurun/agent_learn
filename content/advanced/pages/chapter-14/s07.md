## 真实问题

前六节把 PydanticAI 的六个环节逐一拆开讲透了：结构化输出的鸿沟、`output_type` 三层机制、工具注册与自动 Schema、依赖注入与可测试性、`ModelRetry` 纠错前移、可观测与离线测试。但工程师最怕的是「单点都懂、组装就懵」——每个零件单独看都会用，一旦要把它们拼成一条能上线的完整流水线，就不知道谁先谁后、谁管谁。这一节的任务，是把开头那个「金额写成约一万元」的发票故障**从头到尾修一遍**：用一条完整的发票抽取流水线，把当初三处独立缺陷（无结构约束、无自动纠错、无可观测）逐一堵死，让你看清六个零件如何咬合成一个整体。

这一节不引入新机制，而是做「集成」：把前六节的零件按正确的顺序和职责组装起来，并在最后给出这条流水线的完整数据流与一个可离线运行的骨架。

## 原理：一条流水线，六个零件各就各位

先画出这条发票抽取流水线的完整数据流，标注每一步用到前面哪一节的机制：
```text
                        [依赖注入·第4节] Deps{whitelist, exchange_rate}
                                     │ run(deps=...)
用户/上游：自由文本发票 ──────────────▼──────────────────────────────
                          ┌────────────────────────────────┐
                          │ Agent(model, deps_type=Deps,     │
                          │       output_type=Invoice)       │
                          └───────────────┬──────────────────┘
   [可观测·第6节] logfire.instrument      │ 每步记 span
                                          ▼
              模型决策：先调工具查供应商 check_vendor（ctx.deps.whitelist）
                                          │  [工具·第3节：自动 Schema]
                          不在白名单 → raise ModelRetry  [第5节：纠错前移]
                                          │  提示喂回模型，改抬头重试
                                          ▼
              产出候选 Invoice → output_type 类型校验 [第2节：三层机制]
                          amount 不是 float（"约一万元"）→ 自动重试
                                          ▼
              输出校验器：amount 不能为负、币种∈支持集 [第5节：业务校验]
                                          │ 不合规 → raise ModelRetry
                                          ▼
              全部通过 → result.output 是类型安全且业务合规的 Invoice
                                          │
              [可测试·第4/6节] 上述整条链，测试时 override(model=FunctionModel, deps=假依赖) 离线跑
```
看这张图，六个零件的职责边界一目了然：**依赖注入**在最外层供给「白名单、汇率」这些运行时才知道的东西；**工具**在循环中间负责「查」这类确定性动作，并用 `ModelRetry` 把业务校验前移；**output_type 三层机制**在结果产出时守「结构合规」这道关；**输出校验器**在返回前守「业务合规」这道关；**可观测**横贯始终记录每一步；**可测试**让整条链能被 `override` 成离线确定性运行。这就是把开头故障三处缺陷（结构、纠错、观测）分别交给了「output_type + 校验」「ModelRetry + 重试」「logfire」。

## 现象与输入：故障前 vs 故障后的流水线

把「故障前的天真实现」和「故障后的生产实现」并排对照，能看清每处缺陷是被哪个零件堵死的：
```text
故障前（三处缺陷）：                          故障后（六零件组装）：
文本 → 模型返回自由 JSON                       文本 → output_type=Invoice 强制结构 [第2节]
     → json.loads 直接写库                          → Pydantic 校验 amount:float，坏值重试
     ✗ 缺陷1：无结构约束                             → check_vendor 工具查白名单 [第3节]
     ✗ 缺陷2：坏值无纠错静默落库                     → 不在名单 raise ModelRetry 纠正 [第5节]
     ✗ 缺陷3：黑盒，崩了才知道                       → 输出校验器守业务规则 [第5节]
                                                     → logfire 全程记 span，可度量 [第6节]
下游 sum() 崩溃、回滚 3200 条                    落库的每条 amount 都是 float 且业务合规
```
## 最小可运行演示

我们不联网、不用 API Key，用纯 Python 把六个零件组装成一条可离线运行的发票抽取流水线骨架。它用第 4/6 节的 `FunctionModel` 思路注入确定性假模型，用第 4 节的依赖注入供给白名单，把第 2 节的类型校验、第 5 节的 `ModelRetry`、第 6 节的 span 记录全部串起来，完整复现「坏值→重试→纠正→合规落库」。
```python
"""教学参考实现：把六个零件组装成可离线运行的发票抽取流水线骨架。"""
from dataclasses import dataclass, field


class ModelRetry(Exception):
    """第5节：把业务校验前移成模型可纠正的反馈。"""


@dataclass
class Deps:                                   ## 第4节：依赖注入
    whitelist: set[str]


@dataclass
class Invoice:                                ## 第2节：output_type 的目标结构
    vendor: str
    amount: float
    currency: str


@dataclass
class Tracer:                                 ## 第6节：可观测
    spans: list = field(default_factory=list)
    def rec(self, name, **a): self.spans.append((name, a))


def validate_types(raw: dict) -> Invoice:     ## 第2节：类型校验层
    try:
        amount = float(raw["amount"])
    except (TypeError, ValueError):
        raise ModelRetry(f"amount={raw['amount']!r} 应为数字，请只返回阿拉伯数字")
    return Invoice(raw["vendor"], amount, raw.get("currency", "CNY"))


def check_vendor(deps: Deps, name: str) -> None:   ## 第3节工具 + 第5节 ModelRetry
    if name not in deps.whitelist:
        raise ModelRetry(f"'{name}' 不在合作名单，规范名应为 {sorted(deps.whitelist)} 之一")


def output_validator(inv: Invoice) -> None:        ## 第5节：输出校验器（业务规则）
    if inv.amount < 0:
        raise ModelRetry("amount 不能为负数")
    if inv.currency not in {"CNY", "USD", "EUR"}:
        raise ModelRetry(f"不支持的币种 {inv.currency}")


def function_model(turn: int) -> dict:             ## 第6节：确定性假模型（脚本化）
    return [
        {"vendor": "星辰科技有限公司", "amount": "10000", "currency": "CNY"},   ## 第1轮：抬头错
        {"vendor": "星辰科技", "amount": "约一万元", "currency": "CNY"},        ## 第2轮：金额错
        {"vendor": "星辰科技", "amount": "10000", "currency": "CNY"},           ## 第3轮：全部纠正
    ][turn]


def run_pipeline(deps: Deps, tracer: Tracer, max_retries: int = 3) -> Invoice:
    for turn in range(max_retries):
        raw = function_model(turn)
        tracer.rec("model_request", turn=turn, raw=raw)
        try:
            check_vendor(deps, raw["vendor"])       ## 工具关（业务）
            invoice = validate_types(raw)           ## 类型关（结构）
            output_validator(invoice)               ## 输出校验关（业务）
            tracer.rec("success", invoice=invoice)
            return invoice
        except ModelRetry as e:
            tracer.rec("retry", turn=turn, reason=str(e))
            print(f"[第{turn+1}轮] 触发重试：{e}")
    raise RuntimeError("重试耗尽：转人工核验队列")


if __name__ == "__main__":
    deps = Deps(whitelist={"星辰科技", "云海数据"})   ## 生产注入真库，测试注入假的
    tracer = Tracer()
    invoice = run_pipeline(deps, tracer)
    print("最终落库：", invoice)
    retries = sum(1 for n, _ in tracer.spans if n == "retry")
    print(f"[观测] 共 {len(tracer.spans)} 个 span，重试 {retries} 次")
    assert invoice.amount == 10000.0 and isinstance(invoice.amount, float)
    print("断言通过：amount 是 float 且业务合规")
```
保存为 `invoice_pipeline.py`，运行 `python invoice_pipeline.py`。完整预期输出：
```text
[第1轮] 触发重试：'星辰科技有限公司' 不在合作名单，规范名应为 ['云海数据', '星辰科技'] 之一
[第2轮] 触发重试：amount='约一万元' 应为数字，请只返回阿拉伯数字
最终落库： Invoice(vendor='星辰科技', amount=10000.0, currency='CNY')
[观测] 共 6 个 span，重试 2 次
断言通过：amount 是 float 且业务合规
```
读懂这段轨迹，你就读懂了整条流水线：第 1 轮模型给的抬头带「有限公司」后缀，`check_vendor` 抛 `ModelRetry`；第 2 轮抬头对了但 `amount` 是「约一万元」，`validate_types` 抛 `ModelRetry`；第 3 轮脚本给出全部合规的值，代码里三处校验按「工具→类型→输出校验」顺序依次通过后落库。整条链把开头故障三处缺陷全堵死了：`amount` 落库保证是 `float`（结构）、供应商保证在白名单（业务）、每一步都有 span 可度量（观测），共 6 个 span（3 次模型请求 + 2 次重试 + 1 次成功）、恰好 2 次重试。而且因为用了确定性假模型和注入的假白名单，这条测试**不联网、不花钱、结果可断言**——生产上线前，这样的离线测试就能覆盖住绝大多数逻辑分支。

> 校验顺序小贴士：本骨架把 `check_vendor`（工具/业务）放在 `validate_types`（结构）之前，是为了演示两类校验都会触发重试；真实 PydanticAI 里工具调用发生在循环中间、类型校验发生在结果产出时，顺序由 Agent 循环决定，这里的线性顺序是教学简化。

## 真实系统对应

**官方公开机制**：这条流水线用到的每个零件都是官方公开机制——`output_type` 结构化输出与校验重试 [来源](https://ai.pydantic.dev/output/)、`@agent.tool` 工具与自动 Schema [来源](https://ai.pydantic.dev/tools/)、`deps_type`/`RunContext`/`override` 依赖注入 [来源](https://ai.pydantic.dev/dependencies/)、`ModelRetry` 与输出校验器纠错前移 [来源](https://ai.pydantic.dev/tools-toolsets/tools-advanced/)、Logfire 可观测 [来源](https://ai.pydantic.dev/logfire/)、`TestModel`/`FunctionModel` 离线测试 [来源](https://ai.pydantic.dev/testing/)。**通用工程模式**：「结构关 + 业务关 + 观测 + 可测试」这套流水线分层，可迁移到任何 LLM 抽取/结构化任务，不限于 PydanticAI。**教学参考实现**：上面的骨架为可离线复核做了简化（线性校验顺序、脚本化模型），真实 Agent 循环的调用时序、重试计数由框架管理。

需要点明边界：这条流水线解决的是「把不可信文本抽成可信结构」，它不保证「模型抽得准」——`vendor` 抽错成另一家白名单内的公司，结构和业务校验都拦不住，这类语义准确性要靠评估集（第 16 章）和必要的人工抽检。流水线是「护栏」，不是「正确性证明」。

## 生产踩坑

| 症状 | 根因 | 如何观测与复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| 零件都会用、组装后顺序混乱 | 没理清工具/校验/观测的职责边界 | 画数据流图看每步归属哪个零件 | 按「依赖→工具→结构→业务→观测」分层 | 极简单任务可不必全套 |
| 结构合规但供应商抽错 | 校验只管结构业务、不管语义准 | 喂一张抬头是另一白名单公司的发票 | 加评估集与人工抽检（第16章） | 语义容错高的场景可放宽 |
| 上线才发现某分支没覆盖 | 未用假模型离线测各分支 | 统计测试覆盖的重试/失败分支 | 用 FunctionModel 脚本化覆盖每分支 | 分支极少的简单流水线 |
| 重试耗尽整批失败无兜底 | 只写了成功路径 | 喂无法抽出金额的文本看是否崩 | 耗尽转人工核验队列、单条隔离 | 可整体重跑的离线批处理 |
| 观测只在成功路径埋点 | 失败/重试分支漏记 span | 制造重试看 span 是否缺失 | 重试/失败分支也记 span | 无观测要求的一次性脚本 |
| 依赖硬编码导致无法灰度 | 白名单/汇率写死在代码 | 想换测试库发现要改代码 | 全走 deps 注入，按环境注入不同实例 | 无环境差异的内部工具 |
| 把整条链当一次性 workflow | 没意识到中间有模型自主决策 | 看模型是否会自主选调工具 | 分清固定流程与循环 Agent（第3章） | 确定性抽取可用纯 workflow |

## 思考：这条流水线到底修好了开头故障的哪几处？逐条对应给面试官讲。

### 回答

开头「金额写成约一万元」的故障有三处独立缺陷，这条流水线逐一对应地修好了，讲的时候要一一咬合。第一处，「`amount` 时而数字时而中文，下游 `sum()` 崩溃」——根因是无结构约束。修法是 `output_type=Invoice` 把 `amount` 声明为 `float`，Pydantic 在结果产出时强制校验，`"约一万元"` 转不成 `float` 就触发自动重试（第 2 节三层机制），落库的每条 `amount` 都保证是 `float`，数据库字段也能从 `VARCHAR` 改回 `DECIMAL`。第二处，「坏数据静默落库八天无纠错」——根因是无自动纠错、无业务校验。修法是两道：工具 `check_vendor` 用 `ModelRetry` 把「供应商必须在白名单」这条业务规则前移，输出校验器用 `ModelRetry` 守住「金额非负、币种合法」，不合规当场让模型纠正而不是坏值落库（第 5 节）。第三处，「崩了才知道，八天混进多少坏数据无从查起」——根因是黑盒无可观测。修法是 `logfire.instrument_pydantic_ai()` 把每次运行、每次工具调用、每次重试都记成 span，「坏数据率」「重试率」变成可聚合、可告警的曲线（第 6 节）。三处缺陷分别对应「结构关、业务关、观测」，而依赖注入（第 4 节）让白名单可按环境注入、可测试（第 6 节）让整条链能离线验证——这就是为什么本章要按这个顺序讲六节：它们不是六个孤立特性，而是修好一个真实故障所需的六个咬合零件。

### 面试精简表达

三处缺陷逐一对应：无结构→output_type+Pydantic 校验重试（第2节）；无纠错→check_vendor 的 ModelRetry+输出校验器（第5节）；黑盒→logfire 记 span 可度量（第6节）。加上依赖注入按环境供料、假模型离线测试，六零件咬合成一条流水线。

## 思考：既然纯 workflow（写死的抽取代码）也能做发票抽取，为什么要用带模型自主决策的 Agent？

### 回答

这正是第 3 章「workflow 还是 Agent」在本场景的具体化，答案是「看输入的多样性和决策的必要性」。如果发票格式高度统一（比如都是同一个 OCR 模板出来的定长字段），那根本不需要模型自主决策，一段写死的正则/解析代码（纯 workflow）又快又稳又便宜，硬套 Agent 是杀鸡用牛刀、徒增成本和不确定性。但现实里发票来自成千上万种措辞和版式的自由文本邮件，「金额」可能写成「¥12,000」「一万二」「12000元」，「供应商」可能藏在抬头、落款或正文任意位置——这种输入多样性下，写死的规则会无穷无尽地打补丁且永远漏case，而模型的语言理解能力恰好擅长「从多样表达里抽取语义」。这时候用 Agent 才划算。但关键在于：**用 Agent 不等于放任模型自由发挥**，本章这条流水线的全部工程努力，正是给模型的自主决策套上护栏——结构关限定输出形状、业务关限定取值范围、观测记录每一步、测试覆盖每分支。所以正确的判断不是「Agent vs workflow 二选一」，而是「用模型处理它擅长的语言理解不确定性，用工程护栏约束它的不可靠性」。能把「何时该用 Agent」和「用了 Agent 如何用护栏约束它」两件事一起讲清，才是这道题的完整答案。

### 面试精简表达

看输入多样性：格式统一用纯 workflow（快稳省）；自由文本多样表达才需模型的语言理解（Agent）。但用 Agent 不等于放任——本章流水线正是给自主决策套护栏（结构关、业务关、观测、测试）。判断是「用模型处理语言不确定性+用工程约束其不可靠性」，非二选一。
