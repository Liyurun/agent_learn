## 真实问题

「金额写成约一万元」故障的第一现场，是那条让对账批处理崩溃的数据库记录。运维把它捞出来一看：`vendor` 是 `"星辰科技"`，看着没问题；`amount` 却是字符串 `"约一万元"`。更让人心里一凉的是，往前翻这八天的落库记录，`amount` 字段五花八门——有的是 `12000`（整数），有的是 `"12000.00"`（带引号的字符串），有的是 `"¥1.2万"`，有的干脆是 `"约一万元"`。同一个字段，四五种形态并存。

问题的根子不在某一条坏数据，而在**上游那个没有结构化约束的 Agent**。团队最初的实现大致是：给模型一段发票文本，让它「返回一个 JSON」，然后 `json.loads` 一下写库。demo 阶段肉眼看结果都对，于是就上线了。但生产里，模型每天要处理成千上万种措辞的发票，它对「金额」的理解随上下文漂移：遇到「大约一万元」它就照抄成 `"约一万元"`，遇到「¥12,000」它可能保留货币符号和千分位。下游代码要吃这个输出去做 `sum()`、去入库、去生成报表，格式一乱，整条链路就断。这就是「能跑」和「能上线」之间那道鸿沟——**demo 里你肉眼看结果没问题，生产里下游系统要吃这个输出，格式一乱整条链路就断**。

这一节要把这道鸿沟量化成可验收的标准，并说清 PydanticAI 为什么把「结构化输出」当成立身之本，而不是一个附加功能。

## 原理：把「生产级」拆成可验收的「三可」

「生产级」是个模糊词。把它拆成三个可以逐条验收的标准，你就知道该盯什么了。PydanticAI 官方文档把自己定位为「用类型提示（type hints）保证类型安全、把 Pydantic 的校验能力带到 GenAI 应用」的框架 [来源](https://ai.pydantic.dev/)，对应到「三可」如下：

| 标准 | 含义 | PydanticAI 的对应能力（官方公开机制） |
|---|---|---|
| 可预测 | 输出结构稳定，下游能放心消费 | `output_type` 强制结构化输出 |
| 可校验 | 不合规的输出能被自动挡下 | Pydantic 强类型校验 + 失败自动重试 |
| 可观测 | 每一步可追踪、可度量、可复盘 | `logfire.instrument_pydantic_ai()` / OpenTelemetry |

外加两个工程属性——**可测试**（依赖注入让你注入假依赖）、**可维护**（类型标注让 IDE 和静态检查器帮你兜底）——共同构成了 PydanticAI 的价值主张。本章后面各节，其实就是逐一展开这五个属性。

要理解 PydanticAI 的「气质」，得知道 Pydantic 是谁。Pydantic 是 Python 生态里最广泛使用的数据校验库，FastAPI 的类型安全手感就建立在它之上——你定义一个数据模型，它负责解析、校验、转换、报错。做 Agent 框架时，Pydantic 团队等于把自己最擅长的「数据校验」直接嫁接到「LLM 的不确定输出」这个新战场上。这解释了 PydanticAI 的核心信念：**LLM 的输出本质上是「一段需要被校验的不可信数据」，而校验不可信数据正是 Pydantic 的看家本领。** 别的框架可能把「结构化输出」当成一个附加功能，PydanticAI 把它当成立身之本。

## 现象与输入：无结构 vs 有结构

把「金额写成约一万元」的两种世界并排画出来，鸿沟就一目了然：
```text
无结构化约束（故障前）：                     有结构化约束（PydanticAI）：
模型 -> 自由文本/自由 JSON（格式随机）          模型 -> 强制符合 Invoice Schema 的对象
       │                                            │
       ▼                                            ▼
json.loads 后你写一堆 if/正则去猜             result.output.amount  # 直接就是 float
"约一万元"? "¥1.2万"? 12000? "12000.00"?          │
       │                                            ▼
       ▼                                     校验失败自动重试，稳定可预测
措辞一变就崩，坏数据静默落库                 得到类型安全对象，IDE 补全、mypy 静态检查
```
左边这一整列的痛苦——写正则、写 `try/except`、写「如果是中文金额就……如果带货币符号就……」的胶水代码，而且模型只要换个措辞就崩——正是 PydanticAI 要消灭的。右边你只写一个 `output_type=Invoice`，就把「让 LLM 稳定返回结构化输出」的全部复杂度交给了框架。

## 最小可运行演示

下面用纯 Python 模拟「无结构」世界的脆弱，让你亲手看到鸿沟。它不依赖 `pydantic_ai`、不联网，只演示「同一个下游函数吃到不同形态的 amount 会怎样」。
```python
"""教学参考实现：模拟无结构化约束下，下游消费模型输出的脆弱性。"""
import json


def downstream_sum(records: list[dict]) -> float:
    """下游对账：把所有发票金额加总。它天真地假设 amount 是数字。"""
    return sum(r["amount"] for r in records)


def run() -> None:
    ## 模拟模型在不同措辞下返回的四种 amount 形态（都是"能跑"的 JSON）
    raw_outputs = [
        '{"vendor": "星辰科技", "amount": 12000}',
        '{"vendor": "云海数据", "amount": "12000.00"}',
        '{"vendor": "微光传媒", "amount": "约一万元"}',
    ]
    records = [json.loads(x) for x in raw_outputs]
    print("落库的三条记录 amount 类型：")
    for r in records:
        print(f"  vendor={r['vendor']:<6} amount={r['amount']!r:<12} type={type(r['amount']).__name__}")
    print("\n下游对账 sum() 结果：")
    try:
        print(downstream_sum(records))
    except TypeError as e:
        print(f"  崩溃！TypeError: {e}")
        print("  这正是'金额写成约一万元'故障的复现：格式不统一，下游一算就炸")


if __name__ == "__main__":
    run()
```
保存为 `gap_demo.py`，运行 `python gap_demo.py`。完整预期输出：
```text
落库的三条记录 amount 类型：
  vendor=星辰科技   amount=12000        type=int
  vendor=云海数据   amount='12000.00'   type=str
  vendor=微光传媒   amount='约一万元'      type=str

下游对账 sum() 结果：
  崩溃！TypeError: unsupported operand type(s) for +: 'int' and 'str'
```
这段崩溃逐字复现了开头故障：三条记录都是「能跑」的合法 JSON，`json.loads` 全部成功，肉眼看也「差不多对」，但下游 `sum()` 一执行就炸。**「能跑」骗过了 demo，却骗不过生产。** 第 2 节会展示，同样这三段输入喂给 `output_type=Invoice` 的 Agent，`"约一万元"` 会在校验层被挡下并触发重试，而不是静默落库。

## 真实系统对应

**官方公开机制**：PydanticAI 的 `Agent` 构造函数接受一个 `output_type` 参数，官方 Output 文档明确它支持标量、`list`/`dict`、`TypedDict`、dataclass 和 Pydantic 模型，默认借助模型的工具调用（tool calling）能力来强制返回结构化数据，并用 Pydantic 构建 JSON Schema、校验模型返回的数据 [来源](https://ai.pydantic.dev/output/)。**通用工程模式**：「把 LLM 输出当成不可信数据来校验」这条原则，可迁移到任何框架——即便你不用 PydanticAI，也应在模型输出与下游之间架一道结构校验层。**教学参考实现**：上面的 `gap_demo.py` 只为演示脆弱性，`downstream_sum` 的「天真假设」是刻意为之，用来对照后面的强类型方案。

需要点明边界：PydanticAI 官方文档指出，当没有指定 `output_type`、或 `str` 在允许的输出类型里时，模型的纯文本回复会被直接当作输出 [来源](https://ai.pydantic.dev/output/)。也就是说「结构化」不是强加于所有场景的——纯问答、闲聊这类本就该返回文本的任务，不必套结构。鸿沟只存在于「下游要消费结构化数据」的场景。

## 生产踩坑

| 症状 | 根因 | 如何观测与复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| demo 通过、上线后偶发解析崩溃 | 只肉眼验收、无结构约束 | 抓一周线上输出统计字段类型分布 | 用 Pydantic 模型作 `output_type` 强制结构 | 纯文本问答场景无需结构 |
| 同一字段多种形态并存 | 模型对字段理解随措辞漂移 | 用不同措辞的输入回放对比 | 字段声明精确类型（如 `amount: float`） | 自由文本摘要字段可保留 str |
| 坏数据静默落库 | 无校验层直接 `json.loads` 写库 | 构造中文金额输入看是否落库 | 校验通过才落库，失败进兜底队列 | 允许人工事后清洗的低频场景 |
| 胶水代码越写越多且脆弱 | 用正则/if 手工归一化模型输出 | 统计解析相关代码行数与 bug 数 | 交给 `output_type` + Pydantic 统一处理 | 极简单一格式可不引框架 |

## 思考：为什么说「结构化输出」是 PydanticAI 的立身之本而非附加功能？

### 回答

因为它对应的是 PydanticAI 团队的核心能力与核心信念的交汇点。第一，从能力看：Pydantic 团队最擅长的就是「用类型系统校验不可信数据」，FastAPI 的成功证明了这套能力在「解析 HTTP 请求体」上极其好用，而「校验 LLM 输出」本质是同一个问题——都是把一段不可信的外部数据，按声明的 Schema 解析、校验、报错。第二，从信念看：别的框架往往把 LLM 输出默认当成「可以直接用的文本」，结构化只是锦上添花；PydanticAI 把 LLM 输出默认当成「需要被校验的不可信数据」，于是结构化校验成了地基而非装饰。第三，从工程后果看：把结构化当地基，意味着「校验失败自动重试」「类型安全对象」「IDE 补全」「静态检查」这些能力都能自然长出来，因为它们都建立在「有一个被强制的 Schema」这个前提上。所以它不是一个可选开关，而是整个框架价值主张的承重墙。

### 面试精简表达

Pydantic 团队最擅长校验不可信数据，而 LLM 输出正是不可信数据；把结构化校验当地基而非装饰，可预测、可校验、类型安全、自动重试这些能力才能自然长出来。

## 事故回放：八天里到底混进了多少坏数据

回到「金额写成约一万元」。批处理崩溃后，团队想回答一个朴素的问题：这八天到底混进了多少条坏数据？结果发现无从查起——落库表里 `amount` 是 `VARCHAR` 类型（因为当初为了「兼容模型的各种输出」故意设成了字符串），坏数据和好数据混在一起，只能写一堆正则去反向识别哪些「不是合法数字」。跑完统计吓一跳：八天 2.6 万条记录里，有 1.9% 的 `amount` 无法直接转成数字，其中大部分是带货币符号或千分位（还能抢救），但有 37 条是「约一万元」「一万多」这类纯中文描述，彻底无法还原准确金额，只能逐条回原始邮件人工重录。

这个事故的教训有两层。表层教训是「amount 该用数字类型」；深层教训是**当初把数据库字段设成 VARCHAR「兼容一切」，恰恰是放弃了校验、把鸿沟从模型侧推给了数据库侧**。正确的做法是反过来——在模型输出与数据库之间架一道 `output_type=Invoice` 的强类型闸门，让 `amount: float` 成为一个「不合规就进不来」的硬约束。优化后，坏数据在校验层就被挡下并触发重试，落库的每一条 `amount` 都保证是 `float`，数据库字段也能安心设成 `DECIMAL`。这道闸门就是下一节要拆解的 `output_type` 三层机制。
