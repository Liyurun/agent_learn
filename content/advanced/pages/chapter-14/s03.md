## 真实问题

发票抽取上线一段时间后，业务提了个新需求：抽取到 `vendor`（供应商）后，要顺带查一下这家供应商的信用评级和是否在合作名单里。第一版实现里，工程师把「查供应商信息」的逻辑硬写进了 prompt——把整个供应商名录（三千多家、几万 token）塞进系统提示，让模型「自己在里面找」。结果三件事同时爆发：一是每次调用的 input token 暴涨，成本翻了五倍；二是名录一更新就要改 prompt、重新测试；三是模型经常「找错」或「编造」一个名录里根本没有的评级。团队这才明白：**「查名录」这种确定性的、该由代码干的活，不该塞进 prompt 让模型去猜，而应该做成一个「工具」，让模型在需要时来调用。**

这一节讲 PydanticAI 怎么注册工具，以及一个让工程师直呼省心的能力——**工具的参数 Schema 从类型标注和 docstring 自动生成，无需手写 JSON**。

## 原理：两个装饰器与自动 Schema

PydanticAI 官方文档给出三种注册工具的方式 [来源](https://ai.pydantic.dev/tools/)：

- `@agent.tool`：**默认**装饰器，用于需要访问上下文（`RunContext`，从而拿到依赖）的工具；
- `@agent.tool_plain`：用于**不**需要上下文的工具（比如掷骰子、取当前时间这类无依赖的纯函数）；
- 通过 `Agent(..., tools=[...])` 构造参数注册，可传普通函数或 `Tool` 实例，便于复用与精细控制。

真正体现「工程化手感」的是 Schema 的自动生成。官方文档明确：**函数参数从函数签名中抽取，除 `RunContext` 外的所有参数都用来构建该工具的 Schema；PydanticAI 还会抽取 docstring，并借助 griffe 从 docstring 里提取参数描述、加进 Schema** [来源](https://ai.pydantic.dev/tools/)。griffe 支持 google、numpy、sphinx 三种 docstring 风格，PydanticAI 会自动推断，也可用 `docstring_format` 显式指定，还能用 `require_parameter_descriptions=True` 强制每个参数都有描述。

这意味着你写工具时的心智负担极低：
```text
你写的（普通 Python 函数 + 类型标注 + docstring）：
    def check_vendor(ctx, name: str) -> str:
        """校验供应商是否在合作名单。
        Args:
            name: 供应商名称
        """
        ...
        │
        ▼  PydanticAI + griffe 自动转换
模型收到的（JSON Schema，你一行没写）：
    {
      "name": "check_vendor",
      "description": "校验供应商是否在合作名单。",
      "parameters": {
        "properties": {"name": {"type": "string", "description": "供应商名称"}},
        "required": ["name"]
      }
    }
```
## 现象与输入：工具 vs 结构化输出，别搞混

初学者常把「注册工具」和「结构化输出」搞混，其实它们解决的是不同问题。官方文档在「Function Tools vs. Structured Outputs」一节点明：两者都用模型的「tools/functions」API，一个模型可能同时拥有多个工具——有些是普通函数工具，有些是用来结束运行、产出最终输出的「输出工具」[来源](https://ai.pydantic.dev/tools/)。用一张表分清：

| 对比 | `@agent.tool`（工具） | `output_type`（结构化输出） |
|---|---|---|
| 解决什么 | 让 Agent「能做事」（查库、调 API、算数） | 让 Agent「输出规整」（返回可校验的结构） |
| 发生时机 | 循环中间，可多次调用，结果回传给模型 | 循环末尾，产出最终结果，结束运行 |
| 类型标注的作用 | 生成工具的参数 Schema | 生成最终输出的 Schema |
| 对应书中原理 | 第 6 章工具机制、第 8 章 Function Calling | 第 8 章 Function Calling 强制结构化 |

一个记忆口诀：**工具管「过程中怎么获取信息」，output_type 管「最后怎么把结果交出来」。** 两者常常配合——发票 Agent 先用 `check_vendor` 工具查名单（过程），最后用 `output_type=Invoice` 把结果整理成结构化对象（结果）。官方还有一个专门的「输出函数（output functions）」概念：它像工具，但模型被强制调用其中之一、调用即结束运行、结果不回传给模型 [来源](https://ai.pydantic.dev/output/)——这是介于「工具」和「结构化输出」之间的第三种形态。

## 最小可运行演示

我们不联网、不用 API Key，用纯 Python 复刻「从函数签名 + docstring 自动生成参数 Schema」这一核心能力，让你看清 PydanticAI 到底帮你省了什么。
```python
"""教学参考实现：复刻 PydanticAI「从类型标注 + docstring 自动生成工具 Schema」。"""
import inspect
import re


def build_tool_schema(func) -> dict:
    """从函数签名和 docstring 生成 JSON Schema（简化版 griffe 行为）。"""
    sig = inspect.signature(func)
    doc = inspect.getdoc(func) or ""
    ## 抽取一句话描述（docstring 首行）
    summary = doc.split("\n")[0].strip()
    ## 抽取 Args: 段落里的 "参数名: 描述"（只匹配带缩进的参数行，排除 Args: 本身）
    param_docs = dict(re.findall(r"^[ \t]+(\w+):[ \t]*(.+)$", doc, re.M))
    py_to_json = {"str": "string", "int": "integer", "float": "number", "bool": "boolean"}

    properties, required = {}, []
    for pname, param in sig.parameters.items():
        if pname == "ctx":                      ## RunContext 不进 Schema
            continue
        ann = param.annotation.__name__ if param.annotation is not inspect._empty else "str"
        properties[pname] = {"type": py_to_json.get(ann, "string")}
        if pname in param_docs:
            properties[pname]["description"] = param_docs[pname]
        if param.default is inspect._empty:
            required.append(pname)
    return {"name": func.__name__, "description": summary,
            "parameters": {"type": "object", "properties": properties, "required": required}}


def check_vendor(ctx, name: str, strict: bool = True) -> str:
    """校验供应商是否在合作名单里。

    Args:
        name: 供应商名称，例如 星辰科技
        strict: 是否严格匹配大小写
    """
    return "in_whitelist"


if __name__ == "__main__":
    import json
    print(json.dumps(build_tool_schema(check_vendor), ensure_ascii=False, indent=2))
```
保存为 `auto_schema.py`，运行 `python auto_schema.py`。完整预期输出：
```text
{
  "name": "check_vendor",
  "description": "校验供应商是否在合作名单里。",
  "parameters": {
    "type": "object",
    "properties": {
      "name": {
        "type": "string",
        "description": "供应商名称，例如 星辰科技"
      },
      "strict": {
        "type": "boolean",
        "description": "是否严格匹配大小写"
      }
    },
    "required": [
      "name"
    ]
  }
}
```
看清楚这段输出的价值：你只写了一个带类型标注和 docstring 的普通函数，`name` 的类型（`string`）、描述（「供应商名称」）、必填性（`strict` 有默认值故不在 `required` 里），全都被自动推导出来。**在没有这个能力的框架里，上面这份 JSON 要你手写、手维护，函数签名一改还得记得同步改 Schema，极易漂移出 bug。** PydanticAI 用类型系统当唯一事实来源，从根上消灭了这类漂移。

## 真实系统对应

**官方公开机制**：`@agent.tool`（需上下文）与 `@agent.tool_plain`（无需上下文）是官方推荐的两个装饰器；参数 Schema 从函数签名抽取、`RunContext` 参数被排除、docstring 经 griffe 解析成参数描述；若单参数是对象类型（dataclass/TypedDict/Pydantic 模型），Schema 会简化为就是那个对象 [来源](https://ai.pydantic.dev/tools/)。工具可返回任何 Pydantic 能序列化为 JSON 的东西。**通用工程模式**：「用类型标注当唯一事实来源、自动派生 Schema」这一思路，可迁移到任何需要暴露工具给 LLM 的系统，避免手写 Schema 的漂移。**教学参考实现**：上面的 `build_tool_schema` 是极简复刻，只覆盖标量类型和 google 风格 docstring，真实的 griffe 支持远更丰富的类型与三种 docstring 风格。

需要点明边界：具体的 Schema 字段、`docstring_format` 可选值、`require_parameter_descriptions` 行为，以当前官方文档为准；本节讲「自动派生」这个稳定机制，不把某次检索到的字段拼写写成永久承诺。

## 生产踩坑

| 症状 | 根因 | 如何观测与复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| 把确定性查询塞进 prompt 让模型猜 | 没意识到该做成工具 | 统计系统提示 token 占比与查错率 | 把查询逻辑抽成 `@agent.tool` | 极少量静态知识可留在提示里 |
| 改了函数签名 Schema 没同步 | 手写并维护了独立 Schema | 改参数后看模型是否按旧 Schema 调 | 用类型标注自动派生，删掉手写 Schema | 需完全自定义 Schema 的特殊工具 |
| 模型不知道参数含义、频繁传错 | 工具无 docstring 或参数无描述 | 去掉 docstring 看传参正确率下降 | 补 docstring，必要时 `require_parameter_descriptions=True` | 参数名已极其自解释时可放宽 |
| 无依赖工具误用 `@agent.tool` | 混淆两个装饰器 | 无依赖工具的 `ctx` 参数从未被用 | 无依赖用 `@agent.tool_plain` 更清晰 | 未来可能加依赖时先留 ctx 也可 |
| 工具越加越多、模型选错 | 同时暴露工具过多且语义重叠 | 记录候选工具与实际调用分布 | 收敛工具集、两阶段路由、写清负向边界 | 领域本需大量工具时另设 |
| 工具返回值无法序列化 | 返回了非 JSON 可序列化对象 | 返回一个自定义类实例观察报错 | 返回可被 Pydantic 序列化的类型 | 高级多模态输出见官方 advanced 文档 |

## 思考：为什么说「把确定性查询塞进 prompt」是反模式，而做成工具才对？

### 回答

有三重代价，恰好对应开头故障的三个爆发点。第一是成本：把三千家供应商名录塞进系统提示，意味着每次调用都要重发这几万 token，而模型是无状态的、每轮重发历史（第 8 章的成本结构），多轮下来 token 线性放大，成本翻几倍。做成工具后，名录留在代码/数据库里，模型只在需要时用一个极小的 `check_vendor(name=...)` 调用去查，请求体里只有工具定义（几十 token），而非整个名录。第二是可维护性：名录更新时，塞进 prompt 的方案要改提示、重新测试、重新评估；工具方案只改工具函数背后的数据源，Agent 定义一行不动。第三是可靠性：让模型「在几万 token 里自己找」，它会找错、会编造一个不存在的评级（幻觉）；而工具是确定性代码，查到就是查到、查不到就返回明确结果，不给幻觉留空间。一句话——**确定性的活交给代码（工具），不确定的判断才交给模型**，这是 workflow 与 Agent 分工的微观体现。

### 面试精简表达

塞进 prompt 有三重代价：token 成本随轮次放大、数据更新要改提示重测、模型会在长文本里找错或编造；做成工具则请求体只带小调用、数据源独立维护、查询确定无幻觉。原则是确定性的活交给代码。

## 机制推导：docstring 为什么值得你认真写

很多人写工具函数时把 docstring 当可有可无的注释，但在 PydanticAI 里，docstring 是**直接发给模型、影响模型选工具和传参正确率的一等公民**。因为参数描述会经 griffe 抽取进 Schema，模型看到的不是光秃秃的 `name: string`，而是 `name: string（供应商名称，例如 星辰科技）`。这条描述的作用是双向的：正向告诉模型「这个参数该填什么」，负向（如果你写了）告诉模型「什么时候不该用这个工具」。

由此推出两条工程实践。其一，工具的一句话描述（docstring 首行）要写清「这个工具在什么场景下用」，因为当多个工具语义相近时，模型主要靠描述来区分——描述含糊，模型就会在近义工具间反复选错。其二，对关键参数用 `require_parameter_descriptions=True` 强制描述，让「忘写描述」在开发期就抛 `UserError`，而不是等到线上模型频繁传错才发现 [来源](https://ai.pydantic.dev/tools/)。把 docstring 当成「写给模型的 API 文档」来对待，而不是「写给后来人的注释」，你的工具调用正确率会明显提升。这也呼应第 8 章「工具描述质量直接决定选择准确率」的结论。
