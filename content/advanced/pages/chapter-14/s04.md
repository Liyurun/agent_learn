## 真实问题

发票 Agent 的 `check_vendor` 工具第一版是这么写的：函数内部直接 `import` 了一个全局的数据库连接对象，然后 `db.query("SELECT ... FROM vendor_whitelist WHERE name=...")`。功能上没问题，但麻烦在写单元测试的时候集中爆发了。测试同学想验证「供应商不在白名单时，工具应该触发一次纠错」，结果发现：要跑这个测试，得先连上一个真实的数据库，往里塞好测试数据，测完再清理；CI（Continuous Integration，持续集成）流水线里没有这个数据库，测试直接挂掉；两个测试并行跑时，还会互相污染对方写进去的测试数据。一个本该几毫秒跑完的纯逻辑测试，被一个硬编码的数据库依赖拖成了「必须连真实系统才能跑」的集成测试。

问题的本质是：**工具函数把「它需要什么」和「这个东西从哪来」焊死在了一起。** `check_vendor` 既关心「怎么判断在不在白名单」（业务逻辑），又关心「白名单从哪个数据库连接来」（依赖获取），两件事耦合在一起，就没法在测试里用一个假的白名单替换真库。这一节讲 PydanticAI 怎么用依赖注入（Dependency Injection）把这两件事解耦，让「测试注入假库、生产注入真库、工具代码一行不改」成为可能。

## 原理：deps_type 声明依赖，RunContext 取用依赖

PydanticAI 的依赖注入围绕两个东西展开 [来源](https://ai.pydantic.dev/dependencies/)：

- **`deps_type`**：在构造 `Agent(..., deps_type=MyDeps)` 时声明「这个 Agent 运行时需要一包依赖，类型是 `MyDeps`」。`MyDeps` 通常是一个 dataclass，把 Agent 运行需要的连接、配置、客户端、白名单等都装进去。官方推荐用 dataclass，因为它能带来良好的类型检查手感。
- **`RunContext`**：工具函数的第一个参数声明成 `ctx: RunContext[MyDeps]`，就能通过 `ctx.deps` 拿到运行时注入的那包依赖。官方文档说明 `RunContext` 是一个泛型 dataclass，除了 `deps`，还携带 `model`（当前模型实例）、`usage`（累计用量）等执行环境信息 [来源](https://ai.pydantic.dev/dependencies/)。

运行时，你在 `agent.run_sync(prompt, deps=真实的MyDeps实例)` 里把依赖传进去，PydanticAI 会把它顺着 `RunContext` 送到每一个 `@agent.tool` 工具、系统提示函数和输出校验器手里。画成图：
```text
构造期：Agent(deps_type=Deps)        ← 声明"我需要一包 Deps"
              │
运行期：agent.run_sync(prompt, deps=真实实例)  ← 注入具体依赖
              │
              ▼  PydanticAI 顺着 RunContext 分发
      ┌───────┴────────┬──────────────┐
      ▼                ▼              ▼
  @agent.tool     系统提示函数     输出校验器
  ctx.deps.xxx    ctx.deps.xxx    ctx.deps.xxx
```
关键收益在测试。官方文档专门讲了：写测试时不必构造真实依赖，可以用 `Agent.override(deps=假的实例)` 在一段代码块内临时替换掉依赖 [来源](https://ai.pydantic.dev/dependencies/)。于是同一个工具函数，生产注入连真库的 `Deps`、测试注入装着假白名单的 `Deps`，**工具代码一个字都不用改**。

## 现象与输入：耦合 vs 解耦

把「焊死依赖」和「注入依赖」两种写法并排看，解耦的价值就清楚了：
```text
耦合写法（难测）：                          注入写法（易测）：
def check_vendor(name):                     @dataclass
    db = get_global_db()   # 焊死！          class Deps:
    return name in db.whitelist()               whitelist: set[str]  # 依赖被声明

                                            @agent.tool
测试时：必须连真实 db、塞数据、清理          def check_vendor(ctx, name):
CI 里没有 db → 测试挂                            return name in ctx.deps.whitelist
并行测试互相污染                                        │
                                            测试：override(deps=Deps({"星辰科技"}))
                                            生产：run(deps=Deps(从真库加载的集合))
                                            工具代码一行不改，纯逻辑、毫秒级、可并行
```
左边那些痛苦——测试要连真库、CI 挂、并行污染——都来自「依赖从哪来」被写死在函数体内。右边把「依赖是什么」（`Deps` 的字段）和「依赖从哪来」（`run`/`override` 时才决定）分开，工具只管用 `ctx.deps.whitelist`，不关心它是真库查的还是测试塞的。

## 最小可运行演示

我们不联网、不用 API Key，用纯 Python 复刻「同一个工具函数，注入不同依赖，行为随之改变」的依赖注入骨架，并演示 `override` 式的测试替换。
```python
"""教学参考实现：复刻 deps_type + RunContext 依赖注入，及 override 式测试替换。"""
from contextlib import contextmanager
from dataclasses import dataclass, field


@dataclass
class Deps:
    """一包依赖：白名单从哪来，运行/测试时才决定。"""
    vendor_whitelist: set[str]


@dataclass
class RunContext:
    """教学替身：真实 RunContext 还携带 model/usage 等，这里只留 deps。"""
    deps: Deps


@dataclass
class Agent:
    """极简 Agent：持有默认依赖，支持 override 在代码块内临时替换。"""
    default_deps: Deps
    _overridden: Deps | None = field(default=None)

    @contextmanager
    def override(self, deps: Deps):
        self._overridden = deps          ## 进入代码块：临时替换
        try:
            yield
        finally:
            self._overridden = None      ## 退出代码块：自动还原

    def run(self, name: str) -> str:
        deps = self._overridden or self.default_deps
        return check_vendor(RunContext(deps=deps), name)


def check_vendor(ctx: RunContext, name: str) -> str:
    """工具函数：只管用 ctx.deps.whitelist，不关心它从哪来。"""
    return "in_whitelist" if name in ctx.deps.vendor_whitelist else "NOT_in_whitelist"


if __name__ == "__main__":
    ## 生产：注入"真库加载的"白名单
    prod = Agent(default_deps=Deps(vendor_whitelist={"星辰科技", "云海数据"}))
    print("生产依赖下 查 星辰科技 ->", prod.run("星辰科技"))
    print("生产依赖下 查 皮包公司 ->", prod.run("皮包公司"))

    ## 测试：用 override 注入"假白名单"，工具代码一行不改
    with prod.override(Deps(vendor_whitelist={"皮包公司"})):
        print("测试override下 查 皮包公司 ->", prod.run("皮包公司"))
    print("退出override后 查 皮包公司 ->", prod.run("皮包公司"))
```
保存为 `deps_inject.py`，运行 `python deps_inject.py`。完整预期输出：
```text
生产依赖下 查 星辰科技 -> in_whitelist
生产依赖下 查 皮包公司 -> NOT_in_whitelist
测试override下 查 皮包公司 -> in_whitelist
退出override后 查 皮包公司 -> NOT_in_whitelist
```
看这段轨迹：`check_vendor` 从头到尾没变过，但因为注入的 `Deps` 不同，同一次「查皮包公司」在生产依赖下返回 `NOT_in_whitelist`、在 `override` 的假依赖下返回 `in_whitelist`，退出代码块后又自动还原。这就是依赖注入让工具「可测试」的核心手感——**换依赖，不换代码**。真实的 PydanticAI 把这套封装成 `deps_type` + `RunContext` + `Agent.override`，还额外解决了向系统提示、输出校验器分发依赖的问题。

## 真实系统对应

**官方公开机制**：PydanticAI 通过 `deps_type` 声明依赖类型、`RunContext[Deps]` 让工具/系统提示/输出校验器访问 `ctx.deps`，并推荐用 dataclass 承载依赖以获得类型检查；测试时用 `Agent.override` 在代码块内替换依赖，避免连真实系统 [来源](https://ai.pydantic.dev/dependencies/)。`RunContext` 还携带 `model`、`usage` 等执行环境信息 [来源](https://ai.pydantic.dev/dependencies/)。**通用工程模式**：依赖注入是通用的解耦手法（Spring、FastAPI 都在用），核心是「声明依赖类型 + 运行时注入具体实例」，可迁移到任何自建 Agent 框架。**教学参考实现**：上面的 `Agent`/`RunContext` 是极简替身，只保留 `deps` 与 `override`，真实实现的分发路径和生命周期管理远更复杂。

需要点明边界：依赖注入让「单元测试」不必连真实系统，但它不替代「集成测试」——你仍需要少量真的连数据库、连模型 API 的端到端测试来验证真实链路。`override` 是为测试和局部替换设计的，不是让你在生产逻辑里到处切换依赖的开关。

## 生产踩坑

| 症状 | 根因 | 如何观测与复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| 单测必须连真实数据库才能跑 | 工具内部硬编码依赖获取 | 在无数据库的 CI 环境跑单测看是否挂 | 用 `deps_type` 声明、`RunContext` 取用 | 集成测试本就该连真实系统 |
| 并行测试互相污染数据 | 共享同一份全局可变依赖 | 两个测试并行写同一份状态复现 | 每个测试 `override` 独立的假依赖 | 只读依赖并行安全 |
| 依赖散落在各处、难追踪 | 没有统一的依赖容器 | 搜索工具函数里的全局 `import` | 把依赖收进一个 dataclass 统一注入 | 极简单 Agent 无外部依赖时可省 |
| override 忘了还原污染后续测试 | 手工替换未用上下文管理器 | 一个测试改了全局态后跑下一个 | 用 `with agent.override(...)` 自动还原 | 单次脚本运行影响可忽略 |
| 依赖类型与实际注入不符 | `deps_type` 与传入实例漂移 | 传入缺字段的 deps 观察运行时报错 | 用 dataclass + 类型检查器提前发现 | 动态依赖需自行校验 |
| 把非依赖也塞进 deps | 混淆「运行时依赖」与「配置常量」 | deps 里出现大量不变常量 | 常量走模块级配置，deps 只放运行时才知的 | 少量配置随 deps 传也可接受 |

## 思考：依赖注入除了「好测试」，对生产架构还有什么价值？

### 回答

「好测试」只是最显眼的收益，依赖注入对生产架构至少还有三重价值。第一是**环境隔离**：同一个 Agent，开发环境注入指向测试库的 `Deps`、预发环境注入指向预发库的 `Deps`、生产注入指向生产库的 `Deps`，Agent 定义完全不变，环境差异全部收敛到「注入哪包依赖」这一处，避免了「靠 if 判断环境」散落各处的坏味道。第二是**关注点分离**：工具函数只表达业务逻辑（「在不在白名单」），不掺杂「连接怎么建、连接池多大、超时多少」这些基础设施细节，代码更聚焦、更易读、更易复用。第三是**可替换性与演进**：今天白名单来自 MySQL，明天要换成 Redis 缓存或远程配置中心，只需改 `Deps` 的构造和字段来源，所有用到 `ctx.deps.whitelist` 的工具无感。这三点合起来，本质是**把「不稳定的、随环境变的东西」从「稳定的业务逻辑」里挤出去**，让核心逻辑保持纯净稳定——这正是可维护软件的通用追求，PydanticAI 只是把它做成了 Agent 的一等公民。

### 面试精简表达

依赖注入不止好测试：还能环境隔离（开发/预发/生产注入不同 deps，Agent 不变）、关注点分离（工具只写业务逻辑不掺基础设施）、可替换（换数据源只改 deps 构造）。本质是把随环境变的东西从稳定业务逻辑里挤出去。

## 机制推导：为什么依赖要从 RunContext 走，而不是直接全局访问

有人会问：既然工具要用白名单，为什么不让它直接 `import` 全局白名单，非要绕一道 `ctx.deps`？答案在「运行时才知道」这五个字。很多依赖在构造 Agent 时根本不存在——同一个 Agent 实例可能被不同用户、不同请求复用，每个请求的白名单版本、汇率快照、用户身份、数据库连接可能都不同。如果工具直接访问全局态，就没法为「这一次运行」定制依赖；而 `RunContext` 恰恰把「这一次运行的上下文」显式地传给工具，让每次 `run` 都能带上自己那份 `deps`。

这也解释了为什么 `RunContext` 还携带 `model`、`usage` 等信息 [来源](https://ai.pydantic.dev/dependencies/)：它是「本次运行的执行环境」的载体，依赖只是其中一部分。工具通过它不仅能拿依赖，还能知道「我这次跑在哪个模型上、已经花了多少 token」。把依赖收进 `RunContext` 而非全局，本质是**用显式的运行上下文替代隐式的全局状态**——这让 Agent 天然支持并发（每次运行的上下文互不干扰）、天然可测试（换上下文即换依赖），是「无状态服务 + 请求级上下文」这一经典 Web 架构在 Agent 世界里的翻版。
