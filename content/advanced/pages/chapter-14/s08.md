## 真实问题

发票抽取流水线稳定上线后，团队被拉去做一次技术评审：其他小组也想上 Agent，问了一连串「到底该不该用 PydanticAI、什么时候不该用、上线要注意什么」的问题。评审会上暴露出两类典型误区。一类是「锤子综合征」——有人拿 PydanticAI 去做一个「把用户输入的一段话原样返回摘要」的纯文本任务，套上一堆 `output_type` 和工具，结果比直接调模型 API 还慢还复杂。另一类是「上线即裸奔」——有小组把 demo 直接推生产，没有重试上限、没有可观测、依赖硬编码、没有离线测试，重演了「金额写成约一万元」的老路。

这一节做两件事收口全章：先给出 PydanticAI 的**选型边界**（什么场景适合、什么场景不适合、和其他框架怎么比），再汇成一张覆盖全章各环节的**生产建议矩阵**和一个可运行的**选型/诊断器**，最后用多道「思考+回答」对齐高频面试题，把本章方法论钉成可复用的判断力。

## 原理：先分清「要不要用」，再决定「怎么用好」

选型判断分两步走。**第一步，判断这个任务要不要用 Agent 框架**（呼应第 3 章）：
```text
这个任务的输出要被下游程序消费吗？
  否（纯文本问答/闲聊/摘要给人看）→ 直接调模型 API 即可，别套框架
  是 → 继续
输入格式高度统一、规则能写死吗？
  是（定长字段/固定模板）→ 纯 workflow（正则/解析代码）更快更稳更便宜
  否（自由文本、多样表达）→ 需要模型的语言理解 → 值得上 Agent 框架
```
**第二步，在「决定用 Agent 框架」后，判断 PydanticAI 相比其他框架的适配度**。PydanticAI 的差异化定位很清晰——它由 Pydantic 团队出品，把「类型安全 + 数据校验」作为一等公民 [来源](https://ai.pydantic.dev/)。据此归纳它的适配光谱：

| 场景特征 | PydanticAI 适配度 | 原因 |
|---|---|---|
| 输出要结构化、被下游程序消费 | 高 | `output_type` + Pydantic 校验是立身之本 |
| 团队已用 Pydantic/FastAPI，重视类型 | 高 | 心智模型一致，类型安全手感延续 |
| 要求可测试、可观测的生产级交付 | 高 | 依赖注入 + `TestModel` + Logfire 一等公民 |
| 纯文本问答、无结构、无下游消费 | 低 | 套框架是过度工程，直接调 API |
| 需要复杂多 Agent 编排/图工作流 | 视情况 | PydanticAI 有 Graph 能力，但重编排也可结合专用编排框架 |

一句话选型口诀：**输出要被程序吃、且团队重视类型安全与可测试性，PydanticAI 是强选项；纯给人看的文本任务，别上框架。**

## 现象与输入：三种「用错」的样子

把评审会暴露的误用画成对照，帮你在自己项目里对号入座：
```text
误用A「锤子综合征」：            误用B「上线即裸奔」：           误用C「框架错配」：
纯文本摘要也套 output_type       demo 直接推生产：             用它硬做重编排多Agent图，
+ 一堆工具                        无重试上限/无观测/            却不用其编排能力，
→ 比直接调 API 还慢还复杂         依赖硬编码/无离线测试         强行拼胶水
纠正：无下游消费就别套框架       纠正：补齐本章六个环节        纠正：评估是否结合专用编排
```
三种误用的共同根因，是**没先想清「要不要用、用哪个环节」就一把梭**。选型不是「PydanticAI 好不好」的问题，而是「这个任务的特征匹不匹配 PydanticAI 的强项」的问题。

## 最小可运行演示

我们不联网、不用 API Key，把上面两步选型逻辑固化成一个可运行的「选型/诊断器」，输入任务特征，输出「该不该用、用哪条路径」，避免拍脑袋。
```python
"""教学参考实现：PydanticAI 选型/诊断器——把选型判断固化成可复核的规则树。"""
from dataclasses import dataclass


@dataclass
class TaskProfile:
    consumed_by_program: bool     ## 输出是否被下游程序消费
    input_is_uniform: bool        ## 输入格式是否高度统一、可写死规则
    team_uses_pydantic: bool      ## 团队是否已用 Pydantic/FastAPI、重视类型
    needs_heavy_orchestration: bool  ## 是否需要复杂多 Agent 编排


def recommend(p: TaskProfile) -> str:
    ## 第一步：要不要用 Agent 框架
    if not p.consumed_by_program:
        return "直接调模型 API：纯文本给人看，套框架是过度工程"
    if p.input_is_uniform:
        return "纯 workflow（正则/解析）：格式统一、规则可写死，更快更稳更便宜"
    ## 第二步：用 Agent 框架的话，PydanticAI 适配度
    reasons = ["输出结构化且被程序消费 → output_type 立身之本"]
    if p.team_uses_pydantic:
        reasons.append("团队重类型 → 心智模型一致")
    verdict = "强烈推荐 PydanticAI"
    if p.needs_heavy_orchestration:
        verdict = "推荐 PydanticAI，但重编排部分评估结合专用编排框架"
        reasons.append("需重编排 → 单一 Agent 框架可能不够")
    return f"{verdict}（理由：{'；'.join(reasons)}）"


if __name__ == "__main__":
    cases = {
        "发票抽取（本章）": TaskProfile(True, False, True, False),
        "纯文本闲聊摘要": TaskProfile(False, False, True, False),
        "定长模板解析": TaskProfile(True, True, True, False),
        "重编排多Agent图": TaskProfile(True, False, True, True),
    }
    for name, prof in cases.items():
        print(f"[{name}] -> {recommend(prof)}")
```
保存为 `selector.py`，运行 `python selector.py`。完整预期输出：
```text
[发票抽取（本章）] -> 强烈推荐 PydanticAI（理由：输出结构化且被程序消费 → output_type 立身之本；团队重类型 → 心智模型一致）
[纯文本闲聊摘要] -> 直接调模型 API：纯文本给人看，套框架是过度工程
[定长模板解析] -> 纯 workflow（正则/解析）：格式统一、规则可写死，更快更稳更便宜
[重编排多Agent图] -> 推荐 PydanticAI，但重编排部分评估结合专用编排框架
```
这个诊断器把「选型」从玄学变成了可复核的规则树：发票抽取（结构化、自由文本、团队重类型）落进「强烈推荐」；纯文本摘要（无下游消费）直接被劝退别套框架；定长模板（可写死规则）被导向纯 workflow；重编排场景给出「推荐但需评估结合编排框架」的分寸答案。**把选型逻辑写成代码的价值，是逼你把「拍脑袋的感觉」拆成「可以逐条辩论的判据」**——评审会上有了它，讨论就从「我觉得该用」变成「这条任务特征匹配哪条规则」。

## 真实系统对应

**官方公开机制**：PydanticAI 官方定位为「用类型提示保证类型安全、把 Pydantic 校验带到 GenAI 应用」的框架，核心能力是结构化输出、工具、依赖注入、可观测（Logfire）、可测试 [来源](https://ai.pydantic.dev/)；官方仓库为 MIT 许可 [来源](https://github.com/pydantic/pydantic-ai)。**通用工程模式**：「先判要不要用 Agent（第 3 章），再判框架适配度」这套两步选型法可迁移到任何 Agent 框架选型；三条误用（过度工程、上线裸奔、框架错配）是通用反模式。**教学参考实现**：上面的 `recommend` 是把选型判据固化的教学工具，判据是从公开定位提炼的可迁移规则，不代表任何官方选型评分。

需要点明边界：框架对比会随版本快速变化——各框架的编排能力、生态、性能都在演进，本节讲「按任务特征匹配框架强项」这一稳定方法，不把某次检索到的功能对比写成永久结论；具体功能以各框架当前官方文档为准。选型也不是非此即彼，实践中常见「PydanticAI 管结构化 Agent + 专用编排框架管多 Agent 流程」的组合。

## 生产建议：PydanticAI 全章环节症状矩阵

下面把全章各环节的坑汇成一张矩阵，每行都是真实会发生、可观测、有修复、也有不适用边界的条目，作为上线前的检查清单。

| 症状 | 根因 | 如何观测与复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| demo 通过、上线偶发解析崩溃 | 无结构约束、只肉眼验收 | 抓一周线上输出统计字段类型分布 | 用 `output_type` 强制结构（第2节） | 纯文本问答无需结构 |
| 以为声明结构就 100% 不出错 | 忽视重试有上限 | 喂无法抽出的文本看最终抛错 | 写重试耗尽的兜底分支（转人工） | 结构极简、失败率极低时 |
| 加 prompt 约束仍偶发坏值 | 纯提示无强制力 | 多样措辞回放统计违背率 | 约束落到 Schema+校验而非提示 | 纯文本任务本无约束 |
| 把确定性查询塞进 prompt | 没做成工具 | 统计系统提示 token 占比与查错率 | 抽成 `@agent.tool`（第3节） | 极少量静态知识可留提示 |
| 改函数签名 Schema 没同步 | 手写维护了独立 Schema | 改参数看模型是否按旧 Schema 调 | 用类型标注自动派生 Schema | 需完全自定义 Schema 的工具 |
| 单测必须连真实库/模型 | 依赖硬编码、直连模型 | 无库无网的 CI 环境跑单测看是否挂 | 依赖注入+`TestModel`（第4/6节） | 集成测试本就连真实系统 |
| 并行测试互相污染 | 共享全局可变依赖 | 两测试并行写同一状态复现 | 每测试 `override` 独立假依赖 | 只读依赖并行安全 |
| 结构合规但业务非法数据落库 | 只做类型校验无业务校验 | 构造负数金额/黑名单供应商 | `ModelRetry`/输出校验器（第5节） | 无业务约束的纯抽取 |
| 抛 ModelRetry 模型仍反复错 | 提示含糊无可操作线索 | 把提示改成只写「错误」看纠对率 | 提示写清「哪错+正确选项」 | 模型能力上限需换路径 |
| 重试烧光 token 不收敛 | 无重试上限或错误不可纠 | 让工具永远抛 ModelRetry 复现 | 设 `retries` 上限、耗尽转人工 | 可纠的瞬时错误可多试 |
| 重试导致副作用重复执行 | 非幂等工具无幂等保护 | 让扣款工具首次成功后被重试 | 副作用工具绑幂等键（第8章） | 只读工具重试本就安全 |
| 崩了才知道无法定位哪层坏 | 线上无埋点、Agent 黑盒 | 关掉 instrument 复现查不到中间态 | `instrument_pydantic_ai()`（第6节） | 极低价值一次性脚本 |
| CI 偷偷联网真调模型烧钱 | 没设请求保险丝 | 误留一处真实 model 未 override | `ALLOW_MODEL_REQUESTS=False` | 明确集成测试阶段允许 |
| 观测把 PII 明文写进 span | 未脱敏就埋点 | 检查 span 是否含身份证/手机号 | 埋点前最小化并脱敏 PII | 已合规脱敏字段可保留 |
| 纯文本任务硬套 output_type | 锤子综合征、过度工程 | 对比直接调 API 的复杂度与延迟 | 无下游消费就别套框架 | 确需结构化的任务除外 |
| 依赖硬编码无法灰度/多环境 | 白名单/汇率写死代码 | 想换测试库发现要改代码 | 全走 deps 注入按环境切换 | 无环境差异的内部工具 |

TTL（Time To Live，生存时间）适用于可过期的缓存与配置，不应用于删除法律保留数据；上线前应对照本表逐条核对，而非等故障复现才补。

## 思考：面试官问「为什么选 PydanticAI 而不是别的 Agent 框架」，怎么答出水平？

### 回答

这道题考的不是「你会背 PydanticAI 的优点」，而是「你会不会按任务特征做技术选型」。低水平的答法是罗列特性——「它类型安全、有依赖注入、集成 Logfire」，这只是复述文档。高水平的答法要分三层。第一层，**先反问任务特征**：选型没有脱离场景的最优解，得先明确「输出要不要被下游程序消费、输入是不是自由文本、团队技术栈是什么」，这一步就体现你懂「选型是匹配而非崇拜」。第二层，**讲清 PydanticAI 的差异化定位**：它是 Pydantic 团队出品，把「数据校验/类型安全」这个他们最擅长的能力嫁接到 LLM 输出上，所以它的强项高度集中在「需要结构化输出、被程序消费、且团队重视类型安全与可测试性」的场景——这正是本章发票抽取这类任务的画像。第三层，**主动说边界**：如果是纯文本问答，套它是过度工程；如果是重量级多 Agent 编排，可能要结合专用编排框架。能把「先看场景→讲清差异化强项→主动认边界」这三层讲出来，面试官会立刻判断你是「按工程判断选型的人」，而不是「追新框架的人」。记住：**说得出一个框架不适合什么场景，比说得出它适合什么场景，更能证明你真的懂它。**

### 面试精简表达

不罗列特性，分三层：先问任务特征（输出是否被程序消费、是否自由文本、团队栈）；再讲 PydanticAI 差异化定位（Pydantic 团队把数据校验/类型安全嫁接到 LLM，强项集中在结构化输出+可测可观测）；最后主动认边界（纯文本别套、重编排结合专用框架）。能说清它不适合什么，才证明真懂。

## 思考：PydanticAI 的「类型安全」到底安全在哪？它能保证模型不出错吗？

### 回答

要拆成「类型安全保证什么」和「不保证什么」两面讲，才不会把它说成万能。**它保证的是「结构层面的确定性」**：`output_type=Invoice` 让 `result.output.amount` 一定是 `float`，你的 IDE 能补全、mypy 能静态检查、下游 `sum()` 不会因为吃到字符串而崩——错误从「线上运行时才炸」前移到了「写代码时就被发现」，这是类型安全最实在的价值。**但它保证不了「语义层面的正确性」**：类型系统能规定 `amount` 是 `float`，规定不了「这个 float 是不是这张发票的真实金额」——模型完全可能把 `12000` 抽成 `1200`，类型上完美、语义上错误。这就是为什么本章反复强调三道防线要分工：类型校验管结构（第 2 节）、`ModelRetry`/输出校验器管业务规则（第 5 节）、评估集和人工抽检管语义准确性（第 16 章）。把这三者混为一谈，是最常见的认知错误——有人以为「上了 PydanticAI 类型安全，模型就不会错了」，恰恰相反，类型安全只是把「结构错误」这一类问题根除了，「业务错误」和「语义错误」还得靠另外两道防线。能清晰区分「类型安全 = 结构确定性 ≠ 模型正确性」，说明你真正理解了这个框架的能力边界，而不是被「类型安全」这个词的光环唬住。

### 面试精简表达

类型安全保证「结构确定性」：output_type 让 amount 一定是 float，错误从运行时前移到编码期，IDE/mypy/下游都受益。但它不保证「语义正确」：模型可能把 12000 抽成 1200，类型完美语义错。三道防线分工：类型校验管结构、ModelRetry/校验器管业务、评估集管语义。别把「类型安全」当「模型不出错」。

## 思考：把本章六节压缩成一句话的「PydanticAI 心法」，你会怎么说？

### 回答

一句话心法是：**把 LLM 的输出当成一段需要被校验的不可信数据，然后用类型系统、工具、依赖注入、纠错重试、可观测和离线测试，把这段不可信数据一步步驯化成可预测、可校验、可测试、可维护、可观测的生产级结果。** 这句话之所以能统摄全章，是因为它抓住了 PydanticAI 的信念内核——别的框架默认「模型输出可以直接用」，PydanticAI 默认「模型输出是不可信的、必须校验」，于是本章六个环节全都是这个信念的自然推论：因为不可信，所以要用 `output_type` 强制结构（第 2 节）；因为要做确定性的事，所以抽成工具（第 3 节）；因为要能换环境、能测试，所以依赖注入（第 4 节）；因为校验会失败，所以要能纠错重试（第 5 节）；因为线上不确定，所以要可观测、可离线测试（第 6 节）；最后把它们组装成一条堵死真实故障的流水线（第 7 节）。回到开头「金额写成约一万元」——那个故障的深层病根，就是团队当初把「模型输出」当成了「可信数据」。本章从头到尾，其实只在纠正这一个认知：**LLM 会说话，但它说的话，得先过校验这一关才能算数。** 把这句心法记住，你不仅会用 PydanticAI，还能在任何框架里做出同样健壮的 LLM 应用。

### 面试精简表达

心法一句话：把 LLM 输出当需要校验的不可信数据，用类型/工具/依赖注入/纠错重试/可观测/离线测试把它驯化成生产级结果。六节都是「输出不可信」这一信念的推论，开头故障的病根就是把模型输出当成了可信数据。
