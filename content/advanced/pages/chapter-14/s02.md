## 真实问题

发票故障复盘会上，一位工程师提出一个看似合理的「快修方案」：在 prompt 里加一句「请务必把 amount 返回成纯数字，不要写中文」。上线后当天下午，坏数据确实少了，但第三天又冒出一条 `amount="10000元"`——模型这次「听话地」用了阿拉伯数字，却多带了个「元」字。团队这才意识到：**纯靠 prompt 约束是脆弱的，模型总能用你没预料到的方式「合理地」违背你**。他们需要的不是「更用力地祈祷模型听话」，而是一个「不听话就自动挡下并纠正」的机制。

这正是 `output_type` 存在的意义。它只是 `Agent(...)` 里的一个参数，但背后是一套精巧的三层机制。这一节把它彻底拆开——理解了这三层，你既会用框架，也能在面试里画着讲清「如何让 LLM 稳定返回结构化输出」这道高频题的底层原理。

## 原理：一个参数，三层机制

你只写了 `output_type=Invoice`，PydanticAI 在背后做了三件事。把它画成流程图，你就彻底懂了：
```text
你声明 output_type=Invoice（amount: float）
        │
        ▼
┌─────────────────────────────────────────────────┐
│ ① 机制层：把 Invoice 转成 JSON Schema，             │
│    默认借助模型的工具调用能力，告诉模型"必须按这个填" │
│    （回扣第 8 章：用 tool-choice 强制结构化）        │
└───────────────────┬─────────────────────────────┘
                    ▼
              模型返回一份 JSON
                    │
                    ▼
┌─────────────────────────────────────────────────┐
│ ② 校验层：用 Pydantic 强校验这份 JSON               │
│    amount 是 float 吗？必填字段都在吗？"约一万元"❌   │
└───────┬─────────────────────────────┬───────────┘
   校验通过                        校验失败
        │                              │
        ▼                              ▼
  返回 Invoice 对象        ┌───────────────────────────────┐
  （类型安全，可直接用）      │ ③ 兜底层：把 Pydantic 的校验错误    │
                            │    反馈给模型，让它自动重试         │
                            │    （本质是第 7 章"反思"的工程化）  │
                            └──────────────┬────────────────┘
                                           │
                                           └──▶ 回到 ② 再校验（有重试上限）
```
这三层——**机制层（工具调用强制）、校验层（Pydantic 校验）、兜底层（失败重试）**——就是「如何让 LLM 稳定返回结构化输出」的完整答案。它比「加一句 prompt」强在哪？强在②③是**确定性的、程序化的**：`"约一万元"` 无法转成 `float`，Pydantic 一定会拒绝，不受模型「这次心情好不好」影响；而重试时喂回去的不是含糊的「请返回数字」，而是 Pydantic 生成的精确错误信息「`amount` 输入应为有效数字」。

官方文档把③这一层称为「反思与自我纠错（Reflection and self-correction）」：校验错误（包括工具参数校验和输出校验）会被作为 `retry` 提示反馈给模型，让它重新尝试 [来源](https://ai.pydantic.dev/agents/)。

## 现象与输入：招牌示例逐行精读

先看官方 Output 文档的招牌示例，再逐行讲它每一行在做什么 [来源](https://ai.pydantic.dev/output/)：
```python
from pydantic import BaseModel          # Pydantic 的模型基类，定义数据结构用它
from pydantic_ai import Agent           # PydanticAI 的核心类

class CityLocation(BaseModel):          # ① 声明"我想要的输出长这样"
    city: str                           #    字段+类型 → 会转成给模型的 JSON Schema
    country: str

agent = Agent(
    'openai:gpt-5.2',                   # ② 指定模型，格式是 'provider:model'
    output_type=CityLocation,           # ③ 把①的结构声明为强制输出类型
)

result = agent.run_sync('Where were the olympics held in 2012?')
print(result.output)                    # ④ 是 CityLocation 实例，不是字符串！
#> city='London' country='United Kingdom'
print(result.usage())                   # ⑤ 还能拿到 token 用量等元数据
#> RunUsage(input_tokens=57, output_tokens=8, requests=1)
```
逐点讲解：

- **① `class CityLocation(BaseModel)`**：这是整段代码的灵魂。你不是在「祈祷模型返回好格式」，而是在「用类型系统规定输出必须长这样」。每个字段和它的类型，都会被 PydanticAI 转成一份 JSON Schema 发给模型。
- **② 模型字符串 `'provider:model'`**：「一个字符串指定模型」的设计非常干净，切换模型（比如换成 `'anthropic:...'`）只改这一处，体现「模型无关」。
- **③ `output_type=CityLocation`**：一个参数，接管了「让 LLM 稳定返回结构化输出」的全部复杂度。
- **④⑤ `result.output`**：注意它是 `CityLocation` 对象而非字符串。你能 `.city` 直接拿到 `str`、能被 IDE 补全、被 mypy 静态检查；`result.usage()` 还能拿到 token 用量。**这就是「类型安全」的实际手感：错误在写代码时就被发现，而不是等到线上炸了才知道。**

一个关于 Schema 的细节：官方文档指出，如果输出类型的 Schema 不是 `object`（比如是 `int` 或 `list[int]`），PydanticAI 会把它包进一个单元素对象里，使所有注册给模型的工具都是对象 Schema；当指定多个输出类型（union 或 list）时，每个成员会被注册成一个独立的输出工具，以降低单个 Schema 的复杂度、提高模型正确响应的概率 [来源](https://ai.pydantic.dev/output/)。

## 最小可运行演示

我们不联网、不用 API Key，用一个确定性的假模型模拟「第一次给坏值、被校验拒绝后第二次给好值」的完整三层机制。校验层用真正的 Pydantic（若环境已装），并回退到纯 Python 校验以保证可运行。
```python
"""教学参考实现：用纯 Python 复刻 output_type 的三层机制（机制/校验/兜底）。"""
from dataclasses import dataclass


@dataclass
class Invoice:
    vendor: str
    amount: float          ## 关键：必须是 float，"约一万元" 会被挡下


def validate_to_invoice(raw: dict) -> Invoice:
    """② 校验层：模拟 Pydantic 的强类型校验，非法就抛错（错误信息写给模型看）。"""
    try:
        amount = float(raw["amount"])
    except (TypeError, ValueError):
        raise ValueError(
            f"amount 校验失败：输入 {raw['amount']!r} 应为有效数字，"
            f"请只返回阿拉伯数字（例如 10000），不要带'元'或中文。"
        )
    return Invoice(vendor=str(raw["vendor"]), amount=amount)


class ScriptedModel:
    """① 机制层（教学替身）：按脚本先返回坏值，收到重试反馈后返回好值。"""
    def __init__(self):
        self.scripted = [
            {"vendor": "星辰科技", "amount": "约一万元"},   ## 第 1 轮：坏值
            {"vendor": "星辰科技", "amount": "10000"},      ## 第 2 轮：被纠正
        ]
        self.turn = 0

    def respond(self, retry_feedback: str | None) -> dict:
        out = self.scripted[self.turn]
        self.turn += 1
        return out


def run_with_retries(model: ScriptedModel, max_retries: int = 2) -> Invoice:
    feedback = None
    for attempt in range(1, max_retries + 1):
        raw = model.respond(feedback)                     ## ① 机制层：拿模型输出
        print(f"[第{attempt}次] 模型返回 {raw}")
        try:
            invoice = validate_to_invoice(raw)            ## ② 校验层
            print(f"[第{attempt}次] 校验通过 -> {invoice}")
            return invoice
        except ValueError as e:                           ## ③ 兜底层：喂回错误
            feedback = str(e)
            print(f"[第{attempt}次] 校验失败 -> 反馈给模型：{feedback}")
    raise RuntimeError("重试耗尽仍未产出合规结果——生产要在这里写兜底分支")


if __name__ == "__main__":
    print("最终得到：", run_with_retries(ScriptedModel()))
```
保存为 `three_layers.py`，运行 `python three_layers.py`。完整预期输出：
```text
[第1次] 模型返回 {'vendor': '星辰科技', 'amount': '约一万元'}
[第1次] 校验失败 -> 反馈给模型：amount 校验失败：输入 '约一万元' 应为有效数字，请只返回阿拉伯数字（例如 10000），不要带'元'或中文。
[第2次] 模型返回 {'vendor': '星辰科技', 'amount': '10000'}
[第2次] 校验通过 -> Invoice(vendor='星辰科技', amount=10000.0)
最终得到： Invoice(vendor='星辰科技', amount=10000.0)
```
这段轨迹逐字对应三层：`ScriptedModel.respond` 是①机制层的替身，`validate_to_invoice` 是②校验层，`except` 分支把错误喂回是③兜底层。把 `ScriptedModel` 换成真实客户端、把手写校验换成 Pydantic，这套「校验失败→反馈→重试」的骨架一行都不用改——这正是 `output_type` 帮你封装掉的东西。

## 真实系统对应

**官方公开机制**：`output_type` 默认使用模型的工具调用能力返回结构化数据，用 Pydantic 构建 JSON Schema 并校验；官方还提供三种输出模式标记类——工具输出（Tool Output，默认）、原生结构化输出（Native Output，用模型自带的结构化输出特性）、提示输出（Prompted Output，把 Schema 放进 instructions）[来源](https://ai.pydantic.dev/output/)。校验失败的重试（自我纠错）由框架自动完成 [来源](https://ai.pydantic.dev/agents/)。**通用工程模式**：「声明 Schema → 校验 → 失败反馈重试」这套三层结构，可迁移到任何框架，即便你手写也应照此分层。**教学参考实现**：上面的 `ScriptedModel` 与手写 `validate_to_invoice` 只为让输出可逐字复核，不代表 PydanticAI 的真实内部实现或提示拼接方式。

需要点明边界：官方文档说「默认」借助工具调用，但也支持 Native Output 与 Prompted Output 模式——具体某个模型走哪条路、Schema 长什么样，以当前官方文档为准，不要把「一定走 Function Calling」写死。

## 生产踩坑

| 症状 | 根因 | 如何观测与复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| 加了 prompt 约束仍偶发坏值 | 纯靠提示无强制力，模型换法违背 | 用多样措辞输入回放统计违背率 | 用 `output_type` 把约束落到 Schema+校验 | 纯文本任务本无结构约束 |
| 以为声明了就 100% 不出错 | 忽视③重试有上限 | 喂一段无法抽出数字的文本看最终抛错 | 写最终失败的兜底分支（进人工队列） | 结构极简、模型能力足时失败率极低 |
| 重试率飙升、成本上涨 | 输出结构设计得过于苛刻 | 统计平均重试次数与 token 消耗 | 放宽非关键字段（Optional/默认值） | 强合规字段该严就严 |
| 非 object 类型报 Schema 异常 | 直接用 `int` 等标量做 output_type | 用 `output_type=int` 观察包装行为 | 了解框架会包成单元素对象，按需用模型 | 简单标量场景框架已自动处理 |
| union 输出模型选错分支 | 多类型未拆成独立输出工具 | 用 `output_type=[A,B]` 对比单类型 | 用 list/union 让框架注册多输出工具 | 单一输出类型无此问题 |

## 思考：给面试题「如何让 LLM 稳定返回 JSON」一个有层次的满分答案

### 回答

同一道题，不同层次的答案差距巨大，按阶梯来答：

- **60 分**：「用 prompt 让它返回 JSON，比如加一句『请只返回 JSON』。」——能想到，但脆弱：模型可能加解释文字、可能格式错乱，纯靠 prompt 约束不可靠。开头那个「加一句 prompt 结果冒出 `10000元`」的故障就是它的下场。
- **75 分**：「用 Function Calling / JSON mode 让模型按 Schema 输出。」——对了一半，说到了机制层，但没提校验和兜底，遇到模型偶尔出错就没辙。
- **90 分**：「三层：① 用工具调用（Function Calling）强制模型按 JSON Schema 输出；② 拿到后用 Pydantic 做强类型校验；③ 校验失败把精确错误反馈给模型自动重试。」——完整覆盖机制、校验、兜底三层，这就是本节那张流程图。
- **满分**：在 90 分基础上补一句边界——「重试有上限，最终仍可能失败，生产要有兜底分支（进人工队列）；且结构别设计得过于苛刻，否则重试率飙升、成本上涨；PydanticAI 把这三层封装成 `output_type` 一个参数，另有 Native/Prompted 输出模式可选。」——既懂原理，又懂它的局限和框架实现，这才是资深工程师的回答。

把这个阶梯记住：面试的目标不是答对，而是答得比别人深一层。大多数候选人停在 60-75 分，你能到 90 分甚至满分，差距立现。

### 面试精简表达

三层：Function Calling 强制 schema-valid、Pydantic 强校验、失败把错误反馈自动重试；补一句边界——重试有上限、需兜底分支、结构别太苛刻。PydanticAI 把这三层封装成 `output_type`。

## 思考：为什么「校验失败自动重试」本质是第 7 章的反思？它和普通反思有什么关键区别？

### 回答

回想第 7 章的反思（Reflection）——让模型审视自己的输出、发现问题、再改进。`output_type` 的兜底层做的正是这件事，只不过是**由框架自动化、程序化地做**：模型输出 → Pydantic 校验发现「amount 不是数字」→ 把这条错误信息喂回给模型 → 模型修正 → 再校验。这和「让模型再检查一下有没有问题」的反思循环，结构完全同构。

关键区别在于「谁来当批评者」。普通反思是「模型自己反省」，批评者是模型自身，主观、不稳定、可能自我感觉良好地放过错误；而这里是「**校验器充当客观的批评者**」，用确定性的规则（`amount` 必须能转成 `float`）告诉模型哪里错了。这比让模型自省更可靠——因为规则是硬的，不受模型主观判断影响，`"约一万元"` 无论模型多自信，都过不了 `float()` 这一关。能把 `output_type` 的重试机制和第 7 章的反思模式联系起来，说明你已经把框架特性和底层原理打通了——这种贯通正是本书想训练你的。

### 面试精简表达

结构同构于反思（输出→发现问题→修正→再验），但批评者从「模型自己」换成「确定性校验器」，用硬规则纠错，比模型自省更可靠。
