## 真实问题

发票 Agent 又出了一类新故障，和之前的「格式错」不同，这次是「格式对、业务错」。有一条记录，`amount` 是规规矩矩的 `10000.0`（float，通过了 Pydantic 类型校验），`vendor` 是 `"星辰科技"`（字符串，也合规），结构上无懈可击，顺利落库。但财务复核时发现：这家「星辰科技」根本不在公司的合作供应商名单里——它是模型从发票抬头里读到的一个从未合作过的主体，很可能是钓鱼发票。类型校验拦不住它，因为**类型对了不代表业务对了**：`"星辰科技"` 是合法字符串，`float` 是合法数字，但「这家供应商必须在白名单里」「金额不能是负数」「币种必须是我们支持的那几种」这些是**业务规则**，不是类型能表达的。

团队面临一个选择：是等 Agent 把结果整个交出来后，在下游代码里写一堆 `if` 做业务校验（发现不合规就整个丢弃、重跑）？还是有办法在 Agent 运行过程中就把「不合规」告诉模型、让它当场纠正？这一节讲 PydanticAI 的两个纠错前移利器——工具里的 `ModelRetry` 和结果上的输出校验器（output validator），它们让「业务校验」也能像「类型校验」一样触发模型自动重试。

## 原理：两种纠错前移，覆盖过程与结果

回顾第 2 节：`output_type` 的重试是「结果的类型校验失败 → 重试」。但很多校验发生得更早（工具执行时）或更晚（结果拿到后要做业务校验），PydanticAI 为这两处分别提供了机制 [来源](https://ai.pydantic.dev/tools/) [来源](https://ai.pydantic.dev/output/)：

| 机制 | 发生位置 | 触发方式 | 典型用途 |
|---|---|---|---|
| Pydantic 类型校验重试 | 结果产出时 | 类型不合规自动触发 | `amount` 不是 float（第 2 节） |
| `ModelRetry` | 工具执行过程中 | 工具函数内主动 `raise ModelRetry(...)` | 参数合法但业务不通过（供应商不在白名单） |
| 输出校验器 | 结果产出后、返回前 | `@agent.output_validator` 里 `raise ModelRetry(...)` | 对最终结构做业务规则校验 |

三者的共同点是：**都把一条「哪里错了、该怎么改」的自然语言提示反馈给模型，让它重新尝试**——这正是第 2 节说的「反思工程化」。区别在于触发时机：类型校验在「结果是否合规」这一关，`ModelRetry` 在「工具执行」这一关，输出校验器在「结果的业务规则」这一关。

官方文档对 `ModelRetry` 的描述很关键：除了自动的参数校验错误，工具自身的内部逻辑也能主动抛 `ModelRetry` 异常来请求重试——适用于「参数技术上合法，但执行时出了问题」的场景，比如瞬时网络错误，或工具判断这次尝试需要换个参数再来 [来源](https://ai.pydantic.dev/tools-toolsets/tools-advanced/)。这条提示会被发回给 LLM，告知它错误并允许它修正参数、重试工具调用。

画成图，看清「纠错」在 Agent 循环里被前移到了哪些点：
```text
用户输入 → 模型决定调用 check_vendor(name="星辰科技")
                    │
                    ▼
        工具执行：发现"星辰科技"不在白名单
                    │
        raise ModelRetry("星辰科技 不在合作名单，请核对抬头或换正确的供应商名")
                    │
                    ▼  ← 纠错前移点①：在工具这一关就拦下，不等结果出来
        模型收到提示，重新决策（可能改名、可能追问）
                    │
                    ▼
        产出 Invoice 结果 → 输出校验器检查"amount 不能为负"
                    │
        若为负 raise ModelRetry("amount 不能为负数，请核对")
                    │
                    ▼  ← 纠错前移点②：结果的业务规则关
        全部通过 → 返回类型安全且业务合规的 Invoice
```
## 现象与输入：类型校验 vs 业务校验

一个常被混淆的点：Pydantic 校验和 `ModelRetry`/输出校验器管的不是一回事。用一个对照讲清：
```text
Pydantic 类型校验（结构层）：           ModelRetry / 输出校验器（业务层）：
"amount 必须是 float"                   "vendor 必须在白名单里"
"currency 是必填字符串"                 "amount 不能是负数"
"items 是 list[str]"                    "币种必须是 CNY/USD/EUR 之一"
        │                                       │
        ▼                                       ▼
结构不对 → 自动重试                     结构对但业务不对 → 主动 raise ModelRetry 重试
（框架内建，你不用写）                  （你在工具/校验器里写业务规则）
```
关键认知：**`strict` 模式、Pydantic 校验只保证「结构合规」，保证不了「业务合规」。** 一个 `amount=-5000.0` 的负数金额，类型上是完美的 `float`，但业务上荒谬。业务规则必须由你显式写出来，而 `ModelRetry` 让你能把这些业务规则「前移」成模型可纠正的反馈，而不是「先拿到坏结果再在下游丢弃」。

## 最小可运行演示

我们不联网、不用 API Key，用纯 Python 复刻 `ModelRetry` 的完整循环：工具做业务校验，不通过就抛 `ModelRetry`，把提示喂回给（脚本化的）模型，模型改参数后再来。
```python
"""教学参考实现：复刻 ModelRetry —— 工具做业务校验，不通过则反馈模型重试。"""


class ModelRetry(Exception):
    """教学替身：真实的 pydantic_ai.ModelRetry 语义一致——把消息反馈给模型重试。"""


WHITELIST = {"星辰科技", "云海数据"}          ## 业务规则的事实来源：合作名单


def check_vendor(name: str) -> str:
    """工具：校验供应商是否在合作名单，不在则请求模型纠正。"""
    if name not in WHITELIST:
        raise ModelRetry(
            f"'{name}' 不在合作供应商名单。请核对发票抬头，"
            f"若确为下列之一请用规范名：{sorted(WHITELIST)}"
        )
    return f"'{name}' 已确认在合作名单"


class ScriptedModel:
    """脚本化模型：先给一个不在白名单的名，收到重试提示后改成规范名。"""
    def __init__(self):
        self.scripted = ["星辰科技有限公司", "星辰科技"]   ## 第1轮多了后缀，第2轮规范
        self.turn = 0

    def decide_arg(self, retry_hint: str | None) -> str:
        arg = self.scripted[self.turn]
        self.turn += 1
        return arg


def run_agent(model: ScriptedModel, max_retries: int = 2) -> str:
    hint = None
    for attempt in range(1, max_retries + 1):
        name = model.decide_arg(hint)
        print(f"[第{attempt}次] 模型决定调用 check_vendor(name={name!r})")
        try:
            result = check_vendor(name)
            print(f"[第{attempt}次] 工具通过 -> {result}")
            return result
        except ModelRetry as e:
            hint = str(e)
            print(f"[第{attempt}次] 工具请求重试 -> 反馈模型：{hint}")
    raise RuntimeError("重试耗尽：生产要在此转人工核验队列")


if __name__ == "__main__":
    print("最终:", run_agent(ScriptedModel()))
```
保存为 `model_retry.py`，运行 `python model_retry.py`。完整预期输出：
```text
[第1次] 模型决定调用 check_vendor(name='星辰科技有限公司')
[第1次] 工具请求重试 -> 反馈模型：'星辰科技有限公司' 不在合作供应商名单。请核对发票抬头，若确为下列之一请用规范名：['云海数据', '星辰科技']
[第2次] 模型决定调用 check_vendor(name='星辰科技')
[第2次] 工具通过 -> '星辰科技' 已确认在合作名单
最终: '星辰科技' 已确认在合作名单
```
看这段轨迹：第 1 轮模型传的名字带了「有限公司」后缀，业务校验不通过，工具主动 `raise ModelRetry` 并在提示里给出了「规范名清单」这条可操作的线索；模型据此在第 2 轮改成规范名，通过。**注意提示的质量——它没有只说「错了」，而是告诉模型「哪里错了、正确的选项是什么」，这直接决定了模型能否一次纠对。** 把 `ScriptedModel` 换成真实客户端、把 `WHITELIST` 换成 `ctx.deps.whitelist`（第 4 节的依赖注入），这套骨架就是生产可用的业务校验前移。

## 真实系统对应

**官方公开机制**：`ModelRetry` 可由工具内部逻辑主动抛出，用于「参数合法但执行有问题」的场景（如瞬时网络错误、需换参重试），提示会被反馈给模型让它修正重试 [来源](https://ai.pydantic.dev/tools-toolsets/tools-advanced/)；输出校验器（`@agent.output_validator`）用于在结果返回前做校验，校验器内同样可 `raise ModelRetry` 触发重试 [来源](https://ai.pydantic.dev/output/)。重试次数由 Agent/工具的 `retries` 上限控制。**通用工程模式**：「把业务校验前移成模型可纠正的反馈」是可迁移的做法——即便手写 Agent 循环，也应区分「结构校验」（自动）与「业务校验」（显式写规则并反馈），并让反馈可操作。**教学参考实现**：上面自定义的 `ModelRetry` 与 `ScriptedModel` 只为让循环可离线复核，真实的重试计数、上下文累积由框架管理。

需要点明边界：`ModelRetry` 不是万能纠错器。如果错误是「模型能力上限」（比如它就是读不出这张模糊发票的抬头），无限重试只会烧 token；重试必须有上限，耗尽后走人工兜底。另外，对于**非幂等的副作用工具**（如「已扣款」），重试前要有幂等保护（第 8 章），否则重试可能重复执行副作用。

## 生产踩坑

| 症状 | 根因 | 如何观测与复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| 结构合规但业务非法数据落库 | 只做类型校验、无业务校验 | 构造负数金额/黑名单供应商看是否落库 | 用 `ModelRetry`/输出校验器加业务规则 | 无业务约束的纯抽取场景 |
| 抛了 ModelRetry 模型仍反复错 | 提示含糊，没给可操作线索 | 把提示改成只写「错误」看纠对率 | 提示写清「哪错了+正确选项」 | 模型能力上限时需换路径 |
| 重试烧光 token 不收敛 | 未设重试上限或错误不可纠 | 让工具永远抛 ModelRetry 复现 | 设 `retries` 上限，耗尽转人工 | 明确可纠的瞬时错误可多试几次 |
| 重试导致副作用重复执行 | 非幂等工具无幂等保护 | 让扣款工具首次成功后被重试 | 副作用工具绑幂等键（第 8 章） | 只读工具重试本就安全 |
| 把业务校验写在下游而非前移 | 拿到坏结果才在下游丢弃重跑 | 统计下游丢弃率与重跑成本 | 校验前移到工具/输出校验器 | 下游有独立强校验的双保险场景 |
| 输出校验器里做重 IO 拖慢每轮 | 校验器内查库/调远程 | 给校验器注入延迟观察每轮耗时 | 校验器只做轻量规则，重查放工具 | 必要的最终一致性校验除外 |
| 用 ModelRetry 处理程序 Bug | 混淆「模型可纠错」与「代码有 Bug」 | 工具内空指针也抛 ModelRetry | 代码错该抛真异常，别喂给模型 | 确需模型换参的执行错才用它 |

## 思考：ModelRetry 和 output_type 的重试是同一个东西吗？该怎么向面试官讲清它们的关系？

### 回答

它们是「同一个反思机制」在「不同触发点」的两次应用，既不是完全相同、也不是互相独立。讲清楚要分三层。第一层，共同的内核：两者最终都做同一件事——把一条自然语言的错误提示反馈给模型，让它重新尝试，这就是第 2 节说的「反思工程化」，批评者是确定性规则而非模型自省。第二层，触发点不同：`output_type` 的重试由「结果的类型校验」自动触发，管的是「结构对不对」；`ModelRetry` 由「工具或输出校验器里你写的业务逻辑」主动触发，管的是「业务通不通」。一个是框架内建的结构关，一个是你显式写的业务关。第三层，为什么要分开：因为「结构合规」和「业务合规」是两个正交的维度——`amount=-5000.0` 结构完美但业务荒谬，`amount="约一万元"` 业务意图清楚但结构不合规。类型系统只能表达结构，表达不了「必须在白名单里」这类业务规则，所以框架把业务校验的口子（`ModelRetry`）交给你，让你把业务规则也接入同一套「反思重试」的基础设施。能把这三层讲清，就说明你既懂机制的统一性（同一个反思内核），又懂它的分工（结构 vs 业务），这比只会说「都是重试」深了不止一层。

### 面试精简表达

同一个反思内核（把错误提示反馈模型重试），不同触发点：output_type 重试管「结构合规」由框架自动触发，ModelRetry 管「业务合规」由你在工具/输出校验器主动抛。因为结构和业务正交，类型系统表达不了业务规则，才需要 ModelRetry 这个口子。

## 思考：一条好的 ModelRetry 提示应该写成什么样？

### 回答

一条好的重试提示要满足三个条件，缺一个模型就可能纠不对。第一，**指明错在哪**：不能只说「参数错误」，要说清是哪个参数、什么值、违反了什么规则，比如「vendor='星辰科技有限公司' 不在合作名单」。第二，**给出可操作的线索**：光说错了模型只能瞎猜，要给它能据以修正的信息，比如上面演示里附上「规范名清单 [星辰科技, 云海数据]」，模型立刻就能对号入座。第三，**约束修正方向而非重复原问题**：如果只是把原问题原样再问一遍，模型很可能给出同样的错误答案；提示要引导它换一个不同的、更可能正确的尝试。这三条其实和第 8 章「工具错误处理要回传可操作信息」一脉相承——无论是工具执行错误还是业务校验失败，反馈给模型的都不该是「一堵墙」，而应是「一块路标」。反过来，如果错误根本不可纠（模型能力上限、数据本身缺失），那就不该用 `ModelRetry` 硬试，而应尽早失败、转人工，避免重试风暴烧光预算。

### 面试精简表达

三条：指明哪个参数什么值违反什么规则、给可操作线索（如正确选项清单）、引导换方向而非重复原问题。呼应第 8 章「错误回传要给路标不给墙」。不可纠的错误（能力上限/数据缺失）别用 ModelRetry 硬试。
