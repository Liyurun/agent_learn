## 真实问题

一个团队想做「公司内部知识助手 Agent」，直接拿基础大模型接了个对话框就上线。第一周就收到三类投诉：一是问「我们上个季度的营收」，模型编了个数字（它根本不知道公司内部数据）；二是问「帮我把这份报告发给张三」，模型只会说「好的我已发送」，实际什么都没做（它不能行动）；三是同一个用户昨天说过「我在深圳办公室」，今天再问相关问题，模型完全不记得（它会遗忘）。

三类投诉指向基础模型的三个**结构性短板**：知识会过时、不能行动、会遗忘。团队一开始以为是「模型不够强」，想换更大的模型，结果换了也没用——因为这三个短板不是「智力」问题，而是「能力边界」问题。真正的解法不是换更聪明的大脑，而是给大脑装上三个「外设」。Anthropic 把装了外设的基础模型称为**增强型 LLM（Augmented LLM）**，它正是构建一切 Agent 的基本单元。

## 原理：增强型 LLM = 基础模型 + 检索 + 工具 + 记忆

Agent 并非凭空出现，它建立在一个更基础的单元之上——Anthropic 称之为**增强型 LLM（Augmented LLM）**，即在基础模型之上，附加了**检索（Retrieval）、工具（Tools）、记忆（Memory）** 三种能力 [来源](https://www.anthropic.com/engineering/building-effective-agents)。

关键在于：这些增强能力不是被动挂载的，而是**模型可以主动使用**的——它能自主生成检索查询、选择合适的工具、决定哪些信息值得保留。增强型 LLM 是所有 Agent 系统的「细胞」，后续无论多复杂的多智能体系统，本质上都是若干增强型 LLM 的组合。
```text
        ┌─────────────────────────────┐
        │        增强型 LLM             │
        │                             │
   查询 →│  ┌──────┐   ┌──────┐        │→ 响应
        │  │检索   │   │记忆   │        │
        │  └──────┘   └──────┘        │
        │       ┌──────┐              │
        │       │工具   │              │
        │       └──────┘              │
        └─────────────────────────────┘
```
Lilian Weng 在《LLM Powered Autonomous Agents》里给出的经典框架与此高度一致：一个 LLM 驱动的自主 Agent 由「Agent 核心（LLM 本身）+ 规划（Planning）+ 记忆（Memory）+ 工具使用（Tool use）」四部分组成，其中工具使用被描述为「模型学会调用外部 API 获取权重里缺失的信息，包括实时信息、代码执行能力、专有信息源等」[来源](https://lilianweng.github.io/posts/2023-06-23-agent/)。这印证了「基础模型有边界、要靠外设补齐」的判断。

## 三种增强能力，各自解决什么问题

| 增强能力 | 解决的核心问题 | 没有它会怎样 | 本书对应章节 |
|---|---|---|---|
| **检索（Retrieval）** | 模型知识有截止日期、不知道你的私有数据 | 只能靠训练时的旧知识，无法回答实时/专有问题 | 第 7 章（RAG） |
| **工具（Tools）** | 模型只能「说」不能「做」，且不擅长精确计算 | 无法查实时信息、无法操作外部系统、算术易错 | 第 6、8 章 |
| **记忆（Memory）** | 上下文窗口有限，跨会话信息会丢失 | 每次对话都「失忆」，无法积累长期知识 | 第 5 章 |

这张表回答了一个常见困惑：「既然大模型这么强，为什么还要外挂这些东西？」答案是——**基础模型有三个结构性短板**：知识会过时、不能行动、会遗忘。检索、工具、记忆恰好是对这三个短板的针对性补丁。理解了「补丁对应短板」，你就理解了增强型 LLM 每一部分存在的必要性。

回到开头的三类投诉，逐一对号入座：编造营收数字 → 缺检索（应从内部数据库检索真实数字）；说「已发送」却没动作 → 缺工具（应调用真实的发送接口）；记不住用户在深圳 → 缺记忆（应把关键事实存入跨会话记忆）。三个短板，三个补丁，一一对应。团队后来正是按这个映射逐项补齐，投诉才消失——而不是靠换更大的模型。

## 最小可运行演示：三个补丁如何补齐三个短板

我们用一段代码把「短板→补丁」的对应关系变得可运行。程序模拟一个基础模型的三个短板，再分别用检索、工具、记忆补齐，对比补丁前后的输出。纯标准库，无需 API Key。
```python
INTERNAL_DB = {"上季度营收": "1240 万元"}   # 私有数据，模型训练时见不到
MEMORY = {}                                # 跨会话记忆


def base_model(query: str) -> str:
    """模拟基础模型：只会根据"训练知识"猜，遇到私有/实时/需行动的问题就露怯。"""
    if "营收" in query:
        return "大约几百万元吧（编造，因为不知道私有数据）"
    if "发送" in query:
        return "好的，我已发送（其实什么都没做）"
    return "（凭记忆回答，但我不记得你是谁）"


def with_retrieval(query: str) -> str:
    """检索补丁：先查私有库，再回答。"""
    for key, value in INTERNAL_DB.items():
        if key in query:
            return f"根据内部数据：{value}"
    return base_model(query)


def send_report(to: str) -> str:
    """工具补丁：真正执行动作（这里模拟为返回一个可核验的回执）。"""
    return f"已调用发送接口 → 回执:{to}#OK"


def with_memory(user: str, fact: str = None) -> str:
    """记忆补丁：写入并读取跨会话事实。"""
    if fact:
        MEMORY[user] = fact
        return f"已记住：{user} → {fact}"
    return f"我记得：{MEMORY.get(user, '暂无记录')}"


def main() -> None:
    print("短板1 知识过时 →", base_model("上季度营收多少"))
    print("补丁1 检索     →", with_retrieval("上季度营收多少"))
    print("短板2 不能行动 →", base_model("帮我发送报告"))
    print("补丁2 工具     →", send_report("张三"))
    print("补丁3 记忆(写) →", with_memory("user01", "在深圳办公室"))
    print("补丁3 记忆(读) →", with_memory("user01"))


if __name__ == "__main__":
    main()
```
保存为 `augmented_llm.py`，运行 `python augmented_llm.py`。预期输出：
```text
短板1 知识过时 → 大约几百万元吧（编造，因为不知道私有数据）
补丁1 检索     → 根据内部数据：1240 万元
短板2 不能行动 → 好的，我已发送（其实什么都没做）
补丁2 工具     → 已调用发送接口 → 回执:张三#OK
补丁3 记忆(写) → 已记住：user01 → 在深圳办公室
补丁3 记忆(读) → 我记得：在深圳办公室
```
对比前两行，你能直观看到检索如何把「编造」变成「有据可查」；对比三四行，看到工具如何把「口头承诺」变成「可核验的动作回执」；最后两行则展示记忆如何跨调用保留事实。三个补丁各补一个短板，缺哪个补哪个。

## 「细胞—器官—生物」：一个层层组合的比喻

把增强型 LLM 理解成「细胞」非常关键，因为整本书的架构都建立在「组合」这个思想上。用一个生物学比喻来串起来：
```text
   细胞           器官              生物体
   ┌────────┐    ┌──────────┐     ┌─────────────────┐
   │增强型LLM│──▶│单个Agent  │──▶ │多智能体系统       │
   │(LLM+检索│    │(细胞放进  │     │(多个Agent协作,   │
   │+工具+   │    │ 循环里)   │     │ 编排者-工作者等) │
   │ 记忆)   │    │          │     │                 │
   └────────┘    └──────────┘     └─────────────────┘
```
- **细胞（增强型 LLM）**：能感知（检索/接收输入）、能记忆、能行动（工具）的最小功能单元，但它自己不构成循环。
- **器官（单个 Agent）**：把细胞放进「思考—行动—观察」的循环里，它就获得了自主推进任务的能力。
- **生物体（多智能体系统）**：多个 Agent 分工协作，一个负责编排、几个负责干活（后续章节的编排者-工作者模式）。

这个比喻的价值在于：无论你看到的系统多复杂，都可以逐层往下拆，最终一定会落到「一个个增强型 LLM 的调用」上。**复杂系统 = 简单单元的组合**，这是驾驭复杂度的根本方法。反过来说，如果你连「细胞」都没做稳（检索不准、工具会崩、记忆错乱），堆再多「器官」和「生物体」也只会放大问题。所以本书的顺序是先把细胞讲透，再谈组合。

## 真实系统对应

**官方公开机制**：Anthropic 把「增强型 LLM」列为构建 Agent 的基础模块，明确它由基础模型加检索、工具、记忆构成，且这些能力由模型主动调用 [来源](https://www.anthropic.com/engineering/building-effective-agents)；Lilian Weng 的框架把 Agent 拆成 LLM 核心加规划、记忆、工具使用，与之呼应 [来源](https://lilianweng.github.io/posts/2023-06-23-agent/)；OpenAI Agents SDK 里，工具就是被装饰的普通函数，模型按需调用 [来源](https://openai.com/business/guides-and-resources/a-practical-guide-to-building-ai-agents/)。**通用工程模式**：「基础模型 + 三补丁」是可迁移的构建单元，把复杂系统逐层拆到增强型 LLM 是通用的复杂度治理方法。**教学参考实现**：上面的 `INTERNAL_DB`、`send_report`、`MEMORY` 都是为演示短板与补丁构造的最小实现，不代表任何产品的检索/记忆/工具内部机制。

需要提醒边界：Anthropic 和 Lilian Weng 的框架描述的是「构成」而非「实现」——它们告诉你 Agent 由哪几块组成，但不规定检索必须用哪种向量库、记忆必须存哪里。所以看到「增强型 LLM」这个词时，理解它是一个**架构抽象**（有哪几类能力），而不是一个**具体产品**（某个特定实现），才不会把「有检索」误当成「用了某某检索库」。

## 生产踩坑

| 症状 | 根因 | 如何观测与复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| 助手编造公司内部数据 | 缺检索，靠训练知识猜 | 问一个只在私有库里的事实 | 接入检索，回答须带来源 | 纯公开常识问答可不接私有检索 |
| 模型说「已完成」实际没动作 | 缺工具，只会生成文本 | 检查是否真有接口被调用 | 把动作接成真实工具并核验回执 | 纯咨询类问答无需执行动作 |
| 跨会话完全失忆、反复问同样问题 | 缺记忆，上下文窗口一满就丢 | 隔一会话再问之前说过的事实 | 关键事实写入跨会话记忆并带来源 | 一次性无状态任务无需长期记忆 |
| 换更大模型后三类问题依旧 | 误把能力边界当智力问题 | 换模型后复测三类投诉是否消失 | 按短板补对应补丁，而非换模型 | 确因模型能力不足时才需升级 |
| 检索/记忆返回过期或错误事实 | 补丁本身没做来源与时效管理 | 注入一条过期数据看是否被采信 | 事实带来源与生效时间，冲突时暴露 | 时效不敏感的静态知识可放宽 |
| 复杂多智能体系统难以调试 | 没先把单个增强型 LLM 做稳就堆组合 | 逐层拆到单个细胞看哪层出错 | 先保证细胞可靠，再组合成器官/生物体 | 极简单场景无需多层组合 |

## 思考：既然大模型这么强，为什么还要外挂检索、工具、记忆？

### 回答

因为基础模型有三个结构性短板，它们是能力边界问题，不是智力问题，换更大的模型也解决不了。第一，知识有训练截止日期、且看不到你的私有数据，所以需要检索把外部/专有信息取进来；第二，模型只能生成文本、不能真正操作外部系统，且不擅长精确计算，所以需要工具把「说」变成「做」；第三，上下文窗口有限、跨会话会丢信息，所以需要记忆积累长期事实。检索、工具、记忆恰好是对这三个短板的针对性补丁，缺哪个补哪个。理解「补丁对应短板」，就理解了增强型 LLM 每部分存在的必要性。

### 面试精简表达

基础模型三大短板：知识过时、不能行动、会遗忘。检索、工具、记忆是三块对症的补丁。这是能力边界问题，不是换大模型能解决的。

## 思考：RAG 和 Agent 是什么关系？

### 回答

用「细胞 vs 器官」的比喻最清楚。RAG（Retrieval-Augmented Generation，检索增强生成）是「增强型 LLM」这个细胞里的「检索」这一味能力。它本身可以只是一次固定检索——先检索、再把结果拼进提示、生成回答，整个流程写死，那它还只是增强型 LLM 的一次调用，不是 Agent。当模型能**自主决定**要不要检索、检索几次、上一次没查到就换关键词再检索时，检索就被「装进了循环」，RAG 才升级成 Agentic RAG（智能体式检索增强）。所以 RAG 与 Agent 不是并列的两个东西，而是「一味能力」与「把能力放进循环后涌现的系统」的关系。

### 面试精简表达

RAG 是增强型 LLM 里的「检索」这味能力；一次固定检索还不是 Agent，当模型自主决定检索与否、检索几次、如何改写查询、把检索装进循环，才成为 Agentic RAG。

## 从「补丁」到「循环」：本章拼图如何合拢

到这里，本章的两块核心拼图可以合拢了。第 03、04 节讲的是**循环**——Agent 的运行时骨架（LLM 在循环里用工具、基于反馈决策）；本节讲的是**细胞**——循环里那个「大脑」其实是一个增强型 LLM（基础模型 + 检索 + 工具 + 记忆）。把两者叠起来看，一个完整 Agent 的图景就清晰了：**一个增强型 LLM 被放进「思考—行动—观察」的循环里，自主决定何时检索、何时调工具、何时读写记忆、何时收尾**。

这也解释了为什么第 04 节的最小骨架里，工具（metrics/calculator）就是增强能力的一种具体体现——那段代码其实已经是一个「带工具的增强型 LLM 放进循环」的雏形，只是检索和记忆还没显式出现。理解了「细胞 + 循环」这个组合，你再看任何复杂 Agent，都能先问两个问题：它的细胞（增强型 LLM）做稳了吗？它的循环（谁决定下一步与何时停）清晰吗？下一节我们把这些判断收敛成一张可操作的四判据体检表。
