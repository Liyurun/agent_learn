## 真实问题

一个刚接触 Agent 的工程师读完了所有定义文章，还是写不出第一个 Agent。他卡在一个具体的地方：「文章都说 Agent 是 LLM 在循环里用工具，可我没有 API Key，也不想为了学个概念先充值买额度，我到底怎么在本地跑通一个能看见循环的东西？」他试着直接调 OpenAI 接口，结果卡在网络、鉴权、计费上，概念还没摸到就先被环境劝退。

这一节就是为解决这个问题：用一个**完全可运行、无需任何 API Key、只用标准库**的纯 Python 程序，把「循环 + 工具 + 模型决定何时停」这三件事变成你能亲手跑、能打印轨迹、能改参数观察行为的代码。我们用一个「假的 LLM」（用规则模拟决策）代替真实模型——因为本节要看清的是**结构**，而结构与真实模型完全一样：输入上下文，输出「下一步动作」。看清了结构，把假 LLM 换成真模型只是替换一个函数。

## 现象与输入：贯穿案例的输入与期望轨迹

沿用本章的贯穿案例——值班扩容问答。输入与期望输出固定如下，任何人跑代码都应得到同一条轨迹：
```text
任务：checkout-api 要扩容到 960 QPS，当前每副本 120 QPS，现有 4 个副本，需新增几个副本？
期望循环轨迹：
  第1步：查询现状（工具：metrics）→ 观察：当前副本=4，单副本=120 QPS
  第2步：计算所需副本（工具：calculator）→ 观察：ceil(960/120)=8
  第3步：计算新增数（工具：calculator）→ 观察：8-4=4
  第4步：给出最终答案（final）→ 需新增 4 个副本
```
这条轨迹就是我们要用代码复现的目标。它天然需要「先查询、再计算」两类工具和多轮循环，正好把 03 节讲的原理落成代码。

## 最小可运行演示：完整的 ReAct 骨架

下面这段代码用一个「假 LLM」（用规则模拟决策）和三个真实可跑的工具，演示 Agent 循环的骨架。它完全可运行，不需要任何 API Key，直接复制到本地即可执行。重点感受「循环 + 工具 + 模型决定何时停」这三件事。
```python
import re
import math


def metrics(service: str) -> str:
    """模拟可观测性平台：返回服务的当前副本数与单副本处理能力。"""
    table = {"checkout-api": "replicas=4;per_replica_qps=120"}
    return table.get(service, "unknown service")


def calculator(expression: str) -> str:
    """一个安全的四则运算工具，只接受数字与运算符。"""
    if not re.fullmatch(r"[\d\s\+\-\*\/\.\(\)]+", expression):
        return "错误：表达式包含非法字符"
    try:
        return str(eval(expression))  # 教学演示用；生产请用 ast 安全解析
    except Exception as exc:
        return f"错误：{exc}"


TOOLS = {"metrics": metrics, "calculator": calculator}


def fake_llm(task: str, history: list) -> dict:
    """假 LLM：用规则模拟"下一步做什么"的决策。真实系统这里调用 GPT/Claude，结构相同。"""
    seen = " ".join(h["observation"] for h in history)
    if "replicas=" not in seen:
        return {"action": "metrics", "input": "checkout-api", "thought": "先查现状"}
    if "8" not in seen:
        need = math.ceil(960 / 120)  # 目标 QPS / 单副本 QPS
        return {"action": "calculator", "input": f"{need}", "thought": "算所需副本数"}
    if "新增" not in seen and "4" == seen.strip().split()[-1] if False else "delta" not in seen:
        return {"action": "calculator", "input": "8-4", "thought": "算新增副本数"}
    return {"action": "final", "input": "需新增 4 个副本（目标 8 - 现有 4）",
            "thought": "信息齐了，收尾"}


def run_agent(task: str, max_steps: int = 6):
    history = []
    for step in range(1, max_steps + 1):
        decision = fake_llm(task, history)                  # 模型决定下一步
        print(f"[第{step}步] 思考:{decision['thought']} 决策:{decision['action']}({decision['input']})")
        if decision["action"] == "final":                   # 模型判断"完成" → 跳出循环
            print(f"最终答案: {decision['input']}")
            return decision["input"]
        tool = TOOLS[decision["action"]]                    # 运行时执行工具（不是模型执行）
        observation = tool(decision["input"])
        print(f"        观察: {observation}")
        history.append({"observation": observation})        # 反馈进入下一轮
    print("达到最大步数，强制停止")


if __name__ == "__main__":
    run_agent("checkout-api 扩容到 960 QPS，每副本 120 QPS，现有 4 副本，需新增几个？")
```
上面 `fake_llm` 里第三个分支的判定写得有些绕，是为了演示「真实决策逻辑往往需要读历史」。为清晰起见，把它替换成一个更直白、等价的版本，这也是最终推荐的写法：
```python
def fake_llm(task: str, history: list) -> dict:
    """假 LLM：根据已观察到的历史，决定下一步动作。"""
    seen = " ".join(h["observation"] for h in history)
    if "replicas=" not in seen:                 # 还不知道现状 → 先查询
        return {"action": "metrics", "input": "checkout-api", "thought": "先查现状"}
    if "need=" not in seen:                      # 已知现状但没算所需副本 → 算 960/120
        return {"action": "calculator", "input": "960/120", "thought": "算所需副本数"}
    if "delta=" not in seen:                      # 已知所需但没算差值 → 算 8-4
        return {"action": "calculator", "input": "8-4", "thought": "算新增副本数"}
    return {"action": "final", "input": "需新增 4 个副本（目标 8 - 现有 4）",
            "thought": "信息齐了，收尾"}
```
为让 `"need="` 与 `"delta="` 出现在历史里，把 `run_agent` 里记录观察的那行改为携带标签（这是教学化处理，真实系统靠模型自己读数字，不需要打标签）：
```python
def run_agent(task: str, max_steps: int = 6):
    history = []
    tags = ["", "need=", "delta="]  # 给前几步观察打标签，方便假 LLM 判断进度
    for step in range(1, max_steps + 1):
        decision = fake_llm(task, history)
        print(f"[第{step}步] 思考:{decision['thought']} 决策:{decision['action']}({decision['input']})")
        if decision["action"] == "final":
            print(f"最终答案: {decision['input']}")
            return decision["input"]
        observation = TOOLS[decision["action"]](decision["input"])
        tag = tags[len(history)] if len(history) < len(tags) else ""
        print(f"        观察: {tag}{observation}")
        history.append({"observation": f"{tag}{observation}"})
    print("达到最大步数，强制停止")
```
把这三段整合进一个文件（`metrics`、`calculator`、`TOOLS`、上面第二版 `fake_llm`、第二版 `run_agent`、`if __name__` 入口），保存为 `min_agent.py`，运行 `python min_agent.py`。预期输出：
```text
[第1步] 思考:先查现状 决策:metrics(checkout-api)
        观察: replicas=4;per_replica_qps=120
[第2步] 思考:算所需副本数 决策:calculator(960/120)
        观察: need=8.0
[第3步] 思考:算新增副本数 决策:calculator(8-4)
        观察: delta=4
[第4步] 思考:信息齐了，收尾 决策:final(需新增 4 个副本（目标 8 - 现有 4）)
最终答案: 需新增 4 个副本（目标 8 - 现有 4）
```
## 逐行讲解：这段代码为什么「是 Agent」

- `metrics` / `calculator`：两个**工具**。它们是普通 Python 函数，执行发生在你的代码里——这印证了后续章节反复强调的「模型提议、运行时执行」原则。模型只是说「调 calculator(960/120)」，真正的除法是你的解释器算的。
- `calculator` 里的 `re.fullmatch(...)`：这是**边界处理 / 护栏**。真实工具必须校验输入，绝不能把模型给的字符串无脑塞进 `eval`。这一行就是「不该做的事写进代码」的雏形——即便模型被诱导传入恶意字符串，护栏也会拦下。
- `fake_llm`：模拟**大脑**。它接收任务和历史，返回一个「决策」——要么调工具，要么给最终答案。真实系统里这一步是调用 GPT/Claude，但**结构完全一样**：输入上下文，输出「下一步动作」。
- `run_agent` 里的 `for step in range(...)`：这就是**循环**。它不是执行固定次数，而是「直到模型说 final 才停」。`max_steps` 是安全阀，防止无限循环（生产环境的必备护栏）。
- `if decision["action"] == "final"`：**模型决定何时停止**——这是 Agent 的灵魂。停止条件不是代码写死的「跑 3 次」，而是模型基于反馈判断「任务完成了」。
- `history.append(...)`：**环境反馈进入下一轮**。每一步的观察结果都被记下来，喂给下一次决策。这就是闭环。

## 反例对比：把 Agent 和「不是 Agent」放一起

把上面的 Agent 和一个反例对比，你立刻能看出区别：
```python
def not_an_agent(text: str) -> str:
    """反例：这不是 Agent —— 单次调用，没有循环，没有基于反馈的决策。"""
    prompt = f"请把下面这段话总结成一句话：\n{text}"
    return fake_llm_summarize(prompt)  # 调一次，拿到结果就返回，结束
```
`not_an_agent` 里没有 `for` 循环、没有工具执行后的观察、没有「要不要再来一轮」的判断。控制流完全在函数体里写死。它是一个「增强型 LLM 的调用」，但不是 Agent。把它和 `run_agent` 并排看，分界线一目了然：一个是直线（调用即终点），一个是闭环（观察后再决定）。

再看一个更隐蔽的反例——它有循环，却仍然不是 Agent：
```python
def fixed_loop(items: list) -> list:
    """反例：有循环，但循环次数由数据长度写死，模型不决定何时停。"""
    results = []
    for item in items:            # 循环次数 = len(items)，代码说了算
        results.append(fake_llm_summarize(item))
    return results
```
`fixed_loop` 对 1000 条数据逐条调模型，看起来「循环 + 模型」都有了，但循环次数是 `len(items)` 写死的，模型只是被反复调用的一环，不决定「要不要再来一轮、何时停」。它是**固定循环批处理**，不是 Agent。这印证了第 02 节的结论：有循环、有工具、有模型，都不是充分条件，**控制流归属与「谁决定何时停」才是**。

## 一次完整循环的运行轨迹解读

对着前面那段预期输出，Agent 定义里的每个字都活了起来：

- **第 1 步**：模型发现自己不知道现状，于是行动——查 metrics。这一步体现「工具是为了获取新信息」。
- **第 1 步的观察**：拿到 `replicas=4;per_replica_qps=120`，这条信息此刻并不在模型「脑子」里，而是通过工具从环境取回的——这就是**环境反馈**。
- **第 2 步**：模型基于上一步的观察，决定计算所需副本数。**注意这个决策依赖第 1 步的结果**——不知道单副本能力就没法算。这是「基于反馈的决策」，也是循环不可省略的活证据。
- **第 3 步**：模型基于「需要 8 个、现有 4 个」，决定算差值。
- **第 4 步**：模型判断「信息齐了，可以收尾」，输出 `final`。**停止是模型自己决定的**，不是代码数到 4 就停。

把这段轨迹和 03 节「Thought → Action → Observation，然后回到 Thought」对照，会发现它们是同一件事：每一步的「思考+决策」就是 Thought+Action，每一步的「观察」就是 Observation，「进入下一步」就是循环的下一轮。**你刚刚亲眼看到了一个 ReAct 循环在跑。**

## 真实系统对应

**官方公开机制**：OpenAI 的 Agents SDK 用一个 `Runner` 来「驱动循环」——调用模型、执行模型请求的工具、把结果喂回去、再问下一步，直到得到最终输出；工具就是被装饰器标注的普通 Python 函数，SDK 读取其签名与文档字符串生成模型看到的 schema [来源](https://openai.com/business/guides-and-resources/a-practical-guide-to-building-ai-agents/)。LangGraph 里同样的循环表现为「LLM 节点 →（有工具调用则）工具节点 → 回到 LLM 节点」，直到 LLM 产出不含工具调用的回复，路由才返回 END [来源](https://langchain-ai.github.io/langgraph/)。把这两者和我们的 `run_agent` 对照：`fake_llm` 对应 LLM 节点，`TOOLS[...]()` 对应工具节点，`for + final 判断` 对应驱动循环与退出条件。**通用工程模式**：「模型提议、运行时执行工具、结果反馈、循环到模型说停」是各框架共有骨架。**教学参考实现**：`fake_llm` 用规则模拟决策、给观察打标签都是教学处理，真实系统靠模型读上下文自行决策，不需要打标签，也不会把决策逻辑写成 if 链。

换句话说，你在本节写的 30 行代码，和生产框架里那个驱动循环，结构是同构的。区别只在于：生产框架把 `fake_llm` 换成真实模型调用、把工具 schema 自动生成、把错误处理和并发做得更完善。理解了这个骨架，读任何框架源码你都能先找到那个 while 循环。

## 生产踩坑

| 症状 | 根因 | 如何观测与复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| Agent 在搞不定的任务上无限自我对话烧钱 | 忘了设 max_steps 安全阀 | 给一个无解任务，看是否停不下来 | 设置 max_steps 并在到达时优雅退出 | 明确有界的短任务风险较低 |
| 模型每轮都从头开始、反复调同一工具 | 忘了把 observation 反馈进历史 | 打印每轮传入模型的 history 是否累积 | 每步把观察 append 进历史再喂下一轮 | 无状态独立子任务可不累积历史 |
| 工具被模型传入的恶意字符串搞崩 | 工具没做输入校验就 eval/执行 | 传入含字母或注入的表达式复现 | 工具入口做白名单/类型校验（如正则） | 完全可信的内部调用可简化校验 |
| 模型编造不存在的工具名 | system 提示没清晰列出可用动作 | 看决策里出现未注册的 action | 明确列出可用工具，并对未知 action 报错 | 工具集极小且稳定时风险较低 |
| 换成真实模型后 JSON 解析崩溃 | 模型偶尔返回带 ```json 包裹或多余文字 | 让真实模型多跑几次看输出格式 | json.loads 加容错、失败重试与兜底 | 强约束结构化输出接口可简化 |
| 轨迹看不见，出错无法定位 | 没有打印每步思考/决策/观察 | 关掉打印后复现 bug，感受黑盒之痛 | 默认打印完整轨迹，作为调试第一手段 | 生产高频调用可降级为采样打印 |

## 思考：在这段最小循环里，哪一行体现「模型决定何时停」？去掉 max_steps 会怎样？

### 回答

`if decision["action"] == "final":` 这一行体现「模型决定何时停」——退出循环的触发条件是模型在决策里返回了 `final`，而不是代码数到某个固定次数。这正是 Agent 区别于固定循环批处理的关键：停止权在模型。去掉 `max_steps` 后，一旦 `fake_llm`（或真实模型）在某个搞不定的任务上永远不返回 `final`，循环就会无限跑下去，不断消耗算力或 token，直到进程被外部杀掉。所以 `max_steps` 是安全阀：它不参与业务判断（正常情况下模型会先返回 final），只在模型「卡住」时兜底止损。生产环境里，去掉安全阀是最常见、最烧钱的新手错误之一。

### 面试精简表达

`action==final` 那行是模型决定何时停；max_steps 是防失控的安全阀。停止逻辑归模型（业务判断），安全阀归代码（兜底止损），两者分工不能混。

## 思考：把 fake_llm 换成真实模型，需要改动哪些地方？为什么说「结构不变」？

### 回答

只需改一处核心：把 `fake_llm` 的规则判断，换成「构造消息、调用真实模型接口、解析模型返回的决策」。循环体（for + 工具执行 + 反馈进历史 + final 判断）、工具定义、安全阀都不用动。这就是「结构不变，只换大脑」——因为 Agent 的骨架是「输入上下文→模型输出下一步动作→执行→反馈」，真实模型和假 LLM 在这个接口上是一致的，输入都是任务加历史，输出都是一个「调工具或给答案」的决策。换真实模型时要额外补三件工程事：一是 system 提示里明确列出可用工具（否则模型会编造工具名）；二是强制模型返回结构化 JSON 并对解析做容错（模型偶尔会加多余文字或 ```json 包裹）；三是给工具调用加错误处理（真实工具会超时、报错）。但这些都是「加固」，不改变循环结构本身。

### 面试精简表达

只换决策函数，循环、工具、安全阀都不动。因为骨架是「上下文→决策→执行→反馈」，真假 LLM 在这个接口上一致，换模型是升级大脑不是重构骨架。

## 从最小骨架到能上手改的三个练习方向

这段代码的价值在于「可改」。你可以立刻动手做三件事来加深理解，每件都能在本地跑、都能看见行为变化。第一，**故意让 metrics 返回一个不存在的服务**（比如把任务里的服务名改成 `pay-api`），观察 Agent 会不会陷入「查不到→反复查」的循环，然后思考如何在观察里加入「服务不存在」的信号让模型停下——这会让你体会「错误也是一种必须反馈的观察」。第二，**把 max_steps 改成 2**，看任务在第 4 步才收尾却被强制在第 2 步截断时会打印什么，体会安全阀触发时应该给出可诊断的信息而不是静默失败。第三，**新增一个工具**（比如 `converter` 做单位换算），并在 `fake_llm` 里加一个分支决定何时调它，体会「工具越多，决策逻辑越复杂」——这正是真实 Agent 里「工具选择」成为难点的起点，也是后续章节讲工具设计的动机。

三个练习都不需要联网、不需要 Key，改几行就能跑。把它们跑一遍，你对「循环 + 工具 + 反馈 + 模型决定何时停」的理解，会从「读懂了」变成「改得动」——这正是本节要交付的能力。
