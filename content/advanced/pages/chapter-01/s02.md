## 真实问题

一个团队上线了「智能客服 Agent」，对外宣传能自主处理咨询。上线两周后，用户投诉「机器人答非所问、一个问题要问三遍才走对分支」。工程师排查代码，发现所谓的「Agent」其实是这样的结构：先让 LLM 判断用户意图属于「查订单 / 查物流 / 退款 / 转人工」四类之一，然后代码按 `if 意图 == "查订单": ...` 走进对应分支，每个分支里再调一次 LLM 生成回复。整个系统没有循环，模型只在四个预设格子里选一个，选错了也没有「再看一眼、重来一轮」的机制。

它到底算不算 Agent？如果算，为什么表现得像个僵硬的流程？如果不算，它明明用了大模型、还让模型做了判断。这个问题困住了整个团队。答案是：**它不是 Agent，是一个「路由型工作流」**。要说清为什么，我们需要一把可复用的尺子。

## 现象与输入：三个都用了 LLM 却都不是 Agent 的系统

理解一个概念，反例往往比正例更有力。以下这些**都不是** Agent，尽管它们都用到了 LLM：
```text
反例一 · 单轮问答：
  输入 prompt → 调一次模型 → 返回文本 → 结束
  没有循环、没有工具、没有基于反馈的决策。

反例二 · 情感分类器：
  输入一条评论 → 模型输出「正面/负面」→ 结束
  一次固定的模型调用，输出即终点。

反例三 · 固定翻译流水线：
  抽取字段 → 调 LLM 翻译 → 格式化输出
  每一步由代码写死，模型只是被调用的一环。
```
Anthropic 特别强调：**集成了 LLM、但并不用它来控制工作流的应用，不是 Agent** [来源](https://www.anthropic.com/engineering/building-effective-agents)。这三个反例的共同点是：「谁决定下一步做什么」的答案是「程序员写的代码」，而不是「模型」。开头那个客服系统也一样——四个分支是程序员写死的，模型只是在里面挑一个。

## 原理：控制流归属，就是那把尺子

三个反例加上开头的客服系统，共同点值得单独拎出来当成一把可复用的尺子：**看控制流（control flow）掌握在谁手里**。所谓控制流，就是「程序按什么顺序执行、在分叉处走哪条路、什么时候结束」。

- 在**普通脚本/工作流**里，控制流写死在代码里：`if / else / for` 决定一切，模型只是被 `call_llm()` 调用的一个函数。流程图可以在写代码前就完整画出来。
- 在**Agent** 里，控制流被「让渡」给了模型：下一步调哪个工具、要不要再来一轮、什么时候停，都是模型在当轮输出里决定的。流程图无法提前画全，因为路径依赖运行时模型看到的反馈。

这把尺子好用，是因为它把一个模糊的哲学问题（「它够不够智能」）转化成一个可观察的工程问题（「谁在决定 next step」）。一个业界流传很广、可操作的判断法与此一致：**如果你能在写代码前就把完整流程图画出来（prompt A → tool B → prompt C → 返回），那是 workflow；如果必须等运行时才知道模型会选哪条路、要循环几次，那才是 Agent** [来源](https://www.anthropic.com/engineering/building-effective-agents)。

## 一个特别容易混淆的边界：带 if-else 的 LLM 脚本

开头的客服系统正是最容易引起争论的边界情况。很多人会反驳：「我的脚本会先让 LLM 判断用户意图，再根据意图走不同分支，这不就是模型在控制流程吗？」

答案是：**这仍然更接近工作流，而不是开放式 Agent**。关键在于——分支是你**事先枚举好的、有限的、写死在代码里的**。模型只是在你划好的几个格子里选一个，它不能创造新格子、不能决定「再来一轮」、不能自己发明一个你没预设的动作。这种模式有个专门的名字叫「路由（Routing）」，属于自主性光谱上偏低的位置，是 Agent 的近亲，但不是完整意义上的 Agent。
```text
   工作流 / 路由（控制流在代码手里）        Agent（控制流在模型手里）
   ┌──────────────────┐                  ┌────────────────────┐
   │ LLM 判断意图        │                  │  LLM 决定下一步      │◀──┐
   │ if 意图==A: 分支A   │  ← 分支写死        └─────────┬──────────┘   │
   │ if 意图==B: 分支B   │                            │ 调用工具        │
   │ if 意图==C: 分支C   │                  ┌─────────▼──────────┐   │
   └──────────────────┘                   │  观察结果 → 反馈      │───┘
   模型只在预设格子里选一个                  └────────────────────┘
                                          循环由模型判断何时停止
```
这里要破除一个极常见的误区：**把「用了 function calling / tool calling API」等同于「这是 Agent」**。函数调用只是一个能力接口——你完全可以只调用一次、拿到结果就返回，那仍然是单次增强 LLM，不是 Agent。**决定它是不是 Agent 的，是有没有「循环 + 模型决定何时停」，而不是有没有工具接口。** 开头的客服系统就有工具调用（查订单、查物流都是工具），但它没有循环、模型不决定何时停，所以仍然不是 Agent。

## 最小可运行演示：同一个尺子，量出不同结论

我们把「控制流归属」做成可运行的判定器。给它三个系统的结构描述，它输出每个系统的控制流归属与最终判定。纯标准库，无需 API Key。
```python
def classify(system: dict) -> str:
    control = system["control_flow_owner"]
    has_loop = system["has_loop"]
    model_stops = system["model_decides_stop"]
    if control == "code" and not has_loop:
        return "工作流 / 单次调用（控制流在代码）"
    if control == "code" and has_loop:
        return "固定循环工作流（循环次数写死，非模型决定）"
    if control == "model" and has_loop and model_stops:
        return "完整 Agent（控制流在模型，模型决定何时停）"
    return "路由型工作流（模型选分支，但不掌控循环）"


def main() -> None:
    cases = {
        "单轮问答": dict(control_flow_owner="code", has_loop=False,
                     model_decides_stop=False),
        "带if-else意图路由": dict(control_flow_owner="code", has_loop=False,
                            model_decides_stop=False),
        "固定次数批处理": dict(control_flow_owner="code", has_loop=True,
                        model_decides_stop=False),
        "自主调研执行器": dict(control_flow_owner="model", has_loop=True,
                        model_decides_stop=True),
    }
    for name, s in cases.items():
        print(f"{name:14s} → {classify(s)}")


if __name__ == "__main__":
    main()
```
保存为 `classify_by_control.py`，运行 `python classify_by_control.py`。预期输出：
```text
单轮问答          → 工作流 / 单次调用（控制流在代码）
带if-else意图路由   → 工作流 / 单次调用（控制流在代码）
固定次数批处理      → 固定循环工作流（循环次数写死，非模型决定）
自主调研执行器      → 完整 Agent（控制流在模型，模型决定何时停）
```
注意「带 if-else 意图路由」和「单轮问答」被判成同一类——这正是本节要传达的核心：**有没有 if-else、有没有工具调用，都不改变控制流归属**。只要分支和循环次数是代码写死的，它就还在工作流一侧。

## 真实系统对应

**官方公开机制**：Anthropic 把 workflow 定义为「LLM 与工具被预定义代码路径编排」，把 agent 定义为「LLM 动态指挥自己的流程」，并明确把「路由（Routing）」列为一种 workflow 模式而非 agent [来源](https://www.anthropic.com/engineering/building-effective-agents)。LangGraph 官方文档把 Agent 的核心刻画为「在循环里调用 LLM 问它下一步做什么，直到模型给出不含工具调用的回复才结束」，其框架专门强调「不是 DAG（Directed Acyclic Graph，有向无环图）框架，而是要支持环（cycle）」——因为环正是 Agent 行为的前提 [来源](https://langchain-ai.github.io/langgraph/)。**通用工程模式**：用「能否提前画全流程图」区分 workflow 与 agent，是可迁移的判断法。**教学参考实现**：上面的 `classify` 函数是本书为讲清尺子构造的，不代表任何产品的内部分类逻辑。

把这条边界讲清楚有直接的工程收益：很多团队以为自己在「做 Agent」，其实做的是路由型工作流，于是用错了评估方法（拿「自主性」指标去评一个本该确定性的系统），也用错了优化方向（去调提示词，而问题其实在分支设计）。先判清自己在做哪一类，才谈得上用对方法。

## 把 Agent 和几个近亲摆在一起比

「什么不是 Agent」还有一层容易混淆的地方：市面上有一堆听起来很像、边界又模糊的词——Chatbot（聊天机器人）、Copilot（副驾驶助手）、RPA（Robotic Process Automation，机器人流程自动化）。它们和 Agent 到底差在哪？把它们放进一张表，用「谁控制流程」这把尺子去量，差异立刻清晰：

| 形态 | 谁控制流程 | 有无循环 | 能否用工具影响世界 | 与 Agent 的关系 |
|---|---|---|---|---|
| Chatbot（传统对话机器人） | 人（用户逐句驱动） | 无自主循环 | 通常不能 | 只是一问一答，缺自主推进 |
| Copilot（助手/副驾驶） | 人为主，AI 建议 | 半自主 | 能，但需人确认每一步 | 「人在方向盘上」的低自主 Agent |
| RPA（传统流程自动化） | 代码/规则写死 | 固定循环 | 能 | 流程僵硬，不由模型决策，是工作流 |
| **Agent** | **模型** | **自主循环** | **能，且自主决定** | 本书定义的完整形态 |

这张表点出三条常见的「差一点」：Chatbot 差在**没有自主推进任务的循环**（要人一句句喂）；RPA 差在**流程由规则写死、模型不参与决策**（本质是工作流）；Copilot 最接近 Agent，但它把「方向盘」留在人手里——每一步都要人拍板，自主性被刻意压低。理解这三个「差一点」，你就能在任何产品面前迅速判断它站在自主性光谱的哪个位置。

需要补一句：这四者不是互斥的物种，而是**同一套技术在自主性旋钮上的不同刻度**。把 Copilot 的「每步都要人确认」这个约束放开，它就滑向 Agent；把 Agent 的循环次数写死成固定值，它就退回工作流。理解「它们是光谱上的位置而非四个物种」，比死记表格更重要。

## 生产踩坑

| 症状 | 根因 | 如何观测与复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| 「Agent」上线后表现僵硬、分支走不对 | 实为路由型工作流，分支写死却按 Agent 宣传 | 检查代码是否有 `if 意图==X` 硬分支 | 承认它是路由工作流，或改造为真循环 | 意图确实有限且稳定时，路由本就够用 |
| 加了 function calling 就宣称做成了 Agent | 混淆「工具接口」与「自主循环」 | 看是否只调用一次即返回 | 加入循环与模型决定停止的逻辑 | 单次工具增强满足需求时无需升级 |
| 用「自主性」指标评估一个固定流程 | 没先判清系统属于哪一类 | 对照控制流归属做分类 | 工作流用确定性指标，Agent 才评自主性 | 混合系统需分层分别评估 |
| Copilot 硬改成全自主导致失控 | 把「人在回路」的确认环节全砍掉 | 回放高风险操作是否还有人工闸门 | 高风险动作保留人工确认 | 低风险、可逆操作可全自主 |
| RPA 场景硬塞大模型反而更不稳 | 流程本可写死，却引入非确定性 | 对比规则版与模型版的稳定性 | 稳定流程用规则，动态部分才用模型 | 流程频繁变化时模型更有弹性 |
| 团队争论「这算不算 Agent」无法收敛 | 未用统一的尺子 | 让双方各自指出「谁决定下一步」 | 统一用控制流归属 + 四判据 | 词源/学术语境讨论除外 |

## 思考：一个带 if-else 分支的 LLM 脚本，到底算不算 Agent？

### 回答

不算，它是路由型工作流。判断依据只有一条：分支是不是你事先枚举、写死在代码里的。如果模型只是在你划好的有限格子里选一个，它就没有掌控控制流——它不能新增格子、不能决定再来一轮、不能自己发明动作。真正的 Agent 里，「下一步做什么、要不要再循环、何时停」都是模型在运行时决定的，你无法在写代码前把路径画全。有 if-else、有工具调用，都不改变这个结论。

### 面试精简表达

有没有 if-else 不是分界线，控制流归属才是。分支写死、模型只是挑一个，那是路由（工作流）；模型自己决定下一步和何时停，才是 Agent。

## 思考：Copilot 和 Agent 有什么本质区别？

### 回答

它们不是两类东西，而是自主性光谱上的两个位置。Copilot 把控制权更多留给人——每一步需要人确认、人在回路（human-in-the-loop），AI 只提供建议；Agent 把控制权更多让渡给模型——自主决定下一步和何时停。同一套技术，调低自主性、加上「每步人工确认」就偏 Copilot，调高自主性、去掉确认环节就偏 Agent。所以问「是 Copilot 还是 Agent」，本质是在问「方向盘更多在人手里还是模型手里」。

### 反例

一个代码补全工具，每次都要你按 Tab 才采纳建议、从不自己连续改多个文件，这是典型 Copilot；如果它能自己规划「先改接口、再改调用方、再跑测试、失败就重来」并连续执行到测试通过，那它已经滑到 Agent 一侧了。

## 事故回放：一个「假 Agent」如何在验收时露馅

某金融团队交付一个「智能审批 Agent」，宣称能自主审核贷款申请。验收时，甲方出了一个刁钻用例：申请材料里缺一张收入证明，正常人会「发现缺件→向申请人索要→拿到后继续审」。结果这个「Agent」直接走进了「材料齐全」分支，因为它的意图判断只有「通过 / 拒绝 / 补充材料」三个写死的出口，而「补充材料」分支只是返回一句固定话术，没有任何「拿到材料后回到审核循环」的机制。它看起来像 Agent，实则是一个三分支路由器。

复盘时，团队用本节的尺子逐项检查，结论一目了然：控制流在代码（三个分支写死）、没有真正的循环（补件后无法回到审核）、模型不决定何时停（每次调用即终点）。三项全部落在工作流一侧。团队随后做了两个选择——对确定性强的部分（材料齐全性校验）保留规则化工作流，对需要多轮交互的部分（缺件补件循环）才改造成真正的 Agent 循环。这个「分而治之」的决定，正是先判清「什么不是 Agent」带来的直接收益：不是所有环节都需要 Agent，把该写死的写死、该循环的循环，系统才既稳又灵。
