## 真实问题

一场架构评审会上，两位资深工程师为「我们这个系统到底算不算 Agent」争了四十分钟。A 说「它用了大模型、能调工具、还能多轮对话，当然是 Agent」；B 说「它每一步都是我们代码里写死的分支，模型只是填空，这顶多算工作流」。两人都有道理，也都说服不了对方，因为他们用的是**定性词**——「智能」「自主」「高级」——这些词无法证伪，争到最后变成立场之争。会议纪要写下一句和稀泥的结论：「介于两者之间」，然后不了了之。

问题不在于谁对谁错，而在于**缺一套可观察、可逐项打勾的判据**。资深工程师和新手的区别，往往就在这里：新手争「它够不够智能」，资深工程师问「它满足哪几条可验证的条件」。本节把前面五节的所有讨论，收敛成一张任何人都能当场逐项打勾的「四判据体检表」——把定性的争论，变成定量的判定。

## 原理：把定义拆成四个「是/否」问题

前面章节反复出现一句权威定义的浓缩：**Agent 是由 LLM 控制工作流、在循环中自主使用工具、并根据环境反馈推进任务直至完成的系统**。这句话很漂亮，但落到实际判断时，你需要更可操作的抓手。可以把它拆成四个「是/否」问题，全部为「是」才是完整的 Agent：
```text
   判据 1：有没有循环？        （不是一次调用就结束）
   判据 2：有没有工具？        （能影响外部世界或获取新信息）
   判据 3：谁决定下一步？      （是模型，不是写死的代码）
   判据 4：谁决定何时停止？    （是模型基于反馈，不是固定次数）

   四个都"是" → 完整的 Agent
   缺 1、2    → 更像单次增强 LLM
   缺 3、4    → 更像工作流（workflow）
```
这四个判据不是随意罗列，而是分别对应本章前几节的核心：判据 1、2 来自 03 节「循环 + 工具」的骨架；判据 3、4 来自 02 节「控制流归属」这把尺子。它们构成一张「体检表」——不看系统「说自己是什么」，只看它「可观察地满足哪几条」。回到开头的争论：A 强调的是判据 1、2（有循环、有工具），B 强调的是判据 3、4（谁决定下一步与何时停）。用这张表一摆，两人立刻发现分歧点是判据 3、4——那个系统的分支和停止是代码写死的，所以判据 3、4 为「否」，结论是路由型工作流。四十分钟的争论，本可以用四个勾结束。

## 用体检表给几种系统打勾

下面的对比表把几种常被混淆的系统放在一起体检，分界线非常清晰：

| 系统 | 有循环 | 有工具 | 模型定下一步 | 模型定何时停 | 结论 |
|---|:---:|:---:|:---:|:---:|---|
| 单轮问答脚本 | 否 | 否 | 否 | 否 | 增强/普通 LLM 调用 |
| 情感分类器 | 否 | 否 | 否 | 否 | 一次固定调用 |
| 固定翻译流水线 | 否 | 是 | 否 | 否 | 工作流 |
| 意图路由客服（分支枚举） | 部分 | 是 | 有限 | 否 | 路由型工作流 |
| 固定次数批处理 | 是 | 是 | 否 | 否 | 固定循环工作流 |
| 自主调研 Agent | 是 | 是 | 是 | 是 | **完整 Agent** |

这张表的价值在于：面试或评审时，与其争论「这个到底算不算 Agent」，不如直接把它甩出来逐项打勾。把定性的争论变成逐条的判定，是资深工程师的思维习惯——**先建立可操作的判据，再下结论**。注意「固定次数批处理」这一行：它有循环、有工具，却因为「循环次数写死、模型不决定何时停」而落在工作流一侧，这再次说明判据 4 的分量——**光有循环不够，循环的控制权必须在模型手里**。

## 最小可运行演示：一张自动打分的体检表

把体检表做成可运行的程序，输入任意系统的四个布尔判据，输出结论。纯标准库，无需 API Key。
```python
def checkup(name: str, loop: bool, tools: bool, next_by_model: bool, stop_by_model: bool) -> str:
    flags = {"循环": loop, "工具": tools, "模型定下一步": next_by_model, "模型定何时停": stop_by_model}
    passed = [k for k, v in flags.items() if v]
    if loop and tools and next_by_model and stop_by_model:
        verdict = "完整 Agent"
    elif not next_by_model and not stop_by_model:
        verdict = "工作流（控制流在代码）"
    else:
        verdict = "介于增强调用与 Agent 之间（缺循环或缺工具）"
    return f"{name:16s} 满足[{'/'.join(passed) or '无'}] → {verdict}"


def main() -> None:
    print(checkup("单轮问答脚本", False, False, False, False))
    print(checkup("固定翻译流水线", False, True, False, False))
    print(checkup("意图路由客服", False, True, True, False))
    print(checkup("固定次数批处理", True, True, False, False))
    print(checkup("自主调研 Agent", True, True, True, True))


if __name__ == "__main__":
    main()
```
保存为 `agent_checkup.py`，运行 `python agent_checkup.py`。预期输出：
```text
单轮问答脚本      满足[无] → 工作流（控制流在代码）
固定翻译流水线     满足[工具] → 工作流（控制流在代码）
意图路由客服      满足[工具/模型定下一步] → 介于增强调用与 Agent 之间（缺循环或缺工具）
固定次数批处理     满足[循环/工具] → 工作流（控制流在代码）
自主调研 Agent    满足[循环/工具/模型定下一步/模型定何时停] → 完整 Agent
```
这段程序把「体检」自动化：你只要如实回答四个布尔问题，结论就确定了，没有争论空间。评审时把它跑一遍，比争四十分钟高效得多。

## 真实系统对应

**官方公开机制**：四判据是对 Anthropic「LLM 动态指挥流程 vs 代码预定义路径」[来源](https://www.anthropic.com/engineering/building-effective-agents) 与 LangGraph「在循环里调 LLM 直到不再调用工具才结束」[来源](https://langchain-ai.github.io/langgraph/) 的操作化拆解——判据 1（循环）、判据 4（模型决定何时停）直接对应 LangGraph 的退出条件；判据 3（模型决定下一步）对应 Anthropic 的「LLM 动态指挥」。**通用工程模式**：用「四个可观察判据」代替定性词做系统分类，是可迁移到任何评审的方法。**教学参考实现**：上面的 `checkup` 打分逻辑是本书为落地判据构造的，四个布尔字段的组合规则是教学简化，真实系统可能存在混合形态（部分环节是 Agent、部分是工作流），需要分层分别体检。

补一个重要边界：判据是用来**分类**的，不是用来**评优劣**的。一个系统被判为「工作流」不代表它差——Anthropic 明确建议大多数场景优先用更可预测的工作流，只在路径无法提前确定时才上 Agent [来源](https://www.anthropic.com/engineering/building-effective-agents)。所以体检表的正确用法是「先判清是哪一类，再用对应的方法去评估和优化」，而不是「判成 Agent 就高人一等」。

## 生产踩坑

| 症状 | 根因 | 如何观测与复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| 评审争「算不算 Agent」长时间无结论 | 用定性词而非可观察判据 | 统计争论里有几句可验证 | 直接跑四判据体检表逐项打勾 | 学术/词源讨论另当别论 |
| 混合系统被粗暴判成单一类别 | 没意识到系统可分层、各层不同 | 拆出各环节分别体检 | 分层打勾：哪层是 Agent、哪层是工作流 | 结构极简单的系统无需分层 |
| 判成「工作流」被误解为「做得差」 | 把分类当成优劣评价 | 回看是否有人据此贬低方案 | 明确判据只分类不评优劣 | 需要选型对比时另用成本/可控性指标 |
| 判据 3 与判据 4 被混为一谈 | 「定下一步」和「定何时停」概念不分 | 找一个模型选分支但不决定停的系统 | 分别验证两条，路由型常缺判据 4 | 两者恰好同时具备时可合并观察 |
| 只看「有没有工具」就下结论 | 误把工具接口当 Agent 充分条件 | 找一个只调一次工具即返回的系统 | 补看判据 1、4，工具非充分条件 | 明确单次工具增强场景无需纠结 |
| 体检表打勾主观、同一系统不同人不同结论 | 判据没有落到可观察证据上 | 让两人独立打勾对比差异 | 每条判据要求指出代码/轨迹证据 | 判据确实模糊的前沿形态可标注存疑 |

## 思考：面试官问「你怎么定义 Agent」，怎样回答能拿高分？

### 回答

高分回答有固定结构：**定义 + 分界线 + 反例 + 判据**。先抛权威定义——「Agent 是由 LLM 控制工作流、在思考-行动-观察循环中自主使用工具、并根据环境反馈推进任务直至完成的系统」；再点分界线——「关键不在于是否用了 LLM，而在于控制流在谁手里：归模型是 Agent，归代码是工作流」；接着给反例——「一个带 if-else 分支的 LLM 脚本、或对一千条数据逐条调模型的批处理，都有工具甚至循环，但控制权在代码，所以是工作流不是 Agent」；最后落到可操作判据——「实际判断我会用四条：有没有循环、有没有工具、模型是否决定下一步、模型是否决定何时停，全为是才是完整 Agent」。这个结构展示的不只是知识，更是「把模糊概念操作化」的工程思维，这正是面试官想看的。

### 面试精简表达

Agent = LLM 控制工作流、循环用工具、按反馈推进到完成。分界线是控制流归属，不是用没用 LLM。落地判断用四判据：循环、工具、谁定下一步、谁定何时停，全中才是完整 Agent。

## 思考：为什么说「先建立判据、再下结论」是资深工程师的习惯？

### 回答

因为它把不可证伪的争论变成可验证的判定。定性词（智能、自主、高级）无法证伪，两个人各执一词只能比嗓门；而可观察判据（有没有循环、控制流在谁手里）可以对着代码和运行轨迹逐条核实，谁对谁错由证据说话，而不是由立场说话。资深工程师在任何模糊问题前的第一反应，都是「先找到可观察、可验证的判据」，因为只有这样团队才能收敛到共识、决策才能被复盘。这个习惯不止用于判断 Agent——判断「这个 bug 修好了没」「这个架构合不合理」都适用：先定义可观察的通过条件，再逐项验证。本章教的四判据，本质是这个思维习惯在「Agent 定义」这个具体问题上的一次演练。

### 面试精简表达

定性词不能证伪，只能比立场；可观察判据能对着代码和轨迹逐条核实，让证据说话。资深工程师遇到模糊问题，第一步永远是把它操作化成可验证的判据。

## 完整实践：给你手边的三个系统做体检

学完四判据，最好的巩固方式是立刻拿它去体检真实系统。给你三个常见系统，请对照四判据逐项打勾，并写下每条判据的观察证据（而不是凭印象）。这里给出参考判定与理由，供你对答案：

第一个，**一个网页插件：选中文本后调用 LLM 生成摘要，返回结果即结束**。判据 1（循环）否——调一次即终点；判据 2（工具）否——只有一次模型调用；判据 3、4 否。结论：**不是 Agent**，是单次增强 LLM 调用。观察证据：代码里没有 for/while，没有工具执行后的观察。

第二个，**一个客服机器人：能根据用户问题决定「查订单/查物流/转人工」，调用相应工具，拿到结果后再决定是否继续追问**。这里要抠细节——如果「拿到结果后再决定是否继续追问」是模型基于观察自主判断的、可以循环多轮直到它认为解决，那么判据 1、2、3、4 都为是，结论是**完整 Agent**；但如果「是否追问」也是代码里写死的固定分支，那判据 3、4 存疑，退回路由型工作流。观察证据：看「是否继续」这个决定是模型输出的还是代码 if 出来的。这个例子的价值恰恰在于它落在边界上——同一句话描述，实现方式不同，结论就不同，这正是必须看代码而非听描述的原因。

第三个，**一个批处理脚本：对 1000 条评论逐条调用 LLM 打分，汇总成报表**。判据 1（循环）是——有 for 循环；判据 2（工具）视情况；判据 3 否——每条都做同样的事，模型不决定下一步；判据 4 否——循环次数是 `len(评论)` 写死的，模型不决定何时停。结论：**不是 Agent**，是固定循环批处理（工作流）。观察证据：循环次数由数据长度决定，模型只是被反复调用的一环。

做完这三道体检，你应该能体会到本章最想传递的能力：**判断 Agent 不靠感觉，靠对着代码和运行轨迹，逐条回答四个可观察的问题**。把这套习惯带到你自己的项目里，下次再有人问「这算不算 Agent」，你不必争论——把四判据摆出来，逐项打勾，结论自然浮现。
