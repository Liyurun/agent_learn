## 真实问题

回到导读里那场评审会。四个人对「Agent」有四种理解，返工三天。如果复盘会议录音，你会发现分歧点非常具体：产品经理说的是「效果」（能自动处理退款），后端说的是「接口」（调一次大模型），算法说的是「架构」（自主循环），测试说的是「可预测的流程」（能写死用例）。四个人都没错，错的是**这个词同时背负了太多期待，却没有一个公认的分界线**。

这类事故在 2023 年之后极其普遍：招聘 JD（Job Description，职位描述）写「Agent 开发」，来的候选人一半在讲提示词技巧、一半在讲多智能体编排；技术方案里写「引入 Agent」，评审时才发现有人指的是一次 GPT 调用、有人指的是一个能跑几十轮的执行器。词义不统一带来的沟通成本，往往比技术本身还高。要止损，第一步不是写代码，而是**回到最有工程指导价值的一手定义，锚定一条清晰的分界线**。

## 现象与输入：这个词被贴到了多少东西上

把 2023 年之后被叫做「Agent」的东西列出来，会看到一个惊人宽的光谱：
```text
被称为 "Agent" 的东西（从简单到复杂）：
1. 单轮问答脚本        —— 给 prompt，返回一段文本，结束
2. 情感分类器          —— 输入评论，输出「正面/负面」
3. 接了插件的聊天机器人  —— 能查天气、能算数，但每次都要人追问
4. 固定翻译流水线        —— 抽字段 → 调 LLM → 格式化，步骤写死
5. 带 if-else 的意图路由  —— LLM 判断意图，代码按分支执行
6. 自主调研执行器        —— LLM 自己决定查什么、算什么、何时停
```
从第 1 项到第 6 项，「自主性」单调递增，但它们全被塞进了「Agent」这一个词里。这就是**词义膨胀**：一个词的外延被无限扩大，直到失去区分能力。当一个词能指代从「问答脚本」到「自主执行器」的一切，它在技术讨论里就等于没有信息量。

## 原理：老词的低门槛遇上新词的高期待

理解这个词为什么乱，要往前看一点。「Agent（智能体）」不是大语言模型（Large Language Model，LLM）时代的发明。在经典人工智能教科书里，Agent 早有严格定义：**一个能感知环境（perceive）、并对环境采取行动（act）以实现目标的实体**。按这个古典定义，恒温器是 Agent（感知温度、开关加热），扫地机器人是 Agent（感知障碍、规划路径），下棋程序也是 Agent。这个定义强调的是「感知—行动」闭环，跟今天的 LLM 毫无关系，门槛也极低——连一个 `if 温度 < 20: 开加热` 的恒温器都算。

到了 2023 年，大模型突然让「用自然语言驱动的自主系统」成为可能，媒体和厂商就把这个老词借来贴到新东西上。冲突就此产生：

- **老词的门槛极低**：感知加行动就够了，恒温器都满足。
- **新词想表达的门槛极高**：能自己规划、自己调工具、自己纠错、自己判断任务是否完成。

同一个词，承载了两套差距巨大的期待。有人用古典的低门槛去理解（「能自动做点事就是 Agent」），有人用大模型时代的高期待去理解（「能自主完成复杂任务才是 Agent」），于是评审会上四个人各说各话。

本书的策略是**不纠结词源，只锚定当下最有工程指导价值的定义**。Anthropic 在工程博客《Building Effective Agents》里把这类系统统称「agentic systems（智能体系统）」，并在其中划出一条关键的架构分界：**工作流（workflow）是由预定义代码路径来编排 LLM 和工具的系统；而 Agent 是由 LLM 动态地指挥自己的流程与工具使用、自主掌控如何完成任务的系统** [来源](https://www.anthropic.com/engineering/building-effective-agents)。OpenAI 在《A Practical Guide to Building Agents》里的表述与之呼应：Agent 是**能代表用户独立完成任务的系统**，关键在于由模型控制工作流的走向 [来源](https://openai.com/business/guides-and-resources/a-practical-guide-to-building-ai-agents/)。

两家权威定义有一个共同的关键词：**由 LLM（模型）控制工作流**。这就是区分「Agent」与「非 Agent」的分水岭，也是本章后续所有判断的地基。

## 最小可运行演示：把「词义膨胀」变成可打分的判据

空谈定义没用，我们把「谁控制流程」变成一段可运行的打分程序。它给六种系统各打一个「自主性分数」，让你直观看到光谱。完全用标准库，无需 API Key。
```python
def autonomy_score(system: dict) -> int:
    keys = ["has_loop", "has_tools", "model_decides_next", "model_decides_stop"]
    return sum(1 for k in keys if system.get(k))


def label(score: int) -> str:
    if score >= 4:
        return "完整 Agent"
    if score >= 2:
        return "工作流 / 增强型调用"
    return "非 Agent（普通调用）"


def main() -> None:
    systems = {
        "单轮问答脚本": dict(has_loop=False, has_tools=False,
                        model_decides_next=False, model_decides_stop=False),
        "固定翻译流水线": dict(has_loop=False, has_tools=True,
                         model_decides_next=False, model_decides_stop=False),
        "意图路由客服": dict(has_loop=False, has_tools=True,
                        model_decides_next=True, model_decides_stop=False),
        "自主调研执行器": dict(has_loop=True, has_tools=True,
                         model_decides_next=True, model_decides_stop=True),
    }
    for name, s in systems.items():
        score = autonomy_score(s)
        print(f"{name:8s} 分数={score} 判定={label(score)}")


if __name__ == "__main__":
    main()
```
保存为 `autonomy_score.py`，运行 `python autonomy_score.py`。预期输出：
```text
单轮问答脚本   分数=0 判定=非 Agent（普通调用）
固定翻译流水线  分数=1 判定=非 Agent（普通调用）
意图路由客服   分数=2 判定=工作流 / 增强型调用
自主调研执行器  分数=4 判定=完整 Agent
```
这段代码的价值不在算法，而在于它把一个模糊的哲学争论（「它够不够智能」）替换成四个可勾选的布尔问题。评审会上再有人争「这算不算 Agent」，你就让他逐项回答这四个问题——分歧会立刻收敛到具体的一项上，而不是停在情绪化的定性争论。这四项就是第 06 节要展开的「四个可观察判据」。

## 真实系统对应

**官方公开机制**：Anthropic 明确把「agentic systems」拆成 workflow 与 agent 两类，判据是「LLM 与工具是被预定义代码路径编排，还是由 LLM 动态指挥」[来源](https://www.anthropic.com/engineering/building-effective-agents)；OpenAI 官方指南同样以「模型是否控制工作流」为核心 [来源](https://openai.com/business/guides-and-resources/a-practical-guide-to-building-ai-agents/)。**通用工程模式**：把系统按「控制流归属」而非「用没用大模型」来分类，是可迁移到任何团队的做法。**教学参考实现**：上面的 `autonomy_score` 只是把这条分界线做成可运行的打分器，四个布尔字段是本书为教学构造的抓手，不代表任何厂商内部的分类算法或评分标准。

值得强调的是：Anthropic 在同一篇文章里反复提醒「大多数应用其实应该用 workflow 而不是 agent」——因为 workflow 更可预测、成本可控，只有当任务的路径无法提前画出流程图时，才值得引入真正的 Agent。所以「不是 Agent」经常不是缺点，而是更合适的选择。词义收敛的目的不是给系统分高低贵贱，而是让「我们到底在做哪一类」这件事变得可讨论。

## 思考：为什么不干脆放弃「Agent」这个被玩坏的词，另造一个新词？

### 回答

因为词是沟通的既成事实，另造新词无法阻止别人继续用旧词，只会再增加一个需要对齐的术语。更有效的做法不是换词，而是**给词绑定一条可验证的分界线**：当有人说「Agent」，你追问「控制流在谁手里、谁决定何时停」，模糊的词立刻被拆成可回答的问题。行业已经这么做了——Anthropic 和 OpenAI 都没有放弃这个词，而是各自给出了「LLM 是否控制工作流」的判据。词的价值取决于是否有共识的判据，而不是词本身是否漂亮。

### 面试精简表达

不要纠结「Agent 这个词好不好」，要给它一条可判定的边界：控制流归模型就是 Agent，归代码就是工作流。定义清楚，争论自然消失。

## 思考：古典 AI 里恒温器也算 Agent，那本书的定义是不是「不严谨」？

### 回答

不是不严谨，而是**换了语境**。古典定义（感知+行动+目标）在描述「智能体」这个通用抽象时完全严谨，恒温器确实是一个最简单的反应式 Agent。本书的定义是它在大模型语境下的**收窄**：我们只讨论「由 LLM 作为决策核心、在循环中自主使用工具」的那一类，因为这一类才是当下值得被单独命名、单独讨论工程方法的对象。两个定义不矛盾，是「通用抽象」与「特定子类」的关系——就像「鸟」和「会飞的鸟」都成立，只是讨论范围不同。面试时若被问到这点，能主动点出「我用的是大模型语境下的收窄定义」，反而显出你对概念史有把握。

## 从一次招聘错配看词义收敛的价值

某团队曾发出一条「资深 Agent 工程师」的招聘需求，两周收到的候选人画像五花八门：三分之一的人简历重点是提示词工程与角色扮演；三分之一在讲检索增强与向量库；还有三分之一在讲多智能体编排与消息总线。面试时才发现，团队真正缺的是「能把带循环、带工具调用、带失败重试的执行器做稳」的人，而 JD 里只写了「Agent」两个字，导致筛选成本翻倍。

复盘后，团队把 JD 改成三段式：先给一句本书式定义（LLM 在循环中控制工作流、自主决定下一步与何时停），再写清「本岗位聚焦执行器的循环设计、工具接口与错误处理，不是纯提示词岗」，最后附一道小题——「请判断以下三个系统哪个是 Agent，并说明理由」。改版后候选人画像立刻收敛，面试通过率上升。这个例子说明：词义收敛不是学术洁癖，而是能直接省下真金白银的工程动作。把「Agent」从一个情绪词，变成一个带判据的技术词，是本章要交付的第一项能力。
