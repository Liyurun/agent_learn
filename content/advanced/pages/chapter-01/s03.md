## 真实问题

一个数据分析 Agent 被要求「统计上周各渠道的转化率并找出异常渠道」。第一版工程师用了「一次性规划」的思路：让 LLM 一口气生成完整的五步计划（拉数据→清洗→按渠道分组→算转化率→挑异常），然后代码依次执行。结果第二步就崩了——拉回来的数据里有个渠道字段是空的，清洗步骤没预料到，后面三步全部基于错误的中间结果，最终报告把一个正常渠道标成了异常，误导运营做了一次无意义的排查。

工程师第二版换了思路：不再让模型一次想好全部步骤，而是「想一步、做一步、看结果、再想下一步」。当清洗步骤发现空字段时，模型在下一轮看到了这个观察结果，于是插入一步「先填充或剔除空渠道」，再继续。这版跑通了。两版代码用的是同一个模型、同一批数据，差别只在于**有没有循环、有没有把每步的结果反馈回去**。这就是 Agent 的本质所在。

## 原理：Agent = LLM + 循环 + 工具 + 环境反馈

什么让一个系统「配得上」Agent 这个称呼？答案是一个简洁的心智模型：

> **Agent = LLM + 循环 + 工具 + 基于环境反馈的决策**

拆开来看：

- **LLM**：作为「大脑」，负责推理和决策——下一步该做什么。
- **循环（Loop）**：Agent 不是一次调用就结束，而是「思考—行动—观察」反复迭代，直到任务完成。
- **工具（Tools）**：Agent 能调用外部能力（搜索、计算、读写文件、调 API）来影响真实世界或获取新信息。
- **环境反馈（Feedback）**：每次行动后，Agent 观察结果，并据此决定下一步——这正是「自主性」的来源。

这个循环最经典的形式就是 **ReAct（Reasoning and Acting，推理与行动）循环**：`Thought（思考）→ Action（行动）→ Observation（观察）`，然后回到 Thought，如此往复。ReAct 由 Yao 等人在 2022 年提出，核心主张是让语言模型**交替产生推理轨迹与行动**——推理帮助模型决定下一步做什么，行动则让模型获取能改进后续推理的新信息 [来源](https://arxiv.org/abs/2210.03629)。我们将在第 4 章深入它，这里你只需记住：**「在循环中根据反馈调整」是 Agent 区别于一次性调用的灵魂。**

## 为什么「循环」是不可省略的：从部分可观测说起

初学者常问：为什么非要循环？让模型一次性把整个计划想好、一口气执行完，不行吗？开头那个数据分析的事故已经给了答案，这里从原理上说清。

**LLM 无法在行动之前预知行动的结果**。当 Agent 决定「拉上周数据」时，它并不知道会拉回什么（可能有空字段）；当它「读取一个文件」时，它不知道文件里有什么；当它「调用一个 API」时，它不知道会返回成功还是报错。真实世界是**部分可观测（partially observable）**的——信息要靠行动一点点揭开，而不能在开始时就全部预知。

这意味着计划必须是**走一步、看一步、再修正**的。这正是循环存在的根本理由：
```text
   一次性规划（脆弱）                循环式规划（鲁棒）
   ┌────────────────┐              ┌──────────────────────────┐
   │ 想好全部 5 步    │              │ 想第 1 步 → 做 → 看结果    │
   │ 依次执行         │              │ 基于结果想第 2 步 → 做     │
   │ 第 2 步就偏了    │              │ 发现空字段 → 插入清洗 → 继续│
   │ 后面全错         │              │ 直到判断"任务完成"         │
   └────────────────┘              └──────────────────────────┘
   环境一变就崩                      每轮都吸收新信息、自我纠错
```
换句话说，循环把「一次性的开卷考试」变成了「持续的反馈控制系统」。控制论里有个词叫**闭环控制（closed-loop control）**——系统根据输出的反馈不断调整输入。Agent 的循环本质上就是把 LLM 放进了一个闭环里。这也是为什么定义里「基于环境反馈的决策」这几个字是灵魂：去掉反馈，循环就退化成机械的重复；去掉循环，反馈就无处可去。两者缺一，自主性就不成立。

## 部分可观测：一个可运行的对照演示

我们用一段代码把「部分可观测」变得可触摸。同一个任务，用「一次性规划」和「循环式规划」各跑一遍，看前者如何在环境变化时崩掉。纯标准库，无需 API Key。
```python
def fetch_data():
    """模拟拉数据：故意混入一个空渠道，代表运行时才暴露的意外。"""
    return [("直播", 100, 12), ("搜索", 200, 30), ("", 0, 0)]


def one_shot_plan(rows):
    """一次性规划：预设所有渠道都有效，遇到空渠道会算出除零或误判。"""
    result = []
    for name, visit, convert in rows:
        rate = (convert / visit) if visit else 999  # 空渠道被赋一个荒谬值
        result.append((name or "未知", rate))
    return result


def loop_plan(rows):
    """循环式规划：每处理一步先观察，发现异常输入就先清洗再继续。"""
    cleaned = [r for r in rows if r[1] > 0]  # 观察到空渠道 → 先剔除
    result = [(name, round(convert / visit, 3)) for name, visit, convert in cleaned]
    return result


def main() -> None:
    rows = fetch_data()
    print("一次性规划结果：", one_shot_plan(rows))
    print("循环式规划结果：", loop_plan(rows))


if __name__ == "__main__":
    main()
```
保存为 `observability_demo.py`，运行 `python observability_demo.py`。预期输出：
```text
一次性规划结果： [('直播', 0.12), ('搜索', 0.15), ('未知', 999)]
循环式规划结果： [('直播', 0.12), ('搜索', 0.15)]
```
一次性规划把空渠道算成了转化率 999（一个会污染后续判断的荒谬值），因为它在「规划时」根本不知道数据里有空字段；循环式规划先观察到异常、先清洗再计算，输出干净。这就是「部分可观测」的代价与「循环+反馈」的价值——不是模型更聪明，而是它有机会看见结果、修正下一步。真正的 Agent 里，`loop_plan` 的「先剔除再算」这个决定是模型在看到观察结果后做出的，而不是代码预先写死的。

## 真实系统对应

**官方公开机制**：ReAct 论文明确提出「交替进行推理与行动」的范式，并在多跳问答、事实核查、交互决策等任务上验证其可解释的决策轨迹 [来源](https://arxiv.org/abs/2210.03629)。LangGraph 官方把 Agent 的运行刻画为「在循环里反复调用 LLM 问它下一步的动作，直到模型返回不含工具调用的最终回复」，并强调它是一个支持「环（cycle）」的框架而非 DAG（Directed Acyclic Graph，有向无环图）——因为环正是「在循环中调用 LLM」这一行为的技术前提 [来源](https://langchain-ai.github.io/langgraph/)。OpenAI 的 Agents SDK（Software Development Kit，软件开发工具包）用一个 `Runner` 来「驱动这个循环」：调用模型、执行模型请求的工具、把结果喂回去、再问下一步，直到得到最终输出 [来源](https://openai.com/business/guides-and-resources/a-practical-guide-to-building-ai-agents/)。**通用工程模式**：把「思考—行动—观察」做成显式循环，是各框架共有的骨架。**教学参考实现**：上面的对照代码是本书构造的最小演示，`loop_plan` 里的清洗逻辑代表模型基于反馈做出的决策，不代表任何框架的内部实现。

三家来源指向同一件事：Agent 的运行时形态就是一个 while 循环，循环体是「问模型下一步→执行→反馈」，退出条件是「模型说完成了」。理解了这一点，你看任何 Agent 框架的源码，都能一眼找到那个循环在哪里。

## 从 CoT 到 ReAct：为什么「只推理」还不够

在 ReAct 之前，让模型「想清楚」的经典手法是 CoT（Chain-of-Thought，思维链）——让模型把推理过程一步步写出来，答案的准确率会显著提升。但 CoT 有个天花板：**它只在模型「脑内」推理，无法与外部世界交互**。如果一道题需要「查一个模型不知道的事实」，再漂亮的思维链也只能靠模型的记忆去猜，猜错了也没有纠正的机会。

ReAct 的贡献正是补上这块短板：**让推理和行动交替进行**。模型先推理（Thought：我需要先知道当前副本数），再行动（Action：查询指标接口），观察结果（Observation：当前 4 个副本），再推理（Thought：目标 960 QPS，每副本 120，需要 8 个），如此循环。推理决定「做什么」，行动带回「新信息」，新信息又改进下一轮推理。用一句话概括三者关系：
```text
CoT（思维链）      ：只在脑内推理，不与外界交互 —— 会算，但查不到新事实
Tool use（工具）   ：能调外部能力，但若只调一次不成循环 —— 能查，但不会基于结果迭代
ReAct（推理+行动） ：推理与行动交替、循环 —— 既会算又会查，还能基于观察纠错
```
这解释了为什么本书把「循环 + 工具 + 反馈」三者绑在一起讲：单有工具（只调一次）不是 Agent，单有推理（CoT）不是 Agent，只有当推理与行动在循环里交替、每轮行动的结果都反馈进下一轮推理时，才涌现出我们称之为「自主」的行为。

## 生产踩坑

| 症状 | 根因 | 如何观测与复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| 复杂任务前几步就跑偏且无法纠正 | 用一次性规划，模型无法看到中间结果 | 打印每步中间产物，注入一条异常输入复现 | 改为循环式，每步观察后再决定下一步 | 步骤简单且环境完全可预测时可一次规划 |
| 任务需要外部事实却总靠模型猜 | 只有推理没有工具（纯 CoT） | 问一个训练截止后才发生的事实 | 加入检索/查询工具，让行动带回新信息 | 纯逻辑推理题无需外部工具 |
| 加了工具但只调一次就返回 | 有工具无循环，退化成单次增强调用 | 检查是否有 while/for 与停止判定 | 把工具调用放进循环，由模型决定是否再来 | 单次工具增强满足需求时无需循环 |
| 循环跑起来但模型每轮都从头开始 | 观察结果没有反馈进下一轮上下文 | 打印每轮传入模型的历史，看有无累积 | 把 observation 追加进历史再喂给下一轮 | 无状态的独立子任务可不累积 |
| 环境返回错误但 Agent 视而不见 | 反馈里只传成功结果，吞掉了报错 | 故意让工具抛错，看下一轮是否感知 | 把错误信息也作为 observation 反馈 | 明确可忽略的软错误可降级处理 |

## 思考：为什么循环不能改成「让模型一次性规划好全部步骤再执行」？

### 回答

因为真实世界是部分可观测的——模型在行动前无法预知行动的结果。一次性规划假设「所有信息在开始时就已知」，可现实里数据可能有空字段、API 可能报错、检索可能落空，这些只有做了才知道。一次性规划遇到第一个意外就会连环崩溃，因为后续步骤全部建立在错误的中间结果上。循环式规划则每做一步就观察结果、再决定下一步，能在环境变化时自我纠错。循环的本质是把 LLM 放进闭环控制里：根据输出的反馈不断调整下一步输入。

### 面试精简表达

真实世界部分可观测，信息要靠行动一点点揭开，所以必须走一步看一步。循环 = 把 LLM 放进闭环控制，一次性规划 = 开环，环境一变就崩。

## 思考：ReAct 相比只用工具调用（Tool use）或只用思维链（CoT）好在哪？

### 回答

CoT 只在模型脑内推理，会算但查不到新事实，遇到需要外部信息的任务只能猜；单纯的工具调用如果只调一次、不成循环，能查一次但不会基于结果迭代纠错。ReAct 把两者绑进循环：推理决定「做什么」，行动带回「新信息」，新信息又改进下一轮推理，并且每轮的观察都能触发纠错。所以 ReAct 既会算又会查，还能在观察到错误后调整——这是前两者单独都做不到的。关键不在某一项能力，而在「推理与行动在循环中交替、反馈闭环」这个结构。

### 面试精简表达

CoT 只会想不会做，单次工具只会做一次不会迭代，ReAct 让想和做在循环里交替、用观察纠错，三者的差别是结构而非能力堆叠。

## 机制推导：一次循环里，信息是怎么流动的

把贯穿案例（扩容问答）放进循环里走一遍，能看清信息流。第一轮，模型的上下文里只有任务「扩容到 960 QPS 需要几个副本」和可用工具列表。它没有当前副本数这个事实，于是推理「我得先查现状」，行动「调用指标查询工具」。工具执行后，环境返回「当前 4 个副本、单副本 120 QPS」——这条信息此刻并不在模型「脑子」里，而是通过行动从环境取回的，这就是 environment feedback。

第二轮，模型的上下文变了：多了上一轮的观察结果。它现在能推理「目标 960，每副本 120，需要 8 个，当前 4 个，还差 4 个」，于是行动「调用计算工具算 960/120 与 8-4」。第三轮，模型看到计算结果齐全，推理「信息够了，可以收尾」，输出最终答案并退出循环。

这个流动过程有三个不变量，任何 Agent 都成立：第一，**每一轮的决策都依赖上一轮的观察**——没查到副本数就没法算差值，这是循环不可省略的活证据；第二，**新信息通过行动进入、通过反馈累积**，上下文随轮次增长；第三，**退出由模型基于「信息是否足够」判定**，而非代码数到某个固定次数。把这三个不变量记牢，你调试任何 Agent 时，都能问出三个精准问题：这一轮的决策依据了哪条观察？新信息有没有正确反馈进下一轮？停止是模型判定的还是代码强停的？下一节我们就把这个循环用可运行的代码完整实现出来。
