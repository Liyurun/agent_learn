## 真实问题

前面五节把 CoT（Chain-of-Thought，思维链）、ReAct（Reasoning and Acting，推理与行动）、Plan-and-Execute（先规划后执行）、ReWOO（Reasoning WithOut Observation，无观察推理）、ToT（Tree of Thoughts，思维树）都讲了一遍。但面试和实战里最容易翻车的，是把它们停留在“能背定义”的层面。一个真实的追问是：“同一个任务，你用 ReAct 和 Plan-Execute 分别实现，运行轨迹和调用成本到底差在哪？请当场写出来。”很多人这时才发现，自己能说清概念，却写不出两种骨架的**控制流差异**——ReAct 是“每步回模型问下一步”，Plan-Execute 是“先规划一次、执行不回头”，这个差异必须落到代码的循环结构上才算真懂。

这一节不引入新范式，而是把最实用的两种——ReAct 与 Plan-Execute——拼成一个**完整可运行**的对比程序，让你亲手跑出“同一任务、两种骨架、不同调用轨迹”的结果，并补上生产必备的“死循环护栏”。全部代码纯 Python、无需 API Key。

## 原理：两种控制流的差异落到代码上

把第 03、04 节的原理浓缩成两句代码级的判断：
```text
ReAct 的循环结构:
  while 未完成:
      decision = LLM(context)     # 每一轮都调一次 LLM 决定下一步
      obs = 执行(decision.action)  # 执行工具
      context += [thought, action, obs]  # 观察回写,进入下一轮

Plan-Execute 的控制流:
  plan = LLM(question)            # 只调一次 LLM,产出完整计划
  for step in plan:              # 逐步执行,循环体内不调 LLM
      results[step] = 执行(step)
  answer = LLM(results)          # 再调一次 LLM 汇总
```
核心差异一目了然：**ReAct 的 LLM 调用在循环体内（随步数增长），Plan-Execute 的 LLM 调用在循环体外（头尾各一次）。** 这就是第 04 节量化过的“调用成本差异”的代码根源。下面用一个可运行程序把这个差异跑出来。

## 最小可运行演示：同一任务，两种骨架

这段程序用贯穿任务 A（折扣计算，两步）分别跑 ReAct 和 Plan-Execute，打印各自的完整运行轨迹和 LLM 调用统计。
```python
"""规划模式实战:同一个"多步折扣计算"任务,分别用 ReAct(边想边做)与
Plan-Execute(先规划后执行)两种骨架跑一遍,打印各自的运行轨迹与统计,
让你直观看到两种控制流的差异。纯 Python,无需 API Key。"""

import re

## 共享工具区:真实副作用都在这里发生
def calculator(expr: str) -> str:
    if not re.fullmatch(r"[\d\s\.\+\-\*\/\(\)]+", expr):
        return "错误:非法字符"
    try:
        return str(round(eval(expr), 4))
    except Exception as exc:
        return f"错误:{exc}"

## ReAct 骨架:每一步都回模型问"下一步",靠已观察数量推进
def run_react(question: str, max_iters: int = 6) -> dict:
    print("=== ReAct 轨迹 ===")
    context: list[str] = [f"问题:{question}"]
    llm_calls = 0
    steps = [
        ("先算 7 折后再减 20 元", "120*0.7-20"),
        ("再算相比原价省了百分之几", "(120-64)/120*100"),
    ]
    for i in range(max_iters):
        observations = [x for x in context if x.startswith("Observation:")]
        llm_calls += 1                        # 每轮都要一次 LLM 决策
        if len(observations) >= len(steps):   # 自然终止
            print(f"[LLM 决策#{llm_calls}] 判定任务完成")
            return {"mode": "ReAct", "llm_calls": llm_calls,
                    "answer": "最终 64.0 元,省约 46.67%"}
        thought, arg = steps[len(observations)]
        obs = calculator(arg)
        context += [f"Thought: {thought}", f"Action: calculator({arg})",
                    f"Observation: {obs}"]
        print(f"[LLM 决策#{llm_calls}] Thought={thought}")
        print(f"                Action=calculator({arg}) -> {obs}")
    return {"mode": "ReAct", "llm_calls": llm_calls, "answer": "达到步数上限"}

## Plan-Execute 骨架:先一次规划出完整计划,再逐步执行,执行不再调 LLM
def run_plan_execute(question: str) -> dict:
    print("=== Plan-Execute 轨迹 ===")
    llm_calls = 0
    llm_calls += 1                            # 步骤1:一次性规划
    plan = [
        ("算折后价", "120*0.7-20", "#S1"),
        ("算节省比例", "(120-64)/120*100", "#S2"),
    ]
    print(f"[LLM 规划#{llm_calls}] 产出计划:")
    for desc, expr, slot in plan:
        print(f"    {slot}: {desc} = calculator({expr})")
    results = {}
    for desc, expr, slot in plan:             # 步骤2:批量执行,不调 LLM
        results[slot] = calculator(expr)
        print(f"    执行 {slot} -> {results[slot]}")
    llm_calls += 1                            # 步骤3:一次性汇总
    print(f"[LLM 汇总#{llm_calls}] 代入 {results}")
    return {"mode": "Plan-Execute", "llm_calls": llm_calls,
            "answer": f"最终 {results['#S1']} 元,省约 {results['#S2']}%"}

def main() -> None:
    q = "某书原价120元,打7折后再减20元优惠券,最终多少钱?省了百分之几?"
    react = run_react(q)
    print()
    plan = run_plan_execute(q)
    print()
    print("=== 对比小结 ===")
    print(f"ReAct        : LLM调用={react['llm_calls']} 答案={react['answer']}")
    print(f"Plan-Execute : LLM调用={plan['llm_calls']} 答案={plan['answer']}")
    print(f"结论: 本例两步任务, Plan-Execute 省 {react['llm_calls'] - plan['llm_calls']} 次 LLM 调用")

if __name__ == "__main__":
    main()
```
保存为 `planning_lab.py`，运行 `python planning_lab.py`。预期输出为：
```text
=== ReAct 轨迹 ===
[LLM 决策#1] Thought=先算 7 折后再减 20 元
                Action=calculator(120*0.7-20) -> 64.0
[LLM 决策#2] Thought=再算相比原价省了百分之几
                Action=calculator((120-64)/120*100) -> 46.6667
[LLM 决策#3] 判定任务完成

=== Plan-Execute 轨迹 ===
[LLM 规划#1] 产出计划:
    #S1: 算折后价 = calculator(120*0.7-20)
    #S2: 算节省比例 = calculator((120-64)/120*100)
    执行 #S1 -> 64.0
    执行 #S2 -> 46.6667
[LLM 汇总#2] 代入 {'#S1': '64.0', '#S2': '46.6667'}

=== 对比小结 ===
ReAct        : LLM调用=3 答案=最终 64.0 元,省约 46.67%
Plan-Execute : LLM调用=2 答案=最终 64.0 元,省约 46.6667%
结论: 本例两步任务, Plan-Execute 省 1 次 LLM 调用
```
读懂这段输出的关键：

- **ReAct 有 3 次 LLM 决策**：两次“决定并执行一步”+ 一次“判定完成”。每次决策都发生在循环体内，携带完整 `context`。
- **Plan-Execute 只有 2 次 LLM 调用**：一次规划 + 一次汇总。中间两步执行（`#S1`、`#S2`）都在循环体内完成，不调 LLM。
- **工具调用次数两者相同**（都算了两个表达式）——差异只在“决定下一步”的 LLM 调用。任务步数越多，这个差距越大，这正是第 04 节 ReWOO “省 token” 的同源直觉。
- 两者答案一致（都是 64.0 元、约 46.67%），说明在“步骤依赖可预测”的任务上，Plan-Execute 用更少的 LLM 调用得到了同样正确的结果。

## 生产必备：给 ReAct 循环加“死循环护栏”

上面的 ReAct 演示是“乖巧”的——假模型每步都推进。真实模型可能“原地打转”：反复调同一个工具、传同样的参数，卡在一个状态出不来。光靠 `max_iters` 硬上限还不够（它要浪费满所有步数才停），生产里还需要“检测连续重复动作并主动打断”。下面这段代码演示这个护栏。
```python
"""死循环检测:当模型连续提出相同 Action 时主动打断,
而不是傻等到 max_iters 才停。这是 ReAct 生产化必备的护栏之一。"""

def run_with_guard(actions: list[str], max_iters: int = 8, repeat_limit: int = 3) -> str:
    history = []
    for step, action in enumerate(actions[:max_iters], start=1):
        history.append(action)
        # 检测最近 repeat_limit 步是否为同一个 Action
        recent = history[-repeat_limit:]
        if len(recent) == repeat_limit and len(set(recent)) == 1:
            return f"第{step}步触发重复护栏:连续 {repeat_limit} 次调用 {action},主动打断"
        print(f"[步骤{step}] 执行 {action}")
    return "正常结束或达到步数上限"

def main() -> None:
    # 模拟一个"原地打转"的轨迹:反复搜同一个查询
    loop_trace = ["search(天气)", "search(天气)", "search(天气)", "search(天气)"]
    print(run_with_guard(loop_trace))

if __name__ == "__main__":
    main()
```
保存为 `loop_guard.py`，运行 `python loop_guard.py`。预期输出为：
```text
[步骤1] 执行 search(天气)
[步骤2] 执行 search(天气)
第3步触发重复护栏:连续 3 次调用 search(天气),主动打断
```
这段护栏的价值：模型第 1、2 步都在重复搜“天气”，到第 3 步连续重复达到 `repeat_limit=3`，护栏立刻打断，而不是白白跑满 8 步。真实系统里，打断后的处理可以是“强制换工具/换参数”“把重复事实提示给模型”或“升级为人工介入”。注意护栏要区分“恶性重复”和“合法重试”——带指数退避的重试（比如 API 限流后隔几秒再试）不应被误杀，所以生产实现通常会把“参数完全相同且无退避”作为触发条件。

## 真实系统对应

**官方公开机制**：LangGraph 的 `create_react_agent` 内置了“LLM 调用—工具执行循环—条件路由”，并支持 `recursion_limit` 之类的步数上限；LangChain 官方文档把 Agent 描述为“推理与行动的交替”，并提供 plan-and-execute 参考实现 [来源](https://docs.langchain.com/oss/python/langchain-agents)。**通用工程模式**：本节的“循环体内/外 LLM 调用”结构、死循环护栏、观察回写，都是可迁移到任何框架的通用做法。**教学参考实现**：`planning_lab.py`、`loop_guard.py` 用规则模拟 LLM 决策与轨迹，不代表任何框架的内部调度；真实框架用模型原生工具调用接口拿结构化动作，其 token 计费也取决于每次携带的上下文长度。

需要明确边界：本节代码统计的是“LLM 调用次数”，这是 token 成本的一个代理指标，但不是全部——真实成本还取决于每次调用携带的上下文长度（ReAct 越到后面上下文越长，单次调用越贵）。所以 ReAct 相对 Plan-Execute 的真实成本劣势，往往比“调用次数差”更大。

## 生产踩坑

| 症状 | 根因 | 如何观测与复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| ReAct 跑满 max_iters 才停，浪费大量调用 | 只有硬上限，没有重复检测 | 注入原地打转轨迹，看是否提前打断 | 加“连续重复动作”护栏主动打断 | 合法退避重试不应触发护栏 |
| 用关键词判断进度导致误判 | 问题文本恰好含该关键词 | 让问题包含状态关键词复现 | 改用“已观察次数”等结构化状态判断 | 无状态的一次性任务无需进度判断 |
| Plan-Execute 计划一次成型后错到底 | 缺重规划，执行不回头 | 注入中途失效步骤复现 | 关键步失败触发 Replan 或回退 ReAct | 完全确定的流水线可省 |
| 只统计调用次数，低估真实成本 | 忽略每次调用的上下文长度 | 记录每次调用的 token 数 | 同时监控调用数与累计 token | 短任务差异可忽略 |
| 两种骨架混用导致行为难预测 | 没有明确的路由规则 | 记录哪些任务走哪条骨架 | 按“依赖可预测性”明确路由 | 单一任务类型无需路由 |
| 护栏把合法重试也打断 | 触发条件只看动作名 | 构造带退避的重试序列 | 触发条件加“参数相同且无退避” | 幂等且无害的重复可放宽 |

## 思考：面试时被要求“当场写一个最小 ReAct 循环”，最容易漏掉什么？

### 回答

最容易漏掉三点，任漏一点都会被追问。第一，**两种终止条件缺一不可**：只写自然终止（模型判定完成）会死循环，只写 max_iters 硬上限会浪费步数且无法在完成时提前退出，必须两者都有。第二，**“模型提议、运行时执行”的分工**：动作必须由代码执行、观察必须回写上下文，不能让模型“假装”执行了工具——这是安全边界，也是 ReAct 区别于 CoT 的本质。第三，**运行时校验**：工具执行前要校验参数合法性（如本章 calculator 的正则白名单），绝不盲信模型输出。能把这三点写进循环，才算真正理解 ReAct，而不是背了个“Thought-Action-Observation”。

### 面试精简表达

三件套别漏：双终止（自然+硬上限）、模型只提议代码才执行、执行前先校验参数。

## 思考：为什么本章的演示代码都用“假模型”而不是真调 API？

### 回答

三个原因。第一，**可复现**：假模型的输出是确定的，读者在任何机器上跑都能得到与书里逐字一致的预期输出，便于核对是否理解正确；真调 API 每次结果都可能不同，无法作为教学基准。第二，**聚焦控制流**：本章要讲的是“规划的骨架和循环结构”，而不是“提示词怎么写”，用假模型能把注意力集中在循环、终止、护栏、调用计数这些结构性问题上，不被模型能力波动干扰。第三，**零门槛**：无需 API Key、无需联网、无需付费，读者立刻能跑。真实工程里，你只需把假模型（`fake_model`/固定 steps）换成一次真实 LLM 调用（配合 Function Calling 拿结构化动作），骨架完全不用变——这恰恰证明了“范式与具体模型解耦”。

## 完整实践：把两种骨架接到你自己的任务上

要把本节的教学骨架变成能用的东西，只需三步替换，骨架结构完全保留。第一步，把 `calculator` 换成你真实的工具（数据库查询、HTTP 调用、检索接口），并保留“执行前校验参数”这一行——这是安全底线。第二步，把 ReAct 里的 `steps`（固定脚本）和 Plan-Execute 里的 `plan`（固定计划）换成真实 LLM 调用：ReAct 每轮把 `context` 发给模型、用 Function Calling 拿回结构化的 `{thought, tool, arg}`；Plan-Execute 则把 `question` 发给模型、拿回一份带步骤和依赖的计划 JSON。第三步，把 `loop_guard` 的重复检测并进 ReAct 主循环，并为 Plan-Execute 补上“关键步失败即触发 Replan 或回退 ReAct”的分支。

替换后你会发现一个规律：**决定用哪种骨架的，不是模型多强，而是任务的依赖结构**。步骤独立、可预先确定的（如“分别查 N 个指标再汇总”）用 Plan-Execute 省调用；依赖运行时才显现的（如“先搜到线索才知道下一步搜什么”）用 ReAct 边看边定。绝大多数真实 Agent 是“ReAct 主干 + 局部 Plan-Execute/ReWOO 优化热点 + 关键推理用 Self-Consistency 兜底”的混合体，而不是纯粹的单一范式。
