## 真实问题

一家出海电商的客服 Agent 被问：“我上周下的那单，物流到哪了？”第一版用纯 CoT（Chain-of-Thought，思维链）实现，没有接任何工具。模型“脑内推理”得很流畅：“根据一般跨境物流时效，上周下单，现在应该已经到清关环节了，预计 2～3 天送达。”听起来很专业，却全是编的——它根本不知道这个用户的订单号，更没查过物流系统，那句“到清关环节”是纯粹的幻觉。用户按这个回复等了三天，包裹其实早在两天前就因地址错误被退回了。

问题的根源是：**CoT 只能在模型脑内推理，无法与外部世界交互，信息全靠记忆，遇到需要实时/私有数据的任务必然幻觉。** 团队把它改成 ReAct 后，同样的问题变成：模型先 Thought“我需要用户的订单号才能查物流”，Action 调用 `get_recent_order(user_id)` 拿到订单号，再 Action 调用 `track_logistics(order_id)`，Observation 返回“因地址错误已退回”，最后据此给出准确回复。**推理让它知道该查什么，行动让它拿到真实数据，两者交织，幻觉被真实观察锚定住了。**

## 原理：ReAct 的核心循环

**ReAct（Reasoning and Acting，推理与行动）** 的贡献是把推理和行动交织起来，让模型一边思考、一边调用工具获取真实信息，再根据观察调整下一步推理 [来源](https://arxiv.org/abs/2210.03629)。它的循环结构是本章乃至全书最核心的公式：
```text
┌──────────────────────────────────────────────┐
│  Thought(思考):我现在该做什么?               │
│      ↓                                         │
│  Action(行动):调用某个工具 + 参数            │
│      ↓                                         │
│  Observation(观察):工具返回的结果            │
│      ↓                                         │
│  (回到 Thought,直到得出最终答案)             │
└──────────────────────────────────────────────┘
```
一个具体的 ReAct 轨迹（回答“某公司现任 CEO 是谁”）：
```text
Thought: 我需要查最新信息,用搜索工具。
Action: search("XX公司 现任 CEO 2026")
Observation: 搜索结果显示现任 CEO 是张三,2025 年上任。
Thought: 已获得答案,可以回复了。
Answer: XX 公司现任 CEO 是张三(2025 年上任)。
```
ReAct 的关键优势用论文的话说是：**动作空间 = 任务动作 + 语言空间**——模型既能执行外部动作（搜索、计算），又能用语言进行内部推理，两者在同一个循环里协同。论文显示，相比只会行动、不会推理的基线（Act-only）和只会推理、不会行动的基线（CoT-only），ReAct 在知识密集型问答（如 HotpotQA）和交互决策任务（如 ALFWorld、WebShop）上都更好，且更不容易幻觉 [来源](https://arxiv.org/abs/2210.03629)。现代几乎所有 Agent 框架的内核，本质上都是 ReAct 循环的实现——LangChain 的 `create_agent()` 就明确说明自己是“基于 ReAct 论文的、生产就绪的推理与行动 Agent 实现” [来源](https://docs.langchain.com/oss/python/langchain-agents)。

## 为什么“推理”和“行动”缺一不可

ReAct 论文最精彩的论证，是它对照三条基线，说明为什么两者必须交织：
```text
只推理不行动(CoT-only):
   模型在脑内推理很流畅,但信息全靠"记忆",
   容易产生幻觉——它会自信地编造一个不存在的物流状态。

只行动不推理(Act-only):
   模型会调工具,但不会"想",
   拿到搜索结果不知道下一步该干嘛,容易在动作间迷失。

ReAct(推理 + 行动):
   Thought 负责"消化观察、决定下一步",
   Action 负责"从真实世界取证",
   两者互相校准 —— 推理指导行动,观察修正推理。
```
一句话总结：**推理让行动有方向，行动让推理有依据。** 纯推理的 CoT 像一个闭卷考试的学生，全凭记忆容易记错；纯行动的 Agent 像一个只会翻书却不会思考的人，找到资料也不知道怎么用。ReAct 把两者拧在一起，形成“思考→取证→再思考”的良性循环，这也是它能大幅抑制幻觉的根本原因——每一步推理都有真实观察来锚定。

## 最小可运行演示

原论文给出的是伪代码骨架，这里我们把它落成一段**可以真正跑起来**的最小 ReAct 实现。它不依赖任何框架，用一个基于“已观察次数”的假模型来驱动循环，方便你在本地直接运行、单步调试。这段代码完整演示了贯穿任务 A（折扣计算）的两步 ReAct 轨迹。
```python
import re

## 工具区:真实副作用都在这里发生
def calculator(expr: str) -> str:
    if not re.fullmatch(r"[\d\s\.\+\-\*\/\(\)]+", expr):   # 只允许算术字符
        return "错误:表达式含非法字符"
    try:
        return str(eval(expr))          # 教学演示用 eval,生产请用受限解析器
    except Exception as exc:
        return f"错误:{exc}"

def search(query: str) -> str:
    kb = {"原价": "某书原价为 120 元"}
    for key, value in kb.items():
        if key in query:
            return value
    return "未找到相关结果"

TOOLS = {"calculator": calculator, "search": search}

## 假模型:根据已有观察数量决定下一步
def fake_model(context: list[str]) -> dict:
    observations = [line for line in context if line.startswith("Observation:")]
    if len(observations) == 0:                    # 第一步:先算折后价
        return {"final": False, "text": "先算 7 折后再减 20 元",
                "tool": "calculator", "arg": "120*0.7-20"}
    if len(observations) == 1:                     # 第二步:再算节省比例
        return {"final": False, "text": "再算省了百分之几",
                "tool": "calculator", "arg": "(120-64)/120*100"}
    return {"final": True, "answer": "最终价格 64 元,相比原价省了约 46.7%"}

## ReAct 主循环
def react_agent(question: str, max_iters: int = 10) -> str:
    context = [f"问题:{question}"]
    for step in range(max_iters):        # 强制步数上限,防止死循环
        decision = fake_model(context)
        if decision["final"]:            # 自然终止:模型认为任务完成
            return decision["answer"]
        tool, arg = decision["tool"], decision["arg"]
        obs = TOOLS[tool](arg)           # 运行时真正执行工具
        context.append(f"Thought: {decision['text']}")
        context.append(f"Action: {tool}({arg})")
        context.append(f"Observation: {obs}")
        print(f"[步骤{step + 1}] Thought={decision['text']}")
        print(f"          Action={tool}({arg}) -> Observation={obs}")
    return "达到最大步数,未能完成任务"     # 强制终止

def main() -> None:
    print(react_agent("某书原价120元,打7折后再减20元优惠券,最终多少钱?省了百分之几?"))

if __name__ == "__main__":
    main()
```
保存为 `react_agent.py`，运行 `python react_agent.py`。预期输出为：
```text
[步骤1] Thought=先算 7 折后再减 20 元
          Action=calculator(120*0.7-20) -> Observation=64.0
[步骤2] Thought=再算省了百分之几
          Action=calculator((120-64)/120*100) -> Observation=46.666666666666664
最终价格 64 元,相比原价省了约 46.7%
```
逐处讲解，重点看三个设计：

- **工具区**：`calculator` 里有一行正则白名单校验 `re.fullmatch(...)`——这是“运行时校验”的缩影。模型提议算什么，代码都要先检查参数合法性再执行，绝不盲目信任模型输出。这一原则会在第 6 章“工具使用”里展开为黄金原则。
- **假模型**：`fake_model` 扮演 LLM 的角色，它的决策**完全依赖 `context`**——这印证了“上下文就是 Agent 的工作记忆”。真实工程里，这里换成一次 LLM 调用，通过 prompt 让模型输出结构化的 `Thought/Action`。注意它是靠“已观察次数”而非“关键词”判断进度的，这避免了一类隐蔽 bug：如果用关键词判断状态，而问题文本里恰好包含那个关键词，就会误判进度。
- **主循环**：`for step in range(max_iters)` 是**强制步数上限**，`decision["final"]` 是**自然终止**。两种终止缺一不可：只有自然终止会死循环，只有强制上限会浪费步数。`obs = TOOLS[tool](arg)` 这一行体现了“模型决定 action、运行时执行工具”的分工——模型永远只是“提议”，真正的副作用由代码执行，这是 Agent 安全的基石。

## 真实系统对应

**官方公开机制**：ReAct 论文公开了“Thought-Action-Observation 交织”这一范式及其相对基线的优势 [来源](https://arxiv.org/abs/2210.03629)；LangChain 官方文档明确 `create_agent()` 是基于 ReAct 论文的生产就绪实现，并把 Agent 行为描述为“推理与行动的交替” [来源](https://docs.langchain.com/oss/python/langchain-agents)；LangGraph 的 `create_react_agent` 预置了“LLM 调用—工具执行循环—条件路由”的完整 ReAct 图。**通用工程模式**：把“模型提议、运行时执行、观察回写”封装成一个带熔断（max_iters）的循环，是所有工具型 Agent 的通用骨架。**教学参考实现**：上面的 `fake_model` 用规则模拟 LLM 决策，不代表任何框架的内部实现；真实框架会用模型原生的 Function Calling（函数调用）/ tool use 接口拿到结构化动作，而不是靠我们这样的 if-else。

需要明确边界：现代生产框架已很少靠“正则解析自由文本”来提取动作，而是用模型原生的结构化工具调用接口——这一点在下面的踩坑里会展开。ReAct 是“范式”，Function Calling 是“更稳的落地方式”，二者不矛盾。

## 生产踩坑

| 症状 | 根因 | 如何观测与复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| Action 解析时好时坏 | 靠正则匹配自由文本，模型改个格式就失败 | 记录原始模型输出与解析结果，注入格式变体复现 | 改用模型原生 Function Calling / tool use 拿结构化动作 | 不支持工具调用的老模型只能容错解析 |
| 长任务上下文爆炸、变贵变慢 | 每轮 Thought/Action/Observation 都追加进 context | 统计 token 随轮数增长曲线 | 对旧轮次摘要压缩或只保留最近 K 轮 | 短任务无需压缩 |
| 死循环、原地打转 | 反复调同一工具传同样参数，卡在一个状态 | 记录连续重复的 Action，注入循环轨迹复现 | max_iters 硬上限 + 检测连续重复动作主动打断 | 合法的重试（带退避）不应误杀 |
| Observation 太长把推理带偏 | 工具返回整页 HTML，注意力被无关内容吸走 | 记录每条 Observation 的长度与后续推理质量 | 工具返回前先裁剪、提炼要点再入上下文 | 需要全文的场景应存外部再给指针 |
| 模型幻觉“调用了不存在的工具” | 工具清单未约束或描述不清 | 校验 Action 里的工具名是否在白名单 | 用 schema 约束可选工具，非法工具名直接拒绝 | 动态工具集需运行时校验 |
| 工具报错后模型不会恢复 | 没把错误信息作为 Observation 喂回 | 让工具返回结构化错误，观察是否重试或换路 | 把错误当 Observation 回写，让模型据此调整 | 不可恢复错误应直接终止并上报 |

## 思考：为什么说 ReAct 的“动作空间 = 任务动作 + 语言空间”是它优于纯行动基线的关键？

### 回答

因为纯行动基线（Act-only）的动作空间只有“外部工具调用”，模型拿到工具返回后没有一个“想一想”的环节来消化观察、规划下一步，容易在动作之间迷失方向、或对着结果不知所措。ReAct 把“语言空间”（Thought）也纳入动作空间，意味着模型在两次外部动作之间可以先用自然语言推理：这条观察说明了什么、下一步该查什么、当前假设是否被推翻。于是推理为行动提供方向、行动为推理提供依据，形成闭环校准。这也是它比纯行动更稳、比纯推理更不幻觉的根本原因——它同时拥有“取证能力”和“消化证据的能力”。

### 面试精简表达

Act-only 只会动手不会想，CoT-only 只会想不会取证；ReAct 把“想”也当成一种动作，让每步行动被推理指挥、每步推理被观察锚定。

## 思考：既然有了模型原生的 Function Calling，ReAct 这个“范式”还有意义吗？

### 回答

有，而且二者是不同层面的东西。ReAct 是“思考—行动—观察交织”的**范式/控制流**，回答的是“Agent 应该怎么组织推理和行动”；Function Calling 是**拿到结构化动作的接口/落地方式**，回答的是“怎么可靠地把模型的行动意图变成机器可执行的调用”。生产系统通常是“用 Function Calling 作为 ReAct 循环里 Action 的实现手段”——范式不变，只是把脆弱的“正则解析自由文本”换成了稳健的“结构化工具调用”。理解 ReAct 范式能帮你设计循环的终止、观察回写、错误恢复；而 Function Calling 帮你把这个循环落得更稳。丢掉范式只谈接口，你会写出没有熔断、不会恢复的循环。

## 事故回放：一次“Observation 过长”引发的连环失焦

某内部知识库 Agent 用 ReAct 回答“我们的报销上限是多少”。它的第一步没错：Thought“查报销制度文档”，Action `search("报销制度")`。问题出在 Observation——搜索工具直接把整篇 8000 字的《员工手册》原文塞了回来，其中报销上限那一句被淹没在考勤、假期、着装等无关章节里。模型的注意力被开头的“考勤打卡”吸走，第二轮 Thought 变成“用户可能想问考勤”，接着去查考勤制度，彻底跑偏。三轮之后触达 max_iters，返回了一段答非所问的考勤说明。

复盘定位到两层问题。**观察层**：工具不该把全文原样返回，而应先做检索内的重排与截断，只回“报销上限：单次不超过 X 元”这一句加原文指针。**循环层**：即便返回了长文本，也应在入上下文前做长度检查，超阈值就先摘要。修复后，同样的问题一轮命中：Observation 只含相关句，Thought 直接进入“已找到答案”。这个案例说明：ReAct 的质量不只取决于模型和提示，**工具返回的“观察质量”同样是循环成败的命门**——垃圾观察会污染后续所有推理。

## 优化前后对比

| 维度 | 纯 CoT 客服（无工具） | ReAct 客服（有工具） | 验证方式 |
|---|---|---|---|
| 实时/私有数据 | 靠记忆编造（幻觉） | 靠工具真实取回 | 断网/断工具看是否仍“自信作答” |
| 每步依据 | 无外部锚点 | 每步被观察锚定 | 回放每步 Thought 是否引用上条 Observation |
| 终止控制 | 一次输出即止 | 自然终止 + max_iters 双保险 | 注入不收敛任务看是否被熔断 |
| 错误恢复 | 无 | 错误当观察回写后可换路 | 让工具报错看是否重试或改道 |
| 主要风险 | 幻觉 | 解析脆弱、上下文膨胀、原地打转 | 见本节踩坑表 |

ReAct 解决了 CoT “无法取证”的硬缺口，但它仍是**单条线性路径**：每一步只沿一个方向往下走，走错了只能靠后续观察补救，没有“同时探索多条路再择优”的能力。当任务需要在多个候选方案间试错、回溯时，就要请出下一层的 ToT。而在此之前，还有一个更贴近工程的问题：规划应该“边走边想”，还是“先想好整条路再走”？这就是第 04 节 Plan-and-Execute 与 ReWOO 的主题。
