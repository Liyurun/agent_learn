## 真实问题

告警上写着“Agent 任务成功率下降”，但这句话无法直接行动。对一个带推理与规划的 Agent 来说，故障可能出在推理链本身（CoT，Chain-of-Thought，思维链算错某一步）、行动环节（ReAct，Reasoning and Acting，推理与行动交织的工具调用失败或参数错误）、规划环节（Plan-Execute 的计划一次成型后错到底）、搜索环节（ToT，Tree of Thoughts，思维树的评估函数失灵），或者根本是选型错了（该用 ReAct 的任务硬套 Plan-Execute）。生产诊断的第一原则是：**先保存实际的推理轨迹与调用序列（Thought / Action / Observation 的完整记录），再按“范式—步骤—工具”三层定位，绝不把一切归结为“模型不够强”。**

推理与规划类故障和普通问答故障有一个本质区别：它是**多步的、有状态的**。一次失败可能是第 3 步的观察被污染，导致第 4、5 步顺着错误前提越走越偏。因此排查不能只看最终答案，必须回放整条轨迹，找到“第一个出错的步骤”，而不是在终点做归因。

## 诊断顺序

1. **回放轨迹**：固定问题、模型版本、温度、工具快照，完整打印 Thought / Action / Observation 序列，定位“第一个出错的步骤”。
2. **区分错误层**：是推理错（某步算错/前提错）、行动错（工具调用或参数错）、还是观察错（工具返回被误读）。
3. **检查终止条件**：是否只有硬上限没有自然终止（跑满步数才停），或只有自然终止没有硬上限（不收敛时死循环）。
4. **检查选型**：任务的依赖结构是“可预先确定”还是“运行时才显现”，当前范式是否匹配。
5. **检查护栏**：死循环、重复动作、非法参数、越权工具是否有拦截。
6. **检查成本**：LLM 调用次数与每次携带的上下文长度，是否随步数失控增长。
7. **比较基线**：同一输入在固定模型上的多次结果，以及切换范式后的对照实验。
8. **离线评估**：用失败样本建回归集，改动后跑全量对照，而不是只看单条 case。

## 症状矩阵（推理与规划专用）

下面把本章各范式在生产里最常见的故障，按“症状—根因—如何观测与复现—修复与预防—不适用边界”五列整理。这些行都可以直接搬进值班手册。

| 症状 | 根因 | 如何观测与复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| 简单事实题也强套长 CoT 反而错 | 过度思考，冗长推理引入不存在的复杂度 | 对事实召回题对比短/长推理准确率 | 按任务匹配推理深度，事实题走短路径 | 多步计算题仍需展开 CoT |
| 自洽投票加大 N 仍纠不了偏 | 错误是系统性缺知识，非“各错各的” | 记录 N 条链是否给出同一错误答案 | 接入检索或工具，而非加大 N | 各错各的随机错仍可投票纠偏 |
| ReAct 反复调同一工具原地打转 | 只有 max_iters 硬上限，无重复检测 | 注入原地打转轨迹看是否提前打断 | 加“连续相同动作”护栏主动打断 | 带退避的合法重试不应被打断 |
| ReAct 观察被污染后越走越偏 | 工具返回未校验即回写上下文 | 注入脏观察复现后续步骤崩坏 | 观察回写前做 schema/范围校验 | 可信内部工具可放宽校验 |
| Plan-Execute 计划一次成型错到底 | 缺重规划，执行不回头 | 注入中途失效步骤复现 | 关键步失败触发 Replan 或回退 ReAct | 完全确定的流水线可省 |
| ReWOO 变量占位符代入错步骤 | `#S1/#S2` 依赖关系写错 | 打印计划的依赖图核对 | 校验依赖拓扑，执行前做 dry-run | 无依赖的独立步骤不受影响 |
| ToT 展开成本爆炸、延迟不可控 | 分支因子×深度未设预算 | 记录扩展节点数与总调用 | 设 beam 宽度、深度上限与总预算熔断 | 单路径足够的任务不该上 ToT |
| ToT 选错分支，评估函数失灵 | 状态价值评估不可靠 | 对已知答案题看是否剪掉正确分支 | 校准评估器，或改用可验证的终局判据 | 无法定义评估函数时不宜用 ToT |
| 关键词判断进度导致误判完成 | 问题文本恰好含状态关键词 | 让问题包含状态词复现误判 | 改用“已观察次数”等结构化状态 | 无状态一次性任务无需进度判断 |
| LLM 调用次数随步数线性爆炸 | ReAct 每步回模型，长任务累积 | 统计每任务调用数与累计 token | 可预定步骤改 Plan-Execute/ReWOO | 短任务差异可忽略 |
| 只统计调用次数低估真实成本 | 忽略每次调用携带的上下文长度 | 记录每次调用的 token 数 | 同时监控调用数与累计 token | 上下文很短时近似成立 |
| 模型提议非法/越权动作被直接执行 | 未在执行前做参数与权限校验 | 让模型提议非法参数看是否被拦 | 执行层白名单+权限校验+人工确认 | 幂等只读工具可适度放宽 |
| 多范式混用行为难预测 | 没有明确的路由规则 | 记录哪些任务走哪条骨架 | 按“依赖可预测性”明确路由 | 单一任务类型无需路由 |
| 轨迹无法审计，事后无法复盘 | 日志只存最终答案 | 关联 trace_id 与逐步轨迹 | 结构化记录每步 T/A/O 与调用元数据 | 隐私要求可能限制原文留存 |
| 指标正常但用户仍失败 | 只量调用数/延迟，不量任务成功 | 增加任务成功率与约束遵循率 | 建端到端评估集，指标联看 | 指标不取代人工复核 |
| 恢复后重复执行有副作用的动作 | 动作无幂等键，崩溃后重放 | 崩溃注入看是否重复下单/发信 | 动作日志+幂等键+提交检查点 | 外部系统需支持幂等 |

上表把“调用成本”拆成“调用次数”和“单次上下文长度”两项，是因为 ReAct 相对 Plan-Execute 的真实成本劣势往往比“次数差”更大——越到后面上下文越长，单次调用越贵。生产里两项必须同时监控。

## 最小可运行演示：选型决策器

把本章反复强调的“选型判据”落成一段可运行的规则代码，方便你在真实系统里把它接到任务分类器后面。它根据任务的四个结构化特征输出推荐范式。
```python
"""规划范式选型决策器:根据任务的四个结构化特征,输出推荐的规划范式。
这是把本章"选型判据"落成可运行规则的教学实现,纯 Python,无需 API Key。
真实系统里,这些特征可由任务分类器或人工标注给出。"""

from dataclasses import dataclass


@dataclass
class Task:
    name: str
    steps_predictable: bool   # 步骤依赖是否可预先确定
    needs_external: bool      # 是否需要查外部世界(检索/工具)
    high_value: bool          # 是否高价值低容错(值得多花算力兜底)
    step_count: int           # 预估步骤数


def route(task: Task) -> str:
    if not task.needs_external and task.step_count <= 1:
        return "CoT"                      # 单步纯推理,一条链即可
    if task.high_value:
        return "Self-Consistency"        # 高价值低容错,多路投票兜底
    if task.steps_predictable and task.step_count >= 2:
        return "Plan-Execute/ReWOO"      # 步骤可预定,批量执行省调用
    return "ReAct"                        # 依赖运行时才显现,边看边定


def main() -> None:
    tasks = [
        Task("判断一句话情感", False, False, False, 1),
        Task("分别查3个指标再汇总", True, True, False, 3),
        Task("先搜线索才知下一步搜什么", False, True, False, 4),
        Task("关键财务核算", False, False, True, 2),
    ]
    for t in tasks:
        print(f"{route(t):<20} <- {t.name}")


if __name__ == "__main__":
    main()
```
保存为 `route_planner.py`，运行 `python route_planner.py`。预期输出为：
```text
CoT                  <- 判断一句话情感
Plan-Execute/ReWOO   <- 分别查3个指标再汇总
ReAct                <- 先搜线索才知下一步搜什么
Self-Consistency     <- 关键财务核算
```
读懂这段输出：四个任务分别命中四条不同的路由规则。情感判断是单步纯推理，走 CoT；三个指标可预先确定、彼此独立，走 Plan-Execute/ReWOO 省调用；“先搜到线索才知道下一步”是典型的运行时依赖，只能 ReAct 边看边定；关键财务核算高价值低容错，用 Self-Consistency 多路投票兜底。这段规则不是要取代模型判断，而是给出一个**可解释、可测试的选型基线**——真实系统里你会把规则和分类器结合，并对边界样本做人工复核。注意规则的顺序有讲究：高价值判断放在“可预定步骤”之前，是因为“答对的价值”优先级高于“省调用”，宁可多花算力也要保对。

## 真实系统对应

**官方公开机制**：LangGraph 官方文档提供 `create_react_agent` 的“推理—行动”循环封装，并支持 `recursion_limit` 一类的步数上限配置；LangChain 文档把 Agent 描述为“推理与行动的交替”，并给出 plan-and-execute 的参考实现思路 [来源](https://docs.langchain.com/oss/python/langchain-agents)。CoT、ReAct、ToT、Self-Consistency、Plan-and-Solve、ReWOO 的机制均来自公开论文，可逐一核验其适用条件与实验设定。**通用工程模式**：本章反复出现的“双终止条件、观察回写校验、死循环护栏、按依赖结构路由、调用数与上下文长度双监控”都是可迁移到任意框架的做法，不绑定具体产品。**教学参考实现**：本章所有代码用规则模拟 LLM 决策，目的是可复现、可测试地展示控制流，不代表任何框架的内部调度；真实系统用模型原生工具调用接口拿结构化动作，其计费和延迟取决于每次携带的上下文长度。

具体的采样率、超时阈值、护栏触发条件、评估集规模，都应由团队按风险和成本设计，本文不声称存在一套普适的默认参数。

## 思考：线上说“Agent 又卡死了”，你第一步做什么？

### 回答

第一步不是重启，而是**抓取并回放这次卡死的完整轨迹**——把 Thought / Action / Observation 序列打出来，看它到底卡在哪种模式。最常见的是 ReAct 原地打转：连续几步调同一个工具、传同样参数。确认是这种后，短期止血是让重复动作护栏和 max_iters 硬上限生效（很多“卡死”其实是既没自然终止判断、又没硬上限导致的无限循环）；中期修复是给护栏加“连续相同动作即打断”的触发条件，并区分“恶性重复”和“带退避的合法重试”。如果轨迹显示不是打转而是每步都在推进但永远差一步完成，那问题在终止条件的判定逻辑——通常是用关键词判断进度导致误判，应改成用“已观察步数”等结构化状态。整个过程的核心是：**先定位是哪一类不收敛，再对症下药，而不是靠重启碰运气。**

## 思考：ReAct 明明更灵活，为什么生产里还要费劲上 Plan-Execute？

### 回答

因为“灵活”是有成本的。ReAct 每一步都要回模型问“下一步做什么”，LLM 调用次数随步数线性增长，而且越到后面上下文越长、单次调用越贵——一个十步任务，ReAct 可能要十几次带长上下文的调用。对那些**步骤依赖可以预先确定**的任务（比如“分别查 5 个指标再汇总”），这些中间的“问下一步”全是浪费：计划一开始就能定死，何必每步都问。Plan-Execute/ReWOO 把它压成“规划一次+批量执行+汇总一次”，调用数从 O(N) 降到 O(1)，省的还不只是次数，更是每次调用的上下文长度。所以选型的真正依据不是“哪个更灵活”，而是**任务的依赖结构**：可预定的用 Plan-Execute 省钱，运行时才显现的才用 ReAct 换灵活。绝大多数成熟系统是“ReAct 主干 + 热点用 Plan-Execute/ReWOO 优化 + 关键推理用 Self-Consistency 兜底”的混合体。

## 思考：如何把本章的范式安全地引入一个已有的 Agent 系统？

### 回答

先加观测，再改结构，最后做优化，每步都留回滚开关。第一步，**先把轨迹记全**：在现有系统里记录每轮的 Thought / Action / Observation、LLM 调用次数、每次调用的 token 数和 trace_id，没有这些数据谈优化都是空谈。第二步，**用失败样本建回归集**：把线上失败的 case 固化成离线评估集，任何范式改动都先在这上面跑对照。第三步，**按优先级动结构**：先补齐双终止条件和死循环护栏（这是止血，收益最大风险最低），再把执行前参数/权限校验加上（安全底线），然后才把“可预定步骤”的热点任务从 ReAct 切到 Plan-Execute/ReWOO 省成本，最后对高价值任务叠加 Self-Consistency。第四步，**灰度加对照实验**：每个改动只在一小部分流量上开，用 A/B 对比任务成功率和成本，确认无回退再放量。全程的铁律是：不要一上来就重写成某个“更先进”的范式，范式服务于任务结构和业务指标，而不是反过来。

## 思考：面试官问“你怎么判断一个 Agent 该用哪种规划范式”，怎么答才有深度？

### 回答

不要背“简单用 CoT、复杂用 ReAct”这种口水答案，要给出**可操作的判据**。我会先问三个问题：任务的步骤依赖是运行时才显现，还是可以预先确定？任务是否需要查外部世界？答对的边际价值是否远高于多花的算力？这三个问题分别对应三个坐标轴。步骤运行时才显现、需要边看边定的，用 ReAct；步骤可预先确定、彼此独立的，用 Plan-Execute 或 ReWOO 把调用从 O(N) 压到 O(1)；单步纯推理的用 CoT 就够；高价值低容错的，在上面任意范式外再叠 Self-Consistency 做多路投票兜底；只有当“单条最优路径不可靠、需要探索多分支并可定义状态评估”时，才付出代价上 ToT。深度体现在两点：一是我能把选型量化到“调用次数”和“单次上下文长度”这两个成本维度，二是我知道真实系统几乎都是混合范式，会指出“ReAct 主干 + 热点 Plan-Execute + 关键推理 Self-Consistency”这种组合，而不是幻想用单一范式包打天下。
