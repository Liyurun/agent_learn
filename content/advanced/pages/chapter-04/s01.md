## 真实问题

一个运维 Agent 接到告警：“支付回调成功率从 99.9% 跌到 96%。”它没有规划，直接开始动手：第一步就去重启了回调服务（因为“重启”在训练数据里是高频修复动作），结果把正在处理的一批回调打断，成功率进一步跌到 92%；接着它又去改了超时配置，把 3 秒改成 30 秒，让问题被“拖平”但没有消失；最后它在群里回复“已修复”，实际上根因是上游一个新上线的风控接口偶发 500，跟它改的两处毫无关系。事后统计：它一共执行了 11 个动作，其中 9 个是无效或有害的，真正定位根因所需的“先看错误分布、再看上游依赖”这两步它一步都没做。

问题不是模型“不够聪明”，而是它**在没有把目标拆成“先观测、再定位、后修复、最后验证”的可执行子步骤之前，就凭直觉行动了**。规划的本质，就是把一个大而模糊的目标，分解成一串小而明确、可执行、可验证、有先后依赖的子步骤，并在执行过程中根据观察不断校正。Lilian Weng 在其被广泛引用的综述里，把规划（Planning）列为自主 Agent 的四大核心组件之一，并指出任务分解（如 CoT、Tree of Thoughts）与自我反思是其中的关键手段 [来源](https://lilianweng.github.io/posts/2023-06-23-agent/)。

## 原理：为什么“一次性输出”会失败

要理解规划为什么有用，得先理解大语言模型的生成机制。自回归语言模型本质上在做一件事：给定已有的 token 序列，预测下一个 token 的概率分布，然后采样。它没有“草稿纸”，没有“回退键”，一旦吐出一个 token，就无法收回，只能在这个既定前缀上继续往下写。

这带来一个根本约束：**模型必须在有限的、一次性的前向传播里，把答案“一口气”算出来。** 对于“17 × 24”这种需要多步中间计算的问题，如果强迫模型直接输出结果，它就得在单次前向传播里同时完成“拆解、相乘、相加”——而 Transformer 每一层的计算量是固定的，深度也是固定的，它并没有足够的“串行计算预算”来完成本该分几步做的事。
```text
一次性输出的困境：
  问题 ──▶ [单次前向传播,固定算力] ──▶ 答案
             ↑
       没有中间步骤落地,
       复杂计算被压缩进一步,容易出错

规划/CoT 的破局：
  问题 ──▶ 中间步骤1 ──▶ 中间步骤2 ──▶ ... ──▶ 答案
             ↑            ↑
       每个中间 token 都会被写回上下文,
       成为下一步计算的输入 = 把"串行计算"摊开在时间轴上
```
这就是规划（以及下一节要讲的 CoT，Chain-of-Thought，思维链）真正的底层价值：**用“生成更多中间 token”的方式，把原本需要在单步内完成的深度计算，摊开成时间轴上的多步浅计算。** 每生成一个中间结果，它就被写回上下文，成为下一步推理的已知条件。模型于是获得了一种“外部工作记忆”——它写在自己的输出里。这也解释了为什么 OpenAI 的 o 系列推理模型会在给出最终答案前，先生成一段（对用户隐藏的）推理链：它们通过在测试期（推理期）投入更多“思考 token”来换取更高的复杂任务准确率 [来源](https://openai.com/index/learning-to-reason-with-llms/)。

## 规划能力的三个层次

在展开具体范式前，先建立一张心智地图。本章后面所有技术都可以归位到这张图里：
```text
层次一:单步推理增强   →  CoT(让单步答案更靠谱)
层次二:推理+行动交织   →  ReAct(能查外部世界、边做边调整)
层次三:多路径搜索      →  ToT(同时探索多条路、评估、回溯剪枝)
```
层次越高，能力越强，但**算力成本和工程复杂度也越高**。工程上的黄金法则是：**用能解决问题的最低层次。** 一个能用 CoT 心算解决的问题，套上 ToT 的 beam search（束搜索）只会白白多花几十倍算力；反过来，一个必须查实时信息的任务，无论 CoT 写得多漂亮，也补不上“没有观察”这个硬缺口。这条“最低层次原则”会贯穿本章的每一次选型讨论。

## 最小可运行演示

下面这段代码把“一次性输出”和“一步步想”做了对比：`direct_answer` 模拟模型被迫在单步内猜答案（猜错成 400），`cot_answer` 则把乘法摊开成三个可落地的中间步骤。
```python
def direct_answer(a: int, b: int) -> int:
    """模拟"一步到位":把多步计算硬塞进一次输出,容易在进位处出错。"""
    # 故意省略中间步骤,模拟模型在单步内把 17*24 猜成 400
    return 400

def cot_answer(a: int, b: int) -> int:
    """模拟"一步步想":把乘法摊开成可落地的中间步骤。"""
    step1 = a * 20          # 17*20=340
    step2 = a * 4           # 17*4=68
    result = step1 + step2  # 340+68=408
    print(f"步骤1: {a}x20 = {step1}")
    print(f"步骤2: {a}x4  = {step2}")
    print(f"步骤3: {step1}+{step2} = {result}")
    return result

def main() -> None:
    truth = 17 * 24
    print(f"真实答案: {truth}")
    print(f"一次性输出: {direct_answer(17, 24)}  正确={direct_answer(17, 24) == truth}")
    print("CoT 展开:")
    cot = cot_answer(17, 24)
    print(f"CoT 答案: {cot}  正确={cot == truth}")

if __name__ == "__main__":
    main()
```
保存为 `serial_compute.py`，运行 `python serial_compute.py`。预期输出为：
```text
真实答案: 408
一次性输出: 400  正确=False
CoT 展开:
步骤1: 17x20 = 340
步骤2: 17x4  = 68
步骤3: 340+68 = 408
CoT 答案: 408  正确=True
```
这段代码当然不是真的在调用模型，`direct_answer` 的“400”是硬编码的错误，用来模拟“单步硬猜”的失败。它想传达的唯一道理是：**把一步拆成三步、让每步的中间结果落地成下一步的输入，正确率就有了结构性保障**——这正是规划和 CoT 的共同内核。真实模型上，你会把 `cot_answer` 里的三行计算换成“让我们一步步思考”触发的自然语言推理链。

## 真实系统对应

**官方公开机制**：OpenAI 在“Learning to reason with LLMs”中公开说明，o1 通过大规模强化学习学会“用思考链高效地思考”，且性能随训练期算力和测试期思考时间同时提升 [来源](https://openai.com/index/learning-to-reason-with-llms/)。这印证了“给模型更多思考的时间步能提升复杂推理表现”这一底层判断。**通用工程模式**：把大目标显式拆成有依赖的子步骤，是可迁移到任何 Agent 的规划范式，与具体模型无关。**教学参考实现**：上面的 `serial_compute.py` 只是用硬编码演示“摊开计算”的效果，不代表任何模型的真实前向传播，也不代表 o 系列的内部推理格式（其推理 token 对用户隐藏）。

需要明确边界：官方从未承诺“加了推理就一定对”，也没有公开 o 系列的内部思考链具体长什么样。因此我们只能说“测试期投入更多思考 token 通常能提升复杂任务表现”，不能反推它的私有算法。

## 生产踩坑

| 症状 | 根因 | 如何观测与复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| Agent 不规划直接乱动手，越修越坏 | 缺少“先观测再行动”的显式规划骨架 | 记录每轮的 Thought 与 Action，统计“无效/有害动作”占比 | 在系统提示中强制“先给计划再执行”，并对高风险动作加确认 | 极简单任务（单步查询）无需规划，强加反而增加延迟 |
| 简单事实题也强套 CoT，变慢变贵 | 把“多想想总没错”当通用策略 | 对比加/不加 CoT 的准确率与 token 用量 | 按任务类型路由：事实召回类走短路径 | 需要多步推理的题仍必须展开 |
| 推理模型“过度思考”把对的绕错 | 简单题上分配了过多思考预算 | 记录思考 token 数与最终正确率的相关性 | 对简单任务限制思考预算或改用非推理模型 | 数学/代码等难题需要充分思考预算 |
| 规划一次成型后再不更新，一路错到底 | 没有“执行中发现前提失效则重规划”的机制 | 注入一个中途失效的前提，观察是否纠正 | 引入重规划触发条件（见第 04 节） | 完全可预测的流水线可省略重规划 |

## 思考：为什么让模型“一步步想”能提升准确率？它又没变聪明

### 回答

因为模型的单次前向传播算力是固定的，深度也是固定的。让它输出中间步骤，等价于把本该在一步内完成的“串行计算”摊开到多个生成时间步上，每一步都能利用前面已生成的中间结果作为“外部工作记忆”。这不是让模型变聪明，而是给了它更多“思考的时间步”和一块可复用的草稿纸。所以准确率的提升来自“计算被摊开、中间结果可落地”，而不是参数或知识发生了变化。

### 面试精简表达

单步算力是常数，把难题拆成多步，就是用“更多时间步”换“更深的有效计算”，中间结果写回上下文当草稿纸——是给时间，不是变聪明。

## 思考：既然规划这么好，为什么不给所有任务都加上最强的规划

### 回答

因为规划有成本：每多一层（CoT→ReAct→ToT）都意味着更多 token、更多 LLM 调用、更高延迟和更复杂的工程。对“法国首都是哪”这种一步事实召回，加 CoT 是纯浪费，甚至可能因“过度思考”把对的绕错。正确策略是“最低层次原则”：先判断任务是否需要多步推理、是否需要外部信息、是否需要多路径探索，用能解决问题的最低层次。规划架构应该是被真实问题逼出来的，而不是一开始就过度设计。

## 事故回放：从“凭直觉行动”到“先规划再执行”

回到开头那个运维 Agent。它的失败可以拆成四个独立问题，每个都对应本章后面的一节。第一，它没有“先观测”——正确的第一步应是拉取错误分布和时间线，而不是重启服务；这属于规划的“任务分解”缺失。第二，它把“重启”这种高频修复动作当成了万能钥匙，没有让行动被观察锚定——这正是第 03 节 ReAct 要解决的“推理与行动必须交织”。第三，它改超时把问题“拖平”，是典型的“计划与现实脱节却不重规划”——第 04 节会展开重规划机制。第四，它在没验证的情况下就宣布“已修复”，缺少终止条件的校验——第 06、07 节会讲循环的终止与验证。

改造后的骨架很简单：系统提示强制它“先输出一份带依赖的分步计划，再逐步执行，每步执行后用观察校验前提是否仍成立，不成立就重规划”。同样的告警，它这次先看错误分布（发现集中在带某风控标记的请求）、再看上游依赖（定位到新上线的风控接口 500）、再联系上游确认、最后才在群里给出准确结论。动作数从 11 降到 5，且没有一个有害动作。这个对比不是因为换了更强的模型，而是因为**给它套上了“想清楚路再走”的结构**。

## 优化前后对比

| 维度 | 不规划（凭直觉行动） | 有规划（先分解再执行） | 验证方式 |
|---|---|---|---|
| 首个动作 | 直接重启服务（高频但盲目） | 先拉错误分布与时间线 | 检查第一个 Action 是观测还是变更 |
| 行动依据 | 靠训练数据里的高频修复 | 靠当轮观察锚定 | 回放每步是否引用了上一步观察 |
| 计划更新 | 无，一路错到底 | 前提失效即重规划 | 注入中途失效前提看是否纠正 |
| 结束判定 | 未验证就宣布“已修复” | 用验证步确认再收尾 | 检查是否存在显式验证动作 |
| 动作总数/有害数 | 11 / 9 | 5 / 0 | 统计动作日志 |

需要强调：这张表里的数字来自这个具体案例的复盘，不是普适基准。它说明的是“结构带来的确定性收益”，而非“规划能把任意任务的动作数固定压到 5 步”。真实系统里，规划的收益必须用你自己的回归任务集来度量，而不是照搬别人的数字。
