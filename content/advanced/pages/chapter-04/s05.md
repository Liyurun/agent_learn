## 真实问题

一个教学 Agent 要解“24 点”游戏：给定 4 个数字（比如 4、6、6、9），用加减乘除凑出 24。第一版用单条 CoT（Chain-of-Thought，思维链）：模型一口气写下“4×6=24，然后……剩下 6 和 9 没用上，不行；换 6+6=12，12×… 也凑不出”，写到一半发现走不通，但因为是单条线性路径，它**没有回退能力**，只能硬着头皮把这条错路写完，最后给出“无解”——而这道题其实有解（如 (6-4)×(9+6)=30 不对，正确解需要枚举）。单链 CoT 的致命弱点在这里暴露无遗：**一旦某一步选错，后面全错，且无法回头换一条路。**

24 点正是 Tree of Thoughts 原论文用来验证的经典任务之一：它需要“探索、试错、可能走回头路”，单链推理束手无策，而引入“每步生成多个候选、评估打分、剪枝、回溯”后成功率大幅提升 [来源](https://arxiv.org/abs/2305.10601)。这一节讲两种“突破单条路径”的方法：**Self-Consistency（自洽，多条独立链投票）** 和 **ToT（Tree of Thoughts，思维树，结构化树搜索）**。

## 原理：从单链到多路径

前面几节的 CoT、ReAct 都是**单路径**推理：一次只沿一个方向往下走。突破单路径有两种思路，复杂度递增：
```text
思路一:多条独立链 + 投票(Self-Consistency)
  同一问题采样 N 条互不相干的完整推理链,只对"最终答案"做多数投票。
  不评估中间步骤,不回溯,链与链之间无交互。

思路二:结构化树搜索(Tree of Thoughts)
  把推理组织成一棵树:每步生成多个候选想法(分支),
  对每个候选评估打分,剪掉差的,沿好的深入,必要时回溯。
  显式引入"评估"和"回溯",链与链之间通过共享前缀相连。
```
Self-Consistency 已在第 02 节展开，这里只强调它与 ToT 的关系：**Self-Consistency 是“并行 N 条完整链、末端投票”，ToT 是“边生成边评估边剪枝的树”**。前者简单、易并行、成本 N 倍且固定；后者能中途止损（剪掉没希望的分支）、能回溯，但工程复杂、成本更高且随深度增长。

## ToT 的四个必备组件

ToT 不是“多想几条”这么简单，它是一个结构化的搜索框架。原论文把它拆成四个必须回答的设计问题 [来源](https://arxiv.org/abs/2305.10601)：
```text
1. 思维分解(Thought decomposition)
   一步"想法"的粒度是多大?一句话?一个中间方程?一段子计划?

2. 思维生成(Thought generator)
   给定当前状态,怎么生成 k 个候选下一步?(独立采样 or 顺序提议)

3. 状态评估(State evaluator)
   怎么给每个候选打分?让 LLM 自评"这条路有没有希望",
   或用规则/外部检验判断(如 24 点里"剩余数字还能凑出 24 吗")。

4. 搜索算法(Search algorithm)
   用 BFS 广度优先(每层留最优的 b 个)还是 DFS 深度优先
   (一条路走到底,不行就回溯)?
```
理解这四个组件的意义在于：**ToT 把“思考”变成了一个可以用经典搜索算法操作的图搜索问题。** CoT 是这棵树上“只往下走一条路、不评估、不回溯”的退化特例；而 ToT 显式引入了“评估”和“回溯”，这正是它能解决 CoT 束手无策的难题（24 点、数独、创意写作的多稿择优）的关键。
```text
              初始问题
             /    |    \
         想法A   想法B   想法C     ← 每步生成多个候选(思维生成)
          / \     |
       A1   A2   B1      ← 评估每个候选打分,剪掉差的(状态评估+搜索)
                          ← 沿最优路径深入,走不通则回溯
```
## 最小可运行演示

下面这段可运行代码用 beam search（束搜索）演示 ToT 的骨架：每步生成候选、评估打分、只保留最优的 `beam_width` 条继续展开。为了让输出可复现，`evaluate` 用了一个确定性的启发式（分支序号越靠前视为越有希望），真实场景里这一步应换成 LLM 评估或规则检验。
```python
from dataclasses import dataclass

@dataclass
class Node:
    path: list      # 到当前节点的想法序列
    score: float    # 评估分数,越高越有希望

def generate_thoughts(node: Node, k: int = 3) -> list[Node]:
    """给定当前节点,生成 k 个候选下一步。真实场景是一次 LLM 提议调用。"""
    return [Node(path=node.path + [f"想法{len(node.path) + 1}.{i + 1}"], score=0.0)
            for i in range(k)]

def evaluate(node: Node) -> float:
    """确定性启发式评估:分支序号越靠前视为越有希望(便于复现)。
    真实场景是让 LLM 判断"这条路有没有希望"。"""
    depth = len(node.path)
    last = node.path[-1]                 # 形如 想法2.1
    branch = int(last.split(".")[-1])    # 取分支号
    return depth * 1.0 + (10 - branch) * 0.1

def tree_of_thoughts(depth: int = 3, beam_width: int = 2, k: int = 3) -> Node:
    frontier = [Node(path=[], score=0.0)]        # 初始根节点
    for level in range(depth):                    # 逐层展开
        candidates = []
        for node in frontier:
            for child in generate_thoughts(node, k):   # 每个节点生成 k 个候选
                child.score = evaluate(child)           # 评估打分
                candidates.append(child)
        # 剪枝:只保留分数最高的 beam_width 条
        frontier = sorted(candidates, key=lambda n: n.score, reverse=True)[:beam_width]
        print(f"第{level + 1}层:候选 {len(candidates)} 条,剪枝后保留 {len(frontier)} 条,"
              f"最高分 {frontier[0].score:.2f}")
    return frontier[0]

def main() -> None:
    best = tree_of_thoughts(depth=3, beam_width=2, k=3)
    print("最优路径:", best.path)
    print("最优得分:", round(best.score, 2))

if __name__ == "__main__":
    main()
```
保存为 `tree_of_thoughts.py`，运行 `python tree_of_thoughts.py`。预期输出为：
```text
第1层:候选 3 条,剪枝后保留 2 条,最高分 1.90
第2层:候选 6 条,剪枝后保留 2 条,最高分 2.90
第3层:候选 6 条,剪枝后保留 2 条,最高分 3.90
最优路径: ['想法1.1', '想法2.1', '想法3.1']
最优得分: 3.9
```
逐处讲解：

- `frontier` 是“当前活跃的搜索前沿”，初始只有一个空的根节点。
- 外层 `for level in range(depth)` 控制搜索深度；内层对每个前沿节点调用 `generate_thoughts` 生成 k 个候选——这就是“每步生成多个想法”（思维生成）。
- `evaluate` 给每个候选打分（状态评估），真实场景里这一步往往也是一次 LLM 调用（让模型判断某条路“有没有希望”）。**评估质量是 ToT 成败的命门**——评估器不准，剪枝就会把好路径剪掉。
- `sorted(...)[:beam_width]` 只保留分数最高的 `beam_width` 条路径，其余全部丢弃（剪枝）。这是 ToT 控制算力爆炸的关键——不剪枝的话，候选数会随深度指数级增长（k 的 depth 次方）。

从输出能直观看到 ToT 的成本来源：第 2、3 层的“候选 6 条”= `beam_width(2) × k(3)`。假设不剪枝、depth=3、k=3，候选会膨胀到 3³=27 条；而 beam search 把每层稳定压在 6 条候选、2 条保留，用“剪枝”换来了可控的算力。真实场景里每个候选的生成和评估都可能是一次 LLM 调用，所以这里的“6 条候选”意味着约 6 次生成 + 6 次评估调用——这就是为什么 ToT 比单链 CoT 贵十几到几十倍。

## 真实系统对应

**官方公开机制**：ToT 论文公开了“思维分解/生成/评估/搜索”四组件框架，并在 24 点、创意写作、迷你填字等需要探索的任务上验证了相对 CoT 的显著提升 [来源](https://arxiv.org/abs/2305.10601)；Self-Consistency 论文公开了“多链投票”这一更轻量的多路径方法 [来源](https://arxiv.org/abs/2203.11171)。**通用工程模式**：把 beam search / DFS / BFS 这类经典搜索算法套在“想法节点”上，是可迁移的通用做法；LangGraph 等框架也提供了 ToT 风格的参考实现。**教学参考实现**：上面的 `evaluate` 用确定性启发式仅为可复现，不代表任何真实评估器；真实 ToT 的评估通常是 LLM 自评或规则检验，其质量直接决定成败。

需要明确边界：ToT 论文报告的成功率提升是特定任务（如 24 点从个位数百分比提升到高百分比）下的结果，不是所有任务的通用增益。ToT 强依赖一个靠谱的评估器；评估器不准时，ToT 甚至可能比 CoT 更差——因为它会自信地把正确路径剪掉。这一点是选型时的核心风险。

## 三种范式的对比与选择

| 范式 | 一句话本质 | 是否交互外部 | 路径 | 是否评估回溯 | 相对算力成本 | 适用场景 |
|---|---|---|---|---|---|---|
| CoT | 一步步想 | 否 | 单条线性 | 否 | 1× | 纯推理问题（数学、逻辑） |
| Self-Consistency | 想 N 条再投票 | 否 | 多条独立链 | 只对最终答案投票 | N× | 高价值纯推理题 |
| ReAct | 边想边做 | 是（调工具） | 单条线性 | 靠观察隐式修正 | 视工具调用次数 | 需查外部信息的任务（主力） |
| ToT | 想多条再选 | 可结合 | 多路径树 | 是（评估+剪枝+回溯） | 十几到几十倍 | 需探索试错的高难任务 |

选择原则：**默认用 ReAct**；纯推理不需要工具时 CoT 足矣，高价值低容错的纯推理题叠加 Self-Consistency；只有当任务确实需要探索多条路径、且你愿意承担额外算力成本、且能提供靠谱评估器时，才上 ToT。

## 一张决策流程图帮你选型

把上面的原则画成可执行的决策流程，遇到新任务时照着走一遍：
```text
                 拿到一个任务
                      │
          需要访问外部信息/执行动作吗?
              /                    \
           是                        否
            │                         │
        用 ReAct              这是纯推理问题
            │                         │
    任务需要多路径          答对的代价很高、容错很低吗?
    探索/回溯吗?              /              \
      /       \             是                否
    是         否            │                 │
     │          │      Self-Consistency     单条 CoT
  ReAct+ToT   纯 ReAct     (多链投票)         就够了
  混合搜索
```
关键提醒：**这四种范式不是互斥的，而是可以嵌套组合的。** 现实中的强 Agent 常常是“以 ReAct 为主干，在某个特别难的子步骤上局部启用 ToT 搜索，同时对关键推理用 Self-Consistency 兜底”。不要把它们当成非此即彼的单选题。同时牢记第 01 节的“最低层次原则”：能用 CoT 解决就别上 ToT，ToT 是杀手锏不是日常武器。

## 思考：ToT 的四个必备组件是什么？为什么说“评估器质量是 ToT 成败的命门”？

### 回答

四个组件是：思维分解（一步想法的粒度）、思维生成（给定状态生成 k 个候选）、状态评估（给每个候选打分）、搜索算法（BFS/DFS/beam search 决定怎么展开和剪枝）。说评估器是命门，是因为 ToT 的核心增益来自“剪枝”——只保留有希望的分支、丢弃没希望的，从而在可控算力下探索大空间。而“哪条有希望”完全由评估器判断。如果评估器不准，剪枝就会系统性地把正确路径当成“没希望”剪掉，或把错误路径当成“有希望”保留，导致 ToT 不仅不比 CoT 好，反而更差（多花了几十倍算力还剪错了路）。所以上 ToT 前必须先确认：这个任务是否存在一个足够可靠的评估信号（LLM 自评是否可信，或是否有规则/外部检验可用）。

### 面试精简表达

四组件=分解/生成/评估/搜索；ToT 靠剪枝省算力，剪谁全看评估器，评估器错=把对的路剪掉，所以它是命门。

## 思考：CoT、ToT、Graph of Thoughts 之间是什么关系？

### 回答

它们是同一个搜索框架下复杂度递增的谱系，核心区别在“探索的拓扑结构”和“是否有评估与回溯”。CoT 是“一条链、不评估、不回溯”——树上只往下走一条路的退化特例。ToT 引入了“分支 + 评估 + 回溯”，把推理变成一棵可剪枝、可回溯的树，能解决 CoT 束手无策的探索型难题。再往后的 Graph of Thoughts（思维图）允许不同分支的想法节点合并、复用，把树推广成图，适合“不同子路径的中间结果可以互相拼接”的问题。复杂度和算力成本沿这个谱系递增，工程上仍应遵循“用能解决问题的最低层次”，绝大多数生产 Agent 用 ReAct 就够，ToT 及以上是高难任务的杀手锏。

## 机制推导：为什么 Self-Consistency 和 ToT 都能突破单链，但代价不同

单链 CoT 的失败模式是“一步错、步步错、且不回头”。突破它必须引入“冗余”或“反悔”。Self-Consistency 引入的是**并行冗余**：跑 N 条互不相干的完整链，赌“正确答案会在多条链上重合、错误各错各的”，用末端投票滤掉零星错误。它的优点是极易并行（N 条链可同时跑）、实现简单（不需要评估器）；缺点是成本固定 N 倍（无论中途多没希望都要把每条链跑完），且只能对“有明确最终答案、可投票”的任务生效（开放式写作没法投票）。

ToT 引入的是**反悔与止损**：边生成边评估，没希望的分支当场剪掉，不浪费算力跑完，还能回溯换路。它的优点是能中途止损、能处理开放式任务（用评估器择优）、能回溯；缺点是工程复杂（要实现生成器、评估器、搜索算法三件套）、成本随深度增长、且强依赖评估器质量。一句话对比：**Self-Consistency 是“多买几张彩票开奖时比大小”，ToT 是“边买边看走势、不行就止损换股”。** 前者省心但不省钱，后者省算力但难实现。选哪个，取决于任务能否投票、是否需要中途止损、以及你有没有靠谱的评估信号。

## 优化前后对比

| 维度 | 单链 CoT | Self-Consistency | ToT |
|---|---|---|---|
| 突破单链的方式 | 无（就是单链） | 并行 N 条链末端投票 | 边生成边评估边剪枝回溯 |
| 是否需要评估器 | 否 | 否（只需投票） | 是（且质量决定成败） |
| 能否中途止损 | 否 | 否（每条链跑完） | 能（剪掉没希望分支） |
| 能否处理开放式任务 | 单稿 | 需可投票的最终答案 | 能（评估器择优多稿） |
| 成本结构 | 1× | 固定 N× | 随深度增长，十几到几十× |
| 典型任务 | 一般多步推理 | 高价值可投票推理题 | 24 点、数独、多稿创意择优 |
