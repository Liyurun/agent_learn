## 真实问题

一个财报分析 Agent 要回答：“对比 A、B、C 三家公司最近一个财年的营收、净利率和研发投入占比，给出投资建议。”第一版用纯 ReAct（Reasoning and Acting，推理与行动）实现，边想边做：查 A 营收→想→查 A 净利率→想→查 A 研发→想→查 B 营收……每查一个数字都要回模型问一次“下一步查什么”。这个任务需要取 9 个独立数字（3 家 × 3 指标），ReAct 因此产生了 9 次“取数”+9 次“决定下一步”+1 次汇总 ≈ 19 次 LLM 调用，其中大量调用只是在重复“接下来该查 X 了”这种毫无悬念的决策，token 成本和延迟都很高。

关键观察是：**这 9 个数字之间没有依赖关系——查 A 营收根本不需要先知道 B 净利率。** 既然步骤是可预先确定的，为什么要一步一回头地问模型？这正是 **ReWOO（Reasoning WithOut Observation，无观察推理）** 要解决的问题：先让模型一次性规划出完整的取数蓝图（用占位符表示还没拿到的结果），再批量执行所有工具，最后一次性代入求解。改造后，LLM 调用从约 19 次降到 2 次（1 次规划 + 1 次求解），token 效率大幅提升。

这一节讨论规划的“放置方式”：是**边走边想**（隐式规划，ReAct 式），还是**先想好整条路再走**（显式规划，Plan-and-Execute 与 ReWOO）。

## 原理：规划的两种放置方式

在工程实现上，规划可以放在不同位置：

- **隐式规划（内嵌于 ReAct）**：模型在每一轮的 Thought 里即时决定下一步，不预先制定完整计划。灵活，能随时改方向，但可能走弯路，且每步都要一次 LLM 调用。
- **显式规划（Plan-and-Execute）**：先让模型生成一份完整的分步计划，再逐步执行。计划清晰、可审计、适合长任务；缺点是计划可能与执行中出现的新情况脱节，因此常配合“重规划（Replan）”机制。

Plan-and-Solve 论文正是这一思路的学术化表达：它发现 Zero-shot CoT（Chain-of-Thought，思维链）存在“计算错误、漏步、语义理解错误”三类问题，于是提出让模型先“制定一个把整个任务划分为若干子任务的计划”，再按计划执行子任务，从而减少漏步 [来源](https://arxiv.org/abs/2305.04091)。

## ReWOO：把推理与观察解耦

**ReWOO（Reasoning WithOut Observation，无观察推理）** 更进一步。传统 ReAct 每次调用工具后，都要把观察结果拼回上下文再问模型下一步，这导致上下文随步数膨胀、且每步都重复携带完整历史，token 消耗大。ReWOO 的核心洞察是：**如果步骤之间的依赖是可预测的，就不必在每步之后都回头问模型。** 它把流程拆成三个模块 [来源](https://arxiv.org/abs/2305.18323)：
```text
ReWOO 三模块:
  1. Planner(规划器):一次性产出完整蓝图,用占位符 #E1、#E2... 表示
     "此处将来要填入某工具的返回结果",步骤之间可引用彼此的占位符。
  2. Worker(执行器):按蓝图批量执行所有工具调用,把真实结果填进占位符。
  3. Solver(求解器):拿到填好的证据,一次性推理出最终答案。
```
论文报告 ReWOO 在多步推理基准 HotpotQA 上取得约 5 倍的 token 效率和 4% 的准确率提升，因为它把“规划推理”和“逐条观察”解耦了，规划只发生一次，观察批量发生，不再每步都重复携带历史 [来源](https://arxiv.org/abs/2305.18323)。
```text
ReAct(边想边做):
  想→做→观察→想→做→观察→想→做→观察→汇总
  每个"想"都是一次 LLM 调用,携带全部历史

ReWOO(先规划后执行):
  想(一次规划出全部步骤)→[做 做 做](批量执行,不调 LLM)→求解(一次)
  只在头尾各一次 LLM 调用
```
## 显式规划的时序与“重规划”

先想好整条路的风险是：路可能中途断了。把 Plan-and-Execute 的运行时序画出来，能看清“重规划”为什么必要：
```text
显式规划(Plan-and-Execute + Replan):

  用户目标
     │
     ▼
  ┌─────────┐   生成完整计划   ┌──────────────────────────┐
  │ Planner │ ───────────────▶│ 步骤1 → 步骤2 → 步骤3 ...  │
  └─────────┘                 └──────────────────────────┘
                                        │ 逐步执行
                                        ▼
                              ┌──────────────────┐
                              │  Executor 执行    │
                              └──────────────────┘
                                        │
                          执行中发现"现实和计划不符"
                          (步骤2 的前提没了 / 出现新信息)
                                        │
                                        ▼
                              ┌──────────────────┐
                              │  触发 Replan 重规划 │──┐
                              └──────────────────┘  │
                                        ▲           │
                                        └───────────┘
                                     基于新现实生成新计划
```
“重规划”的本质是承认一件事：**再周密的计划也无法预料执行中的所有变化。** 一份在 t=0 时刻制定的计划，到了 t=3 时刻可能已经因为“某个 API 挂了”“搜索结果推翻了原假设”而失效。因此显式规划系统必须具备“发现计划失效 → 重新规划”的能力，否则它就会僵硬地按错误计划一路错到底。这也是 ReWOO 相对 Plan-and-Execute 的一个权衡点：ReWOO 因为“执行阶段不回头问模型”而省 token，但也因此**对“计划中途失效”更不敏感**——如果 #E2 的工具挂了，纯 ReWOO 不会像 ReAct 那样立刻感知并调整。生产中常用“ReWOO 打底 + 关键步骤失败时回退到 Replan”的混合策略。

## 最小可运行演示

下面这段代码用贯穿任务 B（查原价、查折扣、查优惠券再求最终价）对比 ReAct 与 ReWOO 的 LLM 调用次数。三个数字之间没有依赖，正是 ReWOO 的理想场景。
```python
"""对比 ReAct(边想边做)与 ReWOO/Plan-Execute(先规划后执行)两种骨架,
统计各自的 LLM 调用次数和工具调用次数,直观看到 token 效率差异。"""

## 共享工具
def price_tool(_: str) -> str:
    return "120"

def discount_tool(_: str) -> str:
    return "0.7"

def coupon_tool(_: str) -> str:
    return "20"

TOOLS = {"price": price_tool, "discount": discount_tool, "coupon": coupon_tool}

## ReAct:每一步都要一次 LLM 调用来决定下一步
def run_react() -> dict:
    llm_calls = 0
    tool_calls = 0
    facts = {}
    plan_order = ["price", "discount", "coupon"]
    for name in plan_order:
        llm_calls += 1                 # 每观察一次都要重新问 LLM 下一步
        facts[name] = TOOLS[name]("")
        tool_calls += 1
    llm_calls += 1                     # 最后一次 LLM 汇总答案
    final = float(facts["price"]) * float(facts["discount"]) - float(facts["coupon"])
    return {"mode": "ReAct", "llm_calls": llm_calls,
            "tool_calls": tool_calls, "answer": final}

## ReWOO / Plan-Execute:先一次规划出全部步骤,执行时不再调用 LLM
def run_rewoo() -> dict:
    llm_calls = 0
    tool_calls = 0
    # 步骤1:Planner 一次性产出带占位符的完整蓝图
    llm_calls += 1
    plan = [
        ("price", "#E1"),
        ("discount", "#E2"),
        ("coupon", "#E3"),
    ]
    # 步骤2:Worker 批量执行工具,不再调用 LLM
    evidence = {}
    for name, slot in plan:
        evidence[slot] = TOOLS[name]("")
        tool_calls += 1
    # 步骤3:Solver 一次性代入证据求解
    llm_calls += 1
    final = float(evidence["#E1"]) * float(evidence["#E2"]) - float(evidence["#E3"])
    return {"mode": "ReWOO", "llm_calls": llm_calls,
            "tool_calls": tool_calls, "answer": final}

def main() -> None:
    for result in (run_react(), run_rewoo()):
        print(f"{result['mode']:>6} | LLM调用={result['llm_calls']} "
              f"工具调用={result['tool_calls']} 答案={result['answer']}")
    react = run_react()
    rewoo = run_rewoo()
    saved = react["llm_calls"] - rewoo["llm_calls"]
    print(f"结论: ReWOO 比 ReAct 少 {saved} 次 LLM 调用,答案一致={react['answer'] == rewoo['answer']}")

if __name__ == "__main__":
    main()
```
保存为 `plan_vs_react.py`，运行 `python plan_vs_react.py`。预期输出为：
```text
 ReAct | LLM调用=4 工具调用=3 答案=64.0
 ReWOO | LLM调用=2 工具调用=3 答案=64.0
结论: ReWOO 比 ReAct 少 2 次 LLM 调用,答案一致=True
```
这段代码的关键点：两种模式的**工具调用次数相同**（都要取 3 个数字），但 **LLM 调用次数不同**——ReAct 每取一个数字都要问一次“下一步”，加上汇总共 4 次；ReWOO 只在头（规划）尾（求解）各一次，共 2 次。任务里的独立步骤越多，这个差距越大：如果是 9 个独立数字，ReAct 约 10 次 LLM 调用，ReWOO 仍是 2 次。这正是 ReWOO 论文所说的“token 效率提升”的工程直觉——**省的不是工具调用，而是重复的“决定下一步”推理调用**。

## 真实系统对应

**官方公开机制**：Plan-and-Solve 论文公开了“先规划分解、再按计划执行子任务”的 zero-shot 提示策略及其对漏步问题的改善 [来源](https://arxiv.org/abs/2305.04091)；ReWOO 论文公开了 Planner-Worker-Solver 三模块解耦，以及在 HotpotQA 上约 5 倍 token 效率、4% 准确率提升的实验结论 [来源](https://arxiv.org/abs/2305.18323)。**通用工程模式**：LangGraph 等框架提供了 plan-and-execute、ReWOO 的参考实现，把“规划节点—执行节点—重规划边”组织成状态图，可迁移到自己的 Agent [来源](https://docs.langchain.com/oss/python/langchain-agents)。**教学参考实现**：上面的 `run_react`/`run_rewoo` 用计数器模拟调用次数，不代表任何框架的真实 token 计费；真实系统的 token 消耗还取决于每次调用携带的上下文长度。

需要明确边界：论文报告的“5 倍效率”是 HotpotQA 特定基准下的结果，不是所有任务的通用倍率。ReWOO 的收益强依赖“步骤依赖可预测”这一前提；当后续步骤高度依赖前一步的具体观察（比如“先搜到人名，才知道下一步搜什么”）时，ReWOO 的占位符蓝图就难以一次成型，此时 ReAct 的“边看边定”反而更合适。

## 生产踩坑

| 症状 | 根因 | 如何观测与复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| ReWOO 蓝图一次生成后处处对不上 | 步骤间存在“看了才知道下一步”的强依赖 | 检查计划里是否有无法预填的占位符 | 强依赖段回退到 ReAct 边看边定 | 依赖弱、步骤独立的任务无需回退 |
| 计划中途失效仍一路执行到底 | 缺少重规划触发条件 | 注入一个中途失效的前提复现 | 关键步失败/前提变化时触发 Replan | 完全确定的流水线可省重规划 |
| 显式计划质量参差、忽好忽坏 | 一次性规划对模型要求高，长任务尤甚 | 人工审核计划步骤的完整性 | 先小范围试点，用回归集评估计划质量 | 短任务隐式 ReAct 更省心 |
| Replan 逻辑复杂到难以维护 | 一上来就做“高大上”的重规划系统 | 统计 Replan 触发频率与维护成本 | 先用 ReAct 跑通，观察弯路再引入显式规划 | 合规类必须审计的任务需显式计划 |
| ReWOO 省了 token 但答案变差 | 执行阶段不回头，错误无法及时纠正 | 对比两种模式在同一任务集的成功率 | 关键步加校验，失败即回退 Replan | 低风险批处理可接受 |
| 计划可审计但无人真去审 | 把“可审计”当成“已审计” | 检查是否有计划评审环节与责任人 | 对高风险任务设强制人工审核关卡 | 低风险任务自动执行即可 |

## 思考：显式规划相比隐式规划的优点和风险各是什么？为什么需要“重规划”？

### 回答

显式规划（先出完整计划再执行）的优点有三：一是**可审计**，计划是一个明确的产物，可以人工审核、留痕、追责，特别适合合规流程；二是**可优化调用成本**，像 ReWOO 那样把“决定下一步”的重复推理省掉，token 效率更高；三是**结构清晰**，长任务不易漏步。风险也有三：一是**计划与现实脱节**，t=0 制定的计划到 t=3 可能因外部变化失效；二是**对模型一次性规划能力要求高**，长任务的计划质量容易参差；三是**执行阶段若不回头（如纯 ReWOO），错误难以及时纠正**。“重规划”正是为了对冲第一个风险：当执行中发现前提失效、API 挂了、新信息推翻原假设时，触发重新规划，避免僵硬地按错误计划一路错到底。没有重规划的显式规划，是一份“不会拐弯的地图”。

### 面试精简表达

显式规划=可审计、可省 token、少漏步，但会和现实脱节；重规划就是给计划装上“发现走错就重新画路”的能力。

## 思考：什么时候用 ReAct，什么时候用 ReWOO/Plan-Execute？

### 回答

关键判据是**步骤之间的依赖是否可预测**。如果后续步骤高度依赖前一步的具体观察（“先搜到某个人名，才知道下一步搜什么”），依赖是运行时才显现的，用 ReAct 边看边定更合适。如果步骤之间相互独立或依赖关系在规划时就能确定（“分别查 3 家公司的 3 个指标再汇总”），用 ReWOO/Plan-Execute 能省下大量重复的“决定下一步”调用。次要判据是**是否需要审计**：合规、金融等需要留痕审核的场景倾向显式计划。工程上更稳的路径是“先用 ReAct 跑通、观察它在哪些环节反复走弯路、再针对性引入显式规划”，而不是一开始就上复杂的 Replan 系统——规划架构应该被真实问题逼出来，而非过度设计。

## 事故回放：一次“不该用 ReWOO”的翻车

某招聘 Agent 要完成“找到候选人 X 最近的一篇论文，总结其研究方向，再据此推荐 3 个匹配岗位”。工程师看到“任务可分步”，就直接套了 ReWOO：Planner 一次性产出蓝图“#E1=搜索候选人论文；#E2=总结#E1；#E3=根据#E2匹配岗位”。看起来很美，执行却崩了——`#E1` 搜索返回的是“未找到该候选人的论文”，但 ReWOO 的 Worker 阶段不回头问模型，机械地把这条“空结果”填进 `#E2`，Solver 于是基于“没有论文”硬编了一段研究方向，再推荐了 3 个牛头不对马嘴的岗位。整条链没有一个环节察觉到“第一步就没拿到有效数据”。

复盘的结论不是“ReWOO 不好”，而是“**这个任务的步骤依赖是强的、且第一步可能失败**”：后两步完全依赖第一步是否真的拿到论文。正确做法是回退到 ReAct（第一步观察到“未找到”就立刻改问“换关键词或直接问候选人要”），或者用“ReWOO 打底 + 关键步失败即回退 Replan”的混合策略。这个案例是本节踩坑表第一行的真实注脚：**ReWOO 的省钱红利，只在“依赖可预测”的前提下成立。**

## 优化前后对比

| 维度 | ReAct（边想边做） | ReWOO（先规划后执行） | 验证方式 |
|---|---|---|---|
| LLM 调用次数 | 随独立步数线性增长 | 头尾各一次，基本恒定 | 用本节代码统计不同步数下的调用数 |
| 对中途失效的敏感度 | 高，下一步立刻感知 | 低，执行阶段不回头 | 注入中途失效前提看是否纠正 |
| 适合的依赖结构 | 强依赖、运行时才显现 | 弱依赖、规划时可确定 | 检查计划能否一次填满占位符 |
| 可审计性 | 计划藏在过程里 | 蓝图是显式产物 | 能否导出并人工审核计划 |
| 典型风险 | token 成本高 | 依赖误判导致空结果传播 | 见本节两处事故回放 |

到这里，我们已经覆盖了“单步增强（CoT）—推理行动交织（ReAct）—规划放置（Plan/ReWOO）”。它们有一个共同点：**每一步都只沿一条路往下走**。当任务需要“同时探索多条路、评估、回溯剪枝”时，就要进入本章的最高层次——ToT 与多路径搜索。
