## 真实问题

候选人 A 复盘时还有一句委屈：「我第 21 到 24 章的方法都背了，概念题、设计题、实操题、场景题各有一套框架，可一到现场就串了——设计题我用了概念题的答法，只讲了『是什么』，忘了谈架构和权衡。」这是很典型的问题：**四套框架分开记，负担重、临场易串**。这一节要做两件事：先把四类题的框架浓缩成一张扫一眼就能用的速查表，再揭示一个更省力的真相——**四类题其实共享同一条高分公式**，记住这一条，比记四套框架更抗压。

## 原理：四张速查框架

把前四章的方法浓缩成一张速查表，面试前扫一眼即可：

| 题型 | 核心框架 | 一句话要诀 |
|---|---|---|
| 概念题（第 21 章） | 定义 → 区分 → 例子 | 一句话定义打头，别堆名词 |
| 系统设计题（第 22 章） | 澄清 → 架构 → 流程 → 工程 → 权衡 | 先问需求，主动谈工程化和取舍 |
| 框架实操题（第 23 章） | 骨架 → 细节 → 补生产差距 | 边写边讲，主动说 Demo 与生产的差距 |
| 场景题（第 24 章） | 分析 → 方案 → 验证 | 先拆解问题，用数据说话 |

这张表的用法是「面试前扫一眼建立索引」：拿到题先在心里快速归类——这是概念题还是设计题？归好类，对应的框架骨架就浮现出来，你就不会像候选人 A 那样「用错框架」。但更进一步，你会发现这四套框架背后其实是同一件事。

## 现象与输入：四类题的高分点惊人地一致

虽然四类题框架不同，但它们的高分点惊人地一致：**都要求你在「标准答案」之外，额外展示工程意识和权衡意识**。

- 概念题的高分点是「能说出这个概念的代价和边界」，而不只是背定义；
- 设计题的高分点是「主动谈评估、护栏、成本」，而不只是画架构图；
- 实操题的高分点是「主动说 Demo 和生产的差距」，而不只是写出能跑的代码；
- 场景题的高分点是「先定位再动手、用数据验证」，而不只是给个方案。

所以如果你只想记一件事，就记这句：**任何题，答完「是什么/怎么做」之后，都要再补一句「它的代价/边界/如何验证」**。这一句往往就是初级和资深的分水岭，也和第 20 章里那套系统「输出看起来正常不是判据，关键是每个决策都有来源、越界能拦、失败可定位」的工程观完全一致。

## 最小可运行演示

我们把「先归类、再套框架、最后检查高分公式」这套流程写成一个可运行的路由器，让你直观看到「一道题从输入到高分骨架」的全过程。
```python
"""第25.2节：题型分诊 + 高分公式检查器（纯 Python，无需 API Key）。"""
from dataclasses import dataclass

## 题型关键词（教学 mock：靠信号词粗分，真实场景靠你自己判断）
TYPE_KEYWORDS = {
    "概念题": ["是什么", "区别", "解释一下", "定义", "什么叫"],
    "设计题": ["设计", "架构", "从零", "怎么搭", "如何构建"],
    "实操题": ["手写", "实现", "写一个", "代码", "跑一遍"],
    "场景题": ["线上", "遇到", "如果出现", "怎么排查", "指标下降"],
}
FRAMEWORK = {
    "概念题": "定义 → 区分 → 例子",
    "设计题": "澄清 → 架构 → 流程 → 工程 → 权衡",
    "实操题": "骨架 → 细节 → 补生产差距",
    "场景题": "分析 → 方案 → 验证",
}
## 三段高分公式：所有题共享
HIGH_SCORE = ["标准答案（是什么/怎么做）", "工程意识（评估/护栏/成本/验证）", "权衡意识（代价/边界/何时不适用）"]


@dataclass
class Plan:
    qtype: str
    framework: str
    checklist: list


def plan_answer(q: str) -> Plan:
    best, best_hits = "场景题", 0
    for t, kws in TYPE_KEYWORDS.items():
        hits = sum(1 for k in kws if k in q)
        if hits > best_hits:
            best, best_hits = t, hits
    return Plan(best, FRAMEWORK[best], HIGH_SCORE)


QUESTIONS = [
    "请解释一下 Agent 和 Workflow 的区别",
    "从零设计一个生产级客服 Agent 你会怎么做",
    "手写一个最小的 ReAct 循环",
    "线上 Agent 突然幻觉率上升，你怎么排查",
]


def run() -> None:
    for q in QUESTIONS:
        p = plan_answer(q)
        print(f"题：{q}")
        print(f"  归类={p.qtype}  骨架={p.framework}")
        print(f"  别忘补：{p.checklist[1]} + {p.checklist[2]}")


if __name__ == "__main__":
    run()
```
保存为 `s2_router.py`，运行 `python s2_router.py`。完整预期输出：
```text
题：请解释一下 Agent 和 Workflow 的区别
  归类=概念题  骨架=定义 → 区分 → 例子
  别忘补：工程意识（评估/护栏/成本/验证） + 权衡意识（代价/边界/何时不适用）
题：从零设计一个生产级客服 Agent 你会怎么做
  归类=设计题  骨架=澄清 → 架构 → 流程 → 工程 → 权衡
  别忘补：工程意识（评估/护栏/成本/验证） + 权衡意识（代价/边界/何时不适用）
题：手写一个最小的 ReAct 循环
  归类=实操题  骨架=骨架 → 细节 → 补生产差距
  别忘补：工程意识（评估/护栏/成本/验证） + 权衡意识（代价/边界/何时不适用）
题：线上 Agent 突然幻觉率上升，你怎么排查
  归类=场景题  骨架=分析 → 方案 → 验证
  别忘补：工程意识（评估/护栏/成本/验证） + 权衡意识（代价/边界/何时不适用）
```
无论归到哪一类，脚本都提醒你补同一条「工程意识 + 权衡意识」——这正是四类题共享高分公式的直观体现。**注意**：关键词分类只是教学演示，真实面试靠你自己判断题型（ReAct（Reasoning and Acting，推理与行动）这类题往往兼具实操与概念，怎么归类取决于面试官想考什么）。

## 真实系统对应

**官方公开机制**：设计题和场景题的「补工程意识」之所以是高分点，是因为业界权威指南都把「评估、可观测、护栏、成本」列为 Agent 从 Demo 走向生产的必备环节——OpenAI 的实践指南明确把评估与护栏列为上线前提 [来源](https://cdn.openai.com/business-guides-and-resources/a-practical-guide-to-building-agents.pdf)，Anthropic 的指南也强调用最简单方案起步、复杂度要由收益证明 [来源](https://www.anthropic.com/engineering/building-effective-agents)。所以你在设计题里主动谈「我会先搭评估集、加输出护栏、算 token 成本」，不是耍花枪，而是复述了公开工程共识。**通用工程模式**：「标准答案 + 工程意识 + 权衡意识」的三段高分公式，可迁移到任何技术面试题型。**教学参考实现**：上面的题型分诊器用关键词粗分是为可复核而构造，不代表任何面试官真实的题型划分。

一个必须澄清的边界：题型的边界是模糊的。同一道「手写一个 ReAct Agent 并说说它在生产里的问题」，既是实操题也是设计题；「解释 RAG（Retrieval-Augmented Generation，检索增强生成）为什么会幻觉」既是概念题也带场景题色彩。所以别在「精确归类」上纠结，归类只是为了调出框架骨架，真正兜底的是那条通用高分公式——无论怎么归，补上工程与权衡总没错。

## 生产踩坑：套框架时最常见的翻车与修复

| 症状 | 根因 | 如何观测与复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| 设计题只画了架构图就停 | 只走到框架第二步，漏了工程和权衡 | 录音回听，看有没有说到评估/护栏/成本 | 强制在结尾补「工程 + 权衡」两句 | 面试官明确只想听架构时 |
| 概念题堆了一堆名词 | 误以为「说得多」等于「懂得深」 | 数一段话里出现几个未解释的术语 | 一句话定义打头，每个术语配一句人话 | 面向专家的深挖追问除外 |
| 实操题闷头敲代码不出声 | 把它当笔试而非「边写边讲」 | 回看录屏，看有没有同步讲思路 | 边写边念，主动说「这里生产要加 X」 | 明确要求安静作答的笔试环节 |
| 场景题上来就给方案 | 跳过「先定位」，凭直觉猜原因 | 看有没有先问指标、先看日志再动手 | 先分析定位、用数据验证再下结论 | 题目已给全信息、无需澄清时 |
| 四套框架临场记串 | 分开硬记，未提炼共同底层 | 模拟面试里看会不会用错框架 | 只记「归类→骨架→补高分公式」一条链 | 单一题型的专项练习时 |
| 归类纠结耽误时间 | 把「精确分类」当成答题前提 | 计时看开口前卡了几秒 | 归类求快不求准，靠高分公式兜底 | 题目本身就是「请判断题型」时 |

## 思考：既然有通用高分公式，为什么还要分四类题型？

### 回答

因为「高分公式」解决的是「答什么才加分」，而「题型框架」解决的是「按什么顺序组织」，二者是互补而非替代关系。只有高分公式没有框架，你会知道「要补工程和权衡」，却不知道一道设计题该先澄清需求还是先画架构，容易上来就一头扎进细节、丢了主线；只有框架没有高分公式，你会按部就班走完流程，却可能全程停在「标准答案」层面，拿不到区分资深的分。正确的用法是两者叠加：**先用题型框架搭出回答的骨架和顺序（横向的流程），再用高分公式给每一步注入深度（纵向的层次）**。举个例子，设计题的框架告诉你「澄清→架构→流程→工程→权衡」这个顺序，而高分公式提醒你即使在「架构」这一步，也要顺带说一句「这个架构的代价是……」。所以框架管「路线」，公式管「海拔」，一个负责别走错路，一个负责别走得太浅。面试前扫一眼速查表建立题型索引，临场兜底靠那条通用公式，这才是最省力又最稳的组合。

### 面试精简表达

框架管「按什么顺序组织」，公式管「答什么才加分」，二者互补。框架给路线避免走偏，公式给海拔避免答浅。临场先归类调框架、再用「工程+权衡」兜底加分。

## 思考：为什么「先分析定位、再动手」是场景题的核心，而不是快速给方案？

### 回答

因为场景题考的从来不是「你知不知道某个解决方案」，而是「面对一个模糊的线上问题，你有没有系统的定位能力」——这恰恰是真实工作里最值钱的能力。设想面试官问「线上 Agent 幻觉率突然上升怎么办」，一个上来就说「加个护栏、换个模型」的候选人，暴露的是「凭直觉猜、头痛医头」的工作习惯；而一个先问「幻觉率从多少升到多少、是全量还是某类 query、是不是伴随某次变更上线」的候选人，展现的是「先用数据定位、再对症下药」的工程素养。真实故障里，同样是「幻觉率上升」，根因可能是检索没命中却硬答、可能是新上线的 prompt 改动、可能是某个知识库文档过期——不先定位就给方案，大概率药不对症。这与第 20 章里「优化后每个决策都可定位、失败可复现」是同一套思维。所以场景题的高分答法是：**先把问题拆成可观测的信号（哪个指标、什么范围、伴随什么变化），锁定最可能的根因，再给方案，最后说怎么用数据验证方案有效**——这条「分析→方案→验证」的闭环，比任何单个方案都更能证明你能扛线上。

### 面试精简表达

场景题考的是定位能力而非方案储备。先把问题拆成可观测信号锁定根因，再对症给方案，最后用数据验证闭环。上来就给方案暴露的是「凭直觉、头痛医头」的坏习惯。
