## 真实问题

贯穿案例里那道设计题「要不要上多 Agent」，候选人 A 答得不错，可面试官顺势追了一句：「你提到用 MCP（Model Context Protocol，模型上下文协议）来接工具，那 MCP 的传输层和 Function Calling 在协议层面具体差在哪？」——这一下问到了 A 的知识盲区。他的第一反应是硬撑：「呃……MCP 应该是……用了一种更高级的协议……」，越说越虚，最后被面试官一个反问「你确定吗」直接问懵。

**没人能答对所有题**，面试官会一直问到你答不上来为止（第 3 节讲过，这是在探边界）。真正决定成败的不是「你是否全会」，而是**你「不会时的反应」**。硬编、沉默、慌乱都是减分项——A 的硬撑恰恰坐实了「不懂装懂」这条态度类红旗。这一节要给你三种「答不上来时的体面接法」，让你在触到边界时，把「不会」变成「展示思维和心态」的机会。

## 原理：三种体面接法

记住三种体面接法，它们的共同内核是「诚实 + 展示可迁移能力」：

1. **坦诚 + 思路法**：「这块我没深入研究过，不过按我的理解，思路应该是……」——诚实不丢分，还能展示推理能力。
2. **拆解 + 缩小法**：「这个问题挺大的，我先说我确定的那部分，不确定的部分我说说我会怎么去查证。」——把大问题拆成「我会的」和「我会去查的」。
3. **反问 + 澄清法**：「这里的 X 您是指哪种情况？」——如果是题目本身模糊，主动澄清比瞎答强。

这三种接法之所以有效，是因为它们把面试官的注意力，从「你不知道的那个具体答案」引导到「你如何面对未知」上——而后者恰恰是面试官更看重的东西。就像第 20 章意图路由里「模型自己拿不准就转人工兜底」的置信度机制：**当你对答案的置信度低时，坦诚地「转人工」（说不确定并给思路），远好过强行给一个高风险的硬编答案**。

## 现象与输入：三种「不会」的场景各配一种接法

「不会」其实分几种情况，对应不同的接法。用一张表把「情境—错误示范—优秀示范」对齐（表头用「情境」）。

| 情境 | 错误示范 | 优秀示范 |
|---|---|---|
| 完全没听过的概念 | 硬编一个听起来像的答案 | 「这个我不确定，但从名字推测它可能是解决……的」 |
| 记不清具体细节 | 支支吾吾装作记得 | 「具体数值我记不清了，但量级和原理是……」 |
| 题目太开放没法答 | 随便挑一个方向乱答 | 先澄清约束，再给「如果是 A 我会……如果是 B 我会……」 |
| 概念听过但没深究 | 强行展开、越说越虚 | 「我用过但没深挖底层，我理解它的作用是……」 |
| 被追问到能力边界外 | 慌乱、沉默、乱编 | 「到这一层我确实没实践过，我会这样去查证……」 |

面试官问难题，很多时候**根本不指望你答对**，而是想看你的**思维过程和心态**。一个能坦然说「我不确定，但我的思路是……」的人，比一个硬编答案的人可信得多。

## 最小可运行演示

我们把「根据置信度选接法」这套逻辑写成一个可运行的决策器：输入你对某个问题的「掌握程度」和「问题类型」，它给出建议的接法和一句可直接用的模板。这把第 20 章的「置信度兜底」思想迁移到了答题现场。
```python
"""第25.5节：答不上来时的接法决策器（纯 Python，无需 API Key）。"""
from dataclasses import dataclass


@dataclass
class Reply:
    method: str
    template: str


def choose(confidence: float, ambiguous: bool, ever_used: bool) -> Reply:
    ## 题目本身模糊 -> 先澄清，别急着答
    if ambiguous:
        return Reply("反问+澄清法", "这里的 X 您是指哪种情况？我按不同情况分别说思路。")
    ## 高置信 -> 正常作答（不属于“答不上来”）
    if confidence >= 0.6:
        return Reply("正常作答", "用 PREP-T 直接答，答完主动补一句权衡。")
    ## 用过但没深挖 -> 拆解+缩小，先讲确定的
    if ever_used:
        return Reply("拆解+缩小法", "我用过但没深挖底层。我确定的部分是……不确定的我会这样查证……")
    ## 完全不确定 -> 坦诚+思路
    return Reply("坦诚+思路法", "这块我没深入研究过，不过按我的理解，思路应该是……")


CASES = [
    ("MCP 传输层细节", 0.2, False, True),
    ("一个完全没听过的库名", 0.1, False, False),
    ("一道没给约束的开放设计题", 0.3, True, False),
    ("Agent 与 Workflow 区别", 0.9, False, True),
]


def run() -> None:
    for name, conf, amb, used in CASES:
        r = choose(conf, amb, used)
        print(f"[{name}] 置信度={conf}")
        print(f"    建议接法：{r.method}")
        print(f"    可用模板：{r.template}")


if __name__ == "__main__":
    run()
```
保存为 `s5_fallback.py`，运行 `python s5_fallback.py`。完整预期输出：
```text
[MCP 传输层细节] 置信度=0.2
    建议接法：拆解+缩小法
    可用模板：我用过但没深挖底层。我确定的部分是……不确定的我会这样查证……
[一个完全没听过的库名] 置信度=0.1
    建议接法：坦诚+思路法
    可用模板：这块我没深入研究过，不过按我的理解，思路应该是……
[一道没给约束的开放设计题] 置信度=0.3
    建议接法：反问+澄清法
    可用模板：这里的 X 您是指哪种情况？我按不同情况分别说思路。
[Agent 与 Workflow 区别] 置信度=0.9
    建议接法：正常作答
    可用模板：用 PREP-T 直接答，答完主动补一句权衡。
```
回到候选人 A 那道 MCP 追问：他的置信度低、但 MCP 他确实用过（只是没深挖协议层），决策器建议用「拆解+缩小法」——他本该说「我用 MCP 接过工具，确定的是它把工具发现和调用标准化了；至于传输层和 Function Calling 在协议字节层面的差异我没深挖，我会去翻 MCP 的官方规范确认」。这个回答诚实、有信息量、还展示了「知道去哪查」的能力，远胜硬撑。**注意**：置信度是你对自己的诚实评估，别为了「显得会」而虚报——虚报的代价就是被追问时穿帮。

## 真实系统对应

**官方公开机制（方法论层面）**：「置信度低就保守处理」是有工程共识支撑的思路——第 20 章引用的 OpenAI 护栏与审批机制中，「模型拿不准的高风险动作要暂停/转人工」正是同一逻辑 [来源](https://cdn.openai.com/business-guides-and-resources/a-practical-guide-to-building-agents.pdf)；把它迁移到答题，就是「我拿不准时，坦诚+给思路，而不是硬输出」。**通用工程模式（沟通模式）**：「诚实标注不确定性 + 展示如何求证」是可迁移的专业表达方式，在技术评审、事故复盘里同样加分。**教学参考实现**：上面的决策器用 confidence 阈值选接法是为可复核而构造，真实临场靠你自己判断，不存在这样一个精确的分数。

一个必须澄清的边界：「坦诚说不会」不等于「一问就投降」。三种接法的关键都在「诚实之后还要往前走一步」——要么给思路、要么讲确定的部分、要么澄清后分情况答。如果你只说「这个我不会」然后闭嘴，那依然是减分的，因为你没展示任何可迁移能力。诚实是底线，「诚实 + 推理/求证」才是加分点。

## 生产踩坑：答不上来时的常见翻车与修复

| 症状 | 根因 | 如何观测与复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| 硬编一个像是对的答案 | 怕「不会」丢人，虚报置信度 | 模拟时故意问盲区，看会不会硬编 | 坦诚说不确定，再给推测思路 | 确实高置信、只是一时卡壳时 |
| 说完「不会」就沉默 | 只做了诚实，没做「再走一步」 | 回听有没有在坦诚后补思路 | 诚实后必接思路/求证/分情况 | 题目确实与岗位完全无关时 |
| 开放题上来就乱答 | 没先澄清约束，猜错方向 | 看有没有先问约束就动手 | 先反问澄清，再分情况给方案 | 面试官明确说「你自己定约束」时 |
| 越说越虚、逻辑崩掉 | 强撑一个不熟的点硬展开 | 录音看不熟的点是否越说越乱 | 触到边界立刻切「拆解+缩小」 | 只是紧张、内容其实会时 |
| 反问澄清变成挑刺 | 澄清语气生硬、像质疑题目 | 让朋友判断你的反问是否礼貌 | 用「我想确认一下」这类软化措辞 | 题目已经非常明确、无需澄清时 |
| 虚报「我很熟」被追问穿帮 | 为显得会而夸大掌握程度 | 顺着你的「熟」连问三层看崩点 | 如实标注掌握深度，不夸大 | 你确实精通该点时 |

## 思考：为什么「坦诚说不确定」在面试里通常不会致命，反而可能加分？

### 回答

因为面试官评估的核心是「你入职后能不能放心共事」，而「坦诚说不确定」恰恰是共事时最稀缺、最宝贵的品质之一。设想两个未来的同事：一个遇到不确定的问题会说「这块我不太确定，我去查证一下」，另一个会不懂装懂、给你一个似是而非的答案。前者你可以放心把事情交给他——他知道自己能力的边界，不会在没把握的地方乱来，还知道怎么去补齐；后者是隐患——他会用「假装知道」掩盖盲区，等你基于他的错误答案做了决策，才发现被坑。面试里的硬编和不懂装懂，正是后一种人的预演。所以当你坦诚说「我不确定，但我的思路是……」时，你传递的信号是「我诚实、有自知之明、知道怎么求证」，这些恰恰是面试官最想要的协作特质。当然,坦诚有个前提:它必须发生在「你确实触到了能力边界」时,而不是「稍微一想就放弃」——如果每道题你都秒答「不确定」,那暴露的是准备不足和不肯思考,那是另一种减分。所以坦诚要「用对地方」:该会的扎实答出来,触到真边界时诚实标注并给思路,这个组合才是最可信的。

### 面试精简表达

面试评估的是「能否放心共事」，而坦诚说不确定正是共事最稀缺的品质：它意味着有自知之明、不会在没把握处乱来。前提是发生在真边界处而非一想就放弃；该会的扎实答、触边界时诚实给思路，才最可信。

## 思考：把「答不上来」类比成 Agent 的「置信度兜底」，这个类比对准备面试有什么实际启发？

### 回答

这个类比的实际启发是：**你应该像设计一个可靠系统那样，提前设计好自己「低置信时的默认行为」，而不是临场即兴发挥**。第 20 章里，意图路由之所以稳，是因为工程师提前写好了「置信度低于阈值就转人工」的兜底逻辑，而不是指望模型每次都判断对。同理，面试临场时人是紧张的、认知资源是紧缺的，你没有余力在被问懵的瞬间从头设计「我该怎么优雅地承认不会」——所以正确的做法是把这套兜底逻辑提前「编译」进肌肉记忆：提前想好并练熟三句模板（坦诚+思路、拆解+缩小、反问+澄清），让它们成为你「低置信时的默认动作」。这样一来，当你真的被问到盲区、大脑一片空白时，你不需要现场创作，只要触发那个练熟的默认动作就行——就像 Agent 触发兜底分支一样自动。这也解释了为什么模拟面试要「专门练被追问、被问到不会」：不是为了把盲区补全（盲区永远补不完），而是为了把「优雅兜底」这个动作练到不假思索。准备面试的高手，准备的不只是「会的部分」，更是「不会时的默认反应」。

### 面试精简表达

启发是提前设计好「低置信时的默认行为」并练成肌肉记忆，而非临场即兴。像 Agent 提前写好兜底分支一样，把三种接法练到不假思索。模拟面试要专门练被问到盲区，练的是「优雅兜底」这个动作本身。
