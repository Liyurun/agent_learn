## 真实问题

同一场招聘里，还有一位候选人 B，知识面不如候选人 A 广，却拿到了 offer。面试官事后的评价一针见血：「A 什么都懂一点，但一追问实践就空；B 会的没那么多，可他每个方案都会主动说『这么做的代价是……』『我踩过一个坑是……』，让人放心。」这句话点破了一个残酷事实：**面试官心里有一份「减分项清单」，触发任何一条，哪怕你知识再广也会被扣分**。这一节先给出 Agent 面试中最常见的红旗清单，再往下挖一层——**理解面试官「为什么」介意这些红旗，比死记清单更有用**。

## 原理：三类红旗清单，逐条自查

面试官心里那份减分清单，在 Agent 岗位上高度集中在三类。逐条自查，确保自己不踩。

**认知类红旗**：

- 把「能调 API（Application Programming Interface，应用程序编程接口）」等同于 Agent，讲不清「由模型控制工作流」这个本质；
- 认为「模型自己执行了 Function Calling 的函数」（模型只输出调用请求，真正执行的是你的代码）；
- 把 MCP（Model Context Protocol，模型上下文协议）和 Function Calling 混为一谈，分不清层次；
- 无脑认为「多 Agent 比单 Agent 高级」，答不出多 Agent 的代价。

**工程类红旗**：

- 设计的 Agent 循环没有终止条件（死循环隐患，会烧钱）；
- 完全轻信模型说「任务完成」，不做任何验证；
- 对 `run_command`、`write_file` 等高危操作毫无安全意识；
- 谈方案只讲功能，完全不提评估、可观测、护栏、成本。

**态度类红旗**：

- 「我自己试了几个例子感觉不错」——没有系统评估意识；
- 声称自己的方案「完美无缺、没有缺点」——缺乏权衡意识；
- 不懂装懂，硬编 API 名或编造数据；
- 只会背概念，一问「你实际怎么用的」就卡壳。

这些红旗的共同点是**「停留在概念、缺乏实战和批判性思维」**。避开它们的最好方式，就是真正动手做过项目（第一部分卷四、卷六），并养成「任何方案都想想代价」的习惯。

## 现象与输入：红旗背后的心理学

理解面试官「为什么」介意这些红旗，比死记清单更有用。招聘一个人本质上是在**为一段未来的合作下注**，面试官最怕的是三种人。下面这张表把「红旗—怕的类型—后果」串起来，表头用「面试官怕的类型」而非「维度」。

| 面试官怕的类型 | 对应红旗 | 一旦招进来会发生什么 |
|---|---|---|
| 「纸上谈兵」型 | 只会背概念、答不出实践 | 上手项目就卡住，需要人手把手带 |
| 「埋雷」型 | 没有终止条件/安全/成本意识 | 写出的 Agent 上线后死循环烧钱、越权操作 |
| 「听不进意见」型 | 说方案「完美无缺」、不懂装懂 | 团队协作困难，代码 review 时听不进反馈 |
| 「无评估习惯」型 | 「我试了几个例子感觉不错」 | 每次改动全凭手感，线上问题反复复发 |

看懂这张表你就明白：**避开红旗的本质，是向面试官证明「我是那个能放心一起干活、不会埋雷、听得进意见的人」**。所以哪怕你某个知识点不熟，只要展现出「有实战、懂敬畏、能自省」的特质，依然是加分的——这正是候选人 B 胜出的原因。

## 最小可运行演示

我们把红旗清单写成一个「回答体检器」：给它一段回答文本，它扫描是否命中红旗信号词，并给出对应的补救建议。这能帮你在练习时快速发现「哪句话可能踩雷」。
```python
"""第25.3节：回答红旗体检器（纯 Python，无需 API Key）。"""
from dataclasses import dataclass

## 红旗信号词 -> (类别, 补救建议)
RED_FLAGS = {
    "完美": ("态度类", "改成主动说一个代价或边界，别称方案完美"),
    "没有缺点": ("态度类", "任何方案都要能说出至少一个不适用场景"),
    "感觉不错": ("态度类", "把'感觉'换成'我用评估集回归验证过'"),
    "肯定没问题": ("态度类", "过度自信是红旗，改成'我会用数据验证'"),
    "模型自己执行": ("认知类", "模型只输出调用请求，执行的是你的代码"),
    "多Agent更高级": ("认知类", "补一句多 Agent 的代价：路由/延迟/上下文"),
    "一直循环": ("工程类", "补终止条件：最大轮次 + 兜底转人工"),
}


@dataclass
class Report:
    hits: list


def checkup(text: str) -> Report:
    hits = [(kw, cat, tip) for kw, (cat, tip) in RED_FLAGS.items() if kw in text]
    return Report(hits)


ANSWERS = {
    "踩雷版": "我这个方案很完美，没有缺点，我自己试了几个例子感觉不错，多Agent更高级。",
    "稳健版": (
        "我默认用单 Agent，代价是多领域时职责会不清；上线前我会用评估集回归验证，"
        "循环也设了最大轮次和转人工兜底。"
    ),
}


def run() -> None:
    for name, ans in ANSWERS.items():
        r = checkup(ans)
        if not r.hits:
            print(f"[{name}] 未命中红旗，稳健")
            continue
        print(f"[{name}] 命中 {len(r.hits)} 处红旗：")
        for kw, cat, tip in r.hits:
            print(f"    [{cat}] “{kw}” -> {tip}")


if __name__ == "__main__":
    run()
```
保存为 `s3_redflag.py`，运行 `python s3_redflag.py`。完整预期输出：
```text
[踩雷版] 命中 3 处红旗：
    [态度类] “完美” -> 改成主动说一个代价或边界，别称方案完美
    [态度类] “没有缺点” -> 任何方案都要能说出至少一个不适用场景
    [态度类] “感觉不错” -> 把'感觉'换成'我用评估集回归验证过'
[稳健版] 未命中红旗，稳健
```
「踩雷版」一句话踩了三处态度类红旗，体检器逐条给出改法；「稳健版」主动谈了代价、验证、兜底，全部避开。**注意**：信号词匹配只是提醒，真正的红旗判断在语义而非字面——比如你说「这个方案在我的场景里目前没发现明显问题」是稳健的，但说「这个方案完美无缺」就是红旗，字面相近而实质相反。

## 真实系统对应

**官方公开机制**：工程类红旗里的「没有终止条件」「不做验证」「无安全意识」之所以是硬伤，是因为权威工程指南把这些列为 Agent 上线的基本要求——OpenAI 的实践指南把评估、护栏、人工审批列为必备环节 [来源](https://cdn.openai.com/business-guides-and-resources/a-practical-guide-to-building-agents.pdf)，Anthropic 也强调复杂自治要用收益证明、不能无脑上多 Agent [来源](https://www.anthropic.com/engineering/building-effective-agents)。所以「无脑上多 Agent」被判红旗，不是面试官的个人偏好，而是与公开工程共识相悖。**通用工程模式**：「任何方案都想想代价、任何结论都用数据验证」是可迁移的工程习惯。**教学参考实现**：上面的体检器用信号词匹配是为可复核而构造，不代表任何面试官真实的减分判定。

一个必须澄清的边界：红旗清单是「常见减分项」的归纳，不是「命中即淘汰」的硬规则。面试官是人，会综合判断——你偶尔踩一个认知类红旗（比如一时混淆了 MCP 和 Function Calling），但整场展现出扎实实践和自省能力，未必致命；反之，全程无一处硬伤却始终停在概念层、答不出任何实践，同样拿不到高分。红旗清单的正确用法是「自查排雷」，而非「逐条对答案」。

## 生产踩坑：红旗自查表（面试前一晚过一遍）

把清单变成可打勾的自查表，面试前一晚逐条过。表头用「自查问题」而非「维度」。

| 自查问题 | 我能做到吗 |
|---|---|
| 我能用一句话说清「Agent 和 Workflow 的本质区别」吗 | 待确认 |
| 我写的 Agent 循环有终止条件和兜底吗 | 待确认 |
| 谈方案时我会主动提评估/护栏/成本吗 | 待确认 |
| 被问「实际怎么做」时，我有真实项目细节能顶上去吗 | 待确认 |
| 我能说出自己方案的至少一个缺点/边界吗 | 待确认 |
| 不确定时我会坦诚说「不确定」，而不是硬编吗 | 待确认 |
| 我能分清「模型输出调用请求」和「代码执行函数」吗 | 待确认 |
| 我能说清 MCP 和 Function Calling 分属哪个层次吗 | 待确认 |

## 思考：为什么「说方案完美无缺」比「答错一道概念题」更致命？

### 回答

因为二者暴露的问题层级完全不同：答错概念题暴露的是「知识盲区」，是可以补的、局部的；而说方案完美无缺暴露的是「思维方式缺陷」，是难改的、全局的。面试官对这两者的容忍度天差地别。知识盲区人人都有，面试官自己也不可能全懂，他看到你答错一道题，最多判断「这块你还没学到」，只要你其他地方展现出扎实基础，不影响大局；但当你说「我这方案完美无缺」时，你暴露的是「你看不到自己方案的代价、没有批判性思维」——这意味着招进来后，你写的代码可能自己觉得没问题、review 时听不进质疑、线上出了事还坚持「我的设计没错」。这种人是团队的隐患，因为工程的本质就是权衡，不存在没有代价的方案，一个看不到代价的工程师会不断制造「他自己看不见」的问题。所以哪怕你的方案确实很好，也一定要主动补一句「它的代价是……在什么场景下我就不这么做了」——这句话不会削弱你的方案，反而证明你「看得到全景」，是面试官眼里最放心的那种工程师。这与第 20 章反复强调的「输出看起来正常不是判据」是同一种批判性思维。

### 面试精简表达

答错概念题暴露的是可补的知识盲区，说方案完美暴露的是难改的思维缺陷。工程本质是权衡，看不到代价的人会不断制造自己看不见的问题。所以再好的方案也要主动补一句代价与边界。

## 思考：面试官问一个你明显不熟的领域，是想淘汰你，还是另有目的？

### 回答

大多数时候不是为了淘汰，而是在「探边界」——他想知道你的能力半径到哪里，以及更重要的，你在能力边界之外会怎么表现。一场面试的题目往往是由易到难铺开的，面试官会一直问到你答不上来为止，这几乎是必然会发生的，不是你的失败，而是他在校准「你的上限在哪」。真正被评估的，是你触到边界那一刻的反应：你是坦诚说「这块我没深入研究过，但我的思路是……」，还是硬编一个听起来像的答案糊弄过去？前者展现的是「诚实 + 推理能力」，是加分的；后者一旦被追问细节就穿帮，反而坐实了「不懂装懂」这条态度类红旗。所以遇到明显不熟的领域，正确的心态是「这是在测我的边界和诚实，不是在否定我」——把它当成展示「我如何面对未知」的机会，而不是当成必须蒙对的送命题。这也正是第 5 节「答不上来时的三种体面接法」要专门解决的问题。

### 面试精简表达

多半是探边界而非淘汰。面试会一直问到你答不上来，这是校准你的上限。真正被评估的是触到边界时的反应：坦诚说思路是加分，硬编糊弄是坐实「不懂装懂」的红旗。
