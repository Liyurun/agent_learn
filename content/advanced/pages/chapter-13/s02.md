## 真实问题

一个数据分析 Agent 接到任务：「查北京、上海、广州三城的常住人口，算出总和，判断是否超过 6000 万。」团队最初用传统的 JSON（JavaScript Object Notation，一种数据交换格式）工具调用实现，上线后发现两个问题：一是**慢且贵**——每查一个城市就要「模型→工具→模型」往返一次，三个城市三轮，最后模型还要自己把三个数加起来、比大小，又一轮，一共四轮，每轮都要重发历史，token 消耗和延迟都翻倍；二是**算错**——最后那一步「模型自己心算求和并比较」偶尔出错，2189 + 2487 + 1867 明明是 6543 万，模型有时给出 6443 万，导致「是否超过 6000 万」的结论直接反了。

问题的根子不在模型笨，而在**动作的表达方式**：JSON 工具调用把每个动作切成孤立的一次调用，既不能在一次动作里循环，也不能把确定性计算留在动作里做。这一节要讲清 smolagents 最独特的招牌——「代码即动作（Code as Action，CodeAct）」范式，为什么它能同时治好「慢、贵、算错」这三个病，以及它的代价在哪。

## 原理：两种动作表达方式的对比

smolagents 的 `CodeAgent` 最独特的地方是：它的动作不是传统的「JSON 工具调用」，而是**直接生成并执行 Python 代码片段** [来源](https://github.com/huggingface/smolagents)。官方文档明确区分了两类智能体——`CodeAgent` 以 Python 代码形式表达工具调用（默认），`ToolCallingAgent` 以 JSON 形式表达 [来源](https://huggingface.co/docs/smolagents/index)。两者的差别可以浓缩成一行对比：
```text
传统工具调用（ToolCallingAgent）：
  模型输出 JSON → {"tool": "search", "args": {"q": "北京 人口"}}
  一次动作 = 一次工具调用，组合逻辑要靠多轮往返

代码即动作（CodeAgent）：
  模型输出 Python → results = search("北京 人口"); total += parse(results)
  一次动作 = 一段可含循环/条件/组合的代码，一轮内完成多步
```
**为什么写代码更好？** 因为代码天然支持三种 JSON 单次调用做不到的能力：

- **循环**：一段动作里就能 `for` 遍历多个输入，连续调用工具，而 JSON 一次只能发一个调用。
- **条件与组合**：`if`、函数嵌套让「搜索 → 过滤 → 再基于结果计算」在一个动作里流式衔接。
- **确定性计算**：求和、比大小这种「模型容易算错」的逻辑，交给 Python 解释器精确执行，而不是让模型心算。

这三点合起来，就是「代码即动作」既省步骤、又更准的根本原因。

## 现象与输入：把「减少 30% 步骤」还原成公开研究

「代码即动作能减少步骤」不是 smolagents 的营销话术，而是有公开学术研究支撑的结论。CodeAct 论文《Executable Code Actions Elicit Better LLM Agents》系统对比了「用可执行 Python 代码作为统一动作空间」与「用 JSON/文本作为动作」的差异，结论是：代码动作在需要多工具、多轮交互的任务上成功率显著更高（论文报告在部分基准上成功率最高提升约 20 个百分点），同时完成任务所需的动作数更少 [来源](https://arxiv.org/abs/2402.01030)。smolagents 正是这一研究思路的工程化落地。

把论文的抽象结论还原成本节开头的具体任务，就能看清「步骤从哪省下来」：
```text
【传统 JSON 工具调用】需要 4 轮往返（每轮 = 一次模型调用 + 一次工具返回）
  轮1: {"tool":"search","args":{"q":"北京 常住人口"}}  → 观察: 2189万
  轮2: {"tool":"search","args":{"q":"上海 常住人口"}}  → 观察: 2487万
  轮3: {"tool":"search","args":{"q":"广州 常住人口"}}  → 观察: 1867万
  轮4: 模型自己把三数相加、比大小（易算错） → 输出结论
  合计：4 轮，历史重发 4 次，最后一步靠模型心算

【代码即动作】理想情况 1 段代码完成组合逻辑
  cities = ["北京", "上海", "广州"]
  total = sum(get_population(c) for c in cities)   # 循环内连续调用工具
  print(f"总人口 {total} 万，超过6000万？ {total > 6000}")  # 计算+判断一步到位
  合计：理想 1-2 轮，求和比较交给解释器（永不算错）
```
## 最小可运行演示：亲手对比两种范式的步骤数

下面用一段纯 Python 代码，把「JSON 往返」和「代码即动作」两种范式的步骤数、以及「谁来做最后的求和比较」直观对比出来。它不联网、不需要 API（Application Programming Interface，应用程序编程接口）Key，用固定假数据让输出可逐字复核。
```python
"""对比 JSON 工具调用 vs 代码即动作 的步骤数与计算可靠性（纯 Python，无需 API Key）。"""

## 固定假数据：真实项目里这里是联网搜索的返回
POPULATION = {"北京": 2189, "上海": 2487, "广州": 1867}  # 单位：万


def search_population(city: str) -> int:
    return POPULATION[city]


def json_style() -> tuple[int, int]:
    """模拟传统 JSON 工具调用：每城一轮往返，最后模型心算求和。"""
    rounds = 0
    observed = []
    for city in POPULATION:
        rounds += 1                       ## 每次工具调用算一轮往返
        observed.append(search_population(city))
    rounds += 1                           ## 最后模型「心算」求和比较，再一轮
    model_sum = sum(observed)             ## 教学里用真值代替；真实模型此处可能算错
    return rounds, model_sum


def code_action() -> tuple[int, int]:
    """模拟代码即动作：一段代码内循环调用 + 解释器精确计算。"""
    rounds = 1                            ## 一段代码搞定组合逻辑
    total = sum(search_population(c) for c in POPULATION)  ## 解释器求和，永不算错
    over = total > 6000
    print(f"    [代码内] 总人口 {total} 万，超过6000万？ {over}")
    return rounds, total


def run() -> None:
    j_rounds, j_sum = json_style()
    print(f"JSON 工具调用：{j_rounds} 轮往返，求和={j_sum}（最后一步靠模型心算，可能出错）")
    c_rounds, c_sum = code_action()
    print(f"代码即动作：  {c_rounds} 轮，求和={c_sum}（解释器精确计算）")
    print(f"步骤减少：{j_rounds} → {c_rounds} 轮，省下 {j_rounds - c_rounds} 轮往返")


if __name__ == "__main__":
    run()
```
保存为 `paradigm_compare.py`，运行 `python paradigm_compare.py`。完整预期输出：
```text
JSON 工具调用：4 轮往返，求和=6543（最后一步靠模型心算，可能出错）
    [代码内] 总人口 6543 万，超过6000万？ True
代码即动作：  1 轮，求和=6543（解释器精确计算）
步骤减少：4 → 1 轮，省下 3 轮往返
```
逐行看结论：`[代码内]` 那行来自 `code_action` 内部的 `print`（代码动作把「计算 + 判断」写在了动作里），随后主流程打印汇总。JSON 方式 4 轮往返，且最后一步的求和在真实模型里可能出错；代码方式 1 轮，且 `6543` 是 Python 解释器算的，永远精确。**这就是代码即动作的双重收益：步骤更少（省 token 和延迟）、计算更准（把确定性运算从不可靠的模型脑子挪进可靠的解释器）。**

## 真实系统对应

**官方公开机制**：smolagents 官方明确 `CodeAgent` 以 Python 代码表达动作、`ToolCallingAgent` 以 JSON 表达，且 `CodeAgent` 是默认选择 [来源](https://github.com/huggingface/smolagents) [来源](https://huggingface.co/docs/smolagents/index)。**学术依据**：CodeAct 论文用 17 个大语言模型（Large Language Model，LLM）在 API-Bank 与自建基准上做对比，报告代码动作在多工具多轮任务上成功率更高、动作数更少 [来源](https://arxiv.org/abs/2402.01030)——这是「减少约 30% 步骤」这类说法的原始出处，请以论文原文的具体数字与实验设定为准，不同基准结论强弱不同。**通用工程模式**：把「组合逻辑（循环/条件/计算）尽量收进一个动作」是可迁移到任何框架的优化思路。**教学参考实现**：上面的 `paradigm_compare.py` 用固定假数据模拟两种范式的步骤差异，`json_style` 里用真值代替「模型心算」只为演示，真实模型的心算恰恰是不可靠的那一环。

需要点明边界：代码即动作并非在所有任务上都赢。同一批研究也显示，在「原子的、单工具的调用」任务上，代码动作相比 JSON 的优势会缩小甚至不明显——它的红利集中在「多工具 + 多轮 + 需要组合计算」的场景 [来源](https://arxiv.org/abs/2402.01030)。这解释了为什么 smolagents 既主推 CodeAgent，又保留 ToolCallingAgent：范式要匹配任务，不是「代码永远更好」。

## 生产踩坑

| 症状 | 根因 | 如何观测与复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| 简单单工具任务用 CodeAgent 反而更绕 | 误以为代码动作永远更优 | 用单次结构化抽取任务对比两种范式 | 原子任务改用 ToolCallingAgent / 结构化输出 | 多工具组合任务代码动作仍占优 |
| 最后一步求和/比较结果出错 | 把确定性计算留给模型心算 | 让模型手算多位数求和复现偶发错误 | 把计算写进代码交给解释器 | 无需数值计算的任务不涉及 |
| 步骤数居高不下、token 烧得快 | 组合逻辑被拆成多轮 JSON 往返 | 统计每任务平均轮次与 input token | 把循环/条件收进一个代码动作 | 短对话或单步任务影响可忽略 |
| 弱模型下 CodeAgent 频繁失败 | 代码动作对模型代码生成能力要求高 | 用能力差的模型跑代码任务看失败率 | 换更强模型后端或降低代码复杂度 | 强模型下问题很少出现 |
| 下游系统难解析代码动作的产物 | 代码输出不如 JSON 规整 | 让下游按固定字段解析代码 print | 需结构化产物时改用结构化输出 | 产物只给人看时无所谓 |

## 思考：「代码即动作」相比 JSON 工具调用的核心优势是什么？为什么能减少步骤？

### 回答

核心优势有两个，都源于「动作的表达方式从孤立调用变成了可执行代码」。第一是**减少步骤**：代码天然支持循环、条件和函数组合，所以「搜索多个数据 → 过滤 → 计算 → 判断」这一串组合逻辑可以写进一段代码、在一轮里完成，而 JSON 工具调用一次只能发一个调用，同样的组合要好几轮「模型→工具→模型」往返。步骤少了，直接省 token 和延迟，更重要的是每减少一次往返就少一次复合错误累积的机会（第 3 章）。第二是**计算更准**：求和、比大小这类确定性运算，代码即动作会交给 Python 解释器精确执行，而 JSON 方式往往要模型自己心算，多位数运算容易出错。把确定性计算从不可靠的模型脑子挪进可靠的解释器，是这个范式的隐藏红利。需要补一句边界：这些优势集中在「多工具 + 多轮 + 需组合计算」的任务上；单工具原子任务里，代码动作相比 JSON 的优势会缩小，所以 smolagents 也保留了 ToolCallingAgent，范式要匹配场景。

### 面试精简表达

代码动作能把循环、条件、计算写进一段代码一轮完成，比 JSON 的多轮往返省步骤；且把求和比较等确定性计算交给解释器，比模型心算更准。红利集中在多工具多轮组合任务，单工具原子任务优势会缩小。

## 深入：代码即动作的代价——不是免费的午餐

任何设计都有代价，必须诚实地把代码即动作的短板列清楚，否则你会误以为「全都该用它」：

| 优势 | 对应代价 |
|---|---|
| 表达力最强（循环 / 条件 / 组合） | 要执行不可信代码，必须上沙箱（第 5 节），安全责任推给了你 |
| 步骤少、复合错误低 | 一段代码里出错时调试粒度更粗（一整段一起失败，不好定位是哪一行） |
| 确定性计算交给解释器，更准 | 对模型的代码生成能力要求更高，弱模型容易写出跑不了的代码 |
| 透明、可读 | 结构化程度不如 JSON，下游系统解析没那么规整 |

**结论**：代码即动作在「代码密集 / 需要组合计算」的任务上优势巨大，但它把安全责任推给了你（沙箱），也对模型能力提出了更高要求。这解释了为什么它是绝佳教具与原型工具，但生产上你常常需要权衡是否引入更结构化的方案。这也呼应第 12 章的核心结论——**范式没有绝对优劣，只有场景匹配**。

一个常见误区值得钉死：**以为「代码即动作」就等于「更好，全都该用它」。** 不对。如果你的任务只需要一次简单的结构化输出（比如把一段文本抽成固定字段），JSON 工具调用或 PydanticAI 的结构化输出（第 14 章）反而更简洁、更安全。判断标准很简单：任务是否需要「在一次动作里做组合逻辑」——需要，代码即动作发光；不需要，结构化输出更省心。
