## 真实问题

本章开头「删库惊魂」结案后，团队想把整章教训沉淀成一份能防复发、也能应付面试追问的清单，却发现难点不在「知道要用沙箱」，而在**报障太模糊**。线上只有一句「smolagents 做的分析 Agent 又不稳定了」，无法行动：根因可能在执行安全（不可信代码跑在本地执行器）、工具定义（描述含糊模型不调）、循环控制（无限重试烧 token）、范式选择（单工具原子任务硬用 CodeAgent）、模型能力（弱模型写不出合法代码）任意一层。把一句模糊报障拆成可定位的层，再给每层配上「症状—根因—观测—修复—边界」，才是这份清单的价值。

这一节做两件事：先给出一张覆盖 smolagents 端到端各层的生产建议矩阵与一个可运行的分层诊断器；再用多道「思考 + 回答」把全章方法论收口，直接对齐与 smolagents、代码即动作（Code as Action，CodeAct）相关的高频面试题。

## 诊断顺序：先分层，再归因

遇到「CodeAgent 又出错了」，不要先归结为「模型不行」，而是按数据流分层排查，每层都有可观测证据：

1. **复现**：固定模型标识、温度、工具集快照、`executor_type`、`max_steps` 与输入。不能复现就先把这些变量钉死。
2. **安全层**：是否有不可信输入（用户上传、联网抓取的内容）流进了 `LocalPythonExecutor`。这是最高优先级——它不是安全边界（第 5 节）。
3. **工具层**：模型是否不肯调你的工具、或老传错参数。观测工具调用率与参数非法率，回看 docstring 与类型标注（第 4 节）。
4. **范式层**：任务是「多工具 + 多轮 + 需组合计算」还是「单工具原子调用」。前者 CodeAgent 占优，后者 ToolCallingAgent 更省心（第 2 节）。
5. **循环层**：是否频繁触顶 `max_steps`、是否有重试风暴。观测平均步数与触顶率（第 3 节）。
6. **执行层**：代码报错率是否偏高。高报错率常是弱模型写不出合法代码，或工具报错文案太笼统模型无法自愈（第 6 节）。
7. **对照**：同一输入用确定性假模型多次运行的结果，与真实模型的多变表现比较，分清「结构问题」还是「模型问题」。

## 生产建议：smolagents 端到端症状矩阵

下面把全章各层的坑汇成一张矩阵，每行都是一个真实会发生、可观测、有修复、也有不适用边界的条目。它是这份清单的主体。

| 症状 | 根因 | 如何观测与复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| 不可信代码删了本地文件/读到密钥 | 误以为 LocalPythonExecutor 是沙箱 | 喂含 shutil.rmtree 的注入文本复现 | 切 executor_type 到 e2b/docker/wasm | 学习期跑完全可信代码风险较低 |
| 以为 AST 白名单等于绝对安全 | 把「尽力缓解」当「安全边界」 | 查官方 not a security boundary 声明 | 不可信代码一律进隔离运行时 | 可信内部代码白名单确有价值 |
| 沙箱开了仍被提示注入牵着走 | 只做执行隔离没做注入防护 | 注入文本操纵业务逻辑而非删文件 | 沙箱 + 注入防护 + 最小权限叠加 | 完全可信输入注入风险低 |
| 沙箱内代码联网偷传数据 | 沙箱未设网络白名单 | 让代码 curl 外部地址复现外联 | 沙箱内限制出网、白名单域名 | 任务本需联网时精细放行 |
| 模型不肯调我的工具 | docstring 含糊、函数名不表意 | 把描述写模糊再写清晰对比调用率 | 动词开头写清用途，名字见名知义 | 工具本不适用该任务时另说 |
| 模型老是传错参数 | 参数无类型标注或无说明 | 去掉类型标注复现传参错误 | 每参标具体类型 + 写含义与示例 | 无参数工具不涉及 |
| 手动改 name/description 不生效 | 这两项只读、自动从函数名/docstring 填 | 尝试手动赋值观察被覆盖 | 通过改函数名和 docstring 控制 | 用 Tool 子类时可显式定义 |
| 简单单工具任务用 CodeAgent 反而绕 | 误以为代码动作永远更优 | 用单次抽取任务对比两种范式 | 原子任务改用 ToolCallingAgent | 多工具组合任务代码动作占优 |
| 最后一步求和/比较结果出错 | 把确定性计算留给模型心算 | 让模型手算多位数求和复现偶错 | 把计算写进代码交给解释器 | 无需数值计算的任务不涉及 |
| 循环永不终止、token 烧光 | 只靠 final_answer 无步数上限 | 提模型答不出会反复试的问题复现 | 设 max_steps 兜底 + 提示强调 final_answer | 明确单步任务影响有限 |
| 一次工具名笔误让整个 Agent 崩溃 | 执行异常未捕获成 Observation | 故意写错工具名看是否抛出主循环 | 每次执行 try 捕获转 is_error 回填 | 致命错误确需整体中止时例外 |
| 模型拿到报错却不纠错反复重试 | 报错文案太笼统模型读不懂 | 把报错改成「出错了」复现空转 | 回填具体异常类型与信息 | 模型能力上限仍需换后端 |
| 换个弱模型就跑不出合法代码 | 代码动作对模型能力要求高 | 用能力差的模型跑代码任务复现 | 换更强后端或降低代码复杂度 | 结构化任务可改 ToolCallingAgent |
| 把 smolagents 当生产终点难维护 | 忽视其定位是理解与原型工具 | 拿它做类型安全结构化输出很别扭 | 结构化交 PydanticAI、状态机交 LangGraph | 代码密集原型任务它本就够用 |
| 接 MCP 工具后行为不可控 | 引入的第三方工具描述/权限未审计 | 记录 MCP 工具候选与实际调用分布 | 审计工具描述与权限、最小暴露 | 完全可信内部工具风险较低 |
| GAIA 复现分数与官方对不上 | 模型/版本/工具集与官方不一致 | 固定模型与工具集再比对 | 以官方当前公布的设定为准复现 | 只做能力演示不追求刷分时 |
| 每轮 input token 线性膨胀 | 工具说明与历史每轮重发 | 统计各轮 input token 增长 | 精简工具集、压缩历史 | 短对话影响可忽略 |
| 日志里出现密钥明文 | 密钥进了执行环境或被 print | 在环境变量放假密钥看是否可读 | 密钥不进执行环境、用短期令牌 | 沙箱内确需凭证走最小权限 |

TTL（Time To Live，生存时间）适用于可过期的缓存与偏好，不应用于删除法律保留或未完成事务。PII（Personally Identifiable Information，个人可识别信息）在写入日志与追踪前应最小化与脱敏——尤其当 CodeAgent 会把中间结果 `print` 到 Observation 时，更要防止敏感数据顺着日志外泄。

## 最小可运行演示：smolagents 分层诊断器

把上面的诊断顺序固化成一个规则树，输入一组指标，输出首要嫌疑层，避免「一切归结为模型不行」。
```python
"""smolagents 生产分层诊断器（纯 Python，无需 API Key）：
把『CodeAgent 又出问题了』这句模糊报障，拆到可行动的层。"""
from __future__ import annotations


def diagnose(m: dict) -> list[str]:
    findings = []
    if m["untrusted_code_on_local_executor"]:
        findings.append("安全层：不可信代码跑在 LocalPythonExecutor，切 executor_type 到隔离沙箱")
    if m["tool_call_rate"] < 0.5:
        findings.append("工具层：模型不肯调工具，检查 docstring 与类型标注是否清晰")
    if m["avg_steps"] >= m["max_steps"]:
        findings.append("循环层：频繁触顶 max_steps，检查 final_answer 引导与重试风暴")
    if m["code_exec_error_rate"] > 0.3:
        findings.append("执行层：代码报错率过高，可能是弱模型写不出合法代码，换更强后端")
    if m["single_tool_atomic_task"] and m["agent_type"] == "CodeAgent":
        findings.append("范式层：单工具原子任务用 CodeAgent 偏重，考虑 ToolCallingAgent")
    return findings or ["指标正常，用固定输入 + 假模型做回归对照"]


def run() -> None:
    metrics = {
        "untrusted_code_on_local_executor": True,
        "tool_call_rate": 0.3,
        "avg_steps": 6,
        "max_steps": 6,
        "code_exec_error_rate": 0.4,
        "single_tool_atomic_task": True,
        "agent_type": "CodeAgent",
    }
    for line in diagnose(metrics):
        print(line)


if __name__ == "__main__":
    run()
```
保存为 `smol_diagnose.py`，运行 `python smol_diagnose.py`。完整预期输出：
```text
安全层：不可信代码跑在 LocalPythonExecutor，切 executor_type 到隔离沙箱
工具层：模型不肯调工具，检查 docstring 与类型标注是否清晰
循环层：频繁触顶 max_steps，检查 final_answer 引导与重试风暴
执行层：代码报错率过高，可能是弱模型写不出合法代码，换更强后端
范式层：单工具原子任务用 CodeAgent 偏重，考虑 ToolCallingAgent
```
这个诊断器的价值不在规则本身，而在**它把「Agent 不稳定」这句无法行动的话，翻译成了五条各自有修复动作的诊断**。真实项目里把这些布尔/比率指标接上你的观测数据，就能在报障时先自动定位到嫌疑层，而不是从「是不是模型不行」开始漫无边际地猜。

## 真实系统对应

**官方公开机制**：smolagents 官方提供 `CodeAgent` / `ToolCallingAgent` 两类智能体、`@tool` 与 `Tool` 子类、`executor_type` 切换隔离执行器、`WebSearchTool` 等内置工具，并支持通过 `ToolCollection` 从 MCP（Model Context Protocol，模型上下文协议）服务器接入外部工具集，把第三方能力当作可调用工具暴露给 Agent [来源](https://huggingface.co/docs/smolagents/index) [来源](https://github.com/huggingface/smolagents)。官方还提供命令行入口 `smolagent`（如 `smolagent "Plan a trip..." --tools web_search`）用于快速试跑 [来源](https://github.com/huggingface/smolagents)。基于 smolagents 的开源智能体曾在 GAIA（General AI Assistants，通用 AI 助手基准）验证集取得开源领先成绩，具体分数随模型与版本变化，以官方当前公布为准 [来源](https://huggingface.co/docs/smolagents/index)。**通用工程模式**：分层诊断、按威胁模型选隔离粒度、把工具描述当提示词精心撰写、确定性计算交给解释器——都是可迁移到任何框架的原则。**教学参考实现**：上面的 `smol_diagnose.py` 是本书构造的规则树，指标名与阈值仅为演示，不代表任何产品的内置诊断。

需要点明边界：接入 MCP 工具会引入第三方的工具描述与权限，等于把外部代码的「说明书」直接拼进你的系统提示——务必审计工具描述、限制权限、最小暴露，这与第 8 章「工具结果里的指令可能被当命令执行」的注入风险一脉相承。GAIA 分数、`executor_type` 可选值、CLI（Command-Line Interface，命令行界面）子命令等会随版本变化，本节讲稳定的方法论，不把某次检索到的数值写成永久承诺。

## 事故回放：从「删库惊魂」到一张分层清单

把本章贯穿的「删库惊魂」完整回放一遍，正好串起矩阵里的多层：

1. **触发**：工程师用默认 `LocalPythonExecutor` 处理「用户上传文档」，文档里藏了 `import shutil; shutil.rmtree(...)` 的提示注入（第 5 节安全层）。
2. **放大**：他没设 `max_steps`，如果模型陷入循环还会持续烧 token（第 3 节循环层）。
3. **误判**：出问题后第一反应是「模型被越狱了、换个模型」，方向全错——真正的处置权在运行时的 `executor_type`，不在模型自觉（第 5、8 章）。
4. **收口**：正确修复是三层叠加——切隔离执行器（安全层）+ 设 `max_steps`（循环层）+ 对不可信输入做注入防护（护栏层），而不是指望模型不生成坏代码。

这条回放的价值在于示范**分层归因**：同一起事故，症状是「删文件」，但可定位到安全层、循环层、认知层三个不同的根因，每个根因都有独立的修复。把事故拆成这样，才能防复发，而不是留下一句「smolagents 有点危险」的模糊印象。

## 生产建议：把 smolagents 学到的原理迁移到重型框架

smolagents 的定位是「理解工具 + 原型工具」，生产上你常会把它教会你的原理，迁移到更工程化的框架。这张迁移表把「smolagents 里学到的东西」对应到「生产框架里的落点」：

| smolagents 学到的原理 | 生产框架里的落点 | 迁移要点 |
|---|---|---|
| ReAct 循环 = 调模型→执行→回填→判终止 | 任何框架的 Agent 主循环 | 骨架不变，换的是模型后端与执行器 |
| 代码即动作省步骤但需沙箱 | LangGraph 节点内的工具编排 | 组合计算收进一步，安全落运行时 |
| 工具描述即提示词 | OpenAI/Anthropic/MCP 工具 schema | 描述写清「何时用、参数含义」通用 |
| LocalPythonExecutor 不是沙箱 | 生产统一用隔离执行环境 | 不可信代码永远进 E2B/Docker/Wasm |
| max_steps 兜底防死循环 | 生产循环的硬上限 + 预算护栏 | 终止条件必须有，且要有降级 |
| 确定性计算交给解释器 | 数值/校验交代码而非模型 | 把易错的心算挪出模型脑子 |

**一句话总结迁移逻辑**：smolagents 像化学课的透明烧杯，让你看清反应；生产是工业级密闭反应釜，但你对反应的理解正是从透明烧杯里来的。

## 思考：smolagents 用在生产环境，最需要警惕的三件事是什么？

### 回答

第一是**执行安全**：默认的 `LocalPythonExecutor` 不是沙箱，只要有不可信输入（用户上传、联网抓取的内容）可能流进代码执行，就必须切到 E2B / Docker / Wasm 隔离执行器，并叠加最小权限、网络白名单、资源限额——安全阀门握在运行时（`executor_type`），不能指望模型自觉。第二是**循环成本**：必须设 `max_steps` 兜底，防止模型陷入无限重试把 token 预算烧光，并对触顶做降级处理。第三是**定位边界**：smolagents 是绝佳的理解与原型工具，但类型安全的结构化输出该交给 PydanticAI（第 14 章）、复杂长时状态机该交给 LangGraph（第 15 章），别把它硬用在不擅长的场景。这三件事对应安全、成本、架构三个维度，是把 smolagents 从「玩具」用成「可靠工具」的分水岭。

### 面试精简表达

三件事：①执行安全（LocalPythonExecutor 不是沙箱，不可信代码切 executor_type 到隔离环境 + 最小权限）②循环成本（设 max_steps 兜底防烧 token）③定位边界（结构化交 PydanticAI、状态机交 LangGraph，别硬用）。

## 思考：面试官问「CodeAgent 和 ToolCallingAgent 怎么选」，怎么答出层次？

### 回答

要答出「按任务特征选，而非按谁更先进选」的层次。`CodeAgent` 以 Python 代码表达动作（smolagents 默认），它的红利集中在**多工具、多轮、需要组合计算**的任务：一段代码里能循环调用工具、做条件判断、把确定性计算交给解释器，省步骤又更准（第 2 节，有 CodeAct 论文支撑）。`ToolCallingAgent` 以 JSON（JavaScript Object Notation，一种数据交换格式）表达动作，它在**单工具、原子、需要规整结构化产物**的任务上更简洁——不必为一次简单调用承担「执行代码」的安全成本，下游解析也更规整。判断标准一句话：任务是否需要「在一次动作里做组合逻辑」——需要，选 CodeAgent；不需要，选 ToolCallingAgent。更进一步，还要提醒代码动作把安全责任推给了你（必须上沙箱），这也是选型时的隐性成本。能从「任务特征 + 各自红利 + 隐性成本」三层回答，就比只会说「CodeAgent 更先进」的人高出一截。

### 面试精简表达

按任务选：多工具/多轮/需组合计算选 CodeAgent（省步骤、计算准，但要沙箱）；单工具/原子/需规整结构化产物选 ToolCallingAgent。标准是「是否需要在一次动作里做组合逻辑」。

## 思考：为什么说「LocalPythonExecutor 有 AST 白名单」不能作为「可以跑不可信代码」的理由？

### 回答

因为「做了防护」和「是安全边界」是两回事。`LocalPythonExecutor` 确实比裸 `exec` 安全——它把代码解析成 AST（Abstract Syntax Tree，抽象语法树）逐节点求值、对导入做白名单、对操作次数设上限，能挡掉一部分明显危险的操作。但官方明确它只提供「尽力而为的缓解（best-effort mitigations）」、「不是一个安全边界（not a security boundary）」。根本原因是它终究运行在你的本地进程里，与你的文件系统、环境变量（含密钥）、内网访问共享同一个信任域；AST 白名单只能拦「已知的坏模式」，而攻击面无法穷举，一旦被绕过，损害直接落在宿主。所以正确的心智是：白名单是为「减少可信代码的误操作」设计的，不是为「抵御刻意构造的不可信代码」设计的。只要代码可能触及不可信输入，就一律进真正隔离的执行器，绝不能拿「它恰好挡住了这一个」当安全依据。

### 面试精简表达

AST 白名单是「尽力缓解」不是「安全边界」（官方明说），因为它和你的文件/密钥/内网共享信任域、攻击面无法穷举；白名单为「防误操作」设计，不为「防不可信代码」设计。不可信代码一律进隔离执行器。

## 思考：smolagents 通过 MCP 接入外部工具，需要注意什么？

### 回答

smolagents 支持用 `ToolCollection` 从 MCP（Model Context Protocol，模型上下文协议）服务器接入外部工具集，把第三方能力（如网页抓取、搜索、数据库）当作可调用工具暴露给 Agent。方便之外，有三点必须警惕。第一是**信任边界**：MCP 工具的名称、描述会像自定义工具一样被拼进系统提示（第 4 节「描述即提示词」），等于把外部方写的「说明书」直接放进了你的上下文，若描述里夹带诱导性文字，就构成提示注入风险（呼应第 8 章「工具结果里的指令可能被当命令执行」）。第二是**权限最小化**：只暴露任务真正需要的工具，别把一个大而全的工具集全量接入，减少攻击面与误调用。第三是**执行隔离仍不可少**：MCP 提供的是工具能力，不改变「模型生成的代码要在执行器里跑」这一事实，不可信场景该上的沙箱一个都不能少。一句话：MCP 让「接外部工具」变简单，但信任、权限、隔离三道关口不能因为「官方支持」就省掉。

### 面试精简表达

MCP（模型上下文协议）经 ToolCollection 接入外部工具很方便，但要守三关：①信任边界（工具描述会进提示，防注入）②权限最小化（只暴露需要的工具）③执行隔离照旧（沙箱不能省）。

## 深入：把「透明玻璃」的价值用到底

全章走到这里，回头看 smolagents 最独特的价值，其实不是「约 1000 行内核」这个数字，也不是「代码即动作」这个范式本身，而是它把一个 Agent 循环变成了**一块你能看进去的透明玻璃**。第 1 节的透明内核让你敢读源码，第 2 节的代码即动作让你看清动作的真实形态，第 3 节的逐帧循环让 ReAct 从名词变成画面，第 4 节让你明白工具描述就是提示词，第 5 节让你记住执行器不是沙箱，第 6 节让你亲手把这一切接成一个能跑的闭环。

这块透明玻璃的终极价值，是让你在学后面任何重型框架时都有「原来如此」的通透感——当 LangGraph 让你定义节点和边，你知道那背后还是「调模型→执行→回填→判终止」的循环；当 PydanticAI 让你声明 `output_type`，你知道那是把「结构化产物」这件事从 CodeAgent 的自由代码里收紧成类型契约；当你在生产里排查一个 Agent 故障，你会本能地分层归因，而不是笼统地说「模型不行」。**smolagents 教给你的从来不是它自己，而是透过它看清的 Agent 本质——这才是把它放在动手第一站的全部理由。**
