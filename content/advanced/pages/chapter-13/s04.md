## 真实问题

一个团队给客服 Agent 写了个查订单的工具，函数逻辑完全正确，本地单测也过了，可上线后模型「就是不肯用它」——用户问「我的订单到哪了」，模型要么自己瞎编一个物流状态，要么反问用户一堆本可以查到的信息。工程师排查了三天，怀疑是模型太弱、怀疑是框架 Bug、甚至重训了提示词，都没用。最后一位老同事扫了一眼工具定义，只说了一句话：「你这个函数叫 `q`，docstring 写的是『查东西』，参数叫 `x`——模型怎么知道它是查订单的？」改成 `get_order_status`、把 docstring 写清「根据订单号查询物流状态」、参数改成 `order_id: str`，模型立刻就会用了。

这个故事戳中一个新手最常忽视、也最反直觉的事实：**在 smolagents 里，工具的名字、docstring 和类型标注不是「给人看的注释」，而是会实打实进入模型上下文的「提示词（Prompt）的一部分」。** 写工具不只是写函数逻辑，更是在「为模型写一份说明书」。这一节要把这件事钉死。

## 原理：@tool 装饰器把函数变成模型能读的说明书

除了内置的 `WebSearchTool`，smolagents 用 `@tool` 装饰器把一个普通函数变成工具。官方文档明确：工具的名字、描述（来自 docstring）、参数说明都会**自动被注入 Agent 的系统提示（system prompt）**，所以「要尽量写清楚」[来源](https://huggingface.co/docs/smolagents/guided_tour)。看一个完整例子：
```python
from smolagents import CodeAgent, tool, InferenceClientModel

@tool
def get_exchange_rate(base: str, target: str) -> float:
    """查询两种货币之间的实时汇率，返回 1 单位 base 可兑换的 target 数量。

    Args:
        base: 基准货币的三字母代码，例如 'USD'
        target: 目标货币的三字母代码，例如 'CNY'
    """
    # 真实实现应调用汇率 API；这里用假数据演示
    fake_rates = {("USD", "CNY"): 7.1}
    return fake_rates.get((base, target), 0.0)

agent = CodeAgent(tools=[get_exchange_rate], model=InferenceClientModel())
agent.run("100 美元大约能换多少人民币？")
```
把这段代码的每一部分，对应到第 6 章「工具三要素」（名称 + 描述 + 参数 Schema）：
```python
@tool                                   # ① 装饰器：把普通函数登记成 Agent 可调用的工具
def get_exchange_rate(base: str,        # ② 参数类型标注 str → 自动生成参数 Schema
                      target: str) -> float:  # ③ 返回类型 → 告诉模型工具产出什么
    """查询两种货币之间的实时汇率。        # ④ docstring 首行 = 工具"做什么"的描述
    Args:
        base: 基准货币代码，例如 'USD'    # ⑤ 每个参数的说明 = 参数"是什么"
        target: 目标货币代码，例如 'CNY'
    """
    fake_rates = {("USD", "CNY"): 7.1}   # ⑥ 函数体 = 工具的真实实现（运行时处置）
    return fake_rates.get((base, target), 0.0)
```
逐点讲解，每一点都对应模型「用得对不对」的一个因素：

- **① `@tool`**：这行装饰器是「魔法」发生的地方。它读取函数签名和 docstring，自动生成一份工具描述（名称 + 说明 + 参数 Schema），组装 prompt 时告诉模型「你有这么一个工具可用」。官方特别提醒：工具的 `name` 和 `description` 是只读的、从函数名和 docstring 首行自动填充，不要手动去设 [来源](https://huggingface.co/docs/smolagents/guided_tour)。
- **② 参数类型标注**：`base: str` 不是给人看的注释，它会被转成参数 Schema 里的类型约束。类型提示要用具体类型（`str`、`int`、`float`、`list[str]`），避免 `Any` 或不标类型，否则模型对参数的理解会变模糊 [来源](https://huggingface.co/docs/smolagents/guided_tour)。
- **④ docstring 首行**：这是模型判断「什么时候该调这个工具」的最主要依据。写得含糊（比如只写「汇率」），模型就容易漏用或误用。
- **⑥ 函数体**：这是工具真正干活的地方，也是第 8 章「运行时处置」的落点。示例用假数据，真实项目里这里会去调外部汇率 API。

**焊死一个认知：工具描述（名称 + docstring + 类型）就是 prompt 的一部分，会实打实进入模型的上下文。** 所以「写工具」不只是写函数逻辑，更是在「为模型写说明书」——说明书写不好，再强的模型也用不对你的工具。

## 现象与输入：docstring 如何变成模型看到的文本

为了让「docstring 进 prompt」这件事从抽象变具体，把 `@tool` 装饰器对上面函数的「加工结果」摊开看——它大致会生成这样一份结构化描述，塞进系统提示里给模型读：
```text
（模型在系统提示里实际「看到」的工具说明，示意）
可用工具：
- name: get_exchange_rate
  description: 查询两种货币之间的实时汇率，返回 1 单位 base 可兑换的 target 数量。
  arguments:
      base   (string): 基准货币的三字母代码，例如 'USD'
      target (string): 目标货币的三字母代码，例如 'CNY'
  returns: float
```
对照就能明白：你在 Python 里写的每一个字段，都变成了模型上下文里的一行说明。**模型不是「看你的函数体」来决定怎么调工具的——它看的是这份从签名和 docstring 生成的说明书。** 函数体它根本看不见（那是运行时执行的），它能依据的只有名称、描述、参数说明和类型。这就是为什么「函数逻辑对、模型却不会用」的怪事会发生：逻辑对，但说明书没写好。

## 最小可运行演示：亲眼看到「工具描述」被生成出来

真实 `@tool` 依赖安装 smolagents。为了让你无依赖地看清「装饰器从函数生成了什么描述」，下面用纯标准库（`inspect` + `typing`）复刻这个「抽取工具描述」的过程，把一个函数变成模型能读的说明书，并对比「好描述」和「坏描述」生成结果的差异。
```python
"""复刻 @tool 装饰器的『抽取工具描述』过程（纯标准库，无需安装 smolagents）。
说明它如何从函数名、类型标注、docstring 生成一份『给模型看的说明书』。"""
import inspect
from typing import get_type_hints


def build_tool_spec(fn) -> dict:
    """模拟 smolagents @tool：从函数抽取 name / description / 参数类型。"""
    hints = get_type_hints(fn)
    doc = inspect.getdoc(fn) or ""
    description = doc.splitlines()[0] if doc else "(无描述)"     ## docstring 首行=描述
    params = {}
    for name in inspect.signature(fn).parameters:
        t = hints.get(name, "未标注")                            ## 类型标注→参数 Schema
        params[name] = getattr(t, "__name__", str(t))
    return {"name": fn.__name__, "description": description,
            "params": params,
            "returns": getattr(hints.get("return"), "__name__", "未标注")}


## 反例：名字含糊、无类型、无描述
def q(a, b):
    """汇率"""
    ...


## 正例：动词开头讲清用途、有类型、docstring 首行清晰
def get_exchange_rate(base: str, target: str) -> float:
    """查询两种货币之间的实时汇率，返回 1 单位 base 可兑换的 target 数量。"""
    ...


def show(fn) -> None:
    spec = build_tool_spec(fn)
    print(f"工具名: {spec['name']}")
    print(f"  描述: {spec['description']}")
    print(f"  参数: {spec['params']}")
    print(f"  返回: {spec['returns']}")


def run() -> None:
    print("=== 反例（模型难判断何时用、参数怎么传）===")
    show(q)
    print("=== 正例（模型能准确判断与传参）===")
    show(get_exchange_rate)


if __name__ == "__main__":
    run()
```
保存为 `tool_spec.py`，运行 `python tool_spec.py`。完整预期输出：
```text
=== 反例（模型难判断何时用、参数怎么传）===
工具名: q
  描述: 汇率
  参数: {'a': '未标注', 'b': '未标注'}
  返回: 未标注
=== 正例（模型能准确判断与传参）===
工具名: get_exchange_rate
  描述: 查询两种货币之间的实时汇率，返回 1 单位 base 可兑换的 target 数量。
  参数: {'base': 'str', 'target': 'str'}
  返回: float
```
把两份输出并排看，你就明白模型的困境：面对反例，它只知道有个叫 `q` 的工具、描述是「汇率」、有两个不知类型不知含义的参数 `a`、`b`——它既难判断「用户问汇率时该不该调它」，更不知道该往 `a`、`b` 里传什么。面对正例，名称、用途、参数含义、类型、返回一目了然，模型自然用得准。**这就是「工具描述即提示词」的实证：同一个功能，说明书写得好坏，直接决定模型能不能用对。**

## 真实系统对应

**官方公开机制**：smolagents 官方 Guided tour 明确 `@tool` 装饰的函数，其名称、描述（docstring）、参数说明会被自动注入 Agent 的系统提示，并建议「description 是给驱动 Agent 的 LLM 的使用手册，务必写清」、「类型提示要用具体类型」；`name` 与 `description` 只读、自动填充，不应手动设置 [来源](https://huggingface.co/docs/smolagents/guided_tour)。smolagents 也支持用 `Tool` 子类（定义 `name`、`description`、`inputs`、`output_type`、`forward`）来获得更多控制，等价于装饰器的展开形式 [来源](https://huggingface.co/docs/smolagents/index)。**通用工程模式**：把「工具描述当成 prompt 的一部分来精心撰写」是可迁移到任何框架（OpenAI/Anthropic 的函数定义、MCP 工具 schema）的通用原则。**教学参考实现**：上面的 `build_tool_spec` 用 `inspect` 复刻抽取过程，是为了在无依赖下看清机制，不代表 smolagents 内部生成 schema 的确切格式。

需要点明边界：不同版本的 smolagents、不同模型，注入系统提示的具体文本格式会有差异；docstring 的解析规则（比如是否严格要求 `Args:` 段）也可能随版本变化，以当前官方文档为准。本节讲的是稳定的原则——「描述与类型进上下文、直接影响模型用工具」，而不是某个版本的确切模板。

## 生产踩坑

| 症状 | 根因 | 如何观测与复现 | 修复与预防 | 不适用边界 |
|---|---|---|---|---|
| 模型不肯调我的工具 | docstring 首行含糊、名字不表意 | 把描述写模糊再写清晰对比调用率 | 动词开头写清用途，名字见名知义 | 工具本就不适用该任务时另说 |
| 模型老是传错参数 | 参数无类型标注或无说明 | 去掉类型标注复现传参错误 | 每个参数标具体类型 + 写含义与示例 | 无参数工具不涉及 |
| 手动改 name/description 不生效 | 这两项只读、自动从函数名/docstring 填 | 尝试手动赋值观察被覆盖 | 通过改函数名和 docstring 来控制 | 用 Tool 子类时可显式定义 |
| 用 Any 或不标类型导致理解模糊 | 类型提示不具体 | 用 Any 标注复现模型乱传 | 用 str/int/float/list[str] 等具体类型 | 确实多态的参数需额外说明 |
| 近义工具模型选错 | 多个工具描述语义重叠 | 放两个功能相近工具看选择分布 | 描述里写清「何时用、何时不用」 | 领域本需大量工具时用两阶段路由 |
| 工具报错模型不会纠错 | docstring 没说明哪些输入非法 | 传非法输入看模型是否重试 | docstring 注明非法输入，让报错可自愈 | 致命错误需人工介入时例外 |

## 思考：自定义工具的 docstring 为什么如此重要？它对应第 6 章的什么概念？

### 回答

因为在 smolagents 里，docstring（连同函数名和类型标注）不是给人看的注释，而是会被 `@tool` 装饰器抽取、自动注入到 Agent 系统提示里的文本——也就是说，**它是 prompt 的一部分**，是模型判断「什么时候该用这个工具、该往参数里传什么」的唯一依据。这精确对应第 6 章的「工具三要素」：函数名对应「名称」，docstring 首行对应「自然语言描述」，参数类型标注和 `Args` 说明对应「参数 Schema」。模型根本看不见你的函数体（那是运行时执行的），它能依据的只有这份说明书。所以当出现「模型不肯用我的工具」或「老是传错参数」时，正确的排查顺序是**先回去看 docstring 和类型标注写得够不够清楚，而不是先怀疑模型笨**——绝大多数「工具用不对」的问题，根源在说明书写得差。给一个对比：反例 `def q(a, b): '''汇率'''` 名字含糊、无类型、无参数说明，模型常漏用或传错；正例 `def get_exchange_rate(base: str, target: str) -> float` 动词开头讲清用途、有类型、有参数含义与示例，模型就能准确判断何时调用、怎么传参。

### 面试精简表达

docstring + 函数名 + 类型标注会被 @tool 注入系统提示，是模型用工具的唯一依据，对应第 6 章「工具三要素」；「模型不肯用工具」先查描述写得清不清楚，而非怀疑模型。

### 反例

最典型的反例是「把 docstring 当可有可无的注释删掉，或写成一个字『汇率』」。此时模型看到的说明书只有一个不表意的名字和空描述，它无法判断这个工具的用途和适用场景，于是要么彻底不用、要么在近义工具间乱选。这类问题在代码评审里极易被放过（因为函数逻辑是对的），却是线上「工具用不对」的头号根因。

## 深入：组合工具——让搜索与计算在一个动作里配合

自定义工具真正的威力，在于和内置工具组合，配合第 2 节的「代码即动作」完成组合任务。回到本章贯穿案例，给 Agent 同时装「联网搜索」和「按预算判断」两个工具：
```python
from smolagents import CodeAgent, WebSearchTool, tool, InferenceClientModel

@tool
def apply_budget(total: float, limit: float) -> str:
    """判断合计金额是否超过预算，返回一句结论。

    Args:
        total: 合计金额（元）
        limit: 预算上限（元）
    """
    return f"合计 {total} 元，{'超过' if total > limit else '未超过'}预算 {limit} 元"

agent = CodeAgent(
    tools=[WebSearchTool(), apply_budget],   # 两个工具：搜索 + 预算判断
    model=InferenceClientModel(),
    stream_outputs=True,
)
agent.run("搜一下当前美元兑人民币汇率，帮我算 100 美元换多少人民币、是否超过 500 元预算。")
```
逐行讲解：

- `tools=[WebSearchTool(), apply_budget]`：同时给 Agent 装了「联网搜索」和「预算判断」两个工具。
- Agent 会在一段代码动作里先 `web_search` 拿到汇率、解析出数字、乘以 100 得到人民币金额，再调用 `apply_budget(amount, 500)`——**搜索是「查外部世界」，计算与判断是「精确处理」，两者在一个动作里流式衔接**，正是代码即动作的典型用武之地。
- 注意「换算与比大小」这种确定性数学，交给代码而非让模型心算，结果才可靠——再次印证第 2 节的「把确定性计算挪出模型脑子」。

这个例子把本章前几节焊在了一起：`@tool` 定义工具（本节）、代码即动作做组合（第 2 节）、循环驱动执行（第 3 节）。而这段代码里 `web_search` 拿到的、`apply_budget` 处理的，都是要在执行器里跑的模型生成代码——这就引出了下一节最重要的问题：**这些代码在哪里跑、安全吗？**
